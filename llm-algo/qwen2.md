## 0. 一句话锚点

**Qwen2**(2024-06)与 **Qwen2.5**(2024-09)是阿里巴巴通义千问团队开源的第二代大语言模型家族。它们仍是 **Decoder-only Transformer**(和 GPT、LLaMA 同一谱系),核心定位是：

- **全系标配 GQA**(Grouped-Query Attention,分组查询注意力)——推理省显存。
- **长上下文**——从一代的 8K 一路推到 **128K token**(Qwen2.5 多数尺寸)。
- **补齐 MoE**——推出 Qwen2-57B-A14B 稀疏专家版。
- **多语言 + 数学/代码专项**——基座覆盖 29+ 语言,另出 Qwen2.5-Math / Qwen2.5-Coder 垂类模型。

一句话:**Qwen2.5 = "更长上下文 + 更强数理代码 + GQA 全面铺开"的开源 LLaMA 竞品,中文场景尤强。**

## 1. 地基/前置(不假设你记得)

在拆 Qwen2 之前,把它"站立"所需的几块地基讲到原子级。

**(1) Decoder-only Transformer**——模型只有"解码器"堆叠。每个 token 只能看到自己**左边**(因果掩码),逐字预测下一个词。一层 = `注意力子层 + 前馈(FFN)子层`,两者都套残差和归一化。

**(2) 自注意力(Attention)** 的本质:每个 token 生成三个向量——Query(我在找什么)、Key(我能被什么找到)、Value(我携带的信息)。打分公式:

$$\text{Attention}(Q,K,V)=\text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

$\sqrt{d_k}$ 是缩放,防止点积过大把 softmax 推向饱和(梯度消失)。

**(3) KV Cache(关键!理解 GQA 的前提)**:生成第 $t$ 个 token 时,前面 $1..t-1$ 个 token 的 K、V 不会变,缓存起来避免重算。代价是**显存随上下文线性增长**——上下文越长,KV Cache 越吃显存。这就是 GQA 要解决的痛点。

**(4) RoPE(旋转位置编码)**:把位置信息以"旋转角度"注入 Q、K(详见 [[llm-algo/旋转编码RoPE]])。优点是天然支持**外推到更长序列**——这是 Qwen2 长上下文的基础。

**(5) RMSNorm**:LLaMA 系常用的归一化,只做均方根缩放、不减均值,比 LayerNorm 更省算。

**(6) SwiGLU**:FFN 用门控激活,`SwiGLU(x)=(Swish(xW_1) ⊙ xW_3)W_2`,比传统 ReLU-FFN 表达力强,代价是多一个权重矩阵。

```
          ┌────────────── Decoder Layer (重复 N 次) ───────────────┐
 输入嵌入 →│  RMSNorm → GQA(RoPE) → +残差 → RMSNorm → SwiGLU-FFN → + │→ ... → 输出头
          └────────────────────────────────────────────────────────┘
```

## 2. 家族与规模:有哪些"型号"

Qwen2.5 把尺寸切得很细,覆盖从手机端到服务器。

```
Qwen2.5 Dense 家族(稠密,所有参数都参与计算)
 ┌─────┬─────┬─────┬─────┬─────┬──────┐
 │0.5B │1.5B │  3B │  7B │ 14B │  32B │  72B
 └─────┴─────┴─────┴─────┴─────┴──────┴────┘
   端侧轻量 ───────────────────────►  旗舰

Qwen2 MoE 版(稀疏,只激活一部分专家)
 ┌──────────────────┐
 │ Qwen2-57B-A14B   │  总57B参数 / 每token只激活~14B
 └──────────────────┘
       │
       └─ "A14B" = Activated 14B,见第6节

垂类专项
 ├ Qwen2.5-Math   (1.5B / 7B / 72B)   数学推理
 └ Qwen2.5-Coder  (0.5B…32B)          代码生成
```

要点:**Dense 尺寸越大,质量越高但显存/算力线性涨**;MoE 在"总参数大"的同时把"每步实际算的参数"压低,换取更高性价比。

## 3. 架构升级:相对 Qwen(一代)改了什么

Qwen2 不是推倒重来,而是在 Qwen 的 Decoder-only 骨架上做四处关键调整:

```
        Qwen(一代)                         Qwen2 / 2.5
   ┌──────────────────┐               ┌──────────────────────┐
   │ MHA(多头注意力)  │   ───────►    │ GQA(分组查询)全系标配│ ← 省KV Cache
   │ 部分尺寸用GQA     │               │                      │
   ├──────────────────┤               ├──────────────────────┤
   │ QKV 带 bias       │   保留 →      │ QKV 仍带 bias        │ ← 利于长度外推
   │                   │               │ (有别于LLaMA无bias)  │
   ├──────────────────┤               ├──────────────────────┤
   │ 上下文 8K         │   ───────►    │ 32K~128K             │ ← 长上下文
   ├──────────────────┤               ├──────────────────────┤
   │ 词表 ~151.6K      │   微调 →      │ 词表 ~151.6K(沿用)  │ ← 多语言/中文友好
   └──────────────────┘               └──────────────────────┘
```

**三个最重要的"为什么"**:

- **为什么全系换 GQA?** 一代里小尺寸用 MHA(多头各自一套 KV),长上下文时 KV Cache 爆显存。GQA 让多个 Query 头共享一组 KV,直接把 KV Cache 砍数倍(第4节细算)。
- **为什么 QKV 保留 bias?** 通义团队发现在注意力 QKV 投影上加偏置项,有助于**长度外推**(训练短、推理长时更稳)。这是 Qwen 系与 LLaMA 系一个显眼差异——LLaMA 的注意力线性层是无 bias 的。
- **为什么词表这么大(15万级)?** 大词表能把中文/多语言的常用词压成更少 token,既提速又省上下文,见第7节。

## 4. GQA 深拆:省的就是 KV Cache

**MHA / MQA / GQA 三态对照**(设 $H$ 个注意力头):

```
MHA(Multi-Head):     每个Q头配独立K、V头   → KV组数 = H        显存最大、质量基准
MQA(Multi-Query):    所有Q头共享1组K、V     → KV组数 = 1        显存最小、质量略降
GQA(Grouped-Query):  Q头分G组,每组共享K、V → KV组数 = G(1<G<H) 折中,Qwen2选它

  H=32, G=4 的示意:
   Q头:  q1 q2 q3 q4 | q5 q6 q7 q8 | ... (8个一组,共4组)
   KV :  [   kv_1   ] [   kv_2    ] [kv_3] [kv_4]
          ↑ 8个Q头共享一组KV
```

**KV Cache 显存公式**(单序列,bytes):

$$\text{KVmem} = 2 \times L \times S \times G \times d_{head} \times b$$

其中 $2$=K和V,$L$=层数,$S$=序列长度,$G$=KV 组数(=KV 头数),$d_{head}$=每头维度,$b$=每元素字节(FP16=2)。

**节省比例** = $\dfrac{G}{H}$。例如 $H=32, G=4$,KV Cache 直接降到原来的 **1/8**。这正是 Qwen2 敢把上下文拉到 128K 的底气——否则 KV Cache 会成为绝对瓶颈。

> 直觉:Query 决定"我想看哪些信息",这部分必须头多才精细;Key/Value 是"被检索的信息库",适度共享对质量损伤小,却能成倍省显存。

## 5. 长上下文:8K 怎么变 128K

Qwen2.5 多数尺寸支持 **128K 输入 / 8K 输出**。这不是简单地"训练时就用 128K"(那样太贵),而是组合技:

```
 训练: 用32K长度做长文训练 (打好基础)
   │
   ▼
 推理外推:把有效窗口拉到128K
   ├─ RoPE 外推:旋转位置编码本身可外推
   ├─ YaRN:对RoPE做频率插值/缩放,缓解外推时的位置混乱
   └─ DCA(Dual Chunk Attention):把超长序列切块,
       块内用相对位置、块间也用相对位置,避免"位置编号越界"
```

**为什么不能裸外推到 16 倍?** RoPE 在远超训练长度时,高频维度的相位会"绕圈"导致注意力分布崩坏。**YaRN** 通过按维度调整旋转频率(低频维度少插值、高频维度多插值)让模型在长序列上仍能正确感知相对距离;**DCA** 则用分块策略把"绝对位置很大"转化为"块内+块间的小相对位置",从工程上规避数值问题。

**实践要点**:128K 不是免费的——KV Cache 随 $S$ 线性涨(见第4节公式),128K 上下文的 KV Cache 比 8K 大 16 倍。所以"长上下文"必须和"GQA 省显存"配套使用,二者是一体两面。

## 6. MoE 版:理解 "A14B"

**MoE(Mixture of Experts,混合专家)**:把一层 FFN 换成"多个并列的专家 FFN + 一个路由器(Router)"。每个 token 只被路由到 Top-K 个专家,其余专家这一步不参与计算。

```
      token x
        │
        ▼
   ┌─ Router(打分,选Top-K)─┐
   │   ↓选中           ↓选中  │   ✗未选(本步不算)
 [E1] [E2] [E3] [E4] [E5] ... [En]
   └───────┬───────┘
        加权求和 → 输出
```

- **总参数(Total)**:所有专家加起来的参数,决定"知识容量上限"。
- **激活参数(Activated)**:每个 token 实际过的参数,决定"单步算力/速度"。

**Qwen2-57B-A14B**:总参数约 57B,但每 token 只激活约 14B → **拥有 57B 的容量,却只付 14B 的推理算力**。这是 MoE 的核心卖点:**容量与算力解耦**。代价是 57B 全部权重都要常驻显存,所以 MoE 省的是"算力(FLOPs)",不是"显存"。

> 对比 Dense:Qwen2.5-14B 是 14B 全部参数都算、也都存;Qwen2-57B-A14B 算的量近似 14B,但要存 57B。选型时看你卡的是算力还是显存。

## 7. 多语言:为什么中文/小语种友好

Qwen2 基座覆盖 **29+ 语言**(中、英及欧洲、中东、东亚、东南亚多语种)。两个关键设计:

```
大词表(~151.6K)的好处:
  英文 "internationalization"  → 少数几个BPE子词
  中文 "国际化"                → 直接成词,1~2 token
  对比小词表(如32K):中文常被切成单字甚至字节,token暴增

token经济学:同一句话
  小词表:  [国][际][化][是][...]   (字级,token多 → 慢、占上下文)
  Qwen词表:[国际][化][是][...]     (词级,token少 → 快、省上下文)
```

**为什么大词表对多语言关键?** 词表越大,越能给每种语言留出"自己的常用词槽位",避免某语言被迫退化成字节级编码。代价是嵌入矩阵(`vocab × hidden`)变大、输出 softmax 变慢——这是用嵌入层显存换多语言效率的权衡。Qwen 系一贯把词表做大(15 万级),所以中文/小语种的**有效上下文利用率**显著优于小词表模型。

## 8. 数学/代码:专项模型怎么炼

通用基座之外,Qwen2.5 出了两条垂类线:

```
Qwen2.5-Math(1.5B/7B/72B)
  ├ 数据:海量数学语料 + 合成题解 + CoT(思维链)推理轨迹
  ├ 能力:支持 CoT(一步步推) 与 TIR(Tool-Integrated Reasoning,调代码解题)
  └ 评测:GSM8K / MATH 等基准显著领先同尺寸通用模型

Qwen2.5-Coder(0.5B…32B)
  ├ 数据:大规模代码语料(多语言)+ 代码相关文本
  ├ 能力:代码生成 / 补全 / 修复 / 跨语言,支持 FIM(中间填充)
  └ 评测:HumanEval / MBPP 等编程基准接近更大通用模型
```

**为什么要单独炼?** 通用模型的训练数据是"大杂烩",数学/代码这种**强逻辑、低容错**任务在通用语料里占比不足。垂类模型用"配方更纯、CoT 标注更密"的数据继续训练(continue pretrain + 指令微调),把这两项能力顶上去。**TIR**(让模型写 Python 代码算数值再读回结果)尤其关键——纯靠"心算"LLM 容易在大数运算上出错,调用工具能把算术外包给解释器。

## 9. 与 Qwen(一代)差异:一表看清

| 维度 | Qwen(一代) | Qwen2 / Qwen2.5 |
|------|-----------|------------------|
| 注意力 | MHA 为主,部分用 GQA | **GQA 全系标配** |
| QKV bias | 有 | **保留**(助长度外推) |
| 归一化 | RMSNorm | RMSNorm(沿用) |
| 激活 | SwiGLU | SwiGLU(沿用) |
| 位置编码 | RoPE | RoPE + YaRN/DCA 外推 |
| 上下文长度 | 8K | **32K~128K** |
| MoE | 无开源 MoE | **Qwen2-57B-A14B** |
| 尺寸粒度 | 较粗(1.8B/7B/14B/72B) | **更细(0.5B…72B 多档)** |
| 垂类模型 | 较少 | **Math / Coder 成体系** |
| 多语言 | 中英为主 | **29+ 语言** |
| 词表 | ~151.6K | ~151.6K(沿用) |

**一句话总结代际变化**:Qwen2/2.5 没有换骨架,而是把"推理效率(GQA)、上下文(YaRN/DCA)、容量弹性(MoE)、垂类能力(Math/Coder)、尺寸覆盖"五件事系统性补强,工程成熟度大幅提升。

## 10. 数值例子 / 手算

**例 1:KV Cache 显存对比(MHA vs GQA)**

设 Qwen2.5-7B 量级近似参数:层数 $L=28$,$d_{head}=128$,Query 头 $H=28$,FP16($b=2$ 字节),序列 $S=32768$(32K)。

- 若用 **MHA**(KV 组数 $G=H=28$):
$$\text{KV} = 2 \times 28 \times 32768 \times 28 \times 128 \times 2 \approx 13.1\ \text{GB}$$
- 若用 **GQA**(取 $G=4$):
$$\text{KV} = 2 \times 28 \times 32768 \times 4 \times 128 \times 2 \approx 1.9\ \text{GB}$$

**节省 7 倍**($28/4$)。32K 上下文的 KV Cache 从 13 GB 降到约 1.9 GB——单卡就能跑长上下文。(数值为按上述假设的估算,具体配置以官方为准。)

**例 2:128K 上下文 KV Cache 会变多大?**

KV Cache 与 $S$ 线性。上例 GQA 在 32K 时约 1.9 GB,推到 **128K(4 倍)** 则约 $1.9 \times 4 \approx 7.6$ GB。可见即便有 GQA,128K 长上下文仍是显存大户——**GQA 与长上下文必须配套**才可行。

**例 3:MoE 的"算力 vs 显存"账**

Qwen2-57B-A14B,FP16 权重常驻显存 $\approx 57 \times 2 = 114$ GB(需多卡);但单 token FFN 计算量只对应约 14B 激活参数。对比 Qwen2.5-72B Dense:存 144 GB、算也按 72B。**结论**:MoE 在"质量/算力比"上占优,但不省权重显存,适合"显存够、想要更高吞吐"的场景。

**例 4:词表带来的 token 节省(直觉量化)**

一段 500 字中文,小词表(32K)可能切成约 700~900 token(常退化到字级),Qwen 大词表常压到约 350~450 token。**上下文利用率近乎翻倍**——同样 128K 窗口能塞更多实际内容。(具体比例随文本而异。)

## 常见问题

| 问题 | 关键点 |
|------|--------|
| GQA 会掉点吗? | 相比 MHA 质量损失很小,换来数倍 KV Cache 节省,长上下文场景净赚 |
| MoE 省显存吗? | **不省显存**(全部专家常驻),省的是单步算力/FLOPs |
| "A14B" 啥意思? | Activated 14B,每 token 只激活约 14B 参数,总参数 57B |
| 128K 是训练长度吗? | 否,多用 32K 训练 + YaRN/DCA 推理外推到 128K |
| 和 LLaMA 最大架构差异? | Qwen 的 QKV 投影**带 bias**、词表更大(15 万级),LLaMA 无 bias |
| Math/Coder 需另下载吗? | 是,垂类专项权重独立于通用基座 |
| 为何 RoPE 不能裸外推 16 倍? | 远超训练长度时高频相位绕圈,注意力崩坏,需 YaRN 频率插值 |
| 端侧能跑哪档? | 0.5B/1.5B/3B 适合手机/边缘;7B 起需消费级以上 GPU |
