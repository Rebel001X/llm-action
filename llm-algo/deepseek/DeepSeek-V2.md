## 0. 一句话锚点

DeepSeek-V2 = **Transformer 骨架 + 两个魔改件**：

1. **注意力换成 MLA**：不再缓存完整的 K、V，而是把它们压成一个低维"隐向量" $c^{KV}_t$ 存起来，推理时再升维。→ **省 KV Cache 显存**，让长上下文/大 batch 推理变便宜。
2. **FFN 换成 DeepSeekMoE**：把一个大 FFN 切成很多"细粒度小专家"，每个 token 只激活其中一小撮，再加几个"共享专家"兜底。→ **省训练/推理算力**（激活参数远小于总参数）。

记忆口诀：**MLA 管"显存"，MoE 管"算力"**。

## 1. 地基 / 前置（不假设你记得）

### 1.1 标准多头注意力 MHA
对每个 token $t$，把它的隐藏向量 $h_t \in \mathbb{R}^{d}$ 投影成 Query/Key/Value：

$$q_t = W^Q h_t,\quad k_t = W^K h_t,\quad v_t = W^V h_t$$

分成 $n_h$ 个头，每头维度 $d_h$（通常 $d = n_h \cdot d_h$）。注意力：

$$o_t = \sum_{j\le t}\text{softmax}_j\!\Big(\frac{q_t^\top k_j}{\sqrt{d_h}}\Big)\, v_j$$

**关键事实**：自回归推理时，过去所有 token 的 $k_j, v_j$ 必须存下来反复用——这就是 **KV Cache**。每个 token 要存 $2 \cdot n_h \cdot d_h$ 个数。

### 1.2 GQA / MQA（前人的省法）
- **MQA**：所有头共享 1 套 K/V → KV Cache 缩 $n_h$ 倍，但质量掉。
- **GQA**：分 $g$ 组，每组共享 K/V → 折中。
MLA 想做到"**GQA 的省 + MHA 的质量**"。

### 1.3 MoE（混合专家）最小回顾
把 FFN 换成 $N$ 个并列专家 $\{E_i\}$ + 一个路由器（gate）。每个 token 只选 top-$K$ 个专家算：

$$y = \sum_{i\in \text{Top-}K} g_i \cdot E_i(x)$$

→ **总参数大（容量大），但单 token 只算 $K$ 个（算力小）**。详见 [[llm-algo/moe/README]]。

### 1.4 RoPE（旋转位置编码）
通过对 $q,k$ 向量按位置 $t$ 旋转一个角度来注入相对位置信息：$\tilde q_t = R_t q_t$，$\tilde k_j = R_j k_j$，使得点积 $\tilde q_t^\top \tilde k_j$ 只依赖相对距离 $t-j$。**重点**：$R_t$ 是和位置强绑定的矩阵——这点会和 MLA 的"位置无关压缩"冲突，见第 4 节。详见 [[llm-algo/旋转编码RoPE]]。

## 2. 为什么 KV Cache 是推理瓶颈

```
推理一个长序列时，显存里躺着什么？
┌────────────────────────────────────────────┐
│  模型权重 (固定)                              │
│  ████████████████                            │
├────────────────────────────────────────────┤
│  KV Cache  (随 序列长度 × batch 线性增长)      │
│  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  ← 长上下文时这块爆炸
└────────────────────────────────────────────┘
```

MHA 每 token 每层的 KV Cache 元素数 = $2 \cdot n_h \cdot d_h$。
- 序列越长、batch 越大、层数越多 → 线性叠加。
- KV Cache 大 → 单卡能并发的请求数少 → 吞吐低 → 每 token 成本高。

**所以："省 KV Cache" 直接等于 "省钱 + 能开长上下文"。** 这就是 MLA 的动机。延伸阅读 [[llm-optimizer/kv-cache]]。

## 3. MLA 核心一：低秩 KV 联合压缩

### 3.1 核心 idea
不缓存 $k_t, v_t$（各 $n_h d_h$ 维），而是**先把 $h_t$ 压成一个低维隐向量** $c^{KV}_t$，**只缓存它**；用到时再升维还原 K、V。

$$\underbrace{c^{KV}_t = W^{DKV}\, h_t}_{\text{down-projection 降维}},\qquad c^{KV}_t \in \mathbb{R}^{d_c},\ \ d_c \ll n_h d_h$$

$$\underbrace{k^{C}_t = W^{UK}\, c^{KV}_t,\qquad v_t = W^{UV}\, c^{KV}_t}_{\text{up-projection 升维还原}}$$

```
       MHA 缓存                         MLA 缓存
   h_t ─►W^K─► k_t (n_h·d_h)        h_t ─►W^DKV─► c^KV_t (d_c)  ← 只存这个小向量!
   h_t ─►W^V─► v_t (n_h·d_h)                    │
   缓存 = 2·n_h·d_h  (大)                        └►W^UK/W^UV→ 现算 k,v
                                     缓存 = d_c  (小, 约 1/10~1/20)
```

DeepSeek-V2 取 $d_c = 4 d_h$（即 512，当 $d_h=128$），而 MHA 缓存量是 $2 n_h d_h$（128 头时是 32768）——**差了几十倍**。

### 3.2 关键技巧：升维矩阵可被"吸收"
推理算注意力分数 $q_t^\top k^C_j = (W^{UQ}c^Q_t)^\top (W^{UK} c^{KV}_j)$。
把 $W^{UK}$ **吸收进** $W^{UQ}$（即令 $\tilde W^Q = (W^{UK})^\top W^{UQ}$），就**不必真的把 $k^C_j$ 升维**——可以直接用缓存的 $c^{KV}_j$ 算分数。同理 $W^{UV}$ 吸收进输出投影 $W^O$。

> 这意味着：**升维矩阵在推理时不增加额外缓存、也不增加在线计算**——这是 MLA "省得理直气壮"的关键，区别于普通低秩瓶颈。

### 3.3 Query 也压缩（省训练激活显存）
$$c^{Q}_t = W^{DQ} h_t \in \mathbb{R}^{d_c'},\qquad q^{C}_t = W^{UQ} c^{Q}_t$$
Query 压缩主要是为了**减小训练时的激活内存**，不影响 KV Cache（Query 不缓存）。

## 4. MLA 核心二：解耦 RoPE（Decoupled RoPE）

### 4.1 冲突在哪里？
RoPE 要对 $k$ 乘位置矩阵：$k_j \to R_j k_j$。如果 $k^C_j = W^{UK} c^{KV}_j$，那么带 RoPE 的 key 是 $R_j W^{UK} c^{KV}_j$。

算分数时 $q$ 也带 $R_t$：分数里出现 $\;(R_t W^{UQ})^\top (R_j W^{UK})$。**$R_t, R_j$ 夹在中间，依赖具体位置 $t,j$，无法在不同位置间被"吸收/复用"**——即 3.2 的"吸收 $W^{UK}$"技巧失效。换句话说：**RoPE 与低秩压缩天生互斥**。

```
没 RoPE:  score = c^Q_t · (W^UQ)ᵀ W^UK · c^KV_j     ← 中间矩阵与位置无关, 可预先吸收, 缓存 c^KV 即可
带 RoPE:  score = c^Q_t · (W^UQ)ᵀ R_{t-j} W^UK · c^KV_j  ← R_{t-j} 随位置变, 吸收失效, 被迫缓存升维后的 K
```

### 4.2 解法：拆成两路，position 单开小通道
把每个头的维度切成两段：**内容段（NoPE, 走低秩压缩）** + **位置段（RoPE, 单独算）**。

- **内容 key**：$k^{C}_t = W^{UK} c^{KV}_t$（无 RoPE，可吸收，按 3.2 省）。
- **位置 key**：$k^{R}_t = \text{RoPE}(W^{KR}\, h_t) \in \mathbb{R}^{d^R_h}$，**所有头共享这一份**（multi-query 式），维度小（$d^R_h = d_h/2 = 64$）。
- 最终 key 是两段拼接：$k_t = [\,k^{C}_t \,;\, k^{R}_t\,]$；query 同理拼 $[q^{C}_t; q^{R}_t]$。

注意力分数 = 内容点积 + 位置点积：
$$q_t^\top k_j = (q^{C}_t)^\top k^{C}_j + (q^{R}_t)^\top k^{R}_j$$

```
        ┌───── 内容段 (NoPE) ─────┐   ┌── 位置段 (RoPE, 共享一份) ──┐
 q_t =  [   q^C_t  (来自 c^Q_t)    ;     q^R_t (RoPE(W^QR c^Q_t))   ]
 k_t =  [   k^C_t  (来自 c^KV_t)   ;     k^R_t (RoPE(W^KR h_t))     ]
 缓存 =      c^KV_t  (d_c=512)      +        k^R_t  (d^R_h=64)
            ─────── 总每 token 每层缓存 = d_c + d^R_h = 512 + 64 = 576 ───────
```

→ **MLA 实际每 token 每层只缓存 $d_c + d^R_h = 576$ 个数**（远小于 MHA 的 $2 n_h d_h = 32768$）。这就是论文宣称"KV Cache 缩到 GQA-2.25 组水平、但效果优于 MHA"的来源。

## 5. DeepSeekMoE：细粒度 + 共享专家

### 5.1 两个创新
1. **细粒度专家切分（Fine-Grained）**：把每个专家的隐藏维度切小、专家数量切多。原本 $N$ 个大专家选 top-2，改成 $mN$ 个小专家选 top-$2m$（总激活参数不变，但**组合数爆炸**→专家更专精）。
2. **共享专家隔离（Shared Expert）**：留 $K_s$ 个**每个 token 都必过**的共享专家，去学"通用知识"，让路由专家专注差异化知识 → 减少专家间知识冗余。

```
普通 MoE:   token → 路由器 → 选 2 个大专家
DeepSeekMoE: token → [共享专家(必过, 1~2个)] + [路由器从 160 个小专家里选 6 个]
                          通用知识                    差异化知识
```

### 5.2 FFN 输出公式（直观版）
$$y_t = h_t + \sum_{i=1}^{K_s} E^{(s)}_i(h_t) \;+\; \sum_{i\in \text{Top-}K_r}\! g_{i,t}\, E^{(r)}_i(h_t)$$
其中前一项是共享专家（恒激活），后一项是路由专家（按门控 $g$ 选 top-$K_r$）。

### 5.3 DeepSeek-V2 的 MoE 配置（以官方为准）
- 路由专家数：**160**，每 token 激活 **6**；共享专家：**2**（恒激活）。
- 每个专家是细粒度小 FFN（中间维度约为常规 FFN 的 1/几）。
- 首层用 dense FFN（不放 MoE），其余层用 MoE。

## 6. 负载均衡：三类辅助损失

MoE 的老毛病：路由器偏心 → 少数专家被挤爆、多数专家闲置（**路由坍缩**），既浪费容量又拖慢分布式（某卡过载）。DeepSeek-V2 用**三个辅助损失**压住：

| 损失 | 目的 | 直觉 |
|------|------|------|
| **专家级均衡 $\mathcal{L}_{ExpBal}$** | 每个专家被选的频率均匀 | 防止个别专家垄断 |
| **设备级均衡 $\mathcal{L}_{DevBal}$** | 每张卡（专家分组）负载均匀 | 防止某卡成瓶颈 |
| **通信均衡 $\mathcal{L}_{CommBal}$** | 每张卡收发的 token 量均匀 | 防止 all-to-all 通信热点 |

专家级损失的典型形式（$f_i$=专家 $i$ 实际被选频率，$P_i$=门控给它的平均概率，$\alpha$=系数）：
$$\mathcal{L}_{ExpBal} = \alpha \sum_{i=1}^{N_r} f_i \, P_i$$

另外还有 **设备受限路由（device-limited routing）**：限制一个 token 的 top-$K$ 专家最多落在 $M$ 张卡上（V2 中 $M=3$），把昂贵的跨卡 all-to-all 通信量焊死在上限内。

> 演进提示：辅助损失会**轻微伤害模型性能**（梯度被"为了均衡"带偏）。后续 [[llm-algo/deepseek/DeepSeek-V3]] 改用 **aux-loss-free** 的偏置项动态调节路由，去掉了这些辅助损失。

## 8. 为什么"经济高效"（钱省在哪）

```
            训练成本                         推理成本
  ┌─────────────────────────┐     ┌─────────────────────────┐
  │ MoE: 236B 容量, 只算 21B  │     │ MLA: KV Cache 缩 ~20x+   │
  │  → 同等容量, FLOPs ↓      │     │  → 单卡并发请求 ↑         │
  │ DeepSeekMoE 细粒度        │     │  → 吞吐 ↑, 每token成本 ↓  │
  │  → 专家更省更专           │     │ MoE: 激活少 → 解码也省FLOPs│
  └─────────────────────────┘     └─────────────────────────┘
  官方口径: 相比 DeepSeek 67B(dense),
  训练成本 ↓42.5%, KV Cache ↓93.3%, 最大生成吞吐 ↑5.76x
```

三条经济性主线：
1. **训练省 FLOPs**：MoE 让"参数容量"和"每步算力"解耦——堆容量不堆算力。
2. **推理省显存**：MLA 把 KV Cache 砍掉 90%+，单卡塞更多并发 → 吞吐起飞。
3. **推理省 FLOPs**：解码每 token 只过 21B 激活参数，而非 236B。

## 9. 数值手算（逐数算给你看）

### 9.1 KV Cache：MLA vs MHA（每 token 每层元素数）
设 $n_h=128,\ d_h=128,\ d_c=512,\ d^R_h=64$。

- **MHA**：$2 \cdot n_h \cdot d_h = 2 \times 128 \times 128 = 32768$
- **MLA**：$d_c + d^R_h = 512 + 64 = 576$
- **压缩比**：$32768 / 576 \approx 56.9\times$

> 换算成"等价 GQA 组数"：MHA 是 128 组，MLA 缓存量 $\approx$ GQA 的 $576/256 = 2.25$ 组（每组 K+V 共 $2d_h=256$），即**只比 GQA-2.25 大一丢丢，却保住 MHA 级质量**。

### 9.2 整序列 KV Cache 显存（60 层、128K 上下文、batch=1、bf16=2字节）
- **MHA**：$32768 \times 60 \times 131072 \times 2\text{B} \approx 5.15\times10^{11}\,\text{B} \approx 480\,\text{GB}$（单卡放不下！）
- **MLA**：$576 \times 60 \times 131072 \times 2\text{B} \approx 9.06\times10^{9}\,\text{B} \approx 8.4\,\text{GB}$

→ 长上下文从"装不下"变成"轻松装下"。这就是 MLA 能开 128K 的底气。

### 9.3 激活参数占比（MoE 省算力）
$$\frac{\text{激活}}{\text{总参}} = \frac{21\text{B}}{236\text{B}} \approx 8.9\%$$
即**每个 token 只动用约 9% 的参数**，但模型"知道"的是 100% 的容量。

### 9.4 共享/路由专家激活数
每 token 实际过的 MoE 专家 = 共享 2 + 路由 6 = **8 个细粒度专家**。相比"2 个大专家"，组合空间从 $\binom{N}{2}$ 暴涨到 $\binom{160}{6}$，专精度天差地别。

### 9.5 注意力分数为何能省（吸收技巧验证）
内容分数 $= (c^Q_t)^\top \underbrace{(W^{UQ})^\top W^{UK}}_{\text{离线预乘成一个矩阵}\ \tilde W}\, c^{KV}_j$。在线只需 $c^Q_t \cdot \tilde W \cdot c^{KV}_j$——**不解压 $c^{KV}_j$**，缓存和算力都按低维走。

## 10. 面试问答清单（高频问题 → 踩点答案 → 追问）

**Q1：MLA 到底省的是什么？为什么不是 GQA？**
- 踩点：省的是**推理 KV Cache 显存**。GQA 靠"多头共享 K/V"省，会掉质量；MLA 靠"**低秩联合压缩**只缓存隐向量 $c^{KV}_t$，用时再升维"省，且升维矩阵可吸收 → **GQA 级的省 + MHA 级的质量**。
- 追问：MLA 推理时要不要把 K/V 升维回去？→ **不用**。$W^{UK}$ 吸进 $W^{UQ}$、$W^{UV}$ 吸进 $W^O$，直接用 $c^{KV}_j$ 算。

**Q2：为什么要"解耦 RoPE"？不解耦会怎样？**
- 踩点：RoPE 的旋转矩阵 $R_{t-j}$ 夹在 $q,k$ 之间且随位置变，**破坏了"升维矩阵可吸收"的前提**，逼你缓存升维后的完整 K → 省不动。解法：把头维度拆成**内容段（NoPE，走压缩）+ 位置段（RoPE，所有头共享一小份 $d^R_h=64$）**，分数 = 内容点积 + 位置点积。
- 追问：位置段为什么所有头共享？→ 省缓存（MQA 式），$d^R_h$ 很小，对质量影响可忽略。

**Q3：DeepSeekMoE 的"细粒度"和"共享专家"各解决什么？**
- 踩点：细粒度 = 专家切小切多 → **组合数爆炸、专家更专精**；共享专家 = 恒激活的通用专家 → **吸走公共知识，减少路由专家间冗余**。
- 追问：细粒度会不会增加激活参数？→ 不会，通过同时增加 top-$K$ 保持激活参数量不变。

**Q4：MoE 负载不均怎么办？V2 用了几个 loss？**
- 踩点：专家级 + 设备级 + 通信级三个**辅助均衡损失**，外加**设备受限路由**（top-$K$ 最多落 $M=3$ 张卡）控通信。
- 追问：辅助损失有副作用吗？→ 有，会轻微损性能；[[llm-algo/deepseek/DeepSeek-V3]] 改用 **aux-loss-free 偏置法**去掉它。

**Q5：236B 的模型怎么做到推理便宜？**
- 踩点：①MoE 每 token 只激活 21B（≈9%）→ 解码 FLOPs 小；②MLA 把 KV Cache 砍 90%+ → 单卡并发多、吞吐高。两者叠加 → 每 token 成本低。
- 追问：哪一个对"长上下文"更关键？→ **MLA**，因为 KV Cache 随序列长度线性增长，是长文场景的显存瓶颈。

**Q6：MLA 和 MoE 分别属于哪一类优化？**
- 踩点：**MLA = 推理/显存优化（KV Cache 压缩）**，[[llm-optimizer/kv-cache]] 同类；**MoE = 模型容量/算力优化（稀疏激活）**，[[llm-algo/moe/README]] 同类。两者正交、可叠加。

**常见陷阱**
- ❌ "MLA 是 GQA 的一种" → 不是，原理不同（低秩压缩 vs 头共享）。
- ❌ "升维矩阵增加推理开销" → 被吸收了，不增加缓存与在线算力。
- ❌ "共享专家也走路由" → 共享专家**恒激活、不路由**。
- ❌ "细粒度让激活参数变多" → 通过同步增大 top-$K$ 保持激活量不变。

## 对照 / 复杂度表

| 维度 | MHA | GQA | **MLA (DeepSeek-V2)** |
|------|-----|-----|----------------------|
| 每 token 每层 KV 缓存 | $2 n_h d_h$ | $2 g d_h$ | $d_c + d^R_h$（≈576） |
| 质量 | 高（基准） | 中（略降） | **高（≈MHA）** |
| RoPE 处理 | 直接 | 直接 | **解耦（内容段+共享位置段）** |
| 省的对象 | — | KV 显存 | **KV 显存（更狠）** |

| 维度 | 普通 MoE | **DeepSeekMoE** |
|------|----------|-----------------|
| 专家粒度 | 粗（少而大） | **细（多而小）** |
| 通用知识 | 散在各专家（冗余） | **共享专家集中承载** |
| 组合空间 | 小 $\binom{N}{2}$ | **大 $\binom{160}{6}$** |
| 均衡手段 | 单一 aux loss | **专家/设备/通信三 loss + 受限路由** |

## 常见问题 / 高频追问（速查）

| 问题 | 一句话答案 |
|------|-----------|
| MLA 缓存的是什么？ | 低秩隐向量 $c^{KV}_t$（+ 共享 RoPE key $k^R_t$），不是完整 K/V |
| 为什么 KV Cache 缩这么多？ | $d_c+d^R_h \ll 2n_h d_h$，本例 ≈57x |
| 解耦 RoPE 拆成几段？ | 内容段（NoPE 可压缩）+ 位置段（RoPE 共享一小份） |
| 共享专家激活几个？ | 2 个，恒激活、不参与路由 |
| 路由专家激活几个？ | 从 160 选 6 |
| 激活/总参占比？ | 21B / 236B ≈ 9% |
| V2 上下文多长？ | 128K（YaRN 扩展） |
| 和 V3 的最大差异？ | V3 去掉辅助损失（aux-loss-free）、扩到 671B/37B、加 MTP |
