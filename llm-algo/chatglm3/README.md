## 0. 一句话锚点

**ChatGLM3 = ChatGLM2 的"身体" + 一套全新的"语言协议"。**

- "身体"几乎没变：还是 6B 参数、还是那套 GLMBlock + RoPE + RMSNorm + MQA，所以**推理成本与 ChatGLM2 基本一致**。
- "语言协议"大改：把对话从"用户说一句、模型答一句"的纯文本，升级成一套带**角色（role）、元数据（metadata）、特殊 token** 的结构化格式，从而让模型能**调用工具、执行代码、扮演 Agent**。

一句话：**ChatGLM3 的创新主要不在网络结构，而在"如何组织对话"。**

## 1. 地基/前置：先把 ChatGLM2 讲清楚

要理解 ChatGLM3 改了什么，必须先有 ChatGLM2 这块地基。我们不假设你记得，逐个拆原子。

### 1.1 GLM 的训练目标（自回归空白填充）

GLM 不是纯 GPT 式从左到右，而是**自回归空白填充（Autoregressive Blank Infilling）**：把句子里一段连续 token 挖空成 `[MASK]`，让模型按自回归方式把空白补回来。这让它**既能像 BERT 那样看上下文，又能像 GPT 那样生成**。ChatGLM2/3 在对话场景下退化为以因果生成为主，但底子是这套混合目标。

### 1.2 三个关键组件（ChatGLM2 已具备，ChatGLM3 继承）

```
                ChatGLM2 = ChatGLM3 的"硬件底座"
   ┌──────────────────────────────────────────────────┐
   │  ① RoPE 旋转位置编码  —— 位置=对 Q/K 向量旋转角度  │
   │  ② RMSNorm 归一化     —— 只缩放不去均值，省一半算  │
   │  ③ MQA 多查询注意力   —— 多个 Q 头共享 1 组 KV     │
   │  ④ SwiGLU / FFN       —— 门控前馈                  │
   └──────────────────────────────────────────────────┘
```

- **RoPE（旋转位置编码）**：不给每个位置加一个"位置向量"，而是按位置 $m$ 把查询/键向量旋转一个角度。两个 token 的注意力分数只依赖它们的**相对距离** $m-n$，所以能自然外推到更长上下文。详见 [[llm-algo/旋转编码RoPE]]。
- **RMSNorm**：标准 LayerNorm 要算均值和方差两步；RMSNorm 只算均方根 $\text{RMS}(x)=\sqrt{\frac1d\sum x_i^2}$ 再缩放，少一次减均值，更快更稳。
- **MQA（Multi-Query Attention）**：普通多头注意力每个头都有自己的 K、V；MQA 让**所有 Q 头共享同一组 K、V**。这把推理时要缓存的 KV-Cache 缩小到 $1/h$（$h$ 为头数），显存和带宽都大降——这正是 ChatGLM2/3"同等成本"的关键。

### 1.3 ChatGLM2 的对话格式（理解 ChatGLM3 改进的对照物）

ChatGLM2 用很朴素的拼接：

```
[Round 1]
问：<用户问题>
答：<模型回答>
[Round 2]
问：...
答：...
```

问题：纯文本、无结构。模型**分不清**"这段是系统设定、那段是工具返回、这段是用户原话"，更**无法表达"我现在要调一个工具"**这种意图。ChatGLM3 正是来解决这件事的。

## 2. ChatGLM3 改了什么（相对 ChatGLM2 的关键创新）

```
   ChatGLM2 ─────────────────────────► ChatGLM3
   ┌─────────────┐                 ┌──────────────────────────┐
   │ 纯文本对话   │   升级为         │ 结构化对话格式            │
   │ 问/答 拼接   │ ─────────────►  │ role+metadata+special tok │
   ├─────────────┤                 ├──────────────────────────┤
   │ 只能聊天     │                 │ 工具调用 (Function Call)  │
   │             │                 │ 代码执行 (Interpreter)    │
   │             │                 │ Agent (规划/反思/多轮)    │
   ├─────────────┤                 ├──────────────────────────┤
   │ 6B 同等规模  │   网络结构基本不变 │ 6B 同等规模、同等成本     │
   └─────────────┘                 └──────────────────────────┘
```

官方口径（约，以官方为准）的四大改进：

1. **更强的基础模型**：base 模型 ChatGLM3-6B-Base 在更多样的训练数据、更充分的训练步数、更合理的训练策略上得到，号称在 10B 以下 base 模型中综合性能领先（语义、数学、推理、代码、知识等多维度评测，约/以官方榜单为准）。
2. **全新对话格式**（第 3 节详解）：原生支持多角色与元数据，是工具/代码/Agent 能力的载体。
3. **原生工具调用 + 代码解释器 + Agent**：不再靠外部 prompt 拼凑，而是模型训练时就见过这套格式。
4. **更全的开源序列**：6B（对话）、6B-Base（基座）、6B-32K（长上下文），并配套 Demo（工具调用、代码解释器、综合 Agent）。

**一句话区分**：ChatGLM2 的改进是"更长上下文 + 更快推理"（偏工程/结构）；ChatGLM3 的改进是"会用工具、会写代码、会当 Agent"（偏能力/协议）。

## 3. 全新对话格式（最核心、必须吃透）

这是 ChatGLM3 的灵魂。它把对话从"一长串文本"变成"一串带角色的消息"。

### 3.1 四种角色（role）

| role | 含义 | 谁产生 |
|------|------|--------|
| `<\|system\|>` | 系统设定 / 工具清单 | 应用方 |
| `<\|user\|>` | 用户输入 | 用户 |
| `<\|assistant\|>` | 模型回复（可带 metadata，如要调用的工具名） | 模型 |
| `<\|observation\|>` | 外部返回（工具结果 / 代码运行输出） | 工具/环境，回灌给模型 |

新增的 special token 让模型在**生成时就能"声明角色"**，也让应用方在**解析时能精确切分**每一段属于谁。

### 3.2 一条完整消息的 ASCII 结构

```
<|role|>{metadata}\n{content}

   ▲       ▲          ▲
   │       │          └─ 正文（自然语言 / 代码 / JSON 参数）
   │       └──────────── 元数据：assistant 调工具时这里放“工具名”
   └──────────────────── 角色标记：system/user/assistant/observation
```

### 3.3 多轮 + 工具调用的完整数据流（核心图）

```
应用方拼好 prompt ─┐
                  ▼
 <|system|>
 你可以调用以下工具：[ {name:"get_weather", params:{city}} ...]
 <|user|>
 北京今天天气怎么样？
 <|assistant|>get_weather         ◄── metadata=工具名，表示“我要调它”
 {"city": "北京"}                  ◄── content=JSON 参数
                  │
   应用方解析到 assistant 带工具名 → 真正去调用 get_weather("北京")
                  │  返回 {"temp": 28, "desc": "晴"}
                  ▼
 <|observation|>                   ◄── 把工具结果按 observation 角色回灌
 {"temp": 28, "desc": "晴"}
                  ▼
 <|assistant|>                     ◄── 模型基于 observation 生成最终自然语言
 北京今天晴，气温约 28℃。
```

**关键洞察**：模型本身**不会真的联网/执行代码**。它只负责：
1. 决定"该调哪个工具、传什么参数"（输出 `assistant` + 工具名 + JSON）；
2. 拿到 `observation` 后，把结果**翻译成人话**或决定下一步。
真正的执行由**应用方/runtime** 完成。这就是"工具调用"协议的本质：模型与外部世界之间的**结构化握手**。

## 4. 工具调用（Function Call）原理拆解

### 4.1 为什么需要工具

LLM 的知识被冻结在训练时刻，且不会算精确数学、不能查实时数据。工具调用让模型"借用外部能力"：查天气、查数据库、调计算器、搜索。

### 4.2 三步握手

```
 Step1 声明：system 角色里给出工具的 name / 描述 / 参数 schema
 Step2 选择：模型在 assistant 的 metadata 里写工具名，content 写 JSON 参数
 Step3 回灌：应用方执行后，把结果以 observation 角色喂回，模型再总结/续调
```

可多轮循环：模型可在一次任务里**连续调用多个工具**（observation → assistant → observation …），直到能给出最终答案。

### 4.3 与"纯 prompt 工程"的区别

| 维度 | 纯 prompt 拼凑（如早期 ReAct） | ChatGLM3 原生 |
|------|------------------------------|--------------|
| 是否训练见过 | 否，靠提示词诱导 | 是，训练数据含该格式 |
| 解析稳定性 | 易跑偏、格式漂移 | special token 切分，稳定 |
| 角色区分 | 全靠文本约定 | 有显式 role |

## 5. 代码解释器（Code Interpreter）

代码解释器是工具调用的一个**特例**：被调用的"工具"是一个 **Python 沙箱**。

```
 <|user|>     画一个 y=x^2 的图
 <|assistant|>interpreter          ◄── 元数据=interpreter（代码执行通道）
 ```python
 import matplotlib.pyplot as plt
 ...
 ```
        │  应用方在沙箱里真正运行这段代码
        ▼
 <|observation|>                    ◄── 回灌：stdout / 图片 / 报错
 [图片已生成]  或  Traceback ...
        ▼
 <|assistant|>  已为你绘制 y=x² 抛物线。
```

要点：
- 模型**生成代码**，沙箱**运行代码**，结果以 `observation` 回灌；若报错，模型能看到 Traceback 并**自我修正、重写代码**（多轮闭环）。
- 适合数学计算、数据分析、画图、文件处理等"语言模型本身不擅长但代码擅长"的任务。
- 沙箱安全（资源/网络隔离）由应用方负责，不是模型职责。

## 6. Agent 能力（AgentTuning）

Agent = 在工具调用 + 代码执行之上，叠加**多轮规划、调度、反思**。

```
   目标：帮我订一张明天去上海最便宜的机票
        │
   ┌────▼─────────────────────────────────────────┐
   │ 规划：①查航班 ②比价 ③下单                      │
   │ 执行：assistant→tool(search_flight)→observation │
   │ 反思：结果不够便宜 → 再调 tool(filter_price)     │
   │ 收敛：得到最便宜航班 → 调 tool(book) → 回报用户  │
   └───────────────────────────────────────────────┘
```

ChatGLM3 通过 **AgentTuning**（在 Agent 轨迹数据上微调）增强了"看工具集 → 选工具 → 解析返回 → 决定下一步"的能力，使 6B 小模型也能跑通典型 Agent 流程（约/以官方为准）。它复用的正是第 3 节那套 role 格式——Agent 不是新协议，而是**对话格式的高级用法**。

## 8. 架构回顾（与 ChatGLM2 同源，逐层看一眼）

ChatGLM3 网络结构基本沿用 ChatGLM2，这里给出一个 GLMBlock 的内部数据流，便于把第 1 节的组件落到代码层。

```
 输入 hidden_states (B, S, H)
        │
   ┌────▼──────────────┐
   │ RMSNorm           │   ← 先归一化（Pre-Norm）
   └────┬──────────────┘
        │
   ┌────▼──────────────┐
   │ Self-Attention    │
   │  Q,K,V 投影        │
   │  RoPE 旋转 Q,K     │   ← 注入相对位置
   │  MQA: Q多头/KV共享 │   ← 省 KV-Cache
   │  softmax(QKᵀ/√d)V  │
   └────┬──────────────┘
        │  + 残差
   ┌────▼──────────────┐
   │ RMSNorm           │
   └────┬──────────────┘
        │
   ┌────▼──────────────┐
   │ FFN / SwiGLU      │   gate(x)·up(x) → down
   └────┬──────────────┘
        │  + 残差
        ▼
   输出 (B, S, H)，堆叠 ~28 层（约/以官方为准）
```

> 与 ChatGLM（一代）相比，ChatGLM2/3 调整了**激活函数（SwiGLU）**与 **RoPE 的应用位置**等细节（参见 [[llm-algo/chatglm2/README]] 末尾的对照）。ChatGLM3 相对 ChatGLM2 的结构改动很小，**主要差异在数据与对话格式**。

## 9. 部署与推理

> 以下 CLI / API 名称随版本演进，**以官方仓库（THUDM/ChatGLM3）文档为准**，此处给"心智模型"而非逐字命令。

### 9.1 最小推理（transformers）

```python
from transformers import AutoTokenizer, AutoModel

tok = AutoTokenizer.from_pretrained("THUDM/chatglm3-6b", trust_remote_code=True)
model = AutoModel.from_pretrained("THUDM/chatglm3-6b",
                                  trust_remote_code=True).half().cuda().eval()

# chat 接口内部会按第3节的对话格式拼 special token
resp, history = model.chat(tok, "你好，介绍一下你自己", history=[])
print(resp)
```

要点：`trust_remote_code=True` 是因为 ChatGLM3 用自定义建模代码（`modeling_chatglm.py`）；`.half()` 走 FP16。

### 9.2 部署选型对照

```
 ┌──────────────┬────────────────┬─────────────────────────────┐
 │ 方式          │ 适用场景        │ 说明                         │
 ├──────────────┼────────────────┼─────────────────────────────┤
 │ transformers │ 调试 / 单卡 Demo │ 最简单，吞吐一般             │
 │ vLLM         │ 在线服务高并发   │ PagedAttention，高吞吐       │
 │ 量化 INT4/INT8│ 消费级显卡       │ 显存大降，精度略损          │
 │ CPU / MPS    │ 无 GPU 应急      │ 慢，仅小流量                 │
 └──────────────┴────────────────┴─────────────────────────────┘
```

### 9.3 微调
- **LoRA / P-Tuning v2**：低成本适配下游任务，只训少量参数；官方提供微调脚本（以仓库为准）。
- **全参微调**：需要多卡，适合有充足算力且要深度定制时。

### 9.4 工具/代码/Agent 的落地
官方仓库附带三类 Demo：工具调用、代码解释器、综合 Agent。本质都是"应用方按第 3 节格式拼 prompt + 解析 `assistant`/`observation` + 执行外部动作"的循环——**模型给协议，应用补执行**。

## ✚ 数值例子 / 对照

### 例 1：MQA 省了多少 KV-Cache（手算）

设隐藏维 $H=4096$、注意力头数 $h=32$、序列长 $S=8192$、层数 $L=28$、FP16（2 字节）。

普通多头注意力（MHA）每层缓存 K 与 V 各 $S\times H$：

$$
\text{MHA KV} = 2 \times L \times S \times H \times 2\text{B} = 2\times28\times8192\times4096\times2 \approx 7.5\,\text{GB}
$$

MQA 让所有头共享 1 组 KV，等效把每头维度从 $H$ 压到 $H/h$，KV 缩到约 $1/h$：

$$
\text{MQA KV} \approx \frac{7.5\,\text{GB}}{32} \approx 0.23\,\text{GB}
$$

> 直观看到为什么 ChatGLM2/3 能"同等成本上长上下文"——KV-Cache 这块省了一个数量级（数值为示意，实际实现可能保留少量 KV 组，**以代码为准**）。

### 例 2：工具调用一轮的 token 预算（手算）

| 段 | 内容 | 估计 token |
|----|------|-----------|
| system（工具清单） | 3 个工具的 schema | ~300 |
| user | "北京天气" | ~10 |
| assistant（选工具） | 工具名 + JSON 参数 | ~20 |
| observation | 工具返回 JSON | ~30 |
| assistant（总结） | 自然语言回答 | ~40 |

单轮总计约 400 token。**含义**：工具清单是"固定开销"，工具越多、schema 越长，每轮都要付这笔上下文税——所以工具描述要精炼。

### 对照表：三代 ChatGLM 速览

| 维度 | ChatGLM-6B | ChatGLM2-6B | ChatGLM3-6B |
|------|-----------|-------------|-------------|
| 上下文 | ~2K | ~32K（32K版） | ~8K，另有 32K/128K 版 |
| 注意力 | MHA | MQA | MQA |
| 激活 | GELU 系 | SwiGLU | SwiGLU |
| 对话格式 | 朴素文本 | 朴素文本 | **结构化 role 格式** |
| 工具/代码/Agent | 无 | 无 | **原生支持** |
| 核心卖点 | 首发中英对话 | 长上下文+快推理 | **会用工具/会干活** |

## ❓ 常见问题

| 问题 | 解答 |
|------|------|
| ChatGLM3 网络结构比 ChatGLM2 大改了吗？ | 没有。结构基本同源，**主要创新在对话格式与能力（工具/代码/Agent），不在网络**。 |
| 工具调用是模型自己联网执行的吗？ | 不是。模型只输出"调哪个工具、传什么参"，**真正执行由应用方完成**，再以 `observation` 回灌。 |
| 为什么必须用官方对话格式？ | 模型训练时就见过 `system/user/assistant/observation` + special token；乱拼文本会让工具/代码能力失效或解析错乱。 |
| ChatGLM2 的 prompt 能直接喂给 ChatGLM3 吗？ | 不建议。两代对话格式不同，**直接套用会触发格式坑**，应使用 ChatGLM3 的 `model.chat` / 官方模板。 |
| 6B 这么小也能当 Agent？ | 能跑通典型流程（AgentTuning 加持），但复杂规划稳定性弱于大模型；生产可结合更强模型或 [[llm-algo/glm4]]。 |
| `observation` 和 `user` 有什么区别？ | `user` 是人说的话，`observation` 是工具/代码的机器返回。分开是为了让模型知道"这是环境反馈，不是用户指令"。 |
| 想要更长上下文 / 更强能力怎么办？ | 用 ChatGLM3-6B-32K，或升级到下一代 [[llm-algo/glm4]]（更强基座、更长上下文、更完善的工具/Agent 生态）。 |
