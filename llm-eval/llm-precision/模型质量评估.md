## 0. 一句话锚点

**模型质量评估**回答的是"模型的回答好不好"——不是快不快（那是性能指标，见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]），而是**内容质量**：对不对、流不流畅、有没有用。

难点在于：开放式生成**没有唯一标准答案**。问"圆半径 7cm 面积多少"有标准答案，但问"写一首关于秋天的诗"就没有。于是业界用 **LLM-as-Judge**——让一个能力强的模型（GPT-4）扮演评委，去打分或比较。本文给出两种核心范式：**成对比较**与**单一答案评分**。

## 1. 地基：三类评估方法的取舍

评估大模型质量有三条路，各有适用面：

```
                  评估大模型回答质量的三种范式
   ┌─────────────────┬──────────────────┬─────────────────────┐
   │  ① 自动指标      │  ② 人工评估       │  ③ 模型评估(本文)    │
   │  BLEU/ROUGE/EM   │  人来打分/排序    │  GPT-4 当评委        │
   ├─────────────────┼──────────────────┼─────────────────────┤
   │ 快、便宜、可复现 │ 最贴近真实偏好    │ 接近人评、可规模化   │
   │ 只看字面重合     │ 慢、贵、难复现    │ 评委自身有偏差       │
   │ 开放任务失效     │ 标注者间不一致    │ 需精心设计 Prompt    │
   └─────────────────┴──────────────────┴─────────────────────┘
```

- **自动指标**（BLEU/ROUGE）按 n-gram 重叠算分，对翻译/摘要还行，但对开放对话几乎无效——同义改写得 0 分却是好答案。
- **人工评估**是金标准，但一条 1 美元、上万条就是上万美元，且标注者间一致性（IAA）经常很低。
- **模型评估**（LLM-as-Judge）是折中：用一次 API 调用模拟人评，成本是人评的几十分之一，与人类偏好的一致率可达 ~80%（MT-Bench 的经验值）。本文的"成对比较"和"单一答案评分"就是它的两种打分形态。

> 为什么能用模型评模型？因为**判断好坏比生成内容容易**——就像你不会写诗，但能分辨两首诗哪首更好。强模型把"鉴赏力"用作评分能力。

## 2. 成对比较（Pairwise Comparison）

> **原文定义**：成对比较（Pairwise Comparison）——在这种方式下，GPT-4 作为评委，会被告知一个问题和两个答案，任务是确定哪一个更好或者宣布一个平局。

### 2.1 机制

```
          成对比较数据流
   问题 Q ──┐
   答案 A ──┼──► [评委 GPT-4] ──► {A 胜 / B 胜 / 平局} + 理由
   答案 B ──┘         ▲
                      │
              评估标准/打分规则(Prompt 里给定)
```

评委拿到 **(问题, 答案A, 答案B)** 三元组，输出一个**相对判断**。它天然适配 RLHF / DPO 里收集偏好对的场景——见 [[llm-alignment/RLHF]] 的奖励模型训练、[[llm-alignment/DPO]] 的 chosen/rejected 偏好对。

**最简模板（原文）**：

```
问题：[具体问题]
答案A：[候选答案1]
答案B：[候选答案2]
请评估哪个答案更好地回答了问题，并给出理由。
```

### 2.2 为什么"比较"比"打分"更稳？

人和模型对**绝对分数**都不敏感（80 分和 82 分差在哪？说不清），但对**相对优劣**很敏感。成对比较把任务从"估计一个标量"降级为"二选一"，方差更小、一致性更高。代价是：N 个模型两两比较要 $\binom{N}{2}=\frac{N(N-1)}{2}$ 场，再用 Elo / Bradley-Terry 折算成排名。

| N（模型数） | 比较场次 $\binom{N}{2}$ |
|---|---|
| 2 | 1 |
| 5 | 10 |
| 10 | 45 |
| 20 | 190 |

## 3. 单一答案评分（Single Answer Grading）

> **原文定义**：单一答案评分（Single Answer Grading）——在这种方法中，GPT-4 直接给一个答案打分。

### 3.1 机制

```
          单一答案评分数据流
   问题 Q ──┐
   答案   ──┼──► [评委 GPT-4] ──► 分数(如 0~100) + 评分依据
            │         ▲
            └─────────┤
              评分维度(准确性/相关性/清晰度...)
```

**最简模板（原文）**：

```
问题：[具体问题]
答案：[待评分的答案]
请根据准确性、相关性、清晰度等方面给该答案打分，并提供评分依据。
```

### 3.2 与成对比较的取舍

| 维度 | 成对比较 | 单一答案评分 |
|------|----------|--------------|
| 输出 | 谁更好（相对） | 绝对分数 |
| 一致性 | 高（人对相对更敏感） | 较低（分数漂移） |
| 可扩展 | $O(N^2)$ 场对比 | $O(N)$ 次打分 |
| 适用 | A/B 选型、偏好数据、排行榜 | 单模型回归测试、阈值门禁 |
| 主要坑 | 位置偏差（先看到的占优） | 分数标定不稳、啰嗦偏差 |

经验法则：**做排行榜/选模型用成对比较**（更准）；**做 CI 回归门禁用单一评分**（场次少、能设阈值）。

## 4. 多维度评分标准：从"笼统好坏"到"可解释打分"

只说"哪个更好"信息量太低。原文把评判拆成**五个维度**，每维 0~100 分——这是把模糊偏好"原子化"为可审计指标的关键。

> **原文五维评估标准**：
> - **语言理解能力**：答案是否清晰地解释了问题，并使用了易于理解的语言。
> - **生成质量**：答案是否流畅，格式是否正确，是否有语法或打字错误。
> - **知识和事实准确性**：答案中使用的公式和最终结果是否正确。
> - **对话能力**：答案是否直接回答了问题，是否提供了额外的有用信息。
> - **可解释性**：答案是否容易理解，是否提供了足够的解释来帮助用户理解结果。

```
                单维"好/坏"          五维雷达打分
                  ┌───┐            语言理解 ●
                  │好?│            事实准确 ●─┐
                  └───┘            生成质量 ●─┼─► 可加权汇总
              信息量低、不可申诉    对话能力 ●─┘   定位短板
                                   可解释性 ●
```

为什么要拆维度？

1. **可定位**：知道是"事实错"还是"表达差"，才能针对性改进。
2. **抗偏差**：强制评委逐项给理由，能压制"整体感觉"带来的啰嗦偏差/光环效应。
3. **可加权**：不同场景权重不同——客服重"对话能力"，数学题重"事实准确性"。

### 4.1 用原文的"圆面积"例子手算一遍

原文的经典案例：**问题——半径 7cm 的圆面积是多少？**（圆面积公式 $A=\pi r^2$）

两个候选答案：

- **答案（用 3.14）**：$A=\pi\times 7^2 = 3.14\times 49 = 153.86\ \text{cm}^2$，并说明 3.14 是近似值、真实 $\pi=3.14159\ldots$，结果会略有差异。
- **答案（用更精确 π）**：得到 $A = 153.938\ \text{cm}^2$（保留三位），但**表述含乱码/排版错误**（原文中 LaTeX 渲染坏掉、出现 `\\\\` 与 `^^`）。

按真实数学手算校验：

$$A = \pi r^2 = 3.14159265\times 49 \approx 153.938\ \text{cm}^2$$

所以：

| 维度 | 用 3.14 的答案 | 用精确 π 但排版坏的答案 |
|------|---------------|------------------------|
| 知识/事实准确性 | 153.86，**数值偏小**（π 截断） | 153.938，**数值更准** |
| 生成质量 | 流畅、无错字 ✅ | **排版乱码、有打字错误** ❌ |
| 可解释性 | 解释了 π 近似的影响 ✅ | 解释不清 |
| 综合 | 表达完胜，事实略差 | 事实略优，表达崩坏 |

**结论与启示**：评委要在"**事实更准**"与"**表达更好**"之间权衡——这正是为什么需要多维度而非单一总分。同时它揭示一个真实坑：**LaTeX/格式在 Prompt 里转义不当（`\\pi`、`\\(...\\)`、`\\[...\\]`、出现 `^^`）会让评委把好答案误判为差答案**。喂给评委前务必清洗转义。

### 4.2 完整可用 Prompt（原文结构化版本，强烈推荐）

原文给出的、带显式分隔符与逐项打分要求的版本，是工程上最稳的一版：

```
# 问题 #
如果一个圆的半径是7厘米，那么它的面积是多少？

# 答案A #
[候选答案1]

# 答案B #
[候选答案2]

# 评估标准 #
语言理解能力：答案是否清晰地解释了问题，并使用了易于理解的语言。
生成质量：答案是否流畅，格式是否正确，是否有语法或打字错误。
知识和事实准确性：答案中使用的公式和最终结果是否正确。
对话能力：答案是否直接回答了问题，是否提供了额外的有用信息。
可解释性：答案是否容易理解，是否提供了足够的解释来帮助用户理解结果。

请按"评估标准"对每一项标准进行打分（满分为100分），
评估哪个答案更好地回答了问题，同时给出理由。
```

要点：用 `# 标题 #` 把**问题/答案/标准**显式分块，再要求**逐项打分 + 给理由**——这能显著提升评分的稳定性和可复现性。

## 实操：三套即用 Prompt（原文真料，原样保留）

**① 成对比较 · 最简版**

```
问题：[具体问题]
答案A：[候选答案1]
答案B：[候选答案2]
请评估哪个答案更好地回答了问题，并给出理由。
```

**② 成对比较 · 多维打分版**

```
请从语言理解能力、生成质量、知识和事实准确性、对话能力、
可解释性等方面评估哪个答案更好地回答了问题，
并进行打分（满分为100分），同时给出理由。
```

**③ 单一答案评分**

```
问题：[具体问题]
答案：[待评分的答案]
请根据准确性、相关性、清晰度等方面给该答案打分，并提供评分依据。
```

落地建议：

1. **温度设 0**（或极低），让评委判断尽量确定、可复现。
2. **要求结构化输出**（如 JSON：`{"A_score":, "B_score":, "winner":, "reason":}`），便于解析入库。
3. **成对比较做 A/B 双向各跑一次**（A在前一次、B在前一次），取平均以消位置偏差（见下节）。
4. 喂入前**清洗 LaTeX/转义**，避免 4.1 那种"好答案被排版坑死"。

## 常见问题 / 坑

| 坑 | 现象 | 规避 |
|----|------|------|
| **位置偏差** | 评委偏爱排在前面（或后面）的答案 | A/B 交换顺序各评一次取平均；提示语强调"位置无关" |
| **啰嗦偏差** | 越长的答案分越高，哪怕没增信息 | 评分标准里显式写"简洁也是优点，长度不加分" |
| **自偏好偏差** | 评委偏爱与自己风格相似的输出 | 用与被评模型不同家族的评委；或多评委投票 |
| **格式/转义坑** | `\\pi`、`\\(...\\)`、`^^` 等乱码使好答案被误判（见 4.1） | 喂入前反转义、统一渲染 |
| **分数漂移** | 单一评分不同批次标定不一致 | 固定 Prompt+温度0；锚定参考样例（few-shot 校准） |
| **平局过多** | 简单"哪个更好"导致大量平局 | 强制三选一或细化到逐维度打分 |
| **评委≠真理** | 把模型分当作绝对真相 | 抽样人工复核，定期校准评委与人评的一致率 |
| **数据泄漏** | 评测集进了训练集，分虚高 | 用私有/新构造题集，警惕"刷榜" |
