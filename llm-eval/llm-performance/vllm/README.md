## 0. 一句话锚点

**性能评测 = 在一组"受控的负载"下，反复测量服务端的关键指标，得到可对比、可复现的数字。**

核心公式（只有三个变量）：

$$\text{结论} = f(\text{负载}, \text{配置}, \text{硬件})$$

只要"负载、配置、硬件"任意一个变了，数字就不可直接比。这是评测的第一性原理：**先固定变量，再读数**。

## 1. 地基：为什么要做性能评测，它解决什么问题

把一个大模型用 vLLM 跑起来很容易（一行 `api_server` 命令），但真正上线要回答三类问题，全都要靠评测：

1. **容量规划**：一张 A800 上跑 Qwen1.5-7B，能同时扛多少用户？延迟会不会爆？
2. **配置调优**：`--max-num-seqs` 调大到底是变快还是变慢？开 FP8 量化省了多少显存、损了多少精度/速度？
3. **横向对比**：vLLM vs TensorRT-LLM vs SGLang，同样硬件谁更省钱（每元 token 数）？

没有评测，这些都只能"拍脑袋"。评测的本质，是把模糊的"感觉很快"翻译成**带置信度的工程结论**。

```
没有评测                          有评测
─────────                        ─────────
"这配置应该够用吧" ──上线──> 🔥    先压测 ──> P99=820ms，QPS=42 ──> 有依据上线
   (赌运气)                          (可复现、可回归)
```

## 2. 核心指标拆原子（评测到底测什么）

LLM 推理是**两阶段**的，指标必须分两阶段看，否则会被"平均值"骗。

```
一次请求的生命周期（自回归生成）
─────────────────────────────────────────────────────
请求到达
   │   排队等待 (queue)           ← 并发高时这里会变长
   ▼
 ┌──────────┐  Prefill 阶段：一次性处理整段 prompt
 │ 首 token │  ← TTFT 在这里结束
 └──────────┘
   │
 ┌──────────┐  Decode 阶段：一个一个 token 往外吐
 │ token 2  │  ← 相邻两 token 的间隔 = TPOT / ITL
 │ token 3  │
 │   ...    │
 │ token N  │
 └──────────┘
   ▼
请求完成，端到端时延 = TTFT + (N-1) × TPOT
```

| 指标 | 全称 / 含义 | 衡量什么 | 谁关心 |
|---|---|---|---|
| **TTFT** | Time To First Token，首 token 时延 | prefill + 排队的快慢 | 交互式聊天体验（"光标转多久"） |
| **TPOT** | Time Per Output Token，每输出 token 时延 | decode 阶段的吐字速度 | 流式输出流畅度 |
| **ITL** | Inter-Token Latency，token 间隔 | 同 TPOT，逐 token 粒度 | 流式抖动 |
| **E2E Latency** | 端到端时延 | 整条请求耗时 | 同步调用（非流式） |
| **Throughput** | 吞吐：tokens/s 或 requests/s (QPS) | 单位时间产出 | 成本、容量 |
| **并发数** | 同时在处理的请求数 | 负载强度 | 压测的"自变量" |

**为什么要看分位数而不是平均值**：时延分布是长尾的。平均 200ms 听着不错，但 P99=2s 意味着 1% 的用户要等 2 秒。SLA 通常按 **P95 / P99** 定，而不是均值。

```
时延分布（长尾）
 频次
  │ ▇▇▇
  │ ▇▇▇▇▇
  │ ▇▇▇▇▇▇▇
  │ ▇▇▇▇▇▇▇▇▇▇          ← 长尾，被均值掩盖
  └───────────────────────► 时延
     ↑均值    ↑P95  ↑P99
```

**吞吐与时延的根本矛盾**：批越大 → 吞吐越高，但单请求要等更久凑批 → 时延变差。评测的核心就是画出这条**吞吐-时延权衡曲线**，找到 SLA 约束下的最大吞吐点。

```
吞吐(QPS)
  │              ╭─── 进入"时延崩溃"区，QPS 不再涨、P99 飙升
  │          ╭──╯
  │       ╭─╯   ← 拐点(膝点)：性价比最高的工作点
  │     ╭╯
  │   ╭╯
  └──┴──────────────────► 并发数 / 负载
```

## 3. vLLM 为什么快：影响性能的核心机制

评测前必须理解 vLLM 的两大引擎机制，否则读不懂数字为什么这样动。

### 3.1 PagedAttention：KV Cache 的"虚拟内存"

传统做法给每个请求预留**连续的最大长度** KV Cache，导致严重碎片和浪费。PagedAttention 把 KV Cache 切成固定大小的 **block（页）**，像操作系统的分页内存一样按需分配、非连续存储。

```
传统(连续预分配)           PagedAttention(分页)
┌─────────────────┐       block 表(逻辑→物理)
│■■■■░░░░░░░░░░░░░│       req → [blk7, blk2, blk9, ...]
│ 实际用  浪费的预留 │              │    │    │
└─────────────────┘              ▼    ▼    ▼
   碎片+浪费                  物理显存池: [.][7][9][.][2]...
                              按需分配，几乎零浪费
```

**对评测的影响**：显存利用率高 → 同样显存能放更多并发请求 → `--max-num-seqs` 能调更大 → 吞吐上限更高。

### 3.2 Continuous Batching（连续/动态批处理）

传统静态批要等一批全部生成完才能换下一批（短请求被长请求拖死）。vLLM 在**每个 decode step** 动态地把已完成的请求踢出、把排队的新请求塞进来，GPU 永不空转。

```
静态批: [A====][B==][C========]  ← B 早完了也得干等 C
        └─ GPU 利用率有空洞 ─┘

连续批: step 粒度上随到随处理
        A B C
        A B C   ← B 完成
        A · C → A D C  ← 立刻塞入排队的 D
        GPU 始终满载
```

**对评测的影响**：QPS 上去后吞吐能持续增长直到显存/算力打满，这是 vLLM 高吞吐的关键来源。

## 4. 评测系统的整体架构

```
                    性能评测全链路
┌────────────┐   HTTP/并发请求    ┌──────────────────────────┐
│  压测客户端  │ ─────────────────► │   vLLM OpenAI API Server  │
│ (locust /  │                    │  ┌──────────────────────┐ │
│  bench脚本) │ ◄───────────────── │  │ Scheduler(连续批处理) │ │
│            │   流式/非流式响应    │  ├──────────────────────┤ │
│ 控制:      │                    │  │ PagedAttention KV池   │ │
│  ·并发数    │                    │  ├──────────────────────┤ │
│  ·spawn率  │                    │  │ Model Engine (TP/PP)  │ │
│  ·输入/输出 │                    │  └──────────────────────┘ │
│   长度分布  │                    └────────────┬─────────────┘
└─────┬──────┘                                 │ 占用
      │ 采集                                    ▼
      ▼                              ┌────────────────────┐
┌──────────────┐                     │  GPU (显存/算力/功耗) │
│ 指标聚合      │ ◄── nvidia-smi ──── │  A800 / H800 ...    │
│ TTFT/TPOT/QPS│     dcgm 监控        └────────────────────┘
│ P50/P95/P99  │
└──────────────┘
```

要点：**客户端控制负载、服务端是被测对象、GPU 侧要单独监控**（显存占用、利用率、功耗），三方数据对齐才能定位瓶颈到底在排队、显存还是算力。

## 5. 关键启动参数怎么权衡（不背默认值，讲含义与取舍）

文件顶部那条命令里的参数，决定了被测对象的"配置"。逐个讲它做什么、怎么权衡。**具体参数名/默认值以官方文档为准**，这里讲机制。

| 参数（类别） | 它控制什么 | 调大的好处 | 调大的代价 / 风险 |
|---|---|---|---|
| `--gpu-memory-utilization` | 允许 vLLM 占用的显存比例 | 留给 KV Cache 的空间更多→并发上限更高 | 太接近 1.0 易 OOM；要给激活值/碎片留余量 |
| `--max-num-seqs` | 一个 batch 内最大并发序列数 | 提高并发与吞吐 | 受显存约束；过大反而排队抖动 |
| `--max-num-batched-tokens` | 一个 step 最多处理的 token 总数 | 影响 prefill 的批合并能力、吞吐 | 太小限制吞吐，太大增加单 step 时延 |
| `--max-model-len` | 单请求最大上下文长度 | 支持更长输入/输出 | 长度↑→单请求 KV Cache↑→能放的并发↓ |
| `--tensor-parallel-size` (TP) | 模型切到几张卡 | 放得下更大模型/更快 | 引入卡间通信开销；小模型 TP 反而变慢 |
| `--quantization` (如 fp8) | 权重/激活量化 | 省显存、提速、放更多并发 | 可能掉精度；需评测质量与速度的平衡 |
| `--disable-custom-all-reduce` | 关闭自定义 all-reduce | 兼容性/规避特定环境问题 | 可能损失多卡通信性能 |
| `--dtype` | 计算精度（auto/fp16/bf16） | bf16 数值更稳 | 与硬件/模型权重需匹配 |

**核心权衡三角**：

```
         显存预算 (固定)
            ▲
           ╱ ╲
          ╱   ╲
 上下文长度 ◄──► 并发数(max-num-seqs)
 (max-model-len)

显存 ≈ 模型权重 + 并发数 × 上下文长度 × 每token的KV大小
三者此消彼长，评测就是在这个三角里找你场景的最优点。
```

数值直觉：每 token 的 KV Cache 大小 ≈ $2 \times L \times H \times d_{head} \times n_{kv} \times \text{bytes}$（2 是 K 和 V，$L$ 层数）。所以**层数多、隐藏维大、上下文长**的模型，KV Cache 吃显存极快——这也是为什么长文本场景并发上不去。

## 6. 压测工具与方法

| 工具 | 适用场景 | 特点 |
|---|---|---|
| **locust** | 在线服务压测（模拟真实并发用户） | Python 脚本定义行为，`--users` 设并发、`--spawn-rate` 设拉起速率，有 Web UI 看实时 P50/P95 |
| **vLLM 自带 benchmark 脚本** | 离线吞吐/在线 serving 基准 | 仓库内提供（如 benchmark serving/throughput 类脚本），可指定数据集、请求率、输入输出长度 |
| **自写 stream 脚本** | 定制化测 TTFT/TPOT | 直连流式接口，逐 token 打时间戳 |
| **GPU 侧** | 监控显存/利用率/功耗 | `nvidia-smi`、DCGM；判断瓶颈是不是真打满了算力 |

**两种基准范式（必须分清）**：

- **离线吞吐（offline throughput）**：一次性灌入一大批请求，不限速，测"极限吞吐 tokens/s"。回答"这卡天花板多高"。
- **在线 serving（online serving）**：按某个**请求到达率**（如泊松分布的 QPS）持续打，测在该负载下的 TTFT/TPOT 分位数。回答"在目标 SLA 下能扛多少 QPS"。

```
离线: ████████████ 一把全灌 → 看 tokens/s 上限
在线: ▌ ▌  ▌ ▌ ▌   按到达率持续打 → 看 P99 时延 vs QPS
```

**控制变量清单（每次只动一个）**：输入长度、输出长度、并发数、请求到达率、是否流式、batch 参数、量化方式。改两个以上变量，数字就没法归因。

## 7. 完整流程示例（讲含义，命令以你的环境为准）

文件顶部的命令对应的就是这套流程，拆开讲每一步在干什么：

```
① 起服务（被测对象）
python -m vllm.entrypoints.openai.api_server \
  --port 9009 \
  --model /workspace/models/Qwen1.5-7B-Chat \
  --tensor-parallel-size 1 \         # 单卡，7B 放得下
  --gpu-memory-utilization 0.95 \    # 几乎吃满显存给 KV Cache
  --max-model-len 10000 \            # 单请求上下文上限 1w token
  --max-num-seqs 256 \              # 最多 256 并发序列
  --max-num-batched-tokens 10000 \  # 单 step 最多 1w token
  --served-model-name qwen1.5

② 起一个后台流式脚本采时延（TTFT/TPOT）
nohup python vllm-performance-stream-qwen1.5-long.py \
      > latency-...-long.log 2>&1 &

③ 用 locust 加并发负载
locust -f locust-qwen1.5-7b-long.py \
  --users 100 \        # 100 个并发虚拟用户
  --spawn-rate 100 \   # 每秒拉起 100 个（瞬间打满）
  -H http://10.112.xxx.xxx:9009 \
  --run-time 10m       # 持续 10 分钟，让数据稳定

④ 对照组：开 FP8 再跑一遍同样的 ②③
   --quantization="fp8"   ← 只改这一个变量，对比显存/吞吐/时延/质量
```

**读数三步法**：
1. 看 **QPS / tokens-s** 是否随并发增长后趋于平台（说明打到了天花板）。
2. 看 **P95 / P99 TTFT、TPOT** 是否在 SLA 内（崩溃前的拐点就是容量上限）。
3. 看 **GPU 利用率与显存**：若利用率没满但时延已涨，瓶颈在调度/排队而非算力。

**FP8 对比要点**：量化后通常显存↓、可放并发↑、吞吐↑，但要额外用一个质量评测集（如准确率/困惑度）确认精度没掉太多——**性能与质量必须一起评**，否则"更快但更蠢"没意义。

## 常见问题 / 坑

| 坑 | 现象 | 原因 / 对策 |
|---|---|---|
| 只看均值时延 | 上线后偶发卡顿投诉 | 必看 P95/P99，长尾才是体验杀手 |
| 客户端成为瓶颈 | QPS 上不去但 GPU 没满 | locust 机器/网络/单进程被打满；用分布式 locust、换更近的机器 |
| 冷启动混入数据 | 头几秒时延异常高 | 先 warmup 再正式采样，丢弃前 N 秒 |
| `gpu-memory-utilization` 设太高 | 跑着跑着 OOM | 给激活值/碎片留余量，逐步上调而非直接 0.99 |
| 输入/输出长度未固定 | 两次结果没法比 | 固定 prompt 长度与 max_tokens，或用同一数据集 |
| 流式与非流式混测 | TTFT 数据失真 | 测 TTFT/TPOT 必须用流式接口 |
| 小模型上盲目开大 TP | 反而更慢 | TP 通信开销 > 收益；小模型优先单卡 |
| 只测速度不测质量 | 量化后答非所问没发现 | 性能与质量评测配套做 |
| 短测试时间 | 数字抖动大 | 跑足够长（如 10min）让连续批处理进入稳态 |
| 忽略排队时延 | E2E 比预期高很多 | 端到端 = 排队 + prefill + decode，高并发下排队占大头 |
