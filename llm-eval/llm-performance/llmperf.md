## 0. 一句话锚点

**LLMPerf 把"这个推理服务快不快"翻译成 4 个可量化、可复现的数字**：首词元多久来（TTFT）、词元之间间隔多久（ITL）、整句多久出完（E2E）、每秒能吐多少词元（output throughput）。它从**客户端黑盒视角**发请求、掐秒表，不关心服务端用了 vLLM 还是 TGI——只要负载（输入/输出长度分布、并发数）一致，结果就能横向比较。

## 1. 地基：为什么需要"标准化"基准

同一个模型，在同一台机器上，性能数字可以差好几倍，原因有二：

**① 配置爆炸。** 一台 8 卡机（如 AWS `p4de`，8×A100-80G）跑 CodeLlama-34B 有多种切法：

```
8 副本×1 卡   4 副本×2 卡   2 副本×4 卡   1 副本×8 卡
  ↑最多队列      ↑折中          ↑折中          ↑最大吞吐/带宽
```

**② 负载敏感。** 同一配置，输入 100 词元和输入 3000 词元、并发 1 和并发 50，出来的数字完全不同。

所以离开"负载定义"谈性能数字毫无意义。LLMPerf 的价值就是**钉死一套负载**（见第 5 节），让不同服务/配置可比。

```
   服务端(黑盒)                客户端(LLMPerf)
 ┌──────────────┐   HTTP/流式    ┌──────────────────┐
 │ vLLM/TGI/... │ <───请求─────  │ 按固定负载发请求   │
 │  GPU×N       │  ───词元流──>  │ 掐表: TTFT/ITL/E2E │
 └──────────────┘                │ 汇总: RPM/吞吐/分位 │
                                 └──────────────────┘
```

## 2. 四大通用指标（原文定义 + 公式 + 拆解）

> 原文给出的四个"通用指标"：**每分钟完成的请求数、TTFT、ITL、端到端时延**。下面逐个补全原理。

### 2.1 首词元时间 TTFT（Time To First Token）

> 原文：在流式应用中，TTFT 指 LLM 返回第一个词元前所需的时间。

TTFT ≈ 网络往返 + 排队等待 + **Prefill（预填充）**整段 prompt 的时间。它主导**"屏幕开始动"前的卡顿感**。聊天/搜索场景对 TTFT 极敏感。

```
发请求 │← 排队 →│← Prefill 整个prompt →│ 第一个词元
───────┼────────┼──────────────────────┼──────────►
       └──────────── TTFT ─────────────┘
```
prefill 是一次性吞掉全部 N 个输入词元做注意力，计算量 ∝ N，所以**输入越长 TTFT 越大**（但影响有限，见第 6 节）。

### 2.2 词元间时延 ITL（Inter-Token Latency）

> 原文：ITL 指连续输出词元之间的平均时间。计算时将 TTFT 纳入。

ITL 对应 **Decode（解码）**阶段——每步自回归吐一个词元。它决定**"打字机滚动"快不慢**。

$$\text{ITL} = \frac{\text{E2E} }{N_{out}} \quad(\text{把 TTFT 摊进去的口径})$$

其倒数就是**人眼感知的输出速度** tokens/s。注意有两种口径：含不含首词元、含不含 TTFT，横评时必须对齐口径。

### 2.3 端到端时延 E2E（End-to-End Latency）

> 原文：端到端时延应大致等于 **输出长度 × ITL**。

$$\text{E2E} \approx \text{TTFT} + (N_{out}-1)\times \text{TPOT}$$

其中 TPOT（Time Per Output Token）是纯解码每词元时间。这正是原文"≈ 平均输出长度 × ITL"的来源——因为输出通常上百个词元，**decode 累积**支配了总时延。

```
E2E = ┌─TTFT─┐┌─tok─┐┌─tok─┐...┌─tok─┐
       prefill  decode decode    decode
              └────── (N_out-1)×TPOT ──────┘
```

### 2.4 每分钟完成请求数 RPM

吞吐侧指标：固定时间内服务完成多少完整请求。并发越高、单请求越短，RPM 越大；但提高并发会拖慢单请求 ITL——**这是吞吐 vs 时延的根本权衡**。

| 指标 | 单位 | 主导阶段 | 影响什么体验 | 越小/大越好 |
|------|------|---------|-------------|-----------|
| TTFT | 秒/毫秒 | Prefill+排队 | 首屏卡顿 | 越小越好 |
| ITL/TPOT | 毫秒/词元 | Decode | 滚动流畅度 | 越小越好 |
| E2E | 秒 | 全程 | 整句完成 | 越小越好 |
| 输出吞吐 | tokens/s | Decode | 系统产能 | 越大越好 |
| RPM | req/min | 全程 | 系统产能 | 越大越好 |

## 3. 输出词元吞吐与成本

> 原文：总生成词元吞吐量，便于比较成本。

$$\text{output\_throughput}=\frac{\sum N_{out}}{\text{总墙钟时间}}\ \text{(tokens/s)}$$

为什么用它折算成本：GPU 是**按时间租**的，单位时间能吐越多词元，**每百万词元的成本**就越低：

$$\$/\text{1M tokens} = \frac{\text{每小时 GPU 价格}}{\text{output\_throughput}\times 3600}\times 10^6$$

**数值示例**：A100 约 $2/小时，若某配置 output throughput = 2000 tokens/s，则每百万输出词元成本 ≈ 2 / (2000×3600) ×1e6 ≈ **$0.28**。把并发拉满（用满 batch、KV cache）能显著抬高吞吐、压低成本，但会牺牲单请求 ITL。

## 4. 同模型、不同配置的权衡

> 原文核心论断：每个副本 1 卡 → 最低 TTFT（8 个"队列"等输入）；1 副本 8 卡 → 最大吞吐（更大批处理内存 + 8 倍内存带宽）。每种配置基准结果都不同。

```
配置          TTFT    吞吐    解释
8副本×1卡  ┃ 最低 ┃ 较低 ┃ 8条独立队列,排队短;但单卡显存小,batch小
2副本×4卡  ┃ 中   ┃ 中   ┃ 折中
1副本×8卡  ┃ 较高 ┃ 最高 ┃ TP=8聚合8卡显存→大batch+8×带宽,但单请求要等更大批
```

切多卡有两种并行（原文提到流水并行 / 张量并行）：

- **张量并行 TP**：把单层权重按行/列切到多卡，每步都要 **AllReduce** 通信 → 降低单请求时延、扩大可放下的模型/KV，但通信开销随卡数上升。
- **流水并行 PP**：把不同层放不同卡，靠 micro-batch 填满流水线 → 提吞吐，但有 bubble、单请求时延可能变高。

> 结论：**没有"最快配置"，只有"针对某负载/某指标的最优配置"**。所以横评必须连配置一起报告。

## 5. 输入选择：负载分布与并发（原文实测参数）

> 原文给出的标准负载，这是 LLMPerf 可复现性的核心，务必保留：

| 维度 | 取值 | 说明 |
|------|------|------|
| 平均输入长度 | **550 词元**（σ=150） | 假设正态分布 |
| 平均输出长度 | **150 词元**（σ=20） | 假设正态分布 |
| 并发请求数 | **5**（标准化关键数字） | 同时在飞的请求数 |
| 分布假设 | 正态（简化） | 未来拟用 Poisson 等更贴近真实的分布 |

**为什么并发要钉死？** 原文：更多并发会使固定资源的输出变慢。并发数直接决定 batch 大小，进而决定吞吐和单请求时延——不固定并发，两个服务根本不可比。

```
 并发=1            并发=5(LLMPerf标准)        并发=50
单请求最快         折中:有一定batch           吞吐高但单请求ITL被拖慢
吞吐最低           贴近交互式场景             适合离线批处理
```

> 原文为什么用正态而非真实分布：为简化问题假设输入/输出服从正态；未来会考虑 Poisson 等"在建模词元分布方面性质更佳"的分布。

## 6. 输入 vs 输出对时延的影响（原文关键实测数据）

> 这是全文最有价值的定量结论，**逐字保留**：

- 在 250 与 800 输入词元之间，输入词元与 TTFT 之间**无明显关系**，被其他随机噪声"掩盖（swamped）"。
- 用回归比较 **550 输入** 与 **3500 输入** 估梯度：每多 1 个**输入**词元 → 端到端 +**0.3–0.7 ms**。
- 每多 1 个**输出**词元 → 端到端 +**30–60 ms**。
- 因此输入词元对 E2E 的影响约为输出的 **1%**。

**手算验证原文论断**"100 个输入 ≈ 1 个输出"：

$$100 \times 0.5\,\text{ms} = 50\,\text{ms} \approx 1\times(30\text{–}60)\,\text{ms} \checkmark$$

```
对端到端时延的边际贡献(每词元)
输入  │▏ 0.3–0.7 ms
输出  │██████████████ 30–60 ms   (约 50–100×)
```

> 原文工程结论：**想提速，减少输出比减少输入有效得多**。所以"让模型少废话/早停"比"压缩 prompt"对延迟收益大得多。

另一个分析结论（原文）：ITL 和 TTFT 都"足够小不成主要问题"——**人类每秒约读 5 词元**，最慢方案也比人快 6 倍，故方案间在"人能否跟上"层面无显著差异；瓶颈更多在吞吐/成本而非肉眼速度。

## 7. 考虑过但未纳入的指标（原文）

| 指标 | 为何没纳入（原文） |
|------|------------------|
| **预加载时间** | 只能通过"输入大小对首词元的回归"间接测算；250↔800 输入区间内输入与 TTFT 无明显关系、被噪声掩盖，故本轮不加 |
| **总吞吐（含输入+生成词元）** | 原文列出但本轮未展开统计 |

为什么预加载难测：它本质是 prefill 内部的一部分，无法从客户端黑盒直接掐表，只能靠"不同输入长度下 TTFT 的斜率"反推——而该斜率小到被网络/调度噪声淹没，回归不稳定。

典型复现思路（对照上面标准负载）：

```bash
# 安装
git clone https://github.com/ray-project/llmperf.git
cd llmperf && pip install -e .

# 对一个 OpenAI 兼容端点压测：
#   - 输入均值 550(σ150) / 输出均值 150(σ20) / 并发 5
#   - 指标口径见 common_metrics.py: ttft / inter_token_latency /
#     end_to_end_latency / request_output_throughput_token_per_s
# (具体命令以仓库 README 为准，核心是把"标准负载+并发"钉死以保证可复现)
```

> 复现要点：**报告结果时必须连同 (模型, 配置切法, 输入/输出分布, 并发数, 指标口径) 一起给出**，否则数字不可比。

## 常见问题 / 坑

| 坑 | 现象 | 规避 |
|----|------|------|
| 负载不一致 | A 服务用短 prompt、B 用长 prompt，比出来"A 快" | 钉死 550±150 / 150±20 / 并发 5 |
| ITL 口径不同 | 含/不含 TTFT、含/不含首词元，差出几十 ms | 横评统一口径，参照 common_metrics.py |
| 网络噪声掩盖信号 | 输入长度对 TTFT 的影响被淹没 | 多次采样取分位（p50/p90/p99）而非均值 |
| 只看吞吐忽略时延 | 1 副本 8 卡吞吐高但交互卡 | TTFT/ITL 与吞吐一起看，按场景取舍 |
| 误以为压 prompt 能提速 | 砍输入收益微乎其微 | 输入影响仅 ~1%，优先减少输出/早停 |
| 并发未固定 | 两次测试并发不同，结论翻转 | 并发是一等参数，必须固定并标注 |
| 用均值掩盖长尾 | 均值好看，p99 很差 | 关注分位数，尾延迟才是用户痛点 |
