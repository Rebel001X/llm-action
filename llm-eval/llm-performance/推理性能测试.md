## 0. 一句话锚点

> **推理性能测试 = 用受控的工作负载去打一个推理服务，测出"在不破 SLO 的前提下，这台机器/这套配置一秒能吐多少 token、单个用户要等多久"，最终产物是一条吞吐-延迟曲线和一组分位数（P50/P90/P99）。**

它不是"跑一次看个数字"，而是要回答三类决策问题：
- **选型**：vLLM vs TGI vs SGLang，A800 vs H20，谁更快更省？
- **容量规划**：要扛 1000 QPS、TTFT P99 < 500ms，需要几张卡几个副本？
- **调优验证**：开了量化 / Chunked Prefill / 投机解码，到底提了哪个指标、提了多少？

## 1. 地基：一个推理压测由什么构成

压测前必须先把"打什么、怎么打、测什么"三件事钉死，否则数字不可比。

```
┌────────────── 一次推理压测的四要素 ──────────────┐
│                                                  │
│  ① 工作负载 Workload                              │
│     - 输入长度分布 (ISL, Input Seq Len)           │
│     - 输出长度分布 (OSL, Output Seq Len)          │
│     - 数据集 (sharegpt / random / 自己的线上日志) │
│                                                  │
│  ② 负载模型 Load Model                            │
│     - 并发数 concurrency  或  请求率 request-rate  │
│                                                  │
│  ③ 被测系统 SUT (System Under Test)               │
│     - 框架+模型+并行度+量化+GPU+batch调度策略       │
│                                                  │
│  ④ 指标 Metrics                                   │
│     - 吞吐(tokens/s, QPS) + 延迟分位(TTFT/TPOT/P99)│
└──────────────────────────────────────────────────┘
```

**为什么输入/输出长度是第一公民？** 因为 LLM 推理是两阶段的（见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]）：

- **输入长度（ISL）** 决定 prefill 工作量 → 主要影响 **TTFT**（算力受限，注意力还有 $O(L^2)$ 项）。
- **输出长度（OSL）** 决定 decode 步数 → 主要影响 **E2E 延迟** 和总吞吐（OSL 越长，单请求占用 KV-cache 越久）。

> ⚠️ 头号陷阱：用 `input=128, output=128` 的随机短请求测出 5000 tokens/s，拿去给"平均 prompt 2000、输出 800"的线上场景做容量规划，会高估数倍。**工作负载必须贴近真实分布**，最好直接采样线上日志的 ISL/OSL。

## 2. 压测目标：吞吐量 与 延迟分布

两个目标天然打架，必须同时报，缺一不可。

### 2.1 吞吐（Throughput）—— 老板/成本视角

- **输出吞吐 Output tokens/s**：所有并发请求每秒生成的 token 之和（最常用的服务能力指标）。
- **总吞吐 Total tokens/s**：(prompt + 输出) token / 墙钟时间（含 prefill 的全量）。
- **请求吞吐 QPS/RPS**：每秒完成的请求数（请求等长时才稳健）。

$$\text{Output tok/s} = \frac{\sum_i N^{out}_i}{T_{wall}} \approx \text{并发数} \times \frac{1}{TPOT}$$

### 2.2 延迟分布（Latency Distribution）—— 用户/SLO 视角

延迟**绝不能只报均值**。LLM 服务延迟长尾极重（一次抢占、一次长 prefill 就把某请求拖慢），均值会把长尾"洗白"。

```
某次压测 TTFT 实测分布(示意, ms)
频次
 ▲
 │ ██
 │ ████              ← P50≈180ms (大多数请求)
 │ ██████
 │ ██████▒▒
 │ ██████▒▒▒░         ← 长尾,被均值掩盖
 │ ██████▒▒▒░░░  ░    ← P99≈820ms (SLO 红线就看这里!)
 └──────────────────────► TTFT
   均值(被长尾拉高,既不代表典型也不代表最差)
```

- **P50**：典型用户体感。**P90/P95**：大多数用户的上界。**P99**：尾延迟，**SLO 通常写在这**。
- 经典 SLO 写法：`TTFT P99 < 500ms 且 TPOT P99 < 50ms`，意为 99% 请求 0.5s 内见字、后续每字 ≤50ms（≈20 tok/s，比人读快）。

## 3. 负载模型：并发数 vs 请求率（最容易混的概念）

打负载有两种根本不同的范式，决定了你测出来的是什么。

```
┌─ Closed-loop 闭环 (固定并发 concurrency=C) ──────────┐
│  C 个"虚拟用户",每人发一条→等响应完→立刻发下一条      │
│  系统里始终≈C个在飞请求; 系统越慢,发得越慢(自带背压)   │
│  → 测"稳态能力", 不会把系统打爆; 答"C并发下多快"        │
│                                                       │
│   user1: [req]──wait──[resp][req]──wait──[resp]...    │
│   user2: [req]────wait────[resp][req]──wait──...      │
│   ...(共C个)                                           │
└───────────────────────────────────────────────────────┘

┌─ Open-loop 开环 (固定请求率 request-rate=λ req/s) ───┐
│  按到达率λ(常按泊松分布)往里灌,不管前面有没有处理完     │
│  系统慢→请求堆积→排队爆炸→延迟发散                     │
│  → 测"能不能扛住λ的真实流量"; 答"λ流量下会不会崩"       │
│                                                       │
│   到达: ↓  ↓ ↓   ↓  ↓↓    ↓  (泊松,间隔随机)           │
│   队列: ▁▂▃▅█  ← 若λ>服务率, 队列无限涨, 延迟→∞         │
└───────────────────────────────────────────────────────┘
```

- **闭环（concurrency）**：受控、稳定、可重复，**测最大吞吐和稳态延迟首选**。Little 定律：$L=\lambda W$，闭环里在飞数 $L=C$ 固定，吞吐 $\lambda$ 和延迟 $W$ 自洽。
- **开环（request-rate）**：模拟真实泊松到达，**测 SLO 韧性 / 过载行为**首选。λ 一旦超过系统服务率，延迟会发散（队列论的失稳点）。
- 工程上常**两者都扫**：闭环扫并发找峰值吞吐，开环灌不同 λ 看 SLO 何时破。

> 口诀：**concurrency 问"能多快"，request-rate 问"扛不扛得住"。** 报数据时必须写清用了哪种、参数是多少。

## 4. 核心指标：怎么打时间戳算出来

只有流式接口（SSE / streaming）才能测 TTFT/ITL；非流式只能测 E2E。

```
客户端时间轴 (一次流式请求)
t0          t1                 t2    t3        ...      tN
│           │                  │     │                  │
发请求      收到第1个token      tok2  tok3              最后tok
│◄──TTFT───►│◄─ITL─►│◄─ITL─►│ ...                       │
│◄──────────────── E2E Latency ─────────────────────────►│

TTFT  = t1 - t0
ITL_k = t_{k} - t_{k-1}        (相邻token间隔,逐个值)
TPOT  = (tN - t1) / (N_out - 1)   (平均每后续token,不含第1个)
E2E   ≈ TTFT + (N_out - 1)·TPOT
```

| 指标 | 含义 | 算法（客户端打点） | 受限于 | 报什么 |
| --- | --- | --- | --- | --- |
| **TTFT** | 首 token 延迟 | `t(第1个chunk) - t(发请求)` | 算力(prefill) | P50/P99 |
| **TPOT** | 每输出 token 时延 | `(t_last - t_first)/(N_out-1)` | 带宽(decode) | P50/P99 |
| **ITL** | 相邻 token 实测间隔 | `t_k - t_{k-1}`（逐个） | 带宽 | 看分布/抖动 |
| **E2E** | 端到端延迟 | `t_last - t_send` | 综合 | P50/P99 |
| **吞吐** | 输出 tokens/s | `Σ N_out / T_wall` | 综合 | 单值/曲线 |

- **TTFT ≈ 排队 + prefill + 首 token 采样**，prompt 越长越大。
- **TPOT ≈ 解码稳态每步时间**，由显存带宽决定，对 batch 不敏感（权重搬一次全批共用）。
- **ITL vs TPOT**：ITL 是每对相邻 token 的实测间隔（一串值），TPOT 是它的均值/统计量。看 ITL 分布能抓到卡顿（如某步被新请求抢占、chunked prefill 插队）。
- **细节坑**：部分工具的 TPOT 把第 1 个 token 也算进去（用 `E2E/N_out`），与"不含首 token"的口径差一点；报告里要写清。

## 5. warmup（预热）：不预热的数据全是假的

```
未预热的延迟曲线 (前几次请求被一次性开销污染)
延迟
 ▲ █
 │ █                    ← 第1次: CUDA上下文初始化+JIT编译
 │ █▆                   ← 前几次: cudaGraph捕获/算子autotune/权重首次入HBM
 │ █▆▅
 │ █▆▅▃▂▁▁▁▁▁▁▁▁▁▁▁▁▁▁  ← 进入稳态(才是真实性能)
 └──────────────────────────► 请求序号
   └─丢弃这段(warmup)─┘ └──── 统计这段 ────┘
```

**为什么必须 warmup？** 第一次/前几次请求会被一堆**一次性冷启动开销**污染，跟稳态性能毫无关系：

- **CUDA 上下文 & cuBLAS/cuDNN 句柄初始化**（首次几百 ms~秒级）。
- **JIT / 算子 autotune**：很多 kernel（FlashAttention、GEMM）首次运行会试探最优配置。
- **CUDA Graph 捕获**：vLLM 等会在首批请求时捕获 graph，开销大但只一次。
- **权重/缓存首次入 HBM、page table 建立、分配器预热**。
- **Python 解释器/客户端连接池**冷启动。

> 做法：正式压测前先发 N 条 warmup 请求（vLLM `benchmark_latency.py` 里就是先 `run_to_completion()` 一次不计入统计，见 [[llm-eval/llm-performance/vllm-benchmark]]）；或丢弃前若干条结果。**对比实验时所有配置都要同样预热**，否则不公平。

## 6. 规范压测流程（从冷启动到出报告）

```
① 固定环境  → 锁GPU频率(nvidia-smi -lgc)、关ECC波动、独占机器、固定框架版本
② 描述SUT  → 模型/并行度/量化/max-num-seqs/max-model-len/调度策略 全记下来
③ 选负载   → 真实ISL/OSL分布 + 选闭环(扫并发)或开环(扫请求率)
④ Warmup   → 发若干请求,丢弃,等GPU温度/频率稳定
⑤ 正式跑   → 每个工作点跑够时长/够请求数(让长尾被采到,如≥300请求或≥60s)
⑥ 采指标   → TTFT/TPOT/ITL/E2E 的 P50/P90/P99 + 吞吐 + 错误率
⑦ 多点扫   → 改并发/请求率, 重复④~⑥, 得到一系列(吞吐,延迟)点
⑧ 出曲线   → 画吞吐-延迟曲线, 标SLO线, 找拐点/最佳工作点
⑨ 可复现   → 落盘原始结果json + 命令 + 环境, 别人能重跑
```

**两条铁律**：① 每个工作点要跑够久/够多请求，让 P99 这种长尾被真正采样到（请求太少 P99 没意义）；② **一次只改一个变量**（控制变量），否则归因不了。

## 7. 工具

### 7.1 vLLM 自带 bench（最常用）

vLLM 提供官方 benchmark，新版统一成 `vllm bench` 子命令（旧版是 `benchmarks/` 目录下的脚本，见 [[llm-eval/llm-performance/vllm-benchmark]]）。三类：

```
vllm bench latency      # 单批延迟: 固定batch跑,测端到端latency(含warmup,不计第一次)
vllm bench throughput   # 离线最大吞吐: 一把灌完所有请求,测 requests/s + tokens/s
vllm bench serve        # 在线服务压测: 对着OpenAI兼容API打,测TTFT/TPOT/ITL分位数 ★
```

**在线服务压测（最贴近生产）的典型命令**：

```bash
# 先起服务
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000

# 闭环: 固定并发扫吞吐
vllm bench serve \
  --model Qwen/Qwen2.5-7B-Instruct \
  --dataset-name sharegpt --dataset-path ShareGPT.json \
  --max-concurrency 64 \           # ← 闭环并发
  --num-prompts 500 \              # 跑够500条让P99有意义
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90,99 \
  --save-result --result-dir ./out

# 开环: 固定请求率测SLO韧性 (改成请求率,泊松到达)
vllm bench serve ... --request-rate 20   # ← 20 req/s 开环, inf 表示尽快灌
```

输出会给：Output token throughput、Total throughput、Mean/Median/P99 TTFT/TPOT/ITL/E2EL。

> 关键参数：`--max-concurrency`（闭环并发）与 `--request-rate`（开环到达率，`inf`=尽快灌）互斥语义；`--num-prompts` 决定样本量（影响 P99 可信度）；`--ignore-eos` 强制生成到指定长度（控制 OSL）。具体子命令/参数以你装的 vLLM 版本 `vllm bench serve --help` 为准。

### 7.2 NVIDIA genai-perf（Triton 生态，跨后端标准基准）

`genai-perf`（属于 Triton perf_analyzer 套件）是厂商中立的 LLM 基准工具，对任意 OpenAI 兼容端点都能打，长于规范化的 ISL/OSL 控制和分位输出。

```bash
genai-perf profile \
  -m Qwen2.5-7B-Instruct \
  --endpoint-type chat \
  --service-kind openai \
  --url http://localhost:8000 \
  --streaming \                       # 必须流式才有TTFT/ITL
  --concurrency 64 \                  # 闭环并发(也支持 --request-rate 开环)
  --synthetic-input-tokens-mean 2048 \    # 控制ISL分布
  --synthetic-input-tokens-stddev 128 \
  --output-tokens-mean 256 \              # 控制OSL
  --warmup-request-count 10 \         # ← 内建warmup
  --measurement-interval 30000        # 测量窗口
```

输出表含 TTFT、ITL、TPOT（它叫 inter-token latency 相关项）、Request latency、Output token throughput、Request throughput，均带 avg/p90/p95/p99。优点：**同一工具横向对比 vLLM / TGI / TensorRT-LLM / SGLang**，口径统一。

### 7.3 其它常见工具（按场景选）

| 工具 | 定位 | 适合 |
| --- | --- | --- |
| **vllm bench serve** | vLLM 官方在线压测 | 调 vLLM、出 TTFT/TPOT 分位 |
| **genai-perf** | 厂商中立、跨后端 | 横向选型对比 |
| **llmperf** | Anyscale 开源 LLM 压测 | 多 provider/API 压测，见 [[llm-eval/llm-performance/llmperf]] |
| **TGI benchmark** | HF TGI 自带 | 调 TGI |
| **wrk / Locust** | 通用 HTTP 压测 | 只测请求级 QPS/延迟，不懂 token 语义 |
| **evalscope** | 精度+性能一体 | 一站式评测 |

> 通用 HTTP 工具（wrk、Locust）能压 QPS 但**不理解流式 token**，测不出 TTFT/TPOT，做 LLM 专项压测要用 LLM 感知的工具。

## 8. 怎么画吞吐-延迟曲线（核心交付物）

单个数字没意义，**一条曲线**才能定容量、找最佳工作点。做法：固定工作负载（ISL/OSL/数据集），**扫并发数**（或请求率），每个点记录 (吞吐, 延迟分位)，连成线。

```
扫并发: C = 1, 2, 4, 8, 16, 32, 64, 128, 256 ...
每个C跑一轮 → 得一个点 (Output tok/s, TTFT-P99 或 TPOT-P99)

  延迟
 (P99)
   ▲                                    ╱C=256  ← 过载: 吞吐不再涨,延迟爆炸
   │                              ╱C=128       (排队主导, SLO 破)
   │  SLO红线 ─ ─ ─ ─ ─ ─ ─●━━━━╱─ ─ ─ ─ ─ ─    ← 破线点=最大可用并发
   │                   C=64╱ ▲
   │              C=32 ╱    └ 拐点附近=最佳工作点(贴SLO跑,既不浪费也不超时)
   │         C=16 ╱
   │     C=8 ╱
   │  C=4╱     ← 轻载: 加并发吞吐线性涨,延迟几乎不动(系统没吃饱)
   │ C=2
   │C=1
   └────────────────────────────────────────► 吞吐 (Output tokens/s)
```

**怎么读这条曲线**：

1. **轻载段（左下）**：加并发，吞吐近线性上升，延迟几乎不动 → 系统没喂饱，资源闲置。
2. **拐点（knee）**：延迟开始明显抬头但吞吐还在涨 → **饱和点附近，最佳性价比工作点**。
3. **过载段（右上陡升）**：吞吐见顶甚至回落，延迟垂直爆炸 → 排队主导，请求堆积，SLO 破。
4. **SLO 红线与曲线的交点** = 在满足 SLO 前提下能跑的**最大吞吐/最大并发** → 直接用于容量规划。

**容量规划用法**：单副本在 SLO 内能扛 X tokens/s（或 Y QPS），目标流量 Z → 需要 `ceil(Z / X)` 个副本。

> 实操要画**多条曲线对比**：不同模型、不同量化、不同框架各画一条，谁的曲线更靠右下（同延迟下吞吐更高 / 同吞吐下延迟更低）谁更优。

## 9. 数值例子：读懂一组真实读数

设：Qwen2.5-7B（BF16），单卡 A800（HBM 带宽约 2 TB/s，以官方为准），工作负载 ISL=2048 / OSL=256，闭环扫并发，节选三个工作点：

| 并发 C | TTFT-P99 | TPOT-P99 | Output tok/s | 解读 |
| --- | --- | --- | --- | --- |
| 1 | 110 ms | 7 ms | ~140 | 单请求理论上限（带宽下界，见手算） |
| 64 | 380 ms | 22 ms | ~2300 | 拐点附近，吞吐大涨、延迟仍在 SLO 内 |
| 256 | 2100 ms | 65 ms | ~2500 | 过载：吞吐几乎不涨，TTFT/TPOT 爆炸，SLO 破 |

**手算对账（理论下界）**：

- **TPOT 下界（C=1，访存受限）**：每步搬全部权重 $7\times10^9 \times 2\text{B}=14\text{ GB}$：
$$t_{step}\ge \frac{14\text{ GB}}{2\text{ TB/s}}=7\text{ ms}\;\Rightarrow\; \frac{1}{0.007}\approx 143\text{ tok/s}$$
读数 7 ms / 140 tok/s 与下界吻合 → 系统健康，没有异常开销。
- **TTFT 量级（prefill 算力受限）**：prefill FLOP $\approx 2ND = 2\times7\times10^9\times2048\approx 2.87\times10^{13}$，A800 BF16 峰值约 312 TFLOPS（以官方为准）：
$$t_{prefill}\ge \frac{2.87\times10^{13}}{312\times10^{12}}\approx 92\text{ ms}$$
C=1 读数 110 ms 略高于 92 ms（含排队/采样/未满载），量级对。

**结论**：选 **C=64 作为部署工作点**——TTFT P99 380ms、TPOT P99 22ms（≈45 tok/s，比人读快）均在常见 SLO 内，且吞吐 2300 tok/s 是 batch=1 的 16 倍。要扛 20000 tok/s 线上流量 → 约需 `ceil(20000/2300)=9` 个副本。

## 常见问题

| 问题 | 一句话答案 |
| --- | --- |
| 只测均值行不行？ | 不行。LLM 延迟长尾重，SLO 看 P99，必须报分位数。 |
| concurrency 和 request-rate 选哪个？ | 测峰值吞吐用闭环 concurrency；测 SLO 韧性/过载用开环 request-rate；最好都扫。 |
| 不 warmup 会怎样？ | 前几条被 CUDA 初始化/JIT/CUDA-Graph 捕获污染，延迟虚高，数据失真。 |
| TTFT 突然变大查什么？ | prompt 变长、排队（并发过高）、Chunked Prefill 配置、副本不足。 |
| TPOT 怎么压低？ | 量化权重/KV、投机解码、MQA/GQA（降访存量，TPOT 是带宽下界）。 |
| 吞吐上不去？ | 看是否 Continuous Batching、max-num-seqs 太小、显存塞不下更大 batch（PagedAttention）。 |
| 为什么短请求测出的吞吐特别高？ | ISL/OSL 太小，prefill/decode 工作量小，不能外推到真实长请求场景。 |
| 拐点之后加机器有用吗？ | 拐点后单机已过载，应横向加副本而非继续加并发；纵向调优看 MFU/MBU。 |
| 流式和非流式测的指标差别？ | 非流式只能测 E2E；TTFT/ITL/TPOT 必须流式接口才能打点。 |
