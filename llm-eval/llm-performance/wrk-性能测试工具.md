## 0. 一句话锚点

**wrk = 多线程 + I/O 多路复用(epoll/kqueue) + 可选 Lua 脚本** 的 HTTP 基准测试器。
核心卖点：**用很少的线程（通常等于 CPU 核数）维持成千上万条长连接**，从而在单台压测机上产生远超 `ab`（Apache Bench）的负载，用来测一个 HTTP 服务在固定并发下的**吞吐量（Req/Sec）**和**延迟分布（Latency）**。

它不是功能测试工具，不是浏览器模拟器，**它只回答一个问题**：「这个 HTTP 端点，在 N 条并发连接、持续 T 秒的压力下，每秒能处理多少请求、延迟是多少。」

## 1. 地基：它解决什么问题

要测一个 Web/推理服务的性能，传统做法的痛点：

- **`ab`（ApacheBench）**：单线程、阻塞式。一个进程一条连接，想要高并发就得开很多进程，受单核能力限制，很难把服务端压满，常常**压测机先到瓶颈**。
- **JMeter / Locust**：功能强、能编排复杂场景，但**每个虚拟用户开销大**（线程或协程 + JVM/Python 解释器），单机并发数有限，资源占用高。

wrk 的取舍：**砍掉复杂编排，只保留「狠狠地打同一个/同一组 URL」这一件事**，用底层 C + 事件驱动把单机压力做到极致。

```
压测的本质：客户端要"假装"成很多用户，同时给服务端发请求

         ┌─────────────┐  N 条并发连接   ┌─────────────┐
         │  压测客户端  │ ──────────────▶ │  被测服务端  │
         │   (wrk)     │ ◀────────────── │ (vLLM/Nginx)│
         └─────────────┘   响应 + 计时    └─────────────┘
              │
              ▼
   关键矛盾：客户端自己别先成为瓶颈
   ab:   1 线程 1 连接，想高并发就堆进程  → 客户端先累垮
   wrk:  少量线程，每线程管一堆连接(异步) → 客户端很省，能压满服务端
```

一句话：**wrk 把「并发」和「线程数」解耦了**——并发由连接数（connections）决定，而不是由线程数决定。这是它和 `ab` 最本质的区别。

## 2. 整体架构：多线程 + 事件循环 + Lua

wrk 的结构可以拆成三层：

```
┌──────────────────────────────────────────────────────────┐
│                        wrk 进程                            │
│                                                            │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐           │
│  │  Thread 1  │  │  Thread 2  │  │  Thread N  │  (≈CPU核数)│
│  │            │  │            │  │            │           │
│  │ epoll 事件 │  │ epoll 事件 │  │ epoll 事件 │           │
│  │ 循环       │  │ 循环       │  │ 循环       │           │
│  │            │  │            │  │            │           │
│  │ conn ──┐   │  │ conn ──┐   │  │ conn ──┐   │           │
│  │ conn   ├多 │  │ conn   ├多 │  │ conn   ├多 │ 连接平均  │
│  │ conn   │条 │  │ conn   │条 │  │ conn   │条 │ 分给各线程│
│  │ conn ──┘   │  │ conn ──┘   │  │ conn ──┘   │           │
│  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘           │
│        │               │               │                  │
│        └───────────────┼───────────────┘                  │
│                        ▼                                   │
│              每条连接可挂一个 Lua 状态机                    │
│       (LuaJIT：生成请求 / 处理响应 / 自定义统计)            │
└──────────────────────────────────────────────────────────┘
                         │
                    汇总所有线程的计数 → 输出统计报告
```

三个关键设计点：

1. **线程数 ≈ CPU 核数**：每个线程绑一个事件循环（基于 epoll on Linux / kqueue on BSD/macOS）。线程开多了只会增加上下文切换开销，并不增加并发能力。
2. **连接数 = 真正的并发量**：总连接数被**平均分配**到各个线程上。每个连接在它所属线程的事件循环里被异步驱动——发出请求、等待可读事件、读响应、再发下一个请求……如此循环。
3. **LuaJIT 嵌入**：每个线程内嵌一个 LuaJIT 虚拟机，可以在请求生成 / 响应处理 / 统计阶段插入自定义逻辑，这让 wrk 能压非 GET 的复杂场景。

## 3. 核心机制：事件循环与连接复用

理解 wrk 性能高的关键是「一条连接是怎么被复用的」。每条 TCP 连接在事件循环里跑一个状态机：

```
单条连接的生命周期（闭环复用，不是发一次就关）：

  建立 TCP/TLS 连接
        │
        ▼
   ┌─►  写：发送一个 HTTP 请求  ◄──────────┐
   │         │                            │
   │         ▼                            │
   │    注册到 epoll，等"可读"事件         │  (整个测试时长 T 秒内
   │         │                            │   不断循环，不关闭连接 →
   │         ▼                            │   这就是 keep-alive 长连接)
   │    读：接收 HTTP 响应                 │
   │         │                            │
   │         ▼                            │
   │    记录这次请求的延迟、状态码         │
   └─────────┴────────────────────────────┘
```

为什么这样就快？

- **不阻塞**：线程在等某条连接的响应时，不是干等，而是去处理其它已就绪连接的读写。一个线程因此能「同时」推动几百上千条连接。
- **长连接复用**：默认走 HTTP keep-alive，一条 TCP 连接打完一个请求紧接着打下一个，省掉了反复三次握手 + TLS 握手的开销。
- **没有真实「用户思考时间」**：wrk 是**闭环（closed-loop）** 模型——一个响应回来立刻发下一个请求。这意味着 wrk 测的是「服务端能多快地处理」，而不是「真实用户按某个到达率发请求」。这一点在第 7 节会成为压 LLM 时的重要陷阱。

> 注意区分两个数：**connections 是同一时刻保持的并发连接数**；**总请求数 = 每条连接在 T 秒内能完成的请求数 × 连接数**，由服务端处理速度决定，不是你设定的。

## 4. 命令行参数逐项拆解

> 下面讲每个参数「做什么、怎么权衡」。**确切的短/长选项写法、默认值请以 `wrk --help` 和官方 README 为准**，这里不背死默认值。

基本调用形态：

```
wrk [选项] <URL>
例： wrk -t12 -c400 -d30s --latency http://127.0.0.1:8000/
```

| 参数（语义） | 作用 | 怎么设 / 怎么权衡 |
|--------------|------|-------------------|
| 线程数 `-t / --threads` | 启多少个事件循环线程 | **一般设为压测机的 CPU 物理核数**。再多只增加调度开销不增吞吐 |
| 连接数 `-c / --connections` | 保持的并发长连接总数 | **这才是「并发度」**。从小到大扫一遍找拐点；要求 `connections ≥ threads` |
| 持续时间 `-d / --duration` | 压多久（如 `30s`、`2m`） | 太短数据抖动大、有冷启动；一般 ≥30s，关键测试跑 1～5min |
| 延迟分布 `--latency` | 打印 P50/P90/P99 等分位延迟 | **强烈建议总是加**，否则只有均值，掩盖长尾 |
| 脚本 `-s / --script` | 加载一个 Lua 脚本扩展请求逻辑 | 压 POST/带 header/动态 URL 时必用（见第 6 节） |
| 自定义头 `-H / --header` | 给每个请求加 HTTP header | 如 `-H "Authorization: Bearer xxx"`、`-H "Content-Type: application/json"` |
| 超时 `--timeout` | 单请求超时阈值 | 超时的请求会被计入 errors；LLM 长响应要调大，否则全标超时 |
| 打印每条线程统计 | （部分版本/脚本）逐线程明细 | 排查线程间负载不均时有用 |

权衡口诀：
- **`-t` 跟着核数走，别乱加**。
- **`-c` 是你要扫的变量**——做一组实验：c=50/100/200/400/800……观察 Req/Sec 何时不再上升、P99 何时开始爆炸，那就是服务的容量拐点。
- **`-d` 要够长**，让服务进入稳态（缓存预热、JIT、连接池铺满）。

## 5. 输出报告怎么读

一份典型输出（数值为示意，不代表任何真实服务）：

```
Running 30s test @ http://127.0.0.1:8000/
  12 threads and 400 connections
  Thread Stats   Avg      Stdev     Max   +/- Stdev
    Latency    25.13ms   10.20ms  210.5ms   88.7%
    Req/Sec     1.32k    180.4     1.90k    71.2%
  Latency Distribution
     50%   22.5ms
     75%   30.1ms
     90%   41.8ms
     99%   95.3ms
  475200 requests in 30.00s, 1.21GB read
  Requests/sec:  15840.00
  Transfer/sec:  41.3MB
```

逐行解读：

| 行 | 含义 | 怎么用 |
|----|------|--------|
| `Latency Avg/Stdev/Max` | 每条线程内单请求延迟的均值/标准差/最大值 | Stdev 大 = 抖动大；Max 看最坏情况 |
| `+/- Stdev` 那一列的百分比 | 落在「均值 ± 1 个标准差」内的样本占比 | 远小于理论 ~68% 说明分布偏斜、有长尾 |
| `Req/Sec`（Thread Stats 那行） | **单个线程每秒的请求数**，不是总数 | 要总吞吐看下面的 `Requests/sec` |
| `Latency Distribution` | P50/P75/P90/P99 分位延迟 | **看 P99！** 服务质量由长尾决定，均值会骗人 |
| `N requests in Ts, X read` | 总完成请求数、总读取字节 | 用来核对实验规模 |
| `Requests/sec` | **全局总吞吐（核心结果）** | 容量评估主指标 |
| `Transfer/sec` | 每秒传输字节 | 判断是不是被网卡带宽打满了 |

陷阱提醒：`Avg` 是均值，**对长尾不敏感**。一个 P50=20ms、P99=2s 的服务，均值可能只有 60ms，看起来很好，实际 1% 的用户体验极差。**永远看分位数。**

## 6. Lua 脚本扩展（压复杂场景的钥匙）

裸 wrk 只能压固定的 GET URL。要压 POST、带 JSON body、随机化参数、统计自定义指标，就靠 Lua。wrk 在请求生命周期里暴露了几个**回调钩子**（hook），你在脚本里实现对应的全局函数即可：

```
请求生命周期 ── wrk 会在这些时机回调你的 Lua 函数
────────────────────────────────────────────────
  setup(thread)   ── 每个线程启动时调用一次（分发数据、初始化）
        │
        ▼
  init(args)      ── 线程内首次进入时
        │
   ┌──► request() ── 每次要发请求前调用：你返回拼好的请求体
   │      │
   │      ▼
   │    （服务端处理）
   │      │
   │      ▼
   │    response(status, headers, body) ── 每次收到响应后调用
   └──────┘                                （可在这里做自定义统计）
        │
        ▼
  done(summary, latency, requests) ── 整个测试结束，输出自定义报告
```

一个压 POST + JSON 的最小示例（**函数名以官方 wrk 脚本 API 为准**）：

```lua
-- post.lua  —— 压一个需要 JSON body 的接口
wrk.method = "POST"
wrk.headers["Content-Type"] = "application/json"
wrk.body   = '{"prompt": "你好", "max_tokens": 128}'

-- 如需每个请求都不同，可实现 request() 动态生成：
-- request = function()
--   local body = string.format('{"id": %d}', math.random(1, 100000))
--   return wrk.format("POST", nil, nil, body)
-- end
```

运行：`wrk -t8 -c200 -d60s -s post.lua --latency http://127.0.0.1:8000/v1/chat/completions`

要点：
- `wrk.format(method, path, headers, body)` 用来拼一个完整 HTTP 请求字符串。
- 想统计「成功率 / 业务错误码」，在 `response()` 里根据 `status` 或解析 `body` 自己累加，最后在 `done()` 里打印。
- LuaJIT 很快，但脚本里别做重活（如复杂正则、大 JSON 解析），否则**客户端 CPU 成瓶颈**，测出来的是脚本的速度而不是服务端的。

## 7. 用 wrk 压 LLM 推理服务：能用，但要小心

把 wrk 指向 vLLM / TGI / SGLang 的 `/v1/chat/completions` 是可行的（配 Lua POST 脚本即可），但 **LLM 推理和普通 Web 请求有本质差异**，直接套 wrk 容易得到误导性结论：

```
普通 Web 请求          vs        LLM 生成请求
─────────────          ──        ─────────────
响应小、几乎瞬时                 响应是逐 token 流式产出，秒级
一次请求一个数字"延迟"           有多个延迟指标：
                                  · TTFT  首 token 时间
                                  · TPOT  每 token 时间(token间延迟)
                                  · E2E   整条响应总时长
吞吐 = Req/Sec                   吞吐更看 tokens/sec，而非请求/秒
请求间无状态                     有 KV-Cache、连续批处理(continuous
                                  batching)，并发越高单请求越慢
```

wrk 的三大「不够用」：

1. **只懂 Req/Sec，不懂 token**：LLM 真正关心的是 **TTFT、TPOT、输出 tokens/sec**。wrk 默认只给「整条请求的延迟」，无法拆出首 token 时间——除非你在 Lua 里解析 SSE 流自己算，非常别扭。
2. **闭环模型 ≠ 真实负载**：wrk 一收到响应立刻发下一条，是「打满式」压测。真实线上是按某个**到达率（QPS）**来请求的（开环 open-loop）。要测「在 X QPS 下延迟如何」，wrk 难以恒定 QPS（这正是 **wrk2** 诞生的原因，见第 8 节）。
3. **变长输出**：每个 prompt 的输出 token 数不同，请求耗时天然不齐，wrk 的均值/分位统计会被输出长度分布污染——必须固定 `max_tokens` 或控制 prompt 才能公平比较。

**结论**：摸底「服务能不能扛住高并发连接、网关/路由层有没有瓶颈」用 wrk 很合适；但要专业评估 LLM 的 TTFT/TPOT/tokens-per-sec，应该用 **专门的 LLM benchmark 工具**（如 llmperf、vllm 自带 benchmark、genai-perf 等，参见同目录 [[llm-eval/llm-performance/llmperf]] 与 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]）。

## 8. 与同类工具对比

| 工具 | 模型 | 强项 | 弱项 / 适用边界 |
|------|------|------|------------------|
| **wrk** | 闭环、C+Lua | 单机并发极高、轻量、Lua 可扩展 | 不能恒定 QPS；不懂 token 级指标 |
| **wrk2** | **开环**（恒定速率） | 能设定固定 QPS（`-R`），延迟统计修正了「协调遗漏」(coordinated omission) | 基于旧版 wrk fork，功能较老 |
| **ab** (ApacheBench) | 阻塞单线程 | 极简、随 Apache 自带 | 并发能力弱，客户端易先成瓶颈 |
| **hey / vegeta** | Go 实现 | 易用、可设速率、跨平台 | 极限并发通常不如 wrk |
| **JMeter / Locust** | 重型、可编排 | 复杂业务流、分布式压测、丰富报表 | 单机并发低、资源占用大 |
| **llmperf / genai-perf / vllm benchmark** | LLM 专用 | 直接产出 TTFT/TPOT/tokens-per-sec | 仅针对 LLM 推理接口 |

选型口诀：
- 压**普通 HTTP / 网关 / 静态服务**，要单机狠压 → **wrk**。
- 要**固定 QPS、修正长尾统计** → **wrk2**。
- 压**LLM 推理本身（要 token 指标）** → 用 **LLM 专用工具**，wrk 只做粗筛。

## 常见问题 / 坑

| 现象 / 坑 | 原因 | 对策 |
|----------|------|------|
| Req/Sec 上不去，但服务端 CPU 没满 | **压测机自己**成了瓶颈（CPU/网卡/端口耗尽） | 压测机和被测服务分机部署；`-t` 别超核数；看压测机网卡是否打满 |
| 大量 `socket errors` / connect 失败 | 本机临时端口耗尽、`somaxconn`/文件描述符不够 | 调大 `ulimit -n`、内核 `net.ipv4.ip_local_port_range`、服务端 backlog |
| 延迟均值好看但线上体验差 | 只看了 Avg，没看分位 | 永远加 `--latency`，盯 **P99**；必要时用 wrk2 修正协调遗漏 |
| LLM 接口全部 timeout | 生成耗时 > 默认超时 | 调大 `--timeout`；固定 `max_tokens` 控制响应长度 |
| 改了 `-c` 但吞吐不变 | 服务端已饱和，或连接被服务端限流/拒绝 | 这正是容量拐点；继续加连接只会推高延迟 |
| 想测「100 QPS 下的延迟」却测成了打满 | wrk 是闭环，不能恒定到达率 | 换 **wrk2 + `-R 100`** |
| Lua 脚本里做重计算，吞吐莫名很低 | 客户端 CPU 被脚本吃光 | 脚本只做轻量拼装；重逻辑挪走 |
| connections < threads 报错/异常 | 连接没法平均分给线程 | 保证 `-c ≥ -t` |
| 多次测结果飘 | 时间太短 / 没预热 | `-d` 拉长到 ≥30s，先空跑预热再正式测 |
