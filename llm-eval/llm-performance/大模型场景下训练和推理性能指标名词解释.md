## 0. 一句话锚点

- **延迟（Latency）= 等多久**：单个请求/单个 token 花的时间，越小越好，用户体感。
- **吞吐（Throughput）= 干多少活**：单位时间处理的 token / 样本 / 请求数，越大越好，老板看成本。
- **利用率（Utilization）= 钱花得值不值**：实际有效计算 ÷ 硬件理论峰值，越高越省钱。
- 三者**互相打架**：增大 batch 提吞吐 → 但单请求延迟变高；这就是大模型服务调优的核心矛盾。

```
              快(低延迟)
                 ▲
                 │   ← 用户/产品 想要这边
   小batch ──────┼────── 大batch
                 │   ← 老板/成本 想要这边
                 ▼
              省(高吞吐/高利用率)
   调优 = 在这条轴上，按 SLO 找最优工作点
```

## 1. 地基：token、FLOP、FLOPS、算力屋顶

### 1.1 token：一切的计量单位

token 是文本的最小处理单位，由分词器（tokenizer）切分。英文里约 1 token ≈ 0.75 词，中文里约 1 token ≈ 1～1.5 字。**所有性能指标的"工作量"几乎都以 token 计**。

```
"大模型推理"  --分词-->  ["大", "模型", "推", "理"]   (示意,实际依分词器)
   原文                      4 个 token
```

### 1.2 FLOP vs FLOPS：别混！

- **FLOP**（Floating-point Operation，单数/复数同形，看语境）= 一次浮点运算（一次乘或一次加）。这是**工作量**，无时间维度。
- **FLOPS / FLOP/s**（Floating-point Operations **per Second**）= 每秒浮点运算次数。这是**速度/算力**，有时间维度。
- 工程里常写 **TFLOPS**（T=10¹²）、**PFLOPS**（P=10¹⁵）。例：A100 BF16 稠密峰值约 312 TFLOPS。

> ⚠️ 高频陷阱：论文/简历写 "训练用了 3.2e24 FLOPs" 指的是**总工作量**；写 "GPU 有 312 TFLOPS" 指的是**速度**。一个是路程，一个是时速，单位差一个 `/s`。

### 1.3 Transformer 算力的"黄金公式"

对一次**前向**，每个 token 的浮点运算量约为 $2N$，其中 $N$ 是模型参数量（每个参数对应一次乘+一次加 = 2 FLOP）。

$$C_{\text{fwd}} \approx 2 \cdot N \cdot D \quad(\text{FLOP},\ D=\text{token 数})$$

训练含**反向**，反向约是前向的 2 倍，故训练总量经验公式：

$$\boxed{C_{\text{train}} \approx 6 \cdot N \cdot D}$$

推理（只前向）则用 $2ND$。**记住 6 和 2 这两个魔数**，几乎所有训练/推理成本估算都从这里推。

### 1.4 屋顶线模型（Roofline）：算力还是带宽说了算？

一个 kernel 是被"算"卡住还是被"搬数据"卡住，取决于**算术强度（Arithmetic Intensity, AI）**：

$$AI = \frac{\text{FLOP}}{\text{Byte}} = \frac{\text{计算量}}{\text{访存量}}$$

```
 可达性能
 (FLOPS)
   ▲        斜线段:带宽墙        平台段:算力墙
   │            /───────────────────────────
   │           /  ← compute-bound(算力受限)
   │          /
   │         / ← memory-bound(访存受限)
   │        /
   └───────┴──────────────────────────────► 算术强度 AI (FLOP/Byte)
         拐点 AI* = 峰值算力 / 峰值带宽
```

- **AI < AI\***：访存受限（memory-bound）→ 加算力没用，要省带宽。**LLM 自回归解码每步就在这区**。
- **AI > AI\***：算力受限（compute-bound）→ 要更高 FLOPS。**训练、大 batch prefill 在这区**。
- 这是理解 "为什么解码慢、为什么要 KV-cache、为什么要 batch" 的总开关。

## 2. 延迟指标：用户等多久

LLM 推理分两阶段，延迟指标都围绕它定义：

```
请求到达
  │
  ├─[Prefill 预填充]── 并行处理整个 prompt ──► 产出第 1 个 token
  │         ↑ 这段时间 = TTFT 的主体(算力受限)
  │
  └─[Decode 解码]──► tok2 ─► tok3 ─► ... ─► tokN (逐个吐,自回归)
            ↑ 相邻两 token 间隔 = ITL；其平均 = TPOT(访存受限)
```

### 2.1 TTFT（Time To First Token，首 token 延迟）

**定义**：从请求发出，到收到第 1 个输出 token 的时间。

$$TTFT \approx t_{\text{排队}} + t_{\text{prefill}} + t_{\text{首token采样}}$$

- **决定体感**：聊天/流式输出里，TTFT 就是用户"白屏等待"的时间。
- **主要由 prefill 决定**，prefill 要处理整段 prompt，**算力受限**，prompt 越长 TTFT 越大（近似线性甚至更陡，因注意力 $O(L^2)$）。
- **怎么测**：客户端打时间戳，`t(第一个 SSE chunk 到达) - t(请求发出)`；压测工具用 vLLM benchmark、`llmperf`、`genai-perf`。
- **优化方向**：① 缩短/缓存 prompt（Prefix Caching 复用公共前缀的 KV）；② Chunked Prefill 把长 prefill 切片，避免阻塞解码；③ 减少排队（更好的调度、更多副本）；④ 更快的注意力 kernel（FlashAttention）；⑤ 投机解码对 TTFT 无益，主要帮 TPOT。

### 2.2 TPOT（Time Per Output Token，每输出 token 时延）

**定义**：进入解码稳态后，平均每生成一个**后续** token 的时间（通常不含第 1 个）。也叫 **TBT**（Time Between Tokens）。

$$TPOT = \frac{t_{\text{end}} - t_{\text{first token}}}{N_{\text{out}} - 1}$$

- **决定"打字速度"**：流式输出里字蹦多快。$1/TPOT$ 就是单请求的 token 生成速率（tokens/s/req）。
- **访存受限**：每步解码要把整个模型权重 + KV-cache 从显存搬过来算一个 token，AI 极低 → 卡在**显存带宽**，不是算力。这就是为什么解码加 batch 几乎不增加单步时间（权重搬一次给一批共用）。
- **怎么测**：流式接口记录每个 chunk 时间戳，相邻差值取均值；或 `(E2E - TTFT)/(N_out - 1)`。
- **优化方向**：① **量化权重**（W8/W4）直接降访存量 → TPOT 几乎线性受益；② **投机解码 / Medusa / EAGLE**（小模型猜、大模型验，一步出多 token）；③ **KV-cache 量化/压缩**（KV 也要搬）；④ 更大 batch 提吞吐但单请求 TPOT 略升（共享带宽被摊薄）；⑤ MQA/GQA 减小 KV 体积。

### 2.3 ITL（Inter-Token Latency）与 E2E Latency

- **ITL**：相邻两 token 的实测间隔（逐个值），TPOT 是它的平均/统计量。看 ITL 分布能发现卡顿（如某步被抢占）。
- **端到端延迟 E2E Latency**：从请求到最后一个 token：

$$E2E \approx TTFT + (N_{\text{out}}-1)\cdot TPOT$$

> 工程上谈延迟必谈**分位数**：P50 看典型、**P99 看尾延迟（SLO 红线）**。均值会被掩盖长尾，永远报 P50/P90/P99。

```
延迟 SLO 例: TTFT P99 < 500ms  且  TPOT P99 < 50ms
解读: 99%请求 0.5s 内见字, 且后续每字 ≤50ms(≈20 tok/s, 比人读快)
```

## 3. 吞吐指标：系统一秒干多少活

### 3.1 tokens/s（吞吐量，NLP 最核心）

**定义**：单位时间系统处理的 token 总数。注意区分两类：

- **输出吞吐 Output tokens/s**：服务能力指标，所有并发请求**生成** token 速率之和。
- **总吞吐 = (prompt + 输出) tokens/s**：含 prefill 的全量。

$$\text{tokens/s} = \frac{\sum \text{token 数}}{\text{墙钟时间}}$$

- **与单请求 TPOT 的关系**：系统输出吞吐 ≈ `并发请求数 × (1/TPOT)`。**这就是 batch 的威力**：单请求慢一点（TPOT↑一点），但并发多、总吞吐大涨。
- **怎么测**：固定并发压测，统计 `总输出 token / 总耗时`；扫不同并发画 **吞吐-延迟曲线**找拐点。
- **优化方向**：① **Continuous Batching / In-flight Batching**（vLLM、TGI，请求随到随入/完即出，不等齐）；② **PagedAttention** 提高显存利用以塞更大 batch；③ 张量/流水并行 [[ai-infra/算力/GPU工作原理]]；④ 量化腾显存换更大 batch。

### 3.2 samples/s（每秒样本数，训练侧吞吐）

$$\text{samples/s} = \frac{BS_{\text{global}}}{t_{\text{step}}} = \frac{BS_{\text{micro}} \times N_{\text{gpu}} \times \text{累积步数}}{t_{\text{step}}}$$

其中 $BS$ 为 batch size，$N_{\text{gpu}}$ 为卡数，$t_{\text{step}}$ 为一步（含前向+反向+优化器）墙钟时间。训练里也常折算成 **训练 tokens/s = samples/s × seq\_len**，便于和 6ND 公式对账。

### 3.3 QPS / RPS（每秒查询/请求数）

**定义**：单位时间系统处理完的**请求**数（Query/Request Per Second），面向"请求级"的服务容量。

$$QPS = \frac{\text{完成请求数}}{\text{时间}}$$

- 与 tokens/s 的区别：一个请求的 token 数差异极大（短问答 vs 长文生成），所以 **LLM 里 tokens/s 比 QPS 更稳健**；QPS 适合请求长度均匀的场景。
- 排队论视角（Little's 定律）：$L = \lambda W$，平均在系统请求数 = 到达率(QPS) × 平均停留时间(延迟)。延迟一涨，撑住同样 QPS 就要更多并发位 → 更多显存。

```
吞吐-延迟曲线 (服务调优的"心电图")
 延迟P99
   ▲                          ╱  ← 过载,延迟爆炸(SLO破)
   │                       ╱
   │                  ___╱   ← 拐点=最佳工作点
   │        ________╱
   │_______╱  ← 轻载,延迟平稳
   └───────────────────────────► 吞吐(QPS/tokens/s)
   目标: 贴着 SLO 红线跑在拐点附近, 既不浪费也不超时
```

## 4. 利用率指标：算力用上几成

### 4.1 MFU（Model FLOPs Utilization，模型算力利用率）

PaLM 论文提出的**金标准**。定义为：**真正用于模型前/反向的有效 FLOPS ÷ 硬件理论峰值 FLOPS**。

$$\boxed{MFU = \frac{6 \cdot N \cdot D / t_{\text{step}}}{N_{\text{gpu}} \cdot \text{Peak}_{\text{FLOPS}}}} = \frac{\text{有效算力}}{\text{理论峰值算力}}$$

- 分子用 $6ND$（只算"必要"的模型计算），**不含**重计算（recomputation）、padding 浪费等。
- **业界水平**：稠密大模型训练 MFU 通常 **35%～55%** 算优秀；>50% 已很硬核。
- **意义**：MFU=40% 意味着花的钱里只有 40% 变成"有用的模型计算"，其余被通信、空泡（pipeline bubble）、访存等待、kernel 没填满吃掉。

### 4.2 HFU（Hardware FLOPs Utilization，硬件算力利用率）

分子换成**硬件实际执行的全部 FLOP**，**包含**梯度重计算（activation checkpointing 会让前向算两遍）等"虽真实发生但非理论必需"的运算。

$$HFU = \frac{\text{硬件实际执行 FLOP}/t_{\text{step}}}{N_{\text{gpu}} \cdot \text{Peak}_{\text{FLOPS}}}$$

- **恒有 $HFU \ge MFU$**：因为 HFU 把"重复/冗余但真实跑了的算"也算进分子。
- 用激活重计算时，前向重算一次，多出约 1/3 计算 → HFU 比 MFU 高一截。
- **怎么用**：MFU 衡量"算法+系统总效率"（对外报这个）；HFU 衡量"硬件被填满的程度"（看 kernel/调度好不好）。二者差距大 → 重计算开销重，可考虑选择性重计算。

```
理论峰值算力 (100%)
├──────────────── 损耗 (通信/空泡/访存等待/kernel不满) ───────────────┤
│                                                                    │
├─ HFU: 硬件真跑的FLOP ─────────────────────┤
│                                          │
├─ MFU: 理论必需的FLOP(6ND) ──────┤  ↑这段差距 = 重计算等冗余
```

### 4.3 GPU Utilization（nvidia-smi 那个百分比）——最大的陷阱

`nvidia-smi` 的 "GPU-Util" 只表示**过去采样窗口内有 kernel 在跑的时间比例**，**不代表算力被填满**！

- 一个只用了 5% SM、纯搬数据的 kernel 一直在跑，GPU-Util 也显示 100%。
- 真正要看：**SM Occupancy / SM Active**、**Tensor Core 活跃比**、**DRAM 带宽利用**（用 Nsight Compute / DCGM / PyTorch Profiler）。
- **口诀：GPU-Util 100% ≠ MFU 高。** 解码阶段常 Util 100% 但 MFU 个位数（访存受限）。

### 4.4 显存利用率

= 已用显存 ÷ 总显存。推理服务追求"高显存利用"以容纳更大 KV-cache / batch；但要留余量防 OOM。PagedAttention 把 KV 显存碎片从 60%+ 浪费降到 <4%，就是冲这个指标去的。

## 5. 带宽指标：数据搬运的天花板

### 5.1 三种带宽

| 带宽类型           | 连接           | 量级(示意)        | 卡谁                          |
| ------------------ | -------------- | ----------------- | ----------------------------- |
| 显存带宽 (HBM)     | SM↔显存        | ~2～3 TB/s (A100/H100) | **解码 TPOT**、所有访存受限算子 |
| 卡间互联 (NVLink)  | GPU↔GPU(机内)  | ~600～900 GB/s    | 张量并行 all-reduce           |
| 节点间网络 (IB/RoCE)| 机器↔机器      | ~100～400+ Gb/s   | 数据并行梯度同步、流水并行     |

详见 [[ai-infra/算力/GPU工作原理]]。

### 5.2 带宽如何决定延迟（解码的命门）

解码每步必须把**全部权重 + 全部 KV-cache** 从 HBM 读一遍。所以单步时间下界：

$$t_{\text{step}} \gtrsim \frac{\text{Bytes}_{\text{权重}} + \text{Bytes}_{\text{KV}}}{\text{显存带宽}}$$

**这是 TPOT 的物理下界**，与算力无关——解释了量化（降 Bytes）为何直接提速、为何解码是 memory-bound。

### 5.3 MBU（Model Bandwidth Utilization）

类比 MFU 的带宽版：实际达到的有效带宽 ÷ 峰值带宽。解码场景常用 MBU（而非 MFU）评效率，>80% 算把带宽榨干了。

## 6. 训练侧专题：step time、扩展性

- **step time**：一个全局 batch 的端到端时间，= 前向 + 反向 + 梯度同步 + 优化器更新。它是 samples/s、MFU 的分母，**优化的核心抓手**。
- **强扩展（Strong Scaling）**：问题规模固定，加卡看 step time 是否成比例下降。理想 N 卡快 N 倍，实际因通信打折。
- **弱扩展（Weak Scaling）**：每卡负载固定，加卡看总吞吐能否线性增长。大模型预训练追求好的弱扩展。
- **扩展效率** $= \frac{\text{实测加速比}}{N} \times 100\%$。通信、pipeline 空泡、负载不均会拉低它。

```
加速比
   ▲     理想线性 (y=x)
   │    ╱
   │   ╱___ 实际(次线性,被通信吃掉)
   │  ╱ ╱
   │ ╱╱
   └────────────► GPU 数 N
   差距 = 并行损耗 → 反映在 MFU 下降
```

## 7. 一条龙手算（7B 模型，把公式代成数字）

设：模型 $N = 7\times10^9$ 参数，BF16（每参数 2 Byte），GPU 取 A100（峰值 312 TFLOPS，HBM 带宽 2 TB/s）。

### 7.1 推理：单步解码 TPOT 下界（访存受限）

权重访存量 = $7\times10^9 \times 2\text{B} = 14\text{ GB}$（先忽略 KV-cache）。

$$t_{\text{step}} \ge \frac{14\text{ GB}}{2\text{ TB/s}} = \frac{14}{2000}\text{ s} = 7\text{ ms}$$

→ 理论上限速率 $1/0.007 \approx 143$ tokens/s（单请求、单卡、batch=1）。实测会更慢（KV、kernel 开销），但**量级对**。这解释了为什么 7B 单请求生成约百 token/s。

**量化收益**：换 W4（每参数 0.5 Byte）→ 权重访存 3.5 GB → $t_{\text{step}} \ge 1.75$ ms → 理论 ~570 tokens/s，**约 4 倍**。这就是"量化直接提 TPOT"的来源。

### 7.2 推理：prefill 与 TTFT（算力受限）

prompt 长 $L=2048$。prefill FLOP $\approx 2ND = 2 \times 7\times10^9 \times 2048 \approx 2.87\times10^{13}$ FLOP。

$$t_{\text{prefill}} \ge \frac{2.87\times10^{13}}{312\times10^{12}} \approx 0.092\text{ s} = 92\text{ ms}$$

即 **TTFT 量级约 0.1 s**（理想算力满载）。prompt 翻倍 → TTFT 近似翻倍（注意力二次项会让长 prompt 更陡）。

### 7.3 训练：MFU 反推

设 8×A100 训练，全局 batch 处理 $D = 2^{20} \approx 1.05\times10^6$ tokens，实测 step time = 12 s。

有效算力 $= \dfrac{6ND}{t} = \dfrac{6 \times 7\times10^9 \times 1.05\times10^6}{12} \approx 3.67\times10^{15}$ FLOPS = 3.67 PFLOPS。

理论峰值 $= 8 \times 312\text{ TFLOPS} = 2496\text{ TFLOPS} = 2.496\text{ PFLOPS}$ …

等一下，分子 > 分母说明假设的 step time 偏小/不自洽。取更现实的 step time = 30 s：

有效算力 $= 6\times7\times10^9\times1.05\times10^6 / 30 \approx 1.47\times10^{15}$ FLOPS = 1.47 PFLOPS。

$$MFU = \frac{1.47}{2.496} \approx 0.59 = 59\%$$

→ 漂亮的 MFU。**手算的价值**：给定 step time 就能反推 MFU，判断系统是否健康（35%~55% 正常，过低查通信/空泡，过高复核是否漏算）。

### 7.4 系统吞吐 vs 单请求延迟

若服务 64 并发，每请求 TPOT = 30 ms（batch 摊带宽后比 batch=1 略慢）：

- 单请求速率 $= 1/0.03 \approx 33$ tokens/s（用户体感"够快"）。
- 系统输出吞吐 $\approx 64 \times 33 \approx 2100$ tokens/s（老板看的"吞吐"）。

**同一硬件，换个口径数字差 64 倍**——这就是为什么必须问清"你说的吞吐是单请求还是系统级"。

## 8. 面试问答清单（高频问→踩点答→追问）

**Q1. TTFT 和 TPOT 分别由什么决定？**
踩点：TTFT 由 prefill 决定，**算力受限**，随 prompt 长度增长；TPOT 由 decode 决定，**访存（显存带宽）受限**，随权重+KV 大小变化，对 batch 不敏感。
追问：为何 batch 增大 TPOT 几乎不变？→ 权重只搬一次给整批共用，解码 memory-bound，加 batch 是用"闲着的算力"换吞吐。

**Q2. 为什么解码慢但 GPU-Util 显示 100%？**
踩点：GPU-Util 只看"有没有 kernel 在跑"，不看算力是否填满。解码访存受限，Tensor Core 大量空转，MFU 个位数但 Util=100%。要看 SM Active / Tensor 活跃比 / MBU 才准。

**Q3. MFU 和 HFU 区别？为什么 HFU ≥ MFU？**
踩点：MFU 分子用理论必需的 $6ND$；HFU 分子用硬件真实执行的全部 FLOP（含重计算）。激活重计算让前向多跑一遍 → HFU 把这部分算进去 → HFU≥MFU。对外报 MFU（端到端效率），调 kernel 看 HFU。

**Q4. 怎么估一次训练要多少算力/多少卡时？**
踩点：$C \approx 6ND$。例 7B×300B tokens $= 6\times7\times10^9\times3\times10^{11} \approx 1.26\times10^{22}$ FLOP；除以"单卡峰值×MFU"即得卡秒。给数字、给 MFU 假设。

**Q5. 吞吐和延迟矛盾，服务怎么调？**
踩点：定 SLO（TTFT P99、TPOT P99）→ 压测画吞吐-延迟曲线 → 在不破 SLO 前提下增大并发/batch 找拐点 → 工具上用 Continuous Batching + PagedAttention + Chunked Prefill。报分位数不报均值。

**Q6. 量化为什么能提速？提的是哪个指标？**
踩点：解码访存受限，量化降权重/KV 的 Byte → 直接降 TPOT（带宽下界）。对 prefill（算力受限）收益小。所以 W4 主要提 TPOT/吞吐，对 TTFT 帮助有限。

**Q7. 哪些技术分别优化哪个指标？**（速记表）

| 指标   | 受限于 | 优化手段                                                |
| ------ | ------ | ------------------------------------------------------- |
| TTFT   | 算力   | Prefix Cache、Chunked Prefill、FlashAttention、降排队   |
| TPOT   | 带宽   | 量化(W/KV)、投机解码、MQA/GQA、KV 压缩                   |
| 吞吐   | 综合   | Continuous Batching、PagedAttention、并行、量化腾 batch |
| MFU    | 综合   | 减空泡(并行配比)、算子融合、选择性重计算、增大 micro-bs |

**陷阱清单**：① FLOP 与 FLOPS 混用；② 报均值不报 P99；③ 拿 GPU-Util 当利用率；④ 不分单请求/系统级吞吐；⑤ 忘了 KV-cache 也吃带宽和显存。

## 常见问题/高频追问

| 问题                                | 一句话答案                                                       |
| ----------------------------------- | ---------------------------------------------------------------- |
| TPOT 和 ITL 什么关系？              | ITL 是每对相邻 token 的实测间隔；TPOT 是 ITL 的平均/统计量。     |
| 为什么 LLM 报 tokens/s 不报 QPS？   | 请求 token 数差异大，tokens/s 更稳健公平；QPS 适合等长请求。     |
| 训练用 6ND，推理为何 2ND？          | 训练含反向(≈2×前向)，前向本身 2ND，合计约 6ND；推理只前向 2ND。  |
| MFU 50% 算好吗？                    | 稠密大模型训练 35%~55% 属优秀，>50% 很硬核。                     |
| 为什么 batch 大延迟反而升？         | 共享显存带宽被更多请求摊薄，单请求 TPOT 略升，但总吞吐大涨。     |
| 解码到底卡在哪？                    | 卡在 HBM 带宽：每步搬全部权重+KV，AI 极低 → memory-bound。       |
| 想压低 P99 尾延迟怎么做？           | Chunked Prefill 防长 prefill 阻塞、限并发、隔离长短请求、加副本。|
| GPU-Util 100% 还能更快吗？          | 能。Util≠满载，看 MFU/MBU/SM Active，多半是访存受限有提升空间。  |
