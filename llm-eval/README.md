## 0. 一句话锚点

评测要回答两个**正交**的问题：

- **精度（Precision / Quality）**：模型答得**对不对、好不好**？→ 准确率、pass@k、胜率、PPL、ROUGE…
- **性能（Performance / Efficiency）**：模型跑得**快不快、省不省**？→ 延迟、吞吐、显存、利用率（MFU）。

$$\text{评测} = \underbrace{\text{能力维度}}_{\text{考什么}} \times \underbrace{\text{判分方式}}_{\text{怎么打分}} \times \underbrace{\text{运行设置}}_{\text{shot/CoT/温度}}$$

> 一个模型可以「又准又慢」或「又快又笨」。**两类指标必须分开报、分开优化**，混在一起谈是评测里最常见的错误。

## 1. 地基：评测在量什么？为什么需要它

没有评测，模型迭代就是「拍脑袋」。评测给了三件东西：**可比较**（A 比 B 强多少）、**可复现**（换人换机结果一致）、**可定位**（强在知识、弱在推理）。

## 2. 五大能力维度：精度评测「考什么」

把模型能力切成五个稳定的维度，每个维度有自己的代表 benchmark 与判分逻辑。

```
┌─────────┬──────────────────────┬─────────────────┬────────────┐
│ 维度    │ 考什么                │ 代表 benchmark   │ 判分方式    │
├─────────┼──────────────────────┼─────────────────┼────────────┤
│ 知识    │ 背了多少事实/概念      │ MMLU C-Eval CMMLU│ 4选1 准确率 │
│ 推理    │ 多步逻辑/数学          │ GSM8K MATH BBH   │ exact match │
│ 代码    │ 写对能跑的程序         │ HumanEval MBPP   │ 跑单元测试  │
│ 对齐    │ 答得有用/合人类偏好    │ MT-Bench AlpacaEval│ 裁判/胜率 │
│ 安全    │ 说真话/拒答有害        │ TruthfulQA 红队  │ 分类/人评   │
└─────────┴──────────────────────┴─────────────────┴────────────┘
```

逐维拆解（**为什么这样判**）：

- **① 知识（Knowledge）**：4 选 1，随机猜基线 $=1/4=25\%$。所以**任何知识分都要减掉 25 的地板**才看出真水平。常用 logprob（比 4 个选项的对数似然）或生成+正则抽字母两条路线。
- **② 推理（Reasoning）**：答案唯一，靠 **exact match**（抽最终数字/表达式比对）。CoT（先写推理再答）对这类显著提分。
- **③ 代码（Code）**：**不比对文本**，而是把模型补全的函数丢进**隐藏单元测试**跑，全过才算对 → 度量「行为正确性」，用 **pass@k**。
- **④ 对齐（Alignment）**：「写封道歉邮件」没有标准答案 → 靠**裁判模型**或**人评**给相对好坏，输出胜率/分数（§3）。
- **⑤ 安全（Safety）**：是否说真话（TruthfulQA）、是否拒绝有害请求、是否有偏见/毒性（HELM 里 Toxicity/Bias/Fairness 指标）。多为分类或人工红队。

> 关键直觉：**五个维度互不可替代**。代码强不代表安全好，知识高不代表推理强。看单一数字 = 盲人摸象。

## 3. 三种判分方式：自动指标 vs 人评 vs 裁判模型

「怎么把答案变成分数」有三条路，成本、可扩展性、可信度各不同。

```
              自动指标         裁判模型(LLM-Judge)     人工评测
            ──────────       ──────────────────     ──────────
有无标准答案   必须有            不需要                 不需要
速度/成本     极快/几乎免费      快/中(调API)           慢/极贵
可扩展性      ✅ 百万级          ✅ 万级                ❌ 百级
主观题        ❌ 做不了          ✅ 能打                ✅ 金标准
可信度        高(对客观题)       中(有偏见)             最高(但有噪声)
确定性/可复现  ✅ 完全           ⚠️ 受采样/版本影响      ⚠️ 标注者间差异
```

### 3.1 自动指标（rule-based）
有标准答案时用规则直接判，覆盖 §2 的知识/推理/代码：

- **Accuracy / Exact Match**：选择题、填数题，对即 1。
- **pass@k**：代码，跑测试用例（§★ 手算）。
- **F1 / ROUGE / BLEU**：抽取式 QA、摘要、翻译，比对 n-gram 重叠（见 `llm-precision/`）。
- **困惑度 PPL（Perplexity）**：语言建模质量，$\text{PPL}=\exp\!\big(-\tfrac1N\sum\log p(w_i)\big)$，**越小越好**（每个词模型越「不意外」）。是少数**无需标准答案**的内禀指标。

### 3.2 人工评测（human eval）
人来打分/盲投，是**金标准**但贵且慢。典型形态：**Chatbot Arena** 真人两两盲投 → 算 **Elo 排名**。用于校准其他方法是否可信。

### 3.3 裁判模型（LLM-as-Judge）
用强模型（如 GPT-4）读两个回答，判「哪个更好/给 1~10 分」。解决了「主观题没标准答案 + 人评太贵」的矛盾。

```
┌──── LLM-as-Judge ────┐
│  题 →  A答    B答     │
│         │     │       │
│         ▼     ▼       │
│      裁判模型读两答    │
│   "哪个更好? 评分/选胜"│
│         ▼             │
│     A胜 / B胜 / 平    │
└───────────────────────┘
```

**裁判模型的已知偏见（必背）**：
- **位置偏见**：偏向先出现的答案 → 缓解：A/B 交换位置各跑一次取平均。
- **长度偏见**：偏向更长的回答 → AlpacaEval 2.0 做了长度控制（LC）。
- **自我偏好**：偏爱与自己同源/同风格的输出。
- **幻觉**：裁判自己在专业领域也会判错。

> 结论：裁判分适合**相对排序**，不宜当**绝对真值**；高风险场景仍需人工复核。三者关系：自动指标守客观题，裁判模型补主观题，人评做最终校准。

## 4. benchmark 地图：按维度铺开

```
                      ┌─────────── 精度 benchmark 全景 ───────────┐
 知识 ─┬─ MMLU (英,57学科,5-shot)
       ├─ MMLU-Pro (10选1,更难抗污染)
       ├─ C-Eval (中,52学科) / CMMLU (中,67学科)
       └─ AGIEval (高考/法考/SAT)
 推理 ─┬─ GSM8K (小学应用题, CoT)
       ├─ MATH (竞赛数学, LaTeX)
       └─ BBH (Big-Bench Hard, 23类硬任务)
 代码 ─┬─ HumanEval (164题, pass@k)
       ├─ MBPP (~974题, 更基础)
       └─ HumanEval+/MBPP+ (加测试,抗蒙混) / SWE-bench (真实仓库改 bug)
 对齐 ─┬─ MT-Bench (80多轮, 裁判 1~10分)
       ├─ AlpacaEval (805指令, 胜率)
       └─ Chatbot Arena (真人 Elo)
 长文本─┬─ NeedleBench (大海捞针) / LongBench / LV-Eval(256k)
 工具 ──┼─ ToolBench / BFCL (选对 API, 填对参数)
 指令 ──┼─ IFEval (严格遵守格式约束)
 安全 ──┴─ TruthfulQA / HELM(Bias/Toxicity) / 各类红队集
```

榜单分数会**饱和**：GSM8K、HumanEval 已被刷到很高、区分度下降 → 不断推出更难的新集（MATH、SWE-bench、MMLU-Pro）。**每个 benchmark 只是一个能力切片**，要看一组而非一个。详细判分（logprob/抽取/pass@k 公式/few-shot/CoT）见 [[llm-eval/大模型测评集]]。

## 5. 性能评测：另一条正交的轴

精度回答「对不对」，性能回答「快不快、省不省」。LLM 推理分两阶段，指标围绕它定义：

```
请求到达
  ├─[Prefill 预填充]─ 并行处理整段 prompt ─► 第1个token
  │      ↑ 这段 = TTFT 主体(算力受限)
  └─[Decode 解码]─► t2─►t3─►…─►tN (逐个吐)
         ↑ 相邻间隔均值 = TPOT(访存/带宽受限)
```

四类核心性能指标（详见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]）：

| 类 | 指标 | 度量 | 受限于 | 越…越好 |
|----|------|------|--------|--------|
| 延迟 | TTFT / TPOT / E2E | 等多久 / 每字多快 | 算力 / 带宽 | 越小 |
| 吞吐 | tokens/s / QPS | 一秒干多少活 | 综合 | 越大 |
| 利用率 | MFU / HFU / MBU | 算力用上几成 | 综合 | 越大 |
| 显存 | 显存占用/利用 | 装得下多大 batch | — | 看场景 |

关键关系：$E2E \approx TTFT + (N_{\text{out}}-1)\cdot TPOT$；系统吞吐 $\approx$ 并发数 $\times \tfrac{1}{TPOT}$。性能测量工具地图：vLLM benchmark、`llmperf`、`genai-perf`、TGI benchmark（压测）；`nvidia-smi`/DCGM/Nsight（利用率）；Locust/wrk（请求级压测）——均在 `llm-performance/` 下。

> 性能必谈**分位数**：报 P50/P90/**P99**（尾延迟是 SLO 红线），均值会掩盖长尾。

## 6. 性能 vs 精度：为什么是两类、绝不能混

这是面试与实战最易混的点。一句话：**优化精度的手段常常牺牲性能，反之亦然**。

```
                高精度
                  ▲
   慢但准 ◄───────┼───────► 快但准(理想区,难)
   (大模型/CoT)   │          (蒸馏+量化+好系统)
                  │
   慢且笨 ────────┼──────── 快但笨
   (最差)         ▼          (小模型/激进量化)
                低精度
        ◄───────────────────►
       低性能              高性能
```

- **量化（W4/W8）**：降访存 → **TPOT 提速**（性能↑），但可能掉点（精度↓）→ 必须**两类都测**：测速也测 PPL/benchmark 看掉多少。
- **CoT / 大 batch / 投机解码**：CoT 提精度但增延迟；大 batch 提吞吐但单请求 TPOT 略升。
- **结论**：发布一个模型/服务，**精度报告**（一组 benchmark）和**性能报告**（TTFT/TPOT/吞吐 @某并发）要**分别给、配套给**。只给一类 = 信息不完整。EvalScope 这类工具之所以同时支持「模型精度 + 推理性能」，正是因为生产上线必须两条线一起卡。

## 7. 数据污染（Data Contamination）

无论精度数字多漂亮，先问一句：**这题模型训练时见过吗？**

```
理想:  训练集 ∩ 测试集 = ∅
现实:  榜单题公开在 GitHub/HF → 被下一代训练语料爬走
       ┌────────┐   ┌────────┐
       │训练数据│███│测试题  │  ← 重叠区 = 污染 → 分数虚高
       └────────┘   └────────┘
```

**检测/缓解**：① n-gram 重叠扫训练语料；② 用训练截止后的**新题**（LiveBench、定期刷新）；③ 私有 **holdout** 不公开；④ 同义**改写**后看是否暴跌；⑤ MMLU-Pro 加选项/干扰降低「背」「蒙」收益。

> 面试金句：「某模型某榜单分异常高，第一反应是怀疑**污染或过拟合该榜单**，而非真能力。」

## 8. 评测框架与工具地图

不要手写判分逻辑，用成熟框架（统一数据加载、prompt 模板、judge）：

| 框架/平台 | 定位 | 特点 |

## ★ 数值例子/对照

### 例1：知识准确率要减基线
200 题 4 选 1 答对 138：$\text{Acc}=138/200=69\%$。减随机基线 25%：$\frac{0.69-0.25}{1-0.25}=\frac{0.44}{0.75}\approx 59\%$ —— 校正后比裸分 69% 清醒。

### 例2：代码 pass@k（无偏估计）
某题生成 $n=20$ 个候选、$c=4$ 个通过。$\text{pass@}k = 1-\binom{n-c}{k}/\binom{n}{k}$。
- $k=1$：$1-\binom{16}{1}/\binom{20}{1}=1-16/20=0.20$。
- $k=10$：$1-\binom{16}{10}/\binom{20}{10}=1-8008/184756\approx 0.957$。
- 直觉：单次仅 20%，抽 10 次蒙中概率 ~96% → **k 必须一并报告**。

### 例3：裁判模型胜率 + 去位置偏见
AlpacaEval 805 条，胜 510 负 250 平 45（平算 0.5）：$\text{WinRate}=\frac{510+0.5\times45}{805}\approx 66.1\%$。
若 A/B 不换位 A 胜 70%、换位后 52%，去偏后 $\approx\frac{70\%+52\%}{2}=61\%$（18 个点是位置偏见）。

### 例4：性能侧——TPOT 与系统吞吐（7B/A100 量级，约值，以官方为准）
权重 $7\times10^9\times2\text{B}=14$ GB，HBM 带宽约 2 TB/s：单步下界 $14/2000=7$ ms → 单请求约 143 tok/s（batch=1）。
64 并发、每请求 TPOT=30 ms：单请求 $1/0.03\approx33$ tok/s（用户体感），系统吞吐 $\approx 64\times33\approx 2100$ tok/s（老板看的）。**同硬件两个口径差 64 倍**——必问「单请求还是系统级」。

### 例5：困惑度
模型对 5 个词给概率 $\log p=[-0.5,-1.0,-0.7,-0.3,-1.5]$，均值 $=-0.8$：$\text{PPL}=e^{0.8}\approx 2.23$。值越小，建模越好。

## ▤ 常见问题（表格）

| 问题 | 一句话答案 |
|------|-----------|
| 精度评测和性能评测什么关系？ | 正交两类：一管「对不对」，一管「快不快」，分开报分开优化。 |
| 为什么不能只看一个 benchmark？ | 单集只测一个能力切片、会饱和、会被污染/过拟合（Goodhart）。 |
| 自动指标、人评、裁判模型怎么选？ | 客观题用自动指标；主观题用裁判模型（快但有偏见）；最终用人评校准。 |
| 裁判模型有哪些偏见？ | 位置（换位平均）、长度（LC 控制）、自我偏好、幻觉 → 只宜相对排序。 |
| MMLU 50 分算高吗？ | 不高。4 选 1 基线 25%，校正后约 33%。 |
| pass@k 为什么不是 c/n？ | 直接采 k 方差大，用 $n>k$、$c$ 正确的无偏估计；$k=1$ 时退化为 $c/n$。 |
| 量化提速会掉精度吗？ | 可能。所以量化后必须**两类都测**：测 TPOT 也测 benchmark/PPL。 |
| 数据污染怎么检测？ | n-gram 重叠、用训练截止后新题、私有 holdout、改写后看掉分。 |
| 性能为什么要报 P99？ | 均值掩盖长尾，P99 是 SLO 红线（尾延迟）。 |
| 上线前最终看什么？ | 贴合自身任务的私有评测集 + 真实业务 A/B，而非公开榜单裸分。 |
