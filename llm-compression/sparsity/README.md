## 0. 一句话锚点

> **剪枝 = 找出对输出影响最小的一批参数，把它们设为 0（或物理删除），从而减小模型体积、降低计算量。**

两个最容易混淆的词，先钉死：

- **稀疏化(Sparsify)**：把权重矩阵里很多元素变成 0，矩阵"变稀"。值还在那个位置，只是是 0。
- **剪枝(Prune)**：动作上的"剪掉"。**非结构化剪枝**剪完只是置零（矩阵形状不变）；**结构化剪枝**是真的把整行/整列/整个注意力头删掉（矩阵变小）。

记住一句话：**稀疏度(sparsity) = 零元素占比**。50% 稀疏度 = 一半权重是 0。

---

## 1. 地基：剪枝到底解决什么问题

大模型推理慢/贵，瓶颈无非三处。剪枝想同时打击它们：

```
            一次矩阵乘法 y = W·x 的成本
   ┌─────────────────────────────────────────────┐
   │  ① 显存占用   : 存 W 需要 行×列×字节           │
   │  ② 计算量(FLOPs): 行×列×2 次乘加               │
   │  ③ 访存带宽   : 把 W 从显存搬到计算单元        │
   └─────────────────────────────────────────────┘
                 │
       剪枝把 W 中一半元素变 0 ↓
                 │
   ┌─────────────────────────────────────────────┐
   │  ① 显存   : 只存非零值 + 索引 → 可能省一半     │
   │  ② 计算   : 跳过 ×0 → 理论 FLOPs 减半          │
   │  ③ 带宽   : 搬的数据少 → 解码瓶颈缓解          │
   └─────────────────────────────────────────────┘
```

关键洞察：LLM 推理在**自回归解码阶段是访存受限(memory-bound)** 的——每生成一个 token 都要把全部权重读一遍，瓶颈在"搬权重"而不是"算"。所以**把权重变小/变稀疏**往往比想象中更有效。

但有个陷阱：**置零 ≠ 加速**。如果硬件不会跳过 0，乘以 0 照样花一次乘法时间。这就引出了全篇的核心矛盾——

> **稀疏度高 → 理论收益大；但只有"硬件认识的稀疏模式"才能把理论变成真实加速。**

## 2. 三种剪枝粒度：非结构化 / 结构化 / 半结构化

这是整个领域最重要的分类。一张图说清：

```
原始权重矩阵 W (4×8)，每个 □=非零，·=被剪成 0

【非结构化 Unstructured】任意位置置零（50% 稀疏）
  □ · □ · · □ □ ·          自由度最高 → 精度损失最小
  · □ · □ □ · · □          但 0 的位置毫无规律
  □ □ · · · □ · □          → 通用 GPU 无法跳过 → 不加速(需特殊kernel)
  · · □ □ □ · □ ·          存储要额外存"哪里非零"的索引

【结构化 Structured】整行/整列/整头删除
  □ □ □ □ □ □ □ □          删掉第2、4行 → 矩阵真的变小(2×8)
  ▓ ▓ ▓ ▓ ▓ ▓ ▓ ▓ ←删       剩下的是稠密小矩阵
  □ □ □ □ □ □ □ □          → 任何硬件都加速！但精度损失大
  ▓ ▓ ▓ ▓ ▓ ▓ ▓ ▓ ←删       (删掉的整行可能含有用信息)

【半结构化 Semi-structured / N:M】每M个里固定剪N个
  □ · · □ | □ · □ ·          这里是 2:4 → 每4个连续权重恰好2个0
  · □ □ · | · □ · □          位置受约束但仍有局部自由
  □ □ · · | · · □ □          → NVIDIA Sparse Tensor Core 原生支持
  · · □ □ | □ □ · ·          → 真加速 + 精度损失适中(折中方案)
```

**对照三者的本质权衡**：

```
精度损失:   非结构化 < 半结构化(2:4) < 结构化
真实加速:   非结构化 < 半结构化(2:4) < 结构化(任意硬件)
                      ↑
            2:4 是工业界甜点：既有专用硬件加速，精度又比结构化好
```

- **非结构化**：自由度最高，掩码(mask)可以是任意 0/1。精度最好保，但**0 散落各处，普通稠密 GEMM kernel 不会跳过**，所以在标准 GPU 上**不加速**（甚至因为要存索引而更慢）。需要专门的稀疏 kernel（如 DeepSparse CPU 引擎、cuSPARSELt）才能兑现收益。
- **结构化**：直接删掉整个"结构单元"（一行、一列、一个注意力头、一个 FFN 中间维度、甚至一整层）。删完矩阵物理变小，**稠密计算直接受益，任何硬件都加速**。代价是粒度粗 → 容易误删有用信息 → 精度掉得多 → 通常**必须配合再训练/蒸馏恢复**。
- **半结构化(N:M)**：折中。约束"每连续 M 个权重里恰好 N 个为 0"。最常用的是 **2:4**（50% 稀疏），因为 NVIDIA Ampere(A100) 之后的 GPU 在硬件上原生支持它。

## 3. 2:4 半结构化稀疏与硬件加速（重点）

### 3.1 什么是 2:4

把权重按"每 4 个连续元素"分组，**强制每组里有且只有 2 个是 0**（即 50% 稀疏，但 0 的分布被约束）。

```
一组 4 个权重           压缩存储
[ w0  0  w2  0 ]  ──►   值: [w0, w2]      只存 2 个非零值
                        索引: [00, 10]    2-bit 标记"原来在第几位"

为什么是 2-bit？4 个位置选 1 个 → 需 log2(4)=2 bit。
每组省一半值，只多 4-bit 元数据 → 净省接近一半显存。
```

### 3.2 硬件为什么能加速：Sparse Tensor Core

普通 Tensor Core 做稠密矩阵乘。**Sparse Tensor Core（Ampere 起）** 内建了对 2:4 的支持：

```
稠密 GEMM (Dense Tensor Core)
  A(密) × B(密) → 全部乘加，吞吐 = 1×

2:4 稀疏 GEMM (Sparse Tensor Core)
  A(2:4稀疏，压成一半) × B(密)
        │
        ▼  硬件读 2-bit 索引，自动从 B 里"挑出"对应的行
  ┌──────────────────────────────┐
  │ 只把非零值喂进乘加阵列         │
  │ 跳过的那 50% 乘法根本不发生    │
  └──────────────────────────────┘
        │
        ▼
  理论吞吐 ≈ 2×（峰值；实际 1.3~1.7×，受访存/其他层限制）
```

核心机制：**硬件用那 2-bit 索引做"列选择(column selection)"**，在把数据送入乘加阵列前就把对应的 0 跳过。所以这不是"算了再扔"，而是"压根不算"——这才是真加速。

> 同类硬件支持：NVIDIA `cuSPARSELt` / TensorRT 提供 2:4 推理；`torch.sparse` 的 semi-structured 也封装了它。具体 API 与开关以官方文档为准。

### 3.3 数据流全景

```
W → ①选mask(每4选2该剪) → W_sparse → ②可选微调恢复精度
  → ③压缩存储(值+2-bit索引) → Sparse Tensor Core 推理 ~2×峰值
```

## 4. 幅度剪枝(Magnitude Pruning)：最朴素的基线

### 4.1 核心思想

**绝对值越小的权重越不重要**。直接按 $|w|$ 排序，把最小的一批置零。

$$\text{重要度}(w_{ij}) = |w_{ij}|, \quad \text{剪掉重要度最小的 } s\% \text{ 个}$$

直觉：$y = \sum_i w_i x_i$，若某 $w_i \approx 0$，它对输出 $y$ 的贡献本来就小，删了影响不大。

```
某一行权重: [ 0.8, -0.05, 0.6, 0.02, -0.9, 0.01, 0.7, -0.03 ]
                    ↑剪          ↑剪        ↑剪          ↑剪
取 |w| 最小的 4 个(50%稀疏) → 置零:
            [ 0.8,  0,   0.6,  0,  -0.9,  0,  0.7,  0   ]
```

### 4.2 为什么"够用但不最优"

- **优点**：零成本，不需要数据，不需要梯度，一行代码搞定。
- **缺点**：只看权重大小，**没看输入激活的分布**。一个权重虽小，但若它对应的输入特征 $x_i$ 经常很大，那 $w_i x_i$ 未必小——幅度剪枝会误删它。这正是 Wanda 要改进的点。

---

## 5. Wanda：激活感知的幅度剪枝

> 论文：Pruning by Weights **and** Activations，https://arxiv.org/abs/2306.11695

### 5.1 一个关键改进

幅度剪枝只看 $|w|$。Wanda 把**输入激活的尺度**也乘进来：

$$\text{重要度}_{ij} = |w_{ij}| \cdot \|x_j\|_2$$

其中 $\|x_j\|_2$ 是第 $j$ 个输入特征在一小批校准数据上的 L2 范数（"这个特征平时有多大"）。

```
为什么乘激活范数？
  输出贡献 ≈ w_ij · x_j
  权重小但输入大 → 实际贡献可能不小 → 不该剪
  权重大但输入恒为0 → 实际没贡献 → 可以剪

幅度剪枝:  只看  |w|        ❌ 漏看输入
Wanda  :  看 |w|·‖x‖      ✅ 兼顾权重与激活
```

### 5.2 流程

```
跑几十条校准样本 → 统计每个输入特征的 ‖x_j‖2
        │
        ▼
逐"输出"为单位(per-output)比较重要度，剪掉每行最小的 s%
（不更新剩余权重，纯置零）
        │
        ▼ 几乎零成本，无需反向传播、无需求逆
得到稀疏模型（可直接做 2:4）
```

**定位**：Wanda 比幅度剪枝准，又比 SparseGPT 便宜（不用算 Hessian、不更新权重）。是"简单又有效"的代表。

## 6. SparseGPT：一次性(one-shot)高质量剪枝

> 论文：https://arxiv.org/pdf/2301.00774

### 6.1 它解决什么

幅度剪枝/Wanda 剪完就完了——**剩下的权重不动**，所以高稀疏度(如 50%+)时精度会塌。SparseGPT 的杀手锏：**剪掉一些权重后，调整剩余权重去补偿被剪掉的那部分造成的输出误差**。而且**不需要重新训练**，一次前向 + 求解就搞定（one-shot）。

### 6.2 核心机制：把剪枝当成"逐层重建"问题

对每一层，目标是：剪枝后的输出尽量接近原输出。形式化为最小化重建误差：

$$\min_{\widehat{W}} \; \| W X - \widehat{W} X \|_2^2 \quad \text{s.t. } \widehat{W} \text{ 满足稀疏约束}$$

- $X$：校准数据在该层的输入（一批样本）。
- $\widehat{W}$：剪枝并补偿后的权重。

这是个带约束的最小二乘。关键工具是**输入的二阶信息（Hessian）**：

$$H = X X^\top$$

它描述"各输入维度之间的相关性"。利用 $H$ 可以算出：**剪掉权重 $w_q$ 后，应该怎样调整其它权重来把误差补回来**。这套思路继承自经典的 OBS(Optimal Brain Surgeon) 和量化里的 GPTQ。

```
逐列(逐权重组)处理，边剪边补偿：

  for 每一列 q（从左到右）:
    ① 用 H 算每个权重的"剪枝代价"，挑出该剪的
    ② 置零这些权重
    ③ 把误差按 H 的逆"扩散"到右边还没处理的列，更新它们
       └─ 这一步就是"补偿"：剩余权重微调，吃掉被剪的损失
    ④ 移到下一列

  整层处理完 → 输出几乎不变，但已达到目标稀疏度
```

### 6.3 ASCII：剪 + 补偿

```
原始一行: [0.8 0.3 0.6 0.2]   剪掉 0.3、0.2(代价最小)
 朴素(Wanda): [0.8  0  0.6  0]  ← 直接丢，留误差
 SparseGPT : [0.85 0  0.64 0]  ← 微调剩余权重吃掉误差 → 重建误差大降
                ↑增     ↑增
```

### 6.4 代价与定位

- 需要求解涉及 $H^{-1}$ 的运算，比 Wanda 重，但 SparseGPT 用了高效近似（按列分块、Cholesky 等），**对百亿级模型也能在数小时内单卡跑完**，无需反向传播。
- **定位**：在高稀疏度（50%、2:4、甚至更高）下，SparseGPT 通常比幅度/Wanda 精度更好，是"无再训练高质量剪枝"的代表。

## 7. OWL：分层稀疏度分配（Outlier Weighed Layerwise Sparsity）

> 论文：https://arxiv.org/pdf/2310.05175

前面的方法默认**每一层都剪同样比例**（如全都 50%）。OWL 指出：这不公平。

```
观察：LLM 里存在"离群激活(outlier)"——少数特征数值巨大，对性能至关重要。
      不同层的离群点数量不同。

OWL 思路：
  离群点多的层 → 更敏感 → 少剪一点(低稀疏度)
  离群点少的层 → 更鲁棒 → 多剪一点(高稀疏度)
        │
        ▼  保持全局平均稀疏度不变，但按层重新分配
  整体稀疏度相同，精度却明显更好（尤其高稀疏度时）
```

OWL 是个**正交的增强**：它只决定"每层剪多少"，具体怎么剪可以用 Wanda 或 SparseGPT。即 `OWL + Wanda`、`OWL + SparseGPT`。

## 8. 结构化剪枝与 LLM-Shearing

> LLM-Shearing：https://github.com/princeton-nlp/LLM-Shearing ，https://arxiv.org/pdf/2310.06694.pdf

非结构化稀疏要靠特殊硬件/kernel才加速。**结构化剪枝直接删整个结构单元，物理上变小，任何硬件都受益。**

### 8.1 LLM 里可删的"结构单元"

```
Transformer 一个 Block
 ┌────────────────────────────────────────┐
 │  Multi-Head Attention                   │
 │   head1 head2 head3 head4  ← 可整头删除 │
 │   每个 head 的 Q/K/V 维度  ← 可减       │
 ├────────────────────────────────────────┤
 │  FFN: x→[Linear d→4d]→act→[4d→d]        │
 │        中间维度 4d 可砍   ← 删神经元    │
 ├────────────────────────────────────────┤
 │  整个 Layer 也能删 ← 减层数(depth)      │
 └────────────────────────────────────────┘
   还能减 hidden size d ← 减宽度(width)
```

### 8.2 LLM-Shearing：从大模型"剪"出小模型

核心不是简单删一刀，而是**学一组结构掩码(mask)，端到端地决定剪哪些 head/维度/层**，再用少量数据继续训练让小模型恢复性能。还引入**动态批量加载(dynamic batch loading)**，按各领域损失自动调采样比例，加速恢复。

```
大模型(如 LLaMA-7B)
   │ ① 学结构掩码：哪些 head/中间维/层该删
   ▼
中等模型骨架(如 ~1.3B / 2.7B)
   │ ② 继续预训练(蒸馏/数据加权)恢复精度
   ▼
小而稠密的模型 → 任何硬件直接加速，无需稀疏 kernel
```

**权衡**：结构化剪枝精度损失天然更大（删的是粗粒度结构），所以**几乎必然要再训练**，成本比 one-shot 的 SparseGPT/Wanda 高得多；但换来的是**对部署最友好**——产物就是个普通的小稠密模型。

## 9. 为什么能加速 + 精度如何恢复（汇总）

### 9.1 加速从哪来——按粒度对号入座

```
非结构化:   只是置零 → 通用 GPU 不跳零 → ❌不加速
            需 cuSPARSELt / DeepSparse 等专用稀疏 kernel 才提速
2:4 半结构: 硬件(Sparse Tensor Core)用2-bit索引跳过0 → ✅~2×峰值
结构化:     矩阵物理变小，稠密计算量直接减少 → ✅任何硬件都加速
```

一句话：**加速 = "硬件真的少干了活"**。置零不等于少干活，除非硬件/kernel 认识这个稀疏模式并跳过 0。

### 9.2 精度恢复的三条路

```
① 一次性补偿(SparseGPT)：剪的同时微调剩余权重 → 无需训练，高稀疏度也稳
② 选得更准(Wanda/OWL)  ：用激活/离群信息选更该剪的权重，少误伤
③ 再训练/蒸馏          ：剪完用数据继续训(结构化剪枝几乎必须)
                         └─ LLM-Shearing 即此路，恢复最彻底但最贵
```

恢复力度排序（越往右越费，但精度越保得住）：
`纯幅度剪枝 < Wanda < SparseGPT(补偿) < 剪枝+微调 < 剪枝+完整再训练`

## 数值例子 / 典型场景

**例 1：2:4 稀疏的显存与吞吐手算**

设一层权重 $W$：行=4096，列=4096，FP16(2字节)。

- 稠密存储：$4096 \times 4096 \times 2 = 33{,}554{,}432$ 字节 ≈ **32 MiB**。
- 2:4 稀疏：只存一半非零值 + 每组 2-bit 元数据：
  - 值：$32\text{ MiB} \times 0.5 = 16$ MiB
  - 元数据：每 4 个权重 2-bit → 每权重 0.5-bit → $4096\times4096\times0.5/8 = 1$ MiB
  - 合计 ≈ **17 MiB**，省约 **47%**。
- 吞吐：理论峰值 2×；实际因为还有 LayerNorm、激活、KV-cache 访存等非稀疏部分，端到端常见 **1.3~1.7×**。

**例 2：FLOPs 直觉**

一次 $y = Wx$（$W$ 为 $n\times n$）稠密需 $2n^2$ 次乘加。50% 稀疏理论上跳过一半乘法 → $\approx n^2$。但只有当硬件真跳过时才兑现——非结构化在普通 GPU 上 FLOPs 没省到（照样乘 0）。

**例 3：场景化选择**

- 你有 A100/H100，想"零再训练"提速且容忍小精度损失 → **SparseGPT + 2:4**，导出给 cuSPARSELt/TensorRT。
- 你要把 7B 压成 2.7B 部署到任意卡、且有算力再训练 → **LLM-Shearing 结构化剪枝 + 继续预训练**。
- 你只想快速试水、无校准数据 → **幅度剪枝** 做基线；有少量校准数据 → 升级 **Wanda**。

## 常见问题

| 问题 | 解答 |
|---|---|
| 置零了为什么不变快？ | 普通稠密 GEMM 不会跳过 0，乘 0 照样花一次乘法。要么用专用稀疏 kernel(非结构化)，要么用 2:4(硬件支持)，要么结构化让矩阵真变小。 |
| 50% 稀疏一定省一半显存吗？ | 非结构化要额外存"非零位置索引"，省不到一半；2:4 索引只 2-bit/组，接近省一半；结构化直接删，确定省。 |
| Wanda 和 SparseGPT 选哪个？ | 要省事/省算力选 Wanda；要高稀疏度下更高精度、且能承担 Hessian 计算选 SparseGPT。 |
| 2:4 为什么是 50% 而不是更高？ | 因为 N:M 中 2:4 是当前 NVIDIA 硬件原生支持的模式；更高稀疏(如 1:4=75%)目前没有等价的通用硬件加速。 |
| 剪枝和量化能叠加吗？ | 能。常见组合"剪枝(2:4) + INT8/INT4 量化"，显存和算力双重受益；但要注意误差累积，建议先量化敏感性分析。 |
| 离群点(outlier)为什么重要？ | LLM 少数特征数值极大却关键，剪枝/量化误伤它们精度会崩。OWL 据此给敏感层降稀疏度，量化里也有专门保护离群点的做法。 |
| 一次性(one-shot)是什么意思？ | 不用梯度反传、不用完整再训练，跑几十条校准样本做一次前向 + 求解即得稀疏模型(Wanda/SparseGPT 都是)。 |
