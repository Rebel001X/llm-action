## 0. 一句话锚点

> **llm-compressor = 一个把"剪枝/量化算法"封装成可声明的 `Modifier`，用 `recipe`（YAML/Python）编排，靠 `oneshot()` 在少量校准数据上一次性跑完，并以 `compressed-tensors` 格式存盘、被 vLLM 直接加载的压缩库。**

三个名词钉死：

- **Modifier（修饰器）**：一个算法的封装。剪枝相关的有 `SparseGPTModifier`、`WandaPruningModifier`、`MagnitudePruningModifier`、`ConstantPruningModifier`。
- **recipe（配方）**：一段声明式配置，说明"在哪几个阶段、对哪些层、用哪个 Modifier、目标稀疏度多少"。
- **oneshot / apply**：执行入口。`oneshot()` 跑一次性（无需训练）的 Modifier；`apply()/compress()` 跑包含训练阶段的完整多阶段 recipe。

---

## 1. 地基：它解决什么问题

剪枝的学术算法（SparseGPT、Wanda）论文里是一堆零散脚本，落地有三道坎，llm-compressor 就是来填这三道坎的：

```
研究脚本的痛点                      llm-compressor 的答案
─────────────────────────────────────────────────────────
1. 算法各写各的接口         →   统一成 Modifier，参数语义一致
2. 剪完的稀疏权重没人认     →   存成 compressed-tensors 格式
3. 剪枝+量化要手工拼        →   一个 recipe 里多 Modifier 串联
4. 大模型放不进单卡做校准   →   分层/分块校准，逐层释放显存
```

一句话：**它把"会剪枝"变成"能上线"**。剪枝的本质收益在 [[llm-compression/sparsity/README]] 已讲透（省显存/省带宽/省算力），这里只关心**工具怎么把它做出来**。

## 2. 整体架构与核心模块

```
                    ┌─────────────────── recipe (YAML / Python) ───────────────────┐
                    │  stage: [ Modifier_A(start,end,targets,sparsity...), ... ]     │
                    └───────────────────────────────┬───────────────────────────────┘
                                                     │ 解析
                          ┌──────────────────────────▼──────────────────────────┐
   入口 oneshot()/apply() │              Session / Lifecycle 调度               │
                          │  initialize → (校准前向) → on_layer → finalize      │
                          └───┬───────────────┬───────────────┬────────────────┘
                              │               │               │
                     ┌────────▼─────┐  ┌──────▼──────┐  ┌──────▼───────────┐
                     │ Pruning      │  │ Quantization│  │ DataPipeline      │
                     │ Modifiers    │  │ Modifiers   │  │ (校准数据流/hook) │
                     │ SparseGPT…   │  │ GPTQ/FP8…   │  │ sequential 等     │
                     └──────┬───────┘  └──────┬──────┘  └──────────────────┘
                            │                 │
                     ┌──────▼─────────────────▼──────┐
                     │       compressed-tensors       │  ← 稀疏/量化的统一存储格式
                     │  (sparse-bitmask / 2of4 / pack)│
                     └────────────────┬───────────────┘
                                      ▼
                            save_pretrained() → 模型目录 → vLLM 加载
```

核心模块逐个看：

- **Modifier**：算法主体。剪枝家族见第 3-5 节。所有 Modifier 都有 `start/end`（作用的阶段/步数）、`targets`（作用到哪些层）、`ignore`（排除哪些层）这套通用骨架。
- **recipe**：把多个 Modifier 按阶段排好。声明式，不写循环。
- **oneshot()**：对 LLM 最常用。无需反向传播，只跑前向校准，逐层完成剪枝/量化。注意：`oneshot()` 是 `compress()` 的别名/特化，**只运行一次性（oneshot）Modifier**；若 recipe 里含训练阶段，必须用 `apply()/compress()` 跑全部阶段。
- **compressed-tensors**：序列化层。非结构化稀疏存成 bitmask（位掩码 + 非零值），2:4 存成专用的 packed 格式，量化则 pack 进低位整数。

## 3. 稀疏化粒度：非结构化 vs 2:4 半结构化

这是剪枝最先要选的旋钮，由 Modifier 的 `mask_structure` / 隐含模式决定。

```
非结构化 (unstructured)               2:4 半结构化 (semi-structured)
每个 0 的位置任意                       每连续 4 个权重里恰好 2 个为 0
┌─┬─┬─┬─┬─┬─┬─┬─┐                     ┌─┬─┬─┬─┐ ┌─┬─┬─┬─┐
│w│0│w│w│0│0│w│0│  …自由              │w│0│0│w│ │0│w│w│0│  …每组定额
└─┴─┴─┴─┴─┴─┴─┴─┘                     └─┴─┴─┴─┘ └─┴─┴─┴─┘
精度高，但硬件难加速                    精度略低，但 NVIDIA Sparse
（无规则→需 bitmask）                   Tensor Core 可 2× 吞吐
```

- **非结构化**：`sparsity: 0.5`，不写 `mask_structure`（或留空）。理论精度最好，但 GPU 没有原生指令利用任意稀疏，多数情况下只省显存/带宽，**算力不一定加速**。
- **2:4 半结构化**：`mask_structure: "2:4"`，固定 50% 稀疏。每 4 个权重保留 2 个，配 4-bit 元数据记录"留的是哪两个"。这是 Ampere（A100）及以后 Sparse Tensor Core 能直接吃的格式，矩阵乘可达约 2× 加速。这也是 llm-compressor 剪枝在 vLLM 上加速的**主路径**。

数值例子：一个 $4096\times4096$ 的 Linear，FP16 约 $4096^2\times2 \approx 33.5\text{MB}$。2:4 稀疏后保留一半非零值 + 元数据，存储约降到 $\sim 50\%+$ 少量元数据开销 $\approx 18\text{MB}$，且乘法吞吐翻倍。

## 4. SparseGPT：一次性高质量剪枝的机制

SparseGPT（IST-DASLab，arXiv:2301.00774）是 llm-compressor 里**质量最高的一次性剪枝器**，对应 `SparseGPTModifier`。它不是简单"砍小权重"，而是**砍完还补偿误差**。

核心思想：逐层、逐列处理。对某层权重 $W$ 与校准输入 $X$，剪枝后要让输出 $WX$ 变化最小。它用输入的二阶信息（近似 Hessian $H = XX^\top + \lambda I$）来决定剪谁、并把被剪权重的"账"摊到还活着的权重上。

```
逐列扫描权重矩阵 W (一层)：
  for 每个 block (block_size 列):
      1. 用 H^{-1} 的对角衡量每个权重的"剪掉代价"
      2. 按 mask_structure(如 2:4) 在组内挑要剪的
      3. 把剪掉权重的误差，用 H^{-1} 补偿到剩余列   ← 关键！别人没有
      4. 更新 H^{-1}（去掉已处理列）
```

- $H$ 的对角阻尼项 $\lambda$ 由 `dampening_frac` 控制（如 0.001），防止 $H$ 不可逆导致数值爆炸。值越大越稳但越粗糙。
- `block_size`（如 128）：一次处理多少列。大→更准但更慢更吃显存；小→反之。
- 误差补偿这一步是 SparseGPT 比纯幅度剪枝精度高的根本原因：它"剪一个、调一片"，而不是"剪完就走"。

关键 recipe 字段：

```yaml
SparseGPTModifier:
    sparsity: 0.5
    mask_structure: "2:4"      # 不写则为非结构化
    dampening_frac: 0.001      # Hessian 阻尼
    block_size: 128            # 分块列数
    targets: ['Linear']        # 只剪线性层
    ignore: ['re:.*lm_head']   # 排除输出头（敏感，正则匹配）
```

## 5. Wanda 与 Magnitude：两个更轻的剪枝器

**MagnitudePruningModifier（幅度剪枝）**：最朴素，**只看 $|w|$**，把绝对值最小的一批置零。不需要校准数据、不需要前向，最快最省，但精度最差。它支持稀疏度逐步爬升（`init_sparsity → final_sparsity`），常用于训练循环中渐进剪枝：

```yaml
MagnitudePruningModifier:
    start: 5
    end: 10
    init_sparsity: 0.1         # 起步只剪 10%
    final_sparsity: 0.5        # 逐步爬到 50%
    targets: __ALL_PRUNABLE__  # 所有可剪层
```

**WandaPruningModifier（Wanda，arXiv:2306.11695）**：介于两者之间。它在幅度上**乘以输入激活的范数**作为重要性度量：

$$ \text{score}_{ij} = |W_{ij}| \cdot \lVert X_j \rVert_2 $$

直觉：一个权重重不重要，不光看它自己大不大，还要看它**喂进来的激活强不强**。激活几乎为 0 的输入通道，对应权重再大也没用。Wanda 需要少量校准数据（拿激活范数），但**不做误差补偿**，所以比 SparseGPT 快很多、精度介于 Magnitude 与 SparseGPT 之间。

```
三者一句话对比：
  Magnitude :  剪 |w| 最小者                  —— 无需数据，最快，最糙
  Wanda     :  剪 |w|·‖x‖ 最小者              —— 需校准，居中
  SparseGPT :  剪 + 用 Hessian 补偿误差        —— 需校准，最慢，最准
```

实践默认：**追求精度选 SparseGPT，追求速度/无数据选 Wanda/Magnitude**。

## 6. 剪枝调用链（请求生命周期）

以 `oneshot()` 跑 SparseGPT 2:4 为例，看一次剪枝从入口到落盘发生了什么：

```
oneshot(model, dataset, recipe, ...)
   │
   ├─ 1. 解析 recipe → 实例化 SparseGPTModifier
   │
   ├─ 2. initialize：给 targets 命中的每个 Linear 挂 forward hook
   │
   ├─ 3. 校准前向：把 dataset 的少量样本喂进模型
   │       hook 累积每层的输入统计  X → 攒出 H = XXᵀ
   │       （sequential pipeline 下逐层算、逐层放，省显存）
   │
   ├─ 4. on_layer / compress：对每层执行
   │       逐 block 列 → 按 2:4 选剪 → H⁻¹ 误差补偿 → 写回 W
   │
   ├─ 5. finalize：卸载 hook，得到稀疏化后的 model
   │
   └─ 6. save_pretrained：以 compressed-tensors 存盘
           ├─ 2:4 → packed 半结构化格式 + 元数据
           └─ 非结构化 → sparse-bitmask 格式
```

要点：

- **校准数据很少就够**（量级是几百条样本），因为只用来估激活统计/Hessian，不是训练。
- **sequential / layer-sequential pipeline** 是大模型能在单卡剪枝的关键：一次只把一层的统计放显存，处理完即释放，峰值显存接近"单层"而非"全模型"。
- 整个过程**没有反向传播**，所以叫 oneshot——这也是它和量化感知训练（QAT）的本质区别。

## 7. 与量化组合（剪枝 + 量化）

剪枝省的是"零的位置"，量化省的是"每个非零值的位宽"，两者正交，叠加收益最大。llm-compressor 的卖点之一就是在**一个 recipe 里串起来**。

```
原始 FP16 权重
   │  ① 稀疏化 (SparseGPT 2:4)        → 一半权重为 0
   ▼
2:4 稀疏 FP16
   │  ② 量化 (GPTQ / FP8，仅压非零值) → 非零值降到 4/8-bit
   ▼
稀疏 + 量化  (如 "2of4 + W4A16")      → 体积 ≈ 1/2 × 1/4 + 开销
```

组合时的关键点：

- **顺序**：通常**先剪枝、后量化**（或在同一 recipe 的后续 stage 量化），让量化只处理保留下来的非零值。
- **保持稀疏不被量化破坏**：这就是 `ConstantPruningModifier` 的用途——**它本身不剪枝，只是在后续阶段把已有的零"钉住"**，防止量化/微调时零位置被重新写入非零值：

```yaml
# 阶段1：先用 SparseGPT 剪出 2:4
# 阶段2：量化时用 ConstantPruning 保持稀疏结构不变
ConstantPruningModifier:
    start: 0
    end: 5
    targets: __ALL_PRUNABLE__   # 仅维持已有稀疏 mask
```

- 多阶段（含训练）的 recipe 必须用 `apply()/compress()` 而非 `oneshot()`，因为 `oneshot()` 只跑一次性阶段。
- 存储格式由 compressed-tensors 同时承载稀疏 mask + 低位整数 pack，vLLM 端能识别这个组合标记。

## 8. 精度恢复

剪掉一半权重必然掉点，恢复手段从轻到重：

```
掉点小 ──────────────────────────────────► 掉点大
 SparseGPT(自带补偿) < 提高校准数据质量
   < 稀疏感知微调(SFT, 冻结零位置)
     < 知识蒸馏(用原模型当 teacher)
```

- **算法自带**：SparseGPT 的误差补偿本身就是第一道精度恢复，所以同稀疏度下它优先。
- **微调恢复（关键）**：剪完后在下游/通用数据上继续训练，但**必须用 ConstantPruningModifier 把零位置冻住**，否则梯度会把被剪权重又训回非零，稀疏化前功尽弃。这是一个 `apply()` 多阶段 recipe（一个剪枝 stage + 一个带 ConstantPruning 的训练 stage）。
- **蒸馏**：把未剪枝的原模型作为 teacher，让稀疏 student 对齐其 logits/中间表示，恢复效果更好但成本更高。
- **经验**：2:4 在 7B 量级上配 SparseGPT + 少量微调，常能把困惑度损失压到可接受范围；越大的模型对剪枝越鲁棒。

## 9. 在 vLLM 上加速

剪枝最终要变成"更快"，落点在 vLLM。逻辑链：

```
compressed-tensors 模型目录
   │  config 标注 sparsity_config: 2of4 (+ 可选量化)
   ▼
vLLM 加载时识别格式
   │
   ├─ 2:4 半结构化 → 调用 Sparse Tensor Core 内核
   │                   (Ampere+，稀疏 GEMM ≈ 2× 算力)
   │
   └─ 非结构化     → 主要省显存/带宽，
                      算力加速依赖具体内核支持，常无 2× 收益
```

要点与权衡：

- **真正吃到算力加速的是 2:4**，因为它能映射到硬件的稀疏矩阵乘指令；非结构化在 vLLM 上更多是"省显存让你能塞更大 batch / 更长上下文"，而非单步变快。
- 加速依赖硬件代际与内核：**Sparse Tensor Core 是 Ampere(A100) 起的特性**，旧卡（如 V100）无此能力，剪枝只剩显存收益。
- 与量化叠加时（如 2of4 + W4A16），加速来自"稀疏 + 低位"两层，但内核需同时支持该组合——是否命中加速路径**以 vLLM 当前版本对该 compressed-tensors 组合的内核支持为准**。
- 实测建议：剪枝后务必在 vLLM 上跑端到端基准（吞吐/延迟）对比，因为加速强依赖序列长度、batch、矩阵形状是否对齐稀疏内核要求。

## 典型流程 / 配置示例（讲含义）

**A. 一次性 2:4 剪枝（最常见，oneshot）**

```python
from llmcompressor import oneshot
from llmcompressor.modifiers.pruning import SparseGPTModifier

recipe = SparseGPTModifier(
    sparsity=0.5,
    mask_structure="2:4",   # 半结构化 → vLLM 可加速
    targets=["Linear"],
    ignore=["re:.*lm_head"],# 输出头敏感，排除
)
oneshot(model=model, dataset=calib_ds, recipe=recipe)
model.save_pretrained("model-2of4", save_compressed=True)
```
> 含义：用少量 `calib_ds` 估 Hessian，对所有 Linear（除 lm_head）做 2:4 剪枝并补偿误差，存成 compressed-tensors。

**B. 渐进幅度剪枝 + 冻结（多阶段，apply）**

```yaml
# 阶段一：训练中把稀疏度从 0.1 爬到 0.5
MagnitudePruningModifier:
    start: 5
    end: 10
    init_sparsity: 0.1
    final_sparsity: 0.5
    targets: __ALL_PRUNABLE__
# 阶段二：钉住稀疏，继续训练恢复精度
ConstantPruningModifier:
    start: 0
    end: 5
    targets: __ALL_PRUNABLE__
```
> 含义：含训练阶段，**必须 `apply()/compress()`**，`oneshot()` 跑不全。ConstantPruning 保证训练不破坏已有零。

**关键参数权衡速记**：

| 参数 | 调大的影响 | 适用 Modifier |
|---|---|---|
| `sparsity` | 更省但更掉点 | 所有 |
| `mask_structure: 2:4` | 锁 50%、可硬件加速、略掉点 | SparseGPT/Wanda |
| `dampening_frac` | 更数值稳定但更粗糙 | SparseGPT |
| `block_size` | 更准但更慢更吃显存 | SparseGPT |
| `ignore` | 排除敏感层（lm_head/embed） | 所有 |

## 常见问题

| 问题 | 答案 |
|---|---|
| oneshot 和 apply/compress 区别？ | `oneshot()` 是 `compress()` 的别名/特化，只跑一次性 Modifier；含训练阶段的 recipe 用 `apply()/compress()` 跑全部 stage |
| 非结构化剪枝在 vLLM 上为什么不一定快？ | GPU 无任意稀疏指令，主要省显存/带宽；算力 2× 加速靠的是 2:4 + Sparse Tensor Core |
| SparseGPT 比 Wanda 强在哪？ | 多了 Hessian 误差补偿（剪一个调一片），同稀疏度精度更高，代价是更慢 |
| 微调恢复时零位置又变非零怎么办？ | 训练 stage 里加 `ConstantPruningModifier` 钉住稀疏 mask |
| 剪枝能和量化一起做吗？ | 能，同一 recipe 多 stage：先剪后量；存储由 compressed-tensors 统一承载 |
| 2:4 一定 2× 加速吗？ | 否。需 Ampere+ 硬件、内核支持、合适矩阵形状/batch，务必端到端基准实测 |
| `targets: __ALL_PRUNABLE__` 是什么？ | 通配，命中所有可剪枝层；想精细控制用 `['Linear']` + 正则 `ignore` |
| 校准数据要多少？ | 不训练，量级几百条即可，只为估激活/Hessian |
