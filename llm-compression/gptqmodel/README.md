## 0. 一句话锚点

先把最容易混淆的两个词钉死：

- **GPTQ** = 一种**量化算法**（2022 年 Frantar 等人的论文 *GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers*）。它只是「数学方法」。
- **GPTQModel** = 一个 **Python 库 / 工具**，把 GPTQ 算法实现出来，加上「模型适配、kernel、打包格式、保存/加载、推理后端」一整套工程。它是「能跑的代码」。

类比：GPTQ 像「红烧肉的菜谱」，GPTQModel 像「带预设程序的电饭煲」。本文重点讲工具，但要用好工具必须先懂算法，所以第 2 节会把算法拆到原子。

> 它的前身是 **AutoGPTQ**（社区最早的 GPTQ 实现）。AutoGPTQ 在 2024 年后基本停止维护，ModelCloud 团队 fork 出 **GPTQModel** 继续迭代，并成为 Hugging Face Transformers / vLLM 官方推荐的 GPTQ 后端之一。具体版本与官方推荐以官方文档为准。

## 1. 地基 / 前置：量化到底在干什么

### 1.1 为什么要量化

一个 7B 模型有约 70 亿个参数。若每个参数用 FP16（16 bit = 2 字节）存储：

$$7\times10^9 \times 2\ \text{Byte} \approx 14\ \text{GB}$$

显存装不下消费级显卡（如 24GB 卡还要留给 KV cache 与激活）。如果把每个权重压成 **4 bit（0.5 字节）**：

$$7\times10^9 \times 0.5\ \text{Byte} \approx 3.5\ \text{GB}$$

显存直接降到约 1/4。这就是量化的核心动机：**用更少的 bit 表示同一个权重**，换显存、换带宽、换速度，代价是一点点精度。

### 1.2 量化的最原子操作：浮点 → 整数

量化的本质是「**把一段连续的浮点范围，映射到一小撮整数格子上**」。最常用的「非对称均匀量化」公式：

- 量化（float → int）：

$$q = \text{round}\!\left(\frac{w}{s}\right) + z$$

- 反量化（int → float，推理时用）：

$$\hat{w} = s \cdot (q - z)$$

其中：
- $w$：原始浮点权重；$\hat{w}$：反量化后的近似值（和 $w$ 有误差）。
- $s$（**scale**，缩放因子）：一个浮点数，决定「每格代表多大的数值跨度」。
- $z$（**zero-point**，零点）：一个整数，让「浮点 0」能精确落在某个整数格子上。
- $q$：量化后的整数，4-bit 下范围是 $0\sim15$（共 $2^4=16$ 个格子）。

`round` 带来的误差就是**量化误差**。bit 越少，格子越粗，误差越大——这是所有量化方法都在对抗的核心矛盾。

### 1.3 PTQ vs QAT，GPTQ 属于哪类

```
                量化两大流派
   ┌───────────────────────┬───────────────────────┐
   │  PTQ 训练后量化          │  QAT 量化感知训练         │
   │  Post-Training Quant   │  Quant-Aware Training  │
   ├───────────────────────┼───────────────────────┤
   │  不重训，只用少量校准数据   │  在训练/微调中模拟量化     │
   │  几十分钟搞定一个 7B       │  要完整训练，成本高         │
   │  精度略降                │  精度更好                  │
   │  ✅ GPTQ / AWQ 在这里     │  代价大，LLM 上少用         │
   └───────────────────────┴───────────────────────┘
```

GPTQ 是 **PTQ**：不动训练，只拿 128~512 条样本「校准」，几十分钟就能量化一个 7B。这正是它流行的根本原因——**便宜**。

## 2. GPTQ 算法本身（拆到原子）

GPTQModel 是工具，但工具的灵魂是 GPTQ 算法。这一节把算法讲透，你才知道每个超参在调什么。

### 2.1 朴素量化为什么不够好

最朴素的做法（RTN，Round-To-Nearest）：对每个权重独立地 `round` 到最近格子。问题：它**不管这个权重在网络里有多重要**。一个对输出影响大的权重，被舍入误差一砸，整层输出就偏了，误差还会层层累积放大。

### 2.2 GPTQ 的核心思想：边量化边补偿

GPTQ 来自更早的 **OBQ（Optimal Brain Quantization）**。核心洞察是：

> 量化一个权重列会引入误差，但我可以**调整那些还没被量化的权重**去补偿这个误差，让整层的输出尽量不变。

它要最小化的目标是「量化前后，这一层在校准数据上的**输出**差异」：

$$\arg\min_{\hat{W}}\ \big\|\, W X - \hat{W} X \,\big\|_2^2$$

- $W$：原始权重矩阵；$\hat{W}$：量化后权重；$X$：校准数据经过前面层得到的该层输入。
- 注意优化的是 $WX$（输出）的差，不是 $W$ 本身的差——**保住输出比保住权重更重要**。

### 2.3 Hessian 与逐列量化（为什么需要校准数据）

上面目标对 $\hat W$ 求二阶导，得到的 **Hessian** 正比于 $X X^\top$。直觉：

- $XX^\top$ 描述「各输入维度的相关性与能量」。
- 哪个权重列「重要」，由它对应输入的活跃程度决定——这就是为什么**必须喂校准数据**（没有 $X$ 就算不出 Hessian）。

GPTQ 流程（逐层独立处理，每层内逐列量化）：

```
对每一列 j（从左到右）：
  1. 把第 j 列量化：q_j = round(w_j / s) + z
  2. 算出这次舍入造成的误差 e_j
  3. 用 Hessian 信息，把 e_j 按权重"分摊"到右侧还没量化的列上：
        W[:, j+1:] -= e_j · (Hessian 相关的补偿系数)
  4. 处理下一列
```

第 3 步就是「**误差补偿**」——这是 GPTQ 比 RTN 精度高一大截的关键。

### 2.4 group_size：分组量化

如果整列（可能上千个数）共用一个 scale，范围太宽、格子太粗。于是把权重**按行方向切成小组**（如每 128 个一组），每组算自己的 $s, z$：

```
一列权重（示意，行方向 4096 个数）：
[ w0 w1 ... w127 | w128 ... w255 | ... ]
   └─ group 0 ─┘   └─ group 1 ─┘
   s0,z0           s1,z1            ← 每组独立的 scale / zero-point
```

`group_size=128` 是事实标准：精度好，额外开销小。组越小越精确，但要存的 scale 越多（占显存）。

### 2.5 desc_act（act-order）

`desc_act=True`（也叫 act-order）：**按激活的重要性从大到小**决定列的量化顺序，先量化「最重要」的列，让补偿更充分。通常能再涨一点精度，代价是某些推理 kernel 速度略降或不支持。是否开启视后端而定（以官方文档为准）。

## 3. GPTQModel 解决什么问题（为什么不是 AutoGPTQ）

```
   AutoGPTQ（旧）                        GPTQModel（新，ModelCloud）
   ─────────────                        ──────────────────────────
   ✗ 2024 后基本停更                      ✓ 持续维护、活跃迭代
   ✗ 新模型架构适配慢                      ✓ 快速跟进新模型（Llama/Qwen/
   ✗ kernel 旧、慢                        DeepSeek/MoE/多模态 等）
   ✗ 打包格式与新生态脱节                   ✓ 新 kernel：Marlin / ExLlama 等
                                         ✓ HF Transformers / vLLM 官方对接
                                         ✓ 兼容 AutoGPTQ 旧模型（多数可直接读）
```

一句话：**GPTQModel = AutoGPTQ 的精神续作 + 现代工程**。今天要做 GPTQ 量化，社区共识是用 GPTQModel 而非维护已停更的 AutoGPTQ（具体兼容范围、官方推荐以官方文档为准）。

它解决的工程痛点：①**算法落地**——把论文变成一行 `quantize()`；②**模型适配**——自动识别哪些线性层该量化、哪些（lm_head/norm）该跳过；③**打包/序列化**——4-bit 权重高效打包成推理引擎可直接加载的磁盘格式；④**kernel/后端**——提供快速反量化+matmul 的 CUDA kernel，让推理真的快。

## 5. 量化全流程（数据流 ASCII）

```
 ① 准备校准数据                ② 加载 FP16 模型              ③ 配置
 ┌──────────────┐            ┌──────────────────┐        ┌──────────────────┐
 │ 128~512 条文本 │            │ GPTQModel        │        │ QuantizeConfig    │
 │ (代表真实分布)  │            │ .from_pretrained │        │ bits=4            │
 │ 如 C4/wikitext│            │ (model_id)       │        │ group_size=128    │
 └──────┬───────┘            └────────┬─────────┘        └────────┬─────────┘
        │                            │                           │
        └──────────────┬─────────────┴───────────────────────────┘
                       ▼
              ┌─────────────────────┐
              │   .quantize(calib)   │   ← 一行触发整个 GPTQ 过程
              └──────────┬──────────┘
                         ▼
   ┌───────────────────────────────────────────────────────┐
   │  逐层（layer 0 → N）：                                    │
   │   a. 校准数据前向到本层，收集输入 X                          │
   │   b. 算 Hessian ∝ XXᵀ                                  │
   │   c. 逐列量化 + 误差补偿（第 2 节）                          │
   │   d. 用量化后的层继续前向，喂给下一层                         │
   └───────────────────────────┬───────────────────────────┘
                               ▼
                    ┌────────────────────┐
                    │  打包成 int32        │
                    │  + 存 scale/zero     │
                    └─────────┬──────────┘
                              ▼
                    ┌────────────────────┐
                    │  .save(output_dir)  │
                    │  得到可推理的量化模型  │
                    └────────────────────┘
```

### 5.1 最小代码骨架（API 以官方文档为准）

```python
from gptqmodel import GPTQModel, QuantizeConfig

# ① 配置：4-bit、group_size 128
quant_config = QuantizeConfig(bits=4, group_size=128)

# ② 加载原始 FP16 模型
model = GPTQModel.load("meta-llama/Llama-3-8B", quant_config)

# ③ 准备校准数据：一批代表性文本（list[str] 或已 tokenize 的样本）
calibration = ["量化需要有代表性的真实语料 ...", "..."]  # 实际用 128+ 条

# ④ 一行量化（内部跑完第 2 节的整套 GPTQ）
model.quantize(calibration)

# ⑤ 保存
model.save("./Llama-3-8B-gptq-4bit")

# ⑥ 之后推理：直接 load 量化目录
qmodel = GPTQModel.load("./Llama-3-8B-gptq-4bit")
print(qmodel.generate("你好")[0])
```

> 注意：不同版本入口方法名可能是 `load` / `from_pretrained` / `from_quantized` 等，**以你安装版本的官方文档为准**，本文只给心智模型。

### 5.2 校准数据的讲究

**数量** 常用 128~512 条（太少 Hessian 噪声大，太多收益递减还慢）；**代表性 > 数量**，要贴近真实使用分布（聊天模型用对话、代码模型用代码）；**长度** 每条截到常用上下文的一段（如 512~2048 token）。

## 6. 打包格式与推理后端

### 6.1 为什么要「打包（pack）」

GPU 没有原生的 4-bit 数据类型。我们把多个 4-bit 数**塞进一个 32-bit 整数**里存储与传输：

```
一个 int32（32 bit）能装 8 个 4-bit 权重：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ w7 │ w6 │ w5 │ w4 │ w3 │ w2 │ w1 │ w0 │   每格 4 bit
└────┴────┴────┴────┴────┴────┴────┴────┘
         ↑ 这就是 "packed int32" 权重
```

推理 kernel 在算矩阵乘时，先把 int32 **解包**回 8 个 4-bit、再用 scale/zero **反量化**回 FP16，然后做乘加。好的 kernel 把「解包 + 反量化 + matmul」融合在一起，避免来回读写显存。

### 6.2 常见后端对比

| 后端 | 特点 | 适合 |
|------|------|------|
| Marlin | 高吞吐 FP16×INT4 GEMM kernel，速度领先 | 生产推理首选（满足约束时） |
| ExLlama v2 | 经典快速 4-bit kernel | 单卡本地推理 |
| Triton | 用 Triton 写的 kernel，可移植性好 | 跨硬件 / 调试 |
| CUDA（通用） | 兜底实现 | 兼容性优先 |

> 后端是否可用受 `bits / group_size / desc_act / 对称性 / 显卡架构` 约束（比如 Marlin 对这些有要求）。GPTQModel 通常会按当前配置自动挑选可用的最快后端。具体支持矩阵以官方文档为准。

### 6.3 量化模型怎么被「别人」用

量化目录保存后，不止 GPTQModel 自己能读：
- **Hugging Face Transformers**：通过 GPTQ 集成直接 `from_pretrained` 加载。
- **vLLM / SGLang 等推理引擎**：识别 GPTQ 格式，享受高吞吐 serving。

这也是 GPTQModel 比「自造格式」的工具更值钱之处——**它产出生态通用格式**。

## 7. 与 llm-compressor / AWQ 的对比

三者都做量化，但定位不同。先看一张图：

```
            "量化算法" 与 "量化框架" 不在同一层
   ┌─────────────────────────────────────────────────────────┐
   │  算法层： GPTQ          AWQ           SmoothQuant  ...     │
   │            │            │                                 │
   │  实现/框架： GPTQModel    AutoAWQ       llm-compressor      │
   │            (专做 GPTQ)  (专做 AWQ)     (多算法统一框架)       │
   └─────────────────────────────────────────────────────────┘
```

### 7.1 GPTQ vs AWQ（算法层面）

| 维度 | GPTQ | AWQ |
|------|------|-----|
| 核心思想 | 逐列量化 + Hessian 误差补偿 | 找出「重要权重」，按激活幅度缩放后再量化，保护它们 |
| 是否要补偿权重 | 是（改未量化列） | 否（只缩放，不重排补偿） |
| 校准数据 | 需要（算 Hessian） | 需要（算激活幅度） |
| 量化耗时 | 中等（逐列，较慢） | 通常更快 |
| 精度 | 4-bit 下很好 | 4-bit 下很好，常与 GPTQ 互有胜负 |
| 直觉 | 「量错了我补回来」 | 「重要的别量太狠」 |

经验法则：**两者 4-bit 精度都很能打，具体哪个好要按模型实测**，没有绝对赢家。

### 7.2 GPTQModel vs llm-compressor（工具层面）

| 维度 | GPTQModel | llm-compressor |
|------|-----------|----------------|
| 出品方 | ModelCloud 社区 | vLLM / Neural Magic 生态 |
| 覆盖算法 | 专注 GPTQ（做深做精） | 多算法统一框架：GPTQ、AWQ、SmoothQuant、稀疏、W8A8/FP8 等 |
| 定位 | 「GPTQ 的最佳实现」 | 「面向 vLLM 部署的一站式压缩」 |
| 输出格式 | GPTQ 格式（HF/vLLM 通用） | 通常产出 vLLM 原生 compressed-tensors 格式 |
| 何时选 | 我就是要 GPTQ、要最新 GPTQ kernel | 我要在多种量化方案/W8A8/FP8/稀疏之间灵活选，且主战场是 vLLM |

详见 [[llm-compression/llm-compressor/量化方案]]。

### 7.3 一句话选型

- 只要 **4-bit weight-only、GPTQ 路线** → **GPTQModel**。
- 想要 **统一框架横扫多种量化（含 W8A8/FP8/稀疏）且部署在 vLLM** → **llm-compressor**。
- 想试 **AWQ 路线** → AutoAWQ 或 llm-compressor 里的 AWQ。

## 8. 关键超参怎么调

| 参数 | 含义 | 怎么选 |
|------|------|--------|
| `bits` | 量化位宽，4/3/2/8 | 4-bit 是甜点（精度/压缩平衡）；2-bit 精度风险大，需特殊方法 |
| `group_size` | 分组大小 | 128 是事实标准；更小更准但 scale 更多；-1 表示按列（per-channel） |
| `desc_act` | act-order 重排 | 开了通常更准，但可能限制可用后端 / 略慢 |
| `sym` | 对称量化（zero-point 固定） | 对称更省、kernel 更友好；非对称更灵活 |
| `damp_percent` | Hessian 阻尼，防数值不稳 | 一般用默认（如约 0.01），矩阵病态时调大 |

调参直觉：**先用 `bits=4, group_size=128` 默认档跑通**，测困惑度/下游指标，再决定是否开 `desc_act` 或改 group_size。

## 数值例子：手算一个 4-bit group

设某个 group 有 4 个权重（实际是 128 个，这里缩小演示），采用**非对称 4-bit**（$q\in[0,15]$）：

$$W_{\text{group}} = [\,0.10,\ -0.20,\ 0.05,\ 0.40\,]$$

**第 1 步：求 scale 和 zero-point。** 取该组 min/max：$w_{\min}=-0.20$，$w_{\max}=0.40$，4-bit 共 16 格（$q_{\max}=15$）：

$$s = \frac{w_{\max}-w_{\min}}{q_{\max}} = \frac{0.60}{15} = 0.04,\qquad z = \text{round}\!\left(-\frac{w_{\min}}{s}\right) = \text{round}\!\left(\frac{0.20}{0.04}\right) = 5$$

**第 2 步：逐个量化** $q=\text{round}(w/s)+z$：

| $w$ | $w/s$ | $\text{round}$ | $+z$ | $q$（4-bit） |
|-----|-------|----------------|------|------|
| 0.10 | 2.5 | 3 | +5 | 8 |
| -0.20 | -5.0 | -5 | +5 | 0 |
| 0.05 | 1.25 | 1 | +5 | 6 |
| 0.40 | 10.0 | 10 | +5 | 15 |

（$0.10/0.04=2.5$，四舍五入到 3，故 $q=8$；不同实现的舍入规则略有差异。）

**第 3 步：反量化看误差** $\hat{w}=s(q-z)$：

| $q$ | $\hat{w}=0.04\,(q-5)$ | 原 $w$ | 误差 |
|-----|------|------|------|
| 8 | 0.12 | 0.10 | +0.02 |
| 0 | -0.20 | -0.20 | 0 |
| 6 | 0.04 | 0.05 | -0.01 |
| 15 | 0.40 | 0.40 | 0 |

**第 4 步：打包。** 4 个 4-bit 值 $[8,0,6,15]$ 拼进一个整数（低位在前）：

```
 q3=15   q2=6    q1=0    q0=8
 1111    0110    0000    1000   →  0x F 6 0 8
```

GPTQ 的额外贡献就在「第 3 步的误差」上——它不让 `+0.02` 这种误差白白留下，而是把它**补偿到右边还没量化的列**（RTN 则放任不管）。**每个 group 只多存一个 scale(0.04)+zero(5)，就把 4 个 FP16 压成 4 个 4-bit + 极小元数据。** 存储对比（group=4）：原始 $4\times16=64\,\text{bit}$，量化 $4\times4+s(16)+z(\approx4)\approx 36\,\text{bit}$；group 越大（真实 128）摊销越小，压缩率越接近理论 $16/4=4\times$。

## 常见问题

| 问题 | 原因 | 处理 |
|------|------|------|
| 量化时显存 OOM | 量化要把层加载 + 收集激活 | 减小 batch、用 offload/分层处理、换大显存机 |
| 量化后精度掉很多 | 校准数据不具代表性 / bit 太低 | 换更贴近场景的校准集；4-bit 起步别上来就 2-bit |
| 推理比预期慢 | 没用上最快 kernel | 检查后端是否落到 Marlin/ExLlama，确认 group_size/对称性满足 kernel 约束 |
| 加载报后端不支持 | 显卡架构/配置不满足某 kernel | 换通用 CUDA/Triton 后端，或调配置重量化 |
| AutoGPTQ 老模型能用吗 | 格式兼容性 | 多数能直接读；以官方文档为准 |
| 2-bit 能用吗 | 精度风险高 | 需更精细方法/校准，普通场景建议 4-bit |
| 校准要多少条 / 量化太久 | Hessian 需样本、逐列本就慢 | 常用 128~512（代表性 > 数量）；耗时属正常，可减样本/换快机 |
