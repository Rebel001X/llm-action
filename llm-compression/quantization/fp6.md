# FP6 量化（DeepSpeed-FP6 / FP6-LLM）

## 0. 一句话锚点

> **FP6 = 6-bit 浮点权重量化**。它不动激活（激活仍是 FP16），只把**权重**从 16-bit 压到 6-bit，显存约降到 FP16 的 **3/8**；精度上接近无损，避免了 INT4 在「代码生成、摘要」等生成式任务上的明显掉点；并用专门设计的 GPU kernel 把这种「非 2 的幂」位宽跑得比 FP16 cuBLAS **快 2.1×**。

原文两句关键定位（保留）：

- INT4 的痛点：「虽然能减小模型大小，但由于**过拟合问题**，在更一般的许多任务中往往表现不佳，包括**代码生成和摘要**等更多生成任务。」
- FP6 的卖点：「该格式在各种任务的**性能和灵活性**方面均表现出色」，而难点是「FP6 数据格式在当前 AI 硬件的高效支持中存在挑战」——于是提出**「4+2」新颖的 FP6 GPU kernel** 来解决执行效率。

一句话记忆：**INT4 太糙、FP8 太胖、FP6 刚好；硬件不友好，就用 kernel 硬啃。**

## 1. 地基 / 前置

读 FP6 前要先有三块地基。每块都先问「是什么 / 为什么」。

### 1.1 浮点位宽（bit-width）

一个数在显卡里占多少 bit，直接决定**显存**与**访存带宽**。
- FP16 = 16 bit/权重；FP6 = 6 bit/权重 → 同样一个 70B 模型，权重显存约从 140 GB 降到 **52.5 GB**（6/16）。
- **为什么不是 INT4/INT8 那种整数？** 整数（定点）动态范围窄，大权重和小权重无法兼顾；浮点用「指数位」换动态范围，更贴合权重的长尾分布。

### 1.2 仅权重量化（weight-only quantization, W6A16）

FP6 是 **W6A16**：Weight 6-bit、Activation 16-bit。

```
            权重 W (FP6, 显存里就是 6-bit)
                │  读入后在寄存器里 dequant→FP16
                ▼
  激活 X(FP16) ─► [ X · W ]  ← 真正算 GEMM 时两边都是 FP16
                ▼
            输出 Y (FP16)
```

- **为什么激活不一起量化？** decode 阶段激活的 batch 很小，瓶颈在「把巨大的权重从显存搬进来」（memory-bound），而不是算力。压权重直接砍访存量；压激活收益小、还掉精度。
- 代价：算之前必须把 6-bit **反量化（dequantize）** 回 FP16，这一步的开销就是 §4、§5 要解决的核心。

### 1.3 访存瓶颈 vs 算力瓶颈（memory-bound vs compute-bound）

GEMM（矩阵乘）有两种瓶颈：

```
 算术强度 = 计算量(FLOP) / 访存量(Byte)

 小 batch / decode  →  算术强度低  →  搬数据慢 = memory-bound  ← FP6 在这里赢
 大 batch / prefill →  算术强度高  →  算不过来 = compute-bound  ← FP6 优势变小(§7)
```

记住这条线：**FP6 的全部价值，建立在「访存是瓶颈」之上。** 砍权重位宽 = 砍访存字节 = 直接提速。

## 2. E3M2：6 个 bit 怎么编码

FP6 采用 **E3M2** 格式：1 位符号 S + 3 位指数 E + 2 位尾数 M。

```
 bit:   [ S ][ E2 E1 E0 ][ M1 M0 ]
         1       3           2      = 6 bit
 含义:  符号    指数         尾数
```

数值（规格化数，normal）：

$$x = (-1)^{S}\times 2^{\,E-\text{bias}}\times \Bigl(1+\frac{M}{4}\Bigr),\qquad \text{bias}=2^{3-1}-1=3$$

- 指数 3 位 → $E\in[1,6]$ 用于规格化数（$E=0$ 次规格化，$E=7$ 视实现可作 Inf/最大值）。
- 尾数 2 位 → 每个指数档内只有 4 个台阶 $\{1.00,1.25,1.50,1.75\}$。

**动态范围（直觉）**：3 位指数给出大约 $2^{-3}\sim2^{3}$ 量级的跨度，比 INT4 的「线性 16 格」宽得多——这就是为什么 FP6 能同时罩住大权重和接近 0 的小权重，而 INT4 只能均匀切。

> 对照：FP8 有 E4M3 / E5M2（见 [[llm-compression/quantization/fp8]]）。FP6 砍掉 2 个 bit，主要砍在**尾数与指数各让一点**，精度档位变粗，但配 **per-channel/per-group scale**（继承自量化基础）后，对 LLM 权重仍接近无损。

## 3. 为什么 6-bit「难跑」——位宽不对齐

这是 FP6 工程上的核心难点，也是「4+2」存在的原因。

GPU 的内存、寄存器、访存指令都按 **8 / 16 / 32 / 128 bit** 对齐设计。6 不是 2 的幂，于是：

```
 想连续存 8 个 FP6 权重 = 48 bit：

  w0    w1    w2    w3    w4    w5    w6    w7
 |--6--|--6--|--6--|--6--|--6--|--6--|--6--|--6--|
 └──────────── 48 bit，横跨 1.5 个 32-bit word ──────────┘
        ▲           ▲
   单个权重会「骑跨」在两个 32-bit 字之间 → 访存不对齐、要拼接移位
```

原文一句话点透：「运行前**比特层级的数据排布转换**，用以解决权重具有**不规则位宽时不友好的内存访问挑战**，实现 GPU 内存的最优访问。」

不处理的话每读一个权重都要跨字读 + 移位 + 掩码，访存吞吐崩掉，FP6 省下来的带宽全被「拼比特」吃回去。

---

## 4. 「4+2」拆位方案（4+2 split）

核心思想：**把 6 bit 拆成「对齐的 4 bit」+「零散的 2 bit」分两段存**，让大头走对齐的快通道。

```
   一个 FP6 权重 = 6 bit
        ┌────────────┬──────┐
        │   高 4 bit  │ 低2bit│
        └────┬───────┴───┬──┘
             ▼           ▼
   ┌─────────────────┐  ┌─────────────────┐
   │  4-bit 段 (打包)  │  │  2-bit 段 (打包)  │
   │ 8个权重=32bit 对齐 │  │ 16个权重=32bit 对齐│
   └─────────────────┘  └─────────────────┘
        ↑ 走 4-bit 友好通道      ↑ 单独凑成对齐块
```

- **为什么是 4+2 而不是别的？** 4 和 2 都能整除地凑满 32-bit 字：8 个 4-bit = 32 bit，16 个 2-bit = 32 bit。两段各自**完美对齐**，读取时不再跨字。
- 读进来后在寄存器里把「4 段 + 2 段」按位拼回完整 6-bit，再反量化成 FP16。拼接发生在**寄存器内**（不是显存），靠 SIMT 指令完成，所以快。

这就是原文「4+2 新颖的 FP6 GPU kernel 方案」的内核：用**两种对齐位宽**模拟一种不对齐位宽。

## 5. 全栈 GPU kernel 三件套

原文给出三层设计，这里逐层解释「解决什么、为什么有效」。

```
 ┌──────────────────────────────────────────────┐
 │ ① 运行前：比特层级数据排布转换 (offline)         │  ← §3/§4，离线一次性重排成 4+2
 ├──────────────────────────────────────────────┤
 │ ② 运行时：高效 SIMT 反量化 (on-the-fly dequant) │  ← 寄存器内 6bit→FP16，最小化开销
 ├──────────────────────────────────────────────┤
 │ ③ 全栈流水线：SIMT / Tensor Core / 访存 三路调度 │  ← 三种引擎同时转，互相掩盖延迟
 └──────────────────────────────────────────────┘
```

逐层（保留原文表述）：

1. **运行前比特层级排布转换**：「用以解决权重具有不规则位宽时不友好的内存访问挑战，实现 GPU 内存的最优访问。」→ 即 §4 的 4+2 重排，离线做完，运行时直接读对齐块。
2. **运行时高效 SIMT 计算**：「用以**最小化权重反量化的运行时开销**。」→ dequant 用 SIMT（CUDA core）做，与 Tensor Core 的 GEMM 并行，不抢同一条流水。
3. **全栈高效流水线设计**：「其 **SIMT 计算、Tensor Core 计算和 GPU 内存访问**进行高效调度，最大程度提升性能。」

为什么三路并行是关键？

```
 朴素串行:  访存───►反量化───►GEMM───►访存───►...   (每步等上一步)
 流水线:    访存 ░░░░░░░░░░░░░░░░░░░░  (DMA 持续搬)
            SIMT      ▓▓dequant▓▓▓▓▓▓
            TensorCore     ████GEMM████      (三者重叠，延迟被互相掩盖)
```

**实测结果（保留原文数据）**：在 NVIDIA **A100** 上做「因 decoder 矩阵形状**狭长**而导致参数矩阵访存成为瓶颈」的矩阵乘法，FP6 kernel 比 **FP16 cuBLAS 基准快 2.1×**。

## 6. 为什么对 decode / 长序列 / 小 batch 特别香

原文给出 FP6 服务 LLM 的两个关键好处 + 两个「访存瓶颈被放大」的场景。

### 6.1 两个关键好处（保留）

1. **更少 GPU 就能部署**：例如 **LLaMA-70b 在单张 A100-80G 上**就能以 FP6 运行，而 **FP16 至少要两张**。
   - 算账：70B × 2B(FP16) ≈ 140 GB > 80 GB，必须 2 卡；70B × 0.75B(FP6) ≈ **52.5 GB < 80 GB**，单卡装下。
2. **加快小 batch、访存瓶颈下的线性层计算**；同时**降低权重显存 → 能同时服务更多查询 → 吞吐更高**。

### 6.2 长解码为什么访存瓶颈更重（保留两因素）

```
 ┌ 因素一：KV cache 随序列变长而膨胀 ┐
 │  序列越长 → KV cache 越大 → 留给 batch 的显存越少
 │  → batch 变小 → 线性层算术强度↓ → 更 memory-bound
 └──────────────────────────────────┘
 ┌ 因素二：FastGen 的 prefill-decoding mixed-batch ┐
 │  decode 很长时，可拿来和 decode 混批的 prefill 切块「相对不足」
 │  → 纯 decode batch 出现频率↑ → 访存瓶颈进一步加剧
 └────────────────────────────────────────────────┘
```

两条线殊途同归：**越是长输出、小 batch 的 decode，越 memory-bound，FP6 的「砍访存」收益越大**。这正是它在推理服务（[[llm-inference/README]] / [[llm-inference/PD分离]]）里的价值所在。

## 7. 什么时候 FP6 不划算（边界与限制）

原文很诚实地列了边界，必须照搬：

| 场景 | 会发生什么 | 原因 |
|---|---|---|
| **大 batch / 显存充足** | 瓶颈变为 **Tensor Core 计算**（compute-bound），仅权重量化 kernel **可能保不住优势**，尤其对比 cuBLAS | dequant 的额外 SIMT 开销暴露，FP16 路径反而更顺 |
| **MoE 结构** | **目前不支持**，仅支持 Non-MoE，团队「正在努力扩展到 MoE」 | kernel 还未适配专家路由的稀疏 GEMM（见 [[llm-algo/moe/README]]） |
| **非 FP16 输入模型** | **不兼容**，当前 FP6 kernel 仅支持处理 **FP16 激活** | kernel 实现按 FP16 激活硬编码 |

但即便在 compute-bound 时，「我们系统的**低内存占用**仍是一个关键优势」——单卡能装下，本身就是部署价值。

## 8. 数值手算：把一个权重压成 FP6（E3M2）

设某权重 $w = 1.6$，bias=3。

1. 定符号：$S=0$。
2. 找指数：$1.6 = 2^{0}\times1.6$，落在 $[1,2)$ → 实际指数 $0$ → 存储 $E = 0+\text{bias}=3 = (011)_2$。
3. 量化尾数：$1.6 = 1+0.6$，尾数候选 $\{1.00,1.25,1.50,1.75\}$，离 $1.60$ 最近的是 $1.50$（差 0.10）或 $1.75$（差 0.15）→ 取 **1.50**，即 $M=(01)_2$。
4. 拼起来：`S=0, E=011, M=01` → `0 011 01`。
5. 还原：$(-1)^0\times2^{3-3}\times1.50 = 1.50$，量化误差 $|1.6-1.5|=0.1$。

> 误差看着不小？因为这只是「裸 FP6」。实际工程会配 **per-group scale**（量化基础里的缩放）：先把这一组权重除以一个 FP16 scale 落进 FP6 网格，用时再乘回，**有效精度大幅提升**——这也是 FP6 在真实任务上接近无损的原因。手算这步是为了让你看清「2 位尾数 = 每档只有 4 个台阶」的粗糙本质。

对照 INT4（16 个均匀台阶、无指数）：同一个 1.6 在一个跨度大的分组里可能被量到更远的格点上，且无法兼顾同组里很小的权重——这就是原文说 INT4「在代码生成 / 摘要等生成任务表现不佳」的微观来源。

## 9. 对照表

| 格式 | bit | 编码 | 动态范围 | 精度档（尾数） | 显存(70B 权重) | 典型用途 |
|---|---|---|---|---|---|---|
| FP16 | 16 | E5M10 | 宽 | 1024 档/指数 | ~140 GB | 基准 |
| FP8 (E4M3) | 8 | E4M3 | 中 | 8 档/指数 | ~70 GB | 训练+推理（[[fp8]]） |
| **FP6 (E3M2)** | **6** | **E3M2** | **较宽** | **4 档/指数** | **~52.5 GB** | **仅权重、访存瓶颈推理** |
| INT4 | 4 | 定点 | 窄（线性 16 格） | — | ~35 GB | 极致压缩、易掉点 |

复杂度直觉：

```
 访存量 ∝ 权重 bit 数
 FP6/FP16 = 6/16 = 0.375  → 理论上访存砍掉 62.5%
 实测 decode 狭长 GEMM 端到端 ≈ 2.1× (含 dequant 开销后仍达成)
```

## 10. 实操：DeepSpeed-MII 跑 FP6

FP6 通过 DeepSpeed / DeepSpeed-MII 暴露。核心是把 `quantization_mode` 指定为 FP6（`fp6` / `wf6af16`，以你所装版本文档为准），其余按常规 MII pipeline 走。

> 注意：本仓库原文未给出具体脚本，下列为依据 DeepSpeed-FP6 博客约定的最小用法骨架；**实际参数请以你安装的 DeepSpeed/MII 版本与官方博客为准**，不要照抄当成保证可用的固定 API。

```python
# 最小骨架（示意，非逐字命令）：用 DeepSpeed-MII 以 FP6 部署
import mii

pipe = mii.pipeline(
    "NousResearch/Llama-2-70b-hf",
    quantization_mode="wf6af16",   # weight FP6, activation FP16（W6A16）
)
resp = pipe(["写一个快速排序的 Python 实现"], max_new_tokens=128)
print(resp)
```

落地要点（对应原文事实）：

- 目标硬件：**A100**（博客实测平台）。LLaMA-70b 用 FP6 可塞进**单张 A100-80G**。
- 只压权重、激活保持 FP16 → 输入模型须是 **FP16** 权重。
- 仅 **Non-MoE**；MoE 模型暂不要指望该 kernel。
- 收益最大场景：**小 batch、长 decode、KV cache 占满显存**时（§6）。

## 常见坑

| 现象 / 疑问 | 真因 | 对策 |
|---|---|---|
| 大 batch 下 FP6 没比 FP16 快 | 进入 compute-bound，dequant 开销暴露（§7） | 大 batch/算力受限场景别强上 FP6；它的主场是 memory-bound decode |
| MoE 模型用不了 | kernel 当前不支持 MoE | 用 Non-MoE 模型，或等官方扩展 |
| 加载报激活精度不匹配 | FP6 kernel 仅支持 **FP16 激活** | 输入模型转成 FP16，别用 BF16/INT8 激活 |
| 6-bit 直接存访存反而更慢 | 位宽不对齐、权重跨 32-bit 字（§3） | 必须用「4+2」离线重排，别手撸朴素 6-bit 打包 |
| 精度比预期差很多 | 只用了「裸 FP6」、没配 per-group scale | 配合缩放（[[量化基础]]），E3M2 才接近无损 |
| 以为能压激活 / KV cache | FP6 是 **W6A16 仅权重** | KV cache 量化是另一条线（[[kv-cache-quant]]） |
| 单卡装不下 70B | 没换算清楚 | 70B×0.75B ≈ 52.5 GB，A100-80G 可单卡；FP16 的 140 GB 不行 |
