## 0. 一句话锚点

**Dense 模型**：参数量 ≈ 计算量，量化是"等比例压"。
**MoE 模型**：参数量 >> 单 token 计算量（"稀疏激活"），量化要压的主要是**那块谁也躲不掉、却大部分时间睡着的专家权重**。

所以 MoE 量化的核心命题是：

> 用**最少的比特**存下**最多但稀疏使用**的专家权重，同时**不破坏路由器**对专家的选择——一旦路由错了，再好的专家权重也会被送给错的 token。

## 1. 地基 / 前置

### 1.1 MoE 结构（速回顾，详见 [[llm-algo/moe/README]]）

一个 MoE 层把标准 Transformer 的 FFN 替换为：1 个**路由器 (router/gate)** + N 个**专家 (expert)**（每个专家就是一个独立的 FFN）。

```
            ┌─────────── MoE Layer ───────────┐
  x (token) │                                 │
   ───────► │  Router (Wg)  ── logits ─►softmax│
            │      │                           │
            │   top-k 选 k 个专家 (如 k=2)     │
            │      │                           │
            │   ┌──┴──┬──────┬─────┐          │
            │  E1    E2    ...    EN          │  ← N 个 FFN，每个含 W_up/W_gate/W_down
            │  (睡)  ✓     (睡)   ✓            │  ← 本 token 只唤醒 2 个
            │        │            │            │
            │     g2·E2(x) +  gN·EN(x)         │  ← 加权求和
            └──────────────┬──────────────────┘
                           ▼  y
```

关键量（以 Mixtral 8x7B 为例，详见 [[llm-algo/mixtral/README]]）：
- 专家数 $N=8$，每 token 激活 $k=2$。
- 总参数 ≈ 46.7B，但单 token **激活参数** ≈ 12.9B。
- 专家权重占总参数 **绝大多数**（attention + router 占比很小）。

### 1.2 量化基础（速回顾，详见 [[llm-compression/quantization/量化基础]]）

把 FP16 权重 $w$ 映射到 b-bit 整数。对称量化：

$$ s=\frac{\max(|w|)}{2^{b-1}-1}, \qquad q=\mathrm{clip}\!\Big(\mathrm{round}\big(\tfrac{w}{s}\big),\,-2^{b-1},\,2^{b-1}-1\Big), \qquad \hat w = s\cdot q $$

- $s$ = scale（缩放因子，FP16 存）；$q$ = 整数码（b-bit 存）。
- **粒度**：per-tensor（整张共享一个 $s$）< per-channel（每行/列一个 $s$）< per-group（每 g 个元素一个 $s$，如 g=128）。粒度越细越准，但 scale 的开销越大。
- **校准 (calibration)**：用一小批真实数据跑前向，统计激活/权重分布，决定 clip 范围或求解最优 $s$（GPTQ/AWQ 都靠它）。**记住这一点——它是后面所有 MoE 麻烦的根源。**

## 2. 为什么 MoE 特别需要量化（显存账）

MoE 用"稀疏激活"换"参数膨胀"：FLOPs 没怎么涨，但**所有专家权重都得常驻显存**（你不知道下一个 token 会路由到谁）。

```
 Dense 7B FP16:  weights 14 GB ────────────┐ 显存够，不量化也能跑
 Mixtral 8x7B FP16: weights 93 GB ──────────┼─► 单卡 80GB 放不下！
                                   ▲         │   即使只激活 2 个专家，
                  6.7× 参数膨胀     │         │   8 个都得在显存里待命
```

结论：**Dense 量化是"想更快/更省"，MoE 量化常常是"不量化就跑不起来"**。把 93GB 压到 4-bit ≈ 23GB，单卡可跑——这才是 MoE 量化的第一驱动力。

## 3. 挑战一：专家激活稀疏 → 校准数据被打散

这是 MoE 量化区别于 Dense 的**最核心难点**。

GPTQ/AWQ 这类后训练量化 (PTQ) 需要给每层喂校准数据，统计该层输入分布来求最优 scale。Dense 里每个权重都被**全部** token 经过，统计充分。MoE 里——

```
  校准集 512 条 token  ──► Router 分发 ──►  专家收到的 token 数严重不均
                                          E1: 410  (热专家, 样本足)
                                          E2: 180
                                          E3:  95
                                          ...
                                          E7:  12  ◄── 冷专家！样本太少
                                          E8:   3  ◄── 几乎没被校准
```

后果：
1. **冷专家校准不足**：只有 3 个 token 经过 E8，统计出的 scale 噪声极大，量化误差被放大。
2. **样本有偏**：路由对输入有偏好（某些专家专门处理某类 token），E8 收到的 3 个 token 还不能代表它真实推理时的输入分布。
3. **校准开销错配**：你想给每个专家都准备充足校准样本，就得喂海量数据，因为大部分会被路由"浪费"到热专家上。

> 一句话：**Dense 的校准是"广播"，MoE 的校准是"被路由稀释的单播"**。这就是 MoEQuant 提出 **Expert-Balanced Sampling（专家均衡采样）** 的动机——主动挑选/重采样校准 token，让每个专家、尤其冷专家，都拿到足够且有代表性的样本。

### 3.1 应对：专家均衡采样

```
  普通采样:  随机抽 512 token ─► 冷专家饿死
  均衡采样:  按"让每个专家 ≥ T 个样本"目标，
            从大池子里贪心挑 token，优先补给冷专家
            ┌─ E8 缺样本 → 专门找会路由到 E8 的 token 补进来
            └─ 直到所有专家校准样本量达标
```

配合 **Affinity Guidance（亲和度引导）**：用 token 与专家的路由亲和度（gate 权重）给校准样本/损失加权，让"真正强激活该专家"的 token 在求 scale 时贡献更大，弱激活的少干扰。

## 4. 挑战二：专家间重要性不均 → 混合精度

不是所有专家一样重要。有的专家被频繁激活（承载主干语义），有的几乎不用。统一比特数是浪费。

```
   专家重要性 (激活频率 × 对 loss 的敏感度)
   E1 ████████████  → 给 4-bit 甚至更高
   E2 ████████
   E5 ████
   E8 █            → 给 2-bit 也无妨（很少被用 + 不敏感）
```

这正是 **MC-MoE (Mixture Compressor)** 的思路：把**量化比特预算当成一个分配问题**——在总比特预算约束下，给重要专家分配更多比特、给冷门专家更少（混合精度），并可叠加专家级别的剪枝/丢弃。本质是 0/1 背包式的预算最优化：

$$ \min_{b_i} \sum_i \text{Loss}_i(b_i) \quad \text{s.t.} \quad \sum_i \text{size}(E_i)\cdot b_i \le \text{Budget} $$

## 5. per-expert 量化：粒度怎么定

核心原则：**专家是天然的量化单元，scale 不能跨专家共享**。

```
  ✗ 错: per-tensor 跨所有专家共享一个 scale
        E1 权重范围 [-3,3]，E8 范围 [-0.4,0.4]
        共享 scale 会让 E8 的码值全挤在 0 附近 → E8 几乎全损
  ✓ 对: per-expert（每个专家独立 scale），更细可 per-expert + per-channel/group
```

逐层细化的粒度阶梯：

```
 per-tensor (整层)
   └─ per-expert (每专家)            ← MoE 的最低合理粒度
        └─ per-expert × per-channel  ← 每专家内每输出通道一个 scale
             └─ per-expert × per-group (g=128)  ← AWQ/GPTQ 常用，精度最好
```

**为什么 per-expert 是底线**：不同专家在训练中各自特化，权重幅度分布天差地别（见上图数值）。共享 scale = 用一把尺子量大象和蚂蚁。代价：N 个专家就有 N 套 scale，但 scale 体积相对权重极小（见第 8 节手算），完全划算。

## 6. 路由如何保精度：router 必须高精度

路由器 $W_g$（gate）参数量极小，但**决定每个 token 走哪些专家**。量化它是"捡了芝麻丢了西瓜"。

```
  router logits = x · Wg     (Wg 只有 hidden×N，极小)
        │
   若 Wg 被低比特量化 → logits 抖动 → argmax/top-k 选错专家
        │
   选错专家 = 把 token 送进一个没学过它的 FFN
        │
   ▼  误差不是"量化噪声"级别，而是"功能错误"级别 —— 灾难性
```

**实践铁律**：
1. **Router/gate 权重保持 FP16/BF16**（不量化，或最高比特）。它太小，量化省不了多少显存，却风险极高。
2. **top-k 选择在高精度下做**：即使专家权重 4-bit，gate 的 softmax/top-k 用 FP16 算，保证选对专家。
3. **关注边界 token**：top-2 里第 2、3 名 logits 接近时，量化噪声最易翻盘。亲和度引导（第 3.1）也有助于稳住这些边界。

> 口诀：**专家权重狠狠压，路由器一根毫毛别动。**

## 7. 主流方法速览（对应文件原有两篇参考）

### 7.1 MC-MoE — Mixture Compressor for MoE LLMs Gains More

- **核心**：把 MoE 压缩当**预算分配**问题，专家间**混合精度量化** + 专家**剪枝/丢弃**联合优化。
- **洞察**："Gains More" = 利用专家重要性不均，重要专家多给比特、冷专家少给甚至丢弃，同预算下精度更高。
- **训练-free**：PTF（post-training），不需重训。

### 7.2 MoEQuant — Expert-Balanced Sampling & Affinity Guidance

- **问题诊断**：标准 PTQ 校准在 MoE 上失效，因为**路由把校准 token 分配极不均衡**（第 3 节）。
- **两个药方**：
  1. **Expert-Balanced Sampling**：重采样校准集，保证每个专家（含冷专家）拿到足量、有代表性的校准 token。
  2. **Affinity Guidance**：用 token-专家亲和度（gate 权重）引导量化损失/采样权重，让强激活样本主导 scale 求解。
- **效果**：在低比特（如 W4/W3）下显著优于直接套用 GPTQ/AWQ。

```
  MoEQuant 流水线:
  原始校准池 ──► [Expert-Balanced Sampling] ──► 各专家样本达标
                          │
                          ▼
            [按 Affinity 加权求 per-expert scale] ──► GPTQ/AWQ 求解
                          │
                          ▼
              router 保 FP16 + 专家 W4 ──► 量化模型
```

## 8. 逐数手算（把账算给你看）

以 **Mixtral 8x7B** 近似配置：hidden $h=4096$，FFN 中间维 $d_{ff}=14336$，专家数 $N=8$，每专家 3 个矩阵（$W_{gate},W_{up}\in\mathbb{R}^{h\times d_{ff}}$，$W_{down}\in\mathbb{R}^{d_{ff}\times h}$），层数 $L=32$。数字为估算，精确以官方为准。

### 8.1 单个专家参数量

$$ P_{\text{expert}} = 2\cdot(h\cdot d_{ff}) + (d_{ff}\cdot h) = 3\cdot 4096\cdot 14336 \approx 1.76\times10^8 = 176\text{M} $$

一层 8 个专家：$8\times176\text{M}=1.41\text{B}$；32 层：$\approx 45\text{B}$ —— 与"总参 46.7B、专家占绝大头"吻合。

### 8.2 显存：FP16 vs INT4

| 配置 | 每参数字节 | 专家权重显存 | 备注 |
|------|-----------|------------|------|
| FP16 | 2 B | $45\text{B}\times2 = 90$ GB | 单卡 80G 放不下 |
| INT4 | 0.5 B | $45\text{B}\times0.5 = 22.5$ GB | 单卡可跑 |
| INT4+scale | +scale 开销 | ≈ 23–24 GB | 见 8.4 |

**压缩比 ≈ 4×**，这正是"不量化跑不起来"的解法。

### 8.3 per-expert scale：一个真实例子

设 E1 的 $W_{down}$ 元素最大绝对值 $\max|w|=2.83$，做 INT4 对称量化（$b=4$，范围 $[-8,7]$，分母 $2^{3}-1=7$）：

$$ s_{E1}=\frac{2.83}{7}\approx 0.404 $$

取一个权重 $w=1.10$：

$$ q=\mathrm{round}(1.10/0.404)=\mathrm{round}(2.72)=3,\quad \hat w=0.404\times3=1.212,\quad \text{误差}=0.112 $$

若 E8 的 $\max|w|=0.40$（冷专家幅度小），它**必须有自己的** $s_{E8}=0.40/7\approx0.057$。
假如错误地让 E8 共用 E1 的 $s=0.404$：E8 里 $w=0.30$ → $q=\mathrm{round}(0.30/0.404)=1$ → $\hat w=0.404$，误差 $0.104$，相对误差 **35%**！而用专属 scale：$q=\mathrm{round}(0.30/0.057)=5$ → $\hat w=0.285$，误差仅 $0.015$，相对误差 **5%**。**per-expert 把相对误差降了 7×**——这就是第 5 节"不能跨专家共享 scale"的数值证据。

### 8.4 scale 体积开销（per-expert per-group, g=128）

E1 的 $W_{down}$ 有 $14336\times4096$ 个元素，每 128 个一组共享一个 FP16 scale：

$$ \#\text{scales}=\frac{14336\times4096}{128}=458752,\quad \text{体积}=458752\times2\text{B}\approx 0.88\text{MB} $$

而该矩阵 INT4 主体 $=14336\times4096\times0.5\text{B}\approx 29.4\text{MB}$。**scale 仅占 ~3%**——细粒度几乎免费，但精度收益巨大。

### 8.5 校准 token 被路由稀释（挑战一的数值版）

512 条校准序列、每条 256 token = 131072 个 token 进入某 MoE 层，top-2 路由（每 token 激活 2 专家）。**理想均匀**下每专家：

$$ \frac{131072\times2}{8}=32768 \text{ token/专家} $$

但实际路由倾斜，假设最热专家拿 25%、最冷只拿 1.5%：

$$ E_{\text{hot}}: 0.25\times262144\approx 65536,\quad E_{\text{cold}}: 0.015\times262144\approx 3932 $$

冷专家样本量只有热专家的 **1/16**——GPTQ 的 Hessian/AWQ 的激活统计在 3932 样本上噪声陡增，量化误差被放大。**这就是为什么需要 Expert-Balanced Sampling 把冷专家"喂饱"。**

## 9. 对照 / 复杂度表

### 9.1 Dense 量化 vs MoE 量化

| 维度 | Dense 量化 | MoE 量化 |
|------|-----------|----------|
| 主要动机 | 提速/省显存（锦上添花） | 不量化跑不起来（刚需） |
| 量化对象 | 全部权重均匀经过数据 | 专家权重稀疏激活 |
| 校准难点 | 统计充分 | 被路由稀释，冷专家饿死 |
| 推荐粒度 | per-channel/group | **per-expert** × per-group |
| 特殊保护 | 通常无 | **router/gate 保 FP16** |
| 进阶手段 | — | 专家级混合精度 + 专家剪枝 |

### 9.2 粒度 × 精度 × 开销

| 粒度 | 精度 | scale 开销 | MoE 适用性 |
|------|------|-----------|-----------|
| per-tensor（跨专家） | 差（见 8.3） | 极小 | ✗ 禁用 |
| per-expert | 中 | 小（N 套） | ✓ 底线 |
| per-expert × channel | 好 | 中 | ✓ |
| per-expert × group(128) | 最好 | ~3% | ✓✓ 推荐 |

### 9.3 各组件量化策略

| 组件 | 占参数 | 建议比特 | 理由 |
|------|--------|---------|------|
| Router/gate $W_g$ | 极小 | FP16（不量化） | 选错专家=功能性灾难 |
| 专家 $W_{up/gate/down}$ | 绝大多数 | 4-bit（冷专家可 2-3bit） | 显存大头，混合精度 |
| Attention | 小到中 | 4–8 bit | 与 Dense 同 |
| Embedding/LM head | 中 | 8-bit 或保留 | 输出敏感 |

## 10. 面试问答 + 高频追问

| 高频问题 | 踩点答案 | 易错/陷阱 |
|---------|---------|----------|
| MoE 量化为何比 Dense 难？ | 参数膨胀但稀疏激活，校准 token 被路由打散，冷专家样本不足；且 router 不能动 | 答"模型大"不够，要点是**校准被稀释 + 路由敏感** |
| 为什么不能跨专家共享 scale？ | 各专家特化、权重幅度分布迥异，共享 scale 会让小幅度专家全损（见 8.3 相对误差 35% vs 5%） | 别只说"粒度细更好"，要给出**幅度分布不同**这一物理原因 |
| router 要不要量化？ | 不要/最高比特。它极小省不了显存，但量化噪声会让 top-k 选错专家 → 功能性错误 | 陷阱：以为"什么都该量化"。router 是例外 |
| 校准数据怎么准备？ | Expert-Balanced Sampling：保证每个专家（含冷专家）拿到足量代表性 token；可叠加 affinity 加权 | 别答"随机抽一批"，那正是失效原因 |
| 专家该用统一比特吗？ | 不必。混合精度（MC-MoE）：重要专家多比特、冷专家少比特/剪枝，同预算精度更高 | 注意是**重要性**（激活频率×敏感度），非单纯频率 |
| per-expert scale 开销大吗？ | 很小。per-expert×group(128) 下 scale 仅占该矩阵 ~3%（见 8.4），精度收益远大于开销 | 别夸大 scale 开销当成不做细粒度的理由 |

**追问串（面试官常用来挖深）**：
1. "冷专家校准样本太少怎么办？" → 均衡重采样 + 亲和度加权；极端情况合并/丢弃冷专家。
2. "INT4 下 Mixtral 显存降到多少？" → 专家 90GB→~22.5GB，4× 压缩，单卡可跑（见 8.2）。
3. "为什么 top-2 边界 token 最危险？" → 第 2/3 名 logits 接近时，router 量化噪声/激活扰动易翻转 top-k 选择。
4. "MC-MoE 和 MoEQuant 分工？" → MC-MoE 解"比特预算如何在专家间分配（混合精度+剪枝）"；MoEQuant 解"校准数据如何不被路由稀释（均衡采样+亲和引导）"。二者正交，可叠加。
5. "量化后吞吐为何不一定线性提升？" → MoE 推理受**专家加载/dispatch、gather-scatter、负载不均**影响，显存降了但访存/通信可能成新瓶颈。

### 实践要点清单（可直接落地）

```
[1] Router/gate → 保 FP16，绝不低比特
[2] 专家权重 → per-expert × per-group(128) INT4 起步
[3] 校准 → Expert-Balanced Sampling，确保冷专家 ≥ 阈值样本
[4] 重要性不均 → 混合精度，重要专家高比特、冷专家低比特/剪枝
[5] 求 scale → 亲和度(gate权重)加权，强激活样本主导
[6] 验证 → 看 top-k 选择一致率(量化前后路由是否一致)，而非只看 PPL
[7] 部署 → 关注访存/dispatch 瓶颈，显存降≠吞吐线性升
```
