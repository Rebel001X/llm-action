# 张量并行 · 进阶与生产实践

> 本篇是 `tensor_parallel.py` / `手把手教学.md` 的"出厂升级"指南。toy 用单进程、纯 CPU、一个 `for` 循环把 Megatron 列/行切分的**数学等价性**讲清楚了;但真正能训出千亿模型的张量并行(Tensor Parallelism, TP),工程上还差十万八千里。本文按"toy 缺了什么 → 业界怎么补 → 关键变体 → 工程坑 → 量级估算 → 升级路线"展开,目标是把你从"理解原理"带到"理解一个生产 TP 系统为什么长成那样"。
>
> 准确性优先:本文不给捏造的 benchmark 绝对数字,涉及性能的地方用定性结论或量级公式表达。

---

## 0. 本项目 toy 与生产的差距

toy 故意把"对理解原理不重要、但工程上极其昂贵"的部分全删了。先看一张对照表,心里有数:

| 维度 | 本项目 toy 实现 | 生产(Megatron-LM 等)必须补什么 | 为什么生产不能省 |
|------|------------------|-------------------------------------|------------------|
| 进程/设备 | 单进程,`for` 循环依次算各分片 | 每个 TP rank 一个进程,绑一张 GPU,真并行 | toy 没有任何加速;并行的全部意义在于多卡同时算 |
| all-reduce | 一次 Python 张量相加 `CommCounter` | NCCL `dist.all_reduce(op=SUM)`,走 NVLink/PCIe/IB | 通信带宽/延迟才是 TP 的真实瓶颈,toy 完全不体现 |
| 模块覆盖 | 只有 MLP 块前向 | Attention(QKV 列并行 + 输出投影行并行)、Embedding、LayerNorm、LM Head 全切 | 一层 = MLP + Attention,且 embedding/输出层是显存大头 |
| 反向传播 | 无(只验证前向) | 前向 `f`/`g` 共轭算子在反向里互换,反向再 2 次 all-reduce | 训练必须有反向;通信量翻倍 |
| 通信算子抽象 | 直接求和 | Megatron 的 `f`(前向恒等/反向 all-reduce)与 `g`(前向 all-reduce/反向恒等)两个共轭算子 | 自动微分要正确,必须把通信注册成可微算子 |
| 切分整除 | `assert d_ff % N == 0` | padding 到可整除 / 处理 vocab、heads 不整除 | 真实 vocab(如 50257)和 head 数常不整除 TP size |
| 数值精度 | FP32,误差 ~1e-6 | BF16/FP16 混合精度 + FP32 master weights + loss scaling | 大模型不可能纯 FP32;低精度下 all-reduce 顺序敏感 |
| 显存 | 不关心(toy 极小) | 激活值/KV cache/优化器状态都要算账,激活重算、ZeRO | 显存是"能不能放下"的硬约束,TP 的首要动机 |
| 通信-计算重叠 | 无(串行) | SP + 异步通信、reduce-scatter/all-gather 拆分与 GEMM 重叠 | 不重叠的话通信直接吃掉算力,扩展性崩 |
| 权重初始化/RNG | 共享一份权重再切 | 每个 rank 独立但"切分一致"的 RNG,保证等价于单卡初始化 | 分布式下随机数管理是正确性陷阱 |
| 容错/拓扑 | 无 | rank↔GPU 映射、TP group 优先放同节点 NVLink、失败重启 | TP 通信最密集,必须放在最快互联域内 |

一句话:**toy 证明了"切了之后结果对",生产解决的是"切了之后还要快、还要放得下、还能反向、还不崩"。**

## 1. 业界系统怎么做

### 1.1 Megatron-LM:TP 的事实标准

NVIDIA Megatron-LM(arXiv:1909.08053)就是 toy 的"工业放大版"。核心抽象是两个**共轭通信算子** `f` 和 `g`,把通信和自动微分焊在一起:

- `f`:前向**恒等**(identity),反向做 **all-reduce**。放在 TP 区块入口(列并行层之前)。
- `g`:前向做 **all-reduce**,反向**恒等**。放在 TP 区块出口(行并行层之后)。

一个 Transformer 层数据流(把 toy 的 MLP 推广到完整层):

```mermaid
flowchart LR
    X[输入 X 各 rank 相同] --> f1["f (fwd: identity)"]
    f1 --> ATT["Attention: QKV 列并行 → 各 head 本地 attn → 输出投影 行并行"]
    ATT --> g1["g (fwd: all-reduce)"]
    g1 --> f2["f (fwd: identity)"]
    f2 --> MLP["MLP: A 列并行 GeLU → B 行并行"]
    MLP --> g2["g (fwd: all-reduce)"]
    g2 --> Y[输出 Y 各 rank 相同]
```

- Attention 块:QKV 投影是**列并行**(按 head 切,每个 rank 拿一部分 attention head,head 之间天然独立,免通信),输出投影是**行并行**,出口 1 次 all-reduce。
- MLP 块:就是 toy 演示的列→行,出口 1 次 all-reduce。
- 所以**前向每层 2 次 all-reduce**(`g1` + `g2`),反向因 `f1`/`f2` 各产生 1 次,**每层每 step 共 4 次** —— 这正是 toy 注释里那句话的工程出处。

为什么是"列→行"而不是"行→列"?toy 练习 5 已揭示:列并行第一层让 GeLU 免通信,行并行第二层把通信攒到出口一次。反过来则中间还要 all-reduce 一次,每块通信翻倍。**Megatron 的全部精妙就是把通信压到块出口那一次。**

### 1.2 本仓库 `ai-framework/megatron-lm` 与生态

本仓库已经收录了 Megatron 系工程文档,toy 是它们的"最小可运行内核":

- `ai-framework/megatron-lm`:Megatron-LM 框架本体。
- `ai-framework/megatron-deepspeed`、`llm-train/megatron-deepspeed`:Megatron + DeepSpeed 融合,把 TP/PP 和 ZeRO 拼在一起。
- `ai-framework/pai-megatron-patch`:阿里 PAI 对 Megatron 的产线 patch。
- `ai-framework/transformer-engine`:NVIDIA TE,提供 FP8 的 TP-aware 算子。

### 1.3 其它实现取舍一览

| 系统 | TP 实现方式 | 取舍 |
|------|-------------|------|
| Megatron-LM | 手写列/行并行 + `f`/`g` 算子,显式控制通信 | 性能最优、可控性强;侵入式,需按 Megatron 写模型 |
| DeepSpeed | 主打 ZeRO(切的是优化器状态/梯度/参数,不是层内矩阵),TP 借 Megatron 或 AutoTP | ZeRO 易用、改动小;纯 ZeRO 通信量比 TP 大,超大模型仍要配 TP |
| PyTorch `DTensor` / `tensor_parallel` API | 用 `ColwiseParallel`/`RowwiseParallel` 声明式切 `nn.Linear` | 原生、与 FSDP 组合好;成熟度/算子覆盖追赶中 |
| 推理引擎(vLLM / TensorRT-LLM / TGI / lmdeploy) | 推理专用 TP,权重加载时切分,前向 all-reduce | 见 §2.6,推理无反向、无优化器,关注延迟与吞吐 |

## 2. 关键变体与优化

### 2.1 序列并行 Sequence Parallelism(SP)

**它解决什么问题**:TP 切了 Attention/MLP 的矩阵,但 **LayerNorm 和 Dropout 这些"逐 token 但沿 hidden 维不可切"的算子没被切**,它们的激活值在每个 TP rank 上是**完整复制**的。对长序列大 batch,这部分激活显存非常可观。

**怎么做**:在 TP 不切的区域(LayerNorm/Dropout),改为沿**序列维(sequence dim)** 切分,让每个 rank 只持有 `1/N` 的序列长度的激活。代价是 TP↔SP 的边界上,把原来的 all-reduce 拆成 **reduce-scatter(进 TP 区)+ all-gather(出 TP 区)**。

**关键洞察**:reduce-scatter + all-gather 的**总通信量和一次 all-reduce 相同**(all-reduce ≈ reduce-scatter + all-gather)。所以 **SP 几乎不增加通信量,却把 LayerNorm/Dropout 激活显存降到 1/N** —— 近乎免费的显存优化,Megatron 默认开启。

```
普通 TP:  ...→ all-reduce → [LayerNorm 全量激活, 每 rank 复制] → ...
TP + SP: ...→ reduce-scatter → [LayerNorm 沿 seq 切, 每 rank 1/N] → all-gather → ...
```

### 2.2 3D 并行(TP × PP × DP)

单一并行维度都有天花板,生产把三者正交组合:

- **TP(张量并行)**:切层内矩阵。通信最密集(每层多次 all-reduce),**必须放在 NVLink/同节点**内,size 一般 ≤ 单机卡数(如 8)。
- **PP(流水线并行)**:按层切成 stage,stage 间只传激活(point-to-point),通信轻,可跨节点;代价是流水线 **bubble**(用 1F1B/interleaved 调度压缩)。
- **DP(数据并行)**:复制模型、切 batch,梯度 all-reduce;配 ZeRO 进一步切状态。

```mermaid
flowchart TB
    subgraph 全局[全局 GPU 集群]
      subgraph DP1[DP replica 1]
        subgraph PP1[PP stage 1] TP1[TP=8 同节点 NVLink] end
        subgraph PP2[PP stage 2] TP2[TP=8 同节点 NVLink] end
      end
      subgraph DP2[DP replica 2]
        T3[...] 
      end
    end
```

经验排布优先级:**TP 放节点内(吃 NVLink 带宽),PP 跨节点(通信少能容忍慢链路),DP 在最外层**。总卡数 = TP × PP × DP。

### 2.3 ZeRO(零冗余优化器)

**它解决什么问题**:DP 下每张卡都存一份完整的优化器状态(Adam 的 m/v)、梯度、参数,冗余 N 份。对大模型,优化器状态(FP32 master + m + v ≈ 参数量的 12 倍字节,BF16 训练下)是显存第一杀手。

ZeRO 分三级,逐级切掉冗余:

| 级别 | 切什么 | 通信代价 | 显存收益 |
|------|--------|----------|----------|
| ZeRO-1 | 优化器状态 | 基本同 DP | 大 |
| ZeRO-2 | + 梯度 | 略增(reduce-scatter) | 更大 |
| ZeRO-3 | + 参数本身(前向时 all-gather 临时拼回) | 明显增加(每层 all-gather 参数) | 最大,接近线性 |

**ZeRO vs TP 的本质区别**:TP 切的是**单次前向里的矩阵运算**(层内并行),ZeRO 切的是**跨 step 持久化的状态**(本质是更省显存的 DP)。两者正交,常组合:**节点内 TP + 节点间 ZeRO/DP**。本仓库 `ai-framework/deepspeed` 有完整 ZeRO 配置说明。

### 2.4 通信-计算重叠

TP 的 all-reduce 串在前向关键路径上,**不重叠就是纯等待**。生产手段:

- **拆分 GEMM + 异步通信**:把一个大 all-reduce 拆成多个小 reduce-scatter/all-gather,与后续/前面的 GEMM 分块流水。
- **Tensor Parallel 通信与下一层计算重叠**:在 `f`/`g` 边界用异步 collective(`async_op=True`),通信进行时 GPU 继续算不依赖该结果的部分。
- **CUDA stream 分离**:通信走独立 stream,与计算 stream 并发(需小心同步点)。
- **TE / FlashAttention 等融合算子**:减少 kernel launch 和中间激活,留更多带宽给通信。

直觉:当 TP size 增大,**计算被切成 1/N,但 all-reduce 通信量基本不变**(甚至随拓扑变差),所以"重叠"是 TP 扩展性能否撑住的关键,而不是锦上添花。

### 2.5 反向传播与共轭算子

toy 没有反向。生产里 `f`/`g` 必须实现为可微算子:

- 前向 `g` 做 all-reduce → 反向 `g` 是恒等(梯度直接传)。
- 前向 `f` 是恒等 → 反向 `f` 做 all-reduce(把各 rank 对输入的部分梯度求和)。

这就是"反向对称再来 2 次 all-reduce"的来源。实现上在 Megatron 里是两个自定义 `torch.autograd.Function`。

### 2.6 TP 推理(inference)

推理和训练的 TP 形状不同,本仓库 `llm-inference` 有大量相关文档:

- **无反向、无优化器状态**:显存账主要是权重 + **KV cache**。
- **TP 切权重也切 KV cache**:KV cache 沿 head 维切,正好对齐 Attention 的列并行,每个 rank 只存 `1/N` 的 KV。
- **每层仍有 all-reduce**,但推理是延迟敏感的:decode 阶段 batch 小、矩阵瘦,**通信占比比训练更高**,小 TP size(2/4)往往比大 TP 更划算。
- **PD 分离 / 连续批处理**:prefill(算力密集)和 decode(访存密集)对 TP 的偏好不同,vLLM、TensorRT-LLM、lmdeploy 各有 TP 实现(见 `llm-inference/PD分离.md`、`llm-inference/KV-Cache优化.md`)。

## 3. 真实工程权衡与坑

### 3.1 核心取舍(显存 / 吞吐 / 延迟 / 精度 / 通信)

- **TP size 越大,单卡显存越省、但通信占比越高**。TP=8 把权重和激活切到 1/8,但每层 all-reduce 的相对开销随之放大,**超出单节点 NVLink 后(TP 跨节点)性能急剧下降**——这是为什么 TP 几乎不跨节点。
- **TP vs PP vs DP/ZeRO 的选择**:
  - 模型一层都放不下 → 必须 TP(唯一能切层内的)。
  - 层能放下但总层数太多 → PP。
  - 显存够、要加吞吐/扩 batch → DP + ZeRO。
- **精度**:BF16/FP16 下 all-reduce 的求和顺序影响数值;大规模下要用 FP32 梯度累加或 BF16 + stochastic rounding。toy 里 ~1e-6 的"无害误差",在低精度大模型上可能累积成训练不稳定。

### 3.2 线上常见故障与调优

1. **不整除导致崩溃或静默错误**:`d_ff`、`num_heads`、`vocab_size` 不能被 TP size 整除。vocab 要 padding 到整除(Megatron 会自动 pad 到 128 的倍数,兼顾 tensor core 对齐)。toy 的 `assert` 就是这个坑的预演。
2. **RNG 不一致 → 等价性破坏**:Dropout 等随机算子在各 rank 必须用**协调过的种子**(同一 token 位置 mask 一致,或 SP 下各管各的)。种子管理错会让 TP 结果偏离单卡基线——对应 toy"权重要同源"那条坑的放大版。
3. **NCCL hang / 拓扑错配**:TP group 没放进同一 NVLink 域,all-reduce 走了 PCIe 甚至跨节点 IB,吞吐暴跌;rank↔GPU 映射错误会直接 NCCL timeout。务必让 TP 进程绑同节点相邻 GPU。
4. **通信成为瓶颈而非计算**:用 nsys/torch profiler 看 all-reduce 占比,若 >30% 多半是没开 SP / 没做重叠 / TP 切太碎。
5. **激活显存爆**:忘开 SP 和**激活重算(activation/gradient checkpointing)**,长序列下激活吃光显存。SP + 选择性重算是标配。
6. **数值不收敛**:低精度 + loss scaling 配置不当;或 LayerNorm 没在正确精度(通常 FP32)下算。
7. **load/save 切分不一致**:checkpoint 是按某个 TP size 切存的,换 TP size 重启要 reshard,工具链没对齐会加载错位。

## 4. 性能直觉与估算

下面给可手算的量级公式(记号:`P` = 参数量,`N` = TP size,`L` = 层数,`b` = batch,`s` = seq len,`h` = hidden,`B` = 每参数字节数)。

### 4.1 显存估算

- **权重显存(切后)**:训练用混合精度时,每参数约需 **16~18 字节**(FP16 权重 2 + FP16 梯度 2 + FP32 master 4 + Adam m/v 各 4 ≈ 16,Megatron 实现约 18)。TP 把权重相关部分切到 `1/N`:
  `权重类显存 ≈ 16 × P / N`(字节)。
- **激活显存**:正比于 `b × s × h × L`。TP 把 Attention/MLP 激活切到 `1/N`;SP 进一步把 LayerNorm/Dropout 那部分也切到 `1/N`;激活重算可把它压到约 `√L` 量级。
- **KV cache(推理)**:`2 × b × s × h × L × B / N`(2 = K 和 V),TP 切 head 即切到 `1/N`。

快速例子(量级):一个 ~7B 模型纯权重 FP16 约 14GB,训练态优化器+梯度+master 约把它推到 100+ GB,**单卡 80GB 放不下 → 至少 TP=2 或上 ZeRO**。这就是 TP 存在的第一动机。

### 4.2 通信量估算

- **每次 all-reduce 的通信量**(ring all-reduce):每 rank 收发约 `2 × M × (N-1)/N` 字节,`M` 为张量字节数。N 大时趋近 `2M`,**与 N 几乎无关**——这就是"切得越多通信次数不变、单次量也不怎么降"的来源。
- **每层每 step 的 all-reduce 次数**:前向 2 + 反向 2 = **4 次**(toy 注释那句)。整模型 ≈ `4 × L` 次。
- **SP 的妙处**:reduce-scatter + all-gather 的总量 ≈ 一次 all-reduce,所以 SP 省显存不加通信。

### 4.3 加速比 / 扩展性直觉

理想线性加速被通信吃掉,粗略模型:

```
有效加速比 ≈ N / (1 + 通信时间/计算时间)
其中  计算时间 ∝ 1/N (被切小)
      通信时间 ≈ 常数 (all-reduce 量与 N 弱相关)
```

所以 **N 越大,通信/计算比越高,边际收益递减**。在 NVLink 节点内 TP=8 通常仍划算;一旦 TP 跨节点(通信时间陡增),加速比会掉到远低于 N。**这定量解释了"TP 不跨节点"的铁律。** 矩阵越大(算力越足)、互联越快,TP 越能撑到大 N。

## 5. 动手进阶路线

把 toy 往生产推,建议分 5 步,每步都能独立验证:

1. **把 `for` 循环换成真多进程 NCCL**。用 `torch.distributed` + `torchrun` 起 N 个进程,每进程绑一张 GPU(或 CPU gloo 后端先跑通逻辑);把 `CommCounter.all_reduce_sum` 换成真正的 `dist.all_reduce(tensor, op=SUM)`。验证:多 rank 跑出的 `Y` 与单卡 baseline 仍 `allclose`。

2. **补 Attention 块 + 反向**。实现 QKV 列并行(按 head 切)、输出投影行并行;把 `f`/`g` 写成 `torch.autograd.Function`(前向/反向通信互换),用 `torch.autograd.gradcheck` 或对比单卡梯度验证反向正确。此时每层应观察到前向 2 次、反向 2 次 all-reduce。

3. **加序列并行 SP + 激活重算**。把 LayerNorm/Dropout 改沿 seq 维切,TP 边界换成 reduce-scatter/all-gather;给每层包 `torch.utils.checkpoint`。验证:激活显存随 SP/重算下降,数值仍等价。

4. **上混合精度 + 处理不整除**。改 BF16 计算 + FP32 master,加 vocab/head padding 到可整除并对齐 128;验证低精度下仍收敛、误差在可接受带内。

5. **与 PP/ZeRO 组合,搭最小 3D 并行**。先 TP=2 × DP=2 跑通,再叠 PP 或接 DeepSpeed ZeRO;profile all-reduce 占比,尝试异步通信做计算-通信重叠。验证:扩到多节点后吞吐随卡数近线性(节点内 TP、跨节点 PP/DP)。

走完这 5 步,你手里的就不再是 toy,而是一个"麻雀虽小五脏俱全"的 Megatron 缩影。
