# FlashAttention · 面试题库

> 本题库覆盖 FlashAttention 的核心：online softmax 递推、IO-aware（HBM/SRAM 内存层级）、为何「省显存不省 FLOPs」、与朴素注意力的数值等价（精确而非近似）、tiling 两层循环、causal mask、v1→v2→v3 演进。**面什么岗会问**：大模型推理/训练优化、AI-Infra、GPU kernel（CUDA/Triton）、算法工程师（LLM 方向）。答案均可结合本项目 `flash_attention.py`（纯 PyTorch、CPU 可跑、float64 对拍）作答。

---

## 一、基础题（概念是否懂）

### Q1. 一句话说清 FlashAttention 解决了什么问题？

**参考答案**：朴素注意力要把 $S = QK^\top/\sqrt{d}$ 这张 $n\times n$ 的分数矩阵**整张物化（materialize）到 HBM**，再 softmax、再乘 $V$，中间矩阵显存是 $O(n^2)$，且这张大矩阵要在 HBM 里反复写出/读回，使注意力变成**访存受限（memory-bound）**。FlashAttention 通过**分块 tiling + online softmax**，在片上（SRAM）逐块计算、边算边累加，**永不物化完整的 $n\times n$ 矩阵**，把额外中间显存降到 $O(n)$、把 HBM 访存次数从 $O(n^2)$ 降到约 $O(n^2/M)$（$M$ 为 SRAM 容量），从而提速并支持长上下文。

**追问**：它是不是一种「近似注意力」（如 Linformer/Performer 那类）？
> 不是。FlashAttention 是**精确（exact）注意力**——输出与标准 softmax attention 在数学上完全相等，差异只到浮点舍入。本项目用 float64 对拍，`max abs error ≈ 4e-16`（机器精度量级），`torch.allclose(atol=1e-10)=True`，正是「精确而非近似」的硬证据。

---

### Q2. 为什么朴素注意力的显存是 $O(n^2)$？

**参考答案**：因为它显式构造了两张 $n\times n$ 中间矩阵：分数矩阵 $S=QK^\top$ 和 softmax 后的权重矩阵 $P=\mathrm{softmax}(S)$。本项目 `naive_attention` 里对应 `S = (Q @ K^T) * scale` 和 `P = torch.exp(S - m); P = P/P.sum(...)`。`memory_footprint_elements` 把它算成 `2*n*n`。当 $n=8192$ 时仅这两张矩阵就有 $1.34\times10^8$ 个元素（fp16 约 256MB），且这只是**一个头、一层、一条样本**。输出 $O$ 本身只有 $n\times d$，问题在于「只想要小的 $O$，却被迫先造一张和 $n^2$ 同量级的中间矩阵」。

**追问**：那 FlashAttention 的额外显存具体是多少？
> 本项目 `flash_extra = block_q*block_k + 2*block_q + block_q*d`，即临时分数块 `s_blk(Br×Bc)` + 行状态 `m,l(各 Br)` + 累加器 `acc(Br×d)`，**完全不含 $n$**，对每个 Q 块是常数。整体显存的 $O(n)$ 来自最终输出 $O$（$n\times d$）本身。

---

### Q3. softmax 为什么要「减去最大值」？分块时这件事为什么变难？

**参考答案**：直接算 $e^{x_j}$ 在 $x$ 较大时会上溢成 `inf`。标准做法是减去每行最大值 $m=\max_j x_j$：
$$\mathrm{softmax}(x)_i=\frac{e^{x_i-m}}{\sum_j e^{x_j-m}}$$
分子分母同乘 $e^{-m}$ 结果不变，但所有指数输入 $\le 0$，$e$ 值落在 $(0,1]$，绝不上溢。**难点在分块时**：softmax 分母 $\sum_j e^{x_j-m}$ 需要「看完整行」才能确定 $m$ 和分母，而分块一次只能看到一块，看不到整行的真实最大值。FlashAttention 用 **running max** 边看边维护，块来一个就修正一次，看完最后一块时恰好等于完整 softmax。

---

### Q4. online softmax 维护哪三个 running 状态？各自初值是什么？

**参考答案**：针对**每一个 query 行**维护三个累加器（本项目对一个 Q 块就是 `(Br, ·)` 形状）：
- `m` = running max（到目前为止见过的最大分数），初值 `-inf`，形状 `(br,1)`，**只增不减**。
- `l` = running 分母（$\sum e^{s-m}$ 的累加），初值 `0`，形状 `(br,1)`，单调增大。
- `acc` = running 未归一化输出（$\sum e^{s-m}\cdot v$ 的累加），初值 `0`，形状 `(br,d)`，每行仅占 $O(d)$。

`m` 用 `-inf` 是因为 max 要单调，`max(-inf, 任意分数)=该分数`，第一块自然成立，无需特判。

**追问**：为什么 `m` 初值不能用 0？
> 若用 0，当真实分数全为负时，第一块的 max 会被 0 错误压住（`rescale`/`p` 全部以 0 为基准），结果偏差。`-inf` 是 running max 的唯一正确起点。

---

### Q5. FlashAttention 省的是显存还是 FLOPs？为什么？

**参考答案**：**省的是显存占用 + HBM 访存次数，不省 FLOPs**。矩阵乘的总浮点运算量（$QK^\top$、$PV$）和朴素注意力是一样的——同样要算 $n^2 d$ 量级的乘加。FlashAttention 甚至因为要在分块循环里**重算（recompute）**部分指数/rescale，FLOPs 可能略增。但它把数据搬运（HBM read/write）大幅减少。因为 GPU 上注意力是**访存受限**的，瓶颈在带宽而非算力，所以减少访存就直接换来 wall-clock 加速。**一句话：用一点点重算的 FLOPs，换掉大量的 HBM 访存。**

**追问**：本项目在 CPU 上为什么看不到加速、甚至更慢？
> CPU 没有 SRAM/HBM 这种显式内存层级，且本 demo 用 Python `for` 循环逐块（解释器开销大），所以比朴素**更慢**。它证明的是**数值等价 + 显存复杂度**两件事，不是速度。真实加速来自把分块融进**一个** CUDA/Triton kernel，避免中间结果落 HBM。

---

### Q6. 什么是 IO-aware？为什么注意力是 memory-bound？

**参考答案**：IO-aware 指算法设计时**显式考虑不同存储层级之间的数据搬运成本**（GPU 上 SRAM 极快但极小、几十~上百 KB/SM；HBM 大但带宽是瓶颈），并以「最小化慢速 HBM 的读写量」为优化目标，而非只看 FLOPs。注意力是 memory-bound 是因为：$QK^\top$、softmax、$\cdot V$ 这几步**算术强度（arithmetic intensity，FLOPs/Byte）低**——要为相对少的计算搬运巨大的 $n\times n$ 矩阵进出 HBM，GPU 的算力闲着、带宽被打满。FlashAttention 把整条链路**融合（fuse）**进片上，让 $n\times n$ 矩阵根本不落 HBM，从而把瓶颈从带宽解放出来。

---

### Q7. 本项目用 `float64` 而不是 GPU 常用的 fp16，为什么？

**参考答案**：目的是证明「算法精确等价」，要把**低精度舍入**这个干扰项彻底排除。float64 机器精度约 $10^{-16}$，若 Flash 与朴素对不上，那一定是**算法写错了**而非精度问题。对拍结果 `max abs error ≈ 4.4e-16`、`torch.allclose(atol=1e-10)=True`，误差小到接近机器精度才有说服力。真实工程跑 fp16/bf16 会有正常的低精度误差（属于另一回事）；如果把 `DTYPE` 改成 float32，就得把 `atol` 放宽到 `1e-5` 量级再判 PASS，否则会误报 FAIL。

**追问**：fp16 下 FlashAttention 还「精确」吗？
> 在「同一精度下与朴素 fp16 attention 等价」的意义上仍是精确的（无算法近似）；但 fp16 本身的舍入会带来误差。实际 kernel 常把 softmax 的累加（$l$、$m$、$acc$）放在 fp32 累加以保稳定，最后再转回低精度。

## 二、进阶题（原理与权衡）

### Q8. 推导 online softmax 的合并公式，并解释 `rescale` 的本质。

**参考答案**：设某行被切成若干块，新块分数 $S_{blk}$、对应 $V_{blk}$。更新四步：

1. 更新 max（只增不减）：$m_{new}=\max(m_{old},\ \mathrm{rowmax}(S_{blk}))$
2. **rescale 修正因子**（灵魂）：旧累加器里的项是按 $m_{old}$ 算的（即 $e^{s-m_{old}}$），现在基准升到 $m_{new}$，需统一乘 $e^{m_{old}-m_{new}}$ 才能换算：
$$e^{s-m_{old}}\cdot e^{m_{old}-m_{new}}=e^{s-m_{new}},\qquad \mathrm{rescale}=e^{m_{old}-m_{new}}\in(0,1]$$
3. 新块权重（已按新基准）：$p=e^{S_{blk}-m_{new}}$
4. 合并：$l_{new}=\mathrm{rescale}\cdot l_{old}+\mathrm{rowsum}(p)$，$\ acc_{new}=\mathrm{rescale}\cdot acc_{old}+p\,V_{blk}$

收尾只归一一次：$O=acc/l$。**rescale 的本质**：把「按旧最大值基准累加的旧结果」翻译到「新最大值基准」，使分块累加与一次看全行**代数等价**——这正是 FlashAttention 精确的根本原因。本项目 6 步代码（`m_new=maximum(m,m_blk)`→`rescale=exp(m-m_new)`→`p=exp(s_blk-m_new)`→更新 `l`/`acc`→`m=m_new`）与此一一对应。

**追问**：为什么 `rescale` 乘到 `l`/`acc` 而不乘到 `p`？
> `p=e^{S_{blk}-m_{new}}` 已经是按新基准算的，无需修正；需要修正的是「按旧基准 $m_{old}$ 算出来的旧累加值」`l_old`/`acc_old`。

---

### Q9. 代码里 `m = m_new` 这行为什么必须放在内层循环最后？

**参考答案**：因为 `rescale = torch.exp(m - m_new)` 用的是**旧** `m`（$m_{old}$）。如果先执行 `m = m_new`，那 `rescale` 就变成 `exp(m_new - m_new)=1`，所有历史累加都不再被正确缩放，结果全错。所以更新顺序必须是：先用旧 `m` 算 `rescale` 和（间接）合并，**最后**才滚动 `m = m_new`。这是写 online softmax 最常见的 bug 之一（本项目「常见坑」里专门列了这条）。

---

### Q10. FlashAttention 如何处理 $n$ 不能被块大小整除的尾块（ragged tail）？

**参考答案**：靠 Python 切片自动截断 + 读实际行数。`qi = Q[i:i+block_q]` 当 `i+block_q>n` 时自动只取到 `n`；关键是用 `br = qi.shape[0]` 读**实际**行数（尾块更小），所有行状态 `m,l,acc` 按 `br` 而非写死 `block_q` 创建；写回 `O[i:i+block_q] = acc/l` 时左右两边形状一致。本项目 `main` **故意**取 `block_k=24` 除不尽 `n=128`（128/24=5 块余 8，尾块只 8 行）来逼出边界 bug，仍 PASS。真实 GPU kernel 里则用 **mask/边界判断** 把越界位置的分数设 `-inf`（贡献 $e^{-\infty}=0$）来处理。

**追问**：如果有人把尾块写死成 `block_q` 会怎样？
> 在不整除时会越界或形状不匹配而崩溃；即使不崩，把尾块当成满块会引入虚假的 padding 行参与 softmax，污染结果。必须读 `qi.shape[0]`。

---

### Q11. FlashAttention v1、v2、v3 的核心区别是什么？

**参考答案**：
- **v1（2022, arXiv:2205.14135）**：奠基。tiling + online softmax + recompute（反向不存 $S/P$，靠保存的 $m,l$ 重算），把注意力做成 IO-aware 的 exact kernel。
- **v2（2023, arXiv:2307.08691）**：主要是**并行与工作划分优化**。关键改动：把外层循环改为遍历 **Q 块**（每个 Q 块的 online softmax 独立、可并行，且 rescale 只需作用于该块的 `acc`），减少非矩阵乘（如 rescale/exp）的开销与线程间通信；更好地利用 warp 划分；causal 场景跳过纯被 mask 的块。本项目「外层遍历 Q 块、内层遍历 K/V 块」正是 **v2 视角**。
- **v3（2024，面向 Hopper H100）**：利用新硬件特性——**异步**（TMA 搬运、warp-specialization 让计算与数据搬运重叠 producer/consumer）、**FP8** 低精度、与 Tensor Core 的 wgmma 流水线，进一步逼近峰值算力。

**追问**：v2 把外层从 K 块改成 Q 块带来什么好处？
> v1 外层遍历 K 块时，多个 K 块对同一 Q 行的累加要跨循环做 rescale，且 reduction 维度的并行不友好。v2 让每个 Q 块**独占**一组 online 状态、内层扫 K/V，块间可完全并行（映射到 GPU 线程块），rescale 只在该 Q 块内进行，显著减少同步与非 matmul 开销。

---

### Q12. 反向传播怎么做？为什么要 recompute？

**参考答案**：朴素反向需要前向存下的 $S$、$P$（$n\times n$），这又把 $O(n^2)$ 显存吃回来了。FlashAttention 的做法是**前向不保存 $S/P$，只保存每行的归一化统计量**（最终的 $m$、$l$，即 logsumexp，仅 $O(n)$）。反向时**重新分块计算** $S_{blk}$、$P_{blk}$（用保存的 $m,l$ 直接还原归一化权重，无需重跑 max 扫描），再算梯度 $dQ,dK,dV$。这是用**少量重算 FLOPs 换显存**：反向同样不物化 $n\times n$，保持 $O(n)$ 显存。代价是反向比「存 $S/P$ 直接复用」多算一遍 $S$/$P$，但在 memory-bound 场景这笔账划算。

---

### Q13. causal mask（因果掩码）在 FlashAttention 里怎么加？有什么优化空间？

**参考答案**：让每个 query 只看到自己及之前的 key。本项目练习给的做法：算完 `s_blk` 后把「未来位置」分数设 `-inf`：
```python
row_idx = torch.arange(i, i + br).unsqueeze(1)          # 全局行号
col_idx = torch.arange(j, j + kj.shape[0]).unsqueeze(0) # 全局列号
s_blk = s_blk.masked_fill(col_idx > row_idx, float("-inf"))
```
$e^{-\infty}=0$，被遮位置贡献为 0，online softmax 自然处理，与「朴素 + 同样 mask」对拍仍 PASS。**优化空间**：对纯粹位于下三角之外的整块（`j` 整体 > `i` 的块），所有位置都被 mask，可**直接 skip 不计算**——v2 利用这点把 causal 注意力的计算量近似砍半；对角线上跨边界的块才需要逐元素 mask。

**追问**：加了 causal mask 后对拍要注意什么？
> 必须给 `naive_attention` 加**同样**的 mask 才能对拍，否则两边语义不同。

### Q14. 怎么扩展到 batch + multi-head？真实 kernel 怎么并行？

**参考答案**：把 $Q/K/V$ 从 $(n,d)$ 扩到 $(B,H,n,d)$，最外层套 `for b, for h` 复用单头逻辑——每个 $(b,h)$ 是一次独立注意力。**真实 CUDA kernel** 不写这两层 Python 循环，而是把 `(batch, head, Q块)` 三个维度映射到 **GPU grid 的并行 block**：每个线程块负责一个 Q 块，独立持有 online softmax 状态，内层在寄存器/SRAM 里流式扫 K/V 块。这正是 v2 强调的「沿 batch、head、Q-block 三向并行」，把 SM 占满。

**追问**：块大小 `block_q/block_k` 由什么决定？
> 真实 kernel 里由 **SRAM 容量**决定（要装下 $Q_i$、$K_j$、$V_j$、$S_{blk}$ 等），典型 64/128。本项目取 16/24 只为在 toy 规模看清分块逻辑。块越大越能摊薄访存、但受片上容量限制，是显存/并行度/访存的三方权衡。

## 三、深入 / 手撕题（能否动手 / 追问到底）

### Q15.【手撕思路】请描述如何从零实现一个 tiling + online softmax 的注意力（结合本项目）。

**参考答案**（本项目 `flash_attention` 的骨架）：
1. 预备：`scale = 1/sqrt(d)`；分配输出 `O = zeros(n, d)`（唯一的「大」缓冲，是结果不是中间态）。
2. **外层遍历 Q 块** `for i in range(0, n, block_q)`：取 `qi=Q[i:i+block_q]`，`br=qi.shape[0]`（读实际行数防尾块）；初始化该块状态 `m=-inf(br,1)`、`l=0(br,1)`、`acc=0(br,d)`。
3. **内层遍历 K/V 块** `for j in range(0, n, block_k)`：取 `kj,vj`；
   - `s_blk = (qi @ kj.T) * scale`（$Br\times Bc$，**全函数最大临时张量，绝非 $n\times n$**）；
   - `m_new = maximum(m, rowmax(s_blk))`；
   - `rescale = exp(m - m_new)`（用旧 `m`）；
   - `p = exp(s_blk - m_new)`；
   - `l = rescale*l + rowsum(p)`；`acc = rescale*acc + p @ vj`；
   - `m = m_new`（**放最后**）。
4. 收尾：`O[i:i+block_q] = acc / l`（**每个 Q 块只归一化一次**）。
5. 验证：用 float64 与 `naive_attention` 对拍，`torch.allclose(atol=1e-10)` 应为 True。

要点：全程无 $n\times n$ 张量；归一化只在 Q 块收尾；尾块靠切片+`shape[0]`；首块 `m=-inf` 使 `rescale=exp(-inf)=0`，旧累加器被乘 0 自动清零，无需特判。

**追问**：把归一化 `acc/l` 误放进内层每个块会怎样？
> 中间值不再是「未归一化累加器」，后续 `rescale*acc` 的代数关系被破坏，结果全错。归一化必须延后到该 Q 块所有 K/V 块处理完。

### Q16. 怎么向面试官证明你的实现是「精确」而不是「碰巧接近」？

**参考答案**：本项目用了**四重证据**：
1. **高精度对拍**：用 float64（机器精度 $\sim10^{-16}$），`max abs error ≈ 4.4e-16`、`mean ≈ 4.6e-17`，远小于 `atol=1e-10` → `allclose=True`。误差量级正是浮点末位舍入，证明算法层面零误差。
2. **退化案例（edge case）**：令 `block_q=block_k=n`（整序列一块），online softmax 退化为普通 softmax，误差仍 `~6.7e-16`。
3. **故意不整除的块**：`block_k=24` 除不尽 `n=128`，专测尾块仍 PASS。
4. **压力测试**：20 组随机输入重复对拍，worst-case `~1.5e-15`，ALL PASS，排除「某组输入运气好」。

**追问**：为什么误差不是恰好 0？
> 浮点加法不满足结合律，分块累加和一次性求和的运算顺序不同，末位舍入会有 $\sim10^{-16}$ 的差异。这是**浮点而非算法**误差，无法也无需消除。

### Q17. 给定 $n=8192,\ d=128$，估算朴素 vs FlashAttention 的中间显存，并解释长上下文为何只能靠它。

**参考答案**：朴素中间矩阵 $S+P=2n^2$ 个元素 $=2\times8192^2\approx1.34\times10^8$，fp16 下约 **256MB**（仅一头一层一样本）。一个 32 头、几十层的模型，光注意力中间矩阵就会爆几十上百 GB，显存直接撑爆。FlashAttention 每个 Q 块额外状态 `block_q*block_k + 2*block_q + block_q*d`，**不含 $n$**，是常数（本项目默认约 928 个元素）；整体显存 $O(n)$ 来自输出 $O$（$n\times d$）。本项目显存账表显示 ratio 从 $n=128$ 的 35× 涨到 $n=8192$ 的约 14.5 万×。**结论**：朴素随 $n$ **平方**增长（$n$ 翻 4 倍中间矩阵翻 16 倍），几万 token 时不可行；FlashAttention 让中间显存与 $n^2$ 脱钩，这是长上下文（long context）能跑起来的根本原因。

**追问**：FLOPs 是否也随 $n^2$？
> 是。FlashAttention **不改变** $O(n^2 d)$ 的计算量，只改变显存/访存。所以超长上下文最终仍受**算力**和**带宽**约束，需要进一步配合 sparse/sliding-window/线性注意力等思路才能突破 $n^2$ 计算墙。

### Q18. FlashAttention 与 KV Cache 是什么关系？推理时怎么配合？

**参考答案**：两者正交、可叠加。**KV Cache** 解决自回归**解码**时的重复计算：把历史 token 的 $K,V$ 缓存下来，每步只算新 token 的 $q$ 对全部缓存 $K,V$ 的注意力（避免重算前缀），但缓存本身占 $O(n)$ 显存。**FlashAttention** 解决**单次注意力的中间矩阵**显存与访存。解码阶段每步是 $1\times n$ 的注意力（一个 query 对 $n$ 个 key），同样可用 online softmax 分块扫 KV cache，避免物化 $1\times n$ 的中间向量并减少 HBM 读。Prefill 阶段（处理长 prompt）是标准 $n\times n$ 注意力，FlashAttention 收益最大。延伸：PagedAttention（vLLM）进一步解决 KV cache 的显存碎片，与 FlashAttention 的 kernel 思路互补。

**追问**：decode 阶段（query 只有 1 行）FlashAttention 还划算吗？
> 此时是 memory-bound 的 GEMV-like 计算，瓶颈在把 KV cache 从 HBM 读进来。FlashDecoding 等变体在 **KV 序列维**做并行切分（split-K）来打满带宽/SM，是对这一场景的专门优化。

---

### Q19. 为什么说「重算（recompute）反而更快」违反直觉但成立？

**参考答案**：直觉上「重算 = 多做 FLOPs = 更慢」，但在 memory-bound 场景成立的原因是：在 GPU 上，**从 HBM 读一个已存好的 $n\times n$ 矩阵的时间，远大于在片上用已有 $Q,K$ 重新算一遍它的时间**——算术单元（Tensor Core）算力极其充裕、常常空转，而 HBM 带宽是瓶颈。所以前向不存 $S/P$、反向重算，省掉的 HBM 往返 >> 多花的算力。这正是 IO-aware 的精髓：**用便宜的 FLOPs 换昂贵的访存**。本项目「省 FLOPs 还是省显存」的结论（不省甚至略增 FLOPs、大省显存与访存）就是这套权衡的具体化。

### Q20. 如果让你给本项目的纯 PyTorch 实现做工程化，从「能跑」到「真加速」要改什么？

**参考答案**：本项目证明了**数值等价 + 显存账**，但用 Python `for` 循环逐块、解释器开销大、且不利用 GPU 内存层级，所以 CPU 上比朴素还慢。工程化关键：
1. **kernel 融合**：把外/内两层循环 + softmax + 两个 matmul 融进**一个** CUDA/Triton kernel，让 $S_{blk}$ 全程留在寄存器/SRAM，**绝不落 HBM**——这是真正的加速来源。
2. **并行映射**：把 `(batch, head, Q-block)` 映射到 GPU grid 的 thread block（v2 的并行策略），warp 内做 reduction。
3. **块大小调优**：按 SRAM 容量取 `block_q/block_k`（64/128 量级），平衡片上占用与访存摊薄。
4. **低精度 + 高精度累加**：matmul 用 fp16/bf16/fp8 走 Tensor Core，`m/l/acc` 累加用 fp32 保稳定。
5. **causal skip / masking**：跳过全 mask 块。
6. **算 logsumexp 供反向**：前向额外存每行 $m,l$（$O(n)$）以支持 recompute 反向。

**追问**：为什么不直接用 PyTorch 自动微分而要手写反向 kernel？
> autograd 会保存计算图中间张量（含 $n\times n$），把省下的显存吃回去。手写反向 + recompute 才能在反向也维持 $O(n)$ 显存，这是 FlashAttention 的关键工程点。

## 高频追问速答清单

1. **FlashAttention 是近似吗？** 不是，是 exact，与标准 attention 数学等价（误差仅浮点舍入）。
2. **省 FLOPs 还是省显存？** 省显存 + HBM 访存；FLOPs 不省（甚至略增，因 recompute）。
3. **额外显存复杂度？** 中间状态每 Q 块为常数，整体 $O(n)$（来自输出）；朴素是 $O(n^2)$。
4. **online softmax 的灵魂？** `rescale = exp(m_old - m_new)`，把旧累加器换算到新最大值基准。
5. **三个 running 状态？** running max `m`（初 -inf）、running sum `l`（初 0）、未归一化输出 `acc`（初 0）。
6. **归一化做几次？** 每个 Q 块收尾**只除一次** `acc/l`，绝不放内层。
7. **`m=m_new` 放哪？** 内层循环**最后**，因为 `rescale` 要用旧 `m`。
8. **为什么 memory-bound？** 注意力算术强度低，搬 $n\times n$ 矩阵进出 HBM 吃光带宽。
9. **v2 相对 v1 主要改了啥？** 外层改遍历 Q 块、优化并行/工作划分、减少非 matmul 开销、causal skip。
10. **反向怎么省显存？** 不存 $S/P$，只存 $m,l$（logsumexp），反向 recompute，维持 $O(n)$。
11. **块大小由什么定？** SRAM 容量，典型 64/128；本项目用小值仅为演示。
12. **与 KV Cache 关系？** 正交可叠加；KV Cache 省解码重算，FlashAttention 省单次注意力的访存/显存。
