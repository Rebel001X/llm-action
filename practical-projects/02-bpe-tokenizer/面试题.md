# BPE 分词 · 面试题库

> 本题库覆盖 subword tokenization 的核心：BPE / WordPiece / Unigram 三大路线、byte-level BPE、词表大小取舍、OOV、数字/多语言/代码切分、tokenizer 对模型效果与成本的影响。适用于**大模型算法岗、AI-Infra / LLM 推理岗、数据工程岗**的面试。答案均可结合本目录 `bpe_tokenizer.py`（教学 toy 实现）与 `手把手教学.md` 印证。

---

## 一、基础题（概念是否懂）

### Q1. 为什么大模型要做 subword 分词？按字符切和按整词切各有什么致命问题？

**参考答案：** 模型只能吃整数 id，任何文本进模型前都要切成 token。三条历史路线：
- **字符/字节级**：词表极小（字节才 256）、永不 OOV，但**序列太长**。Self-attention 是 $O(n^2)$，序列翻倍算力翻 4 倍，上下文窗口被严重浪费。
- **整词级**：序列短，但**词表爆炸 + OOV**。英语单词加时态/拼写/新词上百万还装不下；没见过的词直接变 `<UNK>`，信息全丢；中文/emoji/代码更是灾难。
- **subword（BPE 等）**：折中——让数据决定哪些片段值得当一个 token。高频整词合成单 token，低频/未见词退化成小片段甚至单字节，照样拼得出。本质是**同时拿到「序列短」与「永不 OOV」两个好处**。

**追问：** 既然字符级永不 OOV、词表又小，为什么 GPT 系列不直接用字符级？
> 因为序列长度是推理/训练的硬成本（注意力 $O(n^2)$、KV cache 线性增长、context 窗口浪费）。subword 用「学高频组合」把序列压短约 3-4x（本项目 toy 实验里 `shrunk 2.97x`），在序列长度和 OOV 之间取得最优权衡。

---

### Q2. 用一句话说清 BPE 的训练过程。

**参考答案：** BPE 原本是数据压缩算法：**反复统计相邻符号对（pair）的频率，把出现最多的那一对合并成一个新符号，循环到词表达到目标大小**。搬到分词上：每个词初始是它的字节序列，每轮 `get_pair_counts` 统计相邻 pair（按词频加权），`argmax` 取最高频 pair，记一条 `merges[(a,b)]=new_id` 规则、把它应用到所有词，重复 `vocab_size - 256` 次。本项目 `train()` 正是这个三步循环。

**追问：** 训练得到的两张核心表是什么？
> `merges: dict[(int,int)->int]`（合并规则，**插入顺序=学习顺序=encode 优先级**）和 `vocab: dict[int->bytes]`（每个 id 对应字节串，0..255 是单字节，≥256 = 两个父 token 字节拼接）。

---

### Q3. 什么是 byte-level BPE？相比在 Unicode 字符上做 BPE 有什么好处？

**参考答案：** byte-level BPE 先把字符串编码成 UTF-8 字节（0..255）再做 BPE，而不是在 Unicode 字符上做。好处：
1. **初始词表天然只有 256 个**（在字符上做，base 词表是全体 Unicode 码点，十几万个，且仍可能漏）。
2. **永不 OOV、round-trip 永远无损**：任何 Unicode 文本（中文、emoji、生僻符号）都能表示为字节序列，哪怕一条 merge 都没学到也能逐字节还原。本项目 `decode(encode("中文也能无损 round-trip 🚀")) == 原文` 即 `ok=True`。
3. 这正是 GPT-2 论文采用 byte-level 的关键原因。

**追问：** GPT-2 既然是 byte-level，为什么还需要 `bytes_to_unicode` 那个映射表？
> GPT-2 把 0..255 字节映射到一组「可打印且不与空白冲突」的 Unicode 字符，是为了让正则预切分和可视化/避免控制字符，纯属工程 trick；本质仍是字节级，merge 规则跑在这层可逆映射之上。

---

### Q4. encode 时是怎么把文本切成 token 的？为什么必须按「学习顺序」合并？

**参考答案：** 先 `text.encode("utf-8")` 得到字节序列，然后**反复挑当前序列里优先级最高（= 最早学到 = new_id 最小）的可合并 pair 并合并**，直到没有规则可用。本项目核心一行：
```python
candidate = min(pairs, key=lambda p: self.merges.get(p, float("inf")))
```
没学过的 pair 返回 `inf`，`min` 取 id 最小者。**必须按学习顺序**是因为：train 时先学 A 再学 B，B 往往以 A 的产物为原料（「滚雪球」），encode 若乱序合并会切出与训练分布不一致的 token 序列，破坏一致性。

**追问：** decode 为什么能保证无损？
> vocab 存的是**字节**，新 token 字节 = 父 token 字节拼接。decode 只是按 id 查字节再 `b"".join` 拼接、UTF-8 解码。无论 encode 怎么合并，拆回字节一定逐字节等于原始字节 → `decode(encode(x)) == x` 对任意 Unicode 成立。

---

### Q5. 什么是压缩率（compression ratio）？它和模型成本有什么关系？

**参考答案：** $\text{ratio} = \dfrac{\#\text{tokens}}{\#\text{bytes}}$。不学任何 merge 时每字节一个 token，ratio = 1.0（baseline）；每学一条 merge 高频组合被压短，token 数下降，ratio 下降。本项目实验里 vocab 从 256→350，ratio 从 1.0→约 0.34，`shrunk ≈ 2.97x`。

意义：**序列变短直接等价于上下文窗口变大、训练/推理算力下降**（attention $O(n^2)$、KV cache、FLOPs、按 token 计费的 API 成本全和序列长度挂钩）。同一段文本 token 越少，模型「看得更远、算得更省、付费更少」。

**追问：** 压缩率随词表无限增大会怎样？
> **收益递减**。最高频的几条 merge 贡献最大（本项目 vocab=280 只学 24 条 merge 就把 token 砍掉约 42%），后面学的都是低频对，省得越来越少；同时词表越大 embedding/softmax 矩阵越大、稀有 token 训练不充分。所以词表大小是个 trade-off。

---

### Q6. BPE 训练时常见的「提前停止」条件是什么？为什么需要？

**参考答案：** 本项目两个条件：
- `if not pair_counts: break`——每个词只剩 1 个 token，没有相邻 pair 可合。
- `if best_count < 2: break`——最高频的 pair 也只出现 1 次，再合并只是「记住一个孤例」，泛化意义不大，浪费词表槽位。

这就是为什么 toy 语料小时跑 `vocab_size=300`（理论 44 条）可能学不满。生产中也常设最低频阈值（min frequency）来过滤噪声/拼写错误。

**追问：** 不设 `best_count < 2` 会有什么害处？
> 会把一次性出现的随机字节组合也吃进词表，产生大量「只服务于训练集某处」的死 token，挤占词表、稀释 embedding 训练，对未见文本毫无帮助。

---

### Q7. BPE、WordPiece、Unigram 三者核心区别是什么？分别被谁用？

**参考答案：**
| 方法 | 合并/选择准则 | 训练方向 | 代表模型 |
| --- | --- | --- | --- |
| **BPE** | 选**频率最高**的相邻 pair 合并（贪心计数） | bottom-up 合并 | GPT-2/3、LLaMA、RoBERTa |
| **WordPiece** | 选使**语言模型似然增益最大**的 pair，准则约为 $\frac{\text{count}(ab)}{\text{count}(a)\cdot\text{count}(b)}$（互信息式） | bottom-up 合并 | BERT、DistilBERT |
| **Unigram LM** | 先建大词表，按**移除后语言模型似然损失最小**的原则反复**剪枝**；切分时用 Viterbi 取概率最大切分 | top-down 剪枝 + 概率模型 | T5、ALBERT、XLNet、多语言模型（SentencePiece 默认） |

一句话：BPE 看「频率」，WordPiece 看「似然增益/互信息」，Unigram 是「概率模型 + 剪枝 + 全局最优切分」。

**追问：** WordPiece 的 `##` 前缀和 BPE 的处理有什么不同？
> WordPiece 用 `##` 标记「词内非首」子词（如 `playing → play ##ing`），靠前缀区分词首/词中；GPT-style BPE 则把空格信息编进 token 本身（GPT-2 的 `Ġ` 前缀代表前导空格），不用显式 `##`。

---

### Q8. 为什么 BPE 训练要先做 pre-tokenization（预切分），而不是把整篇文本拉直了统计？

**参考答案：** 预切分（通常按空白/正则切成「词」）的作用是**防止跨词边界合并**——我们不希望「上一个词的末字节」和「下一个词的首字节」被当成相邻对合并出无意义的跨词 token。本项目用 `line.split()` 做 toy 版预切分，并按词存 `word_freqs`，天然把词与词隔开。真实 GPT-2 用一个正则（把空格、标点、数字、字母分别成组）做更细的预切分。

**追问：** 本项目 toy 预切分有什么已知局限？
> `line.split()` 丢掉了词间空格，所以**空格不参与 merge**（README 局限表已列）。真实 GPT-2 用 `Ġ` 把前导空格并入词，能完全还原排版、且让「空格+词」成为可合并单元。本项目练习 5 就是补这个能力。

## 二、进阶题（原理与权衡）

### Q9. 词表大小（vocab size）怎么取？太大太小各有什么问题？

**参考答案：** 这是一个多目标权衡：
- **太小**：序列长（压缩率差），训练/推理成本高、上下文浪费；稀有概念被切碎，长尾表达能力弱。
- **太大**：① embedding + output softmax 矩阵随 vocab 线性增大，显存/参数量上升；② 稀有 token 训练样本少、embedding 学不充分；③ 边际压缩收益递减。

工程经验值：英文/代码模型常见 **32K–50K**（GPT-2 50257、LLaMA-1 32K），多语言模型为覆盖众多语种常 **100K–256K**（LLaMA-3 128K、GPT-4 cl100k≈100K、Gemma 256K）。选择需结合：语种数、领域（代码需要更大）、目标序列长度、embedding 预算。

**追问：** 增大词表一定能降推理总成本吗？
> 不一定。序列变短省了 attention/KV，但更大的 embedding/softmax 增加每步成本与显存，且 logits 维度变大。对短序列任务可能得不偿失；通常对长文本/多语言收益明显。要按实际负载 profile。

---

### Q10. byte-level BPE 真的「永不 OOV」，但它就没有 OOV 类的问题了吗？

**参考答案：** 「永不 OOV」只是说**永远能被表示并无损还原**，但并不代表「被切得好」。对训练语料里**没学过组合的文本，会退化成接近逐字节**：本项目里中文/emoji 在英文语料上训练后 `34 bytes → 34 tokens`（几乎没合并），虽 `ok=True` 但**压缩率极差、序列暴长**。这就是「token 公平性」问题——某些语言/字符被切得过碎，等价于该语言用户付更多 token 费、占更多上下文、效果也更差。所以 byte-level 解决的是「无损」，没解决「对所有语言都高效」。

**追问：** 怎么缓解这种多语言不公平？
> 训练 tokenizer 时**让语料语种分布更均衡**（对低资源语种上采样），或为重要语种保证一定词表配额；用 SentencePiece/Unigram 在多语场景往往更稳。代价是英语效率可能略降。

---

### Q11. tokenizer 为什么会影响数字运算和代码能力？

**参考答案：**
- **数字**：若把多位数当整体或按不一致的方式切（如 `1234` 可能被切成 `12|34` 或 `123|4`），同一个数在不同上下文切法不同，模型难以学到稳定的逐位算术。改进：**逐位切分数字**（GPT-3.5/4 之前一些模型把 3 位一组，LLaMA 把数字逐位 split），让「位」对齐，算术更稳。
- **代码**：缩进（空格/tab）、`==`、`!=`、`->`、`<\=` 等是高频组合，好的 code tokenizer 会把它们合成单 token；早期通用 tokenizer 把连续空格切碎，导致 Python 缩进占用大量 token、效率和效果都差。GPT-3.5 起对**连续空格/缩进做专门合并**（如 tab、多空格成组）大幅提升代码效率。

**追问：** 为什么「逐位切数字」要写进 pre-tokenization 规则而不是靠 BPE 自己学？
> 因为 BPE 是频率贪心，会自然把 `00`、`000`、年份等高频数字串合并成单 token，导致切法依赖上下文、不规整。用正则在预切分阶段**强制把数字按固定粒度（逐位或定长组）切开**，是一种结构先验，保证一致性。

---

### Q12. 同一个词在不同位置（带空格 vs 不带空格、句首 vs 句中）会被切成不同 token，这会带来什么问题？

**参考答案：** GPT-style BPE 把前导空格编进 token，所以 `"hello"`（句首/无空格）和 `" hello"`（前面有空格）是**不同的 token**。后果：
- 同一个语义单元有多套 token 表示，**embedding 被分摊、样本效率下降**。
- 容易踩坑：prompt 末尾多/少一个空格会改变下一个 token 的切分，影响生成（经典 "trailing whitespace" bug）；few-shot 模板对空格敏感。
- 评测/约束解码时若不注意空格变体，会算错概率或匹配失败。

**追问：** 实际工程怎么规避空格切分坑？
> 模板里统一空格风格、避免行尾多余空格；对受限生成/打分，按 tokenizer 实际切分（而非肉眼字符串）对齐；必要时用 tokenizer 的 `add_prefix_space` 等参数显式控制。

---

### Q13. BPE 的 encode 复杂度是多少？生产级实现（tiktoken）做了哪些优化？

**参考答案：** 本项目 toy `encode` 每轮 `set(zip(...))` 重扫整条序列找最优 pair，整体约 **$O(n^2)$**（n 为序列长度）。生产优化：
- **正则预切分** 把长文本切成短 chunk，BPE 只在 chunk 内跑，n 很小。
- **缓存**：对相同 word/chunk 缓存切分结果（绝大多数词重复出现）。
- **更优数据结构**：用链表 + 优先队列（堆）维护可合并 pair，把每次找 best pair 降到近 $O(n\log n)$ 或线性。
- **Rust/C 实现 + 批处理 + 并行**（tiktoken、HF tokenizers 都是编译型 + 多线程）。

**追问：** 为什么 train 阶段每轮都要 `get_pair_counts` 重新全量统计，能优化吗？
> 能。朴素实现每轮 $O(\text{语料})$，整体 $O(\text{merges}\times\text{语料})$。优化是**增量更新**：合并一个 pair 只影响它周围的局部 pair 计数，用堆 + 受影响位置的增量维护，避免全量重扫（HF tokenizers 即如此）。

---

### Q14. 给定 token 序列，BPE 的切分是「确定且唯一」的吗？和 Unigram 有何不同？

**参考答案：** BPE encode 是**确定性贪心**——给定 merges，按优先级合并，结果唯一（不考虑随机化时）。它**不保证全局最优切分**（不是最少 token 数），只是按学习顺序的局部贪心。Unigram 则把切分当**概率推断**：词表里每个子词有概率，用 **Viterbi 找全局似然最高的切分**，且天然支持**subword regularization**——训练时按概率采样不同切分做数据增强（BPE 对应的版本叫 **BPE-dropout**，以概率丢弃某些 merge 制造多样切分）。

**追问：** subword regularization / BPE-dropout 有什么用？
> 训练时让同一文本有多种切分，相当于数据增强，提升对切分扰动的鲁棒性、改善低资源/形态丰富语言效果。推理时一般关掉用确定性切分。

---

### Q15. tokenizer 的「健康度」怎么评估？上线前该看哪些指标？

**参考答案：**
1. **无损性**：`decode(encode(x)) == x` 对覆盖各语种/emoji/代码的样本全 True（本项目 round-trip 校验）。
2. **压缩率 / fertility**：tokens/word 或 tokens/byte，分语种统计，警惕某语种被切得过碎。
3. **词表覆盖与利用率**：是否有大量从未被用到的死 token；高频 token 分布是否合理。
4. **数字/代码切分一致性**：抽样检查 `1234`、缩进、运算符的切法。
5. **特殊 token / 边界**：`<bos>`、`<eos>`、`<pad>`、空格变体是否处理正确，有无安全相关的可注入 token。

**追问：** 「fertility」具体指什么？
> Fertility = 平均每个词（或每个 Unicode 字符）被切成多少 token。fertility 越接近 1 越高效；某语种 fertility 远高于英语，说明该语种被切碎、成本与效果都吃亏。

---

### Q16. 训练好的 tokenizer 能在已训练的 LLM 上随意更换吗？

**参考答案：** **不能随意换**。tokenizer 和模型是绑定的：embedding 矩阵、output 层都是按这套 vocab 的 id 学出来的，换 tokenizer 等于换了输入语义，需要**重训/大规模继续训练**。常见可控操作：
- **扩词表（vocab expansion）**：给基座加领域/语种新 token，新增 embedding 行随机/均值初始化，再继续预训练让新 token 学起来（如中文社区给 LLaMA 加中文词表）。
- **完全换 tokenizer** 通常意味着从头训或大成本对齐，一般不做。

**追问：** 给 LLaMA 扩中文词表大概要注意什么？
> ① 新 token embedding 初始化（用其原 BPE 子词 embedding 的均值通常比随机好）；② 要继续预训练让新 token 与原参数对齐；③ 控制新增量避免破坏原能力；④ 同步更新 output 层。

## 三、深入 / 手撕题（能否动手 / 追问到底）

### Q17.（手撕思路·结合本项目）请描述如何从零实现一个 byte-level BPE 的 `train`，并给出关键数据结构与循环。

**参考答案：** 按本项目 `bpe_tokenizer.py` 的结构：

1. **初始化两张表**：`merges = {}`；`vocab = {i: bytes([i]) for i in range(256)}`（256 个字节基座）。
2. **预切分 + 词频**：把语料按空白切词，每词 `tuple(word.encode("utf-8"))`，统计 `word_freqs: dict[tuple->int]`。
3. **主循环** `num_merges = vocab_size - 256` 次：
   - `get_pair_counts(word_freqs)`：对每个词 `zip(symbols, symbols[1:])` 取相邻 pair，**按词频加权累加**。
   - `best_pair, best_count = pair_counts.most_common(1)[0]`（argmax）。
   - 提前停：`not pair_counts` 或 `best_count < 2`。
   - 分配 `new_id = 256 + step`，记 `merges[best_pair] = new_id`，`vocab[new_id] = vocab[a] + vocab[b]`（**父字节拼接 → 保证无损**）。
   - `merge_pair_in_word` 把规则应用到所有词，重建 `word_freqs`。

关键代码（合并一个 pair）：
```python
def merge_pair_in_word(symbols, pair, new_id):
    a, b = pair
    out, i = [], 0
    while i < len(symbols):
        if i < len(symbols)-1 and symbols[i]==a and symbols[i+1]==b:
            out.append(new_id); i += 2      # 命中相邻对 -> 合并, 跳两格
        else:
            out.append(symbols[i]); i += 1
    return tuple(out)
```

**追问 1：** `merge_pair_in_word` 遇到 `(a, a, a)` 怎么处理，会不会重叠合并？
> 从左到右贪心扫描：先合并前两个 a 成 new_id 并跳两格，再看第三个 a，**不会重叠合并**。这是 BPE 标准约定。

**追问 2：** 为什么 word 序列要用 `tuple` 而不是 `list`？
> 因为它要当 `word_freqs` 的 dict key，必须不可变（hashable）。

### Q18.（手撕思路·结合本项目）实现 `encode`，并解释那行 `min(pairs, key=...)` 为什么等价于「按学习顺序合并」。

**参考答案：**
```python
def encode(self, text):
    ids = list(text.encode("utf-8"))
    while len(ids) >= 2:
        pairs = set(zip(ids, ids[1:]))
        candidate = min(pairs, key=lambda p: self.merges.get(p, float("inf")))
        if candidate not in self.merges:   # 全是 inf -> 无规则可用
            break
        ids = list(merge_pair_in_word(ids, candidate, self.merges[candidate]))
    return ids
```
`merges` 的 value 是 `new_id = 256 + step`，**越早学到的 pair，new_id 越小**。`self.merges.get(p, inf)` 把没学过的 pair 记为 `inf`；`min(...)` 取 id 最小者 = 最早学到 = 优先级最高的可合并 pair。每轮挑一个全局最高优先级 pair 合并，**和 train 的学习顺序严格一致**，因此切出的 token 序列与训练分布对齐。

**追问 1：** 这种「每轮重扫挑 min」的写法和「按 merges 顺序逐条遍历应用一遍」等价吗？
> 在结果上等价（都尊重优先级），但复杂度不同。逐条遍历是 $O(\text{merges}\times n)$；本写法是每轮选一个最优，循环到收敛，约 $O(n^2)$。生产用堆 + 缓存优化。

**追问 2：** 如果一段文本里某个 pair 学过、但合并后又产生了更高优先级的新 pair，会漏吗？
> 不会。`while` 循环每轮重新 `set(zip(...))` 重算当前序列的所有 pair，新产生的高优先级 pair 会在下一轮被选中——这正是要放在循环里重扫的原因。

### Q19. BPE 训练能否做到「合并一个 pair 只增量更新计数」而非每轮全量重扫？请说明思路。

**参考答案：** 可以，这是生产实现的关键优化。思路：
- 把每个词存成**双向链表**节点（或带前后指针的数组），维护每个 pair 当前出现的位置集合，以及一个**最大堆**按频率排序所有 pair。
- 每轮从堆顶取 best pair，合并它的所有出现位置。合并 `(a,b)→Z` 在位置 i 处时，**只有局部受影响**：消失的 pair 是 `(left, a)`、`(a,b)`、`(b, right)`，新产生的是 `(left, Z)`、`(Z, right)`。对这些 pair 做计数增减并更新堆。
- 这样每次合并的代价正比于「该 pair 出现次数」而非整个语料，整体远快于朴素 $O(\text{merges}\times\text{语料})$。HF tokenizers / sentencepiece 即采用类似增量法。

**追问：** 增量更新里最容易出 bug 的地方？
> ① 处理同一位置相邻重复（`a a a` 或 `a b a b`）时位置失效/重复计数；② 堆里残留过期 pair 计数（用「惰性删除 + 取出时校验当前真实计数」处理）；③ 链表删除节点后前后指针的衔接。

### Q20. 现在要给一个英文基座模型加上对中文/代码的支持，但只能改 tokenizer 不能从头训，你怎么做？权衡是什么？

**参考答案：** 走 **vocab expansion + 继续预训练** 路线：
1. 在**目标领域语料**（中文 + 代码）上单独训练一批新 merge / 新 token，挑高频且原 tokenizer 切得过碎的子词加入词表（控制新增数量，如 +20K–60K）。
2. **扩 embedding 与 output 层**：新 token 的 embedding 用「它在原 tokenizer 下被切成的子词 embedding 的均值」初始化（比随机收敛快、保留语义先验）。
3. **继续预训练 / 持续训练**：在混合语料上训练，让新 token 与原参数对齐；注意混入英文防遗忘（rehearsal）。
4. **验证**：分语种 fertility 下降、round-trip 无损、英文能力无明显回退。

权衡：新增 token 越多中文/代码越高效，但 embedding/softmax 变大、训练成本上升、且有破坏原能力的风险；不扩词表则中文/代码继续被切碎（如本项目里中文几乎逐字节），成本高效果差。这是「效率 vs 成本/风险」的取舍。

**追问：** 如果完全不想改模型，有没有低成本缓解中文切碎的办法？
> 几乎没有「免费午餐」。可在应用层做提示压缩/缓存，但 token 级低效是 tokenizer 决定的，根本解还是扩词表 + 继训。

### Q21. 设计题：为一个「中英 + 大量代码」的模型从头设计 tokenizer，你的关键决策有哪些？

**参考答案：**
1. **算法**：byte-level BPE（保证无损、对代码/罕见符号鲁棒）；多语场景也可考虑 Unigram(SentencePiece)。
2. **词表大小**：偏大，约 64K–128K，给中文和代码留足配额。
3. **训练语料配比**：英文/中文/代码按目标使用分布配比，对中文适当上采样以免被英文挤压（避免 token 不公平）。
4. **pre-tokenization 规则**：
   - **数字逐位切**（保证算术一致性）；
   - **空格/缩进专门处理**（连续空格、tab 成组，对 Python/代码至关重要）；
   - 保护常见代码运算符 `==`、`!=`、`->`、`::` 等成单 token。
5. **特殊 token**：`<bos>/<eos>/<pad>/<unk>` 以及可能的聊天/工具调用控制 token，预留 id 段。
6. **评估**：分语种 fertility、round-trip、代码缩进切分、词表利用率。

**追问：** 为什么代码模型尤其在意空格/缩进切分？
> Python 用缩进表达语法块，连续空格极高频。若被切碎，每行缩进吃掉大量 token → 序列暴长、上下文浪费、模型还难学缩进结构。把缩进成组合并能显著提升代码任务的效率与正确性。

### Q22.（追问到底）本项目 toy 实现和工业级 tiktoken / HF tokenizers 的差距具体在哪几处？

**参考答案：**（对照 `手把手教学.md` 局限表）
1. **预切分**：toy 用 `line.split()`，丢词间空格、不保留排版；工业用正则细切并把空格编进 token（GPT-2 `Ġ`）。
2. **数字/代码无专门规则**：toy 任 BPE 自由合并；工业对数字逐位、空格成组等加结构先验。
3. **性能**：toy encode/train 是 $O(n^2)$ / 每轮全量重扫；工业用增量计数 + 堆 + 缓存 + Rust 多线程。
4. **special tokens / 词表序列化**：toy 没有 `<bos>/<eos>`、没有保存/加载词表；工业有完整的特殊 token 管理与序列化。
5. **subword regularization**：toy 是纯确定性；工业可支持 BPE-dropout / Unigram 采样。
6. **正确性边界**：toy 靠 byte-level 保证无损，但切分质量随语料；工业 tokenizer 经大规模多语语料训练，切分更均衡。

**追问：** 既然差距这么大，写这个 toy 的价值是什么？
> 它把 BPE 最核心的「频率统计 → 贪心合并 → merges/vocab → 无损 round-trip → 压缩率」讲透，是理解一切工业实现（minbpe→tiktoken）的最小心智模型；面试手撕 BPE 要的就是这套骨架。

## 高频追问速答清单

1. **BPE 选 pair 的准则？** 频率最高（贪心 argmax），WordPiece 用似然增益，Unigram 用概率剪枝。
2. **byte-level 为何永不 OOV？** 任何 Unicode 都能拆成 0..255 字节，base 词表 256 全覆盖。
3. **decode 为何无损？** vocab 存字节，新 token 字节 = 父字节拼接，拆回逐字节等于原始。
4. **encode 按什么顺序合并？** 按学习顺序，挑 new_id 最小（最早学到）的可合并 pair。
5. **压缩率定义？** tokens/bytes，baseline=1.0，越小序列越短、越省算力。
6. **词表越大越好吗？** 不是；压缩收益递减 + embedding/softmax 变大 + 稀有 token 学不好。
7. **典型 vocab size？** 英文 32K–50K，多语 100K–256K。
8. **数字为什么要逐位切？** 保证同一数在不同上下文切法一致，利于算术。
9. **代码 tokenizer 关键点？** 缩进/连续空格成组、运算符成单 token。
10. **能随便换 tokenizer 吗？** 不能，与 embedding/output 绑定；扩词表需继续预训练。
11. **BPE 切分是全局最优吗？** 不是，是贪心；Unigram 用 Viterbi 求全局最优切分。
12. **多语言不公平怎么来的？** 低资源语种被切碎，fertility 高 → 更贵更差；靠均衡语料缓解。
