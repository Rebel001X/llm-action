# KV Cache · 面试题库

> 这份题库覆盖 KV Cache 的原理、显存占用公式、prefill vs decode 两阶段差异、为什么 decode 是访存(memory-bound)瓶颈、batch/长序列下的显存爆炸,以及在此之上的系统级优化(PagedAttention / MQA-GQA / 量化 / offload / prefix caching)。这是**大模型推理(LLM Inference)/ AI-Infra / 推理引擎(vLLM、TGI、TensorRT-LLM、SGLang)** 岗位的必考内容,中高级算法/工程岗几乎逢面必问。答案尽量结合本项目 `kv_cache.py` 的 toy 实现作答。

---

## 一、基础题(概念是否懂)

### Q1. 什么是 KV Cache?它解决了什么问题?

**参考答案:**
KV Cache 是自回归(autoregressive)生成时,把每层每个历史 token 的 Key、Value 张量缓存下来、供后续步骤复用的机制。

它解决的问题是**朴素自回归生成的重复计算**:每生成一个新 token,都要做一次注意力,而注意力需要"当前 query 对所有历史 token 的 K/V"。在 decoder-only 因果模型里,历史 token 的 K/V 不会因为追加新 token 而改变,所以没必要每步重算整段。把 K/V 缓存后,每步只对**新来的 1 个 token**算 Q/K/V,再与缓存的全部历史 K/V 做注意力。

本项目 `kv_cache.py` 用 toy GPT 对比了两条路径:`generate_no_cache`(每步整段重算)和 `generate_with_cache`(prefill + decode),并用 `torch.equal` 断言两者**逐 token 输出完全相同** —— KV Cache 只加速,不改变结果。

**追问:为什么叫 KV Cache 而不是 QKV Cache?Q 为什么不缓存?**
因为注意力是"用**当前** token 的 Q 去查询**所有历史** token 的 K/V"。Q 是查询者,每步都换成新 token 的全新 Q,旧 Q 后续用不上;K/V 是被查询的历史库,可以累积复用。代码里 `forward` 只把 `k, v` 用 `torch.cat([k_past, k], dim=2)` 追加进 cache,`q` 不进 cache。

---

### Q2. KV Cache 为什么能成立?它的数学/物理前提是什么?

**参考答案:**
两个支柱:
1. **因果性(causality)→ 历史 K/V 不变。** decoder-only 用 causal attention,位置 $i$ 只能看到 $\le i$。位置 $j$ 的 $K_j, V_j$ 仅由"位置 $j$ 自己的输入"决定,不依赖任何排在它后面的 token。所以在末尾追加新 token 时,前面所有历史的 K/V 完全不变 → 可缓存。
2. **LayerNorm / MLP 是逐 token(per-token)运算。** 这两个子层不跨 token 混合信息,对"单个新 token"算和对"整段"算,对应位置结果一致。注意力是唯一跨 token 的部分,而它的等价性由第 1 点保证。

本项目 `Block.forward` 的注释明确点出了第 2 点,这是 KV Cache 数学等价的另一半原因。

**追问:Encoder(双向注意力,如 BERT)能用 KV Cache 吗?**
不能(也没必要)。双向注意力里,加一个 token 会改变所有位置能看到的上下文,历史的 K/V 表征会变;而且 encoder 不是逐 token 自回归生成,是一次性并行编码,不存在"每步重算历史"的问题。KV Cache 是自回归 + 因果这一特定场景的优化。

---

### Q3. Prefill 和 Decode 两个阶段分别是什么?

**参考答案:**
- **Prefill(预填充)**:把整段 prompt 一次性喂进模型,并行算出所有 prompt token 的 Q/K/V 与注意力,**建立初始 KV Cache**,并产出第一个新 token。这是一次性的整段计算,所有 prompt token 可并行,是**计算密集(compute-bound)**的。
- **Decode(解码)**:之后每步只喂 1 个新 token,复用并扩展 KV Cache,产出下一个 token。每步只算 1 个 token 的 Q/K/V,但要读取整个 KV Cache。它是**逐 token 串行**的,**访存密集(memory-bound)**。

本项目 `generate_with_cache` 严格按这两阶段写:前半段 prompt 整段过一遍存进 `caches`(prefill),后半段 `for` 循环每次只 `forward_step` 一个 token(decode)。

**追问:为什么 prefill 可以并行而 decode 不能?**
prefill 时整段 prompt 已知,可以一次矩阵运算把所有位置的注意力算出来;decode 时下一个 token 依赖上一个 token 的输出(自回归),必须串行,这是逻辑上的依赖链,无法在单个序列内并行化(speculative decoding 等是另想办法绕过)。

### Q4. 写出 KV Cache 的显存占用公式,并解释每一项。

**参考答案:**
单个序列、单 batch 的 KV Cache 总字节数:

$$\text{mem} = 2 \times L \times s \times n_{kv} \times d_h \times b_{\text{dtype}}$$

- `2`:K 和 V 两份;
- `L`:层数(num layers);
- `s`:序列长度(已缓存的 token 数,= prompt + 已生成);
- `n_kv`:KV 头数(MHA 时 = 注意力头数 `n_head`;GQA/MQA 时是更小的 KV 头数);
- `d_h`:每个头的维度 `head_dim`;
- `b_dtype`:每个元素字节数(fp16/bf16 = 2,fp8/int8 = 1)。

注意 $n_{kv} \times d_h$ 在 MHA 下就等于 `n_embd`(hidden size)。带 batch 时再乘 batch size `B`。

**举例(说明量级):** 一个 ~7B 模型,$L=32$,hidden=4096(MHA, $n_{kv}\times d_h=4096$),fp16。每 token 每层每方向 K/V = $4096\times2=8192$ B;乘 2(K+V)、乘 32 层 = $2\times32\times4096\times2 \approx 512$ KB/token。序列 2048 token 就约 **1 GB**;batch=16 就约 **16 GB** —— 已经能把一张卡的显存吃满。

> 注:这是公式推导的量级估算,不是某次真实 benchmark 的精确值。

**追问:KV Cache 显存随什么线性增长?哪些超参能压它?**
随 **序列长度 `s`** 和 **batch size `B`** 线性增长。可压缩的维度:`n_kv`(用 GQA/MQA 把 KV 头数砍小)、`b_dtype`(KV 量化到 int8/fp8 减半)、`L/d_h`(模型结构,推理期不可调)、以及 offload(把 cache 挪到 CPU/磁盘)。

---

### Q5. 不用 KV Cache,自回归生成的计算复杂度是多少?用了之后呢?

**参考答案:**
- **无 cache**:第 $t$ 步要重算 $t$ 个 token 的 Q/K/V 和注意力,生成 $n$ 个 token 总工作量 $\sum_{t=1}^{n} t = \frac{n(n+1)}{2} = O(n^2)$。
- **有 cache**:每步只算 **1 个**新 token 的 Q/K/V,总工作量 $\sum 1 = n = O(n)$(这里指"需要算 Q/K/V 的 token 数";单步的注意力打分仍是新 token 对 $t$ 个历史的 $1\times t$,但省掉了对历史重算 Q/K/V 与历史之间注意力的二次开销)。

本项目末尾打印的 "Complexity intuition" 把这点摊开:生成 8 个 token,no_cache 累计算 `1+2+...+8=36`(O(n²)),with_cache 只算 `1×8=8`(O(n))。这是脱离计时噪声、最干净的复杂度证据。

**追问:既然降到 O(n),加速比为什么还随序列变长而增大?**
因为无 cache 是 $O(n^2)$、有 cache 是 $O(n)$,两者比值 $\propto n$,序列越长差距越大。本项目实测加速比随 gen_len `16→32→64→128` 单调上升(toy 上约 1.5x→2.3x 量级)。

---

### Q6. 为什么 toy 模型上加速比只有约 2x,而真实大模型能到几十倍?

**参考答案:**
因为 toy 模型太小,**固定开销**(token/位置嵌入、LayerNorm、Python 循环、张量创建/拼接、kernel launch)占比很高,把"省下来的注意力计算"稀释了。真实大模型里,层数/隐藏维巨大,注意力与矩阵乘开销占主导,KV Cache 省下的二次重算占比极大,加速比可达数十倍。但**趋势(随长度增大而上升)在 toy 上已经清晰可见**,这正是本项目想验证的。

**追问:那 KV Cache 在 toy 上有没有可能比无 cache 还慢?**
有可能,尤其首次 warmup 或序列很短时,`torch.cat` 反复创建新张量、Python 单步循环的开销可能盖过收益。本项目用 `torch.set_num_threads(1)` 让计时"诚实",并在多个长度上取趋势,而非只看单点。

### Q7. 本项目里 `pos_offset` 是干什么的?为什么不能省?

**参考答案:**
`pos_offset` 是 decode 时新 token 的**绝对位置下标**(= 已生成序列长度 - 1)。因为本项目用**绝对位置嵌入**(`pos_emb`),decode 时只喂 1 个 token,必须给它配对它**真实位置**的位置嵌入,否则位置信息错位。代码里 `pos = torch.arange(pos_offset, pos_offset + T)` 就是取这个正确位置。

如果把它写死成 0,新 token 的位置嵌入就错了,生成序列会和无 cache 路径不一致,本项目末尾的 `assert match` 会失败。**位置编码对齐是 KV Cache 实现里最常见的 bug 来源。**

**追问:换成 RoPE(旋转位置编码)后,KV Cache 怎么处理位置?**
RoPE 是把旋转直接施加在 Q/K 上的。缓存的应是**已应用对应位置旋转后的 K**(或在写入/读取时保证每个 token 的 K 带的是它自身位置的旋转),decode 时新 token 用它的绝对位置做旋转。关键是缓存的 K 的位置语义要和它在序列中的真实位置一致,不能错位。

## 二、进阶题(原理与权衡)

### Q8. 为什么说 decode 阶段是访存(memory-bound)瓶颈而不是计算瓶颈?

**参考答案:**
decode 每步只处理 **1 个** token:它的 Q/K/V 投影、MLP 都是"矩阵 × 向量"(GEMV),算术强度(arithmetic intensity,FLOPs/Byte)很低。但每步都要:
1. 从显存**读取整个模型权重**(每层 Linear 的权重);
2. 从显存**读取整个 KV Cache**(随序列越长越大)。

也就是说,搬运的数据量远大于实际计算量,GPU 的算力(TFLOPs)用不满,瓶颈卡在**显存带宽(HBM bandwidth)**上。这与 prefill 不同:prefill 是整段并行的"矩阵 × 矩阵"(GEMM),算术强度高,是 compute-bound。

**结论性判断:** decode 的速度上限主要由显存带宽决定 ⇒ 优化方向是"减少要读的字节数"(KV 量化、GQA/MQA 减少 KV、Flash-Decoding 优化访存)和"提高每次读权重摊到的有效计算"(batch、continuous batching 让一次读权重服务多个序列)。

**追问:既然 decode 是 memory-bound,加大 batch 为什么能提升吞吐?**
因为权重只需读一次就能服务 batch 内所有序列(GEMV 变 GEMM,算术强度上升),把带宽利用率摊高,吞吐(tokens/s)上升。但代价是 KV Cache 显存随 batch 线性膨胀,且单请求延迟可能略增 —— 这就是 throughput vs latency 的权衡。

---

### Q9. batch 推理下 KV Cache 为什么会"显存爆炸"?有哪些应对手段?

**参考答案:**
KV Cache 显存 $\propto B \times s \times L \times n_{kv} \times d_h$,其中 batch `B` 和序列长度 `s` 都是乘性因子。线上请求往往长短不一、长度事先未知,朴素做法要按 **max_seq_len 给每个序列预分配**一整块连续显存,于是:
- 短请求也占 max 长度的空间 → **内部碎片**;
- 不同请求长度不同、动态进出 → **外部碎片**;
- 实测有效利用率可能只有一小部分,大量显存浪费。

应对手段:
1. **PagedAttention(vLLM)**:把 KV Cache 切成固定大小的 block(页),像操作系统虚拟内存一样按需分配、用 block table 映射,几乎消除碎片,显存利用率大幅提升(参见 PagedAttention 论文 arXiv:2309.06180)。
2. **GQA / MQA**:减少 KV 头数,直接把 KV Cache 体积砍小(GQA 砍到 1/g,MQA 砍到 1/n_head)。
3. **KV Cache 量化**:K/V 存成 int8/fp8,字节数减半甚至更多。
4. **KV offload**:把不活跃的 cache 挪到 CPU 内存/磁盘,需要时再换回(以带宽/延迟换显存)。
5. **continuous batching**:序列粒度动态拼批,完成的腾出空间立刻给新请求,提高 cache 周转率。

本项目 toy 里 cache 是简单的 `torch.cat` 累积、单序列,没有这些工程问题;但它正是理解上述系统优化的地基(注释里也点了 PagedAttention 等是"如何更省内存/更高吞吐地管理这块 cache")。

**追问:PagedAttention 的 block 大小怎么权衡?**
block 太大 → 内部碎片回升(最后一个 block 没填满的浪费变多);block 太小 → block table 元数据多、寻址/kernel 开销上升。需要在碎片和管理开销间折中(vLLM 常用 16 个 token 一块这一量级)。

---

### Q10. MQA、GQA 是怎么省 KV Cache 的?各自的取舍是什么?

**参考答案:**
- **MHA(Multi-Head Attention)**:每个 query 头都有自己独立的 K/V 头,KV 头数 = `n_head`。KV Cache 最大。
- **MQA(Multi-Query Attention)**:**所有** query 头共享**同一份** K/V(KV 头数 = 1)。KV Cache 砍到 1/n_head,decode 访存大幅下降、吞吐高;但表达能力受限,质量可能略降。
- **GQA(Grouped-Query Attention)**:折中,把 query 头分成 `g` 组,每组共享一份 K/V(KV 头数 = `g`)。KV Cache 砍到 g/n_head。在质量和显存间取平衡,是当前主流(Llama-2/3 70B、Mistral 等都用 GQA)。

省的本质:KV Cache 公式里的 $n_{kv}$ 直接变小,且 decode 时要读的 K/V 字节数同比例下降,缓解 memory-bound。

**追问:把 MHA 模型转成 GQA 要重新训练吗?**
通常需要 **uptraining(继续少量训练)**:把多个 KV 头做 mean-pool 初始化成组共享头,再用少量数据微调恢复质量,而不是从零重训。

---

### Q11. KV Cache 量化要量化什么?有什么坑?

**参考答案:**
量化的是缓存里的 **K 和 V 张量**(不是权重),fp16 → int8/fp8,字节数减半,直接缩小 cache 显存、减少 decode 访存。

坑:
1. **离群值(outliers)**:K(尤其某些通道)常有大幅离群值,per-tensor 量化误差大,通常要 **per-token 或 per-channel** 量化粒度。
2. **K 比 V 更敏感**:K 进 softmax 前要做点积,误差会被指数放大;实践中 K 往往需要比 V 更高精度,或对 K/V 用不同策略。
3. **反量化开销**:decode 读 cache 时要反量化,若 kernel 没融合好,可能吃掉省下来的带宽收益。
4. **累积误差**:长序列下量化误差可能随生成累积,影响长文本质量。

**追问:量化 KV 和量化权重(weight-only quant)解决的是同一个瓶颈吗?**
不完全是。weight-only 量化(如 GPTQ/AWQ)主要减少**读权重**的带宽和模型显存;KV 量化主要减少**读 KV Cache** 的带宽和 cache 显存。长序列/大 batch 下 KV 占比高,KV 量化更关键;短序列下权重读取占主导。两者常叠加使用。

### Q12. prefix caching 是什么?适合什么场景?

**参考答案:**
prefix caching(前缀缓存)是把**多个请求共享的相同前缀**(如同一段 system prompt、few-shot 示例、RAG 拼进去的固定文档)的 KV Cache 算一次、存下来,后续请求命中相同前缀就**直接复用**,跳过这段的 prefill 重算。

适合场景:大量请求共享长 system prompt、多轮对话(历史前缀复用)、agent/工具调用(固定指令模板)、批量评测(同一 prompt 模板)。收益是**显著降低 prefill 计算和首 token 延迟(TTFT)**。

实现上常配合 PagedAttention 的 block 机制做 **block 级共享 + 引用计数 + copy-on-write**(前缀相同的请求共享同一批 KV block,分叉时再复制)。

**追问:prefix caching 命中的前提是什么?为什么是逐 token 前缀匹配?**
前提是 token 序列**完全相同的前缀**(包括位置)。因为 KV 是带位置语义的、且后一个 token 的表征依赖前面所有 token,只有从头开始**逐 token 一致**的前缀,其 KV 才严格可复用;中途出现差异,之后的 KV 都不能共享。

---

### Q13. 既然 KV Cache 占显存,能不能干脆不存、每步重算?这是什么权衡?

**参考答案:**
这是典型的**时间 vs 空间(compute vs memory)权衡**:
- **存 cache**:省计算(O(n²)→O(n)),但吃显存(随 s、B 线性膨胀)。
- **不存、重算**:省显存,但 decode 退化回 O(n²) 重算,而且更糟的是 decode 本就 memory-bound,重算会大量重复读权重,延迟爆炸。

实际几乎一定选"存 cache",因为推理瓶颈在带宽和延迟,重算得不偿失。真正的工程取舍是在"存"的前提下**如何更省地存**:量化、GQA、offload、分页。本项目正是先把"为什么要存(等价 + 加速)"讲透,再引出"怎么省着存"的系统优化。

**追问:有没有"部分重算"的中间方案?**
有。比如 **KV offload** 是把 cache 存到 CPU/磁盘(省显存、不重算,但换回有带宽延迟);某些长上下文方案会**丢弃/压缩远处的 KV**(如只保留窗口内 + 少量 attention sink token,牺牲一点远程信息换显存),这算"选择性不存"。纯重算极少用。

---

### Q14. 长上下文(几十 K~百万 token)下 KV Cache 怎么撑得住?

**参考答案:**
KV Cache $\propto s$,百万级 token 会让 cache 远超显存,核心是**别让它无限线性增长**:
1. **GQA/MQA + KV 量化**:降低每 token 的字节数(常数因子优化)。
2. **Sliding Window Attention(滑动窗口)**:每个 token 只 attend 最近 `w` 个 token,KV Cache 上限封顶为 `w`(Mistral 用过)。
3. **Attention Sinks / StreamingLLM**:保留开头少数几个 "sink" token + 一个滑动窗口,稳住长流式生成。
4. **KV 驱逐/压缩(如 H2O、SnapKV)**:按重要性(注意力得分)驱逐不重要的 KV,只留 heavy hitters。
5. **KV offload + 分页**:把冷 KV 放 CPU/NVMe,按需换入。
6. **分离式架构 / 长上下文专用 attention kernel(Flash-Decoding 等)**:优化超长序列下的 decode 访存。

代价:窗口/驱逐/压缩都是**有损**的,可能丢失远距离信息,需在质量和显存间权衡。本项目练习 5 也演示了"无 cache 截断 vs cache 不截"在超过 block_size 时会破坏等价 —— 真实系统就靠上述策略处理超长上下文。

**追问:滑动窗口下,被移出窗口的 token 信息真的彻底丢了吗?**
不一定。虽然该 token 的 K/V 不再被直接 attend,但其信息已通过前面层层注意力**传播进了窗口内 token 的表征**里(receptive field 随层数扩大),所以是"衰减"而非"完全丢失",但确实弱于全局注意力。

## 三、深入 / 手撕题(能否动手 / 追问到底)

### Q15.【手撕思路 · 结合本项目】请描述一个支持 KV Cache 的因果注意力 `forward(x, kv_cache)` 的核心实现。

**参考答案:**
关键是用**一个** `forward` 同时支持两条路径(无 cache 传整段、有 cache 传 1 个新 token),区别只在是否拼接历史 K/V 和是否需要 mask。核心步骤(对应 `kv_cache.py` 的 `CausalSelfAttention.forward`):

```python
def forward(self, x, kv_cache=None):
    B, T, C = x.shape                       # decode 时 T=1, prefill 时 T=整段
    q, k, v = self.qkv(x).split(C, dim=2)   # 一次投影出 Q/K/V
    q, k, v = map(self._split_heads, (q, k, v))   # -> (B, n_head, T, head_dim)

    if kv_cache is not None:                # decode: 复用历史, 只追加新 token 的 K/V
        k_past, v_past = kv_cache
        k = torch.cat([k_past, k], dim=2)   # 沿时间维拼接 —— 省计算的关键一步
        v = torch.cat([v_past, v], dim=2)
    new_kv_cache = (k, v)                    # Q 不缓存! 只缓存 K/V

    att = (q @ k.transpose(-2, -1)) / math.sqrt(self.head_dim)
    if kv_cache is None:                     # prefill: Tq==Tk, 需要下三角因果 mask
        Tq, Tk = att.shape[-2], att.shape[-1]
        mask = torch.tril(torch.ones(Tq, Tk, dtype=torch.bool))
        att = att.masked_fill(~mask, float("-inf"))
    # else: decode 时 Tq==1, 新 token 在末尾, 天然看到全部历史 -> 无需 mask
    att = F.softmax(att, dim=-1)
    y = (att @ v).transpose(1, 2).contiguous().view(B, T, C)
    return self.proj(y), new_kv_cache
```

要点回答时强调三处:**(1)** 只缓存 K/V 不缓存 Q;**(2)** decode 分支用 `torch.cat` 追加历史;**(3)** decode 时新 token 在序列末尾,因果约束天然满足,**不需要 mask**(只有 prefill 需要下三角 mask)。再补一句位置编码要对齐(decode 用绝对位置 `pos_offset`),这是最容易写错的地方。

**追问:外层生成循环怎么组织 prefill + decode?**
prefill:把 prompt 整段过一遍(`kv_cache=None`),但**保存**每层返回的 `new_kv` 进 `caches`,用最后位置 logits 出第一个 token。decode:循环里每次只把上一个 token `forward_step` 进去,传入对应层的 cache 和 `pos_offset = 当前长度-1`,贪心/采样出下一个,追加。对应本项目 `generate_with_cache`。

### Q16.【手撕思路】上一题的 `torch.cat` 每步新建张量,在线上服务里有什么问题?工程上怎么改?

**参考答案:**
问题:每个 decode step 都 `torch.cat([k_past, k_new])` 会**新分配一块更大的连续显存并整块拷贝**历史,$O(s)$ 拷贝 × $n$ 步 = $O(n^2)$ 的显存搬运 + 频繁分配/释放 → 碎片、带宽浪费、延迟抖动。教学代码无所谓,生产不可接受。

工程改法:
1. **预分配 + 原地写入**:开生成前按上限分配一块 `(B, n_head, max_len, head_dim)` 的 cache,用一个 `cur_len` 指针,每步把新 K/V **写到第 `cur_len` 个 slot**,`cur_len += 1`,不做拷贝。
2. **PagedAttention**:把 cache 切成固定 block,按需追加新 block,用 block table 索引,避免大块连续预分配和碎片,支持变长/共享(prefix caching)。
3. **专用 attention kernel**:用 FlashAttention/Flash-Decoding 类 kernel 直接在分页/连续 cache 上算,融合反量化、避免中间大矩阵物化。

**追问:预分配按 max_len 不是又回到"显存爆炸"了吗?**
是的,固定预分配按最大长度会浪费(短请求占 max 的空间),这正是 PagedAttention 用**按需分页**取代"按 max 连续预分配"的动机:只在真正用到时分配 block,显存利用率大幅提升。

### Q17.【追问到底】给定 decode 的耗时模型,推导单步延迟下界,并说明优化点。

**参考答案:**
decode 每步是 memory-bound,单步延迟下界 ≈ **要读的字节数 / 显存带宽**:

$$t_{\text{step}} \gtrsim \frac{\underbrace{P \cdot b_w}_{\text{读权重}} + \underbrace{2 L \cdot s \cdot n_{kv} \cdot d_h \cdot b_{kv}}_{\text{读 KV Cache}}}{\text{HBM bandwidth}}$$

- 第一项:把所有参数 `P` 读一遍(`b_w` = 权重字节/元素);
- 第二项:把整个 KV Cache 读一遍(随序列 `s` 增长)。

由此读出优化点:
- **减权重字节**:weight-only 量化(int8/int4)→ 缩小第一项;
- **减 KV 字节**:GQA/MQA(↓`n_kv`)、KV 量化(↓`b_kv`)→ 缩小第二项;
- **摊薄权重读取**:batch / continuous batching,一次读权重服务多序列(把第一项除以 B);
- **短序列**早期第一项主导,**长序列**第二项主导 → 长上下文时 KV 优化收益最大。

整段总延迟 ≈ TTFT(prefill,compute-bound)+ 每 token 延迟(TPOT,上式)× 生成长度。

**追问:为什么加大 batch 能降"每 token 平均延迟"但 prefill 不太吃 batch 收益?**
decode 加 batch 把"读一次权重"摊给 B 个序列,GEMV→GEMM,每序列分摊的带宽成本下降;prefill 本就是大 GEMM、compute-bound、算力接近打满,加 batch 主要影响吞吐而非把它从带宽瓶颈里解放出来。

### Q18.【陷阱题】同事说"加了 KV Cache 后模型生成结果变了,质量下降",请帮他定位。

**参考答案:**
KV Cache 在数学上**严格等价**,正确实现下输出应与无 cache 逐 token 相同(本项目用 `torch.equal` 断言)。"结果变了"几乎一定是实现 bug,排查清单:
1. **位置编码没对齐**(最常见):decode 时新 token 用了错误的位置(如一直用 0),绝对位置嵌入/RoPE 错位。检查 `pos_offset`(本项目练习 4 就是故意制造这个 bug 看 assert 失败)。
2. **decode 误加了 mask**:新 token 是最后一个,应能看到全部历史;若错套了为 prefill 写的 mask 逻辑,会屏蔽掉合法历史。
3. **cache 拼接维度/顺序错**:`torch.cat` 用错 `dim`,或新 K/V 拼到了历史前面而非后面。
4. **prefill 没把每层 cache 存对**:漏存某层、或 batch 维错位。
5. **采样随机性误判**:若用了随机采样(非贪心),两条路径浮点细节的微小差异会被采样放大成不同 token —— 这**不是 bug**(本项目练习 3),要对比必须用贪心或共享随机状态。
6. **dtype/数值**:cache 存成更低精度(量化)本身就是**有损**的,质量下降可能是量化引入的,不是 cache 机制错 —— 要和"无损 KV Cache"区分开。

定位方法:先用**贪心解码**让 cache 路径和无 cache 路径跑同一 prompt,`torch.equal` 比对;不等就二分定位是哪一层、哪一步开始偏离。

**追问:如何写一个最小回归测试守住等价性?**
就像本项目 `main()` 做的:固定 seed、贪心解码,对多个生成长度同时跑 `generate_no_cache` 和 `generate_with_cache`,`assert torch.equal(out_no, out_kv)`。任何破坏等价的改动(位置、mask、拼接)都会立刻被这个断言抓到。

### Q19.【系统设计】设计一个高吞吐 LLM 推理服务的 KV Cache 管理模块,要点有哪些?

**参考答案:**
围绕"省着存 + 高周转 + 低碎片"设计:
1. **分页存储(PagedAttention)**:固定大小 block + block table,逻辑连续物理分散,几乎零碎片;变长序列随用随分配 block。
2. **continuous batching**:token 级/迭代级动态调度,完成的请求立刻释放 block 给新请求,提高显存周转和 GPU 利用率(对比静态 batching 要等最慢的)。
3. **prefix caching + COW**:共享前缀的 block 引用计数共享,分叉时 copy-on-write,降低重复 prefill 与显存。
4. **GQA/MQA + KV 量化**:结构上和精度上压小 KV,提升可容纳的并发数(更大 batch)。
5. **抢占与换出(preemption / offload)**:显存不足时按策略把某些序列的 cache swap 到 CPU 或 recompute,保证不 OOM。
6. **PD 分离(Prefill/Decode disaggregation)**:prefill(compute-bound)和 decode(memory-bound)放不同资源池/实例,各自打满,KV Cache 在两者间高效传输(参见 Mooncake、PD分离 等)。
7. **专用 kernel**:FlashAttention / Flash-Decoding 处理大 cache 的访存。

核心指标:显存利用率、并发 batch 大小、TTFT、TPOT、吞吐(tokens/s)。

**追问:PD 分离里,prefill 算好的 KV Cache 怎么交给 decode 实例?这是新瓶颈吗?**
通过高速互联(NVLink / RDMA / 共享显存池)把 prefill 产出的 KV Cache 传给 decode 实例。传输量 = 一份完整 KV Cache,长 prompt 时不小,**KV 传输带宽确实可能成为新瓶颈**,所以 PD 分离要配合高带宽网络、cache 复用(prefix caching)和传输/计算重叠来摊薄(Mooncake 等正是在解决这块)。

## 高频追问速答清单

1. **只缓存什么?** 只缓存 K 和 V,Q 不缓存(Q 是每步全新的查询者)。
2. **为什么能缓存?** 因果性 → 历史 token 的 K/V 不随新 token 改变。
3. **复杂度变化?** decode 计算从 $O(n^2)$ 降到 $O(n)$。
4. **显存公式?** $2\cdot L\cdot s\cdot n_{kv}\cdot d_h\cdot b_{\text{dtype}}$,随序列长度和 batch 线性增长。
5. **prefill vs decode?** prefill 整段并行、compute-bound;decode 逐 token 串行、memory-bound。
6. **decode 为何 memory-bound?** 每步只算 1 token(GEMV),却要读全部权重 + 整个 KV Cache,卡在显存带宽。
7. **显存爆炸主因?** batch × 序列长度,加上按 max_len 预分配造成的碎片。
8. **PagedAttention 解决什么?** 用分页 + block table 消除碎片,提升显存利用率。
9. **GQA/MQA 省什么?** 减小 KV 头数 $n_{kv}$,直接缩小 KV Cache 和 decode 访存。
10. **KV 量化量化谁?** 缓存的 K/V(int8/fp8),坑在离群值和 K 比 V 更敏感。
11. **prefix caching?** 共享前缀(system prompt 等)的 KV 复用,降 prefill 和 TTFT。
12. **加 batch 为何提吞吐?** 一次读权重服务多序列,摊薄 memory-bound 成本(GEMV→GEMM)。
