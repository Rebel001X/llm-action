# 连续批处理 + 分页 KV · 面试题库

> 本题库覆盖 **Continuous Batching(iteration-level scheduling)** 与 **PagedAttention(分页 KV cache)** 两大 LLM 推理服务核心机制：静态批 padding 浪费、迭代级调度、block 显存管理、显存碎片、吞吐/延迟权衡、抢占与换出。
> 适用岗位：**LLM 推理引擎 / AI-Infra / 大模型服务化 / GPU 性能优化**。所有答案可结合本项目模拟器（`paged_batching_sim.py`）代码与现象作答，但模拟器是离散事件 toy（不跑真实算子），具体毫秒/吞吐数字仅反映**趋势**，面试时务必说清这一点，不要把 toy 数字当真实 benchmark。

---

## 一、基础题（概念是否懂）

### Q1. 什么是 prefill 和 decode？两者的计算特征有什么本质区别？

**参考答案：**
- **Prefill**：把整段 prompt 一次性喂进模型，并行算出所有 prompt token 的 KV，写入 KV cache。一次前向处理 `prompt_len` 个 token，是**compute-bound**（大矩阵乘，GPU 利用率高）。
- **Decode**：自回归，每步只生成 1 个新 token，把它的 K/V 追加进 cache，下一步复用前面所有 KV。每步只算 1 个 token 却要读全部模型权重 + 全部 KV，是**memory-bound**（算术强度低，受显存带宽限制）。
- 本质区别：prefill 一次吃多 token、算力密集；decode 一次吐一 token、带宽密集。**批处理对 decode 收益最大**——因为 decode 的固定开销（读权重）可以被一个 batch 内多条请求摊薄。本项目的成本模型 `T_step(n) = T_fixed + T_per_req·n` 就是在抽象 decode 的这个特征。

> **追问 1**：为什么说 decode 阶段「批越大越省」？
> 单 token 平摊成本 = `T_fixed/n + T_per_req`。固定开销 `T_fixed`（kernel launch、读权重）与 batch 内请求数 `n` 无关，所以 `n` 越大，`T_fixed/n` 越小，每 token 越划算。这是连续批处理能提升吞吐的数学根据。
> **追问 2**：prefill 也能从大 batch 受益吗？
> 受益有限。prefill 本身已 compute-bound、GPU 打满，再堆 batch 边际收益小，反而会撑大瞬时 KV/激活显存。真实系统更关注 prefill 与 decode 互相干扰的问题（见进阶题 chunked prefill）。

### Q2. 什么是 KV cache？它为什么是推理显存的大头？

**参考答案：**
自回归生成时，每个已生成 token 的 Key/Value 张量被缓存下来，避免下一步重算。KV cache 大小 ≈ `2(K和V) × num_layers × num_kv_heads × head_dim × seq_len × batch × dtype_bytes`。它随**序列长度线性增长**、随**并发请求数线性增长**，长上下文 + 高并发场景下会迅速超过模型权重本身，成为决定「能并发多少请求」的瓶颈资源，也是 OOM 的主因。正因为它这么贵又随时间增长，「怎么管理 KV 显存」才成了 PagedAttention 要解决的核心问题。

### Q3. 什么是静态批处理（static / request-level batching）？它有哪些浪费？

**参考答案：**
静态批：凑齐 `batch_size` 条请求一起送进模型，**整批同步 prefill、同步 decode、同步返回**，调度单位是「一整条请求」。三大浪费：
1. **右 padding 浪费算力**：batch 内输出长度不齐，整批必须跑到批内最长 `output_len` 步；短请求生成完后仍占着 batch 宽度「陪跑」。本项目代码里体现为 decode 循环 `step_time_ms(len(batch))` 传的是整批宽度而非活跃数。
2. **队头阻塞（head-of-line blocking）**：短请求即使第 5 步就完成，也必须等批内最慢那条跑完才能一起返回，延迟被严重拉高。
3. **凑批 / 等齐发车延迟**：错峰到达时早到请求要干等晚到的，新请求进不来。
4. **KV 显存按 max_seq_len 静态预留**，碎片巨大（见 Q5）。

### Q4. 什么是连续批处理（continuous / iteration-level batching）？核心思想一句话。

**参考答案：**
把调度粒度从「一整条请求」降到「一个 forward step」。每跑完一步都重新调度：**生成完 EOS 的请求当步立即退出并释放显存；等待队列里的新请求当步即时补位进运行批次**。于是「短请求陪长请求跑」和「新请求干等整批结束」两个浪费同时消失。源头是 Orca 论文（iteration-level batching），vLLM 把它和 PagedAttention 结合发扬光大。本项目的 `run_continuous_batching` 主循环每个 step 开头都调 `admit_new()` 补位、step 末尾把 `is_done` 的请求 `kv.free()` + 移出 running，就是它的极简实现。

### Q5. 什么是显存碎片？区分内部碎片和外部碎片。

**参考答案：**
- **内部碎片（internal fragmentation）**：分配出去的空间没被实际用满。静态预留按 `max_seq_len` 给每条请求留连续显存，一条实际只用 13 token 却占了 158 个格子，浪费的就是内部碎片。
- **外部碎片（external fragmentation）**：空闲显存总量够，但被切得不连续，没有一整块连续空间满足新请求的「连续预留」需求。
- 分页方案把 KV 切成固定大小 block 按需分配 → **彻底消除外部碎片**（逻辑连续、物理可不相邻）；内部碎片**最多只剩每条请求最后一块的半空部分**，所以很小。本项目 `fragmentation()` 算的就是内部碎片率 `(已分配块容量 − 实际 token) / 已分配块容量`。

> **追问**：为什么静态预留同时有内部和外部碎片，而分页几乎只剩很小的内部碎片？
> 静态预留要「一整块连续」→ 既留多了（内部）又把空闲空间切碎（外部）。分页把「连续」需求拆成「一堆可不相邻的等大块」，只要还有任意空闲块就能分配，外部碎片消失；唯一没填满的就是每条请求最后一个 block。

### Q6. PagedAttention 的「分页」类比的是操作系统什么机制？映射关系是什么？

**参考答案：**
类比操作系统的**虚拟内存分页（paging）**。映射关系：
- 逻辑上连续的 KV 序列 ↔ 进程的连续虚拟地址空间；
- 固定大小的 KV block（vLLM 默认 16 token）↔ 物理页（page）；
- block table（逻辑块号 → 物理块号映射）↔ 页表（page table）；
- 空闲块列表（free list）↔ 操作系统的空闲页帧管理。
本项目 `PagedKVCache` 里 `req.kv_blocks` 存的是**物理块号列表**（不是 token 本身），`free_blocks` 就是 free list；`allocate` = 弹出空闲块，`free` = 放回。这正是「逻辑序列 ↔ 物理块」映射的极简版。

### Q7. block_size 这个超参意味着什么？太大太小各有什么影响？

**参考答案：**
`block_size` = 每个 KV block 容纳的 token 数（vLLM 默认 16）。它是分页粒度。
- **太小（如 1）**：内部碎片几乎为 0（每块只装 1 token，永远满），但 block 数量爆炸 → block table 变大、分配/索引/kernel 寻址开销变大，且难以做高效的连续内存访问。
- **太大（如 128）**：管理开销小、kernel 访问更连续，但「每条请求最后一块半空」的绝对浪费变大 → 内部碎片回升，短请求尤其吃亏。
本项目练习 2 就是改 `BLOCK_SIZE` 1↔16↔64 观察碎片率变化，对应碎片公式：块越大，最后一块半空的浪费越多。16 是工程上碎片与开销的折中。

> **追问**：blocks_needed 为什么要向上取整？
> `ceil(n_tokens / block_size)`：哪怕只多 1 个 token 超出当前块容量，也要整块新分配——这正是「最后一块可能半空」、内部碎片的来源。

### Q8. 衡量一个推理服务好坏，throughput 和 latency 分别指什么？为什么常常此消彼长？

**参考答案：**
- **Throughput（吞吐）**：单位时间处理的 token 数（tok/s），= 总输出 token / makespan(s)。衡量「系统整体产能」，运营成本相关。
- **Latency（延迟）**：单条请求端到端时间（含排队），`finish - arrival`。常看均值和 **p99 尾延迟**（最差用户体验），SLO 相关。
- **为什么权衡**：堆大 batch 能摊薄固定开销 → 吞吐升，但每条请求要等更大的批一起算、排队更久 → 单请求延迟升。反之追求低延迟就要小 batch / 优先短请求，牺牲吞吐。
- 连续批处理的特别之处：它在**两个指标上同时改善**（吞吐升 + 延迟降），因为它消灭的是「padding 陪跑」「队头阻塞」这种**纯浪费**，不是在 throughput–latency 前沿上做取舍。本项目现象（吞吐约翻倍、平均延迟降得更多）正说明这点。

## 二、进阶题（原理与权衡）

### Q9. 连续批处理相对静态批为什么吞吐和延迟能同时变好？分别从哪来？

**参考答案：**
拆成两个独立来源：
1. **step 数变少**：静态批整批要跑到批内 `max(output_len)` 步，短请求陪长请求空跑的步全是浪费；连续批短请求 EOS 当步退出，不再产生这些步。→ makespan 降、吞吐升。
2. **每步成本变低**：静态批每步按**整批宽度** `len(batch)` 计费（`step_time_ms(len(batch))`），跑完的请求仍占位；连续批每步按**真正活跃数** `len(running)` 计费，跑完的踢出去不再计费。→ 每步更便宜。
- **延迟**还多一层收益：完成即返回（`r.finish_ms = clock` 当步结算），无队头阻塞，短请求不被拖。所以延迟改善幅度通常**比吞吐还大**——吞吐看整体 makespan，延迟看每条请求各自的体验，而连续批专门干掉了「短请求陪跑」这个延迟杀手。

> **追问**：如果负载里所有请求输出长度都一样、且同时到达，连续批还有优势吗？
> 优势会大幅缩小——padding 浪费和队头阻塞几乎消失，两者退化到接近。这说明**长尾 + 错峰**才是连续批收益最大的场景。本项目 `make_workload` 故意做 25% 长输出 + 泊松到达，就是为放大这个差距（练习 3 删掉长尾即可验证差距收窄）。

### Q10. 解释 step 成本模型 `T_step(n) = T_fixed + T_per_req·n`。为什么这样建模？两策略差别落在哪？

**参考答案：**
来自 roofline 直觉：一次 decode forward 的延迟 ≈ **固定开销**（kernel launch、读模型权重，与并发数无关）+ **每条请求的边际开销**（KV 读取/注意力计算，随活跃请求线性增）。
- 固定项 `T_fixed`：被整批摊薄，是「批越大越省」的根源（`T_fixed/n` 项）。
- 线性项 `T_per_req·n`：批越大该步绝对耗时越大，但单 token 仍更省。
- **两策略用同一个成本函数，唯一差别是传进去的 n**：静态批传 `len(batch)`（整批宽度，含陪跑者），连续批传 `len(running)`（真正活跃数）。这保证对比公平——差距全部来自调度策略本身，而非成本模型偏袒。
- **局限要主动说**：这是手调常数、不跑真实算子，只反映趋势，绝对毫秒数不可外推到真实 GPU（真实里还有显存带宽、attention 随序列长度变化、量化等）。

### Q11. 显存不够时，真实 vLLM 怎么处理？本项目又是怎么简化的？

**参考答案：**
真实 vLLM 有**抢占（preemption）**两种策略：
1. **Recompute（重算）**：把被抢占请求的 KV 全部丢弃，等显存空出来再从头 prefill 重算。省显存、实现简单，适合 prompt 不太长的场景。
2. **Swap（换出）**：把被抢占请求的 KV block 从 GPU 显存换到 CPU 内存（host），恢复时再换回。省去重算，但占用 PCIe 带宽、有拷贝延迟。
通常抢占**最晚到达 / 优先级最低**的请求，腾出 block 给当前 running 批次推进，避免死锁。
**本项目简化**：在 `run_continuous_batching` 里，decode 时 `kv.allocate(r, r.total_len)` 返回 `False`（显存不够追加块）就 `r.generated -= 1` 回退这一步、不推进，相当于把该请求「卡住等下一轮有空再续」。没有真正的换出/重算，是抢占的最极简抽象。

> **追问 1**：recompute 和 swap 怎么选？
> 看 prompt 长度与 PCIe 带宽。prompt 短 → recompute 重算便宜；prompt 长 / 重算贵但带宽充足 → swap。vLLM 默认 recompute，可配置。
> **追问 2**：抢占可能引发什么问题？怎么防？
> **饥饿（starvation）/ 抖动（thrashing）**：同一请求被反复抢占重算，永远跑不完。防护：抢占有优先级与配额、保证最少 running 数、避免循环抢占同一条。

### Q12. 在线流量下，prefill 和 decode 互相干扰，怎么解决？（chunked prefill / disaggregation）

**参考答案：**
问题：prefill 是 compute-bound 的大算子，一旦插进 decode 批次，会**阻塞**正在 decode 的请求一大步，造成 decode 的 ITL（inter-token latency）尖刺；反之只做 decode 又让 GPU 算力闲置。两类解法：
1. **Chunked prefill（分块预填充）**：把长 prompt 的 prefill 切成若干小块，与 decode 请求**混在同一个 batch** 里跑，平衡每步的算力占用，避免长 prefill 独占一整步。vLLM 支持，能同时压低 TTFT 和 ITL 抖动。
2. **Prefill/Decode disaggregation（PD 分离）**：把 prefill 和 decode 放到**不同的 GPU/实例**上，各自用最适合的并行与批策略，prefill 算完把 KV 传给 decode 实例。彻底隔离干扰，代价是 KV 要跨节点传输（需高速互联）。SGLang、Mooncake、vLLM 的 disagg 模式都走这条路。
本项目把 prefill 简化成「一个 step 计成本」，没建模这层干扰——这是 toy 与生产的主要差距之一，面试可主动点出作为加分。

### Q13. TTFT、TPOT/ITL、E2E latency 分别是什么？连续批处理对它们各有什么影响？

**参考答案：**
- **TTFT（Time To First Token）**：从请求到达到吐出第一个 token，主要由排队 + prefill 决定。连续批的「即时补位」缩短了排队 → TTFT 改善；但若把长 prefill 插入会伤已在跑请求（chunked prefill 缓解）。
- **TPOT / ITL（Time Per Output Token / Inter-Token Latency）**：相邻输出 token 间隔，决定「打字流畅度」。受每步 batch 大小与抢占影响——批太大或被 prefill 插队，ITL 会抖。
- **E2E latency**：端到端总时长 = TTFT + 解码各步时间，含排队。连续批通过消灭队头阻塞显著降 E2E（本项目 `finish - arrival` 即此）。
- 服务化通常对 TTFT 和 ITL 各定 SLO，再在满足 SLO 前提下最大化吞吐。

### Q14. peak KV slots 这个指标为什么关键？本项目里它揭示了什么现象？

**参考答案：**
peak KV slots = 整个运行过程中 KV 显存占用的峰值（以 token 格子计）。它直接决定「这份负载在给定显存上跑不跑得起来」——超过物理显存就 **OOM**。
本项目现象：静态预留的 peak（约 2528 slots）**超过了物理 KV 池容量 1024**，意味着真实显卡上用静态方案这份负载会 **OOM**；而分页方案把峰值压在池子容量 1024 以内（按需分配 + 完成即释放，峰值≈真实并发所需）。这是 PagedAttention「让显存装下更多并发请求」最直观的体现——不是跑得快一点，而是**根本上让原本跑不起来的负载能跑**。

> **追问**：为什么静态批的 peak KV slots 改小 `TOTAL_KV_BLOCKS` 也不变，而连续批会受影响？
> 静态批是「声称要按 max_seq_len 预留」这么多，是个理论需求量，不看物理池实际有多少（本项目里它只记录预留量、不从池子真扣）；连续批是从真实 free list 弹块，池子小了就更容易触发「分配失败 → 回退/抢占」，所以 step 数可能上升（练习 1 的观察点）。

### Q15. 调度顺序（FCFS vs 优先短请求）怎么影响指标？有什么风险？

**参考答案：**
本项目 `admit_new` 默认按 `waiting` 列表顺序补位，近似 **FCFS（先来先服务）**，公平、无饥饿，但平均延迟一般。
- 改为**优先短请求**（按 `output_len` 升序，类似 SJF/SRTF）：短请求更快走 → **平均延迟下降**，吞吐也可能略好。
- **风险：长请求饥饿（starvation）**——总有短请求插队，长请求迟迟排不上，**p99 尾延迟反而恶化**。
- 工程折中：加 aging（等待越久优先级越高）、配额、或按 SLO/优先级分级调度。这就是真实调度器要权衡的「吞吐/平均延迟 vs 公平/尾延迟」。本项目练习 5 正是让你动手改 `admit_new` 排序观察这个 trade-off。

### Q16. PagedAttention 的 block 共享（copy-on-write / prefix caching）是怎么省显存的？

**参考答案：**
因为 KV 被切成独立 block 且有 block table 间接寻址，**多条请求可以共享物理 block**：
- **Prefix caching / shared prompt**：多请求有相同 prompt 前缀（如同一 system prompt、few-shot 例子），它们的 prefix KV 完全相同 → 只存一份物理 block，多个 block table 指向它。大幅省显存、还省掉重复 prefill。
- **Parallel sampling / beam search**：同一 prompt 派生多个候选序列，prompt 部分共享 block；
- **Copy-on-write（写时复制）**：共享 block 在某条序列要写入新内容（分叉）时才复制出独立副本，未分叉前一直共享。
本项目**没有**实现共享/CoW/prefix caching（docstring 明确说做了简化），但理解它能解释 vLLM 在 system-prompt 重、beam search 等场景的额外显存优势。

> **追问**：prefix caching 在什么真实场景收益最大？
> 长 system prompt + 高并发（多用户共享同一指令模板）、few-shot 固定示例、Agent/多轮对话复用历史前缀。前缀越长、复用率越高，省得越多（显存 + 重复 prefill 算力双省）。

## 三、深入 / 手撕题（能否动手 / 追问到底）

### Q17.（手撕思路）请实现一个分页 KV 显存池：要求支持「按需为请求追加块」「请求完成时释放块」「显存不够返回失败」。说设计 + 关键代码。

**参考答案（结合本项目 `PagedKVCache`）：**
核心数据结构只需要一个**空闲块号列表** `free_blocks` + 每个请求持有的**物理块号列表** `req.kv_blocks`。
关键不变量：`used_blocks = total_blocks − len(free_blocks)`；分配=`pop`，释放=`append`，块号守恒永不丢失。

```python
import math

class PagedKVCache:
    def __init__(self, total_blocks, block_size):
        self.block_size = block_size
        self.total_blocks = total_blocks
        self.free_blocks = list(range(total_blocks))   # free list

    def blocks_needed(self, n_tokens):
        return math.ceil(max(1, n_tokens) / self.block_size)   # 向上取整

    def can_allocate(self, n):
        return len(self.free_blocks) >= n

    def allocate(self, req, n_tokens_total):
        need = self.blocks_needed(n_tokens_total)
        have = len(req.kv_blocks)
        if need <= have:                 # 现有块够装,无需追加(很多 decode step 走这里)
            return True
        extra = need - have
        if not self.can_allocate(extra): # 显存不够 -> 让调用方排队/回退/抢占
            return False
        for _ in range(extra):
            req.kv_blocks.append(self.free_blocks.pop())   # 按需追加
        return True

    def free(self, req):                 # 完成立即归还,当步可被复用
        self.free_blocks.extend(req.kv_blocks)
        req.kv_blocks.clear()
```

**设计要点必须讲到：**
1. **按需（on-demand）而非预留**：`need <= have` 时直接返回，因为一块装 16 token，decode 平均 16 步才追加一块——绝大多数 step 根本不分配，这是省显存的关键。
2. **返回布尔而非抛异常**：让上层调度器决定排队 / 回退 / 抢占，分配器只管「够不够」。
3. **完成即释放**：`free` 把块还回 free list，连续批的「即时补位」才有物理基础。
4. **正确性自检**：任意时刻所有请求持有块数 + free_blocks 长度 == total_blocks（块守恒，可写断言）。

> **追问 1**：怎么扩展支持 prefix 共享 + copy-on-write？
> block 上加**引用计数 refcount**：共享时多个 block table 指向同一物理块、refcount++；`free` 时 refcount−−，到 0 才真正回 free list；某请求要写已共享块（分叉）时，先复制一份新块再写（CoW），原块 refcount−−。
> **追问 2**：这个 `allocate` 在多请求并发的真实引擎里有什么坑？
> `free_blocks.pop()` 必须在调度器的**单线程调度循环**里串行做，或加锁——否则两请求同时 pop 同一块会冲突。vLLM 的调度是单线程 step loop，正好规避。

### Q18.（手撕思路）写出连续批处理调度主循环的伪代码，必须体现「即时补位」「完成即退出释放」「成本按活跃数」「显存不够回退」。

**参考答案（对应本项目 `run_continuous_batching`）：**

```python
while finished < total_req:
    if not running:                       # 空窗期:快进时钟到下一个到达时刻,免空转
        clock = max(clock, next_arrival_time())
    admit_new()                           # (1) 每个 step 开头即时补位:已到达且 KV 够 -> 入 running

    clock += step_time_ms(len(running))   # (2) 成本只按当前活跃数,不是固定批宽
    n_steps += 1

    done = []
    for r in running:
        r.generated += 1
        if not kv.allocate(r, r.total_len):   # (3) decode +1,可能追加块
            r.generated -= 1                  #     显存不够 -> 回退这一步(简化抢占)
            continue
        if r.is_done:
            r.finish_ms = clock               # (4) 完成当步结算延迟,无队头阻塞
            done.append(r)

    for r in done:                            # (5) 完成当步释放块 + 移出 running
        kv.free(r); running.remove(r); finished += 1
```

**与静态批逐点对照（面试官想听的就是这个对比）：**
| 点 | 连续批 | 静态批 |
|---|---|---|
| 补位时机 | 每 step 开头 `admit_new()` | 等整批结束才发下一批 |
| 成本传参 | `len(running)`（活跃数） | `len(batch)`（整批宽度，含陪跑） |
| 完成结算 | EOS 当步 `finish_ms=clock` | 拖到整批最后一步 |
| 显存 | 按需 `allocate`/`free` | 一次性按 max_seq_len 预留 |

> **追问 1**：`admit_new` 入队时为什么按 `prompt_len + 1` 预留块，而不是 `prompt_len`？
> 进 running 后第一步 decode 就要写第 `prompt_len+1` 个 token 的 KV，提前确保有块，避免入队即失败。
> **追问 2**：「回退这一步」`r.generated -= 1` 会不会死循环？
> 可能——若一直没请求完成释放块，该请求每步都回退、step 数虚增却无进展（本项目练习 1 调小显存就能观察 step 上升）。真实系统靠**主动抢占**（重算/换出最低优先级请求）腾块来打破，而不是被动回退。

### Q19. 推导：给定 batch 内 N 条请求、输出长度分布，估算静态批相对连续批多浪费多少 step，以及 padding 浪费比例。

**参考答案：**
设 batch 内输出长度为 `o_1 … o_N`。
- **静态批 decode step 数** = `max_i o_i`（右 padding 到最长）。它对所有 N 条都按整批宽度计费，总「请求-步」工作量 = `N · max_i o_i`。
- **连续批 decode 总「请求-步」工作量** = `Σ_i o_i`（每条只在它活着时计费，无陪跑）。
- **padding 浪费比例** = `(N·max − Σ o_i) / (N·max) = 1 − ō/max`，其中 `ō = (Σ o_i)/N` 是平均输出长度。
  - 长度越不齐（`max ≫ ō`）→ 浪费越接近 1。例：N=16，15 条输出 20、1 条输出 120 → `ō≈26.25`，浪费 ≈ `1 − 26.25/120 ≈ 78%`。
  - 全等长（`max = ō`）→ 浪费 0，两者退化一致。
- 这定量解释了为什么本项目造「25% 长尾」负载：长尾把 `max/ō` 拉大，static 的 padding 浪费随之放大，连续批收益最大化。
- **注意**：这只是 decode 计费层面的工作量估算；真实 makespan 还受成本模型固定项、错峰到达、显存约束影响，不能简单线性外推。

> **追问**：连续批是不是就完全没有「等」了？
> 不是。它消灭了「短请求陪长请求」和「队头阻塞」，但仍有：排队等显存/批容量、被抢占回退、空窗期。它优化的是**结构性浪费**，不是物理时间归零。

### Q20. 本项目模拟器相比真实 vLLM 做了哪些简化？哪些会让结论偏乐观/失真？（考批判性思维）

**参考答案：**
主要简化（docstring/README 明示）：
1. **不跑真实算子**，step 耗时用手调线性成本模型 → 绝对数字不可外推，比值也只是趋势。
2. **抢占被简化为「回退这一步不推进」**，没有真正的 recompute/swap → 真实显存压力下行为更复杂（带宽、重算开销）。
3. **没有 chunked prefill / PD 分离** → prefill 对 decode 的干扰、TTFT/ITL 抖动没建模。
4. **没有 prefix caching / block 共享 / CoW** → 低估了 vLLM 在 system-prompt 重场景的真实显存优势（这点是「偏保守」，不是乐观）。
5. **成本模型对 attention 随序列长度增长不敏感**（`T_per_req` 是常数，真实 attention 计算/KV 读取随 `seq_len` 增长）→ 长序列下 static 与 continuous 的差距估计可能失真。
6. **静态批 peak 只记预留量、不真从池扣** → 用来制造「会 OOM」的演示，但不是真实分配行为。
**结论方向是对的**（连续批 + 分页确实更优，且这是工业界共识 + 论文结论），但**具体倍数不可当 benchmark**。面试能主动区分「定性结论可信 / 定量数字仅趋势」是加分项。

> **追问**：那这个模拟器的价值在哪？
> 建立直觉、看懂 vLLM 在解决什么问题、能动手做对照实验（改 block_size/显存/负载长尾观察指标怎么变）。生产上直接用 vLLM/SGLang，不会自己写这套——模拟器是「理解工具」不是「生产组件」。

## 高频追问速答清单

1. **连续批 vs 静态批一句话差别？** 调度粒度从「请求级」降到「step 级」，短请求即退、新请求即补。
2. **PagedAttention 解决什么？** 把 KV 显存从「按 max_seq_len 连续预留」改成「固定 block 按需分配」，消外部碎片、压内部碎片。
3. **block_size 默认多少？** vLLM 默认 16 token/block。
4. **decode 是 compute-bound 还是 memory-bound？** memory-bound（每步读全权重+全 KV 只算 1 token）。
5. **为什么 batch 越大吞吐越高？** 固定开销 `T_fixed/n` 被摊薄，单 token 成本下降。
6. **队头阻塞是什么？** 静态批短请求必须等批内最慢那条才返回，延迟被拖。
7. **显存不够 vLLM 怎么办？** 抢占：recompute（丢弃重算）或 swap（KV 换到 CPU）。
8. **prefix caching 省什么？** 共享相同 prompt 前缀的物理 block，省显存 + 省重复 prefill。
9. **chunked prefill 干嘛？** 把长 prefill 切块与 decode 混批，避免 prefill 阻塞 decode、压 ITL 抖动。
10. **内部碎片 vs 外部碎片？** 内部=分了没用满；外部=总量够但不连续。分页消外部、内部只剩每条最后一块半空。
11. **peak KV 为什么关键？** 直接决定 OOM 与否；分页让原本会 OOM 的负载跑得起来。
12. **优先短请求调度的风险？** 长请求饥饿，p99 尾延迟恶化；需 aging/配额缓解。
