# MoE(Mixture of Experts) · 面试题库

> 本题库围绕"稀疏 MoE"展开:稀疏门控 router、top-k 路由、负载均衡 aux loss、专家容量与 token dropping、路由崩溃(load collapse)、激活参数 vs 总参数。覆盖大厂 **AI-Infra / 大模型训练 / 推理优化 / 算法** 岗的高频考点,答案均可结合本目录 `moe.py`(从零实现的 toy MoE)与 `手把手教学.md` 的实验现象作答。

---

## 一、基础题(概念是否懂)

### Q1. 什么是 MoE?它要解决稠密模型的什么痛点?

**参考答案:**
MoE(Mixture of Experts)把 Transformer 里的单个 FFN 子层替换成 **多个并列的专家(每个专家就是一个小 FFN)+ 一个 router(门控)**。核心痛点是:**在稠密(dense)模型里,参数量和单 token 计算量是绑死的**——把 FFN 放大 100 倍,每个 token 的前向 FLOPs 也涨 100 倍,训练/推理都跑不动。

MoE 的本质是把这两者**解绑**:准备很多个专家(总参数量很大),但每个 token 只激活其中 top-k 个(本项目 `num_experts=8, top_k=2`),所以单 token 计算量只相当于 2 个小 FFN。一句话:**参数量大、单 token 计算量小(sparse activation)**。

**追问:** 为什么"参数多"在固定算力下还能更好?
> 因为它增加的是**模型容量/记忆能力**而非每 token 算力。在相同训练/推理 FLOPs 预算下,MoE 用更多参数装下更多知识,scaling 上常优于同等激活算力的 dense 模型(Switch Transformer 的核心结论)。

---

### Q2. 激活参数(activated params)和总参数(total params)有什么区别?为什么这是 MoE 的核心卖点?

**参考答案:**
- **总参数** = 所有专家 + router + 其它层的参数之和,决定显存占用(权重要全部加载)。
- **激活参数** = 单次前向真正参与计算的参数,约等于 `非专家部分 + top_k/num_experts × 专家部分`。决定**计算 FLOPs**(进而决定延迟/吞吐)。

卖点:MoE 让总参数远大于激活参数。例如 Mixtral 8x7B 总参数约 47B,但每 token 只激活约 13B(2/8 个专家),推理算力接近一个 13B dense 模型,质量接近更大模型。**结合本项目**:8 个专家、top-2,每 token 专家算力 = 2/8 = 1/4 的"全专家算力",但容量是 8 个专家。

**追问:** MoE 省的是显存还是算力?
> 省**算力(FLOPs)**,**不省显存**——所有专家权重都得驻留(甚至更费显存)。所以 MoE 是"用显存换算力效率"。

---

### Q3. router / gating 是怎么实现的?为什么本项目用 `bias=False` 的线性层?

**参考答案:**
router 就是一个 `nn.Linear(d_model, num_experts)`,把每个 token 映射成 `num_experts` 个打分(logits),再 `softmax(dim=-1)` 得到路由概率分布(每行和为 1):

$$\text{logits} = x W_r \in \mathbb{R}^{T\times E}, \quad p_{t}=\mathrm{softmax}(\text{logits}_{t,:})$$

本项目用 `nn.Linear(d_model, num_experts, bias=False)`(见 `SparseMoE.__init__`)。**为什么无偏置**:更接近论文实现;偏置会给某些专家一个**与输入无关的固定偏好**,在训练早期容易加剧"赢者通吃",诱发负载不均衡。

**追问:** softmax 是在哪个维度上做的?
> 在最后一维(专家维 `dim=-1`)上做,使每个 token 对所有专家的概率和为 1;不是在 token 维上做。

---

### Q4. top-k 路由是什么?为什么选出 top-k 后还要对权重"重新归一化"?

**参考答案:**
top-k 路由 = 对每个 token 只保留概率最高的 k 个专家参与计算,其余忽略(稀疏激活)。本项目用 `torch.topk(router_probs, top_k, dim=-1)` 拿到 `topk_probs` 和 `topk_idx`。

**为什么重归一化**:top-2 选出的两个概率(如 0.4、0.3)加起来只有 0.7,不是 1。除以它们的和后变成 0.571、0.429,和为 1,组合输出成为一个**凸组合(convex combination)**,数值更稳定,梯度尺度不随 top-k 概率绝对大小漂移。代码:

```python
topk_weights = topk_probs / (topk_probs.sum(dim=-1, keepdim=True) + 1e-9)
```

`+1e-9` 防除零。这与 Mixtral 的做法一致。

**追问:** top-1(Switch)和 top-2(GShard/Mixtral)各有什么取舍?
> top-1 计算最省、通信最少,但没有"第二选择"做缓冲,更易塌缩、表达更弱;top-2 给每 token 两个专家、组合更平滑、训练更稳,但算力/通信翻倍。Switch 证明 top-1 配合容量+aux 也能稳。

---

### Q5. 一个"专家(Expert)"到底是什么?它有什么特殊结构吗?

**参考答案:**
专家**没有任何特殊之处**,就是一个普通两层 FFN:`fc2(GELU(fc1(x)))`(本项目 `class Expert`)。`fc1` 把 `d_model` 升到 `d_hidden`,`fc2` 降回 `d_model`,**输入输出同维**以便做残差。

MoE 的"魔法"全在外面的 **router + top-k 选择 + 加权组合 + 负载均衡**,不在专家内部。在真实 Transformer-MoE 里,专家就是替换掉 FFN 子层的那个前馈网络,N 份并列。

**追问:** 为什么本项目必须用 `nn.ModuleList` 而不是普通 Python list 装专家?
> 普通 list 里的子模块**不会被 PyTorch 注册**,`model.parameters()` 收不到它们,`opt.step()` 不更新这些专家的参数,loss 几乎不降。`nn.ModuleList` 才能正确注册参数。这是常见 bug。

---

### Q6. 负载均衡辅助损失(load-balancing aux loss)是干什么的?写出本项目用的公式。

**参考答案:**
它用来**防止专家负载不均**(少数专家被反复选中、其余饿死)。本项目用 Switch Transformer 式的辅助损失:

$$\text{aux} = E \cdot \sum_{i=1}^{E} f_i \cdot P_i$$

- $f_i$ = 被路由到专家 $i$ 的 token 比例(由**硬**的 top-k 选择统计,**不可导**),代码 `f_i = expert_mask.float().mean(dim=0)`。
- $P_i$ = 专家 $i$ 在所有 token 上的**平均路由概率**(softmax 概率求平均,**可导**),代码 `P_i = router_probs.mean(dim=0)`。
- 系数 $E$(`num_experts`)做缩放,使理想最小值 = 1.0。

直觉:当某专家**既被选得多($f_i$ 大)又平均概率高($P_i$ 大)**,这一项就大、惩罚就重,梯度去压低热门专家、抬高冷门专家,把负载推向均匀。

**追问:** aux loss 的理论下界是多少?为什么?
> 下界 = **1.0**。当完全均匀时 $f_i = P_i = 1/E$,则 $\text{aux} = E\cdot\sum_i (1/E)(1/E)= E\cdot E\cdot(1/E^2)=1$。越接近 1 越均衡。

---

### Q7. 什么是"路由崩溃 / 专家饿死(routing collapse / load collapse)"?本项目怎么演示它?

**参考答案:**
路由崩溃 = router 一旦稍微偏爱某几个专家,这些专家就得到更多训练、变得更强、于是被选得更多……**正反馈滚雪球**,最终只有少数专家在干活,其余专家**占比塌成 0**,等于浪费了大半参数。这是"赢者通吃(winner-take-all)"的恶果。

**本项目演示(对照实验)**:`moe.py` 的实验 A(`aux_weight=0.0`)故意复现该故障——`route_frac` 里出现 `0.00`,`imbalance`(= max占比/min占比)直接打印 `inf`。实验 B(`aux_weight=0.01`)加上 aux loss 后,`imbalance` 单调下降(约 `2.97→2.09→1.69→1.24`),`route_frac` 全部逼近均匀线 `1/8=0.125`。两者 `task_loss` 都很低——说明**均衡不是靠牺牲任务效果换来的**。

**追问:** 为什么 `imbalance` 会打印 `inf` 而不是报错?
> 本项目 `imbalance_ratio = max(frac)/min(frac)`,当有专家占比≈0 时分母趋零,按设计返回 `float("inf")`。这是**预期现象**,不是 bug,正是用来直观展示"专家死了"。

## 二、进阶题(原理与权衡)

### Q8. aux loss 公式里 $f_i$ 为什么要 `detach()`?梯度到底走哪条路?

**参考答案:**
$f_i$ 来自 `top-k`/`one_hot` 的**硬选择**,这是不可导的(argmax/topk 没有有用梯度)。如果不 `detach`,反传会试图穿过这条不可导路径,数值和语义都不对。

所以做法是:把 $f_i$ 当作一个**固定权重系数** `detach` 掉,真正的梯度通路只走**可导的 $P_i$**(softmax 概率)。代码:

```python
aux_loss = self.num_experts * torch.sum(f_i.detach() * P_i)
```

直觉上:$f_i$ 告诉"哪个专家现在过热(该被惩罚)",$P_i$ 提供"可以被梯度推动"的旋钮——梯度通过 $P_i$ 去压低过热专家的 logits。

**追问:** 如果误把 `index_add_` 写成 `y[sel_token] = ...` 会怎样?
> 会**覆盖**而非累加。同一 token 选了 2 个专家时,第二个专家的输出会冲掉第一个,无法实现 $y_t=\sum_i g_{t,i}E_i(x_t)$,结果错误。必须用 `index_add_` 做加法累加。

### Q9. 什么是专家容量(expert capacity)与 token dropping?为什么需要它?

**参考答案:**
真实分布式 MoE 里,每个专家分配在某张卡上,且为了**静态 shape / all-to-all 通信对齐**,必须给每个专家设一个固定的**容量上限**:

$$\text{capacity} = \text{capacity\_factor} \times \frac{\text{tokens} \times k}{E}$$

如果某专家这一步被路由到的 token 超过容量,**超出的 token 被丢弃(dropped)**——它们这一层不经过任何专家(通常靠残差直接跳过)。

为什么需要:① 分布式下 tensor 必须是固定形状,不能让某个专家无限膨胀;② 容量天然限制了负载倾斜带来的木桶效应。代价:`capacity_factor` 太小 → 丢 token、信息损失、训练不稳;太大 → 浪费显存/算力(pad 很多空槽)。常用 1.0~2.0,推理时可设大些减少丢弃。

**结合本项目**:`moe.py` 是 toy 教学实现,**没有 capacity / token dropping**(README "局限"明确说明)——它用 Python for 循环 + `index_add_`,任何专家被多少 token 选中都照单全收。理解这一点恰好能说清"教学实现"与"工程实现"的关键差距。

**追问:** drop 掉的 token 后续怎么办?会不会丢信息?
> 它们这层不过专家,但因为有**残差连接** `h = h + h_moe`,token 原始表示仍能往后传,不会彻底丢失;只是这一层没拿到专家加工。所以**残差在 MoE 里尤其关键**。

---

### Q10. aux loss 之外还有哪些稳定路由的手段?它们各解决什么问题?

**参考答案:**
- **router z-loss**:惩罚 router logits 的 log-sum-exp 大小($z = \log\sum_j e^{\text{logit}_j}$ 的平方),防止 logits 数值爆炸导致 softmax 饱和、训练不稳(ST-MoE 提出)。
- **noisy top-k / jitter**:在 logits 上加高斯噪声再选 top-k,鼓励早期探索、打破"赢者通吃"的初期正反馈(GShard/Switch)。**本项目练习 5** 就是简化版:`router_logits + torch.randn_like(...)*0.1`。
- **expert capacity + dropping**:见 Q9,硬性限制倾斜。
- **辅助/无辅助均衡**(DeepSeek-V2/V3 的 **auxiliary-loss-free balancing**):给每个专家加一个可学习/动态调整的 **bias** 只影响"选谁"(routing)但不进 gating 权重,避免 aux loss 对主任务梯度的干扰。
- **共享专家(shared experts)**:DeepSeekMoE 让若干专家对所有 token 恒定激活,负责通用知识,其余路由专家负责专精,减少冗余、稳住基础能力。

**追问:** aux loss 权重(本项目 `aux_weight`)怎么调?太大太小各什么后果?
> 太小 → 均衡不够,仍可能塌缩;太大 → 过度约束 router,把均匀性凌驾于任务之上,task_loss 早期变高、收敛变慢。本项目用 `0.01`(典型量级 1e-2~1e-3),是"均衡 vs 任务"的折中。练习 1 放大到 `0.1` 可观察到收敛更快但任务略受拖累。

### Q11. MoE 训练相比 dense 有哪些独有的不稳定来源?怎么缓解?

**参考答案:**
1. **路由崩溃 / 负载不均**:赢者通吃 → aux loss / capacity / 共享专家缓解(见 Q7/Q9/Q10)。
2. **路由的离散性**:top-k 是硬选择,不可导,router 只能靠 aux 的 $P_i$ 和 gating 权重的乘积间接拿梯度,信号弱、易抖。
3. **logits 爆炸 / softmax 饱和**:→ router z-loss。
4. **专家不一致(训练-推理 mismatch)**:训练时 batch 内 token 分布与推理(单条/小 batch)不同,负载统计不稳 → 大 batch、EMA 统计、推理放大 capacity。
5. **梯度尖刺**:MoE 对 lr / 初始化更敏感,常用更小 lr、warmup、bf16 + 选择性 fp32(router 用 fp32 更稳)。

**追问:** 为什么 router 常用 fp32 计算?
> router 的 softmax/topk 对数值精度敏感,bf16/fp16 下小概率差异会被吃掉、放大路由抖动。常见做法是专家用低精度、**router 单独用 fp32** 保证路由决策稳定。

### Q12. 把 MoE 部署到多卡时,主要的系统瓶颈是什么?

**参考答案:**
核心是 **expert parallelism(EP)** + **all-to-all 通信**:专家分散到不同卡,每个 token 要被"派发(dispatch)"到它选中专家所在的卡、算完再"收回(combine)",这需要两次 all-to-all。瓶颈:
- **通信开销**:all-to-all 是 MoE 训练/推理的主要时间占比,随 EP 规模和序列长度增长。
- **负载倾斜导致的木桶效应**:某卡专家过热 → 其它卡空等,GPU 利用率下降。capacity 用来削峰。
- **显存**:所有专家权重常驻,EP 把专家分摊到多卡缓解,但激活/路由缓冲仍占显存。
- **kernel 效率**:朴素 for 循环按专家算很慢,需 **grouped GEMM / dispatch-combine 矩阵 / Megablocks 式 block-sparse** kernel。

**结合本项目**:`moe.py` 单进程 CPU、Python for 循环 + `index_add_`,**可读优先**,完全没有 EP/all-to-all;README 明确指出上规模要换成批量 dispatch/combine + EP + all-to-all。

**追问:** EP 和 TP/DP/PP 怎么组合?
> 实际是 **EP × DP × TP × PP** 混合并行:专家维用 EP,非专家层用 TP/DP,层间用 PP。需要把 all-to-all(EP)和 all-reduce(TP/DP)的通信流水起来。

---

### Q13. 为什么 MoE 在"相同推理算力"下常优于 dense,但实际部署反而更难?

**参考答案:**
**优在**:相同激活 FLOPs 下总参数更多 → 容量更大 → 质量更好(Q1/Q2)。

**难在**:
- **显存墙**:总参数全要加载,8x7B 占的显存接近 47B dense,小显存卡放不下。
- **通信墙**:all-to-all 让低 batch / 在线推理延迟敏感,通信占比高。
- **负载动态**:在线请求 token 分布不稳,易出现专家热点 → 需要更大 capacity 或专家放置策略。
- **batching 不友好**:不同 token 走不同专家,难像 dense 那样规整地打 batch;需要专门的 MoE 推理引擎(vLLM/SGLang/TensorRT-LLM 的 MoE kernel)。

一句话:**算力效率高,但显存/通信/调度复杂度都上去了**——这是典型的"省 FLOPs、费工程"。

**追问:** 推理时能否把不常用的专家放到 CPU/NVMe(offload)?
> 可以,做 **expert offloading**:把冷专家放 CPU/磁盘,用到再换入。适合显存紧张、对延迟不极致敏感的离线/低并发场景;代价是命中冷专家时的换入延迟,需配合预取和路由预测。

## 三、深入 / 手撕题(能否动手 / 追问到底)

### Q14.【手撕思路】请描述如何从零实现一个稀疏 MoE 层的 forward(结合本项目五步流程)。

**参考答案:**
完整五步(对应 `SparseMoE.forward`):

1. **路由打分**:`router_logits = self.router(x)` → `[T, E]`;`router_probs = softmax(logits, dim=-1)`,每行和为 1。
2. **top-k 选择 + 重归一化**:`topk_probs, topk_idx = torch.topk(router_probs, top_k, dim=-1)`;`topk_weights = topk_probs / (topk_probs.sum(-1,keepdim=True)+1e-9)`(凸组合)。
3. **按专家循环前向 + 加权累加**(教学实现):

```python
y = torch.zeros_like(x)
for e in range(self.num_experts):
    sel_token, sel_slot = torch.where(topk_idx == e)   # 哪些token、在第几个slot选了e
    if sel_token.numel() == 0:
        continue                                        # 该专家这步没被选中(饿死表现)
    expert_out = self.experts[e](x[sel_token])          # 一次性前向所有路由到e的token
    weight = topk_weights[sel_token, sel_slot].unsqueeze(-1)
    y.index_add_(0, sel_token, expert_out * weight)     # 累加(同一token的多专家相加)
```

4. **负载均衡统计 + aux**:`expert_mask = one_hot(topk_idx, E).sum(dim=1)` → `[T,E]`;`f_i = expert_mask.float().mean(0)`;`P_i = router_probs.mean(0)`;`aux = E * sum(f_i.detach() * P_i)`。
5. **返回** `y, aux_loss, route_frac`,在外层 `loss = task_loss + aux_weight * aux_loss` 反传。

关键点:**按专家而非按 token 循环**(每个专家只前向一次)、用 `(sel_token, sel_slot)` 双坐标取对权重、用 `index_add_` 累加。

**追问:** 为什么需要 `sel_slot`(不能只用 `sel_token`)?
> 同一 token 有 k 个 slot,各自有独立的归一化权重。`topk_weights` 是 `[T, k]`,只有用 `(token, slot)` 这对坐标 `topk_weights[sel_token, sel_slot]` 才能取到"该 token 在选 e 那个 slot 上"的正确权重。

### Q15.【追问到底】本项目的 for-循环实现和真实高性能实现差在哪?要工业化要补哪些?

**参考答案:**
本项目(可读优先)的实现特征与差距:
- **计算**:Python `for e in range(E)` + `torch.where` + `index_add_`,串行、kernel 小、GPU 利用率低。
  → 工业化:**grouped/batched GEMM**(把所有专家的 token 排序分组后一次性 matmul)、**dispatch/combine 矩阵**或 **Megablocks block-sparse** kernel。
- **无容量管理**:任何专家照单全收,没有 capacity / token dropping。
  → 加 capacity_factor、固定 shape、超额丢弃 + 残差跳过。
- **无分布式**:单进程,无 EP / all-to-all。
  → expert parallelism + all-to-all dispatch/combine,EP×DP×TP×PP 混合并行。
- **稳定性手段单一**:只有 aux loss,无 router z-loss / noisy top-k / jitter / 共享专家。
- **精度**:全 fp32;工业上专家低精度、router fp32。
- **数据**:toy 高斯簇,task_loss 能到≈0、acc=1.0(对单 batch 过拟合,**不代表真实 LM**)。

一句话:**算法骨架(router→topk→combine→aux)已完整且正确,缺的是"工程化的容量管理、分布式通信、高性能 kernel、稳定性套件"。**

**追问:** 如果要在不丢 token 的前提下处理倾斜,有什么思路?
> ① 增大 capacity_factor(费显存);② **BPR(Batch Priority Routing)**:容量内优先保留 router 置信度高的 token;③ DeepSeek 式 **aux-loss-free 动态 bias** 在源头减小倾斜;④ 设备级均衡损失约束每张卡的负载而非每个专家。

### Q16.【现象分析】no_aux 实验里 `task_loss≈0.002、acc=1.0`,但 `imbalance=inf`——这说明什么?能直接得出"路由崩溃不影响效果"吗?

**参考答案:**
**不能**。它说明的是:在这个**极简 toy 任务**上,即使一半专家饿死,剩下的活跃专家也足以把任务过拟合到 acc=1.0。这是因为任务太简单(10 个高斯簇)、模型对单 batch 过拟合,**不是路由崩溃无害的证据**。

真实大模型上,路由崩溃意味着:① 大量参数被浪费(花了显存却没在工作),② 模型有效容量远低于名义总参数,③ scaling 收益消失——你为 MoE 付了显存代价却没拿到容量收益。所以**均衡是为了"把买来的容量真正用上"**,不是为了眼前这个 toy 的 acc。

正确解读 with_aux:`task_loss` 同样低(0.0019)而 `imbalance` 从 `inf` 压到 `1.24`——证明**鱼和熊掌兼得**,均衡没牺牲任务。

**追问:** 怎么改 toy 任务才能让"崩溃伤害效果"显现出来?
> 把任务调难(`make_toy_data` 噪声 `*1.5→*3.0`、中心 `*2.0→*1.0`,见练习 4),让单凭少数专家无法过拟合;此时饿死专家会使 task_loss / acc 明显变差,崩溃的危害就显出来了。

### Q17.【对比设计】top_k 从 2 改成 1(Switch 式)会发生什么?为什么 top-1 更易崩溃?

**参考答案:**
现象(对应练习 2):`top_k=1` 时每个 token 只走 1 个专家,`topk_weights` 归一化后恒为 1。**不加 aux 时塌缩更猛**,因为:
- top-1 没有"第二选择"做缓冲——一旦 router 偏好某专家,token 全押注上去,赢者通吃的正反馈没有任何稀释。
- top-2 至少给每 token 两个专家,负载更分散、组合更平滑,初期不容易锁死。

加 aux 后两者都能拉回均衡,但 top-1 对 aux/capacity 的依赖更强(Switch Transformer 正是 top-1 + 强容量管理 + aux 才稳)。

**取舍**:top-1 省一半专家算力和通信,适合极致效率;top-2 训练更稳、质量略好,是 GShard/Mixtral 的选择。

**追问:** top-k 增大到 k=E(全选)时 MoE 退化成什么?
> 退化成"所有专家加权求和"的 dense ensemble,失去稀疏性,激活参数=总参数,算力优势消失。MoE 的价值恰恰在 `k ≪ E`。

### Q18.【机制追问】aux loss 为什么能"推动"router 走向均衡?请从梯度角度说明,并说明为什么改 num_experts 不改变其下界。

**参考答案:**
**梯度角度**:$\text{aux}=E\sum_i f_i P_i$,$f_i$ 被 detach,梯度只对 $P_i=\frac{1}{T}\sum_t p_{t,i}$ 求。对某个过热专家 $i$($f_i$ 大),$\frac{\partial \text{aux}}{\partial P_i}=E f_i$ 大且为正 → 梯度下降会**压低** $P_i$(即压低它的 router logits);对冷门专家 $f_i$ 小 → 几乎不压,相对被抬高。softmax 的归一化又让"压热门"等价于"抬冷门"。于是负载被推向均匀。

**为什么下界与 $E$ 无关恒为 1.0**:完全均匀时 $f_i=P_i=1/E$,$\text{aux}=E\cdot\sum_{i=1}^E \frac{1}{E}\cdot\frac{1}{E}=E\cdot E\cdot\frac{1}{E^2}=1$。系数 $E$ 正是为抵消 $E$ 个 $1/E^2$ 项而设,使下界固定为 1,**便于跨不同专家数对比均衡程度**(练习 3:`num_experts=4` 时均匀线变 `0.25`,但 aux 下界仍是 1.0)。

**追问:** aux 最小化是否等价于 task 最优?为什么仍要 `aux_weight` 权衡?
> 不等价。aux 的全局最小(完全均匀)可能让 router 忽略 token 的真实需求(把它该去的专家也均摊掉),损害任务。所以用 `aux_weight`(本项目 0.01)做软约束:既鼓励均衡,又不让均衡压过任务信号。

## 高频追问速答清单

1. **MoE 省什么?** 省算力(FLOPs),不省显存(专家全驻留)。
2. **激活参数 vs 总参数?** 算力看激活(top_k/E 比例),显存看总参数。
3. **router 是什么?** 一个 `Linear(d_model, E, bias=False)` + softmax。
4. **为什么 bias=False?** 偏置给专家与输入无关的固定偏好,加剧不均衡。
5. **top-k 后为啥重归一化?** 让 k 个权重和=1,成凸组合,数值稳(Mixtral 做法)。
6. **专家是什么?** 普通两层 FFN(`fc2(GELU(fc1(x)))`),无特殊结构。
7. **专家必须放哪?** `nn.ModuleList`,否则参数不注册、不更新。
8. **aux loss 公式?** $E\sum_i f_i P_i$,下界 1.0;$f_i$ detach、梯度走 $P_i$。
9. **路由崩溃?** 赢者通吃→专家饿死(占比 0、imbalance=inf),浪费参数。
10. **expert capacity?** 每专家固定容量,超额 token 被丢、靠残差跳过。
11. **多卡瓶颈?** expert parallelism + all-to-all dispatch/combine 通信。
12. **router 用什么精度?** 常单独用 fp32,保证路由决策稳定。
13. **稳定性套件?** aux loss + router z-loss + noisy top-k + 共享专家。
14. **index_add_ vs 赋值?** 必须累加(同一 token 选多专家),赋值会覆盖出错。
