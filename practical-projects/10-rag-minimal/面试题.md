# RAG · 面试题库

> 本题库覆盖 RAG（Retrieval-Augmented Generation）的全链路：检索增强动机、文本向量化与相似度、chunking、top-k、prompt 拼接、幻觉缓解、以及召回/忠实度评测。适用于**大模型应用工程师、LLM/AI-Infra、RAG 平台、搜索/推荐转 LLM** 等岗位面试。答案尽量结合本项目 `rag_minimal.py`（纯 numpy 的 TF-IDF + 抽取式生成最小实现）的代码与实验现象作答，便于"既讲原理又讲落地"。

---

## 一、基础题（概念是否懂）

### Q1. 什么是 RAG？它解决什么问题？为什么不直接让 LLM 硬答或干脆做微调？

**参考答案：**
RAG = **检索（Retrieve）→ 增强（Augment）→ 生成（Generate）**：先用 query 去外部知识库检索相关片段，把它们拼进 prompt 的 context 区，再让 LLM 基于这些证据作答。

它解决的核心问题：LLM 的知识被"冻结"在训练截止那一刻的参数里，对**私域知识、时效性强的信息、长尾事实**无能为力，硬答就会**幻觉（hallucination）**——本项目 `closed_book_answer` 就模拟了这个场景，对虚构公司 Acme 的事实题，闭卷命中率为 0/5，返回一句自信但全错的 "founded in 2008 ... 15 vacation days (ungrounded)"。

为什么不靠微调：
- **更新成本**：知识一变就要重训/重微调；RAG 只需更新向量库，秒级生效。
- **可溯源**：RAG 答案带 citation，可定位证据；微调把知识揉进权重，不可解释、易混淆。
- **私域/权限**：RAG 可按用户权限过滤可见文档；微调做不到细粒度访问控制。
- 经验判断：**微调改"风格/格式/能力"，RAG 补"知识/事实"**。两者常组合使用。

**追问1：** RAG 一定比微调好吗？什么情况下你会选微调？
> 不绝对。当任务是固定**输出格式/领域语气/特定推理模式**、知识相对静态、且对延迟极敏感（不想多一次检索）时，微调（或 LoRA）更合适。事实密集、易变、需溯源的场景才是 RAG 的主场。

**追问2：** RAG 能彻底消除幻觉吗？
> 不能。RAG 把幻觉**显著降低**但无法清零：检索没召回到正确文档（漏检）、context 里有冲突信息、或 LLM 不忠实于 context 自己脑补，都会再造幻觉。本项目 100% 命中是因为问句刻意对齐了语料用词，真实场景达不到。

### Q2. RAG 的五个步骤分别是什么？在本项目里各对应哪段代码 / 真实工程里换成什么？

**参考答案：**

| 步骤 | 本项目函数 | 真实工程 |
| --- | --- | --- |
| 知识库 Knowledge Base | `KNOWLEDGE_BASE`（8 条 chunk） | PDF/网页切片入库 |
| 向量化 Embedding | `embed`（TF-IDF + L2 归一化） | BERT/BGE/OpenAI 稠密向量 |
| 检索 Retrieve | `retrieve`（`doc_matrix @ q_vec` 取 top-k） | 向量库 + ANN（HNSW/IVF） |
| 增强 Augment | `build_augmented_prompt`（拼 context） | 拼 context 进 prompt |
| 生成 Generate | `extractive_generate`（挑最匹配句） | LLM decoder |

关键是理解"骨架不变、每步换更强实现"：本项目用 TF-IDF 暴力点积做检索、用"挑词重叠最多的句子"代替 LLM decoder，但每一步承担的角色和生产系统完全一致。

### Q3. 什么是 embedding？为什么要把文本变成向量？TF-IDF 是怎么做的？

**参考答案：**
embedding 是把一段文本映射到一个固定维度的数值向量，使**语义/词面相近的文本在向量空间里距离也近**，这样"问题和文档像不像"就变成"两向量是否接近"的几何问题，可计算、可排序。

TF-IDF 是最经典的**稀疏**编码：
- 先建词表 vocab，每个词占一维（本项目 82 个词 → 82 维）。
- **TF（词频）** $\text{tf}(w,d)=\dfrac{\text{count}(w,d)}{|d|}$，除以总词数抵消长短差异。
- **IDF（逆文档频率）** $\text{idf}(w)=\log\dfrac{1+N}{1+\text{df}(w)}+1$，越普遍的词权重越低。
- **TF-IDF = TF × IDF**：常见词压低、关键词放大。

真实 RAG 这步换成 BERT/BGE/OpenAI 的**稠密语义向量**，但"把文本映射到可比较的向量空间"原理一致。

**追问：** IDF 公式里两个 `+1` 和末尾 `+1` 各是干什么的？
> 分子分母的 `+1` 是**平滑**：避免 df=0 除零，也避免某词出现在所有文档时算出 $\log 1=0$ 把它彻底清零。末尾 `+1` 保证 IDF 恒为正，即使最常见的词也保留一点点权重。

### Q4. 为什么用余弦相似度而不是欧氏距离？本项目里为什么一句 `doc_matrix @ q_vec` 就够了？

**参考答案：**
余弦相似度只看**方向不看长度**：
$$\cos(\mathbf q,\mathbf d)=\frac{\mathbf q\cdot\mathbf d}{\|\mathbf q\|\,\|\mathbf d\|}$$
文本检索里我们关心"主题是否一致"，不关心文档长短带来的向量模长差异，所以方向（余弦）比绝对距离更合适。TF-IDF 非负，余弦取值落在 $[0,1]$。

本项目在 `embed` 末尾做了 **L2 归一化**，把每个向量变成单位向量，于是分母恒为 1，**余弦退化成点积**：
$$\cos(\mathbf q,\mathbf d)=\mathbf q\cdot\mathbf d \quad(\|\mathbf q\|=\|\mathbf d\|=1)$$
因此 `scores = doc_matrix @ q_vec` 一次矩阵乘法（`(8,82)@(82,)`）就同时算出 8 篇文档的余弦相似度，既省事又快。这正是向量库的核心操作，只是它们用 ANN 索引加速。

**追问：** 归一化后余弦与欧氏距离还有关系吗？
> 有。单位向量下 $\|\mathbf q-\mathbf d\|^2 = 2-2\cos(\mathbf q,\mathbf d)$，二者单调对应，按余弦排 top-k 与按欧氏距离排 top-k 结果一致。所以归一化后用内积索引（IP）和 L2 索引等价。

### Q5. 什么是 chunking（分块）？本项目的 chunk 是什么粒度？chunk 太大/太小各有什么问题？

**参考答案：**
chunking 是把原始长文档切成若干**检索单元（chunk）**再入库。本项目 `KNOWLEDGE_BASE` 每条恰好是一句话，所以"chunk = 句子"，但 `extractive_generate` 仍保留了按句切分逻辑（`re.split(r"(?<=[.!?])\s+", doc)`）以兼容"一个 chunk 含多句"的真实情况。

权衡：
- **chunk 太大**：一个块里混入多个主题，向量被稀释、检索精度下降；而且喂进 prompt 占用大量 token，引入噪声、推高成本。
- **chunk 太小**：上下文被切碎，答案所需信息可能跨块，单块语义不完整、召回不全（一个块答不全，要拼多块）。

工程实践：常用 **固定 token 窗 + overlap（重叠）** 切分（如 256~512 token、重叠 10~20%），重叠是为了避免把一句话/一个事实从中间切断；更高级的有按语义/标题层级（如 Markdown header、句子边界）切分。

**追问：** 为什么 chunk 之间要做 overlap？
> 防止关键信息恰好落在切割边界被腰斩，导致任一 chunk 都不完整。重叠让边界附近的内容在相邻两块里都出现，提升召回的鲁棒性。

### Q6. top-k 是什么？本项目 top_k 默认几？调大调小分别有什么影响？

**参考答案：**
top-k 指检索时返回**相似度最高的前 k 个 chunk** 拼进 prompt。本项目 `top_k=2`，`retrieve` 用 `np.argsort(scores)[::-1][:top_k]` 取分数最高的两条。

它是 RAG 最重要的超参之一，体现**召回 vs 噪声**的权衡：
- **k 太小**：答案所需的 chunk 可能没排进 top-k → 漏检，模型无据可依只能拒答或编。本项目教学练习里 `top_k=1` 时若目标文档没排第一就会漏。
- **k 太大**：引入更多无关文档（噪声），稀释 context、增加 token 成本与延迟，还可能让 LLM 被干扰信息带偏（"lost in the middle"）。

实践常配合 **rerank**：先用向量检索召回较大的候选集（如 top-50），再用 cross-encoder 精排取 top-3~5 喂给 LLM。

**追问：** `top_k` 设得比文档总数还大会怎样？
> 本项目 `np.argsort(...)[:top_k]` 会安全返回全部 8 篇不报错，但会把低分噪声文档也塞进去。生产系统同理：k 超过候选数只是返回全部，但拼进 prompt 的噪声变多。

### Q7. "增强（Augment）"具体做了什么？本项目的增强 prompt 里哪两句话最关键？

**参考答案：**
增强就是把检索到的 chunk 拼成 context、和问题一起组织成最终 prompt 发给 LLM。本项目 `build_augmented_prompt` 把 top-k 文档列成清单，外加两句**系统指令**：
1. `"Answer the question using ONLY the context below."` —— 强制模型**只用给定证据**，这是抑制幻觉的核心约束。
2. `"If the context lacks the answer, say you do not know."` —— 允许模型**诚实拒答**而不是硬编。

这两句把"模型不知道的外部知识"注入生成阶段，并约束模型忠实于证据。

**追问（陷阱题）：** 本项目里 `build_augmented_prompt` 真的被调用了吗？
> **没有**。demo 走的是 `extractive_generate`（抽取式生成）那条路，`build_augmented_prompt` 定义了却未在 `main` 调用——它是"教学留痕"，用来展示真实 RAG 喂给 LLM 的 prompt 长什么样。练习里可以把它打印出来。这是个考"是否真读了代码"的细节。

### Q8. RAG 是怎么缓解幻觉的？本项目用什么数字证明了这一点？

**参考答案：**
机制是 **grounding（接地）**：让答案锚定在检索出的真实证据上，而不是靠参数记忆硬猜。配合 prompt 里"只用 context 作答 / 没有就说不知道"的指令，把模型从"自由发挥"约束成"基于证据复述/抽取"。

本项目用一个**对照实验**量化了收益：在 5 道 Acme 私域事实题上
- No-RAG（闭卷）：0/5 = 0%
- RAG（检索+生成）：5/5 = 100%
- 增益：**+100 个百分点**

这个差值就是 RAG 价值的直接度量。需注意 100% 是 demo 刻意对齐用词的理想结果，真实场景不会这么高。

## 二、进阶题（原理与权衡）

### Q9. 稀疏检索（TF-IDF/BM25）和稠密检索（dense embedding）的本质区别？各自优劣？

**参考答案：**
- **稀疏检索**（TF-IDF、BM25）：基于**词面/词项匹配**，向量高维稀疏（每维=一个词）。优点：可解释、无需训练、对**精确关键词/专名/罕见词/数字**召回强、零样本可用、易加权调参。缺点：**吃 vocabulary mismatch**——同义词、改写、跨语言匹配不上（本项目里 `return` vs `returns` 不做词干归并就会失配，`policy/window` 这类 OOV 词压根没列号）。
- **稠密检索**（BERT/BGE/DPR）：基于**语义**，向量低维稠密。优点：能匹配同义改写、捕捉语义相似。缺点：需训练好的 embedding 模型、对精确专名/长尾词可能不如稀疏、不可解释、有 domain shift 风险。

工程结论：常用**混合检索（hybrid）**——BM25 + dense 双路召回再融合（如 RRF, Reciprocal Rank Fusion），兼顾关键词精确性和语义泛化。BM25 是稀疏检索的强基线，本项目的 TF-IDF 是它的简化版。

**追问：** 本项目把 TF-IDF 换成 BGE，哪几行要改、哪几行不用动？
> `embed` 要换成调 BGE 编码（query/doc 用同一模型，必要时按 BGE 要求给 query 加指令前缀）；`build_vocab/compute_idf` 整块可删（稠密向量不需要词表/IDF）。`retrieve` 的 `doc_matrix @ q_vec`（仍对向量 L2 归一化后做内积取 top-k）**几乎不用动**——这正说明"骨架不变"。

### Q10. 为什么 query 和文档必须用同一个 `embed`（同一套 vocab + idf）？混用会怎样？

**参考答案：**
因为点积/余弦只有在**同一坐标系**下才有意义。本项目里向量第 $j$ 维代表词表里第 $j$ 个词，IDF 又给每维定了权重。只有 query 和文档用**同一个 vocab（同样的列含义）和同一份 idf（同样的权重）**，两个向量才落在同一空间，点积才度量"真实的词面重合度"。若 query 用另一套 vocab，维度含义错位，相似度就是噪声。

稠密检索同理：query 和 doc 应使用**同一个（或配套的双塔）embedding 模型**；像 BGE 这类模型还要求 query 端加特定指令前缀、doc 端不加，否则两侧分布不对齐、检索质量下降。

**追问：** query 里出现知识库从没有的词（OOV）会怎样？
> 本项目 `embed` 里 `if word in vocab` 直接忽略 OOV 词（没列号、无法贡献相似度）。若 query 关键词全是 OOV 或全被 stopwords 过滤，余弦会全为 0，检索退化为随机/无效。这是稀疏检索的固有短板，也是升级稠密检索的动机。

### Q11. 本项目 RAG 命中率 100%，真实系统达不到。是哪些"作弊"假设让它这么完美？

**参考答案：**
demo 的高分来自一串理想化假设，逐条对应真实系统的难点：
1. **问句刻意对齐语料用词**：query 关键词都在文档里出现，TF-IDF 词面匹配天然成功；真实用户提问用词千差万别，会撞 vocabulary mismatch。
2. **每条 chunk 就是一句完整事实**：无需跨块拼接、无切分损失；真实文档切分会割裂语义。
3. **知识库极小（8 条）且无冲突/无干扰**：top-2 就能稳稳召回；真实库百万级，含相似/冲突/过期信息。
4. **抽取式生成器只挑原句**，不会脑补；真实 LLM 可能不忠实于 context。
5. **判分用关键词包含**（`keyword_hit`），宽松客观但浅；真实评测要判语义正确与忠实度。

把任一假设放松，命中率就会掉——教学练习里把 Q5 改成 `"return policy window"` 就因 OOV/词形差异掉到 4/5=80%。

### Q12. 什么是 rerank（重排序）？为什么"检索 top-k 直接喂 LLM"往往不够？

**参考答案：**
向量检索（bi-encoder/双塔）为了速度，query 和 doc **各自独立编码**再算相似度，无法建模二者的细粒度交互，召回的 top-k 排序未必精准。**rerank** 用 **cross-encoder**（把 query+doc 拼一起过一个模型，输出相关性分）对召回候选**精排**，精度高但慢。

典型两阶段：**召回（recall）用向量库取 top-50~100（快、保召回）→ 精排（rerank）用 cross-encoder 选 top-3~5（准）→ 喂 LLM**。好处：既不漏（召回宽），又不噪（精排后只留最相关的，省 token、抗 "lost in the middle"）。本项目没有 rerank，直接 `argsort` 取 top-2，相当于只有召回阶段。

**追问：** bi-encoder 和 cross-encoder 的核心区别？为什么不全用 cross-encoder？
> bi-encoder 可**离线预编码文档**、检索时只编码 query 再做向量近邻，能扩到百万级；cross-encoder 必须对每个 (query, doc) 对在线前向，N 篇文档要 N 次推理，无法扫全库。所以用 bi-encoder 召回缩小候选、cross-encoder 只精排少量候选。

### Q13. 当检索召回的 context 里有"相互冲突"或"过期"的信息时，RAG 会怎样？如何缓解？

**参考答案：**
LLM 面对冲突 context 行为不稳定：可能随机选一条、被 prompt 中靠前/靠后的内容带偏（位置偏置）、或综合出一个错误折中答案。过期信息更危险——它"看起来有据"，幻觉更隐蔽。

缓解手段：
- **元数据过滤**：给 chunk 打 timestamp/version/来源标签，检索时按时效或权限过滤，优先新版本。
- **去重与版本治理**：入库时对近重复内容归并，保留权威/最新源。
- **rerank + 来源置信度**：让精排考虑来源可信度。
- **prompt 指令**：要求模型"如证据冲突，指出冲突并以最新/最权威来源为准"。
- **要求 citation**：让模型标注每句答案来自哪条 chunk，便于发现它依据了过期源。

### Q14. RAG 的评测怎么做？召回率（recall）和忠实度（faithfulness）分别衡量什么？

**参考答案：**
RAG 要**分阶段**评测，否则无法定位是检索还是生成出了问题：

**检索阶段（retrieval）**：
- **Recall@k / Hit@k**：top-k 里是否包含正确（标注的相关）chunk。衡量"该找到的有没有找到"。
- **MRR / NDCG**：正确 chunk 排得多靠前，衡量排序质量。
- 本项目用 `keyword_hit` + top-2 是这一类的极简代理。

**生成阶段（generation）**：
- **Faithfulness / Groundedness（忠实度/接地度）**：答案的每个论断是否**都能由检索到的 context 支撑**，不脑补。这是 RAG 幻觉控制的核心指标。
- **Answer Relevance（答案相关性）**：答案是否切题。
- **Context Precision/Recall**：喂进去的 context 有多少真正被用上 / 是否覆盖了答案所需信息。

工程上常用 **RAGAS** 等框架，用 LLM-as-judge 自动打 faithfulness/relevance。注意：**召回高但忠实度低**说明检索没问题、是生成在编；**忠实度高但答错**往往是检索没召回到正确证据。两者要一起看。

**追问：** 答案正确但 context 里其实没这条信息（模型靠自己参数答对了），算不算 RAG 成功？
> 从"答对"看算对，但从 **faithfulness** 看是**不忠实**——它没用证据、是参数侥幸，换个问题就会编。生产中应判它"不接地"，因为不可控、不可溯源。这正是为什么 faithfulness 要和 accuracy 分开评。

### Q15. RAG 的延迟和成本来自哪些环节？工程上怎么优化？

**参考答案：**
延迟/成本拆解：
- **检索**：向量近邻搜索（百万级用 ANN 而非暴力点积）、可能的 rerank（cross-encoder 在线前向较贵）。
- **生成**：context 越长（top-k 越大、chunk 越大），prompt token 越多 → prefill 越慢、$ 越高，且首 token 延迟上升。

优化手段：
- **ANN 索引**（HNSW/IVF-PQ）替代暴力 `doc_matrix @ q_vec`，亚线性检索、PQ 量化省内存。
- **控制 context 预算**：合理 chunk 大小 + 适中 top-k + rerank 后只留最相关几条，避免无脑塞。
- **缓存**：embedding 缓存（doc 离线编码一次）、对热门 query 缓存检索结果甚至答案。
- **prompt 压缩 / context 压缩**：对召回内容做摘要再喂。
- 本项目因知识库只有 8 条，直接暴力矩阵乘法即可，体现"小库无需 ANN"的判断。

### Q16. 为什么本项目要做 L2 归一化、TF 要除以总词数、IDF 用 set 去重？把这三个设计讲清楚。

**参考答案：**
三个设计各对应一个具体目的：
1. **L2 归一化**（`vec /= norm`）：把向量变单位长度，使**余弦相似度退化成点积**，检索时 `doc_matrix @ q_vec` 一句话搞定，且不受文档长短带来的模长差异干扰。`if norm > 0` 防全零向量除零。
2. **TF 除以总词数**（`vec /= len(tokens)`）：归一化词频，**抵消文本长短差异**——长文档每个词原始计数天然偏大，不除会让长文档无脑占优。
3. **IDF 用 `set(tokenize(doc))` 去重**：document frequency 的定义是"含该词的**文档数**"，一个词在同一文档出现多次只算 1 篇，所以先 `set` 去重——这正是 df 区别于 tf 的地方。

能把这三个"为什么"讲清楚，说明真正理解了 TF-IDF 检索而不只是会调库。

## 三、深入 / 手撕题（能否动手 / 追问到底）

### Q17.【手撕代码思路】请实现一个最小 RAG 检索 + 增强流程，说明数据结构与复杂度。

**参考答案（结合本项目）：**
核心是"离线建索引 + 在线检索"两段。骨架（与 `rag_minimal.py` 一致）：

```python
# ---- 离线：建索引（只做一次）----
vocab = build_vocab(KB)                       # {word: col_index}
idf   = compute_idf(KB, vocab)               # idf = log((1+N)/(1+df)) + 1
doc_matrix = np.vstack([embed(d, vocab, idf) # (n_docs, vocab_size)
                        for d in KB])         # 每行 L2 归一化的 TF-IDF

# ---- 在线：检索 + 增强 ----
def rag_answer(query, top_k=2):
    q = embed(query, vocab, idf)             # 同一套 vocab/idf！
    scores = doc_matrix @ q                   # 已归一化 -> 点积=余弦, 一次算全部
    top = np.argsort(scores)[::-1][:top_k]    # 取 top-k
    ctx = [KB[i] for i in top]
    prompt = build_augmented_prompt(query, ctx)  # 拼 context + 指令
    return llm(prompt)                        # 真实系统这里调 LLM
```

要点：
- **同一套 vocab/idf** 编码 query 和 doc（同坐标系，见 Q10）。
- 归一化后 `doc_matrix @ q` 直接是余弦相似度向量。
- **复杂度**：建索引 $O(N\cdot \bar L)$（N 篇、平均长度 $\bar L$）；单次检索暴力点积 $O(N\cdot V)$（V=词表维度，稀疏可优化到非零项）。N 很大时换 ANN 索引把检索降到亚线性。
- 增强 prompt 必带"只用 context 作答 / 无答案则说不知道"指令。

**追问：** 知识库从 8 条涨到 100 万条，这段代码哪里会崩？怎么改？
> `doc_matrix` 全量驻留内存 + 每次 `@` 暴力扫全库，内存和延迟都不可接受。改法：用 **Faiss/Milvus 的 ANN 索引**（HNSW/IVF-PQ），PQ 量化降内存、近似最近邻把检索降到亚线性；vocab 维度爆炸则改用稠密向量（固定低维）。

### Q18.【debug 追问】教学里把 Q5 改成 `"What is the return policy window?"` 后 RAG 准确率从 100% 掉到 80%，定位根因并给三种修法。

**参考答案：**
根因是 **vocabulary mismatch（词表不匹配）**，本项目 TF-IDF 是纯**词面匹配**：
- `policy`、`window` 在知识库里**根本不存在 → OOV**，被 `embed` 的 `if word in vocab` 忽略，对相似度零贡献。
- 文档写的是 `returns ... within 30 days ... receipt`，而问句用 `return`（单数），**不做词干归并 → `return` ≠ `returns`** 视为两个词。
- 结果：query 几乎没有词能和目标文档对齐，余弦偏低甚至为 0，目标文档没排进 top-2 → 漏检 → 抽取式生成器也挑不到，Q5 失败，5 题剩 4 题命中 = 80%。

三种修法（由浅入深）：
1. **朴素 stemming**：`tokenize` 后去掉结尾 `s`，让 `returns→return`。能救本例，但有副作用（`acme's` 的 `s`、`days→day`），说明真实 stemmer 为何更复杂。
2. **同义词扩展 / query 改写**：检索前把 query 扩展近义词（policy↔rules, window↔period）。
3. **换稠密语义检索**（BGE/DPR）：语义向量能匹配 `policy window` ↔ `returns within 30 days`，从根上解决 mismatch——这正是真实系统升级稠密检索的动机。

**追问：** 为什么余弦 cos=0.371 这种"看着很低"的分数其实没问题？
> 因为 query 和文档里大量是停用词和各自独有的词，真正重合的关键词只占一小部分，绝对值天然偏低。**RAG 检索看的是相对排序**——目标文档排进 top-k 即可，不是看绝对相似度高低。把 0.371 当"低分失败"是误判。

### Q19.【设计追问】本项目的 `extractive_generate` 和真实 LLM decoder 有何本质区别？这个简化在评测上掩盖了哪些真实问题？

**参考答案：**
`extractive_generate` 是**抽取式**："不生成新文字，从检索到的句子里挑词重叠最多的那句原文返回"（`overlap = len(q_keywords & s_words)`，并先减停用词）。它和真实 LLM decoder 都承担"基于 context 产出答案"的角色，但有本质区别：
- **抽取 vs 生成**：它只能复述原句，**绝不会脑补、绝对忠实于 context**；真实 LLM 会综合、改写、推理，也因此可能**不忠实**（编出 context 没有的内容）。
- **没有语言理解**：它本质还是词面重叠匹配（和 TF-IDF 同一碗饭），问句改个词形就可能挑错；LLM 有语义理解。
- **无多跳/综合能力**：答案要跨多个 chunk 综合时它无能为力；LLM 可以。

被掩盖的真实问题：因为抽取式天生忠实，本 demo **测不出 faithfulness 问题**（真实 RAG 最大的痛点之一）；也测不出"context 里有答案但 LLM 答错/答偏"、"被噪声/冲突 context 带偏"、"lost in the middle"等只有真生成器才暴露的现象。所以 demo 的 100% 不能外推到生产。

### Q20.【追问到底】请设计一套 RAG 离线评测方案：要哪些数据、哪些指标、怎么分别诊断"检索的锅"和"生成的锅"？

**参考答案：**
**数据**：构造评测集 `{query, 相关 chunk 标注（golden context）, 标准答案}`。可由人工标注或用强 LLM 从文档生成 QA 对再人工抽检。

**指标分两层**（对应 Q14）：
- 检索层：**Recall@k / Hit@k**（golden chunk 是否进 top-k）、**MRR/NDCG**（排序质量）、**Context Recall**（答案所需信息是否被召回）。
- 生成层：**Faithfulness**（答案每句是否被 context 支撑，LLM-judge 或 NLI 判）、**Answer Correctness/Relevance**、**Context Precision**（召回里有多少真有用）。

**归因诊断（关键）**：
| Recall@k | Faithfulness | 答案正确 | 诊断 |
| --- | --- | --- | --- |
| 低 | — | 错 | **检索的锅**：没召回到证据，先修 embedding/chunking/top-k/加 rerank |
| 高 | 低 | 错 | **生成的锅**：证据召回到了但模型脑补/没用，修 prompt 指令/换更强 LLM |
| 高 | 高 | 错 | context 有冲突/歧义或问题本身超纲，查数据质量 |
| — | 高（但 context 无证据却答对）| 对 | 参数侥幸，**不接地**，应判不可靠 |

工程落地：用 **RAGAS / TruLens** 等做自动化回归，每次改 chunk 策略/embedding/top-k 都跑一遍对比，防止"按下葫芦浮起瓢"。本项目的 `keyword_hit` + No-RAG/RAG 对照是这套方案的最小雏形。

**追问：** 没有人工标注 golden context，怎么低成本评测忠实度？
> 用 **LLM-as-judge**：把 (问题, 检索到的 context, 模型答案) 喂给一个强模型，让它逐句判断答案是否能由 context 推出（NLI 风格），输出 faithfulness 分。再对一小批做人工抽检校准 judge 的可信度。成本远低于全量人工标注。

### Q21.【开放设计】给你一个企业知识库（混合 PDF/网页/表格、百万级、需权限控制、内容会更新），从 0 设计一个生产级 RAG，关键决策点列出来。

**参考答案（要点式，体现取舍判断）：**
1. **数据接入与 chunking**：按文档结构切（标题层级/句子边界 + 固定 token 窗 + overlap）；表格/代码单独处理；每个 chunk 带 metadata（来源、时间、权限标签、版本）。
2. **embedding**：选稠密模型（如 BGE / 商用 embedding），中文场景选中文强模型；doc 离线编码入库，query 端按模型要求加指令前缀。
3. **检索**：**hybrid（BM25 + dense）双路召回 + RRF 融合**，兼顾专名精确与语义泛化；向量库用 Faiss/Milvus（HNSW/IVF-PQ）。
4. **过滤**：检索时按用户权限、时效、来源做 **metadata filter**（权限是硬要求，必须在检索层而非生成层做）。
5. **rerank**：cross-encoder 精排，召回 top-50 → 精排 top-3~5，控制 context 预算。
6. **增强**：prompt 带"仅用 context 作答 / 无据则拒答 / 标注 citation"指令；context 拼接注意顺序（重要的放两端缓解 lost-in-the-middle）。
7. **生成**：选合适 LLM，要求输出**带引用**，便于溯源和审计。
8. **更新**：增量入库 + 版本治理 + 近重复去重；过期内容下线。
9. **评测与监控**：上线前用离线评测集跑 Recall@k/Faithfulness（Q20）；上线后监控拒答率、用户反馈、bad case 回流再优化。
10. **降本提速**：embedding/检索/答案多级缓存；context 压缩。

核心判断：**权限/时效在检索层硬过滤，幻觉控制靠"忠实指令 + rerank 减噪 + citation 可溯源"三件套，所有改动都要过离线评测回归。**

## 高频追问速答清单

1. **RAG 三个字母？** Retrieve（检索）、Augment（增强/拼 context）、Generate（生成）。
2. **RAG vs 微调怎么选？** 补知识/要溯源/常更新 → RAG；改风格格式能力/知识静态 → 微调；常组合。
3. **RAG 能消除幻觉吗？** 不能，只能显著降低；漏检、冲突 context、不忠实生成仍会幻觉。
4. **为什么用余弦不用欧氏？** 只看方向不看长度，契合文本"主题是否一致"；L2 归一化后余弦=点积。
5. **L2 归一化的好处？** 余弦退化成点积，一句矩阵乘算全部相似度，且消除长度影响。
6. **chunk 太大太小各坏在哪？** 太大稀释向量+噪声+费 token；太小语义割裂+召回不全；故加 overlap。
7. **top-k 调大调小？** 小了漏检，大了引噪声+费 token+lost-in-the-middle；常配 rerank。
8. **稀疏 vs 稠密检索？** 稀疏（BM25/TF-IDF）吃词面、专名强但同义匹配差；稠密吃语义；生产用 hybrid。
9. **vocabulary mismatch 是什么？** 词面不一致（同义/词形/OOV）导致稀疏检索失配，本项目 `return≠returns`、`policy` OOV。
10. **rerank 为什么需要？** bi-encoder 召回排序不精，cross-encoder 精排提精度、减噪声。
11. **faithfulness 衡量什么？** 答案每句是否都由检索到的 context 支撑（接地），是 RAG 幻觉控制核心指标。
12. **检索的锅还是生成的锅怎么分？** Recall 低=检索锅；Recall 高但 faithfulness 低=生成锅（脑补）。
