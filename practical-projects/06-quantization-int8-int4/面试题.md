## 一、基础题(概念是否懂)

### Q1. 量化到底在做什么?为什么大模型推理一定要量化?
**参考答案:**
量化就是**用更少的比特来表示原本用 FP32/FP16 存的权重(或激活)**,把连续浮点投影到有限的整数格点上。
两个核心动机:
1. **省显存**:7B 模型 FP32 要 $7\times10^9\times4=28$ GB,FP16 要 14 GB,消费级卡装不下;INT8 理论压缩 4x(→7GB),INT4 压缩 8x(→3.5GB)。
2. **省带宽 / 提速**:LLM 自回归解码是 **memory-bound**(瓶颈是把权重从 HBM 搬到计算单元,而非算力)。权重位宽减半,搬运量减半,decode 吞吐近乎翻倍。这也是 **weight-only 量化即便要反量化回 FP16 算也能加速**的根本原因。

代价是**量化误差**:INT8 只有 256 个格点、INT4 只有 16 个,把连续值塞进去必然损失精度。这就是贯穿全场的主线——**精度 vs 压缩的权衡**。

> 追问:既然 INT4 要反量化回 FP16 做矩阵乘,为什么还能加速?
> 答:因为 decode 阶段瓶颈在权重搬运(显存带宽),不在乘法本身。权重以 4bit 存、搬运量小,反量化是在 SRAM/寄存器里就近做的,算力本来就有富余,所以净收益是正的。

### Q2. 写出对称量化的三个核心公式,并解释每一步。
**参考答案:**
$$Q_{max} = 2^{\text{bits}-1}-1 \quad(\text{INT8}=127,\ \text{INT4}=7)$$
$$\text{量化}:\ q = \text{round}\Big(\text{clip}\big(\tfrac{w}{scale},\ -Q_{max},\ Q_{max}\big)\Big)$$
$$\text{反量化}:\ \hat{w} = q \times scale,\qquad scale = \frac{\text{absmax}(w)}{Q_{max}}$$
- `w/scale`:把浮点缩放到整数尺度(投影到格点);`round`:四舍五入取最近整数;`clip`:夹紧防溢出。
- `scale` 是浮点与整数之间的"汇率"——回答"整数 1 代表多大浮点量"。
- absmax 思路:让绝对值最大的权重恰好落到边界 $Q_{max}$,既不浪费格点也不溢出。
本项目 `symmetric_quantize / symmetric_dequantize / per_tensor_scale` 就是这三行的直接实现。

### Q3. 对称量化(symmetric)和非对称量化(asymmetric/affine)有什么区别?各自适合什么数据?
**参考答案:**
- **对称**:整数区间关于 0 对称 $[-Q_{max}, Q_{max}]$,**zero-point 恒为 0**,反量化只需一次乘法 `q*scale`,硬件最友好。本项目全程用对称。
- **非对称**:$scale=\frac{\max-\min}{2^{bits}-1}$,$zp=\text{round}(-\min/scale)$,量化 $q=\text{round}(w/scale)+zp$,反量化 $\hat w=(q-zp)\times scale$。能把整个 $[\min,\max]$ 区间精确覆盖。
- **适用**:权重通常近似**关于 0 对称**(零均值分布)→ 用对称即可,且省去 zero-point 计算;**激活值常偏态**(如 ReLU/GELU 输出非负)→ 用非对称误差更小。

> 追问:对称量化为什么用 $2^{bits-1}-1$ 而不是 $2^{bits-1}$?
> 答:8bit 本可表示 $-128\sim127$(256 个),但对称量化故意弃用 $-128$,换来区间严格对称、zero-point=0、反量化无需加偏移。这是用 1 个码位换硬件简洁性的经典工程取舍。

### Q4. per-tensor / per-channel / group-wise 三种 scale 粒度有什么区别?
**参考答案:**
区别只在 **absmax 在多大范围内取**,粒度从粗到细:

| 粒度 | absmax 范围 | scale 个数(W=[out,in]) | 误差 | 典型用途 |
|---|---|---|---|---|
| per-tensor | 整张张量 | 1 | 最大 | 最省最糙 |
| per-channel(逐行/逐输出通道) | 每行 1 个 | out 个 | 中 | LLM INT8 标配 |
| group-wise(逐组) | 每行切组,每组 1 个 | out×n_groups 个 | 最小 | INT4(GPTQ/AWQ)常用 |

本项目 `per_channel_scale` 用 `amax(dim=1, keepdim=True)` 得到 `[out,1]`;`grouped_quantize` 把每行 reshape 成 `[out, n_groups, group_size]` 在组内取 absmax,得到 `[out, n_groups]`。**粒度越细误差越小,但要多存 scale**。

### Q5. 为什么粒度越细,量化误差越小?
**参考答案:**
核心是**离群值的污染范围**。如果一行/一张里有个特别大的 outlier,它会撑大 absmax → scale 变大 → 格点变稀 → 其余小权重被"压扁"到很少几个格点上,误差暴涨。
absmax 取的范围越局部,**一个离群值能污染的权重越少**:per-tensor 下它污染整张,per-channel 下只污染它所在行,group 下只污染它所在的几十个数。所以 per-channel/group 把误差关进了更小的"隔间"。本项目 [A] 段实验里 INT4 误差 `per_tensor > per_channel > group/g32 > group/g16` 逐级下降,正是这个机制。

### Q6. PTQ 和 QAT 分别是什么?如何选?
**参考答案:**
- **PTQ(Post-Training Quantization,训练后量化)**:模型训完后直接量化,**不需要重训**,只需少量校准数据(calibration set)统计 scale/范围。快、省、对工程友好。本项目就是 PTQ(且是最朴素的 round-to-nearest,无误差补偿)。GPTQ/AWQ/SmoothQuant 都是 PTQ。
- **QAT(Quantization-Aware Training,量化感知训练)**:训练时就插入"伪量化"节点(fake quant),用 **STE(Straight-Through Estimator)** 让梯度穿过不可导的 round,让模型主动适应量化噪声。精度更高,尤其低比特(≤4bit),但要重训、成本高。
- **选择**:大模型优先 PTQ(重训太贵);只有在 PTQ 掉点不可接受、且有训练资源时才上 QAT(或更轻的 QAT 变体如 LLM-QAT)。

> 追问:QAT 里 round 不可导,梯度怎么回传?
> 答:用 STE——前向走真实 round/clip,反向时把 round 的梯度近似为 1(直接把上游梯度透传给输入),clip 区间外则梯度置 0。这样网络能"感知"量化噪声并学着规避。

### Q7. weight-only 量化和 W8A8(权重+激活都量化)有什么区别?
**参考答案:**
- **weight-only(如 W4A16)**:只量化权重,激活保持 FP16。优点:激活有离群值难量化,放着不动就避开了最难的部分;精度好、实现简单。**主要收益是省显存 + 省带宽**(memory-bound 的 decode 受益大)。INT4 weight-only(GPTQ/AWQ)是当前 LLM 部署主流。
- **W8A8(如 LLM.int8、SmoothQuant)**:权重和激活都量化成 INT8,矩阵乘可以走 **INT8 Tensor Core**,**额外吃到算力收益**(compute-bound 的 prefill 阶段、大 batch 服务受益)。但激活量化难、要处理离群值。
- **一句话**:weight-only 省内存为主、好做;W8A8 还能省算力但激活离群值是拦路虎。本项目只做了 weight-only 的雏形。

> 追问:既然 W8A8 能用 INT8 算力,为什么 decode 单序列时 weight-only 反而常更快?
> 答:decode 单序列是 memory-bound,算力不缺,W4 weight-only 的权重更小、搬得更快;而 W8A8 的激活量化/反量化开销在小 batch 下摊不平。大 batch / prefill 才轮到 W8A8 的算力优势发挥。

## 二、进阶题(原理与权衡)

### Q8. LLM 激活里的"离群值(outlier)"问题是什么?为什么它让激活量化变得困难?
**参考答案:**
LLM(尤其 >6.7B)的激活中会出现**系统性的离群值**:极少数特征维度(channel)的激活幅度比其他维度大几个数量级(可达上百倍),且**集中在固定的若干维度**上。
难点:激活量化通常 per-tensor/per-token,一个百倍大的 outlier 撑爆 absmax → scale 巨大 → 其余正常激活被压成几乎全 0,信息尽失,模型直接崩。这正是本项目"离群值撑大 scale 压扁其余值"机制在激活上的放大版(项目练习 3 人为注入 outlier 复现了此现象)。
解法谱系:
- **LLM.int8()**:把离群值所在的少数维度**单独拆出来用 FP16 算**,其余走 INT8,再合并(mixed-precision decomposition)。
- **SmoothQuant**:用等价变换把激活的"量化难度"按 channel **平滑迁移到权重上**($X\to X/s$,$W\to sW$),让两边都好量化。
- **AWQ**:观察到少数"重要权重通道"对应激活大,按激活幅度**搜索 per-channel 缩放**保护重要权重,实现 4bit weight-only。

### Q9. 量化误差的来源有哪些?如何分解?
**参考答案:**
两大来源:
1. **Rounding error(舍入误差)**:`round(w/scale)` 把连续值钉到最近格点,单点误差最大 $\pm scale/2$。格点越密(高 bit / 小 scale)越小。
2. **Clipping error(截断误差)**:超出 $[-Q_{max},Q_{max}]$ 的值被 clip 掉。absmax 法不产生截断(最大值刚好顶到边界),但代价是 scale 被 outlier 撑大、舍入误差变大。
**两者此消彼长**:若用 absmax 则无截断但舍入受 outlier 拖累;若主动收紧范围(如 percentile/MSE 最优 clip)则牺牲少量大值的截断换取多数值更小的舍入,常常总误差更低——这就是 **clipping 与 rounding 的权衡**,也是为什么"absmax 不一定最优"。
此外低比特下还有:格点数本身不足(INT4 仅 16 格)、误差在网络中**逐层累积传播**(本项目 [B] 段两层都量化后误差比单层更明显)。

> 追问:既然 absmax 没有截断误差,为什么实践中常用 percentile/MSE 来定 clip 阈值?
> 答:因为只要存在 outlier,absmax 会把 scale 撑大,导致占绝大多数的"正常值"舍入误差全面上升。用稍小的阈值主动截掉极少数大值,换来多数值的舍入误差下降,总 MSE 反而更低。这是用少量 clipping 换大量 rounding。

### Q10. GPTQ 的核心思想是什么?它比本项目的"朴素 round-to-nearest"强在哪?
**参考答案:**
本项目是 **round-to-nearest(RTN)**:每个权重独立四舍五入,不考虑量化后对输出的整体影响。
GPTQ 的核心是**逐列(逐权重)量化 + 误差补偿**:基于 OBQ/OBS 思想,用该层输入的 **二阶信息(Hessian $H=2XX^T$)** 衡量哪个权重该往哪边舍入代价最小;每量化一个权重,就把它产生的误差**按 Hessian 反向补偿到尚未量化的剩余权重上**,使**整层输出 $\|WX-\hat W X\|$ 最小**而非权重本身误差最小。
强在:RTN 只让 $\|W-\hat W\|$ 小,GPTQ 直接优化"对输出的影响",所以同样 INT4 下精度显著更高。代价是要算 Hessian、要校准数据、更慢。

### Q11. AWQ 和 GPTQ 都做 INT4 weight-only,思路有何不同?
**参考答案:**
- **GPTQ**:基于 Hessian 的**误差补偿**,逐列量化时纠正剩余权重,优化输出重构误差。无显式"保护"概念。
- **AWQ(Activation-aware Weight Quantization)**:观察到**权重重要性由对应激活幅度决定**——激活大的输入通道对应的权重更重要。AWQ 不混合精度,而是给重要通道乘一个 per-channel 缩放 $s$(并把 $s$ 吸收进上一层),**等价变换**把重要权重"放大后再量化"以减小其相对误差,搜索最优 $s$。
- **对比**:AWQ 不需要反向传播/Hessian,更轻量、对校准集更鲁棒、保留通用性好;GPTQ 在某些任务精度略高但更依赖校准。二者都是 group-wise INT4(本项目 group 布局正是它们的简化版)。

### Q12. 同样是 4bit,group-wise 比 per-channel 更准,但为什么不一味把 group 调到最小(如 group=1)?
**参考答案:**
group 越小,scale 越多 → **scale 存储开销越大,有效压缩比越低**。本项目 [A] 段:INT4 per-tensor 压缩 8.00x,g32 降到 7.11x,g16 降到 6.40x——group 减半 scale 数量翻倍,压缩比持续下降。group=1 时每个权重一个 FP16 scale,等于又把数据涨回去了,完全失去量化意义。
所以存在**误差 vs scale 存储的次级权衡**,实践常取 **group=128 或 64**作为甜点(误差已足够低、scale 开销可忽略)。另外 group 太小还会增加 kernel 复杂度、降低访存效率。

> 追问:为什么 group_size 通常取 128/64 而不是任意值?
> 答:一是要能整除 in_features(本项目用 assert 保证);二是要对齐硬件访存/打包边界(如一个 warp、一个 cache line、int4 pack 单元),便于写高效 kernel。128 是误差、存储、kernel 效率三者的工程甜点。

### Q13. 为什么 LLM 权重量化普遍用 per-channel(逐行)而不是 per-token / per-column?
**参考答案:**
关键看**哪个维度在矩阵乘里能被 scale "整除收尾"而不破坏结构**。Linear 的 $Y=XW^T$,$W$ 形状 `[out, in]`。
- **权重 per-channel = 逐 out(逐行)**:每个输出通道一个 scale,反量化时 scale 沿输出维广播,正好对应输出的每一列,**可在 GEMM 后整列乘回 scale**,不破坏累加。这是本项目 `per_channel_scale(dim=1)` 的做法。
- **激活则常用 per-token(逐行 of X)**:每个 token 一个 scale,同样能在输出端干净地缩放回来。
组合 **weight per-channel(out) + activation per-token** 能让两个 scale 在 GEMM 输出处以外积形式干净地乘回,这是 W8A8 高效实现的关键。若选了会"跨进归约维"的粒度,scale 没法提到累加外面,就破坏了整数 GEMM。

### Q14. KV cache 量化是什么?和权重量化有什么不同的考量?
**参考答案:**
长上下文 / 大 batch 服务时,**KV cache 会超过权重成为显存大头**(随 seq_len × batch 线性增长)。把 K、V 缓存量化成 INT8/INT4 能大幅省显存、提升可服务的并发与上下文长度。
不同考量:
- KV 是**激活类数据、有离群值、且逐 token 动态生成**,通常 **per-token / per-head per-channel** 粒度,常用非对称。
- 对**精度敏感**:K 比 V 更敏感(影响 attention 分数),有方案对 K 用更高比特或对 K 做特殊处理。
- 是**在线量化**(边生成边量化),不能像权重那样离线慢慢校准,要求量化开销极低。

## 三、深入 / 手撕题(能否动手 / 追问到底)

### Q15.(手撕)请实现对称 per-channel INT8/INT4 量化-反量化,并说明形状如何广播。
**参考答案(结合本项目 `quantization.py`):**
```python
import torch

def qmax_for_bits(bits):           # INT8->127, INT4->7
    return (1 << (bits - 1)) - 1

def per_channel_quant_dequant(W, bits):
    # W: [out, in]
    qmax = qmax_for_bits(bits)
    absmax = W.abs().amax(dim=1, keepdim=True)   # [out, 1] 每行一个 absmax
    scale  = absmax / qmax                        # [out, 1]
    q = torch.clamp(torch.round(W / scale), -qmax, qmax)  # 广播: [out,in]/[out,1]
    w_hat = q * scale                             # 反量化, 广播回 [out,in]
    return w_hat, scale
```
**广播要点**:`scale` 形状 `[out,1]`,与 `W` 的 `[out,in]` 做逐元素除/乘时,PyTorch 自动把 `scale` 沿 `in` 维广播,**每行用自己的 scale**。`keepdim=True` 是关键——否则 `amax` 返回 `[out]` 无法正确广播。注意要用 `amax` 而非 `max`(后者返回 `(values, indices)` 元组)。

> 追问 1:如果某行权重全为 0 会怎样?如何防护?
> 答:absmax=0 → scale=0 → `W/scale` 出现除零得 NaN。真实框架会给 scale 加下限:`scale = absmax.clamp_min(eps) / qmax`(eps 如 1e-8)。本项目 toy 随机权重不会全 0 故未处理,这是常见坑。
>
> 追问 2:如何在此基础上改成 group-wise?
> 答:把 `W` reshape 成 `[out, n_groups, group_size]`(需 `in % group_size == 0`),在 `dim=2`(组内)取 absmax,得到 `[out, n_groups, 1]` 的 scale,量化后再 reshape 回 `[out, in]`。即本项目 `grouped_quantize` 的做法。

### Q16.(手撕)把对称量化改写成非对称量化,给出公式与代码,并说明何时该用。
**参考答案:**
非对称(affine)量化覆盖任意 $[\min,\max]$ 区间:
$$scale=\frac{\max - \min}{2^{bits}-1},\quad zp=\text{round}\Big(-\frac{\min}{scale}\Big)$$
$$q=\text{clip}\big(\text{round}(w/scale)+zp,\ 0,\ 2^{bits}-1\big),\quad \hat w=(q-zp)\times scale$$
```python
def asymmetric_quant_dequant(W, bits):
    qmax = (1 << bits) - 1                  # 注意: 用满 0..2^bits-1
    wmin, wmax = W.min(), W.max()
    scale = (wmax - wmin) / qmax
    zp    = torch.round(-wmin / scale)
    q     = torch.clamp(torch.round(W / scale) + zp, 0, qmax)
    w_hat = (q - zp) * scale
    return w_hat, scale, zp
```
**何时用**:数据**偏态、不关于 0 对称**时(典型是 ReLU/GELU 后的激活,非负)。此时对称量化浪费一半码位(负半区没数据),非对称把全部码位铺在真实范围上,误差更小。代价是反量化多了 `-zp` 偏移,整数 GEMM 还会引入交叉项(需把 zp 相关项预计算),硬件略复杂——所以**权重(近似对称)用对称、激活(偏态)用非对称**是常见组合。

### Q17.(追问到底)本项目里 toy 权重连 per-tensor INT8 都几乎无损(cosine 0.999992),为什么真实 LLM 不能这么乐观?这暴露了项目的什么局限?
**参考答案:**
toy 权重是 PyTorch 随机初始化、分布温和**无离群值**,256 个格点绰绰有余,所以连最糙的 per-tensor INT8 都近乎无损。但真实 LLM 权重(尤其训练后)有**重尾分布和离群值**,per-tensor 会被少数大值撑大 scale、压扁多数值,误差远大于此。这正是 per-channel/group 在工程上**必要**的原因(项目练习 3 通过人为注入 outlier 复现了这一点)。
本项目**刻意省略**的、与真实工程的差距:
1. 只做**对称量化**(无 zero-point,激活偏态量化不了);
2. **只量化权重不碰激活**(避开了 LLM 最难的激活离群值问题);
3. 用浮点张量**模拟整数**,**无真实 bit-packing**,压缩比是估算、**无真实内存/速度收益**;
4. **PTQ 且 RTN**,无 GPTQ 式误差补偿;
5. **toy 规模**,无法暴露规模相关的离群值现象。
理解这些钩子,正好对接 LLM.int8 / GPTQ / AWQ / SmoothQuant 的动机。

### Q18.(追问到底)本项目用浮点张量"模拟"int8/int4,所以压缩比和加速都是估算。要落地真实加速,工程上还差哪些关键环节?
**参考答案:**
1. **真实 bit-packing**:int4 需把两个 4bit 打包进一个 byte(int8 也要真正以 1 byte 存),否则内存根本没省。本项目 `q` 的 dtype 仍是浮点,无任何打包。
2. **定制 CUDA/Triton kernel**:需要 dequant-in-kernel(把权重以 int4 读入、在寄存器/SRAM 里反量化、立刻参与 GEMM),否则反量化的访存开销吃掉收益。代表:GPTQ 的 exllama kernel、AWQ 的 GEMM kernel、Marlin、bitsandbytes。
3. **scale/zp 的高效布局**:group scale 要和权重 pack 在一起、对齐访存边界,避免额外随机访问。
4. **W8A8 还需 INT8 Tensor Core 路径**与激活的在线量化/反量化融合。
5. **算子融合**:dequant + GEMM + (bias/激活) 融成一个 kernel 减少访存往返。
一句话:**算法决定能压多少,kernel 决定能快多少**——本项目只做了前者的雏形。

### Q19.(设计/权衡)给你一个 7B 模型,要部署到单张 24GB 消费卡做单用户对话,你怎么选量化方案?换成高并发服务器呢?
**参考答案:**
- **单卡单用户对话(memory-bound,batch≈1)**:首选 **INT4 weight-only group-wise(AWQ 或 GPTQ,group=128)**。理由:decode 是 memory-bound,W4 权重最小、搬运最快、吞吐最高;激活保 FP16 避开离群值、精度好;7B INT4 约 3.5GB,余量充足给 KV cache。若上下文很长,再叠加 **KV cache INT8**。
- **高并发服务器(大 batch,prefill 占比高,compute-bound)**:可考虑 **W8A8(SmoothQuant)** 走 INT8 Tensor Core 吃算力收益,大 batch 下激活量化开销摊薄;或 W4A16 + 高效 batched kernel。需实测两条路线在目标 batch 下的吞吐。
- **通用判断**:先定**精度红线**(跑下游评测,INT4 掉点能否接受);再看**瓶颈类型**(小 batch→省带宽选 weight-only;大 batch→省算力可选 W8A8);最后看**kernel 生态**(有没有现成高效 kernel,如 Marlin/AWQ kernel)。

> 追问:如果 INT4 整体掉点超标但只有个别层敏感,怎么办?
> 答:**混合精度量化**——对敏感层(常是首尾层、attention 的某些投影)用 INT8 或保 FP16,其余用 INT4;或对敏感层用更小 group。本质是把比特预算花在刀刃上。

## 高频追问速答清单

1. **Qmax 为什么 INT8 是 127 不是 128?** 对称量化弃用 -128 换 zero-point=0、区间对称、反量化无偏移。
2. **scale 的物理意义?** 浮点与整数的"汇率",整数 1 代表多少浮点量;`scale=absmax/Qmax`。
3. **per-channel 为啥比 per-tensor 准?** outlier 只污染它所在的行,不再撑爆整张的 scale。
4. **INT8 vs INT4 误差差多少?** 本项目权重 MSE 从 ~1e-8 跳到 ~1e-5(约 1000 倍),但 INT4 余弦仍 >0.99 可用。
5. **weight-only 为什么 decode 能加速?** decode 是 memory-bound,权重小→搬得快,算力本就富余。
6. **激活为啥比权重难量化?** 激活有系统性离群值(某些维度幅度大百倍),撑爆 scale 压垮其余。
7. **LLM.int8 的招?** 离群维度拆出来走 FP16,其余走 INT8,再合并(mixed-precision decomposition)。
8. **SmoothQuant 的招?** 等价变换 $X/s,\ sW$ 把激活量化难度平滑迁移到权重,两边都好量化。
9. **GPTQ 比 RTN 强在哪?** 用 Hessian 逐列量化并把误差补偿到剩余权重,优化输出重构误差而非权重误差。
10. **AWQ 的招?** 按激活幅度找重要权重通道,per-channel 缩放保护后再量化,4bit weight-only。
11. **group_size 怎么选?** 误差 vs scale 存储权衡,常取 128/64;太小压缩比反降、kernel 复杂。
12. **PTQ vs QAT?** PTQ 免重训、靠校准数据,主流;QAT 训练时 fake-quant + STE,低比特精度更高但贵。
13. **QAT 里 round 不可导咋办?** STE:前向真 round,反向梯度近似为 1 透传。
14. **压缩比为啥达不到理论值?** per-channel/group 要多存 scale,分母变大;且本项目 scale 按 FP16 估。
15. **scale 为 0 会怎样?** 除零得 NaN,真实框架给 scale 加 eps 下限(`clamp_min`)。
