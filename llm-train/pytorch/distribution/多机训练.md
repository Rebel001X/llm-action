## 0. 一句话锚点

**多机训练 = 在 N 台机器上各启动若干进程，每个进程独占一张 GPU；所有进程通过 rendezvous 互相发现，组成一个 `world_size = N × 每机GPU数` 的通信组，之后用集合通信（AllReduce 等）同步梯度/参数。** 单机多卡你已经会了，多机只是把「同步的范围」从机器内总线（NVLink/PCIe）扩展到机器间网络（InfiniBand/以太网）。

## 1. 地基：单机为什么不够，多机解决什么问题

单台服务器的能力有天花板：

- **显存墙**：一台机器通常 8 张卡。大模型（参数 + 优化器状态 + 激活）放不下，需要更多卡来切分（ZeRO / 张量并行 / 流水并行）。
- **算力墙**：数据量和模型规模上来后，单机吞吐不够，训练一遍要几个月。靠堆机器线性放大算力。
- **扩展性**：业务要求「加机器就能更快」，必须支持跨节点。

多机训练就是把这三堵墙往外推。**但它不是免费的**：

```
机器内通信         机器间通信
NVLink ~数百GB/s   InfiniBand ~数十~数百Gb/s（注意单位 bit vs Byte）
                   以太网（TCP）更慢、延迟更高
```

> ⚠️ 文档原文的关键提醒：**节点间通信延迟是瓶颈**。在「1 台机器的 4 张卡」上训练，通常比「4 台机器各 1 张卡」更快——因为前者走机内高速总线，后者每一步同步都要过网络。所以扩展原则是：**先把单机的卡占满，再加机器**。

## 2. 进程模型：rank / world_size / local_rank

分布式训练的核心抽象是「**每张 GPU 一个进程**」。每个进程需要知道三个身份编号：

| 变量 | 含义 | 范围 | 用途 |
|------|------|------|------|
| `WORLD_SIZE` | 全局进程总数 | = 所有节点 GPU 数之和 | 集合通信组的大小 |
| `RANK`（global rank） | 全局唯一编号 | `0 .. world_size-1` | 标识「我是哪个进程」，rank 0 常作主进程 |
| `LOCAL_RANK` | 本节点内编号 | `0 .. 本机GPU数-1` | **决定我用本机哪张卡**（`cuda:LOCAL_RANK`） |

为什么要区分 global 和 local？因为「我用哪张物理卡」是机器内的事（用 `LOCAL_RANK`），「我在整个通信组里的座位号」是全局的事（用 `RANK`）。

下面这张图把 2 台机器、每台 4 卡（world_size=8）的编号画清楚：

```
                    world_size = 8
   ┌─────────────────────────┐   ┌─────────────────────────┐
   │      Node 0 (机器A)      │   │      Node 1 (机器B)      │
   │ GPU0  GPU1  GPU2  GPU3   │   │ GPU0  GPU1  GPU2  GPU3   │
   │ R=0   R=1   R=2   R=3    │   │ R=4   R=5   R=6   R=7    │  ← RANK 全局唯一
   │ L=0   L=1   L=2   L=3    │   │ L=0   L=1   L=2   L=3    │  ← LOCAL_RANK 各机从0
   └──────────┬──────────────┘   └──────────┬──────────────┘
              │      跨节点网络（IB / Ethernet）       │
              └───────────────┬───────────────────────┘
                       AllReduce 同步梯度
```

注意 Node 1 的 `LOCAL_RANK` 也从 0 开始——**local_rank 在每台机器内独立**，而 `RANK` 跨机器连续不重复。

> ⚠️ 原文警告（很重要）：**不要把 `RANK` 用于训练的关键业务逻辑**。当 torchrun 在「失败/成员数变化」后重启进程时，**不保证某个进程仍是原来的 LOCAL_RANK / RANK**。`RANK` 只适合做「谁来做日志、谁来存 checkpoint（通常 rank 0）」这类幂等的协调工作，不能用它来切分不可重放的数据状态。

## 3. rendezvous（会合）：进程怎么互相找到

多个机器上的进程一开始互不相识，必须先「会合」，确定彼此地址、协商出 `world_size` 和各自 `RANK`。这个过程叫 **rendezvous**。三个关键参数：

| 参数 | 含义 | 例子 |
|------|------|------|
| `--rdzv-id` | 这次作业的唯一标识（一个 job 一个 id） | `job123` |
| `--rdzv-backend` | 会合用的后端（如 `c10d`） | `c10d` |
| `--rdzv-endpoint` | 会合点地址 `host:port`，**所有节点填同一个** | `192.168.1.1:29400` |

会合点本质是一个所有进程都能连到的「集合地」。**关键纪律：每台机器上的 torchrun 命令必须用完全相同的 rendezvous 参数**，它们才能聚到同一个组里。

```
Node0 进程 ─┐
Node0 进程 ─┤
Node0 进程 ─┤        rdzv-endpoint = 192.168.1.1:29400
Node0 进程 ─┼──────► [  会合点 / store  ] ──► 协商出 RANK、WORLD_SIZE
Node1 进程 ─┤        rdzv-id        = job123      并广播给所有进程
Node1 进程 ─┤        rdzv-backend   = c10d
Node1 进程 ─┘
```

会合完成后，进程间会建立真正的通信通道（NCCL 通信子），后续的集合通信就在这条通道上跑。

## 4. 方法一：每台机器跑一条 torchrun 命令

最直接的方式。**在每个节点上手动（或用 ssh/pdsh）执行一条 torchrun**，区别只在 `--node-rank`（本机是第几个节点）。

类别上需要指定的参数（具体参数名以官方文档为准）：

- **本机进程数**：`--nproc-per-node`（通常 = 本机 GPU 数）
- **节点总数**：`--nnodes`（如 `2`，或弹性写法 `1:4` 表示 1~4 个节点）
- **本节点序号**：`--node-rank`（Node0 填 0，Node1 填 1，…）
- **会合三件套**：`--rdzv-id` / `--rdzv-backend` / `--rdzv-endpoint`

调用链（torchrun 帮你做了什么）：

```
你 ── torchrun ──► 读 --nproc-per-node、--node-rank、rdzv-* 参数
                    │
                    ├─► fork 出 N 个 worker 进程（N = nproc-per-node）
                    │     为每个 worker 注入环境变量：
                    │       RANK / LOCAL_RANK / WORLD_SIZE / MASTER_ADDR ...
                    │
                    ├─► 各 worker 走 rendezvous 与其他节点会合
                    │
                    └─► 监控 worker；任一挂掉 → 按弹性策略重启整组
你的训练脚本 ──► 直接读 os.environ["LOCAL_RANK"] 等，无需自己算 rank
```

> 价值：你**不用**手动给每个进程传 rank/world_size，torchrun 通过环境变量注入；你也不用写「拉起多进程」的样板代码。

## 5. 方法二：用 SLURM 把作业部署到集群

在真实的计算集群上，不会手动登录每台机器敲命令，而是交给**作业调度器 SLURM**。你写一份 `sbatch` 脚本声明资源需求（要几个节点、每节点几张卡、跑多久），提交后 SLURM：

1. 从集群里**分配**满足条件的节点；
2. 在每个分配到的节点上**拉起**你的进程（`srun`）；
3. 注入 SLURM 自己的环境变量（如节点列表、本进程编号），你的脚本/torchrun 据此推导 rank。

```
   你 ── sbatch train.slurm ──►  ┌──────── SLURM 控制器 ────────┐
                                 │ 排队 → 分配 node[01-04] → srun │
                                 └───────────┬──────────────────┘
                ┌──────────────┬─────────────┼──────────────┐
              node01         node02        node03         node04
             （8 GPU）       （8 GPU）      （8 GPU）       （8 GPU）
                └──────── 组成 world_size = 32 的通信组 ────────┘
```

SLURM 方式的好处：**多人共享集群、排队公平、资源隔离、自动选机器**；缺点是要懂调度器语法。两种方式底层都是「一进程一卡 + rendezvous + 集合通信」，只是「谁来拉起进程、谁来选机器」不同。参考 [[llm-train/slurm/README]]（若存在）。

## 6. 网络与后端：走哪张网卡、走 IB 还是以太网

多机训练真正「跨机器」的部分由**通信后端**承担：

| 后端 | 适用 | 说明 |
|------|------|------|
| **NCCL** | GPU 训练（首选） | NVIDIA 集合通信库，自动用 NVLink + IB/RoCE，性能最好 |
| **Gloo** | CPU / 调试 / 无 NCCL 环境 | 走 TCP，慢，但通用 |

跨节点同步梯度本质上是一次 **AllReduce**（见 [[ai-infra/网络/集合通信原语]]）。NCCL 在机内走 NVLink、机间走 InfiniBand/RoCE，并用 **Ring / Tree** 等算法把带宽利用到极致（见 [[ai-infra/网络/NCCL]]、[[ai-infra/网络/InfiniBand]]）。

**最常见的多机坑：选错网卡。** 机器往往有多块网卡（管理用千兆以太、训练用 IB）。如果 NCCL/Gloo 误选了慢网卡甚至 docker 虚拟网卡，会卡死或极慢。需要显式指定走哪张网络接口（环境变量类别，具体名以官方文档/源码为准）：

```
NCCL_SOCKET_IFNAME   告诉 NCCL 用哪个网络接口名（如 ib0 / eth0）
NCCL_IB_HBA / IB 相关 强制走 InfiniBand
GLOO_SOCKET_IFNAME   Gloo 的对应项
NCCL_DEBUG=INFO      打印详细日志，定位「它到底选了哪张卡、用了什么算法」
```

> 排错黄金法则（原文也强调）：先确认**节点间 TCP 能互通**（能 ping、会合端口没被防火墙挡），再 `export NCCL_DEBUG=INFO` 看日志。绝大多数「多机卡在第一步」都是网络可达性或网卡选择问题。

## 7. 异构扩展（Heterogeneous Scaling）

torchrun 支持**每台机器 GPU 数不同**。例如机器 A 出 4 张卡、机器 B 出 2 张卡，组成 world_size=6 的作业——只需各自把 `--nproc-per-node` 设成本机实际卡数即可。`RANK` 仍然全局连续编号。这在「凑机器」「集群异构」时很实用，但要注意**各卡负载尽量均衡**，否则快卡会等慢卡（木桶效应）。

## 8. 容错与弹性（Elastic / Fault Tolerance）

torchrun（torchelastic）的一大价值是**弹性**：当某个进程/节点崩溃，它不会让整个作业直接死掉，而是：

```
某 worker 崩溃
   │
   ▼
torchrun 检测到 → 终止本组所有 worker → 重新 rendezvous
   │（成员数可在 --nnodes 的 min:max 范围内变化）
   ▼
从最近一次 checkpoint 恢复 → 继续训练
```

这就是为什么前面强调「**不要依赖 RANK 不变**」——重启后座位会重排。配套要求：**训练脚本必须能从 checkpoint 恢复**（定期由 rank 0 存盘），否则弹性重启只会从头再来。

## 单机多卡代码 → 多机代码：到底改了什么（最小改动）

如果你已经会用 `DistributedDataParallel`（DDP）做单机多卡，迁到多机的**代码改动极小**，核心是「rank 的来源变了」：

| 关注点 | 单机多卡 | 多机多卡 | 说明 |
|--------|----------|----------|------|
| 取 device | `cuda:LOCAL_RANK` | 同 | local_rank 选本机卡，写法不变 |
| 初始化进程组 | `init_process_group(backend="nccl")` | 同 | rank/world_size 从环境变量自动取，**不要硬编码** |
| 全局 rank | 单机时 RANK==LOCAL_RANK | 多机时 RANK≠LOCAL_RANK | 凡是「全局唯一」逻辑（存 checkpoint、打日志）用 `RANK==0` 判断 |
| 数据切分 | `DistributedSampler` 按 world_size 切 | 同 | sampler 自动用 world_size/rank，无需改 |
| 启动方式 | `torchrun --nproc-per-node=K 脚本` | 各节点加 `--nnodes --node-rank --rdzv-*` | **主要改动在这里**，脚本本身几乎不动 |

骨架（示意，具体 API 以官方文档为准）：

```
# 训练脚本里：身份全部从环境变量读，不要自己算
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group(backend="nccl")   # rank/world_size 自动从环境取
model = DDP(model.to(local_rank), device_ids=[local_rank])
# 只有 rank 0 存 checkpoint / 打主日志
if int(os.environ["RANK"]) == 0:
    save_checkpoint(...)
```

**一句话总结改动**：业务代码基本不动，把「身份来源」交给环境变量，把「启动命令」加上节点/会合参数即可。

## 典型配置示例（讲含义，不背默认值）

下面用「2 节点 × 每节点 8 卡 = world_size 16」说明各参数**做什么**（参数名/默认值以官方为准）：

```
# 在 Node0（节点0）执行：
torchrun \
  --nnodes=2 \                       # 总共 2 个节点
  --nproc-per-node=8 \               # 本机起 8 个进程（= 8 张卡）
  --node-rank=0 \                    # 我是第 0 个节点
  --rdzv-id=my_job \                 # 本次作业唯一 id（两节点必须一致）
  --rdzv-backend=c10d \              # 会合后端
  --rdzv-endpoint=10.0.0.1:29400 \   # 会合点（两节点必须填同一个）
  train.py --your-args

# 在 Node1（节点1）执行：只把 --node-rank 改成 1，其余完全相同
torchrun --nnodes=2 --nproc-per-node=8 --node-rank=1 \
  --rdzv-id=my_job --rdzv-backend=c10d --rdzv-endpoint=10.0.0.1:29400 \
  train.py --your-args
```

读法：`--nnodes × --nproc-per-node = world_size`；`--rdzv-endpoint` 让两台机器在同一个会合点碰头；`--node-rank` 是唯一在不同机器上取不同值的参数。**配 SLURM 时，节点列表/会合地址通常由 SLURM 环境变量推导，不手填。**

## 常见问题 / 坑

| 现象 | 根因 | 怎么办 |
|------|------|--------|
| 卡在初始化（hang），不报错 | rendezvous 端口不通 / 防火墙 / endpoint 写错 | 先 ping + telnet 会合端口；确认各节点 rdzv 参数完全一致 |
| 极慢 / 偶发超时 | NCCL 选了慢网卡或虚拟网卡 | 显式设 `NCCL_SOCKET_IFNAME` 指定 IB/正确网卡；开 `NCCL_DEBUG=INFO` 看选了谁 |
| 报「找不到/不能用 IB」 | 没装 IB 驱动 / 容器没透传设备 | 检查 IB 软件栈与容器配置（见 [[ai-infra/网络/IB软件]]）|
| `node-rank` 重复或缺失 | 多节点填了相同 node-rank | 每个物理节点的 node-rank 必须唯一、连续 |
| 重启后数据/状态错乱 | 用 RANK 做了不可重放的关键逻辑 | 改为从 checkpoint 恢复；只用 RANK==0 做幂等协调 |
| 各节点版本/CUDA/NCCL 不一致 | 镜像不统一 | 所有节点用同一镜像/同一依赖版本 |
| 多机比单机还慢 | 误把任务摊到「多机各 1 卡」 | 先占满单机再加机器；让机内走 NVLink |
| 时钟/主机名解析问题 | DNS / hosts 不一致 | 用 IP 作 endpoint，或保证各节点能解析彼此主机名 |

> 通用排错顺序：**网络可达性 → 网卡选择（NCCL_DEBUG=INFO） → 后端/驱动 → 版本一致性 → 代码里的 rank 误用**。
