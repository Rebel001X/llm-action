# PyTorch 分布式通信包(torch.distributed)

> 一句话定位：`torch.distributed` 是 PyTorch 多进程并行训练的「通信底座」——它把分散在多卡/多机上的进程组织成一个进程组(ProcessGroup)，再用集合通信原语(all-reduce 等)让它们交换张量，DDP / 张量并行 / 流水并行全部建立在它之上。📍 导航：[[00-知识地图]]

## 0. 一句话锚点

> **单机单卡 = 一个进程；分布式训练 = N 个进程，每个进程绑一块 GPU，`torch.distributed` 负责让这 N 个进程「说同一种话」并「同步交换张量」。**

记住这条主线，后面所有概念都是它的展开：
- 「说同一种话」→ **Backend(后端：NCCL/Gloo/MPI)**
- 「找到彼此」→ **init_process_group + 环境变量(MASTER_ADDR/RANK/WORLD_SIZE)**
- 「交换张量」→ **集合通信原语(all_reduce / broadcast / all_gather …)**

官方文档：<https://pytorch.org/docs/stable/distributed.html>

## 1. 地基：进程、进程组与 DDP 的设计哲学

### 1.1 它提供了什么(原文真料·Basics)

> `torch.distributed` 包为在一台或多台机器上运行的多个计算节点之间的**多进程并行**提供了 PyTorch 支持和**通信原语**。

> `torch.nn.parallel.DistributedDataParallel()`(DDP)类基于此功能构建，提供**同步分布式训练**作为任何 PyTorch 模型的包装器。

这与两个「看起来像」的东西**本质不同**：

| 方案 | 进程数 | 跨机 | GIL 问题 | 现状 |
|------|--------|------|----------|------|
| `torch.nn.DataParallel` (DP) | **1 个进程多线程** | ❌ 不支持 | 有 GIL 颠簸 | 已不推荐 |
| `torch.multiprocessing` | 多进程 | ❌ 仅单机 | 无 | 底层工具 |
| **DDP(基于 torch.distributed)** | **多进程，每进程 1 卡** | ✅ 支持 | 无 | **主流** |

> 用户必须为每个机器**显式启动主训练脚本的单独副本进程**（这就是为什么要用 `torchrun` / `mpirun` 拉起多份进程）。

### 1.2 为什么 DDP 比 DataParallel 快？(原文两条核心理由)

原文给了两条「即使在单机也更优」的关键理由，这是面试高频点，逐条拆解：

**理由①：每个进程维护自己的优化器，省掉了参数广播。**
> 每个进程都维护自己的优化器，并在每次迭代时执行完整的优化步骤。由于梯度已经被收集在一起并在进程间求平均，因此对每个进程都是相同的 → **不需要参数广播步骤**，减少了节点间传输张量的时间。

```
DataParallel(主从式，串行瓶颈)        DDP(对等式，无主节点)
   ┌──────── GPU0(主) ───────┐         GPU0   GPU1   GPU2   GPU3
   │ 1.scatter 输入到各卡    │          │      │      │      │
   │ 2.各卡前向              │         前向   前向   前向   前向
   │ 3.gather 输出回 GPU0    │          │      │      │      │
   │ 4.GPU0 算 loss/反向     │         反向   反向   反向   反向
   │ 5.broadcast 新参数 ↓↓↓  │          └──┬───┴──all_reduce┴──┐
   └─────────────────────────┘             ▼ 梯度求平均(对称)  ▼
   ★ GPU0 既算又广播 = 瓶颈            ★ 各进程已持有相同梯度
                                          各自更新，无需广播参数
```
> **关键洞察**：DDP 同步的是**梯度**(反向时 all-reduce)，而不是参数。梯度同步后每个进程独立做完全相同的 `optimizer.step()`，结果天然一致，所以无需广播参数。

**理由②：每进程独立 Python 解释器，消除 GIL 颠簸。**
> 每个进程都包含一个独立的 Python 解释器，消除了从单个 Python 进程驱动多个执行线程、模型副本或 GPU 带来的额外解释器开销和「GIL 颠簸」（GIL-thrashing）。

> 这对于**大量使用 Python 运行时的模型**尤其重要，包括具有循环层(RNN/LSTM)或许多小组件的模型——因为这类模型 Python 侧调度频繁，单进程多线程会被 GIL 反复抢锁拖慢。

### 1.3 四个必懂术语

| 术语 | 含义 | 例子(2 机 ×4 卡 = 8 进程) |
|------|------|---------------------------|
| `world_size` | 全局进程总数 | 8 |
| `rank` | 全局进程编号，唯一 | 0~7 |
| `local_rank` | 机器内进程编号 | 每机 0~3 |
| `ProcessGroup` | 一组互相通信的进程 | 默认组含全部 8 个 |

```
   Node 0 (MASTER)              Node 1
 ┌───────────────────┐    ┌───────────────────┐
 │ rank0 local0 GPU0 │    │ rank4 local0 GPU0 │
 │ rank1 local1 GPU1 │    │ rank5 local1 GPU1 │
 │ rank2 local2 GPU2 │    │ rank6 local2 GPU2 │
 │ rank3 local3 GPU3 │    │ rank7 local3 GPU3 │
 └───────────────────┘    └───────────────────┘
        world_size = 8 ; rank ∈ [0,7] ; local_rank ∈ [0,3]
```

## 2. 后端 Backend：进程之间「用什么搬张量」

> 原文 `# Backends` 一节的核心：不同硬件需要不同的通信库。

PyTorch 支持三种后端。**选错后端 = 训练慢或直接报错**，所以这是配置第一步。

| 后端 | 适用设备 | 跨机 | 速度 | 何时用 |
|------|----------|------|------|--------|
| **NCCL** | **GPU(CUDA)** | ✅ | 最快(走 NVLink/IB) | **GPU 训练首选** |
| **Gloo** | CPU / GPU | ✅ | 中等 | CPU 训练、NCCL 不可用时兜底 |
| **MPI** | CPU / GPU | ✅ | 取决于实现 | 已有 HPC/MPI 集群 |

```
  应用层:   DDP / all_reduce(...)
              │  调用同一套 API
        ┌─────┴──────────────────────┐
        ▼                            ▼
   backend="nccl"             backend="gloo"
        │                            │
   ┌────┴─────┐                ┌─────┴────┐
   │ NVLink   │ GPU-GPU 直连   │  TCP     │ 走以太网 socket
   │ InfiniBand│ 跨机 RDMA     │  socket  │
   └──────────┘                └──────────┘
```

> **经验法则**：用 GPU 就选 `nccl`；纯 CPU 调试或 NCCL 装不上就用 `gloo`。

## 3. 初始化与关键环境变量：进程如何「找到彼此」

8 个进程是被 `torchrun` 分别独立拉起的，启动瞬间互不知道对方存在。它们靠一个**约定的会合点(rendezvous)** 凑齐：所有进程都连到 **rank0 所在机器的 IP:PORT**。

```
torchrun --nproc_per_node=4 --nnodes=2 \
         --master_addr=10.0.0.1 --master_port=29500 train.py
                    │
                    ▼ 每个进程内部执行
   dist.init_process_group(backend="nccl")
                    │
   ┌────────────────┴────────────────────────────┐
   │ 读取环境变量:                                 │
   │   RANK / WORLD_SIZE / MASTER_ADDR / MASTER_PORT│
   │   → 所有进程连到 MASTER_ADDR:MASTER_PORT 会合  │
   │   → 凑齐 WORLD_SIZE 个进程后，ProcessGroup 建成 │
   └───────────────────────────────────────────────┘
```

| 环境变量 | 作用 | 谁设置 |
|----------|------|--------|
| `MASTER_ADDR` | rank0 机器 IP(会合地址) | 用户/torchrun |
| `MASTER_PORT` | 会合端口(需空闲，如 29500) | 用户/torchrun |
| `WORLD_SIZE` | 全局进程总数 | torchrun 自动 |
| `RANK` | 本进程全局编号 | torchrun 自动 |
| `LOCAL_RANK` | 本进程机器内编号(用来 `set_device`) | torchrun 自动 |

> **为什么会卡住不动？** 若某个 rank 的 `MASTER_ADDR/PORT` 配错或防火墙挡了端口，`init_process_group` 会一直**阻塞等待**直到超时——这是新手最常见的「程序假死」原因。

## 4. 网络接口选择(原文真料·常用环境变量)

> 默认情况下，NCCL 和 Gloo 后端**都会尝试自动找到**要使用的正确网络接口。

但自动检测**不总是对**——多网卡机器(管理网 + 数据网)上，可能选到慢的那块网卡。此时用环境变量**手动覆盖**：

```bash
# 指定 NCCL 使用的网卡(GPU 后端)
export NCCL_SOCKET_IFNAME=eth0

# 指定 Gloo 使用的网卡(CPU 后端)
export GLOO_SOCKET_IFNAME=eth0
```

**Gloo 可指定多块网卡(NCCL 不可)**：
> 如果使用 Gloo 后端，可通过逗号分隔指定多个接口。后端将以**循环(round-robin)方式**跨这些接口调度操作：

```bash
export GLOO_SOCKET_IFNAME=eth0,eth1,eth2,eth3
```

> ⚠️ **硬性约束**：所有进程必须在此变量中指定**相同数量**的接口，否则会合失败。

```
  多网卡机器                NCCL_SOCKET_IFNAME=eth0
 ┌──────────────┐          只把通信压在 eth0(数据网/IB)
 │ eth0 100Gb IB│◄────────  ✅ 高带宽
 │ eth1  1Gb mgmt│          自动检测可能误选 eth1 → 慢 100 倍
 └──────────────┘
```

> **数值直觉**：100Gb/s 数据网 vs 1Gb/s 管理网，选错网卡 all-reduce 带宽差 **100×**，大模型梯度同步会成为绝对瓶颈。

## 5. NCCL 调试与性能调优(原文真料·其他 NCCL 环境变量)

### 5.1 调试：让 NCCL 把话说清楚

> 如果 NCCL 失败，可设置 `NCCL_DEBUG=INFO` 打印**显式警告消息**以及**基本 NCCL 初始化信息**。

```bash
export NCCL_DEBUG=INFO          # 打印初始化信息与警告(排障第一步)
```

更细粒度用 `NCCL_DEBUG_SUBSYS` 锁定某个子系统：

| `NCCL_DEBUG_SUBSYS=` | 打印什么 | 用来排查 |
|----------------------|----------|----------|
| `COLL` | collective 调用日志 | **挂起(hang)**，尤其 collective 类型或**消息大小不匹配**导致的卡死 |
| `GRAPH` | 拓扑检测详细结果 | 拓扑检测失败；可**保存**供 NCCL 团队进一步分析 |

```bash
# 调试集合通信挂起(各 rank 调用不一致/张量尺寸不一致最常见)
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=COLL

# 拓扑检测失败时
export NCCL_DEBUG_SUBSYS=GRAPH
```

> **为什么 COLL 能定位 hang？** all-reduce 要求**每个 rank 都参与且张量形状一致**；只要有一个 rank 没调用或尺寸不同，整组就会永久互相等待。`COLL` 日志能让你看到「卡在哪个 collective、谁没到齐」。

### 5.2 性能调优：socket 系统上压榨带宽

> NCCL 根据其**拓扑检测自动调优**，以节省用户的调优工作。

> 在某些**基于 socket 的系统**上，用户仍可尝试调整以下两个变量以增加 socket 网络带宽：

```bash
export NCCL_SOCKET_NTHREADS=4      # 每个 socket 连接的线程数
export NCCL_NSOCKS_PERTHREAD=4     # 每线程的 socket 数
```

> 📌 **重要提示(原文)**：NCCL 已针对某些云提供商(如 **AWS、GCP**)**预先调优**了这两个变量——在这些云上通常**不要手动改**，以免越调越慢。

> NCCL 环境变量完整列表见 NVIDIA 官方文档：
> <https://docs.nvidia.com/deeplearning/sdk/nccl-developer-guide/docs/env.html>

## 6. 集合通信原语：DDP 背后真正搬张量的动作

`torch.distributed` 提供的「通信原语」就是这些。理解它们 = 理解分布式训练到底发生了什么。

| 原语 | 语义(一句话) | DDP 中用在哪 |
|------|--------------|--------------|
| `broadcast` | rank0 的张量复制给所有 rank | 训练开始同步初始权重 |
| `all_reduce` | 所有 rank 张量求和(或平均)后人手一份 | **反向时同步梯度** |
| `reduce` | 求和结果只给某一个 rank | 汇总指标 |
| `all_gather` | 收集所有 rank 的张量拼成列表 | 张量并行收集结果 |
| `scatter` | rank0 把分块分发给各 rank | 分发数据 |
| `barrier` | 所有 rank 在此等齐再继续 | 同步检查点 |

**all_reduce 是核心，看它怎么把 4 块卡的梯度变一致：**
```
       reduce 阶段(求和)            broadcast 阶段(分发)
GPU0:[1]──┐                       ┌──►GPU0:[10]
GPU1:[2]──┤                       ├──►GPU1:[10]
GPU2:[3]──┼─► sum = 1+2+3+4 =10 ──┼──►GPU2:[10]
GPU3:[4]──┘                       └──►GPU3:[10]
   结束后每块卡都持有 10；DDP 再除以 world_size=4 → 梯度平均 = 2.5
```
> **数值手算**：4 卡各自 mini-batch 算出梯度 $g_0{=}1, g_1{=}2, g_2{=}3, g_3{=}4$。all-reduce 求和得 $\sum g_i = 10$，DDP 除以 `world_size` 得平均梯度 $\bar g = 10/4 = 2.5$。每卡用同一个 $\bar g$ 更新 → 等价于在 **全局 batch** 上训练。

工程实现用 **Ring-AllReduce**：N 卡环形传递，通信量与卡数无关，带宽最优。详见 [[ai-infra/网络/集合通信原语]]。

## 实操：可直接跑的最小示例

把上面所有概念串起来——一个完整的 all_reduce 最小程序：

```python
import os
import torch
import torch.distributed as dist

def main():
    # 1) 初始化进程组：读取 RANK/WORLD_SIZE/MASTER_ADDR/MASTER_PORT
    #    GPU 训练选 nccl，纯 CPU 调试可改 gloo
    dist.init_process_group(backend="nccl")

    rank = dist.get_rank()
    world_size = dist.get_world_size()
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)          # 每进程绑一块 GPU

    # 2) 每个 rank 造一个值为 (rank+1) 的张量
    t = torch.tensor([rank + 1.0], device=f"cuda:{local_rank}")

    # 3) all_reduce 求和：结束后所有 rank 都持有 sum(1..world_size)
    dist.all_reduce(t, op=dist.ReduceOp.SUM)
    print(f"[rank {rank}/{world_size}] after all_reduce = {t.item()}")

    # 4) 销毁进程组，释放通信资源
    dist.destroy_process_group()

if __name__ == "__main__":
    main()
```

启动(2 机各 4 卡 = 8 进程)：
```bash
# 设网卡 + 打开调试(可选但排障必备)
export NCCL_SOCKET_IFNAME=eth0
export NCCL_DEBUG=INFO

# Node0 (master)
torchrun --nnodes=2 --nproc_per_node=4 --node_rank=0 \
         --master_addr=10.0.0.1 --master_port=29500 demo.py
# Node1
torchrun --nnodes=2 --nproc_per_node=4 --node_rank=1 \
         --master_addr=10.0.0.1 --master_port=29500 demo.py
```
> 预期输出：每个 rank 都打印 `after all_reduce = 36`（$1+2+\dots+8 = 36$），证明 8 个进程真的把张量同步成一致了。`torchrun` 用法详见 [[torchrun]]。

## 常见问题 / 坑

| 现象 | 根因 | 处理 |
|------|------|------|
| `init_process_group` 一直卡住不返回 | `MASTER_ADDR/PORT` 配错、端口被防火墙挡、某 rank 没起来 | 检查所有节点连通性与端口；用 `telnet master 29500` 验证 |
| 训练巨慢，带宽远低于网卡 | 自动检测选到了管理网(慢网卡) | `export NCCL_SOCKET_IFNAME=eth0` 指定数据网/IB |
| 多机 Gloo 会合失败 | 各进程 `GLOO_SOCKET_IFNAME` 接口**数量不一致** | 所有进程指定**相同数量**接口 |
| 某个 collective 永久 hang | 各 rank **张量形状/调用不一致**，或漏调 | `NCCL_DEBUG=INFO` + `NCCL_DEBUG_SUBSYS=COLL` 看谁没到齐 |
| 拓扑检测报错 | NCCL 探测节点拓扑失败 | `NCCL_DEBUG_SUBSYS=GRAPH` 保存结果排查 |
| GPU 训练却选了 `gloo` | 后端选错 | GPU 一律用 `nccl` |
| 云上(AWS/GCP)手调 socket 变量反而更慢 | NCCL 已预调优 | 保持默认，**别动** `NCCL_SOCKET_NTHREADS/NSOCKS_PERTHREAD` |
| 用 `DataParallel` 单机多卡慢且不稳 | DP 单进程多线程，受 GIL 颠簸 | 换 DDP(基于 torch.distributed) |
| `RuntimeError: NCCL not available` | 环境无 NCCL(如纯 CPU/Win) | 调试场景改 `backend="gloo"` |
