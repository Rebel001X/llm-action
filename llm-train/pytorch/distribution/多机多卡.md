## 0. 一句话锚点

**单机多卡**：8 张卡插在同一台主板上，卡间走 NVLink/PCIe，梯度同步不出机箱。
**多机多卡**：卡分布在 N 台物理机上，**梯度同步必须穿过机房网络**。

一句话：多机训练 = 单机训练 + "**让网络变得不是瓶颈**"。90% 的多机问题不是算法问题，而是**网络配通、NCCL 选对网卡、带宽够不够**这三件事。

```
单机8卡                          2机×4卡
┌─────────────────┐             ┌───────────┐   网络   ┌───────────┐
│ GPU0 GPU1 .. GPU7│            │GPU0..GPU3 │═════════│GPU4..GPU7 │
│   └─NVLink─┘     │            │  node0    │  IB/RoCE │  node1    │
└─────────────────┘             └───────────┘  ~穿墙   └───────────┘
 同步走 NVLink(快)               同步要跨节点(可能慢，得调)
```

## 1. 地基：原子概念

在写任何命令前，必须把这几个词刻进脑子。它们是后面一切的"坐标系"。

- **进程 (process)**：一个 GPU 通常由一个独立的 OS 进程驱动。8 卡 = 8 个进程。
- **rank（全局秩）**：每个进程在**整个集群**里的唯一编号，从 0 到 `world_size-1`。rank 0 通常承担保存 checkpoint、打日志、做 rendezvous 主控等"班长"职责。
- **local_rank（局部秩）**：进程在**本机内部**的编号，从 0 开始。它决定这个进程绑哪块卡：`torch.cuda.set_device(local_rank)`。
- **world_size**：集群里进程总数 = `nnodes × nproc_per_node`。
- **node_rank**：机器（节点）的编号，从 0 开始。
- **通信原语**：分布式训练靠几个集合通信操作拼起来，最核心是 **AllReduce**——把所有 rank 的梯度求和再广播回每个 rank，使所有卡看到同一份平均梯度。

```
2机×4卡，world_size=8 的编号坐标系
                node_rank=0                    node_rank=1
        ┌───────────────────────┐     ┌───────────────────────┐
rank →  │  0     1     2     3   │     │  4     5     6     7   │
local→  │  0     1     2     3   │     │  0     1     2     3   │
GPU →   │ cuda0 cuda1 cuda2 cuda3│     │ cuda0 cuda1 cuda2 cuda3│
        └───────────────────────┘     └───────────────────────┘
关键：rank 全局唯一；local_rank 各机重新从 0 数；local_rank → 绑哪块物理卡
```

**为什么要分两套编号？** 因为"我是集群第几号"（rank，决定数据切片、是否当班长）和"我用本机第几块卡"（local_rank，决定 `set_device`）是两件正交的事。混用会导致两台机器都去抢 cuda0 → 卡冲突或 OOM。

## 2. 多机组网：物理链路怎么搭

多机训练第一性问题：**两台机器的进程靠哪条物理链路传梯度？** 选错链路，带宽差 10 倍以上。

### 三类网络对比

| 链路 | 典型带宽（约/以官方为准） | 是否 RDMA | 说明 |
|---|---|---|---|
| 普通以太网 TCP/IP | 10~25 Gb/s | 否 | 走内核协议栈，CPU 拷贝开销大，多机大模型基本不够用 |
| RoCE（RDMA over Converged Ethernet） | 100~400 Gb/s | 是 | 在以太网上跑 RDMA，需交换机支持无损（PFC/ECN） |
| InfiniBand (IB) | 200~800 Gb/s（HDR/NDR） | 是 | 专用网络，延迟最低，AI 集群主流。详见 [[ai-infra/网络/InfiniBand]] |

**RDMA（远程直接内存访问）是关键词**：让一台机器的网卡直接把数据写进另一台机器的 GPU 显存（配合 GPUDirect RDMA），**绕过 CPU 和内核协议栈**，这是高带宽低延迟的根本。普通 TCP 每个包都要 CPU 搬运、拷贝，是大模型多机的头号杀手。

### bond 与多网卡

服务器常把多张物理网卡聚合成一个逻辑接口（如 `bond0`），叠加带宽 + 冗余。文件里命令用了 `NCCL_SOCKET_IFNAME="bond0"`，就是告诉 NCCL"控制面走 bond0 这块网卡"。一台 H800/H100 训练机往往有**8 张 IB 卡**（每卡配一块），让 8 个 GPU 各走各的网卡，避免单网卡成瓶颈。

```
一台典型 8 卡 GPU 服务器的网络拓扑
   GPU0─GPU1─GPU2─GPU3─GPU4─GPU5─GPU6─GPU7   ← NVLink/NVSwitch 全互联(机内)
    │    │    │    │    │    │    │    │
   IB0  IB1  IB2  IB3  IB4  IB5  IB6  IB7      ← 8张 IB 网卡(GPUDirect RDMA)
    └────┴────┴────┴────┴────┴────┴────┴──→  IB 交换机(Spine-Leaf) ──→ 其他节点
   外加一张 bond0(以太网)：跑管理面/rendezvous/数据加载
```

## 3. rank 分配：torchrun 怎么把编号发下去

`torchrun`（旧名 `torch.distributed.launch`）的职责：在**每台机器上**拉起 `nproc_per_node` 个进程，并给每个进程注入正确的 `RANK / LOCAL_RANK / WORLD_SIZE` 环境变量。

### 关键参数（看文件里的命令）

```
torchrun --nproc_per_node=4 --nnodes=2 \
         --node_rank=0 \            # ★ 唯一一处两台机器必须不同的参数
         --master_addr=10.xx.64.12 --master_port=29501 \
         train.py ...
```

| 参数 | 含义 | 权衡/坑 |
|---|---|---|
| `--nproc_per_node` | 本机起几个进程（=本机用几张卡） | 通常 = 本机 GPU 数 |
| `--nnodes` | 总共几台机器 | 也可写 `2:4` 表示弹性范围 |
| `--node_rank` | **本机**是第几号节点 | node0 填 0、node1 填 1，**绝不能重复** |
| `--master_addr` | rendezvous 主控地址 | 所有节点填**同一个**地址（通常 node0 的 IP） |
| `--master_port` | rendezvous 端口 | 所有节点填**同一个**，且端口未被占用 |

**torchrun 内部怎么算 rank？**

$$\text{RANK} = \text{node\_rank} \times \text{nproc\_per\_node} + \text{LOCAL\_RANK}$$

- node0 的 4 个进程：rank = 0×4+{0,1,2,3} = **0,1,2,3**
- node1 的 4 个进程：rank = 1×4+{0,1,2,3} = **4,5,6,7**

```
node_rank=0  ──┐                                ┌── node_rank=1
torchrun 起4进程                                 torchrun 起4进程
LOCAL_RANK 0123                                  LOCAL_RANK 0123
   │ ↓ RANK=node_rank*4+LOCAL_RANK ↓                  │
RANK 0 1 2 3 ─────► c10d rendezvous(master_addr) ◄───── RANK 4 5 6 7
            八个进程在 master 处"会合"，确认 world_size=8 后开始训练
```

训练脚本里只需读环境变量，不要硬编码：
```python
import os, torch, torch.distributed as dist
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group(backend="nccl")   # rank/world_size 自动从环境读取
```

## 4. rendezvous：进程怎么找到彼此

**rendezvous（会合）**：8 个分散在两台机器、刚被拉起、彼此互不相识的进程，如何凑齐、确认总人数、交换连接信息，最后建立 NCCL 通信组？这套"集合点名"机制就是 rendezvous。

PyTorch 默认用 **c10d** 后端：所有进程连到 `master_addr:master_port`（由 rank0 起一个 TCPStore），把自己的连接信息写进去、读出别人的，凑齐 `world_size` 个就握手成功。

```
时间轴(简化)
 t0  node0 rank0 在 master_port 起 TCPStore(会合点)
 t1  rank 0~3、rank 4~7 全部 connect 到 master_addr:master_port
 t2  各 rank 写入自己的 NCCL ncclUniqueId / 地址信息
 t3  TCPStore 计数到 world_size=8 → 通知所有 rank "齐了"
 t4  NCCL 用交换到的信息建立环/树通信拓扑 → init_process_group 返回
 t5  开始第一个 forward
若 t2~t3 长时间凑不齐 → 卡在 init_process_group(超时常见 ~默认十几分钟，以官方为准)
```

**弹性训练**：`torchrun` 支持 `--rdzv_backend=c10d --rdzv_endpoint=host:port --max_restarts=N`，节点挂了能重新 rendezvous 续跑，适合大规模长训练。基础场景用 `--master_addr/--master_port` 即可（等价于静态 rendezvous）。

## 5. NCCL 环境变量：逐个讲清

**NCCL（NVIDIA Collective Communications Library）** 是 GPU 集合通信的底层库，PyTorch `backend="nccl"` 就是它。它负责真正搬运梯度。多机调优 99% 是在调 NCCL 的环境变量。

| 环境变量 | 作用 | 取值含义与权衡 |
|---|---|---|
| `NCCL_DEBUG` | 日志级别 | `INFO` 打印选了哪块网卡、用 IB 还是 socket，**排障第一开关**；`WARN` 只报警告 |
| `NCCL_IB_DISABLE` | 是否禁用 IB | `0`=允许用 IB（高速）；`1`=禁用、回落到 socket（慢）。文件里设 0 表示走 IB |
| `NCCL_SOCKET_IFNAME` | 控制面/socket 走哪块网卡 | 如 `bond0` 或 `eth0`；多网卡机器**必须显式指定**，否则可能选错网卡（如选到 docker0/lo）导致连不上或极慢 |
| `NCCL_IB_HCA` | 指定用哪些 IB HCA 网卡 | 如 `mlx5_0,mlx5_1...`；多 IB 卡机器用来精确绑定 |
| `NCCL_IB_GID_INDEX` | RoCE 场景的 GID 索引 | RoCE v2 常需设特定值，IB 一般不用 |
| `NCCL_NET_GDR_LEVEL` | GPUDirect RDMA 启用级别 | 控制网卡能否直写显存，开启可省一次拷贝 |
| `NCCL_P2P_DISABLE` | 是否禁用机内 P2P(NVLink/PCIe) | 一般保持启用；某些环境出错时临时设 1 排查 |
| `NCCL_ALGO` / `NCCL_PROTO` | 选通信算法/协议 | 如 Ring/Tree；通常自动选最优，调优时才手动指定 |

```
NCCL_DEBUG=INFO 时你该在日志里找到的关键行(示意)
  NCCL INFO NET/IB : Using [0]mlx5_0 ... ← 确认走了 IB(好)
  NCCL INFO NET/Socket : Using [0]bond0 ← 退回 socket(若本想走IB，说明IB没生效!)
  NCCL INFO Channel 00 : 0[..] -> 1[..] [send] via NET/IB ← 通信链路建立
看到 "via NET/Socket" 而你装了 IB → 立刻查 NCCL_IB_DISABLE 和驱动
```

**调参心法**：先用 `NCCL_DEBUG=INFO` 看 NCCL **实际选了什么**，再决定要不要用 `NCCL_IB_HCA / NCCL_SOCKET_IFNAME` 去纠正。不要凭记忆设一堆变量，**让日志说话**。

## 6. 故障排查：三大类症状

### A. 连不上 / 卡在 init_process_group

```
症状：程序停在 init_process_group，几分钟后超时报错
排查链：
 ① master_addr 各节点能 ping 通吗？ ping 10.xx.64.12
 ② master_port 通吗、被占用吗？     telnet/nc 测端口；换个端口
 ③ 防火墙 / 安全组放行该端口了吗？  容器用 --network=host 避免端口映射坑
 ④ node_rank 是否重复？两台都填0 → 永远凑不齐 world_size
 ⑤ NCCL_SOCKET_IFNAME 选错网卡(选到 docker0/lo) → 设成真实网卡(bond0)
```

### B. 跑起来但很慢（吞吐远低于预期）

```
排查链：
 ① NCCL_DEBUG=INFO 看是 NET/IB 还是 NET/Socket？退回 socket=慢
 ② NCCL_IB_DISABLE 是否误设 1？驱动 libibverbs 装了吗(yum install libibverbs)
 ③ 选错了带宽低的网卡(走了管理网而非 IB)？用 NCCL_IB_HCA 锁定
 ④ GPUDirect RDMA 没开 → 看 NCCL_NET_GDR_LEVEL
 ⑤ 网络真的是瓶颈吗？先看第7节手算，再决定是网络问题还是计算问题
```

### C. 偶发挂死 / NCCL timeout

```
 ① 某 rank 崩了但别人还在等它 AllReduce → 看每台机器各自的日志找首个出错 rank
 ② 数据加载不均，某 rank 慢半拍 → AllReduce 是同步点，最慢的拖垮全队(长尾)
 ③ 用弹性 rendezvous + --max_restarts 提高大集群鲁棒性
```

**黄金法则**：多机排障从 **node0 的日志 + `NCCL_DEBUG=INFO`** 开始。先确认"网络物理通不通 → NCCL 有没有选对网卡 → 带宽够不够"，逐层往上。

## 7. 带宽对吞吐的影响：必须会手算

这是理解"为什么多机要好网络"的核心。数据并行下，**每个 step 的反向传播都要对全部参数的梯度做一次 AllReduce**。

### 通信量公式

Ring-AllReduce 中，每个 rank 实际收发的数据量约为：

$$V_{\text{comm}} \approx 2 \times \frac{N-1}{N} \times S_{\text{grad}} \approx 2 \times S_{\text{grad}}\ (N\ \text{大时})$$

其中 $S_{\text{grad}}$ 是梯度总字节数（与参数量同阶），$N$ 是 rank 数。系数 2 来自 ring 的 reduce-scatter + all-gather 两个阶段。

### 手算示例：7B 模型，bf16

- 参数量 $P = 7\times10^9$，bf16 每个数 2 字节 → 梯度 $S_{\text{grad}} = 7\times10^9 \times 2 = 14\text{ GB}$。
- 每个 rank AllReduce 传输量 $\approx 2 \times 14 = 28\text{ GB}$。

**用 IB（约 200 Gb/s = 25 GB/s，以官方为准）：**
$$t_{\text{comm}} \approx \frac{28\text{ GB}}{25\text{ GB/s}} \approx 1.12\text{ s}$$

**用普通以太网（约 25 Gb/s = 3.1 GB/s）：**
$$t_{\text{comm}} \approx \frac{28\text{ GB}}{3.1\text{ GB/s}} \approx 9\text{ s}$$

```
一个 step 的时间构成(示意，单位 s)
                计算(fwd+bwd)      通信(AllReduce)
IB     :  ████████████ 2.0        █ 1.1     → step≈3.1s，通信占比~35%(可重叠后更低)
以太网 :  ████████████ 2.0        █████████ 9.0 → step≈11s，通信吃掉80%！
结论：网络从 IB 换成以太网，吞吐可能掉到 1/3 ~ 1/4
```

**关键优化：通信与计算重叠（overlap）**。PyTorch DDP/FSDP 会在反向传播算出一层梯度后**立即**异步发起该桶（bucket）的 AllReduce，与后续层的计算并行。理想情况下通信被计算"藏住"，但前提是**带宽足够**——带宽不足时通信藏不住，就退化成上图以太网那样的串行墙时。这正是 IB 不可替代的原因。

实际可达带宽通常只有标称的 70%~90%（协议开销、拓扑、争用），手算时记得打折，并以实测为准。

## 8. 数值例子 / 对照 / 实践清单

### 对照：单机 vs 多机命令差异

| 维度 | 单机8卡 | 2机8卡（文件示例） |
|---|---|---|
| `--nnodes` | 1 | 2 |
| `--nproc_per_node` | 8 | 4（每机4卡） |
| `--node_rank` | 0 | node0 填 0 / node1 填 1 |
| `--master_addr` | 127.0.0.1 可 | 必须填 node0 真实 IP |
| 网络相关 NCCL 变量 | 基本不用 | IB/SOCKET 变量是重点 |
| 容器网络 | 随意 | 建议 `--network=host` |

### 完整可运行示例（保留文件原命令，已加注释）

**node0（node_rank=0）执行：**
```bash
sudo docker run -it --rm --gpus all --network=host \
  --shm-size 4G \
  -e NCCL_IB_DISABLE=0 \              # 允许走 IB（高速）
  -e NCCL_SOCKET_IFNAME="bond0" \     # 控制面走 bond0，别选到 docker0
  -e NCCL_DEBUG=INFO \                # 打开排障日志
  -v /data/hpc/home/guodong.li:/workspaces -w /workspaces/code \
  aiharbor.local/base/pytorch-alpaca:v4-h800-ib \
  torchrun --nproc_per_node=4 --nnodes=2 --node_rank=0 \
    --master_addr=10.xx.64.12 --master_port=29501 train.py \
    --model_name_or_path /workspaces/model/llama-7b-hf \
    --data_path /workspaces/data/alpaca_data_cleaned.json \
    --output_dir /workspaces/output \
    --bf16 True --max_steps 200 \
    --per_device_train_batch_size 1 --gradient_accumulation_steps 2 \
    --learning_rate 2e-5 --warmup_ratio 0.03 --lr_scheduler_type cosine \
    --fsdp "full_shard auto_wrap" \
    --fsdp_transformer_layer_cls_to_wrap 'LlamaDecoderLayer' --tf32 True
```

**node1（node_rank=1）执行：** 与上面**几乎完全相同**，只把 `--node_rank=0` 改成 `--node_rank=1`，其余（`--master_addr/--master_port/--nnodes` 等）**保持一致**。

> 走 IB 需在镜像/主机内安装用户态驱动：`yum install libibverbs`（以发行版与官方为准）。

### 上手前自检清单

```
[ ] 两台机能互相 ping 通 master_addr，端口未被占用/已放行
[ ] node_rank 一个填0一个填1，绝不重复
[ ] master_addr/master_port/nnodes/nproc_per_node 在两台机一致
[ ] 容器用 --network=host，避免端口映射与网卡识别问题
[ ] NCCL_SOCKET_IFNAME 指向真实高速网卡(如 bond0)，不是 docker0/lo
[ ] NCCL_IB_DISABLE=0 且 libibverbs 已装，DEBUG=INFO 日志确认走 NET/IB
[ ] 先跑 --max_steps 几十步小验证，看吞吐再放大
```

## 常见问题

| 问题 | 原因 | 解决 |
|---|---|---|
| 卡在 init_process_group 超时 | master_addr 不通 / 端口未放行 / node_rank 重复 | ping+测端口；查 node_rank；用 --network=host |
| 跑通但巨慢 | NCCL 退回 socket，没走 IB | DEBUG=INFO 确认；查 NCCL_IB_DISABLE 与 libibverbs |
| 选到错误网卡（docker0/lo） | 多网卡未指定接口 | 显式设 NCCL_SOCKET_IFNAME=bond0 / NCCL_IB_HCA |
| 两机都抢 cuda0 | 用了 rank 而非 local_rank 绑卡 | `set_device(LOCAL_RANK)` |
| 某 rank 崩全队挂死 | AllReduce 是同步点，长尾/崩溃拖垮全部 | 看各机日志定位首个出错 rank；用弹性 rendezvous |
| 加了卡但吞吐没线性涨 | 通信成为瓶颈 / 通信藏不住 | 第7节手算；换 IB；增大 batch 摊薄通信占比 |
| RoCE 下通信异常 | GID 索引不对 | 设 NCCL_IB_GID_INDEX（以官方/网络配置为准） |
