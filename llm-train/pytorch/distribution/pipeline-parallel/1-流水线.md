## 0. 一句话锚点

**流水线并行 = 把模型「纵向」按层切段，每段（stage）放一张卡，前一卡算完把激活值传给下一卡，像工厂流水线一样。**

三种并行一句话区分：

| 并行方式 | 切什么 | 卡间通信内容 | 主要解决 |
|----------|--------|--------------|----------|
| 数据并行 DP/DDP | 切 **数据**（每卡一份完整模型） | 梯度 all-reduce | 算得快、扩 batch |
| 张量并行 TP | 切 **单层内部**的矩阵 | 层内激活 all-reduce | 单层太大 |
| **流水线并行 PP** | 切 **层与层之间**（模型纵向分段） | 段边界的激活/梯度 point-to-point | 模型整体放不下 |

> PyTorch 里实现同步流水线并行的就是本文主角 `torch.distributed.pipeline.sync.Pipe`，它把 **GPipe 的微批次思想** 和 **激活 checkpointing** 结合在一起。

## 1. 地基 / 前置

读 `Pipe` 之前需要的 4 个概念：

1. **`nn.Sequential`**：把多个子模块按顺序串起来的容器，`Sequential(a, b, c)(x) == c(b(a(x)))`。流水线并行天然要求「顺序执行」，所以 `Pipe` **只接受 `nn.Sequential`**。

2. **设备放置（device placement）**：你要**自己**把每个子模块 `.cuda(i)` 放到目标 GPU 上。`Pipe` 不替你分卡，它只负责「按你放好的设备顺序调度数据流」。
   - 特例：若某子模块**不含任何参数/buffer**，则默认它在 **CPU** 上执行，其输入张量也会在执行前被搬到 CPU。可用 `WithDevice` 包装器**显式指定**该模块运行在哪个设备上，覆盖这个默认行为。

3. **RPC 框架**：`Pipe` 依赖 `torch.distributed.rpc`，所以用之前必须先 `init_rpc(...)`（见下文实操）。这是为了给未来的「跨节点流水线」预留通道。

4. **激活 checkpointing（重计算）**：前向时**不保存**中间激活，反向时**重新算一遍**前向来得到它们。用「多花一次前向计算」换「省下激活显存」。`Pipe` 内置了这个开关（`checkpoint` 参数）。

## 2. 为什么需要流水线并行：显存墙 + 朴素切分的空泡

### 2.1 显存墙

> 如果模块需要大量内存并且不适合单个 GPU，则流水线并行是一种用于训练的有用技术。

一个大模型的显存占用 ≈ 参数 + 梯度 + 优化器状态 + **激活值**。当这些加起来超过单卡显存（显存墙），最直接的办法就是把模型**切段分到多卡**。

### 2.2 朴素切分的问题：流水线「空泡（bubble）」

如果只是简单地「卡0算完→卡1算→卡2算→卡3算」，同一时刻只有 **1 张卡在干活**，其余在等：

```
朴素切分（4 段，1 个 batch），F=前向 B=反向，时间从左到右
                                                  设备利用率极低
GPU0 | F .  .  .              B .  .  . |
GPU1 | .  F .  .           B .  .  . |
GPU2 | .  .  F .        B .  .  .  . |
GPU3 | .  .  .  F  B  .  .  .  .  . |
       └─ 同一时刻只有一个 GPU 在算，"." 全是空泡(bubble) ─┘
```

`Pipe` 的目标正是：

> Pipe 将流水线并行与 checkpointing 相结合，以减少训练所需的峰值内存；同时，**最大限度地减少设备利用率不足的问题**（即压缩空泡）。

## 3. GPipe 微批次机制：用 chunks 压缩空泡

> 该实现基于 **torchgpipe（GPipe）** 论文。

核心思想：把一个 mini-batch 再切成 `chunks` 个 **微批次（micro-batch）**，让它们像流水线工件一样**错峰**流过各段。当微批次足够多时，各卡几乎同时在忙不同的微批次。

```
GPipe 微批次（4 段 × 4 个 micro-batch），数字=第几个 micro-batch
时间 ────────────────────────────────────────────────►
GPU0 |F1 F2 F3 F4 ·  ·  ·  ·  B4 B3 B2 B1|
GPU1 |·  F1 F2 F3 F4 ·  ·  B4 B3 B2 B1 · |
GPU2 |·  ·  F1 F2 F3 F4 B4 B3 B2 B1 ·  · |
GPU3 |·  ·  ·  F1 F2 F3 F4 B4 B3 B2 B1   |   <- 满载段几乎无空泡
        ╲___ 头部填充 ___╱        ╲_尾部排空_╱
        (仍有空泡，但只在头尾)
```

**空泡占比的直觉公式**（设 $p$ 个段、$m$ 个微批次）：

$$
\text{bubble ratio} \approx \frac{p-1}{m+p-1}
$$

- $m=1$（朴素）：$\frac{p-1}{p}$，4 段时 75% 时间在空泡。
- $m=8, p=4$：$\frac{3}{11}\approx 27\%$，空泡大幅下降。

> **数值手算**：4 段、`chunks=8`，空泡比 ≈ 3/(8+3) ≈ 27%；`chunks=16` 时 ≈ 3/19 ≈ 16%。所以 **chunks 越大空泡越小**——但 chunks 太大每个微批次太小，GPU kernel 利用率又会掉，需要折中（常见 4~32）。

## 4. `torch.distributed.pipeline.sync.Pipe` API 逐参数

> 包装任意的 `nn.Sequential` 模块，以使用**同步流水线并行**进行训练。
> 你应该把所有模块放到合适的设备上，并包装进一个定义了执行顺序的 `nn.Sequential` 中。

构造签名（按原文）：`Pipe(module, chunks=1, checkpoint='except_last', deferred_batch_norm=False)`

| 参数 | 类型 | 默认 | 含义（原文保留 + 解释） |
|------|------|------|--------------------------|
| `module` | `nn.Sequential` | 必填 | 用流水线并行的 sequential 模块。**每个子模块的所有参数必须在同一张设备上**；子模块可以是 `nn.Module` 或 `nn.Sequential`（在单设备上组合多个 sequential） |
| `chunks` | `int` | `1` | 微批次数量。即把 mini-batch 切成几份送进流水线（见第 3 节） |
| `checkpoint` | `str` | `'except_last'` | 何时启用激活 checkpoint，取值 `'always'`/`'except_last'`/`'never'`（见第 5 节） |
| `deferred_batch_norm` | `bool` | `False` | 是否使用「延迟 BatchNorm」移动统计。设为 `True` 时，跨多个微批次跟踪统计量，以更新每个 **mini-batch**（而非每个微批次）的 running stats。这样切微批次后 BN 统计才和不切时一致 |

> **为什么需要 `deferred_batch_norm`**：BatchNorm 的 running mean/var 是按「一个 batch」估计的。流水线把 batch 切成微批次后，若每个微批次各自更新 BN，统计量就偏小/偏抖。`deferred_batch_norm=True` 把多个微批次的统计**攒起来**再按 mini-batch 更新，保持语义一致。

## 5. checkpoint 三档：显存与算力的取舍

> `checkpoint` 控制何时启用激活 checkpoint（重计算）。

| 取值 | 行为（原文） | 显存 | 额外算力 | 何时用 |
|------|--------------|------|----------|--------|
| `'never'` | 完全禁用 checkpoint | 最高 | 无 | 显存够、追速度；**也是能被 DDP 包裹的唯一档**（见 6.3） |
| `'except_last'`（默认） | 启用「除最后一个之外」所有微批次的 checkpoint | 中 | 中 | 默认折中：最后一个微批次反向时紧接前向，不重算更划算 |
| `'always'` | 启用所有微批次的 checkpoint | 最低 | 最高 | 显存极度紧张，宁可多算 |

```
显存占用      never  >  except_last  >  always
重计算开销    never  <  except_last  <  always
                       └ 默认在中间取折中 ┘
```

## 6. RPC、RRef 与节点内限制

### 6.1 必须先初始化 RPC

`Pipe` 建立在 `torch.distributed.rpc` 之上，使用前必须 `init_rpc(...)`，否则报错。

### 6.2 forward 返回 RRef

> `Pipe` 目前仅支持**节点内（intra-node）**流水线，未来将扩展支持**节点间（inter-node）**流水线。
> `forward` 函数返回一个 **RRef**（远程引用），以允许将来进行节点间流水线传输——届时输出可能位于远程主机上。
> 对于节点内流水线，你可以用 `local_value()` 在本地取回输出。

```
   model(input)  ──►  返回 RRef（远程引用，不是张量本身）
                          │
   节点内(现在) ──────────┴─► output_rref.local_value()  取回本地张量
   节点间(未来) ──────────► 输出可能在远程主机，RRef 是统一句柄
```

> **为什么是 RRef 而不是直接给张量**：为「跨节点流水线」预留统一接口。即使输出在另一台机器上，RRef 也是同一种句柄；本地场景再用 `local_value()` 落地。

### 6.3 与 DDP 同时使用的限制（重要坑）

> 注：**仅当 `Pipe` 的 `checkpoint` 参数为 `'never'` 时**，才可以用 `torch.nn.parallel.DistributedDataParallel` 包装 `Pipe` 模型。

这就是常见的 **PP + DP 二维并行**：每个流水线副本内做流水线并行，副本之间做数据并行。但 checkpoint 的重计算会与 DDP 的反向钩子冲突，所以**叠 DDP 时必须把 checkpoint 关成 `'never'`**。

### 6.4 实验性警告

> **警告：`Pipe` 是实验性的，可能会发生变化。**

## 实操：命令 / 配置 / 代码（原文真料，逐行解释）

### 7.1 最小可运行示例（来自原文）

```python
# Need to initialize RPC framework first.  必须先初始化 RPC 框架
os.environ['MASTER_ADDR'] = 'localhost'   # 主节点地址
os.environ['MASTER_PORT'] = '29500'       # 主节点端口
torch.distributed.rpc.init_rpc('worker', rank=0, world_size=1)  # 起 RPC

# Build pipe.  构建流水线模型
fc1 = nn.Linear(16, 8).cuda(0)   # 第 1 段放 GPU0
fc2 = nn.Linear(8, 4).cuda(1)    # 第 2 段放 GPU1（注意是不同卡）
model = nn.Sequential(fc1, fc2)  # 按顺序串成 Sequential
model = Pipe(model, chunks=8)    # 包成 Pipe，mini-batch 切成 8 个微批次
input = torch.rand(16, 16).cuda(0)  # 输入放在第一段所在卡 GPU0 上
output_rref = model(input)       # 返回的是 RRef，不是张量
# 取回本地张量：output = output_rref.local_value()
```

逐点说明（为什么这么写）：
- **先 `init_rpc` 再建 `Pipe`**：顺序不能反，`Pipe` 依赖 RPC。
- **`fc1.cuda(0)` / `fc2.cuda(1)`**：你**手动**把两段放到两张卡，`Pipe` 按这个顺序调度数据流。
- **`input.cuda(0)`**：输入要放到**第一段所在的设备**。
- **`chunks=8`**：mini-batch（这里 batch=16）会被切成 8 个微批次错峰流过两段。
- **`output_rref`**：返回值是 RRef，需 `.local_value()` 取回（节点内）。

### 7.2 `forward(*inputs)`

`Pipe` 实例的前向接口签名为 `forward(*inputs)`，输入需在第一段设备上；返回 RRef（见 6.2）。

## 8. 跳跃连接（Skip connections）

> 某些模型（例如 **ResNeXt**）不是完全顺序的，层之间有**跳跃连接**。朴素实现意味着我们要把某些层的输出**跨多个 GPU 一路复制**，直到到达跳跃连接的目标 GPU。为避免这种复制开销，`Pipe` 提供了 **stash/pop** API 在不同层间存取张量。

```
朴素：Layer1 的输出要跨 GPU 一路搬到 Layer3   ──► 复制开销大
         L1 ──► L2 ──► L3
          └────跨卡复制────┘

skip：用 stash 把张量"寄存"，到 L3 再 pop 取出  ──► 由 Pipe 智能调度搬运
         L1 --stash('1to3')-->  ... ──► L3 --pop('1to3')-->
```

### 8.1 基本用法（原文示例）

```python
@skippable(stash=['1to3'])          # 声明本模块会寄存名为 '1to3' 的张量
class Layer1(nn.Module):
    def forward(self, input):
        yield stash('1to3', input)  # 用 yield 寄存（注意是 yield 不是 return）
        return f1(input)

class Layer2(nn.Module):
    def forward(self, input):
        return f2(input)

@skippable(pop=['1to3'])            # 声明本模块会取出 '1to3'
class Layer3(nn.Module):
    def forward(self, input):
        skip_1to3 = yield pop('1to3')   # 取回寄存的张量
        return f3(input) + skip_1to3    # 实现跳跃连接相加

model = nn.Sequential(Layer1(), Layer2(), Layer3())
```

要点：
- 寄存/取出用 **`yield stash(...)` / `yield pop(...)`**，所以 `forward` 是**生成器**写法。
- `@skippable(stash=[...], pop=[...])` 在装饰器里**声明**名字，`Pipe` 据此调度跨段搬运。

### 8.2 一个模块存取多个张量（原文示例）

```python
@skippable(stash=['alice', 'bob'], pop=['carol'])
class StashStashPop(nn.Module):
    def forward(self, input):
        yield stash('alice', f_alice(input))  # 寄存 alice
        yield stash('bob', f_bob(input))      # 寄存 bob
        carol = yield pop('carol')            # 取出 carol
        return input + carol
```

### 8.3 约束与校验

> 每个跳跃张量必须与**一对 stash 和 pop** 相关联。`Pipe` 在包装模块时会**自动检查**此限制；你也可以在不使用 `Pipe` 的情况下，通过 `verify_skippables()` 检查。

相关 API（原文罗列）：

| API | 作用 |
|-----|------|
| `torch.distributed.pipeline.sync.skip.skippable.skippable(stash=(), pop=())` | 装饰器，声明模块的寄存/取出名 |
| `torch.distributed.pipeline.sync.skip.skippable.stash(name, tensor)` | 在 forward 内寄存张量 |
| `torch.distributed.pipeline.sync.skip.skippable.pop(name)` | 在 forward 内取出张量 |
| `torch.distributed.pipeline.sync.skip.skippable.verify_skippables(module)` | 不经过 Pipe 也能校验 stash/pop 配对 |

## 常见问题 / 坑

| 现象 / 问题 | 原因 | 解决 |
|-------------|------|------|
| 报错：RPC 未初始化 | 没先 `init_rpc` 就建 `Pipe` | 先设 `MASTER_ADDR/PORT` 并 `init_rpc(...)`，再建 `Pipe` |
| 输出不是张量，调用 `.shape` 报错 | `forward` 返回的是 **RRef** | 节点内用 `output_rref.local_value()` 取回张量 |
| 套了 DDP 后训练异常 | checkpoint 与 DDP 反向冲突 | 仅当 `checkpoint='never'` 才能用 DDP 包裹 `Pipe` |
| 利用率仍很低、空泡大 | `chunks` 太小（如默认 1） | 增大 `chunks`（如 8/16），但别太大以免单微批次过小掉 kernel 利用率 |
| 不含参数的模块跑到了 CPU 上 | 默认无参/无 buffer 模块在 CPU 执行 | 用 `WithDevice` 包装器显式指定设备 |
| BatchNorm 统计抖动/不准 | 微批次各自更新 BN running stats | 设 `deferred_batch_norm=True` 按 mini-batch 更新 |
| 输入张量在错误的卡上 | 输入没放到第一段设备 | `input.cuda(first_stage_device)` |
| 想跨机器训练却失败 | 当前仅支持 **intra-node** | 现阶段只在单节点多卡用；跨节点为未来特性 |
| 跳跃连接报 stash/pop 不配对 | 名字没成对声明 | 每个 skip 张量须有一对 stash+pop；用 `verify_skippables()` 自查 |
| 把非 Sequential 模型传进 Pipe | `Pipe` 只接受 `nn.Sequential` | 先重构成 `nn.Sequential`，非顺序部分用 skip API |
