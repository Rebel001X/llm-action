## 0. 一句话锚点

**冻结整个 ChatGLM（几十亿参数不动），只在若干线性层旁边挂一对小矩阵 $A,B$ 去学习增量，训练量从“全部参数”降到“千分之几甚至万分之几”，从而在一张消费级显卡上完成领域/指令微调。**

---

## 1. 地基：全量微调为什么贵，PEFT 解决什么

一个 6B 参数模型，FP16 权重就要 $6\text{B}\times2\text{B}=12\,\text{GB}$。**全量微调（Full Fine-Tuning）** 时，显存里同时要放：

```
全量微调显存账本（粗算，以 6B / FP16 为例）
┌────────────────────┬───────────────┬─────────────┐
│ 项目               │ 量级          │ 6B 估算     │
├────────────────────┼───────────────┼─────────────┤
│ 模型权重           │ 2 字节/参数   │ ~12 GB      │
│ 梯度               │ 2 字节/参数   │ ~12 GB      │
│ Adam 一阶动量 m    │ 4 字节/参数   │ ~24 GB      │
│ Adam 二阶动量 v    │ 4 字节/参数   │ ~24 GB      │
│ 激活值(随 seq/bs)  │ 视配置        │ 数 GB~很多  │
└────────────────────┴───────────────┴─────────────┘
合计动辄 70GB+，单张 24GB 卡完全放不下
```

> Adam 优化器状态本身就是参数量的 8 字节/参数（FP32 的 $m$ 和 $v$），这是“显存墙”的主要来源之一。

PEFT（Parameter-Efficient Fine-Tuning）的核心思路：**不动基座权重，只引入极少量可训练参数**。好处有三：

1. **省显存**——只有新增的小参数有梯度和优化器状态，账本里那 60GB 的梯度+优化器状态几乎清零。
2. **省存储**——每个任务只保存几 MB~几十 MB 的“适配器（Adapter）”，而不是几十 GB 的整模型副本。一个基座 + N 个 adapter = N 个专家。
3. **缓解灾难性遗忘**——基座原始能力被冻结保留，不会因为小数据集把通用能力训坏。

LoRA（Low-Rank Adaptation）是 PEFT 家族里最主流的一种，详见 [[llm-train/peft/README]]。

## 2. 被微调的对象：ChatGLM 基座长什么样

ChatGLM 系列基于 **GLM（General Language Model）** 架构，是清华 + 智谱开源的中英双语对话模型。微调前先理解它的几个特征（影响 LoRA 注入哪些层、prompt 怎么拼）：

- **自回归填空式预训练**：GLM 用空白填充（autoregressive blank infilling）目标，兼具理解与生成。
- **注意力里的合并 QKV**：在很多实现中，注意力的 Q、K、V 投影被合并成**一个**线性层，名字常见为 `query_key_value`。这一点直接决定了 LoRA 的 `target_modules` 怎么写——后面第 4 节细讲。
- **对话模板**：ChatGLM 有自己的多轮对话格式（角色标记、轮次拼接）。微调指令数据时必须按它的模板组织，否则推理时对不上。
- **RMSNorm / 旋转位置编码** 等现代组件（具体以版本为准，ChatGLM/2/3 略有差异）。

```
ChatGLM 一个 Transformer Block（简化）
            x ──► [LayerNorm] ──► ┌─ Self-Attention ─┐
                                  │  query_key_value │  ← LoRA 常注入这里
                                  │   (合并的 QKV)   │
                                  │      dense       │  ← 也可注入
                                  └──────────────────┘
                         ┌──────────► (+) 残差
            x ──► [LayerNorm] ──► ┌─ MLP / GLU ──────┐
                                  │ dense_h_to_4h    │  ← 进阶可注入
                                  │ dense_4h_to_h    │
                                  └──────────────────┘
                         ┌──────────► (+) 残差
```

> 基座本身的细节见 [[llm-train/chatglm/README]]。

## 3. LoRA 的数学：$W{+}BA$ 为什么够用

设原始某个线性层权重为 $W_0 \in \mathbb{R}^{d \times k}$。LoRA 不直接改 $W_0$，而是把它**冻结**，并在旁边加一条低秩旁路：

$$
h = W_0 x + \Delta W x = W_0 x + B A x
$$

其中 $A \in \mathbb{R}^{r \times k}$、$B \in \mathbb{R}^{d \times r}$，秩 $r \ll \min(d,k)$。可训练参数从 $d\times k$ 降到 $r\times(d+k)$。

**举个数值例子**：某层 $d=k=4096$，全量是 $4096\times4096\approx1678\,$万参数；取 $r=8$，LoRA 参数只有 $8\times(4096+4096)=65536$ 个——**不到原来的 0.4%**。

```
       x (输入, 维度 k)
        │
        ├─────────────► W0  (冻结, d×k) ──────┐
        │                                     ▼
        └─► A (r×k) ─► [中间维度 r] ─► B (d×r) (+) ─► h
            ↑训练       很窄的瓶颈      ↑训练     缩放 α/r
```

**关键超参的物理含义（讲权衡，不背默认值）：**

| 超参 | 作用 | 调大 / 调小的权衡 |
|------|------|------------------|
| `r`（秩） | 旁路的“表达能力”上限 | 大 → 拟合更强但更易过拟合、更费显存；小 → 省但可能欠拟合。常见取 4/8/16/32/64 |
| `lora_alpha`（$\alpha$） | 缩放因子，实际增量按 $\frac{\alpha}{r}$ 缩放 | 它和 $r$ 一起决定“有效学习率”。常按经验设 $\alpha = 2r$ 或与 $r$ 同量级 |
| `lora_dropout` | 旁路上的 dropout | 数据小/易过拟时调大 |
| 初始化 | $A$ 随机、$B$ 置零 | 保证训练开始时 $\Delta W = 0$，等价于原模型，训练稳定 |

> 之所以低秩就够：研究发现微调对权重的“改动”本身具有很低的内在秩（intrinsic rank），少数几个方向就能承载下游任务所需的调整。

## 4. 注入到哪些层：`target_modules` 怎么选

LoRA 不是注入到所有层，而是指定一组**线性层名字**（`target_modules`）去挂旁路。ChatGLM 的关键就在于注意力的 QKV 通常被合并成 `query_key_value`：

```
注入策略谱（从省到强）
最省 ┌──────────────────────────────────────────┐ 最强
     │ 只注意力QKV → +注意力dense → +MLP两层      │
     │ query_key_value                            │
     │      └─ dense                              │
     │              └─ dense_h_to_4h / 4h_to_h    │
     └──────────────────────────────────────────┘
   参数↑  效果可能↑  显存↑  过拟合风险↑
```

实践要点：

- **起步只注入 `query_key_value` 往往就够**，这是性价比最高的位置。
- 数据较多、任务较难时，可加入 `dense` 和 MLP 层提升容量。
- **名字必须和模型实际模块名完全一致**，否则 PEFT 找不到层、静默不注入。确认方法：打印 `model.named_modules()` 看真实层名（不同版本可能不同）。
- 也可用正则/通配让 PEFT 自动匹配所有同名层。

## 5. 数据与 prompt：指令样本怎么拼、loss 怎么 mask

指令微调数据通常是 `instruction / input / output` 三元组（Alpaca 风格）。训练时要做两件事：

1. **按对话模板拼成一条序列**（prompt 部分 + 答案部分）。
2. **对 loss 做 mask**：只让模型在“答案 token”上计算交叉熵，prompt 部分的 label 置为忽略值（如 `-100`），这样模型学“给定问题该怎么答”，而不是去背诵问题本身。

```
一条样本的拼接与 mask
┌─────────────────────────────┬──────────────────────┐
│  Prompt（指令+输入，按模板） │   Answer（output）   │
├─────────────────────────────┼──────────────────────┤
│  label = -100（不算 loss）  │  label = 真实 token  │
└─────────────────────────────┴──────────────────────┘
        ▲ 模型“看”这部分               ▲ 模型“学”这部分
```

**常见处理细节：**

- **max_seq_len 截断/填充**：过长截断、过短 pad；pad token 的 label 也要置 `-100`。
- **EOS/结束符**：答案末尾要加结束符，否则模型学不会“何时停”。
- **多轮对话**：按 ChatGLM 的多轮模板拼接历史，并决定哪些轮参与 loss。
- **数据质量 > 数据数量**：指令微调中几千~几万条高质量样本常胜过海量噪声数据。

## 6. 训练流水线：端到端调用链

```
┌──────────────┐   ┌──────────────────┐   ┌────────────────────┐
│ 原始数据集    │──►│ Tokenizer 编码    │──►│ 拼模板 + label mask │
│ (jsonl)      │   │ (ChatGLM 专用)    │   │                     │
└──────────────┘   └──────────────────┘   └─────────┬──────────┘
                                                     ▼
┌──────────────────────────────────────────────────────────────┐
│ 加载基座 ChatGLM（可选 4-bit/8-bit 量化）                       │
│        │                                                       │
│        ▼  get_peft_model(model, LoraConfig)                    │
│ 冻结全部基座参数，只给 query_key_value 等挂上 A/B               │
│        │  print_trainable_parameters() → 仅 ~0.x% 可训练       │
└────────┼──────────────────────────────────────────────────────┘
         ▼
┌──────────────────────────────────────────────────────────────┐
│ Trainer / 训练循环                                              │
│  forward → 只在答案 token 上算 loss                            │
│  backward → 梯度只流向 A/B                                     │
│  optimizer.step() → 只更新 A/B（优化器状态也只为它们分配）      │
│  （梯度检查点 / 混合精度 / 梯度累积 省显存）                    │
└────────┼──────────────────────────────────────────────────────┘
         ▼
┌──────────────────────────────────────────────────────────────┐
│ 保存 Adapter（adapter_model + adapter_config，仅几十 MB）       │
└──────────────────────────────────────────────────────────────┘
```

**配置要点（讲含义，不背默认值）：**

| 配置 | 它在调什么 | 权衡 |
|------|-----------|------|
| `per_device_train_batch_size` | 单卡每步样本数 | 大→快但显存涨；爆显存就调小 |
| `gradient_accumulation_steps` | 累积 N 步再更新 | 用“时间换显存”模拟大 batch |
| `learning_rate` | 步长 | LoRA 通常比全量微调用**更大**的 lr（如 1e-4 量级） |
| `gradient_checkpointing` | 重算激活省显存 | 省显存、慢约 20~30% |
| `fp16/bf16` | 半精度 | 省显存提速；bf16 数值更稳，需硬件支持 |
| `num_train_epochs` | 训练轮数 | 小数据集别太多轮，易过拟合 |

## 7. 显存与 QLoRA：为什么能塞进 24GB

LoRA 已经砍掉了梯度/优化器状态的大头，但**基座权重本身**（6B FP16≈12GB）仍占大头。**QLoRA** 进一步把基座权重压成 **4-bit（NF4）** 加载，权重显存再砍到约 1/4：

```
显存占用对比（6B 模型，示意）
全量微调   ████████████████████████████████  70GB+
LoRA(fp16) ██████████████                    ~14-16GB（主要是 fp16 基座）
QLoRA(4bit)██████                            ~6-8GB（4bit基座 + 小 adapter）
```

QLoRA 关键机制（细节见 [[llm-train/qlora/README]]）：

- **4-bit NF4 量化**基座权重 → 大幅降显存。
- 前向/反向时**按需反量化**到计算精度，LoRA 旁路仍以较高精度训练。
- **双重量化、分页优化器**等技巧进一步压显存、防 OOM 峰值。

> 量化基础与误差权衡见 [[llm-compression/quantization/量化基础]]。

## 8. 推理与合并：训完怎么用

训练产物是**轻量 Adapter**，使用时有两种姿势：

```
方式 A：基座 + Adapter 热插拔（推荐多任务）
   基座(冻结) ──► load_adapter(taskA) ──► 推理任务A
              └─► load_adapter(taskB) ──► 推理任务B   ← 同一基座切换

方式 B：合并权重（merge_and_unload）
   W0 + (α/r)·B·A  ──►  W_merged ──► 当作普通模型部署
   优点：推理 0 额外开销；缺点：失去“热插拔”，每任务一份全量权重
```

- **方式 A**：保留基座不变，按需加载不同 adapter，省存储、可一座多用，但推理时多一点旁路计算。
- **方式 B**：把 $\Delta W = \frac{\alpha}{r}BA$ 真正加回 $W_0$，得到一个普通模型，推理无额外开销，便于直接交给 vLLM 等引擎部署。
- **注意**：4-bit 量化训练得到的 adapter，合并时要小心精度与流程（通常需先以高精度加载基座再合并），细节以官方文档为准。

## 常见问题 / 坑

| 现象 / 坑 | 原因 | 应对 |
|-----------|------|------|
| `target_modules` 写了却没注入 | 层名和模型实际名不符（ChatGLM 是合并的 `query_key_value`） | 打印 `named_modules()` 用真实名字 |
| loss 不降 / 学了个寂寞 | 没做 label mask，模型在背 prompt | prompt 段 label 置 `-100`，只在答案算 loss |
| 推理乱答、不停 | 训练 prompt 模板与推理不一致 / 缺 EOS | 训练推理用同一对话模板，答案带结束符 |
| OOM 显存爆 | batch/seq 太大或没省显存技巧 | 调小 batch + 梯度累积 + 梯度检查点 + 量化 |
| 量化报错/不收敛 | 量化层与 LoRA 配合需特定流程 | 用 QLoRA 官方推荐流程，量化层准备好再注入 |
| 合并后效果变差 | 量化基座直接合并有精度损失 | 按官方流程以合适精度加载基座再 merge |
| 过拟合（训练好测试差） | 数据少 + r/epoch 过大 | 减小 r、减少轮数、加 dropout、扩充数据 |
| 半精度数值不稳 | fp16 易溢出 | 优先 bf16（需硬件支持）；关注 loss scale |
