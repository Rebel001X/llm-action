## 0. 一句话锚点

**CodeGeeX = "会写多种编程语言的 GPT"**。它本质上是一个 **decoder-only 自回归 Transformer**（约 13B 参数），用海量代码语料训练，给定一段上文（注释、函数签名、已写代码）后**逐 token 预测**接下来该写什么，从而实现**代码补全、跨语言翻译、注释生成**等能力。训练侧最大的特色是：**用 Megatron-LM 的张量并行**，并且**在昇腾 910 等国产 NPU 集群上完成了大规模训练**。

> 一句话区分：**模型架构**和 GPT 几乎一样，价值在于**数据（代码）+ 训练工程（Megatron + 异构集群）**。

---

## 1. 地基：它解决什么问题

把问题拆成最小原子：

1. **代码生成本质是序列建模问题**。源代码是一串 token（标识符、关键字、符号、缩进），天然适合自回归语言模型逐 token 预测。
2. **通用 NLP 模型不够懂代码**。代码有强结构（括号配对、缩进、作用域）、多语言（Python/Java/C++/Go…）、长依赖（一个函数引用文件顶部的 import）。需要**专门的代码语料**和**足够长的上下文**。
3. **13B 级模型单卡放不下**。13B 参数仅权重就约 $13\times10^9 \times 2\text{B} = 26\text{GB}$（FP16），加上优化器状态（Adam 的一阶/二阶矩）、梯度、激活，远超单张加速卡显存。→ **必须分布式并行训练** → 这正是 Megatron 的用武之地。
4. **算力自主可控诉求**。CodeGeeX 选择在**昇腾 NPU**上训练，需要把原本面向 NVIDIA GPU 的 Megatron 适配到异构后端（CANN/MindSpore 或 PyTorch+NPU）。

```
        想要的能力                    需要的技术拼图
   ┌───────────────────┐        ┌──────────────────────────┐
   │  代码补全/翻译/注释 │  ←──   │  ① 代码专用语料 + 清洗     │
   │  (多语言)          │        │  ② GPT decoder 自回归架构 │
   └───────────────────┘        │  ③ Megatron 张量并行       │
                                │  ④ 昇腾 NPU 集群适配       │
                                └──────────────────────────┘
```

## 2. 模型架构：从 Transformer 到 CodeGeeX

CodeGeeX 是 **decoder-only** 的 GPT 结构，核心就是 **N 层 Transformer Block 堆叠**。对一个输入 token 序列 $x_1,\dots,x_t$，模型用因果自注意力建模条件概率：

$$P(x_{t+1}\mid x_1,\dots,x_t)$$

训练目标是标准的自回归交叉熵（next-token prediction）：

$$\mathcal{L} = -\sum_{t} \log P(x_{t+1}\mid x_{\le t})$$

### 2.1 单层 Block 的内部结构

```
                输入 hidden  h_in  (shape: [seq, hidden])
                       │
        ┌──────────────┴──────────────┐
        │   LayerNorm                 │
        │      │                      │
        │   Masked Multi-Head         │   ← 因果掩码：第 t 个 token
        │   Self-Attention            │      只能看到 ≤ t 的位置
        │      │                      │
        │   + 残差 (h_in)             │
        └──────────────┬──────────────┘
                       │
        ┌──────────────┴──────────────┐
        │   LayerNorm                 │
        │      │                      │
        │   FFN (MLP)                 │   ← 通常 4×hidden 的中间维
        │   Linear → 激活 → Linear     │      激活如 GELU
        │      │                      │
        │   + 残差                    │
        └──────────────┬──────────────┘
                       │
                   h_out  → 喂给下一层
```

把 N 个这样的 Block 串起来，最后接一个 **输出 LayerNorm + 词表投影（lm_head）**，softmax 出每个词表 token 的概率。

### 2.2 整体堆叠（13B 量级的示意）

```
   tokens ──► [Word Embedding] + [Position Embedding]
                         │
                 ┌───────▼────────┐
                 │  Transformer    │  Layer 1
                 │  Block          │
                 └───────┬────────┘
                         │   ...  (堆叠数十层)
                 ┌───────▼────────┐
                 │  Transformer    │  Layer N
                 │  Block          │
                 └───────┬────────┘
                         │
                  [Final LayerNorm]
                         │
                  [LM Head → 词表概率]
                         │
                   下一个 token
```

> 规模量级（**以官方论文/模型卡为准**）：CodeGeeX 总参数约 **13B**，隐藏维、层数、注意力头数、上下文长度等具体数字请查官方仓库，不要凭记忆套用。这里只讲"为什么这样设计"。

**与原版 GPT 的小差异**（机制层面，不背具体常数）：
- CodeGeeX 在顶部额外加了一个 **query layer / 输出层** 的结构来强化预测——这是为长代码生成做的工程调整，**细节以源码为准**。
- Position Embedding 决定了**最大上下文长度**，这对"一个函数引用文件顶部 import"这类长依赖非常关键。

## 3. 数据流水线：代码语料的特殊性

代码数据和自然语言数据处理思路相同（清洗→分词→打包），但有代码独有的关注点：

```
原始仓库(GitHub等)
      │  ① 语言识别 / 许可证过滤
      ▼
按编程语言分桶 (Python / Java / C++ / Go / JS ...)
      │  ② 去重 (近似去重，避免大量复制粘贴样板)
      ▼
质量过滤 (过滤超长行/自动生成/二进制/低质量)
      │  ③ 分词 (tokenizer，对缩进/符号友好)
      ▼
token 序列 → ④ 拼接打包成固定长度样本 (packing)
      │
      ▼
二进制索引数据集 (Megatron 的 .bin/.idx 格式)
```

要点拆解：

| 步骤 | 为什么这么做 |
|---|---|
| 语言识别 + 许可证过滤 | 只保留可用许可证的代码；按语言标注，便于多语言均衡采样 |
| 近似去重 | 代码库里大量重复/fork，去重避免模型"背诵"而非"理解" |
| 质量过滤 | 剔除压缩文件、自动生成代码、超长单行（minified JS）等噪声 |
| 分词器选择 | 代码里空格/缩进/下划线/符号信息量大，分词要能保留这些结构 |
| packing 打包 | 把短样本拼到固定 `seq-length`，让每个 batch 充分利用算力 |
| `.bin/.idx` | Megatron 用内存映射的二进制索引格式做高吞吐随机读取 |

> 多语言均衡是关键权衡：若按"自然分布"采样，Python/Java 会压倒小众语言。通常会**按语言重加权采样**，让小语种也学得到。

## 4. 为什么用 Megatron：张量并行

13B 模型单卡放不下，必须把模型/数据切到多卡多机。Megatron-LM 提供三种正交的并行维度（CodeGeeX 训练主要依赖**张量并行 TP**，可叠加数据并行 DP）：

```
   ┌─────────────────────────────────────────────────────┐
   │ 数据并行 DP：每张卡有"整份模型副本"，吃不同 batch     │
   │   GPU0[模型] GPU1[模型] ... → 各算梯度 → AllReduce 平均│
   ├─────────────────────────────────────────────────────┤
   │ 张量并行 TP：把"单层内的大矩阵"按列/行切到多卡        │
   │   一层的 Linear 权重 [H×4H] 切成 GPU0[H×2H] GPU1[H×2H]│
   │   前向各算一半 → AllReduce/AllGather 拼回             │
   ├─────────────────────────────────────────────────────┤
   │ 流水并行 PP：把"不同层"放到不同卡，像流水线           │
   │   GPU0:第1~k层  GPU1:第k+1~2k层 ... 微批流水          │
   └─────────────────────────────────────────────────────┘
```

### 4.1 张量并行怎么切一层（核心机制）

以 FFN 的两个 Linear 为例（这是 Megatron 张量并行最经典的设计）：

```
   输入 X  [b, s, H]
      │
      │  第一个 Linear：按"列"切权重  A = [A1 | A2]
      ├──────────────┬──────────────
   GPU0: Y1 = X·A1   GPU1: Y2 = X·A2        ← 各算一半，无需通信
      │  GELU(Y1)        │  GELU(Y2)
      │                  │
      │  第二个 Linear：按"行"切权重  B = [B1; B2]
   Z1 = GELU(Y1)·B1  Z2 = GELU(Y2)·B2
      └──────┬───────────┘
             ▼
        AllReduce(Z1 + Z2)  ← 一次通信得到完整输出 Z
```

**为什么这样切？** "列切 + 行切"配对后，前向只需在块末做**一次 AllReduce**，把通信压到最少。注意力层的 QKV / 输出投影同理切分。这就是 Megatron"在单层内并行"的精髓。

### 4.2 一个显存账（直观感受为什么必须并行）

13B 参数，混合精度 + Adam 优化器，粗略每参数需要的字节：

| 项 | 字节/参数 | 说明 |
|---|---|---|
| FP16 权重 | 2 | 前向用 |
| FP16 梯度 | 2 | 反向产生 |
| FP32 权重副本 | 4 | 优化器主权重 |
| Adam 一阶矩 m | 4 | |
| Adam 二阶矩 v | 4 | |
| 合计 | ~16 | 仅参数相关，**未含激活** |

$13\text{B} \times 16\text{B} \approx 208\text{GB}$，再加上激活——**远超任何单卡**。所以张量并行把这 208GB **横向摊到多张卡**，是训练得以进行的前提。

## 5. 异构硬件：昇腾 NPU 上的适配

CodeGeeX 的一个标志性工程是**在华为昇腾（Ascend 910）集群上训练**。把面向 NVIDIA GPU 的 Megatron 跑到 NPU 上，要解决的不是算法，而是**软件栈替换**：

```
   原 GPU 软件栈                昇腾 NPU 软件栈
   ┌──────────────┐            ┌──────────────┐
   │ Megatron-LM  │  ───迁移──► │ Megatron 适配 │
   ├──────────────┤            ├──────────────┤
   │ PyTorch/CUDA │            │ MindSpore 或  │
   │              │            │ PyTorch+NPU   │
   ├──────────────┤            ├──────────────┤
   │ NCCL (集合通信)│           │ HCCL (集合通信)│
   ├──────────────┤            ├──────────────┤
   │ cuDNN/cuBLAS │            │ CANN 算子库    │
   ├──────────────┤            ├──────────────┤
   │ A100/V100    │            │ Ascend 910    │
   └──────────────┘            └──────────────┘
```

适配点（讲机制，**具体 API/版本以官方为准**）：

| 需要替换的层 | GPU 侧 | 昇腾侧 | 影响 |
|---|---|---|---|
| 集合通信库 | NCCL | **HCCL** | AllReduce/AllGather 走 HCCL |
| 底层算子 | cuDNN/cuBLAS | **CANN** | matmul/attention 等需有对应高性能算子 |
| 框架后端 | CUDA | **CANN + MindSpore / torch_npu** | 训练脚本/分布式初始化要改后端 |
| 混合精度 | AMP | NPU 对应实现 | 需确认 FP16/BF16 数值行为一致 |

> 这一步是"算力国产化"的真实代价：算法不变，但通信库、算子库、框架后端全部要打通并调优，**性能是否对齐 GPU 需要实测**，不要假设零开销。

## 6. 典型训练流程

把前面拼图串成一条端到端的链路：

```
[1] 准备代码语料        →  原始仓库 → 清洗去重 → 多语言分桶
        │
[2] 数据预处理          →  分词 → packing → 生成 .bin/.idx
        │
[3] 配置并行策略         →  TP=? DP=? (按集群卡数与单卡显存定)
        │
[4] 初始化分布式         →  各 rank 建通信组 (HCCL/NCCL)
        │
[5] 训练循环            →  load batch → 前向 → 反向 → 优化器 step
        │                  (TP 内 AllReduce 拼算子, DP 间 AllReduce 梯度)
        │
[6] checkpoint          →  按 (TP×PP) 分片保存权重
        │
[7] 转换/合并           →  分片 ckpt → 合并为可推理格式
        │
[8] 推理/部署          →  Docker 镜像 / IDE 插件做代码补全
```

**为什么要"分片保存再合并"？** 张量并行下，每张卡只持有权重的一部分。训练 checkpoint 是按并行切分存的；上线前若推理用更小的并行度（甚至单卡），就需要把分片**合并/重切**成目标格式。这与 [[llm-train/megatron/gpt2/merge_ck_and_inference/README]] 里 GPT-2 的合并思路一致。

## 7. 关键配置项（讲含义，不背默认值）

下面是 Megatron 系训练里**经常要调**的旋钮，理解"它做什么、怎么权衡"比记默认值重要。**确切参数名/默认值以官方脚本为准。**

| 配置类别 | 控制什么 | 调大/调小的权衡 |
|---|---|---|
| 张量并行度 `tensor-model-parallel-size` | 单层切到几张卡 | 调大→单卡省显存，但**层内通信增多**、需高速互联（NVLink/HCCS） |
| 流水并行度 `pipeline-model-parallel-size` | 把层分几段流水 | 调大→省显存，但有**流水气泡**，需调微批数掩盖 |
| 全局 batch / micro-batch | 一步喂多少样本 / 每次前向多少 | 全局 batch 影响收敛与吞吐；micro-batch 受激活显存限制 |
| 序列长度 `seq-length` | 上下文窗口 | 调大→能看更长代码依赖，但**激活显存与注意力计算 ~O(s²)** 暴涨 |
| 学习率 / warmup / 衰减 | 优化器步长曲线 | warmup 防早期发散；衰减影响后期收敛质量 |
| 混合精度 FP16/BF16 | 计算精度 | 省显存提速，但 FP16 易溢出需 loss scaling；BF16 动态范围大更稳 |
| 激活重计算 (recompute) | 是否丢弃中间激活反向时重算 | 开→省激活显存，代价是**多一次前向算力** |
| 梯度累积步数 | 用累积模拟大 batch | 显存不够又想要大 batch 时用，代价是单步变慢 |
| 数据采样权重 | 各语言/数据源占比 | 平衡多语言，避免小语种被淹没 |

**一个权衡直觉：** TP 通信频繁（每层都通信），所以**张量并行尽量放在同一节点内**（走 NVLink/HCCS 高带宽）；PP/DP 跨节点（走 IB/RoCE）相对能容忍。这条原则在 [[ai-framework/megatron-lm/README]] 和 [[ai-infra/网络/InfiniBand]] 里反复出现。

## 8. 推理与部署：Docker 与插件

CodeGeeX 既可作为研究模型推理，也有面向开发者的 IDE 插件（VS Code / JetBrains）做实时补全。

### 8.1 用官方镜像快速起一个推理环境

```bash
# 拉取官方镜像
docker pull codegeex/codegeex:latest

# 启用 GPU（用 --device / --gpus 指定卡号），开 ipc=host 便于共享内存
docker run --gpus '"device=0,1"' -it --ipc=host --name=codegeex codegeex/codegeex
```

> 说明：`--gpus '"device=0,1"'` 表示把宿主机的第 0、1 号 GPU 暴露给容器；`--ipc=host` 让容器与宿主共享 IPC 命名空间，避免多进程数据加载时共享内存不足。**具体镜像标签/依赖以官方仓库为准。**

### 8.2 从源码安装

```bash
git clone git@github.com:THUDM/CodeGeeX.git
cd CodeGeeX
pip install -e .   # 以可编辑模式安装，便于改源码调试
```

### 8.3 补全推理的本质（调用链）

```
   用户在 IDE 里写下半截代码 / 注释
              │  (prompt = 已有上文)
              ▼
   插件把上下文拼成 prompt 发给推理服务
              │
              ▼
   模型自回归逐 token 生成
   (可用 KV-Cache 复用历史，见 [[llm-optimizer/kv-cache]])
              │
              ▼
   按停止条件 (换行/缩进/最大长度) 截断
              │
              ▼
   返回候选补全 → IDE 展示 ghost text
```

> 推理优化（KV-Cache、量化、批处理）不是 CodeGeeX 独有，可直接复用通用方案：见 [[llm-inference/README]] 与 [[llm-compression/README]]。

## 常见问题与坑

| 现象 / 坑 | 原因 | 怎么处理 |
|---|---|---|
| 单卡 OOM | 13B 放不下单卡 | 调大张量并行度 / 开激活重计算 / 减小 micro-batch |
| 多机训练慢、扩展性差 | TP 跨节点走慢速网络 | **TP 放节点内**，PP/DP 跨节点；确认 IB/HCCS 互联 |
| FP16 训练 loss 变 NaN | FP16 动态范围窄、溢出 | 开 loss scaling；或改用 BF16 |
| 昇腾上跑不起来 / 算子缺失 | CANN 算子或后端未对齐 | 核对 CANN 版本与适配分支，缺算子需替换/落 CPU |
| checkpoint 加载形状不匹配 | 训练 TP 度 ≠ 加载 TP 度 | 先做 ckpt 合并/重切到目标并行度 |
| 小众语言生成质量差 | 语料采样被大语言淹没 | 调整各语言**采样权重**做均衡 |
| 长代码上文被截断 | 超出 `seq-length` | 训练/推理上下文窗口受限，需更长上下文模型或检索增强 |
| 模型"背"出训练里的代码 | 语料去重不足 | 加强近似去重，避免大量重复样本 |

> 一句话总结排坑顺序：**先看显存（OOM）→ 再看并行拓扑（TP 别跨节点）→ 再看数值稳定（FP16/BF16）→ 最后看数据（去重/采样均衡）。**
