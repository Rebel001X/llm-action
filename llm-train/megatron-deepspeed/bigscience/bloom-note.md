## 0. 一句话锚点

**一句话：** BLOOM 不是某个新算法，而是一次「把已知的训练技术(GPT 结构 + 3D 并行 + ZeRO + BF16)在 176B 规模、46 种语言、384 卡集群上真正跑通并开源」的系统工程；它的价值在于**完全公开**了训练数据、代码、checkpoint 和踩过的每一个坑。

> 注意区分两个东西：
> - **Megatron-DeepSpeed**(框架)= 工具,见 [[ai-framework/megatron-lm/README]]、本目录 `README.md`。
> - **BLOOM**(模型)= 用这个工具训出来的产物,也就是本篇主角。

## 1. 地基：BLOOM 解决了什么问题

2022 年的背景是：GPT-3(175B)、PaLM、Chinchilla 这些百亿~千亿模型**几乎全是闭源**——你能调 API,但拿不到权重、看不到数据、不知道怎么训的。这带来三个问题：

1. **不可复现**：学术界无法验证、改进。
2. **语言不公平**：训练语料以英文为主,小语种被边缘化。
3. **黑箱风险**：偏见、隐私、安全问题无法审计。

BigScience 是一个由 Hugging Face 牵头、**1000+ 研究者跨 60+ 国家**协作的开放科学项目(类比"大型强子对撞机"那种集体科研),目标就是：

```
            闭源大模型的困境                 BLOOM 的答卷
 ┌──────────────────────────┐    ┌──────────────────────────┐
 │ 权重不公开                │──▶ │ 全量 checkpoint 开源       │
 │ 训练数据不透明            │──▶ │ ROOTS 语料公开 + 文档      │
 │ 英文中心、小语种缺失      │──▶ │ 46 种自然语言 + 13 编程语言 │
 │ 训练方法是商业机密        │──▶ │ 代码 + 日志 + 踩坑全公开    │
 └──────────────────────────┘    └──────────────────────────┘
```

**所以 BLOOM 的"贡献"主要不是分数,而是"把一个 GPT-3 量级模型的完整训练过程开源化、多语言化"。** 这是读这篇笔记时要先建立的认知锚点。

## 2. 模型结构：关键改动

BLOOM 的骨架是标准的 **decoder-only 自回归 Transformer**(GPT 家族),但相对原版 GPT 做了两处对训练稳定性至关重要的改动。底层 Transformer 原理见 [[llm-algo/transformer/模型架构]]。

### 2.1 整体结构(自回归 decoder)

```
 输入 token id
      │
      ▼
 ┌──────────────────────────┐
 │ Word Embedding (250k 词表) │  ← 词表巨大,见 §3.2
 ├──────────────────────────┤
 │ Embedding LayerNorm  ★改动1 │  ← 嵌入后多加一个 LN
 ├──────────────────────────┤
 │  N × Transformer Block:   │
 │   ┌────────────────────┐  │
 │   │ LayerNorm          │  │
 │   │ Multi-Head Attn    │  │
 │   │  + ALiBi  ★改动2    │  │  ← 用 ALiBi 替代位置嵌入
 │   │ LayerNorm          │  │
 │   │ MLP (GeLU)         │  │
 │   └────────────────────┘  │
 ├──────────────────────────┤
 │ Final LayerNorm           │
 ├──────────────────────────┤
 │ LM Head (与 Embedding 绑权)│
 └──────────────────────────┘
      │
      ▼
 下一个 token 的概率分布
```

### 2.2 改动 1：嵌入层后加 LayerNorm(Embedding LayerNorm)

- **是什么**：在 word embedding **之后、第一个 Transformer block 之前**,额外插入一个 LayerNorm。
- **为什么**：在试图训 104B 模型时反复发散(loss 爆炸),实验发现这个额外 LN 能显著稳住早期训练。灵感来自 `bitsandbytes` 的 `StableEmbedding`。
- **代价**：理论上轻微影响表达能力,但换来"训得动"——大规模训练里**稳定性 > 微小的理论最优**。

### 2.3 改动 2：用 ALiBi 替代位置嵌入

- **绝对/可学习位置嵌入的痛点**：训练时序列长度固定(BLOOM 用 2048),推理想用更长序列时,没见过的位置编码会让效果崩。
- **ALiBi(Attention with Linear Biases)做法**：不给 token 加位置向量,而是在 attention 分数上**按 query-key 距离加一个线性递减的惩罚偏置**——距离越远,惩罚越大。

$$\text{score}_{ij} = q_i \cdot k_j - m \cdot (i - j)$$

其中 $m$ 是每个注意力头固定的斜率(slope)。直觉:"离得越远的 token,默认越不重要",这个先验不依赖绝对位置,因此**能外推到比训练时更长的序列**(Train Short, Test Long)。

> 三个改动并不是 BLOOM 发明的,而是它**敢在 176B 规模上押注**这些当时还算新的技术,并验证了有效性。

## 3. 3D 并行：384 张卡怎么排

176B 参数光模型状态(Adam + 混合精度,约 $16\Phi$ 字节)就要 $\approx 2.8$ TB 显存,单卡 80GB 装不下,必须**三个维度同时切**。3D 并行的原理详见本目录 `README.md` 与 [[llm-train/pytorch/distribution/README]],这里只讲 BLOOM 的**具体选型**。

### 3.1 TP × PP × DP 的乘法关系

$$\text{总 GPU 数} = \text{TP} \times \text{PP} \times \text{DP}$$

BLOOM 选择(典型配置):

```
          TP = 4              PP = 12             DP = 8
 ┌───────────────────┐ ┌──────────────────┐ ┌──────────────────┐
 │ 把每个权重矩阵     │ │ 把 72 层(含嵌入) │ │ 复制 8 份整套     │
 │ 横向切成 4 片      │ │ 纵向切成 12 段    │ │ 各喂不同数据      │
 │ → 放进同一节点的   │ │ → 每段约 6 层     │ │ → 数据并行        │
 │   4 张 GPU(走NVLink)│ │   跨节点流水线    │ │   ZeRO-1 分片优化器│
 └───────────────────┘ └──────────────────┘ └──────────────────┘
        4        ×          12         ×          8       = 384 张 GPU
```

**为什么 TP=4?** 这是 BLOOM 一条最重要的实践经验:

> TP 在每层前向/反向都要做 **2 次 all-reduce**,通信极重,**必须跑在卡间高速互联(NVLink)上**。BLOOM 集群每节点 8 卡但只有 4 条 NVLink,所以 **TP 度设为 4(不跨节点)** 最划算。想用 TP=8 就得保证 8 卡全在一个节点且互联够快。

集合通信原语(all-reduce / reduce-scatter 等)见 [[ai-infra/网络/集合通信原语]],NCCL 见 [[ai-infra/网络/NCCL]]。

### 3.2 嵌入层为什么单独占一级流水线?

这是 BLOOM 一个非常具体、也很有教学价值的细节：

- BLOOM 词表 **250,680** 个 token(为覆盖 46 种语言而巨大)。
- 嵌入矩阵 = $250{,}680 \times 14336 \times 2\text{B(bf16)} \approx 7.2$ GB,而**一个普通 Transformer block 只要约 4.9 GB**。
- 如果嵌入层和别的层挤在同一流水线级,那一级会**显存爆炸**,而其余 95% 的卡很空——负载严重不均。

**解决办法**:让 Megatron-DeepSpeed 把**嵌入层当成一个独立的"Transformer 块"**,于是流水线从 70 级变成 **72 级**(首尾各一级专给输入/输出嵌入)。

```
 PP 级:  [emb] [blk] [blk] ... [blk] [emb_out]
          ↑                              ↑
      第 1 级                       第 72 级
      只放嵌入                      只放输出嵌入
   ── 这样首尾级显存 ≈ 中间级,负载均衡 ──
```

> 教学点:**流水线并行的瓶颈是"最重的那一级"**,负载均衡比平均切层更重要。

### 3.3 ZeRO 在 BLOOM 里只开到 Stage 1

DeepSpeed ZeRO 详见 [[ai-framework/deepspeed/README]]。BLOOM 在 DP 维度叠加 ZeRO,但**只启用 Stage 1(只分片优化器状态)**:

| ZeRO Stage | 分片对象 | BLOOM 是否用 | 原因 |
| --- | --- | --- | --- |
| Stage 1 | 优化器状态 | ✅ 用 | 省显存且通信开销小,和 PP 兼容好 |
| Stage 2 | + 梯度 | ❌ 不用 | 每个 micro-batch 多一次 reduce-scatter,PP 用小 micro-batch 时通信开销伤性能 |
| Stage 3 | + 参数 | ❌ 不用 | 通信量大于 3D 并行;且 PP 已把梯度切成 1/PP,再分片省不了多少 |

> 当年评估结论:**Megatron-DeepSpeed 3D 并行 > ZeRO-3**。原文也坦言"如果今天重评,ZeRO-3 已大幅优化,也许会选 Stage 3"——这是个会随框架演进而变的结论,**具体以官方文档/当下基准为准**。

## 4. 数值稳定性：为什么死磕 BF16

这是 BLOOM 最值得记住的一课。

### 4.1 FP16 的"溢出"陷阱

FP16 和 BF16 都是 2 字节,但**指数位/尾数位的分配不同**:

```
 FP32:  1 符号 | 8 指数  | 23 尾数      动态范围大、精度高
 FP16:  1 符号 | 5 指数  | 10 尾数      范围小(±65504)、精度高
 BF16:  1 符号 | 8 指数  |  7 尾数      范围大(同 FP32)、精度差
                   ▲
            指数位决定"能表示多大的数"
```

- FP16 最大约 **65504**,你算 $250\times250=62500$ 没事,但 $255\times255=65025$ 就接近上限,大模型里激活/梯度很容易**溢出成 Inf → NaN → 训练发散**。
- BFloat16 指数位和 FP32 一样多,所以 $10000\times10000=10^8$ 也完全 OK,**几乎不溢出**——代价是尾数只有 7 位,精度差。

BLOOM 团队花了几个月试图用 FP16 训 104B,结果 lm-loss **彻底发散**;Megatron/DeepSpeed 团队训 530B、Meta 训 OPT-175B 都报告 FP16 极难训。结论:**百亿以上规模,FP16 是禁忌,BF16 才稳**(A100 起原生支持 BF16)。

### 4.2 BF16 精度差怎么办?三个保险

精度差为什么不致命?因为 SGD 类优化器本身是"蹒跚下山",单步方向不完美,后续会纠正。再加三道保险:

1. **FP32 master 权重**:优化器始终维护一份 FP32 权重副本来更新,16 位只用于前向/反向计算。
2. **FP32 累加**:所有 PyTorch 累加操作(reduce 等)在 FP32 下做,避免累积误差。
3. **FP32 梯度累积**:流水线并行天然要累积多个 micro-batch 的梯度——这个累积**必须在 FP32 里做**,否则误差滚雪球。这正是专门写的 `BF16Optimizer` 的核心职责。

```
        前向/反向 (BF16,快、省显存)
              │  产出 BF16 梯度
              ▼
        梯度累积 (FP32,防误差累积) ★
              │
              ▼
        优化器更新 FP32 master 权重 ★
              │
              ▼
        转回 BF16 → 下一轮迭代
```

> 一句话:**用 BF16 算得快,用 FP32 存得准**,两者分工。

## 5. 数据流水线：46 种语言怎么混

数据集 ≈ **41.5 TB** 清洗去重后的文本(ROOTS 语料库),最终 tokenize 成约 **350B token**,词表 250,680。Megatron 的高效 DataLoader 做了几件事:

1. **切定长样本**:首次训练前,把每条数据切成固定 2048 长度的样本,并建立索引编号。
2. **多 epoch 索引 + 全局打乱**:按需要的 epoch 数生成有序索引(如 `[0..9, 0..9]`),再**整体打乱**,而不是"走完一遍再重头"。

   ```
   原始:  [0 1 2 ... 9 | 0 1 2 ... 9]   (2 个 epoch 拼接)
   打乱:  [3 8 0 5 ... | ... 1 9 4]     (全局 shuffle)
   效果:  可能先看到同一样本两次,但全程每样本恰好出现 2 次 → 训练曲线更平滑
   ```

3. **索引落盘缓存**:样本偏移、顺序等索引算一次存文件,后续重启训练直接读,**不重算**。
4. **多数据集按权重混合**:46 种语言按设定权重(如保护小语种、平衡资源)混成最终训练流。

> 这部分实现细节(`build_train_valid_test_datasets` 等)见同目录 `source-code.md`;mmap 二进制数据集格式见本目录 `README.md` 的数据流水线一节。

## 6. 工程难题：大规模才暴露的坑

很多问题**小规模根本看不到,上了 48 节点(~384 GPU)才出现**。这部分是 BLOOM 笔记最有价值的"实战经验"。

| 难题 | 现象 | 应对 |
| --- | --- | --- |
| 框架挂起 | 多节点启动直接 hang | 设 `CUDA_LAUNCH_BLOCKING=1`(同步 CUDA 调用便于定位);把优化器参数组拆成更小的组 |
| 硬件故障 | ~400 卡新集群,平均**每周 1-2 张 GPU 坏** | 每 3 小时(~100 迭代)存一次 checkpoint;备用节点热替换;每周约损失 1.5 小时训练 |
| PyTorch 死锁 | 偶发 5-10 小时停机 | 定位并规避死锁;磁盘空间不足也会停机,需监控 |
| SLURM 单用户所有权 | 作业归单个用户,本人不在别人动不了 | 自建"终止方案"让组内他人可安全 kill,解决了 90% 协作问题 |

```
  典型一周的"非训练时间"构成(示意):
  硬件故障恢复 ▇▇▇  ~1.5h
  各类停机     ▇▇▇▇▇  5~10h(偶发)
  checkpoint   ▇      可接受开销
  ── 所以"频繁存档 + 自动恢复 + 备用节点"是大规模训练的命脉 ──
```

> 教学点:百卡千卡级训练,**MTBF(平均无故障时间)会下降到"天"级**,checkpoint 频率和自动恢复机制不是锦上添花,而是能不能训完的生死线。

## 数值例子：BLOOM-176B 的配置账

把零散数字汇总成一张"配置账单"(以公开资料为准,**精确版本号/默认值请查官方仓库**)：

| 维度 | 数值 | 算法/含义 |
| --- | --- | --- |
| 参数量 | ~176B | decoder-only |
| 模型状态显存 | $\approx 16 \times 176 = 2816$ GB | Adam + 混合精度,$16\Phi$ 字节 |
| 集群 GPU | 384 张 A100 80GB(+32 备用) | 48 节点 × 8 卡 |
| 单节点显存 | 640 GB | 8 × 80GB |
| TP | 4 | 不跨节点,走 NVLink |
| PP | 12 | 72 级层 ÷ 约 6 |
| 流水线级数 | 72 | 70 层 + 首尾 2 个嵌入级 |
| DP | 8 | $4\times12\times8=384$ ✅ |
| 序列长度 | 2048 | ALiBi 支持推理时外推 |
| 词表 | 250,680 | 嵌入矩阵 ~7.2 GB(bf16) |
| 训练 token | ~350B | 41.5 TB 文本去重后 |
| checkpoint 周期 | 每 ~100 迭代 / 3 小时 | 抗硬件故障 |

**互联拓扑(简化)**：

```
  节点内:  GPU0─GPU1   GPU2─GPU3   ...   ← 4×NVLink,跑 TP=4
            └─────┴── 同一 TP 组 ──┘
  节点间:  Omni-Path(OPA)无阻塞胖树     ← 跑 PP / DP
  NCCL:    专用子网,与磁盘 IO(GPFS)分离
```

> 这里的具体并行度是**典型公开配置**;不同训练阶段可能微调,**确切数值以 BigScience 官方训练日志为准**。

## 常见问题(典型坑)

| 问题 | 原因 | 怎么办 |
| --- | --- | --- |
| 为什么不能用 FP16 训 176B? | FP16 指数位少、范围 ±65504,大模型激活/梯度溢出成 NaN | 用 BF16(指数位同 FP32);A100 起原生支持 |
| TP 设成 8 反而变慢? | TP 每层 2 次 all-reduce,跨节点互联慢 | **TP 度 ≤ 节点内高速互联卡数**(BLOOM 取 4) |
| 流水线某一级 OOM,别的级很空? | 嵌入层/词表巨大,和普通层挤一级负载不均 | 把嵌入层**单独占一个 PP 级**(BLOOM 72 级由来) |
| 梯度累积后 loss 抖动/精度掉? | 在 BF16 里累积梯度,误差滚雪球 | 梯度累积/累加用 **FP32**(BF16Optimizer 的核心) |
| 多节点一启动就 hang? | 异步 CUDA 调用 + 大优化器组 | `CUDA_LAUNCH_BLOCKING=1` 定位;拆小优化器参数组 |
| 训练老中断、进度丢? | 数百卡集群每周都有 GPU 坏 | 高频 checkpoint(~3h)+ 自动恢复 + 备用节点 |
| ZeRO 为什么只开 Stage 1? | Stage 2/3 与 PP 叠加通信开销大、收益小 | 3D 并行 + ZeRO-1;是否上 Stage 3 视框架版本重评 |

> 通用护栏:本笔记讲的是**机制与权衡**。具体 CLI 参数名、默认值、版本号、API 签名,**一律以 [Megatron-DeepSpeed / BigScience 官方仓库](https://github.com/bigscience-workshop/Megatron-DeepSpeed) 和 Hugging Face 模型卡为准**,切勿凭记忆套用。
