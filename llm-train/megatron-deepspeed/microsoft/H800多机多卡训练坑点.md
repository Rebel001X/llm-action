## 0. 一句话锚点

**H800 多机多卡训练的坑，90% 不在 GPU 算力本身，而在「卡间/机间互联被阉割」与「软件栈版本/环境变量没对齐」**。H800 是 H100 的「中国特供」版，算力接近但 **NVLink/互联带宽被显著限制**，这使得任何依赖大量跨卡通信的并行策略（尤其 TP 张量并行）都比 H100 更容易成为瓶颈，也更容易把环境配置的不当放大成 hang、超时、性能腰斩。

## 1. 地基：H800 是什么，为什么它的坑和 H100 不一样

### 1.1 H800 相对 H100 的关键差异（机制层面）

H800 与 H100 同属 Hopper 架构，**单卡 FP16/BF16 算力、显存（80GB HBM）基本一致**，差异集中在**互联带宽**：

- **NVLink 带宽被限制**：H100 单卡 NVLink 总双向带宽约 900 GB/s 量级；H800 的 NVLink 带宽被下调到明显更低的水平（具体数值以 NVIDIA 官方规格为准）。这直接影响**机内 8 卡之间**的 all-reduce / all-gather 速度。
- **机间网络（IB/RoCE）不受这条限制**：机间靠 InfiniBand 或 RoCE 网卡，单端口可达 200/400 Gbps，这部分和 H100 集群一样。

> 直觉：H800 的「卡内互联」变窄了，「机间互联」没变。所以**机内通信反而可能比机间更值得优化**，TP（重通信）放进单机内、PP/DP（轻通信）跨机，这个原则在 H800 上比 H100 更重要。

```
            H100 vs H800（带宽视角，示意非精确）
   机内 NVL8          机间 IB/RoCE
H100:  ███████████      ██████        (NVLink 宽，网卡常规)
H800:  ████             ██████        (NVLink 被砍，网卡不变)
       ↑                ↑
   差异主要在这          这里两者相近
```

### 1.2 它解决什么问题 / 为什么单机不够

一个 13B~70B 的模型，单卡 80GB 显存放不下「参数 + 优化器状态 + 梯度 + 激活」。以 Adam + 混合精度为例，每个参数大致需要：fp16 参数 2B + fp16 梯度 2B + fp32 参数副本 4B + fp32 动量 4B + fp32 方差 4B ≈ **16 字节/参数**。

$$
\text{显存}_{\text{状态}} \approx 16 \times N_{\text{params}}
$$

70B 模型仅优化器/参数状态就约 $16 \times 70\text{e}9 = 1120\text{ GB}$，远超单卡。所以必须**多机多卡 + 并行切分（TP/PP/DP/ZeRO）**，而一旦跨机，就把上面所有「互联层、环境层、通信层」的坑都引进来了。

## 2. 整体架构：一次多机训练的全链路

把多机训练拆成五层，**坑按层归类**，排查时也按层二分：

```
┌─────────────────────────────────────────────────────────┐
│  L5 训练稳定层  3D并行配置 / OOM / loss spike / ckpt      │ ← 第7节
├─────────────────────────────────────────────────────────┤
│  L4 通信层      NCCL all-reduce/all-gather + 环境变量     │ ← 第6节
├─────────────────────────────────────────────────────────┤
│  L3 启动层      torchrun rendezvous / 心跳 / RANK 编址    │ ← 第5节
├─────────────────────────────────────────────────────────┤
│  L2 互联层      IB/RoCE 网卡 + GDR + NVLink 拓扑          │ ← 第4节
├─────────────────────────────────────────────────────────┤
│  L1 环境层      CUDA / 驱动 / NCCL / 镜像 / Python 栈     │ ← 第3节
└─────────────────────────────────────────────────────────┘
        ↑ 下层不对，上层一定崩；先稳住底层再往上调
```

一次完整的多机拉起流程（调用链）：

```
用户 srun/torchrun
   │
   ├─► 各节点 torchrun 进程  ──► rendezvous（rdzv-endpoint 选 master）
   │        │                         协商出 world_size / 全局 RANK
   │        ▼
   ├─► 每节点 spawn nproc_per_node 个训练进程（每进程绑 1 张 H800）
   │        │
   │        ▼
   ├─► torch.distributed.init_process_group(backend="nccl")
   │        │  握手：交换各 rank 的 IP/IB 地址、建立 NCCL communicator
   │        ▼
   ├─► Megatron 划分 TP/PP/DP 通信组（rank → 三维坐标）
   │        ▼
   └─► 训练 step：前向→反向→TP all-reduce→DP all-reduce/ZeRO→优化器
```

## 3. 环境层坑点（L1）：版本与镜像

### 3.1 CUDA / 驱动 / NCCL 必须配套

- **CUDA 11.8 及以上**（文件原始备注；Hopper/H800 需要较新的 CUDA 才有完整算子与 NCCL 支持）。更高版本（如 12.x）通常对 Hopper 更友好，但要与 PyTorch 编译时的 CUDA 版本一致。
- **核心原则：PyTorch 自带的 CUDA runtime 版本、容器内 CUDA、宿主机驱动三者要相容**。驱动版本要 ≥ 该 CUDA 所要求的最低驱动。
- **NCCL 版本影响巨大**：太老的 NCCL 可能不认识 Hopper 拓扑、不支持某些 IB 特性，导致回退到慢路径甚至 hang。NCCL 通常随 PyTorch 打包，必要时单独升级。

> 具体版本组合以 NVIDIA NGC 镜像说明 / PyTorch 官方 release notes 为准，不要凭记忆钉死某个号。

### 3.2 「能跑通但很慢」常常是环境没对齐

典型现象：单机 8 卡很快，一上多机吞吐暴跌。优先怀疑：
1. NCCL 没走 IB，回退到了 TCP/以太网（见第 4、6 节）。
2. 容器没把 IB 设备 `/dev/infiniband` 透传进去。
3. 驱动/固件不一致，GDR（GPUDirect RDMA）没生效。

### 3.3 多机环境一致性

所有节点的**镜像、CUDA、NCCL、Python 依赖、模型代码、tokenizer 必须逐字节一致**。不一致会出现「某个 rank 行为不同 → 集合通信对不齐 → hang」。实践：用同一个镜像 + 共享存储分发代码，避免「在每台机分别 pip install」。

## 4. 互联层坑点（L2）：IB / RoCE / GDR / 拓扑

### 4.1 机内拓扑：把重通信关在单机里

H800 单机内 8 卡通过 NVLink/NVSwitch 互联（带宽虽被限，仍远快于跨机）。**张量并行 TP 每个 micro-step 都要做 all-reduce，是最重的通信**，所以：

> 黄金法则：`TP_size ≤ 单机 GPU 数（一般 8）`，让 TP 通信永远走机内 NVLink，绝不跨机。PP/DP 才允许跨机。

```
   节点0 (8×H800, NVLink 全互联)      节点1 (8×H800)
   ┌───────────────────────┐         ┌───────────────────────┐
   │ G0 G1 G2 G3 ── TP组    │  IB/RoCE│ G0 G1 G2 G3 ── TP组    │
   │ G4 G5 G6 G7 ── TP组    │◄═══════►│ G4 G5 G6 G7 ── TP组    │
   └───────────────────────┘         └───────────────────────┘
        TP 走机内(快)              DP/PP 走机间(慢，但通信量小)
```

### 4.2 机间互联：IB 还是 RoCE

- **InfiniBand**：原生 RDMA，延迟最低，最省心。需要 OpenSM/子网管理器、正确的 HCA 驱动（MLNX_OFED）。
- **RoCE（RDMA over Ethernet）**：跑在以太网上，**强依赖无损网络（PFC/ECN）配置**，配错就丢包、重传、性能崩。

### 4.3 GDR（GPUDirect RDMA）

让网卡直接读写 GPU 显存，不经过 CPU 内存中转，跨机通信延迟大幅下降。**坑**：需要 GPU 与网卡在**同一 PCIe Switch / 同一 NUMA**下，且 `nv_peer_mem`/`gdrcopy` 模块加载、容器有权限。没生效时 NCCL 会回退到 host 中转，慢但不报错——**最隐蔽的性能坑**。

### 4.4 容器透传清单（最常漏）

跨机训练容器常因没透传设备而退化：
- IB 设备：`/dev/infiniband`
- 共享内存：`--shm-size` 给够（NCCL/DataLoader 用），太小会报 `bus error`
- IPC/网络：`--ipc=host` 或足够大的 shm，`--network=host`（或正确的 overlay）
- ulimit：`memlock=unlimited`（RDMA 需要锁页内存）

## 5. 启动层坑点（L3）：torchrun rendezvous 与心跳

### 5.1 多机 torchrun 三件套

多机训练用 `torchrun` 需要指定（参考 PyTorch elastic 文档 https://pytorch.org/docs/stable/elastic/run.html）：

- `--rdzv-id`：唯一作业 id，**所有参与节点必须一致**（用于会合）。
- `--rdzv-backend`：`RendezvousHandler` 的实现，常用 `c10d`（不必额外起 etcd）。
- `--rdzv-endpoint`：会合后端运行的地址，`host:port` 形式，通常指向 **node 0**。

> 旧式写法用 `--master_addr/--master_port/--nnodes/--node_rank`（仓库内 launch 脚本即此风格）；新式弹性写法用 `--rdzv-*`。两者别混用。固定拓扑场景用 master 风格更简单，弹性扩缩容用 rdzv 风格。

```
   会合(rendezvous) 过程
   node0 ─┐
   node1 ─┼─► 连到 rdzv-endpoint(=node0:port) ─► 凑齐 nnodes 个
   node2 ─┘                                      ↓
                              协商出 world_size、给每进程分配全局 RANK、
                              选出谁是 LOCAL_RANK 0 → 然后才 init_process_group
```

### 5.2 心跳检测失败（原文重点）

报错：
```
The node 'xxx' has failed to send a keep-alive heartbeat to the
rendezvous 'xxx' due to an error of type RendezvousConnectionError.
```
参考 issue：https://github.com/pytorch/pytorch/issues/76287

**机制**：rendezvous 后端（c10d store，常驻 node0）需要各节点周期性发心跳；网络抖动、node0 端口被占/被防火墙拦、DNS 解析慢、节点时钟漂移、某节点 OOM 卡死，都会导致心跳超时，进而整个作业被判定失败重启。

**排查与缓解**：
1. 确认 `rdzv-endpoint`/`master_addr` 在所有节点都能 `ping` 通且端口可达（防火墙、安全组）。
2. master 端口不要选已被占用的；同机多作业要错开端口。
3. 用 IP 而非主机名，规避 DNS 解析不稳。
4. 适当放大超时（rdzv/监控相关超时参数，具体名以版本文档为准），抵抗瞬时抖动。
5. 检查是否某个 rank 实际是因 **OOM/段错误先死**，心跳失败只是表象——去看那个 rank 的真实日志。

### 5.3 RANK 编址错乱

`NODE_RANK` 在每台机必须不同且连续（0,1,2,...），`MASTER_ADDR` 全机一致指向 node0。**两台机都填 NODE_RANK=0** 是高频低级错误，表现为进程数对不上、world_size 不符、init 卡死。

## 6. 通信层坑点（L4）：NCCL 调优与 hang 排查

### 6.1 先打开可观测性

排查通信问题第一件事是开调试输出（环境变量，跨所有 rank 设置）：

- `NCCL_DEBUG=INFO`（甚至 `WARN`/`TRACE`）——看 NCCL 选了哪条传输路径（NVLink/IB/SHM/SOCKET）、用了哪块网卡。**如果日志里跨机走的是 `[Socket]` 而非 `[IB]`，说明没走 RDMA，性能必差**。

### 6.2 常用 NCCL 环境变量（讲用途，不背默认值）

| 变量 | 作用 | 何时调 |
|---|---|---|
| `NCCL_IB_DISABLE` | 是否禁用 IB | 调试时临时设 1 看是否 IB 配置问题；生产应为 0 |
| `NCCL_SOCKET_IFNAME` | 指定走哪张网卡（如 `eth0`/`bond0`） | 多网卡机器选错网卡是经典坑 |
| `NCCL_IB_HCA` | 指定用哪些 IB HCA 设备 | 多 HCA 想绑特定卡/避开坏卡 |
| `NCCL_IB_GID_INDEX` | RoCE 下选 GID | RoCE 环境常需手动设对 |
| `NCCL_P2P_DISABLE` | 禁用卡间 P2P | 拓扑异常时排查用，正常别关 |
| `NCCL_NET_GDR_LEVEL` | 控制 GDR 启用层级 | 想强制/排查 GPUDirect RDMA |
| `NCCL_ALGO` / `NCCL_PROTO` | 选集合算法/协议（Ring/Tree 等） | 调优大集群 all-reduce |

> 具体变量名与取值以 NCCL 官方文档为准；不确定的变量不要乱设，可能适得其反。原则：**先用 `NCCL_DEBUG=INFO` 看现状，再针对性改一两个变量，每次只改一个并对比吞吐**。

### 6.3 NCCL hang（训练卡住不报错）排查

集合通信要求**所有参与 rank 都到达同一个集合调用**，否则一直等。常见根因：

```
   正常: rank0 ─all_reduce─┐
        rank1 ─all_reduce─┼─► 同步完成，继续
        rank2 ─all_reduce─┘
   hang: rank0 ─all_reduce─┐
        rank1 ─all_reduce─┤   ← 大家都在等
        rank2 ─(还在跑别的/已崩)  rank2 没来 → 永久等待
```

诱因：某 rank 走了**不同的代码分支**（如只有部分 rank 满足某 if 条件去做了一次额外通信）、数据量在各 rank 不一致（不等长 batch）、某 rank 先 OOM 死掉但进程没退、IB 链路单边故障。

排查：开 `NCCL_DEBUG=INFO`；用 `py-spy dump` / `gdb` 抓各 rank 栈，看大家卡在哪个集合算子；对比是不是只有某几个 rank 卡住。

## 7. 训练稳定层坑点（L5）：3D 并行与稳定性

### 7.1 3D 并行配置约束（Megatron-DeepSpeed）

总卡数被三个维度切分：

$$
\text{world\_size} = \text{TP} \times \text{PP} \times \text{DP}
$$

例如 2 机 16 卡，设 `TP=2, PP=2`，则 $\text{DP} = 16 / (2\times2) = 4$。坑：
- **`TP×PP×DP` 必须整除总卡数**，否则启动直接报错。
- **`num_layers` 必须能被 PP 整除**（每个 pipeline stage 分到整数层）。
- **`hidden_size`/`num_heads` 要能被 TP 整除**（张量按列/行切分）。
- DeepSpeed ZeRO stage 与 PP 的组合有约束：常见做法是 **ZeRO-1 + TP + PP**（即仓库 README 验证过的 3D 并行）；ZeRO-2/3 与 PP 同开要谨慎，容易冲突。

```
   2机16卡, TP=2 PP=2 DP=4 的 rank 映射(示意)
   PP stage0 ───────────────► PP stage1
   ┌─ TP组(2) ─┐  ┌─ TP组(2) ─┐
   DP0: r0 r1      r8  r9
   DP1: r2 r3      r10 r11
   DP2: r4 r5      r12 r13
   DP3: r6 r7      r14 r15
   竖向DP做梯度all-reduce, 横向PP传激活, 组内TP做all-reduce
```

### 7.2 OOM（显存炸）

- 减小 `micro_batch_size`，靠**梯度累积**维持 `global_batch_size`。
- 开**激活重计算**（activation/gradient checkpointing，仓库脚本里的 `--deepspeed-activation-checkpointing`）：用算力换显存。
- 提高 TP 或用更高 ZeRO stage 切分状态。
- 注意 **PP 的流水线气泡 + 各 stage 显存不均**：第一个/最后一个 stage 常更吃显存（含 embedding/loss）。

### 7.3 loss spike / 训练发散

H800 BF16 训练长跑中偶发 loss 突刺或 NaN。常见处理：
- 开 **梯度裁剪** `GRAD_CLIP=1`（脚本已有）。
- 学习率/warmup 配置：`LR_WARMUP_STEPS` 给足，避免初期梯度过大。
- BF16 比 FP16 数值范围大、更稳，H800 优先 BF16（仓库 DS 配置 `bf16.enabled=true`）。
- 出现 spike 时**从最近 checkpoint 回滚 + 跳过坏数据 batch**，比硬训更省时间。

### 7.4 Checkpoint 保存/加载

- 多机存 ckpt 要落到**所有 rank 都能访问的共享存储**（NFS/并行文件系统），否则 resume 时找不到分片。
- 改变并行度（TP/PP）后不能直接 resume，需要用转换工具重切（仓库 README 提供 `deepspeed_to_megatron.py` 等转换路径）。
- 存盘 I/O 慢会拖慢训练，注意存储带宽与存盘频率的权衡。

## 8. 排查方法论：二分 + 最小复现

遇到「多机训练有问题」，按下面顺序二分，**每步缩小一半范围**：

```
1) 单机单卡能跑? ── 否 → 是代码/环境(L1)问题，与多机无关
        │是
2) 单机8卡能跑且快? ── 否 → 机内NVLink/NCCL(L2/L4)问题
        │是
3) 两机起得来(world_size对)? ── 否 → 启动/会合(L3)问题
        │是
4) 两机能通信不hang? ── 否 → NCCL/IB(L4)，开NCCL_DEBUG=INFO
        │是
5) 两机吞吐≈单机×机数? ── 否 → 没走IB/GDR(L2/L4)或并行配置(L5)
        │是 → 收工
```

配套：始终保留一个**最小可复现脚本**（小模型、2 机、几步就停），出问题先在它上面验证，再回大作业，避免在 70B 大作业上反复试错烧机时。

## 常见问题/坑（表格）

| 现象 | 可能根因 | 排查/解决 |
|---|---|---|
| 多机比单机慢很多 | NCCL 走了 Socket 没走 IB | `NCCL_DEBUG=INFO` 看传输路径；检查 IB 设备透传、`NCCL_SOCKET_IFNAME` |
| `RendezvousConnectionError` 心跳失败 | master 端口不可达/被占/抖动/某 rank 先死 | ping+端口连通性、用 IP、放大超时、查真凶 rank 日志 |
| 训练 hang 不报错 | 集合通信 rank 没对齐 / 某 rank 崩了 | `py-spy dump` 抓栈；查代码是否各 rank 分支不一致 |
| 启动 world_size 不对 | 多机 `NODE_RANK` 重复或 `MASTER_ADDR` 不一致 | 每机 NODE_RANK 唯一连续，MASTER_ADDR 全指 node0 |
| `bus error` / shm 相关 | 容器 `--shm-size` 太小 | 加大 shm、`--ipc=host`、`memlock=unlimited` |
| GDR 没生效（隐性慢） | GPU 与网卡不同 NUMA / 模块没加载 | 装 `nv_peer_mem`，检查 `NCCL_NET_GDR_LEVEL` 日志 |
| 启动即报并行度错 | `TP×PP×DP` 不整除总卡 / 层数不被 PP 整除 | 重算并行度，调 TP/PP/层数 |
| BF16 长跑 loss NaN | 数值发散 / 坏数据 | 梯度裁剪、warmup 给足、回滚 ckpt 跳坏 batch |
| RoCE 环境性能崩 | 无损网络 PFC/ECN 没配 | 配 PFC/ECN，设对 `NCCL_IB_GID_INDEX` |
| 各机行为不一致偶发 hang | 镜像/代码/依赖不一致 | 同一镜像 + 共享存储分发，保证逐字节一致 |
