## 0. 一句话锚点

把分布式训练拆成三个互相耦合的子问题，自动并行就是**同时**自动决策它们：

```
              自动并行要解的三件事
   ┌──────────────┬──────────────┬──────────────┐
   │  切分(How)   │  放置(Where) │  组合(Which) │
   │ 张量沿哪个维 │ 子计算放到哪 │ 多种基础并行 │
   │ 度切成几份   │ 些设备/mesh  │ 如何复合     │
   └──────────────┴──────────────┴──────────────┘
              ↓ 目标：最小化端到端 step 时间 / 显存达标
        argmin_config ( T_compute + T_comm + 重叠收益 )
```

## 1. 地基：手工并行的三种基础切法（前置）

自动并行要自动选的，本质就是把下面这三种「基础并行」自由复合。先把它们的内存/通信特征记牢，否则看不懂代价模型在算什么。

| 基础并行 | 切什么 | 通信内容 | 显存收益 | 典型瓶颈 |
|----------|--------|----------|----------|----------|
| 数据并行 DP | 切 batch（sample 维） | 梯度 AllReduce | 激活省，参数不省（除非 ZeRO） | 大模型参数放不下 |
| 张量并行 TP | 切权重的 hidden/head 维 | 前反向 AllReduce/AllGather | 参数+激活都省 | 通信频繁，须高带宽（NVLink） |
| 流水并行 PP | 按层切（模型纵向） | 层间 P2P（激活/梯度） | 参数按层省 | 流水气泡 bubble |

> 关键洞察（原文 *One weird trick* 给出的直觉）：**不同的层适合不同的并行方式**。卷积层「数据比参数大」→ 适合数据并行；全连接层「参数比数据大」→ 适合模型并行。这一句就是「为什么需要自动并行」的最早动机——既然每一层最优切法不同，整网就不该用同一种并行。

```
   卷积层(数据>>参数)            全连接层(参数>>数据)
   ┌──┬──┬──┬──┐               ┌────────────────┐
   │D0│D1│D2│D3│ 切 batch       │  W 切到 4 张卡  │ 切 weight
   └──┴──┴──┴──┘               └──┬──┬──┬──┬─────┘
   数据并行省激活               模型并行省参数
```

## 2. 自动并行之难（原文三大难点，逐条拆原子）

原文把「自动并行之难」概括为三个方面，这是全文最有价值的判断，原样保留并补足「为什么难」。

### 2.1 多样性（Diversity）—— 没有银弹

- **并行方式多样**：即使是同一个算子，不考虑混合，光基础并行方式之间就有显著差异，导致**不同的内存开销、通信代价、计算效率**。
- **模型多样**：模型架构层出不穷，伴随不同配置（序列长度、层数、隐层宽度），造成**计算负载差异**。
- **硬件多样**：用户面对差异化集群——不同**内存容量、通信带宽、计算能力**。

> 推论：因为这三层多样性叠加，**没有哪种并行技术总能拿到最佳效率**，所以「自动并行」才成为核心挑战。这就是搜索空间存在的根因。

### 2.2 复杂性（Complexity）—— 组合爆炸

同一个算子可以**同时**叠加多种基础并行（= 混合并行）。再叠上大模型计算图「结构非常庞大、集群规模也大」，若对**每个算子**都去探索（选哪些计算资源 + 设计混合并行），搜索空间是组合爆炸的：

```
   每算子可选切法 k 种,  共 N 个算子
   朴素搜索空间 ≈ k^N   ←  N 上千、k 数十 时天文数字
   ⇒ 必须靠 剪枝 + 动态规划 + 等价类合并 压缩
```

举个数值直觉：若 $k=10$、$N=100$，则 $10^{100}$，宇宙原子数（约 $10^{80}$）都装不下——这就是为何**必须**有剪枝策略，不能暴力枚举。

### 2.3 实用性（Practicality）—— 代价模型要准、搜索要快

- **代价模型要准**：搜索时必须给出**比较精确的内存/通信/计算开销**，否则「结果与实际执行偏差过大 → 次优解甚至根本不可用」。→ 需要对不同模型结构和硬件条件精准建模。
- **搜索本身要快**：自动并行带来的**额外时间开销必须可接受**，过于高昂的搜索代价同样无法接受。

> 一句话：自动并行 = 在一个爆炸的空间里，用一个**够准但够快**的代价模型，做一次**够快**的搜索。三者互相拉扯，是工程上最难平衡的点。

## 3. 一切并行都是「张量切分」（统一抽象）

原文（*Exploring Hidden Dimensions*）做出的关键抽象升级：**数据并行、模型并行只是张量切分方式的不同**——有的切数据维，有的切模型维。对多维张量，在不同维度切，效果也不同。

```
   一个激活/权重张量的可切维度（举例 4D）
   ┌─────────────────────────────────────┐
   │ sample(N) │ channel(C) │ H │ W       │
   └────┬───────────┬────────┬───┬────────┘
     切N=数据并行  切C=模型并行  切空间维=另一种并行
        每一种切法 = 一个 configuration(构型)
```

于是「寻找最优并行」被**形式化为一个搜索问题**：在所有构型组成的「构型空间」里搜出最优构型。这就是几乎所有自动并行工作的共同骨架。

## 4. 自动并行的通用流程（这篇脉络勾勒的「基本框架」）

原文判断：*Exploring Hidden Dimensions* 这篇「勾勒了自动并行的基本框架，很多解决自动并行的工作都是这样一个流程」。把它显式画出来：

```
   ┌────────────┐   ┌─────────────┐   ┌──────────────┐   ┌──────────┐
   │ 1.定义      │ → │ 2.构造       │ → │ 3.代价模型    │ → │ 4.搜索+剪枝│
   │ 搜索空间    │   │ 候选构型     │   │ 估开销(内存/  │   │ 出近最优  │
   │(每张量可切维)│   │(切法×放置)   │   │ 通信/计算)    │   │ 构型      │
   └────────────┘   └─────────────┘   └──────┬───────┘   └─────┬────┘
                                              │                 │
                              代价可来自: 解析公式 / 真机profiling / 模拟器
                                                                ↓
                                                       生成分布式执行计划
```

代价模型怎么来？三种路线，越往后越准也越慢：

| 路线 | 怎么估 | 准确性 | 速度 | 代表 |
|------|--------|--------|------|------|
| 解析公式 | FLOPs/带宽公式直接算 | 中 | 快 | 多数早期工作 |
| 模拟器 simulator | 模拟一次执行算 step 时间 | 高 | 中 | **FlexFlow** 的 execution simulator |
| 真机 profiling | 实际跑小段测 | 最高 | 慢 | 混合方案常用 |

## 5. 经典论文演进脉络（原文真料逐篇编排）

> 下面每条都来自原文，按「半自动 → 全自动」的演进顺序重排，并补一句它**新增了什么**。

### 5.1 One weird trick for parallelizing CNN
- **真料**：发现不同层适合不同并行——卷积层数据>参数→数据并行；全连接层参数>数据→模型并行。
- **意义**：提出「分层异构并行」的最初直觉（见 §1）。

### 5.2 Exploring Hidden Dimensions in Parallelizing CNN
- **真料**：① 抽象升级——DP/MP 都是张量切分；多维张量在 sample/channel/width/length 等维度切效果不同。② 把找最优并行**形式化为构型空间搜索**。③ 引入**代价模型**衡量构型优劣 + 一系列**搜索空间剪枝策略** + 实现原型系统。
- **意义**：勾勒了自动并行的**基本框架**（见 §4），后续工作多沿此流程。

### 5.3 FlexFlow — *Beyond Data and Model Parallelism for DNN*
- **真料**：提出 **execution simulator** 来完善 cost model。
- **意义**：把「代价怎么估准」从静态公式推进到**执行模拟**，对应 §4 表里的「模拟器」路线。FlexFlow 提出 SOAP 四维切分空间（Sample / Operation / Attribute / Parameter），覆盖比纯 DP/MP 更广。

### 5.4 Tofu
- **真料**：① 提出一套 **DSL** 方便开发者描述张量划分策略；② 用类似 poly 的 **integer interval analysis** 描述并行策略；③ 在并行策略**搜索算法**上做了很多有特色工作。
- **关注点差异（原文重点判断）**：Tofu 关注的是 **operator 的划分**，其它工作关注 **tensor 的划分**——二者等价，但作者认为**放在 tensor 划分上更好**：不需要用户改 operator 实现；Tofu 需要在 DSL 里描述 operator 的实现方式。
- **意义**：引出 §6「接口放算子上还是张量上」这个 API 哲学之争。

### 5.5 Mesh-TensorFlow
- **真料**：核心理念是 **beyond batch splitting**——数据并行是 batch splitting，模型并行是张量**其它维度**的切分。把集群加速卡抽象成 **mesh** 结构，提出把张量切分并映射到 mesh 的办法。
- **意义**：「设备 mesh」抽象成为后来 GSPMD/Alpa 的基础设施。

```
   把 N 张卡抽象成二维 device mesh（如 2×4=8 卡）
        dim_x →
   dim_y  ┌──┬──┬──┬──┐
     ↓    │g0│g1│g2│g3│   张量某一维沿 dim_x 切4份
          ├──┼──┼──┼──┤   另一维沿 dim_y 切2份
          │g4│g5│g6│g7│   = 一次性表达 2D 混合并行
          └──┴──┴──┴──┘
```

### 5.6 GShard
- 原文此处未展开。一句补全：GShard 在 Mesh 抽象上引入**轻量标注（sharding annotation）**，让用户只标少量张量切分意图、由编译器把切分传播到整图——MoE 超大模型的早期自动切分代表（详见 [[llm-algo/moe/README]] 的并行讨论）。

### 5.7 GSPMD
- 原文此处未展开。一句补全：GSPMD 把 GShard 的标注式切分推广为**通用 SPMD 编译 pass**——给少量张量加 sharding spec，编译器自动**传播**到全图并插入通信，是「半自动」（人标少量、机器补全）的代表。

## 6. 接口该放在算子上还是张量上？（原文的 API 哲学）

这是原文一个非常有价值的工程对照：同样实现了完整 DP/MP 的通用框架，划分接口放的位置不同，用户体验天差地别。

| 框架 | 接口放在 | 用户要做什么 | 单卡 vs 分布式代码 |
|------|----------|--------------|--------------------|
| **MindSpore** | **operator 上** | 在算子上标切分策略（如盘古示例） | operator API 不同 |
| **OneFlow** | **tensor 上（SBP 体系）** | 给张量标 SBP 属性 | **operator API 单卡/分布式完全一样** |

```
   算子级标注(MindSpore)          张量级标注(OneFlow SBP)
   op.shard(strategy=...)         x.to_global(sbp=S(0)/B/P, ...)
        ↑ 改的是算子调用              ↑ 改的是张量属性, 算子调用不动
   迁移分布式要动 op 代码         单卡代码加张量标注即可分布式
```

> SBP 是 OneFlow 的核心抽象：**S**plit（按某维切）/ **B**roadcast（每卡一份完整副本）/ **P**artial（每卡持部分和、需 AllReduce 才完整）。把张量的「分布状态」类型化后，编译器能自动推导算子间需要插入哪种集合通信（对应 [[ai-infra/网络/集合通信原语]] 的 AllReduce/AllGather/ReduceScatter）。

## 7. 全自动并行：Alpa 与 Unity

原文将 **Alpa**、**Unity** 归入「全自动并行」一节（标题保留）。补一句各自定位：

- **Alpa**：把并行分成**两层**——层内（intra-op，TP 类切分，用整数规划求解）+ 层间（inter-op，PP 类切分，用动态规划求解），分层求解压缩了 §2.2 的组合爆炸，是「自动混合并行」的标杆。
- **Unity**：把代数变换（algebraic transformation）与并行化**联合搜索**，统一在一个优化空间里同时考虑「算子怎么改写」和「怎么切」。

```
   Alpa 的两层分解（化解组合爆炸的工程手法）
   ┌─────────────── inter-op (DP求解) ───────────────┐
   │  stage0          stage1          stage2         │ ← 流水切层
   │ ┌─intra-op─┐   ┌─intra-op─┐   ┌─intra-op─┐      │
   │ │ TP/DP    │   │ TP/DP    │   │ TP/DP    │      │ ← 层内ILP求解
   │ └──────────┘   └──────────┘   └──────────┘      │
   └─────────────────────────────────────────────────┘
```

## 常见问题 / 坑

| 现象 / 误区 | 根因 | 对策 |
|-------------|------|------|
| 搜出的方案上机比预测慢很多 | 代价模型不准（§2.3 实用性） | 用 simulator/真机 profiling 校准；建模通信重叠 |
| 搜索几小时都不收敛 | 组合爆炸（§2.2），未剪枝 | 等价类合并 + 动态规划 + 分层求解（Alpa 思路） |
| 以为有一种「最好」的并行 | 忽视多样性（§2.1） | 不同层/模型/硬件最优切法不同，必须按场景搜 |
| 把 DP 和 TP 当成两回事各调各的 | 没意识到都是张量切分（§3） | 统一到「张量沿哪个维度切」的构型抽象下联合搜 |
| 改分布式要重写一堆算子代码 | 接口放在 operator 上（§6） | 选张量级标注体系（OneFlow SBP），算子代码不动 |
| 只切 batch（只会 DP） | 停留在 batch splitting | beyond batch splitting：切 hidden/head 等其它维（Mesh-TF） |
| 显存够但通信打满 | 切法把高频通信压在低带宽链路上 | 把 TP 放进 NVLink 域，PP 走机间，匹配拓扑（[[ai-infra/网络/InfiniBand]]） |
