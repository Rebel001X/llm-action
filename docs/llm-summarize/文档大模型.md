## 0. 一句话锚点

**文档大模型 = 检索（Retrieval） + 生成（Generation）。**

大模型（LLM）本身只会"凭记忆"答题，记忆来自训练语料、且固定不变。文档大模型给它外挂一个"可随时更新的资料库"：用户提问时，先从你自己的文档库里**检索**出最相关的几段，再把这几段连同问题一起塞进 prompt，让 LLM **基于给定材料**回答。

> 关键洞察：整套系统的天花板，**90% 由"检索得准不准"决定**，而不是由 LLM 多大决定。所以工程重心是训练一个好的 **Embedding 模型（召回）+ Rerank 模型（精排）**——这正是本文已有流程（bge / sentence-transformer / stella）的核心。

本仓库该文件原始的 8 步流程，本质就是**"如何用你自己的文档，微调出一个会找对文档的检索模型"**：

```
1. 文档切 chunk → 入库
2. 用 LLM(qwen) 按 chunk 生成"问题"          ← 自动造 (query, doc) 正样本
3. sentence-transformer(stella) 算 embedding,
   query↔doc 相似度 < 0.5 的对 丢掉           ← 数据清洗
4. 选 1 正样本 + 15 负样本                     ← 对比学习样本组装
5. BERT 长度 512→1024, 层次分解位置编码初始化   ← 扩上下文 (bge-large)
6. 训练检索模型 (bge)                          ← 对比学习微调
7. 校验: 取 query 命中的 top-3 文档及分数 + 标准答案
8. 算 ROUGE 指标                              ← 评估
```

## 1. 地基：为什么"光有大模型"不够？

三个硬约束，每一个都直接逼出"检索"这个动作：

```
约束①  上下文窗口有限
  ┌─────────────────────────────────────────┐
  │  你有 50 万字的内部文档                    │
  │  LLM 一次最多吃 8k~128k token             │
  │  → 塞不下，必须先"挑出相关的几段"          │
  └─────────────────────────────────────────┘

约束②  幻觉 (Hallucination)
  问:"公司2024年差旅报销上限?"
  纯LLM: "一般是500元/天" ← 编的, 它没见过你的制度
  RAG:  先检索到《报销制度v3》→"800元/天"→照抄, 可溯源

约束③  知识时效
  LLM 训练截止 2023.x, 你昨天改的文档它不知道
  → 文档库随时更新, 检索即时拿到最新版
```

**结论**：与其把所有知识"烧"进模型参数（贵、慢、易过时），不如把知识放在外部库里**按需检索**。这就是 RAG（Retrieval-Augmented Generation）。

## 2. 全景流水线

分两个阶段：**离线（建库 + 训练检索模型）** 和 **在线（用户提问）**。

```
============ 离线 OFFLINE（建索引 / 训练）============

  原始文档(PDF/表格/Word)
        │  ① 解析 + 切分
        ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ chunk 1  │  │ chunk 2  │  │ chunk N  │   ← 每块 ~256~512 token
   └────┬─────┘  └────┬─────┘  └────┬─────┘
        │ ③ Embedding 模型 (bge/stella)
        ▼              ▼              ▼
     [向量1]        [向量2]   …    [向量N]      ← d=1024 维浮点
        └──────────────┴──────────────┘
                       │ 写入向量数据库 (FAISS/Milvus)
                       ▼
                 ┌───────────────┐
                 │  Vector DB    │  (HNSW/IVF 索引)
                 └───────────────┘

  [训练支线] ② LLM 按 chunk 造问题 → ③ 相似度过滤
            → ④ 组 1正+15负 → ⑥ 对比学习微调 Embedding

============ 在线 ONLINE（推理）============

  用户 query
     │ Embedding(同一个模型)
     ▼
  [query 向量]──ANN 检索──► top-k chunk (粗召回, k≈50)
                              │ ⑧ Rerank 精排
                              ▼
                          top-3 chunk
                              │ ⑨ 填入 prompt 模板
                              ▼
        ┌──────────────────────────────────────┐
        │ 已知材料:{chunk1}{chunk2}{chunk3}      │
        │ 问题:{query}                          │──► LLM ──► 答案
        │ 请仅依据材料作答                       │
        └──────────────────────────────────────┘
```

> 注意：**离线和在线必须用同一个 Embedding 模型**，否则 query 向量和 doc 向量不在同一空间，相似度无意义。

## 3. Chunk 切分：怎么切、切多大

### 3.1 为什么要切

- 文档太长 → 一个向量装不下语义（信息被平均稀释）。
- 检索粒度要"刚好够答一个问题"：太大噪声多，太小语义不全。

### 3.2 切分策略

```
  策略A 定长滑窗(fixed + overlap)         策略B 语义/结构切分
  ┌────────────────────────┐            按 标题/段落/句子 边界切
  │ chunk = 512 token       │            ┌──── # 一级标题 ────┐
  │ overlap = 50 token      │            │  ## 报销标准        │  ← 一块
  └────────────────────────┘            │  正文…              │
   ▼ 滑窗示意 (overlap 防截断语义)         └────────────────────┘
   [0────512]
        [462──974]   ← 与上一块重叠 50
              [924──1436]
```

**overlap 的作用**：防止一个完整句子/答案被切在两块边界，两边都不完整。代价是存储和向量数变多。

### 3.3 切多大？数值直觉

设答案平均长度 ~80 token，问题相关上下文 ~200 token：

- chunk=128：可能装不下完整上下文 → 召回时答案被拦腰截断。
- chunk=512：覆盖完整段落，**多数 QA 场景的默认值**。
- chunk=1024：上下文全但噪声多，向量语义被稀释，检索精度↓。

> 经验：**256~512 token 是 QA 文档检索的甜区**。本文件流程把 BERT 编码长度从 512 扩到 1024（第 5 步），就是为了让"长 chunk / 长 query"也能被完整编码。

## 4. Embedding 向量化：双塔 + 池化 + 相似度

### 4.1 双塔（Bi-Encoder）结构

query 和 doc **各自独立**过同一个编码器，得到两个向量，再算相似度。好处：doc 向量可**离线预计算**入库，在线只需编码 query（快）。

```
   query "差旅上限?"        doc "差旅报销上限800元/天…"
        │                          │
   ┌────▼────┐                ┌────▼────┐
   │ BERT/bge │  ← 同一套权重 → │ BERT/bge │
   └────┬────┘                └────┬────┘
        │  [CLS]/mean pooling       │
        ▼                          ▼
   q ∈ ℝ^1024              d ∈ ℝ^1024
        └──────── cos(q,d) ────────┘   相似度分数
```

### 4.2 池化（Pooling）：token 向量 → 句向量

BERT 输出是每个 token 一个向量 $H \in \mathbb{R}^{L \times d}$。要变成一个句向量，常用两种：

- **[CLS] 池化**：取第 0 个 token 的向量。
- **Mean 池化**（bge/stella 常用）：对所有有效 token 求平均：

$$ v = \frac{1}{\sum_i m_i}\sum_{i=1}^{L} m_i \cdot H_i $$

其中 $m_i$ 是 attention mask（padding 位为 0）。

### 4.3 相似度：余弦 / 内积

$$ \cos(q,d) = \frac{q \cdot d}{\|q\|\,\|d\|} = \frac{\sum_i q_i d_i}{\sqrt{\sum q_i^2}\sqrt{\sum d_i^2}} $$

**手算示例**（取 3 维便于演示，真实是 1024 维）：

```
 q = [0.6, 0.8, 0.0]      d_正 = [0.5, 0.7, 0.1]    d_负 = [-0.2, 0.1, 0.9]
 q·d_正  = 0.6*0.5+0.8*0.7+0=0.30+0.56 = 0.86
 |q| = √(0.36+0.64+0) = √1.0 = 1.0
 |d_正| = √(0.25+0.49+0.01)=√0.75 = 0.866
 cos(q,d_正) = 0.86 / (1.0*0.866) = 0.993   ← 很相关 ✓ (>0.5 保留)

 q·d_负 = 0.6*(-0.2)+0.8*0.1+0 = -0.12+0.08 = -0.04
 |d_负| = √(0.04+0.01+0.81)=√0.86=0.927
 cos(q,d_负) = -0.04/(1.0*0.927) = -0.043  ← 不相关 ✓ (<0.5 丢弃)
```

> 这就是第 3 步"过滤阈值 0.5"在做的事：把自动生成的 (query, doc) 对里**语义对不上的脏数据剔掉**，避免毒化训练。

## 5. 自动造训练数据：用 LLM 生成问题

没有人工标注怎么办？**让大模型(qwen)读 chunk，反向生成"这段能回答的问题"**，自动得到 (query, doc) 正样本对。

```
  chunk: "员工差旅住宿费报销上限为每天800元,需提供发票。"
            │  prompt: "针对以下文档生成3个用户可能提的问题"
            ▼  qwen
  Q1: "差旅住宿一晚最多能报多少?"
  Q2: "报销住宿费需要什么凭证?"
  Q3: "差旅报销上限是多少?"
            │
  → 每个 (Qi, chunk) 就是一条候选正样本
```

**为什么还要第 3 步的相似度过滤？**
LLM 偶尔会生成"跑题问题"或问题里混入了 chunk 没有的信息。用一个**已有的 embedding 模型(stella)** 先算 cos(Qi, chunk)，< 0.5 的直接丢——这是"自蒸馏 + 数据清洗"，保证训练对干净。

```
  生成 100k 候选对  ──相似度过滤──►  保留 ~65k 高质量正样本
  （阈值0.5）            （丢掉跑题/低质 35%）
```

## 6. 正负样本与对比学习（核心训练）

### 6.1 1 正 + 15 负

对每个 query，构造：
- **1 个正样本**：它真正对应的 chunk。
- **15 个负样本**：其它不相关的 chunk。

负样本两种来源：

```
  ┌── 易负 (Easy / In-batch) ──┐   ┌── 难负 (Hard negative) ──┐
  │ 同 batch 里别人的正样本     │   │ BM25/向量检索召回的"看着像 │
  │ 几乎免费, 语义差很远        │   │ 但其实不对"的 chunk        │
  │ 模型一眼区分 → 信号弱       │   │ 逼模型学细粒度区分 → 信号强 │
  └────────────────────────────┘   └──────────────────────────┘
```

> 难负样本是检索模型训练的"题眼"：只有靠近边界的负样本才提供有效梯度。

### 6.2 InfoNCE 对比损失

对一个 query $q$，正样本 $d^+$，负样本集合 $\{d^-_1,\dots,d^-_{15}\}$，损失：

$$ \mathcal{L} = -\log \frac{\exp(\text{sim}(q,d^+)/\tau)}{\exp(\text{sim}(q,d^+)/\tau) + \sum_{j=1}^{15}\exp(\text{sim}(q,d^-_j)/\tau)} $$

其中 $\tau$ 是温度（典型 0.02~0.05），$\text{sim}$ 用余弦。直觉：**把正样本拉近、把 15 个负样本推远**。

```
        训练前                      训练后
     d⁻ d⁻  q  d⁺            d⁻ d⁻ d⁻      q d⁺   ← q,d⁺ 贴一起
        d⁻ d⁺  d⁻        →      d⁻   d⁻   d⁻      ← 负样本被推开
       (混在一起,难检索)         (正样本在 q 旁边,一查就中)
```

### 6.3 损失逐数手算

设 $\tau=0.05$，相似度（已算好）：$\text{sim}(q,d^+)=0.9$，15 个负样本都约 $0.2$。

```
 正项 logit  = 0.9/0.05 = 18.0   → exp(18.0) ≈ 6.566e7
 单负 logit  = 0.2/0.05 = 4.0    → exp(4.0)  ≈ 54.6
 15个负 之和 = 15 * 54.6 ≈ 819

 分母 = 6.566e7 + 819 ≈ 6.566e7
 softmax(正) = 6.566e7 / 6.566e7 ≈ 0.99998
 L = -ln(0.99998) ≈ 1.2e-5   ← 已学好, loss≈0
```

再看**学不好**的情况：正负相似度都 0.5 → 正项 exp(10)=22026，分母=22026*16，softmax=1/16=0.0625，L=-ln(0.0625)=2.77（高 loss，需继续学）。

> 温度 $\tau$ 越小，softmax 越"尖锐"，对难负样本越敏感，但太小训练不稳。

## 7. 扩长上下文：512 → 1024 与层次分解位置编码

### 7.1 为什么要扩

原生 BERT 的位置编码表只有 512 行（`position_embeddings[512, d]`），输入超过 512 token 就没有对应的位置向量。但 chunk / query 可能更长，故需扩到 1024。

```
  原表 (512 行)            目标 (1024 行)
  pos 0   ──► e₀          pos 0..511   保留原值
  pos 1   ──► e₁          pos 512..1023 新增, 怎么初始化?
  ...                     ▲
  pos 511 ──► e₅₁₁        └─ 随机初始化会"撕裂"已学好的语义
```

### 7.2 层次分解（Hierarchical Decomposition）初始化

把一个长位置 $p$ 拆成"块号 × 块大小 + 块内偏移"，用原 512 表里的两个向量组合出新位置：

$$ p = u \cdot m + v \qquad (0 \le v < m) $$

新位置向量 $= \alpha \cdot e_u + (1-\alpha)\cdot e_v$（$e$ 取自原 512 表）。这样**新位置不是凭空随机**，而是由已学好的低位置向量平滑插值/组合得到，下游能直接复用、收敛快。

```
  pos=700, 设 m=512:
   u = 700 // 512 = 1     v = 700 % 512 = 188
   新 e₇₀₀ = α·e₁ + (1-α)·e₁₈₈   ← 全部来自原表, 平滑可微调
```

> bge-large 等模型扩长就用这类技巧（Su 等的"层次分解位置编码"），关键是**用结构化插值替代随机初始化**，保住预训练语义。与 RoPE 的"无表外推"是两条不同的扩长思路，见 [[llm-algo/旋转编码RoPE]]。

## 8. 检索与 Rerank：召回 + 精排两段式

### 8.1 为什么两段

```
  全库 100 万 chunk
        │ ① 召回(Recall): 向量 ANN, 快但粗
        ▼
     top-50 候选          ← 双塔, 一次算完, 毫秒级
        │ ② 精排(Rerank): cross-encoder, 慢但准
        ▼
     top-3 最终           ← query+doc 拼一起进模型, 算 50 次
```

- **双塔召回**：query/doc 独立编码，只算一次 query，库里向量预存 → 极快，但 query 和 doc 没交互，精度有上限。
- **Cross-Encoder 精排**：把 `[query][SEP][doc]` 拼起来过一遍模型，token 级交互 → 准，但每个候选都要跑一次模型，只能用在小集合（top-50）。

```
  双塔(Bi)                     交叉(Cross)
  q→[enc]→qv ┐                 [q;d]→[enc]→score
  d→[enc]→dv ┘ cos             ▲ q,d 在层间充分 attention
  无交互, 可缓存                 有交互, 不可缓存
```

### 8.2 ANN 索引（向量库怎么快）

百万向量逐一算余弦太慢（$O(N)$）。向量库用近似最近邻：

- **IVF**（倒排）：先 k-means 把向量分 nlist 个簇，查询只搜最近几个簇。
- **HNSW**（图）：建多层跳表图，贪心走图，$O(\log N)$ 级。

> 代价是"近似"——可能漏掉真正最近的（召回率<100%），用 `nprobe`/`efSearch` 调精度-速度权衡。

## 9. 拼接进 LLM 生成

检索到 top-3 后，填进 prompt 模板交给生成模型：

```
  系统: 你是文档问答助手, 只能依据【已知材料】回答, 材料里没有就说"未找到"。
  已知材料:
    [1] {chunk_1}
    [2] {chunk_2}
    [3] {chunk_3}
  问题: {query}
  要求: 给出答案并标注引用编号 [1]/[2]。
```

**token 预算手算**（窗口 8192）：

```
  系统+模板        ≈  300 token
  3 个 chunk×512   ≈ 1536 token
  query           ≈   50 token
  ───────────────────────────────
  输入合计         ≈ 1886 token   → 还剩 ~6300 给输出, 充裕
```

> 若改成 top-10 chunk，输入 ≈ 5400 token，留给输出的余量骤减——这也是为什么**精排后只留 3 条**：省 token、降噪、压幻觉。

## 10. 评估：检索指标 + 生成指标

分两层评，缺一不可：

### 10.1 检索层（找得对不对）

设 query 的标准答案文档是 $d^*$，检索返回有序 top-k：

- **Recall@k**：top-k 里是否包含 $d^*$。
- **MRR（平均倒数排名）**：$d^*$ 排第几名，分数 $=1/\text{rank}$。

```
 5 个 query, d* 命中排名: 1, 2, 1, 5, 未命中(∞)
 Recall@3 = 命中前3的个数/总数 = (1,2,1命中, 5和∞没中) = 3/5 = 0.60
 MRR      = (1/1 + 1/2 + 1/1 + 1/5 + 0)/5
          = (1 + 0.5 + 1 + 0.2 + 0)/5 = 2.7/5 = 0.54
```

> 第 7 步"取 top-3 文档及分数 + 标准答案"就是在算这一层。检索层不达标，生成层再好也没用。

### 10.2 生成层（答得对不对）：ROUGE

ROUGE 比对"生成答案"与"标准答案"的 n-gram 重叠。**ROUGE-1** = 单词召回，**ROUGE-L** = 最长公共子序列。

**ROUGE-1 手算**：

```
 参考(标准): "差旅 住宿 上限 800 元"            (5 个词)
 生成:       "差旅 住宿 上限 是 800"            (5 个词)
 共现词(交集): 差旅, 住宿, 上限, 800  = 4 个

 Recall    = 命中/参考词数 = 4/5 = 0.80
 Precision = 命中/生成词数 = 4/5 = 0.80
 F1 = 2PR/(P+R) = 2*0.8*0.8/1.6 = 0.80   → ROUGE-1 = 0.80
```

**ROUGE-L（LCS）手算**：

```
 参考: 差旅 住宿 上限 800 元
 生成: 差旅 住宿 上限 是 800
 LCS = "差旅 住宿 上限 800" 长度 = 4
 R_lcs = 4/5 = 0.8, P_lcs = 4/5 = 0.8, F = 0.8 → ROUGE-L = 0.80
```

> ROUGE 只看字面重叠，对同义改写不友好；生产中常再叠加"LLM-as-judge"或语义相似度做补充评估。

## 数值手算：端到端资源估算

### A. 向量库存储

```
 文档总量 100 万 chunk, embedding 维度 d=1024, fp32(4字节)
 单向量 = 1024 * 4 = 4096 B = 4 KB
 总存储 = 1e6 * 4 KB = 4 GB (裸向量)
 → 用 fp16/int8 量化可降到 2GB / 1GB
 → HNSW 图额外 ~1.5x 内存开销
```

### B. 召回一次的算力

```
 暴力(brute force): 100万 * 1024 维点积 = 1e6 * 1024 ≈ 1e9 次乘加 / query
   单核 GFLOPS 量级要 ~秒级 → 太慢
 IVF(nlist=4096, nprobe=16): 只搜 16/4096 簇
   ≈ 1e9 * (16/4096) ≈ 4e6 乘加 → 毫秒级 ✓ (加速 ~256x)
```

### C. 微调 Embedding 模型的显存（bge-large, 0.3B 参数）

```
 参数  0.3B * fp16(2B)               = 0.6 GB
 梯度  0.3B * 2B                     = 0.6 GB
 Adam 优化器状态 (m,v) 0.3B*2*4B(fp32)= 2.4 GB
 ─────────────────────────────────────────────
 静态合计                            ≈ 3.6 GB
 + 激活值(batch=32,seq=512,1正15负):
   每条要编码 16 个 doc + 1 query = 17 段
   batch有效编码段 = 32*17 = 544 段, 激活随之放大
 → 单卡 24GB 显存足够, 但负样本越多激活越吃显存
```

> 对比学习的隐藏成本：**有效 batch = batch × (1正+负样本数)**。1 正 15 负意味着每步要编码 16 倍的 doc，这是显存和算力的主要消耗点。

## 常见问题

| 问题 | 答案 |
|------|------|
| 为什么不直接把所有文档塞进 128k 长上下文 LLM？ | 贵（token 费按量）、慢（attention $O(L^2)$）、且"大海捞针"召回率会塌；RAG 用检索先收敛到 3 段，便宜又准。 |
| 阈值 0.5 是定死的吗？ | 不是，是**数据清洗超参**。不同 embedding 模型/数据分布下可调（0.4~0.6），目的是剔除自动生成的脏对。以你的验证集 Recall 为准。 |
| 为什么 1 正配 15 负，不是 1:1？ | 检索是"从全库里挑一个"，天然是极端不均衡的多分类；负样本越多，InfoNCE 越接近真实检索难度，但受显存限制，16 是常见折中。 |
| 难负样本怎么挖？ | 用 BM25 或当前 embedding 召回 top-k，去掉正样本后剩下的高分项就是"看着像但不对"的难负样本。 |
| 双塔够了还要 Rerank 吗？ | 双塔无 query-doc 交互，精度有上限；Rerank 用 cross-encoder 补交互，通常 +5~15% 精度，代价是只能跑在 top-50 小集合上。 |
| ROUGE 高就代表答得好？ | 不一定，ROUGE 只看字面重叠，会漏判同义改写、误判抄材料。需配合检索指标 + 人工/LLM 评估。 |
| Embedding 必须自己训吗？ | 通用域可直接用开源 bge/stella；但**垂域（金融/医疗/法律）术语分布差异大，微调收益显著**，本流程正是为此。 |
| 在线和离线 embedding 模型能不一致吗？ | 绝对不能。query 和 doc 必须在同一向量空间，换模型必须**全库重新编码入库**。 |
