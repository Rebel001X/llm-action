## 0. 一句话锚点

千帆 = **把训练大模型的脏活（多卡调度、数据校验、断点续训、推理部署）藏到 UI/API 背后，你只填几个超参数就能跑通 SFT/LoRA/RLHF**。它不是新算法，而是把本仓库里讲过的 [[llm-train/peft/PEFT-API]]、[[llm-alignment/RLHF]]、[[llm-eval/README]] 这些技术**产品化封装**。读这篇的价值：透过平台的"填空界面"看懂背后每个旋钮在动什么。

## 1. 地基：LLMOps 的四段流水线

千帆把大模型生命周期切成四段，每段都有对应的本仓库知识点：

```
   数据         训练               评估            部署
 ┌──────┐   ┌────────────┐   ┌──────────┐   ┌──────────┐
 │ 清洗 │──▶│ SFT / LoRA │──▶│ 规则打分 │──▶│ 推理服务 │
 │ 标注 │   │ RM  / RLHF │   │ 人工评测 │   │ 弹性扩缩 │
 └──────┘   └────────────┘   └──────────┘   └──────────┘
            ↑本篇重点          ↑本篇重点        ↑ vLLM 那套
   原料        炼丹              验货            上货架
```

- **数据**：决定上限。原文强调"统一查看模型的训练状态，选择更适合的训练方式"，本质是让数据质量/数量来反推该用全量还是 LoRA。
- **训练**：本篇核心。平台给出 SFT（全量/LoRA/Prompt Tuning）、奖励模型(RM)、强化学习(RL) 四类入口。
- **评估**：自动规则打分（准确率/F1/ROUGE/BLEU）+ 人工/裁判模型。
- **部署**：对应 [[llm-inference/README]] 与 [[llm-inference/vllm/README]]，平台屏蔽了 KV-Cache/批处理细节。

> 为什么要平台？因为单卡跑不动 70 亿参数的全量微调（见第 3 节显存账），多卡编排 + 容错 + 监控是重复劳动，平台把这些固化成按钮。

## 2. 训练超参：每个旋钮在动什么

原文给出的训练核心概念表（**原料，原样保留**）：

| 概念名 | 描述 |
| --- | --- |
| 训练轮次 | Epoch，训练轮次可以由 步长 × 数据批大小 / 数据量 的形式换算。例如，1w 条样本在数据批大小为 32 的情况下，建议训练轮次至少设置为 2。 |
| 数据批 | Batch_size，即一次训练所抓取的数据样本数量，Batch_size 大小影响训练速度和模型的优化。 |
| 学习率 | Learning rate（LR），梯度下降更新权重时的超参数，过高难收敛、过低收敛慢，平台已给默认推荐值，可按经验调整。 |
| 全量更新 | 训练过程中对大模型的全部参数进行更新。 |
| Prompt Tuning | 固定预训练大模型参数，增加 prompt embedding 参数，训练中只更新 prompt 参数。 |
| LoRA | 固定预训练大模型参数，保留自注意力原始权重矩阵，对权重矩阵低秩分解，训练中只更新低秩部分参数。 |
| [奖励模型](https://cloud.baidu.com/doc/WENXINWORKSHOP/s/Bliu6p62v) | 训练的最终目的是刻画模型的输出在人类看来是否表现不错。 |
| [强化学习](https://cloud.baidu.com/doc/WENXINWORKSHOP/s/Bliu6p62v) | 又称再励/评价/增强学习，利用问题集质问奖励模型，合成问题最优解的应答。 |

### 2.1 Epoch / Batch / Step 三者关系（手算）

平台界面让你填 Epoch 和 Batch_size，背后自动算出 Step（迭代步数）。换算关系：

$$\text{Step}_{\text{per epoch}} = \left\lceil \frac{\text{数据量}}{\text{Batch\_size}} \right\rceil, \quad \text{总Step} = \text{Step}_{\text{per epoch}} \times \text{Epoch}$$

**用原文例子手算**：1w 条样本、Batch_size=32、Epoch=2：

$$\text{Step}_{\text{per epoch}} = \lceil 10000/32 \rceil = 313, \quad \text{总Step} = 313 \times 2 = 626$$

```
数据量 10000 条
 │   ┌── batch 1 (32条) ──┐
 │   ├── batch 2 (32条)   ├─ 走完 313 个 batch = 1 个 epoch
 │   └── ... batch 313 ───┘
 └─ 重复 2 个 epoch ──▶ 总 626 步反向传播
```

> 为什么"至少 2 轮"？1 万条对 70 亿参数太稀疏，单轮模型只"瞥了一眼"每条样本，欠拟合；轮次太多又过拟合。经验：小数据集(<1w)给 2~4 轮，大数据集(>10w)给 1~2 轮。

### 2.2 学习率：为什么有"预热"和"衰减"

原文 Baichuan2 参数表里出现了 `学习率调整计划`、`学习率预热步数占比`、`权重衰减数值`，它们共同刻画 LR 随时间的曲线：

```
 LR
  │        ╭─────╮ 峰值
  │       ╱       ╲___
  │      ╱            ╲____  ← 衰减(cosine/linear)
  │     ╱                  ╲___
  │ ___╱ ← 预热(warmup)        ╲
  └────┴──────────────────────────▶ step
      warmup     主训练
```

- **预热(warmup)**：开头 LR 从 0 慢慢爬到峰值。为什么？刚开始权重随机，大 LR 会让梯度爆炸/震荡；预热让模型"先适应数据"。占比通常 3%~10% 的总 step。
- **衰减(scheduler)**：后期 LR 降低，让模型在最优点附近"微调落位"而非来回跳。
- **权重衰减(weight decay)**：在损失里加 $\lambda \|W\|^2$ 正则项，抑制权重变大 → 防过拟合。典型 $\lambda \in [0.01, 0.1]$。

> 数值直觉：7B 全量微调常用峰值 LR $\approx 1\text{e-}5$；LoRA 因为只动小矩阵、可用更大 LR $\approx 1\text{e-}4 \sim 3\text{e-}4$。

## 3. 训练方式：全量 vs LoRA vs Prompt Tuning（显存账）

这是平台让你"选哪个单选框"的核心决策。本质区别 = **训练时更新多少参数**。

```
全量更新          LoRA              Prompt Tuning
┌─────────┐      ┌─────────┐       ┌─────────┐
│ ███████ │      │ ░░░░░░░ │       │ ░░░░░░░ │  ░=冻结
│ 全部解冻 │      │ +小三角 │       │ +前缀   │  █=训练
│ ███████ │      │  ▲ A,B  │       │  ▶ emb  │  ▲▶=新增可训练
└─────────┘      └─────────┘       └─────────┘
更新 100%        更新 ~0.1%~1%      更新 ~0.01%
```

| 方式 | 可训练参数占比 | 显存需求 | 效果上限 | 适用 |
| --- | --- | --- | --- | --- |
| 全量更新 | 100% | 最高（需存全部参数+梯度+优化器状态） | 最高 | 数据多、算力足、追极致 |
| LoRA | ~0.1%~1% | 低（只为低秩矩阵存梯度/优化器态） | 接近全量 | 主流选择，性价比最高 |
| Prompt Tuning | ~0.01% | 极低 | 一般 | 任务简单、显存极紧 |

**显存为什么差这么多**？Adam 优化器对每个可训练参数要存 参数本身 + 一阶动量 + 二阶动量 ≈ 3 份，再加梯度共 4 份 fp32。7B 全量微调：

$$7\text{B} \times 4\,\text{bytes} \times 4 \approx 112\,\text{GB}$$

单张 A100(80G) 装不下 → 必须多卡 [[ai-framework/deepspeed/README]] 切分。而 LoRA 只为低秩矩阵建优化器态，可训练参数从 70 亿降到几百万，显存骤降到单卡可跑（详见 [[docs/transformer内存估算]]）。

> 这正是平台默认推荐 LoRA 的原因：用户不必关心多卡，单机就能微调。

## 4. LoRA 三参数：rank / alpha / dropout 的几何意义

原文 Baichuan2 表给出 `loraRank`、`loraAlpha`、`loraDropout`，这是 LoRA 的全部旋钮。原理见 [[llm-train/peft/PEFT-API]]。

LoRA 把权重更新 $\Delta W$（一个 $d \times d$ 大矩阵）近似成两个瘦矩阵相乘：

$$W' = W + \Delta W = W + \frac{\alpha}{r} \cdot B A, \quad A \in \mathbb{R}^{r \times d},\; B \in \mathbb{R}^{d \times r}$$

```
       d 列
  ┌───────────┐         ┌─┐
  │           │   ≈   d │B│ × ┌───────────┐
d │  ΔW(d×d)  │         │ │ r └─────A(r×d)─┘
  │           │         └─┘   r 很小(如 8)
  └───────────┘
  参数 d²            参数 2·d·r  （r≪d 时省一两个数量级）
```

| 参数 | 原文说明 | 几何含义 | 调大的后果 |
| --- | --- | --- | --- |
| loraRank (r) | 数值越大 lora 参数越多 | 低秩矩阵的秩，表达能力 | r↑ → 能力↑、参数↑、易过拟合 |
| loraAlpha (α) | 缩放系数，越大影响力越大 | 控制 $\Delta W$ 注入强度，等效放大 LR | α↑ → 微调影响更强 |
| loraDropout | 防止 lora 训练过拟合 | 对 LoRA 路径随机置零 | dropout↑ → 正则更强、收敛更慢 |

**手算 scaling**：若 $r=8, \alpha=16$，则缩放因子 $\alpha/r = 16/8 = 2$，即 LoRA 分支的输出被放大 2 倍再加回主干。常见经验设 $\alpha = 2r$。典型起步：`r=8, alpha=16, dropout=0.05`。

> 坑：单独把 α 调大而 r 不变，等效于偷偷加大学习率，可能训飞。两者要协同调。

## 5. 对齐流水线：SFT → RM → RLHF 为什么是三步

原文表里的"奖励模型"和"强化学习"不是孤立功能，而是 RLHF 三段式的后两段（详见 [[llm-alignment/RLHF]]）：

```
① SFT          ② 奖励模型 RM           ③ 强化学习 RLHF/PPO
监督微调   ──▶  学"人类偏好打分"   ──▶  用 RM 当裁判优化策略
教模型说人话    给(好答案,差答案)对    模型生成→RM打分→PPO更新
```

- **① SFT**：用高质量问答对做监督微调，让模型先学会"按指令格式答题"。这是全量/LoRA 那一套。
- **② 奖励模型(RM)**：原文"刻画模型输出在人类看来是否表现不错"。给同一问题的多个回答排序，训练一个打分器 $R(x,y)$。损失是 pairwise ranking：

$$\mathcal{L}_{RM} = -\log \sigma\big(R(x, y_{\text{好}}) - R(x, y_{\text{差}})\big)$$

- **③ 强化学习(RL)**：原文"利用问题集质问奖励模型，合成最优解应答"。用 PPO 让策略模型最大化 RM 给的奖励，同时用 KL 散度拉住别偏离 SFT 太远：

$$\max_\theta \; \mathbb{E}\big[R(x,y)\big] - \beta \cdot \mathrm{KL}\big(\pi_\theta \,\|\, \pi_{\text{SFT}}\big)$$

> 为什么不能跳过 RM 直接 RL？因为"人类偏好"无法写成显式公式，必须先用 RM 把它**学**成一个可微的打分函数，RL 才有梯度可优化。轻量替代方案见 [[llm-alignment/DPO]]（直接用偏好对优化、省掉显式 RM）。

## 6. 模型评估：自动规则打分指标

原文评估表（**原料保留**），平台在验证集上自动算这些分：

| 指标名称 | 指标说明 |
| --- | --- |
| 准确率 (%) | 忽略停用词后，正确预测(标注与预测完全匹配)的样本数 / 总样本数 |
| F1 分数 (%) | 忽略停用词后，精确率和召回率的调和平均数 |
| ROUGE-1 (%) | 忽略停用词后，生成结果与标准结果按 unigram 拆分后的召回率 |
| ROUGE-2 (%) | 忽略停用词后，按 bigram 拆分后的召回率 |
| ROUGE-L (%) | 忽略停用词后，最长公共子序列的召回率 |
| BLEU-4 (%) | 忽略停用词后，unigram/bigram/trigram/4-gram 的加权平均 |

**注释**（原文保留）：
- Ⅰ) unigram：每个单词单独作为基本单元，不考虑顺序。
- Ⅱ) bigram：每个相邻单词对作为基本单元，描述两词顺序关系。
- Ⅲ) trigram：每三个相邻单词作为基本单元。
- Ⅳ) 4-grams：每四个相邻单词作为基本单元。
- Ⅴ) 最长公共子序列(LCS)：在每个字符串中都存在且顺序相同的最长子序列。

### 6.1 ROUGE vs BLEU：召回 vs 精确（手算）

```
       生成结果                标准答案
        ╲                      ╱
         ╲  匹配的 n-gram 数  ╱
          ▼                  ▼
ROUGE = 匹配 / 标准答案长度   ← 召回(参考被覆盖多少)
BLEU  = 匹配 / 生成结果长度   ← 精确(生成有多少是对的)
```

**手算 ROUGE-1**：标准答案 = "今天 天气 很 好"(4 词)，生成 = "今天 天气 不错"。匹配 unigram = {今天, 天气} 共 2 个。

$$\text{ROUGE-1} = \frac{2}{4} = 50\%$$

**手算 F1**：精确率 = 2/3（生成 3 词对 2 个），召回率 = 2/4，则

$$F_1 = \frac{2 \cdot P \cdot R}{P + R} = \frac{2 \cdot \frac{2}{3} \cdot \frac{1}{2}}{\frac{2}{3} + \frac{1}{2}} = \frac{2/3}{7/6} = \frac{4}{7} \approx 57.1\%$$

> 为什么生成类任务看 ROUGE/BLEU 而非准确率？因为"完全匹配"对开放式生成几乎永远是 0，n-gram 重叠才能给出连续可比的分数。

## 实操：Baichuan2-7B-Chat 真实参数表（原文真料）

> 单条数据支持 **4096 tokens**。Baichuan2-7B-Chat 是在约 **1.2 万亿 tokens** 上训练的 **70 亿参数**模型。

**支持的训练方法**：

| 训练方法 | 简单描述 |
| --- | --- |
| 全量更新 | 训练过程中对大模型的全部参数进行更新 |
| LoRA | 固定预训练参数，保留自注意力原始权重矩阵，对权重矩阵低秩分解，训练中只更新低秩部分参数 |

**参数配置（界面填空项，原样保留）**：

| 超参数 | 简单描述 |
| --- | --- |
| 迭代轮次 | epoch，控制训练过程中的迭代轮数 |
| 批处理大小 | Batchsize，每次迭代使用的样本数；较大可加速但可能 OOM |
| 学习率 | learning_rate，过高难收敛、过低慢，平台给默认推荐值 |
| 学习率调整计划 | 调整训练中学习率的变动方式（scheduler） |
| 学习率预热步数占比 | 训练初期逐渐增加学习率的比例，提高稳定性和性能（warmup） |
| 权重衰减数值 | 正则化技术，控制模型复杂性、减少过拟合（weight decay） |
| loraRank | 选 LoRA 时填，rank，数值越大 lora 参数越多 |
| loraAlpha | 选 LoRA 时填，缩放系数，系数越大 lora 影响力越大 |
| loraDropout | 选 LoRA 时填，Dropout 系数，防止 lora 训练过拟合 |
| 序列长度 | 单条样本最大长度；数据较短时调小可加快训练 |

**一份能跑通的起步配置（结合上文原理）**：

```
训练方式      : LoRA
迭代轮次      : 3            # 小数据集 2~4 轮
批处理大小    : 32
学习率        : 3e-4         # LoRA 可比全量(1e-5)大一个量级
学习率调整计划: cosine
预热步数占比  : 0.05         # 5% 总 step 用于 warmup
权重衰减      : 0.01
loraRank      : 8
loraAlpha     : 16           # 经验 alpha = 2 * rank
loraDropout   : 0.05
序列长度      : 1024         # 数据短就调小，省显存提速
```

> 序列长度从 4096 降到 1024 的收益：注意力是 $O(L^2)$，$L$ 减到 1/4，注意力计算量降到约 1/16，速度与显存双赢（前提是数据确实短）。原理见 [[llm-optimizer/FlashAttention]] 与 [[llm-optimizer/kv-cache]]。

## 常见问题/坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| Loss 不降/震荡 | 学习率过高 | 调小 LR，加大 warmup 占比 |
| 训练后泛化差(过拟合) | 轮次过多 / dropout 太小 / 数据太少 | 减 epoch、加 loraDropout、加 weight decay、扩数据 |
| 模型欠拟合、没学会 | 轮次太少 / LR 太低 / rank 太小 | epoch≥2、调大 LR、调大 loraRank |
| 显存 OOM | Batchsize 或序列长度太大 / 选了全量 | 减 Batchsize、减序列长度、改用 LoRA |
| LoRA 调 α 后训飞 | α 单独调大 ≈ 偷偷加大 LR | α 与 rank 协同调，守 α=2r |
| 生成评估分数一直很低 | 用了"准确率"看开放生成 | 改看 ROUGE/BLEU |
| 训练慢 | 序列长度过大(注意力 $O(L^2)$) | 数据短就调小序列长度 |
| RLHF 输出偏离/胡说 | KL 约束太弱，跑偏 SFT | 增大 KL 系数 β，或改用 [[llm-alignment/DPO]] |
