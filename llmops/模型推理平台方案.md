## 0. 一句话锚点

> **推理平台 = 网关(进来) + 调度(去哪) + 引擎(算) + 监控(看)**，目标是让"模型推理"像"调用一个有 SLA 的 HTTP API"一样可靠、可计量、可演进。

四件套的职责一句话：
- **网关 Gateway**：所有流量的统一入口，管"谁能进、进多少、走哪个协议、怎么计费"。
- **调度 Scheduler/Router**：在多个引擎副本之间分流，管"这条请求发给哪个 Pod 最划算"。
- **引擎 Engine**：真正跑 GPU 推理的进程（vLLM / TensorRT-LLM / SGLang…），管"怎么把 token 算出来"。
- **监控 Observability**：采集延迟/吞吐/排队/显存，管"现在健不健康、要不要扩容、SLO 破没破"。

## 1. 地基：为什么需要"平台"而不是"裸引擎"

你能用一行命令 `vllm serve Qwen2-7B` 起一个服务。但生产环境会立刻撞到 6 堵墙，平台就是为这 6 堵墙而生：

```
裸引擎能跑          平台要解决的 6 个问题
单进程 ┌──────────┐  ① 一个副本扛不住 QPS → 要多副本 + 负载均衡(调度层)
       │ vLLM     │  ② 多个模型/多个版本同时在线 → 要路由 + 模型仓库(网关+仓库)
       │ :8000    │  ③ 流量有波峰波谷 → 要弹性扩缩(扩缩 + K8s)
       └──────────┘  ④ 新模型上线怕翻车 → 要灰度(网关 + 调度)
                     ⑤ 要对外承诺 P99 延迟 → 要 SLO 监控 + 容量规划(监控)
                     ⑥ GPU 贵且稀缺 → 要鉴权/限流/配额/计费(网关)
```

**核心矛盾**：LLM 推理的资源单位是"昂贵的 GPU 显存"，而显存的占用主要来自 **KV-cache**（每个并发请求按其上下文长度持续占显存）。这让 LLM 服务不同于普通无状态微服务——它**有状态、显存敏感、长尾延迟大**，因此调度和扩缩策略都要"懂 KV-cache"。

预备概念（拆到最原子）：
- **Prefill（预填充）**：把整段 prompt 一次性喂进模型，算出首个 token，**算力(compute)受限**。决定 **TTFT（Time To First Token，首字延迟）**。
- **Decode（解码）**：逐个 token 自回归生成，每步读全部权重 + KV-cache，**显存带宽(bandwidth)受限**。决定 **TPOT（Time Per Output Token，每字延迟）**。
- **KV-cache**：把已算过的 token 的 Key/Value 张量缓存下来，避免重复计算。单请求显存占用 $\approx 2 \times L \times n_{layer} \times n_{kv} \times d_{head} \times \text{dtype}$（2 是 K 和 V）。
- **SLO（Service Level Objective）**：你对外承诺的可量化目标，如"P99 TTFT < 800ms、可用性 99.9%"。

## 3. 网关层 Gateway —— 流量的统一入口

**是什么**：所有外部请求的第一跳，做"横切关注点"（cross-cutting concerns），让业务方只面对一个统一的、OpenAI 兼容的端点。

```
请求进来              网关流水线（顺序很重要）
  │
  ▼  ① 鉴权 AuthN/AuthZ  ── API-Key / JWT / mTLS，确认"你是谁、能调哪些模型"
  ▼  ② 限流 RateLimit    ── 令牌桶：按 租户/模型/RPM/TPM 限速，保护后端
  ▼  ③ 配额 Quota        ── 月度 token 预算，超了拒绝或降级
  ▼  ④ 协议适配 Adapt    ── 把 /v1/chat/completions 翻译成引擎内部协议
  ▼  ⑤ 路由 Route        ── 按 model 字段 + 灰度规则选目标模型/版本
  ▼  ⑥ 计费打点 Billing  ── 记录 prompt/completion token 数，异步落账
  │
  ▼ 转发给调度层
```

**关键参数的含义与权衡**：
- **限流维度**：常用"双限流"——RPM（请求数/分钟，防突发连接）+ TPM（token 数/分钟，防大请求打爆显存）。LLM 必须限 TPM，因为一个 10 万 token 的请求可能比 1000 个小请求还耗资源。
- **令牌桶 vs 漏桶**：令牌桶允许突发（攒令牌），漏桶恒定速率。LLM 网关多用令牌桶 + 队列，兼顾突发友好和后端保护。
- **超时与流式**：LLM 响应是流式 SSE（Server-Sent Events），网关要支持长连接透传，**不能**像普通 API 那样设 30s 硬超时（长输出会被截断）。一般设"首字超时"(TTFT timeout) + "空闲超时"(idle timeout) 两段式。

**与同类对比**：通用网关（Nginx/Kong/APISIX）+ LLM 插件，或专用 LLM 网关（如 LiteLLM Proxy / Higress AI 网关）。专用网关内置 token 计数、流式、多供应商 failover，更省事；通用网关更通用但要自己写 token 逻辑。

## 4. 调度层 Router —— 决定请求落到哪个副本

**是什么**：在 N 个引擎副本之间分发请求的"智能负载均衡器"。普通 LB 用轮询/最少连接就够，但 LLM 调度要"懂引擎内部状态"。

```
为什么轮询(Round-Robin)对 LLM 不够好？
副本A: [■■■■■■■■] 8 个长请求在跑，显存 95%，新请求要排队
副本B: [■■]       2 个短请求，显存 30%，很空
轮询 → 50% 概率发给 A → 排队 → P99 飙升
聪明调度 → 看到 A 满了，发给 B → 延迟稳定
```

**三种调度策略（从简单到高级）**：

1. **最少请求 / 最少 token（Least-Loaded）**：选当前 in-flight 请求数或待处理 token 数最少的副本。简单有效，是默认推荐。
2. **KV-cache 亲和路由（Prefix-aware / Cache-aware）**：如果两个请求 prompt 前缀相同（如同一 system prompt、同一文档的多轮问答），把它们路由到**同一个副本**，复用已缓存的 KV，省掉重复 prefill。这是 LLM 调度独有的大杀器。
3. **PD 分离（Prefill-Decode Disaggregation）**：把 prefill（算力受限）和 decode（带宽受限）拆到不同副本/不同 GPU 上，各自优化，避免 prefill 的长任务阻塞 decode 的流式输出。进阶架构。

```
KV-cache 亲和路由示意
请求1: "你是助手。<doc-X>...问题1"  ─┐
请求2: "你是助手。<doc-X>...问题2"  ─┼─▶ 都路由到副本A
请求3: "你是助手。<doc-X>...问题3"  ─┘   复用 <doc-X> 的 KV-cache
                                        prefill 只算一次前缀！
```

**关键权衡**：亲和路由提升缓存命中率但可能导致负载倾斜（热点 prefix 全压一个副本）。实践上做"亲和 + 负载上限"：优先亲和，但副本超过阈值就溢出到次优副本。

## 5. 引擎层 Engine —— vLLM / TensorRT-LLM 的角色

**引擎做的事**：把"一批请求"高效地变成 token。两大核心技术：

- **Continuous Batching（连续批处理）**：传统批处理要等一批请求全部生成完才换下一批（短请求被长请求拖累）。连续批处理在**每个 decode step** 都能把已完成的请求踢出、把新请求塞进来，GPU 永远满载。是 LLM 服务吞吐的基石。
- **PagedAttention（vLLM）**：把 KV-cache 像操作系统的虚拟内存一样分页管理，消除碎片，显存利用率从 ~40% 提到 ~90%+，等价于并发数翻倍。

**vLLM vs TensorRT-LLM 对比**（讲含义，具体数字以官方为准）：

| 维度 | vLLM | TensorRT-LLM (TRT-LLM) |
|------|------|------------------------|
| 定位 | 易用、生态广、迭代快 | 极致性能、深度绑定 NVIDIA |
| 优化方式 | Python + CUDA kernel，PagedAttention | 编译式：提前 build engine，融合 kernel |
| 上手成本 | 低，`pip install` 即用 | 高，需 build、对 GPU 架构敏感 |
| 部署形态 | 直接 serve / 配 Triton | 多搭配 Triton Inference Server |
| 适用 | 多模型、快速迭代、研究/中小规模 | 固定模型、追求极限吞吐/延迟的大规模 |

**实践要点**：平台不绑死单一引擎。**用统一的引擎抽象层**（暴露 OpenAI 兼容接口），底层可以是 vLLM 也可以是 TRT-LLM+Triton，调度层不感知差异。多数团队"vLLM 为主、TRT-LLM 用于核心高流量模型"。

## 6. 多模型多版本 —— 模型仓库 + 动态加载

```
模型仓库 Model Registry（对象存储 OSS/S3/HDFS）
  qwen2-7b/
    ├── v1/  weights.safetensors  meta.json  (sha256)
    ├── v2/  weights.safetensors  meta.json
    └── v2-int8/  量化产物
  llama3-8b/
    └── v1/ ...

         ▲ 拉取（按需，带本地缓存 + checksum 校验）
         │
   引擎 Pod 启动时 / 热加载时从仓库拉权重到本地 NVMe
```

**版本寻址**：网关路由用 `model=qwen2-7b:v2` 三段式（名:版本），或用别名 `qwen2-7b:stable` / `:canary` 解耦"逻辑名"和"物理版本"。灰度切流时只改别名指向，业务方无感。

**多模型共存的两种部署形态**：
- **独占式**：一个模型独占若干 Pod（大模型、高流量首选，隔离好、可单独扩缩）。
- **多模型复用 / LoRA 多租**：一个基座 + 多个 LoRA adapter 动态切换（vLLM 支持 multi-LoRA），适合大量小众微调模型，省显存。

## 7. 弹性扩缩 —— 跟着流量呼吸

**为什么难**：GPU Pod **冷启动慢**（拉镜像 + 拉几十 GB 权重 + 引擎 warmup，可能数分钟），而流量波峰来得快。扩缩策略要"提前扩、缓慢缩"。

```
QPS ▲                          ┌──实际流量
    │                      ┌───┘
    │                  ┌───┘  ← 扩容滞后(冷启动) → 这段会排队/超时!
    │   ┌──副本数──────┘
    │───┘
    └──────────────────────────────────▶ time
缓解: ①预测式扩容(按历史曲线提前拉) ②预热池(常驻 idle 副本) ③快速冷启动
```

**三类扩缩信号（指标）**：
1. **CPU/GPU 利用率**：K8s 原生 HPA 用得最多，但 GPU 利用率波动大、不直接反映排队，**不够**。
2. **自定义业务指标（推荐）**：用 **KEDA** 或 Prometheus Adapter，按"**每副本待处理请求数 / 队列深度 / TTFT**"扩缩——这才直接反映 SLO 压力。
3. **事件驱动**：消息队列积压长度（离线批量推理场景）。

**关键参数权衡**：
- **目标值（target）**：如"每副本 in-flight 请求 = 20"。设低 → 副本多、成本高、延迟好；设高 → 省钱但易破 SLO。
- **scaleUp / scaleDown 速率**：扩容要快（防排队），缩容要慢 + 有 **stabilizationWindow**（防抖，避免流量小抖动就反复扩缩，GPU 冷启动代价太大）。
- **缩到 0（Scale-to-Zero）**：长尾小模型适用（KEDA 支持），省钱，但第一个请求要吃完整冷启动延迟，需配预热或告知调用方。

## 8. 灰度发布 —— 让上线不再赌命

```
四种灰度策略对比
① 蓝绿  旧版(蓝)全量 ──切──▶ 新版(绿)全量   切换快、回滚快，但要双倍资源
② 金丝雀 95%旧 + 5%新 ─逐步加权→ 100%新       平滑、可观测，主流推荐
③ A/B   按用户特征(地域/标签)分流              做效果对比实验
④ 影子  100%旧(返回) + 复制流量给新(丢弃结果)  零风险压测新版，但花双倍算力
```

**LLM 灰度的特殊性**：传统灰度看"5xx 错误率 + 延迟"就够，LLM 还要看**生成质量**（不能只看不报错）。所以金丝雀阶段要挂**在线评估**：采样请求做"新旧版输出对比 / 打分模型评估 / 关键指标（拒答率、幻觉率、格式合规率）监控"。质量退化即自动回滚。

**实现**：用 Argo Rollouts / Flagger 定义渐进式发布，权重从 5%→25%→50%→100%，每步设"分析模板（AnalysisTemplate）"——查 Prometheus 指标，达标才进下一步，否则自动 abort 回滚。

## 9. 与 Kubernetes / vLLM / TRT-LLM 集成

**K8s 是平台底座**，但 GPU 不是 K8s 原生资源，需要一套"GPU 化"组件：

```
K8s 节点 GPU 化栈
┌──────────────────────────────────────────┐
│ Pod: vLLM 容器 (resources: nvidia.com/gpu)│
├──────────────────────────────────────────┤
│ NVIDIA Device Plugin  暴露 GPU 给 kubelet  │  ← 由 GPU Operator 统一装
│ NVIDIA Container Toolkit  容器内访问 GPU    │
│ DCGM-Exporter  导出 GPU 指标给 Prometheus  │
│ MIG/MPS 切分  把 1 张卡切多份给小模型       │
├──────────────────────────────────────────┤
│ RDMA/IB: Network Operator  多机多卡通信     │  ← TP/PP 跨节点必备
└──────────────────────────────────────────┘
```

**官方组件链接**（部署 GPU/IB 底座）：
- GPU 解决方案（一键装 driver/plugin/DCGM）：https://github.com/NVIDIA/gpu-operator
- IB / RDMA 网络（多机互联，TP/PP 大模型必需）：
  - https://github.com/Mellanox/network-operator
  - https://docs.nvidia.com/networking/display/cokan10/network+operator

**调度集成要点**：
- **拓扑感知调度**：8 卡机里 GPU 之间有 NVLink 高速互联，张量并行(TP)的多卡必须落在**同机、NVLink 同组**，否则跨节点走 IB，通信慢几倍。用 gang-scheduling（Volcano/Koordinator）保证"一组卡要么全分配要么不分配"。
- **整卡 vs 切分**：大模型独占整卡；小模型用 **MIG**（硬件隔离，A100/H100 支持）或 **MPS**（软件共享）把一张卡切给多个 Pod，提升利用率。
- **引擎接入**：vLLM/TRT-LLM 容器对 K8s 就是普通 Pod，区别只在 `requests/limits` 里声明 `nvidia.com/gpu: 1`（或 MIG 切片资源名）。

## 10. SLO 保障 —— 把"够快"变成可量化的承诺

**LLM 的四个黄金指标**：
- **TTFT**（首字延迟）：用户体感"它响应了"。聊天场景核心 SLO。
- **TPOT / ITL**（每字延迟 / inter-token latency）：决定生成"流畅度"。
- **吞吐 Throughput**：总 token/s，决定成本效率。
- **可用性**：成功率（排除 4xx 用户错误后的 5xx 率）。

**TTFT 与吞吐是矛盾的**（用排队论理解）：把 batch 调大 → 吞吐高但单请求排队久 → TTFT 升。平台要在 SLO 约束下**最大化吞吐**：

> 用 **M/M/c 排队**直觉：设单副本服务率 $\mu$、到达率 $\lambda$、副本数 $c$，利用率 $\rho = \frac{\lambda}{c\mu}$。当 $\rho \to 1$ 时排队延迟**指数级爆炸**。所以容量规划绝不能把利用率跑到 95%+，要留 buffer（典型把目标利用率压在 60%~70%，给波动和扩缩滞后留空间）。

**容量规划三步**：① 压测单副本得到"在 SLO 内的最大 QPS"（饱和点）；② 按峰值 QPS / 单副本 QPS × 安全系数 算副本数；③ 配扩缩兜底波动。

## 11. 监控与可观测性 —— 三支柱

```
Metrics(指标)  ──▶ Prometheus ──▶ Grafana 看板 ──▶ Alertmanager 告警
  vLLM 暴露: TTFT, TPOT, 运行/等待队列长度, KV-cache 使用率, GPU 利用率
  DCGM 暴露: 显存占用, 温度, 功耗, SM 利用率

Traces(链路) ──▶ OpenTelemetry ──▶ Jaeger/Tempo
  一条请求: 网关→路由→排队→prefill→decode 各段耗时，定位瓶颈

Logs(日志)   ──▶ Loki / ELK
  请求级: model, version, prompt/completion token 数, 状态码, 错误栈
```

**最该盯的告警**：① P99 TTFT 破 SLO；② 等待队列(waiting queue)持续 > 0（说明容量不足，要扩容）；③ KV-cache 使用率长期 95%+（要 OOM 抢占了）；④ 单副本 5xx 突增（坏 Pod，自动剔除）。

## 12. 数值例子 / 对照 / 实践

### 例 1：单请求 KV-cache 显存手算

设模型 7B、`num_layers=32`、KV 头数 `n_kv=8`（GQA）、`head_dim=128`、FP16（2 字节），上下文 `L=4096`：

单请求 KV-cache $= 2 \times L \times n_{layer} \times n_{kv} \times d_{head} \times 2\text{B}$
$= 2 \times 4096 \times 32 \times 8 \times 128 \times 2 \approx 5.37 \times 10^8 \text{B} \approx 0.5\text{ GB}$。

**推论**：一张 80GB 卡，权重占 ~14GB，剩 ~66GB 给 KV-cache → 理论可并发 $66 / 0.5 \approx 132$ 个 4K 上下文请求。若上下文涨到 32K，单请求占 ~4GB → 并发掉到 ~16。**这就是为什么"长上下文"会暴击并发数**，调度和扩缩必须按 token 算账而非按请求数。

### 例 2：副本数容量规划手算

压测得：单副本在 P99 TTFT < 800ms 约束下，能扛 **30 req/s**。业务峰值 **300 req/s**：
- 裸算：$300 / 30 = 10$ 副本。
- 加安全系数（留 buffer，目标利用率 70%）：$10 / 0.7 \approx 15$ 副本。
- 再留扩缩冷启动滞后 buffer：常驻 12 副本 + HPA 弹到 18。

### 例 3：扩缩参数对照

| 参数 | 设激进 | 设保守 | 推荐 |
|------|--------|--------|------|
| scaleUp 速率 | 延迟好、成本高 | 易排队破 SLO | 快（GPU 冷启动慢，宁可早扩） |
| scaleDown 窗口 | 省钱但抖动 | 稳但浪费 | 长（5~10min 防抖） |
| HPA 目标(in-flight/副本) | 低=多副本 | 高=易破 SLO | 压测饱和点的 60~70% |

### 实践清单（落地顺序）
1. **先单引擎跑通**：vLLM serve + OpenAI 兼容，挂 Prometheus 抓指标。
2. **加网关**：限流(RPM+TPM)+鉴权+流式透传。
3. **多副本 + 调度**：最少负载路由起步，再上 KV-cache 亲和。
4. **K8s 化**：GPU Operator 装底座，声明 `nvidia.com/gpu`，拓扑感知调度。
5. **扩缩**：KEDA 按 in-flight 请求数扩缩，配 stabilization 防抖。
6. **灰度**：Argo Rollouts 金丝雀 + 在线质量评估自动回滚。
7. **SLO 闭环**：定义 TTFT/可用性 SLO → 容量规划 → 告警 → 复盘。

## 常见问题

| 问题 | 解答 |
|------|------|
| 为什么不能用普通 Nginx 轮询做 LLM 负载均衡？ | 它不懂引擎内部排队/显存状态，会把请求发给已满的副本，导致长尾延迟。需"最少负载/KV 亲和"调度。 |
| GPU 冷启动太慢怎么办？ | 镜像预拉 + 权重本地 NVMe 缓存 + 引擎 warmup + 预测式扩容 + 常驻预热池。 |
| 限流为什么必须限 TPM 而不只是 RPM？ | 一个超长请求消耗的显存/算力可能抵上千个小请求，只限请求数无法防止显存被打爆。 |
| vLLM 还是 TRT-LLM？ | 多模型快速迭代用 vLLM；固定的核心高流量模型追极致性能用 TRT-LLM（多配 Triton）。平台用统一抽象层屏蔽差异。 |
| 灰度只看错误率够吗？ | 不够。LLM 要额外监控生成质量（拒答率/格式合规/打分模型评估），质量退化即回滚。 |
| 利用率拉到 95% 省钱不好吗？ | 排队论里 $\rho\to1$ 延迟指数爆炸，会大面积破 SLO。目标利用率压在 60~70%。 |
| 长上下文为什么影响并发？ | KV-cache 占用与上下文长度线性相关，上下文翻倍则单请求显存翻倍、并发减半。 |
