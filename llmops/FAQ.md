## 0. 一句话锚点

LLMOps = 把"训练→评估→压缩→部署→推理→监控→回滚"这条大模型生命周期，用**自动化平台 + 标准化流程 + 可观测性**串起来，让模型能被**可重复、可灰度、可回滚地**交付到生产。本 FAQ 收录这条链路上最常见的具体故障与原因，**讲清"为什么会这样、从哪里查、怎么权衡",而非死记某个版本的命令行参数**。

## 1. 地基:LLMOps 解决什么问题

传统 MLOps 面对的是 KB~MB 级模型、CPU 即可推理。大模型把每个环节都放大了一个量级,于是冒出一堆"小模型时代不存在"的问题:

```
            传统 MLOps               →            LLMOps(放大后的新麻烦)
  ┌──────────────────────┐            ┌────────────────────────────────────┐
  │ 模型几十 MB           │            │ 权重几十 GB~TB,单卡放不下          │
  │ 单机训练几小时        │            │ 多机多卡训练几天~几周,通信成瓶颈   │
  │ CPU/单 GPU 推理       │            │ 多卡张量并行 + KV Cache 吃显存      │
  │ 关注 准确率/AUC       │            │ 还关注 吞吐/首token延迟/显存/成本   │
  │ 镜像 = 代码           │            │ 镜像 + 权重 + 数据集 + 算子库 协同  │
  └──────────────────────┘            └────────────────────────────────────┘
```

所以 LLMOps 的 FAQ,本质是围绕四类"放大的资源"出问题:**算力(GPU/NPU)、显存、网络(多机通信/对象存储)、存储(大权重/大数据集)**。记住这四类,排障时就有了方向。

## 2. 全景:一次任务在平台里怎么流转

理解故障发生在哪一环,先要有一张"调用链"地图。下面是训练与推理两条主线在 K8s 化 LLMOps 平台里的典型路径:

```
              ┌─────────────────────────── 控制面(Control Plane) ───────────────────────────┐
   用户/CI ──▶ │  API 网关 ─▶ 任务调度器(K8s/Volcano/Slurm) ─▶ 资源调度(GPU/NPU 拓扑感知) │
              └──────────────┬───────────────────────────────────────────────┬───────────────┘
                             │ 拉镜像                                         │ 拉权重/数据
                  ┌──────────▼──────────┐                          ┌──────────▼──────────┐
                  │ 镜像仓库(Harbor)    │                          │ 对象存储(S3/MinIO)  │
                  │ ★架构要匹配 x86/arm │                          │ ★时间/网络/权限     │
                  └──────────┬──────────┘                          └──────────┬──────────┘
                             │                                                │
            ┌────────────────▼────────────────────────────────────────────────▼───────────┐
            │                          数据面(Worker Pods)                                 │
            │  ┌────────┐  NCCL/HCCL   ┌────────┐  NCCL/HCCL   ┌────────┐                   │
            │  │ Pod0   │◀────────────▶│ Pod1   │◀────────────▶│ PodN   │  ← 多机多卡通信   │
            │  │ GPU×8  │   IB/RoCE    │ GPU×8  │   IB/RoCE    │ GPU×8  │                   │
            │  └────────┘              └────────┘              └────────┘                   │
            └───────────────────────────────────────────────────────────────────────────────┘
                             │                                                │
                       训练:写 checkpoint                              推理:暴露 Service
                             ▼                                                ▼
                     对象存储/PVC                                   网关/LB ─▶ 在线流量
```

**这张图的用法**:任何一个故障,先问"卡在控制面、还是数据面?是拉镜像、拉数据、还是 Pod 间通信?"——下面各节按这条链路从外到内排列。

## 3. 基础设施类(K8s / 网络 / 存储 / 调度)

### 3.1 K8s 的 Pod 中下载 S3 对象存储的数据网络不通?

这是最经典的"看着像网络问题、其实未必"的坑。可能的根因:

1. **服务器时间与 S3 对象存储服务器时间不一致**。S3 协议(AWS Signature V4)会用请求时间戳参与签名,客户端与服务端时间偏差超过允许窗口(通常分钟级),签名校验失败,表现为 `RequestTimeTooSkewed` 或连接被拒,**看起来像"网络不通"**。排查:在 Pod 内确认 NTP 是否同步,宿主机时区/时钟是否正确。
2. **异构集群导致网络镜像架构不匹配**。例如昇腾 NPU 服务器是 aarch64 架构,Calico(或其他 CNI)网络组件镜像本该是 aarch64,却拉成了 x86 架构镜像,导致网络插件容器起不来 → Pod 网络根本没就绪 → 自然连不上 S3。排查:`kubectl describe pod` 看 CNI 相关 Pod 是否 CrashLoopBackOff,确认镜像 `manifest` 是否多架构(multi-arch)。

```
   现象:"Pod 连不上 S3"  ←── 这是表象,真因可能在三条不同的路径上 ──┐
        │
   ┌────┼─────────────────┬──────────────────────────┐
   ▼    ▼                 ▼                          ▼
 时钟偏差          CNI 架构不匹配            真·网络策略/DNS
 (签名失效)        (Pod 网络没起来)         (NetworkPolicy/路由)
   │                 │                          │
 校时 NTP        拉对 arch 的镜像          查 svc/endpoint/DNS
```

**经验**:异构(x86 + ARM/NPU)集群里,几乎所有"莫名其妙的网络问题"都要先怀疑**镜像架构**和**时钟**这两件最容易被忽略的小事。

### 3.2 GPU/NPU 在容器里"看不到"或数量不对?

- 容器需要正确的**设备插件(Device Plugin)**把卡暴露给 K8s 调度器(GPU 用 NVIDIA Device Plugin,昇腾用 Ascend Device Plugin)。Pod 看不到卡,先查 Node 上对应 Device Plugin 的 DaemonSet 是否健康、`Allocatable` 里有没有 `nvidia.com/gpu` / `huawei.com/Ascend910` 这类资源。
- 容器运行时要配置对(GPU 需要 nvidia-container-runtime,使 `/dev` 与驱动库挂进容器)。
- **看到的卡比申请的少**:常见是 `resources.limits` 没写对,或者 MIG/vGPU 切分后实际可用份额变了。

> 具体资源名、插件版本、运行时配置项以官方文档/集群实际部署为准,这里只讲"该往哪查"。

### 3.3 多机训练 Pod 间互相找不到 / 通信建不起来?

多机训练靠"每个 Pod 都知道彼此地址 + 走高速网卡"两件事:

- **服务发现**:常用 K8s **Headless Service** 给每个有状态 Pod 固定 DNS 名,master 地址/端口靠环境变量或 rendezvous 机制分发。Pod 找不到对端,先查 Headless Service 与 DNS 解析。
- **走对网卡**:多机要走 InfiniBand/RoCE 高速网,而不是默认管理网。需要在 Pod 里暴露 RDMA 设备(RDMA Device Plugin),并通过环境变量指明集合通信库使用哪张网卡(让 NCCL/HCCL 选对 HCA)。走错网卡的典型症状:能跑通但**带宽极低、训练奇慢**。

详见 [[ai-infra/网络/NCCL]] 与 [[ai-infra/网络/InfiniBand]]。

## 4. 训练类(分布式 / 通信 / 收敛)

### 4.1 训练卡住(hang)不报错,也不往前走?

分布式训练 hang 住,99% 是**集合通信(collective)对不齐**——某些 rank 进了 all-reduce/all-gather,另一些没进,大家互相等。常见诱因:

```
   rank0  ──all_reduce──▶  ⏳ 等待...
   rank1  ──all_reduce──▶  ⏳ 等待...
   rank2  ──(走了不同分支/挂了/OOM)──▶  ✗ 没来
   ──────────────────────────────────────
   结果:rank0/1 永远等 rank2 → 整个 job hang
```

- **某个 rank 已崩溃/OOM**:进程没了但通信组还在等它 → 看每个 Pod 日志,定位先死的那个。
- **代码里有条件分支导致部分 rank 跳过了集合操作**(比如 `if rank==0` 里多调了一次通信)。
- **网络抖动/网卡降速**导致超时。可借助通信库的超时与 debug 日志(打开集合通信库的 DEBUG 级日志看卡在哪个 op)。

### 4.2 NCCL/HCCL 报错(timeout / unhandled error)?

- **timeout**:某 rank 慢或挂了(见 4.1),或网络/网卡问题。先确认所有 rank 是否都活着、是否走了高速网卡。
- **拓扑/网卡选择问题**:多网卡机器选错了通信网卡。需要通过环境变量约束使用的 HCA / 网络接口。
- **P2P / IB 不可用回退到 socket**:性能骤降但不报错,需要看通信库启动时打印的拓扑信息确认是否走了 IB/NVLink。

### 4.3 loss 变 NaN / 不收敛?

- **混合精度**:fp16 动态范围小,容易溢出成 Inf/NaN;优先用 bf16,或确保 loss scaling 生效。
- **学习率过大 / warmup 不足**:大模型对 LR 敏感,加 warmup、降峰值。
- **数据问题**:脏数据、未对齐的 padding/mask、超长样本截断异常。**先小批量、单机复现,排除分布式因素**,这是分布式 debug 的黄金法则。

### 4.4 checkpoint 太大、保存/恢复慢或失败?

- 大模型权重 + 优化器状态(Adam 是参数的 ~2 倍)非常大。保存到对象存储要考虑**分片(sharded checkpoint)**与并发上传;恢复时注意并行度(TP/PP/DP)改变后能否正确 reshard。
- 断点续训失败常见于:并行策略变了、保存时被抢占写了一半(checkpoint 不完整)。建议**原子写 + 校验**。

## 5. 推理类(显存 / 吞吐 / 延迟)

### 5.1 推理服务 OOM / "CUDA out of memory"?

推理显存 = **权重 + KV Cache + 激活/中间缓冲 + 框架开销**。OOM 时按这个公式逐项砍:

```
   显存占用 ≈  权重(随量化变小)
            +  KV Cache(随 并发数 × 序列长度 线性增长) ← 最容易爆的一项
            +  激活/临时 buffer
            +  框架/碎片预留
```

- **KV Cache 才是大头**:并发越高、上下文越长,KV Cache 越大。降并发上限、限制 `max_model_len`、或用 PagedAttention 类显存管理(见 [[llm-inference/vllm/README]] 与 [[llm-optimizer/kv-cache]])。
- **量化权重**(INT8/INT4/FP8)能显著降权重占用,见 [[llm-compression/quantization/量化基础]]。
- **多卡张量并行**把权重摊到多张卡。

### 5.2 显存"够却报碎片"/利用率上不去?

经典 PyTorch 显存碎片:总量够但没有连续大块。缓解思路是用**显存池/可扩展分段分配**类机制(框架层一般有对应开关或环境变量),以及用 PagedAttention 这种**分页式 KV 管理**从根上避免碎片。具体开关名以框架文档为准。

### 5.3 首 token 慢(TTFT 高)?

首 token 延迟主要来自 **Prefill 阶段**——要把整段 prompt 过一遍。优化方向:

- **Chunked Prefill / 连续批处理(continuous batching)**:把长 prompt 切块,与 decode 交错调度,避免长 prefill 阻塞别人。
- **Prefix Cache**:相同前缀(如同一 system prompt)复用已算好的 KV,跳过重复 prefill。
- 见 [[llm-inference/vllm/README]] 与 [[llm-optimizer/FlashAttention]]。

### 5.4 并发 / 吞吐上不去,GPU 利用率却不高?

- **批处理没打满**:静态 batch 等齐才发,GPU 空转。改用**连续批处理(continuous batching)**,请求随到随入批。
- **调度/排队瓶颈在 CPU 侧**(分词、采样、后处理),GPU 反而饿着。
- **指标要看对**:吞吐看 tokens/s,延迟分 TTFT(首 token)与 TPOT(每输出 token 间隔),别只看 QPS。名词解释见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]。

### 5.5 同一模型,vLLM/SGLang/TensorRT-LLM 选哪个?

| 维度 | 取舍 |
| --- | --- |
| 易用 / 生态快速迭代 | vLLM(PagedAttention、连续批处理成熟) |
| 复杂结构化输出 / RadixAttention 前缀复用 | SGLang |
| 极致延迟 / NVIDIA 平台深度优化 | TensorRT-LLM(需编译引擎,灵活性差些) |

没有银弹,**按"延迟/吞吐/易用/硬件"四象限选**,并以实测为准。

## 6. 运维类(上线 / 灰度 / 监控 / 回滚)

### 6.1 怎么安全地把新模型上线?

```
   旧模型 v1 ──100%──▶ 流量
         │  灰度开始
         ▼
   旧 v1 ──90%──▶ 流量      新 v2 ──10%──▶ 影子/小流量
         │  指标(质量+延迟+错误率)都 OK?
         ▼
   逐步 90/10 → 50/50 → 0/100,任一指标恶化即一键回滚
```

- **金丝雀/灰度发布**:小流量验证新模型质量与性能,再逐步放量。
- **影子流量(shadow)**:复制真实请求给新模型,只看结果不影响用户,适合上线前评估。
- **可回滚**:权重与镜像都要版本化,回滚 = 切回上一个稳定版本,**秒级生效**。

### 6.2 上线后要监控什么?

- **业务/质量**:回复质量(可抽样人评/LLM 评测)、拒答率、安全过滤命中率。
- **性能**:TTFT、TPOT、吞吐、排队长度。
- **资源**:GPU 利用率、显存占用、KV Cache 命中率、温度/功耗。
- **稳定性**:错误率、超时率、重启次数、OOM 次数。

### 6.3 服务偶发 500 / 超时,GPU 没满载?

常见非 GPU 瓶颈:排队超时、单条超长请求拖垮一个批、上游网关超时设置过短、健康检查把正在加载大权重(冷启动几分钟)的 Pod 误判为不健康而反复重启。**大模型 Pod 的就绪探针要给足启动时间**。

## 7. 资产管理类(模型 / 权重 / 数据集)

- **权重存哪**:几十 GB~TB,放对象存储(S3/MinIO)做版本化,Pod 启动时拉到本地 NVMe 或经 CSI 挂载。注意冷启动拉权重耗时(可预热/常驻/镜像内置)。
- **版本化**:模型 = 权重 hash + 训练配置 + 数据版本,三者绑定才可复现。
- **数据集**:大数据集走流式读取/分片,避免一次性下载;注意脱敏与权限。

## 8. 排障通用方法论

```
   出问题  ──▶  ① 定位在链路哪一环(控制面/拉镜像/拉数据/通信/计算)
                │
                ▼
            ② 缩小规模复现:多机→单机,多卡→单卡,大batch→小batch
                │
                ▼
            ③ 看"最先死的那个":分布式里第一个崩的 rank 才是真因
                │
                ▼
            ④ 异构集群额外两查:镜像架构(x86/arm)、时钟同步
                │
                ▼
            ⑤ 改一个变量验证一次,别一次改一堆
```

这套顺序能覆盖本 FAQ 绝大多数案例。核心心法:**先分层定位,再缩小复现,只改一个变量**。

## 常见问题 / 坑(速查表)

| 现象 | 高频根因 | 第一步怎么查 |
| --- | --- | --- |
| Pod 连不上 S3 | 时钟偏差(签名失效)/ CNI 架构不匹配 | 校时 + 看 CNI Pod 状态 |
| 异构集群网络异常 | 拉了 x86 镜像到 ARM/NPU | 确认镜像是否多架构 |
| 容器看不到 GPU/NPU | Device Plugin 未就绪 / 运行时没配对 | 查 DaemonSet 与 Node Allocatable |
| 训练 hang 不报错 | 集合通信对不齐(某 rank 挂/分支不一致) | 看最先死的 rank 日志 |
| NCCL timeout | rank 挂 / 网卡选错 / 网络抖动 | 确认 rank 存活 + 走没走 IB |
| loss NaN | fp16 溢出 / LR 过大 / 脏数据 | 换 bf16 + 加 warmup + 单机复现 |
| 推理 OOM | KV Cache 随并发×长度膨胀 | 降并发/限长 + 量化 + TP |
| 显存够却碎片 | 分配器碎片 | 用显存池/分页 KV 管理 |
| 首 token 慢 | Prefill 阻塞 | Chunked Prefill + Prefix Cache |
| 吞吐低但 GPU 空 | 静态批 / CPU 侧瓶颈 | 连续批处理 + 看 CPU 占用 |
| 上线后偶发 500 | 冷启动被探针误杀 / 超长请求 | 放宽就绪探针 + 限单条长度 |

> 提醒:本表给的是**排查方向**。具体命令、环境变量名、资源字段、默认值请以你所用框架/调度器/云厂商的官方文档与集群实际配置为准,切勿照搬版本相关细节。
