## 0. 一句话锚点

**LLMOps 就是 DevOps + MLOps 在"超大参数、超贵算力、生成式不确定输出"三重约束下的特化版本**：它要解决的不是"训一个模型"，而是"让一群模型在一个团队、一套算力、一个平台上，持续、安全、低成本地被训练-评测-发布-观测-迭代"。

## 1. 地基/前置：它到底解决什么问题

### 1.1 从最底层问：为什么传统 MLOps 不够用

传统机器学习模型（一个 XGBoost、一个 ResNet）有几个隐含假设：

1. 模型小，单机单卡甚至 CPU 就能训练和推理。
2. 输入输出是结构化/定长的（一张图→一个类别），评测有明确的标准答案（准确率、AUC）。
3. 一次训练几分钟到几小时，失败重跑成本低。

大模型把这三条假设全部打破：

- **参数巨大**：一个 7B 模型 FP16 权重就 14 GB，70B 就 140 GB，单卡装不下，**必须多机多卡并行**。
- **输出是开放文本**：没有唯一标准答案，"好不好"要靠人评、规则评、模型当裁判（这正是旧文件里"人工评估/自动规则/自动裁判员"的来源），评测本身变成一个子系统。
- **训练贵且长**：一次预训练可能跑几周、烧几百上千张卡，**中断恢复（checkpoint）、容错、抢占式调度**成为刚需，"重跑一次"代价是几十万到上百万。
- **推理也贵**：自回归一个 token 一个 token 地出，**显存被 KV Cache 持续吃掉**，吞吐和延迟强相关于 batch、序列长度、并发，需要专门的推理引擎和服务层。

所以 LLMOps 不是"MLOps 改个名"，而是**围绕算力稀缺 + 生成式不确定性，新增了一整套基础设施和流程**。

### 1.2 LLMOps 的关注点全景图

```
                        ┌──────────────── LLMOps ────────────────┐
   数据                  训练               评测           部署         监控
 ┌──────┐   清洗/去重   ┌──────┐  保存    ┌──────┐  门禁  ┌──────┐  采集  ┌──────┐
 │ 语料 │ ───────────► │ 训练 │ ──────► │ 评测 │ ────► │ 服务 │ ────► │ 观测 │
 │ 标注 │              │ 微调 │ ckpt    │ 打分 │ gate  │ 推理 │ logs  │ 告警 │
 └──────┘              └──────┘         └──────┘       └──────┘       └──────┘
     ▲                     │                              │              │
     │                     ▼                              ▼              │
     │              ┌─────────────┐               ┌─────────────┐        │
     │              │ 模型 Registry │◄──版本/血缘──│ 灰度/AB/回滚 │        │
     │              └─────────────┘               └─────────────┘        │
     │                                                                   │
     └────────────────── 反馈数据回流（badcase → 新一轮训练）◄────────────┘
```

关键洞察：**这是一个闭环，不是一条直线**。线上观测到的 badcase、用户反馈、新数据会回流成下一轮训练语料，形成"数据飞轮"。LLMOps 平台的价值就在于把这个环自动化、可追溯。

## 2. 全生命周期：训练-评测-部署-监控

### 2.1 训练阶段（Training / Fine-tuning）

```
   数据管道                     算力层                     产物
┌─────────────┐   提交Job   ┌──────────────────┐   写出   ┌──────────┐
│ 数据集版本   │ ─────────► │ 调度器(K8s/Slurm) │ ──────► │ Checkpoint│
│ (DVC/LakeFS) │            │  ├ 多机多卡并行    │         │ + 训练指标 │
│ tokenize    │            │  ├ 断点续训        │         │ + 血缘元数据│
└─────────────┘            │  └ 容错重启        │         └──────────┘
                           └──────────────────┘
```

最底层要理解的三件事：

- **并行**：模型装不下一张卡，于是有数据并行（DP，复制模型切数据）、张量并行（TP，把一层的矩阵切开）、流水线并行（PP，把不同层放不同卡）、专家并行（EP，MoE 专用）。它们的组合叫"3D/4D 并行"。详见训练章节。
- **Checkpoint**：每隔 N 步把权重+优化器状态写盘，崩了能从上次继续。优化器状态（Adam 的 m、v）通常是权重的 2 倍大，所以 checkpoint 体积 ≈ 权重 × (1+2+1) = 4 倍量级（含 FP32 主权重）。
- **可复现**：同一份数据 + 同一份代码 + 同一组超参 + 同一个随机种子 = 同一个模型。Registry 必须记录这条"血缘"。

### 2.2 评测阶段（Evaluation）—— 上线前的门禁

旧文件已点到三种评测，这里把它们放进工程化框架：

```
                 ┌──── 评测三板斧 ────┐
 候选模型 ──┬──► 人工评估   主观打分（专家/众包），维度：有用/无害/诚实
           ├──► 自动规则   ROUGE/BLEU/EM 等文本相似度，适合有标准答案的题
           └──► 模型裁判   用更强模型当 Judge 打分，适合开放/复杂问答
                 │
                 ▼
            综合分 ≥ 阈值？ ──否──► 拦住，不让发布（Quality Gate）
                 │是
                 ▼
              进入部署
```

为什么要三种并存：规则评快但只能评有标准答案的；人工准但慢且贵；模型裁判介于两者之间，便宜可规模化但有偏差（裁判模型自身的偏好、位置偏置）。**工程上把"评测分数"作为发布门禁（Gate）**，分数不达标就卡住流水线，这是 LLMOps 把评测从"做实验"变成"自动卡口"的关键。

### 2.3 部署阶段（Deployment）

把通过门禁的模型变成一个能被调用的服务。核心不是"起个进程"，而是：选引擎（vLLM/TGI/TensorRT-LLM 等）、配并行度、申请 GPU、暴露 API、接入网关、配置自动扩缩容。详见第 5 节推理平台。

### 2.4 监控阶段（Monitoring）

服务跑起来后持续采集三类信号（系统、业务、质量），异常告警并回流 badcase。详见第 7 节可观测。

## 3. K8s 编排：为什么是它，怎么管 GPU

### 3.1 为什么用 Kubernetes

最底层的问题：你有几百张 GPU、几十个团队、上百个训练和推理任务，怎么**公平、高效、自动地把任务放到机器上**？手工 ssh 上机器跑 `python train.py` 在 3 张卡时还行，到 300 张卡就完全失控。K8s 就是这个"算力的操作系统"：它把一堆机器抽象成一个大资源池，你声明"我要 8 张 A100"，它负责找到机器、拉容器、挂载、重启、回收。

### 3.2 核心对象（拆到最原子）

```
┌─────────────────── Kubernetes 集群 ───────────────────┐
│                                                        │
│   Deployment / StatefulSet   ← 你声明"要几个副本"      │
│        │  管理                                         │
│        ▼                                               │
│      Pod  ←─ 最小调度单位，1个或多个容器共享网络/存储   │
│        │  里面跑                                       │
│        ▼                                               │
│     Container (vLLM / 训练进程)                        │
│        │  申请                                         │
│        ▼                                               │
│   resources: limits: nvidia.com/gpu: 1  ← GPU 当资源申请│
│                                                        │
│   Service  ←─ 给 Pod 一个稳定的访问入口(负载均衡)       │
│   HPA      ←─ 按指标自动增减副本数(弹性伸缩)            │
│   PVC      ←─ 挂载模型权重/数据集(持久卷)              │
└────────────────────────────────────────────────────────┘
```

- **Pod** 是最小调度单位，GPU 任务通常一个 Pod 占整数张卡（GPU 不像 CPU 能任意切分，虽然有 MIG/MPS 可做共享）。
- **GPU 怎么被 K8s 看见**：通过 **Device Plugin**（NVIDIA Device Plugin）把 `nvidia.com/gpu` 注册成一种可申请资源，再配合容器运行时（nvidia-container-toolkit）把驱动和设备透传进容器。
- **训练用 StatefulSet/Job 系**：训练任务有状态、需要稳定的网络标识（rank 0/1/2…要互相找到对方），常用 Kubeflow 的 **PyTorchJob/MPIJob** 这类自定义资源（CRD）来描述"多 Pod 协同训练"。
- **推理用 Deployment + HPA**：无状态、可水平扩展，按 QPS 或 GPU 利用率自动扩缩容。

详细展开见 [[llmops/kubernetes]]。

## 4. 多机多卡调度：让一群卡协同工作

### 4.1 为什么默认调度器不够

K8s 默认调度器是**逐个 Pod** 决策的。但一个 8 卡训练任务需要 8 个 Pod **要么全部拿到卡、要么一个都别起**——如果只起了 5 个，它们会卡在等待 rank 6/7/8，**白白占着 5 张卡却谁也跑不动**（资源死锁）。

### 4.2 Gang Scheduling（成组调度）

```
   普通调度（坏）                    Gang 调度（好）
 任务A: 需8卡                      任务A: 需8卡
 ┌─┬─┬─┬─┬─┐ 拿到5卡              ┌──────────────┐
 │A│A│A│A│A│ 卡死等待            │ 检查: 8卡够吗? │
 └─┴─┴─┴─┴─┘                     └──────┬───────┘
 任务B: 需4卡                       够 ─┤ 一次性全调度A的8个Pod
 ┌─┬─┬─┐ 也拿到3卡                  不够┤ A整体排队, 不占坑
 │B│B│B│ 也卡死                          先让B(4卡)上
 → 死锁, 利用率=0                   → 无死锁, 利用率高
```

实现方案：**Volcano**、**Koordinator**、**YuniKorn**、Kubeflow 的 **scheduler-plugins(coscheduling)** 等。核心机制是 **PodGroup**：声明"这组 Pod 要么一起调度成功，要么一起等待（all-or-nothing）"。

### 4.3 拓扑感知与通信

多卡训练 90% 的时间可能在做 AllReduce（梯度同步）。**卡和卡之间的连接方式决定通信速度**：

```
 同机卡间:  GPU ←NVLink→ GPU      (几百 GB/s, 最快)
 跨机卡间:  机A ←RDMA/IB→ 机B     (几十~上百 Gb/s)
 普通网络:  机A ←TCP→ 机B          (慢, 训练杀手)
```

所以调度器要**拓扑感知**：尽量把同一个任务的卡放在同机/同机架/同 NVLink 域里，减少跨机通信。否则 8 张卡分散在 8 台机器上，通信开销能让训练慢好几倍。

### 4.4 抢占与配额

- **抢占（Preemption）**：高优先级任务（线上紧急训练）来了，可以踢掉低优先级任务（离线实验）腾出卡。被踢的任务因为有 checkpoint 不会丢进度。
- **配额（Quota）**：团队 A 最多用 100 卡，团队 B 最多 50 卡，防止一个团队把集群占满。Volcano 的 Queue、K8s 的 ResourceQuota 负责这件事。

## 5. 推理平台：从请求到 token 的分层

### 5.1 整体架构

```
 用户请求
   │
   ▼
┌──────────────┐  鉴权/限流/计费/路由
│  API 网关     │  (Higress/Kong/APISIX, 或自研 LLM Gateway)
└──────┬───────┘
       │ 按模型名/版本/灰度规则
       ▼
┌──────────────┐  负载均衡 + 灰度切流
│  路由/调度层  │  (把请求发给某个模型的某个版本副本)
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────────────┐
│  推理引擎层 (vLLM / TGI / TensorRT-LLM / SGLang)│
│   ├ 连续批处理 (Continuous Batching)            │
│   ├ KV Cache 管理 (PagedAttention 分页)         │
│   ├ 张量并行 (大模型跨卡)                        │
│   └ 量化 (INT8/INT4/FP8 降显存)                 │
└──────┬───────────────────────────────────────┘
       │
       ▼
   GPU 集群 (K8s 管理, HPA 弹性伸缩)
```

### 5.2 推理引擎解决什么问题（核心机制）

自回归生成有两个天敌，推理引擎就是来对付它们的：

**(1) 请求长短不一 → 连续批处理（Continuous Batching）**
传统静态 batch 要等一批请求里最慢的那个生成完才能换下一批，短请求被长请求拖死。连续批处理在**每生成一个 token 的粒度上**动态地把已完成的请求换出、新请求换入，GPU 几乎不空转，吞吐能提升数倍。

**(2) KV Cache 吃显存且碎片化 → PagedAttention（分页）**
生成时每个 token 都要缓存它的 Key/Value 向量（KV Cache）以避免重算。序列越长，KV Cache 越大。传统做法给每个请求预留"最大长度"的连续显存，浪费严重。PagedAttention 借鉴操作系统虚拟内存，把 KV Cache 切成固定大小的"页"，按需分配、非连续存储，**显存利用率从 ~20-40% 提升到 ~90%+**，等价于能塞下更多并发请求。

### 5.3 引擎选型一句话

- **vLLM**：吞吐之王，PagedAttention 原创，社区活跃，通用首选。
- **TensorRT-LLM**：NVIDIA 自家，单卡极致延迟，但编译/适配成本高，绑定 NVIDIA。
- **TGI (Text Generation Inference)**：HuggingFace 出品，生态好，部署省心。
- **SGLang**：复杂结构化生成、Agent 多轮、prefix 复用场景强（RadixAttention）。

更多见 [[llmops/模型推理平台方案]]。具体版本号/参数以官方文档为准。

## 6. 模型版本管理与灰度发布

### 6.1 模型 Registry（一切的源头）

```
┌──────────────────── Model Registry ────────────────────┐
│ 模型名: chat-7b                                          │
│  ├ v1.2.0  stage=Production   血缘:{data:d3, code:c8}    │
│  ├ v1.3.0  stage=Staging      评测分:0.82  指标:...      │
│  └ v1.4.0  stage=None         (新训出, 待评测)           │
└─────────────────────────────────────────────────────────┘
```

Registry 记录每个版本的：权重位置、训练数据版本、代码 commit、超参、评测分数、当前所处阶段（Staging/Production/Archived）。**没有 Registry，你无法回答"线上这个模型是怎么来的、出了问题怎么回滚"**。工具如 MLflow Model Registry。

### 6.2 灰度发布的几种姿势

```
 (a) 金丝雀 Canary        (b) 影子 Shadow          (c) AB 测试
  90% ──► v1.2 (旧)        100% ──► v1.2 (旧,生效)   50% ──► v1.2
  10% ──► v1.3 (新)         拷贝 ──► v1.3 (新,丢弃结果) 50% ──► v1.3
  观测新版指标, 逐步加比例   只看新版会不会崩,不影响用户  对比业务指标决胜负
       │ 好 → 100%               │ 稳 → 切金丝雀          │
       │ 坏 → 回滚 0%            └────────────────────────┘
```

- **金丝雀**：先放一小撮真实流量给新版本，盯着错误率/延迟/质量，没问题再逐步放大（10%→30%→100%）。坏了立刻把比例打回 0（回滚）。
- **影子流量**：把生产流量**复制**一份给新版本，但**丢弃新版本的输出**（不返回给用户），纯粹压测和对比，零风险验证。
- **回滚**：因为有 Registry 的版本记录，回滚就是把路由规则里的 `Production` 指针从 v1.3 改回 v1.2，秒级生效。

为什么大模型尤其需要灰度：**生成式输出无法离线穷尽测试**，一个新版本可能在某类 prompt 上突然胡说八道，只有真实流量小比例验证才能发现。

## 7. 可观测（Observability）

### 7.1 三大支柱 + LLM 专属

```
┌───────── 通用可观测三支柱 ─────────┐   ┌──── LLM 专属 ────┐
│ Metrics 指标(数值, 时序)           │   │ Token 用量/成本    │
│   QPS, 延迟P50/P99, GPU利用率, 显存 │   │ TTFT(首token延迟)  │
│ Logs 日志(离散事件)                │   │ TPOT(每token延迟)  │
│   错误堆栈, 请求记录               │   │ 拒答率/有害率      │
│ Traces 链路追踪(一次请求全路径)     │   │ 幻觉/质量漂移      │
│   网关→路由→引擎→GPU 各段耗时       │   │ Prompt/Response留存│
└────────────────────────────────────┘   └──────────────────┘
        Prometheus + Grafana + Loki/Tempo/OpenTelemetry
```

### 7.2 为什么 LLM 要额外指标

- **TTFT (Time To First Token)**：用户点了发送到看见第一个字的时间，决定"感觉卡不卡"，强相关于 prefill 阶段和排队。
- **TPOT (Time Per Output Token)**：吐字速度，决定"读起来流不流畅"。
- **Token 成本**：推理按 token 计费/计算，必须监控用量防止成本失控。
- **质量漂移**：模型不会变，但用户问题分布会变（新热点、新攻击 prompt），导致线上质量悄悄下降，需要持续抽样评测（把第 2.2 节的评测搬到线上做定时巡检）。

这些指标的精确定义见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]。

### 7.3 闭环：badcase 回流

监控不只是看仪表盘。检测到的低分回复、用户点踩、安全拦截，都应**自动沉淀成数据集**，进入下一轮训练（第 1.2 节的数据飞轮）。这是 LLMOps 区别于普通运维的灵魂——**观测的终点是下一次训练的起点**。

## 数值例子 / 典型场景（手算）

### 例 1：7B 模型推理要几张卡、能跑多少并发

- 权重显存：7B 参数 × 2 字节(FP16) = **14 GB**。
- 一张 A100-40G：40 GB − 14 GB(权重) − ~2 GB(框架/激活) ≈ **24 GB 留给 KV Cache**。
- 单 token 的 KV Cache 大小 ≈ $2 \times L \times H \times d \times 2\text{字节}$。对 7B（约 $L=32$ 层，隐藏维 $H \cdot d=4096$）：
  每 token ≈ $2 \times 32 \times 4096 \times 2 = 524288$ 字节 ≈ **0.5 MB/token**。
- 若平均上下文 2048 token：每个并发请求 KV ≈ $2048 \times 0.5\text{MB} = 1\text{GB}$。
- 并发数 ≈ $24\text{GB} / 1\text{GB} ≈ $ **24 个并发请求**（用了 PagedAttention 后利用率更高，实际可更多）。
- 结论：**一张 A100-40G 跑 7B，量级是几十并发**；要更高并发或更长上下文，就上 INT8 量化（权重砍半到 7 GB）或加卡做张量并行。

### 例 2：70B 预训练要多少卡

- 权重 FP16 = $70 \times 2 = 140$ GB，单张 80G 卡装不下 → **必须张量并行切到多卡**。
- 训练时还要存：FP32 主权重(280G) + Adam 的 m/v(各 280G) + 梯度(140G) + 激活值。优化器+权重+梯度 ≈ $140 \times (1+2+2+1) ≈ 840$ GB（混合精度量级估算）。
- $840\text{GB} / 80\text{GB} ≈ $ **至少 11 张卡**才装得下状态，实际为留激活和通信余量、配合并行策略，常用 **16~32 张卡起步**（TP=8 × DP=多组）。

### 例 3：灰度比例怎么定

- 日请求 100 万。新版本先放 **1%**(1 万次)观测一天：若新版 P99 延迟、错误率、质量分都不劣于旧版，次日放 **10%**，再次日 **50%→100%**。
- 为什么从 1% 起：万一新版有严重问题，影响面 = $1\% \times 100\text{万} = 1\text{万}$ 请求，**可控且可秒级回滚**；若一上来 100%，等于拿全量用户做实验。

## 对照表

### LLMOps vs MLOps

| 维度 | MLOps | LLMOps |
|------|-------|--------|
| 模型规模 | MB~GB，单机可训 | GB~TB，**必须多机多卡** |
| 训练时长 | 分钟~小时 | 天~周，**需 checkpoint/容错** |
| 输出 | 结构化、有标准答案 | 开放文本、**无唯一答案** |
| 评测 | 准确率/AUC | **人工+规则+模型裁判** 三合一 |
| 推理 | 一次前向 | **自回归 + KV Cache + 专用引擎** |
| 发布 | 离线可充分测试 | **必须灰度/影子**(无法穷尽测试) |
| 核心瓶颈 | 数据/特征 | **算力/显存/通信** |

### 自建平台 vs 用云厂商平台

| 维度 | 自建(K8s+vLLM+...) | 云平台(如千帆/SageMaker 等) |
|------|--------------------|------------------------------|
| 起步成本 | 高(要搭一整套) | 低(开箱即用) |
| 灵活性/可控 | 高(全栈自主) | 低(受平台约束) |
| 数据私有性 | 高(全在自己集群) | 取决于厂商方案 |
| 适合 | 有规模、有团队、要降本 | 快速验证、团队小、不想搬轮子 |

> 旧版本文档提到的**千帆大模型平台**就是"云平台"路线的代表：把训练、数据集管理、评估都做成托管服务，你只管调 API。本文讲的是其**底层通用机制**，自建或选平台都该理解。

## 常见问题

| 问题 | 速答 |
|------|------|
| LLMOps 和 MLOps 是一回事吗？ | 不是。LLMOps 是 MLOps 在"巨参数+贵算力+生成式"约束下的特化，新增了并行训练、推理引擎、模型裁判评测、灰度发布等。 |
| 为什么训练必须多机多卡？ | 70B 权重 140G，单卡装不下；且训练状态(优化器+梯度)是权重的好几倍，**物理上放不下**，只能切。 |
| K8s 默认调度器为什么不行？ | 它逐个 Pod 调度，会让多卡任务"拿到一半卡却跑不动"造成死锁，需 Gang Scheduling(Volcano 等)。 |
| 推理为什么要专门的引擎？ | 自回归 + KV Cache 导致显存浪费和 GPU 空转，vLLM 的连续批处理 + PagedAttention 把吞吐和显存利用率拉满。 |
| 为什么大模型上线必须灰度？ | 生成式输出无法离线穷尽测试，新版本可能在某类 prompt 上突然崩，只能用小比例真实流量验证。 |
| 监控只看仪表盘吗？ | 不。监控的终点是把 badcase 回流成下一轮训练数据，形成数据飞轮，这是 LLMOps 的灵魂。 |
| TTFT 和 TPOT 区别？ | TTFT=出第一个字的等待(卡不卡)，TPOT=后续吐字速度(流不流畅)，分别由 prefill 和 decode 阶段决定。 |
