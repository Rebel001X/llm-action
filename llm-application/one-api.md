## 0. 一句话锚点

**One API = "大模型界的统一收银台 + 配电箱"。** 上游接各家模型（OpenAI、Azure、国产大模型、本地推理服务……），下游对所有应用只暴露**一套 OpenAI 风格的 HTTP 接口**。应用拿一个 One API 发的"令牌"就能调任意已配置的模型，而把"用哪家、哪个密钥、扣谁的钱、超没超额"全交给网关处理。

它本质上是一个 **API 网关（Gateway）** 的垂直特化：通用网关解决"流量路由"，One API 在此之上加了**大模型语义**——模型名映射、按 token 计费、按渠道路由、按用户配额。

## 1. 地基：它解决什么问题

设想一个团队同时在用很多模型：

```
没有网关时（N×M 的混乱）：

  应用A ──key1──> OpenAI
  应用A ──key2──> Azure OpenAI       每个应用都要：
  应用B ──key3──> 国产大模型甲         · 自己存 N 个密钥
  应用B ──key4──> 本地 vLLM           · 自己处理 N 套鉴权/计费差异
  应用C ──key5──> 国产大模型乙         · 自己做限流/重试/降级
  ...                                 · 换供应商=改所有应用代码
```

痛点可以拆成几个"原子问题"：

1. **密钥散落**：上游密钥写死在各应用里，泄露风险高、轮换困难。
2. **接口不统一**：不同厂商鉴权头、参数名、流式格式都不同，应用要写一堆适配。
3. **看不见账**：谁调了多少、花了多少钱、哪个 key 快超额，全靠人肉。
4. **没有弹性**：一个供应商挂了/限流了，没法自动切到备用。
5. **难以多租户**：想给不同子团队/客户发不同额度的访问权，没有抓手。

One API 用一个**中间层**把这些问题收口：

```
有网关时（N→1→M 收口）：

  应用A ┐
  应用B ┤── one-api 令牌 ──> [ One API 网关 ] ──> OpenAI / Azure / 国产 / 本地…
  应用C ┘     (统一接口)        密钥/路由/计费        (真正的上游密钥只在这里)
```

应用侧只认 One API；上游怎么变，应用无感。这就是"**关注点分离**"在 LLM 接入层的落地。

## 2. 整体架构：网关站在调用链哪里

```
        ┌────────────────────────────────────────────────────┐
        │                     One API                         │
        │                                                     │
 应用 ──┼─> [鉴权:校验令牌] ─> [路由:选模型/渠道] ─> [适配:协议转换]┼─> 上游模型
  (用    │        │                  │                  │       │   供应商
  OpenAI │        v                  v                  v       │
  SDK)   │   令牌/用户/分组       渠道列表+权重        各厂商     │
        │     (数据库)          负载均衡/重试        Adapter     │
        │        │                                    │        │
        │   [计量:统计token] <───── 响应回流 ──────────┘        │
        │        │                                             │
        │   [扣费:更新配额] ─> 日志/账单                         │
        └────────────────────────────────────────────────────┘
                              │
                         管理后台 Web UI
                    (配渠道、发令牌、看用量)
```

几个分层职责：

- **接入层**：暴露 OpenAI 兼容的 HTTP 路由（如 `/v1/chat/completions`、`/v1/embeddings`、`/v1/models` 等），让现有 OpenAI SDK 改个 `base_url` 就能用。
- **控制层**：鉴权、按"模型 → 渠道"路由、负载均衡、配额检查。
- **适配层（Adapter/Relay）**：把"统一请求"翻译成各上游厂商各自的协议，再把各自的响应翻译回 OpenAI 格式（含流式 SSE）。
- **数据层**：存渠道、令牌、用户、用量、日志（常见用关系型数据库，缓存层可用 Redis 之类）。
- **管理层**：Web 管理后台，配置渠道、签发令牌、查看统计。

> 注：以上是该类网关的通用架构与职责划分；具体路由名、表结构、可选组件以官方仓库为准。

## 3. 核心抽象：五个你必须理解的概念

One API 的配置心智，全建立在这几个对象上：

| 概念 | 类比 | 作用 |
|------|------|------|
| **渠道 Channel** | 上游"供货商账户" | 一条到某供应商的连接：类型(厂商)+上游密钥+可服务的模型列表+权重 |
| **令牌 Token / Key** | 下发给应用的"消费卡" | 应用拿它访问网关；可设额度、可用模型、过期时间 |
| **用户 User** | 账户主体 | 拥有总配额；令牌挂在用户下；用量从用户额度扣 |
| **分组 Group** | "套餐档位" | 把用户/令牌分组，不同组路由到不同渠道集合（如高价优质组 vs 廉价组） |
| **模型映射 Model Mapping** | "别名表" | 把请求里的模型名重写/映射到上游真实模型名 |

它们的关系：

```
  用户(总额度)
    └── 令牌(子额度, 限定可用模型/分组)
            │ 请求 model="gpt-style-x", group=premium
            v
  路由器：在 group=premium 且支持 "gpt-style-x" 的渠道里挑一个
            │
            v
  渠道(类型=某厂商, 上游key, 模型映射: gpt-style-x -> 厂商真实模型名)
```

**为什么要"渠道"和"令牌"两层而不是一层？**
因为它们解决两个方向的问题：**渠道管"对上游怎么连"（密钥、厂商、配额来自供应商），令牌管"对下游怎么发"（额度、权限来自你的分配策略）**。两者解耦后，你换上游渠道完全不影响已发出去的应用令牌。

## 4. 一次请求的完整处理流程

以一次 `/v1/chat/completions` 为例，走完整条链：

```
[1] 应用发请求
    Authorization: Bearer sk-oneapi-xxxx
    body: {"model":"chat-fast","messages":[...],"stream":true}
        │
        v
[2] 鉴权：查令牌 sk-oneapi-xxxx
    · 存在? 未过期? 未禁用?
    · 该令牌允许调 "chat-fast" 吗?
    · 用户/令牌额度 > 0 吗?     ── 任一失败 → 4xx 直接拒
        │ 通过
        v
[3] 选渠道：在(令牌分组 ∩ 支持chat-fast的渠道)集合里
    按权重/优先级做负载均衡，挑出 渠道#7
        │
        v
[4] 协议适配：用渠道#7的 Adapter
    · 模型名映射：chat-fast -> 上游真实模型名
    · 重写鉴权头为上游密钥
    · 字段对齐（不同厂商参数差异）
        │
        v
[5] 转发到上游，开始流式回传
    上游 SSE chunk ─> Adapter 转回 OpenAI 格式 chunk ─> 应用
        │
        v
[6] 计量：累加 prompt_tokens + completion_tokens
        │
        v
[7] 扣费：按"模型单价 × token 数"换算额度，更新用户/令牌余额，写日志
        │
        v
[8] 若[5]上游报错(限流/超时/5xx) → 进入重试/换渠道逻辑(见§5)
```

记忆口诀：**鉴权 → 选路 → 适配 → 转发 → 计量 → 扣费**。前两步是"准入"，中间两步是"翻译与传输"，后两步是"算账"。

## 5. 负载均衡与重试：多渠道高可用

同一个模型常常配**多条渠道**（不同厂商、不同 key、不同区域），网关据此做弹性：

```
  请求 model=chat-fast
        │
        ├─ 候选渠道池(都能服务 chat-fast):
        │     渠道A 权重=5   渠道B 权重=3   渠道C 权重=2
        │
        ├─ 按权重随机/加权挑选 → 选中 渠道A
        │        │
        │        ├─ 成功 → 返回
        │        └─ 失败(限流/超时/上游5xx)
        │               │
        │               └─ 自动重试：从剩余候选(B/C)再挑 → 渠道B
        │                       └─ 成功 → 返回；仍失败 → 继续，直至用尽
        v
   全部失败 → 给应用返回错误
```

几个**权衡点**：

- **权重**：体现"想优先用谁"。便宜/额度多的给高权重，备用的给低权重。加权随机让流量大致按比例分布。
- **优先级/分层**：可让一组渠道做主、另一组做灾备，主全挂才用灾备。
- **失败转移（failover）**：把"可重试错误"（限流 429、网关 5xx、超时）和"不可重试错误"（鉴权失败、请求参数非法）区分开——只有前者才换渠道重试，后者重试也没用，直接返回。
- **渠道健康/自动禁用**：连续失败的渠道可被标记不可用，避免持续把流量打到坏节点。

数值直觉：若渠道 A 月额度 100 万 token、B 50 万、C 30 万，按 $5:3:2$ 加权随机即可让消耗大致正比于额度，避免某条提前耗尽。

## 6. 计量与配额：token 怎么变成钱

这是 One API 区别于"通用网关"的核心增值能力。

**计量**：一次调用产生 `prompt_tokens`（输入）和 `completion_tokens`（输出）。换算成扣减额度的通用思路：

$$\text{cost} = \text{prompt\_tokens}\times p_{in} + \text{completion\_tokens}\times p_{out}$$

其中 $p_{in}, p_{out}$ 是该模型每 token（或每千 token）的单价/倍率。很多模型**输出比输入贵**，所以两者分开算。

```
  示例（单价仅为说明，非真实）：
    输入 1200 token，输出 800 token
    p_in = 0.001 额度/token,  p_out = 0.002 额度/token
    cost = 1200*0.001 + 800*0.002 = 1.2 + 1.6 = 2.8 额度
    扣 user.quota -= 2.8 ，token.used += 2.8
```

**配额（quota）的几层闸门**：

- **用户总额度**：用户级"钱包"，所有令牌共享消耗。
- **令牌子额度**：单张令牌可设独立上限，防止某应用把整个用户额度吃光。
- **限流**：可对令牌/用户做速率限制（RPM/并发），保护上游也防滥用。
- **预扣 vs 后扣**：流式请求开始时输出 token 未知，常先做"余额是否够最小消费"的准入判断，结束后按实际用量结算——这是为什么余额刚好卡线时偶尔会出现"开始了又被截断"的情况。

> 具体倍率表、是否预扣、限流粒度等以官方实现为准；这里讲的是计费网关的通用机制。

## 7. 配置项语义：做什么用、怎么权衡

下面按"类别"讲含义与取舍，**不背具体参数名与默认值（以官方文档为准）**：

| 配置类别 | 作用 | 怎么权衡 |
|----------|------|----------|
| 渠道类型 | 选上游是哪家厂商/协议 | 决定用哪个 Adapter，必须与上游真实接口匹配 |
| 上游 Base URL | 上游网关地址 | 自建/代理/区域域名时要改；本地推理服务填本地地址 |
| 上游密钥 | 调上游的凭证 | 一渠道一密钥；轮换在网关侧完成，应用无感 |
| 渠道可服务模型 | 这条渠道支持哪些模型名 | 路由的依据；填错会导致"无可用渠道" |
| 模型映射 | 别名→上游真实名 | 想对应用稳定暴露统一模型名、屏蔽上游改名 |
| 权重/优先级 | 负载分配与主备 | 见 §5；贵且稳的高权重，备用低权重 |
| 令牌额度/有效期 | 下发给应用的额度与时效 | 按应用重要性分配，临时用途设短有效期 |
| 分组 | 把令牌路由到不同渠道集合 | 做"优质组/廉价组""内部/外部"分层 |
| 数据库 | 持久化渠道/令牌/用量 | 单机可用嵌入式库，多副本需用外部数据库共享状态 |
| 缓存/会话存储 | 加速鉴权、共享限流计数 | 多副本部署时需要外部缓存来共享状态 |
| 日志/统计 | 审计与计费追溯 | 生产环境务必开启并定期归档 |

**部署中最容易被忽略的一点**：当你跑**多个 One API 副本**做高可用时，渠道/令牌/用量这些状态必须放在**共享的外部数据库**（和共享缓存）里，否则各副本各算各的账、限流计数也对不上。单副本时用嵌入式存储很方便，但**不能水平扩展**。

## 8. 部署形态

```
  ┌── 单机/容器（最简单） ─────────────────────────┐
  │   docker run one-api  →  内置/挂载数据库         │
  │   适合：个人、小团队、PoC                         │
  └─────────────────────────────────────────────┘

  ┌── 多副本 + 外部数据库（高可用） ────────────────┐
  │       负载均衡器(LB)                            │
  │      ┌────┴────┐                               │
  │  one-api#1  one-api#2  one-api#3               │
  │      └────┬────┘                               │
  │   共享数据库 + 共享缓存(状态/限流/会话)            │
  └─────────────────────────────────────────────┘

  ┌── 编排到 Kubernetes ──────────────────────────┐
  │   Deployment(多Pod) + Service + 外部DB/Redis    │
  │   见 [[llmops/kubernetes]]                      │
  └─────────────────────────────────────────────┘
```

放在更大的链路里，One API 常和**应用层网关/RAG/Agent**配合：

```
  用户 → 业务后端 → [One API 网关] → 各家大模型
                        ↑
                 也可前置通用网关(如 Higress)做
                 入口鉴权/WAF/灰度，再进 One API
```

## 9. 与同类对比（选型）

| 方案 | 定位 | 何时选它 |
|------|------|----------|
| One API | 大模型多供应商**分发+计费+多租户**网关 | 要统一接口 + 给多团队/客户发额度算账 |
| 通用 API 网关 / [[Higress]] | 通用流量入口（鉴权/路由/WAF/灰度） | 需要企业级入口治理；可前置在 One API 之前 |
| LiteLLM 等 SDK/代理 | 多供应商**统一调用库/轻代理** | 偏 SDK 内嵌、轻量统一调用，计费多租户较弱时 |
| 自建 MaaS 平台 [[llm-maas/README]] | 完整模型即服务平台 | 需要更重的产品化（模型托管、计费、控制台一体） |
| 直连各厂商 SDK | 不加中间层 | 只用一家、量小、不需要计费与多租户 |

一句话：**One API 的甜点区是"多供应商 + 多租户 + 要算账"**。如果只用一家模型且不需要发额度，直连更简单；如果要企业级入口治理，让通用网关在前、One API 在后各司其职。

## 常见问题 / 坑

| 现象 | 可能原因 | 处理方向 |
|------|----------|----------|
| 报"无可用渠道 / no available channel" | 没有渠道支持该 model 名，或匹配渠道全被禁用/超额 | 检查渠道的"可服务模型"列表与模型映射；看渠道是否被自动禁用 |
| 401/鉴权失败 | 应用用的是上游 key 而非 One API 令牌；或令牌过期/禁用 | 应用必须用 One API 发的令牌；上游 key 只配在渠道里 |
| 上游 401 但 One API 令牌没问题 | 渠道里配的上游密钥失效/额度耗尽 | 在渠道侧轮换/补充上游密钥 |
| 余额够却被中途截断 | 流式预扣判断卡线，实际输出超出余额 | 留足余额缓冲；理解预扣/后扣机制 |
| 多副本下额度/限流对不上 | 各副本用了各自的本地状态 | 改用共享外部数据库 + 共享缓存 |
| 改了 base_url 还连不上上游 | 上游域名/区域/代理不对，或网络不通 | 核对渠道 Base URL；自建代理时确认链路可达 |
| 流式格式应用解析不了 | 上游流式与 OpenAI SSE 有差异，Adapter 未对齐 | 选对渠道类型；以官方支持的厂商类型为准 |
| 计费倍率和预期不符 | 模型单价/倍率配置与认知不一致 | 核对该模型计费倍率配置，区分输入/输出单价 |

> 以上为该类网关的通用经验；精确的报错文案、参数名、计费倍率请以 One API 官方仓库与文档为准，不要凭记忆当真。
