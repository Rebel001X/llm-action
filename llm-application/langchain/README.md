## 0. 一句话锚点

把一个 LLM 应用想象成一条**流水线**：用户输入 → 拼 prompt → 调模型 → 解析输出 →（可能）查资料/调工具 →（可能）记住上一轮 → 返回结果。

LangChain 做的事就一句话：**把这条流水线上的每个零件标准化成可插拔的「积木」，再给你一根管道把它们拼起来。**

```
裸调 LLM：                       LangChain 编排：
┌──────────┐                    ┌────────┐ ┌────────┐ ┌────────┐
│ 你手写所有 │                    │ Prompt │→│  LLM   │→│ Parser │
│ 字符串拼接 │   ===升级==>        └────────┘ └────────┘ └────────┘
│ + HTTP 请求│                         ↑ 可换 ↑ 可换  ↑ 可换
│ + 重试逻辑 │                    每块独立、可替换、可测试、可观测
└──────────┘
```

## 1. 地基：先看清「裸调一次 LLM」缺什么

不假设你记得任何前置。一次最朴素的 LLM 调用，本质是一个 **HTTP 请求**：

```
输入：一段文本 prompt（字符串）
   ↓  POST https://api.xxx/chat/completions
输出：一段文本 completion（字符串）
```

它有四个「天生缺陷」，每个缺陷正好对应 LangChain 的一个核心抽象：

| 裸调的缺陷 | 含义（从最底层说） | LangChain 的解药 |
|-----------|-------------------|-----------------|
| **无状态** | 模型每次调用互不记得，是纯函数 `f(prompt)→text` | **Memory** |
| **不知道私有/最新知识** | 训练数据有截止日，且不含你公司的文档 | **RAG / Retriever** |
| **不能行动** | 只会吐字，不能查天气、跑代码、下订单 | **Tool + Agent** |
| **拼 prompt 全靠手** | 变量替换、few-shot 示例、角色设定全是字符串体力活 | **PromptTemplate** |

> 关键直觉：LLM 是一个**无状态、封闭、只会说话**的函数。LangChain 的全部价值，就是围绕这个函数补上「记忆、知识、行动、组装」这四件外套。

## 2. 为什么需要「编排框架」

你完全可以不用框架，自己写。那为什么还要它？答案是：当应用从「调一次」变成「调很多次、还要互相依赖」时，复杂度会**爆炸**。

```
单步：           prompt ─→ LLM ─→ 答案                （手写够用）

多步（RAG）：     问题 ─→ 改写 ─→ 检索 ─→ 拼上下文 ─→ LLM ─→ 解析 ─→ 答案
                                                                  （开始头疼）

Agent 循环：     问题 ─→ LLM 想 ─→ 选工具 ─→ 执行 ─→ 观察 ─→ 再想 ─→ ...（直到完成）
                          ↑__________________________________________│
                                      （手写=灾难）
```

编排框架解决三类问题：

1. **解耦（换零件不改主干）**：今天用 GPT，明天换成本地 Qwen，只改一行 `model=...`，业务流程不动。
2. **组合（把小积木拼成大流程）**：检索器、提示词、解析器、记忆，像乐高一样 `A → B → C`。
3. **横切关注点（callbacks / 可观测 / 流式 / 重试 / 缓存）**：这些「每一步都要做但和业务无关」的事，框架统一接管。

```
        ┌─────────── 横切层（callbacks/trace/cache/重试）───────────┐
        │                                                          │
用户 ─→  │  Prompt ──→ Model ──→ Parser ──→ Retriever ──→ Memory   │ ─→ 用户
        │   ↑ 每一步都被同一套机制「监听、记录、流式、缓存」          │
        └──────────────────────────────────────────────────────────┘
```

一句话：**编排框架 = 业务积木（横向）× 横切能力（纵向）的乘积。** 自己写也能写，但写出可维护的横切层成本极高。

## 3. 核心抽象总览（一张图记住全家桶）

```
                       ┌──────────────────────────────┐
                       │            Chain / LCEL        │  ← 编排：把下面零件串起来
                       └───────────────┬────────────────┘
        ┌───────────┬──────────┬───────┼────────┬───────────┬──────────┐
        ▼           ▼          ▼       ▼        ▼           ▼          ▼
   PromptTemplate  Model    OutputParser Memory  Retriever   Tool      Agent
   （拼提示词）   （调模型） （解析输出） （记忆） （查资料）   （动手）  （决策循环）
        │           │          │       │        │           │          │
   变量→字符串    text/json   str→结构   读写历史  向量检索   函数调用   边想边做
```

逐个用一句「从底层」的话定义：

- **Model（LLM / ChatModel）**：被包装成统一接口的「会说话的函数」。`ChatModel` 接收消息列表（system/human/ai），返回一条 ai 消息。
- **PromptTemplate**：带「填空位」的字符串模板，`{变量}` 在运行时被实参替换——把「写死的 prompt」变成「带参数的函数」。
- **OutputParser**：把模型吐出的**自由文本**，强制变回程序能用的**结构**（如 JSON、列表、Pydantic 对象）。
- **Chain**：一串「输入→输出」的零件按顺序连起来，上一个的输出喂给下一个。
- **Memory**：在多轮对话间**持久化历史**，并在每次调用前注入 prompt，给无状态模型「装上记忆」。
- **Tool**：一个**带描述的普通函数**（搜索、计算器、SQL、HTTP），让模型可以「请求执行」它。
- **Agent**：一个**带循环的决策者**——让模型自己决定「现在该调哪个工具 / 还是该回答了」。

## 4. Prompt 模板：把字符串拼接升级为函数

最底层问题：prompt 里 90% 是固定话术，10% 是变量。手写 `f"你是助手，请翻译：{text}"` 在示例多、角色多时会变成字符串地狱。

```
PromptTemplate（普通模板）：
   "把下面句子翻译成{language}：{text}"
        ↓ .format(language="法语", text="你好")
   "把下面句子翻译成法语：你好"

ChatPromptTemplate（对话模板）：
   ┌ system: 你是专业翻译，只输出译文
   ├ human : 把下面句子翻译成 {language}：{text}
   └─────────────────────────────────────────
        ↓ 运行时填充
   [SystemMessage(...), HumanMessage("...法语...你好")]
```

三个进阶能力：

1. **Few-shot（少样本）**：把「示例输入→示例输出」对塞进模板，教模型照葫芦画瓢。
2. **角色分离**：system（人设/规则）、human（用户话）、ai（历史回答）分开，符合 Chat 模型的训练范式。
3. **Partial（偏应用）**：先填一部分变量（如固定的当前日期），剩下的运行时再填。

> 直觉：PromptTemplate 之于 prompt，就像 **函数签名** 之于一段写死的代码——参数化让它可复用、可测试。

## 5. Chain（链）：把零件按顺序焊起来

Chain 就是「**数据流图**」。最简单的链是「模板→模型→解析」三连：

```
输入 {text:"猫"} 
   │
   ▼
[PromptTemplate] ──"给我一个关于猫的笑话"──▶ [Model] ──"为什么猫…"──▶ [OutputParser] ──▶ 干净字符串
```

常见链型：

```
顺序链（Sequential）：   A ─→ B ─→ C        （A 的输出是 B 的输入）

路由链（Router）：           ┌─→ 数学链
                  问题 ─→ 判断 ─┼─→ 历史链   （按内容分流到不同子链）
                            └─→ 闲聊链

并行链（Parallel）：      输入 ─┬─→ 摘要 ──┐
                              └─→ 关键词 ─┴─→ 合并   （同时跑，省时间）
```

注意：老式 `LLMChain`、`SequentialChain` 这类「类继承式」API 已被官方逐步标记为 legacy，新代码应优先用下面的 **LCEL**。

## 6. LCEL：LangChain 表达式语言（重点中的重点）

LCEL（LangChain Expression Language）是 LangChain 现代的**核心编排语法**，用一个 `|`（竖线，管道符）把零件连起来，像 Unix 管道：

```
chain = prompt | model | output_parser
          ▲        ▲          ▲
        Runnable Runnable  Runnable   ← 三者都实现了统一接口 Runnable
                  │
        管道含义：prompt 的输出 → 喂给 model → 输出 → 喂给 parser
```

**为什么 LCEL 是个大事？** 因为只要拼好这条链，你**免费**得到一整套能力：

| 你只写 `a \| b \| c` | 自动获得的能力 | 底层方法 |
|----------------------|----------------|----------|
| — | 同步调用 | `.invoke()` |
| — | 流式逐 token 输出 | `.stream()` |
| — | 异步并发 | `.ainvoke()` |
| — | 批量处理一组输入 | `.batch()` |
| — | 自动并行 / 重试 / 回退 | `.with_retry()` 等 |

```
Runnable 协议（所有积木的统一插口）：
   ┌─────────────────────────────────────────┐
   │ invoke / stream / batch / ainvoke / ...  │
   └─────────────────────────────────────────┘
        ▲           ▲            ▲
     Prompt       Model        Parser     ← 都长一样的口 → 才能 | 起来
```

并行与分支用 `RunnableParallel`（字典）和 `RunnablePassthrough`（原样透传）：

```
{
  "context": retriever,            # 并行：检索
  "question": RunnablePassthrough() # 并行：原样透传问题
} | prompt | model | parser
```

> 直觉：LCEL 把「编排」从**写胶水代码**变成**写一个表达式**。`|` 的本质是函数复合 `c∘b∘a`，而 Runnable 协议保证任意两块都能拼。

## 7. Memory：给无状态模型装上记忆

模型是纯函数，自己不记得上一句。Memory 的机制其实很朴素：**把历史对话拼回到 prompt 里**。

```
第 3 轮提问时，实际发给模型的是：
   ┌──────────── Memory 注入 ────────────┐
   │ Human: 我叫小明                       │
   │ AI:   你好小明                        │  ← 前两轮历史
   │ Human: 我喜欢猫                       │
   │ AI:   猫很可爱                        │
   └──────────────────────────────────────┘
   Human: 我叫什么名字？   ← 本轮新问题
        ↓
   模型看到全部历史，于是答得出「小明」
```

但历史会越拼越长，撞上**上下文窗口上限**。所以有不同记忆策略：

| 策略 | 机制 | 代价 |
|------|------|------|
| Buffer（全量缓冲） | 原样保存所有历史 | 简单，但 token 暴涨 |
| Window（窗口） | 只保留最近 k 轮 | 丢远期信息 |
| Summary（摘要） | 用 LLM 把旧历史压成摘要 | 省 token，但多花一次调用 + 可能失真 |
| Token-Buffer | 按 token 预算裁剪 | 精确控成本 |

```
窗口策略 k=2：
   [轮1][轮2][轮3][轮4][轮5]
                  └─保留─┘  ← 只喂最近 2 轮，前面丢弃
```

> 现代实践：LangChain 把状态管理逐步迁移到 **LangGraph** 的「持久化状态」，传统 `Memory` 类多用于简单场景。

## 8. Tool + Agent：让模型从「会说」到「会做」

### Tool（工具）= 带说明书的函数

一个 Tool 三要素：**名字 + 自然语言描述 + 函数本体**。描述至关重要——模型靠读描述来决定「这个工具能干嘛、该传什么参数」。

```
Tool「天气查询」
  ├ name: get_weather
  ├ description: "输入城市名，返回该城市当前天气"   ← 模型靠它选工具
  └ func: def get_weather(city): return ...
```

### Agent = 让模型自己跑循环

Agent 的核心是经典的 **ReAct（Reason + Act，边想边做）** 循环：

```
        ┌───────────────────────────────────────────┐
        │                                             │
  问题 ─▶ [模型 Thought：我该查天气]                    │
        │        ↓                                    │
        │ [Action：调用 get_weather("北京")]            │
        │        ↓                                    │
        │ [Observation：晴，25℃]  ───────────────────┐ │
        │        ↓                                   │ │
        │ [模型 Thought：信息够了]                     │ │
        │        ↓                                   │ │
        └─▶ [Final Answer：北京今天晴，25℃] ←─────────┘ │
                                                       │
            若信息不够 → 继续选下一个工具，回到顶部 ──────┘
```

```
单步 Chain：   输入 → → → 输出        （流程固定，开发者画好的图）
Agent 循环：   输入 → 模型自己决定走几步、走哪条 → 输出  （流程由模型动态决定）
```

> 关键区别：**Chain 的路径是你写死的；Agent 的路径是模型当场决定的。** 这带来灵活性，也带来不可控（见第 11 节批评）。现代 LangChain 推荐用 **LangGraph** 把 Agent 建模成显式状态机，比传统 `AgentExecutor` 更可控、可调试。

## 9. RAG 集成：把私有/最新知识喂给模型

RAG（Retrieval-Augmented Generation，检索增强生成）解决「模型不知道你公司文档」的问题。机制：**先检索相关片段，再把片段塞进 prompt 让模型基于它作答。** 详见 [[llm-application/rag/README]]。

```
离线（建库一次）：
   文档 ─→ 切块(chunk) ─→ Embedding(向量化) ─→ 存入向量库
   "公司手册.pdf"   [块1][块2]…    [0.1,0.7,…]      VectorStore

在线（每次提问）：
   问题 ─→ Embedding ─→ 向量库相似检索 top-k ─→ 拿到相关块
                                                    │
   "如何报销?"                              [块7][块12][块3]
                                                    │
        ┌───────────────────────────────────────────┘
        ▼
   塞进 prompt：「根据以下资料回答：{块7}{块12}{块3}\n问题：如何报销?」
        ▼
   Model ─→ 基于资料的答案（可附引用来源）
```

LangChain 用 LCEL 写 RAG 极简洁：

```
{"context": retriever, "question": RunnablePassthrough()}
     │ 并行：左边去向量库检索，右边把问题原样传
     ▼
prompt   →   model   →   parser   →   带依据的答案
```

LangChain 在 RAG 里提供的标准积木：`DocumentLoader`（加载各种格式）、`TextSplitter`（切块）、`Embeddings`（向量化接口）、`VectorStore`（向量库统一接口，背后可换 FAISS/Chroma/Milvus/PGVector…）、`Retriever`（检索器，统一 `.invoke(query)→docs`）。

> 价值定位：LangChain 在 RAG 上的最大贡献是**把几十种向量库/Loader/Embedding 抽象成统一接口**，换底座只改一行。深入原理见 [[llm-application/rag/README]]。

## 10. 何时用 / 何时不用（决策树）

```
你的需求是？
│
├─ 只调一次 LLM、prompt 固定、无工具无检索
│     └─▶ ❌ 别上 LangChain，直接用模型 SDK（如 openai/anthropic）几行就够
│
├─ 需要 RAG / 多步链 / 流式 / 想随时换模型底座
│     └─▶ ✅ 用 LCEL，收益明显（统一接口 + 免费横切能力）
│
├─ 需要 Agent 自主决策、多工具、循环、人审介入
│     └─▶ ✅ 用 LangGraph（比裸 AgentExecutor 可控）
│
├─ 已重度依赖某云厂商的全套 SDK / 团队反感额外抽象
│     └─▶ ⚠️ 评估「抽象税」，可能自己写薄封装更透明
│
└─ 生产级、需严格可观测/评测/版本锁定
      └─▶ ✅ 配合 LangSmith（追踪+评测），但要锁版本
```

经验法则：

- **越接近「单次、确定性」的任务，越不需要框架**；裸 SDK 更短、更透明、更少惊喜。
- **越接近「多步、动态、要换零件」的任务，框架收益越大**；尤其 RAG 与 Agent。
- **生产环境务必锁定版本**（见下节），并配 LangSmith 做可观测。

## 11. 批评与争议（不吹不黑）

LangChain 是社区事实标准之一，但争议也最大。诚实列出：

| 批评 | 具体含义 | 缓解方式 |
|------|----------|----------|
| **抽象税（over-abstraction）** | 简单任务被包了好几层，读源码才知道实际发了什么 prompt | 优先用透明的 LCEL；用 LangSmith 看真实 prompt |
| **版本动荡** | API 大改过多次（旧 Chain → LCEL → LangGraph），教程很快过时 | **生产严格锁版本**；认准「现代」写法 |
| **黑盒 prompt** | 内置 Agent/Chain 的 prompt 藏在库里，调优困难 | 自己写 prompt，少用「魔法」预设链 |
| **调试难** | 多层封装出错时栈很深，难定位 | 全程接 callbacks / LangSmith 追踪 |
| **包庞大、依赖多** | 装一个引一堆 | 用拆分后的 `langchain-core` / 各 partner 包按需装 |
| **「不就是字符串拼接？」** | 批评者认为核心价值被高估 | 承认：单步确实如此；价值在编排与生态广度 |

```
社区典型态度光谱：
  「啥都别用，自己写」 ←─────────────────────────→ 「全套 LangChain+LangSmith」
                          ▲ 多数务实做法：
                          用 LCEL 做编排 + RAG 标准件，
                          但 prompt 自己写、版本锁死、关键路径自控
```

> 平衡观点：把 LangChain 当**「可选的标准件库 + 编排语法」**，而非「必须信奉的全家桶」。需要的积木拿来用，不需要的别硬塞抽象。

## 数值例子 / 对照：算一笔 RAG 的账

假设一个客服 RAG：检索 top-4 文档块，每块约 250 token，系统提示约 200 token，用户问题约 50 token，模型回答约 300 token。

**单次请求 token + 成本估算（手算）**（价格假设输入约 \$0.5/百万、输出约 \$1.5/百万，**具体以各模型官方价为准**）：

$$
T_{in} = \underbrace{200}_{system} + \underbrace{4\times250}_{检索块} + \underbrace{50}_{问题} = 1250,\quad T_{out}=300,\quad T_{total}=1550 \text{ token}
$$

$$
\text{cost} = \tfrac{1250}{10^6}\times 0.5 + \tfrac{300}{10^6}\times 1.5 \approx \$0.00108 \;\Rightarrow\; 10\text{万次/天} = 10^5\times0.00108 \approx \$108/\text{天} \approx \$3240/\text{月}
$$

**延迟拆解（典型量级，约值）：**

```
检索(向量库)  ≈  20~50 ms   ┐
拼 prompt     ≈   <1 ms     ├─ 几乎可忽略
首 token(TTFT)≈ 200~800 ms  ┘
生成 300 token：若约 50 token/s ⇒ 300/50 = 6 s   ← 主要耗时在这
─────────────────────────────────────────────
端到端 ≈ 6.5~7 s（用 .stream() 流式可让用户「立刻看到字」改善体感）
```

**关键洞察（从数字读出工程结论）：** ① **检索几乎不耗时，生成才是大头** → 优化延迟主攻「输出长度 + 流式」而非检索；② **top-k 越大输入越贵** → `k=4`→`k=10` 输入从 1250 涨到 2750、成本翻倍而召回未必更好，要权衡；③ **Summary Memory 省输入 token** 但多一次 LLM 调用，只有长对话才划算。

## 常见问题（FAQ）

| 问题 | 简答 |
|------|------|
| LangChain 是模型吗？ | 不是。它是**编排框架/胶水层**，自己不含模型，要外接 OpenAI/Anthropic/本地模型等。 |
| LCEL 和老 Chain 区别？ | LCEL 用 `\|` 管道 + 统一 `Runnable` 接口，**免费**带流式/异步/批处理；老 `LLMChain` 是 legacy。 |
| LangChain vs LangGraph？ | LangChain 偏「线性链 + 标准件」；LangGraph 偏「带循环/分支/状态的图」，更适合复杂 Agent。 |
| LangChain vs LlamaIndex？ | LangChain 编排面更广（Agent/Tool）；LlamaIndex 更专注 RAG/索引；两者可混用。 |
| 简单任务该用吗？ | 单步、prompt 固定、无工具 → **直接用模型 SDK 更好**，别引入抽象税。 |
| 生产最大坑？ | **版本动荡**：务必锁版本，并接 LangSmith 做可观测与回归。 |
| Chain 和 Agent 怎么选？ | 流程能你画死 → Chain；流程要模型当场决定走几步 → Agent。 |
| Memory 会无限变长吗？ | 会撞上下文上限，用 Window/Summary/Token-Buffer 策略裁剪。 |
| 工具是怎么被「选中」的？ | 模型读每个 Tool 的**自然语言描述**来决定调谁，所以描述要写清楚。 |
| RAG 一定要用 LangChain 吗？ | 不一定，但它把 Loader/Splitter/VectorStore/Retriever 标准化，换底座成本低。详见 [[llm-application/rag/README]]。 |
