## 0. 一句话锚点

> **RAG = 把"开卷考试"搬给大模型**：考试前不要求模型把所有知识背进参数里（闭卷、易记错=幻觉），而是允许它在答题时翻一本随时可换的"参考书"（你的知识库）。

$$\text{答案} = \text{LLM}\big(\underbrace{\text{用户问题}}_{q} \;+\; \underbrace{\text{检索到的相关片段}}_{\text{context}}\big)$$

核心只有两步：**检索（Retrieval）**找到相关资料，**生成（Generation）**基于资料作答。所有花哨技巧都是在优化这两步。

## 1. 地基：RAG 解决什么问题

大模型（LLM）的"知识"被固化在训练时学到的几百亿个参数里。这带来三个天然缺陷，RAG 正是对症下药：

**问题①：知识冻结（Knowledge Cutoff）**
模型训练有截止日期。问它"昨天发布的财报"，它根本不知道。重新训练一次要几百万美元、几周时间——不可能每天训。
→ **RAG 的解法**：知识放在外部库里，库随时增删改，模型代码一行不动。

**问题②：幻觉（Hallucination）**
模型本质是"预测下一个最像样的词"。当它不知道答案时，不会说"我不知道"，而会**一本正经地编**一个看起来合理的答案。
→ **RAG 的解法**：把真实资料塞进上下文，让模型"照着资料说"，并能给出**出处**（溯源），把"凭记忆胡诌"变成"看着材料回答"。

**问题③：私有/领域知识缺失**
公司内部文档、个人笔记从未进入过训练集，通用大模型完全不懂。
→ **RAG 的解法**：把私有文档建成库，无需把敏感数据拿去微调（fine-tune），即插即用。

```
       为什么不直接微调(Fine-tune)就好?
  ┌────────────────────┬──────────────────────┐
  │      微调            │        RAG            │
  ├────────────────────┼──────────────────────┤
  │ 把知识"焊"进参数    │ 知识放外部库          │
  │ 更新=重训, 慢且贵   │ 更新=改库, 秒级        │
  │ 难溯源(说不清来源)  │ 可给出处, 可审计       │
  │ 改一句话很难"删除"  │ 删一条记录即可         │
  │ 擅长"改风格/学技能" │ 擅长"补事实/补时效"    │
  └────────────────────┴──────────────────────┘
  实践: 两者常组合——微调调"会不会说", RAG 补"说什么".
```

> 一句记忆：**微调改变模型的"行为"，RAG 改变模型能看到的"事实"。**

## 2. 整体架构：两条流水线

RAG 系统在时间上分成**离线（建库，慢，做一次）**和**在线（问答，快，每次请求）**两条流水线。

```
============ 离线: 建知识库 (Indexing, 跑一次) ============
  原始文档              切块              向量化            写入向量库
 ┌─────────┐  Load   ┌────────┐ Chunk ┌─────────┐ Embed ┌──────────┐
 │PDF/Word │ ──────▶ │ 全文本  │ ────▶ │ 一堆小块 │ ────▶ │ [向量+原文]│
 │网页/MD   │         │        │       │ chunk_i │       │  存索引   │
 └─────────┘         └────────┘       └─────────┘       └──────────┘
                                                              │
============ 在线: 实时问答 (Retrieval+Generation, 每次请求) ┘ ====
  用户问题 q
     │ Embed(同一个模型!)
     ▼
 ┌────────┐  ANN搜索  ┌──────────┐  重排   ┌─────────┐  填模板  ┌──────┐
 │ q向量   │ ───────▶ │ top-N 候选│ ─────▶ │ top-k精排│ ──────▶│Prompt │
 └────────┘          └──────────┘         └─────────┘         └──┬───┘
                       (粗召回多)           (精选少而准)            │
                                                          ┌───────▼──────┐
                                                          │   LLM 生成    │
                                                          │ 基于context作答│
                                                          └───────┬──────┘
                                                                  ▼
                                                            带出处的答案
```

**关键不变量**：建库时用的 embedding 模型，和在线给问题向量化用的 embedding 模型**必须是同一个**，否则两套向量不在同一空间，检索全乱。详见 [[llm-application/rag/embedding]]。

下面 3~7 节逐个拆解在线流水线的每一环。

## 3. 切块（Chunking）——把长文档切成"可检索的小单元"

**为什么要切？** 两个硬约束：
1. **检索粒度**：一整本 300 页 PDF 作为一个向量，语义被"平均"掉了，问"第 5 章某细节"也匹配不到。切小才能精准定位。
2. **上下文窗口**：LLM 一次能读的 token 有上限。不可能把整本书塞进去，只能塞最相关的几块。

```
长文档 ──────────────────────────────────────────▶
[................第1章................第2章........]
切块 (chunk_size=400, overlap=50):
[ block1 ]
       [ block2 ]      ← overlap 重叠区, 防止把一句话/一个概念切断
              [ block3 ]
   └─重叠─┘
```

**两个核心参数：**
- **chunk_size（块大小）**：每块多少 token。太大→检索不精准、浪费上下文；太小→语义不完整、上下文被切碎。常见 256~512 token。
- **chunk_overlap（重叠）**：相邻块共享一段文字（如 10%~20%）。作用：避免把一个完整句子/论点从中间劈开，导致两块都看不全。

**进阶切法（呼应"段落智能划分"）：**
- **固定长度切**：最简单，按字符/token 数硬切。可能切断句子。
- **按结构切**：按 Markdown 标题、段落、句子边界切——语义更完整。
- **语义切块（Semantic Chunking）**：用 embedding 算相邻句子的相似度，相似度骤降处=主题切换点，在此断开。
- **父子块（Parent-Child）**：检索用小块（精准匹配），喂给 LLM 时返回它所在的大块（上下文完整）。见第 8 节。

## 4. Embedding——把文字变成"语义坐标"

**最底层的直觉**：计算机不懂文字，只懂数字。Embedding 就是一个模型，把一段文字映射成一个**定长向量**（一串数，如 768 或 1536 个），使得**语义相近的文字，向量在空间里也相近**。

```
"猫"     ─Embed─▶ [0.21, -0.4, 0.9, ...]  ┐
"小猫咪" ─Embed─▶ [0.19, -0.38, 0.91,...] ┤ 这两个向量挨得很近
"汽车"   ─Embed─▶ [-0.7, 0.2, -0.1, ...]  ┘ 这个离得很远

  语义空间(示意, 实际是几百维):
        猫● ●小猫咪
                        ●狗
   汽车●  ●卡车
```

**怎么衡量"近"？** 最常用**余弦相似度（cosine similarity）**——看两个向量的夹角，只关心方向不关心长度：

$$\text{cos}(\vec{a}, \vec{b}) = \frac{\vec{a}\cdot\vec{b}}{\|\vec{a}\|\,\|\vec{b}\|}\in[-1,1]$$

值越接近 1 越相似。检索的本质就是：**把问题向量和库里每个块向量算相似度，取最高的几个。**

> 进阶（呼应原文 Instructor/动态向量）：有的 embedding 模型支持**指令化**，对"用于检索的查询"和"用于入库的文档"用不同前缀编码，针对 QA 场景优化召回。

详细的 embedding 模型选型、维度权衡见 [[llm-application/rag/embedding]]。

## 5. 向量检索（召回）——在亿级向量里"光速"找近邻

**问题**：库里有 100 万个向量，每次提问都和每个都算一遍余弦相似度（暴力搜索/Brute Force）太慢。

**解法：近似最近邻（ANN, Approximate Nearest Neighbor）**——不保证找到绝对最近的，但以极小的精度损失换取百倍提速。最主流的是 **HNSW**（分层可导航小世界图）：

```
HNSW 直觉: 像"地图导航", 先看高速路(稀疏层)再下到小路(密集层)
  Layer 2 (稀疏)   ●────────────────────●      先大跳
                   │                    │
  Layer 1          ●───●────────●───────●      再中跳
                   │   │        │       │
  Layer 0 (全量)   ●─●─●─●─●─●─●─●─●─●─●─●     最后小跳到目标
                          ▲
                       查询落点, 逐层逼近最近邻
```

向量库（[[llm-application/vector-db/README]]）负责管理索引、增删改、过滤等工程问题。

**混合检索（Hybrid Search，呼应原文 BM25+HNSW 融合）：**
纯向量检索擅长"语义相近"，但对**精确关键词/专有名词/型号代码**反而弱（"GPT-4o" 这种 token 语义不明显）。于是把两路召回融合：

```
        用户问题 q
        ┌────┴────┐
        ▼         ▼
  向量检索(语义)  BM25/关键词(字面)
   "意思相近"      "词命中"
        └────┬────┘
             ▼
     融合排序 (如 RRF 倒数排名融合)
             ▼
        候选 top-N
```

- **向量检索**：召回语义相关的（同义、改写也能匹配）。
- **BM25（关键词）**：召回字面命中的（精确术语、代码、人名）。
- **RRF（Reciprocal Rank Fusion）**：把两个排名按 $\sum \frac{1}{k+\text{rank}}$ 融合，互补取长。

## 6. 重排（Rerank）——从"粗召回"里精挑细选

**为什么召回完还要再排？** 检索阶段为了快，用的是 Bi-Encoder：问题和文档**各自独立**编码成向量再算相似度——快，但没让问题和文档"互相看一眼"，排序不够准。所以先**粗召回 top-N（如 50 条，宁滥勿缺）**，再用更准但更慢的模型精排出 **top-k（如 5 条）**。

```
Bi-Encoder (检索, 快):          Cross-Encoder (重排, 准):
 q ─Embed─▶ [向量]               ┌─────────────┐
 d ─Embed─▶ [向量]    算cos      │ q + d 一起喂 │ ─▶ 相关分(0~1)
 两者分开编码, 可预存            │  让它们交互  │
 → 适合海量, 但粗                └─────────────┘
                                 不能预存, 但精
召回50条 ───Cross-Encoder逐条打分排序──▶ 取最相关5条
```

**为什么不一开始就用 Cross-Encoder？** 因为它要把 (问题, 每个文档) 拼起来现算，100 万文档算不过来。所以分两段：**Bi-Encoder 快速粗筛 → Cross-Encoder 精排**，又快又准。

> 经验：加重排往往是性价比最高的一步提升，能显著改善最终答案质量。

## 7. 拼上下文 + 生成——把资料"喂"给模型作答

把 top-k 片段填进 Prompt 模板，连同问题一起交给 LLM：

```
┌──────────────── Prompt 模板 ────────────────┐
│ 你是问答助手。只根据下面【参考资料】回答,    │
│ 资料中没有的内容请回答"资料中未提及",        │
│ 不要编造。回答末尾标注引用编号。             │
│                                              │
│ 【参考资料】                                 │
│ [1] {chunk_1 内容}  (来源: 文档A 第3页)      │
│ [2] {chunk_2 内容}  (来源: 文档B)            │
│ ...                                          │
│                                              │
│ 【问题】{用户原问题}                          │
│ 【回答】                                     │
└──────────────────────────────────────────────┘
```

**几个关键设计点：**
- **强约束指令**："只根据资料回答""没有就说没有"——这是压制幻觉的最后一道闸。
- **引用编号**：让模型标 `[1][2]`，实现**可溯源**，用户能点回原文核对。
- **"Lost in the Middle"（呼应原文）**：研究发现 LLM 对上下文**开头和结尾**最敏感，放中间的内容容易被忽略。所以把最相关的片段放在**最前或最后**，别埋中间。

```
LLM 注意力对位置的敏感度(示意):
注意力 ▲
      │█                          █
      │██                        ██
      │███                      ███
      │████____低谷(易被忽略)___████
      └──────────────────────────────▶ 上下文位置
       开头        中间         结尾
   → 把最重要的片段放两端
```

## 8. 进阶技巧（呼应原文的"百花齐放"）

当基础流程不够用时，常见的增强手段：

| 技巧 | 解决的痛点 | 一句话原理 |
|------|-----------|-----------|
| **HyDE** | 短问题向量信息太少，召回差 | 先让 LLM 据问题**生成一段假设答案**，用这段（更长更具体）去检索，召回率↑ |
| **父子块 / 小块检索大块返回** | 小块好检索但上下文不全 | 用小块匹配，命中后**返回它所属的大块**给 LLM |
| **多查询改写（Multi-Query）** | 单一问法漏召回 | LLM 把问题**改写成多个版本**分别检索再合并 |
| **上下文压缩（LLMLingua，呼应原文）** | 召回太多挤爆窗口、稀释重点 | 压缩/裁剪掉无关句子，只留与问题相关的部分 |
| **Self-RAG（呼应原文）** | 流程环节多、要不要检索难定 | 让模型**自己决定**何时检索、检索到的是否有用、要不要重检 |
| **元数据过滤** | 检索范围太大 | 先按 `时间/部门/标签` 过滤，再向量检索 |

```
HyDE 示意:
 短问题 q ──直接检索──▶ 信息少, 召回飘
 短问题 q ─LLM生成假设答案─▶ "一段像样的答案" ──检索──▶ 信息丰富, 召回准
           (答案可能有错没关系, 只用它的"语义"去找真资料)
```

## 9. 关键参数总表（一张表调参）

| 参数 | 作用 | 太小 | 太大 | 常见起点 |
|------|------|------|------|---------|
| `chunk_size` | 每块 token 数 | 语义碎 | 检索糊 | 256~512 |
| `chunk_overlap` | 块间重叠 | 切断句意 | 冗余多 | 10%~20% |
| `top_k` (召回) | 粗召回数量 | 漏答案 | 噪声多/慢 | 20~50 |
| `top_n` (重排后) | 喂给 LLM 的块数 | 信息不足 | 撑爆窗口/稀释 | 3~8 |
| `相似度阈值` | 过滤弱相关 | 放进噪声 | 误杀好块 | 经验定 |
| `temperature` | 生成随机性 | 死板 | 易跑偏/幻觉 | 0~0.3 |
| `embedding 维度` | 向量长度 | 表达弱 | 存储/算力↑ | 768~1536 |

> 调参口诀：**召回阶段宁多勿少（top_k 大）→ 重排阶段宁缺勿滥（top_n 小而精）。**

## 10. 数值例子（手算一遍）

**场景**：企业知识库，10 万篇文档，平均每篇 2000 token。

**① 切块数量与库规模**
- 用 `chunk_size=400`，约 $2000/400 = 5$ 块/篇 → 共 $10^5 \times 5 = 50$ 万个 chunk。
- 用 1536 维 float32（4 字节）embedding：每向量 $1536\times4 = 6144$ 字节 ≈ 6 KB。
- 向量总存储 $\approx 50\text{万}\times 6\text{KB} = 3\text{ GB}$（还没算原文和索引开销，HNSW 索引通常再加几成）。

**② 单次问答的上下文预算**
- 召回 `top_k=30` → 重排取 `top_n=5`，每块 400 token → context $= 5\times400 = 2000$ token。
- 加 Prompt 指令 + 问题 ≈ 300 token → 输入约 **2300 token**，输出预留 500 token，远在常见上下文窗口内。✓

**③ 成本/延迟直觉（量级感，非精确报价）**
- 假设某模型 \$X / 百万输入 token：单次 2300 输入 token 成本 $\approx 2300/10^6 \times X$ ——单看很便宜，但**乘上日活百万次请求就放大百万倍**，所以 top_n 和 chunk_size 直接关系账单。
- 延迟拆解：`embedding 问题(~10ms) + ANN检索(~10ms) + 重排5~50条(几十ms) + LLM生成(首token几百ms~秒级)` → **生成几乎总是延迟瓶颈**，检索通常不是。

**④ 召回率手算**
- 测试集 100 个问题，每题已知 1 个"标准答案块"。检索 top_k=20 后，命中 85 个 → 召回率 $= 85/100 = 85\%$。说明还有 15% 的问题"答案根本没召回回来"，这部分 LLM 再强也答不对——**先修检索，再修生成**。

## 11. 评估——怎么知道 RAG 好不好

RAG 是个流水线，得**分段评估**，否则不知道病在哪：

```
        检索好不好?              生成好不好?
  ┌──────────────────┐   ┌──────────────────────┐
  │ Context Recall   │   │ Faithfulness 忠实度   │
  │ (该召回的召回了吗)│   │ (答案有没有照资料说,  │
  │ Context Precision│   │  没瞎编)              │
  │ (召回的相关吗)   │   │ Answer Relevancy      │
  └──────────────────┘   │ (答案切不切题)        │
                         └──────────────────────┘
```

- **检索侧**：召回率（Recall，该找到的找到没）、精确率（Precision，找到的相关吗）、MRR/命中率。
- **生成侧**：
  - **忠实度（Faithfulness）**：答案的每句话能否由检索到的资料支撑？防幻觉的核心指标。
  - **答案相关性（Answer Relevancy）**：答没答到点子上。
- **常用工具**：**RAGAS** 等框架用 LLM 当裁判，自动给上面这些维度打分；也常人工标注小测试集做基准。

> 排查铁律：**答错先看"召回里有没有正确答案"**。召回里没有 → 改检索（切块/embedding/混合/top_k）；召回里有但答错 → 改生成（Prompt/重排/位置/模型）。

## 对照表：RAG vs 其他知识注入方式

| 维度 | RAG | 微调 (Fine-tune) | 长上下文全量塞 | 提示工程 |
|------|-----|------------------|----------------|---------|
| 知识更新 | 改库即可，秒级 | 重训，慢且贵 | 改输入即可 | 改 Prompt |
| 时效性 | 强 | 弱 | 强 | 弱 |
| 可溯源 | 强（给出处） | 弱 | 中 | 弱 |
| 处理海量私有数据 | 强 | 中 | 弱（窗口有限/贵） | 弱 |
| 单次成本 | 中（多了检索+长输入） | 推理便宜，训练贵 | 高（token 多） | 低 |
| 擅长 | 补"事实/时效" | 调"风格/技能" | 资料少且固定 | 简单任务 |
| 何时选 | 知识大/常变/要溯源 | 要改模型行为 | 资料就那么几页 | 通用闲聊 |

## 常见问题（FAQ）

| 问题 | 原因 | 对策 |
|------|------|------|
| 答案胡编（仍幻觉） | 召回里压根没正确资料 / Prompt 约束弱 | 先查召回；强化"没有就说没有"指令；加重排 |
| 检索召回不相关 | 切块太大/太碎；embedding 不匹配领域 | 调 chunk_size；换/微调 embedding；上混合检索 |
| 专有名词、型号搜不到 | 纯向量对字面 token 弱 | 加 BM25 混合检索 + RRF 融合 |
| 召回对了但答得差 | 重要片段被放中间被忽略 | 关注 Lost in the Middle，最相关放两端；加重排 |
| 上下文被撑爆/很贵 | top_n 太大、chunk 太大 | 减 top_n、上下文压缩（LLMLingua）、父子块 |
| 建库和检索结果对不上 | 两端 embedding 模型不一致 | 同一个 embedding 模型；改模型要全量重建库 |
| 长文档某细节答不全 | 小块上下文不完整 | 父子块：小块检索、大块返回 |
| 多跳/复杂问题答不好 | 单次检索拿不全证据 | 多查询改写、Self-RAG 迭代检索 |
