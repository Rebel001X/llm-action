## 0. 一句话锚点

RAG（Retrieval-Augmented Generation，检索增强生成）= **先检索后生成**：在不重新训练大模型的前提下，把"与问题相关的外部知识片段"塞进提示词，让模型"开卷考试"，从而降低幻觉、引入私域/实时知识、可溯源。

> 一句口诀：**模型负责"会说话"，检索负责"知道答案在哪"。** RAG 的工程难点 90% 在"检索"，不在"生成"。

## 1. 地基 / 前置

### 1.1 RAG 全链路数据流

```
                       ┌──────────────── 离线建库（Indexing）────────────────┐
   原始文档              切块            嵌入            写入向量库
  PDF/HTML/MD  ──清洗──► Chunk ──► Embedding模型 ──► [向量, 元数据] ──► VectorDB
                          │            (e5/bge-m3)                    (HNSW/IVF)
                          └─►(可选)BM25 倒排索引（稀疏）
                       └─────────────────────────────────────────────────────┘

                       ┌──────────────── 在线问答（Serving）──────────────────┐
   用户 query ─► Query改写 ─► 多路召回 ─► 候选合并 ─► Rerank ─► Top-K ─► 拼Prompt ─► LLM ─► 答案
                (rewrite/HyDE) (dense+BM25) (RRF/去重) (cross-enc)        (+引用)
                       └─────────────────────────────────────────────────────┘
```

两条链路共享同一个嵌入模型，否则 query 向量与文档向量不在同一空间，召回必然崩。

### 1.2 为什么不直接把全部文档塞进上下文

- **上下文窗口有限且贵**：tokens 线性收费，长上下文还有"迷失在中间"（lost-in-the-middle）问题——模型对上下文中部信息利用率最低。
- **检索是一次"信息压缩"**：把 100 万 token 的知识库压成最相关的几千 token。
- 所以 RAG 的核心矛盾是：**召回要全（不漏），上下文要精（不噪）**。这对矛盾贯穿全文。

### 1.3 失败根因的分层定位

| 现象 | 大概率根因 | 看哪一节 |
|------|-----------|----------|
| 答非所问、编造 | 召回里压根没有答案（漏召回） | 2/5/6/7 |
| 召回里有答案但排在第 20 名 | 排序差，没 rerank | 8 |
| 答案被切成两半 | 切块粒度/重叠不当 | 2/3 |
| "我不知道"过多 | 阈值过严或 query 与文档措辞不匹配 | 7 |

> 调优铁律：**先量化再优化**（见第 9 节），否则你只是在凭感觉拧旋钮。

## 2. 切块策略（固定 / 语义 / 重叠）

切块（Chunking）= 把长文档切成"检索的最小单元"。这是 RAG 里**最被低估、收益最高**的一步。

### 2.1 为什么必须切块

1. 嵌入模型有最大输入长度（e5/bge 系列通常 512 token，bge-m3 支持到 8192）。
2. 整篇文档嵌成一个向量，语义被"平均"掉，相关段落被无关段落稀释。
3. 检索单元越小越精准，但越小越容易丢上下文——这就是第 3 节父子块要解决的。

### 2.2 三种策略对比

```
固定大小切块 (Fixed)                语义切块 (Semantic)
[████████|████████|████████]       [██句群A██|███句群B███|█句C█]
 每块=固定token，简单粗暴            按句间相似度"断点"切，块大小不均

重叠切块 (Overlap, 几乎必开)
[████████]
      [████████]      相邻块共享尾/首 overlap token
            [████████]  防止答案恰好落在切割线上被劈开
```

| 策略 | 怎么切 | 优点 | 缺点 | 适用 |
|------|--------|------|------|------|
| 固定大小 | 按 token/字符数硬切，配 overlap | 实现简单、块大小可控、易管显存 | 可能切断句子/语义 | 通用首选、结构松散文本 |
| 递归分隔符 | 按 `\n\n`→`\n`→`。`→空格 逐级切 | 尽量沿自然边界 | 仍可能超长再硬切 | Markdown/代码/带结构文本 |
| 语义切块 | 算相邻句嵌入相似度，低于阈值处断开 | 块内语义内聚 | 慢（要先嵌入所有句）、块大小不可控 | 高质量场景、长论述文本 |

### 2.3 重叠（overlap）为什么几乎必开

设一个关键事实横跨切割边界：

```
...净利润同比增长 | 23%，主要由于...   ← 切割线劈开了"增长23%"
   块1结尾 ────────┘ └──── 块2开头     召回任一块都答不全
```

加 overlap 后，"增长 23%" 同时出现在块 1 尾和块 2 头，任一被召回都能答对。**经验值：overlap = chunk_size 的 10%~20%**。

### 2.4 块大小怎么定（核心权衡）

```
chunk 小（128 token）          chunk 大（1024 token）
└ 检索精准、噪声少              └ 上下文完整、召回更鲁棒
└ 但易丢上下文、块数多          └ 但语义被稀释、易引入噪声
        ↑ 用"父子块"两头都要 ↑（见第3节）
```

- 起步默认：**chunk = 256~512 token，overlap = 50~80 token**，再用评估集调。
- FAQ/短问答 → 偏小；技术文档/法律条文 → 偏大或父子块。

## 3. 父子块（Small-to-Big / Parent-Child）

### 3.1 动机

第 2 节的矛盾："小块召得准，大块答得全"。父子块直接**把检索粒度和喂给 LLM 的粒度解耦**。

```
         父块 Parent（大，512~1024t，给LLM读）
   ┌──────────────────────────────────────────┐
   │  子块s1  │  子块s2  │  子块s3  │  子块s4   │  ← 子块（小,128t,用来检索）
   └──────────────────────────────────────────┘
            ▲ 命中子块s2
            └─► 但喂给 LLM 的是整个父块（上下文完整）
```

### 3.2 流程

1. 文档先切成**父块**，每个父块再切成**子块**，记录 `child→parent` 映射。
2. **只把子块嵌入入库**（检索精准）。
3. 检索命中子块后，**用映射换回父块**（甚至父块再上溯一层），去重后喂给 LLM。

### 3.3 变体

- **Sentence-Window**：以句子为检索单元，命中后向左右各扩 N 句作为上下文窗口。
- **Auto-Merging**：若同一父块下多个子块被命中，自动合并为父块，减少碎片。

> 落地价值：实践中父子块常带来召回质量与答案完整度的明显提升，是性价比很高的"第二刀"优化（第一刀是 rerank）。

## 4. 嵌入与向量库（地基组件）

### 4.1 嵌入模型选型（沿用本仓库已选）

嵌入（Embedding）= 把文本映射成定长向量 $v\in\mathbb{R}^d$，语义近→向量近（余弦相似度高）。

| 模型 | 维度 d（约） | 最大长度 | 特点 | 链接 |
|------|------|----------|------|------|
| multilingual-e5-large | 1024 | 512 | 多语稠密，需加 `query:`/`passage:` 前缀 | https://huggingface.co/intfloat/multilingual-e5-large |
| BAAI/bge-m3 | 1024 | 8192 | **一模三用**：稠密+稀疏+ColBERT多向量，长文本友好 | https://huggingface.co/BAAI/bge-m3 |

> e5 系列**必须加前缀**：查询用 `query: ...`，文档用 `passage: ...`，否则两端不对齐、召回明显变差——这是高频坑。
> bge-m3 一个模型同时产稠密向量+稀疏权重，天然适合做第 5 节的混合检索，省一套 BM25 工程。

余弦相似度（衡量两向量方向接近度）：
$$\text{cos}(a,b)=\frac{a\cdot b}{\lVert a\rVert\,\lVert b\rVert}\in[-1,1]$$

### 4.2 向量索引（详见 [[llm-application/vector-db/README]]）

```
暴力Flat        IVF(倒排)            HNSW(图)
全量算距离      聚类分桶,只搜近桶      多层近邻图,贪心跳转
召回100%/最慢   快/召回略降           快且召回高/内存大(主流默认)
```

- 度量统一用 **cosine / 内积**，且**入库前 L2 归一化**，否则内积≠余弦。
- HNSW 三参数：`M`（每点邻居数，越大召回越高内存越大）、`efConstruction`（建图质量）、`efSearch`（查询时探索宽度，越大召回越高越慢）。

## 5. 混合检索（Hybrid：稠密 + 稀疏 BM25）

### 5.1 为什么单靠向量不够

- **稠密向量**懂语义（"汽车"≈"轿车"），但对**精确关键词、型号、专有名词、数字**不敏感（"GPT-4o" 可能被语义糊成"某个 GPT 模型"）。
- **稀疏检索 BM25**（词频倒排）擅长精确字面匹配，但不懂同义/改写。
- 二者**互补**，融合后召回上限更高。

```
query ──┬─► 稠密检索(向量) ──► 候选A (语义相关)
        └─► 稀疏检索(BM25) ──► 候选B (字面命中)
                                   │
                              RRF 融合去重
                                   ▼
                              统一候选集
```

### 5.2 RRF（Reciprocal Rank Fusion，倒数排名融合）

不依赖两路分数的绝对量纲，只看**排名**，鲁棒：
$$\text{RRF}(d)=\sum_{i\in\text{各路}}\frac{1}{k+\text{rank}_i(d)}$$
$k$ 常取 60，`rank` 从 1 起。某文档在多路都靠前→总分高。具体手算见数值节。

### 5.3 BM25 直觉

$$\text{BM25}=\sum_{t\in q}\text{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\,(1-b+b\frac{|d|}{\text{avgdl}})}$$
- IDF：词越稀有权重越大；$f(t,d)$：词在文档中频次；$b$ 调长度归一化。
- 直觉：**罕见词命中 + 命中多次 + 文档不太长** → 分高。

## 6. 多路召回（Multi-Recall）

混合检索是"两路（dense+sparse）"，多路召回是把这个思路推广。

```
            ┌─► query原文  ──稠密──┐
 query ─改写─┼─► 改写q1    ──稠密──┤
            ├─► 改写q2    ──稠密──┼─► 大候选池 ─去重─► RRF ─► Rerank
            ├─► HyDE假设答案─稠密──┤
            └─► query     ──BM25──┘
   还可加：多索引（标题索引/正文索引/QA对索引）、元数据过滤路（按时间/部门）
```

要点：
- 每路各取 Top-N（如 N=20~50），**合并去重**后再交给 rerank（第 8 节）。
- "宁可多召回再让 rerank 筛"，因为**漏召回无法补救，多召回可被精排压下去**。
- 代价是延迟与成本上升，需在第 9 节用指标平衡。

## 7. Query 改写（Query Rewriting）

用户的问题往往口语化、含指代、信息不全，直接拿去检索命中率低。改写就是把"烂 query"变"好 query"。

### 7.1 常见手法

| 手法 | 做什么 | 解决的问题 |
|------|--------|-----------|
| 多查询 Multi-Query | LLM 生成 N 个语义等价但措辞不同的问法 | 单一措辞与文档不匹配 |
| 子问题分解 | 复杂问题拆成多个可独立检索的子问 | 多跳/复合问题 |
| HyDE | LLM 先**假设性回答**，用"假答案"去检索 | query 短而文档长，向量不对齐 |
| 指代消解/上下文重写 | 多轮对话中把"它/上面那个"还原成实体 | 多轮指代 |
| 退一步 Step-back | 把具体问题抽象成上位问题再检索 | 需要背景/原理性知识 |

### 7.2 HyDE 直觉图

```
原始query: "h100 显存多大"      （短，与长文档向量不对齐）
        │ LLM 生成假设答案
        ▼
"H100 配备 80GB HBM3 显存，带宽约3.35TB/s…"  ← 用这段去检索
        │ 这段"看起来像文档"，更易召回真实文档
        ▼  （即便假答案有错，向量邻域也对了）
```

> 注意：改写引入额外 LLM 调用→延迟+成本；多轮对话务必做指代消解，否则"它的价格"这类 query 永远召不对。

## 8. 重排 rerank（精排）

### 8.1 双编码器 vs 交叉编码器（为什么需要 rerank）

```
召回用的 Bi-Encoder(双塔)            Rerank 用的 Cross-Encoder(交叉)
 query─►[Enc]─►向量v_q                [query ; doc] ─►[Enc]─► 相关性分数
 doc  ─►[Enc]─►向量v_d   离线可算       query与doc在模型内部"逐词交互"
 相关度=cos(v_q,v_d)                   精度高很多，但必须在线、每对都算
 快(可建索引)、精度有限               慢(无法预算索引)、只能对候选少量做
```

结论：**召回阶段用双塔（快、可索引），对召回出的几十~上百个候选用 cross-encoder 精排取 Top-K**。这是 RAG 提升相关性的**最高性价比一刀**。

### 8.2 本仓库已选 reranker（cross-encoder）

- https://huggingface.co/BAAI/bge-reranker-v2-m3 （多语，与 bge-m3 嵌入配套）

```python
import torch
from transformers import AutoModelForSequenceClassification, AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained('BAAI/bge-reranker-v2-m3')
model = AutoModelForSequenceClassification.from_pretrained('BAAI/bge-reranker-v2-m3')
model.eval()

# 每个 pair = [query, 候选文档]；模型直接输出相关性分数
pairs = [['what is panda?', 'hi'],
         ['what is panda?', 'The giant panda (Ailuropoda melanoleuca), '
          'sometimes called a panda bear or simply panda, is a bear '
          'species endemic to China.']]
with torch.no_grad():
    inputs = tokenizer(pairs, padding=True, truncation=True,
                       return_tensors='pt', max_length=512)
    scores = model(**inputs, return_dict=True).logits.view(-1, ).float()
    print(scores)  # 第二个分数远高于第一个 → 据此重排取 Top-K
```

### 8.3 流水线位置与参数

```
召回 Top-50  ──► Rerank(cross-encoder) 重新打分 ──► 取 Top-3~5 喂 LLM
（多路合并去重后）         逐 pair 在线计算            截断噪声、控上下文长度
```

- 召回宽（N 大些，如 50）+ 精排窄（K 小，如 3~5）通常最优。
- reranker 是逐 pair 的，**延迟随候选数线性增长**，所以放在召回之后、候选已收敛时做。

## 9. 评估（怎么量化“RAG 好不好”）

不评估的 RAG 调优都是玄学。**分两层评：检索层 + 生成层。**

### 9.1 检索层指标（先保证召回里"有"答案）

| 指标 | 含义 | 直觉 |
|------|------|------|
| Recall@k | 前 k 个里是否含正确片段 | 召回有没有漏（最关键） |
| Precision@k | 前 k 个里相关的占比 | 噪声多不多 |
| MRR | 第一个正确结果排名的倒数均值 | 正确答案排得靠前吗 |
| NDCG@k | 带位置折扣的相关性增益 | 排序整体好坏 |
| Hit Rate | 命中率（有一个就算命中） | 最宽松的门槛 |

### 9.2 生成层指标（RAGAS 等，常用 LLM-as-judge）

```
            检索到的上下文 Context
              ▲              │
   Faithfulness│（答案有没有据上下文,不编）
              │              ▼
 用户Query ──► RAG答案 Answer ──► Answer Relevancy（答案切不切题）
              │              ▲
 Context Recall│（该召的召全没）│Context Precision（召的有没有用）
              ▼              │
          标准答案/Ground Truth
```

- **Faithfulness（忠实度）**：答案是否都能从上下文推出（治幻觉）。
- **Answer Relevancy**：答案是否切题。
- **Context Precision / Recall**：检索内容的精与全。

### 9.3 评估工作流

1. 构造评估集：50~200 条 `(问题, 标准答案, 相关文档id)`，可用 LLM 辅助生成再人工校。
2. 固定评估集，**每改一个旋钮（chunk/overlap/rerank/k）就跑一遍**，看指标涨跌。
3. 在线再配 A/B、点击/点赞反馈做长期监控。

## 数值例子 / 手算对照

### 例 1：分块数量与建库嵌入量

- 知识库：1000 篇文档 × 平均 4000 token。chunk=400、overlap=80 → 步长 stride=320。
- 单篇块数 $\approx \lceil (4000-80)/320\rceil + 1 \approx 14$ 块；总块数 ≈ $1000\times14=1.4$ 万块。
- 用 d=1024、float32 的嵌入：每向量 $1024\times4=4096$ B ≈ 4 KB；
- 向量总占用 ≈ $14000\times4\text{KB}\approx 56$ MB（加 HNSW 图结构与元数据，实际约 2~4×，仍轻量）。

### 例 2：嵌入模型显存粗算（bge-m3 类，约 5.6 亿参数，以官方为准）

- 推理 fp16：参数显存 $\approx 0.56\text{B}\times2\text{B}=1.12$ GB；加激活/批处理，**单卡几 GB 足够**。
- 吞吐取决于 batch 与序列长度，建库阶段大 batch 离线跑即可，不在线路径。

### 例 3：RRF 融合手算（k=60）

文档 D 在稠密路 rank=2、BM25 路 rank=5；文档 E 仅稠密路 rank=1。
$$\text{RRF}(D)=\frac{1}{60+2}+\frac{1}{60+5}=0.01613+0.01538=0.03151$$
$$\text{RRF}(E)=\frac{1}{60+1}=0.01639$$
→ D 虽两路都非第一，但**双路都靠前**，融合后 0.0315 > E 的 0.0164，排到 E 前面。这正是 RRF 奖励"多路共识"的体现。

### 例 4：召回→精排 token 预算

召回 50 块 × 400 token = 2 万 token，全塞 LLM 太贵且噪声大。
rerank 后取 Top-4 → $4\times400=1600$ token 上下文，+ 系统/问题约 2000 token 总输入，**成本与噪声同时压下**。

## 常见问题（坑表）

| 坑 | 现象 | 解法 |
|----|------|------|
| query/doc 嵌入不对齐 | 召回质量莫名很差 | e5 加 `query:`/`passage:` 前缀；两端同模型同归一化 |
| 没归一化就用内积 | 相似度排序错乱 | 入库前 L2 归一化，或显式用 cosine |
| 切块太大 | 答案被无关内容稀释 | 缩小 chunk 或上父子块 |
| 切块太小无 overlap | 关键句被切割线劈开 | 加 10~20% overlap / 父子块 |
| 只用稠密检索 | 型号/数字/专有名词召不到 | 上混合检索 + BM25 |
| 不做 rerank | 答案在召回里但排第 20 | 加 cross-encoder 精排取 Top-K |
| 召回太窄 | 漏召回，怎么改 prompt 都没用 | 先放宽 N，靠 rerank 收敛 |
| 多轮不消解指代 | "它的价格"永远召不对 | query 改写做指代消解 |
| 上下文塞太多 | lost-in-the-middle、变贵 | rerank 后只取 Top-3~5 |
| 不建评估集 | 凭感觉调，反复横跳 | 先建评估集，量化每次改动 |
| 文档更新不重建索引 | 答旧知识 | 增量/定时重建，记录版本与时间元数据 |
| 表格/代码被当纯文本切 | 结构信息丢失 | 结构化解析，表格转 Markdown 再切 |
