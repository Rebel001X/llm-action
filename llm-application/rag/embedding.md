## 0. 一句话锚点

**Text embedding 就是把一段文本（词、句、段、文档）映射成一个固定长度的实数向量 $\mathbf{v} \in \mathbb{R}^d$，使得"语义越接近的文本，向量越接近"。**

我们熟悉的 **word embedding** 以 token 为基本单位（一个词一个向量）；**text embedding** 则以整段文本为基本单位（一整段话一个向量）。

> 理想的 text embedding 应尽可能保留文本的语义信息：相同语义但不同表述的文本被映射到相近位置，而不同语义的文本在向量空间保持应有的距离。

---

## 1. 地基：它解决什么问题

传统的关键词检索（BM25、倒排索引）只会"字面匹配"。用户问"怎么给猫咪剪指甲"，文档里写的是"宠物美容修剪爪子"，字面一个词都不重叠，关键词检索就抓瞎了。

Embedding 把文本投影到一个**语义空间**：在这个空间里，"剪指甲"和"修剪爪子"距离很近，于是即使一个字都不重合，也能被检索出来。这就是 **语义检索（semantic / dense retrieval）**，也是 RAG（检索增强生成）的核心一环。

```
   字面世界（稀疏）              语义世界（稠密）
  "剪指甲" ≠ "修剪爪子"   ===>   v1 ≈ v2  （距离很小）
   一个词都不重叠                 在向量空间里挨得很近
```

一句话：**Embedding 把"找意思相近的文本"这个模糊问题，变成了"找向量空间里最近邻"这个数学问题。**

---

## 2. word embedding vs text embedding

| 维度 | word embedding | text embedding |
|------|---------------|----------------|
| 基本单位 | 一个 token / 词 | 一整段文本 |
| 典型代表 | Word2Vec / GloVe | Sentence-BERT / BGE / E5 等 |
| 是否带上下文 | 早期静态（一词一向量） | 带上下文（同一句不同语境向量不同） |
| 直接用途 | 当作模型输入层 | 直接做检索 / 聚类 / 相似度 |

核心区别：text embedding 必须把"任意长度的一串 token 向量"**汇聚（aggregate）成一个固定维度向量**。怎么汇聚，就是下一节的主题。

---

## 3. 如何从语言模型中获得 Text embedding（4 种方式）

以主流的 **Transformer-Encoder**（如 BERT 家族）为例。Encoder 吃进一串 token，吐出每个位置一个向量（最后一层隐藏态），形状是 $[L, d]$（$L$ 个 token，每个 $d$ 维）。问题是：怎么从这 $L$ 个向量得到 **1 个** 句向量？

```
输入: [CLS] 怎么 给 猫 剪 指甲 [SEP]
                    │  Transformer-Encoder（N 层）
                    ▼
最后一层隐藏态:  [ h_CLS , h1 , h2 , ... , h_SEP ]   形状 [L, d]
                    │
        ┌───────────┴────────────┬──────────────┐
        ▼                        ▼               ▼
    (a) 取 h_CLS          (c) 对所有 h 做 Pooling   ...
        │                        │
        ▼                        ▼
   句向量 v ∈ R^d           句向量 v ∈ R^d
```

四种常见做法：

- **a) CLS 向量**：直接取最后一层 `[CLS]` 位置的向量作为句向量。最简单，但裸 BERT 的 CLS 向量未经专门训练时质量一般。
- **b) CLS + MLP**：把 `[CLS]` 向量再过一个 MLP（投影头）。训练时给 CLS 一个"被监督"的出口。
- **c) Pooling 所有位置**：把最后一层**所有位置**的向量做池化。大多数情况用 **mean pooling（平均池化）**，有时也用 max pooling 等。**这是 Sentence-BERT 类模型的主流做法。**
- **d) Pooling + MLP**：所有位置先池化，再过一个 MLP。

> 现代的"大模型当 embedder"（基于 Decoder，如 LLM-based embedding）通常取**最后一个 token** 的隐藏态（因为自回归注意力下只有最后位置"看到了全文"），或对所有 token 做加权池化，本质同样是"把序列汇聚成一个向量"。具体取法以各模型官方说明为准。

---

## 4. 为什么"平均池化"这么好用

mean pooling 就是把所有有效 token（去掉 padding）的向量取算术平均：

$$\mathbf{v} = \frac{1}{\sum_i m_i}\sum_{i=1}^{L} m_i \, \mathbf{h}_i$$

其中 $m_i\in\{0,1\}$ 是 attention mask（padding 位置为 0，不参与平均）。

直觉：每个 token 向量都带一部分语义，求平均相当于"语义的重心"。它天然鲁棒——少一两个词不会让重心剧烈漂移，比"只信一个 CLS 位置"更稳。

**关键工程点：一定要用 mask 排除 padding。** 如果把 padding 的向量也算进平均，短句会被大量 0 向量（或垃圾向量）稀释，相似度全乱。

```
错误：(h1+h2+h3+h_pad+h_pad)/5   <- padding 拉低了重心
正确：(h1+h2+h3)/3               <- 只平均真实 token
```

## 5. 训练目标：对比学习（Contrastive Learning）

裸 BERT 直接做 mean pooling，检索效果其实平平（各向异性、向量挤在锥形区域里）。真正好用的 embedding 模型，几乎都用**对比学习**专门训练：拉近正样本对、推开负样本对。

最常用的损失是 **InfoNCE**：对一个 query $q$，它的正样本 $p^+$ 要比同一个 batch 里其他所有负样本 $p^-_j$ 更近：

$$\mathcal{L} = -\log \frac{\exp(\text{sim}(q, p^+)/\tau)}{\exp(\text{sim}(q, p^+)/\tau) + \sum_j \exp(\text{sim}(q, p^-_j)/\tau)}$$

- $\text{sim}$ 一般是余弦相似度；$\tau$ 是温度（temperature），越小越"锐"。
- **正样本** 怎么来：同义改写、问答对、标题-正文、翻译对等。
- **负样本** 怎么来：
  - **In-batch negatives**：同 batch 里别人的正样本就当我的负样本（免费、量大）。
  - **Hard negatives（难负例）**：字面很像但语义不对的样本（如用 BM25 召回再筛），最能逼模型学会细分语义，效果提升最明显。

```
        拉近 (正样本对)
  q ●───────────● p+
    │
    │  推开 (负样本对)
    ▼
  p-      ● ← 难负例：长得像但意思不同，要使劲推开
```

> 很多强模型还做"两阶段"：先在海量弱监督对上预训练，再在高质量标注对 + 难负例上精调。

## 6. 相似度度量：余弦、内积、L2

拿到两个向量后，怎么算"近不近"？

| 度量 | 公式 | 特点 |
|------|------|------|
| 余弦相似度 | $\cos\theta=\dfrac{\mathbf{a}\cdot\mathbf{b}}{\|\mathbf{a}\|\,\|\mathbf{b}\|}$ | 只看方向，不看长度；最常用 |
| 内积（点积） | $\mathbf{a}\cdot\mathbf{b}$ | 既看方向也看长度 |
| 欧氏距离 L2 | $\|\mathbf{a}-\mathbf{b}\|_2$ | 距离越小越相似 |

**重要等价关系**：如果向量都做了 **L2 归一化**（长度变成 1），那么 **余弦相似度 = 内积**，且 **L2 距离与余弦单调对应**（$\|a-b\|^2 = 2-2\cos\theta$）。所以工程上常见做法是：**入库前把所有向量归一化，向量库用内积（IP）索引**，既快又等价于余弦。

数值例子：$\mathbf{a}=(3,4)$，$\mathbf{b}=(4,3)$。
点积 $=3\cdot4+4\cdot3=24$；$\|a\|=\|b\|=5$；$\cos\theta=24/25=0.96$，非常相近。

## 7. 非对称检索与指令前缀

**对称 vs 非对称**：
- **对称（symmetric）**：query 和文档"同质"，比如句子相似度、找重复问题。两边用同一种编码方式。
- **非对称（asymmetric）**：query 是短问句，document 是长段落，二者形态差很多——这正是 RAG 的典型场景。

很多现代 embedding 模型为非对称检索引入了**指令前缀 / prompt**，给 query 和 passage 加不同的引导语，例如给查询加一句"为这个查询检索相关段落"。这能显著拉开 query 端和 passage 端的表示，提升检索质量。

> 注意：**用了带前缀训练的模型，推理时就必须按它要求的方式加前缀**（query 用 query 模板、passage 用 passage 模板），否则效果大跌。具体前缀文案、是否需要前缀，**以该模型官方文档为准，切勿臆造**。

## 8. 整条 RAG 调用链（入库 + 查询）

Embedding 在 RAG 里出现两次：建库时给所有文档编码，查询时给问题编码。

```
========== 离线：建库（Indexing） ==========
原始文档
  │  ① 切块 Chunking（按字数/句子/语义切，常带重叠 overlap）
  ▼
文本块 chunk_1 ... chunk_n
  │  ② Embedding 模型逐块编码  +  ③ L2 归一化
  ▼
向量 v_1 ... v_n  ─────────────►  向量数据库（建 ANN 索引）
                                  原文也存一份（用于回填）

========== 在线：查询（Retrieval + Generation） ==========
用户问题 query
  │  ④ 同一个 Embedding 模型编码（query 端模板）
  ▼
查询向量 q
  │  ⑤ 在向量库做 Top-k 近邻搜索（ANN，如 HNSW/IVF）
  ▼
命中 chunk_3, chunk_7, ...（最相近的 k 块）
  │  ⑥（可选）Reranker 精排
  ▼
拼进 Prompt 上下文  ──►  LLM 生成最终回答
```

铁律：**建库和查询必须用同一个 embedding 模型同一套预处理**。换了模型、改了归一化方式、漏了前缀，整个向量空间就对不齐，检索全废。

> 第 ⑤ 步的"近邻搜索"在大库上不会暴力两两比较，而用 **ANN（近似最近邻）** 索引（HNSW、IVF-PQ 等）把 $O(N)$ 降到近似对数级，用一点点召回率换巨大速度。

## 9. 怎么评估好坏

Text embedding 能用在：**Classification、Clustering、Pair Classification、Reranking、Retrieval、STS（语义文本相似度）、Summarization、Bitext Mining（双语句对挖掘）** 等任务中。评价它的好坏，就是看它在这些任务上的表现。

业界常用 **MTEB（Massive Text Embedding Benchmark）** 这类综合榜单：把一个 embedding 模型丢到几十个数据集、覆盖上面这 8 类任务上跑分，取平均。看榜要点：

- 别只看总分，**看你真正要用的那类任务**（做 RAG 就重点看 Retrieval / Reranking 分）。
- 看**语言**（中文场景要看中文榜，英文模型在中文上可能很差）。
- 看**维度和体积**：高分但 4096 维的大模型，存储和检索成本也高，要权衡。

## 10. 工程参数与权衡（讲含义，不背默认值）

| 项 | 是什么 / 怎么权衡 |
|----|------------------|
| **向量维度 $d$** | 维度越高表达力越强，但存储、内存、检索成本线性上升。部分模型支持 **Matryoshka（套娃）表示**，可截断到更短维度只损失少量精度——按预算选。 |
| **最大输入长度** | 模型有最大 token 上限，超长会被截断丢信息。长文档要先 chunking，别指望一次塞进去。 |
| **chunk 大小 / 重叠** | 块太大→一个向量混了多主题，检索不准；太小→语义不完整。常用"按句子/段落切 + 适当 overlap"避免切断关键信息。 |
| **是否归一化** | 见第 6 节。要用余弦/内积索引就归一化；务必和向量库的度量方式对齐。 |
| **池化方式** | mean / CLS / last-token，取决于模型怎么训练的，**用模型推荐的那种**，别自己换。 |
| **query/passage 前缀** | 用了就两端都按规范加；不确定查官方文档。 |
| **batch / 精度** | 批量编码提吞吐；FP16/INT8 能省显存换速度，注意精度对相似度的微小影响。 |

## 常见问题 / 坑

| 现象 / 坑 | 原因 | 处理 |
|----------|------|------|
| 检索结果"什么都有点像" | 没做对比学习的裸模型，向量各向异性、挤成一团 | 换专门训练过的 embedding 模型 |
| 短句相似度全偏高/偏低 | mean pooling 把 padding 也平均进去了 | 用 attention mask 排除 padding |
| 建库好好的，上线检索全乱 | 查询和建库用了不同模型 / 不同归一化 / 漏前缀 | 严格对齐两端的模型与预处理 |
| 中文效果差 | 用了英文为主的模型 | 选中文或多语模型，看中文榜 |
| 余弦和库里分数对不上 | 向量没归一化却用了余弦，或库用 L2 你以为是余弦 | 统一归一化 + 对齐索引度量类型 |
| 长文档召回不到关键句 | 整篇编成一个向量，细节被稀释 | 切块后逐块编码再检索 |
| 字面像但语义反的没排开 | 训练时缺难负例 | 选带 hard negative 训练的模型，或加 Reranker 精排 |
| 改了 chunk 策略后变差 | 块切碎了语义 / 切断了关键信息 | 调块大小与重叠，按句/段切 |
