## 0. 一句话锚点

RAG = **检索（Retrieve）+ 生成（Generate）**。它的全部错误只会出在两个地方：**没找对**（检索召回了错误/不全的证据）或**没用好**（模型拿到证据后仍乱编、读不全、推不动）。

$$\text{答案质量} \;\le\; \underbrace{\text{召回了正确证据的概率}}_{\text{检索上限}} \times \underbrace{\text{模型正确利用证据的概率}}_{\text{生成上限}}$$

这是一个**乘积**：任意一环为 0，整体就是 0。所以优化 RAG 永远要先问"是检索的锅还是生成的锅"。

## 1. 地基：RAG 的最小数据流与五个失效点

先把最朴素的 RAG（"naive RAG"）拆到最原子。一个问题进来，发生这些事：

```
                    ┌────────────── 离线建库 (Indexing) ──────────────┐
  原始文档 ──切块──> chunk ──向量化(embedding)──> 向量库(向量+原文)
   (PDF/网页)   ①        ②                          ③
                    └────────────────────────────────────────────────┘

  ┌────────────────── 在线问答 (Retrieve + Generate) ──────────────┐
  用户问题 ─向量化─> 在向量库里算相似度 ─取最相近 topK 块─> 拼进 Prompt ─> LLM ─> 答案
            ④              (余弦相似度)        ⑤              ⑥        ⑦
  └────────────────────────────────────────────────────────────────┘
```

**最原子的概念，逐个说清"为什么"：**

- **切块（chunk）**：文档太长塞不进模型，也不利于精确定位，所以切成小段。切多大是第一个坑——切太碎语义断裂，切太大噪声多。
- **embedding（向量化）**：把一段文字映射成一个 $d$ 维向量（常见 $d=768/1024/1536$），**语义相近的文字向量也相近**。这样"找相关文档"就变成了"找距离最近的向量"。
- **相似度**：通常用**余弦相似度** $\cos(\theta)=\dfrac{\mathbf{q}\cdot\mathbf{d}}{\lVert\mathbf{q}\rVert\,\lVert\mathbf{d}\rVert}$，取值 $[-1,1]$，越接近 1 越相关。
- **topK**：只取最相近的 $K$ 个块（如 $K=5$）。$K$ 太小漏证据，太大灌噪声+超上下文。
- **拼 Prompt + 生成**：把 topK 块当"参考资料"和问题一起喂给 LLM，要求"根据资料回答"。

**五个失效点（贯穿全文）：**

```
①切块差  ②向量表达弱  ③索引不全/过时  ④query与文档语义错位  ⑤模型读不全/乱编
   └──────────── 检索侧 ────────────┘        └──────── 生成侧 ────────┘
```

下面五节，每个问题对应一个失效点，并给出优化。

## 2. 问题① 召回不准（最高频、危害最大）

**现象**：明明知识库里有答案，topK 里却没有正确的块；或者召回的块"看着相关其实没用"。因为 0 节那个乘积，**召回不准是 RAG 的头号杀手**——证据没进来，生成再强也救不回来。

**为什么会发生（三类根因）：**

1. **语义鸿沟**：用户口语 "退款要多久到账" 和文档书面语 "退款处理时效说明"，字面不重叠，纯关键词检索（BM25）召不回；而纯向量检索又可能被"到账""时效"等通用词带偏。
2. **稠密向量的"模糊"**：embedding 把整段压成一个向量，**精确实体/编号/型号容易被平均掉**。问 "iPhone 15 Pro 的快充功率"，向量可能召回一堆"iPhone 充电"通用内容。
3. **粗排只看相似度，不看真相关**：余弦相似度高 ≠ 真能回答问题。

**优化打法（三件套，从便宜到贵）：**

```
            ┌─ 稀疏检索(BM25/关键词) ─┐
   query ──>│                        ├─ 合并去重 ─> 候选 50~100 块 ─> 重排器 ─> top 3~5
            └─ 稠密检索(向量, topK大) ─┘                              (cross-encoder)
              ① 混合检索 (Hybrid)                  ② 重排 (Rerank)
```

**① 混合检索（Hybrid Search）**：稀疏（BM25，擅长精确词/实体/编号）+ 稠密（向量，擅长同义/语义）双路召回再融合。融合常用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：对每路里排名第 $r$ 的文档给分 $\frac{1}{k+r}$（$k$ 常取 60），两路相加。它**只看排名不看原始分数**，省去了 BM25 分和余弦分量纲不同的归一化烦恼。

**② 重排（Rerank）**：第一阶段（向量/BM25）是 **bi-encoder**——query 和文档**各自独立**编码，速度快但不够准；重排用 **cross-encoder**——把 `[query, 文档]` **拼在一起**送进模型，让两者充分注意力交互，输出一个真"相关性分数"。代价是慢（每个候选都要过一次模型），所以只对第一阶段的 50~100 个候选做精排，取 top 3~5。

```
bi-encoder:   [query]→向量   [doc]→向量   再算余弦   (快, 可预存doc向量)
cross-encoder:[query ‖ doc]→ 模型 → 相关性分  (慢, 但query-doc逐词交互, 准)
```

**③ query 改写/扩展**：把一个查询变成多个/更好的查询，覆盖语义鸿沟（详见第 7 节，因为它同时帮多跳）。

**实践要点**：先上**混合检索 + 重排**，这是性价比最高的两步，通常能把召回相关性显著拉起来。重排器是开销大头，控制候选数量（rerank 的候选数 × 单次延迟 = 总延迟）。

## 3. 问题② 上下文过长（召回多了反而变差）

直觉是"多塞点证据更保险"，但有两个硬约束：

**① "中间迷失"（lost in the middle）**：实验上，长上下文里模型对**开头和结尾**的信息利用最好，**塞在中间的关键证据容易被忽略**，召回曲线呈 U 形。所以把第 7 名的块也塞进去，可能把第 1 名的有效证据"挤到中间"被淹没。

**② 成本与延迟**：上下文越长，prompt token 越多，**费用和首 token 延迟近似线性上涨**，注意力计算更是随长度增长（自注意力对序列长度是平方级）。

```
  召回利用率
   高 │■                       ■
      │ ■                     ■
      │   ■                 ■
   低 │      ■  ■  ■  ■  ■            ← 关键证据落在"中间"利用率最低
      └────────────────────────────► 在上下文中的位置
        开头        中间        结尾
```

**优化打法：**

**① 父子块（Parent-Child / Small-to-Big）**：用**小块**做检索（小块语义聚焦、向量更准、召回更精），命中后**返回它所属的大块/父文档**给 LLM（保证上下文完整、不断句）。一举两得：检索用小、生成用大。

```
建库:  父块(整节, ~1500字)
         ├─ 子块a(~200字) ─embedding─┐
         ├─ 子块b(~200字) ─embedding─┤─> 子块进向量库, 记录 child→parent
         └─ 子块c(~200字) ─embedding─┘
检索:  query 命中"子块b" ──映射──> 取出整个"父块"喂给 LLM
```

**② 上下文压缩 / 抽取**：检索回来后，用一个小模型或规则**只保留与问题相关的句子**，丢掉无关段落，再给主模型。等价于"召回后再做一次句子级精排"。

**③ 控制 topK + 重排兜底**：与其塞 10 个，不如重排出 top 3 高质量块。**重排不仅提准，也是控长的手段**——它让你敢只取少量块。

**实践要点**：父子块对"FAQ/手册/合同"这类有清晰层级的文档收益最大；压缩对"长文档少量金句"场景收益最大。

## 4. 问题③ 幻觉残留（接了 RAG 还是会编）

**现象**：给了正确证据，模型仍编造数字/条款；或证据里没有，模型不说"不知道"反而硬答。这正是开头文件里提到的真实痛点——"哪怕是 GPT3.5，幻觉依然严重，客服/研究场景没法支持"。

**为什么 RAG 不能根除幻觉：**

- LLM 本质是"续写最可能的下一个词"，**它不会天然区分"我从证据里读到的"和"我参数里记得的"**。证据和参数记忆冲突时，可能用错的参数记忆。
- 证据召回不全（第 2 节）时，模型倾向"补全"缺口而非留白。

```
  无 RAG:  问题 ─────────────> LLM ──(全凭参数记忆)──> 高幻觉
  有 RAG:  问题 + 证据 ──────> LLM ──(证据+记忆混用)──> 幻觉↓但未清零
  目标:    问题 + 证据 + 约束 ─> LLM ─(只用证据,标引用)─> 可核查
```

**优化打法（让答案可核查）：**

1. **强约束 Prompt**：明确要求"**只依据给定资料回答；资料中没有就回答'未找到'；每个结论标注来源块编号**"。把"不许编"写进指令，并要求**带引用 [来源1][来源2]**，让答案可溯源。
2. **引用对齐 / NLI 校验（事后兜底）**：生成后，用一个判别步骤检查"答案的每句话能否被引用的证据**蕴含（entailment）**"。$\text{支持度} = \dfrac{\text{被证据蕴含的句子数}}{\text{答案总句子数}}$，低于阈值就触发重答或标"低置信"。
3. **拒答路由**：若 topK 的最高重排分都低于阈值，说明"知识库里大概没有"，直接回"未找到相关信息"而非硬答——这往往比答错更安全（尤其客服/医疗/法律）。

**实践要点**：幻觉的根在第 2 节的召回。**先把召回做对，再谈引用约束**；引用约束是把"残余幻觉"变成"可发现的幻觉"，是兜底不是主治。

## 5. 问题④ 多跳推理弱（naive RAG 的结构性短板）

这是原文件里那个经典例子：**"Elon Musk 的兄弟是谁？"** 知识库里只有"Elon Musk 的妈妈是 Maye"和"Maye 的儿子有 Elon、Kimbal"，要答对需要两跳：`Elon → 妈妈Maye → Maye的另一个儿子Kimbal`。

**为什么 naive RAG 答不出来：**

- 它**只用原始问题做一次检索**。问"Elon 的兄弟"，向量最相近的是含"Elon""兄弟"字样的块，而真正的桥梁块"Maye 的儿子有谁"里**根本没出现"Elon"也没出现"兄弟"**，相似度低，召不回来。
- 一次性、平铺的相似度检索，**无法表达"实体之间的关系链"**。

```
naive RAG (一跳):
   "Elon的兄弟?" ──向量─> 召回含"Elon/兄弟"的块 ──❌ 桥梁块召不回 ──> 编一个

迭代检索 (多跳):
   Q ─> 检索 ─> "妈妈是Maye" ─生成子问题─> "Maye的儿子有谁?" ─再检索─> "Kimbal" ─> 汇总答

GraphRAG (图):
   Elon ──(母亲)──> Maye ──(儿子)──> Kimbal
        实体作节点, 关系作边; 沿边游走 = 天然多跳
```

**优化打法：**

**① 迭代/多步检索（Iterative Retrieval）**：检索→读到中间结论→生成下一个子问题→再检索，循环若干轮。本质是把"多跳问题"拆成"多个一跳问题"。这是 Agentic RAG（第 7 节）的核心机制之一。

**② GraphRAG（图谱增强）**：离线先从文档**抽取实体和关系**建成知识图谱，节点是实体、边是关系。多跳查询变成**沿图游走**：`Elon -母亲→ Maye -儿子→ Kimbal`，天然支持关系链。还能在社区/子图上做摘要，回答"全局性"问题（如"这批文档主要讲了哪几个主题"），这是向量检索做不到的。

**③ query 分解（Decomposition）**：把复杂问题用 LLM 先拆成若干子问题分别检索再合并（与改写同源，见第 7 节）。

**实践要点**：GraphRAG 建库成本高（要跑实体/关系抽取，token 消耗大）；如果多跳问题占比不高，**优先用迭代检索**这种轻量方案，把 GraphRAG 留给"关系密集、需要全局理解"的场景。

## 6. 问题⑤ 时效 + 统计/预测类盲区

原文件列的几类"RAG 解不了的问题"，本质是触到了检索的边界：

| 问题类型 | 例子 | 为什么 naive RAG 不行 | 该怎么办 |
|---|---|---|---|
| **时效** | "今天的政策是什么" | 索引是离线建的，**库里是旧文档** | 增量/实时索引；联网检索工具 |
| **统计类** | "昨天多少销售反馈折扣不足" | 答案要**聚合计算**，不在任何单块里 | 路由到 **Text2SQL / 数据库查询** |
| **预测类** | "2025 会怎样" | 答案**不存在于任何文档**，要推断 | 明确拒答或转预测模型/工具 |
| **逻辑/计算** | 复杂推理、算账 | 检索给不出"推理过程" | 调用 **工具/代码执行 + CoT** |

**核心认知：RAG 只擅长"答案以文本形式存在于某些块里"的问题。** 一旦答案需要**聚合、计算、预测、实时**，就要把 RAG 升级为"会用工具的 Agent"。

```
              ┌─ 事实查询 ──> 向量/混合检索 (经典RAG)
   问题 ─路由─┤─ 统计查询 ──> Text2SQL → 数据库
   (router)   │─ 实时查询 ──> Web 检索 / API
              └─ 计算/推理 ─> 代码执行 / 计算器工具
```

**优化打法：查询路由（Query Routing）**——先用一个轻量分类判断"这个问题该走哪条路"，再分发。这是 Agentic RAG 的另一根支柱。

**时效专项**：建立**增量索引**（新文档进来即向量化入库，删旧文档同步删向量），并给块带上**时间戳元数据**，检索时按时间过滤/加权（"优先最近 30 天"）。

## 7. 优化总盘：五大武器一张图

把前面散落的优化收拢成一条**升级版流水线**，对照"必须覆盖"的五个优化点：

```
┌──────────────────────────── Advanced / Agentic RAG ────────────────────────────┐
│                                                                                 │
│  用户问题                                                                        │
│     │                                                                           │
│   [路由 Routing] ──统计→Text2SQL  ──实时→Web  ──事实↓                            │
│     │                                                                           │
│   [Query 改写/分解 Rewrite]  ① 多视角改写  ② HyDE  ③ 子问题分解                  │
│     │ (一个问题 → 多个更好的查询)                                                │
│     ▼                                                                           │
│   [混合检索 Hybrid] ── BM25 + 向量 ──RRF融合──> 候选 100                          │
│     │                                                                           │
│   [重排 Rerank, cross-encoder] ──────────────> top 3~5                           │
│     │                                                                           │
│   [父子块 Parent-Child] ── 小块命中 → 取父块 ── 控长又完整                        │
│     │                                                                           │
│   [生成 + 引用约束] ── 只用证据, 标来源                                           │
│     │                                                                           │
│   [NLI 校验] ── 支持度低 → 触发迭代检索/拒答  ←──┐                                │
│     │                                            │ 多跳/不够 → 再来一轮(Agentic) │
│     ▼                                            │                              │
│   答案(可核查)  ──────────────────────────────────┘                              │
│                                                                                 │
│  GraphRAG: 关系/全局问题走独立的"图谱检索"分支                                    │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**五大优化点逐个定性：**

| 优化 | 治哪个问题 | 核心机制（一句话） | 主要权衡 |
|---|---|---|---|
| **重排 Rerank** | ①召回不准 ②上下文长 | cross-encoder 精排 top 候选 | 准↑ 但每候选过一次模型，延迟↑ |
| **Query 改写** | ①召回不准 ④多跳 | 一问→多查/子问题/HyDE，补语义鸿沟 | 召回↑ 但多次检索，成本↑ |
| **父子块** | ②上下文长 ③幻觉 | 小块检索、父块生成 | 召回精+上下文全，建库与映射变复杂 |
| **GraphRAG** | ④多跳 ⑥全局 | 实体-关系图，沿边游走 | 多跳/全局强，但建库贵、维护重 |
| **Agentic RAG** | ④多跳 ⑤时效统计 | LLM 当大脑：路由+迭代检索+用工具 | 能力最强，但多轮调用、延迟与成本最高 |

**Query 改写里的两招术语补全：**
- **HyDE（Hypothetical Document Embeddings，假设性文档嵌入）**：先让 LLM 对问题"**先编一个假设答案**"，再拿这个**假设答案**去做向量检索。原理：答案的措辞往往比问题更接近目标文档，从而缩小语义鸿沟（注意假设答案可能含错误实体，所以它**只用来检索、不用来回答**）。
- **多视角改写（Multi-Query）**：把一个问题改写成 3~5 个不同问法分别检索再并集，降低"一种问法召不回"的风险。

**Agentic RAG 一句话**：不再是"固定一条流水线跑到底"，而是让 **LLM 作为决策者**，自己判断"要不要再检索一次、该用哪个工具、证据够不够"，把**路由 + 多跳迭代 + 工具调用**串成一个能反思的循环。它统一了第 5、6 节的解法。

## 8. 数值例子 / 手算

**例 1：召回率与 topK 的关系（为什么要混合检索 + 大候选 + 重排）**

设某 query 的"真正相关块"在知识库里有 3 个。某向量检索把它们排在第 2、8、40 位。

- 若 $K=5$（只取前 5）：命中 1 个（第 2 位），**召回率 $=1/3\approx 33\%$**，answer 注定残缺。
- 若先用大候选 $K=100$ 把三个都捞进来，再用重排把它们提到前 3：**召回率 $=3/3=100\%$**，且最终只塞 3 块给模型。

> 结论：**"召回阶段取大、重排阶段取小"** 是同时兼顾召回率和上下文长度的标准姿势。

**例 2：上下文预算手算（为什么不能无脑塞）**

假设模型上下文窗口 8K token，留给"问题+指令+答案"约 1K，证据预算 ≈ 7K token。
若每个块约 350 token：

$$\text{可塞块数} \approx \frac{7000}{350} = 20 \text{ 块}$$

但"中间迷失"告诉我们：塞 20 块里，中间的 ~12 块利用率很低 → **有效证据其实只有头尾几块**。
若用父子块：子块 200 token 命中后取 1500 token 父块，塞 3~4 个父块就用满预算，但每个都是完整段落，**有效信息密度远高于 20 个碎块**。

**例 3：RRF 融合手算**

某文档在 BM25 里排第 1、在向量里排第 3，取 $k=60$：

$$\text{RRF} = \frac{1}{60+1} + \frac{1}{60+3} = 0.01639 + 0.01587 = 0.03226$$

另一文档只在向量里出现且排第 1：$\frac{1}{60+1}=0.01639$。
→ 第一个文档（两路都靠前）综合得分更高，**被两路共同认可的证据自动上浮**，这正是 RRF 想要的效果。

**例 4：私有化部署的成本直觉（呼应原文件"客户要私有化、没服务器"）**

- 向量库本身轻量：100 万块 × 1024 维 × 4 字节 ≈ **4 GB** 向量，普通服务器内存可放下（以实际索引结构为准，HNSW 等会有额外开销）。
- 真正吃显存的是**生成模型**：一个 7B 模型 FP16 推理约需 **14 GB** 显存量级（$7\text{B}\times 2\text{字节}=14\text{GB}$，KV cache 另算，以官方/实测为准）。
- 启示：**检索可以做很重（混合+重排+GraphRAG），瓶颈通常在生成端的算力**。私有化时优先把"召回做到极致"，让小模型也能答好，是务实路线。

## 常见问题

| 问题 | 答案 |
|---|---|
| 接了 RAG 为什么还幻觉？ | RAG 不改变模型"会续写编造"的本质；召回不全时它仍补缺口。需引用约束 + NLI 校验 + 拒答兜底（第 4 节）。 |
| 召回不准先调哪里？ | 先上**混合检索 + 重排**，性价比最高；再考虑 query 改写、调 chunk 大小（第 2 节）。 |
| chunk 切多大？ | 没有银弹。语义聚焦用小块，上下文完整用大块——用**父子块**两头都要（第 3 节）。 |
| topK 设多少？ | 召回阶段取大（如 100）保召回，重排后取小（如 3~5）控长控质（例 1）。 |
| 多跳问题（"X 的兄弟"）怎么办？ | naive RAG 一跳召不回桥梁块；用**迭代检索**或 **GraphRAG**（第 5 节）。 |
| 统计/预测/实时类怎么办？ | 超出 RAG 边界，靠**查询路由**分发到 Text2SQL / 工具 / Web（第 6 节）。 |
| GraphRAG 一定要上吗？ | 不。建库贵、维护重；多跳占比低就用迭代检索，把 GraphRAG 留给关系密集/全局问题。 |
| Agentic RAG 和普通 RAG 区别？ | 普通 RAG 是固定流水线；Agentic 让 LLM 当决策者，自主路由+多跳迭代+用工具，能力强但延迟成本高（第 7 节）。 |
| 重排器会不会很慢？ | cross-encoder 每个候选过一次模型，是延迟大头。控候选数量（rerank 候选 × 单次延迟 = 总延迟）。 |
