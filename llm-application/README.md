## 0. 一句话锚点

**LLM 应用 = 一个"语言推理内核(LLM)" + 一圈"把它接到真实世界的工程外壳"。**

LLM 本身只会做一件事：**给定一段文本(prompt)，预测下一个 token，循环到结束**。它没有记忆、没有联网、不知道你公司昨天的财报、也不会真的去调 API。所有"看起来很智能的应用"，本质都是在这个内核外面**包了一层工程**：把外部知识塞进 prompt(RAG)、把工具描述塞进 prompt 让它输出调用指令(Tool/Agent)、把多轮历史塞进 prompt(对话)。

> 记住这条主线：**应用工程的 90% 工作，是在"如何构造一个好的 prompt 上下文"和"如何处理模型吐出的那段文本"上。**

## 1. 地基 / 前置

理解后文需要先夯实四个最原子的概念。

**(1) Token(词元)** —— 模型不认字，只认整数 ID。文本先被"分词器(tokenizer)"切成 token。中文大致 **1 个汉字 ≈ 1~2 token**，英文 **1 个单词 ≈ 1.3 token**。计费、上下文长度、延迟都按 token 算。

**(2) 上下文窗口(context window)** —— 模型一次能"看见"的最大 token 数(输入 + 输出)。例如 8K / 32K / 128K。**它就是模型的"工作记忆"上限**——超出的内容必须靠外部系统(检索、摘要)塞回来。

**(3) 自回归生成(autoregressive)** —— 输出是一个 token 一个 token 蹦出来的，每个新 token 都依赖前面所有 token。这解释了两件事：① 输出越长越慢(线性)；② 流式(streaming)返回成为标配。

**(4) 概率采样(temperature / top-p)** —— 同一 prompt 多次调用结果可能不同。$\text{temperature}=0$ 近似确定性(贪心)，越大越发散。应用里**事实型任务调低、创意型任务调高**。

```
        文本 "你好世界"
            │  分词器 tokenize
            ▼
        [你, 好, 世界]  →  [101, 872, 686, 4518]   (token id)
            │  喂进模型，自回归
            ▼
        预测下一个 token 的概率分布 P(next | 前文)
            │  采样(temperature/top-p)
            ▼
        逐个吐出 → 拼回文本(detokenize)
```

## 2. 四种应用模式

按"模型要做的事有多复杂"从低到高排列。**复杂度越高，工程外壳越厚、可控性越差、评估越难。**

```
复杂度 ↑
        ┌──────────────────────────────────────────┐
  Agent │ 自主多步：规划→调工具→观察→再规划→...      │  ← 最强也最难控
        ├──────────────────────────────────────────┤
   工具 │ 单步函数调用：模型说"调 X(参数)"，系统执行  │
        ├──────────────────────────────────────────┤
   RAG  │ 检索外部知识 → 拼进 prompt → 生成有据回答   │
        ├──────────────────────────────────────────┤
   对话 │ 纯 prompt-in / text-out，多轮上下文        │  ← 最简单最可控
        └──────────────────────────────────────────┘
```

**(A) 对话 / 纯生成(Chat)** —— 最基础形态。输入历史消息，输出回复。没有外部知识、没有动作，能力边界 = 模型训练时见过的知识。适合：闲聊、写作、翻译、改写、头脑风暴。**软肋**：会"一本正经地胡说(幻觉)"、知识有截止日期、不知道你的私有数据。

**(B) RAG(检索增强生成)** —— 在生成前，先去外部知识库(向量库/数据库/搜索)**检索**出相关片段，拼进 prompt 当"参考资料"，让模型"看着资料回答"。解决对话模式的"不知道私有数据 + 幻觉"两大软肋。详见 §5。

**(C) 工具调用(Function/Tool Calling)** —— 给模型一份"工具清单"(每个工具的名字、用途、参数 schema)。模型判断需要时，**不直接回答，而是输出一段结构化的调用请求**(如 `{"tool":"查天气","args":{"city":"北京"}}`)；系统真正执行该函数，把结果再喂回模型，由它组织成自然语言。这是 Agent 的"手脚"。

> 关键认知：模型**自己并不会执行任何函数**。它只是"建议调用"，真正的执行权永远在你的代码手里——这正是安全控制的抓手。

**(D) Agent(智能体)** —— 把"工具调用"放进一个**循环**里：模型规划下一步→调工具→看结果→判断够不够→不够就接着调，直到完成目标。它能处理"订一张明天去上海最便宜的票并发到我邮箱"这种**需要多步、需要中途决策**的任务。详见 §6 与 [[llm-application/agent/OpenCode/README]]。

| 模式 | 外部知识 | 能执行动作 | 步数 | 可控性 | 典型场景 |
|---|---|---|---|---|---|
| 对话 | ✗ | ✗ | 单轮文本 | 高 | 写作、翻译、客服话术 |
| RAG | ✓(只读检索) | ✗ | 单轮文本 | 较高 | 知识库问答、文档助手 |
| 工具 | 可经工具 | ✓(单次) | 1 步动作 | 中 | 查天气、查订单、算账 |
| Agent | ✓ | ✓(多次) | 多步循环 | 低 | 自动化任务、Coding Agent |

## 3. 三种知识注入

"模型不知道我的数据"是落地第一难题。把外部/私有知识喂进去有三条路，**不是三选一，而是按场景组合**。

```
   知识规模大、更新慢、要"内化为能力"
        ▲
        │   ┌──────────┐
   微调 │   │ Fine-tune │  改模型权重
        │   └──────────┘
        │   ┌──────────┐
   RAG  │   │ Retrieval │  改"喂进去的上下文"(外挂)
        │   └──────────┘
        │   ┌──────────┐
 Prompt │   │ In-context│  直接写在提示词里
        ▼   └──────────┘
   知识量小、变化快、要"即时生效"
```

**(1) Prompt 注入(In-Context Learning)** —— 把知识/示例**直接写进提示词**。最轻量、零训练、改一行字立刻生效；但受**上下文窗口**限制，塞不下大量知识，且每次请求都重复占 token(贵)。适合：少量规则、几个示例(few-shot)、风格约束。

**(2) RAG 注入** —— 知识放在**外部库**里，按需检索相关片段拼进 prompt。**知识更新只需更新库，不动模型**；可承载海量、高时效知识；带来"出处可追溯"。代价：多了检索系统，召回质量直接决定回答质量。这是企业知识问答的**默认首选**。

**(3) 微调注入(Fine-tuning)** —— 用领域数据**继续训练模型，改其权重**，让知识/风格/格式"长进模型里"。优点：推理时不占上下文、风格最稳、能学会 RAG 难表达的"隐性技能"(如特定输出格式、领域语气)。缺点：要数据、要算力、知识一变就得**重训**，时效差。常用 **LoRA/QLoRA** 等参数高效方法降低成本。

| 维度 | Prompt | RAG | 微调 |
|---|---|---|---|
| 改的是什么 | 提示词 | 外挂知识库 | 模型权重 |
| 知识更新速度 | 实时 | 近实时(更新库) | 慢(需重训) |
| 可承载知识量 | 小(受窗口限) | 大(库无上限) | 中(进权重) |
| 出处可追溯 | 否 | ✓ 强 | 否 |
| 推理时 token 成本 | 高(每次带) | 中(带检索片段) | 低 |
| 一次性投入 | 几乎为零 | 中(建检索) | 高(数据+训练) |
| 最适合 | 规则/示例 | 时效知识问答 | 风格/格式/领域能力 |

**选型口诀**：**先 Prompt，不够上 RAG，RAG 仍解决不了"模型不会做"才上微调；三者常叠加**(微调出"会答的模型" + RAG 喂"最新的料")。

## 4. 工程链路(一个请求的一生)

从用户输入到最终响应，生产级应用通常经过这条流水线。**每个环节都是可独立优化、独立监控的"工位"。**

```
用户输入
   │
   ▼
┌─────────────┐  鉴权、限流、敏感词、prompt 注入攻击检测
│ 1 接入网关  │
└─────┬───────┘
   ▼
┌─────────────┐  判断意图：闲聊？查知识？要不要调工具？走哪个模型？
│ 2 路由/编排 │
└─────┬───────┘
   ▼
┌─────────────┐  RAG：检索知识库；Agent：取记忆/历史
│ 3 上下文构造│  → 组装成最终 prompt（系统提示+检索片段+历史+用户问）
└─────┬───────┘
   ▼
┌─────────────┐  调 LLM 推理（可流式）；工具调用在此循环
│ 4 模型推理  │
└─────┬───────┘
   ▼
┌─────────────┐  解析结构化输出、格式校验、引用回填、再检查幻觉/越权
│ 5 后处理    │
└─────┬───────┘
   ▼
┌─────────────┐  日志、Trace、Token 计量、评分、用户反馈采集
│ 6 观测/反馈 │ ──┐
└─────┬───────┘   │ 回流，喂给 §7 迭代
   ▼              │
 返回用户 ◀────────┘
```

**逐工位说明：**

- **接入网关**：鉴权、按用户/租户限流(防刷爆账单)、内容安全过滤、检测 **prompt 注入**(用户试图用"忽略以上指令"劫持系统提示)。
- **路由/编排**：决定这条请求该怎么走——简单问题用小模型省钱，复杂问题用大模型；要不要触发 RAG/Agent。LangChain / LlamaIndex 等框架主要服务这一层(见 `langchain/`)。
- **上下文构造**：把"系统提示 + 检索片段 + 多轮历史 + 当前问题"拼成一个 prompt。**这是质量的命门**——拼得好不好直接决定答得好不好。要管好 token 预算(见 §9)。
- **模型推理**：调用 LLM。生产上通常接**推理服务**(vLLM / TGI / 商用 API)。工具调用与 Agent 循环在此发生。
- **后处理**：把模型吐的文本**变可靠**——JSON 校验/重试、引用来源回填、敏感信息脱敏、二次幻觉检查。
- **观测/反馈**：记 Trace(整条链路耗时分解)、计 token、打分、收集"赞/踩"。**没有观测就没有迭代**。

## 5. RAG 拆解(检索增强生成)

RAG 分两条流水线：**离线建库**(把知识变成可检索的向量) + **在线检索增强**(每次请求查库拼 prompt)。详见 [[llm-application/rag/README]]。

```
┌──────────────── 离线建库（一次/定期） ────────────────┐
 原始文档(PDF/网页/DB)
     │ ① 切块 chunking（按段落/句子切成小片，带重叠）
     ▼
 文本块 chunk_1 ... chunk_n
     │ ② Embedding 模型把每块编码成向量（语义→数值）
     ▼
 向量 v_1 ... v_n  ──③ 存入向量库（Faiss/Milvus/PGVector）
└───────────────────────────────────────────────────────┘

┌──────────────── 在线检索（每次提问） ──────────────────┐
 用户问题 q
     │ ④ 同一 Embedding 模型把 q 也编码成向量 v_q
     ▼
 向量库做相似度搜索（取与 v_q 最近的 top-k 块）
     │ ⑤ （可选）重排序 rerank：用更强模型精排 top-k
     ▼
 拿到最相关的 k 段文本
     │ ⑥ 拼 prompt：「参考资料：<k段> 。问题：q。请据资料回答」
     ▼
 LLM 生成「有据可查」的回答 + 标注出处
└───────────────────────────────────────────────────────┘
```

**为什么用向量而不是关键词？** 关键词匹配("社保")查不到语义相近但用词不同的句子("五险一金缴纳")。**Embedding 把语义映射到向量空间，意思相近的句子向量也相近**，用余弦相似度 $\cos(\theta)=\frac{v_q\cdot v_i}{\|v_q\|\|v_i\|}$ 衡量，从而做到"按意思找"。Embedding 模型选型见 `embbedding-model.md`、`rag/embedding.md`。

**三个最常翻车的旋钮(讲含义与权衡)：**

- **chunk 大小**：太小→语义被切碎、单块信息不全；太大→一块里混入无关内容、稀释相关性、还更占 token。常配**重叠(overlap)**避免把一句话从中切断。
- **top-k**：取几段。太小→可能漏掉答案所在块(召回不足)；太大→噪声多、token 贵、模型被无关内容带偏。
- **rerank(重排)**：向量检索快但粗，先粗召回 50 段，再用更精的模型精排出最相关 5 段，**召回率与精度兼得**，代价是多一次模型调用的延迟。

RAG 的常见问题(检索不准、答非所问、引用错位)见 `rag/存在的一些问题.md`、`rag/方案.md`。

## 6. Agent 拆解(智能体)

Agent 的灵魂是一个**循环**：让模型像人一样"想一步、做一步、看结果、再想"。最经典的范式是 **ReAct = Reason(推理) + Act(行动)**。

```
        目标：「帮我查北京明天天气并提醒带伞」
                    │
        ┌───────────▼────────────┐
        │   ① 规划 Plan/Reason    │  模型想：要先查天气
        └───────────┬────────────┘
                    ▼
        ┌────────────────────────┐
        │   ② 行动 Act            │  输出工具调用：天气API(北京,明天)
        └───────────┬────────────┘
                    ▼ 系统真正执行工具
        ┌────────────────────────┐
        │   ③ 观察 Observe        │  得到：「明天小雨」喂回模型
        └───────────┬────────────┘
                    ▼
        ┌────────────────────────┐
        │   ④ 反思 Reflect        │  下雨→该提醒带伞→目标达成？
        └───────────┬────────────┘
              达成 │ 未达成→回到①继续循环
                    ▼
                最终回答
```

**Agent 的四大支柱(每个都是一个工程子系统)：**

1. **规划(Planning)**：把大目标拆成可执行的小步。弱则乱调工具、绕圈子。
2. **工具(Tools)**：Agent 的手脚——搜索、代码执行、读写文件、调 API。工具描述写得清不清楚，直接决定模型会不会用、用得对不对。
3. **记忆(Memory)**：短期(本轮对话历史) + 长期(把过往经验存进向量库，需要时检索回来)——本质又是 RAG。
4. **反思(Reflection)**：自检结果对不对、要不要换路子，避免在错误路径上一条道走到黑。

**最大风险——失控与放大**：Agent 能自主调工具，一旦规划出错可能**连锁犯错**(删错文件、发错邮件、烧光预算)。因此生产上要加：**步数上限**(防死循环)、**预算上限**、**高危动作人工确认(human-in-the-loop)**、**工具最小权限**。

> Coding Agent(如 OpenCode/OpenClaw)是 Agent 最成熟的落地形态——目标明确、工具齐(读写代码、跑测试)、反馈即时(编译/测试通过与否)。详见 [[llm-application/agent/OpenCode/README]] 与 `agent/OpenClaw.md`。

## 7. 评估与迭代

**LLM 应用最反直觉的一点：你很难像传统软件那样"测对错"**——同一输入输出可能不同，"好不好"还常常主观。所以要建一套"评估飞轮"。

```
   ┌─────────── 评估飞轮 ───────────┐
   │  离线评测集（固定题+标准答案/评分标准）
   │        │ 每次改 prompt/模型/RAG 先在这跑
   │        ▼
   │   A/B 灰度上线（小流量真实用户）
   │        │ 比指标：满意度、解决率、成本
   │        ▼
   │   线上观测 + 用户反馈（赞/踩、人工抽检）
   │        │ 把 bad case 沉淀回评测集
   │        └──────────────► 回到离线评测集（飞轮转起来）
   └────────────────────────────────┘
```

**三层评估方法(各有取舍)：**

- **规则/指标(自动、便宜)**：精确匹配、关键词命中、JSON 格式合法率、是否引用了来源。适合有标准答案的任务。
- **LLM-as-Judge(用强模型当裁判)**：让另一个(更强的)模型按评分标准给回答打分。**能评开放题、可规模化**，但裁判自身有偏见、需校准；评分标准(rubric)要写细。
- **人工评估(最准、最贵)**：专家逐条看。用于校准前两者、把关高危场景。

**该盯哪些指标？** 质量类：**忠实度**(回答是否忠于检索资料、有没有幻觉)、**相关性**、**解决率**；工程类：**延迟(P50/P95)**、**Token 成本/请求**、**错误率**；业务类：**留存、转化、人工兜底率**。

**迭代铁律**：**一次只改一个变量**(换了模型又改了 prompt，出了问题分不清是谁的功劳/锅)，每次都用同一套评测集回归，防止"按下葫芦浮起瓢"。

## 8. 落地考量(上线前要算的账)

| 维度 | 要回答的问题 | 常用手段 |
|---|---|---|
| **成本** | 每千次请求烧多少钱？ | 小模型路由、prompt 瘦身、KV/语义缓存、批处理 |
| **延迟** | 用户等几秒？首 token 多久出？ | 流式输出、并行检索、小模型、就近部署 |
| **并发/吞吐** | 高峰扛得住吗？ | 推理服务(vLLM 连续批处理)、限流、排队降级 |
| **可靠性** | 模型挂了/超时怎么办？ | 超时重试、多供应商兜底、降级到规则 |
| **安全** | 会被注入/越狱/泄露吗？ | 输入过滤、输出审查、工具最小权限、敏感信息脱敏 |
| **合规/隐私** | 数据能出域吗？要私有化吗？ | 本地部署、数据脱敏、审计日志、可解释/留痕 |
| **可控性** | 输出格式/内容稳吗？ | 结构化输出+校验重试、温度调低、护栏(guardrails) |

**两条最容易被忽视的落地真相：**
- **缓存是省钱第一杠杆**：高频重复问题(FAQ)做**语义缓存**(问法不同但意思相同也命中)，能砍掉大量重复推理。
- **"够用就好"原则**：90% 场景用小模型 + 好的 RAG，效果接近大模型而成本低一个数量级。**别用大炮打蚊子**。

## 9. 数值例子 / 手算

下面三笔账帮你建立"工程直觉"。**数字为便于心算的演示值，实际以官方计价/实测为准。**

**例 1：上下文窗口够不够装我的知识库？**
设知识库 1000 篇文档，每篇约 2000 中文字 ≈ 3000 token，共 $1000\times3000=3\times10^6$ token。
模型窗口 128K = $1.28\times10^5$ token。
$$\frac{3\times10^6}{1.28\times10^5}\approx23\ \text{倍}$$
**结论**：全量塞 prompt 差 23 倍，根本塞不下 → **必须用 RAG**，每次只取最相关几段。这就是 §3"知识量大→走 RAG"的量化由来。

**例 2：RAG 一次请求的 token 预算。**
取 top-k=5，每块 500 token → 检索片段 2500 token；系统提示 300；多轮历史 1200；用户问题 200。
输入合计 $2500+300+1200+200=4200$ token，再留输出 800 token，**单请求约 5000 token**。
在 8K 窗口下**已用掉 62%**——说明 chunk 不能太大、历史要适时摘要，否则容易"撑爆窗口"。

**例 3：月度 Token 成本估算。**
日活 10000，人均 5 轮，每轮约 5000 token(承例 2)。
日 token $=10000\times5\times5000=2.5\times10^8$；月 $\approx7.5\times10^9$ token。
设综合单价"约 $X$ 元 / 百万 token(以供应商报价为准)"，月成本 $\approx 7500\times X$ 元。
**杠杆**：把人均轮次中 40% 的重复 FAQ 走**语义缓存**(0 推理成本)，月成本立降约 40%；再把简单轮路由到小模型，可再省一截。

**例 4：召回足够吗(简单概率直觉)。**
设单段被检中的概率 0.7，答案分散在 2 个段里，二者都召回(独立近似)概率 $0.7\times0.7=0.49$。
$$1-0.49=0.51$$ 即**约一半概率漏掉完整答案** → 这就是要**加 rerank、适当增大 top-k、改进 chunk** 的动机。

## 常见问题

| 问题 | 答 |
|---|---|
| RAG 和微调到底选哪个？ | 知识"变得快、要追溯"选 RAG；要模型"学会某种风格/格式/技能"选微调；多数生产是**微调打底 + RAG 供料**。 |
| 模型还是会幻觉怎么办？ | 强约束"只依据资料回答，无依据就说不知道" + 引用回填 + 后处理校验 + 降温度；RAG 减幻觉但**不能根除**。 |
| 为什么我的 RAG 答得很烂？ | 90% 是**检索**问题不是生成问题：先查召回率(chunk 切法、embedding 选型、top-k、要不要 rerank)，见 `rag/存在的一些问题.md`。 |
| Agent 总是绕圈/烧钱？ | 加步数上限、预算上限、把工具描述写清楚、复杂任务先固化成确定性流程，别全交给自由 Agent。 |
| 一定要用 LangChain 这类框架吗？ | 早期/简单场景直接调 API 更透明可控；编排复杂(多工具/多步/多数据源)时框架能省胶水代码，见 `langchain/`。 |
| 怎么压成本？ | 优先级：语义缓存 > 小模型路由 > prompt 瘦身 > 批处理 > 私有化部署摊薄。 |
| 怎么选 Embedding 模型？ | 看语种支持、检索榜单表现、向量维度(影响存储/速度)、是否需私有化，见 `embbedding-model.md`、`rag/embedding.md`。 |
