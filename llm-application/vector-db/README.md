## 0. 一句话锚点

**向量数据库 = 专门存"高维向量"并能对它做"近似最近邻（ANN）检索"的数据库。**

传统数据库问的是"`name = '张三'` 的行在哪"（精确匹配）；
向量数据库问的是"和这个 1024 维向量**方向最像**的前 10 个向量是哪些"（相似度匹配）。

它的核心价值：把语义相似度计算从 $O(N)$ 暴力扫描，降到近似 $O(\log N)$，让亿级数据的语义检索可在毫秒内返回。

## 1. 地基：从"词搜索"到"语义搜索"

文件给的方向是 `词搜索 ---> 语义搜索`，我们就从这里出发。

**词搜索（关键词/字面匹配，如 BM25、倒排索引）**：
- 机制：把文档切成词，建"词 → 文档列表"的倒排表。查询时按词命中。
- 痛点：只认**字面**。查"如何降低汽车油耗"，命中不了写着"提升燃油经济性"的文档——同义不同字。

```
查询: "降低油耗"
文档A: "提升燃油经济性"   ← 语义相同，但一个字都不重叠 → 词搜索漏掉(召回为0)
文档B: "降低油价"         ← 字面重叠"降低""油"，但语义无关 → 词搜索误命中
```

**语义搜索**：不比字面，比**意思**。怎么做？把文本映射成一个向量（embedding），意思相近的文本，向量在空间里靠得近。于是"找意思像的"变成了"找几何上近的"。

```
                  embedding 模型
  "降低油耗"   ───────────────►  [0.21, -0.08, ..., 0.55]   ┐
  "燃油经济性" ───────────────►  [0.19, -0.07, ..., 0.52]   ┝ 这两个向量夹角很小 → 判为相似
  "降低油价"   ───────────────►  [-0.33, 0.41, ..., -0.12]  ┘ 与上面夹角大 → 判为不相似
```

> 一句话：**词搜索比字符串，语义搜索比向量。向量库就是为后者而生的引擎。** embedding 怎么训练、怎么选，见 [[llm-application/embbedding-model]]。

## 2. embedding 向量检索：向量从哪来、怎么比

### 2.1 向量从哪来

一段文本经 embedding 模型（如 BGE、GTE、OpenAI text-embedding、M3E）编码，得到一个**定长稠密向量**，维度 $d$ 常见为 384 / 768 / 1024 / 1536 / 3072。这个向量是文本语义的"数值指纹"。

```
文本 ──► [Tokenizer] ──► token ids ──► [Transformer] ──► 池化(mean/CLS) ──► 向量 v ∈ R^d
                                                                          ↓ 常做 L2 归一化
                                                                      ||v|| = 1
```

### 2.2 怎么衡量"近"——相似度度量

设两向量 $u, v \in \mathbb{R}^d$。三种常用度量：

- **余弦相似度**（最常用，只看方向）：$\cos(u,v)=\dfrac{u\cdot v}{\|u\|\,\|v\|}$，取值 $[-1,1]$，越大越相似。
- **内积 / 点积 IP**：$u\cdot v=\sum_i u_i v_i$。向量**已归一化**时，内积 = 余弦。
- **欧氏距离 L2**：$\|u-v\|_2=\sqrt{\sum_i (u_i-v_i)^2}$，越小越近。

**关键事实**：若所有向量都做了 L2 归一化（$\|u\|=\|v\|=1$），则

$$\|u-v\|^2 = \|u\|^2+\|v\|^2-2\,u\cdot v = 2 - 2\cos(u,v)$$

即**欧氏距离与余弦相似度单调对应**。所以工程上常**先归一化，再用内积**——内积无开方、最快，等价于余弦。归一化后所有向量落在单位超球面上，**夹角才是语义距离，长度被抹掉**。

### 2.3 检索 = top-k 最近邻

给定查询向量 $q$，在库 $\{v_1,\dots,v_N\}$ 中找相似度最高的 $k$ 个。这就是 **k-NN（k 最近邻）** 问题。它是向量库的全部计算核心。

---

## 3. 暴力检索的瓶颈：为什么必须近似

最朴素的做法：把 $q$ 和库里每个向量都算一遍相似度，排序取 top-k——**Flat / 暴力检索**。

它**100% 准确（recall=1.0）**，但代价是：计算量 $\approx N\times d$ 次乘加（$O(Nd)$），内存 $N\times d\times 4$ 字节（float32 存全部原始向量）。

**手算感受规模**（$N=10^7$，$d=768$）：单次查询乘加 $10^7 \times 768 \approx 76.8$ 亿次浮点运算；原始向量内存 $30.7\,\text{GB}$。

单机 CPU 每秒约 $10^9$ 量级有效相似度比较，一次查询要数秒——**QPS 极低，内存吃满**。这就是 ANN（近似最近邻）登场的理由：**牺牲一点点准确率，换几个数量级的速度。**

---

## 4. ANN 总览：加速的三条路

ANN（Approximate Nearest Neighbor）放弃"绝对正确"，只要"大概率找到真正的近邻"。三大加速思路（可组合）：

```
暴力 Flat: 比全部 N 个 → 准但慢
   ├─ 思路A【少比一些】图索引 HNSW：建"近邻图"沿边贪心走，只摸一小撮
   ├─ 思路B【分桶筛选】倒排 IVF：先聚类成 nlist 个桶，只搜最近 nprobe 个桶
   └─ 思路C【压缩向量】量化 PQ/SQ：把向量压小，比较更快、内存更省
                       └─ 常与 A/B 组合，如 IVF+PQ、HNSW+PQ
```

| 流派 | 代表算法 | 加速来源 | 牺牲 |
|------|---------|---------|------|
| 图（graph） | HNSW、NSG | 只访问图上一条路径附近的点 | 内存大（要存边） |
| 倒排/聚类 | IVF、IVF-Flat | 只搜部分簇 | 边界点可能漏 |
| 量化（quant） | PQ、SQ、OPQ | 向量压缩、查表代替乘加 | 精度损失 |

下面把三个最重要的——**HNSW / IVF / PQ**——讲到原子。

## 5. HNSW：分层可导航小世界图（最常用的图索引）

HNSW（Hierarchical Navigable Small World）几乎是当今默认首选。理解它要先懂两个直觉。

**直觉1：跳表的多层结构。** 想在有序链表里快速定位，可以建多层"高速路"：上层稀疏跳得远，下层密集走得准。HNSW 把这思想搬到图上。

**直觉2：小世界图。** "六度分隔"——稀疏连接的图里，任意两点也能很少步数到达。给每个向量连若干近邻，搜索时贪心地"往离目标更近的邻居走"。

### 5.1 结构

```
Layer 2 (最稀疏，长跳)   ●─────────────●
                         |              \
Layer 1 (中等)       ●───●────●─────●────●
                     |   |    |     |    |
Layer 0 (含全部点)  ●─●─●─●─●─●─●─●─●─●─●─●   ← 所有向量都在底层，连接最密
                          ▲
                       查询从顶层入口进入，逐层下沉，越往下越精细
```

- 每个点随机分配一个最高层级（指数衰减，多数点只在 Layer 0）。
- 每层是一张近邻图；同一点在相邻层间纵向相连。

### 5.2 搜索过程（贪心 + 下沉）

1. 从**顶层入口点**出发。
2. 在当前层贪心移动：看当前点的邻居，谁离 $q$ 更近就跳过去，直到本层走不动（局部最优）。
3. 以该点为入口**下沉一层**，重复，直到 Layer 0。
4. 在 Layer 0 用一个大小为 `ef`（efSearch）的候选堆做精细搜索，返回 top-k。

```
顶层粗定位:   入口 ●→●→●  (一步跨很远，快速接近目标区域)
                       │下沉
中层细化:        ●→●→●
                       │下沉
底层精搜:   ●→●→●→●(在小邻域内用 ef 扩展候选，挑最终 top-k)
```

### 5.3 关键参数（决定召回/速度/内存）

| 参数 | 含义 | 调大的后果 |
|------|------|-----------|
| `M` | 每点最大邻居数（边数），取 16~64 | 召回↑、内存↑、构建慢 |
| `efConstruction` | 建图时候选集大小 | 图质量↑、建索引慢 |
| `efSearch`(ef) | 查询时候选集大小 | 召回↑、延迟↑ |

**经验**：`ef` 是**在线调召回/延迟的旋钮**——同一个索引调大 ef 就用更慢换更高召回，无需重建。查询复杂度近似 $O(\log N)$；内存额外开销 ≈ 每点 $M$ 条边的 id（在原始向量之上）。

> HNSW 强在召回-延迟曲线最优、支持增量插入；弱在内存大、删除较麻烦。

## 6. IVF：倒排文件 / 聚类分桶（缩小搜索范围）

IVF（Inverted File）核心：**先聚类，查询只看相关的几个簇**，避开全库扫描。

### 6.1 建索引（训练阶段）

1. 用 k-means 把所有向量聚成 `nlist` 个簇，得到 `nlist` 个质心（centroid）。
2. 每个向量归到最近质心，形成"质心 → 该簇成员列表"的倒排表。

```
            ◇ 质心c1        ◇ 质心c2
        v·  v·  v·       v·   v·
         v·   v·          v·  v·   v·
   桶1: [v3,v7,v8,...]    桶2: [v1,v5,v9,...]   ...   桶_nlist
        ◇ 质心c3
       v·  v·  v·
   桶3: [v2,v4,v6,...]
```

### 6.2 查询（nprobe 是关键旋钮）

1. 算 $q$ 到全部 `nlist` 个质心的距离，选最近的 `nprobe` 个桶。
2. **只在这 `nprobe` 个桶内**做精确比较，其余桶整体跳过。

```
查询q ──算到各质心距离──► 选最近的 nprobe=2 个桶
                              │
                      ┌───────┴───────┐
                   桶2(成员)        桶5(成员)   ← 只比这些，其它桶不看
                      └───────┬───────┘
                          top-k
```

- `nprobe=1`：最快，但若真近邻在隔壁桶就漏 → 召回低。
- `nprobe=nlist`：退化成暴力，召回 1.0 但无加速。
- **`nprobe` 是 IVF 的召回/延迟旋钮**，与 HNSW 的 `ef` 角色对应。

**边界问题（IVF 的本质缺陷）**：真正的近邻可能恰好落在相邻桶。`nprobe` 越大越能补救，代价是延迟。

**经验**：`nlist` ≈ $\sqrt{N}$ 到 $4\sqrt{N}$；`nprobe` 取 `nlist` 的 1%~10% 起调。

## 7. PQ：乘积量化（压显存的关键）

PQ（Product Quantization）解决的是**内存**问题——HNSW/IVF 仍要存原始向量，亿级 float32 动辄上百 GB。PQ 把向量**压缩**，并让比较变成"查表"。

### 7.1 核心思想：切段 + 各段聚类 + 用编号代替

把 $d$ 维向量切成 $m$ 个子段，每段 $d/m$ 维。对每个子段独立做 k-means，得到 $k^*$（常 256）个**子质心码本**。原向量 → 每段用"最近子质心的编号"表示。

```
原向量 (d=8, float32 = 32字节):
[ 0.1 0.3 | 0.9 0.2 | 0.5 0.5 | 0.7 0.1 ]
    段1        段2        段3        段4      (m=4 段)
     │          │          │          │
  查段1码本   查段2码本   查段3码本   查段4码本   (各256个子质心)
     ▼          ▼          ▼          ▼
   id=37      id=210     id=5       id=128     ← 每段1字节
压缩后: [37, 210, 5, 128]  = 4字节   (32B → 4B, 压缩8倍)
```

### 7.2 压缩比与查询加速

- **内存**：原 $d\times4$ 字节 → 压成 $m$ 字节（每段一个 8-bit id）。$d=768, m=96$ 时 $3072\text{B}\to96\text{B}$，**压缩 32 倍**。
- **查询提速（ADC，非对称距离计算）**：查询向量不压缩；预先算好"查询每段 vs 该段 256 个子质心"的距离表（$m\times256$）。比较库内向量时，按它的段编号**查表累加**即可，把高维乘加换成 $m$ 次查表加法。

```
查询q各段 ──► 距离查找表 LUT[m][256]  (一次性算好)
库内向量编码 [37,210,5,128] ──► LUT[0][37]+LUT[1][210]+LUT[2][5]+LUT[3][128] = 近似距离
                                  └── 只是 m 次"查表+加"，极快
```

### 7.3 代价与组合

- 代价：**有损压缩**，距离是近似值 → 召回下降。`m` 越大越准但越占内存。
- **OPQ**：先对向量做旋转再 PQ，让各段更"独立"，精度更高。
- **常见组合 `IVF + PQ`**：IVF 缩小范围、PQ 压缩向量——这是 Faiss 处理**十亿级**数据的经典配方（如 `IVF4096,PQ64`）。

```
十亿级方案: 向量 ──[IVF 选nprobe个桶]──► 桶内向量是PQ编码 ──[查表算近似距离]──► top-k
            └── 既快(只搜部分桶) 又省内存(PQ压32倍) ──┘
```

## 8. 召回 vs 延迟：核心矛盾与调参

这是向量库工程的**第一性矛盾**。

- **召回率 Recall@k**：返回的 top-k 里，有多少是真正的最近邻。$\text{Recall@}k=\frac{|\text{返回}\cap\text{真实top-k}|}{k}$。
- **延迟 Latency / QPS**：单次查询耗时 / 每秒查询数。

二者**此消彼长**：摸的候选越多，越可能找到真近邻（召回↑），但也越慢（延迟↑）。

```
召回率
 1.0 ┤            ●Flat(暴力,100%但最慢)
     │        ●HNSW(ef大)
     │     ●IVF(nprobe大)
 0.9 ┤   ●HNSW(ef中)
     │ ●IVF(nprobe小)
 0.8 ┤●PQ(m小,内存最省但召回低)
     └────────────────────────► 延迟(ms)
     快                        慢
   （理想: 曲线越靠左上越好; HNSW 通常最优）
```

**调参旋钮总表**：

| 算法 | 召回/延迟旋钮 | 调大 → |
|------|-------------|--------|
| HNSW | `efSearch` | 召回↑ 延迟↑（不用重建） |
| IVF | `nprobe` | 召回↑ 延迟↑ |
| PQ | `m`（段数） | 召回↑ 内存↑ |

实践方法：定一个**召回目标**（如 Recall@10 ≥ 0.95），在该约束下把延迟压到最低 / QPS 拉到最高。

## 9. 混合检索：向量 + 关键词

纯向量擅长语义，但有短板：**精确词、专有名词、型号、编号**（"iPhone 15 Pro"、"GB/T 1234"、人名）——这些字面信息 embedding 容易"糊掉"。关键词检索（BM25/稀疏）恰好相反。**混合检索 = 两者取长补短。**

```
            ┌─► 稠密向量检索(语义) ─► 结果列表A(带分数) ─┐
查询 q ─────┤                                            ├─► 融合排序 ─► 最终top-k
            └─► 稀疏/BM25检索(字面) ─► 结果列表B(带分数) ─┘
```

**融合方式**：

- **RRF（Reciprocal Rank Fusion，倒数排名融合）**：只看排名不看分数量纲，鲁棒、最常用。
  $$\text{score}(d)=\sum_{i\in\{\text{向量},\text{BM25}\}}\frac{1}{k+\text{rank}_i(d)}\quad(k\approx60)$$
- **加权线性融合**：$\alpha\cdot s_{\text{vec}} + (1-\alpha)\cdot s_{\text{bm25}}$，需先把两路分数归一化。
- **稀疏向量法**：SPLADE 等把关键词也表达成（稀疏）向量，统一在向量库里检索。

**再加一步 Rerank（重排）**：用 Cross-Encoder 对融合后的候选做精排，召回-精度再上一个台阶（属 RAG 检索后处理，见 [[llm-application/rag/README]]）。

> 经验：生产级 RAG 几乎都用"混合检索 + RRF + Rerank"，明显优于单路向量。

## 10. 主流产品：Faiss / Milvus / Qdrant

> 版本与精确指标以各项目官方文档为准，下面是稳定的定位差异。

**Faiss（Meta，是"库"非数据库）**：C++/Python **算法库**，ANN 的"事实标准实现"（HNSW/IVF/PQ/IVFPQ/OPQ 几乎全有），支持 GPU。极致性能与灵活，但**只管索引与检索**——网络服务、元数据过滤、持久化/分布式/增删要自己包。适合研究、离线大批量、嵌进自己系统。很多向量库底层借鉴它。

**Milvus（Zilliz，云原生分布式向量数据库）**：面向**生产、超大规模、分布式**的完整数据库。存算分离、组件化（接入/协调/查询/数据节点 + etcd/对象存储/消息队列），水平扩展到十亿~百亿级、多副本高可用、多索引、标量过滤、混合检索。运维相对重，适合大数据量、要高可用与弹性扩展的企业场景。

**Qdrant（Rust 编写的向量数据库）**：性能与**易用**兼顾，单机即开即用也能集群，核心索引 HNSW。Rust 实现内存安全且快；**强 payload 过滤**（带 filter 的 ANN 做得好）；Docker 一把起；支持量化压内存、混合检索。适合中小到中大规模、看重开发体验与过滤能力的团队。

```
   库/引擎 ───────────────────────────────────► 完整数据库
   Faiss            Qdrant              Milvus
   只算法/GPU强      单机+集群/过滤强/易用  云原生分布式/超大规模/高可用
   自己包服务        Rust                 组件多/运维重
   轻 ◄───────────────────────────────────────► 重
   其它: Weaviate(模块化/GraphQL)、Chroma(轻量/本地RAG首选)、
         pgvector(PG插件,复用现有库)、ES/OpenSearch(已有ES栈)
```

## 11. 选型决策

按"数据规模 + 已有技术栈 + 运维能力 + 功能需求"四问决策：

```
你的场景?
├─ 几万~几十万条, 本地原型/个人RAG ──────► Chroma / FAISS(内存) / Qdrant单机
├─ 已经在用 PostgreSQL, 量不大 ──────────► pgvector(零新增组件, SQL+向量一站)
├─ 已经在用 Elasticsearch ──────────────► ES/OpenSearch 向量字段(复用栈)
├─ 百万~千万, 要过滤+易用+不想重运维 ───► Qdrant / Weaviate
├─ 亿级以上, 要分布式/高可用/弹性扩展 ──► Milvus(/Zilliz Cloud)
├─ 纯离线大批量检索/研究/要GPU ─────────► Faiss(自己写服务)
└─ 完全不想运维 ────────────────────────► 托管云(Pinecone/Zilliz Cloud等)
```

**决策要点**：

| 维度 | 怎么权衡 |
|------|---------|
| 规模 | 十万级单机够；亿级上分布式（Milvus） |
| 过滤 | 需"向量+标量条件"强过滤 → Qdrant/Milvus（注意 pre/post-filter 对召回影响） |
| 栈复用 | 已有 PG/ES，优先 pgvector/ES，少加组件 |
| 索引 | 通用首选 HNSW；省内存且超大用 IVF+PQ |
| 运维 | 团队小 → 托管或 Qdrant/Chroma；有 SRE → Milvus 自建 |
| 一致性/更新 | 频繁增删改 → 选支持实时插入与删除回收的（HNSW 删除较弱要注意） |

## 数值例子 / 对照（动手算）

### 例1：原始向量内存（决定能否放进单机）

$N=10^7$（千万），$d=768$，float32：$N\times d\times 4 = 10^7\times768\times4 = 30.7\,\text{GB}$。单机 32GB 内存几乎放不下原始向量，**这就是要用 PQ 压缩或上分布式的理由**。

### 例2：PQ 压缩后内存

同上数据，用 PQ，$m=96$ 段、每段 1 字节：$N\times m = 10^7\times96 \approx 1\,\text{GB}$。即 30.7GB → 1GB，**压缩约 32 倍**，轻松进单机（精度略降，用 IVF+PQ 找回）。

### 例3：HNSW 边的额外内存

$N=10^7$，`M=32`，每条边存 1 个 int32 id：$N\times M\times 4 = 1.28\,\text{GB}$。这是**在原始向量之上**的额外开销——印证"HNSW 召回好但费内存"。

### 例4：IVF 把计算量砍掉多少

$N=10^7$，`nlist=10000`（每桶约 1000 条），`nprobe=32`：选桶 ≈ $10^4$ 次比较，桶内 $32\times1000=3.2\times10^4$ 次，合计 ≈ $4.2\times10^4$ 次。相比暴力 $10^7$ 次，**计算量降到约 1/238**，延迟从秒级降到毫秒级（召回取决于 nprobe）。

### 例5：召回-延迟权衡的直觉数字（示意，非基准）

| 配置 | Recall@10 | 相对延迟 | 内存 |
|------|-----------|---------|------|
| Flat 暴力 | 1.00 | 100× | 100% |
| HNSW(ef=64) | ~0.98 | 1× | 130%（含边） |
| IVF(nprobe=8) | ~0.90 | 0.8× | 100% |
| IVF+PQ | ~0.85 | 0.5× | ~5% |

> 规律：要召回上 HNSW，要省内存上 IVF+PQ，二者之间用 nprobe/ef/m 微调。

## 常见问题

| 问题 | 答 |
|------|-----|
| 余弦还是内积？ | 向量归一化后二者等价，工程上"先归一化再用内积"最快 |
| HNSW 和 IVF 选哪个？ | 要最佳召回-延迟、内存够 → HNSW；超大规模/省内存 → IVF(+PQ) |
| PQ 一定要用吗？ | 内存放得下就别用（有损降召回）；放不下/十亿级才上，配 IVF 找回精度 |
| 召回突然变差？ | ef/nprobe 太小、PQ 段数 m 太小、向量没归一化、过滤把候选删太多 |
| 带条件过滤为什么慢/召回低？ | post-filter（先 ANN 再筛）可能筛空、pre-filter 实现差则慢——选过滤强的库(Qdrant/Milvus) |
| 增量插入/删除？ | HNSW 支持插入；删除多为"标记+定期重建"，频繁删改要评估 |
| 向量库能替代 RAG 全流程吗？ | 不能。它只管"检索"，前有切分/embedding、后有 rerank/拼 prompt，见 [[llm-application/rag/README]] |
| GPU 有用吗？ | Faiss-GPU 在大批量构建/检索上提速明显；在线低延迟单查询提升有限 |
| 维度越高越好？ | 不一定，更高维更准但更占内存更慢；按 embedding 模型与召回需求权衡 |
