## 0. 一句话锚点

把 Higress 想成机场的**统一安检与登机口**：所有去往不同"航空公司"（OpenAI、通义千问、DeepSeek、本地 vLLM……）的旅客（请求）都先经过它，由它来**验票（鉴权）、分流（路由）、限流（配额）、记账（计费/可观测）、改写登机牌格式（协议转换）**，然后才转发给真正的后端模型服务。

```
                 ┌────────────────────────────┐
   客户端  ───▶  │        Higress AI 网关        │  ───▶  各家大模型 / 推理服务
 (一套 OpenAI    │  鉴权 限流 路由 缓存 改写 观测  │       (vLLM / SGLang / 云 API)
  兼容协议)      └────────────────────────────┘
```

## 1. 地基：它到底解决什么问题

当一个团队从"调一个大模型"走向"生产级 LLM 应用平台"时，会撞到一连串**非模型本身、却绕不开**的工程问题：

1. **多模型、多供应商**：今天用 OpenAI，明天接通义/DeepSeek，后天上自建 vLLM。每家的鉴权方式、URL、参数字段、流式格式都不同。应用代码不该为每家写一套适配。
2. **鉴权与多租户**：谁能调？调哪个模型？用哪个 API Key？需要在入口统一卡住，而不是把密钥散落在各业务代码里。
3. **限流与配额（尤其按 token）**：LLM 成本主要由 token 决定，普通"按 QPS 限流"不够，需要**按 token 计数**做配额。
4. **稳定性**：某家模型挂了/超时/限流，要能**自动重试、降级、切换备用模型（fallback）**。
5. **可观测与成本**：每个请求消耗多少 prompt/completion token、延迟多少、命中缓存没有，都要能统计。
6. **内容安全 / 合规**：输入输出要能接内容审核，拦截违规内容。

这些问题的共性是：**它们都应该在"入口层"统一解决，而不是在每个业务里重复实现**。这正是"AI 网关"这个品类存在的理由，Higress 是其中一个实现。

> 类比：传统微服务时代我们用 API 网关（Kong/APISIX/Spring Cloud Gateway）统一处理鉴权限流；LLM 时代把同样的思路延伸到"模型流量"，多出了**协议统一、token 计量、模型路由、语义缓存**等 AI 专属能力。

## 2. 整体架构：数据面 + 控制面 + 插件

Higress 的内核是 **Envoy**（高性能 C++ 代理，做数据面）加上从 **Istio** 体系裁剪/演进而来的控制面，再叠加 **Wasm 插件**层提供可扩展能力。

```
                    ┌──────────────── 控制面 (Control Plane) ────────────────┐
   配置来源          │   监听 K8s Ingress / Gateway API / Higress CRD / 控制台   │
 (Ingress/CRD/UI) ─▶ │   → 转换成 Envoy xDS 配置 (LDS/RDS/CDS/EDS) 下发         │
                    └────────────────────────┬────────────────────────────┘
                                             │  xDS 动态下发(热更新,不重启)
                                             ▼
   客户端 ──HTTP──▶  ┌──────────────── 数据面 (Envoy 代理) ──────────────────┐
                    │  Listener → 过滤器链(Filter Chain) → Router → 上游集群    │
                    │           ├─ 鉴权插件(Wasm)                            │
                    │           ├─ 限流插件(Wasm)                            │
                    │           ├─ AI Proxy / AI 统一协议插件(Wasm)           │
                    │           └─ 可观测/日志                               │
                    └────────────────────────┬────────────────────────────┘
                                             ▼
                              上游(Upstream): 模型服务 / 云厂商 API
```

- **数据面（Envoy）**：真正"过流量"的地方。每个请求按"过滤器链"逐层处理：连接 → 解析 HTTP → 走一串过滤器（鉴权、限流、AI 处理…）→ 路由匹配 → 转发到上游。
- **控制面**：负责"把人类写的配置翻译成 Envoy 能懂的配置"。它监听 K8s 资源（Ingress、Gateway API）或 Higress 自己的 CRD，转换成 Envoy 的 **xDS** 协议配置，**动态下发**给数据面——好处是改配置**不需要重启**网关，流量不中断。
- **插件层（Wasm）**：把可扩展逻辑（鉴权、限流、AI 协议转换、内容安全等）做成 **WebAssembly 模块**，挂在过滤器链上。这是 Higress AI 能力的主要载体（见第 6 节）。

> 为什么基于 Envoy/Istio：复用成熟内核的高性能、动态配置、丰富的可观测与可扩展能力，避免重造轮子；同时面向"无 Sidecar / 单网关"的部署做了简化与增强。具体内核版本/兼容矩阵以官方文档为准。

## 3. 三大角色：一个网关顶三个

Higress 经常被概括为"**三网合一**"。理解这三个角色有助于摆放它在系统里的位置：

```
            南北向流量(外部 → 集群)            东西向流量(服务间)
                   │                                │
         ┌─────────┴─────────┐                      │
         │  1) 流量网关        │   替代 Nginx Ingress  │
         │  (Ingress 入口)    │   做 TLS/路由/限流      │
         └─────────┬─────────┘                      │
                   │                                │
         ┌─────────┴─────────┐            ┌─────────┴─────────┐
         │  2) 微服务网关      │            │   服务发现/治理     │
         │  (对接注册中心)     │◀──────────▶│ Nacos/K8s Service │
         └─────────┬─────────┘            └───────────────────┘
                   │
         ┌─────────┴─────────┐
         │  3) AI 网关         │  本文重点：面向 LLM 的统一入口
         └───────────────────┘
```

1. **流量网关（Ingress 网关）**：替代/兼容 Nginx Ingress Controller，做 TLS 终止、域名/路径路由、限流、灰度等南北向入口能力。
2. **微服务网关**：对接服务注册发现（如 Nacos、Kubernetes Service），把网关同时当作微服务的统一入口，做服务级治理。
3. **AI 网关**：面向大模型的专用能力（协议统一、多模型路由、token 限流、语义缓存、内容安全、可观测）。这是它在"LLM 应用"语境下最被关注的角色。

## 4. AI 网关的核心能力（逐项拆解）

下面这些能力**多数以 Wasm 插件形式提供**，名字以"AI 网关插件"为类别理解即可，**确切插件名/参数键以官方文档为准**。

| 能力 | 解决什么 | 机制（原理）| 怎么权衡 |
| --- | --- | --- | --- |
| 协议统一 | 各家模型 API 字段不一 | 对外暴露**一套 OpenAI 兼容协议**，对内转换成各供应商格式 | 统一接入成本低；但新字段/新供应商需插件跟进 |
| 多模型路由 | 按模型名/租户/权重分流 | 根据请求体里的 `model` 字段、Header、权重做路由 | 灵活；规则复杂时要注意可维护性 |
| 失败重试 / fallback | 某模型超时或限流 | 配置主备模型，失败时自动切换 | 提升可用性；fallback 模型质量/成本要可接受 |
| 基于 token 的限流 | 按成本而非 QPS 限流 | 统计每请求 prompt+completion token，扣减租户配额 | 更贴合成本；需要可靠的 token 计数与共享计数存储(如 Redis) |
| 语义/结果缓存 | 重复或相似问题重复烧 token | 命中则直接返回缓存结果 | 省钱省延迟；要处理一致性与"相似度阈值" |
| 内容安全 | 合规、防违规输出 | 接入内容审核服务，拦截/改写输入输出 | 合规必要；增加一跳延迟 |
| 可观测 | 看用量/延迟/成本 | 记录 token 数、模型、延迟、缓存命中等指标与日志 | 运营必备；注意日志含敏感内容时脱敏 |

### 4.1 协议统一为什么重要（举例）

应用只需面向一套接口写代码（通常是 OpenAI 风格的 `/v1/chat/completions`）：

```
应用 ──▶ Higress: POST /v1/chat/completions { "model": "qwen-max", "messages":[...] }
                     │
        AI Proxy 插件根据 model 选供应商, 改写 URL/鉴权/字段
                     ▼
         上游: 通义千问真实 API (字段/鉴权与 OpenAI 不同)
                     │
         把通义返回再"翻译"回 OpenAI 兼容格式
                     ▼
应用 ◀── 统一的 OpenAI 风格响应(含 usage.total_tokens 等)
```

好处：**换模型/换供应商只改网关配置，应用代码零改动**，包括流式（SSE）也由网关统一处理。

### 4.2 基于 token 的限流（数值例子）

设给某租户的配额是每分钟 $N=100{,}000$ token。某请求 prompt 用了 $1{,}200$ token，生成了 $800$ token，则本次消耗
$$\Delta = 1200 + 800 = 2000 \text{ token}.$$
网关在该租户的计数器上扣减 $2000$，当窗口内累计达到 $100{,}000$ 时拒绝（返回 429）或排队。多副本网关需要把计数放在**共享存储（如 Redis）**里，否则各副本各算各的会超发。

## 5. 一条请求的完整链路（调用链）

```
[客户端]
   │ POST /v1/chat/completions  (OpenAI 兼容, Bearer <token>)
   ▼
[Envoy Listener] 解析 HTTP / TLS 终止
   ▼
[过滤器链 Filter Chain] —— 逐个 Wasm/原生过滤器 ——
   ① 鉴权插件      : 校验 token / 解析租户 → 失败则 401
   ② 限流插件      : 查租户 token 配额(读 Redis) → 超额则 429
   ③ 缓存插件(可选): 命中则直接返回, 不打后端
   ④ AI Proxy 插件 : 按 model 选供应商, 改写鉴权/URL/字段
   ⑤ 内容安全(可选): 审核输入
   ▼
[Router] 按路由规则匹配上游集群(可带权重/灰度)
   ▼
[Upstream Cluster] 转发到真实模型服务(支持流式 SSE 透传)
   ▼  (响应回程)
   ⑥ 统计 usage token、写日志/指标
   ⑦ 内容安全(可选): 审核输出
   ⑧ 把响应翻译回 OpenAI 兼容格式
   ▼
[客户端] 收到统一格式响应
```

关键点：**请求方向和响应方向都会过过滤器**。token 计量、内容安全、格式回译这些事多发生在**响应回程**，因为只有拿到模型返回才知道 completion 用了多少 token。

## 6. 插件机制：为什么用 Wasm

Higress 的扩展能力主要靠 **WebAssembly（Wasm）插件**，挂在 Envoy 的过滤器链上。

```
        Envoy 数据面进程
        ┌───────────────────────────────┐
        │  原生过滤器  │  Wasm 沙箱(VM)    │
        │   (C++)     │  ┌─────────────┐  │
   流量 ─┼────────────▶│  │ 鉴权插件     │  │
        │             │  ├─────────────┤  │
        │             │  │ token 限流   │  │
        │             │  ├─────────────┤  │
        │             │  │ AI Proxy     │  │
        │             │  └─────────────┘  │
        └───────────────────────────────┘
          插件用 Go/Rust/C++ 等编译成 .wasm
```

为什么选 Wasm 而不是直接改 Envoy 源码或写 Lua：

- **安全隔离**：Wasm 跑在沙箱里，插件崩溃/越界不会拖垮整个网关进程。
- **语言灵活**：可用 Go、Rust、C++ 等编译成 `.wasm`，不必懂 Envoy C++ 内部。
- **热插拔**：插件可独立分发、按路由/域名级别开关与配置，**不必重新编译网关**。
- **可移植**：同一份 `.wasm` 在兼容 Proxy-Wasm ABI 的代理上都能跑。

代价：Wasm 有一定性能与内存开销，且能力受 ABI 约束（不能随意访问宿主一切资源）。对绝大多数治理类逻辑这点开销可接受。

## 7. 配置形态：你怎么"告诉"网关该怎么做

Higress 支持多种配置入口，**底层都会被控制面翻译成 Envoy xDS**：

| 配置方式 | 适合谁 | 说明 |
| --- | --- | --- |
| K8s **Ingress** 注解 | 已有 K8s/Nginx Ingress 习惯的人 | 兼容 Nginx Ingress 注解风格，迁移友好 |
| **Gateway API** | 想用 K8s 新标准的人 | 更结构化的路由/网关资源模型 |
| Higress **CRD / 控制台** | 想用 AI 专属能力的人 | 图形化配置模型路由、限流、插件等 |
| 非 K8s（单机/standalone）| 没有 K8s 的小场景 | 也支持脱离 K8s 独立部署 |

> 注意：**具体的注解键名、CRD 字段、控制台选项以官方文档/对应版本为准**，本文只讲"有这几类入口、各自定位"，不背具体默认值。

一个"模型路由 + token 限流"配置在概念上长这样（伪示意，非真实字段）：

```
路由规则:
  - 匹配: path = /v1/chat/completions 且 model = "qwen-*"
    上游: 通义千问 (注入对应 API Key, 改写为其真实协议)
    插件:
      - token 限流: 租户 A 每分钟 100000 token, 超额 429
      - 失败 fallback: 主 qwen-max → 备 qwen-plus
  - 匹配: model = "gpt-*"
    上游: OpenAI 兼容端点
```

## 与同类对比（定位差异，非优劣定论）

| 维度 | Higress | 传统 API 网关(Kong/APISIX) | 朴素自研反向代理 |
| --- | --- | --- | --- |
| 内核 | Envoy + Istio 体系 | 各自内核(OpenResty/Nginx 等) | 通常是一段业务代码 |
| AI 专属能力 | 内置(协议统一/token 限流/模型路由/语义缓存等) | 需自行扩展插件 | 几乎都要自己写 |
| 配置动态性 | xDS 热更新 | 多数支持热更新 | 往往要重启 |
| 扩展方式 | Wasm 插件 | Lua/插件体系 | 改代码 |
| 适用 | LLM 平台统一入口、云原生 | 通用 API 治理 | 极简/原型场景 |

实践上：若你的核心诉求是**统一管理大量大模型流量并做精细治理**，AI 网关品类（Higress 是其一）比"自己用 Nginx 拼"省力很多；若只是临时代理一两个模型，朴素反代也够。

## 常见问题 / 坑（表格）

| 现象 / 坑 | 根因 | 应对 |
| --- | --- | --- |
| 多副本网关 token 限流"超发" | 各副本各自计数 | 用**共享计数存储(Redis)**，让配额全局一致 |
| 流式(SSE)响应被缓冲、客户端"卡住一次性出" | 中间某环节没正确透传流 | 确认 AI Proxy/缓存等插件对**流式**的处理；缓存通常对流式要特殊处理 |
| 换了模型供应商应用就报错 | 字段/鉴权差异没在网关层抹平 | 用协议统一插件做**字段/鉴权/格式回译**，让对外仍是 OpenAI 兼容 |
| token 计量不准 | 不同模型 tokenizer 不同、流式难统计 | 以模型返回的 `usage` 为准；流式需在结束时汇总，必要时按供应商口径校准 |
| 改配置担心断流 | 误以为要重启 | xDS 是**动态下发**，正常改路由/插件不需要重启数据面 |
| 内容安全增加延迟 | 多了一跳同步审核 | 评估异步/采样审核与延迟的权衡，按合规要求取舍 |
| 直接照抄网上的字段名失败 | 版本/字段已变 | **以你部署版本的官方文档/CRD schema 为准**，本文只讲机制 |

> 再次强调护栏：本文刻意**不写**精确版本号、确切注解键名、API 默认值与性能数字。落地时这些**一律以官方文档与你所用版本的源码/CRD 为准**。
