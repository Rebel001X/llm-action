## 0. 一句话锚点

LLM 应用本质上只有三种"能力原语"，所有场景都是它们的组合：

```
  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
  │  ① 理解+生成 │   │ ② 检索+接地 │   │ ③ 规划+行动 │
  │  (Prompt)   │   │   (RAG)     │   │  (Agent)    │
  │ 对话/总结/  │   │ 知识问答/   │   │ 多步任务/   │
  │ 翻译/分类/  │   │ 文档助手/   │   │ 工具编排/   │
  │ 代码        │   │ 客服        │   │ 自动化      │
  └─────────────┘   └─────────────┘   └─────────────┘
         越往右：能力越强、可控性越低、成本越高
```

一句话：**Prompt 让模型"会说"，RAG 让模型"说得对"，Agent 让模型"会做"。**

## 1. 地基：LLM 到底是什么、不是什么

### 1.1 本质：一个"下一个 token 概率"机器

LLM 做的唯一一件事是：给定前文 token 序列 $x_{1..t}$，预测下一个 token 的概率分布

$$P(x_{t+1} \mid x_1, x_2, \dots, x_t)$$

然后采样一个 token，拼回去，再预测下一个——**自回归续写**。"对话""写代码""翻译"在模型眼里都是同一件事：**在合适的前文条件下续写出合适的后文**。

为什么这点重要？因为它解释了一切应用设计的根因：

- 想让它"答得对" → 你得把"对的信息"放进前文(上下文) → 这就是 **RAG** 的动机。
- 想让它"按格式答" → 你得在前文里示范格式 → 这就是 **Prompt/Few-shot** 的动机。
- 想让它"做事" → 你得让它续写出"动作指令"，再由外部执行 → 这就是 **Agent/Function Calling** 的动机。

### 1.2 三条硬边界(应用必须绕开的坑)

```
边界1：上下文窗口有限      → 长文档塞不下 → 需要切分/检索(RAG)
边界2：知识冻结在训练时    → 不知道实时/私有数据 → 需要外接(RAG/工具)
边界3：会"一本正经胡说"   → 幻觉(hallucination) → 需要接地+引用+校验
```

- **上下文窗口**：模型一次能"看到"的 token 数(如 8K / 128K / 200K)。超出就得截断或检索。
- **知识截止**：参数里冻结的是训练时的世界。问"今天股价"必然过时。
- **幻觉**：因为它是概率续写而非查表，缺信息时会"流畅地编造"。这是 RAG 与引用机制存在的根本理由。

> 记住这张地基图：**后面每个场景，都是在用某种方式"喂前文 / 取动作 / 防幻觉"。**

## 2. 场景一：对话 / 智能助手

最基础形态：用户多轮交互，模型扮演某角色作答。

```
┌──────────────────────── 一次对话请求 ────────────────────────┐
│  System: 你是耐心的客服，只用中文，不编造政策             │  ← 设定人格/规则
│  User:   我的订单怎么还没发货？                           │
│  Assistant: 请提供订单号…                                 │  ← 历史
│  User:   订单号 88231                                     │  ← 本轮
└──────────────────────────────────────────────────────────┘
                          │ 整段拼成前文送入模型
                          ▼
                  自回归生成回复
```

核心设计点：

- **System Prompt**：定义角色、语气、禁区。它是"全局前文"，对每轮生效。
- **多轮历史管理**：历史会越堆越长 → 超窗。常见策略：滑动窗口(只留最近 N 轮)、摘要压缩(把旧历史总结成一段)、向量召回(只取与当前问题相关的历史)。
- **记忆(Memory)**：跨会话记住用户偏好，通常落库 + 检索注入，而非靠模型参数。

何时用：闲聊、答疑、陪伴、引导式表单。可控性需求高时叠加 RAG(防编造)或 Function Calling(查真实数据)。

## 3. 场景二：RAG 检索增强生成

> 详见 [[llm-application/rag/README]]，这里讲清"为什么"和整体数据流。

**它解决什么问题**：边界1(窗口)+边界2(知识冻结)+边界3(幻觉)三杀。把"私有/实时/海量"知识在**回答时**检索出来塞进前文，让模型"看着资料答"。

```
┌──── 离线建库 (Indexing) ────┐      ┌──── 在线问答 (Query) ────┐
                                                                  
 文档 → 切块(chunk) → Embedding         用户问题                  
                       │                  │                       
                       ▼                  ▼ Embedding             
                  ┌─────────┐        ┌─────────┐                  
                  │ 向量库   │◄──────│ 相似检索 │ top-k           
                  │ (Vector │  ↑     └────┬────┘                  
                  │  DB)    │  存          │ 命中的 chunk         
                  └─────────┘             ▼                       
                                  ┌──────────────┐                
                                  │ 拼 Prompt：   │                
                                  │ 资料+问题     │→ LLM → 带引用回答
                                  └──────────────┘                
```

关键机制：

- **切块(Chunking)**：文档太长，切成几百 token 的小块。块太大→噪声多、超窗；块太小→语义破碎。常重叠切分(overlap)保上下文连贯。
- **Embedding + 向量检索**：把文本映射成向量，用余弦相似度找"语义最近"的块。相似度 $\cos(\vec q, \vec d)=\dfrac{\vec q\cdot \vec d}{\lVert\vec q\rVert\,\lVert\vec d\rVert}$。
- **召回增强**：混合检索(向量+关键词 BM25)、重排序(rerank)、查询改写。
- **接地与引用**：Prompt 里要求"只根据资料回答，标注来源"，把幻觉压到最低。

何时用：企业知识库、文档问答、客服、法律/医疗等**要求可溯源**的问答。优点是改知识只需改库、无需重训，且天然支持引用。

## 4. 场景三：Agent 智能体

**它解决什么问题**：单次问答搞不定的**多步、需调用外部世界**的任务(查天气→订机票→发邮件)。Agent = LLM 作"大脑"，循环地"想→做→看→再想"。

```
        ┌──────────────── Agent 循环 (ReAct) ────────────────┐
        │                                                    │
 用户目标 ─►│  Thought: 我需要先查航班                          │
        │     │                                              │
        │     ▼                                              │
        │  Action: search_flight(city, date)  ──► 工具/API   │
        │     │                                       │      │
        │  Observation: 返回 3 个航班 ◄───────────────┘      │
        │     │                                              │
        │  Thought: 选最便宜的并下单 …(继续循环)             │
        │                                                    │
        └────────────► 直到 Thought: 任务完成 → 输出 ────────┘
```

四要素：

- **规划(Planning)**：把大目标拆成步骤(可一次性规划，也可边走边定，如 ReAct = Reasoning+Acting 交替)。
- **工具(Tools)**：搜索、计算器、数据库、代码执行、其它 API——通过 **Function Calling**(见第5节)调用。
- **记忆(Memory)**：短期(当前任务上下文)+长期(向量库存历史)。
- **循环控制**：何时停、最多几步、失败怎么重试——防止"无限打转/烧 token"。

关键权衡：Agent 能力最强但**最不可控**——步数不定→延迟与成本难预估，错误会累积放大。生产中常加：步数上限、人工确认(human-in-the-loop)、可观测日志、对每步工具结果做校验。

何时用：跨系统自动化、复杂任务编排、需"自己找工具用"的场景。简单问答**不要**上 Agent(杀鸡用牛刀，又慢又贵又飘)。

## 5. 场景四：Function Calling(函数/工具调用)

**它解决什么问题**：让模型从"输出自然语言"升级到"输出结构化的、可被程序执行的调用意图"。这是 Agent 与"接真实系统"的底层协议。

机制(分四步)：

```
1. 你声明工具(给模型看 JSON Schema)：
   { "name":"get_weather",
     "description":"查询某城市天气",
     "parameters":{ "type":"object",
        "properties":{ "city":{"type":"string"} },
        "required":["city"] } }

2. 用户问："北京冷不冷？"  → 连同工具声明一起送模型

3. 模型不直接答，而是输出一个调用意图：
   { "tool":"get_weather", "arguments":{ "city":"北京" } }

4. ★你的代码★执行 get_weather("北京") → 拿到 5℃
   → 把结果再喂回模型 → 模型用自然语言总结："北京约 5℃，偏冷。"
```

要点：

- 模型**只负责"决定调谁、传什么参数"**，真正执行由你的后端完成——安全边界在你手里。
- 参数靠 **JSON Schema** 约束，能显著降低"答非格式"的概率。
- 是"让 LLM 走出文本框、接入确定性系统(数据库/计算/下单)"的标准方式，也是 Agent 调工具的实现底座。

何时用：需要实时/私有数据、需要执行确定性操作(下单、发消息、算数)的任何场景。

## 6. 任务化场景：代码 / 总结 / 翻译 / 分类

这些是"一次性 Prompt 能力"的典型落地，差别只在**前文怎么搭、输出怎么约束**。

| 场景 | 输入→输出 | 设计要点 | 常见坑 |
|------|----------|---------|--------|
| **代码** | 需求/上下文 → 代码 | 给足上下文(签名/依赖)、要求可运行、配测试 | 幻觉 API、忽略边界条件 |
| **总结** | 长文 → 摘要 | 超窗→分段总结再合并(map-reduce)；指定长度/要点 | 遗漏关键信息、引入原文没有的内容 |
| **翻译** | 源语 → 目标语 | 给术语表、保留格式/占位符、指定语气 | 术语不一致、漏译标签 |
| **分类** | 文本 → 标签 | 枚举标签集、Few-shot 示范、强制只输出标签 | 输出多余解释、超出标签集 |

长文总结的 map-reduce 思路(绕开窗口限制)：

```
长文档 ──切分──► [块1][块2][块3]...[块N]
                  │     │     │       │   每块各自总结(map)
                  ▼     ▼     ▼       ▼
                [摘1] [摘2] [摘3] ... [摘N]
                  └──────拼起来再总结(reduce)──────► 最终摘要
```

代码场景常配 RAG(检索代码库)或 Agent(自己跑测试改 bug)，是当下落地最成熟的方向之一。

## 7. Prompt 工程(把"会说"调到位)

Prompt 工程 = **用最小代价(不改参数)操纵前文，让续写命中目标**。性价比最高，永远先试它。

常用手法，从弱到强：

```
Zero-shot   直接问                     "把这句翻译成英文：…"
   │ 不够准
Few-shot    给几个示范(输入→输出对)    模型照葫芦画瓢，格式/风格立刻稳
   │ 推理类还不够
CoT         "让我们一步步想"           逼出中间推理步，数学/逻辑题大涨
   │ 想更稳
自洽/多采样  采样多条取多数            降低单次随机性
   │ 需结构化
结构约束     "只输出 JSON / 只输出标签"  配 Schema/正则，便于程序消费
```

底层为什么有效？回到 1.1：**模型是按前文条件续写**。示范、推理引导、格式声明都是在"收窄续写分布"，把概率质量压到你要的输出上。

工程化要点：明确角色与任务、给约束(长度/格式/语气)、给示例、划定禁区、必要时拆成多步。**先把 Prompt 榨干，再考虑 RAG/微调。**

## 8. 选型决策：微调 vs RAG vs Prompt

这是落地最常被问的问题。先看一句话区分：

```
Prompt   = 改"怎么问"      → 调行为/格式，零训练成本，最先试
RAG      = 改"看什么"      → 注入知识/实时数据，知识可热更新
微调     = 改"模型本身"    → 内化风格/能力/领域语感，需数据+算力
```

决策树：

```
                 ┌─ 问题是"输出格式/语气/简单行为"不对？
 起点 ──────────►│   └─►是 ── Prompt 工程(+Few-shot)  ★先试这个
                 │
                 ├─ 问题是"缺知识/要私有或实时数据/要引用"？
                 │   └─►是 ── RAG
                 │
                 └─ 问题是"懂格式也给了知识，但风格/领域能力/
                     稳定性仍不行，且有标注数据"？
                     └─►是 ── 微调 (可与 RAG 叠加)
```

三者对比：

| 维度 | Prompt | RAG | 微调 |
|------|--------|-----|------|
| 改的是 | 输入前文 | 外部知识 | 模型参数 |
| 知识更新 | 改提示词 | 改库(秒级热更) | 需重训 |
| 一次性成本 | 最低 | 中(建库/检索系统) | 高(数据+算力) |
| 推理成本 | 低 | 中(多了检索+长上下文) | 低(无需塞资料) |
| 可溯源/引用 | 弱 | **强** | 弱 |
| 擅长 | 行为/格式 | 知识接地、防幻觉 | 风格/领域能力内化 |
| 数据门槛 | 无 | 文档即可 | 需高质量标注 |

实战原则：**Prompt → RAG → 微调**逐级加码，能用前者绝不上后者；三者**可叠加**(微调出领域语感 + RAG 给实时知识 + Prompt 控格式)。

## 9. 数值例子 / 典型场景(手算)

### 9.1 Token 与成本估算

约定：英文 1 token ≈ 0.75 词；中文 1 字 ≈ 1.5~2 token(取 1.7 估)。设某 RAG 客服调用：

- System + 指令：约 300 token
- 检索注入 top-5 块，每块 400 token：$5\times400=2000$ token
- 用户问题：约 60 token
- → **输入** $\approx 300+2000+60 = 2360$ token
- 回答 200 字 ≈ $200\times1.7 \approx 340$ token **输出**

若计费为 输入 ¥0.01/千token、输出 ¥0.03/千token：

$$\text{成本} = \frac{2360}{1000}\times0.01 + \frac{340}{1000}\times0.03 \approx 0.0236 + 0.0102 = \textbf{¥0.034/次}$$

一天 10 万次 → 约 **¥3400/天**。这就是为什么要**压缩注入块数、缓存、走小模型分流**。

### 9.2 RAG 注入预算 vs 上下文窗口

设窗口 8K token，留出回答 1K，System 0.3K，问题 0.1K：

$$\text{可注入} = 8000 - 1000 - 300 - 100 = 6600\ \text{token}$$

每块 400 token → 最多注 $6600/400 \approx 16$ 块。但块越多噪声越大、成本越高、延迟越长，实测常 **top-3~5** 即够。这是"召回数量"的硬约束来源。

### 9.3 延迟直觉

延迟主要由**输出 token 数**决定(逐 token 生成)。设吞吐 50 token/s：

- 答 340 token → $340/50 \approx 6.8$ s 生成时间(+检索/网络约 0.5~1 s)。
- 对话场景用**流式输出(streaming)**：首 token 出来就显示，体感延迟降到首 token 时间(常 <1 s)。

结论：要快就**控制输出长度 + 流式 + 小模型**；要省就**控制输入(注入)长度 + 缓存**。

## 对照表：四类应用形态怎么选

| 形态 | 能力 | 可控性 | 成本 | 延迟 | 何时选 |
|------|------|--------|------|------|--------|
| 纯 Prompt | 中 | 高 | 低 | 低 | 格式/风格/简单生成 |
| RAG | 中高 | 高 | 中 | 中 | 知识问答、要引用、私有/实时数据 |
| Function Calling | 高 | 高 | 中 | 中 | 接真实系统、做确定性操作 |
| Agent | 最高 | 低 | 高 | 高(步数不定) | 多步自动化、需自主编排工具 |

## 常见问题

| 问题 | 回答 |
|------|------|
| RAG 和微调到底选哪个？ | 缺"知识"→RAG；缺"能力/风格"→微调；缺"格式/行为"→先 Prompt。可叠加。 |
| 为什么模型会胡说？怎么治？ | 概率续写、缺信息就编。治法：RAG 接地 + 要求标引用 + 输出后校验 + 降温(低 temperature)。 |
| 上下文越长越好吗？ | 否。长上下文成本↑延迟↑，且"中间信息易被忽略"。注入精准的少量块通常优于堆一堆。 |
| Agent 和 Function Calling 区别？ | Function Calling 是"调一次工具"的机制；Agent 是"循环地规划+多次调工具"的系统，后者以前者为底座。 |
| 什么时候**不该**上 Agent？ | 任务能一两步搞定时。Agent 慢、贵、易跑飞，简单场景用 Prompt/RAG/单次 Function Calling 即可。 |
| 没标注数据能微调吗？ | 难。先用 Prompt+RAG;微调需要质量过关的标注样本，否则越调越偏。 |
| 怎么评测应用好不好？ | 离线集 + 在线指标：准确率/引用命中率/有用性，配人工评分与回归测试，别只看 demo。 |
