## 0. 一句话锚点

**Coding Agent = 一个会"自己跟自己对话很多轮"的程序**：

```
        ┌──────────────────────────────────────────────┐
        │  你说："给 utils.py 的 parse() 加上空值检查"      │
        └───────────────────────┬──────────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │   while 任务没完成:                    │
              │     1) 模型 想 (Reason)               │
              │     2) 模型 选一个工具调用 (Act)        │
              │     3) 程序 真去执行工具，拿回结果 (Obs)  │
              │     4) 把结果塞回对话，继续下一轮         │
              └──────────────────┬──────────────────┘
                                 │
                       任务完成 / 用户确认
```

OpenCode、Aider、Claude Code、Cursor Agent、Cline 等都是这个范式的不同外壳。OpenCode 是**开源、终端原生(TUI)、模型无关(provider-agnostic)** 的一种实现（具体特性以官方文档为准）。本文讲的是这一**类**系统的底层原理，而非某个产品的逐项功能。

> 关键认知：Agent 的"智能"= 模型的推理能力 × 工具设计的好坏 × 循环/上下文工程的好坏。三者缺一，体验都会塌。

## 1. 地基/前置：LLM 本身"什么都不会做"

要理解 Agent，先把一个反直觉的事实钉死：

**大模型(LLM)是一个纯函数**：输入一段文本(token 序列)，输出"下一个 token 的概率分布"，采样得到下一个 token，再拼回去继续——这叫**自回归生成**。

$$
P(\text{下一个 token} \mid \text{已有所有 token}) \xrightarrow{\text{采样}} \text{token}
$$

它**不能**直接打开你的文件、不能运行 `pytest`、不能联网。它唯一能做的就是"吐字"。

那它怎么"改代码"？答案：**约定一种文本格式，让模型用吐字的方式"请求"外部程序帮它做事**。这就是**工具调用(Tool Use / Function Calling)**。

```
模型不会做事，它只会"喊话"：
  ┌─────────────────────────────────────────────┐
  │ 模型输出(文本/JSON):                            │
  │   { "tool": "read_file",                       │
  │     "args": { "path": "utils.py" } }           │
  └───────────────────┬─────────────────────────┘
                      │  ← Agent 框架(普通程序)拦截这段输出
                      ▼
  ┌─────────────────────────────────────────────┐
  │ 框架真去读磁盘 → 把文件内容作为"工具结果"        │
  │ 再拼成一条新消息，喂回模型                       │
  └─────────────────────────────────────────────┘
```

所以 **Agent 框架 = 模型与真实世界之间的"翻译官 + 执行器"**。模型负责"想和说"，框架负责"听懂并真的去做"。

> 为什么要强调这点？因为初学者常以为"模型自己会跑命令"。不是。是框架在解析模型的输出、调用真实工具、再把结果回灌。整套 Agent 的可靠性，一大半在框架工程上。

## 2. 总体架构：五个部件

把一个 Coding Agent 拆到最原子，是 5 个协作部件，外加一个把它们串起来的**编排器(Orchestrator)**：

```
                         ┌───────────────────────────┐
   用户任务 ───────────▶ │      Orchestrator(主循环)    │ ◀── 系统提示词/规则
                         │  管理对话历史、决定何时停      │
                         └──┬─────────┬─────────┬─────┘
            ┌───────────────┘         │         └───────────────┐
            ▼                         ▼                          ▼
   ① 规划 Planner          ② 工具调用 Tool-Use         ⑤ 反馈 Feedback
   "先读哪、改哪、           解析模型想调的工具，          把执行结果/报错
    分几步走"               校验参数，真去执行            回灌给模型，触发重想
            │                         │                          ▲
            │                    ┌────┴─────┐                     │
            │                    ▼          ▼                     │
            │             ③ 编辑 Editor   ④ 执行 Executor          │
            │             改文件(diff)     跑 shell/测试/编译 ──────┘
            ▼
       (规划常常不是独立模块，而是模型在 ReAct 思考里隐式完成)
```

逐个看每个部件"是什么、解决什么、核心机制"：

| 部件 | 是什么 | 解决什么 | 核心机制 |
|------|--------|---------|---------|
| ① 规划 Planner | 把大任务拆成可执行小步 | 防止"一上来就乱改" | 显式 plan 模式 / 或隐式写在 Thought 里 / 或 TODO 列表 |
| ② 工具调用 | 解析模型选的工具+参数并执行 | 让"吐字"变成"行动" | function-calling 协议、JSON Schema 校验 |
| ③ 编辑 Editor | 精确修改文件局部 | 改一行不必重写整文件 | search/replace、unified diff、行号锚点 |
| ④ 执行 Executor | 跑命令、测试、编译、linter | 拿到"客观真相" | 子进程、沙箱、超时控制 |
| ⑤ 反馈 Feedback | 把结果(尤其报错)结构化回灌 | 让模型自我纠错 | 截断/摘要工具输出，保留关键报错 |

> 直觉：①②③④⑤ 不是五个独立大程序。在很多实现里，**规划是隐式的**(模型在思考文本里就排好了)，真正"硬编码"的是 ②③④⑤ 这套工具+循环。OpenCode 这类的工程重心，就在"工具设计 + 循环控制 + 上下文管理"。

## 3. ReAct 循环：Agent 的"心跳"

ReAct = **Rea**soning + **Act**ing。它规定每一轮模型都按"想→做→看"走，而不是一口气写完答案。

```
  一轮 = 一次心跳：
  ┌────────────┐   ┌────────────┐   ┌──────────────┐
  │ Thought    │──▶│ Action     │──▶│ Observation  │──┐
  │ (推理:我要  │   │ (调用工具:  │   │ (工具返回:    │  │
  │  先看文件)  │   │  read_file)│   │  文件内容)    │  │
  └────────────┘   └────────────┘   └──────────────┘  │
        ▲                                              │
        └──────────────  回灌，开始下一轮  ◀────────────┘

  典型一次"加空值检查"任务的真实轨迹：
  轮1  Thought: 先看 parse() 长啥样   Action: read_file utils.py
  轮2  Thought: 找到了，第 12 行入参    Action: grep "parse(" -r .   (看谁调它)
  轮3  Thought: 在第 13 行插 if 判断     Action: edit utils.py (search/replace)
  轮4  Thought: 改完跑测试确认           Action: bash "pytest tests/test_utils.py"
  轮5  Observation: 1 failed (类型错)    Thought: 我把 None 判反了 → 再 edit
  轮6  Action: bash pytest → all passed  Thought: 完成，停止
```

**为什么要一轮一轮，而不是让模型一次性输出全部修改？**

- 真实世界**会反驳模型**：它以为函数叫 `parse`，实际叫 `parse_line`；以为测试在 A 文件，其实在 B。只有"做一步、看一眼真实结果、再想"才能纠偏。
- 这就是**闭环 vs 开环**的区别。开环(一次生成)= 蒙；闭环(ReAct)= 边做边校准。Agent 之所以比"让 ChatGPT 写一段代码贴回去"强，核心就在这个闭环。

**停止条件**(Orchestrator 怎么知道该收工)：模型主动声明完成 / 达到最大轮数(防死循环) / 用户中断 / 连续多轮无进展。设最大轮数是**安全阀**——否则模型可能在两个错误间反复横跳烧 token。

## 4. 工具层：Agent 的"手脚"清单

一个 Coding Agent 的能力上限，由它**有哪些工具**决定。典型工具集(命名因实现而异)：

```
  读类(只读，安全)              写类(有副作用，常需确认)
  ┌───────────────────┐        ┌───────────────────────┐
  │ read_file  读单文件 │        │ edit_file   局部改文件   │
  │ glob       找文件名 │        │ write_file  整体写文件   │
  │ grep       搜内容   │        │ bash        跑任意命令   │
  │ ls         列目录   │        │ apply_patch 打补丁      │
  └───────────────────┘        └───────────────────────┘
        ▲                                ▲
        │  低风险，可自动放行              │  高风险，常走"权限确认"
        └────────────────────────────────┘
```

设计要点(讲含义不背默认值)：

- **读写分离 + 权限分级**：读类工具几乎无害，可自动执行；`bash`/`write` 能删库、能联网，通常要么人工确认、要么白名单、要么沙箱隔离。这是 Coding Agent 安全模型的核心，权衡是"自动化程度 vs 失控风险"。
- **工具描述就是模型的"说明书"**：每个工具用 JSON Schema 描述名字、参数、用途。**描述写得好 = 模型选得准**。这是 prompt 工程里收益最高的地方之一。
- **grep/glob 优于让模型"凭记忆找"**：模型不知道你仓库长啥样，给它精准的检索工具，比让它瞎猜文件名靠谱得多——呼应第 7 节的上下文问题。

> 实践要点：工具不是越多越好。工具一多，模型选择困难、容易调错、还占系统提示词的 token。精炼的一组正交工具(读/搜/改/跑)往往胜过几十个重叠工具。

## 5. 编辑机制：怎么"只改一行"

这是 Coding Agent 工程上最容易翻车、也最见功力的一环。难点：**模型擅长生成文本，但不擅长精确定位"改文件的第几个字符"**。

三种主流编辑策略：

```
  策略A 整文件重写 write_file
    模型输出整个新文件 ──▶ 直接覆盖
    优点: 简单         缺点: 长文件烧爆 token、易把没动的地方改坏

  策略B 查找-替换 search/replace        ★最常用
    模型给出:  <要替换的原文片段> + <新片段>
    框架在文件里"精确匹配原文片段"再替换
    优点: 省 token、改动局部、可校验
    缺点: 原文片段必须逐字符匹配，错一个空格就失败

  策略C 统一 diff (unified diff / patch)
    模型直接产出 @@ -12,3 +12,4 @@ 形式的补丁
    优点: 行业标准、可读、可 review
    缺点: 模型对行号/上下文容易算错，需框架容错
```

**为什么 search/replace 成为主流？**

```
  原文(模型必须原样给出，当"锚点"):
    def parse(line):
        return line.split(",")

  替换为:
    def parse(line):
        if line is None:           ← 新增
            return []              ← 新增
        return line.split(",")

  框架做的事：在文件里找到那段"锚点"，确认唯一匹配，替换。
  若匹配到 0 处或 多处 → 报错回灌，让模型重新给更精确的片段。
```

它的精妙在于：**用"原文片段"代替"行号"做定位**——文本是模型自己读到的、记得住的；行号则容易数错。匹配失败时把错误回灌，模型会自我修正。这正是第 6 节"反馈闭环"在编辑层面的体现。

> 实践要点：好的编辑工具一定会做"匹配唯一性校验"和"失败即回灌"。否则模型"以为改了"实则没改，后续全错。

## 6. 执行与反馈：让 Agent 自己发现自己错了

模型会**自信地胡说**(hallucination)。对抗它的唯一硬办法：**让客观世界来打脸**——跑测试、跑编译、跑 linter，把结果(尤其报错)回灌。

```
   ┌────────────┐   生成补丁   ┌────────────┐
   │   模型      │ ───────────▶│  Editor 改  │
   └─────▲──────┘             └─────┬──────┘
         │                          ▼
         │ 报错全文/摘要        ┌────────────┐
         │ 作为 Observation    │ Executor:   │
         └─────────────────────│ pytest /    │
                               │ tsc / build │
                               └─────┬──────┘
                                     ▼
                          pass? ──是──▶ 收工
                            │否
                            └──▶ 回到模型，带着报错再想（自我纠错闭环）
```

为什么这是 Coding Agent 远超"纯聊天写代码"的关键：

- **测试/编译是"廉价的真相来源"**。一段红色 traceback 比一万句提示词都管用——它精确告诉模型错在哪一行、什么类型。
- 这把"生成"问题转成了"**生成 + 验证 + 修正**"的迭代，本质上是给模型装了**外部记忆与外部判官**。

工程权衡：

- **工具输出会爆 token**：`pytest` 失败可能吐几千行。框架要**截断/摘要**，只保留关键报错(第一个 traceback、失败用例名)，否则一次执行就把上下文塞满(见第 7 节算账)。
- **执行要带超时与沙箱**：死循环命令、`rm -rf`、联网下载都得防。超时控制 + 受限工作目录 + 权限确认是三道闸。

## 7. 上下文管理：百万行仓库 vs 几十万 token 窗口

这是 Coding Agent 最硬的工程瓶颈，单独拎出来讲。

**矛盾**：真实仓库动辄几十万~几百万行代码(海量)，而模型一次能看的上下文窗口(context window)只有典型几万到几十万 token(稀缺，**具体上限以所用模型官方为准**)。**不可能把整个仓库塞进去**，只能从海量里挑一点点进窗口。

四类应对手段：

| 手段 | 做什么 | 解决什么 | 权衡 |
|------|--------|---------|------|
| **按需检索** | 用 grep/glob/语义检索只取相关片段 | 不塞整库 | 检索不准则模型瞎改 |
| **历史压缩** | 对话变长时把旧轮次摘要成几句 | 防窗口溢出 | 摘要可能丢关键细节 |
| **输出截断** | 工具结果只留关键部分 | 防单次爆窗口 | 截太狠会漏报错 |
| **外部记忆** | 把"项目约定/已知结论"写进规则文件(如 AGENTS.md/CLAUDE.md) 长期带着 | 跨会话记忆 | 文件过大反占 token |

```
  上下文 = 一块预算固定的"白板"，每写一笔都要付 token：
  ┌─────────────────────────────────────────────┐
  │■■■■ 系统+工具(固定成本)                          │
  │■■■■■■■■ 对话历史(只增不减 → 必须定期压缩)          │
  │■■■■ 当前相关文件(检索来的，要准)                   │
  │■■ 最近工具输出(要截断)                            │
  │░░░░░░ 留给模型"思考+生成"的余量(必须留够!)          │
  └─────────────────────────────────────────────┘
   一旦白板写满 → 要么溢出报错，要么被迫压缩丢信息 → 质量塌
```

> 核心直觉：**Coding Agent 的工程，本质是一场"上下文预算管理"**。谁能在固定 token 预算里塞进"最相关的信息 + 最少的噪声"，谁的 Agent 就更聪明、更省钱。

## 8. 与 Claude Code 类的对比

> 说明：以下是**这一类系统的架构维度对比**，帮助理解设计空间；不同产品的具体特性请以各自官方文档为准，下面不绑定任何精确版本/参数。

```
  谱系(都共享"LLM + 工具 + ReAct 循环"内核，区别在外壳与策略):

   终端原生(TUI)            IDE 内嵌            CLI/脚本
   OpenCode / Aider /      Cursor / Cline       很多自建脚本
   Claude Code(终端)       (VS Code 插件)
        │                      │                    │
        └──── 同一内核，不同交互面与生态绑定 ────────────┘
```

| 维度 | OpenCode 类(开源 TUI) | Claude Code 类 | 说明 |
|------|----------------------|---------------|------|
| 交互形态 | 终端 TUI 为主 | 终端/IDE 集成 | TUI 轻量、可远程、易嵌 CI |
| 模型绑定 | 强调 **模型无关**，可接多家 provider | 与自家模型深度协同 | 模型无关=灵活/可控成本；深度协同=调教更顺 |
| 开放性 | 开源、可自托管、可改 | 取决于产品策略 | 开源利于审计/定制/数据合规 |
| 工具/权限 | 读写分离 + 人工确认 + 沙箱(实现各异) | 类似的权限确认模型 | 这是 Coding Agent 的通用安全范式 |
| 上下文策略 | 检索+压缩(各家工程不同) | 检索+压缩+长期记忆文件 | 同问题、不同实现 |
| 适用场景 | 自托管/隐私敏感/多模型实验/CI 集成 | 开箱即用、与生态强绑 | 按团队约束选 |

选型直觉(讲含义)：

- 你**在意数据合规/想自托管/想随时换模型** → 倾向 OpenCode 这类**开源、模型无关**方案。
- 你**要开箱即用、追求与某家模型最佳协同** → 倾向产品化、深度集成的方案。
- 但**它们的底层都是本文第 2~7 节那套东西**。理解了内核，换哪个壳都一样上手。

## 9. 关键能力清单(评判一个 Coding Agent 的维度)

```
  ┌─────────────────────────────────────────────────────┐
  │  ① 代码理解  能跨文件读懂调用关系吗?(检索+上下文)         │
  │  ② 精确编辑  改一行不破坏其余? (编辑机制 第5节)          │
  │  ③ 闭环自纠  会跑测试并据报错修正? (反馈 第6节)          │
  │  ④ 上下文工程 大仓库不崩、不超预算? (第7节)              │
  │  ⑤ 工具广度  能搜/改/跑/查 git/装依赖?                  │
  │  ⑥ 规划能力  长任务能拆步、不半途乱掉? (第2/3节)         │
  │  ⑦ 安全可控  危险操作有确认/沙箱? (权限模型)             │
  │  ⑧ 成本可控  token 用得省吗? (压缩/截断/检索)           │
  └─────────────────────────────────────────────────────┘
```

一句话：**①③④是分水岭**——能跨文件理解、能闭环自纠、能管住上下文，体验就"能干活"；缺任一，就退化成"会贴代码片段的聊天框"。

## 数值例子 / 对照 / 实践

**例：一次中等任务的 token 与成本手算**（数字为示意量级，**实际以所用模型计费为准**）。

设上下文窗口 = 200,000 token。一次"改 3 个文件 + 跑 2 次测试"的任务，ReAct 跑了 8 轮。

每一轮模型都要重读**整段对话历史**(自回归特性：上下文是无状态的，每轮都全量重发)。估算各部分：

```
  固定开销 / 每轮都带:
    系统提示词 + 工具说明     ≈  3,000 token
  累积内容(只增不减):
    读进来的 3 个文件          ≈  4,500 token (每个~1500)
    每轮 Thought + Action      ≈   400 token/轮
    每轮工具输出(已截断)        ≈   600 token/轮
```

第 8 轮(最胖那轮)的输入大约：

$$
\underbrace{3000}_{\text{系统}} + \underbrace{4500}_{\text{文件}} + 8\times(\underbrace{400}_{\text{想/做}}+\underbrace{600}_{\text{看}}) \approx 15{,}500 \text{ token}
$$

8 轮**累计输入**(等差求和，每轮带更长历史)粗估：

$$
\sum_{k=1}^{8}\big(7500 + 1000k\big) = 8\times7500 + 1000\times\frac{8\times9}{2} = 60{,}000 + 36{,}000 = 96{,}000 \text{ token}
$$

**结论与直觉**：

- 离 200k 窗口还有余量，**但若工具输出不截断**——假设某次 `pytest` 吐 20,000 token 全塞进去——单轮就可能逼近窗口，且后续每轮都重背这 2 万，**成本指数级膨胀**。这就是第 6/7 节"必须截断/压缩"的硬道理。
- 成本侧：累计 96k 输入 token，若某模型输入价为 $X$/百万 token，则约 $0.096X$ 美元/任务(**具体单价以官方为准**)。**省钱 = 砍历史 + 截输出 + 精检索**，三件事直接乘进账单。

**对照速记表**：

| 你想要 | 该调的旋钮 | 代价 |
|--------|----------|------|
| 更自动(少打断) | 放宽工具权限确认 | 失控/误删风险↑ |
| 更省钱 | 历史压缩更激进、输出截更短 | 可能丢上下文→改错 |
| 更准 | 更好的检索工具、更细工具描述 | 系统提示词更长、稍贵 |
| 更安全 | 沙箱 + 白名单 + 超时 | 自动化程度↓ |

**实践要点(落地清单)**：

1. 先给 Agent **精准检索工具**(grep/glob) 而非让它猜文件——立竿见影提质。
2. 编辑用 **search/replace + 唯一性校验 + 失败回灌**，别让它整文件重写。
3. 工具输出**强制截断/摘要**，尤其测试与构建日志。
4. 设**最大轮数**与**超时**，当安全阀防死循环烧钱。
5. 危险工具(bash/write)走**人工确认或沙箱**；只读工具放行。
6. 长期项目约定写进**规则文件**(项目根的 AGENTS.md/约定文件)当外部记忆。

## 常见问题

| 问题 | 解答 |
|------|------|
| Agent 和"直接问 ChatGPT 写代码"差在哪? | 差在**闭环**：Agent 能真读你的仓库、真跑测试、据报错自我修正(第3/6节)；聊天框只能盲生成。 |
| 为什么不把整个仓库喂给模型? | 窗口装不下且巨贵；必须**按需检索**只取相关片段(第7节)。 |
| 模型为什么有时"改了等于没改"? | search/replace 的原文锚点没逐字匹配上(空格/换行不同)，框架若不做唯一性校验+回灌就会静默失败(第5节)。 |
| ReAct 会不会死循环? | 会——在两个错误间横跳。靠**最大轮数/无进展检测**当安全阀(第3节)。 |
| OpenCode 和 Claude Code 谁强? | 不同取舍：前者强调**开源/模型无关/可自托管**，后者强调**深度协同/开箱即用**；内核相同(第8节)。具体特性以官方为准。 |
| 为什么工具描述这么重要? | 它是模型选工具的唯一依据，写不清模型就选错、调错——是性价比最高的 prompt 工程(第4节)。 |
| 一次任务大概烧多少 token? | 取决于轮数×历史长度，几万到几十万级很常见；省钱关键在压缩历史+截断输出(数值例)。 |
| 怎么防它删库/跑危险命令? | 读写分离的**权限模型** + 沙箱 + 命令白名单 + 超时(第4/6节)。 |
