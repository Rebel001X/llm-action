## 0. 一句话锚点

**OpenClaw = 一个会"自己跟自己对话很多轮"的程序**：你给一句话目标，它在一个循环里反复"想一步、调一个工具、看真实结果、再想下一步"，直到任务完成。

```
        ┌──────────────────────────────────────────────┐
        │  你说："给 utils.py 的 parse() 加上空值检查"      │
        └───────────────────────┬──────────────────────┘
                                │
              ┌─────────────────▼──────────────────┐
              │   while 任务没完成:                   │
              │     1) 模型 想 (Reason)              │
              │     2) 模型 选一个工具调用 (Act)       │
              │     3) 程序 真去执行工具拿回结果 (Obs)  │
              │     4) 把结果塞回对话，继续下一轮        │
              └─────────────────┬──────────────────┘
                                │
                      任务完成 / 用户确认 / 触发安全阀
```

OpenClaw、OpenCode、Aider、Cline、Claude Code 都是**同一范式的不同外壳**。OpenClaw 把自己定位在"**开源 + 终端原生(TUI) + 模型无关(provider-agnostic)**"这一象限：你可以自托管、可以审计源码、可以随时换底层模型。本文用 80% 篇幅讲这套**内核原理**，用 20% 把 OpenClaw 的特性归到对应类别上。

> 关键认知：Agent 的"智能" = 模型的推理能力 × 工具设计的好坏 × 循环 / 上下文工程的好坏。三者缺一，体验都会塌——这条公式对 OpenClaw 同样成立。

## 1. 地基 / 前置：LLM 本身"什么都不会做"

理解 OpenClaw 前，先把一个反直觉的事实钉死：

**大模型(LLM)是一个纯函数**——输入一段文本(token 序列)，输出"下一个 token 的概率分布"，采样得到下一个 token，再拼回去继续。这叫**自回归生成**：

$$
P(\text{下一个 token}\mid \text{已有所有 token}) \xrightarrow{\text{采样}} \text{token}
$$

它**不能**直接打开你的文件、不能运行 `pytest`、不能联网。它唯一能做的就是"吐字"。

那 OpenClaw 怎么"改代码、跑命令"？答案：**约定一种文本格式，让模型用吐字的方式"请求"外部程序帮它做事**——这就是**工具调用(Tool Use / Function Calling)**。

```
模型不会做事，它只会"喊话"：
  ┌─────────────────────────────────────────────┐
  │ 模型输出(结构化文本/JSON):                       │
  │   { "tool": "read_file",                       │
  │     "args": { "path": "utils.py" } }           │
  └───────────────────┬─────────────────────────┘
                     │  ← OpenClaw 框架(普通程序)拦截这段输出
                     ▼
  ┌─────────────────────────────────────────────┐
  │ 框架真去读磁盘 → 把文件内容当"工具结果"          │
  │ 再拼成一条新消息，喂回模型                       │
  └─────────────────────────────────────────────┘
```

所以 **OpenClaw = 模型与真实世界之间的"翻译官 + 执行器"**。模型负责"想和说"，框架负责"听懂并真的去做"。

> 为什么强调这点？初学者常以为"模型自己会跑命令"。不是。是框架在解析模型输出、调用真实工具、再把结果回灌。整套 Agent 的可靠性，一大半在**框架工程**上——这正是 OpenClaw 这类项目的代码主体。

## 2. OpenClaw 在 Agent 谱系里的坐标

把市面上的 Agent 按两条轴摆开，OpenClaw 落在"开源 / 终端 / 模型无关"这一角：

```
                 模型无关(可换 provider)
                          ▲
       OpenClaw ●         │
       OpenCode ●         │   (强调灵活、自托管、可控成本)
       Aider    ●         │
   ───────────────────────┼───────────────────────▶ 与某家模型深度绑定
                          │
                          │   ● Cursor / 某些商业 IDE Agent
                          │     (开箱即用、深度协同)
                          ▼
                 模型强绑定

     交互形态: OpenClaw / OpenCode / Aider → 终端原生 TUI / CLI
              Cursor / Cline             → IDE 内嵌
```

OpenClaw 这一象限的**特征与取舍**（讲含义，不绑死具体功能）：

| 特征 | 是什么 | 带来什么好处 | 代价 / 权衡 |
|------|--------|------------|------------|
| **开源** | 代码可读、可改、可自托管 | 可审计、可定制、利于数据合规 | 要自己维护、自己接模型 |
| **终端原生(TUI)** | 主战场在命令行 | 轻量、可远程、易嵌 CI/CD | 不如 IDE 直观可视 |
| **模型无关** | 抽象出 provider 层，可接多家模型 | 不被单一厂商锁定、可比价/试模型 | 不同模型的工具调用格式要适配(见 §9) |

> 选型直觉：你**在意数据合规 / 想自托管 / 想随时换模型** → OpenClaw 这类开源、模型无关方案天然契合；你**只要开箱即用、追求与某家模型最佳协同** → 倾向产品化深度集成方案。但它们的底层都是 §3~§8 这套东西。

## 3. 总体架构：五部件 + 编排器

把 OpenClaw 拆到最原子，是 5 个协作部件，外加一个把它们串起来的**编排器(Orchestrator)**：

```
                         ┌───────────────────────────┐
   用户任务 ───────────▶ │      Orchestrator(主循环)    │ ◀── 系统提示词/项目规则
                         │  管理对话历史、决定何时停      │
                         └──┬─────────┬─────────┬─────┘
            ┌───────────────┘         │         └───────────────┐
            ▼                         ▼                          ▼
   ① 规划 Planner          ② 工具调用 Tool-Use         ⑤ 反馈 Feedback
   "先读哪、改哪、           解析模型想调的工具，          把执行结果/报错
    分几步走"               校验参数，真去执行            回灌给模型，触发重想
            │                         │                          ▲
            │                    ┌────┴─────┐                     │
            │                    ▼          ▼                     │
            │             ③ 编辑 Editor   ④ 执行 Executor          │
            │             改文件(diff)     跑 shell/测试/编译 ──────┘
            ▼
       (规划常不是独立模块，而是模型在 ReAct 思考里隐式完成)
```

逐个看"是什么、解决什么、核心机制"：

| 部件 | 是什么 | 解决什么 | 核心机制 |
|------|--------|---------|---------|
| ① 规划 Planner | 把大任务拆成可执行小步 | 防止"一上来就乱改" | 显式 plan 模式 / 隐式写在 Thought 里 / TODO 列表 |
| ② 工具调用 | 解析模型选的工具+参数并执行 | 让"吐字"变成"行动" | function-calling 协议、JSON Schema 校验 |
| ③ 编辑 Editor | 精确修改文件局部 | 改一行不必重写整文件 | search/replace、unified diff、锚点匹配 |
| ④ 执行 Executor | 跑命令、测试、编译、linter | 拿到"客观真相" | 子进程、沙箱、超时控制 |
| ⑤ 反馈 Feedback | 把结果(尤其报错)结构化回灌 | 让模型自我纠错 | 截断/摘要工具输出，保留关键报错 |

> 直觉：这 5 个不是 5 个独立大程序。很多实现里**规划是隐式的**（模型在思考文本里就排好了），真正"硬编码"的是 ②③④⑤ 这套工具+循环。OpenClaw 这类项目的工程重心，就在"工具设计 + 循环控制 + 上下文管理 + provider 抽象"。

## 4. ReAct 循环：OpenClaw 的"心跳"

ReAct = **Rea**soning + **Act**ing。它规定每一轮模型都按"想→做→看"走，而不是一口气写完答案。

```
  一轮 = 一次心跳：
  ┌────────────┐   ┌────────────┐   ┌──────────────┐
  │ Thought    │──▶│ Action     │──▶│ Observation  │──┐
  │ (推理:我要  │   │ (调用工具:  │   │ (工具返回:    │  │
  │  先看文件)  │   │  read_file)│   │  文件内容)    │  │
  └────────────┘   └────────────┘   └──────────────┘  │
        ▲                                              │
        └──────────────  回灌，开始下一轮  ◀────────────┘

  一次"加空值检查"任务的真实轨迹：
  轮1  Thought: 先看 parse() 长啥样   Action: read_file utils.py
  轮2  Thought: 找到了，第12行入参     Action: grep "parse(" -r .   (看谁调它)
  轮3  Thought: 在第13行插 if 判断      Action: edit utils.py (search/replace)
  轮4  Thought: 改完跑测试确认           Action: bash "pytest tests/test_utils.py"
  轮5  Observation: 1 failed(判反了)    Thought: None 判反 → 再 edit
  轮6  Action: bash pytest → all passed Thought: 完成，停止
```

**为什么要一轮一轮，而不是让模型一次性输出全部修改？**

- 真实世界**会反驳模型**：它以为函数叫 `parse`，实际叫 `parse_line`；以为测试在 A 文件，其实在 B。只有"做一步、看真实结果、再想"才能纠偏。
- 这是**闭环 vs 开环**的区别。开环(一次生成)= 蒙；闭环(ReAct)= 边做边校准。OpenClaw 比"让聊天框写段代码贴回去"强，核心就在这个闭环。

**停止条件**（Orchestrator 怎么知道收工）：模型主动声明完成 / 达到最大轮数 / 用户中断 / 连续多轮无进展。设**最大轮数**是安全阀——否则模型可能在两个错误间反复横跳烧 token。

## 5. 工具层：OpenClaw 的"手脚"清单

一个 Agent 的能力上限，由它**有哪些工具**决定。典型工具集（命名因实现而异，**具体名称以 OpenClaw 文档为准**）：

```
  读类(只读，安全)              写类(有副作用，常需确认)
  ┌───────────────────┐        ┌───────────────────────┐
  │ read_file  读单文件 │        │ edit_file   局部改文件   │
  │ glob       找文件名 │        │ write_file  整体写文件   │
  │ grep       搜内容   │        │ bash        跑任意命令   │
  │ ls         列目录   │        │ apply_patch 打补丁      │
  └───────────────────┘        └───────────────────────┘
        ▲                                ▲
        │  低风险，可自动放行              │  高风险，常走"权限确认"
        └────────────────────────────────┘
```

设计要点（讲含义，不背默认值）：

- **读写分离 + 权限分级**：读类工具几乎无害，可自动执行；`bash`/`write` 能删库、能联网，通常要么人工确认、要么白名单、要么沙箱隔离。这是 OpenClaw 安全模型的核心，权衡是"自动化程度 vs 失控风险"。
- **工具描述就是模型的"说明书"**：每个工具用 JSON Schema 描述名字、参数、用途。**描述写得好 = 模型选得准**，是性价比最高的 prompt 工程之一。
- **grep/glob 优于让模型"凭记忆找"**：模型不知道你仓库长啥样，给它精准的检索工具，比让它瞎猜文件名靠谱得多（呼应 §8 上下文问题）。

> 实践要点：工具不是越多越好。工具一多，模型选择困难、容易调错、还占系统提示词 token。一组**正交**工具(读/搜/改/跑)往往胜过几十个重叠工具。

## 6. 编辑机制：怎么"只改一行"

这是编码 Agent 工程上最容易翻车、也最见功力的一环。难点：**模型擅长生成文本，但不擅长精确定位"改文件的第几个字符"**。

三种主流编辑策略：

```
  策略A 整文件重写 write_file
    模型输出整个新文件 ──▶ 直接覆盖
    优点: 简单         缺点: 长文件烧爆 token、易把没动的地方改坏

  策略B 查找-替换 search/replace        ★最常用
    模型给出:  <要替换的原文片段> + <新片段>
    框架在文件里"精确匹配原文片段"再替换
    优点: 省 token、改动局部、可校验
    缺点: 原文片段必须逐字符匹配，错一个空格就失败

  策略C 统一 diff (unified diff / patch)
    模型直接产出 @@ -12,3 +12,4 @@ 形式补丁
    优点: 行业标准、可读、可 review
    缺点: 模型对行号/上下文容易算错，需框架容错
```

**为什么 search/replace 成为主流？**

```
  原文(模型必须原样给出，当"锚点"):
    def parse(line):
        return line.split(",")

  替换为:
    def parse(line):
        if line is None:           ← 新增
            return []              ← 新增
        return line.split(",")

  框架做的事：在文件里找到那段"锚点"，确认唯一匹配，替换。
  若匹配到 0 处或 多处 → 报错回灌，让模型重新给更精确的片段。
```

精妙在于：**用"原文片段"代替"行号"做定位**——文本是模型自己读到的、记得住的；行号则容易数错。匹配失败时把错误回灌，模型自我修正。这正是 §7"反馈闭环"在编辑层面的体现。

> 实践要点：好的编辑工具一定会做"**匹配唯一性校验**"和"**失败即回灌**"。否则模型"以为改了"实则没改，后续全错。

## 7. 执行与反馈：让 OpenClaw 自己发现自己错了

模型会**自信地胡说**(hallucination)。对抗它的硬办法：**让客观世界来打脸**——跑测试、跑编译、跑 linter，把结果(尤其报错)回灌。

```
   ┌────────────┐   生成补丁   ┌────────────┐
   │   模型      │ ───────────▶│  Editor 改  │
   └─────▲──────┘             └─────┬──────┘
         │                          ▼
         │ 报错全文/摘要        ┌────────────┐
         │ 作为 Observation    │ Executor:   │
         └─────────────────────│ pytest /    │
                               │ tsc / build │
                               └─────┬──────┘
                                     ▼
                          pass? ──是──▶ 收工
                            │否
                            └──▶ 回到模型，带报错再想(自我纠错闭环)
```

为什么这是 OpenClaw 远超"纯聊天写代码"的关键：

- **测试 / 编译是"廉价的真相来源"**。一段红色 traceback 比一万句提示词都管用——它精确告诉模型错在哪一行、什么类型。
- 这把"生成"问题转成"**生成 + 验证 + 修正**"的迭代，本质是给模型装了**外部记忆与外部判官**。

工程权衡：

- **工具输出会爆 token**：`pytest` 失败可能吐几千行。框架要**截断/摘要**，只留关键报错(首个 traceback、失败用例名)，否则一次执行就把上下文塞满(见 §8 算账)。
- **执行要带超时与沙箱**：死循环命令、`rm -rf`、联网下载都得防。超时控制 + 受限工作目录 + 权限确认是三道闸。

## 8. 上下文 / 记忆管理：百万行仓库 vs 几十万 token 窗口

这是编码 Agent 最硬的工程瓶颈。

**矛盾**：真实仓库动辄几十万~几百万行代码(海量)，而模型一次能看的上下文窗口只有典型几万到几十万 token(稀缺，**具体上限以所用模型官方为准**)。**不可能把整库塞进去**，只能从海量里挑一点点进窗口。

四类应对手段：

| 手段 | 做什么 | 解决什么 | 权衡 |
|------|--------|---------|------|
| **按需检索** | 用 grep/glob/语义检索只取相关片段 | 不塞整库 | 检索不准则模型瞎改 |
| **历史压缩** | 对话变长时把旧轮次摘要成几句 | 防窗口溢出 | 摘要可能丢关键细节 |
| **输出截断** | 工具结果只留关键部分 | 防单次爆窗口 | 截太狠会漏报错 |
| **外部记忆** | 把"项目约定/已知结论"写进规则文件(项目根的约定文件)长期带着 | 跨会话记忆 | 文件过大反占 token |

```
  上下文 = 一块预算固定的"白板"，每写一笔都要付 token：
  ┌─────────────────────────────────────────────┐
  │■■■■ 系统+工具(固定成本)                          │
  │■■■■■■■■ 对话历史(只增不减 → 必须定期压缩)          │
  │■■■■ 当前相关文件(检索来的，要准)                   │
  │■■ 最近工具输出(要截断)                            │
  │░░░░░░ 留给模型"思考+生成"的余量(必须留够!)          │
  └─────────────────────────────────────────────┘
   一旦白板写满 → 要么溢出报错，要么被迫压缩丢信息 → 质量塌
```

> 核心直觉：**OpenClaw 的工程，本质是一场"上下文预算管理"**。谁能在固定 token 预算里塞进"最相关的信息 + 最少的噪声"，谁的 Agent 就更聪明、更省钱。许多 Agent 还支持把长期项目约定写进**项目根的规则文件**当外部记忆(具体文件名以 OpenClaw 约定为准)。

## 9. Provider 抽象层：怎么做到"模型无关"

OpenClaw 自我标榜"模型无关"，落到工程上就是多了一层 **Provider Adapter（适配器）**。不同厂商的模型，"工具调用"的接口格式并不一致：有的用原生 function-calling 字段、有的需要把工具说明拼进 prompt 再解析模型吐出的 JSON、消息角色与流式协议也各异。

```
        ┌──────────────────────────────────────────┐
        │            OpenClaw 核心循环                 │
        │   (统一的内部消息/工具调用抽象)               │
        └───────────────────┬──────────────────────┘
                            │  统一接口: send(messages, tools) → reply
            ┌───────────────┼───────────────┬───────────────┐
            ▼               ▼               ▼               ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
     │ Adapter A  │  │ Adapter B  │  │ Adapter C  │  │ 本地模型     │
     │ (云厂商1)   │  │ (云厂商2)   │  │ (云厂商3)   │  │ (自托管推理) │
     └────────────┘  └────────────┘  └────────────┘  └────────────┘
       各家把"工具调用/消息/流式"差异，封装在适配器里抹平
```

适配器要抹平的差异(讲类别)：

- **工具调用格式**：原生 function-calling 字段 vs "提示词里描述工具 + 解析模型输出的 JSON"两条路线。
- **消息角色 / 多轮结构**：system / user / assistant / tool 等角色的拼装方式。
- **流式协议**：增量 token 的事件格式、工具调用片段如何边流边拼。
- **能力差异**：是否支持并行工具调用、上下文窗口大小、是否支持图片输入等。

> 工程价值：这层抽象让你**换模型只改配置不改业务逻辑**，也能对接本地自托管的推理服务（见 [[llm-inference/vllm/README]] 之类的推理后端）。代价是：每接一家新 provider 都要写/调一个适配器，且不同模型在同一套工具下的"听话程度"差异，需要实测而非纸面比较。

## 10. 与 OpenCode / Claude Code 类的对比

> 以下是**架构维度对比**，帮助理解设计空间；各产品的具体特性请以官方文档为准，不绑定精确版本/参数。

```
  谱系(都共享"LLM + 工具 + ReAct 循环"内核，区别在外壳与策略):

   终端原生(TUI)               IDE 内嵌            CLI/脚本
   OpenClaw / OpenCode /       Cursor / Cline      很多自建脚本
   Aider / Claude Code(终端)   (编辑器插件)
        │                         │                    │
        └──── 同一内核，不同交互面与生态绑定 ───────────────┘
```

| 维度 | OpenClaw / OpenCode 类(开源 TUI) | Claude Code 类 | 说明 |
|------|--------------------------------|---------------|------|
| 交互形态 | 终端 TUI 为主 | 终端 / IDE 集成 | TUI 轻量、可远程、易嵌 CI |
| 模型绑定 | 强调**模型无关**，可接多家 provider | 与自家模型深度协同 | 模型无关=灵活/控成本；深度协同=调教更顺 |
| 开放性 | 开源、可自托管、可改 | 取决于产品策略 | 开源利于审计/定制/数据合规 |
| 工具/权限 | 读写分离 + 人工确认 + 沙箱(实现各异) | 类似权限确认模型 | Coding Agent 的通用安全范式 |
| 上下文策略 | 检索+压缩(各家工程不同) | 检索+压缩+长期记忆文件 | 同问题、不同实现 |
| 适用场景 | 自托管/隐私敏感/多模型实验/CI 集成 | 开箱即用、与生态强绑 | 按团队约束选 |

选型直觉：在意**数据合规/自托管/随时换模型** → 倾向 OpenClaw 这类开源、模型无关方案；要**开箱即用、追求与某家模型最佳协同** → 倾向产品化深度集成方案。**但它们的底层都是 §3~§9 这套东西**——理解了内核，换哪个壳都一样上手。

## 数值例子 / 对照 / 实践

**例：一次中等任务的 token 与成本手算**（数字为示意量级，**实际以所用模型计费为准**）。

设上下文窗口 = 200,000 token。一次"改 3 个文件 + 跑 2 次测试"的任务，ReAct 跑了 8 轮。每一轮模型都要重读**整段对话历史**(自回归特性：上下文无状态，每轮全量重发)。估算各部分：

```
  固定开销 / 每轮都带:
    系统提示词 + 工具说明     ≈  3,000 token
  累积内容(只增不减):
    读进来的 3 个文件          ≈  4,500 token (每个~1500)
    每轮 Thought + Action      ≈   400 token/轮
    每轮工具输出(已截断)        ≈   600 token/轮
```

第 8 轮(最胖那轮)输入约：

$$
\underbrace{3000}_{\text{系统}} + \underbrace{4500}_{\text{文件}} + 8\times(\underbrace{400}_{\text{想/做}}+\underbrace{600}_{\text{看}}) \approx 15{,}500 \text{ token}
$$

8 轮**累计输入**(每轮带更长历史，近似等差求和)粗估：

$$
\sum_{k=1}^{8}\big(7500 + 1000k\big) = 8\times7500 + 1000\times\frac{8\times9}{2} = 60{,}000 + 36{,}000 = 96{,}000 \text{ token}
$$

**结论与直觉**：

- 离 200k 窗口还有余量，**但若工具输出不截断**——某次 `pytest` 吐 20,000 token 全塞进去——单轮就可能逼近窗口，且后续每轮都重背这 2 万，**成本指数级膨胀**。这就是 §7/§8"必须截断/压缩"的硬道理。
- 成本侧：累计 96k 输入 token，若某模型输入价为 $X$/百万 token，则约 $0.096X$ 美元/任务(**具体单价以官方为准**)。**省钱 = 砍历史 + 截输出 + 精检索**，三件事直接乘进账单。

**对照速记表**：

| 你想要 | 该调的旋钮 | 代价 |
|--------|----------|------|
| 更自动(少打断) | 放宽工具权限确认 | 失控/误删风险↑ |
| 更省钱 | 历史压缩更激进、输出截更短 | 可能丢上下文→改错 |
| 更准 | 更好的检索工具、更细工具描述 | 系统提示词更长、稍贵 |
| 更安全 | 沙箱 + 白名单 + 超时 | 自动化程度↓ |
| 换更便宜的模型 | 配 provider 适配器 | 弱模型"听话度"差，需实测 |

**实践要点（落地清单）**：

1. 先给 OpenClaw **精准检索工具**(grep/glob)，而非让它猜文件——立竿见影提质。
2. 编辑用 **search/replace + 唯一性校验 + 失败回灌**，别让它整文件重写。
3. 工具输出**强制截断/摘要**，尤其测试与构建日志。
4. 设**最大轮数**与**超时**当安全阀，防死循环烧钱。
5. 危险工具(bash/write)走**人工确认或沙箱**；只读工具放行。
6. 长期项目约定写进**项目根的规则文件**当外部记忆。
7. 换模型先在小任务上**实测"听话度"**——同一套工具，不同模型的工具调用稳定性差异很大。

## 常见问题 / 坑

| 问题 / 坑 | 解答 |
|----------|------|
| OpenClaw 和"直接问聊天框写代码"差在哪? | 差在**闭环**：能真读你的仓库、真跑测试、据报错自我修正(§4/§7)；聊天框只能盲生成。 |
| 为什么不把整个仓库喂给模型? | 窗口装不下且巨贵；必须**按需检索**只取相关片段(§8)。 |
| 模型为什么有时"改了等于没改"? | search/replace 原文锚点没逐字匹配上(空格/换行/缩进不同)，框架若不做唯一性校验+回灌就会静默失败(§6)。 |
| ReAct 会不会死循环? | 会——在两个错误间横跳。靠**最大轮数/无进展检测**当安全阀(§4)。 |
| "模型无关"是不是换任何模型体验都一样? | 不是。适配器能抹平接口格式，但**模型本身的推理/工具调用能力差异**抹不平，弱模型需实测(§9)。 |
| 为什么工具描述这么重要? | 它是模型选工具的唯一依据，写不清就选错、调错——性价比最高的 prompt 工程(§5)。 |
| 怎么防它删库/跑危险命令? | 读写分离的**权限模型** + 沙箱 + 命令白名单 + 超时(§5/§7)。 |
| 自托管时本地模型接不上? | 多半是 provider 适配器的工具调用格式/流式协议没对齐；先确认本地推理后端支持 function-calling 或回退到"提示词描述工具+解析 JSON"路线(§9)。 |
| 一次任务大概烧多少 token? | 取决于轮数×历史长度，几万到几十万级很常见；省钱关键在压缩历史+截断输出(数值例)。 |
