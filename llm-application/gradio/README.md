# Gradio：用几行 Python 把大模型变成可点击的 Web Demo

> Gradio 是一个纯 Python 的 Web UI 框架，让你不写一行前端代码，就能给模型/函数套上交互式网页（输入框、按钮、流式聊天框、文件上传等）。📍 导航：[[00-知识地图]]

## 0. 一句话锚点

**Gradio 的核心思想：UI = function。** 你写一个普通 Python 函数 `fn(输入) -> 输出`，Gradio 负责：

1. 在网页上为「输入」生成对应的控件（文本框、滑块、图片上传…）；
2. 用户操作后，把控件的值打包成参数，调用你的 `fn`；
3. 把 `fn` 的返回值，渲染成对应的「输出」控件。

你只关心算法逻辑（比如"调用大模型生成回答"），前端、HTTP、序列化全部由 Gradio 托管。

## 1. 地基：它解决了什么问题

做 AI-Infra / 算法的人，常遇到一个尴尬：**模型跑通了，但没法给别人"点一下试试"。** 传统做法要么写一套 Flask/React 前后端（成本高、跨技术栈），要么只能让对方看命令行截图。

Gradio 把这件事压缩到几行 Python：

```
没有 Gradio：
  你 ──（口述/截图）──> 同事："你得自己装环境、跑脚本、改输入"   ❌ 体验差

有 Gradio：
  你 ──> launch() ──> 一个网址 ──> 同事点开就能输入、看结果       ✅
```

它的典型使用场景：

- **模型 Demo**：给 LLM / 图像模型 / 语音模型套个聊天框或上传框。
- **内部工具**：标注、调参、A/B 对比、RAG 检索结果可视化。
- **快速验证**：在推理服务（vLLM、TGI、本地 transformers）前面加一层人能用的界面。

与同类对比（仅讲定位，不背 API）：

| 框架 | 定位 | 适合 |
|---|---|---|
| **Gradio** | 函数→UI，最快出 Demo，自带聊天/流式组件 | 模型 Demo、内部小工具 |
| **Streamlit** | 脚本从上往下重跑，数据看板友好 | 数据分析仪表盘 |
| **FastAPI + 前端** | 纯后端 API，前端自己写 | 正式产品、需要精细前端 |

一句话：**要"快、像聊天、给模型用"选 Gradio；要"复杂数据看板"选 Streamlit；要"上线产品"最终往 FastAPI/前端走。**

## 2. 整体架构：一次点击在内部走了哪些路

Gradio 应用底层其实是一个 **Web 服务器（基于 FastAPI/Starlette）+ 前端页面**。它把"函数调用"包装成了网络请求。

```
┌─────────────────────────────────────────────────────────────┐
│                          浏览器 (前端)                          │
│   渲染出来的控件： [输入框] [按钮] [聊天框] ...                    │
└───────────────┬─────────────────────────▲───────────────────┘
                │ ① 用户点击 / 输入         │ ④ 渲染返回结果
                │   HTTP / WebSocket        │   (一次性或流式逐 token)
                ▼                           │
┌─────────────────────────────────────────────────────────────┐
│                  Gradio 后端 (FastAPI 服务)                     │
│                                                               │
│   ② 把控件的值反序列化成 Python 参数                              │
│   ┌──────────────┐   进入队列    ┌──────────────────────────┐  │
│   │   请求队列     │ ───────────> │  调用你的函数 fn(inputs)   │  │
│   │  (queue)      │   排队/限流   │  → return / yield 结果    │  │
│   └──────────────┘              └──────────────────────────┘  │
│                                                               │
│   ③ 把返回值序列化成前端能渲染的格式（文本/图片/JSON…）            │
└─────────────────────────────────────────────────────────────┘
```

关键点：

- **每个事件（按钮点击、文本提交）对应一次后端调用。**
- **流式输出走 WebSocket / SSE 长连接**：函数用 `yield` 一段段吐内容，前端逐段刷新——这正是大模型"打字机效果"的实现基础。
- **队列（queue）是后端的入口闸门**：所有请求先排队，再按并发上限放行，保护 GPU 不被同时打爆（详见第 6 节）。

## 3. 两种写法：`Interface` vs `Blocks`

Gradio 有两套搭界面的方式，**先理解它们的分工**：

```
                     你要什么？
                         │
        ┌────────────────┴─────────────────┐
   "一个函数，                          "多个组件、
    标准布局就够"                        自定义布局、
        │                               多步交互"
        ▼                                   ▼
   ┌──────────┐                       ┌──────────┐
   │ Interface│  自动帮你排版          │  Blocks  │  你自己用
   │          │  左输入右输出          │          │  Row/Column 排版
   └──────────┘                       └──────────┘
        │                                   │
        └──────── ChatInterface ────────────┘
        （专门给"聊天"场景的高层封装，最常用于 LLM）
```

- **`Interface`**：最高层封装。你给它"函数 + 输入组件列表 + 输出组件列表"，它自动生成一个标准布局的页面。适合单一功能的 Demo。
- **`Blocks`**：低层、自由。你像搭积木一样用「行/列」容器摆放任意组件，并手动绑定事件。适合多步骤、多区块、有条件逻辑的复杂界面。
- **`ChatInterface`**：面向 LLM 聊天场景的专用高层封装，自带消息历史、流式、重试/清空等按钮。给大模型做对话 Demo 首选它。

> 三者关系：`ChatInterface` 和 `Interface` 都是建立在 `Blocks` 之上的"快捷方式"。能力上 `Blocks` 最强，但写起来最啰嗦；`Interface` 最省事但布局固定。

## 4. 核心组件：输入、输出、控制三类

组件（Component）是页面上的可视元素。从"在交互中的角色"上，可以分三类来记：

```
┌── 输入类（采集用户数据）──────────────────────────┐
│  Textbox 文本框   Slider 滑块   Number 数字        │
│  Dropdown 下拉    Checkbox 勾选  Radio 单选        │
│  Image/Audio/Video 媒体上传     File 文件上传      │
└──────────────────────────────────────────────────┘
┌── 输出类（展示结果）─────────────────────────────┐
│  Label 标签/分类   JSON 结构化   Markdown 富文本    │
│  Image/Gallery 图  Plot 图表     Dataframe 表格    │
└──────────────────────────────────────────────────┘
┌── 既输入又输出 / 控制类 ─────────────────────────┐
│  Chatbot 聊天记录显示   Button 按钮                 │
│  State 会话级隐藏状态（存对话历史/中间变量）         │
└──────────────────────────────────────────────────┘
```

理解组件的两个要点：

1. **同一个组件既能当输入也能当输出**：比如 `Textbox` 放在输入位就是让用户填，放在输出位就是展示结果。
2. **组件有"值类型"约定**：每种组件传给函数的参数类型是固定的（文本框给字符串、滑块给数字、图片给数组/路径）。函数签名要按这个约定来接。

> 组件种类、确切参数名与默认值请以 Gradio 官方文档/源码为准（如 `gradio/blocks.py`、各组件类定义），本文只讲它们"做什么用、怎么选"。

## 5. 事件与流式输出

### 5.1 事件监听：把"用户动作"绑到"函数"

在 `Blocks` 里，交互是通过**事件监听**串起来的。心智模型：

```
某个组件.某个事件( fn=要调用的函数,
                  inputs=[读哪些组件的值],
                  outputs=[把返回值写回哪些组件] )
```

常见事件：按钮的"点击"、文本框的"回车提交"、下拉框的"值改变"。一次事件触发，就是：**读 inputs → 调 fn → 写 outputs。**

### 5.2 流式输出：大模型打字机效果的本质

普通函数用 `return` 一次性返回；要做"逐字蹦出"的流式效果，函数改用 **`yield`**（生成器）。Gradio 每收到一次 `yield`，就把当前内容推给前端刷新一次。

```
函数侧（生成器）              传输                前端
─────────────              ──────              ────────
yield "今"        ──WebSocket──>   显示：今
yield "今天"      ──WebSocket──>   显示：今天
yield "今天天"    ──WebSocket──>   显示：今天天
yield "今天天气"  ──WebSocket──>   显示：今天天气
   ...
（函数结束）       ──关闭──>        最终完整文本
```

接大模型时，把推理服务返回的 token 流，一边累加一边 `yield`，就得到了 ChatGPT 式的打字机体验。这也是为什么"流式"在 LLM Demo 里几乎是标配——**用户不必等整段生成完，首字延迟（TTFT）体验大幅改善**（性能指标见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]）。

## 6. 队列与并发：别让 10 个人同时打爆 1 张 GPU

大模型推理慢、占显存。如果 100 个用户同时点"生成"，直接并发调用会瞬间 OOM 或排满显存。Gradio 用**队列（queue）**解决：

```
用户请求 ──> [ 请求队列 ] ──按并发上限放行──> [ 执行 fn (占 GPU) ]
            ↑ 排队等待                       ↑ 同时最多 N 个在跑
   （超出上限的请求在这里等，不会同时冲进 GPU）
```

要点（讲机制，具体参数名/默认值以官方文档为准）：

- **并发上限**：限制"同时有几个请求在真正执行函数"。设为 1，就是严格串行——最省显存、最稳，适合单卡大模型 Demo。设大一点能提吞吐，但要确保显存/后端扛得住。
- **批处理（batch）**：把队列里多个请求攒成一批，一次喂给模型，提高 GPU 利用率（需要你的函数支持批量输入）。
- **进度反馈**：排队中可以给用户显示"你前面还有几个、预计多久"，体验更好。

经验法则：**对接的是 GPU 推理就一定要开队列并合理设并发，否则线上必崩。**

## 7. 启动与部署：`launch()` 的关键参数（讲含义）

应用搭好后，用 `launch()` 启动服务。下面是**最常需要权衡的几类参数（讲用途，不背默认值）**：

| 参数类别 | 作用 | 怎么权衡 |
|---|---|---|
| 监听地址（如 server_name） | 服务绑在哪个网卡上 | 本机调试用回环地址；要让局域网/容器外访问，绑 `0.0.0.0` |
| 端口（如 server_port） | 服务监听端口 | 与现有服务别冲突；容器/反代时要对应映射 |
| 公网分享（如 share） | 生成一个临时公网转发链接 | 临时演示方便；**生产/内网敏感场景别开**，相当于把内网服务暴露到公网 |
| 鉴权（如 auth） | 设访问用户名密码 | 内部工具加一道门；正式系统应接更完整的鉴权体系 |
| 并发/队列相关 | 见第 6 节 | 接 GPU 必调 |
| 根路径（如 root_path） | 反向代理下的子路径前缀 | Nginx 把 `/demo/` 转发进来时需要对齐，否则静态资源 404 |

部署形态（从轻到重）：

```
本地 launch()  ──>  容器化（Docker）  ──>  反向代理(Nginx)+多实例  ──>  K8s 编排
   单机演示          打包环境一致        加 HTTPS/域名/负载均衡      规模化、弹性伸缩
```

> 规模化时与 [[llmops/kubernetes]]、[[llmops/README]] 衔接：Gradio 进程放进 Pod，前面挂 Service / Ingress，GPU 通过节点调度分配。

## 8. 与 LLM 推理服务集成的典型链路

最常见的用法：**Gradio 当前端聊天框，背后接一个推理服务（vLLM / TGI / OpenAI 兼容接口 / 本地 transformers）。**

```
┌──────────┐   用户输入    ┌───────────────┐   OpenAI 兼容    ┌─────────────────┐
│  浏览器   │ ───────────> │ Gradio 应用    │ ──HTTP 请求───>  │ 推理服务 (vLLM/  │
│ 聊天框    │              │ ChatInterface  │   stream=True    │  TGI/llama.cpp) │
│          │ <─────────── │  fn: 流式转发   │ <──token 流──────│  GPU 上跑模型    │
└──────────┘  打字机刷新   └───────────────┘                  └─────────────────┘
                              ↑ 把上游 token 逐个 yield 出去
```

集成时三个关注点：

1. **流式贯通**：上游推理服务开启流式（如 OpenAI 接口的 `stream=True`），你的 Gradio 函数边收边 `yield`，端到端打字机才生效。任何一段没透传流式，体验就退化成"转圈等整段"。
2. **对话历史管理**：多轮对话要把历史消息一并传回模型。用 `State` 组件或 `ChatInterface` 自带的历史机制保存上下文，注意控制长度别超模型上下文窗口。
3. **错误与超时**：上游 5xx、超时、限流要在函数里捕获并友好提示，否则前端会卡死或抛栈给用户。

> 推理后端选型见 [[llm-inference/vllm/README]] [[llm-inference/sglang/README]]；如果是 RAG 应用，Gradio 常作为"问答 + 引用展示"的界面，见 [[llm-application/rag/README]]。

## 常见问题 / 坑

| 现象 / 坑 | 原因 | 应对 |
|---|---|---|
| 别的机器打不开 | 服务只绑了本机回环地址 | 监听地址设为 `0.0.0.0`，并放通防火墙/容器端口 |
| 多用户同时用就 OOM / 卡死 | 没开队列或并发设太高，GPU 被同时打爆 | 开 `queue()`，按显存把并发调到能稳跑的值（大模型常设 1） |
| 流式不生效，只能整段等 | 函数用了 `return` 而非 `yield`，或上游没开流式 | 函数改生成器逐段 `yield`；确认上游推理接口 `stream=True` |
| 多轮对话"失忆" | 没保存/回传历史，或把状态写成了全局变量 | 用 `State`（会话级）保存历史，**别用模块级全局变量存用户数据**（会用户间串台） |
| `share` 链接被人乱访问 | 开了公网临时转发，等于暴露到公网 | 内网/生产关掉 share；需要外部访问走正规反代+鉴权 |
| 反向代理下页面错乱 / 资源 404 | 子路径前缀没对齐 | 设置根路径前缀，和 Nginx 转发路径一致 |
| 上传大文件 / 长生成超时 | 默认超时或代理超时太短 | 调大队列/代理超时；大任务考虑异步+进度反馈 |
| 用户数据互相串台 | 用全局变量或可变默认参数存"每个用户"的状态 | 一切会话级数据走 `State`，函数保持无副作用 |
