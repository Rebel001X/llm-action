## 0. 一句话锚点

DLRover = **弹性（Elastic）** + **容错（Fault-Tolerant）** + **自动化（Automatic）**。

- 弹性：训练过程中 worker 数量可以动态增减，而不需要停训重启。
- 容错：任一节点/进程崩溃，系统能自动定位、隔离、重调度并续训，而不是让整个 job 失败回滚。
- 自动化：资源量（多少 CPU/GPU/内存）尽量由系统自己决策，减少人工反复调参。

记住一个比喻：**普通分布式训练像「手动挡 + 没有安全气囊」，DLRover 像「自动挡 + 自愈底盘」。**

## 1. 地基：为什么万卡训练「必须」容错

### 1.1 概率算账：规模越大，越「一定」会坏

设单台机器的平均无故障时间（MTBF）为 $T$，一个 job 用了 $N$ 台机器。在一段训练时间内，**至少一台机器出故障**的概率随 $N$ 上升而逼近 1。

直觉公式（独立假设下，单位时间内整 job 不出故障的概率）：

$$P_{\text{job 健康}} = \left(P_{\text{单机健康}}\right)^{N}$$

举个数值例子：假设单台机器一天健康概率 $P_{\text{单机}} = 0.999$（已经很高了，千分之一概率坏）。

- $N=8$：$0.999^{8} \approx 0.992$，几乎不会坏。
- $N=1000$：$0.999^{1000} \approx 0.368$，**一天里有 63% 的概率至少坏一台**。
- $N=10000$（万卡，约对应上千台 8 卡机）：$0.999^{1250} \approx 0.287$ … 而真实集群单机日故障率远高于千分之一（GPU ECC 错、NVLink 抖动、网卡、温度、宇宙射线翻位），实测万卡 job 故障间隔常以**小时**计。

> 结论：万卡不是「会不会坏」的问题，而是「每隔几十分钟就坏一次」的问题。

### 1.2 没有容错时的代价：整批回滚

同步数据并行 / 张量并行 / 流水并行的 AllReduce、流水 bubble 都要求**所有 rank 步调一致**。一个 rank 卡死，整个集合通信（NCCL collective）会 hang 住。传统做法：

```
某 rank 掉线
   │
   ▼
NCCL collective 永久 hang（或 watchdog 超时 abort）
   │
   ▼
整个 job 失败 → 从最近一次 checkpoint 重新拉起
   │
   ▼
丢掉「上次存盘到崩溃」之间的全部算力
```

**浪费量** $\approx N \times t_{\text{lost}}$，其中 $t_{\text{lost}}$ 是「距上次 checkpoint 的时长 + 重新调度拉起的时长」。万卡下 $N$ 极大，所以即使 $t_{\text{lost}}$ 只有 30 分钟，损失也是「数千卡 × 0.5 小时」的天价 GPU 时。

### 1.3 三个被放大的瓶颈

| 痛点 | 小规模时 | 万卡时 |
|------|----------|--------|
| 故障 | 偶发，手动重启即可 | 高频，人工跟不上 |
| Checkpoint | 几分钟一存无所谓 | 模型/优化器状态 TB 级，存一次几十分钟，阻塞训练 |
| 资源利用 | 固定分配够用 | 静态分配易碎，坏一台全停，利用率掉 |

DLRover 正是冲着这三点设计：**自动故障恢复、Flash Checkpoint、弹性 + 自动资源配置**。

## 3. 整体架构：Master + Agent + Worker 三层

DLRover 在 Kubernetes 上以 **ElasticJob** 形式运行，核心是一个**中心化大脑 + 每节点代理**的结构。

```
┌──────────────────────────────────────────────────────────────┐
│                      Kubernetes 集群                           │
│                                                                │
│   ┌────────────────────────────────────────────────────┐      │
│   │                DLRover Job Master                   │      │
│   │  （单点，控制面，不参与梯度计算）                    │      │

│   │  │ Node     │ │ Diagnosis│ │ Rdzv     │ │ Brain  │ │      │
│   │  │ Manager  │ │ (诊断)   │ │ Manager  │ │(自动配置)│      │

│   │  └──────────┘ └──────────┘ └──────────┘ └────────┘ │      │
│   └───────▲───────────────▲────────────────▲───────────┘      │
│           │ gRPC 心跳/上报   │ 指令(重启/扩缩) │                 │

│   │  Node 0      │  │  Node 1      │  │  Node K ...  │         │
│   │ ┌──────────┐ │  │ ┌──────────┐ │  │ ┌──────────┐ │         │

│   │ │(每节点1个)│ │  │ │          │ │  │ │          │ │         │
│   │ └────┬─────┘ │  │ └────┬─────┘ │  │ └────┬─────┘ │         │
│   │  拉起/监控    │  │      │       │  │      │       │         │

└──────────────────────────────────────────────────────────────┘
```

三层各自职责（**为什么这样分层**：把「决策」从「计算」里剥出来，故障的 worker 死了不影响掌舵的 Master）：

| 组件 | 是什么 | 干什么 | 为什么需要 |
|------|--------|--------|-----------|
| **Job Master** | 控制面单点进程 | 全局调度、探活、诊断、rendezvous、资源决策 | 需要一个「上帝视角」知道谁活着、谁该重启 |
| **Elastic Agent** | 每个节点一个守护进程 | 拉起/监控本地 worker 子进程、上报心跳、执行 Master 指令（重启/换 rank） | worker 进程会死，需要一个「不死的」代理来复活它 |
| **Worker** | 真正跑 forward/backward 的进程 | 计算梯度、参与集合通信 | 干活的；可被随时杀掉与重建 |
| **Brain** | Master 内的决策模块 | 根据运行画像给资源/并发建议 | 把「调多少资源」从人工试错变自动 |

> Elastic Agent 在设计上**兼容 PyTorch 原生 `torchrun`（torch.distributed.elastic）的 agent 语义**，并在其上叠加了诊断、热重启、与 Master 联动等增强能力。具体兼容范围以官方文档/源码为准。

## 4. 节点故障自动恢复机制

这是「容错」的核心。可拆成四步：**探活 → 诊断 → 隔离/重调度 → 续训**。

### 4.1 探活（Detection）

- Elastic Agent 周期性向 Master 发心跳；Master 维护每个 node/worker 的活性状态机：
  `PENDING → RUNNING →（无心跳/超时）→ SUSPECTED → FAILED`。
- 不仅看「进程在不在」，还会捕捉**集合通信 hang**：NCCL watchdog 超时、训练 step 长时间不前进、GPU 利用率异常归零等信号。

### 4.2 诊断（Diagnosis）

光知道「坏了」不够，要知道「哪坏了、能不能就地修」。Diagnosis 模块汇总日志/错误码/硬件事件，做**根因归类**：

```
故障信号
   │
   ▼
┌───────────────── Diagnosis 决策树（思路示意）────────────────┐
│ 是「软」故障？(进程崩、OOM、临时网络抖动)                      │
│    └─是→ 同节点 in-place 重启 worker 即可，无需换机           │
│ 是「硬」故障？(GPU ECC 不可恢复、NVLink/网卡坏、机器宕)        │
│    └─是→ 标记该节点不可用，向 K8s 申请新节点替换              │
│ 是「掉队/慢节点」(straggler)？                               │
│    └─是→ 隔离慢节点，必要时替换，避免拖垮整批同步             │
└──────────────────────────────────────────────────────────┘
```

> 注：上图为机制思路示意，DLRover 内置故障检测/诊断规则的精确分类与阈值以官方文档/源码为准。

### 4.3 隔离与重调度（Recovery）

两种恢复粒度，**能小就不大**（恢复越局部，浪费越少）：

1. **In-place restart（就地重启，首选）**：节点本身没坏，只是 worker 进程崩了 → Agent 直接在原节点拉起新 worker 进程，复用已就绪的 GPU/驱动/镜像，**省去重新调度的几分钟**。
2. **Node replacement（换节点）**：节点硬件坏了 → Master 把它从拓扑里摘除，向调度器申请一个新 Pod 顶上。

无论哪种，恢复后都要**重新组网**：所有存活 worker + 新 worker 一起做一次 **rendezvous（集合点）**，重新协商 `world_size / rank / master_addr`，重建 NCCL 通信域。

### 4.4 续训不回滚（Resume）

恢复出来的 worker 从**最近一次（Flash）Checkpoint** 加载模型与优化器状态，所有 rank 对齐到同一 step 后继续。关键收益：**只回退到上次 checkpoint，而不是从 0**，而 Flash Checkpoint 又让「上次 checkpoint」非常近（见第 6 节）。

## 5. 弹性扩缩容（Elastic Scaling）

「弹性」= 训练中途 worker 数可变，且**不需要停训重来**。

### 5.1 为什么要弹性

- 集群资源是动态的：高优任务抢占走你几台机器；或半夜空闲机器多了，想临时加机加速。
- 故障恢复本质也是一次「缩容（坏的走）+ 扩容（新的来）」。

### 5.2 怎么做到「不停训扩缩」

核心是**动态 rendezvous**：把「有多少 rank、各自编号」从「启动时写死」变成「运行时协商」。

```
当前: world_size=64  ── 抢占走 8 个 worker ──►  触发 re-rendezvous
                                                     │
                            存活 56 个 worker 重新集合│
                                                     ▼
                        新 world_size=56，重新分配 rank 0..55
                        重建 NCCL 通信域 + 从 ckpt 对齐 step
                                                     │
              ── 稍后空闲资源回来，加 8 个 ──►  再次 re-rendezvous
                                                     ▼
                        world_size 回到 64，继续训练
```

实践要点（**否则扩缩会破坏数学等价性**）：

- **全局 batch size 与 world_size 解耦**：world_size 变了，要相应调整 `gradient_accumulation_steps` 或 per-device batch，保证有效全局 batch 稳定，学习率/收敛不被打乱。
- **数据切分要随 world_size 重映射**：DataSampler 按新 rank 数重新分片，避免漏样本/重样本。
- 对**大模型并行（TP/PP）**，扩缩通常以「一个完整并行组（如一台 8 卡机）」为最小单位，而非任意单卡增减——因为 TP/PP 切分要求 rank 数满足整除关系。

## 6. Flash Checkpoint（异步秒级存盘 + 快速续训）

Checkpoint 是容错的「存档点」，但传统 checkpoint 在大模型上是**性能杀手**：把 TB 级的模型 + 优化器状态从 GPU → CPU → 远端存储（NFS/OSS/HDFS）同步写一遍，训练全程**阻塞等待**，存一次几十分钟。

### 6.1 核心思想：把「持久化」从训练关键路径上挪走

```
传统同步 Checkpoint（阻塞）：
  训练step ──► [GPU→CPU 拷贝] ──► [写远端存储 数十分钟] ──► 继续训练
              └───────────── 全程训练暂停 ─────────────┘

Flash Checkpoint（异步分级）：
  训练step ──► [GPU→Host/共享内存 拷贝(快)] ──► 立刻继续训练 ✅
                        │
                        └─► 后台进程异步：共享内存 ──► 持久化存储
                            （与训练并行，不阻塞 GPU）
```

### 6.2 分级存储与「内存级 checkpoint」

Flash Checkpoint 的关键招数是**利用节点本地内存/共享内存（shared memory）做第一落点**：

1. 训练进程把状态快速拷到**主机共享内存**（带宽极高，秒级甚至亚秒级完成）→ 训练立刻恢复。
2. 一个**独立的后台进程**再把共享内存里的内容异步刷到持久化存储。
3. 妙处：共享内存**独立于训练进程的生命周期**——即使训练 worker 崩溃，只要节点没宕，内存里的最新 checkpoint 还在，**就地重启可直接从内存恢复，连读远端存储都省了**，续训极快。

```
┌──────────── Node ────────────┐
│  Worker 进程（可能崩溃）        │
│      │ ① 秒级拷贝             │
│      ▼                       │
│  共享内存 SHM（进程崩了它还在） │──② 异步刷盘──►  远端存储(OSS/NFS/HDFS)
│      │                       │                 （灾备/换节点用）
│      └─③ 崩溃后就地重启直接读它 │
└──────────────────────────────┘
```

### 6.3 收益与权衡

| 维度 | 传统同步 ckpt | Flash Checkpoint |
|------|---------------|------------------|
| 训练阻塞 | 长（数十分钟） | 极短（秒级拷贝后即恢复） |
| 可承受的存盘频率 | 低（太慢只能少存） | 高（可几步一存，缩短 $t_{\text{lost}}$） |
| 节点未宕时恢复 | 必须读远端存储 | 直接读本机内存，最快 |
| 风险 | — | 内存落点若节点宕机会丢，故需异步落持久化兜底 |

> 直觉：Flash Checkpoint 让「上次存档点」离崩溃时刻**非常近**，从而把第 1 节的浪费量 $N\times t_{\text{lost}}$ 里的 $t_{\text{lost}}$ 压到很小。接口上它对 PyTorch DDP/FSDP/Megatron 等常见保存形态做了适配，使用方式力求贴近原生 `torch.save`/`load`，具体 API 以官方文档为准。

## 7. 自动资源配置 / Auto-Tuning（Brain）

DLRover 名字里的 **Automatic** 指：尽量让系统自己决定「要多少资源、怎么并发」。

- **资源画像**：运行时采集每个角色的 CPU/内存/GPU 利用、通信耗时、step 时长。
- **Brain 决策**：基于画像给出建议——比如 PS 架构下自动增减 PS/Worker 数、纠正内存配额、识别资源瓶颈；目标是**减少人工反复试错配额**导致的 OOM 或资源浪费。
- 对同步大模型训练，自动化更多体现在**故障后的拓扑重决策**与**弹性扩缩策略**上，而非随意改并行度。

> 自动配置在 TF PS 异步训练场景里更成熟（DLRover 早期主战场）；PyTorch 大模型场景以「容错 + Flash Checkpoint + 弹性」为主。具体能力边界以官方文档为准。

## 8. 一次「节点掉线 → 恢复」完整时间线（调用链）

把前面拼起来，看一条端到端故障恢复链路：

```
t0  正常训练，world_size=64，每 100 step 异步 Flash Checkpoint 到 SHM
        │
t1  Node 7 的 GPU 报不可恢复 ECC 错误 → 该 worker 的 NCCL collective hang
        │
t2  Master 检测到 Node7 心跳超时 + 全局 step 停滞 → 状态置 SUSPECTED
        │
t3  Diagnosis 判定为「硬故障」→ 决策：摘除 Node7，向 K8s 申请新 Pod
        │   （若是软故障，则改为同节点 in-place restart，跳过换机）
        ▼
t4  Master 通知存活 63 个 worker 进入「等待重组」；杀掉 hang 的通信域
        │
t5  新 Node 调度就绪，Elastic Agent 拉起新 worker 进程
        │
t6  re-rendezvous：64 个 worker（63 旧 +1 新）重新协商 rank / world_size
        │   重建 NCCL 通信域
        ▼
t7  各 worker 从最近 Flash Checkpoint 加载状态：
        ├─ 存活节点：可能直接读本机 SHM（最快）
        └─ 新节点：从持久化存储读
        │
t8  所有 rank 对齐到同一 step → 继续训练，全程 job 未失败、未从 0 回滚 ✅
```

**关键对比**：传统方案在 t1 就整 job 挂掉、回到上一个（可能很久以前的）checkpoint；DLRover 把一次「致命故障」降级成了「几分钟的局部抖动」。

## 9. 配置与使用示例（讲含义，非逐字 API）

### 9.1 与 torchrun 的关系

DLRover 的弹性 agent 设计上**兼容 `torchrun`/`torch.distributed.elastic` 的使用心智**：训练脚本基本无需大改，主要是把启动入口换成 DLRover 的弹性启动器，让 agent 接管「拉起 worker + 故障重启 + rendezvous」。

```bash
# 概念示意（确切命令/参数以官方文档为准）
# 传统：
torchrun --nnodes=8 --nproc_per_node=8 train.py
# DLRover 弹性启动（由 elastic agent 接管容错与扩缩）：
dlrover-run --nnodes=4:8 --nproc_per_node=8 train.py
#            └ nnodes 给「范围」=弹性下限:上限，体现可缩可扩
```

`--nnodes=4:8` 的语义直觉：**最少 4 节点也能跑，最多扩到 8**——这就是弹性的入口参数。精确语法以官方文档为准。

### 9.2 Flash Checkpoint 的使用心智

```python
# 概念示意：把原生 save/load 换成 DLRover 的异步 checkpointer
# 1) 训练循环里高频调用 save（因为它只是秒级拷到 SHM，不阻塞）
checkpointer.save(step, model, optimizer)        # 立即返回，后台异步落盘
# 2) 恢复时优先从本机内存，其次远端存储
state = checkpointer.load()                       # 自动选最快可用来源
```

要点：**因为存得快，所以可以存得勤** → `t_lost` 变小 → 故障损失变小。这是 Flash Checkpoint 的全部价值闭环。

### 9.3 在 K8s 上以 ElasticJob 运行（CRD 概念）

DLRover 提供 **ElasticJob** 自定义资源（CRD）+ Controller。你声明角色（如 worker 的最小/最大副本数、资源规格），Controller + Job Master 负责实际的弹性调度与容错。字段名与 schema 以官方 CRD 定义为准。

```yaml
# 概念示意（字段以官方 CRD 为准）
kind: ElasticJob
spec:
  replicaSpecs:
    worker:
      minReplicas: 4      # 弹性下限：低于此不开训
      maxReplicas: 8      # 弹性上限
      template: { /* Pod 规格：GPU/镜像/挂载 */ }
```

## 10. 与同类对比 + 实践要点

### 10.1 与同类的差异（思路层面）

| 能力 | 手写脚本 + torchrun | PyTorch TorchElastic | DLRover |
|------|---------------------|----------------------|---------|
| 进程级重启 | 需自己写 | ✅ 内置 | ✅（并增强诊断/热重启）|
| 故障**根因诊断**与软/硬区分 | ❌ | 基础 | ✅ Diagnosis 模块 |
| 换节点 + K8s 调度集成 | 手动 | 需自配 | ✅ ElasticJob/Controller |
| **秒级异步 Checkpoint** | ❌（自己造） | ❌ | ✅ Flash Checkpoint |
| 自动资源/配额决策 | ❌ | ❌ | ✅ Brain（PS 场景更强）|
| 弹性范围式扩缩 | 有限 | ✅ | ✅ + 与诊断/调度联动 |

一句话：**TorchElastic 给了「进程弹性」的地基，DLRover 在其上补齐了「诊断 + 换机调度 + 快速 checkpoint + 自动化」，更贴近生产万卡。**

### 10.2 实践要点（踩坑清单）

- **存盘频率要趁 Flash Checkpoint 提上来**：别还按老习惯一小时一存，秒级存盘就该几百步一存，才吃到容错红利。
- **全局 batch / 学习率与弹性解耦**：扩缩时务必同步调 `grad_accum`，否则收敛曲线被 world_size 抖动污染。
- **TP/PP 并行场景按「并行组」为单位扩缩**，不要奢望任意单卡热插拔。
- **共享内存要预留**：Flash Checkpoint 的内存落点需要节点上有足够 host 内存 / `/dev/shm` 空间，否则退化为慢路径。
- **诊断不是银弹**：宇宙射线级偶发软错可自愈，但持续性硬件劣化（如间歇 ECC）可能反复触发恢复，需配合集群侧坏卡下线策略。
- **Master 是单点控制面**：它不算梯度所以负载轻，但要保证其高可用/可重启，否则失去「掌舵」。

## 常见问题

| 问题 | 解答 |
|------|------|
| DLRover 和 torchrun 是替代关系吗？ | 不是替代而是增强；它兼容 torchrun 心智并接管容错/扩缩/调度。训练脚本基本无需大改。 |
| 容错和「断点续训」有啥区别？ | 断点续训是「整 job 挂了再人工拉起从 ckpt 续」；DLRover 容错是「job 不挂、局部自愈、自动续」，粒度和自动化程度完全不同。 |
| Flash Checkpoint 为什么快？ | 把持久化移出训练关键路径：先秒级拷到主机共享内存让训练立即恢复，再后台异步刷远端；存活节点甚至能直接从内存恢复。 |
| 内存里的 checkpoint 节点宕机会丢吗？ | 会，所以一定有异步落持久化存储兜底；内存落点只是「快路径」，远端存储是「灾备」。 |
| 弹性扩缩会改变训练结果吗？ | 处理得当不会：要保持有效全局 batch 不变（调 grad_accum）、数据按新 rank 重切分。处理不当会影响收敛。 |
| 万卡为什么非要它？ | 概率上万卡每隔几十分钟必坏一台；没有自动容错就是「数千卡 × 小时级」的反复浪费，人工根本跟不上。 |
| 支持 TensorFlow 吗？ | 支持，DLRover 早期主打 TF PS 异步训练的自动扩缩；当下大模型主线是 PyTorch DDP/FSDP/Megatron + 容错 + Flash Checkpoint。 |
| Master 挂了怎么办？ | Master 是控制面单点，需依赖其自身重启/高可用机制恢复；它不参与计算故影响面与 worker 故障不同。具体机制以官方文档为准。 |
