## 0. 一句话锚点

OneFlow 是一个深度学习训练框架，最核心的贡献是 **SBP 抽象** 和 **Global Tensor**：

- **不一样的地方**：别的框架(PyTorch DDP、Megatron-LM)让你**手动**决定"哪个张量切到哪几张卡、什么时候插一次 AllReduce"。OneFlow 让你**只声明**每个张量的分布属性(SBP)，框架**自动推导**出需要的通信，并自动插进计算图。
- **一句话**：把"分布式"从"你写的代码"降级成"张量的一个属性"。

> 类比：Megatron 像手动挡——离合、换挡(通信原语)都得自己踩；OneFlow 像自动挡——你只说"我要去哪、车怎么分配座位(SBP)"，变速箱(SBP 推导器)自己换挡。

## 1. 地基/前置：分布式训练为什么难

### 1.1 三个原子概念

**张量(Tensor)**：一块多维数字数组。训练里到处是张量——输入数据 $X$、权重 $W$、激活值、梯度。

**设备(Device / Placement)**：一张 GPU。多机多卡时，我们有一组设备，记作一个集合，例如 `placement = {机器0:[GPU0,GPU1], 机器1:[GPU0,GPU1]}`，共 4 张卡。

**通信原语(Collective)**：多张卡之间同步数据的标准操作。必须记牢这 4 个：

```
AllReduce  : 每张卡都有一份数据,逐元素求和(或平均),结果广播回所有卡
             卡0:[1,2] 卡1:[3,4]  --AllReduce(sum)-->  卡0:[4,6] 卡1:[4,6]

AllGather  : 每张卡有一个分片,拼起来,每张卡都拿到完整结果
             卡0:[a] 卡1:[b]  --AllGather-->  卡0:[a,b] 卡1:[a,b]

ReduceScatter: 先逐元素求和,再把结果切片分给各卡(AllReduce 的"省一半"版)
             卡0:[1,2] 卡1:[3,4] --ReduceScatter--> 卡0:[4] 卡1:[6]

Broadcast  : 一张卡的数据复制到所有卡
             卡0:[x]  --Broadcast-->  卡0:[x] 卡1:[x]
```

### 1.2 三种并行(必须分清)

```
                  ┌─────────────── 一个 mini-batch (8 条样本, 模型 2 层) ───────────────┐

数据并行 DP    每张卡放【整个模型副本】, 各吃【不同样本】
              卡0: 模型副本 ← 样本0~3        反向后梯度不一样
              卡1: 模型副本 ← 样本4~7        → 必须 AllReduce 同步梯度

模型并行 TP    一层的【权重矩阵切开】, 每张卡算一部分
              卡0: W 的左半列        前向算完要把两半【拼起来】(AllGather)
              卡1: W 的右半列        或把部分和【相加】(AllReduce)

流水并行 PP    把【层】切成段, 卡0 算第1层, 卡1 算第2层
              卡0: Layer1  ──激活──►  卡1: Layer2   (点对点 Send/Recv)
```

**难点核心**：每种并行需要插入的通信**不一样、位置不一样、时机不一样**。手写时极易插错——少插一次梯度就不收敛，多插一次就白白浪费带宽。OneFlow 要解决的就是这个"插通信"的问题。

## 2. 痛点：手写并行到底有多痛

看 Megatron-LM 怎么做张量并行(以一个 MLP `Y = GeLU(X·A)·B` 为例，伪代码)：

```
# Megatron 风格(手动插通信)——程序员必须知道每一步的并行语义
A 按【列】切到 2 卡:  A = [A0 | A1]
X 复制到 2 卡 (Broadcast)
卡0:  Y0 = GeLU(X · A0)      # 各算各的, 不需要通信 (列并行的妙处)
卡1:  Y1 = GeLU(X · A1)
B 按【行】切到 2 卡:  B = [B0; B1]
卡0:  Z0 = Y0 · B0          # 得到部分和
卡1:  Z1 = Y1 · B1
Z = AllReduce(Z0, Z1)      # ★ 程序员必须【手动】知道这里要 AllReduce
```

痛点清单：
1. 程序员得在脑子里维护"现在每个张量是切的还是复制的"。
2. 换个并行策略(比如改成数据并行)，**整段通信代码要重写**。
3. 切 4 卡、8 卡、跨机，AllReduce 的位置/分组都要改。
4. 反向传播的通信和前向是"镜像"的(前向 AllReduce ↔ 反向 Identity)，又是一套容易写错的逻辑。

> OneFlow 的回答：把"每个张量是切的还是复制的"这件事**变成张量的一个标签**，让框架替你维护、替你推导通信。这个标签就是 **SBP**。

## 3. 核心抽象：SBP

SBP 是 OneFlow 的灵魂。它描述一个**逻辑张量**(你眼中"一个完整的张量")是怎么**物理分布**到多张卡上的。SBP 是三个单词的首字母：

```
┌──────────────────────────────────────────────────────────────────┐
│  逻辑张量 T (形状 4×3, 你写代码时看到的"一个"张量)                  │
│                                                                    │
│  S  = Split(dim)   沿某个维度【切开】, 每卡拿一片                   │
│        Split(0): 按行切     卡0:[行0,行1]  卡1:[行2,行3]            │
│        Split(1): 按列切     卡0:[列0]      卡1:[列1,列2]            │
│                                                                    │
│  B  = Broadcast    每卡拿一份【完整副本】                           │
│        卡0:[整个T]  卡1:[整个T]                                     │
│                                                                    │
│  P  = PartialSum   每卡拿一个【部分和】,逻辑值 = 所有卡相加         │
│        卡0:[半成品a]  卡1:[半成品b]   真正的 T = a + b              │
└──────────────────────────────────────────────────────────────────┘
```

逐个说"为什么需要它"：

- **Split(S)** 对应**模型并行切权重**、**数据并行切 batch**。一个张量切了，物理上每卡的内存就只放一片，省显存。
- **Broadcast(B)** 对应**数据并行里的权重**(每卡一份完整权重)、或被复制的输入。
- **PartialSum(P)** 是最巧妙的一个：它表示"**还没加完的中间结果**"。矩阵乘法切开后，每卡算出的是部分和，逻辑上需要相加才是正确答案——但**先不急着加**，把它标成 P，等真正需要完整值时再触发 AllReduce。这让框架能把通信**延迟到最优位置**。

**关键洞察**：DP / TP 看起来是两种不同的并行，但在 SBP 视角下它们只是**张量带了不同的 SBP 标签**而已：

```
数据并行: 输入数据 X 是 Split(0)   ,  权重 W 是 Broadcast
模型并行: 输入数据 X 是 Broadcast  ,  权重 W 是 Split
                  ↑ 同一套抽象,只是标签换了 → 这就是"统一数据并行与模型并行"
```

## 4. Global Tensor：逻辑一个、物理多份

普通 PyTorch 张量只活在**一张**卡上(`tensor.to("cuda:0")`)。OneFlow 的 **Global Tensor**(早期叫 Consistent Tensor)是一个**横跨多卡**的张量，由两个属性定义：

```
Global Tensor = 逻辑数据  +  placement(它住在哪些卡上)  +  sbp(它怎么分布)

例: x.placement = {GPU0, GPU1, GPU2, GPU3}    (住在 4 张卡)
    x.sbp       = Split(0)                     (按第 0 维切成 4 片)

   逻辑视角(你写代码):          物理视角(框架管理):
   ┌─────────────┐             GPU0: x[0:2]
   │   x: 8×512   │   ─────►    GPU1: x[2:4]
   │ (一个张量)   │             GPU2: x[4:6]
   └─────────────┘             GPU3: x[6:8]
```

为什么这是关键一步：有了 Global Tensor，**你写 `z = x @ w` 这一行单机代码**，框架知道：
- `x` 是 Split(0)、`w` 是 Broadcast → 推出 `z` 是 Split(0)，**不需要通信**；
- 或 `x` 是 Broadcast、`w` 是 Split(1) → `z` 是 Split(1)，也不需要通信；
- 或 `x` 是 Split(1)、`w` 是 Split(0) → `z` 是 PartialSum → 后续要完整值时自动插 AllReduce。

**对照另一种用法 Local Tensor + DTensor 风格**：OneFlow 还提供 `to_global()` / `to_local()` 在"单卡本地张量"和"全局张量"之间切换，方便和单机 PyTorch 代码互转。

## 5. 一致性视角(Consistent / Global View)

这是 OneFlow 的世界观，也是它名字"一致性"的来源。

```
两种看世界的方式:

  ┌─ 物理视角 (Local View) ──────────────────┐
  │  你直接面对 4 张卡, 每张卡跑一份程序,      │
  │  手动管 rank、手动写 AllReduce。           │ ← PyTorch DDP / Megatron 的世界
  │  优点:灵活  缺点:容易写错、换策略要重写    │
  └──────────────────────────────────────────┘

  ┌─ 一致性视角 (Global / Consistent View) ──┐
  │  你只面对【一个逻辑程序、一个逻辑张量】,    │
  │  就像写单机代码。多卡是张量的属性(SBP),    │ ← OneFlow 的世界
  │  通信由框架推导。                          │
  │  优点:代码=单机语义,易用、易换策略         │
  └──────────────────────────────────────────┘
```

"一致性"的精确含义：**无论底层用几张卡、用什么并行策略，程序的逻辑语义(算出来的数值结果)和单机一模一样**。并行只是改变了"在哪算、怎么传"，不改变"算什么"。这把"正确性"和"性能"解耦了——你先保证逻辑对(单机就能验证)，再调 SBP 调性能。

> 这正是相对 Megatron 的核心易用性优势：Megatron 的正确性和它手插的那串通信代码**强耦合**，改并行=改正确性逻辑；OneFlow 改并行=只改 SBP 标签，正确性框架替你保证。

## 6. SBP 推导与自动通信:框架怎么自己插通信

OneFlow 内部对每个算子(op)预置了一张 **SBP Signature 表**：给定输入张量的 SBP，输出张量是什么 SBP。框架做两件事：

**(a) SBP 推导**：沿计算图传播 SBP，像类型推断一样。

**(b) Boxing(自动插通信)**：当某个算子**要求**的输入 SBP 与**上游实际产出**的 SBP 不一致时，框架自动插入一次转换(就是一次通信)。这套转换规则是固定的、可查表的：

```
源 SBP → 目标 SBP    需要插入的通信
────────────────────────────────────
PartialSum → Broadcast    AllReduce      (部分和 → 完整副本,经典!)
PartialSum → Split        ReduceScatter  (部分和 → 切片,省一半带宽)
Split      → Broadcast    AllGather      (切片 → 完整副本)
Split(i)   → Split(j)     All2All        (换一个维度切)
Broadcast  → Split        本地切片,无通信 (直接丢掉不要的部分)
Broadcast  → Broadcast    无通信
Split      → Split (同维)  无通信
```

这张表就是 OneFlow 把"程序员脑子里那套通信知识"**沉淀成框架内置规则**的地方。你不再需要记"什么时候 AllReduce"——框架查表自动插。

数据并行的梯度同步在这套机制里是**自然涌现**的：反向传播后，权重梯度被推导成 PartialSum(每卡各自一份基于本地 batch 的梯度)，而优化器更新需要 Broadcast 的完整梯度 → 推导器查表 → 自动插一次 `PartialSum→Broadcast = AllReduce`。**你从没写过 AllReduce，它自己出现了。**

## 7. 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│  用户层:  写【单机风格】Python 代码 (nn.Module / Global Tensor) │
│           只声明 placement 和 sbp                              │
├──────────────────────────────────────────────────────────────┤
│  编译器层 (静态图 nn.Graph):                                   │
│    1. 构建逻辑计算图                                           │
│    2. SBP 推导:为每个张量定 SBP                               │
│    3. Boxing:在 SBP 不匹配处自动插通信 op (AllReduce 等)      │
│    4. 算子放置 / 显存规划 / 自动并行(可选,搜最优 SBP)          │
├──────────────────────────────────────────────────────────────┤
│  运行时层 (Actor 模型):                                        │
│    每个 op = 一个 Actor,用【消息驱动】触发执行;               │
│    计算与通信天然【流水线重叠】(overlap),提升利用率          │
├──────────────────────────────────────────────────────────────┤
│  硬件: 多机多卡 GPU + NCCL/集合通信                            │
└──────────────────────────────────────────────────────────────┘
```

两点设计值得记：
- **静态图编译(nn.Graph)**：先拿到整张图，才能做全局 SBP 推导和通信优化。OneFlow 也支持 Eager 模式(`oneflow.nn` 接口高度兼容 PyTorch，迁移成本低)。
- **Actor 去中心化运行时**：传统框架有一个中心调度器，跨机时成为瓶颈。OneFlow 用 Actor + 消息机制，每个算子自己决定何时运行，使**计算与通信自动重叠**——这是 OneFlow 论文主打的性能点之一。

## 8. 与 Megatron-LM / DeepSpeed 对比

```
                Megatron-LM        DeepSpeed           OneFlow
              ───────────────    ───────────────    ───────────────
底座          基于 PyTorch       基于 PyTorch        独立框架(自研运行时)
并行哲学      手写 TP/PP 通信     ZeRO 切优化器状态   SBP 自动推导通信
              (人决定插哪)        +引擎封装           (框架决定插哪)
统一抽象      无(DP/TP/PP分别实现) 无(各策略独立)      ✅ SBP 统一三种并行
正确性来源    手插的通信代码      引擎内部逻辑        一致性视角(=单机语义)
换并行策略    改通信代码          改 config           ✅ 只改 sbp 标签
显存优化      重计算+TP          ✅ ZeRO-1/2/3 最强   重计算+SBP 切分
易用性        低(要懂并行细节)    中(config 驱动)     ✅ 高(写单机代码)
生态/社区     ⭐最大(LLM事实标准) ⭐很大              较小(国产,一流所开源)
```

**一句话区分三者哲学**：
- **Megatron**：手工艺人——把 TP/PP 通信写到极致、性能标杆，但每种并行各写一套。
- **DeepSpeed**：内存大师——核心武器是 **ZeRO**(把优化器状态/梯度/参数切到各卡，破解显存墙)，并行策略仍是"组合拼装"。
- **OneFlow**：抽象统一者——用 SBP 把 DP/TP/PP **同构**化，主打"分布式易用性"和编译期自动优化。

> 注意:这三者并非纯粹竞争。理念上互相借鉴——后来 PyTorch 的 **DTensor / DeviceMesh** 抽象，思路与 OneFlow 的 Global Tensor + SBP 高度一致(逻辑张量 + placement + 分布规则)，可视为 OneFlow 路线被主流框架吸收。

## 9. 数值例子:用一次矩阵乘手算 SBP 推导

设 2 张卡，做 $Z = X \cdot W$。

- $X$ 形状 $2 \times 4$，$W$ 形状 $4 \times 3$，逻辑结果 $Z$ 形状 $2 \times 3$。
- 选**模型并行**方案：$X$ 设 `Broadcast`(每卡有完整 $X$)，$W$ 沿"内积维(第0维)"切 `Split(0)`。

```
W = Split(0) 切到 2 卡 (按行切, 各 2 行):
  W = [ w0 ]   卡0 拿 W_top = [w0; w1]  (前 2 行, 形状 2×3)
      [ w1 ]   卡1 拿 W_bot = [w2; w3]  (后 2 行, 形状 2×3)
      [ w2 ]
      [ w3 ]

X = Broadcast, 每卡都有完整 X (2×4):  X = [x0 x1 x2 x3]   (每行 4 个数)
```

数学上 $X \cdot W = X[:, :2]\cdot W_{top} + X[:, 2:]\cdot W_{bot}$。所以：

```
卡0:  Z0 = X[:, 0:2] · W_top    (2×2 · 2×3 = 2×3, 一个【部分和】)
卡1:  Z1 = X[:, 2:4] · W_bot    (2×2 · 2×3 = 2×3, 另一个【部分和】)

SBP 推导规则:  Broadcast · Split(0)  →  PartialSum
所以 Z 的 SBP = PartialSum,  逻辑值 Z = Z0 + Z1
```

**手算一组数**(设全 1 便于心算)：$X$ 全是 1(2×4)，$W$ 全是 1(4×3)。逻辑正确答案：$Z_{ij} = \sum_{k=1}^{4} 1\cdot 1 = 4$，即 $Z$ 是全 4 的 $2\times3$ 矩阵。

```
卡0: Z0 = (2×2全1)·(2×3全1) → 每元素 = 1·1+1·1 = 2   → Z0 全 2
卡1: Z1 = (2×2全1)·(2×3全1) → 每元素 = 2              → Z1 全 2
PartialSum 触发完整值时: Z = Z0 + Z1 = 全 4  ✓ 与单机一致!
```

**通信在哪触发？** 只要下游需要 $Z$ 的完整值(比如要送进 LayerNorm，它要求 Broadcast 输入)，推导器查表：`PartialSum → Broadcast = AllReduce`，于是自动插一次 AllReduce 把两个全 2 相加成全 4。**全程你只写了 `Z = X @ W`。**

## 10. 何时用 / 权衡

**适合用 OneFlow**：
- 需要灵活组合 DP+TP+PP，又不想手写一堆通信代码 → SBP 让换策略=换标签。
- 团队想要"先单机验证正确性、再上多机调性能"的开发流程 → 一致性视角的红利。
- 想用编译期自动并行(自动搜最优 SBP)省去人工调参。

**权衡/代价**：
- 生态比 PyTorch/Megatron 小，第三方模型、教程、踩坑经验少;部分前沿模型需自己适配。
- 静态图(nn.Graph)调试不如 Eager 直观;要享受全部优化需进入静态图模式。
- 概念门槛：SBP / Global Tensor 是新心智模型，初学需转弯。
- LLM 训练的"事实标准"仍是 Megatron 系;选 OneFlow 多见于其能力被吸收进 PyTorch DTensor 后的理念学习，或特定国产生态。

## 常见问题

| 问题 | 答 |
|------|-----|
| SBP 三个字母分别是什么 | **S**plit(切)、**B**roadcast(广播复制)、**P**artialSum(部分和) |
| 数据并行和模型并行在 OneFlow 里有何区别 | 没有本质区别——只是输入/权重带的 SBP 标签对调:DP 是"数据Split+权重Broadcast",TP 是"数据Broadcast+权重Split" |
| 谁来插 AllReduce | 框架。SBP 推导发现"产出 SBP ≠ 下游要求 SBP"时,Boxing 查表自动插对应通信 |
| PartialSum 有什么用 | 表示"还没加完的中间结果",让框架把通信【延迟到真正需要完整值的最优位置】 |
| Global Tensor 和普通张量差别 | 普通张量住单卡;Global Tensor = 逻辑数据 + placement(住哪些卡) + sbp(怎么分布) |
| 一致性视角是什么意思 | 不管用几卡/什么并行,程序逻辑语义与单机【完全一致】,正确性与性能解耦 |
| 和 Megatron 比最大优势 | 易用性:换并行策略只改 sbp 标签,不必重写通信代码 |
| 和 DeepSpeed 比 | DeepSpeed 强在 ZeRO 省显存;OneFlow 强在 SBP 统一并行抽象与编译期自动通信 |
| 它和 PyTorch DTensor 关系 | DTensor/DeviceMesh 思路与 OneFlow 的 Global Tensor+SBP 高度一致,可视为该路线被主流吸收 |
| 静态图还是动态图 | 两者都支持;Eager 高度兼容 PyTorch 接口,nn.Graph 静态图才能做全局通信优化 |
