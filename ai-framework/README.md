## 0. 一句话锚点

把大模型的生命周期想成四个工种，每个工种有自己的"主力框架"：

```
            ┌──────────────────────────────────────────────┐
            │              大模型生命周期                    │
            └──────────────────────────────────────────────┘
   预训练            微调              对齐              推理部署
     │                │                │                  │
  ┌──┴──┐         ┌───┴───┐        ┌───┴──┐          ┌────┴────┐
  底座框架        微调框架         对齐框架           推理框架
  PyTorch         PEFT(LoRA)       TRL(DPO/PPO)       vLLM
     +              基于             基于               TRT-LLM
  并行框架        Transformers     Transformers       llama.cpp
  DeepSpeed
  Megatron-LM
```

- **底座框架（PyTorch/JAX）**：提供张量、自动求导、算子。所有上层框架都站在它肩上。
- **训练扩展/并行框架（DeepSpeed/Megatron-LM）**：解决"模型太大，一张卡放不下、一张卡训不动"。
- **微调框架（PEFT/TRL/Transformers）**：解决"我没有上千张卡，只想用少量资源把现成大模型改成我要的样子"。
- **推理框架（vLLM/TensorRT-LLM/llama.cpp）**：解决"训练好了，怎么高吞吐、低延迟、低成本地服务用户"。

一句话：**训练框架优化"算得快、装得下"，推理框架优化"服务多、回得快"。两者目标不同，所以是两套独立的系统。**

## 1. 地基：为什么一个 PyTorch 不够用（它解决什么问题）

先回到最原子的问题：训练一个神经网络，计算机到底要存什么、算什么？

训练一步（一个 step）= **前向**算出 loss + **反向**算出梯度 + **优化器**更新参数。这三步在显存里要同时住下四样东西：

```
显存里常驻的四类数据（以 Adam + 混合精度训练为例）
┌────────────┬──────────────┬───────────────────────────┐
│   数据      │ 每个参数占用  │  说明                      │
├────────────┼──────────────┼───────────────────────────┤
│ 参数(fp16) │   2 字节     │  前向/反向用                │
│ 梯度(fp16) │   2 字节     │  反向算出，用来更新         │
│ 参数(fp32) │   4 字节     │  优化器主副本(master)       │
│ Adam 动量m │   4 字节     │  一阶矩                     │
│ Adam 方差v │   4 字节     │  二阶矩                     │
└────────────┴──────────────┴───────────────────────────┘
   合计 ≈ 16 字节/参数（不含激活值）
```

**为什么是 16 字节？** 这是大模型显存第一性原理。一个 $P$ 参数的模型，光是"状态"就要 $16P$ 字节。

数值锚点：一个 **7B（70 亿参数）** 模型，状态显存 $\approx 16 \times 7\times10^9 = 112\text{GB}$。而一张 A100/H100 只有 80GB。**结论：7B 模型用最朴素的方式，单卡连训都训不起来。** 这就是"显存墙"。

于是出现三堵墙，对应三类扩展技术：

```
┌─────────────┬────────────────────────┬──────────────────────┐
│   墙         │  现象                   │  谁来拆               │
├─────────────┼────────────────────────┼──────────────────────┤
│ 显存墙       │ 模型状态放不进单卡       │ ZeRO / 模型并行       │
│ 通信墙       │ 多卡间同步梯度太慢       │ 通信重叠 / 拓扑感知   │
│ 吞吐墙       │ 算力没喂饱、卡在等数据   │ 流水线并行 / 重计算   │
└─────────────┴────────────────────────┴──────────────────────┘
```

PyTorch 本身只给你"单机的积木"。把积木堆到上千张卡、还要堆得高效，就是 DeepSpeed 和 Megatron-LM 存在的理由。

## 2. 底座框架：PyTorch（自动微分与动态图）

> 详见 [[ai-framework/pytorch/README]]

**它解决什么问题**：让你只写"前向计算"，框架自动帮你算"反向梯度"。这是深度学习能规模化的根本前提——人类不可能手推上亿参数的链式法则。

**核心机制：动态计算图 + autograd。** 你每写一行带 `requires_grad=True` 张量的运算，PyTorch 就在背后悄悄记一笔"账"，把这次运算挂到一张图上：

```
       前向（你写的）              反向（框架自动）
   x ──► [matmul] ──► h ──► [relu] ──► y ──► loss
        ▲                                      │
        │  每个算子记下"如何对输入求导"          │ loss.backward()
        └──────────────────────────────────────┘
              autograd 沿图反向走一遍，
              用链式法则 dy/dx = Σ 局部导数 连乘
```

链式法则就是反向传播的全部数学：若 $L = f(g(x))$，则 $\frac{\partial L}{\partial x} = \frac{\partial L}{\partial g}\cdot\frac{\partial g}{\partial x}$。autograd 把每个算子的"局部导数"存好，反向时顺着图把它们连乘起来。

**为什么叫"动态图"**：图是**运行时**随代码执行而构建的（define-by-run），所以你能用 Python 的 `if/for` 控制流，调试像调试普通程序。代价是每步都要重建图、难做整图优化——这正是推理框架（TRT-LLM）要把它"编译成静态图"的原因。

**PyTorch 在生态里的位置**：它是**地基**。DeepSpeed、Megatron、PEFT、TRL、vLLM 全部构建在 PyTorch 张量与 autograd 之上。学透 PyTorch 的 `nn.Module`、`autograd`、`DistributedDataParallel`，是看懂其余所有框架的前提。

> 国内同类底座：OneFlow（一致性视角的分布式张量）、PaddlePaddle（飞桨，国产全栈）、MindSpore（昇腾生态）。机制相通，差异在分布式抽象与硬件适配，以官方文档为准。

## 3. 训练扩展框架：DeepSpeed（用 ZeRO 把显存"分摊"出去）

> 详见 [[ai-framework/deepspeed/README]]

**它解决什么问题**：第 1 节算过，模型状态要 $16P$ 字节。**数据并行（DDP）下，每张卡都存了一份完整的 $16P$，纯属浪费。** DeepSpeed 的核心思想 ZeRO（Zero Redundancy Optimizer）：既然有 $N$ 张卡，就把这份状态**切成 $N$ 份**，每张卡只存 $1/N$，用到时再去别的卡上"借"。

**ZeRO 三个阶段，逐级把更多东西切掉：**

```
                 单卡显存占用（N 张卡，每参数字节）
              参数 fp16  梯度 fp16   优化器状态(12B)
  DDP(基线)      2          2            12          ← 每卡都全存 = 16
  ZeRO-1         2          2          12/N          ← 切优化器状态
  ZeRO-2         2         2/N         12/N          ← 再切梯度
  ZeRO-3        2/N        2/N         12/N          ← 连参数也切

  N=8 时：基线 16B → ZeRO-3 ≈ 16/8 = 2B（每参数），省 8 倍
```

**ZeRO-3 的工作流（最精妙的一步）**：参数被切散在各卡，前向走到某一层时，该层参数才被 **all-gather** 临时凑齐，算完立刻丢弃：

```
  前向第 L 层：
   GPU0 [切片0]┐
   GPU1 [切片1]├─ all-gather ─► 临时拼出完整第L层 ─► 算完即丢
   GPU2 [切片2]┘                （只在用的瞬间占满显存）
```

这是**用通信换显存**：省了 8 倍显存，代价是多了 all-gather 通信。

**ZeRO-Offload / Infinity**：更极端——把优化器状态、甚至参数下放到 **CPU 内存乃至 NVMe 硬盘**。让单张消费级卡也能"训"几十 B 模型（慢，但跑得动）。

**DeepSpeed 的定位**：它本质是 **数据并行的极致优化**——不改变"每张卡跑完整模型计算图"这件事，只优化"状态怎么存"。所以它**对模型代码侵入小**（包一层即可），是中小团队、显存吃紧场景的首选。

## 4. 训练扩展框架：Megatron-LM（把模型本身切开）

> 详见 [[ai-framework/megatron-lm/README]]

**它解决什么问题**：ZeRO 切的是"状态"，但**单层的计算**仍要在一张卡上完成。当单层大到一张卡都算不下（如超大 FFN/词表），或要训千亿、万亿模型时，必须把**模型结构本身**切开。Megatron 提供两种"切模型"的并行：

**(a) 张量并行 TP（Tensor Parallel）——把一个矩阵乘法切给多卡**

Transformer 里最重的是 $Y = XW$。把权重 $W$ 按列切成 $[W_1, W_2]$，两张卡各算一半，结果拼起来：

```
   X ─┬─► [W1 on GPU0] ─► Y1 ┐
      └─► [W2 on GPU1] ─► Y2 ┴─ concat ─► Y
   一次矩阵乘 → 两卡并行，每步末尾 all-reduce 同步
```

特点：通信极频繁（每层都要同步），所以 TP **只在单机内 NVLink 高速卡间用**（通常 TP≤8）。

**(b) 流水线并行 PP（Pipeline Parallel）——把不同层放到不同卡**

模型 32 层，切成 4 段，每张卡放 8 层，数据像流水线一样流过：

```
  GPU0: 层1-8  ─► GPU1: 层9-16 ─► GPU2: 层17-24 ─► GPU3: 层25-32
  把一个 batch 拆成多个 micro-batch 填满流水线，减少"气泡"(空等)
```

特点：通信少（只在切口传激活），适合**跨机**扩展。代价是有"流水线气泡"。

**3D 并行 = TP × PP × DP（数据并行）**，这是训千亿模型的标准姿势：

```
   DP 维度（复制整套，喂不同数据）
     ├── PP 维度（机器间，按层切）
     │     └── TP 维度（机器内，按算子切）
   例：1024 卡 = DP 16 × PP 8 × TP 8
```

**Megatron 的定位**：它是**模型并行的事实标准**，为超大模型而生。代价是**对模型代码侵入大**——你的模型必须用 Megatron 风格的并行算子改写。所以实践中常与 DeepSpeed 组合（见第 7 节）。

## 5. 微调框架：PEFT / TRL（用一张卡改大模型 + 对齐）

前面都在讲"从零训练"。但 99% 的团队不预训练，而是**拿现成大模型做微调**。这里资源诉求完全不同：不是"千卡训月余"，而是"单卡/几卡，几小时把模型调成我要的样子"。

**PEFT（Parameter-Efficient Fine-Tuning）——只训一小撮参数**

全量微调 7B 仍要 $16P$ 显存。LoRA 的洞见：微调时权重的"变化量"$\Delta W$ 是**低秩**的，可以用两个小矩阵近似：

$$ W' = W + \Delta W = W + B A, \quad A\in\mathbb{R}^{r\times d},\ B\in\mathbb{R}^{d\times r},\ r\ll d $$

```
   冻结的大权重 W (d×d, 不更新)
        │
        ▼
   x ──►(+)──► 输出
        ▲
        └── B·A·x   只训 B、A 两个瘦矩阵（r=8/16）
   可训练参数从 d² 降到 2dr，常 < 1% → 显存/存储骤降
```

数值锚点：7B 全量微调要存 7B×16B；LoRA 只训约 0.1%~1% 的参数，优化器状态显存几乎可忽略，配合 4-bit 量化（QLoRA）可在**单张 24GB 消费卡**上微调 7B。

**TRL（Transformer Reinforcement Learning）——做对齐**

微调出"会说话"的模型后，还要让它"说得符合人类偏好"。TRL 提供对齐三件套：

```
   SFT（监督微调）──► 教模型基本指令跟随
        │
   Reward / 偏好数据
        │
   ┌────┴────┐
   DPO         PPO/GRPO
  (直接用偏好  (训奖励模型 + 强化学习,
   对比,简单)   即经典 RLHF, 复杂强但贵)
```

PEFT 和 TRL 都构建在 **HuggingFace Transformers**（模型库 + 训练 `Trainer`）之上，常与 Accelerate（屏蔽多卡细节）、DeepSpeed（省显存）叠加使用。

> 相关：`unsloth`、`pai-megatron-patch` 等是面向特定场景的微调加速/适配方案。

## 6. 推理框架：vLLM / TensorRT-LLM（高吞吐服务）

**训练和推理是两个世界。** 训练追求"反向传播算得快"；推理**没有反向**，只做前向，但要面对成千上万并发请求、要省 KV Cache 显存、要低延迟。所以推理有自己的一套框架。

**推理的两大痛点：**

1. **KV Cache 显存碎片**：自回归生成时，每个 token 的 Key/Value 要缓存复用。请求长度不一，传统连续分配会产生大量碎片浪费。
2. **批处理低效**：请求有长有短，固定批一起跑，短的早算完却要等长的，GPU 空转。

**vLLM 的杀手锏：PagedAttention（把 KV Cache 当虚拟内存管）**

借鉴操作系统分页：把 KV Cache 切成固定大小的"块（block）"，用"页表"映射，按需分配，几乎零碎片：

```
   逻辑序列(连续)         物理显存(分块,可不连续)
   tok1 tok2 tok3 ...  →  [块7][块2][块9]...  ← 页表映射
   显存利用率从 ~60% 提到 ~96%，等效装下更多并发请求
```

配合 **Continuous Batching（连续批处理）**：谁算完谁立刻退场、新请求随时插入，GPU 不空转：

```
   传统静态批: [req A====][req B==][req C======]  B/C 算完干等 A
   连续批处理: A 退场 → 立刻塞入 req D，时刻填满 GPU
```

vLLM 定位：**易用、高吞吐的开源推理服务首选**，OpenAI 兼容 API，部署快。

**TensorRT-LLM 的路线：把模型编译成极致优化的引擎**

NVIDIA 出品，走"**编译优化**"路线：算子融合、自动选 kernel、量化（INT8/FP8）、为特定 GPU 生成专用 engine。

```
   PyTorch 动态图 ──► 图优化/算子融合 ──► 量化 ──► GPU 专用 engine
   （灵活但慢）        （静态、可整图优化）      （延迟最低、最榨硬件）
```

定位：**追求极致延迟/吞吐、且锁定 N 卡**时的选择。代价是构建复杂、灵活性低、绑定硬件。

**llama.cpp 的路线**：CPU/边缘/消费端推理，GGUF 量化，让笔记本也能跑 LLM。定位：**端侧、低成本、无 GPU 场景**。

> 注：各引擎的具体编译参数、量化精度组合以官方文档为准；此处只讲稳定的机制差异。

## 7. 如何把它们组合成一条流水线

没有"一个框架打天下"，真实项目是**分阶段换框架**。以一个企业自研对话模型为例：

```
┌─────────────┬──────────────────────────────┬──────────────────────┐
│   阶段       │  目标                         │  框架组合             │
├─────────────┼──────────────────────────────┼──────────────────────┤
│ 1 预训练     │ 千卡训基座，省显存+切模型      │ PyTorch + Megatron    │
│              │                              │ + DeepSpeed(ZeRO)     │
│ 2 SFT 微调   │ 少卡教指令跟随                │ Transformers + PEFT   │
│              │                              │ (+Accelerate/DeepSpeed)│
│ 3 对齐       │ 对齐人类偏好                  │ TRL (DPO/PPO) + PEFT  │
│ 4 推理部署   │ 高吞吐低成本上线              │ vLLM 或 TensorRT-LLM  │
└─────────────┴──────────────────────────────┴──────────────────────┘
```

经典组合 **Megatron-DeepSpeed**（见 `megatron-deepspeed/`）：用 Megatron 的 TP/PP 切模型，用 DeepSpeed 的 ZeRO 切数据并行维度的状态——**两者正交、各管一个维度**，强强联合，是大厂训千亿模型的主流栈。

整条数据流：

```
  原始数据 ─►【Megatron+DeepSpeed 预训练】─► 基座模型
                                              │
  指令数据 ─►【Transformers+PEFT 微调】──────► SFT 模型
                                              │
  偏好数据 ─►【TRL 对齐】───────────────────► 对齐模型(权重)
                                              │
                       ┌──────────────────────┘
            【vLLM/TRT-LLM 加载权重 → 编译/优化 → 起服务】
                                              │
                                          线上 API
```

## 数值例子：一个 70B 模型从训练到上线的资源账

**前提**：70B 参数，Adam + fp16 混合精度，集群是 8 卡/机的 H100（80GB/卡）。

**(1) 全量预训练要多少卡？**
模型状态显存 $= 16 \times 70\times10^9 = 1120\text{GB}$。
即使忽略激活值，单看状态：$1120 / 80 \approx 14$ 张卡刚好放下状态——但激活值、通信缓冲、碎片还要更多。实践配置常用 **64~128 卡**，并行布局如 `DP=8 × PP=4 × TP=4 = 128 卡`：
- TP=4 在机内（NVLink），切每层算子；
- PP=4 跨机，按层切；
- DP=8 复制整套喂不同数据，每路再叠 ZeRO 切状态。

**(2) LoRA 微调要多少卡？**
冻结 70B 主权重（fp16 推理态 $\approx 2\times70=140\text{GB}$），只训 LoRA 小矩阵。140GB 用 2 张 H100（TP=2 或 ZeRO-3）即可放下推理态权重，可训参数 <1%，优化器状态显存可忽略。**结论：从"百卡"降到"个位数卡"，这就是 PEFT 的价值。**

**(3) 推理服务能扛多少并发？**
推理只存权重 + KV Cache。权重 fp16 $\approx 140\text{GB}$，占 2 张 H100。剩余显存全给 KV Cache。若每个请求平均缓存 2000 token，每 token 的 KV 约 0.3MB 量级，则单请求 $\approx 0.6\text{GB}$。
- 传统分配（利用率 ~60%）：可用 KV 显存被碎片吃掉，实际并发受限。
- vLLM PagedAttention（利用率 ~96%）：**等效多塞约 1.6 倍并发请求**，吞吐显著提升。

**手算小结**：同一个 70B 模型，**训练**视角看到的是"128 卡的并行布局"，**推理**视角看到的是"2 卡 + KV Cache 管理"。这正印证第 0 节——训练和推理是两套系统、两套框架。

## 对照表：同类框架怎么选

| 维度 | DeepSpeed | Megatron-LM |
|------|-----------|-------------|
| 核心思想 | 切"状态"(ZeRO) | 切"模型"(TP/PP) |
| 对代码侵入 | 小（包一层） | 大（改写算子） |
| 适合 | 中小团队、显存紧 | 超大模型、千卡集群 |

|------|-----------|----------|
| 可训参数 | <1% | 100% |
| 显存 | 极低（单卡可跑） | 极高（同预训练） |
| 效果 | 多数任务接近全量 | 上限略高 |
| 产物 | 小适配器(几十MB) | 整模型 |

|------|------|--------------|-----------|
| 路线 | PagedAttention 服务 | 编译优化引擎 | CPU/端侧量化 |

| 选它当 | 通用 GPU 服务首选 | 榨干 N 卡极致性能 | 无 GPU/边缘 |

## 常见问题

| 问题 | 解答 |
|------|------|
| 有了 DeepSpeed 为什么还要 Megatron？ | ZeRO 切的是"状态"，单层计算仍在一卡上。单层太大或要训千亿时，必须用 TP/PP 切"模型本身"。两者正交，常组合用。 |
| 训练框架能直接拿来做推理吗？ | 能跑但很差。推理无反向、要管 KV Cache、要连续批处理，PyTorch 裸跑吞吐远低于 vLLM/TRT-LLM。 |
| LoRA 微调会掉效果吗？ | 多数下游任务接近全量微调，上限略低。换来的是单卡可训、产物只有几十 MB、可多适配器切换。 |
| ZeRO-3 和张量并行有何不同？ | ZeRO-3 切参数但**每卡仍跑完整计算图**（临时 gather）；TP 把**单个算子的计算**也切开分给多卡。后者通信更频繁，只在机内用。 |
| 为什么推理要单独编译（TRT-LLM）？ | PyTorch 动态图每步重建、难整图优化。推理结构固定，可一次性编译成静态引擎，融合算子、量化、选最优 kernel，把延迟压到最低。 |
| 小团队最小可用栈是什么？ | Transformers + PEFT(LoRA/QLoRA) 单卡微调 → vLLM 起服务。无需碰 Megatron/DeepSpeed 的重型并行。 |
