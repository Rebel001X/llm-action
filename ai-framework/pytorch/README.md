## 0. 一句话锚点

**PyTorch = 一个会自动求导的、能在 GPU 上跑的「NumPy」，再加上把网络层、优化器、分布式训练打包好的工具箱。**

它的灵魂是两件事：

1. **动态计算图（define-by-run）**：你写一行 Python，它就执行一行、并顺手记录下来——图是「边运行边建」的，所以你能用 `print`、`if`、`for`、断点调试，像写普通 Python 一样写模型。
2. **自动微分（autograd）**：你只写前向（forward），框架自动帮你算反向（梯度）。这是训练神经网络最繁琐、最容易出错的部分，PyTorch 把它自动化了。

## 1. 地基/前置（它解决什么问题）

训练一个神经网络，本质是这个循环：

```
   ┌────────────────────────────────────────────────────┐
   │  1. 前向传播：输入 x → 模型 → 预测 ŷ               │
   │  2. 算损失：  loss = L(ŷ, y)   (预测离真值多远)     │
   │  3. 反向传播：∂loss/∂每个参数  (梯度，怎么调参数)   │
   │  4. 更新参数：参数 ← 参数 - 学习率 × 梯度          │
   │  5. 回到 1，直到 loss 足够小                         │
   └────────────────────────────────────────────────────┘
```

**没有框架时，第 3 步是噩梦。** 一个 10 层网络，手推每个参数的梯度（链式法则）既容易写错、又一改结构就得重推。同时还要：把矩阵乘法搬到 GPU 上、管理显存、多卡通信……

PyTorch 解决的就是这些「重复且易错」的工程：

| 痛点 | PyTorch 的回答 |
|------|----------------|
| 手算梯度 | autograd 自动反向 |
| CPU 算太慢 | Tensor 一行 `.cuda()` 上 GPU |
| 网络结构难复用 | `nn.Module` 把层/参数封装 |
| 单卡放不下大模型 | DDP / FSDP 分布式 |
| 训练太慢/吃显存 | AMP 混合精度 + torch.compile |

> 关键认知：**深度学习框架 ≈ 自动微分引擎 + GPU 张量库 + 神经网络/分布式工具箱**。后面每一节都在拆这三层。

## 2. Tensor 与 device：数据的最小单元

**Tensor（张量）= 多维数组**。标量是 0 维，向量 1 维，矩阵 2 维，一批图片 4 维 `[N, C, H, W]`。它和 NumPy 的 `ndarray` 几乎一样，但多了两个超能力：**能放到 GPU 上**、**能记录梯度**。

```
        Tensor 的关键属性
   ┌───────────────────────────────────────┐
   │ data      : 实际的数字 (一块连续内存)  │
   │ dtype     : float32 / bfloat16 / int64 │
   │ device    : cpu  /  cuda:0  /  cuda:1  │
   │ shape     : (例如 [32, 768])           │
   │ requires_grad : 是否要为它算梯度       │
   │ grad      : 反向后存放的梯度           │
   └───────────────────────────────────────┘
```

### device：CPU 和 GPU 是两块独立内存

GPU 有自己独立的显存（VRAM），和 CPU 内存（RAM）是物理隔离的。一个 Tensor 必须先「搬」到 GPU 才能用 GPU 算：

```
   CPU 内存 (RAM)                 GPU 显存 (VRAM)
   ┌──────────┐    .to('cuda')   ┌──────────┐
   │  tensor  │ ───── 拷贝 ────▶ │  tensor  │
   └──────────┘   (走 PCIe 总线)  └──────────┘

   规则：参与同一次运算的 tensor 必须在同一个 device 上，
        否则报错 "Expected all tensors to be on the same device"。
```

**为什么 device 这么重要？** 因为 CPU↔GPU 拷贝走 PCIe，带宽有限、延迟高，是常见性能杀手。原则：**数据尽量一次性搬上 GPU，整个训练过程留在 GPU 上算**，别频繁来回搬。

### contiguous / view：内存布局的坑

Tensor 底层是一块**连续一维内存** + 一组「步长（stride）」来解释成多维。`transpose`、`permute` 这类操作只改 stride、不真正搬数据（省时），但会让内存「不连续」，某些操作（如 `view`）就会报错，这时需要 `.contiguous()` 真正重排一次。理解这点能解释很多「莫名其妙」的报错。

## 3. 动态图 + autograd：反向传播怎么自动算

这是 PyTorch 最核心、也最该讲透的机制。

### 3.1 什么是计算图

当你对 `requires_grad=True` 的 tensor 做运算，PyTorch 会**偷偷记录一张图**：节点是张量，边是运算。看一个具体例子 $z = (x \cdot y) + y$：

```
   x ──┐
       ├──[ Mul ]── a ──┐
   y ──┘                 ├──[ Add ]── z
   y ────────────────────┘

   每个运算节点都记住了「怎么算它的反向」：
     Mul 的反向：da/dx = y,  da/dy = x
     Add 的反向：dz/da = 1,  dz/dy = 1
```

这张图是**前向执行时同步建好的**，所以叫「动态图 / define-by-run」。和静态图（先定义完整张图再喂数据，如老 TensorFlow 1.x）相比：动态图能用任意 Python 控制流（循环次数可变、条件分支），可以单步调试——这就是 PyTorch 易用性的根。

### 3.2 反向传播 = 沿图自动套链式法则

调用 `z.backward()` 时，autograd 从 `z` 出发**逆着图走一遍**，每经过一个节点就用它记住的「局部导数」按链式法则相乘累加，最终把 $\frac{\partial z}{\partial x}$ 存进 `x.grad`。

链式法则的本质：$\frac{\partial z}{\partial x} = \frac{\partial z}{\partial a}\cdot\frac{\partial a}{\partial x}$。对上例 $a = xy$，所以 $\frac{\partial z}{\partial x} = 1 \cdot y = y$。

```
   前向 (建图)                反向 (backward, 逆向遍历)
   x,y ──▶ Mul ──▶ Add ──▶ z      z.grad=1
                                    │  Add 反向: 把 1 传给两个输入
                                    ▼
                              a.grad=1,  y.grad += 1
                                    │  Mul 反向: da/dx=y, da/dy=x
                                    ▼
                              x.grad = y,  y.grad += x
```

注意 `y` 出现了两次，它的梯度是两条路径**累加**的——这正是为什么每次迭代前要 `optimizer.zero_grad()` 清零，否则梯度会跨 batch 累积。

### 3.3 三个必须理解的细节

- **`requires_grad`**：只有标了它的张量（典型是模型参数）才进图、才有梯度。输入数据通常不需要。
- **`with torch.no_grad()`**：推理/评估时关闭建图，省显存又提速（不用存反向所需的中间结果）。
- **计算图占显存**：反向需要前向的中间激活值（activation）。**模型越深、batch 越大，激活显存越多**——这是训练显存的大头之一，后面数值例子会算。`torch.utils.checkpoint`（梯度检查点）可以丢弃中间激活、反向时重算，用「时间换显存」。

## 4. nn.Module：把参数和计算打包成网络

`nn.Module` 是所有网络层/模型的基类。它干两件事：**自动登记参数（Parameter）** 和 **定义前向计算（forward）**。

```
   class MLP(nn.Module):
       def __init__(self):
           self.fc1 = nn.Linear(768, 3072)   # 自动登记 weight/bias
           self.fc2 = nn.Linear(3072, 768)
       def forward(self, x):                  # 只写前向！反向 autograd 包了
           return self.fc2(torch.relu(self.fc1(x)))

   Module 树形结构（嵌套）：
       MLP
        ├── fc1 (Linear)  →  weight[3072,768], bias[3072]
        └── fc2 (Linear)  →  weight[768,3072], bias[768]

   model.parameters()  → 递归吐出所有可训练参数 (喂给 optimizer)
   model.to('cuda')    → 递归把所有参数搬上 GPU
   model.state_dict()  → 递归导出参数字典 (存/加载 checkpoint)
```

「递归」是关键：你只管嵌套搭积木，`parameters()`/`to()`/`state_dict()` 会自动遍历整棵树。优化器拿到 `model.parameters()` 就知道要更新哪些张量。

## 5. 训练循环：把前面拼起来

最小但完整的训练闭环，每一行对应第 1 节的循环：

```
   for x, y in dataloader:
       x, y = x.cuda(), y.cuda()        # 数据上 GPU
       optimizer.zero_grad()            # ① 梯度清零 (不然会累加)
       y_hat = model(x)                 # ② 前向 (同时建图)
       loss  = criterion(y_hat, y)      # ③ 算损失
       loss.backward()                  # ④ 反向 (autograd 填 .grad)
       optimizer.step()                 # ⑤ 用梯度更新参数
```

```
   数据流与图的生命周期：
   ┌────────┐  forward   ┌──────┐  backward  ┌─────────┐  step
   │ 输入x  │ ─────────▶ │ 图+loss│ ────────▶ │ 各参数.grad│ ─────▶ 更新参数
   └────────┘ (建图,存激活)└──────┘(逆图填梯度)└─────────┘     ↑
        每个 iteration 图都重建一次（动态图），step 后图释放
```

## 6. 混合精度 AMP：用更低精度省显存、提速

### 6.1 为什么低精度有用

默认参数是 FP32（32 位浮点）。改用 16 位（FP16 或 BF16）有两个直接好处：

- **显存减半**：每个数 4 字节 → 2 字节。
- **算得更快**：现代 GPU 的 Tensor Core 对 16 位矩阵乘有数倍吞吐优势。

精度格式对比：

```
   FP32 : 1符号 + 8指数 + 23尾数  → 范围大、精度高 (基准)
   FP16 : 1符号 + 5指数 + 10尾数  → 范围小 (易上溢/下溢)、精度低
   BF16 : 1符号 + 8指数 +  7尾数  → 范围=FP32, 精度更低
                                     (大模型训练首选, 不易溢出)
```

### 6.2 混合精度：哪些算 FP16、哪些保 FP32

「混合」的意思是：**大头计算（矩阵乘、卷积）用 16 位提速，敏感部分（如 loss 累加、归一化、参数主副本）保留 FP32 保精度**。

```
   ┌──────────────┐  cast  ┌──────────────┐
   │ FP32 权重主本 │ ─────▶ │ FP16 权重副本 │──▶ 前向/反向 (快)
   └──────────────┘        └──────────────┘
          ▲                        │ FP16 梯度
          │   optimizer.step()     ▼
          └──────────── 用FP32主本更新 ◀── (回到FP32更新，避免精度丢失)
```

**FP16 的陷阱与 GradScaler**：FP16 表示的最小正数较大，小梯度会下溢成 0。解决办法是 **loss scaling**：反向前把 loss 乘一个大数（如 1024），梯度同比放大避免下溢，更新前再除回去。`torch.cuda.amp.GradScaler` 自动管理这个缩放因子。BF16 因为指数位和 FP32 一样多，范围大、基本不下溢，所以**用 BF16 通常不需要 GradScaler**——这也是大模型训练偏爱 BF16 的原因。

> 用法概念：`autocast` 上下文里自动选精度，`GradScaler` 管 FP16 的缩放。具体 API 以官方文档为准。

## 7. DDP 数据并行：多卡训练同一个模型

当**模型能放进单卡，但数据太多/想更快**时，用 DDP（DistributedDataParallel）。

**核心思想**：每张 GPU 放一份**完整模型副本**，各自喂不同的数据分片，各自算梯度，然后**所有卡把梯度平均**（这样等价于在大 batch 上训练一份模型）。

```
   GPU0          GPU1          GPU2          GPU3
   模型副本      模型副本      模型副本      模型副本
   数据片A       数据片B       数据片C       数据片D
     │             │             │             │
   各自前向+反向，得到各自的梯度 g0,g1,g2,g3
     │             │             │             │
     └─────────────┴──── All-Reduce ───┴─────────┘
              所有卡梯度求和再平均 → 每卡拿到相同的 ḡ
     │             │             │             │
   各自 optimizer.step() —— 因梯度相同，模型始终保持一致
```

**All-Reduce** 是关键通信原语：把所有卡的梯度求和并广播回每张卡。PyTorch 用 NCCL 库做高效的环状（ring）All-Reduce，且**和反向计算重叠**——某层梯度一算完就开始传，不必等整个反向结束，从而隐藏通信延迟。

DDP 的特点：实现简单、扩展性好；代价是**每张卡都存完整模型+优化器状态**，所以模型大小受单卡显存限制。

> 注意区分老的 `DataParallel`（单进程多线程、主卡瓶颈、已不推荐）和 `DistributedDataParallel`（多进程、每卡一进程、推荐）。

## 8. FSDP / 分片：模型大到单卡放不下怎么办

大模型训练，单卡连**一份**模型+优化器状态都放不下。DDP 在每张卡上的冗余副本就成了浪费。**FSDP（Fully Sharded Data Parallel）** 的思路：**把模型参数、梯度、优化器状态切片（shard）分散到各卡，谁也不存完整的**。

```
   DDP: 每卡存完整 (参数+梯度+优化器状态) ── 冗余 N 份
   ┌─────┐┌─────┐┌─────┐┌─────┐
   │ 全部 ││ 全部 ││ 全部 ││ 全部 │
   └─────┘└─────┘└─────┘└─────┘

   FSDP: 每卡只存 1/N 分片 ── 显存 ≈ DDP 的 1/N
   ┌─────┐┌─────┐┌─────┐┌─────┐
   │ 1/4 ││ 1/4 ││ 1/4 ││ 1/4 │
   └─────┘└─────┘└─────┘└─────┘
```

**那计算时怎么办？** 用到某层时，临时把该层参数**All-Gather**回完整形态算前向/反向，算完立刻丢弃分片以外的部分：

```
   计算第 L 层时：
   ① All-Gather: 各卡凑出第 L 层完整参数 ─▶ 前向计算
   ② 用完立即释放非本卡分片 (省显存)
   ③ 反向同理 All-Gather 一次，算完 Reduce-Scatter 把梯度切回各卡

   用「多一点通信」换「少很多显存」。
```

这和 DeepSpeed 的 **ZeRO（零冗余优化器）** 是同一套思想，分三级：
- **ZeRO-1**：切优化器状态（如 Adam 的动量/方差）；
- **ZeRO-2**：再切梯度；
- **ZeRO-3**：再切参数（≈ FSDP）。
切得越多越省显存，但通信越多。详见 [[ai-framework/deepspeed/README]]。

**选型直觉**：模型放得下单卡 → DDP；放不下 → FSDP / ZeRO；超大模型还要叠加张量并行、流水线并行（见 [[llm-train/README]]）。

## 9. torch.compile：eager 慢在哪、编译怎么救

### 9.1 eager 模式的代价

PyTorch 默认是 **eager 模式**：一行 Python 执行一个算子（op），立刻返回结果。好处是直观可调试，坏处是：

- **Python 解释器开销**：每个 op 都要过一遍 Python，小算子尤其亏；
- **无法跨 op 优化**：比如 `a+b` 再 `*c`，本可融合成一个 GPU kernel 少读写一次显存，但 eager 一个个执行就做不到；
- **频繁 kernel 启动**：每个 op 启一次 GPU kernel，启动开销累积。

### 9.2 torch.compile 做了什么

`torch.compile`（PyTorch 2.x 的核心特性）在**几乎不改你代码**的前提下，把模型 JIT 编译成更快的形式。流水线：

```
   你的 Python 模型
        │
   ┌────▼─────┐  TorchDynamo: 从 Python 字节码"抓"出计算图
   │ Dynamo   │  (graph capture, 遇到不支持的就 graph break 回退 eager)
   └────┬─────┘
        │  FX Graph (一张算子图)
   ┌────▼─────┐  AOTAutograd: 同时生成前向+反向图
   │ AOTAutograd
   └────┬─────┘
        │
   ┌────▼─────┐  Inductor: 把图编译成高效 kernel
   │ Inductor │  - 算子融合 (fusion，少读写显存)
   └────┬─────┘  - 生成 Triton(GPU)/C++(CPU) 代码
        │
   编译好的快速可执行体  ← 之后每次调用直接跑它
```

核心收益来自两点：**算子融合**（多个小 op 合成一个 kernel，减少显存往返和 kernel 启动）和**生成专用 kernel**（用 Triton 等生成针对你形状的高效代码）。

### 9.3 关键权衡

- **首次编译有开销**：第一次（或输入形状变化触发重编译）会慢，之后变快。所以适合训练/长时间推理，不适合一次性脚本。
- **graph break**：遇到 Dynamo 不支持的 Python（复杂控制流、某些第三方调用）会「断图」回退 eager，断点越多收益越小。调试时要尽量减少 graph break。
- **动态形状**：序列长度变化大时可能反复重编译，需用动态形状支持。

> 相关的 **CUDA Graphs** 是更底层的技术：把一串 GPU kernel 的「启动序列」录制成一张图，重放时一次性提交，消除 CPU 端逐个启动 kernel 的开销，对大量小 kernel 的场景提速明显。torch.compile 可与之配合。具体开关以官方文档为准。

## 数值例子 / 典型场景

### 例 1：训练显存到底花在哪（手算）

设一个模型有 $P = 70$ 亿参数（7B），用 BF16 训练 + Adam 优化器。各部分显存（字节）：

| 部分 | 公式 | 计算（P=7e9） |
|------|------|---------------|
| 参数（BF16） | $2P$ | $2 \times 7\text{e}9 = 14\,\text{GB}$ |
| 梯度（BF16） | $2P$ | $14\,\text{GB}$ |
| Adam 动量 m（FP32） | $4P$ | $28\,\text{GB}$ |
| Adam 方差 v（FP32） | $4P$ | $28\,\text{GB}$ |
| 参数 FP32 主本 | $4P$ | $28\,\text{GB}$ |
| **小计（不含激活）** | $16P$ | **≈ 112 GB** |

结论：光是「参数 + 梯度 + 优化器状态」就要 $16P \approx 112$ GB，远超单张 80GB 卡。**所以 7B 以上模型训练几乎必须 FSDP/ZeRO 分片。** 若用 ZeRO-3 切到 8 卡，每卡只剩 $112/8 = 14$ GB 这部分，单卡才放得下（再留余量给激活）。

激活显存另算，正比于 $batch \times 序列长 \times 层数 \times 隐藏维$，大 batch 时常成主要瓶颈——这正是梯度检查点（用算力换显存）的用武之地。

### 例 2：DDP 的通信量（手算）

7B 模型用 DDP，每个 iteration 要 All-Reduce 一次梯度。梯度大小 = $2P = 14$ GB（BF16）。Ring All-Reduce 每卡收发的数据量约 $2 \times \frac{N-1}{N} \times 数据量$，8 卡时约 $2 \times \frac{7}{8} \times 14 \approx 24.5$ GB 跨网络传输/卡/步。

直觉：**通信量正比于模型大小、与卡数关系不大**。所以模型越大，机间带宽（如 NVLink/InfiniBand）越关键；带宽不足时，把通信和反向计算重叠（DDP 默认做）就非常重要。

### 例 3：AMP 提速的来源

把矩阵乘从 FP32 换 BF16，Tensor Core 吞吐常有 2~8 倍（视硬件）。同时激活显存减半，意味着同样显存能放更大 batch → GPU 利用率更高 → 进一步提速。这就是「AMP 几乎是大模型训练标配」的原因。

## 对照表（与同类对比）

| 维度 | PyTorch | TensorFlow 1.x | TensorFlow 2 / Keras | JAX |
|------|---------|----------------|----------------------|-----|
| 计算图 | 动态(define-by-run) | 静态(先定义后跑) | 默认动态+可 `@tf.function` | 函数式+`jit` 编译 |
| 调试 | 像普通 Python，最易 | 难(图与执行分离) | 较好 | 函数纯度约束，中等 |
| 上手难度 | 低 | 高 | 中 | 中高(函数式思维) |
| 编译加速 | torch.compile | 天生静态图 | tf.function/XLA | XLA(默认强) |
| 分布式 | DDP/FSDP 生态成熟 | 较繁琐 | 改善 | pmap/sharding |
| 科研主流 | ★ 绝对主流 | 已淘汰 | 工业仍有 | 增长中(尤数值/RL) |
| 大模型生态 | ★ HuggingFace/DeepSpeed 全围绕它 | 弱 | 弱 | 中(部分实验室) |

**为什么 PyTorch 成为主流？**
1. **动态图 = 极致易用**：能用纯 Python 写、能断点调试，科研迭代快——研究者先用它，论文代码就都是它，形成正反馈。
2. **生态壁垒**：HuggingFace Transformers、DeepSpeed、Megatron、vLLM 等几乎都以 PyTorch 为底座，模型/工具/教程海量。
3. **补齐了性能短板**：早年被批「动态图慢」，torch.compile + AMP + FSDP 之后，易用和性能兼得，工业界也大规模采用。
4. **公司投入**：背后有持续的工程投入与活跃社区。

## 常见问题

| 问题 | 答案 |
|------|------|
| 动态图和静态图差别？ | 动态图边运行边建、可调试可变控制流；静态图先编译后执行、利于优化但难调试。PyTorch 走动态图，再用 torch.compile 补编译收益。 |
| 为什么每步要 `zero_grad()`？ | autograd 默认把梯度**累加**进 `.grad`，不清零会跨 batch 叠加。(有意做梯度累积时则故意不清零。) |
| `.to('cuda')` 后原 tensor 变了吗？ | 对 tensor 是返回**新**的 GPU tensor（需接收返回值）；对 `nn.Module` 是**原地**搬移。 |
| FP16 和 BF16 选哪个？ | 大模型训练优先 BF16(范围大、通常免 GradScaler)；老硬件不支持 BF16 时用 FP16+GradScaler。 |
| DDP 和 FSDP 怎么选？ | 模型放得下单卡用 DDP(简单)；放不下用 FSDP/ZeRO(切片省显存，多点通信)。 |
| torch.compile 一定更快吗？ | 不一定。有编译开销和 graph break；适合稳定形状的长时间训练/推理，一次性小脚本可能不划算。 |
| 推理时要注意什么？ | 用 `model.eval()` + `torch.no_grad()`(或 `inference_mode`)，关掉建图与 dropout/BN 更新，省显存提速。 |
| 显存 OOM 怎么救？ | 减小 batch、开 AMP、开梯度检查点、用 FSDP/ZeRO 分片、清理未释放引用、`empty_cache`。 |
