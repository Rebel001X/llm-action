## 0. 一句话锚点

**DeepSpeed 不要求你重写模型，它只「接管」你的训练循环。** 你把 `model / optimizer / 训练数据` 交给 `deepspeed.initialize`，它还回一个 `model_engine`；之后把 `loss.backward()` / `optimizer.step()` 换成 `model_engine.backward(loss)` / `model_engine.step()`，混合精度、梯度同步、ZeRO 切分、学习率调度全部在引擎内部自动发生。**改动只有「三步、不到十行」。**

## 1. 地基：从 DDP 到 DeepSpeed 改了什么

先看原生 PyTorch DDP 训练循环的样子，再看 DeepSpeed 把哪几处「钉子」拔掉了：

```
原生 PyTorch DDP                       DeepSpeed
────────────────────────────         ─────────────────────────────────────
model = DDP(model)              ──►   model_engine, optimizer, _, _ =
optimizer = Adam(...)                     deepspeed.initialize(
                                              args=cmd_args,
                                              model=model,
                                              model_parameters=params)
─────────────────────────────         ─────────────────────────────────────
for batch in loader:                  for batch in loader:
    loss = model(batch)         ──►       loss = model_engine(batch)   # forward
    loss.backward()             ──►       model_engine.backward(loss)  # 含梯度平均
    optimizer.step()            ──►       model_engine.step()          # 含 LR/缩放
    optimizer.zero_grad()       ──►       （step 内部已处理，无需手动 zero_grad）
```

**为什么这样设计？** DDP 只解决「梯度 all-reduce 同步」一件事，参数/梯度/优化器状态仍然每卡各存一份（冗余）。DeepSpeed 的引擎接管这三个动作后，才有机会在 `backward`/`step` 内部插入 **ZeRO 切分**（每卡只存 $1/N$ 片）、**FP16 loss scaling**、**梯度累积** 等逻辑——这些都必须由「拥有训练循环控制权」的一方来做，所以 API 必须从 `model`/`optimizer` 换成 `model_engine`。

## 2. 第一步：初始化 DeepSpeed 引擎

> 通过简单三步将 PyTorch DDP 模型训练改造为 DeepSpeed DP 模型训练。第一步是**初始化 DeepSpeed 引擎**：

```python
model_engine, optimizer, _, _ = deepspeed.initialize(args=cmd_args,
                                                     model=model,
                                                     model_parameters=params)
```

`deepspeed.initialize` 确保在底层适当地完成了所需的分布式数据并行或混合精度训练所需的所有设置。

**返回值四元组拆原子**（按位置返回）：

```
model_engine, optimizer, training_dataloader, lr_scheduler = deepspeed.initialize(...)
     │              │             │                  │
  包装后的引擎    被引擎托管     若传了 dataset      若在 config 里
  替代原 model    的优化器       会还回 loader       配了 scheduler
```

原文示例只接了前两个、后两个用 `_` 丢弃，因为这里没有把 dataloader / scheduler 交给引擎托管。

```
deepspeed.initialize 内部一次性帮你做的事：
  ┌─ 解析 ds_config.json（ZeRO 阶段、FP16、optimizer、scheduler…）
  ├─ 必要时自动 init_distributed（见 §3）
  ├─ 用 DeepSpeedEngine 包住 model
  ├─ 按 ZeRO 阶段切分 优化器状态 / 梯度 / 参数
  └─ 挂好 FP16/BF16 混合精度的 loss scaler
```

**为什么要传 `args=cmd_args`？** DeepSpeed 的命令行启动器会注入 `--local_rank`、`--deepspeed_config` 等参数，`args` 让引擎读到「配置文件路径」与「本进程在本机的卡号」。

## 3. 第二步：初始化分布式环境

> 第二步是**初始化分布式环境**：

```python
deepspeed.init_distributed()
```

**关键结论：通常不用手动调。** DeepSpeed 将在其初始化期间自动初始化分布式环境，因此可以不使用此函数。

```
什么时候需要手动调 deepspeed.init_distributed()？
──────────────────────────────────────────────
在 deepspeed.initialize(...) 之前，你就需要 torch.distributed：
  · 模型并行 / 流水线并行的提前布置
  · 手动建 ProcessGroup、提前做 broadcast 等
此时把 torch.distributed.init_process_group(..)
   替换为 ──► deepspeed.init_distributed()
否则：什么都不用做，initialize 自动搞定。
```

## 4. 第三步：模型训练（三件套 API）

> 使用三个简单的 API 来进行前向传播（callable object）、反向传播（backward）和权重更新（step）来训练模型。

```python
for step, batch in enumerate(data_loader):
    #forward() method
    loss = model_engine(batch)

    #runs backpropagation
    model_engine.backward(loss)

    #weight update
    model_engine.step()
```

三件套各自在「省显存/分布式」语义下做了原生 PyTorch 没做的事：

| API | 表面动作 | 引擎内部额外做的事（原文要点） |
| --- | --- | --- |
| `model_engine(batch)` | 前向，返回 loss | 走混合精度路径，激活值可按配置做重计算 |
| `model_engine.backward(loss)` | 反向传播 | **Gradient Averaging**：训完一个 `train_batch_size` 后，梯度在数据并行进程间平均；**Loss Scaling**：FP16/混合精度下自动缩放 loss 防止梯度精度损失 |
| `model_engine.step()` | 更新权重 | 触发 ZeRO 的优化器更新；若用 DeepSpeed 的 LR 调度器，会在每次 step 调用其 `step()` |

**逐项拆原子（原文真料）：**

- **Gradient Averaging（梯度平均）**：在分布式数据并行训练中，`backward` 确保在对一个 `train_batch_size` 进行训练后，梯度在数据并行进程间进行平均。
- **Loss Scaling（损失缩放）**：在 FP16/混合精度训练中，DeepSpeed 引擎会自动处理缩放损失，以避免梯度中的精度损失。

```
为什么 FP16 要 Loss Scaling？（数值直觉）
FP16 能表示的最小正规数 ≈ 6e-5。深层网络里很多梯度 |g| ~ 1e-7，
直接转 FP16 会下溢成 0（梯度消失）。
做法：loss × S（如 S=1024 ≈ 2^10）── backward ──► 梯度同样 ×S 被「抬」进可表示区
       step 前再 ÷S 还原。
       若某步出现 inf/NaN（S 太大）── 跳过该步 + 自动减半 S（动态缩放）。
```

- **Learning Rate Scheduler（学习率调度器）**：当使用 DeepSpeed 的学习率调度器（在 `ds_config.json` 文件中指定）时，DeepSpeed 会在每次训练步骤（执行 `model_engine.step()` 时）调用调度器的 `step()` 方法。当不使用 DeepSpeed 的学习率调度器时：
  - 如果调度期望在**每次训练步骤**都执行，那么用户可以在初始化 DeepSpeed 引擎时将调度器传递给 `deepspeed.initialize`，让 DeepSpeed 进行管理、更新或保存/恢复。
  - 如果调度应该在**任何其它间隔**（例如训练周期 epoch）执行，则用户在初始化期间不应将调度传递给 DeepSpeed，必须显式地管理它。

```
LR 调度由谁 step() ？决策树
  ┌ 在 ds_config.json 里配了 scheduler  ─► 每次 model_engine.step() 引擎自动调
  ├ 没配，但希望「每步」更新           ─► 传给 deepspeed.initialize，交引擎托管
  └ 希望「每 epoch」等其它间隔更新     ─► 别传给引擎，你自己手动 scheduler.step()
```

## 5. 多节点环境变量

> 当在多个节点上进行训练时，我们发现支持传播用户定义的环境变量非常有用。

默认情况下，DeepSpeed 将传播所有设置的 **NCCL 和 PYTHON 相关**环境变量。如果你想传播**其它**变量，可以在名为 `.deepspeed_env` 的文件中指定它们，该文件包含一个行分隔的 `VAR=VAL` 条目列表。DeepSpeed 启动器将查找你执行的本地路径以及你的主目录（`~/`）。

一个具体例子：有些集群需要在训练之前设置特殊的 NCCL 变量。用户可以简单地将这些变量添加到其主目录中的 `.deepspeed_env` 文件中：

```bash
# ~/.deepspeed_env
NCCL_IB_DISABLE=1
NCCL_SOCKET_IFNAME=eth0
```

DeepSpeed 然后会确保在启动每个进程时，在整个训练工作的每个节点上设置这些环境变量。

```
为什么需要 .deepspeed_env？（机制图）
        节点A (launcher)                节点B / 节点C ...
   ┌──────────────────┐  ssh 拉起进程  ┌──────────────────┐
   │ 你 export 的变量  │ ──不一定带过去──►│ 远端 shell 干净   │
   └──────────────────┘                └──────────────────┘
   解法：把变量写进 ~/.deepspeed_env
        DeepSpeed 在每个节点拉起每个进程时统一注入这些 VAR=VAL
  典型坑：IB 网卡环境关 InfiniBand → NCCL_IB_DISABLE=1
         多网卡选错网口卡死 → NCCL_SOCKET_IFNAME=eth0 指定走哪块网卡
```

相关底层概念见 [[ai-infra/网络/集合通信原语]] 与 [[ai-infra/网络/InfiniBand]]。

## 6. 兼容 MPI

如上所述，DeepSpeed 提供了自己的并行启动器来帮助启动多节点/多 GPU 训练作业。如果你喜欢使用 MPI（例如 `mpirun`）启动训练作业，则 DeepSpeed 提供对此的支持。

**需要注意的是，DeepSpeed 仍将使用 torch 分布式 NCCL 后端，而不是 MPI 后端。** MPI 只当「启动器/进程发现」用，真正的张量通信还是走 NCCL。

要使用 `mpirun` + DeepSpeed（使用 mpirun 作为启动器后端）启动训练作业，你只需要安装 `mpi4py` Python 包：

```bash
pip install mpi4py
```

DeepSpeed 将使用它来发现 MPI 环境，并将必要的状态（例如 world size、rank 等）传递给 torch 分布式后端。

如果你正在使用模型并行、流水线并行，或者在调用 `deepspeed.initialize(..)` 之前需要使用 `torch.distributed` 调用，DeepSpeed 为你提供了额外的 API 调用以支持相同的 MPI。请将你的初始 `torch.distributed.init_process_group(..)` 调用替换为：

```python
deepspeed.init_distributed()
```

```
启动器后端选择：
  deepspeed 启动器 ─┐
                    ├─► 都把 (world_size, rank, local_rank) 喂给 ──► torch.distributed(NCCL)
  mpirun + mpi4py ─┘                                                  ▲
                                                          真正的 all-reduce 仍走 NCCL
```

## 7. 资源配置（单节点）

如果我们只在单个节点上运行（具有一个或多个 GPU），DeepSpeed 不需要使用 hostfile。如果没有检测到或传递 hostfile，则 DeepSpeed 将查询本地计算机上的 GPU 数量来发现可用的插槽数。`--include` 和 `--exclude` 参数与正常工作相同，但用户应将 **"localhost"** 指定为主机名。

**另外需要注意：`CUDA_VISIBLE_DEVICES` 不能用于 DeepSpeed 来控制应该使用哪些设备。**

例如，要仅使用当前节点的 gpu1，请执行以下操作：

```bash
deepspeed --include localhost:1 ...
```

```
单机选卡：为什么用 --include 而不是 CUDA_VISIBLE_DEVICES ？
  DeepSpeed 启动器自己决定要拉起几个进程、各进程绑哪张卡，
  它在拉进程前读 --include/--exclude，而不是读 CUDA_VISIBLE_DEVICES。
  → 用 env 掩盖卡，启动器看到的拓扑和实际不一致，会错配。
  正确姿势：
    deepspeed --include localhost:1 ...      # 只用本机 gpu1
    deepspeed --include localhost:0,2 ...    # 只用本机 gpu0、gpu2
    deepspeed --exclude localhost:3 ...      # 用本机除 gpu3 外的所有卡
  语法：主机名:卡号  ；单机时主机名固定写 localhost
```

## 8. 实操：端到端最小模板（把原文真料编排起来）

把上面三步合成一个可运行骨架（注释标出每行对应的原文要点）：

```python
import deepspeed

# —— 第二步（通常可省略，initialize 会自动做）——
# deepspeed.init_distributed()   # 仅当 initialize 之前就要用 torch.distributed 才需要

# —— 第一步：初始化引擎 ——
model_engine, optimizer, _, _ = deepspeed.initialize(
    args=cmd_args,                 # 含 --local_rank / --deepspeed_config
    model=model,
    model_parameters=params)

# —— 第三步：训练三件套 ——
for step, batch in enumerate(data_loader):
    loss = model_engine(batch)     # forward
    model_engine.backward(loss)    # 反向 + 梯度平均 + FP16 loss scaling
    model_engine.step()            # 更新权重 + 触发 LR scheduler.step()
```

启动方式（单机 / 选卡）：

```bash
# 单机用全部可见 GPU
deepspeed train.py --deepspeed --deepspeed_config ds_config.json

# 单机只用 gpu1
deepspeed --include localhost:1 train.py --deepspeed --deepspeed_config ds_config.json
```

> 配置文件 `ds_config.json`（ZeRO 阶段、FP16、optimizer、scheduler）的字段详解见同目录 [[ai-framework/deepspeed/README]]；ZeRO 显存账与选型同样在 README。

## 常见问题 / 坑

| 现象 / 疑问 | 根因 | 处置 |
| --- | --- | --- |
| 设了 `CUDA_VISIBLE_DEVICES` 但选卡不生效 / 错配 | DeepSpeed 启动器不读该变量来选卡 | 改用 `deepspeed --include localhost:卡号` |
| 多节点远端进程缺自定义环境变量 | 启动器默认只传播 NCCL/PYTHON 相关变量 | 把 `VAR=VAL` 写进 `~/.deepspeed_env`（每行一条） |
| IB 集群 NCCL 卡死 / 多网卡选错网口 | 未指定 IB / socket 网卡 | `.deepspeed_env` 写 `NCCL_IB_DISABLE=1`、`NCCL_SOCKET_IFNAME=eth0` |
| 重复手动 `init_process_group` 报错 | `initialize` 已自动初始化分布式 | 删掉手动调用；确需提前用就换 `deepspeed.init_distributed()` |
| FP16 训练 loss 变 NaN | loss scale 太大致梯度 inf | 引擎动态缩放会自动跳步并减半 S，无需手动；持续 NaN 检查数据/LR |
| 用了 `mpirun` 但以为通信走 MPI | DeepSpeed 仅用 MPI 发现环境 | 通信仍走 torch NCCL 后端；需装 `mpi4py` |
| 学习率不按预期变化 | LR scheduler 归属不清 | 每步更新→配进 ds_config 或传给 initialize；按 epoch→自己手动 `scheduler.step()` |
| 忘了 `optimizer.zero_grad()` | 误以为和原生 PyTorch 一样 | `model_engine.step()` 内部已处理，不需手动 zero_grad |
