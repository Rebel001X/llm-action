## 0. 一句话锚点

**PAI-TorchAcc = "GraphCapture 把 PyTorch 动态图转成静态图" + "在静态图上做编译优化和分布式优化"。** 它追求的是:**你几乎不改训练代码**(理想情况下只在模型/训练循环外面包一层),就能拿到接近"手工优化静态图"的训练吞吐。

它属于 **编译型训练加速器** 这一类工具,和 `torch.compile`、XLA、TensorRT(推理侧)是同一思想脉络:**先拿到完整计算图,再在图上做全局优化**,而不是逐个 Python 算子地解释执行。

## 1. 地基:它到底解决什么问题

要理解 TorchAcc,先理解 PyTorch 原生"动态图(eager 模式)"的代价。

### 1.1 动态图(eager)的执行模型

PyTorch 默认是 **define-by-run**:你每写一行 `y = torch.matmul(a, b)`,Python 解释器**立刻**把这个算子派发(dispatch)到底层 kernel 执行。好处是灵活、好调试(可以随时 print、加 if);代价是:

```
Python 逐行解释执行(eager):
┌──────────────────────────────────────────────┐
│ for each op in 训练 step:                      │
│   Python 解释 → dispatch → 申请显存 → launch    │
│   kernel → 等结果 → 回到 Python → 下一行         │
└──────────────────────────────────────────────┘
   ▲ 每个算子都要过一遍 Python + dispatch 开销
   ▲ 看不到"全局",无法跨算子做优化
```

带来三类开销:

| 开销 | 来源 | 后果 |
|------|------|------|
| **解释器/派发开销** | 每个算子都要走 Python + ATen dispatch | 小算子多时,GPU 经常空等(launch-bound) |
| **缺少全局视野** | 编译器一次只看到一个算子 | 无法做算子融合、无法全局调度内存 |
| **内存反复申请/释放** | 中间张量逐个分配 | 显存峰值高、碎片多 |

当模型很大、算子很碎(比如 Transformer 里大量 elementwise + reshape)时,**GPU 利用率被 Python 拖累**,这就是加速的空间所在。

### 1.2 静态图(graph)的思路

如果能**先把整个 step 的计算图拿到手**(一张 DAG:节点是算子,边是张量),再交给编译器,就能做 eager 模式做不到的事:

- **算子融合**:把 `add → mul → relu` 融成一个 kernel,少几次 kernel launch、少几次显存读写。
- **内存复用**:全局看到生命周期,提前规划哪块显存可以重用。
- **通信/计算重叠**:在图上识别梯度通信,可与后续计算并行。

代价是:**静态图不灵活**(图固定后,改 shape/改控制流就要重来)。**TorchAcc 的核心价值,就是用 GraphCapture 自动完成"动态图→静态图"这一步,让你既写动态图的代码,又享静态图的性能。**

## 2. 整体架构:四层

可以把 TorchAcc 想成一条"从 PyTorch 代码到优化后可执行图"的流水线:

```
        PyTorch 训练代码(几乎不改)
                  │  你只是在外面包一层
                  ▼
┌─────────────────────────────────────────────┐
│ ① 前端:GraphCapture                          │
│   拦截/追踪算子,记录成中间表示(IR)            │
│   动态图 ──tracing/lazy──▶ 计算图 DAG          │
└─────────────────────────────────────────────┘
                  │  IR(计算图)
                  ▼
┌─────────────────────────────────────────────┐
│ ② 计算优化:图编译器                           │
│   算子融合 / 常量折叠 / 内存规划 / 布局优化     │
└─────────────────────────────────────────────┘
                  │  优化后的图
                  ▼
┌─────────────────────────────────────────────┐
│ ③ 分布式优化                                  │
│   切分 / 通信插入 / 通信-计算重叠 / 梯度聚合     │
└─────────────────────────────────────────────┘
                  │  可执行计划
                  ▼
┌─────────────────────────────────────────────┐
│ ④ 后端执行:编译为目标 kernel 并运行           │
│   (底层常借助 XLA / 编译器后端,具体以官方为准) │
└─────────────────────────────────────────────┘
                  │
                  ▼
            GPU/加速卡 高效执行
```

四层各自的职责:

1. **前端 GraphCapture**:这是 TorchAcc 的招牌。负责把"你随便写的 PyTorch 代码"捕获成一张静态可优化的图。
2. **计算优化**:在图上做与硬件无关 + 与硬件相关的优化(融合、内存、布局)。
3. **分布式优化**:把单卡的图扩展成多卡协同的图,自动安排通信。
4. **后端执行**:把优化后的图下沉到真正的编译器/运行时去生成 kernel。业界这类框架后端常对接 **XLA** 这样的图编译器,但**具体后端实现以官方文档为准**。

## 3. GraphCapture:动态图怎么变成静态图

这是全文最该讲透的一节。把"动态→静态"拆成原子步骤。

### 3.1 核心难点

PyTorch 是 define-by-run,**图在运行时才存在,运行完就没了**。要拿到图,必须在"运行"和"真正执行 kernel"之间插一层,把算子**记录下来而不是立刻算**。常见两种技术路线(TorchAcc 这类框架会综合使用,**具体以源码为准**):

```
技术路线对比:
                能否拿到完整图     处理控制流(if/for)
 ① Tracing      ✅ 跟着跑一遍记录   ❌ 只记录"走过的那条路"
 ② Lazy Tensor  ✅ 延迟执行成图     ⚠️ 需要"守卫"判断图是否复用
```

### 3.2 Lazy Tensor 式捕获(理解机制)

直觉:把张量从"立刻算"改成"记一笔账,攒够了再一起算"。

```
eager:    a+b ─立刻算→ t1 ;  t1*c ─立刻算→ t2  (两次 launch)

lazy:     a+b ─记账→ [add]
          t1*c ─记账→ [add → mul]   ← 攒成图,没真算
          遇到"必须要结果"(如 .item()/打印/到达 step 末) → 触发编译+执行
                         ▼
                 编译器拿到 [add→mul] 整张图 → 融合成 1 个 kernel → 执行
```

关键概念:

- **图边界(graph boundary)**:什么时候"结账"。通常是一个训练 step 的边界,或遇到必须落地的操作(取标量、依赖数据走向的控制流)。边界划得好,图就大、优化空间就大。
- **守卫 / 缓存(guard & cache)**:同一段代码第二次跑时,如果输入 shape、dtype 等"签名"没变,就**直接复用上次编译好的图**,不必重新编译。签名一变就**重编译**(recompile)——这正是性能坑的来源(见坑表)。

### 3.3 为什么"第一步慢、后面快"

```
step 0:  捕获图 → 编译(融合/排内存/生 kernel)  ← 编译开销大,这一步慢
step 1:  shape 没变 → 命中缓存 → 直接执行编译好的图  ← 快
step 2:  同上,快
...
step k:  某个 batch 的 seq_len 变了 → 守卫失效 → 重新编译  ← 又慢一下
```

所以编译型加速器都有"**预热(warmup)**"现象:头几个 step 在编译,稳定后才到峰值吞吐。评测吞吐时**一定要跳过预热 step**,否则数字会被严重低估。

## 4. 计算优化:图到手后做了什么

拿到静态图后,编译器在图上做一系列变换(都是"经典编译优化"思想):

| 优化 | 它做什么 | 为什么有用 |
|------|---------|-----------|
| **算子融合(fusion)** | 把多个相邻小算子合成一个 kernel | 减少 kernel launch 次数 + 减少中间张量进出显存(省带宽) |
| **常量折叠** | 编译期能算的就先算好 | 运行时少算 |
| **内存规划/复用** | 全局分析张量生命周期,复用显存块 | 降显存峰值、减碎片,可上更大 batch |
| **布局/精度优化** | 选对张量内存布局、配合混合精度 | 让底层 kernel 跑在最优路径 |
| **死代码消除** | 删掉对输出无贡献的节点 | 少算 |

**融合的直觉数值例子**:假设 LayerNorm 后接 GELU,eager 下是两个 kernel,中间结果(设大小 $N$ 个元素,fp16 即 $2N$ 字节)要写回显存再读出,来回 $4N$ 字节带宽;融合后中间结果留在寄存器/共享内存,**省掉这 $4N$ 字节往返**。当这类小算子成百上千个时,省下的显存带宽很可观——而很多 Transformer 训练恰恰是 **memory/launch-bound** 的。

## 5. 分布式优化:从单卡图到多卡图

大模型训练一定是多卡的。TorchAcc 在图层面做分布式,而不是让用户手工写通信。

### 5.1 数据并行 + 通信计算重叠(核心收益点)

数据并行下,每张卡跑同一个图、不同数据,反向算完梯度后要做 **AllReduce** 把各卡梯度求平均。朴素做法是"等所有梯度算完再一次性通信",GPU 会空等通信:

```
朴素(串行):
  反向计算 ███████████████  然后  通信 ░░░░░░░░  (GPU 空等通信)

重叠优化(图层面识别依赖后自动安排):
  反向计算 ███████████████
  通信        ░░░░  ░░░░  ░░░░   ← 算完一层梯度就开始通信,与后续层计算并行
                                  通信被"藏"在计算后面
```

因为 TorchAcc 在**图**上能看到"哪个梯度先算好、哪个通信不依赖后面的计算",所以能自动把 AllReduce 拆开、提前发起,与反向计算重叠,**把通信时间藏起来**。底层集合通信通常走 **NCCL**(参考 [[ai-infra/网络/NCCL]])。

### 5.2 与并行策略的关系

数据并行只是基础。更大的模型还需要张量并行、流水线并行、ZeRO 式优化器状态切分(这是 DeepSpeed 的强项,见 [[ai-framework/deepspeed/README]])。TorchAcc 的定位是**编译加速层**,它与这些并行框架是**互补**关系:并行框架负责"怎么把模型切到多卡",TorchAcc 负责"切完之后每张卡的图怎么跑得更快、通信怎么重叠"。**具体支持哪些并行、如何组合,以官方文档为准。**

## 6. 与同类工具对比(定位差异)

| 工具 | 类别 | 核心做法 | 与 TorchAcc 的关系 |
|------|------|---------|-------------------|
| **PAI-TorchAcc** | 训练编译加速 | GraphCapture→静态图→图优化+分布式优化 | 本文主角 |
| **torch.compile** | 训练编译加速(PyTorch 官方) | TorchDynamo 抓图 + Inductor 生成 kernel | 同思想脉络;TorchAcc 是 PAI 自研,深度结合阿里云环境与后端 |
| **XLA / PyTorch-XLA** | 图编译器后端 | 把图编译为 XLA HLO 再生成 kernel | TorchAcc 这类框架常以 XLA 为后端之一(以官方为准) |
| **DeepSpeed** | 分布式/显存优化 | ZeRO、卸载、并行 | 关注"怎么放下/切分大模型",与编译加速互补 |
| **Megatron-LM** | 大模型并行训练 | 张量/流水线并行 | 关注并行切分,可与编译加速叠加 |
| **TensorRT** | 推理优化 | 图优化+kernel自动调优(推理侧) | 同"先拿图再优化"思想,但用于推理不是训练 |

一句话区分:**TorchAcc / torch.compile 解决"算得快",DeepSpeed / Megatron 解决"放得下、切得开"。** 二者往往一起用。

## 7. 典型接入方式与配置项含义(讲含义,不背默认值)

> 下面是**思路层面**的接入形态。确切的 import 路径、类名、参数名与默认值**以官方文档/源码为准**,这里只解释每类配置"是干嘛的、怎么权衡"。

### 7.1 接入形态(理想情况:只在外面包一层)

```
原始训练循环:
  model = MyModel()
  for batch in loader:
      loss = model(batch); loss.backward(); opt.step()

接入 TorchAcc(示意,非真实 API):
  model = torchacc.accelerate(model, config=...)   # 包一层
  for batch in loader:                              # 训练循环基本不动
      loss = model(batch); loss.backward(); opt.step()
       └─ 第一次触发 GraphCapture+编译,之后命中缓存高速执行
```

### 7.2 配置项的"类别"与权衡(而非具体名字)

| 配置类别 | 控制什么 | 怎么权衡 |
|----------|---------|---------|
| **是否启用图编译** | 开/关 GraphCapture 加速 | 关闭可回退 eager,方便调试对比 |
| **混合精度** | fp16 / bf16 | bf16 数值更稳;fp16 省显存但需 loss scaling |
| **算子融合级别** | 融合多激进 | 越激进越快,但可能增加编译时间/调试难度 |
| **分布式/通信** | 数据并行、通信重叠开关 | 多卡才需要;单卡可关 |
| **动态 shape 处理** | 是否容忍 shape 变化 | 变长输入场景关键,影响重编译频率 |
| **缓存/预热** | 编译缓存策略 | 影响"冷启动"与跨任务复用 |

### 7.3 上手检查清单

```
[ ] 先用 eager 跑通、记录基线 loss 曲线与吞吐
[ ] 包上 TorchAcc,先确认 loss 曲线与基线一致(正确性优先)
[ ] 评测吞吐时跳过前几个预热 step(它们在编译)
[ ] 观察是否频繁重编译(日志里看 recompile/warmup 信号)
[ ] 多卡时确认通信重叠生效、GPU 利用率上升
[ ] 对比 eager vs TorchAcc 的端到端吞吐与显存峰值
```

## 常见问题 / 坑

| 现象 | 根因 | 应对 |
|------|------|------|
| 头几个 step 特别慢 | 在做 GraphCapture + 编译(预热) | 正常现象;评测时跳过预热 step |
| 训练中途反复变慢 | shape/dtype 变化导致**频繁重编译** | 固定 batch/seq_len,或开启动态 shape 支持;对变长做分桶(bucketing) |
| 含 `if`/早停/`.item()` 的代码加速差 | 数据依赖的控制流会**打断图**(graph break),图变碎 | 尽量把控制流移出热点循环;减少在 step 内取标量 |
| 加了 TorchAcc 后 loss 对不上 | 多为混合精度/融合带来的数值差异,或捕获到错误图 | 先用 bf16、降融合级别核对;以 eager 结果为正确性基准 |
| 多卡没提速 | 通信没重叠,或被通信带宽/拓扑卡住 | 确认通信-计算重叠生效;检查 NCCL/网络([[ai-infra/网络/NCCL]]) |
| 显存反而更高 | 编译缓存/融合策略不当,或预热阶段保留多份图 | 调融合/内存规划相关配置;以官方建议为准 |
| 某些自定义算子捕获失败 | GraphCapture 无法追踪非标准/有副作用的算子 | 用框架支持的算子改写,或让该段回退 eager |

> 通用心法:**编译型加速器最怕"图被打断"和"频繁重编译"。** 让计算图尽量大、尽量稳定(固定 shape、少控制流、少在 step 内取标量),收益最大。
