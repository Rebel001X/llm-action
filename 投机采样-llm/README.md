# 投机采样 / 投机解码 深度分析库

> 从"它为什么必须存在"（带宽墙），到"它为什么是无损的"（拒绝采样的完整证明），
> 到十年的**历史演化**（2018 blockwise → 2023 双论文奠基 → Medusa/EAGLE/MTP → 2026 前沿），
> 再到**未来判断**（哪些分支会活下来）。
> 外加**社区精彩解释的精选与评点**、**优秀文章附录**，以及一个把断言变成数字的**可执行验证层**。

---

## 这个库和别处有什么不一样

同一个 `llm-action` 仓库里，投机解码已经以**单章**形式出现过至少六次。本库的存在理由是那六篇都做不到的三件事：

1. **完整的历史演化线** —— 谱系图 + 被淘汰的分支 + 每代的「新增了什么 / 什么被后来推翻」；
2. **社区解释的精选与评点** —— 好在哪、错在哪，逐条给出处；
3. **可执行的验证层 `_lab/`** —— 无损性、接受率、加速比，全部跑数字判真假，而不是靠转述。

判据：如果一句话在那六篇里已经说清楚了，本库就一句话带过 + 指路；本库的每一页都要有它们没有的东西。边界详见 `_meta/写作规范.md` §0。

## 五条铁律

| | 铁律 | 由什么强制 |
|---|---|---|
| 一 | **说「无损」必须标口径**：L1 分布无损 / L2 贪心等价 / L3 近似，三选一 | `verify.py --rules` |
| 二 | **加速比数字不许裸奔**：必须同段给出 batch、γ、接受率、模型组合、硬件精度、测的是延迟还是吞吐、任务分布 | `verify.py --rules` |
| 三 | **每个「它很好」必须配一条「它什么时候是负收益」** | `verify.py --struct` |
| 四 | **数学断言必须有可执行验证，且正文指名引用** | `verify.py --tests`（强制零虚引） |
| 五 | **史料必须可追溯**：年月 + arXiv/URL + 作者机构 + 新增了什么 + 什么被推翻；禁止无主语句子 | `verify.py --consistency` |

铁律一与铁律二的完整理由见第 07 篇与第 18 篇 —— 它们不是格式洁癖，是这个主题上最高频的两类错误的解药。

## `_lab/` —— 论证的一部分，不是配套代码

本库的断言多数是**数学命题**，能被代码判定真假。所以 `_lab/` 不是"示例代码"，它是论证本身。

| 文件 | 提供什么 |
|---|---|
| `spec.py` | 标准投机采样参考实现（纯 numpy）+ **精确枚举**路径：不掷骰子，把所有分支的概率加起来 |
| `accept.py` | 接受率恒等式 $\beta=\sum\min(p,q)=1-\mathrm{TV}(p,q)$、$E[\tau]$、最优 $\gamma$、温度扫描 |
| `regime.py` | 公式失效条件的可控实验（黏性双区制模型）+ 更新过程的长度偏置 |
| `caliber.py` | L2 贪心等价与 L3 近似判据偏差的判定性实验 |
| `tree.py` | 树注意力 mask 构造、树链等价性、"该深还是该宽"的可算比较 |
| `speedup.py` | roofline + KV 流量 + batch 崩塌 + 量化交互 + chunked prefill 的"免费额度"账本 |
| `moe.py` | MoE 专用账本：激活专家数的饱和曲线、小 batch 的多读权重惩罚、为什么 MoE 与稠密两头相反 |
| `citecheck.py` | **引用核验**：把全库每个 arXiv 编号拿去问官方 Atom API，核对存在性、v1 年月、标题主名 |
| `verify.py` | 全库自检：死链、测试虚引、五条铁律体检、跨篇一致性审计 |

跑一遍：

```bash
cd _lab
python -m pytest -q            # 全部测试
python spec.py --proof         # L1 无损：精确枚举 vs 目标分布，误差 ~1e-16
python spec.py --bias          # 三种社区常见错法的精确偏差
python caliber.py --greedy     # L2 贪心等价：16 组配置逐 token 相同
python accept.py --temp        # 接受率随温度：形状由 argmax 一致率决定
python regime.py --renewal     # 公式高估的机制：更新过程的长度偏置
python tree.py --mask          # 树注意力 = 换了形状的 mask（误差 4.4e-16）
python speedup.py --batch      # batch 崩塌曲线
python speedup.py --quant      # 量化与投机是竞争不是叠加
python moe.py --redhat         # MoE 为什么在并发 200 仍然赚（与稠密相反）
python citecheck.py            # 引用核验：147 个 arXiv 编号，编造 0 个
python verify.py               # 全库自检
```

## 本库自己跑出来的几条结论

这些不是转述，是 `_lab/` 里可复跑的：

- **草稿模型的好坏只影响速度，不影响分布。** 接受率低到 0.31、甚至草稿把质量押在目标最不可能的 token 上，输出分布的最大逐点误差仍是 $10^{-17}$ 量级。
- **两种社区常见错法的偏差被精确量化**：拒绝后直接从 $p$ 重采 → 0.132；判据写成 $p\ge q$ 就接受 → 0.224。而"不发赠品 token"是**无偏**的（只是慢）—— 由此得到判据：**少发 token 只是慢，改分布才是错**。
- **加速比公式 $(1-\alpha^{\gamma+1})/(1-\alpha)$ 的前提是两条不是一条**：沿链不相关 **且** 起点无偏。本库两次猜错方向，最后查到真机制是**更新过程的长度偏置**（难区的迭代更短 → 按迭代计数时难区被过采样），净效果是公式**高估**，实测最大 10.5%。
- **compute-bound 极限下加速比收敛到 $E[\tau]/(\gamma+1)\times(1-s)$，恒小于 1**，且**调参救不了**。这条渐近线任何新方法都逃不掉。
- **量化与投机采样是竞争关系不是叠加关系**：权重从 fp16 到 int4，可用 batch 区间从 265 塌到 52（缩小 5.1 倍），但 bs=1 的加速比几乎不变（2.80 附近）—— **只在 bs=1 做兼容性测试会系统性漏掉这个冲突**。
- **"草稿不准就该把树加宽"是错的**：宽度值不值钱取决于**边际覆盖率增益** $c_k-c_1$，而不是草稿好不好。一个整体跑偏的草稿，宽度买不到任何东西。
- **接受率随温度不是单调的**：形状由草稿与目标的 argmax 一致率决定。好草稿呈 U 形（贪心 0.697 → 中温 0.657 低谷 → 高温 0.995），烂草稿单调上升。**所以 T=0 测的接受率不能外推到线上温度。**
- **全库 147 个 arXiv 编号，编造 0 个、不存在 0 个** —— 不是抽样，是拿官方 Atom API 全量核过的（`citecheck.py`）。而且**新增引用不先核实，`pytest` 会直接红**。
- **MoE 与稠密两头都相反**：稠密的甜区在 batch=1，MoE 上 batch=1 反而亏（0.804×，因为投机的 5 个 token 激活 18.8 个专家而基线只激活 4 个）；而稠密在 batch=1024 已跌到 0.566× 时，MoE 仍有 2.16×。
