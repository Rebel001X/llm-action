## 1. 致命

### F1 · 第 06 篇：「用实测 $E[\tau]$ 反推 $\alpha$ 会偏高」——**方向写反了，而且与它自己的算例自相矛盾** 〔已修〕

**位置**
- `06-期望接受长度与加速比模型-完整推导.md:243`（§7.4 第 2 条）
- `06-期望接受长度与加速比模型-完整推导.md:271–272`（§9 自测题 3）

**原文**

> §7.4：「**别用它反推 $\alpha$。** 由实测 $E[\tau]$ 套公式解出的 $\alpha$ 会**高于**真实的平均接受率（因为公式高估 $E[\tau]$，反解就得补偿），于是高估草稿质量。」

> §9-Q3 答案：「…解出的 $\alpha$ **必然偏高**。§7.2 的 sticky=0.99 行就是例子：真实 $\alpha=0.7439$ 时公式给 3.633，而实测只有 3.253 —— 若拿 3.253 反推，得到的 $\alpha$ 会明显**低于** 0.7439。」

**问题**：同一段答案里前半句说"必然偏高"，后半句给的算例说"明显低于"。**两句直接打架，而错的是前半句。**

**证据（复跑）**

```bash
cd _lab && python -c "
from accept import expected_tokens
def invert(e,g):
    lo,hi=1e-9,0.999999
    for _ in range(200):
        m=(lo+hi)/2
        if expected_tokens(m,g)<e: lo=m
        else: hi=m
    return (lo+hi)/2
print(expected_tokens(0.7439,8))   # 3.6323  公式值
print(invert(3.2526,8))            # 0.7059  拿实测值反解
print(invert(3.2,8))               # 0.7001  自测题 3 的题干场景
"
```

$E[\tau]$ 关于 $\alpha$ **严格单调增**。公式在难度连片时给出的值（3.6323）**高于**实测（3.2526），所以要让公式吐出 3.2526，代进去的 $\alpha$ 只能**更小**：$0.7059 < 0.7439$。**反推出的 $\alpha$ 系统性偏低，是低估草稿质量，不是高估。**

原文的因果链「因为公式高估 $E[\tau]$，反解就得补偿」是个 non sequitur —— "补偿"往哪边补正好写反了。

顺带：自测题 3 的题干说 $E[\tau]=3.2$、$\gamma=8$ 反推「得到约 0.74」，实际反解是 **0.70**。

**严重程度：致命。** 这不是措辞问题 —— §7.4 是一条给读者用的工程戒律（"于是高估草稿质量"），照它办的人会往相反方向纠偏。

**已做的修改**：§7.4 与 §9-Q3 两处均改正方向、补上反解算例、题干数字 0.74→0.70，并在原地留了修正说明行。

**扩散检查（好消息）**：这条错误**没有传染到别的篇**。第 05 篇 `:245/:447`、第 21 篇 `:674/:698/:813`、第 27 篇 `:184/:185`、第 28 篇 `:238` 都只说"别反推、会系统性偏"而不给方向；第 29 篇 `:96` 写的是"方向还取决于负载"，是对的。**只有第 06 篇给了方向，而且给反了。**

## 2. 重要

### F2 · 第 18 篇：§4 的渐近线定理**缺一个从未点明的前提**，本库自己的模型就是反例

**位置**：`18-batch与吞吐-收益衰减曲线.md:11`（§1）、`:94–101`（式 4.1 与推论 1、2）

**原文**

> §1：「这个极限**恒小于 1**，而且**调参救不了**……所以"投机解码在大 batch 下会亏"不是工程没做好，是算术。」
> §4 推论 1：「投机吞吐在 compute 区**封顶**，而基线吞吐也封顶但在更高的位置。**所以交叉点必然出现，只是早晚。**」
> §4 推论 2：「$E[\tau]/(\gamma+1)\le 1$ 恒成立……**极限严格小于 1**。」

**问题**：§4 的推导在 `:74` 处用了 $\text{TPS}_{\text{base}}=\text{batch}/T_{\text{target}}(\cdot,1)=\text{peak}/F$ —— 这一步**假设基线前向也已经是 compute-bound**。但这个假设**不是 batch 大就自动成立的**：

$\text{batch}\to\infty$ 时，访存项（$\text{batch}\cdot\text{seqlen}\cdot\text{kv}$）与算力项（$\text{batch}\cdot n_q\cdot F$）**都是 batch 的一次函数**，batch 在两边同时约掉。所以"谁主导"由一个**与 batch 无关**的比值决定：

$$\frac{\text{seqlen}\cdot\kappa\,/\,\text{BW}}{\big(2P+4L\,\text{seqlen}\,d\big)\big/\text{peak}}$$

**这个比值大于 $\gamma+1$ 时，无论 batch 多大，验证与基线都留在 memory 区，交叉点根本不存在** —— 不是"晚一点出现"。

**证据（复跑，用的就是本库的 `speedup.py`）**

```bash
cd _lab && python -c "
from speedup import H100, MODELS, scale, spec_throughput, fwd_time
hw=scale(H100,8)
for s in (1024,2048,4096,8192,16384,32768):
    r=spec_throughput('llama3-70b','llama3.2-1b',hw,2_000_000,s,4,3.0)
    a=fwd_time(MODELS['llama3-70b'],hw,2_000_000,s,1)
    print(s, round(r['speedup'],3), a['bound'], r['verify_bound'])
"
```

| seqlen | batch=2×10⁶ 的加速比 | 基线 | 验证 |
|---|---|---|---|
| 1 024 | **0.569** | compute | compute |
| 2 048 | 0.732 | memory | compute |
| 4 096 | **1.295** | memory | compute |
| 8 192 | **2.104** | memory | compute |
| 16 384 | **2.143** | memory | memory |
| 32 768 | **2.143** | memory | memory |

**seqlen ≥ 约 3 400 时，加速比在 batch 加到两百万仍然大于 1，且已经收敛。** §1 的"恒小于 1"与推论 1 的"交叉点必然出现"在这一整片区域里都不成立。

这条不是我造出来的边角情形 —— 本库自己有一条测试正是它：`_lab/test_speedup.py::test_long_context_still_no_crossover_even_quantized`（`crossover_batch(..., 16384, ..., bmax=8192)` 返回 `None`）。**测试早就说了"扫到 8192 没有交叉点"，而 §4 的定理说"交叉点必然出现"。**

MoE 也一样：`moe_spec_speedup('gpt-oss-120b', hw, 8_388_608, ...)` 给 **1.1965**，基线全程 memory-bound。

**严重程度：重要**（不是致命，因为 §8 失效条件第 2、5 条已把长上下文与 MoE 列为例外；但 §1 与 §4 把结论写成了无条件定理，且 §8 给的理由与真实机制不同 —— 见 F3）。

**建议**：在 §4 的 (4.1) 上方加一行前提声明：

> 本推导假设**基线前向也已进入 compute 区**。这不是 batch 够大就自动成立的：访存项与算力项都正比于 batch，谁主导由 $\dfrac{\text{seqlen}\cdot\kappa/\text{BW}}{(2P+4L\,\text{seqlen}\,d)/\text{peak}}$ 决定，**这个比值与 batch 无关**。比值超过 $\gamma+1$ 时（本配置约 seqlen ≥ 3 400），交叉点在任何 batch 下都不存在。

并把 §1 的"恒小于 1"、推论 1 的"交叉点必然出现"各加上"（短上下文下）"的限定。

### F3 · 第 18 篇：把"长上下文不翻转"归因为**显存装不下**，而模型说的是**根本不存在交叉点**

**位置**：`18-batch与吞吐-收益衰减曲线.md:142–144`（§5 第二张表下方）

**原文**

> 「**这一段不翻转。** 长上下文的 KV 读把前向死死钉在 memory 区，验证依旧近乎白送。**但它换来另一个约束：显存装不下大 batch**。……长上下文场景下投机采样**在能装下的全部 batch 范围内**都是赚的……只是那个范围本身被显存卡死。」

**问题**：「在能装下的范围内都赚 / 范围被显存卡死」这个措辞，读起来是**"如果显存够，它还是会翻转，只是我们够不着"**。F2 的扫描表说明这是错的 —— 把显存约束整个拿掉，batch 加到 2×10⁶，seqlen=16384 的加速比仍然是 **2.143** 并且已经收敛。**显存不是掩盖翻转点的幕布，那里压根没有翻转点。**

这一条与 F2 是同一个根因的两个表面症状，但值得单列，因为**它们给读者的工程直觉完全不同**：按原文，读者会以为"上更大显存的卡 = 长上下文投机也会亏"；按模型，读者应该得到"长上下文是投机采样唯一一个 batch 加不死的区间，显存是它唯一的限制"。后者才是可操作的。

**严重程度：重要。**

**建议**：把那段改成两句分开的话 ——「① 在本模型里，seqlen=16384 时**任何 batch 都不翻转**（不是"翻转点在显存之外"，是不存在，见 §4 的前提讨论）；② 显存是**另一条独立的**硬约束，它限制的是 batch 上限，不是收益方向。」

## 6. 给下次续写的三条

1. **F1 那类错误是这个库最该防的**：一条方向性论断，配着一个方向相反的算例，同时躺在同一段答案里，而且 `verify.py` 的任何一条检查都抓不到它（它既不是死链、不是虚引、不是裸奔倍数）。**"每个断言都有可执行验证"目前只覆盖到"有没有引测试"，没覆盖"引的那个测试是不是在说同一件事"。** 值得加一条人工 checklist：凡是写了"方向"（偏高/偏低/变大/变小）的句子，必须在同段给一个数值算例，且算例方向要与论断一致。

2. **F2/F3 揭示的是"定理的前提没写全"**。这个库的推导质量很高，但 §4 那种"设已深入 compute 区"的措辞会让读者以为前提是"batch 够大"，而真实前提是一个**与 batch 无关**的比值条件。**凡是写 $\lim_{x\to\infty}$ 的地方，都要问一句"$x\to\infty$ 时另一侧也跟着变吗"。**

3. **F4/m1/m2/m3/m4 是同一个根因**：`speedup.py` / `moe.py` 改过之后，下游数字散落在正文表格、自测题、冲突矩阵、测试 docstring 四个地方，只更新了前两处。建库审计 §4 第 8 条已经记过这个坑，但**没记全下游清单**。建议在 `_meta` 里维护一张「模型改动 → 需重算的位置」表，或者更好：把关键数字改成由脚本生成、正文只留 include 标记。
