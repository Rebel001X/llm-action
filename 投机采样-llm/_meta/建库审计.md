## 4. 建库过程中踩过的坑（不要重踩）

1. **Bash heredoc 里嵌中文 Python 代码**：`print("...「引号」...")` 用 ASCII 双引号会直接语法错误；一律用 `「」` 或改用 Write 工具写文件。
2. **控制台显示乱码 ≠ 文件编码错**：Git Bash 控制台按 GBK 显示 UTF-8 会花屏，但文件本身是正确的 UTF-8。用 `open(..., 'rb')` 看字节确认，别乱"修"。
3. **自检器自身的假阳性**（三次）：
   - 铁律一把**双链文件名**里的"无损"二字判成违规 → 检查前必须剥掉 `[[...]]` 与行内代码；
   - 铁律五把**正在声明禁用**那些句式的行判成违规 → 加"元陈述"豁免；
   - 铁律五逐处计数，把交叉引用全判成违规 → 改成按 (篇目 × 编号) 聚合。
   **把可执行验证当论证基础的库，必须同时怀疑自己的验证。**
4. **并发 agent 上限是 20**，且调研 agent 会自己再派子 agent，很容易占满；写作 agent 要分批派。
5. **WebSearch 配额 200/200 会被并行 agent 快速吃光**。用完后改走 `WebFetch` + `https://lite.duckduckgo.com/lite/?q=` 或直接构造 arXiv/GitHub raw URL。**配额用完不是编造的理由。**
6. **调研 agent 边写边扩**：写作 agent 可能读到半成品版本（RS-1 从 483 行扩到 2001 行）。派写作 agent 前要确认调研已完成，或事后用 SendMessage 让它复核。
7. **WebFetch 的摘要模型会编造内容**：建库中至少两次 —— 一次编造了一张 12 行的 MagicDec 表格，一次把 SGLang release 的年份从 2026 读成 2024。**凡二手摘要给的表格与日期，必须回一手页面（atom/API/raw）核对。**
8. **改了基座代码要通知所有下游**：`speedup.py` 修了 attention FLOPs 漏乘层数的 bug 之后，第 18、19、22、23 篇的数字全要重算。SendMessage 时**要发对收件人**（我曾把给第 22 篇的勘误发给了第 19 篇）。
9. **⭐ 别把 arXiv 版本号焊死进正文 URL**（2026-08-22 复核挖出来的坑，本库为它误禁了一条真数据）：库里四处都写 `https://arxiv.org/html/2601.11580**v1**`，于是**永远读不到 2026-03-18 的 v2**，而树验证那整节只在 v2 里。结果是网站摘要与"论文正文"看起来互相矛盾，我按"论文正文优先"把一条**真数据**判成【待核验】并禁止引用，还连累第 25 篇把一条判断从 A 降到 B。
   **规矩三条**：① 引用论文正文**先开 `abs/` 页**看 *"last revised …(this version, vN)"*，正文 URL 用**不带版本号**的形式，或显式写明"本库核的是 vX、哪天核的"；② **"论文里没有 X"这类否定断言，必须连版本号与核验日期一起记** —— 否定断言的保质期比肯定断言短得多；③ **网站摘要与论文"打架"时，第一件事不是判谁可信，是查它们是不是同一个版本。**
10. **⭐ "我抽不到" ≠ "原文没有"**（同日复核的另一半）：DeepSeek-V3 那两个数四次抽取失败，其中一次明确报告 *"Content truncated due to length"*，本库当时正确地忍住没编，但也差点把它读成"原文可能根本没有"。**正确动作是换渲染 + 落盘本地检索**（HTML v1/v2 + 官方 PDF 三份 `curl` 下来，`pdftotext -layout` + 正则），**而不是换一个摘要模型再问一遍** —— 摘要模型问十遍还是那个截断。三渲染交叉一致，才是"核实"。
