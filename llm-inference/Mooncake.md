## 0. 一句话锚点
**一句话**:Mooncake 把"键值缓存(KV Cache)"从单卡显存里的私有数据,抽象成**整个集群共享的、分层存储的池化资源**;然后把负责"生成 KV"的 prefill 节点、负责"消费 KV 逐字吐字"的 decode 节点、以及负责"谁去算/去哪取缓存"的调度器(Conductor),全部解耦,围着这个 KV 池子重新编排。

**为什么这是大事**:在 LLM 推理里,**KV Cache 是显存的头号吞噬者**,也是**重复计算的头号来源**(同样的系统提示词、同样的文档前缀,被无数请求一遍遍重算)。谁把 KV 管好,谁就同时拿下"省显存"和"提吞吐"两件事。Mooncake 的答案是:**别让 KV 绑死在某张卡上,把它池化、分层、共享、复用。**

## 1. 地基:KV Cache 是什么、为什么占显存(从最底层讲起)

### 1.1 Transformer 推理为什么需要缓存
自回归生成是"一次吐一个 token"。生成第 $t$ 个 token 时,注意力(attention)要让当前 query 去看**前面所有 token** 的 Key 和 Value:

$$\text{Attn}(Q_t, K_{1:t}, V_{1:t}) = \text{softmax}\!\left(\frac{Q_t K_{1:t}^\top}{\sqrt{d}}\right) V_{1:t}$$

如果每生成一个 token 都把前面所有 token 的 $K, V$ 重新算一遍,复杂度是 $O(t^2)$ 级、且每步都重复劳动。**KV Cache 的本质**:把每个 token 算出来的 $K_i, V_i$ **存下来**,下一步直接复用,只算新 token 的那一份。于是每步 attention 从"重算全部"降为"算 1 个新的 + 读历史缓存"。

```
不缓存(慢):  step t 重新算 K1..Kt, V1..Vt   ← 每步都 O(t)
缓存(快):    step t 只算 Kt,Vt 追加进 cache  ← 每步 O(1) 新算 + 读历史
            cache:  [K1 K2 K3 ... Kt]  [V1 V2 V3 ... Vt]
                      └────── 越生成越长 ──────┘
```

### 1.2 KV Cache 占多少显存(关键公式,后面要手算)
一条序列的 KV Cache 字节数:

$$\text{Bytes}_{KV} = 2 \times L \times n_{kv} \times d_{head} \times S \times \text{dtype} $$

- $2$:K 和 V 两份;
- $L$:层数(每层都有自己的 KV);
- $n_{kv}$:KV 注意力头数(用 GQA/MQA 时远小于 query 头数);
- $d_{head}$:每个头的维度;
- $S$:序列长度(token 数);
- $\text{dtype}$:每个数的字节(FP16=2,FP8=1)。

**关键直觉**:KV 显存 **随序列长度 $S$ 线性增长**。长上下文(几万到几十万 token)时,KV Cache 会**超过模型权重本身**,成为显存第一大户。这就是为什么"KV 管理"=推理系统的命门。

## 2. 痛点:为什么传统"PD 一体化"卡在 KV 上

传统做法:一张(组)GPU 既做 **prefill**(把整个 prompt 一次性吃进去、生成全部 KV、产出第一个 token),又做 **decode**(基于 KV 一个一个往外吐字)。这两阶段的资源画像**完全相反**:

```
            算力(compute)        显存带宽/容量(memory)
prefill:    ███████████ 吃满       ▒▒ 轻
            (大矩阵乘,算力受限)
decode:     ▒▒ 轻                  ███████████ 吃满
            (一次只算1个token,带宽/容量受限)
```

把两个画像相反的活塞进同一张卡,必然有一方被另一方拖累:
- **显存墙**:decode 阶段每条活跃序列都长期占着一大块 KV 显存,序列越长占越多,并发数被显存死死卡住。
- **前缀重算**:请求 A 和请求 B 共享同样的系统提示词("你是一个助手…")或同一篇长文档,一体化架构里它们在不同卡、各算各的 KV,**同样的几千 token 被重复 prefill 无数次**,算力白白烧掉。
- **资源错配**:prefill 想要算力、decode 想要显存带宽,绑一起没法各自扩缩容。

一句话:**KV 既是显存负担,又是可复用资产,但一体化架构既没把它的负担卸掉,也没把它的资产用起来。**

## 3. 核心思想:把 KV 变成"池化资源"

Mooncake 的转折点:**不要再把 KV Cache 当成某张卡的私有内存,而把它当成一份可以被全集群读写、可以分层存储、可以跨请求共享的"数据"。**

```
传统:  KV 绑死在算它的那张卡的显存里(私有、易失、不可共享)
          GPU0[KV_A]  GPU1[KV_B]  GPU2[KV_C]   ← 各管各的,算完即焚

Mooncake: KV 进"池子",算力来"取"
          ┌──────────────  KVCache 池(共享)  ──────────────┐
          │  显存层(HBM)  ──  DRAM 层  ──  SSD/远端层        │
          └──────────▲───────────────────▲─────────────────┘
                     │ 写入新 KV          │ 读取/复用 KV
              Prefill 池(算 KV)     Decode 池(用 KV)
```

这一步解耦带来三个能力:
1. **解耦"算 KV"与"存 KV"**:prefill 节点算完 KV 写进池子就走,不必继续占着这块显存陪 decode 跑到结束。
2. **跨请求复用**:KV 在池子里有"地址"(按前缀内容索引),后来的请求若前缀相同,直接从池子取,免算。
3. **分层放置**:热的 KV 放最快的 HBM,温的放 DRAM,冷的下沉到 SSD/远端,用便宜大容量换显存空间。

## 4. 架构总览:四大件

Mooncake 论文把系统拆为以 KVCache 为中心的几块。用 ASCII 串起来:

```
                 ┌────────────────────────────┐
   请求 ──────►  │   Conductor(全局调度器)     │  缓存感知 + 负载均衡
                 │  - 查前缀缓存是否命中         │
                 │  - 选 prefill 节点 / decode 节点 │
                 └───────┬───────────────┬──────┘
                         │ 派 prefill     │ 派 decode
                         ▼                ▼
                ┌─────────────┐   ┌─────────────┐
                │  Prefill 池  │   │  Decode 池   │
                │ 算法力密集    │   │ 带宽/容量密集 │
                │ 产出新 KV    │   │ 逐 token 生成 │
                └──────┬──────┘   └──────▲──────┘
                       │ 写KV            │ 读KV / 续写
                       ▼                 │
        ┌──────────────────────────────────────────┐
        │       KVCache 池(分层 + 前缀索引)          │
        │  HBM(显存) │ DRAM(内存) │ SSD/远端(冷)   │
        │  传输引擎(Transfer Engine)跨节点搬 KV       │
        └──────────────────────────────────────────┘
```

- **Conductor(调度大脑)**:决定一个请求"前缀是否已缓存""去哪个 prefill 节点补算缺失部分""哪个 decode 节点接手"。它是"缓存感知调度"的核心。
- **Prefill 池**:专做 prefill。可做 **chunked prefill / 分块流水**,把长 prompt 切块,边算边把 KV 写入池子;甚至跨多节点把一条长序列的不同层/块并行 prefill。
- **Decode 池**:专做 decode。从池子拉来对应 KV,逐 token 生成。decode 节点只在"自己负责的活跃序列"上占 KV 显存。
- **KVCache 池 + 传输引擎**:统一管理多层存储、做前缀索引、负责把 KV 在节点之间高速搬运(RDMA / NVLink / 网络)。

## 5. KVCache 分层池(显存/DRAM/SSD):容量与速度金字塔

为什么要分层?因为存储介质是**速度与容量的取舍**:越快越贵越小,越慢越便宜越大。

```
        速度快、容量小、最贵
   ┌──────────────┐
   │ HBM(GPU显存) │  ~TB/s 级带宽   放最热的 KV(正在 decode 的)
   ├──────────────┤
   │ DRAM(主机内存)│  ~几十 GB/s    放温的 KV(可能很快被复用的前缀)
   ├──────────────┤
   │ SSD / 远端池  │  ~GB/s         放冷的 KV(长尾前缀、历史会话)
   └──────────────┘
        速度慢、容量大、最便宜
```

**机制要点**:
- KV 按"块(block/page)"为粒度管理(类似 PagedAttention 的分页),便于在层间搬运和按前缀对齐。
- **下沉(evict)**:HBM 满了,把最久没用的 KV 块挪到 DRAM,再挪到 SSD,而不是直接丢弃——因为丢了就要重算,重算很贵。
- **回升(load)**:某请求命中了一个躺在 DRAM/SSD 的前缀,传输引擎把它搬回 HBM 供计算。
- **为什么省显存**:同一时刻 GPU HBM 里只需放"正在用"的 KV,海量"暂时不用但有复用价值"的 KV 躺在便宜的 DRAM/SSD,于是**显存容量不再是并发上限的硬墙**。

权衡:搬运不是免费的。把 KV 从 SSD 拉回 HBM 要花带宽和时间;Mooncake 用"高带宽传输引擎 + 调度预取"来摊掉这个延迟,核心是让"取缓存的成本 < 重算的成本"。

## 6. 前缀复用(Prefix Cache)机制

这是 KV 池化最直接的红利。很多请求共享**相同前缀**:
- 系统提示词("You are a helpful assistant…"几百 token);
- 同一篇被反复提问的长文档 / 代码库;
- 多轮对话里前面已经发生的历史轮次。

```
请求1:  [系统提示 SSSS][文档 DDDDDD][问题1 Q1]
请求2:  [系统提示 SSSS][文档 DDDDDD][问题2 Q2]
                └──── 公共前缀 ────┘
        这段前缀的 KV 只需算一次,存进池子,
        请求2 命中后直接复用,只 prefill 自己独有的 [问题2] 部分
```

**机制**:对前缀内容做哈希/树形索引(如 radix tree),把"前缀 → 已缓存 KV 块地址"建表。新请求来时,Conductor 沿前缀做**最长公共前缀匹配**:
- 命中部分 → 直接取池子里的 KV(免 prefill);
- 未命中的尾部 → 只对增量部分 prefill。

**为什么省算力**:prefill 的计算量与 token 数成正比。命中 $k$ 个前缀 token,就省下这 $k$ 个 token 的 prefill FLOPs(以及第一个 token 的延迟 TTFT 大幅下降)。命中率越高,省得越多。

## 7. prefill / decode / 调度三分离:各自吃不同资源

把第 2 节那张"资源画像相反"的图落地成"分池":

```
prefill 节点群           decode 节点群
  ↑算力打满                ↑显存带宽打满
  · 大 batch 大矩阵乘       · 一次一个 token
  · 算完写 KV 进池          · 长期持有活跃序列 KV
  · 可独立按"算力需求"扩缩   · 可独立按"并发/显存需求"扩缩
```

**分离的好处**:
- **独立扩缩容**:prompt 突然变长(prefill 压力大)就加 prefill 节点;在线并发涨(decode 压力大)就加 decode 节点。两者解耦,不再"一动全动"。
- **互不抢占**:prefill 的大矩阵乘不会卡住 decode 的低延迟出字;decode 的显存占用不会逼着 prefill 减小 batch。
- **各自最优批处理**:prefill 适合大 chunk;decode 适合 continuous batching(连续批处理)。分开后各自用最优策略。

代价:prefill 算好的 KV 要**跨节点传给** decode 节点(或经由池子),这需要高带宽互联(RDMA/NVLink)和好的调度来隐藏传输延迟。这正是"传输引擎"和"缓存感知调度"要解决的。

## 8. 调度器:为什么能"同时"省显存又提吞吐

Conductor 不是简单的轮询负载均衡,而是**缓存感知(cache-aware)+ 过载感知**:

- **缓存感知**:优先把请求派给"已经持有/最接近该前缀 KV 的节点",从而最大化前缀命中、最小化跨节点搬运。
- **负载/过载感知**:同时看节点排队长度、显存占用、SLO(TTFT 首字延迟、TBT 字间延迟)。命中再好,如果那台已经过载,也要权衡是排队还是去别处重算。
- **面向 SLO 的取舍**:在"重算 vs 取缓存""排队 vs 转发"之间做选择,目标是**在满足延迟 SLO 的前提下最大化有效吞吐**。论文里甚至有"过载时主动拒绝部分请求(early reject)"以保住整体 SLO 的策略。

**为什么能两头都赢(不是零和)**:
- 省显存来自**分层池化**(把不活跃 KV 下沉到 DRAM/SSD)→ 同样的 HBM 能服务更多并发。
- 提吞吐来自**前缀复用**(免重算)+**PD 分离**(各自满负荷、独立扩缩)→ 单位算力服务更多 token。
- 两者的公共底座都是"KV 被池化、被共享、被分层"——所以是**同一个设计同时产出两个收益**,而非互相拆台。

## 9. 数值示例 / 手算

### 9.1 KV Cache 到底多大(线性增长的可怕)
设一个模型:层数 $L=80$,KV 头数 $n_{kv}=8$(GQA),头维 $d_{head}=128$,FP16(2 字节)。
单 token 单条序列的 KV 字节:

$$2 \times L \times n_{kv} \times d_{head} \times \text{dtype} = 2 \times 80 \times 8 \times 128 \times 2 = 327{,}680 \text{ B} \approx 0.3125 \text{ MB / token}$$

- 序列 $S = 4{,}000$ token:$0.3125 \times 4000 = 1{,}250 \text{ MB} \approx 1.22 \text{ GB}$。
- 序列 $S = 128{,}000$ token(长上下文):$0.3125 \times 128000 = 40{,}000 \text{ MB} \approx 39 \text{ GB}$。

**结论**:一条 128k 的序列,光 KV 就吃掉 ~39GB。一张 80GB 的卡,这种长序列**只能放一两条**。这就是显存墙的具体数字,也是 Mooncake 要把 KV 往 DRAM/SSD 下沉的根本原因。

### 9.2 并发墙:HBM 能放几条
设 GPU 有 80GB HBM,权重已占 ~40GB,留给 KV 的约 40GB。每条 4k 序列 ~1.22GB。

$$\text{最大并发} \approx \frac{40\text{ GB}}{1.22\text{ GB/条}} \approx 32 \text{ 条}$$

把不活跃序列的 KV 下沉到 DRAM(假设有 512GB 主机内存,可放 $512/1.22 \approx 419$ 条),HBM 只需驻留"此刻正在 decode 的活跃子集"。于是**池子能托管的会话数从 ~32 跃升到数百级**,而 HBM 仍只装活跃的那几十条。

### 9.3 前缀复用省多少 prefill
设系统提示 + 共享文档共 $3{,}000$ token,用户问题各 $200$ token。1000 个请求共享这段前缀。

- **不复用**:每请求都 prefill $3000+200=3200$ token,总计 $1000 \times 3200 = 3{,}200{,}000$ token 的 prefill。
- **复用前缀**:前缀 $3000$ 只算一次,之后每请求只 prefill 自己的 $200$:$3000 + 1000\times200 = 203{,}000$ token。

$$\text{节省比例} = 1 - \frac{203{,}000}{3{,}200{,}000} \approx 93.7\%$$

**省下约 94% 的 prefill 计算**。同时第二个请求起的 TTFT(首字延迟)从"算 3200 token"降到"算 200 token + 取缓存",显著变快。

### 9.4 取缓存 vs 重算:盈亏平衡
设 prefill 算 1 个 token 约 $c$ 微秒算力,从 SSD 搬 1 个 token 的 KV 回 HBM 约 $m$ 微秒。当 $m < c$,取缓存就划算;当前缀很长($k$ 很大)时,$k\cdot m$ vs $k\cdot c$ 的差距被放大——**前缀越长,复用越值**。Mooncake 用高带宽传输引擎把 $m$ 压到很小,并用调度预取把搬运藏到计算背后,使"取"几乎总是赢过"算"。

## 10. 对照 / 复杂度表

| 维度 | 一体化(PD 不分离) | 朴素 PD 分离 | Mooncake(KV 池化) |
|---|---|---|---|
| KV 归属 | 绑死单卡显存 | 各阶段卡内 | 集群共享分层池 |
| 显存上限 | HBM 即天花板 | HBM 即天花板 | HBM+DRAM+SSD 三层 |
| 前缀复用 | 几乎无 | 有限 | 全局前缀索引,跨请求复用 |
| prefill/decode 扩缩 | 绑定一起 | 各自独立 | 各自独立 + 缓存感知调度 |
| 调度 | 负载均衡 | 负载均衡 | 缓存感知 + 过载/SLO 感知 |
| 主要收益 | 简单 | 资源各取所需 | 省显存 + 提吞吐 + 降 TTFT |
| 主要代价 | 资源错配 | 跨节点传 KV | 传输/索引/分层管理复杂度 |

**复杂度直觉**:
- KV 显存:随序列长度 $S$ **线性** $O(S)$ 增长 → 必须分层。
- 前缀匹配:用 radix/trie,匹配近似 $O(\text{前缀长度})$。
- 传输成本:与命中前缀的 KV 字节量成正比,被高带宽 + 预取摊薄。

## 11. 常见问题(疑问→真相)

| 疑问 | 真相 |
|---|---|
| Mooncake 是个模型吗? | 不是。它是 Kimi 背后的**推理服务架构/系统**(及开源实现),与具体模型解耦。 |
| "KV 池化"是不是就是 PagedAttention? | 不是同一层。Paged 解决"单卡内 KV 碎片化分页";Mooncake 把视野拉到**跨节点、跨介质的共享池**,Paged 可作其块管理基础。 |
| 把 KV 放 SSD 不会很慢吗? | 慢的是 SSD 本身,但前提是"取回成本 < 重算成本"且用预取藏延迟;冷数据本就不在关键路径上。 |
| PD 分离不就够了吗,为何还要池? | PD 分离解决"算力错配";池化额外解决"显存墙 + 前缀重算"。两者叠加才完整。 |
| 前缀复用会不会串了不同用户的数据? | 复用的是**相同内容**前缀的 KV(按内容哈希匹配),内容不同自然不命中;隔离按内容与权限边界控制。 |
| 为什么说它"以 KVCache 为中心"? | 因为调度、分层、分离、复用,**全部围绕 KV 这份数据**来设计,而不是围绕"某张卡"或"某个请求"。 |
| 长上下文是不是它的最大受益场景? | 是。$O(S)$ 的 KV 显存让长上下文最先撞显存墙,池化+分层正好缓解;前缀复用对"长共享文档"也最划算。 |
| 具体的 API/部署参数怎么配? | 以官方文档与开源仓库为准(github.com/kvcache-ai/Mooncake);本文只讲稳定的原理与机制,不固化版本号/参数。 |
