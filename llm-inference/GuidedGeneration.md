## 0. 一句话锚点

**受限生成（Constrained / Guided / Structured Generation）= 在每一步解码时，先算出"当前合法的下一个 token 集合"，把所有非法 token 的 logits 设成 $-\infty$，再正常采样。**

结果：模型生成的文本**保证**能被 JSON 解析器 / 正则引擎 / 语法分析器接受——不是"提示词求它输出 JSON 然后祈祷"，而是从数学上**不可能**输出非法字符。

```
普通生成:   prompt ──► LLM ──► 采样 ──► 文本 ──► [可能解析失败 ❌]
受限生成:   prompt ──► LLM ──► logits ──► [掩码过滤] ──► 采样 ──► 文本 ──► [一定能解析 ✅]
                                              ▲
                                       约束(JSON/正则/语法)
```

## 1. 地基：它解决什么问题

### 1.1 LLM 的输出本质是"概率，不是结构"

回顾解码（详见 [[llm-inference/解码策略]]）：模型每一步输出一个长度为词表大小 $V$（常见 $V \approx 3.2\text{万} \sim 15\text{万}$）的向量 **logits**，记作 $z \in \mathbb{R}^V$。经过 softmax 得到下一个 token 的概率分布：

$$P(\text{token}_i) = \frac{e^{z_i / T}}{\sum_{j=1}^{V} e^{z_j / T}}$$

其中 $T$ 是温度。然后从这个分布里**采样**一个 token。

关键事实：**这个分布对"语法合法性"一无所知**。它只学到了"训练数据里常见的下一个词"。所以即使你在 prompt 里写"请输出合法 JSON"，模型在 99% 的步骤会配合，但只要有 1 步采样到了一个引号没闭合、逗号多了一个，整段 JSON 就废了。

### 1.2 为什么"可靠的结构化输出"是刚需

下游系统是**程序**，不是人。程序需要确定性：

```
LLM ──JSON──► 业务后端          需要: json.loads() 不抛异常
LLM ──工具调用 arguments──► 函数  需要: 字段名/类型精确匹配 schema
LLM ──SQL/正则/代码──► 执行器     需要: 语法可解析
Agent ──结构化 action──► 环境     需要: 枚举值在合法集合内
```

任何一次解析失败，传统做法是**重试**——重新跑一遍整个生成。在高 QPS 服务里这意味着：延迟翻倍、成本翻倍、且无上限保证（可能连续失败）。受限生成把"重试期望次数"从 $\frac{1}{p_{\text{success}}}$ 直接压到 **1**。

### 1.3 它能强制哪几类约束（由弱到强）

```
┌─────────────────────────────────────────────────────────┐
│ 选项约束 (Choice)   : 输出 ∈ {"yes","no","maybe"}         │  最简单
│ 正则约束 (Regex)    : 匹配 \d{4}-\d{2}-\d{2} (日期)       │  正则语言
│ JSON Schema         : 字段/类型/嵌套/必填 全部符合        │  ≈正则+语法
│ 语法约束 (Grammar)  : 符合一段 EBNF/CFG (如 SQL 子集)     │  上下文无关
└─────────────────────────────────────────────────────────┘
                                                              最强
```

核心洞察（来自论文《Efficient Guided Generation for LLMs》, Outlines 团队）：**正则和 JSON Schema 都可以编译成有限状态机（FSM）；更强的语法需要下推自动机。** 后面逐层拆。

## 2. 核心动作：在 logits 上加掩码

无论用什么约束，落地到引擎里只有一个统一动作——**logits processing（logits 处理 / logit bias）**。

```
                  ┌──────────── 每一步解码 ────────────┐
 已生成前缀  ──►   │  1. LLM forward → logits z[V]       │
 "{\"name\":"      │  2. 约束器: 算出合法 token 集合 A    │
                  │  3. 掩码: z[i] = -inf  若 i ∉ A     │
                  │  4. softmax + 采样 → next token     │
                  │  5. 用 next token 推进约束状态       │
                  └────────────────────────────────────┘
```

掩码的数学形式（记合法集合为 $A$）：

$$\tilde{z}_i = \begin{cases} z_i & i \in A \\ -\infty & i \notin A \end{cases}
\qquad\Rightarrow\qquad
P(i) = \frac{e^{\tilde z_i}}{\sum_j e^{\tilde z_j}} = 0,\ \forall i \notin A$$

因为 $e^{-\infty}=0$，非法 token 概率被精确归零，**采样永远碰不到它们**。这一步不改模型权重、不重训，纯推理期生效，所以可以对任何模型即插即用。

实现上 $A$ 用一个长度 $V$ 的 **bitmask（位掩码）** 表示，1=允许、0=禁止。掩码与温度、top-p、top-k 等采样手段**正交**：先掩码再做这些。重要细节：约束器还要负责决定**何时允许 EOS（结束符）**——只有当约束状态处于"可接受终止"时才放行 EOS，否则模型可能在 JSON 没闭合时就停了。

> 关键权衡：第 2 步"算出合法集合"如果每步都遍历整个词表 $V$ 去试，会非常慢。所有工程优化都在围绕"如何 $O(1)$ 或预计算地拿到这个集合"。这就引出 FSM。

## 3. 把约束编译成有限状态机 (FSM)

### 3.1 为什么是 FSM

正则表达式在理论上等价于**有限状态机（Finite State Machine）**。一个 FSM 是：

- 一组**状态** $Q$（比如"刚开始""读了几位数字""读完了"）；
- 一个**转移函数** $\delta(q, c) \to q'$：在状态 $q$ 读到字符 $c$，跳到状态 $q'$；
- **接受状态**集合（到这里就算匹配成功）。

把正则 `[0-9]{4}-[0-9]{2}` 编译成 FSM（按字符）：

```
     digit   digit   digit   digit    '-'    digit   digit
 s0 ─────► s1 ───► s2 ───► s3 ───► s4 ───► s5 ───► s6 ───► (接受)
            (任何不符合的字符 → 死状态 ✗)
```

在任意状态，**"合法的下一个字符"是确定且已知的**。比如在 s0，只允许 `0-9`；在 s4，只允许 `-`。

### 3.2 Outlines 的核心贡献：预编译 token×state 索引

朴素做法是 FSM 按**字符**走，但 LLM 按**token**走（一个 token 可能是 "name"、"123"、"\":" 这种多字符串）。如果每步都把候选 token 逐字符喂进 FSM 检查，复杂度是 $O(V \times \text{len})$。

Outlines 论文的关键优化：**离线预计算一张索引表**

$$\text{index}[\,q\,] = \{\text{所有能从状态 } q \text{ 出发被 FSM 接受的 token}\}$$

```
         预计算 (一次性, 编译期)
 ┌───────────────────────────────────────┐
 │ for 每个 FSM 状态 q:                    │
 │   for 每个 token t in 词表(V):          │
 │     把 t 的字符逐个喂进 FSM             │
 │     若全程不进死状态 → 把 t 加入 index[q]│
 │     记录 t 走完后到达的状态 q'          │
 └───────────────────────────────────────┘

         运行期 (每步解码)
 当前状态 q ──► index[q] 直接给出合法 token 集合 ──► 掩码
                       O(1) 查表, 不再遍历词表!
```

**这就是受限生成"几乎零额外延迟"的根本原因**：把昂贵的"算合法集合"搬到了生成开始前的编译阶段，运行期只是查表 + 套掩码。

```
时间轴:
 [编译约束→FSM→索引表]      [token1] [token2] [token3] ...
 └── 一次性, 几ms~几百ms ──┘ └─ 每步只是查表(微秒级) ─┘
```

## 4. 比正则更强：语法约束 (CFG/EBNF)

### 4.1 正则的天花板

正则（=FSM）**数不清括号嵌套**。例如"任意深度嵌套的 JSON 数组""配平的括号""JSON 里对象套对象套数组"——这些是**上下文无关语言（Context-Free Grammar, CFG）**，FSM 表达不了，因为 FSM 只有有限个状态，记不住"还差几个右括号"。

> 实践注脚：很多 JSON Schema 约束在**固定深度**下仍可用 FSM 近似（把嵌套展开成有限层），但要支持**任意递归**结构就必须上语法。

### 4.2 用下推自动机 (PDA) + 栈

CFG 对应**下推自动机（Pushdown Automaton, PDA）**= FSM + 一个**栈**。栈用来记住"还没闭合的结构"。

```
 输入: { "a": [ 1, 2 ] }
 栈演化:
   读 {  → push '}'        栈: [}]
   读 [  → push ']'        栈: [} ]]
   读 ]  → pop, 匹配 ✓     栈: [}]
   读 }  → pop, 匹配 ✓     栈: []   ← 空栈=合法终止
```

每一步合法的 token 集合 = "语法在当前栈顶 + 已读前缀下，允许接续的终结符"。XGrammar、llama.cpp 的 GBNF、Outlines 的 CFG 模式都走这条路。

### 4.3 工程难点：语法约束更难预计算

CFG 的"当前合法集合"依赖**栈内容**，而栈是无界的，无法像 FSM 那样把所有 (状态→合法 token) 全部离线打表。所以语法约束通常采用：

```
 预计算: 把语法每个"上下文相关展开"能在词表里命中的 token 缓存起来 (XGrammar 的"自适应 token 掩码缓存")
 运行期: 大部分 token 走缓存的"上下文无关"快路; 少数依赖栈的走慢路实时检查
```

XGrammar 的思路是把词表 token 分成"上下文无关 token"（多数，可缓存）和"上下文相关 token"（少数，运行期检查），并用字节级 Trie 加速，从而把语法掩码的开销也压到接近零。

## 5. 最难的坑：token 与字符不对齐

这是受限生成所有 bug 的源头，必须讲透。

**约束是按字符/字节定义的，但 LLM 按 token 生成。** 一个 token 边界可能横跨约束的两个状态。

例子：正则要求输出 `true`。词表里可能恰好有一个 token 就叫 `"true"`，也可能 `true` 被拆成 `tr` + `ue`，还可能有个 token 是 `"true,"`（带逗号，在代码语料里常见）。

```
 想匹配: t r u e
 词表可能的切法:
   ① [true]          ← 一个 token 直接搞定
   ② [tr][ue]        ← 两个 token
   ③ [t][rue]        ← 另一种切法
   ④ [true,]         ← 危险! 多吞了一个逗号
```

后果与对策：

| 问题 | 说明 | 对策 |
|---|---|---|
| 多 token 拼一个字符串 | FSM 必须支持"一个 token 推进多个字符状态" | 预编译时按 token 整体喂 FSM，记录跨字符跳转 |
| 一个 token 跨越约束边界 | 如 `true,` 把分隔符也吞了 | 索引表里这种 token 只在"接下来正好需要逗号"时才合法 |
| 空格/前导空白 token | `▁true`（带空格前缀）vs `true` | 约束需感知 tokenizer 的字节级表示（BPE/SentencePiece） |
| Unicode 多字节 | 一个汉字 = 多字节，可能跨 token | 在**字节级** FSM 上做，而非字符级 |

**结论**：正确的受限生成必须在**该模型自己的 tokenizer 词表**上编译约束——换模型就要重编译。这也是为什么约束器和 tokenizer 强绑定。

## 6. 性能影响：开销到底在哪

### 6.1 三段开销

```
 ┌──────────────┬───────────────────────┬──────────────────────┐
 │ 编译期(一次)  │ 把约束→FSM/PDA→索引表  │ 几 ms ~ 几百 ms        │
 │              │ 复杂正则/大schema更久  │ 可缓存! 相同schema复用 │
 ├──────────────┼───────────────────────┼──────────────────────┤
 │ 运行期/每步   │ 查索引表 + 套位掩码     │ FSM: 微秒级, 近乎免费  │
 │              │ 语法慢路径偶尔实时计算  │ CFG: 略高但仍小        │
 ├──────────────┼───────────────────────┼──────────────────────┤
 │ 间接收益      │ 跳过非法分支, 不重试    │ 端到端可能更快!        │
 └──────────────┴───────────────────────┴──────────────────────┘
```

### 6.2 为什么有时**反而更快**（关键反直觉点）

受限生成有时让端到端**总 token 数减少**：因为模型被约束在"必填字段"上，不会生成寒暄、解释、markdown 代码块围栏（```json）等多余内容。少生成 token = 少 forward = 更快。再叠加"不重试"，端到端吞吐常常**优于**无约束。

### 6.3 它对采样质量的影响（要警惕）

掩码会**重新归一化**分布。如果约束和模型的"自然意图"冲突，可能把概率挤到模型本不想要的 token 上，导致输出质量下降或"机械"。

```
 模型本想说: P(" Sure")=0.6  P("{")=0.05  ...
 JSON约束:    " Sure" 非法 → 掩掉
 归一化后:    "{" 被迫升到 1.0  (即使模型对此"不自信")
```

缓解：约束要尽量贴合模型已学到的格式（用模型熟悉的 schema 风格）、配合好的 prompt、合理温度。

### 6.4 对批处理/连续批处理的影响

在 vLLM / SGLang（见 [[llm-inference/sglang/README]]）这类引擎里，**每个请求有自己的约束状态**。在连续批处理（continuous batching）中：

```
 batch step:  req1(JSON状态q3)  req2(正则状态s5)  req3(无约束)
              ↓ 各自查各自索引表 ↓
 掩码必须 per-request 应用 → 引擎要为每条请求维护独立 FSM 指针
```

工程上需要把"per-request 掩码"做成可并行的 GPU 操作（一个 `[batch, V]` 的掩码张量），避免在 CPU 上逐条 Python 循环成为瓶颈。这正是 XGrammar 等强调"GPU 上批量套掩码"的原因。SGLang 的 **RadixAttention** 还能让相同约束前缀复用 KV cache，进一步省算力（以官方文档为准）。

## 数值例子：手算一个 JSON 约束

**场景**：约束输出 `{"age": <整数>}`，词表简化为 8 个 token。

词表（简化）：

```
id: 0=`{"age":`  1=`}`  2=`0`  3=`1` ... (数字)  6=`Hello`  7=` the`  8=`<EOS>`
```

FSM 状态：`S0`(起点) → `S1`(读了开头) → `S2`(读了≥1位数字) → `S3`(闭合,接受)

预编译索引表：

```
 index[S0] = {0}            ← 只允许 `{"age":`
 index[S1] = {2,3,4,5}      ← 只允许数字 token
 index[S2] = {2,3,4,5, 1}   ← 数字(继续) 或 `}`(闭合)
 index[S3] = {8}            ← 只允许 EOS
```

**逐步推演**（假设模型 logits 原始排序，但被掩码裁剪）：

| 步 | 状态 | 模型想要的(原始top) | 合法集合 | 实际可选 | 选中 |
|---|---|---|---|---|---|
| 1 | S0 | `Hello`(0.7) | {0} | 只剩 `{"age":` | `{"age":` |
| 2 | S1 | ` the`(0.5) | {2,3,4,5} | 只剩数字 | `4`(=token 5 假设) |
| 3 | S2 | `Hello`(0.4) | {2,3,4,5,1} | 数字 或 `}` | `}` |
| 4 | S3 | 任意 | {8} | 只剩 EOS | `<EOS>` |

输出：`{"age":4}` —— **保证合法**，即使第 1、2、3 步模型"本来想跑题"。

**开销估算**：设 $V=128000$，FSM 状态数 $|Q|=50$。

- 预编译索引表大小 ≈ $|Q| \times V$ 个 bit $= 50 \times 128000 / 8 \approx 0.8$ MB，可常驻并跨请求复用。
- 每步运行期：一次查表（$O(1)$）+ 一次 $[V]$ 位掩码加法（在 GPU 上与 softmax 同量级，约几微秒）。
- 对比无约束每步 forward 通常是**毫秒级**，掩码开销占比 < 1%，可忽略。

## 对照表（与同类对比）

| 方案 | 约束能力 | 核心机制 | 何时选 | 关键权衡 |
|---|---|---|---|---|
| **Prompt 工程**(求模型输出JSON) | 无强制 | 仅靠提示 | 快速原型/无引擎支持 | 不保证合法，要重试 |
| **logit_bias 手动**(OpenAI 等) | 弱(限选项) | 手填 token 偏置 | 限定几个选项 | 难表达复杂结构 |
| **Outlines** | 正则/JSON/CFG | FSM 预编译索引表(论文方法) | 通用、可读性好 | CFG 模式较重 |
| **lm-format-enforcer** | JSON/正则 | 逐步剪枝合法 token | 与 HF/vLLM 易集成 | 纯 Python 路径可能慢 |
| **XGrammar** | JSON/EBNF 语法 | 上下文无关 token 缓存 + 字节 Trie + GPU 批量掩码 | 高吞吐生产、语法约束 | 实现复杂(已被多引擎集成) |
| **llama.cpp GBNF** | EBNF 语法 | PDA + 栈 | 本地/边缘部署 | 生态偏 C++ |
| **引擎内置**(vLLM `guided_json` / SGLang) | JSON/正则/语法 | 集成上述后端 | 已用该引擎服务 | 受引擎版本支持限制(以官方文档为准) |

> 趋势：FSM 路线（Outlines）解决了"近乎零运行期开销"，XGrammar 进一步把**语法**约束的开销也压到接近零并支持批量 GPU 掩码，逐渐成为各推理引擎（vLLM/SGLang/TGI）的默认结构化生成后端之一。

## 常见问题

| 问题 | 解答 |
|---|---|
| 它会改变模型权重吗？ | 不会。纯推理期对 logits 做掩码，对任何模型即插即用。 |
| 为什么 prompt 求 JSON 不够？ | 概率采样总有非零概率走偏；受限生成把非法 token 概率**精确**置 0。 |
| 会让结果变笨吗？ | 可能。掩码强行归一化，若约束与模型意图冲突会牺牲质量；schema 越贴近自然格式越好。 |
| 慢吗？ | 编译有一次性开销（可缓存）；运行期 FSM 几乎免费，语法约束略高；常因少生成废话+不重试而端到端更快。 |
| JSON Schema 一定能转 FSM 吗？ | 固定深度可以；**任意递归**嵌套需上语法（CFG/PDA）。 |
| 换模型要重做吗？ | 要。约束编译绑定该模型 tokenizer 的词表，换 tokenizer 必须重编译。 |
| 能保证语义正确（如 age 合理）吗？ | 不能。只保证**结构/语法**合法，不保证**内容/数值**有意义。 |
| 批处理里每条请求约束不同怎么办？ | 引擎为每个请求维护独立 FSM/栈指针，掩码 per-request 并行套在 `[batch,V]` 上。 |
| 流式输出受影响吗？ | 不影响逐 token 流式；每生成一个 token 即推进约束状态并发送。 |
