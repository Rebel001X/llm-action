## 0. 一句话锚点

**传统推理引擎在任一时刻只让 GPU 的一种资源（算力 或 显存带宽 或 网络）忙碌，其余两种闲着。NanoFlow 把一个 batch 在卡内再切成若干 nano-batch，让"算 / 读写显存 / 跨卡通信"在同一时刻分别由不同 nano-batch 占用，三条流水线并行推进，从而把单卡利用率从"轮流忙"提升到"同时忙"。**

记住这张时间轴对比图（后文展开）：

```
传统(串行)：  [GEMM算]→[AllReduce通信]→[Attention访存]→[GEMM算]→...
              算力忙   算力闲          算力闲          算力忙
              通信闲   通信忙          通信闲          通信闲
              访存闲   访存闲          访存忙          访存闲
              ↑ 每个时刻只有一种资源在干活，其余白白浪费

NanoFlow：    nB0:[算]   nB0:[通信] nB0:[访存]
              nB1:    [算]      nB1:[通信] nB1:[访存]
              nB2:         [算]       nB2:[通信] ...
              ↑ 错位流水后，同一竖直时刻 算+通信+访存 都有 nano-batch 在用
```

## 1. 地基：它到底解决什么问题

### 1.1 一次 LLM 前向里发生了什么

给定一个 Transformer 层，推理时大致顺序执行这些操作：

1. **QKV 投影**：输入 $X$ 乘权重矩阵 → 大 GEMM（矩阵乘），**吃算力（Tensor Core）**。
2. **Attention**：$\text{softmax}(QK^\top/\sqrt{d})V$，要把 **KV Cache 从显存搬进搬出**，**吃显存带宽（HBM）**。
3. **AllReduce / AllGather**：张量并行（TP）下，多卡之间要把部分结果加起来，**吃通信带宽（NVLink / NIC）**。
4. **FFN（MLP）**：两个大 GEMM，**又吃算力**。

把它画出来：

```
 一个 Transformer 层的资源画像
 ┌──────────┬───────────┬────────────┬──────────┐
 │ QKV GEMM │ Attention │  AllReduce │  FFN GEMM│
 ├──────────┼───────────┼────────────┼──────────┤
 │ 算力 ███ │ 访存 ███   │ 通信 ███    │ 算力 ███ │
 │ 访存 ·   │ 算力 ·     │ 算力 ·      │ 访存 ·   │
 │ 通信 ·   │ 通信 ·     │ 访存 ·      │ 通信 ·   │
 └──────────┴───────────┴────────────┴──────────┘
   每个阶段都只"重度使用一种资源"，是天然的瓶颈错位
```

### 1.2 问题一句话

> 单个算子（GEMM、Attention、AllReduce）几乎**只能压满一种资源**。串行执行时，GPU 在每个阶段都有大量空闲单元。**这就是单卡利用率上不去的根因**——不是 batch 太小，而是资源在时间上"轮流忙"。

## 2. 先把 GPU 的三类资源讲到原子

| 资源 | 物理载体 | 谁吃它 | 类比 |
|------|----------|--------|------|
| **计算 Compute** | Tensor Core / CUDA Core | 大矩阵乘 GEMM（QKV、FFN） | 工人的"手"——做乘加 |
| **访存 Memory** | HBM 显存带宽 | Attention 读写 KV Cache、加载权重 | 工人去"仓库"取料 |
| **通信 Comm** | NVLink（卡间）/ NIC（机间） | TP/EP 的 AllReduce、AllGather | 工人之间"传话" |

关键事实：**这三套硬件单元是物理上独立的电路**。Tensor Core 在算的时候，显存控制器和 NVLink 引擎完全可以同时工作——只要你给它们活干。传统引擎没给，所以它们闲着。

```
           一张 GPU 内部（简化）
   ┌─────────────────────────────────────┐
   │  ┌──────────┐  ┌──────────┐         │
   │  │TensorCore│  │CUDA Core │ ← 计算单元│
   │  └──────────┘  └──────────┘         │
   │  ┌──────────────────────────┐       │
   │  │   HBM 显存 + 带宽         │ ← 访存 │
   │  └──────────────────────────┘       │
   │  ┌──────────────────────────┐       │
   │  │  NVLink / NIC 引擎        │ ← 通信 │
   │  └──────────────────────────┘       │
   └─────────────────────────────────────┘
   三者并行能力天生存在，问题是"同一时刻有没有被同时调度"
```

## 3. 为什么"开了大 batch / 连续批"还是压不满

很多人以为：把 batch 调大、用 continuous batching 塞满请求，利用率就上去了。**对一半，错一半。**

- 大 batch **确实**能让单个 GEMM 更接近算力峰值（提升算术强度，从访存瓶颈走向算力瓶颈）。
- 但它**改变不了"算子串行"这件事**：再大的 batch，QKV GEMM 跑的时候 NVLink 还是闲的；AllReduce 跑的时候 Tensor Core 还是闲的。

```
 大 batch 的效果              NanoFlow 的效果
 ┌─────────────┐            ┌─────────────┐
 │ 把每个台阶   │            │ 把不同台阶   │
 │ 加宽(吞吐↑)  │            │ 在时间上重叠 │
 │ 但仍是台阶   │            │ (填平空隙)   │
 └─────────────┘            └─────────────┘
  纵向(单算子更满)            横向(跨算子并行)
```

> 结论：连续批解决的是"**请求维度**"的空隙（让 GPU 不要因为某条请求结束而空转）；NanoFlow 解决的是"**资源维度**"的空隙（让算力/访存/通信不要轮流闲置）。两者**正交，可叠加**。详见第 6 节层次关系。

## 4. 核心思想：nano-batch 切分

### 4.1 定义

把当前要执行的**全局 batch**（一批 token，可能来自很多请求），在**单卡内部**沿 batch 维度再切成几份小块，每一份叫一个 **nano-batch**（纳米批）。

```
 全局 batch (例如 512 个 token 的隐藏态)
 ┌──────────────────────────────────────┐
 │  t0 t1 t2 ... t511                    │
 └──────────────────────────────────────┘
                 │ 切成 4 份
                 ▼
 nano-batch:  [nB0:128][nB1:128][nB2:128][nB3:128]
```

### 4.2 为什么"切小"反而更快——关键直觉

切小**不是**为了减少计算量（总量不变，单看更慢，因为 GEMM 变小算术强度略降）。切小是为了制造**可以错位流水的独立单元**：

- nB0 做完 GEMM（用算力）后，去做 AllReduce（用通信）；
- **就在 nB0 通信的这段时间**，nB1 接着上 Tensor Core 做它的 GEMM；
- nB2、nB3 依次跟进。

于是同一时刻：nB0 在通信、nB1 在算、nB2 在访存……**三类资源被不同 nano-batch 同时点亮**。

```
 时间 →
 算力轴:   [nB0 GEMM][nB1 GEMM][nB2 GEMM][nB3 GEMM]
 通信轴:            [nB0 AR ][nB1 AR ][nB2 AR ][nB3 AR]
 访存轴:                     [nB0 Att][nB1 Att][nB2 Att]
              ↑ 中段每一竖列都同时有 算/通/访 在跑 = 三资源重叠
```

这就是 NanoFlow 名字的来源：用 **nano** 级别的细粒度切分，制造 **flow**（流水）。

## 5. intra-device 并行调度：三资源如何被"同时"喂饱

"intra-device"= **设备内部**。区别于把不同层放到不同卡（inter-device / 流水线并行）。NanoFlow 的并行发生在**一张卡里**。

实现"同时"需要三件事：

1. **操作分类（operation-level 资源标注）**：把每个 kernel 标成"算力型 / 访存型 / 通信型"，知道它主要吃哪种资源。
2. **执行单元隔离**：让不同资源的 kernel 跑在**不同的执行通道**上（在 CUDA 里通常对应不同的 stream / 用 SM 划分把 GEMM 和通信 kernel 放到不同 SM 子集，避免互相抢占）。
3. **依赖编排（operation scheduling）**：按 nano-batch 间的依赖关系，把"算→通→访"的接力顺序排成稳定流水，让流水线满载段尽量长。

```
              NanoFlow 单卡调度器
 ┌─────────────────────────────────────────────┐
 │  全局 batch 进来                              │
 │         │                                     │
 │   ┌─────▼──────┐  切分                         │
 │   │ Nano 切分器 │ → nB0 nB1 nB2 nB3             │
 │   └─────┬──────┘                              │
 │         │                                     │
 │   ┌─────▼───────────────────────────┐         │
 │   │  资源感知调度器                  │         │
 │   │  ┌────────┐ ┌────────┐ ┌───────┐ │         │
 │   │  │算力通道│ │访存通道│ │通信通道│ │         │
 │   │  │(部分SM)│ │(部分SM)│ │(NVLink)│ │        │
 │   │  └────────┘ └────────┘ └───────┘ │         │
 │   │   nB们错位流过这三条通道          │         │
 │   └─────────────────────────────────┘         │
 └─────────────────────────────────────────────┘
```

> 关键权衡：把 SM 划给通信 kernel，意味着 GEMM 能用的 SM 变少、单个 GEMM 变慢；但换来通信"免费"地与计算并行。**只有当节省的串行通信时间 > GEMM 因 SM 减少而变慢的时间，重叠才划算**。NanoFlow 的调度就是在搜这个平衡点。具体 SM 划分比例随模型/硬件而变，**以官方实现与文档为准**。

## 6. 与"连续批 continuous batching"的层次关系

这是本主题最容易混的点，单独讲清。

```
 ┌───────────────────────────────────────────────┐
 │ 第3层 请求调度：Continuous Batching             │
 │   决定"哪些请求的哪些 token 进入这一步前向"      │
 │   解决：请求间空隙(有的请求长/短，不要空等)      │
 ├───────────────────────────────────────────────┤
 │ 第2层 全局 batch 形成：一步要算的 token 集合     │
 ├───────────────────────────────────────────────┤
 │ 第1层 卡内执行：NanoFlow nano-batch 流水         │
 │   决定"这一步前向在卡内怎么切、怎么重叠三资源"   │
 │   解决：资源间空隙(算/通/访不要轮流闲)           │
 └───────────────────────────────────────────────┘
        ↑ 连续批在"上面"决定批的内容
        ↑ NanoFlow 在"下面"决定这批怎么高效执行
```

| 维度 | 连续批 Continuous Batching | NanoFlow Nano-batching |
|------|----------------------------|------------------------|
| 解决的空隙 | **请求维度**（迭代级动态进出） | **资源维度**（计算/访存/通信） |
| 工作层 | 调度/请求管理层 | 单卡 kernel 执行层 |
| 切分对象 | 一步要不要纳入某请求的 token | 已成形 batch 在卡内再切 nano |
| 是否互斥 | 否 | 否——**可叠加** |

> 正确心智模型：**先用连续批把一个尽量满的全局 batch 攒出来 → 再交给 NanoFlow 在卡内把这批的三类资源重叠跑满**。

## 7. 整体架构与执行流

```
 请求流入
   │
   ▼
┌──────────────────┐
│ 连续批调度器      │  形成本步全局 batch
└────────┬─────────┘
         ▼
┌──────────────────┐
│ NanoFlow 切分器   │  batch → nB0..nBk
└────────┬─────────┘
         ▼
┌─────────────────────────────────────────┐
│ 单卡流水执行（逐 Transformer 层）          │
│   for layer in layers:                    │
│     for nB in nano-batches:               │
│       算: QKV/FFN GEMM   ─┐               │
│       通: AllReduce       ─┼ 错位重叠      │
│       访: Attention(KV)   ─┘               │
└────────┬─────────────────────────────────┘
         ▼
   token 输出 → 回连续批调度器，进入下一迭代
```

执行循环的伪逻辑（示意，非真实 API）：

```
切分 batch 为 [nB0, nB1, nB2, nB3]
建立 stream_compute / stream_comm / stream_mem 三条通道
for 每个 nano-batch i:
    在 stream_compute 上发 GEMM(i)
    GEMM(i) 完成后，在 stream_comm 上发 AllReduce(i)   # 与 GEMM(i+1) 并行
    在 stream_mem  上发 Attention(i) 访存
通过事件(event)依赖把三条流水对齐，使满载段最大化
```

## 数值例子 / 手算（重叠前后吞吐对比）

设一个 Transformer 层在某卡上，单个全局 batch 各阶段串行耗时（假设值，便于算账）：

| 阶段 | 主吃资源 | 串行耗时 |
|------|----------|----------|
| GEMM（QKV+FFN） | 算力 | $4.0$ ms |
| Attention | 访存 | $2.0$ ms |
| AllReduce | 通信 | $2.0$ ms |

**串行总时间** = $4.0 + 2.0 + 2.0 = 8.0$ ms / 层。

**NanoFlow 重叠（理想上界）**：三条流水并行，层耗时趋近于"最长那条资源轴的占用"。把 batch 切 4 份后，每类资源被均匀铺开，理论下界 ≈ $\max(4.0, 2.0, 2.0) = 4.0$ ms（算力为瓶颈轴），再加上流水**填充 + 排空**的头尾开销 ≈ $1.0$ ms：

$$
T_{\text{nano}} \approx \max(\text{算},\ \text{访},\ \text{通}) + T_{\text{头尾}} = 4.0 + 1.0 = 5.0\ \text{ms}
$$

**加速比**：

$$
\text{Speedup} = \frac{8.0}{5.0} = 1.6\times
$$

对应**单卡有效吞吐**（token/s，假设每步处理 512 token）：

- 串行：$512 / 0.008 = 64{,}000$ token/s
- NanoFlow：$512 / 0.005 = 102{,}400$ token/s

**利用率视角**：串行时算力轴在 8.0 ms 里只忙了 4.0 ms → 算力利用率 ≈ $4/8 = 50\%$；重叠后算力轴在 5.0 ms 里忙 4.0 ms → ≈ $4/5 = 80\%$。**这就是"提升单卡利用率"的量化含义**。

> 注意：以上为讲解用的假设数字。真实收益取决于三类资源耗时是否接近（越接近，重叠收益越大；若某一资源极度主导，重叠空间就小）、切几份 nano-batch、SM 划分比例与流水头尾开销。**具体数值以官方 benchmark 为准。**

```
 资源轴占用对比（█=忙 ·=闲，每格0.5ms）
 串行(8ms):
   算力 ████████········  (8忙? 否, 实为 GEMM4ms 段)
   实际→ 算 ████····  访 ····██··  通 ······██   ← 互不重叠
 NanoFlow(5ms):
   算力 ████████        (≈一直忙)
   访存 ··████··
   通信 ····████
        ↑ 头尾各有少量填充/排空空隙
```

## 对照表（与同类对比）

| 引擎 | 核心优化层次 | 是否做卡内三资源重叠 | 定位 |
|------|--------------|----------------------|------|
| **NanoFlow** | 单卡 nano-batch 流水 | **是（核心卖点）** | 把单卡利用率推到极限的吞吐引擎 |
| **vLLM** | PagedAttention + 连续批 | 否（重在显存管理与请求调度） | 高吞吐、易用的通用服务引擎 |
| **TGI（HF）** | 连续批 + 张量并行 | 否 | 生产级服务部署 |
| **TensorRT-LLM** | 编译期 kernel 融合 + 量化 | 部分（kernel 级融合/重叠，非 nano-batch 调度） | 极致单 kernel 性能 |
| **DeepSpeed-Inference** | 张量/流水并行 + kernel 注入 | 否 | 大模型多卡推理 |

> 选型直觉：
> - 想要**最大化单卡/单机吞吐**、愿意接受较新、研究性更强的系统 → 关注 NanoFlow 的思路。
> - 要**稳健好用的通用服务**、生态成熟 → vLLM。
> - 要**编译期榨干单 kernel + 量化** → TensorRT-LLM。
> - NanoFlow 的"卡内重叠"思想与上述并不冲突，**可以叠加在连续批 / Paged KV 之上**。

## 与 [[llm-optimizer/计算通信重叠]] 的关系

NanoFlow 是"计算通信重叠"思想的一个**系统化、自动化、细到 nano-batch 粒度**的落地：

- 传统"计算通信重叠"常指：把 TP 的 AllReduce 拆段，与 GEMM 分块流水（如 把一个 matmul 切块，算完一块就开始 reduce 这块）。
- NanoFlow 把这个思想**推广到三类资源**（多加了"访存"这一轴，把 Attention 的 KV 访存也纳入重叠），并把切分单位上升到**整个 batch 的 nano 切片**，让调度更统一、覆盖整层而非单算子。

## 常见问题

| 问题 | 解答 |
|------|------|
| nano-batch 切越多越好吗？ | 不是。切多了流水头尾开销和 kernel 启动开销上升、单 GEMM 更小算术强度更低。存在最优份数（常见 2~4，**以实测为准**）。 |
| 它需要多卡吗？ | 通信轴（AllReduce）在 TP/多卡时最明显；单卡也能重叠"算 vs 访存"两轴，但三资源全开通常在 TP 场景收益最大。 |
| 和 FlashAttention 冲突吗？ | 不冲突。FlashAttention 优化的是 Attention 这个 kernel 内部（少访存），NanoFlow 决定的是这些 kernel 之间怎么重叠调度，两者叠加。 |
| 为什么不直接靠 CUDA 多 stream 自动重叠？ | 多 stream 给了并行可能，但默认调度不会智能地按资源类型错位、也不会划分 SM 防抢占。NanoFlow 的价值在**资源感知的显式编排**。 |
| 会增加显存吗？ | nano 切分本身不显著增显存（同一 batch 的子集），但需要为多条流水保留中间缓冲，略有上升。 |
| 延迟会变差吗？ | 单请求延迟可能因切分流水略有变化，但目标是**吞吐**（throughput）最大化；典型适用于吞吐优先的离线/高并发在线场景。 |
| 适合 prefill 还是 decode？ | prefill（计算密集、batch 大）三资源更易铺满，重叠收益通常更显著；decode（访存密集、batch 小）收益取决于能否攒出足够 nano 份数。 |
