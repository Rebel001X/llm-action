## 0. 一句话锚点

**KV Cache = 自回归生成时,把已经算过的每层每头的 Key 向量和 Value 向量存起来,下一步只算新 token 的 Q 去跟旧 K/V 做注意力,从而把每步复杂度从 $O(n^2)$ 摊销到 $O(n)$。** 代价是显存:序列越长、batch 越大,KV Cache 越能吃满显存,甚至超过模型权重本身。所有优化都围绕「这块显存」展开。

---

## 1. 地基:为什么必须缓存 K/V(从最底层讲起)

### 1.1 注意力一步在算什么

单头注意力:对当前 query 向量 $q_t$,与历史所有 key $k_1..k_t$ 做点积得分,softmax 后对 value 加权求和。

$$\text{attn}(q_t) = \sum_{i=1}^{t} \underbrace{\frac{\exp(q_t\cdot k_i/\sqrt d)}{\sum_j \exp(q_t\cdot k_j/\sqrt d)}}_{\text{权重}\,a_{ti}} \; v_i$$

### 1.2 不缓存会怎样:重复计算爆炸

生成第 $t$ 个 token 时,需要 $k_1..k_t$ 和 $v_1..v_t$。这些 $k_i, v_i = W_K x_i,\,W_V x_i$ **只依赖于第 $i$ 个 token 的输入** $x_i$,而 $x_i$ 在第 $i$ 步就固定了,后面永远不变。

```
不缓存(每步重算全部历史):          缓存(每步只算新 token):
step1: K[1]                          step1: 算 K[1] V[1]  → 存
step2: K[1] K[2]      ← 重算 K[1]    step2: 算 K[2] V[2]  → 追加
step3: K[1] K[2] K[3] ← 又重算       step3: 算 K[3] V[3]  → 追加
总投影量 ∝ 1+2+3+... = O(n²)         总投影量 ∝ n  = O(n)
```

**为什么只缓存 K/V 不缓存 Q?** 因为 $q_t$ 只在当前步用一次(去查历史),下一步换成 $q_{t+1}$,旧的 $q_t$ 再也用不到;而 $k_i,v_i$ 在之后每一步都要被复用。这是 KV Cache 名字的由来。

### 1.3 两个阶段(承接 [[llm-inference/PD分离]])

```
Prefill(预填充): 一次性吃整段 prompt → 并行算出所有 K/V,塞满 cache。算力(compute)瓶颈。
Decode (解码):   一次吐 1 个 token  → 只追加 1 列 K/V。访存(memory)瓶颈,KV Cache 是主要被读对象。
```

Decode 阶段每生成一个 token 就要把**整个 KV Cache 读一遍**算注意力 → KV Cache 越大,decode 越慢。所以「省显存」往往同时「提速度」,这是优化的双重动机。

## 2. KV Cache 显存账(核心公式)

### 2.1 单个 token 占多少字节

每个 token,在**每一层**都要存一份 K 和一份 V,每份是 `头数 × 每头维度` 个数,每个数占 `精度字节`。

$$\boxed{\text{bytes/token} = 2 \times L \times n_{kv} \times d_h \times b}$$

- $2$:K 和 V 各一份
- $L$:层数(num layers)
- $n_{kv}$:**KV 头数**(注意不是注意力头数 $n_q$!MQA/GQA 在这里做文章)
- $d_h$:每头维度 = $d_{model}/n_q$
- $b$:每元素字节数(FP16=2,INT8=1,INT4=0.5)

### 2.2 整个 cache

$$\text{KV total} = \text{bytes/token} \times S \times B$$

$S$=序列长度(prompt+已生成),$B$=batch size。

```
内存布局(一层,一个 batch 元素):
          d_h 列
       ┌───────────┐
头0    │ k k k ... │  ┐
头1    │ k k k ... │  │ n_kv 行(K)
...    │ ...       │  ┘
头0    │ v v v ... │  ┐
...    │ ...       │  │ n_kv 行(V)
       └───────────┘  ┘
        × L 层 × S token × B batch
```

> 关键直觉:KV Cache 大小**线性正比于 $S$ 和 $B$**。要服务长上下文 / 高并发,这块会比权重还大 —— 见第 9 节手算。

## 3. PagedAttention:像操作系统分页消碎片

### 3.1 问题:连续分配 → 内部+外部碎片

传统实现给每个请求**预留**一段连续显存,按「最大可能长度」分配。

```
请求A(实际用了 300 / 预留 2048):
[████░░░░░░░░░░░░░░░░░░░░░░░░░░]  ← 浪费 1748 (内部碎片)
请求B 来了想要 2048 连续块,但剩余被切碎放不下 → 外部碎片
实测传统方案有效利用率常 < 40%。
```

### 3.2 解法:KV 也分页(vLLM 提出)

把 KV Cache 切成固定大小的 **block(页)**(如每页 16 个 token 的 KV),逻辑序列通过一张 **block table(页表)** 映射到物理页,物理页可以**不连续**。

```
逻辑视角(请求A的token序):  [t0..t15][t16..t31][t32..t47]
                              │        │         │
block table(页表)           ▼        ▼         ▼
物理显存池(乱序复用):     page#7   page#2    page#9
                            ┌────┐  ┌────┐   ┌────┐
                            │KV  │  │KV  │   │KV  │  ← 物理上不相邻
                            └────┘  └────┘   └────┘
```

- **按需分配**:写满一页才申请下一页 → 内部碎片 ≤ 一页(实测浪费 <4%)。
- **外部碎片消失**:所有页等大,任意空闲页都能用。
- **天然支持共享**:多个请求的页表可指向同一物理页(引用计数),这是前缀复用与 beam search 共享的底座。

**权衡**:多一层页表间接寻址(轻微开销),需要定制 attention kernel 来处理非连续内存(PagedAttention kernel)。收益远大于成本,已成事实标准。

## 4. 前缀复用(Prefix Caching / 自动前缀缓存)

### 4.1 动机

很多请求共享同一**前缀**:系统提示词(system prompt)、few-shot 示例、RAG 拼接的相同文档、多轮对话的历史。这段前缀的 K/V 对每个请求算出来**完全一样**。

```
请求1: [系统提示 600 tok][用户问题A 20 tok]
请求2: [系统提示 600 tok][用户问题B 30 tok]
                  ▲ 这 600 token 的 KV 一模一样,算两遍纯属浪费
```

### 4.2 解法:复用前缀的 KV 页

基于第 3 节的分页 + 引用计数:对前缀做哈希,命中则**直接指向已存在的物理页**,跳过这段的 prefill 计算。

```
共享前缀页(只算/只存一次):
   page#1 page#2 ... page#37   ← "系统提示"的 KV
     ▲                  ▲
请求1 页表 ────┘                  └──── 请求2 页表 也指过来
请求1 私有: page#80(问题A)
请求2 私有: page#81(问题B)   ← 只为各自后缀分配新页
```

- **省的是什么**:省掉前缀的 prefill FLOPs(首 token 延迟 TTFT 大降)+ 省掉重复存储。
- **何时收益最大**:长系统提示、agent 工具说明、RAG 固定文档、多轮对话。
- **失效场景**:前缀不同(哪怕只差一个 token,后续 KV 全因位置/注意力依赖而不同)→ 命中率取决于业务前缀稳定性。

## 5. 量化 KV:用更少字节存同一份缓存

### 5.1 思路

公式里 $b$(每元素字节)直接乘在总量上。FP16→INT8 显存对半;→INT4 砍到 1/4。这与权重量化(见 [[llm-compression/quantization/量化基础]])同源,但对象是**激活值缓存**而非权重。

### 5.2 对称量化一步手算

把一段 K 值用 INT8 表示。设某通道一组值 $\max|x| = 3.2$:

$$\text{scale} = \frac{\max|x|}{2^{b-1}-1} = \frac{3.2}{127} = 0.0252$$

量化:$x_q = \text{round}(x / \text{scale})$,例如 $x=1.5 \Rightarrow \text{round}(1.5/0.0252)=\text{round}(59.5)=60$。
反量化:$\hat x = 60 \times 0.0252 = 1.512$,误差 $0.012$。

### 5.3 工程要点(为什么不能无脑量化)

```
K 和 V 的分布不同 → 常分开处理:
  K: 通道间存在尖锐离群值(outlier channel)→ 倾向 per-channel 量化
  V: 分布较平 → per-token 量化即可
量化粒度:per-tensor(最省/最糙) < per-token < per-channel(最准/开销大)
```

- **权衡**:精度下降主要伤长上下文「大海捞针」类任务;INT8 通常近乎无损,INT4 需精心选粒度+保留离群值。
- **额外成本**:存 scale/zero-point;attention kernel 需支持在读时反量化(dequant-on-the-fly)。

## 6. 窗口 / 驱逐:不是所有 token 都值得留

公式里 $S$ 是另一个可砍的因子 —— 如果能**只保留一部分 token 的 KV**,显存就随保留量而非真实长度增长。

### 6.1 滑动窗口(Sliding Window)

只保留最近 $w$ 个 token 的 KV,旧的丢弃。复杂度从 $O(S)$ 降到 $O(w)$。

```
全注意力:  [▓▓▓▓▓▓▓▓▓▓▓▓]  存 S
滑动窗口w=4:        [▓▓▓▓]   只存最近4(更早的丢)
代价:看不到窗口外信息,远距离依赖丢失。
```

### 6.2 StreamingLLM:Attention Sink + 窗口

观察:模型会把大量注意力「倾倒」到**最前面几个 token**(attention sink),哪怕语义无关。纯滑窗一旦丢掉这几个起始 token,困惑度会爆炸。解法:**保留最前 4 个 sink token + 最近窗口**,即可在近无限长流式输入下保持稳定。

```
保留:[sink×4]···········[最近窗口 w]   ← 中间整段丢弃,仍稳定
```

### 6.3 基于重要性的驱逐(H2O 等)

按累积注意力得分判断哪些是「重锤 token(Heavy Hitter)」,驱逐低分 token 的 KV,保留高分的 + 最近的。

```
KV 满了要赶人:
  得分: t0=0.9★ t1=0.1 t2=0.05 t3=0.8★ ... t_last=最近(强制留)
  驱逐 t1,t2(低分),保留 ★ 和最近窗口
```

### 6.4 kvpress(NVIDIA)

> 参考:https://github.com/NVIDIA/kvpress —— 把上述各种「KV 压缩 / 驱逐」策略统一成可插拔的 press 接口,便于在推理时对每层施加不同压缩比并基准评测。**具体 API 以官方仓库文档为准**,这里只取其「按重要性压缩 KV、可逐层配置压缩率」的通用思想。

**权衡**:驱逐是**有损**的 —— 被丢的 token 之后无法再被注意到。对需要全局精确召回的任务(长文 QA、代码)要谨慎设压缩比。

## 7. MQA / GQA / MLA:从架构上降系数

回看公式 $\text{bytes/token}=2 L\, n_{kv}\, d_h\, b$ —— 前面几节动的是 $b$(量化)、$S$(驱逐);本节直接动 $n_{kv}$。

### 7.1 三种共享方案

```
MHA(标准多头):  每个 Q 头配独立 K/V 头   n_kv = n_q          KV 最大
                  Q:[h0 h1 h2 h3 h4 h5 h6 h7]
                  K:[h0 h1 h2 h3 h4 h5 h6 h7]

GQA(分组查询):  几个 Q 头共享一组 K/V    n_kv = g (组数)     折中
                  Q:[h0 h1 | h2 h3 | h4 h5 | h6 h7]
                  K:[ g0   |  g1   |  g2   |  g3  ]   (8头→4组,KV 减半)

MQA(多查询):    所有 Q 头共享 1 组 K/V   n_kv = 1           KV 最小
                  Q:[h0 h1 h2 h3 h4 h5 h6 h7]
                  K:[          g0          ]   (KV 缩 n_q 倍)
```

**降系数 = $n_q / n_{kv}$**:MQA 把 KV 缩 $n_q$ 倍;GQA(8 头分 4 组)缩 2 倍。代价是表达力略降,GQA 是质量与显存的甜点(Llama-2/3 70B、Mistral 等广泛采用)。

### 7.2 MLA(Multi-head Latent Attention,DeepSeek)

更激进:不直接存每头的 K/V,而是把它们**压缩成一个低维潜向量** $c$ 存下来,用时再通过投影矩阵「解压」回各头的 K/V。

```
存的不是:每头完整 K/V(大)
存的是:  低秩潜向量 c (小)  ──(上投影 W_UK,W_UV)──▶ 还原各头 K/V
```

- KV Cache 只需存潜向量维度 $d_c \ll n_{kv}\,d_h$ → 比 GQA 还省一个量级。
- 配合 RoPE 需做解耦设计(部分维度承载位置)。
- **权衡**:多了上投影计算,但显存收益巨大,且质量接近 MHA。属于「用一点算力换大量访存/显存」。

## 8. 组合拳:怎么叠加

这些技术作用在公式的**不同因子**上,基本**可乘叠加**:

```
   bytes/token = 2 · L · n_kv · d_h · b        × S × B
                          │              │       │
                          ▼              ▼       ▼
                    MQA/GQA/MLA       量化KV   窗口/驱逐
                    (降 n_kv)        (降 b)   (降有效 S)
        ─────────────────────────────────────────────
        分页(PagedAttention)= 让以上节省真正落地、不被碎片吃掉
        前缀复用            = 进一步让多请求共享同一份 KV 页
```

**推荐叠法(从底到顶)**:
1. 架构层先选 **GQA/MLA**(训练期决定,推理免费白赚)。
2. 运行时用 **PagedAttention** 做内存管理(消碎片,是其他优化的容器)。
3. 高并发/重复前缀场景开 **前缀复用**(降 TTFT)。
4. 显存仍紧张 → **量化 KV(INT8 起步)**。
5. 超长上下文且可容忍有损 → 叠 **窗口/驱逐**。

**冲突点**:驱逐/量化都是有损,叠太狠会复合误差;前缀复用 + 量化要保证量化是确定性的(否则哈希命中但数值微差);MLA 的存储格式特殊,与「逐头驱逐」类方法需适配。

## 9. 数值示例 / 手算(Llama-7B 量级)

**模型设定**:$L=32$ 层,$n_q=32$ 头,$d_h=128$($d_{model}=4096$),FP16($b=2$)。

**MHA 情况** $n_{kv}=n_q=32$,每 token:

$$2 \times 32 \times 32 \times 128 \times 2 = 524{,}288 \text{ 字节} = \mathbf{0.5\ MB/token}$$

**单请求 4K 上下文**:$0.5\text{MB} \times 4096 = \mathbf{2\ GB}$。
**batch=16,各 4K**:$2\text{GB} \times 16 = \mathbf{32\ GB}$ —— 已超过 7B 权重(FP16 约 14GB)本身!这正是「KV 比模型还大」的来源。

**叠加优化后**(同一条 4K 请求,2GB 基线):

| 优化 | 作用因子 | 倍率 | 该请求 KV |
|---|---|---|---|
| 基线 MHA FP16 | — | 1× | 2 GB |
| GQA(8 组,$n_{kv}=8$) | $n_{kv}$ ÷4 | 1/4 | 0.5 GB |
| + INT8 量化 | $b$ ÷2 | 1/2 | 0.25 GB |
| + 滑窗保留 1K | 有效 $S$ ÷4 | 1/4 | 0.0625 GB |
| 三者叠加 | 连乘 | **1/32** | **64 MB** |

**手算验证连乘**:$\frac{1}{4}\times\frac{1}{2}\times\frac{1}{4}=\frac{1}{32}$,$2\text{GB}/32 = 64\text{MB}$。✅

**前缀复用账**:若 16 个请求共享 600 token 系统提示(GQA+INT8 下每 token $0.5\text{MB}\times\frac14\times\frac12=0.0625\text{MB}$),不复用要存 $16\times600\times0.0625=600\text{MB}$;复用只存 $1\times600\times0.0625=37.5\text{MB}$,省 **93.75%**,且省掉 15 份 600 token 的 prefill 计算。

## 常见问题

| 疑问 | 真相 |
|---|---|
| 为什么不连 Q 也缓存? | $q_t$ 只在当前步查一次,下一步就换;K/V 才被反复复用 |
| KV Cache 会比模型权重大吗? | 会,长上下文+高并发时 KV 轻松超过权重(见第9节 32GB vs 14GB) |
| 量化 KV 和量化权重一回事? | 同思想不同对象:权重是静态可离线校准,KV 是动态激活,需 on-the-fly 量化,粒度更讲究 |
| GQA 减了头会掉点吗? | 略掉但很小,8→4/8 组是公认甜点;MQA 减太狠掉点明显,故 GQA 更流行 |
| 滑动窗口为何会崩? | 丢了起始 attention sink token → StreamingLLM 保留前几个 sink 即可救 |
| 分页会变慢吗? | 多一层页表寻址,但定制 kernel 摊掉开销,且提利用率反而能上更大 batch → 总吞吐升 |
| 这些能一起用吗? | 能,作用在公式不同因子上基本可乘;但多个有损技术叠加要控复合误差 |
| 长上下文首选哪招? | 架构上 MLA/GQA + 运行时分页 + 前缀复用;显存仍紧再上量化,最后才动有损驱逐 |
