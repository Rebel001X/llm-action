## 0. 一句话锚点

SGLang 源码 = **三层 + 一棵树**：

```
前端 DSL  (sglang/lang/*)        你"写"一个生成程序
   │  编译成 IR / 一串后端原语
   ▼
通信层    (HTTP server + ZMQ)     把请求送进后端进程
   ▼
后端 Runtime (sglang/srt/*)       Tokenizer→Scheduler→Model→Detokenizer
   │
   └─ 一棵树：RadixCache（RadixAttention 的载体），贯穿调度与显存
```

记住一个缩写：**SRT = SGLang RunTime**，后端几乎所有重活都在 `python/sglang/srt/` 里。

## 1. 地基：顶层目录怎么分

SGLang 是个 Python 包（`python/sglang/`），按职责切成几块。**目录名以源码为准**，但职责划分长期稳定：

```
python/sglang/
├── api.py / global_config.py     # 对外入口：gen/select/system 等 DSL 函数门面
├── lang/                         # 【前端】结构化生成语言（DSL）
│   ├── ir.py                     #   把 DSL 程序编译成中间表示 IR
│   ├── interpreter.py            #   解释执行 IR，发请求给后端
│   ├── chat_template.py          #   对话模板
│   └── backend/                  #   前端可对接的后端：本地 Runtime / OpenAI / ...
├── srt/                          # 【后端】SGLang RunTime —— 重头戏
│   ├── server.py / entrypoints/  #   HTTP 服务入口（FastAPI/uvicorn）
│   ├── managers/                 #   三大管理器（见 §4/§5）
│   │   ├── tokenizer_manager.py  #     文本↔token，前置进程
│   │   ├── scheduler.py          #     调度循环 + 连续批（核心）
│   │   ├── detokenizer_manager.py#     token→文本，后置进程
│   │   └── schedule_batch.py     #     一个"批"的状态机 Req/ScheduleBatch
│   ├── mem_cache/                #   显存与缓存
│   │   ├── radix_cache.py        #     RadixCache（RadixAttention 载体，核心）
│   │   ├── memory_pool.py        #     KV 池 / token 槽位分配
│   │   └── chunk_cache.py        #     非前缀复用场景的简单缓存
│   ├── model_executor/           #   模型前向
│   │   ├── model_runner.py       #     ModelRunner：加载权重+跑 forward
│   │   ├── forward_batch_info.py #     ForwardBatch：一次 forward 的输入打包
│   │   └── cuda_graph_runner.py  #     CUDA Graph 捕获/重放
│   ├── layers/                   #   注意力后端、采样、量化、各种 kernel 封装
│   │   ├── attention/            #     FlashInfer / Triton 等 AttentionBackend
│   │   └── sampler.py            #     采样（温度/top-p/top-k/约束）
│   ├── models/                   #   各模型结构（llama/qwen/deepseek/...）
│   ├── constrained/              #   约束解码（JSON/正则/语法→状态机）
│   └── sampling/                 #   采样参数 SamplingParams
├── bench_*.py                    # 压测脚本（bench_offline_throughput 等）
└── launch_server.py              # `python -m sglang.launch_server` 入口
```

**一句话记忆**：`lang/` 是"怎么写程序"，`srt/` 是"怎么把程序跑快"。两者通过网络/进程边界解耦——你甚至可以只用 `srt`（开个 OpenAI 兼容服务），不碰前端 DSL。

## 2. 进程拓扑：一条命令起了几个进程

`python -m sglang.launch_server --model-path X` 不是单进程，而是**多进程流水线**，进程间用 **ZeroMQ（ZMQ）** 传消息。这样设计的"为什么"：让 GPU 进程（Scheduler）**永远不被 Python 的 tokenize/detokenize/HTTP 这种 CPU 活儿堵住**。

```
                ┌──────────────────────────────────────────────┐
   HTTP 请求 ──▶│  HTTP Server 进程 (FastAPI)                    │
                │   /generate /v1/chat/completions ...          │
                └───────────────┬──────────────────────────────┘
                                │ 进程内调用
                ┌───────────────▼──────────────────────────────┐
                │  TokenizerManager（前置）                      │
                │   文本 → input_ids，组装 Req                    │
                └───────────────┬──────────────────────────────┘
                                │ ZMQ (input queue)
                ┌───────────────▼──────────────────────────────┐
                │  Scheduler 进程（GPU 端，核心循环）             │
                │   ├─ RadixCache    前缀匹配/插入               │
                │   ├─ ScheduleBatch 组连续批                    │
                │   └─ ModelRunner   forward 出 logits→采样      │
                └───────────────┬──────────────────────────────┘
                                │ ZMQ (output queue)
                ┌───────────────▼──────────────────────────────┐
                │  DetokenizerManager（后置）                    │
                │   token_id 流 → 文本增量（流式 SSE）           │
                └───────────────┬──────────────────────────────┘
                                │
                            HTTP 响应（流式/非流式）
```

> 关键洞察：**Scheduler 是唯一持有 GPU 的进程**。Tokenizer/Detokenizer 拆出去，是为了把字符串处理这种"会卡 GIL"的活儿挪走，让 Scheduler 的批循环跑得"零开销"（见 §5）。多卡张量并行（TP）时，Scheduler 会有多个 worker（每卡一个），由 `tp_rank` 协同。

## 3. 前端：DSL 是怎么"编译"成请求的（`sglang/lang/`）

### 3.1 DSL 原语 → IR

你写的前端程序（伪代码）：

```python
@sgl.function
def few_shot(s, question):
    s += sgl.system("你是助手")
    s += "Q: " + question + "\nA:"
    s += sgl.gen("answer", max_tokens=64, stop="\n")
```

`sgl.gen / select / fork / system` 这些不是"立即执行"，而是往一个 **IR（Intermediate Representation，中间表示）** 里追加节点。`lang/ir.py` 定义这些节点类型：常量文本、`Gen`（要生成）、`Select`（多选一，靠 logprob 比较）、`Fork`（并行分支）。

### 3.2 解释器 → 后端

`lang/interpreter.py` 遍历 IR：

```
IR 节点流
  ├─ 文本节点      → 直接拼进 prompt
  ├─ Gen 节点      → 发一次 backend.generate(prompt, sampling)
  ├─ Select 节点   → 对每个候选算 logprob，取最大
  └─ Fork 节点     → 复制状态，并发跑多个分支（共享前缀！）
```

**这里是 RadixAttention 在前端的价值兑现点**：`fork` 出来的并行分支、few-shot 共享的系统提示，在后端**自动命中同一棵 RadixTree 的前缀**，省掉重复 prefill。前端只是"自然地写出共享结构"，省算是后端自动做的。

`lang/backend/` 提供多种后端实现：本地 `Runtime`、`RuntimeEndpoint`（连远端 SGLang server）、`OpenAI`（连 OpenAI API）。所以前端 DSL 可以"换后端不换代码"。

## 4. `TokenizerManager`：前置进程（`srt/managers/tokenizer_manager.py`）

**它是什么**：后端流水线的**第一站**，住在 HTTP server 进程一侧，负责"人话 ↔ 数字"的入口方向，并把请求打包成后端能认的 `Req`。

**它解决什么**：① 把 tokenize 这种 CPU 活从 GPU 进程剥离；② 做请求级的参数校验/采样参数归一化；③ 维护一个 `request_id → asyncio.Future` 的映射，等 Detokenizer 那边把结果回填——这就是**异步、流式**的底座。

```
HTTP handler ─▶ TokenizerManager.generate_request(req)
   1. apply chat template（如果是 /v1/chat）
   2. tokenize：text → input_ids
   3. 构造 Req（input_ids + SamplingParams + rid）
   4. ZMQ send 到 Scheduler 的 input queue
   5. await 这个 rid 的输出（边收边 yield 给 HTTP 流）
```

> 为什么要"管理器(Manager)"而不是函数：因为它要**跨进程**维护状态——哪些 rid 在飞、哪些已完成、背压控制。它是请求生命周期的"账本"。

## 5. `Scheduler`：调度循环 + 连续批（`srt/managers/scheduler.py`，核心）

**它是什么**：GPU 进程的**心脏**，一个永不停的 `event_loop`。每一"步（step）"它都要回答两个问题：**这一步把谁塞进批里？**（调度策略）、**这一步是 prefill 还是 decode？**（混合批）。

### 5.1 调度主循环（伪结构）

```
while True:
    reqs = recv_requests()              # 从 ZMQ 收新请求（非阻塞）
    self.waiting_queue.extend(reqs)

    batch = self.get_next_batch_to_run()   # ← 决策核心
        ├─ 能否做 prefill？挑等待队列里的请求
        │     · RadixCache.match_prefix() 看前缀能复用多少
        │     · 检查 KV 池剩余槽位是否够（避免 OOM）
        │     · 按 schedule_policy 排序（lpm/fcfs/lof/dfs-weight/random）
        └─ 否则做 decode：所有 running 请求各前进 1 个 token

    result = self.run_batch(batch)         # 调 ModelRunner.forward + 采样
    self.process_batch_result(result)      # 写回 KV、判停、RadixCache.insert()
```

### 5.2 "零开销"批调度（Zero-Overhead Scheduler）的"为什么"

朴素实现里，CPU 端（建批、采样后处理）和 GPU 端（forward）是串行的：GPU 算完要等 CPU 准备下一批，GPU 出现气泡。SGLang 的做法是**让 CPU 端为「下一批」的准备，与 GPU 端跑「当前批」的 forward 重叠**（overlap scheduling）：

```
时间 ───────────────────────────────────▶
GPU:  [forward batch_t ][forward batch_{t+1}][...]
CPU:        [build batch_{t+1}]    [build batch_{t+2}]
            └ 与 GPU 重叠，GPU 不空等 ┘
```

效果：GPU 利用率拉满，这是 SGLang 高吞吐的第二根支柱（第一根是 RadixAttention 省算）。

### 5.3 `schedule_policy` 五种策略的权衡

| 策略 | 含义 | 适合 |
| --- | --- | --- |
| `lpm` | Longest-Prefix-Match，优先调度"和缓存里前缀重合最多"的请求 | 共享前缀多（系统提示/few-shot）→ 默认推荐之一 |
| `fcfs` | 先来先服务（默认） | 公平、低延迟敏感 |
| `lof` | Longest-Output-First | 长输出优先，减少尾延迟抖动 |
| `dfs-weight` | 按 RadixTree DFS 权重，倾向把同子树请求聚一起 | 树状会话，最大化缓存命中 |
| `random` | 随机 | 基线/调试 |

> 权衡核心：`lpm/dfs-weight` 最大化**缓存命中（省算）**但可能牺牲公平；`fcfs` 最公平但命中率随机。`Req` 与 `ScheduleBatch`（`schedule_batch.py`）是这一切的状态载体——一个 `Req` 记录 input_ids/已生成长度/采样参数/它在 RadixTree 上挂的节点。

## 6. `RadixCache` / RadixTree：核心数据结构（`srt/mem_cache/radix_cache.py`）

这是 SGLang 区别于 vLLM 的灵魂。**README 讲的是"为什么"（RadixAttention 概念），这里讲"代码里它长什么样、四个方法怎么动"。**

### 6.1 它是什么：把 token 序列建成一棵基数树

普通 Trie 一条边一个 token，路径长则节点爆炸。**基数树（Radix Tree / 压缩前缀树）**把"只有一个孩子的链"压成一条边，边上挂**一段 token 序列**，节点挂这段序列对应的 **KV Cache 块的指针**。

```
            root
             │  "你是一个有用的助手。"   ← 系统提示，被所有会话共享
            (N1)──────────┐
        "请翻译:" │        │ "请总结:"
            (N2)          (N3)
       "猫" │  │ "狗"
         (N4) (N5)
   每个节点存：① 这条边的 token 段
              ② 这段 token 的 KV 在 MemoryPool 里的物理位置（indices）
              ③ ref_count（被几个在跑的请求引用，>0 不可驱逐）
              ④ last_access_time（LRU 用）
```

### 6.2 四个核心操作（调用链的关节）

```
match_prefix(input_ids)
   └─ 从 root 沿 token 逐字符匹配，返回：
        · 命中的 KV indices（这段不用重算！）
        · 失配点（从这里开始才需要 prefill）

insert(token_ids, kv_indices)
   └─ 把"新算出来的那段"挂回树上，必要时分裂(split)边
        （命中一半时，把原边在失配点切成两段）

inc_lock_ref / dec_lock_ref(node)
   └─ 请求开始用某节点 → ref_count++（钉住不被驱逐）
      请求结束        → ref_count--（可被 LRU 回收）

evict(num_tokens)
   └─ KV 池快满时，从叶子开始按 LRU 驱逐 ref_count==0 的节点
      （驱逐叶子才安全：删中间节点会断掉别人的前缀）
```

### 6.3 一条请求在树上的旅程（数据流）

```
请求 input_ids = 系统提示 + "请翻译:猫"
  1) match_prefix → 命中 root→N1→N2→N4 已有 KV（系统提示+"请翻译:猫"全中）
  2) inc_lock_ref 钉住路径上的节点
  3) 只需 prefill 失配后的部分（本例 0 个！直接进 decode）
  4) decode 边生成边把新 token 的 KV 写进 MemoryPool
  5) 生成完 → insert 把新生成段挂成 N4 的子节点
  6) dec_lock_ref 释放，节点变可驱逐
```

### 6.4 命中率/省算的小数值例子

设系统提示 200 token，被 1000 条请求共享，每条用户问题平均 30 token。

- 无前缀复用：每条都要 prefill $200+30=230$ token，总 prefill ≈ $1000\times230=230{,}000$ token。
- 有 RadixCache：系统提示只算 1 次（$200$），其余 999 条命中前缀，各只 prefill $30$。
  总 ≈ $200 + 1000\times30 = 30{,}200$ token。

省算比例 $\approx 1-\dfrac{30200}{230000}\approx 86.9\%$ 的 prefill 计算被省掉。这正是 `match_prefix` 命中带来的红利。

## 7. 模型前向：`ModelRunner` / `AttentionBackend` / `MemoryPool`（`srt/model_executor/`、`srt/layers/`）

### 7.1 `ModelRunner`（`model_runner.py`）

**它是什么**：把"加载权重 + 跑一次 forward + 出 logits"封装起来的对象，是 Scheduler 调用 GPU 的唯一接口。职责：① 按 `--model-path` 从 `srt/models/` 选对应模型类加载权重（含量化/TP 切分）；② 把 `ScheduleBatch` 转成 `ForwardBatch`（`forward_batch_info.py`）——里面打包了 input_ids、各请求在 KV 池的位置、是 prefill 还是 decode 的标志；③ 调模型 forward 出 logits，交给 `sampler.py` 采样。

### 7.2 `AttentionBackend`（`srt/layers/attention/`）

注意力是**可插拔后端**：FlashInfer、Triton 等。SGLang 把"prefill 整段注意力"和"decode 单步注意力 + 读 RadixCache 命中的 KV"都委托给它。RadixCache 给出的 KV indices，最终就是喂给 AttentionBackend 的"去哪读 K/V"的地址表。

### 7.3 `MemoryPool`（`srt/mem_cache/memory_pool.py`）

**它是什么**：一块预分配的大显存，切成固定数量的 **token 槽位**，存所有请求所有层的 K/V。RadixCache 节点里存的 `indices` 就是指向这个池的下标。`--mem-fraction-static` 决定这块池占多少显存。

```
ForwardBatch 拿到的就是：
  input_ids ─┐
  位置表(out_cache_loc) ─┤  → AttentionBackend 按表读/写 MemoryPool
  KV indices(命中前缀)  ─┘
  forward_mode = PREFILL | DECODE | MIXED
```

### 7.4 `CUDA Graph`（`cuda_graph_runner.py`）

decode 阶段每步的 kernel 启动开销（CPU launch）很贵且固定。SGLang 把固定 batch size 的 decode 路径**捕获成 CUDA Graph**，重放时绕过 Python/驱动的 launch 开销——这是"零开销"的另一半（计算侧）。

## 8. 端到端调用链：一条 `/v1/chat/completions` 的完整时序

把前面所有模块串成一张图（**最该背下来的图**）：

```
① HTTP Server 收到 chat 请求
        │
② TokenizerManager: chat_template → tokenize → 构造 Req(rid, input_ids)
        │ ZMQ
③ Scheduler.recv_requests() 收进 waiting_queue
        │
④ get_next_batch_to_run():
        ├─ RadixCache.match_prefix(input_ids) → 命中段 + 失配点
        ├─ inc_lock_ref 钉住命中节点
        ├─ MemoryPool 分配新 token 的槽位（不够→evict）
        └─ schedule_policy 排序，组成 ScheduleBatch
        │
⑤ ModelRunner.forward(ForwardBatch):
        ├─ AttentionBackend 读命中 KV + 算失配段(prefill)/单步(decode)
        ├─ 得 logits → sampler 采样出 next token
        │
⑥ process_batch_result():
        ├─ 写新 KV 进 MemoryPool
        ├─ RadixCache.insert(新生成段)
        ├─ 判停（EOS/stop/max_tokens）→ dec_lock_ref
        └─ ZMQ send 输出 token 到 Detokenizer
        │
⑦ DetokenizerManager: token_id → 文本增量
        │ ZMQ
⑧ TokenizerManager 回填 rid 的 Future → HTTP 流式吐字
        │
   未结束的请求 → 回到 ④ 进下一步 decode（连续批）
```

> 这条链里，**Scheduler 是 orchestrator（④⑥），RadixCache 是它的"记忆"，ModelRunner 是它的"手"，MemoryPool 是"仓库"**。读源码就盯着 `④ get_next_batch_to_run` 和 `⑥ process_batch_result` 两个函数，整台机器的逻辑都在这。

## 9. 关键启动参数 → 对应模块（知道"调它影响哪段代码"）

| 参数 | 落到哪个模块 | 含义与权衡 |
| --- | --- | --- |
| `--mem-fraction-static` | MemoryPool | KV 池占显存比例。大→能装更多并发/更长上下文，但留给激活值的少→可能 OOM |
| `--schedule-policy` | Scheduler | 见 §5.3，命中率 vs 公平 |
| `--chunked-prefill-size` | Scheduler/ForwardBatch | 把长 prefill 切块，避免一个长请求把 decode 饿死 |
| `--max-running-requests` | Scheduler | 并发上限，控显存与尾延迟 |
| `--kv-cache-dtype`（`auto/fp8_e5m2/fp8_e4m3`） | MemoryPool/Attention | FP8 省一半 KV 显存→更高并发，但精度有损（e4m3 需 scaling factor） |
| `--tp-size` | ModelRunner | 张量并行卡数，每卡一个 Scheduler worker |
| `--attention-backend` | layers/attention | 选 FlashInfer/Triton 等 |
| `--enable-torch-compile` / CUDA Graph | model_executor | 降 launch 开销 |
| `--dtype`（默认 bf16） | ModelRunner 权重加载 | 见 `服务器启动参数.md` |

> 数值/默认值随版本变，**以 `python -m sglang.launch_server --help` 与源码为准**，本文只给"参数↔模块"的映射关系。

## 10. 与 vLLM 源码结构对照（怎么对着看）

| 维度 | vLLM | SGLang |
| --- | --- | --- |
| 显存复用粒度 | PagedAttention：**一条请求内**分页防碎片 | RadixAttention：**跨请求/跨轮**前缀树复用 |
| 核心数据结构 | BlockManager（块表） | RadixCache（基数树）+ MemoryPool |
| 调度器 | `Scheduler`（waiting/running/swapped 队列） | `Scheduler`（零开销 overlap + 连续批） |
| 入口分层 | `LLMEngine`/`AsyncLLMEngine` | `TokenizerManager`→`Scheduler`→`Detokenizer` 三进程 |
| 前端 | 纯推理 API / OpenAI 兼容 | 额外有 **DSL 前端**（`gen/fork/select`） |
| 模型库 | `vllm/model_executor/models/` | `srt/models/`（结构相近，都按模型一个文件） |

**对照读法**：两者的"Scheduler + 模型前向 + KV 池"骨架几乎同构，差异集中在**缓存层**——vLLM 看 `block_manager`，SGLang 看 `radix_cache`。先读懂 vLLM 的块表，再看 SGLang 怎么把"块"升级成"树节点+ref_count+LRU"，过渡最顺。详见 [[llm-inference/vllm/源码]]。

## 11. 常见问题

| 问题 | 答 |
| --- | --- |
| 为什么 Tokenizer 要单独进程，不直接在 Scheduler 里 tokenize？ | 隔离 CPU 活，保证持 GPU 的 Scheduler "零开销"不被字符串处理堵住；也便于背压与流式。 |
| RadixCache 满了会怎样？ | `evict` 按 LRU 从**叶子**开始驱逐 `ref_count==0` 的节点；驱逐中间节点会断别人前缀，故只动叶子。 |
| 命中前缀后还要不要进 forward？ | 命中段**不重算**（KV 直接读），只对失配后的新 token 做 prefill，再进 decode。完全命中则直接 decode。 |
| `lpm` 和 `dfs-weight` 选哪个？ | 共享前缀场景都能提命中率；`dfs-weight` 更倾向把同子树请求聚批，会话树状结构收益更大。具体看 workload 压测。 |
| 想读源码从哪进？ | `launch_server.py`→`srt/server.py`→`tokenizer_manager.py`→**`scheduler.py` 的 `event_loop` / `get_next_batch_to_run`**→`radix_cache.py`→`model_runner.py`。盯 §8 那两个函数。 |
| 这些类名/路径会变吗？ | 职责骨架稳定，**精确文件名/签名随 tag 变**，按你 checkout 的版本核对（见 `source-code.md` 的 tag 检出流程）。 |
