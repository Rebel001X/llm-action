## 0. 一句话锚点

SGLang 启动一个常驻的 HTTP/OpenAI 兼容服务，背后是一个**持续运行的调度循环（scheduler loop）**：它把进来的请求拆成 prefill / decode 两类工作，塞进 GPU 上一块预分配好的 KV Cache 显存池，按某种顺序（调度策略）一批一批喂给模型前向。**启动参数就是在服务进程起来之前，一次性把这套机器的"形状"固定下来**——模型多大、用什么精度、占几张卡、留多少显存给 KV、用哪种注意力算子、按什么顺序调度。起来之后这些大多不能改。

> 命令形态（参数名以官方 `--help` / 源码为准，本文讲含义与权衡）：
> ```bash
> python -m sglang.launch_server \
>     --model-path <模型目录> \
>     --tp-size 4 \
>     --mem-fraction-static 0.85 \
>     --host 0.0.0.0 --port 30000
> ```

## 1. 地基：这些参数到底在配置什么

### 1.1 SGLang 的运行时长啥样

要理解参数，先看引擎跑起来后内部有哪些"被参数决定"的部件：

```
                 HTTP 请求 (OpenAI /v1/chat/completions)
                          │
                 ┌────────▼─────────┐
                 │  Tokenizer 进程   │  ← --tokenizer-path / --chat-template
                 └────────┬─────────┘
                          │ (token ids)
                 ┌────────▼─────────┐
                 │   Scheduler       │  ← --schedule-policy
                 │  (连续批处理循环)  │  ← --chunked-prefill-size
                 │                   │  ← --max-running-requests
                 └────────┬─────────┘
            分配 KV slot  │  从显存池取空闲 token 槽位
                 ┌────────▼─────────────────────────┐
                 │   Model Runner (GPU)              │
                 │  ┌──────────┐   ┌──────────────┐  │
                 │  │ 模型权重  │   │  KV Cache 池  │  │ ← --mem-fraction-static
                 │  │ (dtype)  │   │ (kv-cache-   │  │ ← --kv-cache-dtype
                 │  └──────────┘   │   dtype)     │  │
                 │   AttentionBackend (FlashInfer)  │ ← --attention-backend
                 │   切分: TP/DP/EP/PP               │ ← --tp-size 等
                 └────────┬─────────────────────────┘
                          │ (logits → 采样)
                 ┌────────▼─────────┐
                 │  Detokenizer 进程 │
                 └──────────────────┘
```

每个标了 `← --xxx` 的地方，就是一类启动参数的作用点。把参数按"作用在哪个部件"分组，就不会被几十个旋钮淹没。

### 1.2 它解决什么问题

一台 GPU 服务器要跑大模型推理，必须在启动时回答四个互相牵制的问题：

1. **放得下吗**（显存）：权重 + KV Cache + 激活 + 框架开销 ≤ 显存总量。参数：精度、`mem-fraction-static`、并行切分。
2. **算得快吗**（吞吐/延迟）：批多大、注意力算子用哪个、要不要编译。参数：`max-running-requests`、`chunked-prefill-size`、`attention-backend`、`torch-compile`。
3. **多卡怎么协作**（并行）：一个模型切到几张卡、按层切还是按 head 切。参数：`tp-size` / `dp-size` / `ep-size` / `pp-size`。
4. **请求怎么排队**（调度）：谁先算、长短请求怎么混。参数：`schedule-policy`。

启动参数本质就是**在"放得下、算得快、协作好、排得顺"之间做一次静态权衡**。

## 2. 模型与精度参数

### 2.1 `--model-path` / `--tokenizer-path`

`--model-path` 指向 HuggingFace 格式权重目录（或 Hub 名）。tokenizer 默认与模型同目录，特殊场景（如蒸馏、自定义词表）可用 `--tokenizer-path` 单独指定。`--chat-template` 决定对话消息如何拼成单条 prompt 字符串——选错模板会让模型答非所问。

### 2.2 `--dtype`：权重与激活的数据类型

控制模型权重和激活用什么浮点格式加载。常见取值类别：

| 取值 | 含义 | 何时用 |
|------|------|--------|
| `auto` | FP32/FP16 模型→FP16；BF16 模型→BF16 | 默认，跟随权重 |
| `half` / `float16` | FP16，5 位指数 10 位尾数 | 老卡、AWQ 量化推荐 |
| `bfloat16` | BF16，8 位指数 7 位尾数，动态范围大 | 现代主流，数值稳定 |
| `float` / `float32` | FP32 | 调试/对齐精度，显存翻倍 |

底层为什么 BF16 成主流：FP16 指数只有 5 位，表示范围约到 $6.5\times10^4$，大模型某些激活会溢出成 `inf`；BF16 牺牲尾数精度换来和 FP32 一样的指数范围（$\sim3.4\times10^{38}$），更不容易 NaN。代价是相同位宽下 BF16 有效精度更低，但对 LLM 推理通常够用。

### 2.3 `--kv-cache-dtype`：KV 缓存单独的精度

KV Cache 往往是显存最大头（见第 4 节），把它单独降精度能省一大块显存。取值类别：

| 取值 | 含义 |
|------|------|
| `auto` | 跟随模型 dtype |
| `fp8_e5m2` | 8 位浮点，5 指数 2 尾数，范围大精度低 |
| `fp8_e4m3` | 8 位浮点，4 指数 3 尾数，精度高范围小 |

> 注意：`fp8_e4m3` 范围小，通常需要配套的缩放因子（scaling factor / `quantization-param-path`）来把数值映射进可表示区间，否则会因截断而掉精度；不提供时默认 scale=1.0 往往不够好。`fp8` 路径对 CUDA 版本与硬件有要求（如较新的 Hopper/Ada 架构原生 FP8）。**具体支持矩阵以官方文档为准。**

KV 降到 FP8 一般能让可容纳的并发序列数 / 上下文长度**翻倍**，是长上下文场景的关键开关；但对精度敏感任务要做评测验证。

### 2.4 `--quantization`：权重量化

把权重从 16 位压到更低位宽以省显存、提吞吐。常见方法类别：AWQ、GPTQ（4 位整数权重量化）、FP8、以及 W8A8 等。要点：

- 量化是**权重侧压缩**，KV-cache-dtype 是**缓存侧压缩**，两者独立可叠加。
- 量化模型通常需要对应格式的权重文件（AWQ/GPTQ 模型是离线量化好的），启动时方法要与权重格式匹配。
- 权衡：位宽越低越省显存、显存带宽压力越小（decode 阶段是带宽瓶颈，故常提速），但精度风险越大。

延伸阅读：[[llm-compression/quantization/量化基础]]。

## 3. 并行与多卡切分

单卡放不下时，把一个模型切到多张卡。SGLang 支持多种并行维度，启动时用 `*-size` 系列参数指定。

```
          一个 Transformer 层在 4 卡上的张量并行(TP=4)
   ┌─────────────────────────────────────────────┐
   │  Attention: QKV/输出投影按 head 维度列/行切分   │
   │  MLP:       两个大矩阵按列/行切分               │
   └─────────────────────────────────────────────┘
      GPU0      GPU1      GPU2      GPU3
     [1/4 W]   [1/4 W]   [1/4 W]   [1/4 W]
        └──────── AllReduce (每层2次) ───────┘   ← 需要高速互联(NVLink/IB)
```

| 参数（类别） | 并行维度 | 切什么 | 通信代价 |
|------|------|--------|----------|
| `--tp-size` | 张量并行 TP | 把每层权重矩阵按行/列切到多卡 | 每层多次 AllReduce，**带宽敏感**，最好同机 NVLink |
| `--dp-size` | 数据并行 DP | 复制多份模型，各自处理不同请求 | 仅负载均衡层面通信，显存不省（每份完整） |
| `--ep-size` | 专家并行 EP | MoE 模型把不同专家分到不同卡 | All-to-All 路由通信，MoE 专用 |
| `--pp-size` | 流水线并行 PP | 按层切，前几层在卡0、后几层在卡1 | 层间点对点传递，跨机更友好但有气泡 |

实践口诀：
- **优先 TP** 把单模型塞进单机多卡（TP=卡数），前提是卡间有 NVLink；跨机做 TP 会被网络拖死。
- **DP** 用来横向扩并发（多副本），不省单副本显存。
- **MoE 模型**（如 DeepSeek、Mixtral）才用 **EP**，把巨量专家摊开。
- TP×PP×DP 的乘积要等于（或整除）你拥有的 GPU 数。

多卡之间走 NCCL 集合通信，相关原理见 [[ai-infra/网络/NCCL]] 与 [[ai-infra/网络/集合通信原语]]。

## 4. 显存与 KV Cache 管理

### 4.1 显存预算分解

这是最容易 OOM、也最值得理解的部分。一张卡的显存被这样瓜分：

```
 GPU 总显存
 ├── 模型权重         (固定: 参数量 × dtype字节数 / TP)
 ├── CUDA/框架开销     (cuda context、cudnn、通信buffer…)
 ├── 激活/临时显存     (前向中间结果，随 batch 波动)
 └── KV Cache 池      ◄── 剩下的全给它，由 --mem-fraction-static 圈定
        每 token 的 KV 大小:
        2(K和V) × 层数 × kv_head数 × head_dim × dtype字节
```

### 4.2 `--mem-fraction-static`：静态显存占比

把"总显存的多少比例划给 SGLang 的静态池（权重 + KV Cache 等）"。**它是 OOM 与吞吐之间最核心的旋钮**：

- 调**高**（如 0.9）：留给 KV Cache 的空间大 → 能同时跑更多/更长的请求 → 吞吐高。但留给临时激活、通信 buffer 的余量变小 → 长 prompt 或大 batch 时可能 OOM。
- 调**低**（如 0.8）：更安全，但 KV 池小 → 高并发时请求排队，吞吐下降。

调参经验：从一个保守值（如 0.8）起步，看显存占用与是否 OOM，逐步上调到刚好不 OOM 再回退一点。多卡 TP、长上下文、开了 `torch-compile`（编译期额外占显存）时要更保守。

### 4.3 KV Cache 的页式/Token 池管理

SGLang（与 vLLM 同源思想）用 **PagedAttention 式的分页 KV**：把 KV 显存切成固定大小的 block/page，请求按需领取，避免为"最大长度"预留连续大块造成的碎片浪费。这也是为什么 `mem-fraction-static` 能近乎榨干显存。再叠加 **RadixAttention**（SGLang 标志性特性）：相同前缀的请求**共享 KV**（前缀缓存），系统提示、few-shot 例子只算一次。相关基础见 [[llm-optimizer/kv-cache]]。

`--max-total-tokens`（KV 池总 token 容量）、`--max-prefill-tokens` 等参数可进一步约束池大小，多数时候交给框架自动推导即可。

## 5. 批处理与调度策略

### 5.1 连续批处理（continuous batching）

SGLang 用连续批处理：不等一批全部生成完，谁结束了就把它的 slot 让出来塞新请求，GPU 始终满载。`--max-running-requests` 限制同时在跑的请求数上限——太大易 OOM/抢占，太小吞吐低。

### 5.2 `--chunked-prefill-size`：分块预填充

prefill（处理输入 prompt）是计算密集、一次吃很多 token；decode（逐字生成）一次只算 1 个 token。若一个超长 prompt 的 prefill 独占整个 step，会让正在 decode 的其他请求卡顿（TTFT/ITL 抖动）。**分块预填充**把长 prompt 的 prefill 拆成固定大小的 chunk，与 decode 交错执行：

```
 不分块:  [████ 长prefill 独占 ████] [decode][decode]...
                                 ↑ 其它请求被饿死

 分块:    [prefill块][decode混][prefill块][decode混]...
          chunk=8192      平滑，延迟更可控
```

`--chunked-prefill-size` 即 chunk 的 token 数。调大→prefill 吞吐高但 decode 延迟抖；调小→延迟平滑但 prefill 效率略降。

### 5.3 `--schedule-policy`：请求调度顺序

决定 scheduler 从等待队列里**先挑谁**进 batch。常见取值含义：

| 策略 | 全称/含义 | 适用 |
|------|----------|------|
| `fcfs` | 先来先服务（默认） | 公平、可预期，通用基线 |
| `lpm` | Longest-Prefix-Match，优先调度与缓存前缀匹配最长的请求 | 大量共享前缀（系统提示/RAG），最大化 RadixAttention 命中 |
| `dfs-weight` | 基于前缀树 DFS 加权遍历的顺序 | 树状共享前缀的批量场景 |
| `lof` | Longest-Output-First 等长度优先类策略 | 特定吞吐优化 |
| `random` | 随机 | 实验对照 |

直觉：**`lpm` 等前缀感知策略**通过让"前缀相同的请求挨着跑"提高 KV 复用与命中率，对 agent / 多轮 / RAG 这类前缀高度重复的负载吞吐提升明显；普通混合负载用 `fcfs` 即可。

## 6. 注意力后端 AttentionBackend

`--attention-backend` 选择注意力算子的实现。注意力是推理最热的 kernel，后端选择直接影响速度与显存。常见类别：

| 后端 | 特点 | 何时选 |
|------|------|--------|
| FlashInfer | 面向 LLM 推理高度优化的算子库，支持分页 KV、各种 mask、FP8 | 新硬件默认首选，吞吐好 |
| Triton | 用 Triton 写的内核，可移植、易调试 | 缺 FlashInfer 支持时的兜底 |
| FlashAttention 系 | 经典 IO 感知精确注意力 | 兼容性场景 |
| Torch native | PyTorch 原生 SDPA | 调试基线 |

底层为什么需要专门后端：朴素注意力要把 $N\times N$ 的注意力矩阵写回显存，长序列时显存与带宽爆炸。FlashAttention 类算法用**分块 + 在线 softmax** 让注意力矩阵不落地，复杂度从显存 $O(N^2)$ 降到 $O(N)$。原理见 [[llm-optimizer/FlashAttention]]。推理还要叠加**分页 KV** 的支持（KV 不连续存放），所以推理专用后端（FlashInfer）比训练用的 FA 更合适。

不同后端对硬件、dtype、特殊 mask（如滑动窗口、MLA）的支持不同，**遇到报错优先怀疑后端兼容性，换一个后端试**。具体支持矩阵以官方文档为准。

## 7. 编译与重叠等加速开关

### 7.1 `--enable-torch-compile`

用 `torch.compile` 把模型前向图编译/融合，减少 Python 与 kernel 启动开销，对小 batch 的 decode 提速明显。代价：

- 首次启动有**编译预热**耗时（几十秒到几分钟），且编译期额外占显存。
- 只对捕获到的 batch size 形状最优，常配合 `--cuda-graph-max-bs` 等限定形状。

### 7.2 CUDA Graph

把固定形状的一串 kernel 录制成一张图，重放时省掉每个 kernel 的 launch 开销，对 decode（大量小 kernel）收益大。SGLang 默认对一组 batch size 捕获 CUDA Graph，可用参数调整捕获范围或禁用（`--disable-cuda-graph`，调试时用）。

### 7.3 两批次重叠 TBO（Two-Batch Overlap）

把一个大 batch 拆成**两个微批次**，让一个微批次在做计算时、另一个在做通信（如 TP 的 AllReduce / EP 的 All-to-All），从而**让计算与通信重叠**，隐藏通信延迟；同时因为有效批大小减半，**峰值激活显存也下降**。

```
   不重叠:  [计算 microbatch] → [等通信] → [计算] → [等通信]
                                ↑ GPU 在通信时空转

   TBO:     mb1: [计算 ]──[通信 ]──[计算 ]
            mb2:        [计算 ]──[通信 ]──[计算 ]
                   ↑ 一个算、一个通，互相填满气泡
```

适合通信占比高的大并行场景（大 TP、MoE 的 EP）。收益依赖通信/计算比例，需实测。

## 典型启动命令逐行解读

下面是一个面向**高吞吐离线/在线服务**的示例，逐行说明每个参数为什么在这里（参数名以官方为准）：

```bash
python -m sglang.launch_server \
    --model-path /workspace/Qwen2.5-32B-Instruct-FP8 \   # ① 模型(已FP8量化)
    --tp-size 4 \                                          # ② 4卡张量并行,32B单卡放不下
    --mem-fraction-static 0.9 \                            # ③ 显存榨到90%给KV,追吞吐
    --kv-cache-dtype fp8_e5m2 \                            # ④ KV降FP8,容纳更多并发
    --max-running-requests 48 \                            # ⑤ 并发上限,防抢占OOM
    --chunked-prefill-size 8192 \                          # ⑥ 长prompt分块,平滑延迟
    --schedule-policy lpm \                                # ⑦ 前缀感知调度,RAG命中高
    --attention-backend flashinfer \                       # ⑧ 推理专用注意力后端
    --enable-torch-compile \                               # ⑨ 编译加速decode
    --host 0.0.0.0 --port 30000                            # ⑩ 对外服务
```

逐行逻辑：① 选定量化权重 → ② 因模型大而 4 卡 TP 切分（同机 NVLink）→ ③④ 用激进显存比 + FP8 KV 把容量拉满 → ⑤⑥ 用并发上限和分块预填稳定延迟 → ⑦ 用前缀策略提升缓存命中 → ⑧⑨ 选高效算子并编译 → ⑩ 起服务。

> 压测可用 `python -m sglang.bench_offline_throughput --model-path ... --dataset-name random --random-input 2048 --random-output 1024 --num-prompts 1000 ...` 对照不同参数组合的吞吐，再固化到上线命令。

## 常见问题/坑

| 现象 | 可能原因 | 处理方向 |
|------|----------|----------|
| 启动即 CUDA OOM | `mem-fraction-static` 太高 / 权重就放不下 | 调低占比；增大 TP；用量化/FP8 KV |
| 跑着跑着 OOM | 并发或长 prompt 撑爆 KV 池 | 降 `max-running-requests`；降占比留余量 |
| TTFT 抖动大、长请求拖慢全场 | 未分块预填充 | 设 `chunked-prefill-size` |
| 多机 TP 极慢 | 跨机做张量并行被网络拖死 | TP 限同机；跨机改用 PP 或多副本 DP |
| 精度明显下降 | FP8 KV/量化未配缩放因子 | 提供 `quantization-param-path`；换 e4m3+scale；或回退 BF16 KV |
| 换硬件后注意力报错 | 后端不支持该 GPU/dtype/mask | 切 `--attention-backend`（Triton 兜底） |
| 首次启动很久没响应 | `torch-compile`/CUDA Graph 预热 | 正常，等编译完；调试可临时禁用 |
| 对话答非所问 | chat template 不匹配 | 指定正确 `--chat-template` |
| `tp-size×pp-size` 与卡数对不上 | 并行乘积不整除 GPU 数 | 调整切分使其匹配 |

> 反复强调：本文讲的是**参数类别与权衡机制**。精确的参数名、默认值、取值列表、硬件/CUDA 支持矩阵会随 SGLang 版本变化，**上线前务必以 `python -m sglang.launch_server --help` 和官方文档/源码为准**。
