## 0. 一句话锚点

**LMDeploy = 模型量化 + 高性能推理引擎(TurboMind / PyTorch) + OpenAI 兼容服务**。

把它放进推理生态里对比一句话记忆：

- **vLLM**：以 PagedAttention 起家，社区生态最广，纯 Python + 自定义 CUDA kernel。
- **TGI(Text Generation Inference)**：HuggingFace 出品，Rust 调度 + Python/C++ kernel。
- **TensorRT-LLM**：NVIDIA 官方，编译式、极致性能但工程门槛高。
- **LMDeploy**：自研 **TurboMind**(C++/CUDA，脱胎于 FasterTransformer 思路)做极致吞吐，又提供 **PyTorch 后端**做新模型快速适配；**KV 量化 + W4A16** 是其传统强项。

> 一句话：**TurboMind 拼性能与显存效率，PyTorch 后端拼灵活性与新模型覆盖，两者共用同一套服务/接口层。**

## 1. 地基：它解决什么问题

部署一个大模型在线服务，工程上要同时按住四只"拦路虎"：

1. **吞吐(Throughput)**：单卡每秒能服务多少 token？直接决定成本。
2. **延迟(Latency)**：首 token 时间(TTFT)和每 token 间隔(TPOT)影响体验。
3. **显存(Memory)**：权重 + KV Cache 吃满显存，决定能开多大 batch、多长上下文。
4. **易用性(Usability)**：能不能一行命令起服务、兼容 OpenAI API、支持新模型。

朴素的 `model.generate()` 逐请求跑，问题在哪？

```
朴素逐请求推理的浪费
┌──────────────────────────────────────────────┐
│ 请求A: [prefill]→[decode decode decode ...]    │  decode 阶段
│ 请求B:               (排队等待 A 全部跑完)      │  GPU 利用率极低
│ 请求C:                              (继续等)    │  (一次只算 1 条)
└──────────────────────────────────────────────┘
   GPU SM 大量空转；KV Cache 静态预分配 → 显存碎片浪费
```

LMDeploy 的对策：
- **持久批(persistent batch)** → 让多请求在 token 粒度上拼批，填满 GPU。
- **KV 量化 / Blocked KV Cache** → 省显存，腾出空间开更大 batch / 更长上下文。
- **W4A16 权重量化** → 权重显存砍到约 1/4，单卡能装更大模型。
- **TurboMind 高度优化的 kernel(融合、量化 GEMM)** → 把单步算到极致。

## 2. 整体架构：三层 + 两后端

```
                  LMDeploy 全景架构
┌───────────────────────────────────────────────────────┐
│  服务/接口层 (Serving / API)                            │
│   ├─ pipeline()        Python 批量离线推理               │
│   ├─ lmdeploy serve api_server  → OpenAI 兼容 HTTP       │
│   ├─ lmdeploy chat     交互式命令行                      │
│   └─ Gradio / proxy(多机多模型路由)                     │
└───────────────────────────────────────────────────────┘
                          │  统一的 Engine 抽象
        ┌─────────────────┴──────────────────┐
        ▼                                     ▼
┌────────────────────┐              ┌────────────────────┐
│  TurboMind 后端     │              │  PyTorch 后端       │
│  (C++/CUDA)         │              │  (纯 Python)        │
│  ├ persistent batch │              │  ├ continuous batch │
│  ├ blocked KV cache  │             │  ├ paged KV cache    │
│  ├ KV INT8/INT4     │              │  ├ 量化(AWQ/W8A8等) │
│  ├ W4A16 GEMM       │              │  ├ TP / 部分新特性   │
│  └ TP 张量并行       │             │  └ 易扩展新模型      │
└────────────────────┘              └────────────────────┘
        │                                     │
        └────────────┬────────────────────────┘
                     ▼
┌───────────────────────────────────────────────────────┐
│  压缩/量化层 (lmdeploy lite)                            │
│   ├ W4A16(AWQ)  ├ KV 量化标定  ├ W8A8(SmoothQuant 类)  │
└───────────────────────────────────────────────────────┘
```

三层职责：
- **服务层**：对外暴露统一入口，两套后端对用户透明，只靠 `backend_config` 切换。
- **引擎层**：两套各有侧重(下面 3、4 节)。
- **压缩层**：`lmdeploy lite` 离线把模型量化成 4bit/8bit，产物喂给引擎加载。

> 关键设计哲学：**接口统一、引擎可换**。同一份 OpenAI API、同一套 `pipeline`，底层 TurboMind 还是 PyTorch 由配置决定。

## 3. TurboMind 后端(性能担当)

**它是什么**：用 C++/CUDA 写的高性能推理引擎，思路上脱胎于 NVIDIA FasterTransformer，但在调度、KV 管理、量化上做了大量重写。**它解决什么**：把单卡吞吐和显存效率压到极致。

### 3.1 核心模块

```
TurboMind 内部结构
┌─────────────────────────────────────────────────┐
│ Request Queue   ← 接收来自服务层的请求            │
│        │                                          │
│        ▼                                          │
│ Persistent Batch Scheduler                        │
│   维护一个"常驻"批，token 粒度动态进出请求        │
│        │                                          │
│        ▼                                          │
│ Model Executor (逐层 Transformer)                 │
│   ├ Attention: 融合 kernel + Blocked KV Cache     │
│   ├ FFN/GEMM:  支持 FP16/BF16 / W4A16 量化 GEMM    │
│   └ Sampling:  topk/topp/温度/重复惩罚            │
│        │                                          │
│        ▼                                          │
│ Block Manager  ← 管理分块 KV Cache 的分配/回收     │
└─────────────────────────────────────────────────┘
```

- **Persistent Batch Scheduler(持久批调度器)**：维护一个长期存在的 batch，请求随到随入、生成完即出，见第 5 节。
- **Blocked KV Cache(分块 KV 缓存)**：KV 不再为每个序列连续大块预分配，而是切成固定大小的 block 按需分配，思路与 vLLM 的 PagedAttention 同源——**消除碎片、提高显存利用率、支持更高并发**。
- **量化 GEMM**：W4A16 下，权重以 4bit 存储，计算时反量化为 FP16 与激活相乘，配套高效 CUDA kernel。
- **Attention 融合 kernel**：把 QKV 投影、scale、softmax、上下文聚合尽量融合，减少访存。

### 3.2 单次解码的数据流

```
一个 token 的诞生(decode 步, TurboMind)
输入 token id
   │ embedding lookup
   ▼
┌──────── 逐层(× N) ─────────┐
│  RMSNorm → QKV GEMM(W4A16) │
│       │                     │
│  从 Block KV Cache 取历史 KV │
│       ▼                     │
│  Attention(融合 kernel)     │
│       ▼                     │
│  写回新 KV 到 Block Cache    │
│       ▼                     │
│  RMSNorm → FFN GEMM(W4A16)  │
└─────────────────────────────┘
   ▼ 最后一层 → LM Head → logits
   ▼ Sampling(topk/topp/温度)
输出 token id ──► 拼回 persistent batch，进入下一步
```

### 3.3 适配范围与取舍

- **强项**：主流 LLM(LLaMA 系、InternLM、Qwen、Baichuan 等结构相近的)上吞吐最优、KV/W4A16 量化最成熟。
- **代价**：新出的、结构奇特的模型适配需要写 C++/CUDA，**迭代速度不如纯 Python**。这正是 PyTorch 后端补位的地方。

## 4. PyTorch 后端(灵活性担当)

**它是什么**：用纯 Python + PyTorch 实现的推理引擎(`lmdeploy/pytorch`)。**它解决什么**：新模型/新结构的**快速适配**，以及一些 TurboMind 暂未覆盖的特性试验。

```
为什么需要两套后端
   新模型上线 ──► PyTorch 后端先跑通(Python 改一改即可)
                       │  验证 + 沉淀优化
                       ▼
   性能要求高 ──► 迁移/沉淀到 TurboMind(C++/CUDA 极致优化)
```

- 同样实现了 **continuous batching**(连续批处理)与 **paged/分块 KV Cache**。
- 支持张量并行(TP)、常见量化路径(如 AWP/W8A8 类，**以官方文档为准**)。
- 用 PyTorch 生态(triton kernel、torch 编译等)做加速。
- **权衡**：极致峰值吞吐通常略逊 TurboMind，但**模型覆盖更广、改起来更快**。

> 选型口诀：**结构主流、追极致性能 → TurboMind；新模型 / 特殊结构 / 快速验证 → PyTorch。** 不确定先用默认(LMDeploy 会按模型自动选合适后端，具体策略以官方文档为准)。

## 5. 持久批 / 连续批调度(吞吐核心)

传统"静态批"(static batching)：凑齐一批一起 prefill、一起 decode，必须等批里**最慢**的那条生成完才整体释放——短请求被长请求拖死，GPU 空转。

**持久批 / 连续批**：以 **token(迭代)粒度**调度。

```
静态批 vs 连续批(每列 = 一个解码步)
静态批:
  step:  1  2  3  4  5  6  7
  A   :  ■  ■  ■  done(但还占着槽)······
  B   :  ■  ■  ■  ■  ■  ■  done
  C   :  (整批等 B 完才能进来) ········
                  ↑ A 早完了却空转，C 进不来

连续批(persistent batch):
  step:  1  2  3  4  5  6  7
  A   :  ■  ■  ■  ✔(立刻让出槽位)
  B   :  ■  ■  ■  ■  ■  ■  ✔
  C   :  -  -  -  ■  ■  ■  ■   ← A 一空就补进来
                  ↑ 槽位始终填满，GPU 利用率拉高
```

机制要点：
- **常驻 batch**：引擎维护一个"持续运行"的批，**请求随到随入、完成即出**，无需整批对齐。
- **prefill/decode 混合调度**：新请求的 prefill 与在跑请求的 decode 交织安排，平衡 TTFT 与吞吐。
- **配合 Blocked KV Cache**：进出请求只需分配/回收若干 KV block，**不产生大块碎片**，所以才能频繁换人。
- **可调旋钮**：最大并发数、KV block 数(由可用显存换算)、最大上下文长度等共同决定能塞多少并发。

数值直觉：若平均一条回复 200 token，静态批 batch=8 要等最慢的跑完;连续批下早完的位置不断被新请求填满，**有效并发常能数倍于静态批**(具体倍数取决于长度分布与显存)。

## 6. KV Cache 量化(省显存、提并发)

### 6.1 为什么 KV Cache 是显存大户

自回归生成中，每生成一个 token，都要缓存所有历史层、所有 token 的 Key 和 Value，避免重复计算。其大小：

$$
\text{KV 显存} = 2 \times L \times n_{kv} \times d_{head} \times S \times B \times \text{bytes}
$$

其中 $L$ 层数、$n_{kv}$ KV 头数(GQA 下远小于注意力头数)、$d_{head}$ 头维度、$S$ 序列长、$B$ 并发数，前面的 2 表示 K 和 V。

**例**：$L=32,\ n_{kv}=32,\ d_{head}=128,\ S=4096,\ B=1$，FP16(2 字节)：
$$
2 \times 32 \times 32 \times 128 \times 4096 \times 1 \times 2 \approx 2.1\ \text{GB（单条）}
$$
并发到 16 就是约 34 GB——**KV Cache 往往比权重还吃显存**。

### 6.2 INT8 / INT4 在线量化机制

把缓存里的 K、V 从 FP16 压成 INT8(2×) 或 INT4(4×)：

```
KV 量化数据流(per-block / per-channel 标定)
写入时:  K_fp16 ──[量化]──► K_int8 + scale/zero ──► 存进 KV Cache(省 2~4×)
读取时:  K_int8 + scale ──[反量化]──► K_fp16 ──► 参与 attention 计算
```

- **量化公式(对称/非对称之一)**：$q = \mathrm{round}(x / s)$，$\hat{x} = q \cdot s$，$s = \dfrac{\max|x|}{2^{b-1}-1}$($b$=8 或 4)。
- **粒度**：按通道/按 block 选 scale，比整张一个 scale 精度好得多。
- **省下的显存** → 直接换成**更大 batch 或更长上下文**。
- **精度账**：INT8 几乎无损，INT4 需要更细粒度标定，长序列/高精度任务上略有损失，建议先评测。

> 对应文件里 "kv quantization and inference switch"：开启即在 `backend_config` 里设置 KV 量化位宽(如 `quant_policy`，**具体字段名以官方文档为准**)。

## 7. W4A16 权重量化(装更大模型)

**W4A16**：**W**eight 用 **4** bit、**A**ctivation 用 **16** bit(FP16/BF16)。即权重压到 4bit 省显存，激活保持 16bit 保精度。LMDeploy 走 **AWQ(Activation-aware Weight Quantization)** 路线。

```
W4A16 计算流(一个线性层)
权重 W: 4bit 存储(显存约 1/4)
            │ 运行时 dequant
            ▼
        W_fp16  ×  X_fp16(激活, 全精度)  =  Y_fp16
            ▲
   AWQ: 按激活分布给"重要通道"更高有效精度
        (per-group scale, group_size 如 128)
```

要点：
- **显存收益**：FP16→INT4，权重约省 **4×**。7B 模型权重从约 14GB 降到约 3.5GB，单张消费级卡也能跑。
- **AWQ 思路**：不是所有权重一样重要;通过校准集观察**激活幅度大的通道更敏感**，对其施加 per-channel 缩放，让量化误差集中到不重要处——比朴素 round-to-nearest 精度高很多。详见 [[llm-compression/quantization/量化基础]]。
- **group_size**：每多少个权重共享一组 scale(常见 128)。越小越精细但元数据开销越大。
- **为什么不量化激活(A 保 16bit)**：激活分布动态、含离群值，量化到 4bit 易掉点;W4A16 是"显存收益大、精度损失小"的甜点。
- **量化命令**：`lmdeploy lite auto_awq` 离线产出 4bit 权重，再用引擎加载。

数值直觉：单卡 24GB，FP16 跑 7B(14GB 权重 + KV)很快被 KV 挤爆;W4A16 后权重仅 ~3.5GB，**剩余显存几乎全给 KV Cache** → 并发/上下文大幅提升。W4A16 与 KV 量化**可叠加**。

## 8. 多模型 / 多模态 / 分布式 / 长上下文

### 8.1 分布式：张量并行(TP)

单卡装不下时，把每层权重沿张量维切到多卡：

```
张量并行 TP=4(单层 FFN 切分)
        输入 X(各卡复制)
   ┌──────┬──────┬──────┬──────┐
  GPU0   GPU1   GPU2   GPU3
  W列切0  W列切1  W列切2  W列切3   ← 第一矩阵按列切
   └──────┴──────┴──────┴──────┘
        部分结果 → AllReduce/AllGather 通信
        合并 → 下一层
```

- 启动只需设 `tp=N`(N 通常为 2/4/8，需整除注意力头数)。
- **代价**：每层引入 all-reduce 通信，需 NVLink/高速互联才划算;跨机走 PP/多实例。
- 多机多卡 / 多实例由服务层 proxy 做路由(见 8.4)。

### 8.2 多模态(VLM)

支持视觉语言模型(如 LLaVA、InternVL、Qwen-VL 类，**具体清单以官方文档为准**)：

```
VLM 推理流
图像 ──► Vision Encoder ──► 视觉 token(embedding)
                                  │ 拼接
文本 ──► Tokenizer ──► 文本 token ─┘
                ▼
        LLM(TurboMind/PyTorch)逐 token 解码
```

视觉编码与 LLM 解码分阶段，视觉特征作为前缀 token 注入。

### 8.3 长上下文与 Prefix Caching

- **长上下文(long context switch)**：通过 RoPE 缩放(动态 NTK / 线性插值等)外推位置编码 + Blocked KV Cache 支撑超长 KV，开关在配置里(对应文件 "long context switch")。
- **Prefix Caching(prefix caching switch)**：多个请求共享相同前缀(如同一段 system prompt / few-shot 示例)时，**复用已算好的 KV block，跳过重复 prefill**。

```
Prefix Caching 命中
请求1: [系统提示 P][问题 A]  → 算出 P 的 KV(缓存)
请求2: [系统提示 P][问题 B]  → P 命中! 直接复用 KV,只算 B
                                ↑ 省下 P 的 prefill 计算 → TTFT 大降
```

### 8.4 多模型 / 多实例服务

```
多模型路由(proxy)
            ┌──► 实例A: 模型X (GPU0-1, TP=2)
客户端 ──► proxy ──► 实例B: 模型Y (GPU2-3, TP=2)
            └──► 实例C: 模型X 副本(负载均衡)
```

- 同机/多机起多个 `api_server`，前面挂 proxy 做模型路由与负载均衡。
- 统一 OpenAI 兼容接口，客户端按 `model` 字段选目标。

## 9. 功能矩阵(讲机制，不背版本)

| 能力 | TurboMind | PyTorch 后端 | 机制一句话 |
|------|-----------|--------------|------------|
| 持久/连续批 | ✅ persistent batch | ✅ continuous batch | token 粒度调度，槽位填满 |
| 分块 KV Cache | ✅ Blocked | ✅ Paged | 固定块按需分配，消碎片 |
| KV INT8 | ✅ | ✅(以文档为准) | 写入量化、读取反量化，2× 省显存 |
| KV INT4 | ✅ | 视版本 | 4× 省显存，需细粒度标定 |
| W4A16(AWQ) | ✅ | ✅ | 4bit 权重 dequant×16bit 激活 |
| W8A8 | 视版本 | ✅(SmoothQuant 类) | 权重激活皆 8bit |
| 张量并行 TP | ✅ | ✅ | 每层切多卡 + all-reduce |
| Prefix Caching | ✅ | ✅ | 共享前缀复用 KV |
| 长上下文 | ✅ | ✅ | RoPE 缩放 + 大 KV |
| 多模态 VLM | ✅(部分) | ✅(部分) | 视觉 token 前缀注入 |
| 新模型适配速度 | 慢(C++/CUDA) | 快(Python) | 灵活性 vs 极致性能 |

> 标 ✅/视版本者请以**当下官方文档/源码**为准，本表讲的是"机制存在与否的逻辑"，不锁定精确版本支持。

## 典型配置示例(讲含义)

以 Python `pipeline` 为例(字段名以官方文档为准，重在理解含义)：

```python
from lmdeploy import pipeline, TurbomindEngineConfig

backend = TurbomindEngineConfig(
    tp=2,                  # 张量并行卡数：单卡装不下/想提吞吐时调大
    session_len=8192,      # 单会话最大上下文长度：决定 KV 上限
    max_batch_size=128,    # 最大并发：受 KV block 数与显存约束
    cache_max_entry_count=0.8,  # KV Cache 占可用显存比例：越大并发越高
    quant_policy=8,        # KV 量化位宽(8=INT8)：省显存换并发
    model_format='awq',    # 加载 W4A16(AWQ) 量化权重
)
pipe = pipeline('your/awq-model-path', backend_config=backend)
print(pipe(['解释一下张量并行']))
```

关键参数的权衡：

| 参数 | 含义 | 调大的影响 | 调小的影响 |
|------|------|-----------|-----------|
| `tp` | 张量并行卡数 | 能装更大模型/更高吞吐，但增通信开销 | 省卡，但单卡可能装不下 |
| `session_len` | 最大上下文 | 支持长文，但 KV 占用线性上升 | 省显存，长输入会截断 |
| `cache_max_entry_count` | KV 占显存比例 | 并发更高 | 留余量更安全，并发降 |
| `quant_policy` | KV 量化位宽 | (开启)显存省、并发升、精度略降 | (关闭)精度最高、显存吃紧 |
| `max_batch_size` | 最大并发批 | 吞吐潜力大，需显存撑得住 | 延迟更稳，吞吐受限 |

> 起服务一行命令：`lmdeploy serve api_server <模型路径> --tp 2 --backend turbomind`，对外即 OpenAI 兼容 `/v1/chat/completions`。

## 常见问题

| 问题 | 答案 |
|------|------|
| TurboMind 和 PyTorch 后端怎么选？ | 主流结构 + 追极致性能选 TurboMind；新/特殊模型、快速验证选 PyTorch；拿不准用默认让其自动选 |
| W4A16 会掉点吗？ | AWQ 校准下通常损失很小；对极敏感任务先用评测集验证 |
| KV INT8 和 INT4 区别？ | INT8 近无损、最常用；INT4 省更多显存但需更细标定，长序列可能掉点 |
| W4A16 和 KV 量化能一起开吗？ | 能，分别作用于权重和 KV Cache，显存收益叠加 |
| 为什么开了量化反而能提吞吐？ | 省下的显存换成更多 KV block → 更高并发 → 吞吐升 |
| 持久批和静态批差别？ | 持久批 token 粒度进出，槽位填满；静态批要等最慢请求，GPU 空转 |
| TP 是不是越大越好？ | 不是，通信开销随卡数增长，需高速互联；超出收益区间反而变慢 |
| Prefix Caching 什么时候有用？ | 大量请求共享同一前缀(system prompt/few-shot)时，省重复 prefill，降 TTFT |
| 长上下文怎么开？ | 配置里开 long context(RoPE 缩放)+ 调大 session_len，注意 KV 显存 |
| 精确版本/CLI 默认值在哪查？ | 一律以官方文档与源码为准，本笔记只讲稳定机制 |
