## 0. 一句话锚点

> **启动参数 = 把一块 GPU 的「显存 + 算力」切成几份给「权重 / KV Cache / 激活」，再决定一次批处理能塞多少请求、多长序列。**

记住三句话即可建立直觉：

1. **显存预算固定**：`权重 + KV Cache + 激活/碎片 ≈ gpu_memory_utilization × 显存总量`。
2. **KV Cache 是变量**：权重大小固定，激活基本固定，**KV Cache 是唯一随并发/序列长度膨胀的大头**，所以绝大多数参数最终都在调它。
3. **批越大吞吐越高、但单条时延越差**，`max-num-seqs` / `max-num-batched-tokens` 就是这把双刃剑的刻度。

- 引擎启动参数：https://docs.vllm.ai/en/stable/models/engine_args.html
- 并行配置参数：https://github.com/vllm-project/vllm/blob/v0.5.2/vllm/config.py

## 1. 地基：vLLM 引擎在做什么

要理解参数，先要知道 LLM 推理分两个阶段：

```
       一次请求 = Prefill(预填充) + Decode(解码)
  ┌─────────────────────────┬──────────────────────────────┐
  │ Prefill                 │ Decode                       │
  │ 把 prompt 全部 token    │ 自回归一次生成 1 个 token    │
  │ 一次性过一遍模型        │ 反复跑，直到 EOS/到长度上限  │
  │ 计算密集(compute-bound) │ 访存密集(memory-bound)       │
  │ 产出整段 prompt 的 KV   │ 每步追加 1 个 token 的 KV    │
  └─────────────────────────┴──────────────────────────────┘
```

vLLM 的两大核心机制，决定了参数为什么这么设计：

- **PagedAttention**：把 KV Cache 切成固定大小的「块(block)」，像操作系统的分页内存一样按需分配，几乎消灭显存碎片 → 这是 `--gpu-memory-utilization` 能开到 0.9 的底气（参见 [[llm-optimizer/kv-cache]]）。
- **Continuous Batching（连续批处理）**：不等整批请求都结束才换批，而是**每一步迭代都动态把已完成的请求踢出、把等待队列里的新请求加进来** → 这是 `--max-num-seqs` / `--max-num-batched-tokens` 存在的根本原因。

```
传统静态批：  [A B C D] ───跑到最长的那条结束───> 全部释放（GPU 空转等齐）
连续批处理：  step t  : [A B C D]
              step t+1: [A   C D E]   ← B 结束，E 从 waiting_list 补位
              step t+2: [A   C   E F] ← D 结束，F 补位
              GPU 永远满载，这就是 vLLM 高吞吐的来源
```

参数都挂在 `EngineArgs` 上；用 `vllm serve <model>` 或 `python -m vllm.entrypoints.openai.api_server` 时，命令行 flag 一一映射到这些字段。

## 2. 显存这块蛋糕怎么分

### 2.1 `--gpu-memory-utilization`

> 用于模型执行的 GPU 内存比例，范围 0~1。例如 0.5 表示用 50% 显存。**未指定时默认 0.9。**

这是**整块蛋糕的总大小**。vLLM 启动时：

```
可用显存 = gpu_memory_utilization × 显存总量
KV Cache 可用空间 = 可用显存 − 权重显存 − 激活/CUDA Graph/临时缓冲
```

留 10% 余量（默认 0.9）是为了激活、CUDA Graph 捕获、NCCL 缓冲等。**调太高（如 0.98）容易在峰值并发时 OOM；调太低则 KV Cache 块数变少、能并发的请求数下降。**

### 2.2 `--max-model-len`

> 模型上下文长度。**未指定则自动从模型 config 派生**（如 Llama-3 的 8192）。

它直接决定**单条序列最多占多少 KV Cache 块**。手算一条序列的 KV Cache 显存：

$$
\text{KV bytes} = 2 \times L \times n_{kv} \times d_{head} \times \text{seq\_len} \times \text{dtype\_bytes}
$$

其中 2 = K 和 V 两份，$L$ = 层数，$n_{kv}$ = KV 头数（GQA 下远小于 Q 头数）。

**数值示例（Llama-2-7B，fp16）**：$L=32$、$n_{kv}=32$、$d_{head}=128$、`max-model-len=4096`：

$$
2 \times 32 \times 32 \times 128 \times 4096 \times 2\,\text{B} \approx 2.1\ \text{GB / 条}
$$

一张 80GB A100 装完 14GB 权重后剩约 58GB（按 0.9），最多约能并发 $58/2.1 \approx 27$ 条满长度序列。**这解释了为什么把 `max-model-len` 从 4096 砍到 2048，并发上限直接翻倍。**

```
80GB ┌──────────────────────────────────────────────┐
     │ 权重 14GB │  KV Cache 可分块区 ~58GB  │留 8GB │
     └──────────┴───────────────────────────┴───────┘
                  ↑ max-model-len 越大，单条吃得越多，能并发的越少
```

## 3. 批处理的两个上限（吞吐核心旋钮）

vLLM 的一步迭代受**两个独立上限**约束，谁先到顶谁生效：

### 3.1 `--max-num-seqs`（一次最多几条序列）

> 每次迭代的最大序列数，**默认 256**。

原文踩坑（保真保留）：

- **`max-num-seqs` 太小**：较迟到的 request 进入 `waiting_list`，要等前面有 request 结束才被加进生成队列 → 排队时延高、GPU 没吃饱。
- **`max-num-seqs` 太大**：会出现一部分 request 在生成了 3-4 个 token 后被**挤回 `waiting_list`**（有些用户表现为「生成到一半卡住」），因为 KV Cache 块被抢占（preemption）。

> **过大或过小的 `max-num-seqs` 都会影响用户体验。** 它本质是「允许多少条并发」，但能不能真容下，还要看 KV Cache 够不够（见第 2 节）。

### 3.2 `--max-num-batched-tokens`（一次最多几个 token）

> 每次迭代的最大批处理 Token 数。原文要点：

- 这是**很重要的配置**。比如配 `max-num-batched-tokens=1000`，那么一个 batch 大概能处理 **10 条平均长度约 100 tokens** 的 inputs。
- 它**应尽可能大**，来充分发挥 continuous batching 的优势。
- 在提供 HF 模型时，该值**似乎能被自动推导**出来（注：原文标注「对 TGI 是这样，vLLM 不太确定」，保留此存疑结论）。

```
两个闸门同时卡：哪个先满，这一步就停止收新请求
   seqs 闸门:  ███████░░  (已 200/256)
   tokens 闸门:███████████  (已满 → 触顶，本步不再加序列)
   ⇒ Prefill 阶段通常 tokens 先触顶；纯 Decode 阶段 seqs 容易先触顶
```

**对照直觉**：

| 现象 | 多半是哪个上限 | 调法 |
|---|---|---|
| 吞吐上不去、GPU 利用率低 | 两者都偏小 | 一起调大 |
| 长 prompt 请求卡顿 | `max-num-batched-tokens` 太小 | 调大 + 开 chunked-prefill |
| OOM / 请求被抢占 | KV Cache 不够撑 `max-num-seqs` | 减小 seqs 或 max-model-len |

## 4. Chunked Prefill 与前缀缓存

### 4.1 `--enable-chunked-prefill`

> 如果设置，预填充请求可以根据 `max_num_batched_tokens` 进行**分块**。

为什么需要？一条 8K token 的长 prompt 做 Prefill 会**长时间霸占整步**，让正在 Decode 的其他请求「卡住」（time-between-tokens 飙升）。

```
不分块:  step ──[ 一条长 Prefill 占满 ]── 其他 Decode 全部等待 → 卡顿
分块  :  step1 [Prefill 前 512 + 多条 Decode]
         step2 [Prefill 中 512 + 多条 Decode]   ← Prefill 被切片，
         step3 [Prefill 后 512 + 多条 Decode]      Decode 不再被饿死
```

效果：把 Prefill 切成小片，**与 Decode 混在同一步**跑，平滑长 prompt 对在线时延的冲击，是改善 TTFT/TBT 的关键开关（指标见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]）。

### 4.2 `--enable-prefix-caching`

> 启用自动前缀缓存（Automatic Prefix Caching）。**默认 false。**

原理：多个请求共享相同前缀（如同一个 system prompt、few-shot 模板）时，**这段前缀的 KV Cache 只算一次、跨请求复用**。靠的就是 PagedAttention 的「块」可被多个序列以哈希引用共享。

```
请求1: [系统提示词 1024 tok][用户问题A]
请求2: [系统提示词 1024 tok][用户问题B]   ← 前 1024 tok 的 KV 直接命中缓存，跳过重算
适用场景: 固定 system prompt、RAG 同文档多问、多轮对话历史
```

收益：命中时 Prefill 计算量大降、TTFT 显著下降。代价：缓存占 KV Cache 空间，低复用场景几乎无收益（参见 [[llm-optimizer/kv-cache]]）。

## 5. 多卡并行：TP 与 PP

当单卡装不下模型，或想进一步提吞吐：

```
张量并行 TP (-tp):  把每一层「横切」，每张卡算一部分矩阵，逐层 all-reduce 同步
   GPU0 ─┐
   GPU1 ─┼─ 每层都要通信，对带宽极敏感 → 通常只在单机内 NVLink 上做
   GPU2 ─┤
   GPU3 ─┘   tensor-parallel-size 一般 = 单机卡数

流水并行 PP (-pp):  把模型「纵切」成几段，卡 i 算第 i 段，激活在卡间传递
   GPU0[1-8层] → GPU1[9-16层] → ...  通信少，可跨机，但有流水气泡
```

- `--tensor-parallel-size, -tp`：张量并行大小，**默认 1**。`-tp 4` = 4 卡张量并行（注意：`头数 % tp == 0` 才能整除切分）。
- `--pipeline-parallel-size, -pp`：流水线并行大小，**默认 1**。
- `--disable-custom-all-reduce`：禁用自定义 all-reduce Kernel，**回退到用 NCCL**。当自研 all-reduce 在某些拓扑/驱动下出错或更慢时用它兜底。

> 通信原理见 [[ai-infra/网络/集合通信原语]]；机间互联见 [[ai-infra/网络/InfiniBand]]。总卡数 = tp × pp。

## 6. 精度与量化

### 6.1 `--dtype` 权重与激活精度

> 可能的选择：`auto`、`half`、`float16`、`bfloat16`、`float`、`float32`。

`auto` = 跟随模型 config。**bf16 动态范围比 fp16 大、不易溢出**，大模型训练/推理多用 bf16（Ampere 及以上支持）。

### 6.2 `--kv-cache-dtype` KV Cache 精度（省显存利器）

> kv 缓存存储的数据类型，可能的选择：`auto`、`fp8`、`fp8_e5m2`、`fp8_e4m3`。`auto` 时使用模型数据类型。

把 KV Cache 从 fp16 → fp8，**KV Cache 显存直接减半**，等价于第 2 节并发上限翻倍。`e5m2`（5 指数 2 尾数，范围大）与 `e4m3`（4 指数 3 尾数，精度高）是两种 fp8 编码，权衡见 [[llm-compression/quantization/fp8]]。

```
fp16 KV:  ████████████████  2 字节/元素
fp8  KV:  ████████          1 字节/元素  → 同显存装 2 倍序列，略损精度
```

### 6.3 `--quantization, -q` 权重量化

> 用于量化权重的方法，可能选择（原文保留）：`aqlm`、`awq`、`deepspeedfp`、`tpu_int8`、`fp8`、`fbgemm_fp8`、`modelopt`、`marlin`、`gguf`、`gptq_marlin_24`、`gptq_marlin`、`awq_marlin`、`gptq`、`compressed-tensors`、`bitsandbytes`、`qqq`、`experts_int8`、`neuron_quant`、`ipex`、`None`。
> 若为 `None`：**先检查模型 config 的 `quantization_config` 属性；若也为 None，则假设权重未量化，用 `--dtype` 决定数据类型。**

量化把权重 fp16 → int4/int8/fp8，**权重显存大降**（int4 ≈ 1/4），给 KV Cache 让出空间、并发上限上升。常见 GPTQ/AWQ 见 [[llm-compression/quantization/GPTQ]] 与 [[llm-compression/quantization/量化基础]]。

## 7. CUDA Graph 与 `--enforce-eager`

> 在 vLLM 中，`--enforce-eager` 标志用于**强制使用 PyTorch 的 eager 执行模式**，而非默认的图执行模式。eager 模式逐行执行代码，便于调试和动态控制流，但**性能可能较低**。图执行模式则优化性能，但调试复杂。开发或调试时用此标志可更灵活地控制模型行为。

补充原理：默认情况下 vLLM 用 **CUDA Graph** 把 Decode 步的众多小 kernel「录制」成一张图，重放时省掉 CPU 逐个 launch kernel 的开销（这正是 Decode 访存密集、kernel 又多又小时的性能关键）。

```
eager:   每步 CPU 逐个 launch:  k1→k2→k3→...→kN   ← launch 开销大
graph:   首次录制成一张图，之后整图重放一次        ← launch 开销摊薄
```

代价：CUDA Graph 捕获**额外占显存**，且要求形状相对固定。所以 `--enforce-eager` 的两个用途：① 调试；② **显存极度吃紧时关掉 Graph 省那部分显存**（以吞吐换显存）。

### 7.1 `--use-v2-block-manager`（已废弃，保留说明）

> [DEPRECATED] block manager v1 has been removed and `SelfAttnBlockSpaceManager`（即 block manager v2）is now the default. Setting this flag to True or False has no effect on vLLM behavior.
>
> [已废弃] v1 版本的块管理器已被移除，现在默认使用 `SelfAttnBlockSpaceManager`（即块管理器 v2）。把这个标志设为真或假对 vLLM 的行为没有影响。

### 启动示例（按上述参数组合）

```bash
# 单卡起一个 OpenAI 兼容服务（最小可用）
vllm serve facebook/opt-125m \
    --served-model-name opt \
    --gpu-memory-utilization 0.9 \
    --max-model-len 2048

# 4 卡张量并行 + 长上下文 + 省显存（fp8 KV）+ 在线时延优化
vllm serve /models/llama2-7b \
    --tensor-parallel-size 4 \
    --max-model-len 4096 \
    --dtype bfloat16 \
    --kv-cache-dtype fp8 \
    --enable-prefix-caching \
    --enable-chunked-prefill \
    --max-num-batched-tokens 8192 \
    --max-num-seqs 256 \
    --gpu-memory-utilization 0.9

# 显存吃紧 / 调试：关 CUDA Graph 走 eager
vllm serve /models/llama2-7b --enforce-eager --gpu-memory-utilization 0.85
```

## 常见问题 / 坑

| 现象 / 问题 | 根因 | 处理 |
|---|---|---|
| 启动即 OOM | `--gpu-memory-utilization` 太高 / 权重太大 | 降到 0.85；上量化 `-q`；加 `--enforce-eager` 省 Graph 显存 |
| 请求「生成到一半卡住」 | `max-num-seqs` 太大，KV Cache 不够被抢占(preemption) | 减小 `--max-num-seqs` 或 `--max-model-len` |
| 新请求长时间排队 | `max-num-seqs` 太小，后到的进 waiting_list | 适度增大 `--max-num-seqs`（前提是 KV Cache 够） |
| 吞吐上不去、GPU 不满载 | 批太小 | 一起调大 `--max-num-seqs` 与 `--max-num-batched-tokens` |
| 长 prompt 拖累其他请求时延 | Prefill 霸占整步 | 开 `--enable-chunked-prefill` |
| 固定 system prompt 仍重复算 Prefill | 没开前缀缓存 | 加 `--enable-prefix-caching` |
| 多卡报 all-reduce 错误 / 反而变慢 | 自定义 all-reduce kernel 在该拓扑不适配 | `--disable-custom-all-reduce` 回退 NCCL |
| `-tp N` 启动失败 | 注意力头数不能被 N 整除 | 选能整除头数的 `tensor-parallel-size` |
| KV Cache 显存爆 | `max-model-len` 设太大 | 砍 `--max-model-len`，或 `--kv-cache-dtype fp8` |
| 加载远程模型代码报错 | 默认不信任远程代码 | 加 `--trust-remote-code` |
| `--use-v2-block-manager` 不生效 | 该 flag 已废弃，v2 已成默认 | 删掉它，无需设置 |
| 推导不出 `max-num-batched-tokens` | 自动推导对 vLLM「不太确定」（原文存疑） | 显式手动配置，别依赖自动推导 |
