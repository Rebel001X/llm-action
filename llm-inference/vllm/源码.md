## 0. 一句话锚点

> **读 vLLM 源码，只要抓住一条主循环 `LLMEngine.step()`，其余全是它的下属。**

```
   一次 step() = 调度一拍 + 执行一拍 + 收尾一拍
   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ Scheduler    │→  │ ModelExecutor│→  │ process_     │
   │ .schedule()  │   │ .execute()   │   │ outputs()    │
   │ 决定跑哪些 seq│   │ 真正前向一次 │   │ 出 token/收尾│
   └──────────────┘   └──────────────┘   └──────────────┘
        ▲ 账本                ▲ 手脚              ▲ 采样+回收
    BlockManager        Worker/ModelRunner    Sequence 状态机
```

记住：**Scheduler 不碰 GPU，Worker 不做决策。** 决策与执行分离，是看懂整个仓库的钥匙。

## 1. 地基：为什么要切成这么多模块

朴素推理框架常把"读请求、排队、算 attention、采样"糊在一个 `generate()` 里。vLLM 要做**连续批处理 + 分页 KV-Cache**，就必须把三件事拆开：

1. **决策**（这一步该跑哪些序列、显存够不够）——纯 CPU 逻辑，要快、要可测试，不该和 CUDA 绑死 → `Scheduler` + `BlockManager`。
2. **执行**（把决策变成一次真实的 GPU 前向）——和硬件、并行方式强相关 → `Worker` + `ModelRunner` + `AttentionBackend`。
3. **编排**（驱动上面两者一拍一拍转，管理每条请求的状态机）→ `LLMEngine`。

这种"决策/执行/编排"三分，带来三个好处：

```
  解耦的回报
  ├─ 可替换执行后端：CUDA / ROCm / CPU / TPU 只换 Worker 层
  ├─ 可替换注意力实现：FlashAttn / FlashInfer / xFormers 只换 Backend
  └─ 调度逻辑可单测：BlockManager 是纯 Python，不需要 GPU
```

> 为什么强调"讲架构不背行号"：vLLM 迭代极快（V0→V1 重写、文件常搬家），**行号 3 个月就失效，但"谁负责决策、谁负责执行"的骨架长期稳定**。下面只讲机制与职责，不钉死行号；精确签名以你本地源码为准。

## 3. LLMEngine：唯一的编排循环

`LLMEngine` 是整个系统的中枢。它持有：调度器（Scheduler）、执行器（ModelExecutor）、分词器、以及全部 `SequenceGroup` 的状态。对外只有两类动作：

- `add_request(...)`：把一条新请求包成 `SequenceGroup`，丢进 Scheduler 的 `waiting` 队列。
- `step()`：**推进一拍**——调度一次、前向一次、收尾一次。返回这一拍产出的（部分或完整）输出。

```
   LLMEngine.step()  伪代码骨架（讲机制，非逐行）
   ┌─────────────────────────────────────────────┐
   │ 1. seq_group_meta, sched_out =               │
   │        self.scheduler.schedule()             │  ← 决策
   │                                              │
   │ 2. output = self.model_executor              │
   │        .execute_model(seq_group_meta, ...)   │  ← 执行(真前向)
   │                                              │
   │ 3. self._process_model_outputs(output, ...)  │  ← 采样结果回填
   │        ├ 把新 token 追加到各 Sequence         │
   │        ├ 命中停止条件的标记 FINISHED          │
   │        └ scheduler.free_finished()           │
   │                                              │
   │ 4. return [RequestOutput ...]                │
   └─────────────────────────────────────────────┘
```

关键认知：

- **离线 `LLM.generate()`** 内部就是一个 `while engine.has_unfinished_requests(): engine.step()` 的循环——所有请求一起喂进去，反复 step 直到全部完成。
- **在线服务**用 `AsyncLLMEngine` 把 `step()` 放进 asyncio 后台循环，每个 HTTP 连接拿到一个 `AsyncStream`，token 一边生成一边流式返回。它**不是新调度逻辑**，只是给同一个 `LLMEngine` 套了异步外壳 + 请求注册表。

> `step()` 是**同步阻塞**一拍的：一次 step 内全 batch 共同前向一个 token。连续批处理的"连续"，体现在**不同 step 之间**序列可以自由进出 batch，而不是 step 内部。

## 4. Scheduler：谁先跑、抢谁、换谁

`Scheduler` 是纯 CPU 决策器，维护三个队列：

```
  waiting  ──(显存够 & prefill)──►  running  ──(显存不够,被抢占)──►  swapped
   等待首次                          正在解码                         换出到CPU
   prefill                          的序列                          的序列
     ▲                                                                 │
     └──────────────(资源恢复, 换回 / 重算)──────────────────────────────┘
```

每次 `schedule()` 大致做四件事：

1. **挑选**：在显存预算（由 BlockManager 给出的可用块数）内，从 `running`/`swapped`/`waiting` 里挑出本拍要跑的 `SequenceGroup`。优先保 `running`，再尝试 `swapped` 换回，最后才放新 `waiting` 进来。
2. **抢占（preemption）**：显存不够时，牺牲优先级低的 running 序列。两种策略：
   - **Swap**：把它的 KV 块换出到 CPU（`blocks_to_swap_out`），资源好转再换回。
   - **Recompute**：直接丢弃 KV，下次当新 prefill 重算（短序列更划算，省得搬数据）。
3. **生成搬运指令**：产出 `blocks_to_swap_in / swap_out / copy` 三张表，交给执行层照做（写时复制的 copy 用于 beam search / 前缀共享分叉）。
4. **打包元数据**：把选中序列封成 `SequenceGroupMetadata`（含每个序列的 block table、要算的 token 等）。

> 调度策略可配（如 FCFS / priority）。这一节的"挑选 + 抢占 + 搬运"三段是稳定骨架，具体阈值/策略名以源码 `SchedulerConfig` 为准。Chunked Prefill（把长 prefill 切块、与 decode 混批）也是在这里决定每序列本拍算多少 token。

## 5. BlockManager：KV 分页的"页表"账本

这是 PagedAttention 的"内存管理单元"。它**不存数据，只记账**——哪些物理块空闲、哪条序列用了哪些块。

核心数据结构（概念）：

```
  逻辑块(Logical Block)        物理块(Physical Block)
  序列视角:第0..k块             显存视角:第0..N号块
       │                              │
       └────── block table ───────────┘   (每条序列一张映射表)

  block_size = 16 tokens/块  (典型默认值, 以配置为准)
```

它管两类资源：**GPU blocks** 与 **CPU blocks**（swap 用）。核心能力：

- **按需分配**：序列每多生成约 `block_size` 个 token，才申请一个新物理块——不预留"最大长度"，碎片几乎归零。
- **引用计数 + 写时复制（CoW）**：多个序列共享同一前缀时，物理块被多条序列引用（refcount>1）；某条要写新内容时先复制再写（产生一条 `copy` 指令）。**前缀缓存（Prefix Caching）**正是靠"相同前缀 → 同一批物理块"实现的。
- **可用块数 = 调度预算**：Scheduler 问它"还能塞下几个块"，以此判断 `can_allocate / can_append_slots`，决定是否抢占。

数值直觉：

> 设模型 KV 每 token 占 $b$ 字节，`block_size=16`，则每块占 $16b$。若给 KV 留 $M$ 字节显存，则总块数 $N=\lfloor M/(16b)\rfloor$。一条长 $L$ 的序列占 $\lceil L/16\rceil$ 块。能并发的序列数 $\approx N / \lceil L/16\rceil$——**块越能共享/越按需，分母越小，并发越高**。

```
  显存占用对比(示意, 同样显存)
  朴素预留:  [████████预留到max_len████████]  ← 实际只用前 1/4, 浪费 3/4
  分页按需:  [██用██][空][空]...→需要才加块     ← 浪费≈不足一块
```

## 6. Worker / ModelRunner / CacheEngine：手脚三件套

调度结果到了执行层，由三个类接力：

```
  Worker (= 1 进程 / 1 GPU)
    ├─ CacheEngine    管这块卡上的 KV 物理显存(GPU+CPU缓冲)
    │     ├ swap_in / swap_out   按 Scheduler 给的表搬 KV
    │     └ copy                 写时复制
    └─ ModelRunner    本拍真正的前向执行
          ├ prepare_inputs   把 SequenceGroupMetadata → 张量
          │                  (token ids / positions / block tables / slot mapping)
          ├ model(...)       调 model_executor 里的网络前向
          └ sampler(...)     按采样参数出下一个 token
```

- **Worker**：进程级单位，张量并行时一卡一个 Worker。它先做 `determine_num_blocks`（profiling 显存→定 KV 块数，这就是 `gpu_memory_utilization` 起作用的地方），再在每拍 `execute_model` 时先让 CacheEngine 搬块、再让 ModelRunner 前向。
- **ModelRunner**：执行层的"翻译官"。最关键是 `prepare_inputs`——把每序列的 block table 摊平成 **slot mapping**（每个 token 的 KV 写到哪个物理 slot），attention kernel 据此读写分页 KV。它还负责 **CUDA Graph 捕获/重放**（decode 阶段形状固定，捕获成图省去启动开销）。
- **CacheEngine**（你原文已抓到的类）：初始化并持有 GPU/CPU 的 KV 张量，提供 `swap_in/swap_out/copy`。它是 `BlockManager` 决策的"物理执行者"——**账本在 core，搬运在 worker**。

> `CacheConfig`（原文已列字段）就是喂给这一层的旋钮：`block_size` 决定页粒度，`gpu_memory_utilization` 决定留多少显存给 KV，`swap_space` 决定 CPU 换出空间，`enable_prefix_caching` 打开前缀块共享，`cache_dtype`（如 fp8）压缩 KV 省显存。

## 7. ModelExecutor 与分布式：执行的统一入口

`LLMEngine` 不直接持有一堆 Worker，而是持有一个 **Executor**（`ExecutorBase` 的实现）。Executor 是"对上屏蔽并行方式"的抽象层：

```
            LLMEngine
                │ execute_model(...)
                ▼
        ┌───────────────┐
        │  Executor     │   按部署方式选实现:
        └───────────────┘   ├ 单卡:    直接调本进程 Worker
            │   │   │       ├ 多卡同机: 多进程(mp)广播
            ▼   ▼   ▼       └ 多机:    Ray actors
         Worker0 ... WorkerK
         (各管一块GPU, TP/PP 切分)
```

- **张量并行 TP**：同一层的权重按列/行切到多卡，每拍各卡算自己那片再 all-reduce。Executor 负责把同一份 `SequenceGroupMetadata` 广播给所有 Worker，并收集结果。
- **流水并行 PP**：把层分段放到不同卡/机，配合 micro-batch 提利用率。
- 对 `LLMEngine` 而言，"单卡 / 多卡 / 多机"调用签名一致，**并行复杂度被 Executor 吃掉了**——这是又一处关键解耦点。

> 注意区分两个"executor"：`executor/`（分布式执行入口，本节）和 `model_executor/`（装模型权重与算子层，第 8 节的上游）。命名相近但层次不同。

## 8. AttentionBackend：PagedAttention 落到 kernel

模型里的每个 attention 层不自己写 CUDA，而是调一个**可插拔的后端**。这是为了在不同硬件/不同 kernel 库间切换而不改模型代码。

```
  AttentionLayer.forward()
        │ 传入: query, key, value, kv_cache(分页), attn_metadata
        ▼
   AttentionBackend (抽象)
   ├─ FlashAttention backend
   ├─ FlashInfer backend
   ├─ xFormers backend
   └─ (ROCm / CPU / TPU ...)
        │
        ▼  分两条路径
   prefill: 变长批量 attention(可用 flash)   decode: paged attention kernel
                                            (按 block table 读分页 KV)
```

后端要回答两件事：

1. **怎么读 KV**：decode 时 KV 不连续，分散在多个物理块里。Backend 拿 `attn_metadata` 里的 block table，做 **paged attention**——每个 query 按页表索引去对应物理块取 K/V 再算 softmax。
2. **prefill 与 decode 形状不同**：prefill 是一段连续新 token（可走标准 flash attention），decode 是每序列 1 个 query 配一长串历史 KV（走 paged kernel）。Backend 内部分流处理（Chunked Prefill 时两者还会混在一拍）。

> 后端通过环境变量/配置选择（如 `VLLM_ATTENTION_BACKEND`）。具体哪个后端默认、支持哪些 dtype/head_dim，以你本地版本的 backend selector 为准——这是变动最频繁的地方之一。

## 9. 完整调用链：一次 step() 的全程穿透

把前面所有模块串成一条线（离线场景）：

```
LLM.generate(prompts, params)
  └─ for p in prompts: engine.add_request(p)        # 入 waiting 队列
  └─ while engine.has_unfinished_requests():
        out = engine.step()
        │
        ├─[决策] Scheduler.schedule()
        │     ├─ BlockManager.can_allocate / can_append_slots   (查账本)
        │     ├─ 必要时 preempt → blocks_to_swap_out / recompute
        │     └─ 产出 SequenceGroupMetadata + 三张搬运表
        │
        ├─[执行] Executor.execute_model(meta, swap_in/out/copy)
        │     └─ 广播到每个 Worker:
        │           ├─ CacheEngine.swap_in/out/copy            (搬 KV)
        │           └─ ModelRunner.execute_model
        │                 ├─ prepare_inputs → slot mapping
        │                 ├─ model.forward
        │                 │     └─ 每层 AttentionBackend (paged attn)
        │                 └─ Sampler → 下一个 token id
        │
        └─[收尾] engine._process_model_outputs
              ├─ 新 token 追加到 Sequence
              ├─ 触发停止条件 → 标记 FINISHED
              └─ Scheduler.free_finished → BlockManager 回收物理块
```

读源码建议的**入口顺序**：`entrypoints/llm.py` → `engine/llm_engine.py: step` → `core/scheduler.py: schedule` → `worker/model_runner.py: prepare_inputs/execute_model` → `attention/backends/*`。顺着 `step()` 往下钻，比从底层往上看清晰得多。

## 10. 扩展点：想加东西从哪下手

| 你想做的事 | 该改哪一层 | 思路 |
|-----------|-----------|------|
| 接一个新模型结构 | `model_executor/models/` | 实现 `*ForCausalLM`，复用现成 layers + attention 接口 |
| 换/优化注意力 kernel | `attention/backends/` | 实现一个 `AttentionBackend` 子类并注册到 selector |
| 改调度/抢占策略 | `core/scheduler.py` | 自定义挑选与 preempt 逻辑，输入输出契约不变 |
| 改 KV 显存分配 | `core/block/` + `worker/cache_engine.py` | 账本逻辑在 core，物理搬运在 worker，成对改 |
| 加新硬件后端 | `worker/` + `executor/` | 新 Worker/Executor，沿用上层调度不变 |
| 自定义采样/logits 处理 | `model_executor/sampling/` 或 `logits_processor` | 在 sampler 前后插钩子 |
| 量化 KV / 权重 | `cache_dtype` / `quantization` 配置 + 对应 layer | fp8 KV 走 CacheConfig，权重量化走 layer |

设计上反复出现的模式：**上层只依赖抽象接口（Scheduler 的输出契约、AttentionBackend 抽象、ExecutorBase 抽象），换实现不动调用方。** 这就是它能快速支持新模型/新硬件的根因。

## 11. V0 vs V1：新架构改了什么（方向性认识）

vLLM 后续推出 **V1 引擎**重写，思路上的关键变化（讲方向，细节以官方文档/源码为准）：

```
  V0: 调度+执行较耦合, Python 开销在主循环里更显眼
  V1: 更彻底的"调度/执行进程分离" + 更统一的调度抽象
      ├─ EngineCore 独立进程跑调度+执行, 与前端 API 解耦
      ├─ prefill/decode 调度更统一(默认拥抱 chunked prefill)
      └─ 减少每步 Python 开销, 更友好的 CUDA Graph / 重叠
```

但**骨架没变**：仍然是"调度决策（谁跑/抢谁）+ 分页 KV 账本 + Worker 执行 + 可插拔 attention 后端"。本文讲的职责划分在 V0/V1 都成立——这正是"讲架构不背行号"的价值：实现层会重写，**职责边界长期稳定**。

> 你本地装的是哪个版本，先 `import vllm; vllm.__version__`，再决定按 V0 还是 V1 目录去对照。两者入口都从 `LLMEngine`（或 V1 的 `LLM`/`EngineCore`）的"加请求 + step 循环"看起。

| 问题 | 答 |
|------|----|
| Scheduler 会调 GPU 吗？ | 不会。它纯 CPU 决策，只产出"跑谁 + 搬哪些块"的指令 |
| KV 真正的显存谁分配？ | `CacheEngine`（worker 层）分配物理张量；`BlockManager`（core 层）只记账 |
| `block_size` 越大越好吗？ | 否。大块减少元数据但增内部碎片；小块省显存但调度开销大，典型取 16 |
| 前缀缓存靠什么实现？ | BlockManager 让相同前缀映射到同一批物理块 + 引用计数 + 写时复制 |
| 抢占用 swap 还是 recompute？ | 看序列长短：长序列搬 KV(swap)划算，短序列直接重算(recompute)更省 |
| 在线和离线调度不同吗？ | 同一个 `LLMEngine`/`Scheduler`；`AsyncLLMEngine` 只是异步外壳 + 流式返回 |
| 想换 FlashInfer 怎么做？ | 配置 attention backend（如 `VLLM_ATTENTION_BACKEND`），不改模型代码 |
| 为什么读源码别背行号？ | 文件常搬家、V0→V1 重写；职责边界稳定，行号 3 个月就失效 |
