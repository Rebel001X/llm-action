## 0. 一句话锚点

**vLLM 的本质：把"批"的粒度从「一整个请求」降到「一次前向迭代（one step）」，并用「分页 KV Cache（PagedAttention）」消除显存碎片，从而把 GPU 吞吐打满。**

一个请求不是"独占 GPU 跑到结束"，而是被切成无数个 step，每个 step 和别的请求拼成一个 batch 一起算。这叫 **continuous batching（连续批处理 / in-flight batching）**。

---

## 1. 地基：它解决什么问题

### 1.1 传统"静态批处理"的两大痛点

```
痛点① padding 浪费（序列长度不齐）—— 短请求被迫陪长请求跑完
       ┌────────── batch 一起算到最长 ──────────┐
A: ████████████████████████████████████████  有效（生成8个token）
B: ████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  ░=B早结束却在陪算padding

痛点② KV Cache 显存碎片
       为每个请求预分配 max_len 连续显存 → 短请求浪费大量预留 → 并发上不去
```

### 1.2 vLLM 的两把武器

| 武器 | 解决的痛点 | 机制 |
|---|---|---|
| **Continuous Batching** | padding 浪费 / 请求陪跑 | 以迭代为粒度，请求一结束立刻让位，新请求随时插入 |
| **PagedAttention** | KV 显存碎片 | KV 切成固定大小 block，按需分配，像 OS 虚拟内存分页 |

> 直觉类比：OS 不给进程一整块连续物理内存，而是分页 + 页表。vLLM 对 KV Cache 做了同样的事——**block 就是页，block_table 就是页表**。

## 2. 顶层架构与核心模块

```
   HTTP/API        ┌──────────────────── LLMEngine（总控）─────────────────────┐
  ┌──────────┐add_ │ ┌───────────┐  ┌────────────────┐                         │
  │ OpenAI    ├req─▶│ │ Tokenizer  │  │   Scheduler     │  每 step：             │
  │ 兼容Server │     │ │文本↔tokenid│  │ 三队列+抢占决策  │  调度→执行→处理输出     │
  └──────────┘     │ └───────────┘  └───────┬────────┘                         │
       ▲           │                        ▼                                  │
       │流式 token  │                ┌───────────────┐   ┌──────────────────┐  │
  ┌────┴───┐detok  │                │  BlockManager  │   │  Worker/Executor  │  │
  │  用户   │◀──────│                │ KV block/页表  │──▶│ ModelRunner+前向   │  │
  └────────┘       │                └───────────────┘   │ PagedAttention核   │  │
                   │                                     └──────────────────┘  │
                   └────────────────────────────────────────────────────────────┘
```

| 模块 | 职责 | 一句话 |
|---|---|---|
| **API Server** | 接 HTTP、OpenAI 兼容、流式回包 | 网络层 |
| **LLMEngine** | 总编排，驱动 `step()` 循环 | 心脏 |
| **Tokenizer** | 文本 ↔ token id | 翻译官 |
| **Scheduler** | 维护 waiting/running/swapped，决定每 step 跑谁、抢谁 | 大脑 |
| **BlockManager** | 管物理 KV block 池，维护逻辑→物理 block_table | 内存管理器 |
| **Worker/Executor** | 持权重，跑前向+采样；多卡做 TP/PP | 肌肉 |
| **ModelRunner** | 组装输入张量、调 PagedAttention 内核 | 算子调度 |

> 注：vLLM 后续推出 V1 架构，将调度/执行更彻底异步化、引入 EngineCore 进程隔离。具体类名/进程边界**以官方源码为准**，但"调度器 + 分页 KV + 迭代级批处理"的核心思想不变。

## 3. 入口：从文本到 SequenceGroup

```
用户 prompt "请翻译：Hello"
   │ ① tokenize：文本 → token_ids = [101, 5678, 233, ...]
   │ ② 封装（add_request）：
   │     Sequence      = 一条具体生成序列（token_ids + 状态）
   │     SequenceGroup = 同一 prompt 派生的一组 Sequence
   │                     n=1 普通采样→组里1条；n=4/beam=4→组里4条共享 prompt
   │ ③ 入队：Scheduler.waiting.append(seq_group)
   ▼
```

**为什么要 SequenceGroup 这层？** 同一 prompt 的多候选（`n>1`/beam）**共享 prompt 的 KV Cache**，打包成组便于：① prompt KV 共享（prefix 复用省显存）；② 统一调度与抢占（要换出一起换出）。

```
SequenceGroup 状态机：
WAITING ──分配到资源──▶ RUNNING ──采样到EOS/到长度──▶ FINISHED
   ▲                      │ 显存不够被抢占
   └──重计算丢KV回waiting──┤
                          ▼ swap抢占 KV换到CPU
                       SWAPPED
```

## 4. 三队列模型：调度器的状态机

vLLM 调度器维护三个队列（参考 `vllm.core.scheduler.Scheduler`）：

| 队列 | 含义 | 谁在里面 |
|---|---|---|
| **waiting** | 还没拿 KV block、等首次 prefill 的新请求 | 刚 add_request / 重计算抢占后重排 |
| **running** | 已分配 KV block、正参与每 step 前向 | 正常生成中的请求 |
| **swapped** | 曾 running，因显存不足被抢占、KV 换到 CPU | 被 swap 抢占的请求 |

### 每个 step 调度器的决策（`_schedule`）

```
   swapped ──┤ 显存够了？→ swap_in 换回 GPU → 进 running
   waiting ──┤ 还有 block？→ 分配 KV → prefill → 进 running
   running ──┤ 每个都要 +1 token：够分新 block 吗？
             │   不够 → 触发抢占（swap_out 或 recompute）
```

优先级常见考量：**先来先服务（按到达/等待时间）**，并受 `max_num_seqs`（同时 running 上限）、`max_num_batched_tokens`（一个 batch 的 token 上限）约束。优先恢复 swapped、再纳新 waiting，避免老请求饿死。vLLM 还允许 prefill 与 decode 在同 batch 混合（chunked prefill 等），不必严格"先做完所有 prefill 才 decode"。具体策略以版本为准。

## 5. KV block 分配：PagedAttention 的分页本质

KV Cache = 每个 token 在每层都要存的 K、V 张量。PagedAttention 把它切成**固定大小 block**（一个 block 存 `block_size` 个 token 的 KV，常见 16）。

```
逻辑视图（序列看到的连续 token）        物理视图（GPU 显存 block 池）
seq: t0..t15 t16..t31                ┌Block#7┐┌Block#2┐┌Block#5┐
     └block0┘└block1┘                │t0..t15││t16..t31││空闲   │
                                     └───────┘└────────┘└──────┘
block_table（页表）: [7, 2, ...] ← 逻辑block → 物理block 映射
```

- block 物理上**不连续**，靠 `block_table` 串起来 → 像 OS 页表。
- 写满当前 block 才申请下一个 → **按需分配，零预留浪费**。

### 显存预算算账（数值例子）

设层数 $L=32$，KV 头数 $H_{kv}=8$，head_dim $d=128$，FP16（2B），block_size=16。单 token 全层 KV 字节：

$$\text{bytes/token} = 2_{(K,V)} \times L \times H_{kv} \times d \times 2_{\text{FP16}} = 2\times32\times8\times128\times2 = 1\text{ MB}$$

一个 block（16 token）= 16 MB。若可用 KV 显存 40 GB：

$$\#\text{blocks} = \frac{40\times1024\text{ MB}}{16\text{ MB}} = 2560 \Rightarrow 2560\times16 = 40960 \text{ token 容量}$$

这 40960 token 容量在所有并发请求间**动态共享**——谁用谁拿，结束就还，这正是高并发的来源。

**Prefix 共享与 Copy-on-Write**：多序列共享相同 prompt 前缀时共用同批物理 block（引用计数+1）；某序列要在共享 block 上写分叉新 token 时触发 **Copy-on-Write**（复制再写），避免污染他序列。对 `n>1`、beam、系统 prompt 复用极有用。

## 6. prefill 阶段：吞掉整段 prompt

```
prompt: [t0 t1 ... t_{m-1}] 共 m 个
   │ 一次前向（一个 step 内）
   │ 并行算 m 个位置的 attention，K/V 全部写入刚分配的 block
   ▼ 只取最后位置 t_{m-1} 的 logits → 采样出第 1 个新 token
```

- **prefill 是计算密集（compute-bound）**：m 个 token 一次过模型，矩阵"胖"，算力吃满。
- 产物：① 整段 prompt 的 KV 落入 block；② 第一个输出 token —— 用户感知的 **TTFT（首 token 时延）** 主要来自这里。
- 长 prompt 的 prefill 很重，**chunked prefill** 把它切成若干小块跨多 step 完成，避免超长 prefill 卡死所有 decode。

## 7. decode 循环：一次迭代只产一个 token

这是 `LLMEngine.step()` 的核心（参考 `vllm.engine.llm_engine.LLMEngine.step`）。

```
┌────────────── 一次 step（one decoding iteration）──────────────┐
│ ① Scheduler.schedule()                                        │
│    选本轮要算的 SG（running + 换入的 swapped + 新 prefill）；    │
│    决定 swap_in / swap_out / copy 哪些 block                    │
│ ② Worker 执行模型前向                                          │
│    每个 running 序列只送"上一个 token"进去（decode 是 1 token 前向）│
│    读历史所有 block 的 KV（PagedAttention 按 block_table 取）→ logits│
│ ③ Sampler 采样：logits → 下一个 token id（见第8节）             │
│ ④ 处理输出：新 token 追加到序列；写新 KV 到 block；              │
│    detokenize 增量文本；命中 EOS/到 max_tokens → FINISHED 并释放 block│
│ ⑤ 返回本轮所有序列的新增 token（供流式发送）                     │
└────────────────────────────────────────────────────────────────┘
   循环 ①~⑤ 直到该序列结束
```

### prefill vs decode 对比

| 维度 | prefill | decode |
|---|---|---|
| 一次处理 token 数 | 整段 prompt（m 个） | 1 个 |
| 瓶颈 | 算力（compute-bound） | 访存（memory-bound） |
| 决定指标 | TTFT（首 token 时延） | TPOT/ITL（token 间时延） |
| 矩阵形状 | 胖（并行度高） | 瘦 |

decode 瓶颈是反复读庞大 KV/权重，所以**把更多序列拼进同一 batch**（continuous batching）摊薄权重读取开销，是吞吐的关键。

---

## 8. 采样：logits → 下一个 token

采样在每 step 前向之后，把 logits 变成具体 token id（详见 [[llm-inference/解码策略]]）。

```
logits ──▶ ① 温度缩放 z_i/T（T<1更确定，T→0退化为greedy）
        ─▶ ② top-k：留分数最高 k 个
        ─▶ ③ top-p 核采样：高到低累计概率到 p 截断
        ─▶ ④ 惩罚：repetition/presence/frequency 抑制重复
        ─▶ ⑤ softmax → 概率分布 → 抽样（或 greedy 取 argmax）
        ─▶ 下一个 token id
```

温度+softmax 下 token $i$ 的概率 $p_i = \dfrac{\exp(z_i/T)}{\sum_j \exp(z_j/T)}$。

| 参数 | 含义 | 权衡 |
|---|---|---|
| `temperature` | 分布锐度 | 低=稳定/重复，高=多样/易跑偏 |
| `top_p` | 核采样累计概率阈值 | 控候选集，常 0.9~1.0 |
| `top_k` | 候选 token 上限 | 限长尾噪声 |
| `n` | 一个 prompt 生成几个候选 | 越大越费显存/算力 |
| `max_tokens` | 最大生成长度 | 防失控/控成本 |
| `stop` | 停止字符串 | 命中即结束该序列 |

## 9. detokenize 与流式返回

**增量 detokenize 的坑**：token ≠ 完整字符——汉字/emoji 可能跨多个 token，UTF-8 字节可能切在 token 边界，**不能简单对每个新 token 单独 decode**。

```
增量 detokenize：维护已生成 token 与已输出文本
  每来新 token → 解码"含上下文的一小段" → 与上次输出 diff → 只发新增安全字符
  未凑齐完整字符的字节 → 暂存，等下一个 token 再一起解码
```

```
Engine.step() 产新 token → 增量 detokenize 得 Δtext
   → API Server 以 SSE 逐块发送：
     data: {"choices":[{"delta":{"content":"你"}}]}
     data: {"choices":[{"delta":{"content":"好"}}]}
     data: [DONE]   ← 序列 FINISHED 后发结束标记
   → 用户终端逐字看到输出（打字机效果）
```

非流式则把所有片段拼好，等序列 FINISHED 一次性返回完整回复。

## 10. 调度与抢占：显存不够怎么办

当 running 里某序列要 +1 token 却**没有空闲 block**，调度器须抢占其他序列腾显存。两种模式：

```
① Swapping（换出/换入）：被抢占序列 KV block → 拷到 CPU 内存（GPU block 释放）
   恢复时 swap_in 拷回 GPU。省：不重算；费：PCIe 拷贝。状态 RUNNING→SWAPPED→RUNNING
② Recomputation（重计算）：直接丢弃 KV block；恢复时把"prompt+已生成token"当新 prompt
   重新 prefill。省：不占 CPU 内存/无拷贝；费：重算算力。状态 RUNNING→丢KV→WAITING
```

| 模式 | 代价 | 适合 |
|---|---|---|
| **Swap** | CPU 内存 + PCIe 拷贝带宽 | 已生成很长（重算贵）、CPU 内存充足 |
| **Recompute** | 重新 prefill 的算力 | 已生成较短（重算便宜）、省 CPU 内存与拷贝 |

抢占连锁：block 池空 → 选牺牲者（常按调度策略，如最晚到达者优先被抢）→ swap 换到 CPU 进 swapped / recompute 丢 KV 回 waiting → 腾出 block 给当前序列 → 未来显存富余时再换回/重 prefill。**抢占多 = 显存吃紧信号**，可下调 `max_num_seqs`、缩 `max_model_len`、提 `gpu_memory_utilization`、开 prefix 复用缓解。

## 配置项含义 + 与同类对比

**一个请求的完整路径**：进来 → 切词(tokenize) → 入 waiting → 抢到 block → prefill 吐首 token → [decode 循环：每 step +1 token → 采样 → detokenize → 流式发] → EOS/到长度 → 放 block → DONE。

| 配置项 | 含义 | 调大的影响 |
|---|---|---|
| `gpu_memory_utilization` | 允许占用 GPU 显存比例 | KV 容量/并发↑；过高易 OOM |
| `max_num_seqs` | 同时 running 序列上限 | 并发↑吞吐↑；显存压力↑抢占↑ |
| `max_num_batched_tokens` | 一个 batch token 总数上限 | 单 step 更满；首 token 时延可能↑ |
| `max_model_len` | 单序列最大上下文长度 | 支持更长输入；每序列 KV 预算↑ |
| `block_size` | 一个 KV block 容纳 token 数 | 影响碎片粒度与页表开销 |
| `swap_space` | CPU 上 swap 内存大小 | swap 抢占能力↑ |
| `enable_prefix_caching` | 复用相同前缀 KV | 系统prompt/多候选显存↓、TTFT↓ |
| `tensor_parallel_size` | 张量并行卡数 | 跨多卡放更大模型 |

> 默认值与精确写法**以官方文档为准**，此处只讲含义与权衡。

| 引擎 | 调度粒度 | KV 管理 | 特点 |
|---|---|---|---|
| **vLLM** | 迭代级连续批处理 | PagedAttention 分页 | 高吞吐、显存利用高、生态广 |
| **TensorRT-LLM** | in-flight batching | 自家 KV 管理 | NVIDIA 深度优化、编译态 |
| **HF TGI** | 连续批处理 | 借鉴分页思想 | 与 HF 生态整合 |
| **朴素 HF generate** | 静态批/单请求 | 连续预留 | 易用、吞吐低 |

## 常见问题

| 问题 | 答案 |
|---|---|
| prefill 和 decode 本质区别？ | prefill 一次算整段 prompt（算力密集，定 TTFT）；decode 每 step 只算 1 token（访存密集，定 TPOT）。 |
| decode 慢却靠"批"提速？ | decode 瓶颈是反复读 KV/权重，多序列拼一 batch 摊薄权重读取，吞吐显著上升。 |
| 三队列各是什么？ | 等首次 prefill 的新请求 / 正在生成的请求 / 被抢占且 KV 换到 CPU 的请求。 |
| swap 和 recompute 怎么选？ | 已生成很长选 swap（重算贵）；已生成短选 recompute（省 CPU 与拷贝）。 |
| 为何不能逐 token 直接 detokenize？ | 字符可能跨多 token、UTF-8 字节会被切断，需增量解码+暂存未完成字节。 |
| block_size 设多大？ | 太小页表开销大，太大碎片回升；常见 16，权衡填充率与管理开销。 |
| 抢占频繁说明什么？ | 显存吃紧。降 `max_num_seqs`、缩 `max_model_len`、提 `gpu_memory_utilization`、开 prefix caching。 |
| n>1/beam 为何省显存？ | 共享 prompt 物理 block（引用计数），分叉时才 Copy-on-Write 复制。 |
| 首 token 慢、后续快？ | 首 token 含整段 prompt 的 prefill（TTFT），之后每 token 只是轻量 decode（TPOT）。 |
