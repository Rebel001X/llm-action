## 0. 一句话锚点

> **vLLM 把操作系统"虚拟内存 + 分页"的思想搬到了 GPU 上的 KV-Cache 管理。**
> 朴素推理给每条请求预留一整块"最大长度"的连续显存 → 大量浪费；
> vLLM 把 KV-Cache 切成固定大小的**块（block / page）**，按需分配、可共享、可换出 → 同样的显存能塞下 **数倍**的并发请求，吞吐随之翻倍。

记住两个支柱即可：

```
            ┌─────────────────────────────┐
   vLLM  =  │  PagedAttention  (省显存)    │
            │        +                    │
            │  Continuous Batching (提吞吐)│
            └─────────────────────────────┘
```

## 1. 地基：它到底解决什么问题

### 1.1 LLM 推理的两个阶段

一次生成分两段，二者计算特征完全不同：

```
 Prefill (预填充)              Decode (解码)
 ───────────                  ──────────
 一次性吃完整个 prompt          一次只产 1 个 token
 计算密集 (GEMM 大矩阵)         访存密集 (读巨大 KV-Cache)
 GPU 算力打满                   GPU 算力闲、带宽是瓶颈
 例: 处理 512 个输入 token       例: 循环 200 次, 每次 1 token
```

- **Prefill**：把 prompt 的所有 token 一次喂进去，并行算出每个位置的 KV，写进缓存。瓶颈是**算力**（FLOPs）。
- **Decode**：自回归，每步只新增 1 个 token，但要读取**前面所有 token 的 KV**。瓶颈是**显存带宽**（要把 KV 从显存搬进计算单元）。

> 关键洞察：**Decode 阶段 GPU 算力大量闲置**。所以提升吞吐的核心手段是——**把更多请求塞进同一批**，用并发把闲置算力填满。而"能塞多少"取决于显存里能放多少 KV-Cache。于是问题归结为：**如何高效管理 KV-Cache 显存**。

### 1.2 朴素方案的三大浪费

HuggingFace `transformers` 的朴素 `generate` 给每条请求预分配一块 `max_seq_len` 的连续 KV 显存。问题：

```
请求实际只用 100 token, 却按 max_len=2048 预留:
┌──────┬───────────────────────────────────┐
│ 用了  │            预留但没用 (内部碎片)      │
│ 100  │              1948                  │
└──────┴───────────────────────────────────┘
         ▲ 浪费 ~95%
```

| 浪费类型 | 成因 | vLLM 怎么解 |
|---------|------|------------|
| **内部碎片** | 按最大长度预留，实际短 | 按需分配，用多少给多少 |
| **外部碎片** | 连续块要求，块间空隙塞不下新请求 | 分页 → 非连续也能用 |
| **预留浪费** | 给"未来可能生成的 token"先占着 | 边生成边追加页 |

论文实测：朴素方案 KV 显存有效利用率常 **<40%**，PagedAttention 可达 **>90%**。利用率翻倍 ≈ 并发翻倍 ≈ 吞吐翻倍。

## 2. 先讲清 KV-Cache：为什么必须缓存

Transformer 注意力：每个新 token 的输出要和**前面所有 token** 做注意力：

$$\text{Attn}(q_t,K_{1:t},V_{1:t})=\text{softmax}\!\left(\frac{q_t K_{1:t}^\top}{\sqrt{d}}\right)V_{1:t}$$

- $q_t$：当前第 $t$ 个 token 的 query（仅当前 token，1 行）。
- $K_{1:t},V_{1:t}$：**前面所有 token** 的 key/value。

如果不缓存，生成第 $t$ 个 token 时要重算前 $t-1$ 个的 K、V → 总计算量 $O(n^2)$ 且大量重复。**缓存 K、V** 后，每步只算当前 token 的 KV 并追加：

```
 step t-1:  KV-Cache = [k1 v1][k2 v2]...[k_{t-1} v_{t-1}]
 step t  :  只算 k_t,v_t → 追加 → [.....][k_t v_t]
            attention 直接读整段 cache
```

**单 token KV 大小**（一条序列、一个 token 占的显存）：

$$\text{bytes} = 2 \times L \times H \times d_{head} \times \text{dtype}$$

- 因子 2：K 和 V 各一份。
- $L$：层数；$H$：KV 头数（GQA 下比 Q 头少）；$d_{head}$：每头维度；dtype：fp16=2 字节。

> 这块缓存随序列变长**线性膨胀**，是长上下文推理的头号显存吃货。vLLM 的全部内存魔法都围绕它。

## 3. PagedAttention：把 KV-Cache 分页

### 3.1 核心类比——操作系统虚拟内存

```
   操作系统                       vLLM
   ─────────                     ─────
   进程虚拟地址      ←对应→        逻辑 token 序列
   物理内存页帧      ←对应→        GPU 上的 KV block
   页表             ←对应→        Block Table (每序列一张)
   按需分页/换出      ←对应→        按需分配 block / 换出到 CPU
```

把每条序列的 KV-Cache 切成固定大小的 **block**（典型一块装 16 个 token 的 KV）。block 在显存里**物理上不必连续**，靠一张 **Block Table** 把"逻辑位置"映射到"物理块号"。

### 3.2 图解：逻辑连续，物理分散

```
逻辑视图 (序列看到的连续 token):
 [t0 t1 ... t15][t16 ... t31][t32 t33 ...]
   block0          block1        block2(半满)

Block Table (序列A的页表):
   逻辑块0 → 物理块 #7
   逻辑块1 → 物理块 #2
   逻辑块2 → 物理块 #9

物理显存 (KV block 池, 乱序填充):
 #0 #1 [#2=A1] #3 #4 #5 #6 [#7=A0] #8 [#9=A2] ...
        ▲ A的KV散落各处, 但逻辑上连续
```

- **消除外部碎片**：任何空闲块都能用，不要求连续。
- **几乎消除内部碎片**：只有每条序列的**最后一块**可能半满，浪费 < 1 个 block（最多 15 个 token），与 max_len 无关。
- **按需增长**：生成到第 17 个 token 时才申请 block1，绝不为"可能的未来"预留。

### 3.3 改写后的注意力 kernel

普通 attention 假设 KV 连续；PagedAttention 的自定义 CUDA kernel 先查 Block Table，**逐块**把分散的 KV 取来参与计算：

```
for each block in block_table[seq]:
    取该物理块的 K,V  →  算 q·Kᵀ, 累加 softmax  →  乘 V 累加
```

代价：kernel 复杂一点、有一层间接寻址；收益：显存利用率从 ~40% 提到 ~90%+。这是典型的**用一点算力换大量显存**，而 decode 阶段算力本就闲着，稳赚。

## 4. 连续批处理（Continuous Batching）

### 4.1 静态批 vs 连续批

朴素**静态批**：凑一批一起进，必须等**最长的那条**生成完，整批才能返回、才能放新请求。短请求被长请求"绑架"：

```
静态批 (× 浪费):
 req1 ████░░░░░░░░  (早就生成完, 却干等)
 req2 ██████████░░
 req3 ████████████  ← 最长, 全批被它拖住
      └ req1,req2 的 GPU 时间全在空转 ┘
```

**连续批处理**（也叫 in-flight / rolling batching）：以 **iteration（一步 = 一个 token）** 为粒度调度。哪条请求生成完了就**立刻退出**、腾出的槽位**立刻**让新请求进来：

```
连续批 (✓ 紧凑):
 t→  1  2  3  4  5  6  7
 req1 █  █  █  ✓  →req4 进场
 req2 █  █  █  █  █  ✓
 req3 █  █  █  █  █  █  █
 req4          █  █  █  █  ← 复用 req1 退出后的槽
      批永远填满, GPU 不空转
```

> 之所以能做到，正是因为 PagedAttention 让每条序列的 KV 独立分页——加入/退出一条序列只是改 Block Table，不需要重排整块连续显存。**分页是连续批处理的地基。**

### 4.2 Chunked Prefill（分块预填充）

新请求的 prefill 是个大计算块，会卡住正在 decode 的请求（"卡顿"）。vLLM 可把长 prefill **切成小块**，和 decode 步混在同一批里跑，平滑延迟、稳住吞吐：

```
without: [====长prefill====] 期间 decode 全停
with   : [pf][dec][pf][dec][pf][dec]  交错, 不卡
```

## 5. 前缀缓存（Prefix Caching / 自动前缀缓存）

很多请求**共享同一段前缀**：相同 system prompt、few-shot 示例、RAG 拼接的同一文档、多轮对话历史。这段前缀的 KV **算一次就能反复用**。

分页让共享变得自然——**相同前缀的 token 映射到同一批物理块**（写时复制，copy-on-write）：

```
请求A: [系统提示 64 token][用户问1]
请求B: [系统提示 64 token][用户问2]
            │                  │
            └──共享同一组物理块──┘   (前缀只 prefill 一次)
                                  各自从分叉点起新建块
```

- 命中前缀缓存时，这部分 **prefill 计算直接跳过**，首 token 延迟（TTFT）大幅下降。
- 实现上对前缀做哈希索引；命中即复用物理块并递增引用计数，写时再分裂（copy-on-write）。
- 典型收益：聊天/Agent 等长 system prompt 场景，TTFT 可降数倍。

> 这是 PagedAttention "块可共享" 特性的直接红利，本质和 [[llm-inference/sglang/README]] 的 RadixAttention 同源，后者用基数树把共享做得更彻底。

## 6. 调度器（Scheduler）

调度器是大脑：每一步决定**哪些序列上 GPU、谁等、谁被抢占换出**。它管理三个状态队列：

```
        ┌─────────┐ 显存够 ┌─────────┐ 一步步 ┌──────────┐
新请求→ │ WAITING │ ────→  │ RUNNING │ ────→  │ FINISHED │
        └─────────┘        └────┬────┘        └──────────┘
             ▲                  │ 显存不够(抢占)
             │  抢回/换回         ▼
        ┌─────────┐ swap/recompute
        │ SWAPPED │ (KV 存到 CPU 或丢弃)
        └─────────┘
```

每个 iteration 的决策逻辑（机制层面，具体策略以官方文档为准）：

1. **能否容纳**：检查空闲 block 数，决定 RUNNING 集合能放多少序列。
2. **准入新请求**：从 WAITING 取请求，按 block 预算放进 RUNNING（FCFS 为主）。
3. **抢占（preemption）**：显存吃紧时挑选低优先级/晚到的序列踢出。两种回收方式：
   - **Swap（换出）**：把它的 KV block 拷到 CPU 内存，腾出 GPU；恢复时换回。
   - **Recompute（重算）**：直接丢弃 KV，恢复时重新 prefill。短序列重算更划算，省了拷贝带宽。
4. **混合 prefill/decode**：配合 chunked prefill，把新请求的 prefill 块与在跑的 decode 步组装成一个均衡批次。

> 调度的目标函数：在**不 OOM** 的前提下，让每一步的批尽量满（高吞吐），同时尽量不饿死请求（控延迟）。这是吞吐 vs 延迟的核心权衡旋钮。

## 7. 张量并行与分布式推理

模型一张卡放不下，或要更低延迟时，按维度切分：

### 7.1 三种并行（先分清）

| 并行 | 切什么 | 通信 | 何时用 |
|------|--------|------|--------|
| **张量并行 TP** | 每层权重按行/列切到多卡 | 每层多次 AllReduce（重） | 单层放不下 / 降延迟，**卡间高速互联（NVLink）** |
| **流水线并行 PP** | 按**层**切成多段，串成流水线 | 段间传激活（轻） | 跨节点、互联带宽低时 |
| **数据并行 DP** | 复制整模型，分摊请求 | 几乎无（各自独立） | 单卡放得下、要扩并发/吞吐 |

### 7.2 张量并行图解（以 MLP 为例）

把一层的权重矩阵按列切成 $N$ 份，各卡算一部分，最后 **AllReduce** 汇总：

```
            输入 x (每卡都有完整 x)
   ┌──────────┼──────────┐
 GPU0       GPU1       GPU2     GPU3
 W列块0     W列块1     W列块2    W列块3   ← 权重各持 1/4
   │          │          │        │
 部分积0    部分积1    部分积2   部分积3
   └──────────┴── AllReduce ──┴────────┘
                  ↓
            完整输出 y (每卡一致)
```

- TP=4 → 每卡只存 1/4 权重和 1/4 的 KV-Cache，显存压力降到 1/4。
- 代价：**每层前向都要 AllReduce**，通信频繁。所以 TP 强烈依赖 **NVLink/NVSwitch** 这类高带宽卡间互联；跨节点走 PP 更合适。

启动通常只需指定并行度（如 `tensor_parallel_size=4`、`pipeline_parallel_size=2`），具体参数名与组合**以官方文档为准**。TP×PP×DP 可叠加：单机内用 TP，跨机用 PP，再用 DP 复制扩吞吐。

参考：
- 数据并行示例：https://github.com/vllm-project/vllm/blob/v0.9.0/examples/offline_inference/data_parallel.py
- DP 相关 PR：https://github.com/vllm-project/vllm/pull/15977
- 分布式部署官方文档：https://docs.vllm.ai/en/latest/serving/distributed_serving.html

## 8. 整体架构图

把前面所有组件串起来——一条请求从进来到吐 token 的全旅程：

```
┌───────────────────────────────────────────────────────────────┐
│                        vLLM 服务进程                            │
│                                                                 │
│  HTTP/OpenAI 兼容 API ──→ ┌──────────────┐                      │
│  (/v1/chat/completions)   │  Tokenizer   │ 文本→token id        │
│                           └──────┬───────┘                      │
│                                  ▼                              │
│                          ┌──────────────┐  WAITING/RUNNING/SWAP │
│                          │  Scheduler   │  每步挑选序列组批      │
│                          └──────┬───────┘                      │
│              查/改页表 ┌─────────┼──────────┐ 申请/释放 block    │
│                       ▼         ▼          ▼                   │
│              ┌──────────────┐  ┌───────────────────────────┐   │
│              │ Block Table  │  │  KV-Cache Block Pool (GPU) │   │
│              │ (每序列页表)  │  │  [blk0][blk1][blk2]...     │   │
│              └──────────────┘  └───────────────────────────┘   │
│                       │ 前缀命中→共享块  ▲ 换出↕换入(CPU mem)    │
│                       ▼                                         │
│   ┌──────────────────────────────────────────────────────┐    │
│   │  Model Executor (1..N GPU, TP/PP 切分)                 │    │
│   │   ┌────────────────────────────────────────────┐      │    │
│   │   │ PagedAttention CUDA kernel (按块取 KV)       │      │    │
│   │   └────────────────────────────────────────────┘      │    │
│   └──────────────────────────┬───────────────────────────┘    │
│                              ▼  每步产 1 token / 序列            │
│                        ┌──────────┐  采样(温度/top-p)            │
│                        │ Sampler  │ ──→ 流式返回 token           │
│                        └──────────┘                            │
└───────────────────────────────────────────────────────────────┘

闭环: Sampler 产出 token → 追加进对应序列的 KV block
      → Scheduler 下一步重新组批 → 循环, 直到 EOS/达到 max_len
```

## 9. 数值例子（手算显存与吞吐）

### 9.1 单 token KV 显存

设一个 7B 级模型：层数 $L=32$，KV 头 $H=8$（GQA），$d_{head}=128$，fp16（2 字节）。

$$\text{每 token KV} = 2 \times 32 \times 8 \times 128 \times 2 \text{ B} = 131{,}072 \text{ B} \approx 128 \text{ KB}$$

一条 2048 token 的序列：

$$128\text{ KB} \times 2048 \approx 256 \text{ MB}$$

### 9.2 能并发多少条？

设一张卡（如 24 GB 显存）扣掉权重和激活后，剩 **14 GB 给 KV-Cache**。

```
14 GB / 256 MB ≈ 56 条满长(2048) 序列同时在跑
```

但真实请求往往没用满 2048。若平均只用 400 token：

```
每条 ≈ 128KB × 400 ≈ 50 MB
14 GB / 50 MB ≈ 280 条并发  ← 按需分页才吃得到这个红利
```

> **对比朴素方案**：朴素按 max_len=2048 预留，无论实际多短，每条都吃 256 MB → 卡死在 ~56 条。
> **vLLM 按需分页**：按实际 ~400 token 吃 ~50 MB → ~280 条。**并发提升约 5×**，吞吐随之约 5×。这就是 PagedAttention 的钱景。

### 9.3 block 数与碎片

block_size=16，14 GB / (128KB×16) ≈ **7000 个 block** 可分配。每条序列只在**最后一块**有不满浪费，最坏 15 token ≈ 1.9 MB/条，相对 50MB 占用 < 4%——碎片几乎可忽略，且**与 max_len 无关**。

### 9.4 前缀缓存收益

100 条请求共享一段 1000 token 的 system prompt：

```
无前缀缓存: prefill 1000 token × 100 次
有前缀缓存: prefill 1000 token × 1 次 (其余 99 次命中)
            ≈ 节省 99% 的前缀 prefill 计算, TTFT 大幅下降
```

> 以上为机制示意数字，便于建立量级感；真实数值随模型/硬件/请求分布变化，**以实测与官方文档为准**。

## 10. 对照表（与同类对比）

| 维度 | HF `transformers` | TGI | **vLLM** | SGLang |
|------|------------------|-----|----------|--------|
| KV 内存管理 | 连续预留 | 分页(借鉴) | **PagedAttention(原创)** | 分页 + RadixAttention |
| 批处理 | 静态 | 连续 | **连续批 + chunked prefill** | 连续批 |
| 前缀缓存 | 无 | 部分 | **自动前缀缓存** | **RadixAttention(树状共享更强)** |
| 张量并行 | 需手搭 | 支持 | **TP/PP/DP 内建** | 支持 |
| 定位 | 训练/原型 | 生产服务 | **高吞吐通用推理服务** | 复杂结构化/Agent 工作流 |
| 吞吐(相对) | 1× 基准 | 高 | **很高** | 很高 |

> 速记：**通用高吞吐服务选 vLLM；前缀复用极重、结构化生成/多轮 Agent 选 SGLang**（见 [[llm-inference/sglang/README]]）。两者机制同源、互相借鉴，差异主要在前缀共享策略与编程模型。

## 11. 常见问题

| 问题 | 答案 |
|------|------|
| PagedAttention 到底省的是什么？ | 省 **KV-Cache 显存**：消除内部/外部碎片，利用率从 ~40% 提到 ~90%+ |
| 为什么省显存能提吞吐？ | 显存省下来 → 能塞更多并发序列 → 填满 decode 阶段闲置的算力 → 吞吐升 |
| block_size 怎么选？ | 太小则页表/寻址开销大，太大则最后一块浪费多；常用 16，**以官方默认为准** |
| 连续批处理和分页什么关系？ | 分页是地基：序列独立分页，才能随时加入/退出而不重排显存 |
| 抢占后数据丢了吗？ | 不丢：要么 **swap** 到 CPU 内存，要么 **recompute** 重算 prefill |
| 张量并行一定更快吗？ | 不一定：TP 每层都 AllReduce，**没有 NVLink 时通信反成瓶颈**，跨节点优先 PP |
| 前缀缓存什么时候最值？ | 长 system prompt、few-shot、同文档 RAG、多轮对话——共享前缀越长越值 |
| 适合超长上下文吗？ | KV 随长度线性涨，仍是瓶颈；分页+换出能缓解，但需配合长上下文专门优化 |
| 量化能和它叠加吗？ | 可以：权重量化省权重显存、KV 量化(如 FP8)再省 KV，叠加 PagedAttention 进一步提并发 |
