## 0. 一句话锚点

长文本推理不是"模型变大"，而是**序列变长**。三件事同时恶化：

1. **prefill 算力墙**：注意力是 $O(L^2)$，prompt 越长，第一个 token 出来前要算的越多 → 首 token 延迟（TTFT）爆炸。
2. **KV 显存墙**：每个 token 都要把它的 K、V 向量存下来给后续 token 注意，显存随 $L$ **线性**涨，128K 上下文动辄吃掉几十 GB。
3. **调度墙**：一个 256K 的长请求做 prefill 时会"霸占"整个 GPU，让正在 decode 的短请求停顿，TPOT（每 token 时间）抖动。

vLLM 的三把刀分别对应：**chunked prefill** 砍延迟墙、**PagedAttention 分页** 砍显存墙、**带预算的调度器** 砍调度墙。

## 1. 地基：长文本推理的问题画像

### 1.1 推理分两个阶段

```
请求生命周期：
                                                    ┌──────────────────────┐
  prompt (L 个 token)                               │  每步只算 1 个新 token │
        │                                           │  但要 attend 前面所有  │
        ▼                                           ▼
   ┌─────────────┐   一次性算完所有 prompt   ┌──────────────────────────────┐
   │  PREFILL     │  ───────────────────▶   │  DECODE (自回归，一次一 token) │
   │ 计算密集      │   产出第 1 个 token       │  访存密集 (memory-bound)       │
   │ O(L^2) 注意力 │   + 填满 KV-Cache        │  每步 O(L) 注意力              │
   └─────────────┘                          └──────────────────────────────┘
        ↑                                            ↑
     TTFT 主要来源                              TPOT / 吞吐主要来源
```

- **Prefill**：把整段 prompt 喂进去，并行算出每个位置的 K/V，写入 KV-Cache，吐出第一个 token。算力（GEMM）密集。
- **Decode**：之后每生成一个 token，都要拿当前 query 去和**缓存里全部 K/V**做注意力。算得少、读得多，属访存密集。

长文本让两边都变坏：prefill 的 $L^2$ 让 TTFT 暴涨；decode 的 KV 越来越大，单步要读的显存越来越多。

### 1.2 为什么"长"这么贵——两条曲线

```
开销
  ▲
  │                          ╱  prefill 注意力 ~ O(L^2)
  │                        ╱
  │                      ╱
  │                    ╱
  │                  ╱            ____________  KV 显存 ~ O(L)  (线性)
  │                ╱        ______/
  │            __╱_________/
  └──────────────────────────────────────────▶  序列长度 L
   4K      32K       128K        256K     1M
```

记住两句话：**算力是平方的（prefill 痛），显存是线性的（decode 痛）**。长文本工程几乎全在这两条曲线上做文章。

## 2. KV-Cache 显存账：一个 token 到底占多少

这是长文本第一性原理，必须会手算。单 token 的 KV-Cache 字节数：

$$\text{bytes/token} = 2 \times L_{\text{layer}} \times H_{kv} \times d_{head} \times \text{dtype\_bytes}$$

- 系数 `2`：K 和 V 各一份。
- $L_{\text{layer}}$：层数；$H_{kv}$：KV 头数（GQA/MQA 下远小于 query 头数）；$d_{head}$：每头维度；dtype_bytes：fp16=2、fp8=1。

### 数值例子（GQA 模型，类 Qwen2.5-7B 规模，仅示意）

设 $L_{\text{layer}}=28$，$H_{kv}=4$，$d_{head}=128$，fp16：

$$\text{bytes/token} = 2 \times 28 \times 4 \times 128 \times 2 = 57{,}344 \approx 56\,\text{KB}$$

那么不同上下文长度的 **单序列** KV 占用：

| 上下文 L | KV 显存（fp16） | fp8（kv-cache-dtype=fp8） |
|---------|----------------|--------------------------|
| 8 K     | ~0.44 GB       | ~0.22 GB |
| 32 K    | ~1.75 GB       | ~0.88 GB |
| 128 K   | ~7.0 GB        | ~3.5 GB |
| 256 K   | ~14 GB         | ~7 GB |
| 1 M     | ~56 GB         | ~28 GB |

> 结论：一个 1M 上下文的请求，光 KV 就要 56GB（fp16）——这就是为什么 GLM-4-9B-Chat-1M 官方示例要 `tp_size=4`：把 KV 摊到 4 张卡上。GQA 把 $H_{kv}$ 从几十降到几，是长文本能跑的前提；MHA 老模型在长上下文下几乎不可行。

## 3. PagedAttention 与 block 分页

### 3.1 它解决什么

朴素实现给每个序列预留一段**连续**显存，按 `max_model_len` 预留 → 短请求也按最长留，浪费严重；还会产生外部碎片，导致"明明有空间却分不出连续块"。

PagedAttention 借鉴操作系统**虚拟内存分页**：把 KV-Cache 切成固定大小的 **block（物理块）**（每块存 `block_size` 个 token 的 K/V，常见 16），按需分配，逻辑上连续、物理上可不连续。

```
逻辑序列 (一个请求看到的连续 token)：
  tok0 tok1 ... tok15 | tok16 ... tok31 | tok32 ...
   └──逻辑块 0──┘        └──逻辑块 1──┘     └逻辑块2

block_table (每序列一张映射表)：
   逻辑块0 ──▶ 物理块 #7
   逻辑块1 ──▶ 物理块 #2
   逻辑块2 ──▶ 物理块 #9   ← 物理上散落，注意力 kernel 按表索引读取

GPU 物理 KV 池 (一块大显存切成等长 block)：
  ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
  │ #0 │ #1 │ #2 │ #3 │ ...│    │ #7 │    │ #9 │    │
  └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
```

### 3.2 关键收益（长文本尤甚）

- **近零碎片**：只在最后一个 block 内有少量浪费（< 1 个 block），不再为 max_len 预留。
- **按需增长**：序列每写满 16 个 token 才申请一个新 block，128K 上下文也是逐块长出来的。
- **前缀共享 / Copy-on-Write**：相同前缀（system prompt、few-shot）可让多个序列指向**同一物理块**，长公共前缀的批处理显存大幅下降。
- **抢占友好**：以 block 为粒度，可整段换出（swap）或丢弃后重算（recompute），见第 5 节。

> 关键参数 `gpu_memory_utilization`（默认约 0.9）决定多少显存划给 KV 物理池：vLLM 启动时先量出模型权重+激活占用，把剩余 × 该比例切成 block。这个池子能装的 token 总数（≈ block 数 × block_size）就是你**并发长度的总预算**。

## 4. chunked prefill：把长 prompt 切片喂

### 4.1 没有它会怎样

prefill 一个 256K prompt 是一次巨大的 GEMM，会**独占** GPU 很久。这期间所有正在 decode 的请求停摆 → 它们的 TPOT 出现巨大尖刺；同时这一大块还可能直接撑爆单步显存。

### 4.2 chunked prefill 的做法

把长 prompt 的 prefill **拆成多个 chunk**，每个 chunk 不超过 `max_num_batched_tokens` 个 token；并允许把 **decode 步骤和 prefill chunk 混在同一个 batch** 里跑（这正是 SplitFuse / Dynamic SplitFuse 的思想，见 [[llm-optimizer/SplitFuse]]）。

```
关闭 chunked prefill：
  step1: [───────── 256K prefill 一口气 ─────────]   ← 别的请求全停
  step2: [decode][decode][decode] ...

开启 chunked prefill (max_num_batched_tokens = 8192)：
  step1: [ prefill chunk0  8192 ][d][d][d]   ← 长请求切片 + 顺手带几个 decode
  step2: [ prefill chunk1  8192 ][d][d][d]
  step3: [ prefill chunk2  8192 ][d][d][d]
   ...                              ▲
                          每步都给 decode 留位置 → TPOT 平稳
```

### 4.3 它换来什么、代价是什么

| 维度 | 不开 chunked prefill | 开 chunked prefill |
|------|--------------------|-------------------|
| 长请求 TTFT | 一步出，但整步很久 | 略增（分多步），但系统不僵 |
| 短请求 TPOT | prefill 期间剧烈抖动 | 平稳，无长尾尖刺 |
| 显存峰值 | 单步可能 OOM | 受 `max_num_batched_tokens` 封顶，可控 |
| GPU 利用 | prefill 算力满、decode 时算力闲 | prefill(算力)与 decode(访存)互补，利用率更高 |

> `max_num_batched_tokens` 是核心旋钮：**调小**→ chunk 更碎，decode 更不被打断、显存更稳，但长 prompt 的 prefill 总步数变多（TTFT 略升）；**调大**→ prefill 更快但又开始挤压 decode。长文本 OOM 时，官方建议正是 `enable_chunked_prefill=True` + 把 `max_num_batched_tokens` 设到 8192 左右（见文末 GLM-4-1M 示例）。

## 5. 调度器：长文本如何不饿死短请求

vLLM 调度器在每个 step 决定"这一拍跑哪些序列、跑多少 token"，受两个预算约束：

- **token 预算**：本 step 总 token ≤ `max_num_batched_tokens`。
- **序列预算**：并发序列数 ≤ `max_num_seqs`。
- **KV block 预算**：所有活跃序列要的 block ≤ 物理池可用 block。

```
调度循环 (每个 step)：
  ┌───────────────────────────────────────────────┐
  │ 1. running 队列里的 decode 请求各要 1 个新 token │
  │ 2. 还有 token/block 预算？ → 从 waiting 队列     │
  │    取新请求做 (chunked) prefill 填满预算         │
  │ 3. 预算/显存不够？ → 触发 PREEMPTION (抢占)      │
  └───────────────────────────────────────────────┘
                          │
                抢占两种回收方式：
        ┌───────────────────────┴────────────────────────┐
        ▼                                                 ▼
   RECOMPUTE（默认）                                    SWAP
   丢掉被抢占序列的 KV block，                      把 KV block 换到 CPU 内存，
   将来重新 prefill 算回来。                        将来再 swap 回 GPU。
   省 CPU 带宽，长 prompt 重算贵。                  省重算，但 PCIe 拷贝慢、占 CPU 内存。
```

### 长文本下的调度要点

- **抢占更常发生**：长请求 KV 大，可用 block 容易告急，短请求 decode 时可能把长请求挤出去（preempt），稍后再恢复。
- **recompute 对长 prompt 是隐性大开销**：256K 的 prompt 被抢占后重算一遍 prefill 非常贵；显存非常紧张时可考虑 swap 策略，用 CPU 内存换避免重算。
- **chunked prefill 让调度更平滑**：因为长 prefill 被切片，调度器每个 step 都能腾出位置给 decode，避免"长请求一来全卡住"。
- **公平性**：`max_num_seqs` 控制并发条数，过大→单条分到的 KV 预算变少、长请求更易被抢占；过小→吞吐上不去。长文本场景通常把 `max_num_seqs` 调小（如 128 甚至更低），保证每条长序列有足够 block。

## 6. 并行策略：长序列的切法

```
张量并行 TP (tensor_parallel_size=N)：
  把每层的注意力头 / FFN 按列-行切到 N 张卡，
  KV-Cache 也按 KV 头切开 → 每卡只存 1/N 的 KV。
  ┌── GPU0 ──┐  ┌── GPU1 ──┐  ┌── GPU2 ──┐  ┌── GPU3 ──┐
  │ heads0-1 │  │ heads2-3 │  │ heads4-5 │  │ heads6-7 │   每步 all-reduce 同步
  │ KV 1/4   │  │ KV 1/4   │  │ KV 1/4   │  │ KV 1/4   │
  └──────────┘  └──────────┘  └──────────┘  └──────────┘

流水并行 PP (pipeline_parallel_size=M)：
  按层切：GPU0 跑 layer0-k，GPU1 跑 layer k-2k... 跨节点扩展更友好。
```

长文本下的策略权衡：

| 策略 | 对长文本的作用 | 代价 |
|------|--------------|------|
| **TP（首选）** | 把巨大的 KV 显存均摊到 N 卡，单卡 KV 降为 1/N，是 1M 上下文能跑的关键 | 每层 all-reduce，卡间带宽要求高（NVLink 最佳） |
| **PP** | 跨多机扩展、突破单机显存；权重按层分摊 | 流水气泡；KV 仍按层落在各自卡，单层 KV 大时帮助有限 |
| **TP × PP 混合** | 超大模型+超长上下文，单机装不下时组合用 | 通信拓扑复杂，调参成本高 |

> 经验法则：长文本优先加 **TP** 来摊 KV 显存（GLM-4-1M 用 `tp_size=4`）；单机卡不够再叠 PP 跨机。`tensor_parallel_size` 通常需整除 KV 头数。注意 TP 不会降低注意力的 $O(L^2)$ 计算量，只摊显存与算力，TTFT 仍随 $L$ 增长。

## 7. 长上下文外推：RoPE 与 YARN

模型预训练的最大位置（如 32K）之外，位置编码会"没见过"，直接外推质量崩。要把 32K 模型用到 128K，需对 **RoPE** 做缩放（rope_scaling）。

```
原始 RoPE 频率 ── 训练只覆盖 0..32K 位置
        │
   位置插值 / YARN  把"位置坐标"压缩，使 128K 落进模型熟悉的频率范围
        ▼
  factor = 目标长度 / 原始长度，例如 128K/32K = 4.0
```

Qwen2.5 的做法（配置示意，见文末）：在 `config.json` 加

```json
"rope_scaling": { "factor": 4.0, "original_max_position_embeddings": 32768, "type": "yarn" }
```

- `factor=4.0`：把 32K 外推到约 128K。
- `type=yarn`：YARN 是一种比朴素位置插值更保质量的方案（对不同频段分段处理）。

> ⚠️ 重要权衡：vLLM 目前对 YARN 多为**静态**实现——缩放因子固定，无论输入实际多长都按 4× 缩放，这会**损害较短文本的质量**。因此官方建议：**只在确实要处理长上下文时**才加 `rope_scaling`，短任务部署不要默认开启。具体支持的 scaling 类型与是否动态，以官方文档/源码为准。

## 8. KV 压缩与 fp8 cache

把 KV-Cache 从 fp16 降到 **fp8**（`--kv-cache-dtype fp8`）：

- **显存直接减半**（见第 2 节表格：1M 上下文 56GB→28GB），等价于能装两倍长度或两倍并发。
- 代价：KV 量化引入数值误差，长上下文累积可能轻微影响精度；attention 的 query/输出仍按高精度算，影响通常可接受。
- 与第 7 节配合：fp8 KV + TP + chunked prefill 是当前跑超长上下文的"标准三件套"。

> 还有更激进的 KV 压缩方向（量化/稀疏/驱逐如 H2O、StreamingLLM 式 sink+window），属算法层优化，详见 [[llm-inference/KV-Cache优化]]。本文聚焦 vLLM 引擎已内建的 fp8 路径。

## 9. 典型配置示例（逐参数讲含义）

### 9.1 GLM-4-9B-Chat / 1M —— 离线 LLM 接口

```python
from transformers import AutoTokenizer
from vllm import LLM, SamplingParams

# GLM-4-9B-Chat-1M ：百万上下文需要更大并行度
# max_model_len, tp_size = 1048576, 4
# GLM-4-9B-Chat ：默认 128K；OOM 时减小 max_model_len 或增大 tp_size
max_model_len, tp_size = 131072, 1

model_name = "THUDM/glm-4-9b-chat"
prompt = [{"role": "user", "content": "你好"}]

tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)
llm = LLM(
    model=model_name,
    tensor_parallel_size=tp_size,    # 把 KV 摊到多卡：1M 上下文用 4
    max_model_len=max_model_len,     # 引擎允许的最长序列；决定 KV 池规划上界
    trust_remote_code=True,
    enforce_eager=True,              # 禁用 CUDA Graph，省构图显存、利于调试；牺牲少量速度
    # GLM-4-9B-Chat-1M 若 OOM，开启以下两项：
    # enable_chunked_prefill=True,   # 长 prompt 切片，降显存峰值 + 平滑 TPOT
    # max_num_batched_tokens=8192    # 每步 token 上限（即 prefill chunk 大小）
)
stop_token_ids = [151329, 151336, 151338]
sampling_params = SamplingParams(temperature=0.95, max_tokens=1024,
                                 stop_token_ids=stop_token_ids)

inputs = tokenizer.apply_chat_template(prompt, tokenize=False, add_generation_prompt=True)
outputs = llm.generate(prompts=inputs, sampling_params=sampling_params)
print(outputs[0].outputs[0].text)
```

### 9.2 OpenAI 兼容服务 —— 长上下文 + chunked prefill + fp8 KV

```bash
python3 -m vllm.entrypoints.openai.api_server \
  --port 9009 \
  --gpu-memory-utilization 0.95 \   # 给 KV 池更大比例显存；越高越能装但越易碰激活峰值 OOM
  --dtype auto \                    # 权重精度，auto 一般落到 bf16/fp16
  --model /workspace/models/your-long-ctx-model \
  --max-num-seqs 128 \              # 最大并发序列；长文本调小以保证每条 KV 预算
  --max-model-len 131072 \          # 服务允许的最长上下文 128K
  --tensor-parallel-size 1 \        # 摊 KV：单卡装不下就加大
  --enforce-eager \                 # 关 CUDA Graph，省显存
  --enable-chunked-prefill \        # 切片 prefill：长 prompt 不再卡死短请求
  --max-num-batched-tokens 10000 \  # 每步 token 预算 / chunk 大小，与上一项配套
  --kv-cache-dtype fp8              # KV 降 fp8，显存减半，可换更长上下文/更高并发
```

### 9.3 参数权衡速查

| 参数 | 调大 | 调小 | 长文本建议 |
|------|------|------|-----------|
| `max_model_len` | 支持更长上下文，KV 池规划上界高 | 省显存 | 设成实际需要的最大值，别盲目拉满 |
| `gpu_memory_utilization` | KV 池更大、能装更多 | 更安全 | 0.9~0.95，过高易激活峰值 OOM |
| `max_num_batched_tokens` | prefill 更快 | decode 更稳、显存更省 | OOM 时降到 ~8192 |
| `max_num_seqs` | 吞吐高 | 每条长序列 KV 更充裕 | 长文本调小（如 ≤128） |
| `tensor_parallel_size` | 单卡 KV/算力降为 1/N | 省卡、省通信 | 长上下文优先加它摊 KV |
| `kv-cache-dtype=fp8` | —— | —— | 显存紧张就开，换长度/并发 |

---

## 常见问题

| 问题 | 原因 | 处理 |
|------|------|------|
| 加载/推理直接 OOM | 1M KV 太大、单卡装不下 | 增大 `tensor_parallel_size`；开 `kv-cache-dtype fp8`；减小 `max_model_len` |
| 长 prompt 期间短请求卡顿、TPOT 尖刺 | prefill 独占 GPU | 开 `enable_chunked_prefill`，配 `max_num_batched_tokens` |
| 开了长上下文后短文本质量变差 | 静态 YARN 缩放因子恒定 | 仅在需要长上下文时加 `rope_scaling`；短任务用不带缩放的部署 |
| 首 token 很慢（TTFT 高） | prefill $O(L^2)$，序列越长越慢 | 这是本质开销；TP 摊算力、chunked 平滑，但无法消除 $L^2$ |
| 并发一上来就被抢占、吞吐抖 | KV block 池不够，频繁 preemption/recompute | 减小 `max_num_seqs`；提高 `gpu_memory_utilization`；fp8 KV 腾空间 |
| 单步显存峰值忽高忽低 | prefill chunk 太大 | 调小 `max_num_batched_tokens` 封顶单步 token |
| 多卡报维度不整除 | TP 需整除 KV 头数 | 选能整除 KV 头数的 `tensor_parallel_size` |

> 凡涉及精确默认值、支持的 scaling 类型、API 签名，请以**官方文档/源码为准**——本文讲机制与思路，版本相关细节会变。
