## 0. 一句话锚点

一次 LLM 请求分两步走:先把 prompt 一次性算完(Prefill,算力密集),再逐 token 往外吐(Decode,带宽密集)。**把这两步放在同一张卡上会互相拖累**——分离式推理就是把它们拆到两组卡,各自用最优的并行度、批大小和硬件,中间把 **KV Cache** 搬过去。

## 1. 地基:从最底层讲起

### 1.1 自回归生成的两个阶段

Transformer 解码器生成文本是**自回归**的:第 $t$ 个 token 依赖前面所有 token。但首次进入模型时,整个 prompt 是已知的,可以并行算;之后每生成一个新 token 才能算下一个。于是天然分两段:

- **Prefill(预填充)**:输入 prompt 共 $S$ 个 token,一次前向把这 $S$ 个位置全部算出来,顺便产出每一层、每个位置的 **Key/Value 向量**(即 KV Cache),并吐出**第一个**输出 token。这一步决定 **TTFT(Time To First Token,首 token 延迟)**。
- **Decode(解码)**:每一步只输入**上一个** token($S{=}1$),复用已缓存的 KV,算出下一个 token。重复直到结束。每步耗时决定 **TPOT(Time Per Output Token,出字间隔)**。

### 1.2 KV Cache 是什么、为什么必须缓存

注意力的核心计算:

$$\text{Attn}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}\right)V$$

新 token 的 $Q$ 要和**所有历史** token 的 $K$、$V$ 做注意力。若不缓存,每生成一个 token 都要把前面所有 token 的 $K,V$ 从头重算一遍——$O(S^2)$ 的浪费。所以把每个 token 每一层的 $K,V$ 存下来,Decode 时只算新 token 的 $Q$,与缓存的 $K,V$ 做注意力,复杂度降到每步 $O(S)$。

**KV Cache 每 token 字节数**(关键公式,后面手算要用):

$$\text{bytes/token}=2\times L\times H_{kv}\times d_{head}\times b$$

其中 2 是 K 和 V 各一份,$L$ 层数,$H_{kv}$ 是 KV 头数(GQA 下远小于 Q 头数),$d_{head}$ 每头维度,$b$ 每元素字节(FP16=2)。

### 1.3 两阶段的算术强度天差地别

**算术强度(Arithmetic Intensity)** = FLOPs ÷ 访存字节。它决定一个 kernel 是**算力受限(compute-bound)**还是**带宽受限(memory-bound)**。

- **Prefill**:一次处理几百上千个 token,矩阵乘是大 $\times$ 大,FLOPs 多、权重读一次被很多 token 复用 → **算力受限**,GPU 利用率高。
- **Decode**:每步只 1 个 token(batch 内也就 batch_size 个),却要把**整个模型权重 + 整份 KV Cache** 从显存读出来 → 算得少、读得多 → **带宽受限**,算力利用率常常个位数百分比。

```
   算术强度 (FLOPs / Byte)
   高 ┤  ██ Prefill  (compute-bound, 打满 Tensor Core)
      │  ██
      │  ██
      │  ░░
   低 ┤  ░░ Decode   (memory-bound, 打满 HBM 带宽)
      └───────────────────────────────►
        把两者塞一张卡 = 一个吃算力一个吃带宽,互相抢、都吃不饱
```

## 2. 两阶段画像:为什么必须分离

把 P 和 D 混在同一引擎、同一批次里,会产生三类干扰:

1. **延迟互相污染**。一个长 prompt 的 Prefill 可能占用 GPU 几十毫秒,期间所有正在 Decode 的请求被**卡住**,TPOT 抖动剧烈(jitter)。
2. **批策略冲突**。Prefill 想要**小批大序列**(已经算力受限,加 batch 没收益还涨延迟);Decode 想要**大批**(才能摊薄权重读取、提升带宽利用)。一套 batch 策略满足不了两者。
3. **并行度冲突**。Prefill 受算力限,适合**张量并行 TP** 把单次大矩阵乘切开提速(详见 [[llm-inference/大模型推理张量并行]]);Decode 受带宽限,**TP 收益递减**,有时更适合**数据并行/小 TP** 以提高每卡批吞吐。

```
混合部署 (Colocated):
  GPU0: [Prefill_A ████][Decode_x][Decode_y][Prefill_B ████████][Decode_x] ...
                ↑ 长 prefill 插队,Decode 卡顿,TPOT 尖刺

分离部署 (Disaggregated):
  Prefill 集群: [Prefill_A][Prefill_B][Prefill_C] ...  ← 专心打满算力
  Decode  集群: [Decode_x][Decode_y][Decode_z] ...     ← 专心打满带宽,平稳出字
        二者用各自最优并行度/批大小,互不打断
```

> 一句话:分离 = **解耦延迟、解耦批策略、解耦并行度**,用 KV 传输换来两阶段各自的"独占资源"。

## 3. PD 分离整体架构

典型分离式系统由四类角色组成:

```
                      ┌─────────────────────────────┐
   请求 ──────────────►│   全局调度器 / 路由器        │
                      │  (Global Scheduler/Router)  │
                      └───────┬─────────────┬───────┘
                调度 Prefill  │             │  调度 Decode
                              ▼             ▼
            ┌──────────────────────┐   ┌──────────────────────┐
            │   Prefill 实例池      │   │   Decode 实例池        │
            │  (P-instances)        │   │  (D-instances)         │
            │  并行度 TP=Pp         │   │  并行度 TP=Pd          │
            │  小批大序列           │   │  大批短步              │
            └──────────┬───────────┘   └──────────▲───────────┘
                       │  ① 算出 KV Cache          │
                       │                           │
                       ▼                           │
            ┌─────────────────────────────────────┴───┐
            │     KV Cache 池 / 传输层                  │
            │  (KVCache Pool + Transfer: NVLink/RDMA)   │
            └──────────────────────────────────────────┘
                 ② 把整段 prompt 的 KV 从 P 搬到 D
                 ③ D 拿到 KV,逐 token 生成,流式返回
```

**端到端一条请求的生命周期**:

1. 路由器收到请求,挑一个 Prefill 实例,把 prompt 发过去。
2. P 实例做一次大前向,产出第一个 token + 全量 KV Cache,写入 KV 池/本地显存。
3. 路由器挑一个 Decode 实例,**把这条请求的 KV 传过去**(§4)。
4. D 实例加载 KV,进入连续批(§7),逐 token 生成,流式返回给用户。
5. 请求结束,释放 D 上的 KV 块。

关键指标解耦后各自优化:**TTFT 由 P 决定,TPOT 由 D 决定**,SLO 可以分别拍。

## 4. KV 缓存池与传输

这是分离架构的**命门**:KV 传输的延迟会直接叠加进 TTFT,传输带宽不够会让整条流水线憋住。

### 4.1 要传多少数据

一条请求要传的 = `每 token 字节数 × prompt 长度`。用 §1.2 的公式,$S$ 越长传输量线性增长。所以**长上下文场景对 KV 传输带宽极其敏感**(参见 §9 手算)。

### 4.2 传输介质与拓扑

```
传输路径从快到慢:
  同节点 GPU↔GPU:  NVLink / NVSwitch   (数百 GB/s ~ TB/s 级)
  跨节点 GPU↔GPU:  RDMA over IB/RoCE   (GPU-Direct, 绕过 CPU/内存)
  退而求其次:      经 CPU 内存中转       (慢, 有拷贝开销, 尽量避免)
```

- **GPUDirect RDMA**:让远端 GPU 直接读写本地 GPU 显存,绕过 CPU、绕过系统内存拷贝,是跨机 KV 传输的主力。
- **分层 KV 池**:HBM(显存,最快最贵)→ DRAM(主机内存)→ SSD/远端存储。把**热**的、即将复用的 KV 放 HBM,**温/冷**的(如可复用的公共前缀)下沉到 DRAM/SSD。Mooncake 的 KVCache Store 即此思路(详见 [[llm-inference/Mooncake]])。

### 4.3 隐藏传输延迟:逐层流水(layer-wise pipelining)

朴素做法是"P 全算完 → 整体传 → D 开始",传输完全暴露。优化:**P 每算完一层就把该层 KV 发出去**,D 这边边收边准备,把传输和计算**重叠**:

```
朴素 (传输暴露):
  P: [算L0 算L1 ... 算L31]──────[传 0..31 全量 KV]────► D 才开始
                                  ↑ 这段纯等待,计入 TTFT

逐层流水 (传输隐藏):
  P: [算L0][算L1][算L2]...[算L31]
        └传L0┘ └传L1┘ └传L2┘ ...  ← 算下一层时传上一层
                                D 收齐即可启动, TTFT 几乎只剩计算时间
```

### 4.4 前缀复用(Prefix Cache)

多请求常共享前缀(同一 system prompt、同一文档)。把公共前缀的 KV 缓存在池里**按内容寻址**(哈希 token 序列),命中就跳过这段 Prefill,直接复用。这把昂贵的 Prefill 摊薄,是分离架构 + 全局 KV 池的一大红利。

## 5. 调度器

调度器要同时管 **请求路由** 和 **资源分配**,目标是在满足 SLO(TTFT、TPOT)前提下最大化吞吐。

### 5.1 路由要回答的三个问题

1. **派给哪个 Prefill 实例?** 看队列长度、看前缀缓存命中(命中则省一大段计算,优先派给持有该前缀的实例 → **缓存亲和性路由**)。
2. **派给哪个 Decode 实例?** 看该实例**当前批里还剩多少 KV 显存额度**、当前 batch 大小、它的 TPOT 是否还在 SLO 内。
3. **何时传 KV?** 协调 P 算完与 D 有空闲 KV 块这两个事件。

### 5.2 P:D 比例是核心旋钮

Prefill 和 Decode 的负载比随**输入/输出长度比**剧烈变化。设一条请求输入 $S$ token、输出 $G$ token:

- Prefill 工作量 $\propto S$(一次性)。
- Decode 工作量 $\propto G$(逐步),且每步要读全量权重 → 实际"卡时间"占比常更高。

```
负载随 (输入长/输出长) 变化:
  长输入短输出 (RAG/摘要):   Prefill 重 → 多配 P 实例
      P:D = 2:1
  短输入长输出 (Agent/推理链): Decode 重 → 多配 D 实例
      P:D = 1:3
  → 调度器需"按当下流量动态调整 P:D 配比",否则一边排队一边空转
```

### 5.3 准入控制与抢占

- **准入控制**:当 D 集群 KV 显存吃紧,新请求先排队,避免 OOM。
- **抢占/换出(swap/recompute)**:显存不够时,把某些 Decode 请求的 KV 暂时**换出到 DRAM**或**丢弃后重算**,给高优先级请求让路。这与 PagedAttention 的块管理天然契合(§7)。

## 6. 弹性扩缩(Elastic Scaling)

分离架构的最大运维红利:**P 池和 D 池可以独立扩缩容**。

```
监控信号 ──► 自动扩缩控制器 ──► 调整实例数
  TTFT p99 ↑  ──►  Prefill 排队 → 加 P 实例
  TPOT p99 ↑  ──►  Decode 批挤爆/KV 满 → 加 D 实例
  GPU 利用率↓ ──►  缩容,省成本
```

要点与权衡:

- **独立伸缩**:白天交互流量(短输入长输出)多扩 D;夜间批处理(长文档)多扩 P。混合部署做不到这种精细。
- **冷启动成本**:新拉起的实例要加载几十 GB 权重,有秒级延迟 → 维持**预热池(warm pool)**。
- **角色转换**:更高级的做法是让同一批 GPU **在 P 与 D 角色间动态切换**(只需切并行配置 + 重载权重路由),应对潮汐流量,避免两边都备冗余。
- **传输带宽随规模变化**:P、D 实例多了,KV 传输变成**多对多**,要避免网络成为新瓶颈,需拓扑感知放置(同机架优先)。

## 7. 与连续批 / PagedAttention 的配合

分离不是替代连续批和 PagedAttention,而是**在其之上**再加一层"阶段维度"的拆分。三者正交、叠乘。

### 7.1 连续批(Continuous Batching)主要在 Decode 侧发力

传统静态批要等一批请求**全部**生成完才能换下一批,短请求被长请求拖着空转。连续批(又称 in-flight batching)做到**token 级别动态进出**:某请求生成完就立刻让出槽位,新请求随时插入。

```
静态批:  [A____][B________][C__]   ← A,C 早完了还占着槽,空转
连续批:  [A__]→换 D进 [D_____]
         [B________]                ← 每步重组 batch,槽位永不空转
         [C__]→换 E进 [E___]
```

在分离架构里,**Decode 实例内部用连续批**把多条请求的逐 token 步骤打包,最大化带宽利用率;**Prefill 实例**也可用 chunked-prefill 把长 prompt 切块、与其他请求拼批(避免单条长 prompt 独占)。

### 7.2 PagedAttention 让 KV 显存像虚拟内存一样分页

KV Cache 长度不可预知,连续分配会产生大量**内部碎片**。PagedAttention 把 KV 切成固定大小的 **block(页)**,用**块表(block table)**把逻辑序列映射到物理块,按需分配、用完归还。

```
逻辑视角 (一条序列的 KV):  [tok0 tok1 tok2 | tok3 tok4 tok5 | tok6 ...]
                              ▼ 块表映射 ▼
物理显存 (非连续的页):     页#7      页#2      页#9   ...
  优点: 几乎零碎片; 前缀共享 = 多序列指向同一物理页(写时复制)
```

**和分离的关键耦合点**:

- KV **传输**以 page 为粒度,正好对齐 RDMA 的批量传输。
- KV **抢占/换出**(§5.3)以 page 为单位换进换出 DRAM,代价可控。
- **前缀复用**(§4.4)= 多请求的块表指向同一组物理页,零拷贝命中。

> 组合拳:**分离**(P/D 拆开)× **连续批**(Decode 内 token 级动态批)× **PagedAttention**(KV 分页 + 共享 + 可换出)= 现代高吞吐推理系统的标配三件套。

## 9. 逐数手算(端到端数字账)

设一个 Llama-2-13B 量级模型(便于整数演算,取近似规格):

- 层数 $L=40$,采用 MHA(非 GQA)时 KV 头数 $H_{kv}=40$,每头维 $d_{head}=128$ → 隐藏维 $H=40\times128=5120$。
- 精度 FP16,$b=2$ 字节。

### 9.1 KV Cache 每 token 字节数

$$\text{bytes/token}=2\times L\times H_{kv}\times d_{head}\times b
=2\times 40\times 40\times 128\times 2$$

逐步:$40\times40=1600$;$1600\times128=204{,}800$;$\times2(\text{KV})=409{,}600$;$\times2(\text{FP16})=819{,}200$ 字节 $\approx \mathbf{0.78\ MiB/token}$。

### 9.2 一条 2048-token prompt 要传多少 KV

$$819{,}200\ \text{B/token}\times2048\ \text{token}=1{,}677{,}721{,}600\ \text{B}\approx \mathbf{1.56\ GiB}$$

### 9.3 这段 KV 在不同链路上的传输时间

传输时间 = 数据量 ÷ 有效带宽。取 $1.56\,\text{GiB}=1.6\times10^9\,\text{B}$ 量级:

| 链路 | 有效带宽 | 传输时间 ≈ |
|---|---|---|
| NVLink(同节点) | 400 GB/s | $1.6/400 \approx \mathbf{4\ ms}$ |
| RDMA 200Gb IB | 25 GB/s | $1.6/25 \approx \mathbf{64\ ms}$ |
| 100Gb RoCE | 12.5 GB/s | $1.6/12.5 \approx \mathbf{128\ ms}$ |

**结论**:若 TTFT 预算是 300 ms,NVLink 传输只吃 4 ms 可忽略;但跨机 100Gb 网就吃掉 128 ms,逼近预算的一半——这正是 §4.3 **逐层流水隐藏传输**和 §4.2 **同机架优先放置**如此重要的原因。

### 9.4 Decode 侧带宽受限的直观验证

设模型权重 13B 参数 × FP16 = 26 GB。Decode **每生成一个 token**(忽略 KV 读取,先看权重)至少要把 26 GB 权重从 HBM 读一遍。某卡 HBM 带宽 2 TB/s:

$$t_{\min}=\frac{26\ \text{GB}}{2000\ \text{GB/s}}=13\ \text{ms/token}\ (\text{batch}=1)$$

batch=1 时算力几乎闲置 → 印证 Decode 是带宽受限,**必须靠大 batch(连续批)摊薄这 26 GB 的读取**,才能把每 token 成本降下来。这就是为什么 Decode 池要专门用大批策略。

### 9.5 P:D 配比的粗略估算

设 Prefill 处理 2048 token 耗时 $\approx$ 80 ms(算力受限,一次),输出 256 token 每步 13 ms → Decode 总 $256\times13\approx 3328$ ms。单实例视角,Decode 的"卡时间"是 Prefill 的约 $3328/80\approx 42$ 倍。当然 Decode 靠大批并发摊薄,但仍说明**短输入长输出场景 D 远比 P 吃资源**,调度器应大幅倾斜 D 实例数。

| 维度 | 混合部署 Colocated | PD 分离 Disaggregated | 备注 |
|---|---|---|---|
| TTFT/TPOT 干扰 | 强(prefill 卡 decode) | 弱(各自独占) | 分离的核心收益 |
| 批策略 | 一套,妥协 | 各自最优 | P 小批、D 大批 |
| 并行度 | 一套 TP | P、D 各自最优 | 见 [[llm-inference/大模型推理张量并行]] |
| 弹性扩缩 | 整体扩 | P、D 独立扩 | 省成本 |
| KV 传输开销 | 无(同卡) | 有(需 NVLink/RDMA) | 分离的主要代价 |
| 适合场景 | 流量小、长度均匀 | 大规模、长度差异大、长上下文 | — |

## 复杂度/数量级速记

| 量 | 量级关系 |
|---|---|
| KV bytes/token | $2 L H_{kv} d_{head} b$,与上下文长度无关(单 token) |
| 一条请求 KV 总量 | $\propto$ prompt 长度 $S$(线性) |
| Prefill FLOPs | $\propto S$(一次),算力受限 |
| Decode 每步访存 | $\propto$(模型大小 + 当前 KV),带宽受限 |
| KV 传输时间 | $S \div$ 链路带宽 |

## 常见问题

| 疑问 | 真相 |
|---|---|
| 分离就是简单地多开两组进程? | 不。命门在 **KV 传输**与**全局调度**,传输打不好,省下的干扰还不够还传输的债。 |
| KV 传输会不会抵消分离的收益? | 同节点 NVLink 几乎免费;跨机靠 GPUDirect RDMA + 逐层流水 + 同机架放置把延迟压到 SLO 内(§9.3)。 |
| 分离能取代连续批/PagedAttention 吗? | 不。三者**正交叠乘**:分离拆阶段、连续批拆 token 级槽位、PagedAttention 管 KV 显存(§7)。 |
| P:D 配几比几? | 没有定值,随**输入/输出长度比**动态调:长输入多配 P,长输出多配 D,调度器实时调(§5.2)。 |
| Decode 为什么算力利用率那么低? | 它带宽受限——每步读全量权重却只算几个 token,只能靠大 batch 摊薄(§9.4)。 |
| 长上下文为何对分离最敏感? | KV 总量与 $S$ 线性增长,传输量、显存、换出代价全部放大(§9.2)。 |
| 一定要用 RDMA 吗? | 同机用 NVLink 即可;跨机才需要 RDMA。经 CPU 中转最慢,尽量避免。 |
