## 0. 一句话锚点

> **生成式 LLM 服务的高效化，本质是一道两层联合优化题：算法层让"每一步算得更少 / 每一步多产出"，系统层让"算力、带宽、显存、并发被榨到极限"——综述把两层的所有代表性技术编成一棵分类树，并指出它们各自压的是哪个瓶颈。**

LLM 推理慢、贵的根因不是 FLOPs 不够，而是**自回归（autoregressive）的串行性**＋**KV Cache 的内存墙**。这篇综述的价值，是把散落在几百篇论文里的招数，按"它到底在攻哪个瓶颈"归位，让你做系统设计时知道"该往哪儿下手、几种招能不能叠加"。

```
                    高效 LLM 服务（Efficient LLM Serving）
                                  │
            ┌─────────────────────┴─────────────────────┐
       算法创新                                      系统优化
   (Algorithmic)                                   (System)
        │                                              │
   ┌────┼─────────┐                      ┌──────┬──────┼──────┬───────┐
 解码算法 架构设计  模型压缩            低比特量化 并行计算 内存管理 请求调度 Kernel优化
```

## 1. 地基：为什么 LLM 推理这么贵？（问题背景）

### 1.1 两个阶段：Prefill 与 Decode

一次生成请求分两段，它们的"性格"完全相反：

```
输入 prompt: "今天天气"  ──►  ┌──────────────┐
                              │  Prefill 阶段 │  把整段 prompt 一次性过一遍
  (N 个 token 并行算)         │  compute-bound│  → 算出每层的 K,V 存进 cache
                              └──────┬───────┘     产出第 1 个新 token
                                     ▼
                              ┌──────────────┐
                              │ Decode 阶段   │  每次只喂"上一个 token"
  (一个一个吐, 串行)          │ memory-bound │  → 读全部历史 KV + 算 1 步
                              └──────┬───────┘     产出下一个 token，循环到 EOS
                                     ▼
            "今天天气 → 很 → 好 → ，→ 适合 → 出门 → <eos>"
```

- **Prefill**：N 个输入 token 一起算，矩阵乘是大 GEMM，GPU 算力打满 → **compute-bound**（算力受限）。
- **Decode**：每步 batch 内每条序列只新增 1 个 token，权重要从显存搬到片上、却只算很少的乘加 → **memory-bound**（带宽受限）。**LLM 服务的大头开销在 Decode。**

### 1.2 KV Cache：又救命又要命

为避免每生成一个 token 都把前面所有 token 重算一遍，把每层每个历史 token 的 Key/Value 缓存下来。代价是显存：

$$\text{KV Cache 字节数} = 2 \times L \times n_{\text{layer}} \times n_{\text{head}} \times d_{\text{head}} \times b_{\text{bytes}}$$

其中 2 是 K 和 V，$L$ 是序列长度，$b_{\text{bytes}}$ 是每个数的字节（FP16=2）。

**手算（以 LLaMA-13B 量级、FP16 为例，数字示意）**：$n_{\text{layer}}{=}40$、$n_{\text{head}}{\times}d_{\text{head}}{=}5120$（即 hidden=5120）：

$$2 \times 5120 \times 40 \times 2\text{B} \approx 819{,}200\ \text{B} \approx 0.8\ \text{MB / token}$$

- 一条 2048-token 的序列 ≈ **1.6 GB** KV Cache。
- 并发 32 条 ≈ **51 GB**——**比 13B 权重（FP16 约 26 GB）还大**。这就是"内存墙"。

> 一句话：**Decode 是 memory-bound，KV Cache 又吃满显存**——综述里几乎每个系统技巧（量化、分页、调度）都在打这两点。

## 2. 算法创新（一）：解码算法——让"每一步"更值

自回归一步一个 token，是串行瓶颈。解码算法的目标：**在不（明显）降质的前提下，要么一步多吐几个、要么有些 token 用更便宜的方式产生。**

### 2.1 投机解码（Speculative Decoding）⭐

**直觉**：让一个便宜的小模型（draft）先"猜"未来 k 个 token，再让大模型（target）**一次并行验证**这 k 个。猜对的白赚，猜错的从第一个错点丢弃重来。关键是**验证用一次 forward 就能并行算 k 个位置**（因为 token 已知，可像 Prefill 一样并行）。

```
草稿模型 ──► 猜:  t1' t2' t3' t4'   (便宜, 串行 4 步但小)
大模型并行验证 ──► [t1 t2 t3 t4] 同一次 forward
                   √  √  √  ✗
              接受 t1 t2 t3, 拒绝 t4 → 用大模型在该位的分布重采一个
结果: 这一轮大模型只跑 1 次, 却前进了 3~4 个 token
```

- **为什么不降质**：验证用了拒绝采样（rejection sampling）的变体，保证输出分布**严格等于**只用大模型采样的分布（无损加速）。
- **变种**：自投机（Medusa：给大模型加多个预测头，省掉独立小模型）、前瞻解码（Lookahead）、SpecInfer（用小模型生成 **token 树**一次验证多条路径）。
- **收益**：取决于"接受率"，接受率高时单请求延迟可显著下降（**倍数见原文**）。

### 2.2 非自回归解码（Non-autoregressive, NAR）

一次性并行产出**整段** token，不再逐个依赖。速度极快，但因为丢了 token 间的依赖，质量通常下降，需迭代精修（iterative refinement）补偿。多用于翻译等任务，开放生成上仍是难点。

### 2.3 早退（Early Exiting）

不是每个 token 都需要走完全部 L 层。在中间层加分类头，**"容易"的 token 在浅层就置信地输出、提前退出**，只有难 token 才走到深层。

```
token "the"  ── 层1 ─ 层2 ─[置信度高?✓]─► 退出 (省了后面 30 层)
token "量子" ── 层1 ─ ... ─ 层40 ─► 必须走到底
```

难点：每个 token 退出深度不同，**batch 内对不齐**，工程实现与硬件利用率是挑战。

### 2.4 级联推理（Cascade Inference）

按难度路由到不同大小的模型：**简单请求走小模型，搞不定再升级大模型**。把"模型选择"做成动态决策，整体平均成本下降。

## 3. 算法创新（二）：架构设计——把模型本身改便宜

直接重塑 Transformer，让每一步的算力/显存内禀更低。

### 3.1 注意力简化（Attention Simplification）⭐⭐

标准多头注意力（MHA）每个 head 有独立 K/V，KV Cache 与 head 数成正比。两招砍 KV：

```
        MHA                  GQA                   MQA
   Q1 Q2 Q3 Q4          Q1 Q2 Q3 Q4           Q1 Q2 Q3 Q4
   │  │  │  │            \  /   \  /            \ \ / /
   K1 K2 K3 K4            K12    K34              K(单份)
   V1 V2 V3 V4            V12    V34              V(单份)
  KV与head同数        每组共享一份KV          所有Q共享一份KV
  (基线)              KV缩小为1/组数          KV缩小为1/head数
```

- **MQA（Multi-Query Attention）**：所有 Q head 共享**一份** K/V → KV Cache 缩到 1/$n_{\text{head}}$，但质量略降。
- **GQA（Grouped-Query Attention）**：折中，把 head 分组、组内共享 K/V（LLaMA-2/3 采用）。**这是当代主流。**
- **线性注意力 / 核化注意力**：把 softmax 注意力近似为可结合律重排的形式，将复杂度从 $O(L^2)$ 降到 $O(L)$，并能写成**循环（recurrent）形式**省 KV。

> 链接：[[llm-optimizer/kv-cache]] · [[llm-algo/transformer/模型架构]]

### 3.2 配置瘦身（Config Downsizing）

直接调小 hidden、层数、head 维度、词表等"超参旋钮"，或用浅而宽 / 深而窄的折中。简单粗暴但有效，常与蒸馏配合。

### 3.3 循环单元（Recurrent Unit）

引入类 RNN/SSM 的循环状态（如 RWKV、Mamba 类思路）：用**固定大小的状态**取代随长度增长的 KV Cache，推理显存与 $L$ 解耦，长序列友好。

### 3.4 激活共享 & 条件计算（MoE）⭐

- **激活共享（Activation Sharing）**：跨层/跨 head 复用中间激活，减少重复计算。
- **条件计算 / 专家混合（MoE）**：每个 token 只**激活一小部分专家（FFN）**。参数总量很大但**每步实际算的 FLOPs 很小**，是"大参数、低单步成本"的代表。

```
MoE 层:  token ──► Router ──► 选 Top-2 专家
        E1  E2  E3  E4  E5  E6  E7  E8   (8 个专家)
              ▲           ▲
            激活          激活            ← 只算 2/8，省 75% FFN 算力
```

> 链接：[[llm-algo/moe/README]]

## 4. 算法创新（三）：模型压缩——蒸馏与剪枝

### 4.1 知识蒸馏（Knowledge Distillation, KD）

用大"教师"模型的软标签/中间表示，教小"学生"模型，让小模型逼近大模型质量。LLM 时代更流行**黑盒蒸馏**：直接用 GPT-4 等生成的数据微调小模型。

### 4.2 网络剪枝（Pruning）

```
非结构化剪枝: 砍掉单个权重 → 稀疏矩阵 (理论省, 但需硬件/Kernel支持才提速)
   W: [● ● ● ●]      →    [● 0 ● 0]
      [● ● ● ●]            [0 ● 0 ●]

结构化剪枝: 砍掉整行/整列/整个 head/层 → 直接变小，立刻提速但更伤质量
```

- **非结构化（unstructured）**：粒度细、保质好，但稀疏不规则，常规 GPU 难加速（需 2:4 等半结构化稀疏 + 专用 Kernel）。
- **结构化（structured）**：粒度粗、立刻减小矩阵尺寸、好加速，但更易掉点。

> 链接：[[llm-compression/sparsity/README]]

## 5. 系统优化（一）：低比特量化

把权重/激活从 FP16 降到 INT8/INT4/FP8，**一举三得**：显存减半甚至 1/4、内存带宽压力下降（直接缓解 Decode 的 memory-bound）、低比特张量核更快。

| 方案 | 含义 | 典型代表 |
|---|---|---|
| W8A16 / W4A16 | 只量化权重，激活仍 FP16 | GPTQ、AWQ |
| W8A8 | 权重+激活都 INT8 | SmoothQuant、LLM.int8() |
| FP8 (E4M3/E5M2) | 8 位浮点，动态范围更好 | Hopper/Ada 原生支持 |
| KV Cache 量化 | 把 KV 也压到 INT8/INT4 | 直接砍 §1.2 的内存墙 |

**核心难点：激活里的"离群值（outlier）"**。少数通道幅值极大，直接量化会被它们撑爆动态范围、精度崩。

- **SmoothQuant**：把量化难度从"难量的激活"**数学等价地迁移**一部分到"好量的权重"上：$Y = (X \cdot \text{diag}(s)^{-1})(\text{diag}(s)\cdot W)$，选合适的逐通道缩放 $s$ 让两边都好量。
- **GPTQ**：逐层用近似二阶（Hessian）信息做误差补偿的权重量化，4-bit 仍保质。
- **AWQ**：识别"重要权重通道"并保护，按激活幅度做缩放。

> 链接：[[llm-compression/quantization/量化基础]] · [[llm-compression/quantization/fp8]]

## 6. 系统优化（二）：并行计算

单卡放不下 / 算不快，就摊到多卡。

```
张量并行 TP（层内切）          流水线并行 PP（层间切）
 ┌─────一层────┐               GPU0: 层 1-10
 │ W 按列/行切 │               GPU1: 层 11-20   ← 像流水线传递激活
 GPU0  GPU1 GPU2               GPU2: 层 21-30
 每步需 All-Reduce 同步        靠 micro-batch 填满流水避免气泡
 → 通信密集, 适合卡间高速NVLink → 通信少, 但有 bubble
```

- **张量并行（TP）**：把每个权重矩阵切到多卡，每层算完做一次 **All-Reduce** 汇总。通信频繁，需高带宽互联（NVLink），多用于**单机 8 卡内**。
- **流水线并行（PP）**：按层段切，卡间只传层边界激活，通信少，但有"流水线气泡"，靠多 micro-batch 缓解。
- **去中心化推理（Decentralized Inference）**：把模型摊到**地理分散、异构、低带宽**的设备（如 Petals）上协作推理——用算力换带宽，适合"众筹算力"场景。

**TP 通信量手算（一层）**：All-Reduce 一个 $[b, s, h]$ 激活（FP16），Ring-AllReduce 总传输约 $2\frac{p-1}{p}\cdot(b\,s\,h\cdot 2\text{B})$。$b{=}1,s{=}1$（Decode 单步）、$h{=}5120$、$p{=}8$：约 $2\cdot\frac{7}{8}\cdot 10\text{KB} \approx 17.5$ KB/层，再乘层数与每秒步数——**Decode 阶段 TP 的通信延迟会显著吃掉收益**，这也是为什么超过单机就更偏向 PP。

## 7. 系统优化（三）：内存管理——KV Cache 怎么管

§1.2 算过：KV Cache 是显存第一杀手，且**长度不可预知**。传统做法按"最大长度"预留连续显存 → 巨大浪费（内部碎片）。

**PagedAttention（vLLM 的核心）**：借鉴操作系统**虚拟内存分页**思想。

```
传统(连续预留):  [████░░░░░░░░░░░░]  按 max_len 占满, 实际只用前面一点 → 浪费
                  已用    预留浪费

PagedAttention:  逻辑KV ─► 页表 ─► 物理块(非连续, 按需分配)
  序列A: blk3 blk7 blk1     ┌──┐┌──┐┌──┐   显存按"页(block)"
  序列B: blk2 blk5          │  ││  ││  │   随用随取, 几乎零碎片
                            └──┘└──┘└──┘   还能跨请求"共享前缀"(Copy-on-Write)
```

- **几乎消除碎片**，显存利用率大增 → 同样显存能装下**更多并发序列** → 吞吐暴涨。
- **前缀共享**：多个请求共享相同 prompt 前缀（如同一 system prompt）时，物理块可共享，写时复制。

## 8. 系统优化（四）：请求调度

服务端要同时处理大量到达时间、长度各异的请求，怎么排队、怎么拼 batch 决定了吞吐。

**连续批处理 / 迭代级调度（Continuous Batching, a.k.a. iteration-level scheduling，源自 Orca）**：

```
静态批处理(吃亏): 一批里短请求早完, 却得等最长的那条结束才换批
  req1 ████░░░░░░░░  (早完, 但 GPU 空转等待 ↓)
  req2 ██████████░░
  req3 ████████████  ← 整批被它拖住

连续批处理(高效): 谁完成谁立刻退出, 空位立刻塞新请求进来
  req1 ████[换 req4 进来]████
  req2 ██████████[换 req5]██
  每"一步(iteration)"都重新组 batch → GPU 几乎不空转
```

- 调度粒度从"整个请求"细到"每一步迭代"，**完成的序列立刻让位**，新请求无需等整批结束。
- 配合 §7 的分页显存，可动态增删 batch 成员。
- 进一步：**PD 分离（Prefill/Decode Disaggregation）**——把 compute-bound 的 Prefill 与 memory-bound 的 Decode 拆到不同实例/卡上，各自用最优 batch 策略，互不干扰。

## 9. 系统优化（五）：Kernel 优化

把 GPU 算子本身榨干，是上面所有招数的"地基性能"。

### 9.1 Kernel 融合（Fusion）

把多个小算子（如 LayerNorm + 残差 + 偏置 + 激活）**合并成一个 Kernel**，减少 GPU kernel 启动开销和"读写显存往返"。Decode 是 memory-bound，**省一次 HBM 读写就是省时间**。

### 9.2 定制注意力 Kernel：FlashAttention ⭐⭐

标准注意力要把 $L\times L$ 的注意力矩阵**写回 HBM 再读回来**，HBM 读写量是 $O(L^2)$，对长序列致命。

```
朴素注意力:  Q,K → 写S(L×L)到HBM → 读回 → softmax → 写回 → 读回 ×V
            ↑ 大矩阵反复进出慢速HBM, IO 爆炸

FlashAttention: 分块(tiling), 让 S 的一块一直待在片上 SRAM
            └─ 边算边用 online-softmax 累积, 永不把完整 L×L 落地HBM
            → HBM 读写从 O(L²) 降到 O(L²/M) 量级 (M=SRAM块大小), 还省显存
```

它是 **IO-aware** 算法的典范：不减少 FLOPs，而是**减少慢速显存的读写次数**。

> 链接：[[llm-optimizer/FlashAttention]]

### 9.3 采样优化 & 变长序列

- **采样优化（Sampling Optimization）**：top-k / top-p / 温度采样的 GPU 高效实现，避免在最后一步成为瓶颈。
- **变长序列（Variable Sequence Length）**：一个 batch 内长短不一，朴素做法 padding 到最长 → 浪费。用 **packing / ragged batching + cu_seqlens** 等手段去掉 padding 计算。
- **自动编译（Auto Compilation）**：用编译器（TVM、torch.compile、TensorRT-LLM 等）自动生成融合 Kernel、做图优化，省去手写。

## 关键公式 / 算法 / 数值示例

### A. KV Cache 显存（再强化）

$$\text{Mem}_{KV} = 2 \cdot n_{\text{layer}} \cdot h \cdot L \cdot B \cdot b_{\text{bytes}}$$

$B$=并发数。LLaMA-13B（$n_{\text{layer}}{=}40,h{=}5120$）、$L{=}2048$、$B{=}1$、FP16：
$$2\cdot40\cdot5120\cdot2048\cdot2\text{B} \approx 1.6\ \text{GB/序列} \Rightarrow B{=}32 \approx 51\ \text{GB}$$
→ 量化 KV 到 INT8（$b{=}1$）直接砍半到 ~26 GB，**这就是为什么 KV 量化 + 分页是 Decode 显存的两大主力**。

### B. Roofline：判断在打哪个墙

算术强度 $I = \dfrac{\text{FLOPs}}{\text{Bytes 搬运}}$。

- Decode 单步：权重要全搬一遍（$\sim 2N$ 参数字节），却只算 $\sim 2N$ FLOPs（$N$=参数量）→ $I \approx 1/b_{\text{bytes}}$ 很低 → **落在 Roofline 的带宽斜坡上 = memory-bound**。
- 结论：**Decode 增大 batch（提高 $I$）、量化（减少 Bytes）才有用；单纯堆算力没用。**

### C. 投机解码加速比（直觉公式）

设接受长度期望为 $\gamma$（一次验证平均接受 token 数 + 1）、草稿模型相对大模型成本占比 $c$，则单 token 期望耗时 $\approx \dfrac{1 + \gamma c}{\gamma}$ 个大模型 step → **加速比 $\approx \dfrac{\gamma}{1+\gamma c}$**。$\gamma$ 越大（猜得越准）、$c$ 越小（草稿越便宜）越赚。**具体数值见原文。**

### D. 各技术"主攻瓶颈"速查

| 攻 compute-bound（Prefill/算力） | 攻 memory-bound（Decode/带宽） | 攻显存容量（KV 墙） |
|---|---|---|
| MoE、剪枝、配置瘦身、TP | 量化、FlashAttention、Kernel 融合、投机解码、连续批处理增大 batch | KV 量化、GQA/MQA、PagedAttention、循环单元 |

## 评价 / 对照 / 局限

| 维度 | 算法创新 | 系统优化 |
|---|---|---|
| 是否改变模型输出 | 可能（NAR/剪枝/量化降质；投机解码/GQA 设计为近无损） | 多为无损（量化有微损） |
| 是否需重训/微调 | 多数需要（蒸馏、剪枝、改架构） | 多数即插即用（分页、调度、融合） |
| 见效粒度 | 模型级，一次性 | 部署级，随负载持续生效 |
| 工程门槛 | 训练成本高 | 需深入 GPU/系统栈 |
| 可叠加性 | ✅ 与系统优化正交，常叠加（如 GQA 模型 + PagedAttention + 投机解码 + W4A16） | ✅ |

**综述自身的局限/提醒**：

1. 这是 2023 年底的快照，**FP8 训推一体、PD 分离规模化、MoE 推理调度、长上下文专用注意力**等后续是大热点，需结合最新工作看。
2. 分类树是"教学性"的，真实系统里多招耦合（如连续批处理依赖分页显存、投机解码影响 batch 调度），不能孤立评估。
3. 数字普遍依赖模型/硬件/负载，**论文中的加速比是特定设置下的结论，迁移前务必自测**。

> 一句话收尾：**做 LLM 服务优化，先用 Roofline 判断你卡在哪个墙（算力 / 带宽 / 显存），再从这棵树里挑能叠加的招数组合——这正是本综述给你的"作战地图"。**
