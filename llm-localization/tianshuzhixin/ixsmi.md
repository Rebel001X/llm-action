## 0. 一句话锚点

**ixsmi = Iluvatar System Management Interface**,天数智芯 GPGPU 的"体检仪"。
你在英伟达机器上敲 `nvidia-smi` 的所有肌肉记忆——查卡、查显存、查进程、查拓扑、写巡检脚本——在天数智芯机器上几乎都能平移成 `ixsmi`。它本质是一个命令行前端,底层调用厂商的设备管理库(类比 NVML 的 `ixml`)去读内核驱动暴露的设备状态。

> 精确的子命令、参数拼写、字段名以天数智芯官方文档为准;本文讲"为什么这么用、对标谁、易踩什么坑",不锁死具体命令拼写与版本号。

## 1. 地基:天数智芯软件栈定位 + 对标英伟达生态

天数智芯做的是 **GPGPU**(通用 GPU),走的是"尽量兼容 CUDA 生态"的路线,这和昇腾(自成体系的 NPU + CANN)是两种不同的国产化思路。理解这点,迁移心智图就清楚了。

软件栈分层(硬件 → 驱动 → 计算软件栈 → 框架 → 套件),ixsmi 处在"驱动之上、给人看的管理工具"这一层:

```
┌───────────────────────────────────────────────────────────┐
│  应用/套件:  训练框架 / 推理引擎 / 业务代码                  │
├───────────────────────────────────────────────────────────┤
│  框架层:     PyTorch(适配版) / PaddlePaddle / TensorFlow    │
├───────────────────────────────────────────────────────────┤
│  计算软件栈:  IXUCA(天数智芯统一计算架构)                    │
│              ├─ 编译器 / Runtime(对标 CUDA Runtime)         │
│              ├─ 算子/数学库(对标 cuDNN / cuBLAS)            │
│              ├─ 集合通信库(对标 NCCL)                       │
│              └─ ixml 设备管理库(对标 NVML)  ← ixsmi 调它    │
├───────────────────────────────────────────────────────────┤
│  内核驱动:    天数智芯 GPU 驱动(对标 NVIDIA Kernel Driver)  │
├───────────────────────────────────────────────────────────┤
│  硬件:        天垓(BI)/ 智铠 GPGPU(对标 NVIDIA GPU)        │
└───────────────────────────────────────────────────────────┘
        ▲
   ixsmi 站在"ixml 库 + 驱动"之上,把设备状态翻译成人读的表格
```

**天数智芯 ↔ 英伟达生态对照表**(迁移心智图,先认这张表):

| 维度 | 天数智芯(Iluvatar CoreX) | 英伟达(NVIDIA) | 说明 |
| --- | --- | --- | --- |
| 加速卡 | 天垓(BI)/ 智铠 GPGPU | A100 / H100 等 GPU | 都是通用 GPU,非专用 NPU |
| 计算软件栈 | IXUCA | CUDA | 天数主打 CUDA 生态兼容 |
| 设备管理 CLI | **ixsmi** | **nvidia-smi** | 本文主角,几乎一一对应 |
| 设备管理库 | ixml | NVML | CLI 背后的 C 库 |
| 数学/算子库 | IXUCA 数学库 | cuDNN / cuBLAS | 训推性能的地基 |
| 集合通信 | IXUCA 通信库 | NCCL | 多卡 All-Reduce 等 |
| 框架 | 适配版 PyTorch/Paddle | 原生 PyTorch | 多数 API 平移 |
| 编程模型 | 兼容 CUDA 风格 | CUDA C/C++ | 迁移成本相对低 |

**对比一下另一条国产化路线(昇腾)**,帮助你把天数定位得更准:

| 路线 | 代表 | 设备工具 | 思路 |
| --- | --- | --- | --- |
| GPGPU 兼容路线 | 天数智芯 | **ixsmi** | 兼容 CUDA 生态,迁移成本低 |
| 自研 NPU 路线 | 昇腾 Ascend | npu-smi | 达芬奇架构 + CANN 自成体系 |
| 英伟达 | NVIDIA | nvidia-smi | 原生标准 |

一句话:**ixsmi 之于天数,正如 npu-smi 之于昇腾、nvidia-smi 之于英伟达——三者都是"问卡要状态"的标准入口,只是底座不同。**

## 2. ixsmi 在软件栈中的位置:它读的是谁

ixsmi 自己不直接碰硬件寄存器,它的数据链路是这样的:

```
   你(运维/工程师)
        │  敲 ixsmi -q
        ▼
   ┌──────────┐   调用    ┌───────────┐   ioctl/sysfs   ┌──────────────┐
   │  ixsmi   │ ───────▶ │  ixml 库  │ ──────────────▶ │  GPU 内核驱动 │
   │ (CLI 前端)│          │ (对标NVML)│                 │ (对标NV驱动)  │
   └──────────┘          └───────────┘                 └──────┬───────┘
        ▲                                                     │ 读硬件传感器/计数器
        │  格式化成表格输出                                     ▼
        └─────────────────────────────────────────  天垓/智铠 GPGPU 硬件
```

要点:
- **驱动是前提**。`ixsmi` 看不到卡,99% 是驱动没装好/版本不匹配/内核模块没加载,而不是 ixsmi 本身的问题(和 `nvidia-smi` 一个道理)。
- **ixml 库对标 NVML**。如果你写过用 NVML 采集 GPU 指标的监控程序(Prometheus exporter 那类),迁到天数时对应去找 ixml 的接口。
- **ixsmi 是只读为主的观测工具**,真正跑算子是 IXUCA Runtime 的事,别把"ixsmi 能跑通"等同于"训练框架能跑通"。

## 3. 常用查询场景(基于已有命令直觉)

文件里已经出现了几类核心用法,逐一讲清"为什么这么敲"。

### 3.1 看显存占用

```
ixsmi                       # 总览:像 nvidia-smi 默认输出,一张大表
ixsmi -q -l                 # query + loop:循环刷新,持续观测
ixsmi -q -l | grep Used.[^G] # 过滤出"已用显存"等含 Used 的行
ixsmi -q -i 0 -l | grep ... # -i 0 只看 0 号卡
```

讲法:
- `-q`(query)= 详细查询,输出比默认表格更全的键值对,类比 `nvidia-smi -q`。
- `-l`(loop)= 周期刷新,做实时监控用,类比 `nvidia-smi -l`。
- `-i N` = 指定第 N 张卡,类比 `nvidia-smi -i N`。
- `grep Used.[^G]` 是一个**解析技巧**:`Used` 后面跟"非 G 开头字符",目的是把单位为 MiB 的"已用显存"行挑出来、避开某些干扰行——这类正则过滤在 nvidia-smi 脚本里也常见,但**字段措辞两边不一样**,迁移时正则要重写(见迁移坑)。

### 3.2 列出设备清单

```
ixsmi -L     # List:列出每张卡的索引/型号/唯一ID
```

类比 `nvidia-smi -L`。运维做资产盘点、确认"这台机器到底插了几张什么卡"时第一条命令。

### 3.3 温度 / 功耗 / 利用率

这三项是巡检三大件,通常都在 `ixsmi -q` 的详细输出里(温度、功耗 Power、Utilization)。做法和 nvidia-smi 完全同构:`-q` 拿全量,再 `grep` 出你关心的键。具体字段名以官方文档为准。

## 4. 拓扑查询:topo --matrix

```
ixsmi topo --matrix
```

对标 `nvidia-smi topo --matrix`。它打印一张 **N×N 卡间互联矩阵**,告诉你任意两张卡之间走的是什么链路:

```
        GPU0   GPU1   GPU2   GPU3
GPU0     X     高速   高速    跨片
GPU1    高速    X     跨片    高速
GPU2    高速   跨片    X      高速
GPU3    跨片   高速   高速     X
        (示意:实际链路类型/亲和性以 ixsmi 输出与官方文档为准)
```

为什么重要:
- **多卡训练/推理的性能,极度依赖这张图**。All-Reduce、张量并行的卡间通信如果踩在低速链路上,吞吐会塌方。
- 对标英伟达里 NVLink vs PCIe 的区别——你要让通信尽量走"近的、高速的"卡对。
- 调度/绑核/设置并行通信组(类比 NCCL ring 的构造)时,先看这张矩阵规划亲和性。这和 [[ai-infra/网络/集合通信原语]] 里 All-Reduce 的环算法选择是同一类问题。

## 5. 监控与运维实践

- **巡检脚本**:把 `ixsmi -q` 输出 `grep`/`awk` 成温度、功耗、显存、ECC 等关键指标,定时采集入库告警。思路与 nvidia-smi 巡检完全一致,只是字段名要按 ixsmi 实际输出对齐。
- **容器里看卡**:容器内能否跑 `ixsmi`,取决于宿主机驱动 + 设备节点是否正确透传进容器(类比英伟达的 nvidia-container-toolkit 机制)。具体的设备透传方式、容器运行时配置以天数智芯官方文档为准。
- **指标采集**:做 Prometheus exporter 时,优先调 ixml 库而不是反复 fork 解析 `ixsmi` 文本——解析文本脆弱且开销大,这条经验从 nvidia-smi/NVML 世界完全平移过来。
- **多卡作业前置检查**:作业拉起前先 `ixsmi -L` 确认卡数、`ixsmi topo --matrix` 确认互联,避免把高强度通信任务排到低速链路上。

## 迁移要点与常见坑

从 `nvidia-smi` 习惯迁到 `ixsmi`,机制层面要注意:

1. **命令骨架平移、字段名不平移**。`-q / -l / -i / -L / topo --matrix` 大体能对应,但详细输出里的**键名措辞、单位、缩进格式**两家不同。所有依赖 `grep`/`awk`/正则切文本的脚本**必须按 ixsmi 真实输出重写匹配规则**(文件里 `grep Used.[^G]` 就是为 ixsmi 输出量身定制的)。
2. **不要硬编码列位置**。文本输出的列宽/顺序可能随版本变化,脚本里别用"取第 5 列"这种写法,优先按键名匹配。
3. **能用库就别 parse 文本**。监控/采集场景走 ixml(对标 NVML),既稳又快。
4. **"ixsmi 能看到卡" ≠ "框架能用卡"**。前者只证明驱动 + ixml 正常;训练/推理还要 IXUCA Runtime、通信库、适配版框架全部就位。排障时分两层看。
5. **驱动与软件栈版本要配套**。驱动、IXUCA、框架适配包之间有版本依赖关系,版本错配是最常见的"看得到卡却跑不起来"。具体配套关系与版本以官方文档为准。
6. **退出码与自动化**。把 ixsmi 嵌进健康检查/告警时,以退出码和能否解析到关键字段为判据,不要只看"有没有报错文本"。

## 常见问题

| 问题 | 可能原因 | 排查方向 |
| --- | --- | --- |
| `ixsmi` 命令找不到 | 设备管理工具未安装或不在 PATH | 确认驱动/工具包安装,具体路径以官方文档为准 |
| 跑得了命令但看不到任何卡 | 内核驱动未加载 / 卡未识别 / 权限不足 | 查驱动模块是否加载、设备节点是否存在、用户权限 |
| 容器内 `ixsmi` 无设备 | 设备未透传进容器 | 检查容器运行时的设备透传配置 |
| 显存数字和框架报告对不上 | ixsmi 看进程级/设备级占用,框架看其内部分配池 | 两者口径不同,以 ixsmi 设备级为准做容量规划 |
| `topo --matrix` 链路类型看不懂 | 各厂商链路命名不同 | 对照官方文档的链路类型说明 |
| 巡检脚本从 NV 迁过来失效 | 字段名/正则不匹配 | 按 ixsmi 实际输出重写 grep/awk 规则 |
| 看得到卡但训练报错 | Runtime/通信库/框架适配包缺失或版本错配 | 分层排查:驱动→IXUCA→框架,核对版本配套 |
