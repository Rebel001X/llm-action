## 0. 一句话锚点

**天数智芯走的是"通用 GPU(GPGPU)"路线,因此它的迁移心智更接近"换一块兼容 CUDA 编程模型的 GPU",而不是"学一套全新的 NPU 编程范式"。**

国产算力大体分两条路:
- **GPGPU 路线(天数智芯、海光等)**:芯片是通用 GPU 架构,沿用 SIMT(单指令多线程)思想,软件栈对标 CUDA,目标是让 PyTorch/Paddle 这类框架"换个后端就能跑"。迁移成本相对低,但生态成熟度、算子覆盖仍需逐项验证。
- **ASIC 路线(昇腾达芬奇、寒武纪)**:为张量运算专门设计的领域专用架构,算力密度高,但编程模型与 CUDA 差异大,**算子覆盖是适配主战场**。

理解天数智芯,关键就是抓住"它在向 GPU 靠拢"这一点——你在英伟达上的并行心智、CUDA 生态经验,大部分可以平移过来。

## 1. 地基:天数智芯的定位 + 三方生态对照

### 1.1 天数在哪一层

和英伟达、昇腾一样,天数智芯卖的不只是芯片,而是**一整摞软件栈**。理解适配,先看清这摞栈的分层:

```
        ┌──────────────────────────────────────────────┐
 应用/套件 │   大模型训练/推理套件(适配版 DeepSpeed 等)    │  ← 训练/推理上层能力
        ├──────────────────────────────────────────────┤
   框架   │   PyTorch / PaddlePaddle(天数适配后端)        │  ← 主流框架 + 后端插件
        ├──────────────────────────────────────────────┤
        │           天数智芯 SDK / 软件栈                │  ← 对标 CUDA 的核心
   软件栈 │   ├ 编译器/运行时   ├ 算子库   ├ 通信库 ixCCL  │
        │   ├ Runtime/Driver API           ├ 监控 ixsmi │
        ├──────────────────────────────────────────────┤
 驱动/固件 │        Driver & Firmware(GPGPU 驱动)         │
        ├──────────────────────────────────────────────┤
   硬件   │   天数智芯 GPGPU(通用 GPU 架构,SIMT)         │
        └──────────────────────────────────────────────┘
```

**记忆要点:天数 SDK 之于天数 GPGPU = CUDA 之于英伟达 GPU。** 它把上层框架的算子调用翻译成 GPGPU 能执行的指令。因为路线"贴近 GPU",这一层在概念上与 CUDA 更同构,迁移时心智负担小于昇腾 CANN。

### 1.2 天数 ↔ 英伟达 ↔ 昇腾 三方生态对照表(最重要的迁移心智图)

| 维度 | 英伟达世界 | 天数智芯(GPGPU 路线) | 昇腾(ASIC 路线) | 说明 / 对应关系 |
|------|-----------|----------------------|-----------------|----------------|
| AI 加速芯片 | GPU(A100/H100…) | **GPGPU**(通用 GPU 架构) | NPU(达芬奇架构) | 天数更"像 GPU",昇腾是 ASIC 化张量核 |
| 底层计算平台 | **CUDA** | **天数 SDK / 软件栈** | CANN | 都是厂商底层异构计算平台 |
| 编程模型 | SIMT(线程网格/块) | **类 SIMT** | 多引擎 AI Core(Cube/Vector) | 天数沿用 GPU 线程模型,迁移直觉可平移 |
| 深度学习算子库 | cuDNN / cuBLAS | **天数算子库** | CANN 算子库 / AOL | 卷积、矩阵乘、归一化等高性能算子 |
| 集合通信库 | **NCCL** | **ixCCL(类 NCCL)** | HCCL | AllReduce/AllGather 等多卡多机通信 |
| 训练框架 | **PyTorch** | **PyTorch / PaddlePaddle(适配后端)** | PyTorch+torch_npu / MindSpore | 天数主打复用主流框架后端 |
| 大模型训练加速 | Megatron-LM / DeepSpeed | **适配版 DeepSpeed 等** | MindFormers / ModelLink | 并行训练能力 |
| 设备选择语义 | `cuda` / `torch.cuda` | 经适配后多沿用类 `cuda` 语义 | `npu` / `torch.npu` | 天数迁移在代码层改动通常更小 |
| 设备监控/管理 | **nvidia-smi** | **ixsmi** | npu-smi | 查显存、利用率、拓扑 |
| 性能分析工具 | Nsight / nvprof | 天数 Profiling 工具链 | msProf | 算子级耗时、流水分析 |
| 模型/数据中心 | HuggingFace Hub | 魔搭 ModelScope | 魔搭 ModelScope | 国内模型与数据集托管 |

> 用法:迁移时把你代码里出现的左列名词逐个找到对应列,这张表就是你的"翻译词典"。天数列与英伟达列的对应关系通常比昇腾列更直接。

## 2. 路线本质:GPGPU vs ASIC(为什么天数迁移更省力)

这是天数智芯最值得记住的一点。两条路线的差别决定了迁移工作量从哪里来。

```
   英伟达 GPU(SIMT)            天数 GPGPU(类 SIMT)        昇腾 NPU(达芬奇/ASIC)
   ┌──────────────────┐        ┌──────────────────┐       ┌──────────────────┐
   │ 海量线程 + warp   │  ≈≈≈→  │ 海量线程 + 类 warp │  ≠≠≠  │ Cube/Vector/Scalar │
   │ 灵活通用,按 kernel│        │ 编程模型同构       │       │ 多引擎,矩阵为原语  │
   │ 组织计算          │        │ 迁移直觉可平移     │       │ 需重新组织计算      │
   └──────────────────┘        └──────────────────┘       └──────────────────┘
        CUDA                        天数 SDK                     CANN
   迁移成本 ── 低 ───────────────────┘                            └─── 高(算子覆盖)
```

**结论:**
- 天数是 GPGPU,沿用线程网格/块的通用计算模型,框架后端适配后,**很多 PyTorch 代码改动很小甚至接近"换设备即可"**。
- 昇腾是 ASIC,把矩阵乘做成硬件原语,算力密度高,但需要把计算"对齐"到 Cube/Vector,**算子覆盖与图模式改造是主要工作量**。

> 注意:"贴近 GPU"不等于"零成本"。天数仍有自己的算子库与运行时,冷门算子、手写 CUDA kernel(如某些 FlashAttention 变体)是否覆盖,要逐项验证;且生态成熟度、第三方库支持仍需以官方文档为准。

## 3. 机制:软件栈分层,每层在适配中干什么

### 3.1 Driver & Firmware(驱动固件层)
让操作系统认识 GPGPU 卡,对标英伟达驱动。**坑:** 驱动、固件、SDK、框架后端插件之间有严格的版本配套关系——版本错配是新手第一大坑。配套矩阵以官方文档为准。

### 3.2 天数 SDK / 软件栈(核心适配层)
对标 CUDA。包含编译器、运行时(Runtime/Driver API)、算子库、通信库 ixCCL、监控工具 ixsmi 等。框架的算子调用最终落到这一层翻译执行。**它在概念上与 CUDA 同构**(都是"设备/内存/流/kernel 下发"那一套),这是 GPGPU 路线迁移省力的根因。

### 3.3 框架层:复用主流框架
天数主打**让 PyTorch / PaddlePaddle 多出一个天数后端**。理想情况下,把设备指向天数卡即可大体跑通;真正的工作量在于验证算子覆盖、对齐精度。**这条路线的卖点就是"复用 PyTorch 生态、迁移成本低"。**

### 3.4 套件层
在框架之上提供大模型训练/推理能力,常见做法是**适配主流开源套件**(如适配版 DeepSpeed 等),让习惯英伟达生态的用户少改代码。具体支持的套件与版本以官方文档为准。

## 4. 设备管理:ixsmi ↔ nvidia-smi(速查)

天数的设备管理命令是 **`ixsmi`**,对标英伟达的 `nvidia-smi`——光看名字就知道是刻意对齐心智的设计:用过 `nvidia-smi` 的人几乎零学习成本。

| 你想做什么 | 英伟达 | 天数智芯 | 说明 |
|-----------|--------|---------|------|
| 看卡状态/显存/利用率 | `nvidia-smi` | `ixsmi` | 总览面板,看每张卡占用 |
| 看显存"已用"明细 | `nvidia-smi -q` 过滤 | `ixsmi -q -l`(配合过滤) | 查 Used 显存(本目录 `ixsmi.md` 有示例) |
| 看指定卡 | `-i <id>` | `ixsmi -q -i <id> -l` | 定位单卡 |
| 看卡间拓扑 | `nvidia-smi topo -m` | `ixsmi topo --matrix` | 看互联关系,通信调优用 |
| 列出所有卡 | `nvidia-smi -L` | `ixsmi -L` | 列设备清单 |

> 同目录 [[ixsmi]] 文件给了几条 `ixsmi` 示例命令;以上仅为"对照心智",**确切参数与输出格式以官方文档为准**。

```
   nvidia-smi 心智                ixsmi 心智(几乎平移)
   ┌────────────────────┐         ┌────────────────────┐
   │ 看卡 / 显存 / 利用率 │  ≈≈≈→   │ 同样的看卡 / 显存    │
   │ topo -m 看拓扑      │         │ topo --matrix 看拓扑 │
   │ -L 列设备           │         │ -L 列设备           │
   └────────────────────┘         └────────────────────┘
```

## 5. 训练侧适配:复用 PyTorch / Paddle / DeepSpeed

**定位:** 天数训练侧的策略是**最大化复用英伟达生态的训练栈**,而不是另起炉灶造一套全新套件。

- **框架后端**:PyTorch / PaddlePaddle 适配天数后端,设备语义尽量贴近原生。
- **分布式加速**:常通过适配主流开源加速库(如 DeepSpeed 等)来提供 ZeRO、数据/张量/流水并行能力,概念与英伟达世界一一对应。
- **通信底座**:多卡多机走 ixCCL(对标 NCCL),见第 7 节。

**迁移含义:** 从英伟达迁到天数,主要是"换设备、换通信后端、验证算子与精度",并行切分的**概念不变**。**坑:** 即便编程模型同构,仍需做端到端精度比对(浮点累加顺序、低精度实现细节会有差异),不能"能跑"就当迁完。

---

## 6. 推理侧适配:大模型推理服务怎么落地

**定位:** 推理侧同样走"复用生态 + 后端适配"思路,目标是把英伟达上的推理服务(如 OpenAI 兼容接口)平移到天数卡上。

```
   请求 ──→ ┌─────────────── 推理服务 ───────────────┐ ──→ 流式输出
            │  调度 / 续批 / KV Cache 管理(类 vLLM)   │
            │  ─────────────────────────────────────  │
            │  算子加速 / Attention / 采样             │
            │  ─────────────────────────────────────  │
            │  天数 SDK + GPGPU 执行                   │
            └─────────────────────────────────────────┘
```

**迁移含义:** 如果你原来用 vLLM / TGI 等提供服务,迁到天数后服务接口形态相近,主要工作是确认:模型结构是否被算子库支持、KV Cache/续批等优化是否到位、精度是否对齐。**支持模型列表与推理优化能力以官方文档为准。**

## 7. 集合通信:ixCCL ↔ NCCL 与环算法

**定位:** 天数的集合通信库(类 NCCL,常称 ixCCL)对标 **NCCL**:提供 AllReduce、AllGather、ReduceScatter、Broadcast 等原语,是多卡多机训练/推理的通信底座。

分布式训练里梯度同步靠 AllReduce,其经典高效实现是 **Ring(环)算法**——天数通信库与 NCCL 在这点上思想一致:

```
   Ring AllReduce(4 卡,简化示意)
   GPU0 ─→ GPU1 ─→ GPU2 ─→ GPU3 ─┐
     ↑                            │   每卡把自己的分块沿环传给下一卡,
     └────────────────────────────┘   边传边累加;两轮后所有卡持有全和。

   优势:每卡收发量 ≈ 2*(N-1)/N * 数据量,与卡数 N 几乎无关 → 带宽友好
```

**机制要点:** 集合通信库会根据物理拓扑(卡间高速互联还是跨节点 RoCE 网络)选择通信算法与路径——用 `ixsmi topo --matrix` 先看清拓扑很重要。**坑:** 跨机通信对网络配置(RDMA/RoCE)敏感,集群组网与 rank 表配置错误是大规模训练起不来的常见原因;具体组网与环境变量以官方文档为准。

## 迁移要点 / 注意事项与坑(从 CUDA 迁到天数,必看)

1. **路线红利要会用**:天数是 GPGPU,编程模型贴近 CUDA,优先尝试"换设备 + 换通信后端"的最小改动路径,通常比迁昇腾省力。
2. **算子覆盖仍要逐项验证**:同构 ≠ 全覆盖。冷门/自定义算子、手写 CUDA kernel(如某些 FlashAttention 变体)是否被算子库支持,要实测,缺失则换等价实现或融合算子。
3. **精度对齐是硬性步骤**:不同硬件浮点累加顺序、fp16/bf16 实现细节不同,迁移后必须做**端到端精度比对**(逐层输出 + 最终指标)。
4. **通信后端切换**:分布式从 NCCL 换 ixCCL,要确保 rank 表、拓扑、网络(RoCE/RDMA)配置正确;先用 `ixsmi topo --matrix` 摸清互联。
5. **版本配套**:驱动/固件/SDK/框架后端/套件之间是强配套关系,版本矩阵以官方文档为准,错配会出现各种诡异报错。
6. **生态成熟度要预期管理**:国产 GPGPU 在第三方库、长尾算子、最新模型结构的覆盖上仍在追赶,迁移前先确认目标模型/套件是否在官方支持范围内。
7. **监控用 ixsmi**:把 `nvidia-smi` 心智平移到 `ixsmi`,排查显存/利用率/拓扑问题,本目录 [[ixsmi]] 有示例。
8. **性能调优思路(机制层)**:用 Profiling 工具找瓶颈(算子耗时、通信占比、显存带宽),而非盲调;关注大算子是否走到高性能库实现、通信是否吃满带宽。

## 常见问题

| 问题 | 解答 |
|------|------|
| 天数智芯和昇腾有什么本质区别? | 天数是 GPGPU(通用 GPU 架构,类 CUDA 编程模型),昇腾是 ASIC(达芬奇多引擎)。天数迁移更"像换 GPU",昇腾迁移需对齐 Cube/Vector 并攻算子覆盖。 |
| 从英伟达迁到天数比迁昇腾省力吗? | 通常更省力,因为编程模型同构、设备语义贴近、可复用 PyTorch/DeepSpeed 生态;但算子覆盖、精度对齐、生态成熟度仍需逐项验证。 |
| 天数 SDK 等于 CUDA 吗? | 定位等价(都是厂商底层异构计算平台),但不是二进制兼容;CUDA 二进制不能直接跑,要走框架/后端适配,只是概念更同构。 |
| ixsmi 是什么? | 天数的设备管理工具,对标 `nvidia-smi`,用法心智几乎可平移(看卡/显存/拓扑/列表)。本目录 `ixsmi.md` 有示例。 |
| ixCCL 和 NCCL 是同一套吗? | 不是同一实现,但原语与算法思想(如 Ring AllReduce)对应,迁移时换后端即可,概念不变。 |
| "换设备就能跑"是真的吗? | 是迁移的**起点**而非终点。最小改动后仍要过算子覆盖、精度对齐、通信配置、版本配套四关。 |
