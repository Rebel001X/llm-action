## 0. 一句话锚点

昇腾不是"另一张卡", 而是**一整套与 CUDA 平行的软件栈**:硬件(NPU)→ 驱动/算子库(CANN)→ 框架(MindSpore / PyTorch+torch_npu)→ 套件(MindFormers / MindIE / msmodelslim)。学习的关键不是记命令, 而是**建立"这一层在 CUDA 世界对应谁"的映射**——映射对上了, 80% 的概念可以平移, 剩下 20% 是真正要踩的坑。本文就是这张映射 + 一份按层级排序的精读清单。

> ⚠️ 全文涉及的安装命令、镜像名、包版本、API 签名一律**以华为昇腾官方文档(Ascend 社区 / Gitee / 昇腾论坛)为准**。本文只讲"读什么、为什么这么读、对标谁、坑在哪", 不写具体版本号和命令行——这类信息更新极快, 抄进笔记就是埋雷。

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

昇腾软件栈是**自底向上分层**的, 每一层都能在 CUDA 世界找到对应物。先把这张表刻进脑子:

| 昇腾(Ascend)生态 | 英伟达(NVIDIA)生态 | 这一层干什么 |
| --- | --- | --- |
| 昇腾 NPU(910/310 系列) | GPU(A100/H100 等) | 算力硬件 |
| 达芬奇(Da Vinci)架构:Cube/Vector/Scalar 单元 | SM:Tensor Core / CUDA Core | 芯片内计算单元 |
| **CANN**(Compute Architecture for Neural Networks) | **CUDA** Toolkit | 异构计算平台/编程框架 |
| AscendCL(ACL) / Ascend C | CUDA Runtime / CUDA C++ | 设备编程 API / 算子开发语言 |
| CANN 内置算子库(AOL) | cuDNN / cuBLAS | 高性能算子库 |
| GE(Graph Engine)图编译 | TensorRT 图优化 / CUDA Graph | 图编译与优化 |
| **HCCL** | **NCCL** | 多卡/多机集合通信 |
| HCCS / 卡间高速互联 + RoCE | NVLink / NVSwitch + IB | 互联网络 |
| **MindSpore** | **PyTorch** / TensorFlow | 深度学习框架 |
| **torch_npu**(PyTorch 昇腾适配) | 原生 PyTorch CUDA 后端 | 让 PyTorch 跑在 NPU 上 |
| **MindFormers** / **ModelLink** | **Megatron-LM** / HF Transformers | 大模型训练套件 |
| **MindIE** | **TensorRT-LLM** / vLLM | 推理引擎/服务 |
| vLLM-Ascend(vLLM 昇腾后端) | vLLM(CUDA) | 高吞吐推理框架 |
| **msmodelslim** | GPTQ / AWQ / llm-compressor | 量化压缩工具 |
| MindStudio / msprof | Nsight / nvprof | 开发与性能分析工具 |
| npu-smi | nvidia-smi | 设备管理命令行 |
| openMind(魔乐社区) | HF Hub | 模型/数据集托管社区 |

ASCII 看一眼整栈:

```
   应用 / 大模型
 ┌──────────────────────────────────────────────┐
 │ 套件层  MindFormers · ModelLink · MindIE       │  ← 对标 Megatron / TensorRT-LLM / vLLM
 ├──────────────────────────────────────────────┤
 │ 框架层  MindSpore   |   PyTorch + torch_npu    │  ← 对标 PyTorch / TF
 ├──────────────────────────────────────────────┤
 │ CANN    AscendCL · AOL算子库 · GE图引擎 · HCCL  │  ← 对标 CUDA · cuDNN/cuBLAS · TensorRT · NCCL
 ├──────────────────────────────────────────────┤
 │ 驱动/固件  Driver + Firmware                    │  ← 对标 NVIDIA Driver
 ├──────────────────────────────────────────────┤
 │ 硬件    昇腾 NPU(达芬奇架构 Cube/Vector)        │  ← 对标 GPU(SM/Tensor Core)
 └──────────────────────────────────────────────┘
```

**记住这张图最大的价值**:遇到任何昇腾名词, 先问"它在哪一层、对应 CUDA 世界谁", 再去查官方文档对应章节, 学习效率翻倍。

## 2. 一手权威资料:按层级精读清单

> 原则:**先官方、后社区**。官方文档负责"准确", 社区/博客负责"踩坑经验"。两者都要, 但事实以官方为准。

### 2.1 总入口(必收藏)

| 资源 | 定位 | 对标 |
| --- | --- | --- |
| 昇腾社区(Ascend 官网/文档中心) | 所有官方文档总入口 | NVIDIA Docs |
| 昇腾论坛 | 提问/踩坑/版本配套答疑 | NVIDIA Developer Forums |
| Gitee 上的 Ascend / MindSpore 各仓库 | 源码 + Issue + 配套表 | GitHub NVIDIA 组织 |
| 魔乐社区 openMind | 国产模型/数据集托管 | Hugging Face Hub |

### 2.2 CANN 与算子开发(地基中的地基)

- **CANN 官方文档**:理解 AscendCL、内存模型、Stream/Event、图模式 vs 单算子模式。对标读法——把它当"CUDA Programming Guide 的昇腾版"来读。
- **Ascend C 算子开发**:类比"写 CUDA Kernel"。重点理解达芬奇的 **Cube(矩阵)/ Vector(向量)** 双引擎与 **Tiling(数据切分)** 思想——这是性能的命门,等价于 CUDA 里 block/thread 切分 + shared memory 复用。

### 2.3 框架层

- **MindSpore 官方教程**:原生昇腾框架, 主打**图算融合 + 全场景**。对标 PyTorch+TF 的合体。从 GPU 转来若想"零适配最大化用昇腾", 这是首选。
- **torch_npu / PyTorch on Ascend**:让现有 PyTorch 代码迁到 NPU 的**适配层**。多数从 GPU 迁移的团队走这条路——改动小、生态熟。重点读"如何把 `cuda` 设备改成 `npu`、哪些算子未支持、如何用昇腾亲和 API"。

### 2.4 训练套件

- **MindFormers**:MindSpore 生态的大模型训练/微调套件, 内置主流大模型 + 并行策略(DP/TP/PP/SP/优化器并行)。对标 **Megatron-LM**(并行能力)+ **HF Transformers**(开箱模型库)。
- **ModelLink**(基于 PyTorch+torch_npu):面向昇腾的大模型训练库, 直接对标 **Megatron-LM** 的并行训练范式。从 Megatron 迁移者读这个最顺。

### 2.5 推理套件

- **MindIE**:昇腾官方推理引擎/服务化方案, 含图优化、KV Cache、连续批处理(continuous batching)等。对标 **TensorRT-LLM + Triton**(性能+服务化)。
- **vLLM-Ascend**:vLLM 的昇腾后端, 把 PagedAttention/连续批处理这套高吞吐机制带到 NPU。对标 **vLLM(CUDA)**——会 vLLM 的人迁移成本最低。

### 2.6 压缩与量化

- **msmodelslim**(昇腾模型压缩工具):提供量化(W8A8、W8A16、W4A16 等)、稀疏等能力。对标 **GPTQ / AWQ / llm-compressor**。读它要先理解量化基础([[llm-compression/quantization/量化基础]]), 再看昇腾上"量化后用什么算子跑、精度怎么校准"。

### 2.7 超节点 / 系统级

- **CloudMatrix384**(已在本仓库引用的《Serving Large Language Models on Huawei CloudMatrix384》):华为以 384 颗 NPU 构成的**超节点(SuperPod)**, 用全互联拓扑把多卡当"一台大加速器"用。对标英伟达 **GB200 NVL72** 这类机柜级超节点。读它能建立"系统级互联如何决定大模型训练/推理上限"的认知, 是从"单卡/单机"跳到"集群"视角的好材料。

## 3. 机制要点:达芬奇架构与 CANN(读资料时要抓的主线)

读硬件/CANN 资料时, 抓住这几条主线就不会迷路:

```
   达芬奇核(Da Vinci Core)
 ┌───────────────────────────────────────┐
 │  Scalar 单元   控制 / 标量             │
 │  Vector 单元   逐元素 / 激活 / 归一化   │  ← 对标 GPU CUDA Core(通用 SIMD)
 │  Cube  单元    矩阵乘加 MAC 阵列        │  ← 对标 Tensor Core(矩阵引擎)
 │  + 多级 Buffer(L1/L0/UB)             │  ← 对标 shared memory / register
 └───────────────────────────────────────┘
   数据流:GM(全局内存) → L1 → L0/UB → 计算 → 写回
```

- **Cube 是大模型算力主力**:GEMM/卷积都压在 Cube 上, 它决定峰值算力。这等价于"H100 的 Tensor Core 决定矩阵吞吐"。
- **Tiling(切分)是性能命门**:数据从全局内存搬到片上 Buffer 的切分策略, 直接决定计算单元利用率。类比 CUDA 里的 tiling + shared memory 复用——搬运没安排好, 算力再强也喂不饱。
- **图模式 vs 单算子模式**:图模式(GE 编译)做算子融合、内存复用, 吞吐高但灵活性低;单算子(Eager)调试方便但开销大。完全对应 PyTorch eager vs `torch.compile`/CUDA Graph 的取舍。
- **AOL 算子库**:CANN 内置高性能算子, 等价于 cuDNN/cuBLAS——能用库就别自己写 kernel。

## 4. 训练套件路线:从 Megatron 迁过来怎么读

```
 Megatron-LM 用户  ──►  读 ModelLink(PyTorch+torch_npu, 并行范式几乎一一对应)
 HF/PyTorch 用户   ──►  读 torch_npu 适配 + MindFormers(看模型库与并行配置)
 想吃满昇腾原生性能 ──►  读 MindSpore + MindFormers(图算融合最深)
```

主线:**并行策略名词在两边几乎通用**(DP/TP/PP/SP/EP、ZeRO/优化器并行)。迁移时真正变的是:① 设备/通信后端从 NCCL 换成 HCCL;② 部分自定义 CUDA kernel 需找昇腾等价算子或用 Ascend C 重写;③ 混精/算子精度行为可能有差异, 要对齐 loss 曲线。

## 5. HCCL 集合通信:对标 NCCL 的主线

HCCL = 昇腾的 NCCL。读它抓三点:

- **原语一一对应**:AllReduce / AllGather / ReduceScatter / Broadcast / AllToAll——名字和语义和 NCCL 一样(见 [[ai-infra/网络/集合通信原语]])。
- **拓扑感知算法**:Ring / 树形等算法按 HCCS、卡间互联拓扑自动选择, 思路同 NCCL 的 Ring/Tree-AllReduce。
- **迁移点**:代码里 `nccl` 后端 → `hccl` 后端;环境/拓扑配置(rank table 等)是昇腾特有, 是多机训练**最容易卡住**的地方, 务必照官方文档配。

```
   AllReduce(Ring 思路, HCCL 与 NCCL 同源)
   NPU0 ─► NPU1 ─► NPU2 ─► NPU3
     ▲                       │
     └───────────────────────┘
   分 Reduce-Scatter + All-Gather 两阶段, 带宽利用率最优
```

## 6. 推理套件路线:从 vLLM/TensorRT-LLM 迁过来怎么读

```
 vLLM 用户         ──►  vLLM-Ascend(PagedAttention/连续批处理直接平移, 成本最低)
 TensorRT-LLM 用户 ──►  MindIE(图优化 + 服务化, 性能路线对标最近)
 要端到端国产化部署 ──►  MindIE + msmodelslim(量化) 组合
```

主线:推理核心机制(KV Cache、连续批处理、PagedAttention、投机解码)是**框架无关**的,概念全部平移;变的是底层算子和服务接口。先把机制吃透([[llm-inference/README]]), 再看昇腾具体实现。

## 7. 量化路线:对标 GPTQ/AWQ 怎么读

- 先补量化基础([[llm-compression/quantization/量化基础]]):对称/非对称、per-channel/per-group、W8A8 vs W4A16、校准集。
- 再看 **msmodelslim** 在昇腾上的落地:量化后用哪些昇腾算子跑、精度如何校准、和 MindIE 推理如何衔接。
- 心智映射:GPTQ/AWQ 是"算法+工具", msmodelslim 是"昇腾上的对应工具"。算法理解通用, 工具用法看官方。

## 迁移要点 / 注意事项与坑

从 CUDA 世界迁到昇腾, 这些是反复踩的坑(机制层面, 非具体命令):

- **版本配套是第一杀手**:Driver / Firmware / CANN / 框架(MindSpore 或 torch_npu)/ 套件之间有**严格配套关系**, 版本错配 = 直接报错或精度异常。务必查官方"版本配套表",**具体版本以华为昇腾官方文档为准**。
- **设备与可见性变量**:`CUDA_VISIBLE_DEVICES` → 昇腾用 `ASCEND_RT_VISIBLE_DEVICES`(进程级)/ `ASCEND_VISIBLE_DEVICES`(容器级);`nvidia-smi` → `npu-smi`。
- **容器特权坑**:`--privileged` 下 docker runtime 会默认把本机所有卡分给容器, 多任务共用机器时易抢卡, 要显式做卡隔离。
- **算子缺失**:自定义 CUDA kernel / 冷门算子在昇腾可能没有现成实现, 需找等价 AOL 算子, 或用 **Ascend C** 重写——这是迁移工作量最大、最难预估的部分。
- **精度对齐**:混精策略、算子累加顺序、溢出处理差异会让 loss/输出和 GPU 不完全一致, 必须用同一份数据对齐 loss 曲线/精度, 别只看"能跑"。
- **通信配置(多机)**:rank table、网络平面(参数面/业务面)配置是昇腾多机训练的高频卡点, 严格按官方拓扑配置文档来。
- **图模式调优**:能上图模式(融合)再上, 但调试期先用单算子模式定位问题, 稳定后切图模式提吞吐——和 `torch.compile` 的用法节奏一致。
- **不要抄网上旧命令**:昇腾版本迭代快, 旧博客里的安装命令/包名经常失效, **一切安装/部署命令以官方文档当前版本为准**。
