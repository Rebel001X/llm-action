## 0. 一句话锚点

单机调试时你几乎感受不到网络；可一旦把训练扩到几百上千张 NPU，**"为什么这次训练比上次慢 20%"的答案，十有八九藏在网络里**——某条 RoCE 链路在悄悄丢包、某张网卡协商到了低速率、某个机柜的光模块在抖动。这些问题不会让训练崩溃报错，只会让它"莫名其妙地变慢"。

FabricInsight 要做的，就是把这张原本**不可见的高速网络变可见**：

> 算力 + HCCL 决定理论上限；**FabricInsight 帮你回答"实际为什么没跑到上限"，并把锅精确甩到某一条链路、某一块网卡上。**

记忆钩子：**Fabric**(网络这块"布")+ **Insight**(洞察)——给那张看不见的大网装上"X 光机"。

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

### 1.1 它不在数据通路上，而在"旁路观测"位置

要先纠正一个常见误解：FabricInsight **不负责传数据**(那是 HCCS/RoCE 物理链路 + HCCL 干的事)，它负责**看着数据怎么传**。用一句话区分：

- **数据面(Data Plane)**：HCCL 把 AllReduce 的张量真正搬过网络——这是"水管里流的水"。
- **管理/观测面(Management / Telemetry Plane)**：FabricInsight 在旁边采集"水管的水压、温度、有没有漏水"——它是**旁路(out-of-band 思路)**的观测者，不抢占数据面带宽。

```
        昇腾集群里 FabricInsight 的位置(旁路观测)
  ───────────────────────────────────────────────────────────
   套件层  MindFormers / MindIE / ModelLink   ← 跑训练/推理
   框架层  PyTorch(torch_npu) / MindSpore      ← 发起 all_reduce
   通信层  HCCL(集合通信)                       ← 数据真正在这里走网络
  ──────────────────────────┬────────────────────────────────
   物理网络 RoCE 交换机 / 网卡 / HCCS 总线  ──┐ 数据面(水在流)
  ──────────────────────────┼───────────────┘
                            │ 采遥测/计数器/流表(旁路)
                            ▼
              ┌───────────────────────────┐
              │   FabricInsight 观测面      │  ← 不在数据通路上,只"看"
              │  采集 → 关联 → 分析 → 告警   │
              └───────────────────────────┘
```

它横跨"硬件/驱动(取网卡与交换机计数器)"和"集群管理(汇总、可视化、告警)"两块，属于**集群运维/可观测性工具**，而不是 CANN 里某个算子库。

### 1.2 昇腾 ↔ 英伟达生态对照表(迁移心智图)

| 维度 | 昇腾(国产) | 英伟达/IB 世界(对标) | 一句话说明 |
| --- | --- | --- | --- |
| 网络可观测平台 | **FabricInsight** | UFM(Unified Fabric Manager) / NetQ | 整张 AI 网的健康度可视化与故障洞察 |
| 底层互联 | RoCE(无损以太) + HCCS(片间总线) | InfiniBand / NVLink+NVSwitch | 被观测的对象 |
| 集合通信库 | HCCL | NCCL | 数据面的通信引擎 → 见 [[HCCL]] |
| 单卡/链路计数器 | NPU 网卡(RoCE NIC)寄存器/计数器 | RDMA NIC counters(perfquery 等) | 丢包、重传、速率等原始指标 |
| 交换机遥测 | 数据中心交换机(CE 系列)telemetry | IB switch counters / sFlow/INT | 端口级流量与错误统计 |
| 无损网络机制 | PFC + ECN(DCQCN 思路) | IB credit / RoCE DCQCN | 防丢包/拥塞控制,FabricInsight 重点观测 |
| 慢节点定位 | straggler/慢链路根因分析 | NCCL profiling + UFM 拓扑分析 | 把"训练变慢"归因到具体节点 |
| 可视化/告警 | FabricInsight 控制台 + 告警 | UFM Web UI / Grafana | 拓扑图 + 指标曲线 + 异常告警 |

> 一句话平移：**把英伟达世界的 UFM/NetQ 换成 FabricInsight、把 InfiniBand 换成 RoCE、把 NCCL 换成 HCCL**，"用一个旁路平台监控大网健康、并把性能锅定位到链路"的思路完全同构。

## 2. 为什么大规模训练一定需要"网络可观测"

单卡看不见网络，但规模会把网络的每一个小毛病放大成大问题。核心原因有三：

1. **集合通信是"木桶短板"**：一次 AllReduce 要等**最慢的那条链路/那个 rank** 完成才算结束。一条链路丢包→重传→变慢，会拖累整个通信组、进而拖累整步训练。**最慢的链路决定整步的节奏。**

2. **故障"静默"且难复现**：链路抖动、间歇性丢包、光模块劣化往往不报错，只表现为"吞吐周期性掉一截"。没有可观测平台时，工程师只能靠"重启大法 + 玄学排查"，浪费大量集群机时。

3. **规模放大概率**：单条链路一年坏一次听起来很少，但上千条链路同时在跑，**"某处出问题"几乎是每天的常态**。必须有自动化的采集与定位，人工根本盯不过来。

```
   一次 AllReduce 的"木桶效应":一条慢链路拖垮整组
  ──────────────────────────────────────────────
   rank0 ──■■■■──┐
   rank1 ──■■■■──┤
   rank2 ──■■■■■■■■■■──   ← 这条链路在丢包/重传(慢)
   rank3 ──■■■■──┘
                  ▲
        整组必须等 rank2 完成 → 整步被拖慢
        FabricInsight 的价值:一眼指出"问题在 rank2 那条链路"
```

所以网络可观测不是"锦上添花"，而是**大集群能否稳定跑出高线性度(scaling efficiency)的刚需基础设施**。

## 3. 数据来源与采集层:它到底"看"什么

FabricInsight 的洞察能力，取决于它能采到哪些原始信号。概念上分三类来源(**具体采集协议、字段名、配置命令以华为昇腾官方文档(Ascend 社区)为准**)：

| 数据来源 | 采到的典型信号(概念层面) | 能回答什么问题 |
| --- | --- | --- |
| **NPU 侧网卡/RoCE NIC** | 收发包数、丢包、重传、协商速率、队列深度 | 这块卡的网络出口有没有异常 |
| **数据中心交换机** | 端口级流量、错误帧、PFC 暂停帧、ECN 标记数、缓存占用 | 哪个端口在拥塞/丢包 |
| **链路/物理层** | 光模块状态、误码、链路 up/down 抖动 | 是不是硬件/光模块层面劣化 |
| **集合通信侧(与 HCCL 关联)** | 通信耗时、各 rank 完成时间差 | 慢的是网络还是计算 |

采集思路上有两类范式，理解它对调优很关键：

- **轮询(Polling)**：周期性去读计数器,简单稳健,但粒度受采集周期限制,瞬时尖峰可能漏看。
- **遥测/订阅(Streaming Telemetry)**：设备主动按高频率推送指标,粒度细、能抓瞬态拥塞,但数据量大、对采集与存储压力更高。

> 注意点:采集频率越高越能抓到瞬态问题,但**采集本身也有开销**(占管理带宽、占存储)。这是一个"看得多细 ↔ 成本多高"的权衡,实际部署要按集群规模折中。

## 4. 架构总览:采集 → 关联 → 分析 → 呈现

把 FabricInsight 拆成四段流水线来理解，每一段都对标可观测系统的经典分层：

```
   FabricInsight 四段流水线(概念架构)
  ───────────────────────────────────────────────────────────
  ① 采集层 Collect      ② 关联层 Correlate    ③ 分析层 Analyze     ④ 呈现层 Present
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │ NIC 计数器    │     │ 把"卡-端口-   │     │ 基线对比/阈值 │     │ 拓扑可视化    │
  │ 交换机遥测    │ ──▶ │  链路-rank"  │ ──▶ │ 异常/慢节点   │ ──▶ │ 指标曲线      │
  │ 光模块状态    │     │  对应起来     │     │ 根因推断      │     │ 告警/事件     │
  │ HCCL 通信信息 │     │ (拓扑映射)   │     │              │     │ (控制台)     │
  └──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
       原始信号             有结构的拓扑           "结论"             人能看的视图
```

- **① 采集层**：从网卡、交换机、光模块、通信库多路取数(见第 3 节)。
- **② 关联层(最有价值的一环)**：原始计数器只是"端口 17 丢了 N 个包",没意义；必须结合**集群拓扑**把它翻译成"rank 128 到 rank 192 这条 AllReduce 路径上的链路在丢包"。**拓扑映射是把'指标'升级成'洞察'的关键。**
- **③ 分析层**：拿当前指标和历史基线/健康阈值对比,识别异常链路、慢节点(straggler)、拥塞热点,并尽量给出根因方向。
- **④ 呈现层**：拓扑图 + 指标曲线 + 告警事件,让运维"一眼看到红点在哪"。

## 5. 故障洞察与根因定位:把"慢"翻译成"哪条链路"

这是 FabricInsight 区别于"普通监控大盘"的核心能力。普通监控告诉你"集群吞吐掉了"；故障洞察要回答"**为什么掉、掉在哪、怎么修**"。典型定位链路如下：

```
   现象            →   观测信号               →   定位结论
  ─────────────────────────────────────────────────────────────
  训练吞吐周期性掉   →  某端口 PFC 暂停帧激增    →  该端口拥塞,需查拓扑/打散流量
  某步特别慢         →  某 rank 通信完成时间最长  →  该 rank 链路丢包/低速率(慢节点)
  偶发卡顿/重传      →  某光模块误码率上升        →  物理层劣化,换光模块/线缆
  长尾延迟          →  ECN 标记数升高           →  拥塞控制在生效但路径过载
```

几个关键概念：

- **慢节点(Straggler)定位**：通过比较各 rank 的通信耗时,找出"总是最慢的那一个",再顺着拓扑查它的链路与网卡——这是大模型训练里最高频的排障场景。
- **拥塞 vs 丢包 vs 物理劣化**：三者现象都是"变慢",但根因不同(分别对应流量调度、网络配置、硬件更换)。FabricInsight 的价值就是**用不同的观测信号把这三类区分开**,避免"一律重启"。
- **基线(Baseline)思维**：很多异常不是绝对阈值能抓的,而是"和这条链路平时的样子比变差了"。所以历史基线对比往往比死阈值更有效。

> 心智模型:**FabricInsight = 网络维度的 profiler。** 计算侧你用 profiler 看算子耗时;网络侧你用它看链路耗时与健康度,目标都是把"长尾/短板"揪出来。

## 6. 与集合通信(HCCL)和训练栈的联动

FabricInsight 单看网络指标已经有用，但**和上层一关联,威力才完整**：

- **和 HCCL 关联**：HCCL 知道"这次 AllReduce 是哪些 rank、走了哪条逻辑路径、耗时多少";FabricInsight 知道"这些路径下面的物理链路健康度"。两者拼起来才能回答"**这次通信慢,是网络物理层的锅,还是通信算法/拓扑编排的锅**"。详见 [[HCCL]] 与 [[ascend-infra/network]]。
- **和并行策略关联**：DP 走 AllReduce、TP 走频繁的小通信、PP 走点对点、EP 走 All-to-All——不同并行模式压在网络上的流量模式不同。把网络观测和并行配置对齐,才能判断"是不是某种并行把某段链路打爆了"。
- **和训练吞吐关联**：最终目的是把"网络指标"映射到"训练 TGS / MFU 的波动"上,形成**端到端的因果链:链路异常 → 通信变慢 → 整步变慢 → 吞吐下降**。

```
   端到端因果链(FabricInsight 帮你打通)
  ──────────────────────────────────────────────
   物理链路丢包 → RoCE 重传 → HCCL AllReduce 变慢
        → 某步通信耗时拉长 → 整步训练变慢 → 吞吐/MFU 掉一截
        ▲                                        ▲
        └──── FabricInsight 看这头 ────────────────┘ 训练日志看这头
                  二者一关联,根因立现
```

## 迁移要点与常见坑(从 IB+UFM 迁到 RoCE+FabricInsight)

从英伟达 InfiniBand + UFM 体系迁到昇腾 RoCE + FabricInsight，认知上要做这些调整：

1. **网络范式从 IB 换成 RoCE(无损以太)**：IB 天生无损靠 credit 机制;RoCE 要靠 **PFC + ECN** 这套"配置出来的无损"。**坑**:PFC/ECN 配置不当(队列、阈值、优先级映射)会导致拥塞扩散或假性丢包——这恰恰是 FabricInsight 重点观测的对象。具体配置参数以官方文档为准。

2. **"无损"是配出来的,不是默认的**：RoCE 上很多性能问题根源是无损配置不一致(不同交换机/网卡配置没对齐)。**坑**:只看 NPU 侧正常、不看交换机侧,会漏掉端口级拥塞。**两侧都要看。**

3. **别把 FabricInsight 当数据面工具**：它是旁路观测,不会提升通信带宽;它的产出是"诊断结论",真正的修复(改拓扑/换线缆/调 PFC/重排并行)要落到对应的层去做。

4. **拓扑信息必须准确**：关联分析的前提是平台知道真实拓扑(谁连谁)。**坑**:布线和登记的拓扑不一致,会导致根因定位指错链路。上线前核对物理拓扑很关键。

5. **采集开销要评估**：高频遥测在超大集群会带来可观的数据量与存储压力。**坑**:盲目拉满采集频率,可能让管理网/存储成为新瓶颈。按规模折中。

6. **"变慢不报错"才是常态**：迁移者最容易低估的,是"静默劣化"。**心态调整**:把网络可观测当成训练稳定性的一等公民,而不是出事才看的事后工具——平时就要建基线、配告警。

> 一句话避坑总纲:**RoCE 的性能=无损配置的正确性 + 物理链路的健康度;FabricInsight 是帮你持续验证这两件事的平台,而不是替你配好它们。**

## 常见问题

| 问题 | 解答(概念层面) |
| --- | --- |
| FabricInsight 会占用训练带宽吗? | 设计上走旁路观测,采集流量与数据面分离;但超大规模高频遥测仍有管理侧开销,需评估。 |
| 它和 npu-smi / npu 监控有什么区别? | npu-smi 偏**单卡设备**状态(算力/显存/温度);FabricInsight 偏**整张网络**的链路/拓扑健康度,是集群网络视角。 |
| 它能直接修复故障吗? | 不能。它负责"看清楚 + 定位根因",修复(换线缆/调 PFC/重排并行)由对应运维动作完成。 |
| 没有它能不能排网络问题? | 能,但要靠手工读交换机/网卡计数器 + 人脑关联拓扑,规模一大就不现实。它的价值是**自动化关联与定位**。 |
| 怎么判断慢是网络还是计算? | 把 FabricInsight 的链路/通信观测与训练 profiler 的算子耗时对齐:通信占比异常高且伴随链路指标恶化 → 网络;否则查计算。 |
| 具体安装/采集配置/支持的设备型号? | 因版本与硬件而异,**具体命令、版本、型号与配置以华为昇腾官方文档(Ascend 社区)为准**。 |
