## 0. 一句话锚点

昇腾(Ascend)NPU 不是"把 GPU 换个名字",它有**自己的驱动、自己的算子库(CANN)、自己的集合通信库(HCCL)、自己的可见性环境变量**。
绝大多数"昇腾卡跑不起来"的问题,不是模型问题,而是 **环境四件套没对齐**:
**驱动/固件 ↔ CANN ↔ 框架(MindSpore/torch_npu)↔ 套件(MindFormers/MindIE)** 的版本必须互相匹配,**以及卡的可见性在 privileged / 容器 / 进程 三层都被正确设置**。

记住一句话:**版本对齐 + 可见性对齐,占了昇腾运维问题的 80%。**

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

昇腾软件栈是分层的,理解了层次,排错就有方向——**报错在哪一层,就去那一层查**。

```
              昇腾(Ascend)栈                       英伟达(NVIDIA)栈
   ┌─────────────────────────────┐      ┌─────────────────────────────┐
   │ 套件层  MindFormers/MindIE   │      │ 套件层  Megatron/TRT-LLM/vLLM │
   │         ModelLink/msmodelslim│      │         GPTQ/AWQ              │
   ├─────────────────────────────┤      ├─────────────────────────────┤
   │ 框架层  MindSpore / torch_npu│      │ 框架层  PyTorch / TensorFlow  │
   ├─────────────────────────────┤      ├─────────────────────────────┤
   │ 算子+通信  CANN(AscendCL)    │      │ 算子+通信  CUDA/cuDNN/cuBLAS  │
   │            HCCL              │      │            NCCL              │
   ├─────────────────────────────┤      ├─────────────────────────────┤
   │ 驱动+固件  Driver / Firmware │      │ 驱动  NVIDIA Driver          │
   ├─────────────────────────────┤      ├─────────────────────────────┤
   │ 硬件  Ascend NPU(达芬奇)     │      │ 硬件  GPU(SM/Tensor Core)    │
   └─────────────────────────────┘      └─────────────────────────────┘
```

**昇腾 ↔ 英伟达 生态对照表**(读者最需要的迁移心智图):

| 维度 | 昇腾(Ascend) | 英伟达(NVIDIA) | 备注 |
|------|--------------|----------------|------|
| 加速器 | NPU(达芬奇架构 Cube/Vector) | GPU(SM + Tensor Core) | 昇腾以 Cube 矩阵单元为核心 |
| 编程/运行时 | CANN / AscendCL | CUDA / CUDA Runtime | CANN ≈ CUDA 全家桶 |
| 算子库 | CANN 内置算子(AOL/aclnn) | cuDNN / cuBLAS | 缺算子要走自定义算子开发 |
| 集合通信 | HCCL | NCCL | 环算法/HD 思路类似 |
| 监控工具 | `npu-smi` | `nvidia-smi` | 子命令不同,理念相同 |
| 进程可见性 | `ASCEND_RT_VISIBLE_DEVICES` | `CUDA_VISIBLE_DEVICES` | 见第 2 节 |
| 框架 | MindSpore / torch_npu(PyTorch 插件) | PyTorch / TensorFlow | torch_npu 让 PyTorch 跑在 NPU |
| 训练套件 | MindFormers / ModelLink | Megatron-LM / HF Trainer | 大模型并行训练 |
| 推理引擎 | MindIE | TensorRT-LLM / vLLM | KV Cache、连续批处理 |
| 量化工具 | msModelSlim | GPTQ / AWQ / TensorRT 量化 | W8A8/W4A16 等 |
| 图编译 | GE(Graph Engine)图模式 | CUDA Graph / TorchInductor | 静态图加速 |

> 具体每一层的安装命令、包名与版本号,**以华为昇腾官方文档(Ascend 社区)为准**。本文只讲"为什么"和"坑在哪"。

## 2. 卡的可见性:三层控制(最容易踩的坑)

这是从 GPU 迁过来的人**第一个被绊倒**的地方。昇腾卡的可见性有**三层**,层层收窄:

```
  物理机 8 张 NPU
        │
   ① privileged / runtime 层 ── 决定容器"能看到几张卡"
        │   --privileged 时 docker runtime 默认把【整机所有卡】塞进容器
        ▼
   ② 容器级  ASCEND_VISIBLE_DEVICES ── 决定这个【容器】可用哪几张
        │
        ▼
   ③ 进程级  ASCEND_RT_VISIBLE_DEVICES ── 决定这个【进程】实际用哪几张
                                          (≈ CUDA_VISIBLE_DEVICES)
```

要点逐条说清:

- **`--privileged` 特权模式下,昇腾或者英伟达的 docker runtime 中会默认分配本机所有卡。**
  这意味着:你以为只给了容器 2 张卡,实际容器里 `npu-smi` 能看到 8 张。多个容器若都用 privileged,就会**互相抢卡**。生产上更推荐**非特权 + 精确挂载设备**的方式(见第 4 节),把卡的隔离做实。

- **`ASCEND_VISIBLE_DEVICES`:容器级控制卡。** 由昇腾容器 runtime(Ascend Docker Runtime)识别,在**启动容器时**指定这个容器能拿到哪些 NPU。作用类似于"给容器划分配额"。

- **`ASCEND_RT_VISIBLE_DEVICES`:进程级控制卡,类似于 `CUDA_VISIBLE_DEVICES`。** 在容器/主机内,**启动训练或推理进程时**指定本进程实际使用哪几张卡,并完成**逻辑编号重映射**(进程内 device 0 映射到你指定的第一张物理卡)。

**三者的关系**:privileged/runtime 决定"端上来几张菜",`ASCEND_VISIBLE_DEVICES` 决定"这桌能吃哪几张",`ASCEND_RT_VISIBLE_DEVICES` 决定"我这一筷子夹哪张"。**排错时三层都要看。**

> 常见坑:在主机上设了 `ASCEND_RT_VISIBLE_DEVICES`,但进了 privileged 容器后没生效——因为容器是新环境,环境变量没带进去;要在**容器内/启动命令里**重新设置。

## 3. 软件栈版本对齐(80% 的"装不上"都在这)

昇腾栈是**强耦合**的:下层不匹配,上层直接崩。对齐链条:

```
  Firmware(固件) ─┐
                  ├─ 必须配套 ──► CANN ──► torch_npu / MindSpore ──► MindFormers/MindIE
  Driver(驱动)  ─┘                (版本号要和 CANN 对得上)   (套件也有自己的兼容矩阵)
```

- **驱动 + 固件**:最底层,装在物理机上。固件管硬件,驱动管 OS 与硬件通信。两者也要互相配套。
- **CANN**:相当于 CUDA Toolkit,提供算子、AscendCL、HCCL。**CANN 版本必须落在驱动支持的区间内**。
- **框架插件**:`torch_npu` 是 PyTorch 的昇腾后端插件,它的版本要**同时**匹配 PyTorch 版本和 CANN 版本(三方对齐);MindSpore 同理要匹配 CANN。
- **套件**:MindFormers / MindIE / ModelLink 各自有"配套版本矩阵",升级套件往往要连带升级 CANN。

> 核心坑:**单独升级任何一层都可能炸**。看到 `import torch_npu` 报错、`libascendcl.so not found`、算子注册失败,九成是版本错配。
> **具体的版本配套表与安装命令,以华为昇腾官方文档(Ascend 社区)的"软件配套关系/兼容性矩阵"为准。** 不要凭记忆拼版本号。

## 4. 容器与设备挂载

昇腾官方提供 **Ascend Docker Runtime**,作用相当于 NVIDIA Container Toolkit:把 NPU 设备、驱动库自动注入容器,免去手动挂一堆设备文件。

```
   docker run ... 
     ├─ 用 Ascend Docker Runtime  ──► runtime 自动注入 NPU 设备 + 驱动 .so
     │     (配合 ASCEND_VISIBLE_DEVICES 选卡)
     └─ 或不用 runtime,手动挂载 ──► 需要 --device 挂 NPU 字符设备
                                    + 挂载 driver/lib 目录 + 设环境变量
```

注意点(讲含义,不写死命令):

- **推荐用官方 runtime**,让它处理设备与库的注入;手动挂载容易漏挂某个驱动库导致容器内"看得见卡却用不了"。
- **驱动在宿主机,CANN 可以在容器里**:常见做法是宿主装驱动/固件,镜像里装 CANN + 框架,容器通过 runtime 复用宿主驱动。所以**容器内 CANN 版本仍要和宿主驱动配套**。
- **privileged 不是必须的**:能用精确设备挂载就别用 privileged,避免多容器抢卡和安全风险(见第 2 节)。

> 具体的 runtime 安装、`--device` 挂载路径、镜像拉取地址,**以华为昇腾官方文档与官方镜像仓库为准**。

## 5. 健康检查与监控:`npu-smi`

排查第一步永远是"卡还活着吗"。`npu-smi` 对标 `nvidia-smi`:

| 你想看的 | nvidia-smi | npu-smi(理念对应) |
|----------|-----------|---------------------|
| 卡列表/利用率/显存 | `nvidia-smi` | `npu-smi info`(子命令以官方为准) |
| 持续刷新 | `-l` | 同样支持轮询查看 |
| 单卡详情 | `-i <id>` | 按设备 id 查询 |
| 进程占用 | 进程列表段 | 查看 NPU 上的进程占用 |

要点:
- 看 **温度、AICore 利用率、HBM/显存占用、Health 状态**,任何一项异常都先排硬件/驱动,再怀疑模型。
- 报错 "device not found / 设备不可用",先 `npu-smi` 确认卡在不在,再看可见性(第 2 节)、再看驱动(第 3 节)。
- **具体子命令与字段名以官方文档为准**,但"先用 smi 体检"的思路与 GPU 完全一致。

## 6. 数据类型与算子坑

迁移训练/推理时,**数值与算子**层面最容易出现"能跑但精度不对"或"某层报不支持":

- **dtype**:昇腾对 **fp16 / bf16** 都支持,但**不同代际硬件支持程度不同**;混合精度训练要确认当前卡与 CANN 对 bf16 的支持。从 GPU 直接搬 `torch.bfloat16` 不一定无缝。
- **不支持的算子**:某些 PyTorch 算子在 `torch_npu` 上**尚未实现或走 CPU 回退**,表现为极慢或报错。遇到要么换等价算子,要么走**自定义算子开发**(CANN 提供算子开发框架)。
- **动态 shape**:图模式(GE)对动态 shape 支持有限,变长序列推理时容易触发反复编译,拖慢性能。常见优化是**分桶(bucketing)/固定档位 shape**。
- **图模式 vs 单算子模式**:图模式(类比 CUDA Graph/编译执行)吞吐高但灵活性低;调试期可用单算子(eager)模式,定位算子问题更直观。

## 7. 多卡通信坑(HCCL)

HCCL 对标 NCCL,多机多卡训练时它的"环境就绪"是另一个高频坑:

```
   单机多卡:进程 ↔ HCCL ↔ NPU 间高速互联(类比 NVLink)
   多机多卡:还需 rank table / 网络配置,把各节点 device 编排成一个通信域
```

要点:
- **rank table / 通信域配置**:多机训练通常需要描述"哪台机器的哪张卡是 rank 几"的配置,配错会卡在初始化(类似 NCCL 的 `init_process_group` 卡死)。
- **HCCL 相关环境变量**:超时、网卡选择、确定性等都有对应环境变量,**具体变量名与取值以官方文档为准**;排查 hang 住先看通信日志。
- **网络**:多机走 RoCE 等,网卡/IP/路由没通,HCCL 直接连不上。和 NCCL 一样,**通信问题先排网络**。

## 迁移要点 / 注意事项与坑(从 CUDA 迁到昇腾的 checklist)

1. **可见性变量改名**:`CUDA_VISIBLE_DEVICES` → `ASCEND_RT_VISIBLE_DEVICES`(进程级);容器级再加 `ASCEND_VISIBLE_DEVICES`。
2. **代码后端切换**:PyTorch 用户引入 `torch_npu`,把 `cuda` 设备改成 `npu`(`tensor.to("npu")`、`torch.npu.*`);很多 `.cuda()` 要替换。
3. **慎用 `--privileged`**:它会把整机卡全塞进容器,生产用精确挂载做隔离。
4. **版本四件套先对齐**:驱动/固件 ↔ CANN ↔ torch_npu/MindSpore ↔ 套件,**装之前先查官方配套矩阵**。
5. **dtype 复核**:确认当前卡对 bf16/fp16 的支持,混精配置可能要调。
6. **算子兜底**:跑通后用 profiling 看有没有算子回退 CPU,找性能黑洞。
7. **通信先打通**:多机先验证 HCCL/网络可达,再上大规模训练。
8. **监控用 `npu-smi`**:把它当成 `nvidia-smi` 用,体检永远是排错第一步。
9. **量化/推理换工具**:GPTQ/AWQ → msModelSlim;vLLM/TRT-LLM → MindIE,概念对应但配置不同。

性能调优思路(机制层面):优先吃满 **Cube 矩阵单元**(让 GEMM 尽量大且对齐),减少 **Vector/标量** 串行;开 **图模式** 提升吞吐;固定 shape 减少重编译;用 **profiling** 找算子回退和通信瓶颈。

## 常见问题

| 现象 | 最可能原因 | 排查方向 |
|------|-----------|---------|
| 容器内看到全部 8 张卡,本想只给 2 张 | 用了 `--privileged`,runtime 默认分配整机卡 | 改用精确挂载 + `ASCEND_VISIBLE_DEVICES` |
| 进程没用我指定的卡 | `ASCEND_RT_VISIBLE_DEVICES` 没设/没带进容器 | 在进程启动环境里重设 |
| `import torch_npu` 报错 / `.so not found` | 驱动/CANN/torch_npu 版本错配 | 对照官方配套矩阵重装 |
| 容器里 `npu-smi` 没卡 | runtime 没注入设备或驱动没装好 | 查 Ascend Docker Runtime、宿主驱动 |
| 某算子报不支持/极慢 | 算子未实现或回退 CPU | profiling 定位,换算子或自定义算子 |
| 多机训练卡在初始化 | rank table/网络/HCCL 配置错 | 先验通信域与 RoCE 网络 |
| 精度异常 | bf16/fp16 支持或混精配置 | 复核 dtype 与当前卡支持 |
| 变长推理越来越慢 | 动态 shape 反复编译 | 分桶/固定 shape 档位 |

> 凡涉及**精确命令、包名、版本号、设备路径、性能数字**,一律**以华为昇腾官方文档(Ascend 社区)为准**;本文只负责把"为什么、坑在哪、怎么对照 GPU 理解"讲清楚。
