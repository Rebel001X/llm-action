## 0. 一句话锚点

**MindIE 让一个已经训练好的大模型，在昇腾 NPU 上"又快又省地把 token 吐出来"。** 它要解决的不是"模型对不对"(那是训练的事)，而是**同样一张卡，怎么扛更多并发、首字更快、每秒生成更多 token、显存更省**。性能调优 = 在"时延(latency)"和"吞吐(throughput)"之间找你业务要的那个平衡点。

本文档顶部那段 `curl ... /v1/chat/completions` 就是 MindIE 对外暴露的 OpenAI 兼容接口：你像调 OpenAI 一样发请求(`model`/`messages`/`max_tokens`/`top_p`/`stream`/`logprobs`)，背后是昇腾 NPU 在算。性能调优就是让这个接口在高并发下依然稳、快、省。

## 1. 地基：在昇腾栈的定位 + 对标英伟达生态

### 1.1 昇腾软件栈是怎么叠起来的

```
        ┌─────────────────────────────────────────────┐
 应用层 │   你的服务 / OpenAI 兼容 API (本文档的 curl)   │
        ├─────────────────────────────────────────────┤
 推理层 │   MindIE  ← 本文主角                          │
        │   ├─ MindIE-Service  对外服务/调度/批处理     │
        │   ├─ MindIE-LLM      大模型推理逻辑(KV/采样)  │
        │   └─ MindIE-RT       图执行/算子下发           │
        ├─────────────────────────────────────────────┤
 框架层 │   MindSpore / PyTorch(torch_npu 适配)         │
        ├─────────────────────────────────────────────┤
 异构计算│   CANN(算子库 + 图引擎 + 运行时 + HCCL)        │
        ├─────────────────────────────────────────────┤
 硬件层 │   昇腾 NPU(达芬奇架构:Cube + Vector + Scalar) │
        └─────────────────────────────────────────────┘
```

记忆要点：**MindIE 站在 CANN 之上**。它自己不直接碰硬件，所有矩阵乘、注意力、通信最终都翻译成 CANN 的算子/HCCL 调用，由达芬奇核心执行。所以 MindIE 的性能 = MindIE 的调度策略 × CANN 算子效率 × 达芬奇硬件利用率，三者缺一不可。

### 1.2 昇腾 ↔ 英伟达 生态对照表(迁移心智图)

| 层 | 昇腾(Ascend) | 英伟达(NVIDIA) | 一句话类比 |
|----|--------------|----------------|------------|
| 加速卡 | NPU(Ascend 910/310 系列) | GPU(A100/H100…) | 都是"训练/推理加速器" |
| 计算核心 | 达芬奇 Cube/Vector 单元 | Tensor Core / CUDA Core | Cube≈矩阵乘心脏 |
| 异构计算平台 | CANN | CUDA | "操作加速卡的全套工具" |
| 算子/数学库 | CANN 算子库(AscendC/TBE) | cuDNN / cuBLAS | 卷积/矩阵乘的高效实现 |
| 集合通信 | HCCL | NCCL | 多卡 all-reduce/all-gather |
| 训练框架 | MindSpore（或 torch_npu） | PyTorch | 写模型的地方 |
| 训练套件 | MindFormers / ModelLink | Megatron-LM / HF | 大模型分布式训练 |
| **推理引擎** | **MindIE** | **TensorRT-LLM / vLLM** | **本文主角** |
| 量化工具 | msModelSlim | GPTQ / AWQ / SmoothQuant | 把权重压成低比特 |
| 服务化 | MindIE-Service(OpenAI 兼容) | vLLM serve / Triton | 起 HTTP 服务扛并发 |

> 读者最该记住的一行：**MindIE ≈ "昇腾上的 vLLM + TensorRT-LLM"**。vLLM 给了它"服务化 + Continuous Batching + PagedAttention"的味道；TensorRT-LLM 给了它"图编译 + 算子融合 + 量化加速"的味道。你在 vLLM 上的调优直觉，大部分可以平移过来。

## 2. MindIE 内部分层：一个请求是怎么被处理的

MindIE 不是单体，它分三层各管一摊。理解分层才能定位"性能瓶颈在哪一层"。

```
请求进来
   │
   ▼
┌────────────────────────────────────────────────────┐
│ MindIE-Service                                     │
│  · OpenAI 兼容路由(/v1/chat/completions)           │
│  · 请求队列 + 动态批处理(Continuous Batching)       │
│  · 多卡/多实例负载均衡                              │
└───────────────┬────────────────────────────────────┘
                ▼
┌────────────────────────────────────────────────────┐
│ MindIE-LLM                                         │
│  · Prefill(处理 prompt) / Decode(逐 token 生成)    │
│  · KV Cache 管理(PagedAttention 式分页)            │
│  · 采样(top_p / temperature / logprobs / stop)     │
└───────────────┬────────────────────────────────────┘
                ▼
┌────────────────────────────────────────────────────┐
│ MindIE-RT                                          │
│  · 把计算图下发到 CANN                             │
│  · 算子融合 / 图模式执行(减少下发开销)             │
└───────────────┬────────────────────────────────────┘
                ▼
          CANN → 达芬奇 NPU 真正算
```

调优时的定位口诀：
- **首字慢(TTFT 高)** → 多半在 Prefill 阶段，prompt 太长 / 图没编译好 / 算子没融合 → 看 MindIE-LLM + MindIE-RT。
- **生成卡顿(TPOT 高)** → Decode 阶段算子效率或 KV Cache 命中问题 → 看 MindIE-LLM + CANN 算子。
- **并发上不去 / 排队** → 批处理调度或显存不够 → 看 MindIE-Service 的批策略 + KV Cache 占用。

## 3. 性能从哪来(一)：Continuous Batching + 分页 KV Cache

这是 MindIE 吞吐量的两大引擎，思路与 vLLM 完全同源。

### 3.1 为什么需要 Continuous Batching(连续批处理)

LLM 生成是自回归的：一个请求要 token-by-token 地出，每个请求生成长度还不一样。如果用"静态批"(凑齐一批一起跑、一起结束)，短请求会被长请求拖死，NPU 大量空转。

**Continuous Batching**：把"批"做成动态的——某个请求生成完了立刻退出、新请求随时插进来，每一步 decode 都尽量把 NPU 喂满。

```
静态批(差):                连续批(MindIE 用的):
步骤 →                     步骤 →
R1 ███████░░░░ (早完空等)   R1 ███████ R4在这插入 ██████
R2 ██████████░            R2 ██████████
R3 ████░░░░░░░ (早完空等)   R3 ████ R5插入 ███████
                          ↑ NPU 利用率一直拉满
```

效果：在高并发下吞吐量(tokens/s 总和)显著提升，因为 NPU 没有空泡。

### 3.2 分页 KV Cache(PagedAttention 思路)

KV Cache 是每个请求历史 token 的 Key/Value 缓存，**它是显存大户**。传统做法给每个请求预留一大块连续显存(按最大长度)，浪费严重(碎片化 + 预留过头)。

分页式：把 KV Cache 切成固定大小的"块(block/page)"，按需分配、可复用、可共享(相同前缀的请求能共享块)。

```
传统(连续预留):  [请求A: ████████████░░░░░░] ← 后半段白占
                [请求B: ██████░░░░░░░░░░░░] ← 浪费更多

分页(按需取块):  块池 [▣][▣][▣][▣][▣][▣]...
                A→ ▣▣▣      B→ ▣▣   按实际用量发块
                              ↑ 显存利用率高 → 能塞更多并发
```

**对性能的意义**：显存省下来 → 同样的卡能容纳更大的 batch / 更长的上下文 / 更多并发请求 → 吞吐量上去。调优时最该盯的一个量就是 **KV Cache 还剩多少 block**，它直接决定你的并发天花板。

## 4. 性能从哪来(二)：量化 + 并行切分

### 4.1 量化(用 msModelSlim 把模型压小)

把权重/激活从 FP16 压到 INT8(W8A8)甚至更低：

- **显存更省** → 同卡塞更大 batch / 更长上下文，间接提吞吐；
- **访存更少 + Cube 算得更快** → 时延下降；
- **代价是精度**：要做校准(calibration)、可能逐层选择是否量化、关注关键层(如最后的输出层)精度。

昇腾上量化由 **msModelSlim** 产出量化权重，MindIE 负责加载并用对应的低比特算子推理。心智对照：`msModelSlim ≈ GPTQ/AWQ/SmoothQuant 工具链`，MindIE 加载量化模型 ≈ TensorRT-LLM 跑 INT8 engine。

> KV Cache 也可以量化(如 INT8 KV)。KV Cache 是显存大户，量化它往往比量化权重对"提升并发"更立竿见影，但同样要权衡长上下文下的精度。

### 4.2 并行切分(单卡装不下就切到多卡)

大模型一张卡放不下时，用张量并行(Tensor Parallel, TP)把每层权重横切到多卡，靠 **HCCL** 做 all-reduce 把结果合起来——这正是 HCCL↔NCCL 的对照点。

```
单层 MatMul 被 TP 切到 4 张 NPU:
  X ──┬─→ NPU0: X·W0 ─┐
      ├─→ NPU1: X·W1 ─┤  HCCL all-reduce
      ├─→ NPU2: X·W2 ─┤  把 4 份部分和加起来
      └─→ NPU3: X·W3 ─┘  → 完整结果
```

调优注意：TP 度数越大，单卡算得越少，但**通信占比越高**。如果卡间互联带宽(昇腾的 HCCS / 服务器拓扑)跟不上，TP 加卡的边际收益会快速衰减。这与 GPU 上"NVLink 不够时 TP 扩展性差"是同一个道理。

## 5. 压测方法学：怎么发请求、看什么指标

### 5.1 三个核心指标(先认指标再谈优化)

| 指标 | 含义 | 谁关心 | 受什么影响 |
|------|------|--------|------------|
| TTFT(首 token 时延) | 从发请求到吐出第一个字 | 交互式体验(对话) | prompt 长度、Prefill、批排队 |
| TPOT(每 token 时延) | 生成阶段平均每个 token 多久 | 流式打字快不快 | Decode 算子、KV 命中、batch 大小 |
| 吞吐(Throughput) | 全系统每秒总 token 数 | 离线/高并发成本 | 批大小、连续批、量化、显存 |

关键 trade-off：**调大 batch 通常提吞吐、但抬高单请求时延**；交互场景优先压 TTFT/TPOT，离线批量场景优先冲吞吐。先想清业务要哪个，再去拧参数。

### 5.2 用文档顶部的 curl 怎么压

回看本文档开头那段请求，逐字段读它对性能的影响：

```
curl -X POST 'http://<ip>:<port>/v1/chat/completions' \
  -d '{
    "model": "qwen1.5-14b",
    "messages": [ ... 多轮对话拼成的 prompt ... ],
    "max_tokens": 256,   ← 生成上限:越大单请求越久、越占 KV
    "top_p": 0.85,       ← 采样参数:影响质量,基本不影响速度
    "n": 10,             ← 一次要 10 个候选!并发/显存压力 ×10,压测重点关注
    "logprobs": true,    ← 返回 logprob 有额外开销
    "stop": "<|im_end|>",← 命中 stop 提前结束 → 省算力
    "stream": true       ← 流式:能更早拿到首字,利于观测 TTFT
  }'
```

要点：
- `n: 10` 是个性能放大器——它让一个请求等价于一束并行生成，压测时务必意识到它对显存/吞吐的乘数效应。
- `stream: true` 才能真实测 **TTFT**(看第一个 chunk 何时到)；非流式只能测端到端总时延。
- 压测要扫"并发数 × 输入长度 × 输出长度"三维，画出"吞吐随并发上升直到饱和/拐点"的曲线，拐点就是这套配置的服务容量。

> 具体的压测脚本、`benchmark` 工具名、端口与服务启动命令、各项配置开关，**以华为昇腾官方文档(Ascend 社区)为准**——本文只讲方法学与每个旋钮的物理含义，不杜撰命令与数字。

## 6. 迁移要点 / 注意事项与坑(从 CUDA/vLLM 搬过来)

### 6.1 心智迁移：直觉大多能平移

你在 vLLM/TensorRT-LLM 上的调优经验，绝大部分是迁移友好的：连续批、分页 KV、量化省显存、TP 加卡、TTFT/TPOT/吞吐这套指标体系，在 MindIE 上**概念完全一致**。先把"我在 GPU 上会怎么调"想清楚，再去找昇腾的对应旋钮。

### 6.2 真正要改 / 容易踩的坑

| 坑 | 现象 | 怎么想 |
|----|------|--------|
| 软件栈版本不匹配 | 模型跑不起来 / 算子报错 | MindIE / CANN / 固件驱动 / torch_npu 必须**配套版本**，错配是头号问题。具体配套矩阵以官方文档为准 |
| 图模式没用上 | TTFT 高、下发开销大 | 昇腾走"图模式(整图编译下发)"比"单算子下发"快得多;确认推理走的是图执行而非逐算子 eager |
| 算子未融合/未覆盖 | 某些层特别慢或回退 | 新模型结构可能缺高效融合算子;关注是否有未优化路径,必要时反馈/等官方算子 |
| 量化精度掉点 | 答案变差 | W8A8/KV 量化要做校准、关键层可保留高精度;不是无脑全量化 |
| KV Cache 设太小/太大 | 并发上不去 或 OOM | block 数/上下文上限要按显存预算配;盯"剩余 block" |
| TP 度数贪多 | 加卡不加速 | 通信占比升高;受服务器互联拓扑限制,不是越多越好 |
| chat template 不对 | 答非所问/不停 | 注意 prompt 里 `<|im_start|>/<|im_end|>` 等特殊 token 与 `stop` 要和模型模板对齐(见文档顶部示例) |
| 数据排布(layout) | 算子效率低 | 昇腾对内存格式/对齐有偏好;迁移时留意 layout/对齐导致的隐性低效 |

### 6.3 调优总思路(机制层面)

1. **先定位在哪一层**(Service 调度 / LLM 的 KV 与采样 / RT 与 CANN 算子)，按第 2 节口诀走。
2. **先吃免费午餐**：开图模式、确认连续批与分页 KV 生效、用上量化——这些是结构性收益。
3. **再调批与并行**：按业务在"时延 vs 吞吐"上选点，调 batch、上下文上限、TP 度数。
4. **最后抠算子**：看是否有未融合/回退路径，必要时换更优算子或反馈官方。
5. **全程以指标说话**：TTFT/TPOT/吞吐三条曲线 + 剩余 KV block，凭曲线找拐点，不要凭感觉拧。

## 常见问题

| 问题 | 回答 |
|------|------|
| MindIE 对标 GPU 上的什么? | TensorRT-LLM + vLLM 的合体:既有图编译/量化加速,又有服务化/连续批/分页 KV |
| 它直接操作 NPU 吗? | 不,它在 CANN 之上,所有算子/通信最终交给 CANN 与 HCCL,由达芬奇核心执行 |
| 提吞吐最该动什么? | 连续批 + 分页 KV + 量化(尤其 KV 量化)省显存 → 塞更大 batch;盯剩余 KV block |
| 提交互速度(首字)最该动什么? | 确认走图模式、缩短/缓存 prompt、降低批排队;`stream:true` 才能真实测 TTFT |
| `n:10` 为什么压测要小心? | 一个请求变成 10 路并行生成,显存与吞吐压力近似 ×10 |
| 量化一定提速吗? | 显存一定省;速度多数提升,但要做校准防精度掉点,关键层可保高精度 |
| TP 加卡为啥有时不快? | 通信(HCCL)占比随 TP 升高,受服务器互联带宽/拓扑限制,边际收益递减 |
| 跑不起来最常见原因? | MindIE/CANN/驱动固件/torch_npu 版本不配套——配套矩阵以官方文档为准 |
| 命令/版本/性能数字去哪查? | 一律以华为昇腾官方文档(Ascend 社区)为准,本文不杜撰 |
