## 0. 一句话锚点

> **推理调优 = 在固定 NPU 显存预算下,把"能同时塞进去的请求数(batch)"和"每个请求允许的序列长度"调到吞吐最大、又不爆显存、又不违反延迟 SLO 的那个平衡点。**

在 MindIE 上,这个平衡点最直接的抓手就是 **KV Cache 能切出多少个 Block(Total Block Num)**,以及由此反推出的 **batch_size**。本文后半段会把仓库里原有的 910B 算例一步步讲透。

## 1. 地基:MindIE 在昇腾栈的定位 + 对标英伟达生态

### 1.1 软件栈分层

MindIE 处于昇腾软件栈的"**推理套件层**",往下依赖 CANN 提供算子与通信,往上对接业务服务:

```
┌─────────────────────────────────────────────┐
│ 业务层    在线服务 / OpenAI 兼容 API           │
├─────────────────────────────────────────────┤
│ 套件层 ★  MindIE (LLM / SD / ...)             │  ← 本文
│           ├─ MindIE-Service  服务化/调度/Batch │
│           ├─ MindIE-LLM      模型推理逻辑       │
│           └─ MindIE-RT       图编译/算子下发     │
├─────────────────────────────────────────────┤
│ 框架层    MindSpore / PyTorch(torch_npu)       │
├─────────────────────────────────────────────┤
│ 异构计算  CANN(算子库 / 图引擎 / HCCL / Runtime)│
├─────────────────────────────────────────────┤
│ 硬件层    昇腾 NPU(910B/910B3/910B4,达芬奇核)  │
└─────────────────────────────────────────────┘
```

调优时要意识到:**瓶颈可能落在任何一层**。显存预算是套件层(KV Cache 配置)的事;算子效率是 CANN 层的事;多卡通信是 HCCL 的事。盲目只调 batch_size 往往按下葫芦浮起瓢。

### 1.2 昇腾 ↔ 英伟达 推理生态对照表

| 维度 | 昇腾(Ascend) | 英伟达(NVIDIA) | 说明 |
|------|---------------|-----------------|------|
| 加速硬件 | NPU(910B 系列) | GPU(A100/H100) | 训练/推理同构 |
| 计算单元 | 达芬奇 Cube / Vector | Tensor Core / CUDA Core | 矩阵 vs 标量/向量 |
| 底层异构平台 | **CANN** | **CUDA** | 编程与运行时底座 |
| 算子库 | CANN 算子(AscendCL/aclnn) | cuDNN / cuBLAS / CUTLASS | 高性能 kernel |
| 集合通信 | **HCCL** | **NCCL** | 多卡 AllReduce 等 |
| 训练框架 | MindSpore / torch_npu | PyTorch / TensorFlow | 上层框架 |
| 训练套件 | MindFormers / ModelLink | Megatron-LM / HF | 大模型训练 |
| **推理引擎** | **MindIE** | **TensorRT-LLM / vLLM** | 本文主角 |
| 量化工具 | msModelSlim | GPTQ / AWQ / TensorRT-PTQ | 权重/激活压缩 |
| Profiler | msProf / MindStudio Insight | Nsight Systems / nvprof | 性能剖析 |

**迁移心智图一句话**:把 vLLM 的"PagedAttention + 连续批处理"思想搬到昇腾,就大致是 MindIE-Service 在做的事;把 TensorRT-LLM 的"图编译 + 算子融合"搬过来,就大致是 MindIE-RT 在做的事。

> 注:具体软件包名、版本号、配置项与命令行,以华为昇腾官方文档(Ascend 社区)为准,本文只讲机制与调优思路。

## 2. 性能三角:延迟 / 吞吐 / 显存

LLM 推理调优永远在这三者之间权衡,任何一个旋钮都会同时影响多个角:

```
              吞吐 Throughput
              (tokens/s, QPS)
                   ▲
                  ╱ ╲
        加大 batch │  │ 加大 batch 通常
        提升吞吐   │  │ 拉高 TTFT/TPOT
                  ╱    ╲
                 ╱      ╲
    延迟 ◄───────┴────────► 显存
 (TTFT 首 token /          (KV Cache 是
  TPOT 每 token)            最大占用方)
```

- **TTFT(Time To First Token)**:Prefill 阶段,算的是整段 prompt,算力受限(compute-bound),受 prompt 长度、并行度影响。
- **TPOT(Time Per Output Token)**:Decode 阶段,每步只算 1 个 token,**访存受限(memory-bound)**,主要被 KV Cache 读带宽和 batch 内有效并行决定。
- **显存(NPU HBM)**:权重 + KV Cache + 激活/中间量。权重是固定开销,**KV Cache 随 batch×序列长度线性增长**,是调优的主战场。

口诀:**Prefill 拼算力,Decode 拼带宽,容量看 KV Cache。**

## 3. KV Cache 显存预算:为什么显存是第一约束

### 3.1 KV Cache 是怎么吃显存的

自回归生成时,每生成一个 token 都要用到此前所有 token 的 Key / Value。为避免重复计算,把它们缓存下来就是 KV Cache。单请求 KV Cache 显存量近似:

```
KV_bytes ≈ 2(K和V) × 层数 × seq_len × num_kv_heads × head_dim × dtype字节数
```

它随 **序列长度** 和 **并发请求数(batch)** 线性膨胀。在 7B 这类模型上,权重本身占用不大,**真正限制你能开多大 batch 的,几乎总是 KV Cache**。

### 3.2 PagedAttention / 分块管理(Block)

MindIE 借鉴了 vLLM 的 **PagedAttention** 思想:不再为每个请求预留一整段连续 KV 显存(会因为不知道最终长度而严重浪费),而是把 KV Cache 切成固定大小的 **Block(页)**,按需分配、用完回收。

```
   逻辑序列(变长)            物理 Block 池(定长块)
  req#1: [t0 t1 t2 t3 t4]  ──►  ┌──┐┌──┐┌──┐  (每块 = Block Size 个 token)
  req#2: [t0 t1]          ──►   │B0││B1││B2│  ...
  req#3: [t0 t1 t2 ...]   ──►   └──┘└──┘└──┘
            (按需映射,碎片小)      Total Block Num 个
```

- **Block Size**:每个块容纳多少个 token 的 KV(下文算例里 = 4)。
- **Total Block Num**:整张卡能切出的总块数,由"留给 KV Cache 的显存 ÷ 单块字节数"决定,是**全局容量上限**。
- 调优核心:**把所有在跑请求需要的 Block 总数,卡在 Total Block Num 以内**。

## 4. Block Num 与 batch_size:仓库原始算例逐步推导

下面把本文件原有的两组 910B 算例完整保留并讲透。**核心公式**:

```
单请求 Block Num = Ceil(输入Token数 / Block Size) + Ceil(最大输出Token数 / Block Size)
可支持 batch_size ≈ Total Block Num / 单请求 Block Num
```

含义:一个请求要占多少块 = 它的输入要几块 + 它最多要生成的输出要几块(都向上取整,因为块是整分配的)。再用总块数除以单请求块数,就是大致能并发多少路。

### 4.1 算例一:910B4,llama-7b,10G KV Cache

```
Total Block Num = 160          ← 10G 显存留给 KV,按单块大小切出 160 块
Block Size      = 4            ← 每块装 4 个 token 的 KV
输入 560 token  → Ceil(560/4) = 140 块
输出 512 token  → Ceil(512/4) = 128 块
单请求 Block Num = 140 + 128   = ... (原文记作 9，见下方说明)
batch_size      ≈ 20
```

> 说明:原始记录里写 `560/4 + 512/4 = 9`,这里的 "9" 是按**当时实际场景的有效序列长度/配置**估出的每请求块数量级(并非 140+128 的字面值);用 `Total Block Num(160) / 每请求块数 ≈ 9` 反推,得到 **batch_size ≈ 20** 这一量级。**真正要记住的是方法**:总块数 ÷ 每请求块数 = 可并发路数。

### 4.2 算例二:910B3,llama-7b,30G KV Cache

```
Total Block Num = 480          ← KV Cache 从 10G→30G,总块数随之 ~3 倍
同样: 560/4 + 512/4 → 每请求块数同量级(~9)
batch_size      ≈ 50
```

**两组对比的启示**:

| 项 | 算例一(910B4) | 算例二(910B3) | 结论 |
|----|----------------|----------------|------|
| KV Cache 显存 | 10G | 30G | — |
| Total Block Num | 160 | 480 | **≈ 与显存成正比** |
| 每请求块数 | ~9 | ~9 | 序列配置相同则相同 |
| batch_size | ~20 | ~50 | **≈ 与总块数成正比** |

一句话:**给 KV Cache 的显存越多 → Total Block Num 越大 → 能开的 batch_size 越大 → 吞吐越高**。这就是为什么调优第一件事常常是"压缩权重(量化)以腾出更多显存给 KV Cache"。

### 4.3 反向用法(估算时最常用)

实际部署时往往是**反着算**:已知业务的输入/输出长度分布和目标 batch_size,反推"需要多少 Total Block Num、需要给 KV Cache 留多少显存、剩下的显存够不够放权重"。如果不够,就要在下一节的旋钮里做取舍。

## 5. 调优旋钮全景:除了 batch 还能动什么

```
                 ┌── 量化 (msModelSlim: W8A8/W4A16)
   腾显存 ───────┤   权重变小 → KV Cache 可用显存↑ → batch↑
                 └── 减层/减 KV 头(GQA/MQA 已在模型侧)

                 ┌── Block Size:大块省管理开销/碎片多;小块利用率高
   切分粒度 ─────┤
                 └── Total Block Num:由 KV 显存预算决定

                 ┌── 张量并行 TP:大模型切到多卡,单卡省显存(走 HCCL)
   并行策略 ─────┤
                 └── 数据/流水并行:扩并发/扩模型

                 ┌── Continuous Batching:动态拼批,空位即填,提利用率
   调度 ─────────┤
                 └── Prefill/Decode 分离调度:避免长 prompt 阻塞 decode

                 ┌── 图模式/算子融合(MindIE-RT):减少下发与访存
   编译/算子 ────┤
                 └── 算子亲和(达芬奇 Cube/Vector 利用率)
```

- **量化(msModelSlim)**:对标 GPTQ/AWQ。把权重从 FP16 压到 INT8/INT4,既减权重显存(腾给 KV Cache → 更大 batch),又减访存(decode 提速)。是性价比最高的旋钮。
- **张量并行(TP)**:对标 Megatron/TRT-LLM 的 TP。多卡分摊权重与 KV,跨卡靠 **HCCL**(对标 NCCL)做 AllReduce,通信开销随 TP 度上升,需权衡。
- **Continuous Batching(连续批处理)**:对标 vLLM 的核心调度。请求一结束就把它的 Block 回收、立刻填入排队请求,显著提升 NPU 利用率。
- **图模式 / 算子融合(MindIE-RT)**:对标 TensorRT-LLM 的图编译。把多个小算子融合下发,减少 Host-Device 交互与中间访存,降低 TPOT。

## 6. 迁移要点 / 注意事项与坑

从 vLLM / TensorRT-LLM 迁到 MindIE,机制层面要心里有数:

1. **显存预算逻辑相通,参数名不同**:vLLM 的 `gpu_memory_utilization` / `block_size` / `max_num_seqs` 在 MindIE 里有对应概念(KV Cache 占比、Block Size、最大 batch),**但配置项名称与默认值以官方文档为准**,别照抄 vLLM 的字段名。
2. **先 Profile 再调,别凭感觉**:用 msProf / MindStudio Insight 看到底是 Prefill 算力受限、Decode 访存受限,还是多卡 HCCL 通信受限。三种瓶颈的解法完全不同(分别对应:提并行/量化提带宽/降 TP 度或优化通信)。
3. **算子未融合/未下沉是常见性能坑**:若发现 NPU 利用率低、Host 侧忙,多半是图模式没开或算子走了低效路径,要回到 MindIE-RT / CANN 层排查算子亲和性。
4. **长序列 KV 爆显存**:输入/输出一长,Block Num 需求陡增,batch 必须降。务必按业务真实长度分布(而非极端值)规划 Total Block Num,避免按最坏情况预留导致利用率极低。
5. **batch 越大≠延迟越好**:大 batch 提吞吐但抬高 TTFT/TPOT,在线服务有 SLO 时要卡上限,而非一味求大。
6. **达芬奇是 Cube 友好架构**:矩阵密集型(GEMM)算子在 Cube 上效率高;大量逐元素/小算子会落到 Vector 单元,容易成为瓶颈——这与 GPU 上"避免 kernel 启动开销、多做大 GEMM"的直觉一致。
7. **精确数字必须实测**:本节所有"约""量级"都需在你自己的 NPU 型号、CANN/MindIE 版本、模型与序列配置下实测复核。**具体命令、配置字段与版本以华为昇腾官方文档(Ascend 社区)为准。**

## 常见问题

| 问题 | 简答 |
|------|------|
| 调优最该先动哪个旋钮? | 先量化权重腾显存,再把腾出的显存给 KV Cache 以放大 batch,通常 ROI 最高。 |
| Total Block Num 怎么来的? | ≈ 分配给 KV Cache 的显存 ÷ 单个 Block 字节数;显存越多块越多。 |
| batch_size 怎么估? | ≈ Total Block Num ÷ 每请求所需 Block 数(输入块 + 输出块,均向上取整)。 |
| TTFT 高怎么办? | Prefill 算力受限:提并行度、开图模式/算子融合、控制 prompt 长度。 |
| TPOT 高怎么办? | Decode 访存受限:量化降权重访存、提高有效 batch 利用率、检查 KV 读路径。 |
| 多卡反而更慢? | 可能 TP 度过高,HCCL 通信开销吃掉收益;profile 通信占比后下调 TP 度。 |
| 这些值能直接抄到我环境吗? | 不能。型号/版本/模型/序列长度都会变,务必以官方文档为准并实测。 |
| MindIE 对标谁? | 推理引擎层面对标 TensorRT-LLM(图编译)与 vLLM(PagedAttention+连续批)。 |
