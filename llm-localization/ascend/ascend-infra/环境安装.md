## 0. 一句话锚点

昇腾环境安装的本质是**自底向上、逐层对齐版本**：先让操作系统认识 NPU 硬件(驱动+固件)，再装计算底座 CANN(对标 CUDA Toolkit)，然后装深度学习框架(MindSpore 原生 / PyTorch+torch_npu 适配)，最后按需叠加训练/推理套件(MindFormers、MindIE 等)。**任何一层版本不匹配，上层都会在导入或算子下发时报错。**

---

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

环境安装不是装"一个包"，而是把一条**纵向软件栈**按依赖顺序铺好。先看这条栈和英伟达世界的对照，建立迁移心智图：

| 层次 | 昇腾(Ascend) | 英伟达(NVIDIA) | 作用 |
|------|--------------|----------------|------|
| 硬件 | NPU(Atlas 训练/推理卡) | GPU | 算力载体 |
| 内核驱动 | Ascend Driver(`npu-smi` 来自这里) | NVIDIA Driver(`nvidia-smi`) | OS 识别并管理设备 |
| 固件 | Firmware | VBIOS / GSP 固件 | 设备底层微码 |
| 计算底座 | **CANN**(Toolkit + 算子库 + Runtime + ACL) | **CUDA Toolkit**(nvcc + cuDNN/cuBLAS + Runtime) | 编译/算子/内存/流管理 |
| 集合通信 | HCCL | NCCL | 多卡多机 AllReduce 等 |
| 框架 | MindSpore(原生) / PyTorch + **torch_npu** | PyTorch / TensorFlow | 自动微分、图执行 |
| 训练套件 | MindFormers / ModelLink | Megatron-LM / HF Transformers | 大模型并行训练 |
| 推理引擎 | MindIE | TensorRT-LLM / vLLM | 推理加速与服务化 |
| 量化工具 | msModelSlim | GPTQ / AWQ 工具链 | 权重压缩 |

**记忆锚点**：装昇腾环境 ≈ 在 GPU 机器上依次装"NVIDIA 驱动 → CUDA Toolkit → cuDNN → PyTorch → Megatron"，只是把每一层换成昇腾对应物。**最大差异**在于：昇腾把"Toolkit + 算子库 + Runtime + 通信库的一部分"打包进 **CANN** 这一个大组件里，所以"装 CUDA + cuDNN + NCCL"在昇腾世界基本对应"装 CANN"这一步。

> 📌 定位：环境安装层位于"硬件 → 框架"之间，是**所有上层套件(MindFormers/MindIE/msModelSlim)的公共前置**。装错这里，后面所有教程都跑不起来。

## 2. 软件栈分层与依赖关系

```
            ┌─────────────────────────────────────────────┐
   套件层    │ MindFormers │ ModelLink │ MindIE │ msModelSlim │  ← 按需安装
            └───────┬──────────┬──────────┬─────────┬───────┘
                    │          │          │         │
            ┌───────┴──────────┴──────────┴─────────┴───────┐
   框架层    │   MindSpore (原生)   或   PyTorch + torch_npu  │
            └───────────────────────┬───────────────────────┘
                                    │ 依赖 CANN 提供算子/Runtime
            ┌───────────────────────┴───────────────────────┐
   底座层    │      CANN  (Toolkit + 算子包 + Runtime + ACL)  │
            │      内含/对接 HCCL 集合通信                    │
            └───────────────────────┬───────────────────────┘
                                    │ 依赖驱动暴露的设备接口
            ┌───────────────────────┴───────────────────────┐
   驱动层    │        Ascend Driver + Firmware (固件)         │
            └───────────────────────┬───────────────────────┘
                                    │
   硬件层    │              NPU (Atlas 卡)                    │
            └───────────────────────────────────────────────┘

   安装方向 = 自底向上 ↑          报错方向 = 版本不匹配从下往上传染
```

**依赖关系三句话**：
1. **驱动/固件**必须先装，且要和**硬件型号**匹配；装完 `npu-smi` 能看到卡才算成功。
2. **CANN** 依赖驱动版本，且**框架/套件会要求特定 CANN 版本区间**——这是踩坑重灾区。
3. **框架与套件**反过来锁 CANN：先确定你要跑的套件(如某版本 MindFormers)，再倒推它要求的 CANN 与框架版本，**从顶层需求倒推、从底层依次安装**。

## 3. 标准安装流程(7 步的含义)

下面只讲**每一步"为什么要做、做错会怎样"**，具体命令/包名/版本以官方文档为准。

**第 1 步:确认硬件与 OS 兼容性。**
先查官方"版本配套表"：你的 NPU 型号、操作系统发行版与内核、架构(多为 aarch64，也有 x86)是否在支持列表内。*坑*：内核版本不在支持范围，驱动编译/加载会失败。

**第 2 步:安装系统依赖与 Python。**
昇腾工具链对 Python 版本有要求(常见为某个 3.x 区间)。需要从源码或包管理装好对应 Python，并装齐编译依赖(如 openssl、gcc、make 等)。源码编译 Python 时通常要带 `--enable-shared` 与 `-fPIC`，因为上层框架要以**共享库**方式链接它；漏了会在 import 时报找不到 `libpythonX.so`。*坑*：系统里有多个 Python，需用 `PATH`/`LD_LIBRARY_PATH` 明确指向目标版本(见下方占位示例)。

**第 3 步:安装驱动与固件。**
让操作系统识别并管理 NPU。一般需要专门的运行用户/用户组，并在装完后**重启或重新加载驱动**。*坑*：固件与驱动有先后与配套关系；安装顺序、用户组权限错了，`npu-smi info` 看不到设备。

**第 4 步:安装 CANN。**
计算底座，至少包含 **Toolkit**(开发/编译)与**算子包**(kernels/nnal 等运行时算子)。装完要 `source` 官方提供的环境变量脚本(设置 `ASCEND_HOME`、库路径、`PATH` 等)，**否则框架找不到 CANN**。*坑*：忘记 source set_env、或在新终端/容器里没重新 source，是最高频的"导入 torch_npu 即崩"原因。

**第 5 步:安装深度学习框架。**
两条路线：(a) **MindSpore 原生**——和 CANN 配套最紧；(b) **PyTorch + torch_npu**——装与 CANN/框架配套的 torch 版本，再装同版本号的 `torch_npu` 适配插件(见第 5 节)。*坑*：torch 与 torch_npu **大版本必须一一对应**。

**第 6 步:按需安装上层套件。**
训练选 MindFormers / ModelLink，推理选 MindIE，量化选 msModelSlim。这些套件对 CANN/框架版本**反向锁定**，安装前先看它们各自的版本配套表。

**第 7 步:验证。**
跑 `npu-smi`、官方自检/样例，确认从驱动到框架整条链路通(见第 7 节)。

> 第 2 步中"指定 Python 版本"的占位示例(**版本号/路径以官方为准**)：
> ```
> # 设置共享库与可执行文件搜索路径，确保使用目标 Python
> export LD_LIBRARY_PATH=/usr/local/python<版本>/lib:$LD_LIBRARY_PATH
> export PATH=/usr/local/python<版本>/bin:$PATH
> python3 --version   # 应输出你期望的版本
> ```

## 4. 容器化部署:为什么生产环境都用镜像

裸机逐层装版本极易踩坑，所以**生产与教程几乎都走容器**。昇腾提供 **Ascend Docker Runtime(Ascend-Docker-Runtime / 早期称 ascend-docker)**，作用对标英伟达的 **NVIDIA Container Toolkit**：

| 容器要素 | 昇腾 | 英伟达 |
|----------|------|--------|
| 容器运行时插件 | Ascend Docker Runtime | NVIDIA Container Toolkit(nvidia-runtime) |
| 设备透传机制 | 把 `/dev/davinciX`、驱动库挂进容器 | 把 GPU 设备 + 驱动挂进容器 |
| 官方基础镜像 | Ascend 官方 CANN/框架镜像 | nvidia/cuda、pytorch/pytorch |

**为什么用容器**：镜像里已经装好配套版本的 CANN + 框架，**驱动留在宿主机**、由 runtime 透传进容器。这样既避免逐层装版本，又能一机多环境并存。

```
   宿主机:  Ascend Driver + Firmware  (只装这一层!)
                    │  Ascend Docker Runtime 透传 /dev/davinci* + 驱动库
                    ▼
   容器内:  [ CANN + 框架 + 套件 ]  ← 来自官方镜像，版本已配套
```

*坑*：**驱动必须装在宿主机、不要装进容器**；容器内 CANN 版本要与宿主机驱动兼容；启动容器时若没用 Ascend runtime 或没透传设备，容器里 `npu-smi` 看不到卡。

## 5. Python 与 PyTorch 适配层(torch_npu)

PyTorch 路线的关键是**插件式适配**，而非改 PyTorch 源码：

```
   你的代码:  import torch
              import torch_npu           # 引入后，"npu" 成为合法 device
              x = x.to("npu")            # 等价于 GPU 世界的 .to("cuda")

   torch_npu:  把 torch 的算子分发 (dispatch) 接到 CANN 的算子上
   CANN:       真正在 NPU 上执行
```

**心智对照**：`"cuda"` → `"npu"`，`torch.cuda.*` → `torch.npu.*`(或经 torch_npu 提供)，NCCL backend → HCCL backend。
*坑*：(1) torch 与 torch_npu 版本必须严格配套；(2) 代码里要 `import torch_npu` 才会注册 npu 后端；(3) 分布式训练把通信后端从 `nccl` 换成 `hccl`。

## 6. 迁移要点与常见坑

**从 CUDA 迁到昇腾，安装环节要改什么:**
- "装 CUDA + cuDNN + NCCL" → 合并为"装 **CANN**(+ 其内含/配套的 HCCL)"。
- "装 PyTorch" → "装配套 PyTorch + **torch_npu** 插件"。
- `nvidia-smi` → `npu-smi info`；`nvidia-runtime` → **Ascend Docker Runtime**。

**高频坑清单:**

| 坑 | 现象 | 根因/对策 |
|----|------|-----------|
| 没 source 环境变量 | import torch_npu 报错、找不到 so | 每个新 shell/容器都要 source CANN 的 set_env 脚本 |
| 版本不配套 | 算子下发失败、莫名 segfault | 严格按官方"版本配套表"对齐 驱动↔CANN↔框架↔套件 |
| 驱动装进容器 | 容器看不到卡或冲突 | 驱动只装宿主机，容器靠 runtime 透传 |
| Python 非共享库编译 | 找不到 libpython.so | 源码编译加 `--enable-shared -fPIC` |
| 多 Python 版本混淆 | 用错解释器 | 用 PATH/LD_LIBRARY_PATH 明确指向目标版本 |
| 权限/用户组缺失 | npu-smi 无权访问设备 | 用户加入驱动安装时指定的运行用户组 |
| 通信后端没改 | 分布式 hang/报错 | 把 nccl 后端换成 hccl |
| aarch64 误用 x86 包 | 安装即失败 | 按机器架构选对应安装包 |

**性能/调优(机制层面)**：安装阶段就要选**与硬件代际匹配的算子包(nnal/kernels)**，否则上层套件即使能跑也可能走不到最优融合算子；图模式(静态图)相关优化也依赖 CANN 版本，版本太旧拿不到新融合 Pass。

## 7. 验证安装是否成功

按"自底向上"逐层验证，能快速定位是哪一层没装对：

```
   1) npu-smi info            → 看得到卡 = 驱动/固件 OK
   2) source set_env 后       → 环境变量指向 CANN = 底座 OK
   3) python -c "import torch_npu" 不报错 → 框架适配 OK
   4) 跑官方样例/自检脚本      → 端到端算子下发 OK
   5) 多卡:跑 HCCL allreduce 样例 → 通信 OK
```

任一步失败，就停在那一层排查，**不要跳着装**。

## 常见问题

| 问题 | 回答 |
|------|------|
| 装环境从哪一层开始? | 自底向上:驱动固件 → CANN → 框架 → 套件;但版本要从顶层套件需求**倒推**。 |
| CANN 对标英伟达的什么? | 约等于 CUDA Toolkit + cuDNN/cuBLAS + NCCL 的一部分,打包成一个组件。 |
| 一定要装 MindSpore 吗? | 不一定。可走 PyTorch + torch_npu 路线;MindSpore 是与 CANN 配套最紧的原生框架。 |
| 为什么总报"找不到 so"? | 99% 是没 source CANN 环境变量,或 Python 未以共享库编译。 |
| 生产怎么部署最省心? | 用官方容器镜像 + Ascend Docker Runtime,驱动留宿主机。 |
| `npu-smi` 看不到卡? | 驱动/固件没装好、用户没在运行用户组、或容器没透传设备。 |
| 命令和版本号去哪查? | 一律以华为昇腾社区(Ascend)官方文档与"版本配套表"为准。 |
