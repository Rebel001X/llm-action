## 0. 一句话锚点

**达芬奇架构是昇腾 AI 处理器里一颗 AI Core 的微架构设计。** 它不是一块完整的芯片,而是芯片里反复堆叠的"计算心脏"。一颗昇腾 NPU(如训练卡)= 多个 AI Core + 片上存储 + 互联 + CPU。每个 AI Core 内部用三种异构计算单元分工:

- **Cube(立方体)单元**:专吃矩阵乘(MatMul / 卷积),对标英伟达的 **Tensor Core**;
- **Vector(向量)单元**:做逐元素的激活、归一化、加减乘除,对标 GPU 的 **CUDA Core / SIMD 通路**;
- **Scalar(标量)单元**:做循环控制、地址计算、标量运算,相当于一个轻量级控制 CPU。

记住一句话:**达芬奇 = "Cube 算大矩阵 + Vector 算逐元素 + Scalar 管控制",三者异步流水协同。** 这就是为什么它对 Transformer 这种"巨型矩阵乘 + 少量逐元素"的负载特别友好。

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

### 1.1 达芬奇在昇腾软件栈的哪一层

昇腾的软件栈自底向上分四层,达芬奇架构处在最底的**硬件层**,是 CANN 之下的物理执行体:

```
┌─────────────────────────────────────────────┐
│  套件层  MindFormers / MindIE / ModelLink ... │  训练/推理上层
├─────────────────────────────────────────────┤
│  框架层  MindSpore / PyTorch(torch_npu)      │  动态图/静态图
├─────────────────────────────────────────────┤
│  异构计算架构 CANN(算子库+图引擎+Runtime+驱动) │  ≈ CUDA 全家桶
├─────────────────────────────────────────────┤
│  硬件层  昇腾 NPU = 多个【达芬奇 AI Core】     │  ← 本文主角
└─────────────────────────────────────────────┘
```

- **CANN** 把上层算子编译/调度到一个个 AI Core 上执行;
- **达芬奇** 决定了"一条指令一次能算多大的矩阵块"——这是硬件的物理上限,框架再优化也跳不出它。

### 1.2 昇腾 ↔ 英伟达 生态对照表(迁移心智图)

| 维度 | 昇腾(Ascend) | 英伟达(NVIDIA) | 备注 |
|------|--------------|----------------|------|
| 加速器 | NPU(昇腾处理器) | GPU | 达芬奇 vs SM 微架构 |
| 矩阵乘单元 | **Cube 单元** | **Tensor Core** | 都是脉动/分形矩阵乘 |
| 向量/通用计算 | **Vector 单元** | CUDA Core(SIMT 通路) | 逐元素运算 |
| 控制 | Scalar 单元 | Warp 调度器 + 标量通路 | — |
| 软件平台 | **CANN** | **CUDA** | 异构计算基座 |
| 算子库 | CANN 算子库 / AOL | **cuDNN / cuBLAS** | 高性能算子 |
| 自定义算子语言 | **Ascend C** | **CUDA C++** | kernel 编程 |
| 集合通信 | **HCCL** | **NCCL** | AllReduce 等 |
| 互联 | **HCCS** | **NVLink** | 卡间高速总线 |
| 深度学习框架 | **MindSpore** / torch_npu | PyTorch | MindSpore 原生支持 |
| 训练套件 | **MindFormers / ModelLink** | Megatron-LM / HF | 大模型并行训练 |
| 推理引擎 | **MindIE** | TensorRT-LLM / vLLM | LLM 推理 |
| 量化工具 | **msModelSlim** | GPTQ / AWQ 工具链 | 权重/激活量化 |
| 编程模型 | AI Core + 异步流水 | SM + Warp/SIMT | 范式不同(见迁移节) |

> 一句话迁移口诀:**"GPU 换 NPU,CUDA 换 CANN,Tensor Core 换 Cube,NCCL 换 HCCL,Megatron 换 ModelLink/MindFormers,TensorRT-LLM 换 MindIE。"**

## 2. AI Core 内部:三大计算单元

一个达芬奇 AI Core 可以看成一个"小型异构 SoC",内部三类计算单元各管一摊:

```
                ┌──────────── AI Core(达芬奇)────────────┐
                │                                          │
   指令/标量 →  │  ┌────────┐   控制循环、地址、标量运算    │
                │  │ Scalar │                              │
                │  └────────┘                              │
                │  ┌────────┐   矩阵乘 / 卷积(吞吐主力)   │
   大块权重 →   │  │  Cube  │   16×16×16 分形 MAC 阵列     │
                │  └────────┘                              │
                │  ┌────────┐   激活/归一化/逐元素运算      │
   特征图 →     │  │ Vector │   SIMD 向量通路              │
                │  └────────┘                              │
                │      ↑ 数据由 MTE 搬运单元在各级 Buffer 间流动 │
                └──────────────────────────────────────────┘
```

- **Cube 单元**:面向 MatMul / Conv,是算力(TFLOPS)的主要来源。Transformer 的 QKV 投影、FFN、注意力打分本质都是大矩阵乘,几乎全跑在 Cube 上。
- **Vector 单元**:面向 Softmax、LayerNorm/RMSNorm、GELU、Add、Mul、量化反量化等逐元素操作。它吞吐远低于 Cube,所以**逐元素算子常常是性能瓶颈**(类比 GPU 上的 memory-bound 算子)。
- **Scalar 单元**:负责标量计算、地址生成、循环与分支控制,相当于"指挥",自身不贡献大算力。

**关键认知**:达芬奇是"Cube 强、Vector 弱"的不对称架构。这与 GPU 的 SIMT(所有线程跑同一种通用核)范式不同,要求算子开发时显式地把工作划分给不同单元。

## 3. 存储层次与数据流

达芬奇是典型的"分级 Buffer + 显式搬运"设计,数据要靠 **MTE(Memory Transfer Engine,搬运单元)** 在各级缓冲间流动,而不是像 GPU 那样靠庞大的 L1/L2 cache 自动命中:

```
  片外 HBM(GB 级,慢)
        │  MTE 搬运
        ▼
  L1 Buffer(片上,KB~MB,放权重/特征)
        │
        ▼
  L0 Buffer(紧贴 Cube:L0A 左矩阵 / L0B 右矩阵 / L0C 结果累加)
        │
        ▼
  Unified Buffer(UB,Vector 单元的工作区)
```

- **数据搬运是显式的、需要编排的**:开发者(或编译器)要安排"先把哪块权重从 HBM 搬到 L1,再搬到 L0A/L0B"。这与 CUDA 里手动管理 shared memory 类似,但层级更多、更需要"双缓冲(ping-pong)"来隐藏搬运延迟。
- **Buffer 容量有限**:大矩阵必须**切块(tiling)** 后分批送入 Cube。Tiling 策略直接决定性能——切得太大放不下,切得太小搬运开销吃掉收益。这是昇腾算子调优的核心战场。

## 4. Cube 单元:矩阵乘怎么算

Cube 单元一次能完成一个固定形状的小矩阵乘,典型为 **16×16×16**(即 16×16 与 16×16 相乘累加),通过 MAC(乘加)阵列在一个节拍批量完成,类似脉动阵列:

```
   左矩阵 A(16×16)        右矩阵 B(16×16)
        │                       │
        ▼                       ▼
   ┌──────────────────────────────┐
   │   16×16 MAC 乘加阵列          │  一拍完成大量乘加
   │   C += A × B  (累加进 L0C)   │
   └──────────────────────────────┘
        │
        ▼
   结果 C(16×16,累加在 L0C)
```

- 大矩阵乘 = 把 M×K×N 的大问题切成无数个 16×16×16 的"分形(fractal)"小块,逐块送入 Cube 并累加。这就是昇腾里 **NZ / 分形格式** 存在的原因(见第 6 节):数据要预先排成对 Cube 友好的形状。
- 这与 Tensor Core 处理 16×16 矩阵片(fragment)的思路一致,只是分块尺寸、累加路径、数据格式由达芬奇硬件固定。
- **对齐很关键**:当 M/K/N 不是 16 的整数倍时,硬件需要补零(padding),会浪费算力。所以模型里 **hidden_size、序列长度尽量对齐到 16/256** 能显著提升 Cube 利用率。

## 5. 指令流水与异步并行

达芬奇把 Scalar、Vector、Cube 以及 MTE 搬运做成**多条并行流水线**,通过队列异步发射、靠同步标志(类似事件/barrier)维持依赖:

```
时间 →
Scalar :  ─控制─控制─控制──────────────
MTE    :  ─搬A──搬B──搬下一块A──搬下一块B─   (与计算重叠)
Cube   :  ──────算块0──算块1──算块2────
Vector :  ───────────激活0──激活1───────
          └─ 理想情况下:搬运/Cube/Vector 时间互相隐藏 ─┘
```

- **性能的本质 = 让三条流水线"忙起来且互相重叠"**。如果 Vector 在等 Cube、Cube 在等 MTE 搬运,就出现"气泡(bubble)",利用率掉下来。
- 调优思路(机制层面):**双缓冲**让搬运与计算重叠;合理 **tiling** 让 L0/UB 不溢出;**算子融合**(把 MatMul + 激活 + 量化拼成一个 kernel)减少 UB↔HBM 往返。理念上类似 GPU 的 kernel fusion / overlap,但 Vector 单元更弱,融合收益往往更明显。

## 6. 数据格式:为什么有 NZ / 分形

为了喂饱 Cube 的 16×16 分块,昇腾在内存里采用对硬件友好的**专用排布格式**,而非框架默认的 NCHW / 行优先:

| 格式 | 含义 | 类比 |
|------|------|------|
| ND | 普通多维(行优先) | PyTorch 默认张量布局 |
| NZ(zN / 分形) | 按 16×16 小块重排,利于 Cube 读取 | GPU 上的 swizzle / 特殊 layout |
| NC1HWC0 | 5 维卷积布局,C 拆成 C1×C0(C0 常为 16) | NHWC 的对齐变体 |

- 框架张量进入 Cube 前,CANN 会插入 **TransData(格式转换)** 算子把 ND 转成 NZ。**多余的 TransData 是常见性能杀手**——profiling 里若看到大量 TransData,通常是算子衔接处布局不一致导致反复转换。
- 迁移时不必手写这些格式,但要理解:**昇腾对"形状对齐与布局"比 GPU 更敏感**,这是它换取高 Cube 利用率的代价。

## 迁移要点 / 注意事项与坑

从 CUDA/GPU 迁移到昇腾达芬奇,心智模型要做几处切换:

1. **编程范式:SIMT → 异构流水。** GPU 写一个通用 kernel 让上万线程跑;达芬奇要显式把矩阵乘交给 Cube、逐元素交给 Vector,并编排 Buffer 搬运。自定义算子用 **Ascend C**(对标 CUDA C++),但思路是"分单元 + tiling + 双缓冲",不是"开多少 block/thread"。
2. **优先用现成算子,别急着手写 kernel。** 绝大多数场景应直接用 CANN 算子库 / 框架(torch_npu、MindSpore)已优化好的算子,只在缺失或瓶颈处才用 Ascend C 自定义。这点和"先用 cuDNN/cuBLAS,再考虑手写 CUDA"一致。
3. **形状对齐坑。** hidden_size、num_heads、seq_len 尽量对齐 16(乃至 256)的倍数,否则 Cube padding 浪费算力。这是 GPU 上不那么敏感、但昇腾上很要命的一类坑。
4. **逐元素算子是瓶颈。** Vector 单元弱,Softmax/LayerNorm/激活/量化反量化容易拖后腿。优化方向是**算子融合**和减少 UB↔HBM 往返。
5. **小心 TransData。** 布局不一致会插入大量格式转换算子,用 profiling 工具定位并消除。
6. **精度与数据类型。** 不同昇腾型号支持的 FP16/BF16/INT8 等及其算力比例不同;混合精度、量化(配合 msModelSlim)要按目标硬件的支持矩阵来选。
7. **API/算子覆盖度。** PyTorch 模型经 torch_npu 迁移时,可能遇到个别算子未适配,需要回退或替换。迁移工具与适配清单**具体以华为昇腾官方文档(Ascend 社区)为准**。
8. **环境/驱动/CANN 版本。** 驱动、固件、CANN、框架插件(torch_npu / MindSpore)之间有严格的版本配套关系,装错会大面积报错。**具体命令与版本以华为昇腾官方文档(Ascend 社区)为准**,本文不给出任何具体版本号或安装命令——核心是理解"驱动↔CANN↔框架"必须版本配套这一依赖关系。

## 常见问题

| 问题 | 速答 |
|------|------|
| 达芬奇是一颗芯片吗? | 不是。它是 AI Core 的微架构;一颗 NPU 含多个 AI Core。 |
| Cube 对标谁? | 英伟达 Tensor Core,都是分块矩阵乘单元。 |
| 为什么逐元素算子慢? | Vector 单元吞吐远低于 Cube,易成瓶颈,需融合优化。 |
| 为什么要对齐 16? | Cube 以 16×16×16 分块计算,不对齐会 padding 浪费算力。 |
| NZ / 分形格式是什么? | 为喂饱 Cube 而做的内存重排;CANN 用 TransData 转换。 |
| Ascend C 对标什么? | CUDA C++,用于写自定义算子。 |
| 迁移先做什么? | 优先用现成算子库/框架适配,瓶颈处再手写 kernel。 |
| 命令/版本去哪查? | 一律以华为昇腾官方文档(Ascend 社区)为准。 |
