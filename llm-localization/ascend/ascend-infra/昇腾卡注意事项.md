## 0. 一句话锚点

**昇腾卡的"注意事项"九成集中在三个面:谁能看到卡(可见性/容器分卡)、卡之间怎么连(亲和性/HCCL)、软件版本是否配套(驱动/固件/CANN/框架)。** 把这三件事捋顺，剩下的训推问题大多是"算子是否支持 + 精度对齐"的常规活。本文按这条主线给出避坑清单，凡涉及确切命令/版本，一律以华为昇腾官方文档(Ascend 社区)为准。

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

昇腾软件栈自底向上分四层，"卡注意事项"贯穿每一层:

```
  应用层    训练/推理脚本、模型权重
  ────────────────────────────────────
  套件层    MindFormers / MindIE / ModelLink / msmodelslim
  ────────────────────────────────────
  框架层    MindSpore / PyTorch(+ torch_npu 适配插件)
  ────────────────────────────────────
  CANN层    AscendCL、图引擎(GE)、算子库、HCCL、Runtime、Profiling
  ────────────────────────────────────
  驱动固件  Driver + Firmware(npu-smi、device 节点、容器 runtime)
  ────────────────────────────────────
  硬件层    Ascend NPU(达芬奇架构:Cube/Vector/Scalar 单元)
```

注意事项的"层归属":分卡/可见性属于**驱动+容器 runtime**层；亲和性/通信属于 **HCCL/CANN** 层；算子不支持/精度属于**框架+CANN 算子库**层；版本配套则是**跨层**的硬约束。

### 昇腾 ↔ 英伟达生态对照表(迁移心智图)

| 维度 | 昇腾(Ascend) | 英伟达(NVIDIA) | 备注 |
|------|------------|---------------|------|
| 加速卡 | NPU(Atlas 训练/推理卡) | GPU | 达芬奇架构 vs SIMT |
| 计算平台 | CANN | CUDA | 编程与运行时基座 |
| 设备管理命令 | npu-smi | nvidia-smi | 查卡/查显存/查健康 |
| 底层编程接口 | AscendCL(ACL) | CUDA Runtime/Driver API | C/C++ 接口 |
| 算子库 | CANN 算子库 / AOL | cuDNN / cuBLAS | 深度学习算子 |
| 集合通信 | HCCL | NCCL | AllReduce/AllGather 等 |
| 容器 runtime | Ascend Docker Runtime | nvidia-container-runtime | 注入 device 与库 |
| 进程可见卡 | ASCEND_RT_VISIBLE_DEVICES | CUDA_VISIBLE_DEVICES | 进程级筛卡 |
| 训练框架 | MindSpore / PyTorch+torch_npu | PyTorch / TensorFlow | torch_npu 是关键适配层 |
| 大模型训练套件 | MindFormers / ModelLink | Megatron-LM / HF | 并行训练 |
| 推理引擎 | MindIE | TensorRT-LLM / vLLM | 高性能推理 |
| 量化工具 | msModelSlim | GPTQ / AWQ 工具链 | 权重压缩 |
| 模型仓库 | ModelScope(魔搭) | Hugging Face Hub | 权重与示例 |

记住这张表，CUDA 世界的每一步几乎都能在昇腾找到对位组件——迁移本质是"换底座、保上层逻辑"。

## 2. 卡的识别与体检(对标 nvidia-smi)

上手第一件事是确认卡能被识别、状态健康。昇腾用 `npu-smi` 这个工具(角色等同 `nvidia-smi`)，关注几类信息:

- **卡是否被识别**:能列出全部物理卡及其芯片 ID。若数量不对，先排查驱动/固件是否正常加载。
- **健康与温度/功耗**:Health 字段、温度、功耗。异常卡应隔离，别拉进训练集群拖垮整轮 AllReduce。
- **显存占用(HBM)**:对标 GPU 显存。残留进程会"吃住"显存导致后续任务 OOM——这是高频坑。
- **算力利用率(AICore)**:对标 GPU-Util，用于判断是否真正跑满。

> 体检要点:训练前 `npu-smi` 看一眼有无"僵尸进程"占着 HBM；任务异常退出后务必确认显存已释放，否则下一次启动会莫名 OOM。具体子命令与字段以昇腾官方文档为准。

## 3. 容器分卡:可见性与 Docker Runtime(本仓核心关注点)

这是昇腾部署最容易踩的一块，对应原文件强调的两点。

### 3.1 两个可见性环境变量

| 变量 | 作用域 | 对标 CUDA | 说明 |
|------|-------|----------|------|
| `ASCEND_VISIBLE_DEVICES` | 容器级 | 容器分卡 | 由 Ascend Docker Runtime 解析，决定**注入容器**的卡 |
| `ASCEND_RT_VISIBLE_DEVICES` | 进程级 | `CUDA_VISIBLE_DEVICES` | 由运行时解析，决定**当前进程**能用哪些卡 |

理解二者的层级关系是关键:

```
  物理机 8 卡:  0  1  2  3  4  5  6  7
                 │
   ASCEND_VISIBLE_DEVICES=4,5,6,7   (容器级:Docker Runtime 只把 4~7 注入容器)
                 ▼
   容器内可见:  [4 5 6 7]  ── 在容器内被重新编号为逻辑 0 1 2 3
                 │
   ASCEND_RT_VISIBLE_DEVICES=0,1    (进程级:进程只用容器内逻辑 0、1)
                 ▼
   进程实际使用: 物理 4、5 两张卡
```

要点:
- **容器级先筛，进程级后筛**。容器只注入了 4~7，进程里写 `ASCEND_RT_VISIBLE_DEVICES=0,1` 指的是容器内逻辑卡(对应物理 4、5)，不是物理 0、1。逻辑/物理卡号混淆是排障时最常见的认知错误。
- `ASCEND_RT_VISIBLE_DEVICES` 用法上类比 `CUDA_VISIBLE_DEVICES`，但**名字、解析方不同**，迁移脚本时必须替换，不能照搬。

### 3.2 --privileged 特权模式默认抢全部卡

> **`--privileged` 特权模式下，昇腾(或英伟达)的 Docker Runtime 会默认把本机所有卡分配给容器。**

这意味着:

- 在共享机器上用 `--privileged` 起容器，会**无视可见性变量**把全部卡塞进容器，多个任务相互抢卡 / 抢显存。
- 生产/共享环境**避免裸用 `--privileged`**；应通过 Ascend Docker Runtime + 可见性变量做精细分卡，或挂载指定 device 节点。
- 容器内还需要 driver、CANN 等宿主库与 device 节点正确注入——这正是 Ascend Docker Runtime(对标 `nvidia-container-runtime`)的职责。具体镜像、挂载项与 runtime 配置以官方文档为准。

### 3.3 device 节点与依赖注入(机制)

容器要用上 NPU，本质要满足:device 字符设备节点可见、驱动用户态库可见、CANN 运行时可见。Ascend Docker Runtime 在容器启动时自动完成这些注入；手工 `docker run` 不走 runtime 时，则需显式挂载相应 device 与库目录(具体路径以官方文档为准，切勿照抄网上路径——不同驱动版本路径不同)。

## 4. 多卡亲和性与通信(HCCL)

多卡训练/推理时，卡之间怎么连决定通信效率。

```
   8 卡常见拓扑(示意):
     ┌─────┐   高速互联   ┌─────┐
     │NPU0 │═════════════│NPU1 │     同组内带宽高、延迟低
     │NPU2 │═════════════│NPU3 │
     └──┬──┘             └──┬──┘
        │  跨组互联(较慢)   │
     ┌──┴──┐             ┌──┴──┐
     │NPU4 │═════════════│NPU5 │
     │NPU6 │═════════════│NPU7 │
     └─────┘             └─────┘
```

- **HCCL 角色等同 NCCL**:做 AllReduce/AllGather/Broadcast 等集合通信，内部也用 Ring 等算法把通信带宽利用起来。
- **亲和性选卡**:选连续且同组的卡(如 0-1-2-3)比跨组散选通信更快。乱序分卡会让梯度同步走慢链路，拖累整体吞吐。
- **rank_table / 通信初始化**:多卡需要正确的设备-rank 映射。卡号映射写错会导致 HCCL 初始化卡死或超时——排障第一步是核对逻辑卡号与 rank 的对应。
- **慢卡/坏卡拖累**:集合通信是同步屏障，一张慢卡会卡住整轮。开训前用 `npu-smi` 体检剔除异常卡。

## 5. 驱动/固件/CANN/框架 版本配套(硬约束)

昇腾栈跨层版本耦合比 CUDA 世界更敏感，**版本不配套是新手最大的坑**:

```
   Firmware(固件) ─┐
   Driver(驱动)   ─┼─ 必须互相配套 ──┐
   CANN(工具包)   ─┘                ├─ 决定 torch_npu / MindSpore 可用版本
   torch_npu / MindSpore ───────────┘
   套件(MindFormers/MindIE/ModelLink) ── 又依赖特定框架版本
```

- 对标:类似 NVIDIA 中"Driver 版本 ↔ CUDA Toolkit ↔ 框架 cuda 编译版本"要匹配，但昇腾的配套表更长、更严。
- 升级任一层前**先查官方配套表**(具体版本组合以昇腾官方文档为准)。常见报错(算子加载失败、`import torch_npu` 报错、HCCL 不可用)很多源于版本错配。
- `torch_npu` 是 PyTorch 生态迁昇腾的关键适配插件:代码里通常 `import torch_npu`，把设备从 `cuda` 改为 `npu`。它的版本必须与 CANN、PyTorch 三者对齐。

## 6. 训推稳定性常见坑(机制层面)

- **显存(HBM)管理**:Atlas 卡单卡显存有限，注意 batch/序列长度。异常退出后 HBM 未释放需手工清理残留进程。
- **算子不支持 / 回退**:部分 PyTorch/自定义算子在 CANN 上无对应实现，会报"算子不支持"或走低效路径。迁移时优先用框架原生算子，自定义算子可能需 Ascend C 重写。
- **精度对齐**:NPU 默认偏好特定精度路径，AMP/混合精度行为可能与 GPU 有差异。迁移后务必做**精度对齐(loss/输出对比)**，别只看"能跑"。
- **图模式 vs 单算子模式**:昇腾支持图下沉执行(整图编译下发，吞吐高)与单算子(eager,易调试)。生产追吞吐用图模式，但首次图编译有耗时，且对动态 shape 敏感——动态 shape 频繁触发重编译是性能坑。
- **首 step 慢**:首个 step 含算子编译/图编译开销，benchmark 要跳过 warmup step，别把编译时间算进吞吐。

## 迁移要点(从 CUDA 到昇腾)

1. **设备字符串**:`cuda` → `npu`；`import torch_npu`。
2. **可见性变量**:`CUDA_VISIBLE_DEVICES` → `ASCEND_RT_VISIBLE_DEVICES`(进程级)，容器分卡另用 `ASCEND_VISIBLE_DEVICES`。
3. **通信后端**:NCCL → HCCL(分布式初始化 backend 改为 hccl)。
4. **设备查询**:`nvidia-smi` → `npu-smi`。
5. **算子审计**:跑一遍模型，收集"不支持算子"清单，逐个找替代或重写。
6. **精度回归**:与 GPU 基线对齐 loss/输出，确认无精度漂移。
7. **版本配套**:固件/驱动/CANN/torch_npu/套件按官方配套表锁定版本。

## 注意事项与坑(速查)

- 不要在共享机裸用 `--privileged`，会默认吃光全部卡。
- 区分容器级与进程级可见性，警惕逻辑/物理卡号混淆。
- 网上的 device/库路径和版本号别照抄，以你机器的驱动版本与官方文档为准。
- 训练前体检剔除异常卡，避免一张慢卡卡住整个 HCCL 同步。
- benchmark 跳过首 step(含图/算子编译)。

## 常见问题

| 问题 | 速答 |
|------|------|
| `ASCEND_VISIBLE_DEVICES` 和 `ASCEND_RT_VISIBLE_DEVICES` 区别? | 前者容器级(Docker Runtime 注入哪些卡)，后者进程级(进程用哪些卡，类比 `CUDA_VISIBLE_DEVICES`)。 |
| 为什么 `--privileged` 容器里看到全部卡? | 特权模式下 Docker Runtime 默认分配本机所有卡，绕过可见性变量。共享机应避免。 |
| 容器里设了 `ASCEND_RT_VISIBLE_DEVICES=0,1` 却没用到物理 0、1? | 进程看到的是容器内逻辑卡号，对应物理卡取决于容器级先筛了哪些卡。 |
| `npu-smi` 对应英伟达哪个工具? | `nvidia-smi`,查卡/显存/健康/利用率。 |
| HCCL 是什么? | 昇腾集合通信库,角色等同 NCCL。 |
| `import torch_npu` 报错怎么办? | 多为驱动/固件/CANN/torch_npu/PyTorch 版本不配套,查官方配套表。 |
| 算子不支持怎么办? | 优先换框架原生算子,必要时用 Ascend C 重写自定义算子。 |
| 任务退出后再启动就 OOM? | 上次进程未释放 HBM,`npu-smi` 查残留进程并清理。 |
| 迁移后精度不对? | NPU 精度路径/AMP 行为与 GPU 有别,需做精度对齐回归。 |

> 全文凡涉及确切命令、包名、版本号、设备路径与性能数字,均以华为昇腾官方文档(Ascend 社区)为准,切勿照抄。
