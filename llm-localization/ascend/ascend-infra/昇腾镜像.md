## 0. 一句话锚点

**昇腾镜像 = 把昇腾这套"非标准、强耦合"的软件栈(固件/驱动/CANN/框架/训练推理套件)冻结成一个镜像，消除"装环境装到崩溃"的痛点。** 它对标的不是某一个 CUDA 库，而是英伟达的 **NGC(NVIDIA GPU Cloud)镜像仓库 + nvidia-docker 整套容器化方案**。

一句话记忆：**GPU 世界 `docker pull nvcr.io/nvidia/pytorch` 的位置，昇腾世界就是 `docker pull ascendhub.huawei.com/...`。**

## 1. 地基：在昇腾栈的定位 + 对标英伟达生态

昇腾软件栈自下而上是一座"塔"，镜像的作用是把塔的上面几层装进盒子：

```
          昇腾软件栈                          镜像打包边界
  ┌─────────────────────────────┐
  │ 训练/推理套件                 │  MindFormers / MindIE / ModelLink   ┐
  │ ─────────────────────────── │                                      │
  │ AI 框架                      │  MindSpore / PyTorch(torch_npu)      ├─ 镜像内
  │ ─────────────────────────── │                                      │
  │ CANN(算子库+图引擎+ACL)      │  ≈ CUDA Toolkit + cuDNN + cuBLAS     ┘
  ├─────────────────────────────┤ ← ← ← 镜像与宿主的"分界线" ← ← ←
  │ Driver + Firmware(驱动固件) │  装在【宿主机】，不进镜像            ┐
  │ ─────────────────────────── │                                      ├─ 宿主机
  │ NPU 硬件(达芬奇 Cube/Vector) │  Atlas 800T A2 / 300I Duo ...        ┘
  └─────────────────────────────┘
```

**关键认知：驱动/固件装在宿主机，CANN 及以上才进镜像。** 这一点和英伟达完全一致——NVIDIA Driver 在宿主、CUDA Toolkit 在镜像。容器里的 CANN 版本必须 ≤ 宿主驱动支持的范围，否则跑不起来。

### 昇腾 ↔ 英伟达 生态对照表(迁移心智图)

| 维度 | 英伟达(CUDA 世界) | 昇腾(Ascend 世界) |
| --- | --- | --- |
| 加速硬件 | GPU(A100/H100) | NPU(Atlas 800T A2 / 300I Duo) |
| 底层计算软件栈 | CUDA Toolkit + cuDNN + cuBLAS | **CANN**(算子库 + 图引擎 + ACL) |
| 宿主侧驱动 | NVIDIA Driver | Ascend Driver + Firmware |
| 容器运行时 | nvidia-container-toolkit / nvidia-docker | **Ascend Docker Runtime**(ascend-docker-runtime) |
| 官方镜像仓库 | NGC(nvcr.io) | **AscendHub**(ascendhub.huawei.com) |
| 训练框架 | PyTorch / Megatron | MindSpore / **torch_npu**(PyTorch 适配) |
| 大模型训练套件 | Megatron-LM / NeMo | **MindFormers** / **ModelLink** |
| 推理引擎 | TensorRT-LLM / vLLM | **MindIE** |
| 量化工具 | GPTQ / AWQ / TensorRT-PTQ | **msModelSlim** |
| 集合通信库 | NCCL | **HCCL** |
| 设备查看命令 | `nvidia-smi` | `npu-smi` |

> 一句话："**装 CUDA = 装 CANN，nvidia-docker = Ascend Docker Runtime，nvcr.io = AscendHub**"，其余框架/套件按上表逐一对号入座。

## 2. 镜像分层：里面到底装了什么

一个典型的昇腾框架镜像，从底到顶大致是这几层(理解层次即可，具体内容以官方镜像说明为准)：

```
  ┌────────────────────────────────────────────┐
  │  Layer 5  训练/推理套件(MindFormers/MindIE) │  按镜像用途选装
  ├────────────────────────────────────────────┤
  │  Layer 4  AI 框架(MindSpore 或 torch_npu)   │  框架 + Python 依赖
  ├────────────────────────────────────────────┤
  │  Layer 3  CANN(toolkit + kernels + nnal)    │  核心：算子库/图引擎/ACL
  ├────────────────────────────────────────────┤
  │  Layer 2  Python + 系统工具链(gcc/cmake...) │  euler/ubuntu + py3.x
  ├────────────────────────────────────────────┤
  │  Layer 1  基础 OS(EulerOS/Ubuntu, arm64)    │  注意架构！多为 ARM64
  └────────────────────────────────────────────┘
            ↑ 不含 Driver/Firmware(由宿主提供)
```

**三个最容易忽略的点：**

1. **CPU 架构基本是 ARM64(aarch64)。** 昇腾服务器(如 Atlas 800T A2)的鲲鹏 CPU 是 ARM 架构，所以镜像几乎都是 `arm64`。这正是为什么本目录里的 `docker pull` 都带 `--platform=arm64`——在 x86 机器上拉/构建时不指定，会拉错架构或构建失败。
2. **CANN 是镜像的"心脏"。** 它对标的是 CUDA Toolkit + cuDNN + cuBLAS 三者合一：既有算子库(kernels)，又有图编译引擎(GE),还有 ACL(Ascend Computing Language，应用层 API)。
3. **kernels 包与芯片型号绑定。** CANN 的算子二进制包(kernels)是按芯片(910A/910B/310P 等)区分的，镜像里装的 kernels 必须匹配你机器的 NPU 型号(见 §7 坑)。

### 怎么读一个镜像标签

以本目录记录的标签为例(仅用于"读懂结构"，不代表当前可用版本)：

```
swr.cn-central-221.ovaijisuan.com / dxy / pytorch2_1_0_kernels : PyTorch2.1.0-cann7.0.0.alpha003_py_3.9-euler_2.8.3-64GB
└────────── 仓库地址 ──────────┘  └组织┘ └─── 镜像名 ───┘  └────────────── tag：框架/CANN/Python/OS/内存规格 ──────────────┘
```

tag 里几乎把"四件套版本"全写进去了：**框架版本 + CANN 版本 + Python 版本 + 基础 OS + (有时)内存规格**。读 tag 时一定核对：**CANN 版本是否匹配宿主驱动、芯片型号(A1=910A / A2=910B)是否对得上。**

另一类 MindSpore 官方镜像的 tag 会标芯片代际：

```
ascend-mindspore : 23.0.0 - A1 - ubuntu18.04
                   └版本┘  └芯片┘ └─ OS ─┘
   A1 → 适配 910A 系列(A300T-9000 / A800-9000 / Atlas 300T Pro 等)
   A2 → 适配 910B 系列(Atlas 900 A2 PoD / Atlas 800T A2 / 200T A2 Box16 / 300T A2 等)
```

> 上面出现的 `docker pull --platform=arm64 ...` 示例展示的是"命令形态"，**实际可用的仓库地址、镜像名与 tag 请以 AscendHub / 昇腾官方文档为准**(版本迭代很快，alpha 版本尤其会过期)。

## 4. 机制：容器是怎么"看见"NPU 的

GPU 容器靠 `nvidia-container-toolkit` 把 GPU 设备注入容器；昇腾靠 **Ascend Docker Runtime**(ascend-docker-runtime)做同样的事。原理对照：

```
     宿主机                                  容器内
  ┌──────────────────┐                  ┌──────────────────┐
  │ Driver/Firmware  │                  │  CANN + 框架      │
  │ /dev/davinciX    │── 设备挂载 ──────▶│ 看到 /dev/davinciX│
  │ /dev/davinci_mgr │   (runtime 注入) │ npu-smi 可用      │
  │ /usr/local/Ascend│── 驱动目录映射 ──▶│ 调用宿主驱动      │
  │   /driver        │                  │                  │
  └──────────────────┘                  └──────────────────┘
        ↑ Ascend Docker Runtime 在 docker run 时自动完成上述注入
```

两条路线(理解机制即可，命令以官方文档为准)：

- **自动方式：** 安装 Ascend Docker Runtime 后，`docker run` 时由 runtime 自动把 `/dev/davinci*` 设备节点、驱动目录(如 `/usr/local/Ascend/driver`)挂进容器。这相当于 GPU 世界的 `--gpus all`。
- **手动方式：** 不装 runtime 时，需要在 `docker run` 里手动 `--device` 挂 `/dev/davinciX`、`/dev/davinci_manager`、`/dev/devmm_svm`、`/dev/hisi_hdc` 等设备，并 `-v` 映射驱动目录和 `npu-smi` 工具。这种方式繁琐易错，**生产环境推荐用 Ascend Docker Runtime。**

> 核心区别记忆点：**容器里不装驱动，只装 CANN；驱动通过设备节点 + 目录映射从宿主"借"进来。** 所以镜像可以跨机器复用，只要宿主驱动版本与镜像内 CANN 兼容。

## 5. 迁移要点：从英伟达镜像搬到昇腾

| 你在 GPU 上的做法 | 昇腾上的对应改法 |
| --- | --- |
| `docker pull nvcr.io/nvidia/pytorch:xx` | 从 AscendHub / 算力云镜像站拉 torch_npu 或 MindSpore 镜像 |
| `docker run --gpus all ...` | 装 Ascend Docker Runtime，或手动 `--device /dev/davinci*` |
| `nvidia-smi` 查卡 | `npu-smi info` 查卡 |
| `import torch; torch.cuda.is_available()` | `import torch, torch_npu; torch.npu.is_available()` |
| `.to("cuda")` / `device="cuda"` | `.to("npu")` / `device="npu"` |
| NCCL 后端 `init_process_group("nccl")` | HCCL 后端 `init_process_group("hccl")` |
| 不关心 CPU 架构(多为 x86) | **必须 `--platform=arm64`**，镜像基本是 ARM64 |
| CUDA Toolkit 在镜像里 | CANN 在镜像里，但版本要匹配宿主驱动 |

**最容易被低估的三件事：**

1. **ARM64 架构。** 在 x86 开发机上拉/构建昇腾镜像必须显式 `--platform=arm64`，否则要么拉错、要么需要 QEMU 模拟构建(慢)。
2. **CANN ↔ 驱动版本配套。** 镜像内 CANN 与宿主 Driver/Firmware 有严格配套关系(类似 CUDA Toolkit 与 NVIDIA Driver 的最低版本要求)。版本错配是第一大坑。
3. **代码层面 torch_npu。** PyTorch 用户要 `import torch_npu` 才能把后端切到 NPU；很多算子/API 行为与 CUDA 不完全等价，迁移时需配合昇腾的算子映射与替换。

## 6. 自己构建/裁剪镜像的思路

不必从零写 Dockerfile——优先在官方基础镜像上叠层：

```
  FROM  <AscendHub 官方 CANN 基础镜像 : 匹配你的芯片/驱动>
        │
        ├─ 装框架(torch_npu 或 MindSpore)与匹配的 CANN nnal 包
        ├─ 装套件(MindFormers / MindIE / msModelSlim 按需)
        ├─ pip 装业务依赖(注意 ARM64 轮子可用性)
        └─ 拷贝模型权重 / 代码 / 启动脚本
```

注意点(机制层面，不写具体命令)：

- **基础镜像选型先定芯片与驱动**：先确定机器是 910A(A1) 还是 910B(A2)、宿主驱动版本，再反推可用的 CANN 版本，再选基础镜像。顺序错了会反复重做。
- **ARM64 依赖坑**：很多 pip 包在 ARM64 上没有预编译 wheel，需要源码编译，构建时间长；提前确认依赖在 aarch64 上的可用性。
- **kernels 包对齐芯片**：若基础镜像未含或含错芯片的算子包，需补装匹配型号的 kernels。
- **镜像很大**：CANN + 框架 + 套件动辄数 GB~数十 GB，注意分层缓存与构建机磁盘。
- **不要把驱动打进镜像**：驱动属于宿主，打进镜像反而会冲突。

> 上述每一步的精确命令、包名、版本号一律**以华为昇腾官方文档(Ascend 社区)与对应镜像的说明页为准**。

## 7. 注意事项与常见坑

```
  坑速查
  ─────────────────────────────────────────────────
  ① 没加 --platform=arm64        → x86 上拉错架构/构建失败
  ② CANN 版本 > 宿主驱动支持      → 容器起来但 NPU 不可用
  ③ A1 镜像跑在 A2 机器(或反之)  → 芯片代际不匹配，算子报错
  ④ 没装 Ascend Docker Runtime   → 容器里 npu-smi 看不到卡
  ⑤ kernels 包与芯片型号不符      → 算子加载失败/精度异常
  ⑥ 代码忘了 import torch_npu     → torch.npu 不可用、仍走 CPU
  ⑦ alpha/试用版 tag 已下线       → 拉不到，需换官方稳定 tag
  ─────────────────────────────────────────────────
```

## 常见问题

| 问题 | 解答 |
| --- | --- |
| 昇腾镜像对标英伟达什么? | 对标 **NGC 镜像仓库 + nvidia-docker 整套方案**，不是单一某个库。 |
| 镜像里要装驱动吗? | **不要**。驱动/固件装在宿主，镜像只到 CANN 这一层为止。 |
| 为什么都是 ARM64? | 昇腾服务器用鲲鹏(ARM)CPU，所以镜像基本是 aarch64，x86 上须 `--platform=arm64`。 |
| A1 和 A2 镜像有什么区别? | A1 适配 910A 系列、A2 适配 910B 系列(Atlas 800T A2 等)，**不可混用**。 |
| 容器里怎么用上 NPU? | 装 Ascend Docker Runtime 自动注入设备，或手动 `--device` 挂 `/dev/davinci*` + 映射驱动目录。 |
| 从哪里拉镜像? | AscendHub(官方，需登录)、昇腾社区、第三方算力云镜像站;具体地址见 §3。 |
| 文中的具体 tag 能直接用吗? | 仅用于讲解结构;**实际可用的仓库/tag/命令/版本以昇腾官方文档为准**。 |
| PyTorch 代码要改吗? | 要 `import torch_npu`，并把 `cuda`→`npu`、`nccl`→`hccl`。 |
