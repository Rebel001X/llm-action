## 0. 一句话锚点

在英伟达世界里,操作系统几乎是"透明"的——Ubuntu 装上 NVIDIA 驱动 + CUDA,基本一路绿灯,很少有人关心发行版。**到了昇腾国产化场景,操作系统从"背景板"升级成"一等公民"**：

1. **政策要求**：信创/党政/金融等场景明确要求"国产 OS + 国产 CPU + 国产 NPU"全栈替换,Ubuntu 往往不被允许进生产。
2. **技术耦合**：昇腾 NPU 驱动(`.ko` 内核模块)与内核版本强绑定,OS 选错或内核升级后,驱动可能装不上、NPU 直接掉线。

所以"操作系统"这一节不是讲怎么装 Linux,而是讲：**在昇腾栈里 OS 怎么选、和上层 CANN/驱动怎么对表、迁移时哪些 CUDA 经验会失效。**

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

### 1.1 OS 在昇腾软件栈的哪一层

```
        ┌──────────────────────────────────────────────┐
        │  套件层  MindFormers / MindIE / ModelLink ... │  ← 训练/推理框架
        ├──────────────────────────────────────────────┤
        │  框架层  MindSpore / PyTorch(torch_npu)        │  ← 深度学习框架
        ├──────────────────────────────────────────────┤
        │  CANN    (AscendCL / GE / 算子库 / HCCL)        │  ← 异构计算架构(≈CUDA)
        ├──────────────────────────────────────────────┤
        │  驱动+固件  Ascend Driver(.ko) + Firmware       │  ← 内核态,绑内核版本
        ├══════════════════════════════════════════════┤
        │  操作系统  Kylin / openEuler / UOS / Ubuntu     │  ★ 本文这一层
        ├──────────────────────────────────────────────┤
        │  硬件   鲲鹏/x86 CPU + 昇腾 NPU(910B/310P...)   │
        └──────────────────────────────────────────────┘
```

操作系统是"硬件"与"驱动/CANN"之间的承托层。它提供：内核(对接 NPU 驱动 KO)、glibc/编译工具链(对接 CANN 算子编译)、aarch64/x86 指令集环境(决定二进制包怎么选)、Python/系统库(对接框架)。**它本身不做 AI 计算,但它决定了上面这一整摞东西能不能装、能不能起来。**

### 1.2 昇腾 ↔ 英伟达生态对照表

| 维度 | 英伟达世界 | 昇腾世界 | 一句话对照 |
|------|-----------|----------|-----------|
| 加速卡 | GPU(A100/H100) | NPU(910B/310P) | 都是 AI 加速器 |
| 异构计算架构 | CUDA | CANN | "算子+运行时+编译器"全家桶 |
| 数学/算子库 | cuDNN / cuBLAS | CANN 算子库(AOL/TBE) | 高性能算子集合 |
| 集合通信 | NCCL | HCCL | 多卡 AllReduce 等 |
| 深度学习框架 | PyTorch | MindSpore / torch_npu | 后者让 PyTorch 跑在 NPU |
| 驱动 | NVIDIA Driver | Ascend Driver + Firmware | 内核态 .ko,绑内核 |
| 设备查询工具 | `nvidia-smi` | `npu-smi` | 看卡、看温度、看占用 |
| 容器运行时 | NVIDIA Container Toolkit | Ascend Docker Runtime | 把 NPU 注入容器 |
| **常用 OS** | **Ubuntu / CentOS** | **Kylin / openEuler / UOS** | ★ 本节核心差异 |
| CPU 架构 | 多为 x86_64 | 多为 **aarch64(鲲鹏)** | 影响所有包的选型 |

**关键迁移心智**：英伟达栈里 "OS 随便、CPU 是 x86" 是默认假设；昇腾栈里 **"OS 大概率国产、CPU 大概率 aarch64"** 才是默认。这两条假设的翻转,是所有迁移坑的根源。

## 2. 主流发行版:四选一怎么选

昇腾官方支持的 OS 是一个**白名单**——只有上了兼容性列表的发行版+版本+架构组合,驱动/CANN 才"官方背书"。常见四类：

### 2.1 Kylin(麒麟)

- 定位：信创主力,党政/金融/电信生产环境最常见。基于 `Kylin Linux Advanced Server V10`(服务器版)。
- 现状(可从机器上读出来,见文末附录)：`ID="kylin"`、`VERSION="V10 (Tercel)"`,内核为国产维护的 4.19/5.10 系。
- 取舍：兼容性列表覆盖最全,排障资料最多,**生产首选**。

### 2.2 openEuler(欧拉)

- 定位：华为主导的开源社区版 OS,与昇腾"同根",对鲲鹏+昇腾适配最积极。常见 `openEuler-22.03 / 24.03 LTS`。
- 取舍：开源、迭代快、对新硬件支持及时;若想用最新 CANN 特性,欧拉往往最早适配。

### 2.3 UOS(统信)

- 定位：另一信创主力,常见于党政终端与部分服务器场景。与 Kylin 同属信创双雄。

### 2.4 Ubuntu

- 定位：开发/验证环境、非信创要求的私有场景。社区资料最多,迁移成本最低。
- 取舍：**生产合规场景常被禁用**;但作为"先在 Ubuntu 上把模型跑通,再移植到 Kylin"的过渡环境非常实用。

```
合规度高 ←─────────────────────────────→ 社区友好/迁移易
 Kylin / UOS    >    openEuler    >    Ubuntu
 (信创生产)        (华为同根开源)        (开发/验证)
```

> 具体支持的发行版/版本/架构组合,**以华为昇腾官方文档(Ascend 社区)的"驱动固件兼容性列表 / CANN 配套表"为准**。不要凭记忆假设某个版本一定支持。

## 3. 架构与内核:aarch64 这条暗线

### 3.1 aarch64 vs x86_64

昇腾整机(如 Atlas 800)大量采用**鲲鹏(Kunpeng)CPU,即 aarch64 架构**。这意味着：

- 你下载的所有东西——OS 镜像、CANN 包、Python wheel、docker 镜像——都要选 **aarch64 / arm64** 版本,选错 x86 版直接装不上。
- pip 上很多包没有 aarch64 预编译 wheel,需要源码编译,这是迁移时巨大的隐性成本。
- 第三方 docker 镜像(`docker pull` 的)默认 x86,在鲲鹏机器上要么拉 arm64 tag,要么用 `--platform` 指定。

> 也有 x86_64 + 昇腾的整机方案,但 aarch64 是国产化主流。**装机第一件事:`uname -m` 看清自己是 aarch64 还是 x86_64。**

### 3.2 内核版本:驱动的"血缘"

NPU 驱动是内核模块(`.ko`),编译时绑定**特定内核版本与头文件**。后果：

```
   内核版本 X  ──编译──►  driver.ko (only for X)
       │
       │  系统 yum/apt upgrade 升级内核 → X 变成 X+1
       ▼
   开机加载 driver.ko  ──►  ✗ 版本不匹配 / 找不到符号 → NPU 掉线
```

这就是为什么生产环境**严控内核升级**,并且驱动包通常带 DKMS 或要求"内核锁版本"。CUDA 世界里 `apt upgrade` 顶多重装一下驱动;昇腾世界里一次盲目的内核升级可能让整台机器的 NPU 全部"消失"。

## 4. OS ↔ 驱动 ↔ CANN:必须"三层对表"

昇腾栈最反直觉、也最容易翻车的一点：**OS 版本、驱动/固件版本、CANN 版本三者必须互相兼容,不能各装各的最新。**

```
┌────────────┐   兼容?   ┌──────────────┐   兼容?   ┌──────────┐
│  OS + 内核  │ ◄──────► │ Driver+Firmware│ ◄──────► │   CANN   │
│ Kylin V10  │           │  (某版本)      │           │ (某版本) │
└────────────┘           └──────────────┘           └──────────┘
       ▲                                                   ▲
       └────────────── 都要对上"配套关系表" ───────────────┘
```

- **驱动 ↔ OS**：驱动 .ko 绑内核,所以 OS/内核 决定能装哪个驱动。
- **CANN ↔ 驱动**：CANN 调用驱动接口,版本错配会报"驱动版本过低/过高"。
- **框架 ↔ CANN**：`torch_npu` / MindSpore 又各自要求对应的 CANN 版本。

实践含义：**先查官方"配套关系表",自上而下定版本**——先定要用的框架/套件,反推 CANN 版本,再反推驱动版本,最后确认 OS 是否在该驱动的兼容列表里。**绝不要"哪个最新装哪个"。**

> 各组件的精确版本配套矩阵,以华为昇腾官方文档(Ascend 社区)发布的"配套关系/兼容性列表"为准。

## 5. 从裸机到 npu-smi:装机流程的"含义"

下面只讲**每一步在干什么、为什么要这步**,不写精确命令(命令与版本以官方文档为准)。

```
① 装 OS(选对发行版+aarch64/x86)
       │   目的:提供内核+工具链,且在驱动兼容列表内
       ▼
② 配软件源 / 准备编译依赖(gcc、make、内核头文件、Python...)
       │   目的:驱动安装可能需编译;CANN 需运行时依赖
       ▼
③ 装 NPU 驱动(Driver) + 固件(Firmware)
       │   目的:让 OS 能识别并驱动 NPU 硬件
       ▼
④ 验证:运行 npu-smi → 能列出每张卡 = 驱动 OK(≈nvidia-smi)
       │
       ▼
⑤ 装 CANN(toolkit / kernels / nnal...)
       │   目的:提供 AscendCL、算子库、HCCL 等"CUDA 等价物"
       ▼
⑥ 装框架(MindSpore 或 torch+torch_npu)+ 套件(MindFormers/MindIE)
       │
       ▼
⑦ source 环境变量(set_env.sh 类)→ 跑一个最小用例验证全栈打通
```

**几个"为什么"**：
- 为什么先验证 `npu-smi` 再装 CANN？因为这是分层排障的关键检查点——`npu-smi` 不通是驱动/硬件问题,通了之后报错才往 CANN/框架查。
- 为什么强调 source 环境变量？CANN 用环境变量(库路径、算子路径等)定位组件,**漏 source 是新手最高频的"明明装了却找不到"类报错**。

> 上述 ①~⑦ 的精确命令行、包名、版本号、安装路径,**一律以华为昇腾官方文档(Ascend 社区)为准**。

## 6. 容器化:为什么还要 Ascend Docker Runtime

很多人想"用 docker 隔离环境",但 NPU 不像普通设备能直接进容器。

- 英伟达：`NVIDIA Container Toolkit` 把 GPU 设备/驱动库注入容器。
- 昇腾：对应的是 **Ascend Docker Runtime**,负责把 NPU 设备节点、驱动用户态库挂进容器,容器内才能 `npu-smi`、才能跑 CANN。

镜像选型要点：
- 镜像基础 OS 与宿主机内核/驱动要**用户态兼容**(驱动内核态在宿主机,用户态库进容器)。
- 优先用昇腾官方提供的基础镜像(已预装匹配的 CANN/框架),避免自己拼版本踩"三层对表"的坑。
- aarch64 宿主机要拉 arm64 镜像(见 §3.1)。

## 迁移要点 / 注意事项与坑(从 CUDA/Ubuntu 思维迁过来)

| 坑 | 现象 | 根因 | 应对 |
|----|------|------|------|
| 拉了 x86 包/镜像 | 装不上 / 段错误 | 机器是 aarch64,你按 x86 习惯下载 | 先 `uname -m`,所有制品选 aarch64 |
| 盲目升级内核 | NPU 突然全掉线 | 驱动 .ko 绑旧内核 | 锁内核版本,升级前重装匹配驱动 |
| "哪个最新装哪个" | CANN 报驱动版本不匹配 | 没看配套关系表 | 自上而下定版本,严格对表 |
| 生产用了 Ubuntu | 合规审计不过 | 信创要求国产 OS | 生产用 Kylin/openEuler/UOS |
| 漏 source 环境变量 | "已安装却找不到库/算子" | CANN 靠环境变量定位 | 每次新 shell 都 source set_env |
| 直接 docker 跑没装 runtime | 容器内看不到 NPU | 没有 Ascend Docker Runtime | 装 runtime,用官方基础镜像 |
| 假设有 pip 预编译包 | 安装巨慢/失败 | aarch64 缺 wheel | 预留源码编译时间或用官方镜像 |

**性能/稳定性调优(机制层面,非具体参数)**：
- OS 层透明大页、CPU 亲和性、NUMA 绑定对 aarch64 多 die 鲲鹏影响显著,跨 NUMA 访存会拖慢 Host 侧。
- 关闭不必要的 OS 安全/审计模块(合规允许范围内)可减少 syscall 开销。
- 多卡训练时 HCCL 走 RoCE 网络,OS 的网卡驱动/RDMA 配置是否就绪直接决定 AllReduce 性能(对标 NCCL+IB)。

## 常见问题

| 问题 | 速查答案 |
|------|----------|
| 生产该选哪个 OS？ | 信创合规优先 Kylin / UOS / openEuler;开发验证可用 Ubuntu |
| 我的机器是什么架构？ | `uname -m`:aarch64=鲲鹏,x86_64=英特尔/AMD;决定一切下载 |
| `npu-smi` 不通怎么办？ | 先查驱动/固件是否装好、内核是否被升级过,而非去查 CANN |
| 装了 CANN 还报找不到库？ | 大概率没 source 环境变量脚本 |
| 能直接 `apt upgrade` 吗？ | 慎重,内核升级可能让驱动失效;生产应锁内核 |
| OS/驱动/CANN 版本怎么定？ | 查官方"配套关系表",自上而下反推,别装最新 |
| 容器里看不到 NPU？ | 检查是否装并使用了 Ascend Docker Runtime |
| 具体命令/版本去哪查？ | 一律以华为昇腾官方文档(Ascend 社区)为准 |
