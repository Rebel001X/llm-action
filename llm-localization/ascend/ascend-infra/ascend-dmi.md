## 0. 一句话锚点

**Ascend-DMI 是昇腾平台的"硬件维测工具":在不写一行训练/推理代码的前提下,直接对 NPU 卡发起 HBM 带宽、矩阵算力、功耗、温度、PCIe/HCCS 拓扑等基准测试与实时查询,用来回答一个问题——"这张卡(这台机器)现在是不是健康、性能是不是达标"。**

它主要服务三类场景:

- **上线验收**:新机器/新卡装好后,先用它确认带宽、算力、拓扑符合预期,再交付给训练/推理任务。
- **故障定位**:任务跑崩或变慢时,用它快速判断是硬件掉速、温度墙、还是软件/模型问题。
- **巡检监控**:周期性查询设备实时状态(温度、功耗、利用率、健康码)。

> 名字里的 DMI = Device Management Interface(设备管理接口);它本质是把底层一堆 C 接口(DCMI/DSMI/ACL)封装成好用的命令行。

## 1. 地基:在昇腾栈的定位 + 对标英伟达生态

### 1.1 昇腾软件栈分层(自底向上)

```
┌──────────────────────────────────────────────────────────┐
│  套件层    MindFormers / ModelLink / MindIE / msmodelslim │
├──────────────────────────────────────────────────────────┤
│  框架层    MindSpore / PyTorch(torch_npu)                 │
├──────────────────────────────────────────────────────────┤
│  CANN 层   GE图引擎 / ACL / HCCL / 算子库(AOL) / Runtime  │
│            ─────────────────────────────────────────────  │
│            DCMI / DSMI  ← 设备管理/系统管理接口            │
├──────────────────────────────────────────────────────────┤
│  驱动+固件 NPU Driver / Firmware                           │
├──────────────────────────────────────────────────────────┤
│  硬件层    Atlas 训练/推理卡(昇腾 910/310 系列 NPU)       │
└──────────────────────────────────────────────────────────┘

           ┌─────────────────────────────┐
           │      Ascend-DMI 工具         │   ← 横跨 CANN 工具链,
           │  (调 DCMI/DSMI/ACL + 系统库) │     向下打硬件、出报告
           └─────────────────────────────┘
```

**Ascend-DMI 处在"CANN 工具链 / 维测层"**:它不是训练/推理框架的一部分,而是一个独立诊断工具,向下通过 DCMI/DSMI 读硬件传感器与拓扑,通过 ACL 下发算力/带宽 benchmark 到 NPU 上跑,再把结果汇总成报告。

### 1.2 对标英伟达生态(迁移心智图)

| 维度 | 昇腾(Ascend) | 英伟达(NVIDIA) | 说明 |
|------|----------------|------------------|------|
| 加速硬件 | NPU(Atlas 卡) | GPU | 异构计算单元 |
| 计算软件栈 | CANN | CUDA | 编程+运行时基座 |
| 设备管理接口 | **DCMI / DSMI** | **NVML** | 取温度/功耗/利用率/拓扑的底层 API |
| 命令行查状态 | `npu-smi` + **Ascend-DMI** | `nvidia-smi` | 实时状态;Ascend-DMI 更偏 benchmark/诊断 |
| 集群健康/诊断 | **Ascend-DMI**(诊断+benchmark) | `dcgmi`(DCGM) | 主动跑测试、出健康码 |
| 带宽/算力压测 | **Ascend-DMI** 带宽/算力测试 | `bandwidthTest` / `nccl-tests` / cuBLAS bench | 基准测试 |
| 集合通信库 | HCCL | NCCL | 多卡通信 |
| 互联总线 | HCCS / PCIe | NVLink / PCIe | 拓扑里要看的链路 |
| 编程语言 | ACL(Ascend Computing Language) | CUDA Runtime/Driver API | 下发任务到设备 |

**一句话迁移锚点**:如果你在 GPU 世界习惯用 `nvidia-smi` 看状态、用 `bandwidthTest`/`nccl-tests` 压带宽、用 `dcgmi diag` 做健康诊断,那么在昇腾世界这些动作很大一部分由 **Ascend-DMI**(配合 `npu-smi`)来承担。

> ⚠️ 注意:`npu-smi` 与 Ascend-DMI 职责有重叠也有分工。粗略地说,`npu-smi` 更像日常的状态查询(对标 `nvidia-smi`),Ascend-DMI 更强调"主动发起 benchmark/诊断并出报告"(对标 `dcgmi`+压测工具)。两者的精确功能边界与命令以华为昇腾官方文档(Ascend 社区)为准。

## 2. 底层接口:工具靠什么取数据

Ascend-DMI 自己不直接读寄存器,而是站在三类已有接口之上,这也是理解它能力边界的关键:

```
        ┌──────────── Ascend-DMI ────────────┐
        │   解析参数 → 选功能 → 取数/压测 → 报告│
        └───┬────────────┬────────────┬───────┘
            │            │            │
        ┌───▼───┐   ┌────▼────┐   ┌───▼────────┐
        │ DCMI  │   │  DSMI   │   │    ACL     │
        │设备控制│   │设备系统 │   │昇腾计算语言 │
        │管理接口│   │管理接口 │   │下发kernel  │
        └───┬───┘   └────┬────┘   └───┬────────┘
            │            │            │
   温度/功耗/      系统级信息/      把算力/带宽
   利用率/健康/     版本/拓扑        benchmark 真正
   传感器           查询            跑到 NPU 上
            │            │            │
        ┌───▼────────────▼────────────▼───┐
        │   NPU Driver / Firmware / 硬件   │
        └──────────────────────────────────┘
```

- **DCMI(Device Control & Management Interface,设备控制管理接口)**:读硬件传感器与状态——温度、功耗、电压、利用率、健康状态、ECC 错误等。对标 NVML 的"读传感器"部分。
- **DSMI(Device System Management Interface,设备系统管理接口)**:系统级管理信息——版本、设备列表、部分拓扑/系统配置查询。
- **ACL(Ascend Computing Language)**:当工具要做"算力测试""带宽测试"这类**主动压测**时,需要真正在 NPU 上跑计算/搬数据,这就要靠 ACL 下发任务到设备。系统级通用信息(如 OS、内存)则调用系统通用库获取。

> 理解要点:**查询类**功能靠 DCMI/DSMI 读传感器(轻量、不占用算力);**压测类**功能(带宽/算力)靠 ACL 真实下发负载(会占用设备,跑测时不要和业务任务抢卡)。

## 3. 七大功能逐一拆解

下面对应文件原有的七个小节,逐一说明"测什么、原理、怎么用结果"。**所有具体命令行参数、阈值、版本一律以华为昇腾官方文档(Ascend 社区)为准**,这里只讲含义与判读方法。

### 3.1 带宽测试

- **测什么**:设备的数据搬运带宽,通常包括 Host↔Device(经 PCIe)、Device 内 HBM 带宽、以及多卡间(HCCS/PCIe)互联带宽。
- **原理**:通过 ACL 反复搬运大块数据,统计单位时间搬运量,得到实测带宽 GB/s,再与该型号理论带宽对比。
- **怎么用结果**:实测明显低于理论值,常见原因是 PCIe 链路降速(x16 掉到 x8/x4)、插槽/线缆问题、NUMA 亲和性不当。
- **GPU 对照**:相当于 `bandwidthTest`(H2D/D2H/D2D)+ `nccl-tests`(卡间)。

### 3.2 算力测试

- **测什么**:NPU 的浮点/整型算力(如 FP16/BF16/INT8 的 TFLOPS/TOPS),核心是达芬奇架构 Cube(矩阵)单元的峰值能力。
- **原理**:通过 ACL 下发大规模矩阵乘(GEMM)类负载,跑满 Cube 单元,统计实测算力,与标称值比对。
- **怎么用结果**:实测算力达不到标称,常见于频率被温度/功耗墙压低(降频)、或散热/供电不足。
- **GPU 对照**:相当于用 cuBLAS GEMM 或专门的 TFLOPS benchmark 压 Tensor Core。

### 3.3 功耗测试

- **测什么**:设备在负载下的实时功耗曲线与峰值功耗。
- **原理**:DCMI 读功耗传感器,通常配合算力/带宽负载,观察满载功耗是否在 TDP 范围内。
- **怎么用结果**:功耗异常偏高/偏低、或负载上不去功耗也上不去,提示供电、固件或硬件问题。

### 3.4 设备实时状态查询

- **测什么**:温度、功耗、利用率(AI Core 占用)、HBM 显存占用、健康状态码、电压、风扇等。
- **原理**:DCMI/DSMI 直接读传感器,轻量、不占算力,可用于巡检与监控。
- **GPU 对照**:对标 `nvidia-smi` 的实时输出;在昇腾日常这块也常用 `npu-smi`。

### 3.5 故障诊断

- **测什么**:综合判断设备是否健康,输出健康码/故障码,定位常见硬件异常(如 ECC、链路、过温)。
- **原理**:汇总 DCMI 健康状态 + 主动跑轻量自检,按规则给出诊断结论。
- **GPU 对照**:对标 `dcgmi diag`(DCGM 健康诊断)。
- **怎么用结果**:这是任务跑崩后"先排硬件还是先排软件"的第一道关——硬件诊断通过,再去查 CANN/模型/数据。

### 3.6 软硬件版本兼容性测试

- **测什么**:驱动、固件、CANN 等组件之间的版本是否匹配。
- **原理**:DSMI 读各组件版本,与兼容性矩阵比对。
- **为什么重要**:昇腾栈对"驱动/固件/CANN 三者版本配套"非常敏感,版本错配是新环境最高频的坑之一,很多"莫名报错"根因都在这。**具体配套关系以官方版本配套表为准**。

### 3.7 设备拓扑检测

- **测什么**:节点内多张 NPU 之间、NPU 与 CPU/PCIe Switch 的连接关系与 HCCS/PCIe 链路。
- **原理**:DSMI/系统库读取拓扑信息,呈现卡间互联结构与链路速率。
- **为什么重要**:HCCL 集合通信的环(Ring)/树(Tree)算法效率高度依赖拓扑;拓扑不对(或 NUMA 亲和差)会让 AllReduce 等通信变慢,直接拖垮多卡训练吞吐。
- **GPU 对照**:对标 `nvidia-smi topo -m`(看 NVLink/PCIe 拓扑矩阵)。

```
节点内拓扑(示意)
   CPU0 ────PCIe Sw0──┬── NPU0 ═══HCCS═══ NPU1
                      └── NPU2 ═══HCCS═══ NPU3
   CPU1 ────PCIe Sw1──┬── NPU4 ═══HCCS═══ NPU5
                      └── NPU6 ═══HCCS═══ NPU7
   ═══ : 高速 HCCS 互联(类比 NVLink)
   ─── : PCIe 链路
判读:同 HCCS 域内的卡通信最快;跨 PCIe Switch/跨 CPU 需注意 NUMA 亲和
```

## 4. 典型工作流:验收与排障怎么跑

```
新机验收                          任务变慢/跑崩排障
   │                                  │
   ▼                                  ▼
版本兼容性测试(3.6)            故障诊断(3.5)出健康码
   │  驱动/固件/CANN 配套吗?         │  硬件 OK?
   ▼                                  ▼ 是
拓扑检测(3.7)                  状态查询(3.4)看温度/功耗
   │  卡间互联符合预期吗?            │  是否撞温度墙/降频?
   ▼                                  ▼
带宽测试(3.1)                  带宽/算力测试(3.1/3.2)
   │  H2D/D2D/卡间达标吗?            │  实测掉速了吗?
   ▼                                  ▼
算力 + 功耗测试(3.2/3.3)        定位:硬件 or 软件/模型
   │  满载达标且功耗正常?            └── 硬件全过 → 转查 CANN/模型/数据
   ▼
交付给训练/推理业务
```

> 经验法则:**先查"配套与拓扑"(便宜、快),再压"带宽与算力"(贵、占卡)**。绝大多数环境问题在前两步就能暴露。

## 迁移要点 / 注意事项与坑

1. **心智迁移**:把 GPU 世界的 `nvidia-smi`(状态)+ `bandwidthTest`/`nccl-tests`(压测)+ `dcgmi diag`(诊断)三件事,映射到昇腾的 `npu-smi` + **Ascend-DMI**。Ascend-DMI 偏"主动 benchmark + 诊断"。

2. **压测会占卡**:带宽/算力测试通过 ACL 真实下发负载,**跑测时该卡不能同时跑业务任务**,否则结果失真且互相干扰。查询类(状态/拓扑/版本)才是轻量、可常态巡检的。

3. **版本配套是头号坑**:驱动 / 固件 / CANN 三者必须按官方配套表匹配。新环境"装好却各种报错",八成是版本错配——上线第一步就该跑兼容性测试。**具体配套以官方版本表为准**。

4. **拓扑决定多卡性能**:实测带宽/算力单卡正常但多卡训练慢,优先看拓扑与 NUMA 亲和——HCCL 的环算法吃拓扑,跨 PCIe Switch/跨 NUMA 会拖慢 AllReduce。

5. **实测低于标称要分层排查**:算力低→多半是降频(温度/功耗墙,看 3.3/3.4);带宽低→多半是 PCIe 链路降速或亲和性问题。

6. **不要把它当训练/推理工具**:Ascend-DMI 只验证"硬件能力",验证通过后,真正训练用 MindFormers/ModelLink,推理用 MindIE。它是体检仪,不是发动机。

7. **命令/参数勿凭记忆**:Ascend-DMI 的具体子命令、参数名、输出字段、阈值在不同 CANN 版本可能不同,**一律以华为昇腾官方文档(Ascend 社区)为准**,本文只讲机制与判读思路。

## 常见问题

| 问题 | 解答 |
|------|------|
| Ascend-DMI 和 npu-smi 啥区别? | 粗分:`npu-smi` 偏日常状态查询(对标 `nvidia-smi`);Ascend-DMI 偏主动 benchmark + 故障诊断(对标压测工具 + `dcgmi`)。精确边界以官方文档为准。 |
| 它对标 CUDA 世界的什么? | 约等于 `nvidia-smi` + `bandwidthTest`/`nccl-tests` + `dcgmi diag` 的合体。 |
| 它靠什么取数据? | 查询类靠 DCMI/DSMI 读传感器;压测类靠 ACL 把负载真正下发到 NPU。 |
| 跑算力测试时能同时训练吗? | 不能,压测会独占该卡算力,结果会失真且互相干扰。 |
| 实测算力达不到标称怎么办? | 先看温度/功耗(3.3/3.4)是否撞墙降频,再查散热/供电。 |
| 多卡训练慢但单卡测试正常? | 查拓扑(3.7)与 NUMA 亲和;HCCL 通信效率依赖拓扑。 |
| 新环境各种报错先查什么? | 先跑版本兼容性测试(3.6),驱动/固件/CANN 配套是头号坑。 |
| 具体命令在哪查? | 华为昇腾官方文档(Ascend 社区)的 Ascend-DMI 工具手册,版本相关。 |
