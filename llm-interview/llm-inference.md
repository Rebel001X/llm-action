## 0. 一句话锚点

> 大模型推理的所有性能指标，本质都在描述同一件事的两个侧面：**单个用户的「快不快」（时延：TTFT、TPOT、端到端）** 和 **整个系统的「省不省」（吞吐、并发请求数、每百万 Token 成本）**。二者天然冲突——增大 batch 提升吞吐却拉高单请求时延。面试时只要能把任一指标定位到「这是时延派还是吞吐派、它被请求生命周期的哪个阶段驱动」，就答到了点子上。

## 1. 地基：一次推理请求的生命周期

LLM 自回归生成天然分两段，理解这两段是理解所有指标的前提：

```
请求生命周期（Prefill / Decode 两阶段）
────────────────────────────────────────────────────────────
用户输入 Prompt（N 个输入 Token）
        │
        ▼
┌──────────────────┐   一次性并行处理全部输入 Token，
│  Prefill 预填充   │   算力密集(compute-bound)，建满 KV-Cache
│  (= 预加载阶段)   │   ↘ 决定「首 Token 何时吐出」
└──────────────────┘
        │  ← 第 1 个输出 Token 出现的瞬间 = TTFT 终点
        ▼
┌──────────────────┐   逐个 Token 串行生成，每步只算 1 个 Token，
│  Decode 解码      │   访存密集(memory-bound)，反复读 KV-Cache
│  (逐 Token 生成)  │   ↘ 决定「后续每个 Token 多快」= TPOT
└──────────────────┘
        │
        ▼
完整响应（M 个输出 Token）
────────────────────────────────────────────────────────────
时间轴：
  ├──────TTFT──────┤──TPOT──┼──TPOT──┼ ... ┼──TPOT──┤
  prefill+首token    tok#2     tok#3         tok#M
  └──────────────── 端到端时延 ────────────────────┘
```

- **Prefill（预填充 / 原文称「预加载」）**：把整段 prompt 一次喂入，所有输入 Token 并行做注意力，矩阵规模大、算力打满（compute-bound）。它产出第一个输出 Token，因此**直接决定 TTFT**。
- **Decode（解码）**：每生成 1 个新 Token 都要重新跑一遍前向，但靠 KV-Cache 复用历史，单步计算量极小，瓶颈在反复搬运权重与 KV（memory-bound）。它**决定 TPOT**。

> 为什么要分两段？因为这两段的硬件瓶颈不同（算力 vs 带宽），所以才有 [[llm-inference/PD分离]]（Prefill/Decode 分离部署）这类优化——让两类硬件各司其职。KV-Cache 的细节见 [[llm-optimizer/kv-cache]]。

## 2. 时延派指标（单用户「快不快」）

> 本节指标全部来源于原文，逐条补全「它被什么驱动、为什么重要」。

### 2.1 首 Token 生成时间 TTFT（Time To First Token）

**定义（原文）**：用户输入提示后，模型生成第一个输出词元所需的时间。

- **被什么驱动**：处理 prompt 并生成首个输出 Token 的时间——即 **Prefill 阶段耗时**。
- **何时重要**：实时交互（聊天、Copilot）下低时延获取响应非常重要；离线批处理任务则不太重要。
- **为什么看分布而非均值**：通常不仅关心平均 TTFT，还关心其**分布 P50 / P90 / P95 / P99**。原因：长尾请求（排队、抢占、超长 prompt）会让少数用户体验极差，均值会掩盖这一点。SLA 一般卡 P95/P99。

```
TTFT 分布为什么右偏（长尾）？
频次 │██
     │████
     │██████              ← 大多数请求落在 P50 附近
     │███████▁▁
     │████████▁▁▁▁▁▁__    ← 长尾：排队 / 超长 prompt / 抢占
     └────────────────────────► TTFT
      P50      P90 P95   P99
```

### 2.2 单个输出 Token 生成时间 TPOT（Time Per Output Token）

**定义（原文）**：为每个用户的查询生成一个输出词元所需的时间。

- **与什么相关**：用户对模型「速度」的主观感知——文字一行行往外蹦的快慢。
- **数值直觉（原文例）**：TPOT = 100 ms/token ⇒ 每秒 10 个 Token ⇒ 每分钟约 450 个词元（按一个词约含多个 Token 折算），远超普通人阅读速度。也就是说 100 ms/token 已是「看不过来」的体验级。

| TPOT | 每秒 Token | 体感 |
| --- | --- | --- |
| 50 ms/tok | 20 tok/s | 非常流畅 |
| 100 ms/tok | 10 tok/s | 超出人眼阅读速度（原文口径） |
| 200 ms/tok | 5 tok/s | 略慢但可接受 |
| 500 ms/tok | 2 tok/s | 卡顿，体验差 |

### 2.3 端到端时延（End-to-End Latency）

**定义（原文）**：模型为用户生成完整响应所需的总时间。

**关键公式（原文给出）**：

$$\text{端到端时延} = \text{TTFT} + \text{TPOT} \times (\text{待生成的词元数})$$

这条公式是本主题的「锚公式」，第 4 节会用它手算。

## 3. 吞吐派与成本派指标（系统「省不省」）

> 同样逐条来自原文。

| 指标（原文） | 含义 | 注意点 |
| --- | --- | --- |
| **每分钟完成的请求数** | 系统并发处理能力 | 来自多用户并发或批量推理任务 |
| **单个请求的成本** | 单次请求开销 | API 提供商常用「牺牲时延换成本」：同模型摊到更多 GPU 或换更高端 GPU 可降时延但抬成本 |
| **最大利用率下每百万 Token 的成本** | 比较不同部署配置的总成本 | 原文例：同一个 Llama 2-7B 可放在 1×A800-80G / 1×H800-80G / 1×A100-40GB 上对比 |
| **生成 Token 吞吐量** | 全部用户请求中每秒生成的输出 Token 数 | 原文强调：因无法直接测预加载时间、且总时延更取决于输出 Token 数，**把注意力放在输出 Token 上通常是正确抉择** |
| **总吞吐量** | 同时计入输入 Token 和生成 Token | 区别于「生成吞吐量」只数输出 |

### 3.1 关于「预加载时间」（原文重点）

原文给出一个重要经验：

- 预加载时间（Prefill 耗时）**只能通过首 Token 的生成间接估算**，难以单独直接测量。
- 一些研究发现：在 **250~800 个输入词元之间**，输入词元数量与 TTFT 之间**看不出明显关系**，因为这点影响被 TTFT 中的随机噪声掩盖了。
- 经验比例：**输入词元对端到端时延的影响约为输出词元的 1%**。

```
端到端时延的构成（经验占比，原文 1% 口径）
 输入 Token 贡献 ▏1%
 输出 Token 贡献 ███████████████████████████████ 99%
            → 所以优化与建模都应聚焦「输出 Token」
```

> 这解释了为什么 3.0 表里说「把注意力放在输出 Token 上」：因为端到端时延几乎被 `TPOT × 输出长度` 这一项支配。

## 4. 端到端时延手算（用锚公式）

把第 2.3 节公式落到具体数字，建立可口算的直觉。

**场景**：TTFT = 0.5 s，TPOT = 100 ms = 0.1 s，期望最大输出长度 = 200 Token。

$$\text{端到端} = 0.5 + 0.1 \times 200 = 0.5 + 20 = 20.5\ \text{s}$$

- 占比：Prefill/TTFT 只占 `0.5/20.5 ≈ 2.4%`，Decode 占 ≈ 97.6%——再次印证「输出 Token 主导」。
- 原文推论印证：**「对总体平均时延，通常只需将预期最大输出 Token 长度 × 每个输出 Token 的平均时延即可。」** 即当输出较长时，可近似 `端到端 ≈ TPOT × 输出长度`，TTFT 可忽略。

```
输出长度对端到端时延的杠杆作用
输出 50 tok :  TTFT0.5 + 5.0  = 5.5 s
输出 200 tok:  TTFT0.5 + 20.0 = 20.5 s    ← 输出翻4倍，时延≈翻4倍
输出 800 tok:  TTFT0.5 + 80.0 = 80.5 s    ← 几乎线性于输出长度
```

## 5. 三条经验规律（原文实测，重点记忆）

原文针对「端到端推理延迟」总结了三条规律，是高频考点：

### 5.1 输出 Token 长度决定总体响应延迟

对总体平均时延，**预期最大输出 Token 长度 × 每个输出 Token 平均时延** 即可估算。本质就是锚公式在「输出主导」下的退化形式。

### 5.2 输入长度对端到端性能不重要，但对硬件要求重要

- **实测（原文）**：在 MPT 模型中，**512 个输入 Token 增加的延迟，小于多生成 8 个输出 Token 的延迟**。即输入很「便宜」。
- **但**：支持长输入会让模型更难服务（KV-Cache 显存随上下文线性增长）。原文建议：服务最大上下文 2048 的 **MPT-7B，通常用 A100-80GB（或更新版本）**。
- **作者亲测（原文踩坑，务必保留）**：在 **MindIE Service** 上用**羊驼中文数据集**，对**百川和千问**大模型做测试，发现 **100 Token 以内，随输入 Token 长度增加，首 Token 时延并无显著增加**。

```
输入 Token 数 vs 首 Token 时延（作者在 MindIE 实测，≤100 Token 区间）
TTFT │ ● ● ● ●  ● ●  ●  ●      ← 基本持平，无显著上升趋势
     │________________________
       20  40  60  80  100   输入 Token 数
结论：短输入区间，输入长度不是 TTFT 的主要矛盾
```

> 为什么输入「便宜」？因为 Prefill 把 N 个输入 Token 一次并行算完，GPU 算力被打满、并行度高；而 Decode 每个输出 Token 都要串行跑一次前向，且 memory-bound，单位成本高得多。

### 5.3 端到端时延与模型大小呈「次线性」关系

同一硬件上，更大的模型推理更慢，**但慢的倍数不等于参数量倍数**（次线性，sub-linear）：

| 对比（原文数据） | 参数量比 | 时延比 |
| --- | --- | --- |
| MPT-30B vs MPT-7B | ≈ 4.3× | **≈ 2.5×** |
| Llama2-70B vs Llama2-13B | ≈ 5.4× | **≈ 2×** |

> 为什么次线性？Decode 阶段 memory-bound，时延更受「权重 + KV 的访存量 / 显存带宽」与并行效率影响，而非纯算力 FLOPs；更大模型能更充分地利用 GPU（算术强度更高），单位参数的边际时延下降，故时延增速慢于参数量增速。

## 6. 指标取舍：时延 vs 吞吐（为什么二者打架）

```
batch 增大 → 吞吐 ↑，但单请求时延 ↑（要等凑批 / 排队 / 共享算力）
                     ▲
   吞吐(tok/s)       │        ____——————  吞吐随 batch 上升后趋平
                     │     __/
                     │  __/
                     │_/
                     └────────────────────► batch size
   单请求 TTFT/TPOT   随 batch 增大而升高（与吞吐反向）
```

- **实时交互场景**：卡 **P95/P99 TTFT、TPOT**，宁可吞吐低些也要响应快 → 小 batch、低排队。
- **离线 / 批量场景**：卡**生成吞吐量、每百万 Token 成本**，时延不敏感 → 大 batch、塞满 GPU。
- 原文点出的「牺牲时延换成本」正是这条曲线的一个工作点选择。

## 7. 成本指标口径（落地对比）

把第 3 节成本指标整理成可执行的对比方法：

```
每百万 Token 成本 = (GPU 单位时间租金 / 该配置的生成吞吐量) 换算到 1e6 Token
对比矩阵（原文示例机型，同模型 Llama 2-7B）：
┌───────────────┬───────────────┬────────────────────────┐
│ 配置          │ 显存          │ 对比维度               │
├───────────────┼───────────────┼────────────────────────┤
│ 1×A800-80G    │ 80 GB         │ 吞吐↑、单卡贵           │
│ 1×H800-80G    │ 80 GB         │ 更高端、时延↓、更贵     │
│ 1×A100-40GB   │ 40 GB         │ 显存小、长上下文吃紧    │
└───────────────┴───────────────┴────────────────────────┘
比较口径：同输出负载下「最大利用率每百万 Token 成本」越低越省
```

> 选卡先看显存能否放下「模型权重 + 峰值 KV-Cache」，再比吞吐/成本。显存估算见 [[docs/transformer内存估算]]，KV 占用见 [[llm-optimizer/kv-cache]]。

## 常见问题/坑

| 问题 / 坑 | 一句话答 |
| --- | --- |
| TTFT 和 TPOT 哪个对聊天体验更关键？ | 两者都要：TTFT 决定「等多久开始吐字」，TPOT 决定「吐字快慢」；实时场景卡 P95/P99。 |
| 端到端时延怎么估？ | 锚公式 `TTFT + TPOT×输出长度`；输出长时近似 `TPOT×输出长度`。 |
| 为什么只盯输出 Token，不盯输入？ | 输入对端到端时延约只占 1%（原文）；Prefill 并行、便宜，Decode 串行、贵。 |
| 输入越长 TTFT 一定越高吗？ | 不一定。原文：250~800 Token 区间看不出明显关系；作者 MindIE 实测 ≤100 Token 无显著上升。但长输入抬高显存/服务难度。 |
| 模型大一倍时延就大一倍？ | 否，次线性。MPT-30B/7B 时延≈2.5×，Llama2-70B/13B≈2×（原文）。 |
| 只看平均 TTFT 行不行？ | 不行，分布右偏有长尾，必须看 P90/P95/P99，否则会漏掉差体验用户。 |
| 「生成吞吐量」与「总吞吐量」区别？ | 前者只数输出 Token，后者输入+输出都数；评估解码速度常用前者。 |
| 选 A800/H800/A100 的依据？ | 先看显存能否容纳「权重+峰值 KV」，再比「每百万 Token 成本」与时延需求。 |
| 吞吐和时延能同时拉满吗？ | 不能，是 trade-off：增大 batch 提吞吐但抬单请求时延，按业务场景选工作点。 |
