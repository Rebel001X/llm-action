## 0. 一句话锚点

- **评测质量**：给模型一批题，看它**答得对不对**。指标分两类——判别式(选择/分类→准确率)、生成式(开放文本→困惑度/BLEU/ROUGE/人评/Elo)。
- **评测性能**：固定模型，看它**跑得快不快、省不省卡**。核心四指标：**TTFT**(首字延迟)、**TPOT**(每字延迟)、**吞吐**(tokens/s)、**MFU**(算力利用率)。
- 面试一句话总结：**「质量看 benchmark + 人评，性能看 TTFT/TPOT/吞吐/MFU，二者用压测在不同并发下画 SLO 曲线联合权衡」**。

## 1. 地基：评测的三种范式

```
                  ┌──────────────────────────────┐
                  │        大模型评测              │
                  └──────────────┬───────────────┘
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
   ① 自动指标             ② 模型/人评             ③ 性能压测
   (有标准答案)           (开放任务)             (不看内容，看速度)
   ┌─────────┐           ┌─────────┐            ┌─────────┐
   │ 准确率   │           │ 人工打分 │            │ TTFT    │
   │ 困惑度   │           │ Elo/Arena│           │ TPOT    │
   │ BLEU/ROUGE│          │ LLM-judge│           │ 吞吐/MFU │
   │ pass@k   │           │ 偏好对比 │            │ P99 延迟 │
   └─────────┘           └─────────┘            └─────────┘
   客观、可复现           主观、贴近真实需求      工程导向
```

**为什么要分三类？**
- 有标准答案的任务(数学、选择题、代码)→ 自动指标最省事、可复现。
- 开放任务(写作、改写、总结)→ 没有唯一答案，BLEU/ROUGE 与人类偏好不对齐，必须靠人评或 LLM 评判 / Elo。
- 性能压测**不关心答案对不对**，只关心系统在并发下的延迟与吞吐——这是部署上线最关键的一环。

## 2. 评测集(Benchmark)

> 详见 [[llm-eval/大模型测评集]]。这里给面试要背的「类别→代表集→指标」对应。

| 能力维度 | 代表评测集 | 形式 | 主指标 | 备注 |
|----------|-----------|------|--------|------|
| 综合知识 | MMLU / MMLU-Pro | 57 学科 4 选 1 | 准确率(acc) | 英文，最常引用 |
| 中文综合 | C-Eval / CMMLU | 多学科选择题 | 准确率 | 中文 MMLU |
| 数学推理 | GSM8K / MATH | 小学/竞赛数学 | 准确率(EM) | 看 CoT 能力 |
| 代码 | HumanEval / MBPP | 函数补全 | pass@1/pass@k | 跑单测看通过率 |
| 推理 | BBH / ARC / HellaSwag | 多任务推理 | 准确率 | 常识/逻辑 |
| 长文本 | LongBench / "大海捞针" | 长上下文检索 | 召回/准确率 | 测 context 利用 |
| 对话/对齐 | MT-Bench / AlpacaEval | 开放多轮 | LLM-judge 分/胜率 | 主观对齐 |
| 综合竞技 | Chatbot Arena | 人类盲评对战 | Elo | 最贴近真实偏好 |

**陷阱(面试常追问)：**
1. **数据污染(contamination)**：测试集泄漏进训练语料 → 分数虚高。判别方法：n-gram 重叠检测、改写题目重测、看 train/test 困惑度差。
2. **few-shot vs zero-shot**：MMLU 常用 5-shot；shot 数不同分数不可比。报分必须注明设置。
3. **答案抽取**：选择题要从生成文本里抽 A/B/C/D，抽取规则(正则/likelihood)不同结果不同。
4. **榜单 ≠ 真实体验**：刷榜过拟合 benchmark，线上仍需 A/B + 人评。

## 3. 质量指标全景

```
                     标准答案?
            ┌──────── 是 ───────────┬──────── 否 ──────────┐
            ▼                       ▼                      ▼
        分类/选择               生成(对照ref)          生成(无ref/开放)
        ┌───────┐              ┌──────────┐           ┌──────────┐
        │准确率  │              │BLEU(翻译) │          │人工打分   │
        │F1     │              │ROUGE(摘要)│          │Elo/胜率   │
        │EM     │              │chrF       │          │LLM-judge │
        │pass@k │              │BERTScore  │          │困惑度(语言)│
        └───────┘              └──────────┘           └──────────┘
```

**关键指标速记：**
- **准确率 acc** = 答对数 / 总数。选择题、分类的主力。
- **EM(Exact Match)**：生成与标准答案逐字符相等才算对(数学最终答案常用)。
- **F1** = $\frac{2PR}{P+R}$，P=精确率、R=召回率；抽取式 QA 常用(部分重叠也给分)。
- **BLEU**：n-gram 精确率的几何平均 × 简短惩罚(BP)，**机器翻译**用。
- **ROUGE**：n-gram 召回(ROUGE-N)/最长公共子序列(ROUGE-L)，**摘要**用。
- **pass@k**：见下。
- **困惑度 PPL**：语言模型本身的拟合度，见第 4 节。

### pass@k 手算

代码题生成 $n$ 个样本，其中 $c$ 个通过单测，无偏估计：

$$\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$$

**例**：$n=10$ 个样本，$c=3$ 个通过，求 pass@1 与 pass@5。

- pass@1 $= 1 - \binom{7}{1}/\binom{10}{1} = 1 - 7/10 = 0.3$ ✅(直觉：随机抽 1 个有 3/10 通过)
- pass@5 $= 1 - \binom{7}{5}/\binom{10}{5} = 1 - \frac{21}{252} = 1 - 0.0833 = 0.9167$
  - $\binom{7}{5}=21,\ \binom{10}{5}=252$。
  - 直觉：抽 5 个里至少 1 个通过的概率，比抽 1 个高得多。

## 4. 困惑度(Perplexity)——从最底层推导 + 手算

**它是什么？** 衡量语言模型对一段真实文本的「惊讶程度」：模型越觉得这段文本「理所当然」(概率越高)，困惑度越低，越好。

**第一步：交叉熵损失。** 给定文本 $w_1,\dots,w_N$，模型逐 token 预测概率 $p(w_i \mid w_{<i})$。平均负对数似然(就是训练用的 CE loss，自然对数)：

$$L = -\frac{1}{N}\sum_{i=1}^{N}\ln p(w_i \mid w_{<i})$$

**第二步：困惑度 = loss 的指数。**

$$\text{PPL} = \exp(L) = \exp\!\Big(\!-\frac{1}{N}\sum_i \ln p(w_i\mid w_{<i})\Big)$$

**为什么取指数？** 让 PPL 有「平均分支数」的直觉：PPL=k 相当于模型每步在 k 个等概率候选里猜。均匀分布 $V$ 个词时 $p=1/V$，PPL $=V$——所以 PPL 上界约等于词表大小，越接近 1 越好(理想模型每步几乎确定下一个词)。

**逐数手算。** 设 3 个 token，模型给真实 token 的概率分别 0.5, 0.25, 0.1：

```
token:  w1     w2     w3
p:      0.5    0.25   0.1
-ln p:  0.693  1.386  2.303      (ln0.5=-0.693, ln0.25=-1.386, ln0.1=-2.303)
```

$$L = \frac{0.693+1.386+2.303}{3} = \frac{4.382}{3} = 1.461$$
$$\text{PPL} = e^{1.461} \approx 4.31$$

直觉：模型平均像在「4.31 个候选里挑」。若三处概率都是 1.0，则 $L=0,\ \text{PPL}=1$(完美)。

**用 2 为底也可以**：$\text{PPL}=2^{H}$，$H$ 用 $\log_2$。底数只要 loss 与 PPL 一致即可，**结果相同**。

**面试陷阱：**
- PPL 只在**相同 tokenizer / 相同测试集**下可比；换分词器 token 数变了，PPL 不可比。
- PPL 低 ≠ 下游任务强(对齐后模型 PPL 可能升高但更好用)。它衡量「语言建模」，不衡量「有用/安全」。
- 衡量长文本时常用 sliding-window，避免长 context 被截断影响。

## 5. 开放性任务怎么评？(写作/改写/总结)

> 这是原文的核心方向，展开讲。

**为什么不用 BLEU/ROUGE？** 开放写作没有唯一参考答案，n-gram 重叠既不体现核心能力，也与人类需求不对齐(偏离实际需求)。一个好答案可以和 reference 完全不重叠。

**三条可行路线：**

```
① 人工评分(Likert 1-5 / 多维)     最可信、最贵、最慢
② 成对偏好 + Elo / Bradley-Terry   只需判A/B谁好，聚合成排名 → 最合理
③ LLM-as-a-judge(GPT-4 当裁判)    便宜可扩展，但有偏差需校准
```

### Elo 评分(贴近真实需求的首选)

来自国际象棋。两模型对一道 prompt 各出一答，人类盲选谁更好；按胜负更新分数。期望胜率：

$$E_A = \frac{1}{1 + 10^{(R_B - R_A)/400}}$$

更新：$R_A' = R_A + K\,(S_A - E_A)$，$S_A\in\{1,0.5,0\}$，$K$ 为步长(如 32)。

**手算**：$R_A=1500, R_B=1500$，A 赢一局。
- $E_A = 1/(1+10^{0/400}) = 0.5$
- $R_A' = 1500 + 32(1 - 0.5) = 1516$；$R_B' = 1500 + 32(0-0.5)=1484$。
- 直觉：势均力敌时赢一局 +16，赢「弱者」加得少、赢「强者」加得多。Chatbot Arena 即用此法(实际用 Bradley-Terry 拟合更稳)。

### LLM-as-a-judge(可扩展但要防偏)

让强模型对答案打分或做 A/B 判断。**已知偏差与对策：**
- **位置偏差**：偏好排在前面的答案 → A/B 各跑一次取平均。
- **长度偏差**：偏好更长答案 → 控长或长度惩罚。
- **自我偏好**：偏好同家族模型 → 用第三方裁判 / 多裁判投票。
- **校准**：与人工标注算一致性(Cohen's κ / 与人评相关系数)，达标才信任。

**业务导向兜底**：若核心业务就是生成/改写/总结，应自建一套**业务指标**(如客服场景的解决率、改写的事实一致性 FactScore、摘要的关键信息覆盖率)，以业务需求为导向，而非套通用 benchmark。

## 6. 推理性能指标(部署最看重)

> 详见 [[llm-eval/llm-performance/大模型场景下训练和推理性能指标名词解释]]。

LLM 推理分两阶段，指标也由此而来：

```
请求到达
  │
  ├─ Prefill(预填充)：并行处理全部 prompt，算出 KV cache，吐出第 1 个 token
  │       └────────► TTFT(Time To First Token) = 排队 + prefill 时间
  │
  └─ Decode(解码)：自回归一次一个 token
          token2 ─ token3 ─ ... ─ tokenN
          └─每相邻两 token 间隔─► TPOT / ITL
```

| 指标 | 定义 | 直觉 | 受什么影响 |
|------|------|------|-----------|
| **TTFT** | 首 token 延迟 | 用户「等多久看到第一个字」 | prompt 长度、排队、prefill 算力 |
| **TPOT** | 每输出 token 平均时间(=ITL 均值) | 「打字快慢」 | KV cache、显存带宽、batch |
| **ITL** | Inter-Token Latency，相邻 token 间隔 | TPOT 的逐点版 | 同上 |
| **E2E 延迟** | 整条请求总耗时 | = TTFT + (N_out−1)×TPOT | 输出长度 |
| **吞吐(Throughput)** | 系统每秒总输出 token(所有并发求和) | 「服务器产能」 | batch、并发、调度 |
| **Goodput** | 满足 SLO 前提下的有效吞吐 | 「合格产能」 | SLO 阈值 |
| **QPS/RPS** | 每秒完成请求数 | 业务侧吞吐 | 请求长度分布 |

**核心公式(必背)：**

$$\text{E2E} = \text{TTFT} + (N_{out}-1)\times \text{TPOT}$$
$$\text{单请求生成速度} = \frac{1}{\text{TPOT}}\ \text{(tokens/s)}$$
$$\text{系统吞吐} = \sum_{\text{并发请求}} \text{生成速度} \approx \frac{B \times N_{out}}{\text{总时间}}$$

**为什么吞吐 ≠ 1/TPOT × 用户数那么简单？** 因为 batch 越大，单请求 TPOT 会变慢(显存带宽被分摊)，但**系统总吞吐上升**——这就是**吞吐 vs 延迟的根本矛盾(throughput-latency tradeoff)**：

```
吞吐↑                              单请求TPOT(延迟)↑
  │        ____________             │           ________
  │      /                          │          /
  │    /     batch越大              │        /   batch越大
  │  /       吞吐越高               │      /     用户感觉越慢
  └──────────────► batch size       └──────────────► batch size
       两条曲线反向 → 必须按 SLO 选工作点
```

**手算 E2E**：TTFT=200ms，TPOT=20ms，输出 256 token：
$$\text{E2E} = 200 + (256-1)\times 20 = 200 + 5100 = 5300\text{ms} \approx 5.3\text{s}$$
单请求速度 $=1000/20 = 50$ tokens/s。

## 7. MFU / HFU——算力到底用了多少？

**MFU(Model FLOPs Utilization)** = 实际有效算力 / 硬件峰值算力。回答「我这张卡的算力榨出了百分之几」。

**第一步：一次前向，每 token 的 FLOPs。** 对 $N$ 参数稠密模型，经验公式：前向约 $2N$ FLOPs/token(每个参数一次乘 + 一次加)，训练含反向约 $6N$ FLOPs/token。

**第二步：推理 MFU。**
$$\text{MFU} = \frac{2N \times \text{吞吐(tokens/s)}}{\text{GPU峰值FLOPS} \times \text{GPU数}}$$

**逐数手算(推理)。** 7B 模型($N=7\times10^9$)，单张 A100 峰值 BF16 = 312 TFLOPS，实测吞吐 2000 tokens/s：
- 有效算力 $= 2N \times 2000 = 2\times 7e9 \times 2000 = 2.8\times10^{13} = 28$ TFLOPS
- $\text{MFU} = 28 / 312 = 8.97\% \approx 9\%$

> 推理(尤其小 batch decode)MFU 普遍低(常 <10%)，因为 decode 是**访存受限**(memory-bound)：每步要把全部权重从显存搬到计算单元，算得快但搬得慢，算力闲置。**这是面试高频点**——decode 阶段瓶颈是显存带宽不是算力，故要靠 batch / 量化 / KV cache 优化提利用率。

**训练 MFU 手算。** 用 $6N$：
$$\text{MFU}_{train} = \frac{6N \times \text{吞吐}}{\text{峰值} \times \text{卡数}}$$
175B 模型、1024×A100、实测 150 tokens/s/卡总 ~150k tokens/s：有效 $=6\times1.75e11\times1.5e5=1.575e17=157.5$ PFLOPS；峰值 $=312\text{T}\times1024=0.32$ EFLOPS；MFU≈49%(大模型训练 40~55% 算优秀)。

**HFU(Hardware FLOPs Utilization)**：算上重计算(activation recomputation)等「重复但必要」的 FLOPs，HFU ≥ MFU。MFU 看「有用功」，HFU 看「硬件真在算的功」。

## 8. 压测方法论

**目标**：在**满足 SLO** 的前提下，找到系统能扛的**最大并发 / 最高吞吐**，并定容量。

```
压测闭环：
 ┌─────────┐   固定/递增   ┌──────────┐    采集      ┌──────────┐
 │ 负载生成 │ ──并发&请求率─►│ 推理服务  │ ──指标──────►│ 指标分析  │
 │(数据集)  │              │(vLLM/TGI)│              │P50/P90/P99│
 └─────────┘               └──────────┘              └──────────┘
      ▲                                                    │
      └──────────── 调整并发，画 吞吐-延迟 曲线 ◄───────────┘
```

**步骤：**
1. **定 SLO**：如 TTFT P99 ≤ 1s、TPOT P99 ≤ 50ms。指标必看**分位数(P50/P90/P99)**，不能只看均值(长尾才是体验杀手)。
2. **构造真实负载**：用真实输入/输出长度分布(prompt 长、output 长直接决定 prefill/decode 配比)；常用 ShareGPT 等数据集。固定输入还是泊松到达要说清。
3. **两种打法**：
   - **闭环(closed-loop)**：固定并发数 C，每个并发完成后立即发下一条 → 测系统极限吞吐。
   - **开环(open-loop)**：按固定请求率 λ 泊松发包 → 测真实流量下延迟，能暴露排队爆炸点。
4. **扫并发画曲线**：从低到高加并发，记录 (吞吐, P99 延迟)。找到**拐点**——延迟开始陡升处即为最大可用并发。
5. **报告**：吞吐、Goodput、TTFT/TPOT 的 P50/P99、MFU、显存占用、错误率。

```
   P99延迟
     │                          ╱← 排队爆炸(超过容量)
     │                        ╱
     │       SLO线 ─ ─ ─ ─ ╱─ ─ ─ ─
     │  ____________╱   ↑ 拐点=最大可用并发
     │ /
     └──────────────────────────► 并发/请求率
```

**常用工具**：vLLM `benchmark_serving`、`llmperf`、`genai-perf`、`locust`/`wrk` 自定义。

**压测陷阱：**
- 只测均值不测 P99 → 上线被长尾打脸。
- 输入输出长度不真实 → prefill/decode 配比错，吞吐数字无意义。
- 预热不足(冷启动、CUDA graph 未捕获、KV cache 未稳态)→ 头部数据偏差，要丢弃 warmup。
- 客户端成瓶颈(单机发包能力不够)→ 误判服务端上限。

## 9. 端到端数值示例(串一遍)

**场景**：13B 模型，单 A100(312 TFLOPS BF16)，并发 32，平均输入 512 token、输出 256 token。实测 TTFT P99=600ms、TPOT P99=25ms、系统吞吐 4000 tokens/s。

1. **单请求 E2E** = 600 + (256−1)×25 = 600 + 6375 = **6975ms ≈ 7s**。
2. **单请求速度** = 1000/25 = **40 tokens/s**；32 并发理论上限 32×40=1280？但实测 4000 → 说明 batch 内并行 + prefill 贡献，**吞吐由系统调度而非简单相乘决定**。
3. **推理 MFU** = (2 × 13e9 × 4000) / 312e12 = 1.04e14/3.12e14 = **33.3%**（含 prefill 的混合负载，比纯 decode 高）。
4. **是否达标**：若 SLO 是 TTFT≤1s、TPOT≤50ms，则 P99(600ms/25ms)均满足 → 此并发下 **Goodput = 4000 tokens/s**。继续加并发直到 P99 触 SLO 线即为容量上限。

## 10. 面试问答清单(高频题→踩点答→追问)

| 高频问题 | 踩点答案(要点) | 追问 |
|----------|----------------|------|
| 困惑度是什么、怎么算 | $\exp$(平均负对数似然)；平均分支数直觉；越低越好；同 tokenizer 才可比 | PPL 低=模型好吗？(否，不等于下游/对齐好) |
| 准确率 vs F1 vs EM 区别 | acc=对/总；EM 全等才对；F1=2PR/(P+R)，给部分重叠分 | 抽取式QA为何用F1？ |
| pass@k 怎么定义 | $1-\binom{n-c}{k}/\binom{n}{k}$，多采样估计 | 为什么不能直接跑1次？(方差大) |
| 开放写作怎么评 | BLEU/ROUGE 不对齐人类需求；用人评/Elo/LLM-judge/业务指标 | LLM-judge 有哪些偏差？(位置/长度/自我偏好) |
| 什么是 TTFT/TPOT | TTFT=首token(prefill)；TPOT=每token(decode)；E2E=TTFT+(N−1)TPOT | 为什么 prefill 快 decode 慢？ |
| prefill vs decode 瓶颈 | prefill 算力受限(compute-bound)；decode 访存受限(memory-bound) | 怎么提 decode 利用率？(batch/量化/PagedAttn) |
| 吞吐和延迟矛盾吗 | 是；batch↑→吞吐↑但单请求TPOT↑；按 SLO 选工作点 | 怎么兼顾？(continuous batching/chunked prefill) |
| MFU 怎么算、为什么推理低 | (2N×吞吐)/峰值；推理 decode memory-bound 故常<10% | HFU 与 MFU 区别?(HFU 含重计算) |
| 如何压测一个推理服务 | 定SLO→真实长度分布→扫并发→看P99→画吞吐-延迟曲线→找拐点 | 为什么必须看P99不看均值? |
| 评测集怎么防作弊 | 数据污染检测(n-gram重叠/改写重测)；榜单+线上A/B+人评 | few-shot数不同能比吗?(不能) |

**一分钟总结模板(背)：** 「评测分**质量**和**性能**两层。质量上，判别任务用准确率/F1，生成任务用 pass@k、困惑度，开放写作 BLEU/ROUGE 不对齐人类需求，靠 Elo / LLM-judge / 业务指标。性能上，LLM 推理分 prefill 和 decode，对应 **TTFT** 和 **TPOT**，E2E=TTFT+(N−1)·TPOT；系统看**吞吐**和 **MFU**，decode 是访存受限所以推理 MFU 常很低。压测要定 SLO、用真实长度分布、扫并发画吞吐-延迟曲线找拐点，重点看 **P99** 不看均值。」
