## 0. 一句话锚点

**MaaS = 推理引擎 + 一层"运营外壳"。** 推理引擎（vLLM / TGI / SGLang 等）负责"算得快"；运营外壳负责"卖得出、管得住、看得见"——也就是 **鉴权、限流、计费、多租户、路由、可观测**。本文只讲外壳；引擎本身见 [[llmops/模型推理平台方案]]。

一个最朴素的类比：

```
                 你已经会"做菜"(模型推理)
MaaS 要解决的是   ┌──────────────────────────────────────┐
                 │ 怎么开成一家"餐厅":                    │
                 │  - 谁能进门 (鉴权)                     │
                 │  - 每桌点菜上限 (限流)                  │
                 │  - 按菜结账、月底对账 (计费)            │
                 │  - 包厢/散座互不打扰 (多租户)          │
                 │  - 同一道菜可换不同厨师 (路由)          │
                 │  - 后厨监控大屏 (可观测)               │
                 └──────────────────────────────────────┘
```

## 1. 地基/前置

### 1.1 从 IaaS 到 MaaS：抽象层层抬高

云计算的本质是"把某一层资源标准化后按需出租"。每抬高一层，用户要操心的东西就更少：

```
你管的部分(深色)随抽象层升高而减少：

IaaS  ┃ 机房 网络 服务器 ┃ 操作系统 运行时 应用 数据   ← 你管 OS 往上全部
PaaS  ┃ 机房 ... 运行时  ┃ 应用 数据                  ← 你只管应用+数据
SaaS  ┃ 机房 ... 应用    ┃ (只用)                     ← 你只用，不管实现
MaaS  ┃ 机房 ... 模型权重 推理引擎 ┃ Prompt + 用量      ← 你只管"问什么"
         └────── 平台方负责 ──────┘  └─ 你负责 ─┘
```

**MaaS 的独特之处**：被出租的"资源"不是 CPU/磁盘，而是**一次模型推理（一次 forward）**，计价单位是 **Token** 而非时间或容量。这带来三个与传统云不同的特性：

1. **无状态**：每次请求自带全部上下文（messages），服务端不保存会话。便于水平扩展，但长上下文要重复传输。
2. **计量颗粒极细**：按"字"（Token）收费，必须精确到每请求记录用量。
3. **资源极贵且稀缺**：单位是 GPU 而非廉价 CPU，所以**限流和调度**比传统 Web 服务重要得多。

### 1.2 控制面 vs 数据面（必须先分清的心智模型）

```
控制面 (Control Plane)：低频、管理类
  注册租户 / 发 API Key / 设配额 / 配模型路由 / 看账单
                      │ 下发配置
                      ▼
数据面 (Data Plane)：高频、每请求都走
  收请求 → 鉴权 → 限流 → 路由 → 推理 → 计量 → 返回
```

下文 3~6 节几乎都在讲数据面上的"每请求动作"；7~8 节讲数据面的"接口形状与去向"；9~10 节讲交付形态与观测，横跨两面。

## 3. API 网关：所有请求的唯一入口

### 3.1 是什么 / 解决什么

API 网关是一个**反向代理 + 策略执行点**。它解决的核心问题是：**把"横切关注点"从模型服务里抽出来，集中处理一次**。否则每个推理实例都要自己实现鉴权、限流、计费，既重复又容易不一致。

### 3.2 核心机制（一次请求穿过网关的内部流水线）

```
请求进来
  │
  ├─[1] TLS 终止        : 解 HTTPS，拿到明文 HTTP
  ├─[2] 鉴权            : 校验 Authorization: Bearer sk-xxx → 找到租户
  ├─[3] 协议适配/校验    : 解析 OpenAI 风格 body，校验 model/messages
  ├─[4] 限流            : 查该租户 RPM/TPM 是否超额(见 §4)
  ├─[5] 路由            : 按 model 字段+策略选一个后端(见 §8)
  ├─[6] 转发            : 反向代理到后端；流式则边收边转 SSE
  ├─[7] 计量            : 累加 prompt_tokens / completion_tokens(见 §5)
  └─[8] 响应/异常       : 正常回包，或降级/重试/返回错误码
```

### 3.3 鉴权：API Key 的本质

最常见的是 **API Key（Bearer Token）**。它本质是"一段随平台预生成的、与某租户绑定的随机串"。请求头里携带：

```
Authorization: Bearer sk-9f2a...c71
```

网关侧不应明文存 Key，而存其**哈希**（如 SHA-256）。校验流程：

```
收到 sk-xxx ──hash──▶ 查哈希表 ──命中──▶ 取出 {租户ID, 权限, 配额}
                                  └未命中─▶ 401 Unauthorized
```

为什么哈希存储？即使配置库泄露，攻击者也无法逆推出可用的 Key（哈希单向）。更高安全场景用 **JWT**（自带签名和过期时间，网关无需查库即可验真）或 mTLS。

### 3.4 流式转发（SSE）——LLM 网关的特殊点

普通 API 是"请求-等待-完整响应"。LLM 要"边生成边吐字"，用 **SSE（Server-Sent Events）**：响应头 `Content-Type: text/event-stream`，正文是一串 `data: {...}\n\n` 块，最后 `data: [DONE]`。网关**不能缓冲整包**，必须做到**逐块透传**（关闭代理缓冲），否则首 Token 延迟（TTFT）会被毁掉。

**实践要点**：流式下计费要在流结束时才能拿到 `completion_tokens`；若客户端中途断开，已生成部分通常仍要计费——需在网关侧记录已吐出的 Token 数。

## 4. 限流：保护稀缺的 GPU

### 4.1 为什么必须限流

GPU 是整套系统里最贵、最容易被打爆的资源。若不限流：单个租户的循环脚本就能占满显存与 KV Cache，导致**所有人**排队（队头阻塞）。限流把"公地悲剧"挡在门口。

### 4.2 两个维度：RPM 与 TPM

LLM 限流通常**双指标**并存：

- **RPM（Requests Per Minute）**：每分钟请求数。挡住"高频小请求"。
- **TPM（Tokens Per Minute）**：每分钟 Token 总量（输入+输出）。挡住"低频但超长上下文"的请求——这才是真正吃 GPU 算力与显存的源头。

只限 RPM 不够：1 个请求若塞 100K Token，照样能压垮后端。所以 **TPM 是 LLM 限流的灵魂**。

### 4.3 核心算法：令牌桶（Token Bucket）

```
        每秒匀速滴入 r 个令牌(r = 限额/60)
              │
              ▼
        ┌───────────┐  桶容量上限 = burst(允许突发)
        │ ●●●●●     │  当前令牌数
        └───────────┘
              │ 来一个请求, 预估需 n 个令牌
              ▼
        够 n 个? ──是──▶ 扣 n 个, 放行
                └否──▶ 拒绝(429 Too Many Requests) 或排队
```

为什么用令牌桶而非"固定窗口计数"？固定窗口在边界会出现**双倍突发**（窗口末尾+下个窗口开头瞬间放行 2 倍）。令牌桶以"匀速补充 + 桶容量"平滑了突发，又用 `burst` 容量保留了对短促峰值的友好度。

**TPM 的难点**：请求**发起时还不知道输出多少 Token**。常见做法：发起时按 `输入Token + 预估最大输出`（即 `max_tokens`）**预扣**令牌，请求结束按实际输出**回补差额**。这保证了悲观情况下也不会超卖 GPU。

### 4.4 超限后的行为（不是只有"拒绝"）

| 策略 | 含义 | 适用 |
|------|------|------|
| 拒绝 429 | 直接拒，附 `Retry-After` | 公有 API、防滥用 |
| 排队等待 | 放进等待队列，FIFO/优先级 | 内部平台、容忍延迟 |
| 降级路由 | 转到更小/更便宜模型 | 成本敏感、可接受降质 |
| 背压 | 向上游传递"慢一点"信号 | 全链路压力调节 |

## 5. 计费：把"一次推理"换算成"钱"

### 5.1 计费原子：Token

LLM 几乎都**按 Token 计费**，且**输入与输出分开定价**（输出通常更贵，因为它是逐个自回归生成的，占用解码步更多）。一次请求的费用：

$$\text{cost} = T_{in}\cdot p_{in} + T_{out}\cdot p_{out}$$

其中 $T_{in}$ 是 prompt（输入）Token 数，$T_{out}$ 是 completion（输出）Token 数，$p$ 是单价（通常以"每百万 Token"计，记为 /M tokens）。

### 5.2 用量从哪来：网关埋点

OpenAI 兼容响应体里自带 `usage` 字段，这是计费的**权威数据源**：

```
"usage": { "prompt_tokens": 1024, "completion_tokens": 256, "total_tokens": 1280 }
```

网关把每条请求的 `{租户, 模型, 时间戳, prompt_tokens, completion_tokens}` 写入**用量日志流**（如 Kafka → 计费库）。

### 5.3 计费数据流（双写：实时配额 + 离线对账）

```
请求结束
   │ usage
   ├──▶ 实时累加器(内存/Redis)  → 更新当期 TPM/额度, 触发限流
   │
   └──▶ 用量日志(持久化 append) → 离线按租户/天聚合 → 出账单
                                       │
                                  对账(实时累加器 vs 日志聚合应一致)
```

为什么要双写？实时累加器快但易丢（重启清零）；持久日志可靠但慢。两者对账可发现"漏计/重复计"。

### 5.4 计费模式对比

| 模式 | 计价 | 优点 | 缺点 |
|------|------|------|------|
| 按量付费（Token） | 用多少付多少 | 弹性、零起步成本 | 流量大时不可预测 |
| 预留/包月配额 | 预付固定额度 | 成本可控、可锁折扣 | 用不满则浪费 |
| 专属算力（按 GPU 时） | 包一段 GPU | 隔离、性能稳定 | 利用率低则贵 |

## 6. 多租户：在同一套设施上服务多个互不信任的用户

### 6.1 隔离的三个层次（由软到硬）

```
软 ←──────────────────────────────────────────────────▶ 硬
逻辑隔离          配额隔离            物理隔离
(同一进程,        (共享后端,          (独占 GPU/
 靠租户ID区分)     按租户限额公平)      命名空间/集群)
成本低/隔离弱      折中(主流选择)       成本高/隔离强
```

- **逻辑隔离**：所有租户共用同一推理后端，仅靠 `租户ID` 在日志/计费上区分。最省钱，但"吵闹邻居"（noisy neighbor）会互相影响。
- **配额隔离**：共享后端，但每租户有独立 RPM/TPM 与优先级，调度器保证**资源公平**。这是大多数 MaaS 的落点。
- **物理隔离**：高价值/合规客户独占一组 GPU（专属部署），彻底无干扰。

### 6.2 资源公平：避免"吵闹邻居"

仅有限额还不够，还需**调度时的公平**。常用思路：

- **加权公平队列（WFQ）**：按租户权重分配 GPU 时间片，高权重租户拿更多，但低权重也不会饿死。
- **优先级抢占**：付费等级高的请求可插队；但需防止低优先级**永久饥饿**（设最小保障份额）。

```
GPU 调度队列(按租户公平出队)：
   高优先级 ▸ [T1][T1][T3] ─┐
   普通     ▸ [T2][T4][T2] ─┼─▶ 加权轮转 ─▶ GPU
   保障份额 ▸ [T5] ─────────┘   (T5 即便低优, 也保留最小份额防饿死)
```

## 7. OpenAI 兼容标准：事实上的"通用插头"

### 7.1 为什么它成了标准

OpenAI 最早把 LLM API 形状定下来（`/v1/chat/completions` + `messages` 数组 + `usage` + SSE 流式）。生态里海量 SDK、Agent 框架、前端都按这个形状写。于是**所有人都去兼容它**——只要你的服务长得像 OpenAI，客户端**改一个 base_url 就能切过来**，迁移成本几乎为零。这是典型的"网络效应造就的事实标准"。

> 注：OpenAI 是 ChatGPT/GPT 的提供方，相关介绍见 [[llm-maas/OpenAI-ChatGPT]]；本仓库聚焦"如何提供一个 OpenAI 兼容的服务"，而非接入 OpenAI 本身。

### 7.2 接口的最小形状

```
POST /v1/chat/completions
Authorization: Bearer <key>

请求体(核心字段):
{
  "model": "qwen2-72b",                ← 选哪个模型(路由的依据)
  "messages": [{"role":"user","content":"你好"}],
  "stream": true,                       ← 是否 SSE 流式
  "max_tokens": 512, "temperature": 0.7 ← 解码参数
}

非流式响应:
{ "choices":[{"message":{...}}],
  "usage":{"prompt_tokens":.., "completion_tokens":..} }  ← 计费就靠它
```

兼容的好处对平台方同样成立：**你换底层引擎（vLLM→SGLang）或换模型，客户端无感知**——接口契约稳定，实现可自由演进。

### 7.3 兼容的边界（实践要点）

"OpenAI 兼容"是**接口形状兼容**，不代表行为完全一致：分词器不同导致同一句话 Token 数不同、`logprobs`/function-calling/JSON mode 等高级特性各家支持程度不一、错误码语义略有差异。**对外宣称兼容时，应明确支持的字段子集**（以各自官方文档为准，不要假定全字段可用）。

## 8. 路由多模型：一个入口，背后一片模型

### 8.1 是什么 / 解决什么

真实平台往往挂着 7B、72B、Embedding、第三方 API 等多个后端。**路由层**根据请求决定"这一发去哪打"，让客户端只面对一个统一入口。

### 8.2 路由依据与策略

```
请求(model="auto"/具体名)
        │
        ▼
   ┌─────────── 路由决策 ───────────┐
   │ 维度1: model 字段精确匹配       │
   │ 维度2: 负载/队列长度(选最闲)     │
   │ 维度3: 成本(优先便宜的够用模型)  │
   │ 维度4: 健康(避开熔断的后端)      │
   │ 维度5: 灰度/AB(按比例分流)       │
   └────────────┬───────────────────┘
                ▼
   ┌──────┬──────┬──────┬──────┐
   │ 7B   │ 72B  │ Embed│ 第三方│
   └──────┴──────┴──────┴──────┘
```

### 8.3 三个高价值场景

- **降级（Fallback）**：首选后端超时/熔断 → 自动转备用后端或更小模型，保证可用性而非完全失败。
- **灰度/A-B**：新模型先接 5% 流量，对比质量与延迟，平滑放量。
- **成本路由**：用一个小模型/规则先判断"难易"，简单请求走便宜模型，难的才上大模型（"模型级联"）。

**实践要点**：路由要带**熔断器**——某后端连续失败则短暂"跳闸"，停止往它发请求，避免雪崩；过一段时间放半开探测恢复。

## 9. 私有化 vs 云：两种交付形态

### 9.1 形态对比

```
        公有云 MaaS                     私有化 MaaS
  ┌────────────────────┐        ┌────────────────────┐
  │ 平台方机房 GPU      │        │ 客户机房/VPC        │
  │ 多租户共享          │        │ 单租户独占          │
  │ 调 API 即用/数据出域│        │ 整套交付/数据不出域 │
  └────────────────────┘        └────────────────────┘
```

### 9.2 权衡矩阵

| 维度 | 公有云 MaaS | 私有化部署 |
|------|------------|-----------|
| 数据主权/合规 | 数据出域，受平台政策约束 | 数据不出域，满足金融/政务强合规 |
| 起步成本 | 近乎零，按量付费 | 高（采购 GPU + 实施） |
| 弹性 | 极强，秒级扩容 | 受限于自有硬件上限 |
| 运维负担 | 平台方承担 | 自己承担（升级/排障/调优） |
| 单位成本 | 流量大时偏贵 | 高利用率下长期更省（TCO 优） |
| 上新模型 | 平台更新即可用 | 需自行下载、适配、压测 |

### 9.3 选型经验法则

- **数据敏感 + 长期高利用率** → 私有化（金融、政务、医疗）。
- **快速验证 + 流量不确定 + 弱合规约束** → 公有云。
- **常见混合**：核心敏感链路私有化，长尾/突发流量溢出到公有云（hybrid burst）。

## 10. 可观测：让黑盒变透明

### 10.1 三大支柱 + LLM 特有维度

通用可观测有三支柱，MaaS 还要叠加 LLM 专属指标：

```
Metrics(指标, 数值/趋势)  ┐
Traces (链路, 一次请求走过哪些节点) ┼─ 通用三支柱
Logs   (日志, 原始事件)   ┘
        +
LLM 专属: TTFT(首Token延迟) / TPOT(每Token延迟) / Token吞吐
          / GPU利用率 / KV-Cache占用 / 队列等待 / 每请求成本
```

### 10.2 一次请求的可观测埋点

```
client → [网关] → [限流] → [路由] → [推理后端] → client
   │        │        │        │          │
  span    span     span     span       span     ← Trace 串成一条链
   └────────┴────────┴────────┴──────────┘
   每段记: 耗时、租户、模型、token数、状态码 → Metrics + Logs
```

### 10.3 必看的几个 LLM 指标（含义 / 为何重要）

| 指标 | 含义 | 为何关键 |
|------|------|---------|
| TTFT | 从请求到吐出第 1 个 Token | 直接决定"卡不卡"的体感（流式场景的首屏） |
| TPOT | 生成每个后续 Token 的平均间隔 | 决定"打字速度"是否流畅 |
| 吞吐 | 单位时间总输出 Token | 衡量 GPU 是否被压满、成本效率 |
| KV-Cache 占用 | 上下文缓存吃掉的显存 | 接近上限会触发排队/OOM |
| 队列等待 | 请求在后端排队时长 | 飙升 = 容量不足，需扩容或限流 |
| 错误/降级率 | 429/5xx/降级占比 | SLO 健康度，触发告警 |

**实践要点**：把 `租户ID`、`模型名` 作为 Metrics 的**标签维度**，才能按租户/模型切片排查"是谁、是哪个模型在出问题"。同时注意 **Prompt/响应日志含敏感数据**，需脱敏或可关闭。

## 11. 数值例子 / 对照 / 实践

> 以下数字均为**便于理解的示意量级**，真实数值随模型/硬件/版本变化，**以官方文档与实测为准**。

### 11.1 TPM 限额够不够：一个手算

设某租户配额 **TPM = 60,000**。它的典型请求：输入 1,000 Token、输出 500 Token，合计 1,500 Token/请求。

$$\text{每分钟可处理请求数} = \frac{60{,}000}{1{,}500} = 40 \text{ 次/分}$$

若它想跑 60 次/分，则需 $60\times1500 = 90{,}000$ TPM，**超额 1.5 倍**，会被限流。结论：给客户报配额时，要用"**典型单请求 Token 数 × 期望 QPS**"反推 TPM，而不是只看 RPM。

### 11.2 一次请求的费用：手算

设输入价 $p_{in}=2$ 元/百万 Token、输出价 $p_{out}=6$ 元/百万 Token（输出更贵）。某请求 $T_{in}=1000$、$T_{out}=500$：

$$\text{cost} = \frac{1000}{10^6}\times 2 + \frac{500}{10^6}\times 6 = 0.002 + 0.003 = 0.005 \text{ 元}$$

即半分钱。若该租户一天 100 万次这样的请求：$100\text{万} \times 0.005 = 5000$ 元/天。**对账核对**：账单库按 `usage` 聚合应得到同一数字，若实时累加器只算出 4800 元，差额 4% 就是"漏计/丢点"，需排查埋点。

### 11.3 单卡能承载多少租户：粗估

设一张 GPU 实测稳定输出吞吐约 **2,000 Token/s**（示意值，约，以实测为准），即 $2000\times60=120{,}000$ Token/分。若每租户配额 TPM=10,000 且平均只用到一半（5,000）：

$$\text{可超售租户数} \approx \frac{120{,}000}{5{,}000} = 24 \text{ 个}$$

这就是**超售（oversubscription）**：因为不是所有租户同时打满，可把配额总和设得高于物理上限。但要靠**限流 + 公平调度**兜底，防止偶发"全员同时打满"打爆后端。

### 11.4 选型速查

```
要不要自建 MaaS 外壳, 还是直接用现成平台?
  流量小/快速验证 ───────────▶ 直接调公有云 MaaS
  有合规/数据不出域要求 ──────▶ 私有化 + 自建外壳
  多模型/要统一计费治理 ──────▶ 自建网关层(本文这套), 引擎用 vLLM/SGLang
  只想要推理引擎本身 ─────────▶ 见 [[llmops/模型推理平台方案]]
```

### 11.5 落地清单（最小可用 MaaS 的待办）

引擎暴露 OpenAI 兼容接口（§7）→ 前置网关做鉴权+限流（RPM/TPM 双指标、令牌桶，§3/§4）→ 用量埋点写日志流再计费对账（§5）→ 多租户配额与公平调度（§6）→ 模型注册表+路由+熔断降级（§8）→ 接入 Metrics/Trace/Logs 与 LLM 专属指标告警（§10）。

## 常见问题

| 问题 | 简答 |
|------|------|
| MaaS 和 LLMOps 是一回事吗？ | 不是。MaaS 偏"对外卖服务"（网关/计费/多租户）；LLMOps 偏"全生命周期运维"（训练-评测-部署-监控）。两者在"推理平台"处交汇，见 [[llmops/模型推理平台方案]]。 |
| 为什么 LLM 限流要 TPM 而不只 RPM？ | 一个超长上下文请求就能吃满 GPU，RPM 拦不住它；TPM 才能约束真正的算力消耗（§4.2）。 |
| 输出 Token 为什么比输入贵？ | 输出是逐个自回归生成的，每个都要一次解码前向；输入可一次性并行编码，单位成本更低（§5.1）。 |
| 流式请求中途断开还计费吗？ | 通常已生成部分仍计费，需在网关记录已吐出的 Token 数（§3.4）。 |
| "OpenAI 兼容"是不是 100% 等价？ | 否，只是接口形状兼容；分词、高级特性、错误语义可能不同，宣称时要标明支持子集（§7.3）。 |
| 多租户怎么防"吵闹邻居"？ | 配额隔离 + 公平调度（WFQ/优先级+最小保障份额），高价值客户可上物理隔离（§6）；超售要靠它兜底（§11.3）。 |
