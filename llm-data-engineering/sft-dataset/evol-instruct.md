## 0. 一句话锚点

**Evol-Instruct = 用 LLM 把"简单指令"自动重写成"更难/更杂的指令"，再用 LLM 生成答案，组成 (指令, 答案) 训练对。**

它要解决的痛点：人写指令又慢又贵，而且人类天然倾向写"中等难度、常见主题"的指令 —— 高难度、长尾主题的样本严重不足。Evol-Instruct 让机器沿两个正交方向"进化"指令：

```
        ┌──────────────── 广度进化 (In-Breadth) ────────────────►  话题更广
        │                "换一个全新主题/领域的同难度指令"
        │
难度↑   │   ● 种子指令 (简单、常见)
        │
        ▼
       深度进化 (In-Depth)
       "加约束 / 加推理步骤 / 更具体 / 更复杂输入"  ──►  同主题但更难
```

记住两个词就够：**In-Depth(变难)** 与 **In-Breadth(变多样)**。

## 1. 地基 / 前置

### 1.1 什么是 SFT 数据
SFT(Supervised Fine-Tuning，监督微调)需要成对样本：`{"instruction": 指令, "output": 期望回答}`(格式细节见 [[llm-data-engineering/sft-dataset/数据格式设计]])。模型学的是"看到这种指令该怎么答"。数据的**难度分布**和**主题覆盖**直接决定模型上限。

### 1.2 为什么"难度"是稀缺资源
设想把所有可能的指令按复杂度排队：

```
指令数量
  ▲
  │        ██
  │      ██████              人类标注/网上爬取的指令
  │     ████████             天然集中在"中等难度"
  │    ██████████
  │  ██            ▁▁        ← 高难度长尾几乎为空
  └────────────────────────►  复杂度
   简单   中等        困难
```

- 简单指令：模型早就会了，再多也没增量。
- **困难指令**：能逼模型学会多步推理、遵守多重约束 —— 但人类很少写，是真正的稀缺品。
- Evol-Instruct 的价值，就是**人为把分布往右(高难度)和往两侧(多主题)拉**。

### 1.3 它跟 Self-Instruct 的关系
- **Self-Instruct**：给少量种子，让 LLM"仿写"出更多**同档次**的新指令 —— 扩的是**数量**。
- **Evol-Instruct**：拿已有指令，让 LLM**改写得更难/更不同** —— 扩的是**难度与多样性**。
- 二者可叠加：先 Self-Instruct 铺量，再 Evol-Instruct 提质。WizardLM 就是用 Evol-Instruct 进化 Alpaca 的 52K 种子起家的。

## 2. 总览：进化数据流(闭环)

Evol-Instruct 是一个**迭代闭环**：每一轮把池子里的指令各进化一次，生成答案，过滤掉失败的，把成活的并回池子，作为下一轮的新种子。

```
        ┌───────────────────────────────────────────────────────┐
        │                                                       │
        ▼                                                       │
 ┌─────────────┐   挑一个   ┌──────────────┐                    │
 │  指令池 D_t  │ ────────► │  进化器 LLM   │                    │
 │ (种子/上一轮) │           │ Instruction  │                    │
 └─────────────┘           │   Evolver    │                    │
                           └──────┬───────┘                    │
            随机选一个进化方向 ↓     │                          │
   ┌────────────────────────────┐  │                          │
   │ In-Depth: 加约束/深化/具体化 │  │                          │
   │          /推理/复杂输入      │  ▼                          │
   │ In-Breadth: 换全新主题       │ 进化后指令 i'                │
   └────────────────────────────┘  │                          │
                                    ▼                          │
                            ┌──────────────┐                    │
                            │  回答器 LLM   │ 生成答案 o'        │
                            │  (Generator) │                    │
                            └──────┬───────┘                    │
                                    ▼                          │
                            ┌──────────────┐  失败→丢弃          │
                            │ 淘汰器 LLM    │ ─────────►✗        │
                            │ (Eliminator) │                    │
                            └──────┬───────┘  通过 (i', o')      │
                                    └───────── 并回池 D_{t+1} ───┘
```

一句话：**选 → 进化 → 答 → 淘汰 → 入池**，重复 M 轮(典型 4~6 轮)。

## 3. 深度进化 In-Depth：把指令"变难"

In-Depth Evolving 用 5 类"变难算子(mutation)"。核心要求：**只让指令更难,不能让人类无法理解或无法回答**。

```
       ┌─────────────── In-Depth 五算子 ───────────────┐
       │ ① Add Constraints   加约束/限制条件            │
       │ ② Deepening         深化(把浅问题问深)          │
       │ ③ Concretizing      具体化(泛化→具体实例)        │
       │ ④ Increase Reasoning 增加推理步骤(显式多步)      │
       │ ⑤ Complicate Input  复杂化输入(加表格/代码/数据)│
       └───────────────────────────────────────────────┘
```

逐个拆(配同一条种子 `写一个排序函数`)：

| 算子 | 含义 / 怎么变难 | 例子(种子→进化) |
|---|---|---|
| ① 加约束 | 增加必须满足的限制条件 | →`写一个排序函数，**不准用内置 sort，且时间复杂度 O(n log n)，原地排序**` |
| ② 深化 | 把"广度问题"换成"深度问题"，要求更深的解释/原理 | →`写排序函数，并**解释为何该算法在近乎有序数据上更快**` |
| ③ 具体化 | 把抽象概念替换成具体场景/实例 | →`给**一个含 100 万条订单记录、按时间戳**的数组排序，内存受限 256MB` |
| ④ 增加推理步骤 | 显式要求"分步推理/给出推导" | →`**逐步推导**该排序的最坏复杂度，并写出递推式与求解过程` |
| ⑤ 复杂化输入 | 在指令里嵌入表格/代码/JSON/公式等结构化数据 | →`下面是一段**有 bug 的排序代码 ```...```**，找出错误并修复` |

**关键约束(Prompt 里要写死)**：
- 进化后指令的"难度增量"要**适中**——加太多反而让指令离谱、无法回答(下一节"质量控制"会淘汰这类)。
- 论文经验:每次进化让 prompt 字数**别超过原来约 +10~20 个词**的复杂度跳跃,避免一步登天。
- 进化器 Prompt 通常这样写(示意，以官方实现为准)：

```
I want you act as a Prompt Rewriter.
你的目标是把 #Given Prompt# 重写成更复杂的版本，让顶尖 AI 也更难回答。
但重写后的 prompt 必须合理、能被人类理解和回答。
你应当用以下方法让它更难：{在五算子里随机抽一个}
重写时增加的内容不超过 10~20 个词。
#Given Prompt#: {原指令}
#Rewritten Prompt#:
```

## 4. 广度进化 In-Breadth：把主题"变多样"

In-Depth 只在**同一主题**里挖深；如果一直深挖，池子会越来越窄(都在排序/算法)。In-Breadth 负责**横向开疆**：基于一条指令，生成一条**全新主题、同等难度**的指令。

```
   原指令(编程/排序)
        │  In-Breadth mutation
        ▼
   ┌─────────────────────────────────────────┐
   │ "受其启发，写一条全新领域、罕见、同难度的指令" │
   └─────────────────────────────────────────┘
        ├─► 法律：起草一份含 3 个对赌条款的并购协议要点
        ├─► 化学：解释勒夏特列原理在工业合成氨中的应用
        └─► 文学：用十四行诗体裁写一首关于熵增的诗
```

In-Breadth Prompt 示意(以官方为准)：

```
I want you act as a Prompt Creator.
根据 #Given Prompt# 创作一个**全新的** prompt：
要求属于**更罕见的领域**、长度与难度与原 prompt 相当、且人类能理解和回答。
#Given Prompt#: {原指令}
#Created Prompt#:
```

**两个方向的分工**：

```
 In-Depth ──► 纵向：同主题 难度↑      (深度，挖井)
 In-Breadth ─► 横向：换主题 难度持平   (广度，开荒)
 合起来 ──► 既深又广，覆盖更大指令空间
```

每轮进化时**随机选**用 In-Depth 的某个算子还是 In-Breadth，从而池子在两个维度上同时扩张。

## 5. 为什么"提升指令复杂度"就能提升模型

直觉上"难题更有用"，但要讲清机制：

**(a) 难指令逼出难能力。** SFT 是模仿学习——模型只会它见过的指令类型。只喂简单指令，模型永远学不会"同时满足 4 个约束 + 多步推理"。难指令把"多约束遵循、多步推理、长上下文整合"这些能力**显式写进训练样本**。

**(b) 填补难度分布的右尾。** 回到 §1.2 的图，进化相当于把分布**主动往右搬**：

```
进化前  ██████▁▁▁▁▁          进化后  ▁▁▁██████████
        简    难                     简      难↑↑
```

模型在评测时遇到的真实用户问题往往偏难，训练分布与之对齐，泛化才好。

**(c) 复杂度是"信息密度"。** 一条带 3 个约束、需 5 步推理的指令，蕴含的"如何决策"的监督信号，远多于一条"今天天气怎样"。同样 N 条样本，平均复杂度越高，单位样本携带的能力信号越多 —— 这也是 WizardLM 用**更少但更难**的数据就超过同期模型的原因。

**(d) 经验证据。** WizardLM 用进化数据微调后，在高难度指令(GPT-4 自动评测、人评)上显著优于用 Alpaca/Vicuna 同量级简单数据训练的模型；难度桶越高，优势越大。

> 注意边界：复杂度不是越高越好。超过模型(或答案生成器)能力的指令会产出**错误答案**，反而污染数据 —— 所以必须配合 §7 的质量控制。

## 6. 自动构造 SFT 数据：完整 Pipeline

把前面拼成可落地的流水线。三个角色都可由同一个强 LLM(如 GPT-3.5/4，或自托管强模型)扮演：

```
角色分工
 ┌────────────────┬──────────────────────────────────────┐
 │ Instruction    │ 输入指令 → 输出"更难/更不同"的指令      │
 │  Evolver       │ (In-Depth 算子 或 In-Breadth)         │
 ├────────────────┼──────────────────────────────────────┤
 │ Response       │ 输入进化后指令 → 生成答案(SFT 的 output)│
 │  Generator     │                                      │
 ├────────────────┼──────────────────────────────────────┤
 │ Instruction    │ 判断这条进化是否"成功" → 失败则淘汰      │
 │  Eliminator    │                                      │
 └────────────────┴──────────────────────────────────────┘
```

伪代码：

```
pool = 种子指令集(如 Alpaca 52K，或 Self-Instruct 生成的)
all_data = []
for round in range(M):              # M ≈ 4~6 轮
    next_pool = []
    for inst in pool:
        op = 随机选(In-Depth 五算子 之一, In-Breadth)
        inst2 = Evolver(inst, op)            # 进化
        ans2  = Generator(inst2)             # 生成答案
        if not Eliminator(inst, inst2, ans2):# 质量门(见 §7)
            continue                          # 进化失败 → 丢弃
        next_pool.append(inst2)
        all_data.append((inst2, ans2))       # 入训练集
    pool = pool + next_pool                   # 旧+新都可继续进化
# all_data 即最终 SFT 数据(指令, 答案)
```

要点：
- **每轮都从"全部历史指令"里取**(或仅新进化的)，使难度逐层累加 —— 第 4 轮的指令可能已被加难 4 次。
- 答案由强模型生成；若有人工/更强模型复核会更干净。
- 进化与生成是**两次独立调用**，便于分别替换模型与做缓存。

## 7. 质量控制：不让"坏进化"污染数据

Evol-Instruct 的成败全在过滤。论文称之为 **Elimination Evolving**，进化"失败"满足任一条即淘汰：

```
 ┌──────────────────────── 淘汰规则 ────────────────────────┐
 │ R1 没增信息：进化后与原指令相比没有提供新信息(用 LLM 判)  │
 │ R2 太难没法答：答案里出现"sorry/无法/不知道"等回避，       │
 │     或答案长度 ≤ 极短阈值(模型答不动)                      │
 │ R3 只是复读：答案只包含 prompt 里的标点/停用词，没实质内容 │
 │ R4 拷贝指令：进化时把"请重写/#Rewritten#"等提示词泄漏进指令│
 └─────────────────────────────────────────────────────────┘
```

除了这 4 条，工程上还要叠加：

```
 进化产物
   │
   ├─► 去重：与池内已有指令做相似度(嵌入余弦/最小哈希)，过近则删
   │
   ├─► 难度封顶：太长/嵌套太深的指令丢弃(避免坍缩成乱码)
   │
   ├─► 数据污染检查：剔除与评测集(MMLU/GSM8K 等)重叠的指令
   │
   ├─► 答案校验：可执行的(代码/数学)跑一遍验证，错误则丢
   │
   └─► 安全过滤：有害/越狱指令剔除
```

**为什么必须严过滤**：进化是迭代的，一条坏样本若进池，下一轮会被继续进化、误差**逐层放大**(error compounding)，最终让数据集坍缩。质量门把每轮的坏样本就地拦下，是闭环能稳定运行的前提。

## 数值例子 / 对照 / 实践

### 例 1：一条指令进化 4 轮(手算难度累加)
种子：`写一封请假邮件`(难度记为 1)

```
轮次  选中算子            进化后指令(摘要)                         难度
0    —                  写一封请假邮件                            1
1    In-Depth 加约束     写一封请假邮件，正式语气、≤120字、含交接   2
2    In-Depth 具体化     给德国总部上司、跨时区、附医生证明的英文版  3
3    In-Breadth 换主题   (受启发)写一封并购尽调延期的正式商务函     3
4    In-Depth 增推理     并附"为何延期合理"的 3 点逻辑论证          4
```

一条种子产出了 4 条难度递增、且跨了主题的新样本。

### 例 2：数据规模估算
设种子 $N_0 = 52{,}000$，进化 $M = 4$ 轮，每轮**每条指令进化一次**且淘汰率约 $r = 30\%$。则每轮新增成活样本：

$$\text{新增}_t = N_{t-1}\times(1-r),\qquad N_t = N_{t-1}+\text{新增}_t$$

逐轮(只算新增进 SFT 的，近似)：

$$52000 \times 0.7 \times 4 \approx 145{,}600 \text{ 条进化样本}$$

加上种子，量级约 **20 万条**。WizardLM 实际约用 25 万级别的进化指令(以论文为准)。

### 例 3：API 调用成本直觉
每条进化样本约需 **2 次** LLM 调用(1 次进化 + 1 次生成答案)，淘汰判定再 ~1 次。20 万样本 × 4 轮 ≈ **百万级**调用 —— 成本主要在这。所以实践中常**缓存**、**批量并发**，并用便宜模型先粗筛、贵模型只生成最终答案。

### 对照：Evol-Instruct vs 同类造数据法

| 方法 | 扩什么 | 难度可控? | 多样性来源 | 代表 |
|---|---|---|---|---|
| Self-Instruct | 数量 | 否(同档) | 种子 + 采样 | Alpaca |
| **Evol-Instruct** | **难度+主题** | **是(算子可选)** | In-Depth/In-Breadth | WizardLM |
| 人工标注 | 质量 | 是(但慢/贵) | 标注员 | OpenAI SFT |
| 蒸馏(直接抄强模型回答) | 质量 | 否 | 强模型分布 | Vicuna |

### 实践要点
- **进化器越强越好**：进化质量受限于进化器 LLM 的能力，弱模型造不出真正难的好指令。
- **In-Depth/In-Breadth 配比**：偏深易窄、偏广易浅；常见做法是大头给 In-Depth、小比例 In-Breadth 保多样。
- **轮数别太多**：4~6 轮后边际收益递减且坏样本累积，及时停。
- **答案质量是天花板**：SFT 学的是答案；指令再难，答案错就是负样本。可执行/可验证的任务(代码/数学)优先上自动校验。
- **务必做污染检查**：进化可能"撞上"评测题，发布前用 n-gram/嵌入比对评测集。

## 常见问题

| 问题 | 解答 |
|---|---|
| Evol-Instruct 和 Self-Instruct 区别? | 前者改写**已有**指令使其更难/更杂(提质)，后者从种子**仿写**新指令(增量)。常叠加用。 |
| 进化几轮合适? | 典型 4~6 轮；再多边际收益低且坏样本累积，难度也会失控。 |
| 为什么要 In-Breadth，光加难不行吗? | 只 In-Depth 会让池子主题坍缩(全是同领域)；In-Breadth 保证主题覆盖广。 |
| 进化后指令"无法回答"怎么办? | 由 Eliminator(R2)淘汰：答案含回避语/过短即判失败丢弃。 |
| 答案由谁生成? | 同一个强 LLM(Generator 角色)生成，可叠加更强模型或人工复核。 |
| 复杂度越高越好吗? | 不是。超过生成器能力会产出错答污染数据，必须封顶+过滤。 |
| 数据污染如何防? | 进化产物与评测集做 n-gram/嵌入重叠检测，命中即剔除。 |
