# 数值精度：为什么 softmax 要减最大值

> **一句话**：减最大值不是优化，是不减就会拿到 nan 的必要操作。
> **前置**：[[02-自回归解码为什么是访存瓶颈]]（本篇会重新用到它 `analytic_cost()` 里的 `dtype_bytes` 参数）

## 0. 这一篇要解决什么问题

"softmax 要减最大值"这句话你大概率也听过很多遍，通常是当作一条"数值稳定性技巧"顺带提一句，
配一句"这样更稳定"就翻篇了。这一篇要打破的正是这种轻描淡写：**减最大值不是"更稳定"，
是"不这样就是 nan"**。这不是夸张的说法——`## 1` 会给出三行代码，你可以现在就打开一个
Python 解释器验证它。

这一篇要回答四个问题：

- 为什么"减一个常数"这个操作不会改变 softmax 的数学结果？（不是"经验上不会"，是能推出来的恒等式）
- 为什么偏偏要减**最大值**，而不是随便一个常数？
- fp32 / fp16 / bf16 这几种精度到底差在哪，什么时候会撞见"数字装不下"？
- 推理这条链路上，精度是在哪几个地方被选择的，为什么"累加的地方"通常要留一档余量？

推完这些之后会发现一件事：**为了避免 softmax 溢出，你付出的代价是要先完整扫一遍数据求
最大值，才能开始算 exp 和求和**。这次"先扫一遍"的代价，正是 `[[01-注意力从朴素到FlashAttention]]`
里 online softmax / FlashAttention 那套技术要精确消灭的东西——这一篇会在 `## 2` 末尾把这个引子
埋下去，具体怎么把注意力矩阵分块处理、怎么和 KV 缓存配合，留给那一篇。

而精度这件事本身，也不只是"数值会不会炸"这么简单——`## 2.7` 会把它和
[[02-自回归解码为什么是访存瓶颈]] 里推出的算术强度公式重新接上：**同一个模型、同一个 batch，
换一档精度就能让访存瓶颈的地板直接抬高一倍**，这条连接是本篇和上一篇之间的接口，也是"为什么
推理默认不用 fp32"这件事在算术强度视角下的完整答案。

## 1. 先看现象（可跑的代码/可算的数）

打开 Python 解释器（或者直接 `cd _lab && python3` 之后 `import numpy as np`），跑这三行：

```python
>>> import numpy as np
>>> np.exp(np.float32(800))
inf
>>> np.exp(np.float32(800)) / np.exp(np.float32(800))

```

第一行 `exp(800)` 在 fp32 下直接溢出成 `inf`——不是"数值不太稳定"，是这个数字在 fp32 这个格式
里根本装不下（`## 2.5` 会给出精确的临界点，大约是 89，`800` 只是让这一点显而易见）。
第二行更关键：**`inf / inf` 是一个没有定义的运算，IEEE 754 规定它的结果是 `nan`**。
而 `inf / inf` 正是朴素 softmax 里"某一项除以所有项之和"这个操作，当分子分母都溢出时会撞见的
形式。这不是理论风险，是三行代码就能现场复现的事故——而且一旦某个位置的注意力分数或 logit
在某次前向里恰好大到这个量级（模型没训好、某层没做归一化、某次异常输入……），**这个 nan 会顺着
后面所有的矩阵乘扩散下去，整条前向全部中毒**，不会报错，只会在某个位置突然开始输出乱码或者
恒定同一个 token。

对照着看一下不做这件事的"朴素版" softmax 会发生什么（这段代码不在 `_lab/` 里，用来做对比，
你可以直接粘贴进解释器验证）：

```python

...     return e / e.sum()
...
>>> softmax_unsafe(np.array([800.0, 801.0, 802.0], dtype=np.float32))
```

三项原本该给出一个正常的、和为 1 的概率分布（其中第三项概率最大，因为分数最高），实际吐出来的

## 2. 原理

### 2.1 先证明一个更一般的命题：`softmax(x) = softmax(x - c)` 对任意常数 `c` 成立

softmax 的定义：

```
softmax(x)_i = exp(x_i) / Σ_j exp(x_j)
```

现在看 `softmax(x - c)`，对任意实数 `c`（不要求是最大值，随便一个数都行）：

```
softmax(x - c)_i = exp(x_i - c) / Σ_j exp(x_j - c)
```

用指数的基本性质 `exp(a - c) = exp(a)·exp(-c)` 展开分子分母：

```
= [exp(x_i)·exp(-c)] / Σ_j [exp(x_j)·exp(-c)]
= [exp(x_i)·exp(-c)] / [exp(-c)·Σ_j exp(x_j)]      ← exp(-c) 是常数，可以从求和号里提出来
= exp(x_i) / Σ_j exp(x_j)                          ← 分子分母的 exp(-c) 约掉
= softmax(x)_i
```

**证毕，而且这个证明没有用到任何关于 `c` 的额外条件**——唯一用到的代数事实是
`exp(a-c)=exp(a)·exp(-c)`，`exp(-c)` 对求和号里的每一项都是同一个正的常数因子，
分子有一个、分母的每一项也各有一个，加权平均之后能整体约掉。**这意味着"减一个常数不改变
softmax 结果"对任意常数都成立，不是只对"最大值"这个特殊选择成立。** `_lab/tests/test_lab.py:79-82`
的 `test_softmax_shift_invariance` 就是这条命题的可执行版本，减的是 `12345.0` 这个随手选的数：

```python
x = np.array([[1.0, 2.0, 3.0]], np.float32)
assert np.allclose(M.softmax(x), M.softmax(x - 12345.0), atol=1e-6)
```

### 2.2 那为什么偏偏选 `c = max(x)`：把上溢彻底封死，顺带保证分母不会归零

既然任意常数都数学等价，接下来的问题就是纯粹的工程选择：**选哪个 `c` 能让计算机意义上的这次
计算最安全？** 答案是 `c = max(x)`，原因有两条，缺一不可：

1. **不可能上溢**。选了 `c = max(x)` 之后，对任意 `i` 都有 `x_i - c ≤ 0`（因为 `c` 本身就是最大值），
   所以 `exp(x_i - c)` 落在 `(0, 1]` 这个区间里——**不管原始的 `x` 有多大，减完之后送进 `exp()`
   的数永远不超过 0，永远不会溢出**。这是纯数学上的保证，不依赖"数字碰巧不够大"这种运气。
2. **分母不可能是 0**。取到最大值的那一项，`x_i - c = 0`，贡献 `exp(0) = 1`；
   其它项贡献的都是 `(0, 1]` 里的正数。所以 `Σ_j exp(x_j - c) ≥ 1`，**永远不会是 0**，
   也就不会出现 `0/0` 这种未定义的除法。这条经常被忽略，但它和"不上溢"同样重要——
   `## 6` 会给出一个具体会撞见分母变 0 的错误用法。

对比一下如果选别的常数会怎样：选 `c = 0`（也就是完全不减）就是 `## 1` 演示的那个溢出版本；
选 `c = mean(x)`（平均值而不是最大值）虽然能把数字整体拉低一些，但**不保证所有 `x_i - c ≤ 0`**——
只要某一项本来就比平均值大很多，减完均值之后依然可能是个很大的正数，依然会上溢。
**`max(x)` 是唯一一个能对"所有项都 ≤ 0"给出无条件保证的选择。**

### 2.3 代价：多扫一遍数据——这正是 online softmax 想省掉的东西

`c = max(x)` 数值上最安全，但它要求你先把 `x` 完整看一遍才能求出 `max`，然后才能开始算
`exp(x_i - c)` 和求和。也就是说朴素实现天然是**两遍扫描**：第一遍求 `max`，第二遍算
`exp` 再求和（如果算完 `exp` 之后还要归一化除以和，严格算是第三遍，但那一遍是逐元素的，
通常和第二遍能融合在一起写，核心的"必须先有 `max` 才能开始"这个依赖关系只挡在第一遍和第二遍之间）。

对于注意力机制，`x` 是一行长度为 `ctx_len` 的分数（某个 query 对所有历史 key 的打分）。
如果 `ctx_len` 很长，"必须先完整扫一遍才能开始算 `exp`"这件事就意味着**你没法一边算
`QK^T` 的分数一边就地做 softmax**——你得先把整行分数都算出来、存好、扫一遍求 `max`，
再回头做第二遍。这正是朴素注意力实现要把整个 `ctx_len × ctx_len` 的分数矩阵先物化出来的原因
之一，也正是 `[[01-注意力从朴素到FlashAttention]]` 要解决的问题：**能不能把这两遍扫描
合并成一遍，不用等看完整行就能开始算？**

### 2.4 边扫边修一次：online softmax 的最小实现

答案是可以，代价是每次遇到比当前记录更大的数时，要把已经累积的和"回头修正"一下。
维护两个状态：当前见过的最大值 `m`，以及**相对于这个 `m` 已经缩放过的累积和** `l`。
每来一个新元素 `xi`：

```
m_new = max(m, xi)
l     = l * exp(m - m_new) + exp(xi - m_new)   # 先把旧的和"重新对齐"到新的最大值，再加新项
m     = m_new
```

关键在中间那一步：如果这次 `xi` 刷新了最大值（`m_new > m`），旧的 `l` 是相对于**旧的** `m`
算出来的，直接加新项会对不齐参照点——所以先乘一个 `exp(m - m_new)`（这个数 `≤ 1`，因为
`m ≤ m_new`，不会引入新的溢出风险）把 `l` "缩放"到新的参照点下，再加上这一项相对新参照点
的贡献 `exp(xi - m_new)`。**全程只需要看一遍数据，每看到一个新元素就用它更新状态，
不需要事先知道整体的最大值是多少。** 最后用最终的 `m` 和 `l` 就能算出和朴素两遍扫描完全一样的
归一化结果：`exp(x_i - m) / l`。

用几行 numpy 验证它和朴素 softmax 给出一样的结果（这段代码同样不在 `_lab/` 里，是本篇专门为了
讲清楚这个思路写的独立演示，你可以直接粘贴运行，包括拿 `## 1` 那组会让朴素版本裸奔就溢出的
`800/801/802` 来试）：

```python
import numpy as np

def softmax_ref(x):
    m = x.max()
    return np.exp(x - m) / np.exp(x - m).sum()

def online_softmax(x):
    m, l = -np.inf, 0.0
    for xi in x:                      # 只看一遍
        m_new = max(m, xi)
        l = l * np.exp(m - m_new) + np.exp(xi - m_new)
        m = m_new
    return np.exp(x - m) / l

big = np.array([800.0, 801.0, 802.0], dtype=np.float32)
print(softmax_ref(big))     # [0.09003057 0.24472846 0.66524094]
print(online_softmax(big))  # [0.09003058 0.24472848 0.665241  ]  —— 一致，且没有 nan
```

这个"边扫边修"的思路，逐元素做是上面这个最小版本；把它推广成逐**块**做（一次处理一小片
`Q·K^T` 而不是一个数），同时再额外维护一个按同样规则缩放的输出累加器（不只是缩放分母的和，
连乘了 `V` 之后的输出也要一起缩放），就是 FlashAttention 的 online softmax 核心机制——
**这一篇只把"为什么可以边扫边修""为什么这样做数值上依然安全"这两件事讲清楚，
分块、和 KV 缓存怎么配合、以及完整的输出缩放公式，留给 `[[01-注意力从朴素到FlashAttention]]`。**

### 2.5 浮点基础：fp32 / fp16 / bf16 差在哪，为什么 bf16 更抗溢出

IEEE 754 浮点数由三部分拼成：1 位符号位、若干位**指数位**、若干位**尾数位**。
指数位决定"能表示多大/多小的数"（动态范围），尾数位决定"同一个数量级里能分辨多细"（精度）。
三种推理里常见的格式：

| 格式 | 符号 | 指数位 | 尾数位 | 最大值（量级） | 最小正规值（量级） | 相对精度 |
|---|---:|---:|---:|---:|---:|---:|
| fp32 | 1 | 8 | 23 | ≈3.40×10³⁸ | ≈1.18×10⁻³⁸ | ≈1.19×10⁻⁷（约 7 位十进制有效数字） |
| fp16 | 1 | 5 | 10 | 65504 | ≈6.10×10⁻⁵ | ≈9.77×10⁻⁴（约 3 位十进制有效数字） |
| bf16 | 1 | 8 | 7 | ≈3.39×10³⁸ | ≈1.18×10⁻³⁸ | ≈7.81×10⁻³（约 2 位十进制有效数字） |

（这张表是用 `numpy.finfo` 现场查出来的标准 IEEE 754 半精度/单精度参数，加上 bf16 的位宽定义
手推出来的常数，不是某个具体硬件的实测值——任何一台装了 numpy 的机器都能自己核对 fp32/fp16 两行。）

**bf16 为什么比 fp16 更抗溢出，现在这张表能直接读出来**：bf16 用的指数位宽度和 fp32
**完全一样**（都是 8 位），所以它的动态范围和 fp32 是同一个量级——一个存成 bf16 的数，
只要在 fp32 下不溢出，存成 bf16 也不会溢出。fp16 的指数位只有 5 位，动态范围窄得多，
最大值只有 65504，**比 fp32 的最大值小了大约 33 个数量级**。代价也在这张表里：
bf16 的尾数只有 7 位，比 fp16 的 10 位还要少——**bf16 是拿精度换来的范围，不是"更好"，
是"换了一种取舍"**（`## 5` 会展开讲什么时候这笔交易不划算）。

这条范围差异对 softmax 意味着什么，把 `## 1` 的例子重新算一遍临界点就清楚了：
`ln(fp32 能表示的最大值) ≈ 88.7`，`ln(fp16 能表示的最大值) ≈ 11.1`。也就是说：
**在 fp32 下，只要送进 `exp()` 的数超过约 89 就溢出；在 fp16 下，这个门槛低到只有约 11**。
`800` 这种数字在 fp32 里已经够炸了，如果直接在 fp16 里对未经处理的原始分数取 `exp`，
门槛会低到离谱，几乎必然见到 `inf`。**减完最大值之后，送进 `exp()` 的数永远 ≤0**——
这意味着无论用 fp32、fp16 还是 bf16 存这个中间结果，`exp()` 这一步本身都不会溢出。
这也解释了为什么"减最大值"这件事在低精度场景下更不是可选项：**精度越低，不做这件事
撞见溢出所需要的数字反而越小、越容易撞上。**

### 2.6 精度出现在推理的四个地方，尤其是"累加器要留一档余量"

一次推理里，精度不是一个整体开关，而是分别在几个地方各自做选择：

- **权重（weights）**：矩阵乘用到的参数，存成什么精度决定了显存占用和读取带宽
  （`## 2.7` 会把这个和算术强度接起来）。
- **激活（activations）**：层与层之间流动的隐藏状态，通常和权重用同一档精度，
  以便矩阵乘的两个输入是同一种类型，硬件的低精度算子才吃得上。
- **KV 缓存**：每生成一个 token 就往里追加的历史 K/V（原理见 `[[03-KV缓存的第一性原理]]`），
  精度选择往往和权重/激活**是分开的一个开关**——`## 4` 会看真实引擎如何把它做成独立配置项。
- **累加器（accumulator）**：矩阵乘或者 softmax 求和内部，把很多项加在一起的那个"运行中的和"。
  **这一项经常被忽略，但恰恰最容易出问题——关键经验是累加器通常要比数据本身的存储精度高一档**
  （典型组合：fp16/bf16 存数据，fp32 做累加）。

为什么累加器需要更高精度，用 softmax 自己的分母做一次实验最直接——`ctx_len=8192` 时，
分母是 8192 项 `exp(x_i - m)`（每一项都落在 `(0, 1]`）加在一起，分别用 fp16 逐项累加和
用 fp32 累加，对比理论值（用 float64 当参照）：

```python
import numpy as np
rng = np.random.default_rng(0)
e = rng.uniform(0.0, 1.0, size=8192).astype(np.float16)   # 模拟 8192 项 exp(x_i - m)

s16 = np.float16(0.0)
for v in e:
    s16 = np.float16(s16 + v)          # 累加器也是 fp16
s32 = np.float32(e.astype(np.float32).sum())  # 累加器升到 fp32

s64 = float(e.astype(np.float64).sum())        # 参照真值
print(float(s16), abs(float(s16) - s64) / s64)  # 2048.0   相对误差 ≈ 49.8%
print(float(s32), abs(float(s32) - s64) / s64)  # 4078.15  相对误差 ≈ 3.3e-8
```

结果非常戏剧化：**fp16 累加器的和被死死摁在 2048 附近，无论真实值应该是多少，相对误差高达
约 50%**；fp32 累加器几乎不损失精度。原因是 fp16 只有 10 位尾数，一旦累加器的量级涨到
2048，这个量级下相邻两个可表示数字之间的间隔已经涨到约 2（`2048 × 2⁻¹⁰ = 2`）——
而新加进来的每一项都 `≤1`，**比这个间隔还小，加上去之后直接被舍入抹掉，累加器纹丝不动**。
这个现象有时被称为"吞没"（swamping）：小数被淹没进一个已经很大的累加器里，贡献凭空消失。
fp32 累加器因为间隔小得多（同样量级下间隔约 `2048 × 2⁻²³ ≈ 0.00024`），远小于每项 `≤1`
的贡献，不会发生这种事。**这就是为什么即便最终存储和计算大量用 fp16/bf16，softmax 内部
的求和、以及矩阵乘内部的累加，通常仍然要用 fp32 完成**——真实硬件的张量核心也是这么设计的：
低精度乘法、高精度累加，`## 4` 会看到这条原则在真实引擎配置里的样子。

（KV 缓存本身还能再往下走一步：量化成 int8/fp8 只存 KV，权重和激活精度不变——
省的是什么、代价是什么，`## 5` 会点一下，细节留给 `[[05-量化]]`，这里不展开。）

### 2.7 精度与算术强度：`dtype_bytes` 怎么把访存地板抬高一倍

[[02-自回归解码为什么是访存瓶颈]] 推出过一条核心结论：`batch=1` 时算术强度恒等于
`2/dtype_bytes`，fp32（`dtype_bytes=4`）下就是 0.5，**与上下文长度完全无关**——单条请求
的解码从第一步起就已经站在访存瓶颈的地板上，没有更低可去。这条式子里 `dtype_bytes` 一直是
一个自由变量，只是那一篇统一固定用了 fp32 来讲。现在把它换成 fp16/bf16 试一下：

`_lab/minigpt.py:197-198` 的 `analytic_cost()` 本来就接受 `dtype_bytes` 参数，实际调用对比
fp32（4 字节）和 fp16（2 字节），默认配置下：

| ctx_len | batch | fp32 强度（`dtype_bytes=4`） | fp16 强度（`dtype_bytes=2`） |
|---:|---:|---:|---:|
| 16 | 1 | 0.500 | 1.000 |
| 16 | 64 | 14.496 | 28.991 |
| 1024 | 1 | 0.500 | 1.000 |
| 1024 | 64 | 0.895 | 1.789 |
| 16384 | 1 | 0.500 | 1.000 |
| 16384 | 64 | 0.525 | 1.050 |

**每一格都精确翻倍，不只是 `batch=1` 那一列的地板。** 原因看 `_lab/minigpt.py:220-238` 的公式
就能明白：`dtype_bytes` 只出现在字节数（`bytes_weights`、`bytes_kv`）的计算里
（`_lab/minigpt.py:226` 和 `:228`），完全不出现在 FLOPs 的计算里——乘加次数只看"算了几次"，
和这次乘加用几个字节存数据无关。所以把 `dtype_bytes` 从 4 减到 2，**总字节数精确减半，
算术强度（FLOPs/字节）精确翻倍**，这个翻倍对表里任意一个 `(ctx, batch)` 组合都成立。

`_lab/tests/test_lab.py:99-103` 的 `test_fp16_doubles_the_floor` 就是这条结论的可执行版本，
验的是 `ctx=1024, batch=1` 这一个点：

```python
ai = M.analytic_cost(cfg, 1024, batch=1, dtype_bytes=2)["arithmetic_intensity"]
assert abs(ai - 1.0) < 5e-3
```

**这就是"低精度省的不只是显存"这句话的完整含义**：省显存是容量账（同样的 KV 缓存字节预算能
装下更长的上下文或更大的 batch），而算术强度翻倍是速度账——同一块硬件、同一个机器平衡点
（`[[02-自回归解码为什么是访存瓶颈]]` `## 2.5` 定义过这个概念），**换一档精度就让你在 roofline
图上向右走了整整一倍的距离，离访存受限的深渊近了一半**。这也是为什么推理默认不用 fp32：
不是"fp32 太贵"，是**同样的硬件、同样的负载，fp32 让你在访存瓶颈的地板上蹲得比 fp16/bf16 更深**。

⚠️ 一个边界要说清楚：`_lab/minigpt.py` 里 `dtype_bytes` 只是 `analytic_cost()` 这个**解析模型**
里的一个参数，用来回答"如果换精度，字节数会怎么变"；本库整个 `_lab/` 全程只用 numpy 的
float32 做真实计算（`_PLAN.md` §7 第 3 条：本库不装 torch，目的是让矩阵乘露出来，不是为了
性能）。**换 `dtype_bytes` 不会让任何一次矩阵乘真的换精度重算一遍**，它只改变这条访存账目
里的字节宽度假设。上面那张翻倍的表是解析计算，不是实测——这个边界和
[[02-自回归解码为什么是访存瓶颈]] `## 1` 强调的完全一样。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang 等，带 `引擎:文件:行`）

`## 2.6` 说精度在推理里不是一个整体开关，而是权重/激活、KV 缓存、累加器（输出层）
各自独立选择——这一点在真实引擎的配置项里能直接对上号，**它们确实是几个互相独立的开关**，
不是一个总开关。

**权重和激活的 dtype 是一个开关**：`vllm:vllm/config/model.py:169-177`，`ModelConfig.dtype`
默认是 `"auto"`，文档字符串原话是——`"auto"` 对 fp32/fp16 模型用 fp16，对 bf16 模型用 bf16；
`"bfloat16"` 被描述为"a balance between precision and range"（精度与范围之间的平衡）。
这句话和 `## 2.5` 的结论是同一件事的两种说法：bf16 拿尾数精度换动态范围，vLLM 自己的配置文档
用几乎一样的措辞确认了这条权衡，不是本篇编出来的说法。

**KV 缓存的 dtype 是另一个独立开关**，不跟权重/激活共用同一个配置项：
`vllm:vllm/config/cache.py:119-128`，`CacheConfig.cache_dtype` 默认同样是 `"auto"`
（跟随模型 dtype），但可以单独选 `fp8`/`fp8_e4m3`/`fp8_e5m2` 等——**权重可以留在 bf16，
KV 缓存单独降到 fp8**，这正是 `## 2.6` 说的"KV 缓存的精度选择往往是分开的一个开关"在真实配置
里的样子。SGLang 有同一个概念的独立实现：`sglang:python/sglang/srt/server_args.py:705-731`，
`kv_cache_dtype` 同样默认 `"auto"`（第 731 行 `] = "auto"`），可选项同样包含
`fp8_e5m2`/`fp8_e4m3`/`nvfp4` 等——两个引擎各自独立地把"KV 缓存精度"和"模型权重精度"
拆成两个配置项，这不是巧合，而是 `## 2.6` 说的"KV 缓存占访存的比例随上下文变长趋近 100%"
（`[[02-自回归解码为什么是访存瓶颈]]` `## 1` 那张表）决定的：**KV 缓存的字节数对访存的影响
远大于权重，所以它值得单独拥有一个精度开关，而不是被绑死在权重精度上。**

**累加器/输出层精度也是一个独立开关**：`sglang:python/sglang/srt/server_args.py:732-734`，
`enable_fp32_lm_head` 默认 `False`，打开后"lm head 的输出（logits）用 fp32 计算"。
`lm_head` 是整条前向里最后一次矩阵乘，规约维度是 `d_model`，输出维度是词表大小 `vocab`
（往往几万到十几万）——这次矩阵乘内部的累加项数量和 `## 2.6` 演示的"8192 项求和在 fp16 下
误差约 50%"是同一类风险，只是求和对象从"softmax 的分母"换成了"矩阵乘的内积"。
`enable_fp32_lm_head` 这个开关的存在，说明"要不要把某一段强制放回更高精度"在真实引擎里
不是一句原则，而是要落到具体某个算子上的具体选择——`## 2.6` 讲的是原理层面"累加器该留一档余量"，
这个开关是这条原理在工程上被具体化之后的样子。

**这里只标出配置项在哪、默认值是什么，不给任何吞吐或精度损失的实测数字**——那些数字依赖具体
模型、硬件、输入分布，任何脱离这些上下文给出的百分比都不可信，也不是这三个配置项本身能回答的
问题（`_PLAN.md` §1 第 4 条的红线）。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：softmax 减最大值，用 `c = max(x)` 而不是别的常数。**
- 为什么这样：`## 2.2` 证明了 `c = max(x)` 是唯一能同时保证"所有指数参数 ≤0（不可能上溢）"
  和"分母恒 ≥1（不可能是 0/0）"的选择，而 `## 2.1` 证明了这个选择不改变数学结果——
  是免费的安全性，没有精度代价。
- 不这样会怎样：`## 1` 已经现场演示过——不减，`exp(800)` 直接溢出成 `inf`，接下来的除法
  变成 `inf/inf = nan`，这个 `nan` 会顺着后续所有计算传播，整条前向中毒且不报错。
- 什么时候可以不这样：如果你能从模型结构上**静态地**保证送进 softmax 的分数永远落在一个很小
  的范围内（比如某个人为限幅过的分数，或者已知量级不超过个位数），减最大值只是白白多扫一遍数据，
  没有实际收益——但这种"能保证"通常需要额外的架构设计或输入约束来兜底，普通的注意力分数
  （`Q·Kᵀ/√d`）在没有这类约束时，数值范围完全可能因为某次异常输入或某层没训好而失控，
  所以默认情况下不建议省略这一步。

**决策二：推理默认用 fp16/bf16 而不是 fp32 存权重和激活。**
- 为什么这样：`## 2.7` 推出的结论——精度从 fp32 换到 fp16/bf16，算术强度（`2/dtype_bytes`）
  精确翻倍，代价只是字节数减半，FLOPs 不变；同时显存占用也减半，能装下更长的上下文或更大的 batch。
- 不这样会怎样：继续用 fp32，同样的硬件在同样负载下访存字节数恒定翻倍，更容易撞上机器平衡点
  这个天花板（`[[02-自回归解码为什么是访存瓶颈]]` `## 2.5`），同时显存也更早耗尽。
- 什么时候可以不这样：某些对精度极敏感的中间量（`## 2.6` 提到的累加器就是其中一类）仍然需要
  fp32，不能无脑把全流程都砍成 fp16/bf16；另外训练阶段的优化器状态通常也需要更高精度，
  本篇只讨论推理阶段的权重/激活存储，不代表训练也该这么做。

**决策三：bf16 和 fp16 之间怎么选——不是"bf16 永远更好"。**
- 为什么这样：`## 2.5` 那张表说明两者是不同方向的取舍——bf16 指数位和 fp32 相同，动态范围大，
  抗溢出；fp16 尾数位比 bf16 多 3 位，同量级下能分辨更细的差异。选哪个取决于你更怕"数值太大装不下"
  还是"数值精度不够"。
- 不这样会怎样：如果数据本身量级本来就不大（比如经过 LayerNorm 之后的激活，量级通常被压在
  个位数附近），却无脑选了 bf16，相当于白白丢掉了本可以用上的尾数精度（fp16 会给出更细的分辨率），
  换来了一个用不上的动态范围。反过来，如果分数量级本身波动很大（比如没做归一化的原始 logits），
  选 fp16 就要时刻提防撞上 65504 这个偏低的上限。
- 什么时候可以不这样（该选 fp16 而不是 bf16）：老一代硬件往往只有 fp16 的原生高速通路、没有
  bf16 张量核心，这时候选择权其实不在"哪个数学上更合适"，而在"硬件支持哪个"；另外如果确定
  数值范围已经被良好控制（比如某一层的输出经过显式的幅度约束），fp16 多出来的尾数精度就是
  实打实的收益，不该为了用不上的动态范围放弃它。

**决策四：累加器要比数据存储精度高一档（典型是 fp16/bf16 数据 + fp32 累加）。**
- 为什么这样：`## 2.6` 的实验——8192 项 `(0,1]` 范围内的数求和，fp16 累加器相对误差约 50%，
  升到 fp32 累加误差降到 `3×10⁻⁸` 量级。累加器精度不够时，误差不是随机抖动，是系统性地
  "小数被大累加器吞掉"，量越大问题越严重。
- 不这样会怎样：长序列的 softmax 分母、大 `d_model` 的矩阵乘内积，累加项数量动辄成千上万，
  用和数据同档的精度做累加会系统性低估求和结果——`## 2.6` 的实验数字（约 50% 相对误差）
  不是极端情况，是均匀分布下的典型情况。
- 什么时候可以不这样：累加项数量本来就很少（比如 `d_head` 只有几十、`ctx_len` 很短）时，
  误差还没有机会累积到显著程度，同档精度累加的风险大幅降低；另外某些硬件路径本来就不提供
  "低精度乘、高精度累加"这个组合，此时这是硬件能力的限制而不是设计选择。

**决策五：KV 缓存单独量化到 int8/fp8，权重和激活精度不变。**
- 为什么这样：`[[02-自回归解码为什么是访存瓶颈]]` `## 1` 那张表说明上下文越长，KV 缓存占访存
  字节的比例越接近 100%——这是整条链路里最值得单独优化的一段，量化 KV 缓存能直接省下这部分
  访存字节和显存容量，收益和上下文长度成正比。
- 不这样会怎样：长上下文场景下继续用 fp16/bf16 存 KV，缓存本身占的显存会先于其它资源耗尽，
  batch 开不大，`## 2.7` 说的"精度翻倍能抬高算术强度"这条收益也拿不到——因为瓶颈根本不在
  算术强度，而在显存放不下这么多 KV。
- 什么时候可以不这样：短上下文场景下 KV 缓存本来就只占访存的一小部分（回看
  `[[02-自回归解码为什么是访存瓶颈]]` `## 1` 表格最后一列，`ctx=16` 时 KV 只占 54.7%，
  ctx 更短时占比更低），这时候量化 KV 省下来的字节数有限，却要额外承担量化/反量化的开销和
  可能的精度损失，收益不一定盖得过成本。量化具体怎么做、int8 和 fp8 的取舍、反量化开销在哪，
  留给 `[[05-量化]]`，这里只点出"值不值得做"取决于上下文长度这一条判据。

## 6. 常见错误与踩坑

**踩坑一：掩码用真正的 `-inf` 而不是一个很大的有限负数，某一行整行都被掩码时会产生 `nan`。**
`_lab/minigpt.py:102` 和 `:151` 用的是 `np.full(..., -1e9, ...)`——一个很大但有限的负数，
不是 `-np.inf`。这不是随手选的写法，换成真正的 `-inf` 会在一种退化情形下直接产生 `nan`：
如果某一行的所有位置都被掩码（比如 padding 到统一长度之后，某一整行全是无效位置），
这一行的分数在加上掩码之后**全部是 `-inf`**。这时候 `## 2.2` 说的"取最大值再相减"这一步
会算出 `max = -inf`，接下来要算 `x - max`，也就是 `-inf - (-inf)`——**这是一个没有定义的
运算，IEEE 754 规定结果是 `nan`**：

```python
row = np.array([-np.inf, -np.inf, -np.inf], dtype=np.float32)
row - row.max()   # array([nan, nan, nan], dtype=float32)
```

换成 `-1e9` 之后，同样全被掩码的一行变成 `[-1e9, -1e9, -1e9]`，最大值是 `-1e9`（一个有限数），
减完之后是 `[0, 0, 0]`，`exp` 之后是 `[1, 1, 1]`，softmax 结果是均匀分布——**语义上"整行都不该
被关注"本来就是一个没有正确答案的病态输入，得到一个替代性的均匀分布，好过让 `nan` 顺着后面
所有计算扩散下去**。代价是：如果某一行真实的合法分数量级恰好也逼近 `1e9`（现实中几乎不可能，
但理论上不是绝对不会发生），掩码就不够"负"，可能漏掉本该被完全屏蔽的位置——**这是用"足够大但
有限"换"不会在退化情形下炸掉"的取舍，不是没有代价的免费选择。**

**踩坑二：取最大值时忘了指定 `axis`，退化成全局标量最大值而不是逐行（逐 query）最大值。**
`_lab/minigpt.py:88` 写的是 `x.max(axis=axis, keepdims=True)`，默认 `axis=-1`——
对每一行（每个 query）**各自**求自己的最大值。如果不小心写成 `x.max()`（没有 `axis`），
会退化成整个矩阵共用同一个标量最大值。这在多行数据里非常危险：如果某一行的分数整体上
比全局最大值所在的那一行低很多（比如某个 query 的所有打分本来就偏负），用一个偏大的全局最大值
去减这一行，会让这一行的每一项都变成很负的数，`exp` 之后全部下溢成 0，**这一行的分母变成 0，
接下来的归一化除法是 `0/0`，同样是 `nan`**：

```python
x = np.array([[1.0, 2.0, 1.5],
              [-500.0, -501.0, -499.0],   # 这一行整体偏负
              [3.0, 0.5, 2.0]], dtype=np.float32)
bad = np.exp(x - x.max())                  # 全局标量最大值（来自第三行）
bad.sum(axis=-1)          # [0.726, 0.0, 1.45]  —— 第二行的和直接是 0
good = np.exp(x - x.max(axis=-1, keepdims=True))
good.sum(axis=-1)         # [1.974, 1.503, 1.450] —— 每一行都正常归一化
```

这条错误和踩坑一表面现象相似（都是 `nan`），根源不同：踩坑一是掩码语义导致的退化输入，
踩坑二是纯粹的实现错误——**维度写错了**，而且往往只在多行、且各行分数量级差异较大时才会露馅，
单行测试或者所有行分数量级接近时很容易蒙混过关。

**踩坑三：softmax 内部的求和（分母）直接用低精度累加，没有升到 fp32。**
`## 2.6` 已经用数字证明过这件事——`ctx_len=8192` 时用 fp16 逐项累加分母，相对误差能到约 50%，
升到 fp32 累加误差降到 `10⁻⁸` 量级。这个错误比前两条更隐蔽：它不产生 `nan` 或崩溃，
**只是安静地给出一个偏小、偏离真实值的和**，进而让整个 softmax 输出的概率分布悄悄失真——
在贪心解码或者采样阶段，这种失真可能改变最终选中的 token，且没有任何报错信号提示你哪里错了。
真实的 GPU softmax/attention kernel 即便输入输出都是 fp16/bf16，内部的规约（reduction）
通常仍然用 fp32 完成，原因正是这条。

**踩坑四：把"减最大值防溢出"和"结果因此更精确"混为一谈。**
`## 2.2` 保证的是"不会上溢、分母不会是 0"，这是**避免灾难性失败**，不是"提高了数值精度"。
减最大值之后，`exp(x_i - c)` 里 `x_i` 远小于 `c` 的那些项会下溢成 0（在 `## 2.5` 给出的最小
正规值以下直接变成 0），这些项对应的 softmax 概率本来就趋近于 0，下溢成 0 通常是可以接受的
（正确答案本就该接近 0），但如果后续代码依赖"这一项是一个很小的正数而不是恰好 0"
（比如接下来要对它取对数），这个下溢就会从"无害的近似"变成实打实的 bug（`log(0)` 是 `-inf`）。
**"数值稳定"解决的是能不能算，不是自动解决"算出来的每一项都足够精确"这件事**，两者是不同的问题。
