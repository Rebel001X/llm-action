# KV 缓存的第一性原理

> **一句话**：K/V 只依赖过去，一旦算出就不再变。
> **前置**：`02-自回归解码为什么是访存瓶颈.md`

## 0. 这一篇要解决什么问题

`02-自回归解码为什么是访存瓶颈.md` 证明了一件事：decode 阶段 batch=1 时算术强度恒为 0.5，天生卡在访存瓶颈的底部。但那篇文章从头到尾**假定了 KV 缓存已经存在**，只是去算"有了缓存之后"的账。它没有回答一个更前置的问题：**KV 缓存凭什么存在？为什么可以把 K、V 存起来不重算，而不是必须老老实实每步都从头算一遍？**

网上大多数材料把这件事讲成一条"优化技巧"——"因为重复计算了历史 token 的 K/V，所以缓存起来能省时间"。这个说法**不算错，但顺序反了**：它把"缓存有用"当成了理由，却没有回答"缓存为什么不会算错"。省时间只是缓存的收益，不是缓存合法的原因。真正的原因是一条数学事实，跟"快不快"无关——这条事实不成立，缓存了也没用，因为缓存出来的值根本是错的。

这一篇要让你自己把三件事推出来，顺序不能换：

1. **为什么能缓存 K、V，而不能（也没必要）缓存别的东西**——比如 Q，比如每层算完的中间激活 `x`？
2. **缓存了之后，为什么输出保证不变**——这必须是一个能推导出来的数学事实，而不是"工程师测过没问题"。
3. **代价是什么**——如果缓存不要钱，所有引擎第一天就该把整段历史全部缓存到天荒地老；可现实是显存永远不够用，代价具体在哪、有多大？

论证顺序刻意反着来：先看现象（selftest 通过），再补上"为什么会这样"的证明，最后才谈"这样做要付什么代价、朴素做法在哪会崩溃"。为什么要反着走，`## 6` 最后会专门说一句。

## 1. 先看现象（可跑的代码/可算的数）

`_lab/minigpt.py` 里有两条从 token 序列算到 logits 的路径，功能上都是"给定到目前为止的 token，算出下一个 token 的 logits"，走的算法却完全不同：

- **`forward_naive`**（`_lab/minigpt.py:95`）——每次调用都吃整条已生成序列，从头把所有位置的 Q/K/V、注意力（attention）、前馈网络（FFN）重新算一遍。它甚至不知道"缓存"这个词，函数签名里只有 `tokens: list[int]`，没有任何状态入参。
- **`forward_cached`**（`_lab/minigpt.py:139`）——只吃**新增的** `new_tokens`，历史的 K/V 从 `KVCache`（`_lab/minigpt.py:121`）里读，只把新 token 的 K/V 写进去。

`selftest()`（`_lab/minigpt.py:241`）里用三条一致性断言层层加码地验证这两条路径：

1. **一次性 prefill 对比**（`_lab/minigpt.py:249-253`）：整段 prompt 一次性喂给 `forward_naive`，再一次性喂给 `forward_cached`（走空缓存），两者最后一个位置的 logits 必须在 `atol=1e-4` 内相等。
2. **逐 token 增量对比**（`_lab/minigpt.py:256-260`）：把同一段 prompt 拆成一个个 token，每次只喂 1 个给 `forward_cached`（缓存从空一路长大），最终结果要跟"一次性喂整段给 `forward_naive`"完全一致。这一条比第 1 条更硬——它验证的是"缓存可以在中途反复暂停、追加读写"，而不只是"缓存了一整段之后一次性读出来对不对"。
3. **端到端生成对比**（`_lab/minigpt.py:263-266`）：分别用 `use_cache=False` 和 `use_cache=True` 跑 `generate()`（`_lab/minigpt.py:178`）生成 8 个新 token，要求生成出来的 token 序列**逐个相同**。这条断言最敏感——greedy decode 每步都会把 logits 的 argmax 喂回去当下一步输入，只要中间有一步 logits 算错，后面全部会分叉，跟前两条断言比，任何细微的错误都无处可藏。

这一个 `PASS` 背后压着两种结构完全不同的算法——一个是每步都要把已有全部历史重新算一遍的暴力实现，一个是只在新增的位置上做增量读写的实现——却被要求在浮点误差范围内给出**逐位相同**的结果。本篇接下来要做的事，就是把"为什么它们必须相同"这件事讲透，而不是把这个 `PASS` 当成运气或者"凑巧写对了"。

## 2. 原理

### 2.1 先把"缓存"这个词从原理里剥掉，只看注意力的定义

对第 `l` 层、位置 `i` 的隐藏状态 `h_i^(l)`（对照 `_lab/minigpt.py` 里 `layernorm` 前的 `x`），因果自注意力（causal self-attention）做的事是（对某一个头，省略头下标）：

```
q_i = h_i @ Wq，k_i = h_i @ Wk，v_i = h_i @ Wv

o_i = Σ_{j≤i} softmax_j(q_i · k_j / √d_head) · v_j
```

只对 `j ≤ i` 求和——`j > i` 被因果掩码设成 `-∞`，softmax 之后权重是 0。这正是 `forward_naive` 里 `att = softmax(q @ k.T / √d_head + mask)` 和 `o = att @ v` 在数学上写出来的样子（对照 `_lab/minigpt.py:109-110`）。

**注意求和范围 `j ≤ i` 是被掩码（`_lab/minigpt.py:102` 的 `mask`）强行砍出来的，不是注意力机制自己天然发生的。** 这是第一个要抓住的前提：**"K/V 可缓存"是因果掩码的推论，不是自注意力这个算子本身自带的性质。** 双向注意力（比如 BERT 那种）里，`k_i` 会被允许依赖整句话——包括位置 `i` 之后的 token——缓存这件事在数学上根本不成立。反过来也能验证这条因果关系：把 `_lab/minigpt.py:102` 那行因果掩码去掉，让 `forward_naive` 变成双向注意力，`## 3` 里的一致性断言会立刻失败——不是因为代码写错了，是因为这时候 `k_i`、`v_i` 已经依赖了未来的 token，"提前算出来存住不变"这个前提本身就不成立了。这也是 BERT 不能像 GPT 一样做增量式自回归生成的根本原因，不是"没人这么实现过"。

### 2.2 归纳证明：`k_i`、`v_i` 只依赖 `token_{1..i}`，与后面的 token 完全无关

对层数做归纳。

**归纳基础（第 0 层，也就是 embedding）**：`h_i^(0) = wte[token_i] + wpe[i]`（对照 `_lab/minigpt.py:101` 与增量版本的 `_lab/minigpt.py:148`）。这一步是逐位置独立的查表加法，`h_i^(0)` 只由 `token_i` 和位置 `i` 决定，跟其它任何位置的 token 无关。

**归纳假设**：假设对第 `l` 层，`h_j^(l)` 只依赖 `token_{1..j}`（对所有 `j` 成立）。

**归纳步骤**：证明 `h_i^(l+1)` 也只依赖 `token_{1..i}`。

- `k_i^(l+1)`、`v_i^(l+1)`、`q_i^(l+1)` 都是 `h_i^(l)` 的逐位置线性变换（`h @ wk` 这种矩阵乘，对照 `_lab/minigpt.py:106-108`）。按归纳假设 `h_i^(l)` 只依赖 `token_{1..i}`，所以 `k_i^(l+1)`、`v_i^(l+1)` 也只依赖 `token_{1..i}`——**这一步已经是我们要的结论**，但还要走完归纳才能说它对所有层都成立，不只是某一层。
- 注意力输出 `o_i^(l+1) = Σ_{j≤i} softmax_j(...) v_j^(l+1)`，求和只跑到 `j ≤ i`。每个 `j ≤ i` 用到的 `k_j^(l+1)`、`v_j^(l+1)`，按上一条只依赖 `token_{1..j}`，而 `token_{1..j} ⊆ token_{1..i}`（因为 `j ≤ i`）。所以 `o_i^(l+1)` 只依赖 `token_{1..i}`。
- 残差连接（`x + o @ wo`）、LayerNorm、FFN（对照 `_lab/minigpt.py:111-113`）都是**逐位置**的运算——它们不会让位置 `i` 的结果去"看"位置 `i` 以外任何位置的值。所以走完这一层之后的 `h_i^(l+1)` 依然只依赖 `token_{1..i}`。

归纳完成：**对任意层 `l`，`h_i^(l)` 只依赖 `token_{1..i}`。** 直接推论：**任何一层的 `k_i`、`v_i` 都只依赖 `token_{1..i}`，与 `token_{i+1}, token_{i+2}, ..., token_T` 完全无关**——不管序列后面还会不会追加第 `i+1`、`i+2` 个 token，`k_i`、`v_i` 都不受影响。

这才是"可以缓存"的真正含义：不是"缓存了会更快所以我们选择去缓存"，而是 **`k_i`、`v_i` 在数学上本来就是一个只吃 `token_{1..i}` 的确定性函数的值**——这个函数一旦在位置 `i` 求值过一次，答案永远不变，跟"记住 `2+2` 的结果、以后不用再算一次加法"是同一回事，不是什么特殊的工程技巧。

### 2.3 反过来问：Q 为什么不用缓存？

同样是 `## 2.2` 那套推导延伸出来的问题：`k_j`、`v_j` 在计算 `o_i`（对所有 `i ≥ j`）时会被**反复读取**——只要后面还有更长的序列在算注意力，位置 `j` 的 `k_j`、`v_j` 每一步都要参与求和。但 `q_i` 只在**第 `i` 步自己的那一次**注意力里被用一次（算 `o_i` 的那个 `softmax(q_i · k_j)`），算完 `o_i` 之后，`q_i` 这个值再也不会被任何未来位置读取——位置 `i+1` 算自己的 `o_{i+1}` 用的是 `q_{i+1}`，不是 `q_i`。

**缓存的价值来自"被重复读取、且值不会变"；`q` 满足后一半（值也不变，同样只依赖 `token_{1..i}`），但完全不满足前一半（从来不会被重复读）。** 缓存一个只用一次就该丢弃的值，纯粹是净亏——多占内存，没有任何"省重算"的收益。这也是为什么 `forward_cached`（`_lab/minigpt.py:139`）里的 `q`（`_lab/minigpt.py:155`）是每次现算现用、从来不进 `KVCache`（`_lab/minigpt.py:121`）的：`KVCache.__init__`（`_lab/minigpt.py:128-133`）里只分配了 `self.k` 和 `self.v` 两个数组，压根没有给 `q` 留位置。

顺带回答第三种候选：每层算完、还没做 K/V 投影之前的隐藏状态 `x` 本身要不要缓存？它同样只依赖 `token_{1..i}`，技术上缓存起来没问题。但缓存 `x` 之后，下次用到还要重新做一遍 `x @ wk`、`x @ wv` 才能拿到 `k`、`v`——**`k`、`v` 已经是注意力唯一会读取的形状，缓存 `x` 只是多占一份内存、还多算一次矩阵乘，没有任何额外好处。** 这就是为什么"缓存 K/V"是唯一合理的选择，而不是"缓存 x"或者"什么都不缓存、每次都全部重算"。

### 2.4 为什么缓存不改变输出——不是巧合，是同一个函数被求值了两次

`## 2.2` 的结论翻译成一句话就是：`k_i`、`v_i` 是关于 `(权重, token_{1..i})` 的**纯函数**——同样输入永远给出同样输出，没有隐藏状态、没有随机性（`_lab/minigpt.py` 权重固定 seed，确实是纯计算，对照 `init_weights`，`_lab/minigpt.py:47-53`）。

`forward_naive` 每次调用都是把这个函数在 `1..T` 每个位置重新求值一遍；`forward_cached` 是把这个函数在新出现的位置求值一次、写进缓存（`_lab/minigpt.py:159-160`），以后凡是要用到这个位置的 `k`、`v`，直接从 `cache.k[li]`、`cache.v[li]` 读出来。**读到的值和"现在重新求值"算出来的值必然相等，因为它们是同一个纯函数在同一个输入上的两次求值。** `selftest` 里三条断言能通过，根源就在这里——不是"工程师测过了正好没问题"，是这条数学性质决定了它不可能不通过。

这也划出了缓存正确性的边界：**只要这个函数不再是纯函数——权重变了（比如推理中途热切换了 LoRA 适配器）、或者位置 `i` 的计算依赖了 `i` 之后的信息（比如换成双向注意力，或者把新 token 插到历史序列中间而不是追加到末尾）——缓存就必须失效重算，继续用旧值就是输出错误的 bug，而且是静默的，不会报错，只会算错。**

### 2.5 代价是什么——K/V 不能像权重一样"共享一份"

到这里已经回答了"能不能缓存"和"缓存了对不对"，还剩最后一条：代价。

权重（`wq`/`wk`/`wv`/`wo`/`w1`/`w2`）在整条序列、乃至整个 batch 里只有**一份**，被所有位置、所有请求共用——这也是 `02-自回归解码为什么是访存瓶颈.md` 里"增大 batch 能摊薄权重访存"的根子。但 `k_i`、`v_i` 是**每个位置独有的**——位置 1 的 `k_1` 跟位置 2 的 `k_2` 是两份不同的数，不能共用，因为它们由不同的 `h_i` 算出来。序列长度是 `T`、层数是 `L`，每层每个位置就要留一份 K、一份 V，**KV 缓存的显存开销是"逐位置线性增长"的，而权重的显存开销是跟位置无关的一次性常数。** 具体数字放到 `## 3` 用 `_lab/minigpt.py:38` 的公式算。

### 2.6 用代码亲手验证：K 写一次之后真的不再变化

`## 2.2` 到 `## 2.5` 全是纸面推导，`_lab/minigpt.py` 暴露的公开函数已经足够让你自己把这条结论坐实成一次可执行的实验，不用改动库里任何一行代码，在 Python 交互环境里跑一遍：

```python
import numpy as np
from minigpt import Config, init_weights, KVCache, forward_cached

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=64, seed=1)
w = init_weights(cfg)
cache = KVCache(cfg)

forward_cached(cfg, w, [3, 14, 15], cache)   # 先喂 3 个 token
k_before = cache.k[0][:, :3].copy()          # 记下这 3 个位置此刻的 K
forward_cached(cfg, w, [62], cache)          # 再追加 1 个新 token（第 4 个）
k_after = cache.k[0][:, :3]                  # 再看一眼前 3 个位置

print(np.array_equal(k_before, k_after))     # True —— 一个 bit 都没变
```

这段代码只用到本文已经引用过的公开接口：`Config`、`init_weights`（`_lab/minigpt.py:47`）、`KVCache`（`_lab/minigpt.py:121`）、`forward_cached`（`_lab/minigpt.py:139`）。它验证的不是"数值上很接近"，而是**逐 bit 精确相等**——`np.array_equal` 不带任何容差，因为这里根本不涉及"重新算了一遍、算出来刚好一样"：第二次调用 `forward_cached` 时 `p0=3`，只会写入 `[3:4]` 这个区间（`_lab/minigpt.py:159-160`），前 3 个位置对应的那段内存根本没有被这次调用碰过。**这不是"重算了一遍、算出了相同的结果"，是"压根没有重算"**——`## 2.4` 证明的"同一个纯函数被求值了两次、所以两次结果相等"，只是理论上足以成立的最弱说法；实际实现更进一步，连"求值两次"都省了，直接读取第一次写下的那块内存。

## 3. 自己动手：`_lab/` 里对应的实现

### 3.1 `forward_cached` 逐行对照

`forward_cached`（`_lab/minigpt.py:139-173`）的函数签名是 `forward_cached(cfg, w, new_tokens, cache)`——注意它不接收完整历史，只接收**新增的** `new_tokens`。逐行拆开看它是怎么落实 `## 2` 的结论的：

- `T = len(new_tokens)`（`_lab/minigpt.py:146`）、`p0 = cache.length`（`_lab/minigpt.py:147`）：`p0` 是"已经写进缓存的历史长度"，新 token 要接在 `[p0, p0+T)` 这段位置上写入。
- `x = w["wte"][new_tokens] + w["wpe"][p0:p0 + T]`（`_lab/minigpt.py:148`）：位置编码从 `p0` 开始切片，不是从 0——因为这批新 token 在整条序列里的真实位置是 `p0..p0+T-1`，不是 `0..T-1`。这一行的坑专门留到 `## 6` 讲。
- `causal = np.triu(np.full((T, T), -1e9, np.float32), k=1)`（`_lab/minigpt.py:151`）：因果掩码只开在新 token 内部，是个 `T×T` 的小矩阵，不是整条序列的 `(p0+T)×(p0+T)`。
- `cache.k[li][:, p0:p0 + T] = kn`、`cache.v[li][:, p0:p0 + T] = vn`（`_lab/minigpt.py:159-160`）：**写入**——新算出来的 `k`、`v` 按 `## 2.2` 证明的性质，写一次之后永远不再改。
- `k_all = cache.k[li][:, :p0 + T]`、`v_all = cache.v[li][:, :p0 + T]`（`_lab/minigpt.py:161-162`）：**读取**——把刚写的和历史已有的拼在一起，形状是 `(n_head, p0+T, d_head)`，注意力要看到的是全部历史加新 token，不只是新 token 自己。
- `scores = q @ k_all.transpose(0, 2, 1) / √d_head`（`_lab/minigpt.py:164`）：新 token 的 `q`（只有 `T` 个）对全部 `p0+T` 个位置的 `k` 做点积，形状是 `(n_head, T, p0+T)`。
- `scores[:, :, p0:] += causal`（`_lab/minigpt.py:165`）：**只对 `scores` 里对应新 token 的那一段（列下标从 `p0` 开始）加因果掩码**——对历史那一段（列下标 `0..p0-1`）完全不加掩码，因为新 token 天然可以看见全部历史，不需要屏蔽任何东西；只有新 token 之间彼此还要遵守"看不到后面"的规则。这一行的坑也留到 `## 6`。
- `cache.length = p0 + T`（`_lab/minigpt.py:171`）：更新游标，供下一次调用当作新的 `p0`。

注释里已经点出一个关键设计（`_lab/minigpt.py:143-144`）：`new_tokens` 既可以是一整段 prompt（这叫 prefill），也可以是一个 token（这叫 decode）——**两者走的是完全同一段代码**，区别只在 `T` 的大小。理解了 `## 2` 的证明就知道为什么这必然成立：`forward_cached` 本质上只是"把 `## 2.2` 里那个纯函数，在 `[p0, p0+T)` 这段位置上求值一次"，跟这段位置有多长（1 个还是一整段 prompt）没有任何关系——纯函数的定义本来就不关心一次调用求值几个点。

### 3.2 不缓存要多算多少：`n=1000` 自己代进去算一遍

`forward_naive` 每次调用都要把**当前已有的全部位置**的 K/V 重新算一遍。设想从空序列开始、一个 token 一个 token 生成到长度 `n`：第 `m` 步（`1 ≤ m ≤ n`）要重算 `m` 个位置的 K/V，`n` 步加起来是：

```
1 + 2 + ... + n = n(n+1) / 2
```

`forward_cached` 每一步只算 1 个新位置的 K/V，`n` 步总共只算 `n` 个位置。

代 `n = 1000`：

```
无缓存：1000 × 1001 / 2 = 500,500 次"位置 K/V 计算"
有缓存：1000 次
```

差了 500.5 倍。而且这个倍数不是常数，是 `(n+1)/2`——随 `n` 线性增长：`n = 10,000` 时差距约 5,000 倍，`n = 100,000` 时约 50,000 倍。**这就是 `## 0` 里"缓存是收益，不是理由"这句话里"收益"的具体数字**——它证明了缓存值得做，但它没有、也不能证明缓存这么做是对的（对的原因在 `## 2`）。

### 3.3 代价量化：一个真实规模的估算（解析计算，不是实测）

`Config.kv_bytes_per_token`（`_lab/minigpt.py:38-39`）给出的公式是：

```python
def kv_bytes_per_token(self) -> int:
    return 2 * self.n_layer * self.d_model * 4
```

即"每 token 的 KV 字节数 = 2（K 和 V）× 层数 × `d_model` × 4 字节"。注意这里的 `4` 是硬编码的 fp32——因为整个 `_lab` 全程用 fp32，`Config` 没有留 `dtype_bytes` 参数（`analytic_cost` 函数单独接收了 `dtype_bytes` 参数，`_lab/minigpt.py:197-198`，但 `kv_bytes_per_token` 没有）。下面换算到真实场景时，把这个 `4` 手动换成更常见的精度。

用跟 `01-推理和训练到底差在哪.md` 里同一组假设（延续同一个例子，方便对照），只是把上下文长度换成 1 万 token：

假设：
- 层数 `L = 32`
- `d_model = 4096`
- 精度 fp16，每个数 2 字节
- 不考虑分组查询注意力（GQA/MQA，会显著压缩 KV，机制见 `## 5`）——用最朴素的算法，即每个头都有自己独立的 K、V

代入公式：

```
每 token KV 字节 = 2 × 32 × 4096 × 2 = 524,288 字节 = 512 KiB
```

上下文长度 1 万 token、单条请求：

```
10,000 × 512 KiB = 5,120,000 KiB ≈ 4.88 GiB
```

**单条请求，1 万 token 上下文，光是 KV 缓存就要将近 5 GiB 显存**——还没算权重、还没算算 attention/FFN 中间产生的激活值。如果同时服务 24 条这样的请求（连续批处理希望达到的并发量级）：

```
24 × 4.88 GiB ≈ 117 GiB
```

这已经超过大多数单卡 GPU 装得下的全部显存，而且这还只是 KV 一项，权重（这个规模的模型 fp16 下大约 14 GiB，算法见 `01-推理和训练到底差在哪.md` `## 3.1`）和激活值都还没算进去。

这组数字跟 `02-自回归解码为什么是访存瓶颈.md` 里"KV 占访存比重随 ctx 增长一路爬到 99.9%"那张表说的是同一件事的两种度量：那张表算的是"每一步 decode 要读多少字节里 KV 占几成"（一个**比例**），这里算的是"KV 缓存本身要占多少 GiB 显存"（一个**绝对量**）。比例告诉你"长上下文时几乎所有访存带宽都在伺候 KV"，绝对量告诉你"这些 KV 字节本身能不能先塞进显存里"——两个问题都成立，且互相独立：就算显存装得下（这里的绝对量问题），`02` 篇证明的访存瓶颈依然存在；就算算力再强、访存带宽再大，显存装不下（这里的问题）照样跑不起来，这是本篇要单独讲清楚的另一层约束。

**由此引出**：显存装不下，就必须精打细算地管理它——不能像 `KVCache`（`_lab/minigpt.py:121`）这样简单粗暴地给每条请求预分配一段连续数组，需要分页管理，见 `[[03-分页KV与块管理]]`；也不能让完全相同的历史前缀在不同请求之间被重复计算和重复存储，见 `## 5` 和 `[[05-前缀缓存]]`。

## 4. 真实引擎是怎么做的（对照 vLLM）

`## 2.2` 证明的结论精确地说是：`k_i`、`v_i` 依赖的是 `token_{1..i}` **这一整段前缀**，不是只依赖 `token_i` 自己。这条区别看着微妙，却是真实引擎做前缀缓存（prefix caching，跨请求共享 KV）时最容易踩的坑，也是 vLLM 块哈希设计成"链式"的直接原因。

设想两个请求，某个块（block）里的原始 token 内容完全相同——比如都是同一句 system prompt 里的第 3 个块。如果只按"这个块自己的 token 内容"算哈希，两个请求会得到相同的哈希、被判定为可以互相复用这段 KV。但按 `## 2.2` 的结论，这个块里每个位置的 `k_i`、`v_i` 依赖的是**从第一个 token 到这个位置为止的全部前缀**——如果两个请求在这个块**之前**的历史不完全相同，即便这个块自己的 token 一模一样，算出来的 K/V 数值也会不同，根本不能复用。所以"内容相同"不是可以复用的充分条件，"内容相同 **且** 之前的全部历史也相同"才是。

vLLM 的做法是把这条数学约束直接编码进哈希函数里。`hash_block_tokens`（`vllm:vllm/v1/core/kv_cache_utils.py:620`）计算一个块的哈希时，输入不是只有这个块自己的 token：

```python
# vllm:vllm/v1/core/kv_cache_utils.py:641-647（节选）
if not parent_block_hash:
    parent_block_hash = NONE_HASH

curr_block_token_ids_tuple = tuple(curr_block_token_ids)
return BlockHash(
    hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
)
```

**`parent_block_hash`（父块的哈希）被直接拼进了子块哈希的输入里**——第一个块的哈希只由它自己的 token 决定（父哈希是一个固定的 `NONE_HASH` 哨兵值），第二个块的哈希是"第一个块的哈希 + 第二个块的 token"算出来的，第三个块的哈希是"第二个块的哈希（其中已经卷入了第一个块）+ 第三个块的 token"……这是一条哈希链（hash chain）。链式哈希直接保证了：**两个请求某个块的哈希相同，当且仅当它们从序列开头到这个块为止的全部内容都相同**——跟 `## 2.2` 证明的"K/V 依赖整段前缀"严丝合缝地对上。

举一个具体例子。请求 A 是 `[system_prompt(64 token), "帮我写一首诗"]`，请求 B 是 `[system_prompt(64 token), "帮我写一段代码"]`，块大小取 32，两条请求共享同一段 `system_prompt`：

| 块序号 | A 的哈希输入 | B 的哈希输入 | 是否相同 |
|---|---|---|---|
| 块 1（`system_prompt[0:32]`） | `(NONE_HASH, sys[0:32])` | `(NONE_HASH, sys[0:32])` | 相同 → 可复用 |
| 块 2（`system_prompt[32:64]`） | `(hash(块1), sys[32:64])` | `(hash(块1), sys[32:64])` | 相同（因为块 1 的哈希相同）→ 可复用 |
| 块 3（各自的问题） | `(hash(块2), "帮我写一首诗"[0:32])` | `(hash(块2), "帮我写一段代码"[0:32])` | 父哈希相同但当前块 token 不同 → 不同，不可复用 |

块 1、块 2 命中，`get_computed_blocks`（`vllm:vllm/v1/core/kv_cache_manager.py:232`）会把这两块对应的 K/V 直接判定为已经算好——这就是"共享 system prompt 省了重复 prefill"这件事落到代码里的样子；请求 B 只需要真正计算块 3 开始的部分。反过来，如果两条请求的 `system_prompt` 只有最后 1 个 token 不一样，块 2 的哈希输入 `sys[32:64]` 就不再相同，块 2 直接不命中——即便块 1 是命中的，`find_longest_cache_hit` 也只会复用块 1，不会"跳过"块 2 去看块 3 会不会碰巧一样。这正是下面这条推论的具体体现。

这条链式设计带来一个直接推论：**前缀命中必须从头开始、连续匹配，不能跳着命中**。查找命中的代码（`vllm:vllm/v1/core/single_type_kv_cache_manager.py:684`）里写得很直白：

```python
# vllm:vllm/v1/core/single_type_kv_cache_manager.py:733-738（节选）
# Phase 1: longest run of cached full blocks from the start. A missing
# block implies every later block misses too (chained hashes).
for block_hash in itertools.islice(full_block_hashes, max_length // block_size):
    cached_block = block_pool.get_cached_block(block_hash, kv_cache_group_ids)
    if not cached_block:
        break
    for computed, cached in zip(computed_blocks, cached_block):
        computed.append(cached)
```

从第一个块开始逐个查，**一旦某个块没命中就立刻 `break`，后面的块哪怕内容凑巧相同也不再查**——注释直接写明原因："A missing block implies every later block misses too（因为哈希是链式的，缺一个块，后面所有块的哈希必然都对不上）"。这不是为了省查找时间的工程取舍，是哈希链本身的数学性质决定了后面不可能命中：既然某个块的哈希本身已经包含了它前面所有块的哈希，前面一旦有一个块不一致，这个块自己的哈希就必然不一致，再往后同理。这个查找函数被调度器主循环通过 `get_computed_blocks`（`vllm:vllm/v1/core/kv_cache_manager.py:232`）调用，发生在每个请求被调度执行之前，决定这条请求有多少前缀可以直接跳过重算。

回过头看，这一整套机制其实就是把 `## 2` 证明过的东西，从"单条请求内部 K/V 不依赖未来"这条性质，**推广成了"跨请求判断能否共享 K/V"的规则**——推广的方式就是把"依赖整段前缀"这条数学性质原样编码进哈希函数的链式结构里。`[[05-前缀缓存]]` 会展开讲调度器怎么用这套哈希做跨请求匹配、命中率怎么算。

## 5. 设计决策与代价

`_lab/minigpt.py:121-126` 的 `KVCache` 类文档字符串里已经自己点破了一句话："这是**第一版**。它有一个致命问题……"——下面把这句话拆成五条具体的设计决策，每条都按"为什么这样 / 不这样会怎样 / 什么时候可以不这样"讲清楚。

### 5.1 要不要引入 KV 缓存这套机制

- **为什么这样**：`## 3.2` 已经算过，`n=1000` 时不缓存要多算 500 倍以上的位置 K/V，而且随 `n` 线性扩大。只要一次推理里会调用超过一次注意力对同一段历史求值，缓存就有收益。
- **不这样会怎样**：每步都重新算全部历史的 K/V，代码确实更简单（`forward_naive` 只有 20 行，不需要维护任何跨调用的状态），但复杂度是 O(n²)，序列一长立刻拖垮吞吐——这正是所有真实推理引擎都上 KV 缓存的原因。
- **什么时候可以不这样**：**只需要单次前向、后面不会再有第二次调用来复用这份 K/V 的场景**——比如只做一次分类打分（对一段固定文本算一个 logits，不生成后续 token）、只算一次 embedding（拿某一层或最后一层的隐藏状态当向量用，不关心 logits）、或者只要"给定完整 prompt 算一次 loss/困惑度"这种评测场景。这些场景根本不存在"未来还会复用这段 K/V"这件事，加一层缓存管理反而是纯粹的复杂度和内存开销，`forward_naive` 那种一次性算完的写法就是对的选择。

### 5.2 要不要按 `max_seq` 预分配一段连续数组

对照 `KVCache.__init__`（`_lab/minigpt.py:128-133`）：`self.k = [np.zeros((cfg.n_head, n, cfg.d_head), ...) for _ in range(cfg.n_layer)]`，这里的 `n` 在调用 `generate`（`_lab/minigpt.py:181-182`）时被设成 `len(prompt) + n_new + 1`——也就是这条请求**能达到的最大长度**，不管它实际会不会用到那么长。

- **为什么这样**：实现极其简单——一次性 `np.zeros` 分配好，后面只需要往固定下标写，不需要处理"空间不够怎么办"，两行代码搞定。numpy 数组本身天然要求连续内存，切片、矩阵乘全都是最直接的写法。
- **不这样会怎样**：真实场景里，一批请求实际长度差异巨大——有的对话 3 轮就结束，有的要写一篇长文——但只要引擎不知道每条请求会在哪一步结束（大多数场景都不知道），就只能按能想到的最大长度预分配。绝大多数请求实际用不到这么长，预留出来但没用上的那部分显存**白白被占着分配不出去**，这就是**内碎片（internal fragmentation）**——碎片发生在"一块已分配的空间内部"，跟外部有没有其他空闲空间无关。
- **什么时候可以不这样**：用分页（把 KV 拆成固定大小的小块、按需追加，不再要求一次性分配整段最大长度），见 `[[03-分页KV与块管理]]`；或者反过来，当所有请求长度提前已知、且彼此相近时——比如批量跑一个定长的评测集，每条样本长度差不多——预分配反而是最简单也最合适的做法，上分页管理的调度开销纯属浪费。

### 5.3 要不要要求一条请求的 KV 物理连续

`KVCache` 每层是一个整块的 numpy 数组，一条请求从头到尾用的是这块数组里连续的一段下标 `[0, cache.length)`。

- **为什么这样**：连续内存让读写和矩阵乘的实现最简单——`cache.k[li][:, :p0+T]`（`_lab/minigpt.py:161`）这种切片操作，前提就是这块内存物理连续，不需要额外一层"这个逻辑位置对应哪块物理内存"的地址翻译。
- **不这样会怎样**：在只服务一条请求的教学场景里（`_lab/minigpt.py` 就是这样）没有任何问题。但在真实服务器里，很多条请求同时存在、又在不同时刻创建和结束，如果坚持"每条请求的 KV 必须是一段连续内存"，请求结束释放掉的那段空间会散落在整块显存的各个角落——就算所有空闲加起来的总量足够装下一条新的长请求，也可能找不到一段单独连续的区间放得下它。这是经典的**外碎片（external fragmentation）**，跟内碎片不是一回事：内碎片是"分配多了没用完"，外碎片是"总量够但拼不成一整块"。
- **什么时候可以不这样**：把 KV 拆成固定大小的物理块，通过一张块表（block table）做"逻辑位置 → 物理块"的地址翻译，不再要求物理连续——这正是分页要解决的问题，见 `[[03-分页KV与块管理]]`。如果引擎从始至终只服务一条请求、不存在并发创建和释放，那连续分配完全没问题，本篇的教学代码就是这种场景，不需要为它引入分页的复杂度。

### 5.4 不同请求之间要不要共享 KV

`generate`（`_lab/minigpt.py:178-192`）里 `cache = KVCache(cfg, ...)` 每次调用都新建一个空缓存，两条请求之间完全独立，互不知道对方存在。

- **为什么这样**：实现最简单——一条请求一个缓存对象，生命周期跟请求本身绑定，请求结束缓存直接丢弃，不需要维护任何跨请求的共享状态或者引用计数。
- **不这样会怎样**：如果大量请求共享同一段前缀——最典型的是相同的 system prompt、相同的 few-shot 示例——每条请求都要独立地把这段前缀重新做一遍 prefill 前向，白白浪费本该只算一次的计算，也白白浪费本该只存一份的显存。`## 4` 讲的 vLLM 链式块哈希，解决的正是这个问题。
- **什么时候可以不这样**：当请求之间的前缀重合度很低时——比如每条都是完全独立的单轮问答、彼此毫无关联——共享缓存的命中率本来就低，维护哈希表、块引用计数这些机制反而是额外的调度开销，不见得划算。共享 KV 的收益跟"重合前缀有多长、有多少条请求共享它"直接挂钩，见 `[[05-前缀缓存]]`。

### 5.5 要不要用 MQA/GQA/MLA 压缩 KV 的头数

标准多头注意力（multi-head attention，MHA）里，每个 query 头都配一份自己独立的 K、V——`_lab/minigpt.py` 里 `n_head` 个头，`kv_bytes_per_token`（`_lab/minigpt.py:38-39`）的公式里隐含的正是"K、V 跟 Q 头数一样多"这个假设。多查询注意力（multi-query attention，MQA）、分组查询注意力（grouped-query attention，GQA）、多头潜在注意力（multi-head latent attention，MLA）这几种变体做的是同一件事的不同程度：**让多个 query 头共享同一份（或同一小组）K、V，而不是一人一份**。MQA 是极端情况——所有 query 头共享唯一一份 K、V；GQA 介于 MHA 和 MQA 之间——把 `n_head` 个 query 头分成几组，组内共享一份 K、V；MLA 走的是另一条路——不直接共享原始的 K、V，而是把 K、V 投影进一个更低维的"潜在（latent）"空间再存起来，读取时再展开回各个头，本质上仍然是"存起来的东西比 `n_head` 份完整 K、V 要小"。

- **为什么这样**：`## 2.5` 已经证明 KV 缓存是"逐位置线性增长、不能像权重一样被共享"的开销，`01-推理和训练到底差在哪.md` 用真实规模的例子算过——KV 缓存能轻松超过权重本身好几倍。既然 KV 字节数直接正比于"独立存了多少份 K、V"，让多个头共享同一份，KV 字节数就按共享的组数等比例下降——这是直接从 `kv_bytes_per_token` 的公式就能看出来的算术关系，不需要新证明什么。
- **不这样会怎样**：标准 MHA 下每个 query 头都有自己独立的 K、V，头数越多、KV 缓存越大，`## 3.3` 算的 5 GiB、117 GiB 这种数字里，头数就是直接的乘法因子之一。
- **什么时候可以不这样**：模型小、上下文短、批量小的场景——比如本库 `_lab/minigpt.py` 默认配置（`ctx` 很小、`bs=1`）——KV 本来就只占访存里很小的一部分（回看 `01-推理和训练到底差在哪.md` 的算术强度表，短 ctx、小 batch 下 KV 占比才 50% 出头，远没到主导地位），这时候上共享 KV 头数没有意义，还要搭进两个真实代价：**表达能力可能下降**（原本每个头能各自关注不同的信息模式，共享之后自由度变少）；**已经训练好的模型如果原来是 MHA，改成 GQA/MQA 通常需要重新训练或者至少做一次转换微调，不是推理阶段能免费拿到的改动**。这两条代价本身不给具体数字——不同模型、不同任务上差异很大，`04-进阶主题/` 会展开讲这几种变体各自的取舍，这里只讲清楚它们在解决同一个问题：KV 太大。

## 6. 常见错误与踩坑

**推理引擎的 bug 绝大多数是静默的**——加了 KV 缓存之后代码照样能跑、不报任何异常、生成出来的文本读起来甚至通顺，但其实从某一步开始就已经算错了。下面三个坑都是这种类型，`## 3.1` 逐行拆过的代码里已经标出了对应位置，这里讲清楚"错了会怎样"，而不只是"要写对"。

### 6.1 位置编码没跟着 `p0` 偏移

正确写法是 `x = w["wte"][new_tokens] + w["wpe"][p0:p0 + T]`（`_lab/minigpt.py:148`）——新 token 的位置编码要从 `p0` 开始切。一个很容易犯的错误是写成 `w["wpe"][:T]`——只看新 token 自己有几个，从位置 0 开始编号。

这个错误**不会报任何异常**：`wpe[:T]` 和 `wpe[p0:p0+T]` 形状完全一样（都是 `(T, d_model)`），矩阵乘、加法全都能正常跑完，程序不会崩溃。但语义已经错了：假设 prompt 长度是 5，第 6 步 decode 一个新 token 时，`p0=5`，正确做法是告诉模型"这是第 5 个位置（从 0 计数）"；如果写成 `wpe[:1]`，模型会以为自己在处理"第 0 个位置"的 token——跟 prefill 阶段处理 prompt 里第一个 token 时用的是完全相同的位置编码。连续生成多个 token 时，每一步都会被错误地当成"位置 0"，`selftest` 里第 2 条断言（`_lab/minigpt.py:256-260`，逐 token 增量对比）会直接失败——因为逐 token 喂的路径每一步位置编码全错，而一次性喂整段 prompt 给 `forward_naive` 的路径位置编码是对的，两者必然对不上。**这条断言存在的意义正是专门抓这类"形状对、语义错"的坑**——只测第 1 条一次性 prefill 对比是抓不到这个 bug 的，因为一次性 prefill 时 `p0` 恒为 0，`wpe[:T]` 和 `wpe[p0:p0+T]` 碰巧一样。

### 6.2 因果掩码加错了范围

正确写法是 `scores[:, :, p0:] += causal`（`_lab/minigpt.py:165`）——因果掩码只作用在 `scores` 里对应"新 token 对新 token"的那一段（列下标从 `p0` 开始），历史那一段（列下标 `0..p0-1`）完全不加掩码。一个容易犯的错误是把掩码加到整个 `scores` 上，或者用一个按 `0..p0+T-1` 重新编号的下三角矩阵去覆盖全部列。

后果是**新 token 会被错误地屏蔽掉一部分本该看得见的历史**：因果掩码的下三角结构，如果从下标 0 重新数起而不是对齐到 `p0`，会把"新 token 相对于它自己在整条序列里的真实位置"的可见范围，错当成"新 token 相对于这批新 token内部的位置"的可见范围，导致新 token 只能看到比它序号小的**新 token**，却看不到全部**历史** token——这跟 `## 2.1` 里因果注意力的定义（`j ≤ i` 里的 `i` 是这个 token 在整条序列里的绝对位置，不是它在这一批新 token 里的相对位置）直接矛盾。这类 bug 同样不会抛异常（矩阵形状照样能对上或者被 numpy 广播吃掉），只会让生成结果在语义上开始跑偏，而且往往要生成好几个 token 之后才会明显看出不对劲——因为最开始几步屏蔽掉的历史信息可能恰好不影响输出。

### 6.3 把 `atol=1e-4` 之内的浮点误差当成 bug（或者反过来，容忍更大的误差）

`selftest`（`_lab/minigpt.py:249-253` 等）用的是 `np.allclose(a, b, atol=1e-4)`，不是精确相等 `a == b`。这条容差不是"写代码偷懒图省事"，是浮点运算本身决定的：`forward_naive` 和 `forward_cached` 虽然在数学上算的是同一个函数，但两条代码路径里加法、矩阵乘的**执行顺序不完全相同**（比如 `forward_cached` 是先算新 token 的 K/V 再拼接历史，`forward_naive` 是整段一起算），浮点加法不满足结合律，顺序不同、累积的舍入误差就不同，所以不能要求逐位精确相等。

这条坑的两个方向都要避免：**过严**——看到 `a` 和 `b` 差了 `1e-6` 就以为哪里写错了，其实那只是正常的浮点噪声；**过松**——为了让测试"更容易过"，把 `atol` 调大到 `1e-2` 甚至更大，这样真正的逻辑 bug（比如 `## 6.1`、`## 6.2` 这种）产生的误差可能也被容差吸收掉，测试变成形同虚设。`atol=1e-4` 这个数量级是"能容纳正常浮点噪声、又能抓住真实逻辑错误"之间刻意选定的平衡点——真正的逻辑错误（位置编码错位、掩码范围错）造成的偏差通常是数量级上的（能看到明显不同的 argmax token），远大于 `1e-4`，不会被这条容差误伤。
