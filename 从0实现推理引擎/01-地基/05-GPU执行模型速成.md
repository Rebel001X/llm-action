# GPU 执行模型速成

> **一句话**：写引擎不写 kernel，但每条引擎设计都在回应 GPU 的几个物理事实。
> **前置**：[[02-自回归解码为什么是访存瓶颈]]（本篇直接复用它证明过的"算术强度"与"机器平衡点"，不重新推导）

## 0. 这一篇要解决什么问题

隔壁 `cuda实战，ai实战/` 那个库教你怎么写一个算得快的 kernel——
线程怎么分工、共享内存怎么用、访存怎么合并。**这一篇不碰那些**，
理由不是"太难"，是**跑偏**：`_PLAN.md` 划得很清楚，本库全程站在引擎层，把算子当黑盒。

但"把算子当黑盒"不等于"对 GPU 一无所知也能把引擎设计对"。
引擎层要回答"什么时候调、调多大的批、数据在不在显存里"这几个问题，
而这几个问题的**正确答案，恰恰是由 GPU 的几条执行机制决定的**——
不懂这几条，引擎会被设计成一个在 GPU 上跑得很差的东西，哪怕每个 kernel 本身写得再快。

判据定死：**知道了会改变你在引擎层的设计决策的才写，不改变决策的一律不写。**
按这条判据筛出四件事：

1. **算力（FLOP/s）与显存带宽（Byte/s）的比值，即"机器平衡点"**——
   `[[02-自回归解码为什么是访存瓶颈]]` 已经证明过 decode 天生卡在访存瓶颈的底，
   本篇要接上的是：这条结论对引擎层意味着什么、为什么"堆更快的 kernel"救不了 decode。
2. **kernel 启动开销与 CUDA Graph**——decode 每步都要发一长串很小的 kernel，
   启动开销在这种粒度下不能再忽略，这是"引擎里到处是分桶和 padding"这件事的**唯一**理由。
3. **同步点**——GPU 执行本质上是异步的，`.item()`/`.cpu()` 这类操作会把 CPU 拖下水等 GPU，
   而推理引擎里几乎总有一个躲不开的同步点：拿采样出来的 token id 去决定下一步调度。
4. **显存的三块账**——权重、KV 缓存、激活/工作区，只有 KV 会随并发和上下文线性增长，
   这决定了**只有 KV 需要一个专门的分配器**。

⚠️ 红线先说在前面：本机没有 GPU，本篇**不会出现任何真实硬件的实测吞吐、延迟或带宽利用率**。
凡是需要举例的地方，要么用 `_lab/` 里能真跑的 numpy 玩具引擎的实测数字（它是我们自己的），
要么用"某加速器标称 X FLOP/s、Y Byte/s"这种带假设的算式，
并明确标注这是算例，不是任何一款真实产品的规格。

### 1.2 数一数一步 decode 到底要发起多少次独立的张量运算

`_lab/minigpt.py:139-173` 的 `forward_cached()` 是本库的前向实现。
跑一步 decode（`T=1`），沿着代码走一遍，数一数每层做了几次"独立的张量运算"
（矩阵乘、逐元素运算、归约各算一次，view/reshape 这类不搬数据的操作不算）：

| 步骤 | 运算 | 次数 |
|---|---|---|
| 输入 LayerNorm | `layernorm()` | 1 |
| Q/K/V 投影 | `h@wq`、`h@wk`、`h@wv` | 3 |
| KV 缓存写入 | 两次切片赋值 | 2 |
| 注意力打分 + 掩码 | `q@k_all.T`、`+= causal` | 2 |
| softmax | `max`/`exp`/`sum`/除 融合算 1 | 1 |
| 加权求和 | `softmax@v_all` | 1 |
| 输出投影 + 残差 | `o@wo`、`x+o@wo` | 2 |
| 第二个 LayerNorm | `layernorm()` | 1 |
| FFN | `h@w1`、`gelu()`、`@w2`、残差加 | 4 |

单层合计约 **17 次**独立运算，`_lab/minigpt.py` 默认配置 4 层，
加上开头的 embedding 查表和结尾的 `lnf` + `lm_head`，
一步 decode 至少要发起**七十次左右**的独立张量操作。

**这不是本库玩具引擎特有的现象，是 Transformer 结构本身决定的**——
不管用什么框架实现，一步前向天然被拆成几十个前后依赖的小算子。
真实 GPU 框架会不会把其中一部分融合（fuse）成更少的 kernel，取决于编译器/算子库，
这里数出的"七十次左右"是一个**逻辑运算次数下界**的直觉，不是任何真实框架的 kernel 数——
但它足够说明一件事：**decode 一步绝不是"发一个大 kernel 算完"，而是一长串小算子接龙**，
`## 2.2` 要讲的启动开销问题，根子就在这个数量级上。

## 2. 原理

### 2.1 机器平衡点：GPU 是"计算单元 + 显存控制器"两条并行流水线

一块加速卡可以粗糙地看成两条各自独立工作的流水线：
一堆做乘加的计算单元，和一条负责把数据从显存搬到计算单元跟前的通路。
两条流水线各自有峰值速度——算力峰值（多少 FLOP/s）和带宽峰值（多少 Byte/s），
`[[02-自回归解码为什么是访存瓶颈]]` `## 2.5` 把两者的比值定义成"机器平衡点"，判据是：
**你的计算的算术强度低于这个比值，计算单元就会有一部分时间在空转，等数据搬到——
不是它算得慢，是数据没喂上来。**

这条判据对引擎层的直接推论是：**当你的工作点确定落在机器平衡点以下
（decode，`batch=1` 恒为 0.5，`## 1.1` 的表），任何"让 kernel 算得更快"的努力，
天花板都是"数据搬运的速度"，跟计算单元多强无关。**
这句话是本篇存在的理由——它意味着**写引擎的人不该把 decode 慢的原因归咎到
"kernel 写得不够快"**，该做的是想办法让同一次数据搬运喂给更多计算
（也就是批处理，`[[04-连续批处理]]` 的主题），而不是去优化 kernel 内部的乘加效率。

反过来，prefill（`[[02-自回归解码为什么是访存瓶颈]]` `## 2.6` 证明过它的强度随 `T` 线性增长，
天然更接近算力受限）确实值得在 kernel 层面下功夫——
这也是为什么"投入精力优化 attention kernel"这件事在 prefill 和 decode 上收益完全不对称，
`## 6` 会点这条常见错误。

### 2.2 kernel 启动开销：为什么引擎里到处是 padding 和分桶

`## 1.2` 数出一步 decode 至少要发起几十次独立的张量运算。
在真实 GPU 执行模型里，每一次这样的运算通常对应至少一次 kernel 启动
（融合能减少这个数字，但减不到 1）。
**每一次 kernel 启动本身有一个和这次 kernel 算的数据量无关的固定开销**——
CPU 端要把这次调用的参数、grid/block 配置准备好，提交进 GPU 的执行队列，
这一段"准备 + 提交"的开销不随这次 kernel 到底要算 100 个元素还是 100 万个元素而改变。

这条开销什么时候要紧、什么时候可以忽略，是一个纯粹的相对关系
（这里不代入任何具体数字，只给算式结构，避免踩红线）：
设一次 kernel 启动的固定开销是 `C`，一步前向要发起 `N` 个 kernel，
这一步"真正算东西"要花的时间是 `T`（`T` 取决于这一步的 FLOPs 和硬件算力，
`N` 则是 `## 1.2` 数出来的那个量级）。当 `N·C` 和 `T` 是同一个数量级甚至更大时，
**发 kernel 本身的开销就不再是可以忽略的常数项，
而是和"真正算东西"平起平坐、甚至反客为主的主要开销**。

decode 恰好是最容易撞上这个情形的场景：`T` 本身就小
（`batch=1` 时算术强度只有 0.5，一步要做的 FLOPs 相对很少），
`N` 又不小（`## 1.2` 的几十次）——`T` 小、`N` 不小，`N·C` 相对 `T` 的占比自然被推高。
**这就是"CUDA Graph 存在的理由"**：与其每一步都重新走一遍
"CPU 组装参数 → 提交 → 排队"的完整流程，
不如把整个"发起这一串 kernel"的过程录成一份可重放的记录（graph），下次直接整体重放——
省下的正是每次单独发起 `N` 个 kernel 各自的那份 `C`。

代价随之而来，而且是结构性的、绕不开的：
**CUDA Graph 录制的是一串"在固定形状下的调用序列"，形状变了，这份录制就不能直接重放**
（batch 里有几条请求、每条请求这一步要算几个 token，都是"形状"的一部分）。
引擎侧要为此付两笔账：

- **按常见的 batch 大小提前分桶捕获**：不可能给"任意 batch 大小"各录一份（组合数太多），
  只能挑一组有代表性的 batch 大小（比如 1、2、4、8、16……），分别录一份 graph。
  真实请求来的时候，batch 大小极大概率不精确等于某个捕获过的桶——
  于是要**向上 padding 到最近的一个已捕获桶**，用无效数据填满多出来的空位，再整体重放。
  **这就是"引擎里到处是 padding"的根源**：padding 不是哪个工程师随手加的技巧，
  是"CUDA Graph 要求固定形状"这条硬约束的直接后果。
- **遇到没捕获过的形状要有 eager 回退路径**：万一 batch 大小超出了所有捕获过的桶的上限
  （比如一次性来了个特别大的并发峰值），引擎不能假装能重放一份不存在的 graph，
  必须退回到"逐个 kernel 正常发起"的 eager 执行路径——
  这条路径慢（付全额的 `N·C`），但必须存在，否则超限请求直接没法处理。

### 2.3 同步点：GPU 执行是异步的，`.item()` 把 CPU 拖下水等 GPU

CPU 把一个 kernel 提交进 GPU 的执行队列之后，默认情况下**立刻返回，不等这个 kernel 真的算完**——
CPU 可以马上去做别的事，GPU 在后台按队列顺序把提交进去的 kernel 依次执行。
这是 GPU 编程模型里最基础的一条：
**提交是异步的，只有你主动要求"给我这个值"的时候，才会被迫等待。**

`.item()`、`.cpu()`、`print(tensor)` 这类操作都属于"主动要求"：
它们要把 GPU 显存里的数据实实在在搬到 CPU 内存里给你用，
而这要求 GPU 必须先把这个值算出来——
**CPU 会在这里被迫阻塞，等 GPU 把队列里排在这个值之前的所有 kernel 都跑完**，
这就是所谓的"同步点"（sync point）。同步点本身不是错误，
模型确实迟早要把结果交回 CPU（比如最终要把生成的 token 打印/发送出去）；
问题是**同步点出现在哪、出现得多频繁**。

推理引擎里最典型、最躲不开的一个同步点在哪：
**每一步 decode 采样出下一个 token 之后，调度器需要拿到这个 token 的具体 id（一个整数），
才能决定接下来的事**——这条请求是不是该结束了（撞上了 EOS）、
下一步要喂给模型的输入是什么。这条"决定"逻辑天然跑在 CPU 上（引擎的调度代码），
但它依赖的数据——采样结果——诞生在 GPU 上。**取这个值的动作，就是一次同步点。**
如果每一步都老老实实同步一次，CPU 端的调度开销就会和 GPU 端的计算时间严格串行叠加，
而不是并行重叠——这正是"CPU 调度与 GPU 执行重叠"这类优化要解决的问题，
`## 4` 会看真实引擎具体怎么绕开这个同步点（用异步拷贝加事件同步取代直接 `.item()`）。

### 2.4 显存的三块账：只有 KV 需要专属分配器

一次推理服务运行起来，显存被三类东西瓜分：

1. **权重（weights）**：模型参数，加载一次之后固定不变，
   跟"现在有多少并发请求、每条请求上下文多长"完全无关——它是一次性、静态的开销。
2. **KV 缓存**：`[[03-KV缓存的第一性原理]]` 证明过它凭什么存在、
   `[[02-自回归解码为什么是访存瓶颈]]` 算过它占访存字节的比例随上下文变长趋近 100%——
   这里要点出的是它在**容量**账上的性质：
   **它是这三块里唯一一块会随并发数和上下文长度线性增长的**。
   并发从 1 涨到 64、上下文从 256 涨到 4096，KV 要占的显存跟着同比例涨，
   权重一个字节都不会多占。
3. **激活/工作区（activations / workspace）**：每次前向临时产生、用完基本可以释放的中间结果
   （LayerNorm 输出、attention 中间打分矩阵等）——
   量级通常远小于长上下文/高并发场景下的 KV，但不是 0，也要占一份预算。

**这条"只有 KV 线性增长"的性质，直接决定了引擎设计上的一个不对称：
权重可以简单地一次性分配好，激活/工作区可以按每次前向的固定上限预留一块暂存区，
唯独 KV 缺不了一个专门的分配器**——请求数量和每条请求的长度在运行时才知道、
还会不断变化（新请求进来、旧请求生成完退出），用"一次性分配一段固定大小的连续内存"来管 KV，
要么必须按最坏情况（`max_seq`）预留、造成大量内碎片，要么根本没法应付时刻变化的并发数。
这正是 `[[03-分页KV与块管理]]` 要解决的问题——
**分页 KV 本质上是"因为只有 KV 需要一个能动态增减的分配器"这条 GPU 显存的物理约束逼出来的**，
不是凭空发明的设计。

**KV 显存的手算公式**（`[[03-KV缓存的第一性原理]]` `## 2.5` 已经点过一句，这里给出完整算式）：

```
KV 字节 = 2 × 层数 × 隐藏维 × 精度字节 × 序列长 × 并发数
          ↑ 2 = K 和 V
```

`_lab/minigpt.py:38` 的 `kv_bytes_per_token()` 就是这条公式去掉"序列长 × 并发数"之后
剩下的部分——每个 token 占多少字节：`2 * n_layer * d_model * dtype_bytes`
（代码里 `dtype_bytes` 固定用了 `4`，即 fp32）。
`## 1.3` 已经现场跑出交叉验证：默认配置 `2×4×128×4=4096` 字节/token，
跟代码实际打印的 `4096` 完全一致；tiny 配置 `2×2×32×4=512`，同样对上。
**这条公式里"序列长 × 并发数"这一项，正是三块账里独一份随请求量变化的部分**——
把这两个数代进去，就是 `## 1.3` 提到的那些具体字节数的来源。

### 2.5 精度：只是"每个元素占几个字节"，但同时压在两本账上

`[[04-数值精度-为什么softmax要减最大值]]` `## 2.7` 已经证明过一条硬结论：
`batch=1` 时算术强度恒等于 `2/dtype_bytes`，fp32（4 字节）是 0.5，
fp16/bf16（2 字节）直接翻倍到 1.0——
`_lab/tests/test_lab.py:99-103` 的 `test_fp16_doubles_the_floor` 是这条结论的可执行版本。

本篇要接上的是：这个 `dtype_bytes` 不只出现在算术强度这一条式子里，
它**同时是 `## 2.4` 那条 KV 公式里的一个乘数**——
换精度不只是把访存瓶颈的地板抬高一倍，**也把 KV 缓存的显存占用砍掉一半**
（同样的并发数和上下文长度，fp16 存 KV 只要 fp32 的一半字节）。
这是同一个数字在两本账上同时起作用：速度账（算术强度）和容量账（能装下多少 KV）。
这也是为什么真实引擎会把 KV 缓存的精度做成一个独立于模型权重精度的开关——
`[[04-数值精度-为什么softmax要减最大值]]` `## 4` 已经看过这个配置项，这里不重复。

### 2.6 引擎层与 kernel 层的边界，画在哪

把 `## 2.1`~`## 2.5` 收束成一句边界声明：
**引擎层管"什么时候调、调多大的批、数据在不在显存里、要不要重放一份录好的执行序列"；
kernel 层管"这一次调用怎么把乘加算得更快"。** 本库全程站在前者。
`## 2.1` 讲的机器平衡点决定了"该不该批"，
`## 2.2` 讲的启动开销决定了"该不该录 CUDA Graph、录哪些形状"，
`## 2.3` 讲的同步点决定了"CPU 端调度代码该怎么写才不拖 GPU 后腿"，
`## 2.4`/`## 2.5` 讲的显存账决定了"KV 该不该有专属分配器"——
**这四条，没有一条要求你懂怎么写一个更快的 attention kernel，
但每一条都要求你懂 GPU 大致是怎么被喂饱的**。
这正是本篇标题"速成"两个字的含义：不追求 kernel 级别的精通，
只追求"够用来做对引擎层决策"的理解深度。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang 等，带 `引擎:文件:行`）

**CUDA Graph 捕获与按 batch 分桶**（`## 2.2` 的真实实现）：
vLLM 的 `CudagraphDispatcher._create_padded_batch_descriptor()`
（`vllm:vllm/v1/cudagraph_dispatcher.py:132-156`）在每次要发起前向之前，
先把这一步实际的 `num_tokens` 通过一张预先算好的映射表翻译成"最近的一个已捕获桶的大小"
（`vllm:vllm/v1/cudagraph_dispatcher.py:141`，
`num_tokens_padded = self._bs_to_padded_graph_size[num_tokens]`）——
这正是 `## 2.2` 说的"向上 padding 到最近的捕获桶"在真实代码里的样子。
捕获这些桶用的入口是 `GPUModelRunner.capture_model()`
（`vllm:vllm/v1/worker/gpu_model_runner.py:6937-6943`），
函数体内注释写着"先捕获大的形状，让小形状能复用大形状分配好的内存池"——
这是捕获顺序上的一条工程细节，不改变 `## 2.2` 讲的核心机制。

**eager 回退路径**（`## 2.2` 讲的第二条代价，真实实现）：
`CudagraphDispatcher.dispatch()`（`vllm:vllm/v1/cudagraph_dispatcher.py:235`）
在 `num_tokens` 超过所有已捕获桶的上限（`max_cudagraph_capture_size`）时，
直接返回 `CUDAGraphMode.NONE`（`vllm:vllm/v1/cudagraph_dispatcher.py:272-281`）——
调用方看到这个返回值就知道这一步不能重放任何 graph，得老老实实按 eager 方式逐个发起 kernel。
这就是 `## 2.2` 说的"遇到没捕获过的形状要有 eager 回退路径"，
不是一个可选项，是 `dispatch()` 函数本身内建的一条分支。
更彻底的一种 eager 模式是整体关掉 CUDA Graph：
`ModelConfig.enforce_eager`（`vllm:vllm/config/model.py:241-245`），docstring 写得很直接——
`True` 时"始终以 eager 模式执行 PyTorch，禁用 CUDA graph"，
`False`（默认）时"混合使用 CUDA graph 和 eager 执行以获得最大性能和灵活性"。
这条开关的存在本身就说明：**CUDA Graph 不是无条件更好的选项**，`## 5` 会展开这条取舍。

**同步点的真实规避**（`## 2.3` 的真实实现）：
vLLM 的 `GPUModelRunner._to_list()`（`vllm:vllm/v1/worker/gpu_model_runner.py:7680-7693`）
专门处理"把采样出的 token id 从 GPU 取回 CPU"这一步，函数体里的注释原话是：
直接调用 `.tolist()` 会触发一次"cuda wide stream sync"，阻塞其它 CUDA stream 上的拷贝操作，
在这条路径每次前向都要走一遍的情况下会造成实打实的性能问题
（注释原话提到这在某些 disagg 部署形态下造成过真实的性能问题）。
它的解决办法（`vllm:vllm/v1/worker/gpu_model_runner.py:7690-7692`）
是先把数据异步拷贝进一块锁页（pinned）CPU 内存
（`pinned.copy_(sampled_token_ids, non_blocking=True)`），
再用一次 CUDA event 同步替代直接同步整条 stream
（`self.transfer_event.record()` / `.synchronize()`），
最后才对这块已经在 CPU 上的锁页内存调用 `.tolist()`。
**这是 `## 2.3` 讲的"同步点是性能杀手"在真实引擎里被认真对待的证据**——
不是不同步（数据终究要到 CPU），
而是把"同步的范围"从"整条 CUDA stream"收窄成"这一次拷贝对应的一个 event"。

**显存三块账的真实预算**（`## 2.4` 的真实实现）：
vLLM 的 `Worker.determine_available_memory()`（`vllm:vllm/v1/worker/gpu_worker.py:481-492`）
docstring 写明它要做的事——
"profile 模型的峰值显存占用，确定还有多少显存能不 OOM 地分给 KV 缓存"。
函数体里先用真实的权重占用
（`vllm:vllm/v1/worker/gpu_worker.py:521-525`，
`weights_memory=int(self.model_runner.model_memory_usage)`）
加上一次真实前向 `profile_run()` 摸出的激活占用，
两者相加才是"权重+激活"这两块账的真实数字，剩下的显存才作为 KV 缓存的预算——
这正是 `## 2.4` 说的"三块账"里权重和激活先各自定量、KV 拿走剩下所有可用空间
这个顺序在真实引擎里的实现，不是本篇编的分类。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：用 CUDA Graph（按 batch 分桶捕获）而不是每一步都走 eager 逐个发起 kernel。**
- 为什么这样：`## 2.2` 的算式——一步 decode 要发起几十个小 kernel（`## 1.2`），
  每个 kernel 的固定启动开销 `C` 在这种粒度下和"真正算东西"的时间 `T` 同一个量级；
  CUDA Graph 把"发起一串 kernel"整体录成一份可重放的记录，
  把 `N` 次分别付出的 `C` 压缩成一次重放开销。
- 不这样会怎样：每一步都完整走一遍"CPU 组装参数 → 提交 → GPU 排队执行"，
  `N·C` 这部分开销原样保留，decode 阶段本来 `T` 就小，这部分相对占比会更显眼——
  `vllm:vllm/config/model.py:241-245` 的 `enforce_eager=True`
  就是"主动选择承担这份开销"的开关。
- 什么时候可以不这样：`vllm:vllm/config/model.py:242-245` 的 docstring 本身给出了答案的另一半——
  需要**最大灵活性**（比如频繁改变模型结构相关的执行路径、调试、
  某些暂不支持图捕获的功能组合）时，eager 执行不需要预先声明一组固定形状，
  代价是启动开销省不掉；如果一次前向本身 `T` 就很大（比如超长 prompt 的 prefill，
  `[[02-自回归解码为什么是访存瓶颈]]` `## 2.6` 证明过它天然更接近算力受限），
  `N·C` 相对 `T` 占比本来就小，省下的这部分开销边际收益也小。

**决策二：CUDA Graph 只覆盖一组预先选定的 batch 大小，其余走 padding 或 eager 回退，
而不是要求所有形状都必须提前捕获。**
- 为什么这样：可能出现的 `(batch, 序列长)` 组合在数学上是无限的，不可能穷举捕获；
  `vllm:vllm/v1/cudagraph_dispatcher.py:132-156` 的实现选择
  "挑一组代表性的桶，其余向上 padding"，用有限的捕获次数覆盖绝大多数请求形态。
- 不这样会怎样：如果坚持"必须精确匹配才能重放"，
  稍微不常见的 batch 大小就完全吃不到 CUDA Graph 的收益，退化成决策一"不这样"的那个后果；
  `vllm:vllm/v1/cudagraph_dispatcher.py:272-281` 的 `dispatch()`
  在超出所有捕获桶上限时明确回退到 `CUDAGraphMode.NONE`，
  这条回退路径必须存在，否则超限请求直接没法处理，不是"性能差一点"而是"跑不起来"。
- 什么时候可以不这样：如果这个部署场景的并发数和序列长几乎恒定
  （比如单用户本地推理，batch 永远是 1），捕获桶的选择问题几乎不存在——
  直接为这唯一的形状捕获一份就够，不需要一整套分桶和 padding 的机制。

**决策三：拿采样结果决定下一步调度这件事，做成异步（拷贝 + event 同步），
而不是直接 `.item()`/`.tolist()`。**
- 为什么这样：`## 2.3` 的机制——直接同步会阻塞整条 CUDA stream，
  波及其它本可以继续排队执行的拷贝/计算操作；
  `vllm:vllm/v1/worker/gpu_model_runner.py:7680-7693` 的 `_to_list()`
  用"锁页内存异步拷贝 + 单独的 CUDA event 同步"把阻塞范围从"整条 stream"收窄到"这一次拷贝"。
- 不这样会怎样：这条路径是每一步 decode 都要走一次的热路径，
  `## 2.3` 已经说明这是推理引擎里几乎躲不开的同步点——
  如果同步的方式选得不好（比如直接 `.tolist()` 整条 stream 同步），
  性能损失会随每一步反复发生，vLLM 源码注释里明确提到
  这在某些部署形态下（disagg 架构）造成过真实的性能问题。
- 什么时候可以不这样：如果调度逻辑本身不需要在 CPU 上做任何依赖 token id 具体数值的决策
  （比如某些固定步数、不检测 EOS 的简化场景），或者把停止判断也挪到 GPU 上做
  （避免把数据搬回 CPU），这个同步点可以被绕开或推迟；
  但一般意义上的"检测到 EOS 就提前结束这条请求"这类逻辑，
  天然需要 CPU 侧拿到具体的 token id，
  这个同步点很难被完全消除，只能把它做得尽量不那么昂贵。

**决策四：显存预算按"先量出权重和激活的实际占用，剩下的全部给 KV"的顺序统一 profiling 决定，
而不是三块账各自静态估算再拼凑。**
- 为什么这样：`## 2.4` 的三块账里，权重是固定常数、激活/工作区依赖具体的最大 batch/序列长配置，
  这两块都可以通过一次真实的前向跑一遍摸清楚；
  `vllm:vllm/v1/worker/gpu_worker.py:481-525` 的 `determine_available_memory()` 正是这个顺序——
  先用真实的权重占用加一次 profiling 摸清权重+激活的真实占用，再把剩余显存整体交给 KV。
- 不这样会怎样：如果每一块显存预算都靠手算/拍脑袋的静态估计
  （尤其是激活/工作区，它依赖的中间张量形状很容易漏算），
  最终要么低估导致 KV 分配后仍然 OOM，要么过度保守浪费本可以用来装更多 KV 的显存，
  `## 1.1` 的表已经说明 KV 每多装一点，batch 能开多大就多一分空间。
- 什么时候可以不这样：模型和部署形态完全固定、显存余量本来就很宽裕（远超实际需要）的场景下，
  精确到字节的预算收益不大，一个偏保守的静态估计足够用；
  这条决策的价值在"显存紧张、需要把每一块都用足"的场景里才体现得明显。

**决策五：引擎层完全不介入 kernel 内部的实现细节，把 attention/矩阵乘等算子当成黑盒调用。**
- 为什么这样：`## 2.6` 划的边界——引擎层的决策变量是"调不调、调多大、数据在不在"，
  这几个变量的最优解不依赖 kernel 内部怎么切分线程/怎么用共享内存；
  反过来，把两层的关注点混在一起，会让引擎代码同时要应付
  "调度逻辑对不对"和"这个 kernel 写得快不快"两种完全不同的正确性/性能问题，
  增加不必要的复杂度。
- 不这样会怎样：如果引擎层试图自己重新实现更快的 attention kernel，
  一方面要重复 `attention-optimization/`、`cuda实战，ai实战/` 这两个库已经在做的事，
  另一方面每次上游算子库（FlashAttention/FlashInfer 之类）更新，
  自己维护的版本都要跟进移植，维护成本会持续累积。
- 什么时候可以不这样：如果目标就是"研究/优化某个具体算子本身"
  （这正是隔壁两个库的定位），那当然需要打开黑盒；
  本库的定位从一开始就是"造引擎骨架"，这条决策对本库没有例外，
  但不代表对所有人都没有例外——写 kernel 的人本来就该打开它。

## 6. 常见错误与踩坑

**踩坑一：把 decode 慢的原因归咎为"kernel 不够快"，一头扎进去优化算子。**
`## 2.1` 已经说明：decode 的算术强度恒为 0.5
（`[[02-自回归解码为什么是访存瓶颈]]` 的核心结论），天生落在机器平衡点以下——
不管这个 kernel 内部写得多精巧，计算单元的利用率上限已经被"数据搬得不够快"卡死。
真正该做的是抬高批处理规模（`[[04-连续批处理]]`）或者砍精度
（`[[04-数值精度-为什么softmax要减最大值]]`），而不是继续雕琢 kernel 内部的乘加效率——
后者投入再多时间，收益也撞在同一堵墙上。

**踩坑二：在热路径上做 `.item()`/`.cpu()`/`print(tensor)`，尤其是写在每步都要执行的调度循环里。**
`## 2.3` 说明这类操作会强制 CPU 阻塞等 GPU——
如果只是调试时打印一次，代价可以忽略；
但如果这类调用不小心留在了"每步 decode 都要执行"的调度代码里
（哪怕只是为了打个日志、做个断言检查），这份同步开销会随生成步数线性累积，
而且不会有任何报错提示你"这里正在拖慢整条流水线"——
`vllm:vllm/v1/worker/gpu_model_runner.py:7680-7693`
专门用一整个函数加详细注释来规避这个问题，说明它在真实引擎里是一个认真对待的坑，
不是想当然的顾虑。

**踩坑三：估算显存只算权重，忘了算 KV。**
`## 2.4` 已经说明三块账里只有 KV 会随并发数和上下文长度线性增长——
如果显存预算只按"模型有多少参数、占多少字节"来估
（这是最直觉、最容易先想到的一笔账），短上下文小并发场景可能刚好蒙混过关，
一旦上下文变长或者并发上去，会突然撞上 OOM，而且这个"突然"具有欺骗性：
**不是显存变多了，是 KV 这一项此前一直被漏算，只是在负载够大之前它的绝对值还不起眼。**
`## 1.1` 的表已经量化过这个占比——`ctx=16384` 时 KV 占访存字节的 99.9%，
同样的比例逻辑也适用于显存容量账。

**踩坑四：CUDA Graph 没有覆盖到某个实际会出现的 batch/形状组合，
静默回退到 eager，吞吐骤降却没有任何报错。**
`## 2.2` 和 `vllm:vllm/v1/cudagraph_dispatcher.py:272-281` 已经说明：
形状超出所有捕获桶的上限时，`dispatch()` 会直接返回 `CUDAGraphMode.NONE`——
**这是一条正确性上完全没问题的回退（不会算错，只是变慢），所以极容易被忽略**：
服务照常在跑、结果照常正确，只有吞吐/延迟指标会不声不响地劣化。
排查这类问题的第一步永远是确认"这一步实际的 batch 形状是否落在了配置好的捕获桶范围内"，
而不是先去怀疑 kernel 或者模型本身出了问题。

**踩坑五：把"CUDA Graph 一定更快"当成无条件成立的常识，不管场景都强行打开。**
`## 5` 决策一已经给出反例：一次前向本身 `T` 就大（比如长 prompt 的 prefill）、
或者场景需要频繁改变执行路径（调试、某些还不兼容图捕获的功能）时，
CUDA Graph 的收益本来就小，却要额外承担
"必须固定形状、需要分桶、每种形状要重新捕获"这些复杂度——
`vllm:vllm/config/model.py:241-245` 的 `enforce_eager` 开关能存在，
本身就说明"要不要用 CUDA Graph"是一个需要按场景权衡的选择，不是无脑打开的默认正确项。

## 7. 自测题与延伸阅读
