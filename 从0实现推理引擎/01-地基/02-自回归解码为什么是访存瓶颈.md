# 自回归解码为什么是访存瓶颈

> **一句话**：单条解码的算术强度恒为 0.5，与上下文长度无关。
> **前置**：[[01-推理和训练到底差在哪]]（若尚未成文，先接受一个前提：推理是逐 token 生成的，训练是整段并行算的）

## 0. 这一篇要解决什么问题

"LLM 推理是访存受限（memory-bound）的" 这句话你大概率已经听过很多遍了，
它是后面几乎所有推理引擎优化的出发点：连续批处理、分页 KV、投机解码、量化……
每一个都能用一句"因为访存是瓶颈"来解释动机。

但这句话如果只是背下来的口号，它就只能用来复述，不能用来做决策。
比如它回答不了这些问题：

- 为什么"访存受限"具体是指哪一个数字，这个数字怎么算？
- 为什么它不会随上下文变长而"更受限"或"没那么受限"——它到底会不会变？
- 为什么"加大 batch"能缓解它，加大到什么程度会失效？
- 同一份推理代码，prefill 和 decode 到底是不是"同一种"计算？

这一篇要做的事只有一件：把"访存受限"从一句定性描述，
变成一条你能亲手算出来、亲手验证的式子——**算术强度
（arithmetic intensity）= 每读 1 字节数据能做多少次浮点运算**。
算完这条式子之后，`[[04-连续批处理]]`、`[[03-分页KV与块管理]]`、`[[03-投机解码]]`
这几篇要解决的问题，会变成这条式子里自然长出来的推论，而不是分别需要单独说服你的新知识点。

（⚠️ 标注一次：这张表**全部是解析计算**——根据模型结构直接推公式算出来的数字，
不是在某块 GPU 上跑出来的实测吞吐。它不需要 GPU，笔记本上瞬间出结果，
这正是"算术强度"这个工具的价值：不用摸到硬件就能看清定性结论。）

1. **竖着看第一列**：`bs=1` 这一列从 ctx=16 到 ctx=16384，**六行全部是 0.50，一丝不差。**
   这不是巧合，也不是精度四舍五入——它是一个可以证明的恒等式（见 `## 2`）。
   意味着：单条请求做解码，从第一步开始就已经在访存瓶颈的地板上了，
   **上下文再短也不会更好，再长也不会更差**，没有"再优化一下"的空间。
2. **横着看同一行**：`bs=1 → bs=256`，数字在涨，涨得还不小（ctx=16 那一行从 0.50 涨到 21.74，44 倍）。

三条读法合起来就是本篇的核心结论：**解码天生卡在访存的地板上；
批处理是唯一的解药；但上下文越长，这剂药效越弱。** 下面把它推导出来。

## 2. 原理

### 2.1 先把"算术强度"这个词钉死

对一段计算，定义：

```
算术强度 = 总浮点运算次数(FLOPs) / 总访存字节数(Bytes)
```

单位是 FLOP/字节。它回答的问题是："硬件每从显存搬 1 个字节过来，
你打算用它做几次乘加？" 如果这个数字**低于**你这块硬件的
"算力峰值 ÷ 显存带宽峰值"（这条阈值就是 roofline 模型里的"机器平衡点"，
详见 `## 2.5`），那么无论算力多强，你都在等数据搬运，
这就是"访存受限"的精确定义——**不是"算得慢"，是"算得比搬得快，所以算力在空转"。**

接下来把一步 decode 的 FLOPs 和 Bytes 拆开算，就知道这个比值到底是多少。

### 2.2 一步 decode 在算什么、在读什么

设配置：`d_model=d`，层数 `n_layer=L`，头数 `n_head=H`，每头维度 `d_head=dh`（`d=H·dh`），
词表 `vocab=V`，dtype 字节数 `dtype_bytes`（fp32 就是 4）。

**参与矩阵乘的权重，一步用到的乘加次数（记作 `matmul_params`）：**
每层有 4 个 `d×d` 投影（`wq wk wv wo`）和两个 FFN 矩阵（`d×4d` 与 `4d×d`），
再加上输出层 `lm_head`（和 embedding 权重共享，形状 `d×V`，只在最后用一次，不随层数重复）：

```
matmul_params = L·(4·d² + 8·d²) + d·V
             = L·12·d² + d·V
```

这是**参数个数**，不是字节也不是 FLOPs——它是接下来两件事共同的分母。

**FLOPs（权重侧）**：每个参数在一次前向里被用来做一次"乘"再做一次"加"（乘加，multiply-add），
计 2 FLOPs。batch 为 `batch` 时，这些权重要被 `batch` 条请求各自用一遍：

```
flops_weights = 2 · batch · matmul_params
```

**Bytes（权重侧）**：这些权重要从显存读进计算单元。**关键点：权重只需要读一遍，
被整个 batch 共用**（这和 FLOPs 侧要"重复用 batch 遍"完全不同）：

```
bytes_weights ≈ dtype_bytes · matmul_params
```

（还有一个小尾巴：每条请求还要去 embedding 表 `wte`/`wpe` 里各取一行，
这是查表（gather），不是矩阵乘，按 `batch` 条请求各读 `2·d` 个数算成
`dtype_bytes·2·batch·d` 字节，量级远小于 `matmul_params`，先记在心里，`## 6` 会讲不算它的后果。）

**FLOPs（KV / 注意力侧）**：新来的这个 token 要和已有的 `ctx_len` 个历史位置做注意力。
每层每个头，`QK^T` 是 `ctx_len` 次长度为 `dh` 的点积，`softmax` 之后再和 `V` 做一次同规模的加权求和，
两步各自是 `ctx_len·dh` 次乘加：

```
flops_attn = batch · L · H · 4 · ctx_len · dh
             ↑ 4 = 2(QK^T 与 AV 两步) × 2(每次乘加算 2 FLOPs)
```

**Bytes（KV 侧）**：要把这 `ctx_len` 个历史位置的 K、V 从 KV 缓存里读出来。
**这是每条请求私有的数据，不能像权重那样被 batch 共用**：

```
bytes_kv = batch · ctx_len · (2 · L · d · dtype_bytes)
           ↑ 2 = K 和 V；L 层；每层每个位置存 d 个 float
```

总量就是两侧相加：

```
total_flops = flops_weights + flops_attn
total_bytes = bytes_weights + bytes_kv
算术强度   = total_flops / total_bytes
```

以上就是 `_lab/minigpt.py:197` 的 `analytic_cost()` 在做的事，`## 3` 会逐行对照代码。

### 2.3 手推 bs=1 恒为 0.5：先证一个引理

**引理**：如果 `a/b = c/d = k`，那么 `(a+c)/(b+d)` 也等于 `k`。
证明也就一行：`a=kb`，`c=kd`，所以 `(a+c)/(b+d) = (kb+kd)/(b+d) = k`。
——两个比值相等的分数，加权平均出来还是同一个值，**跟权重（也就是两边各占多少）完全无关**。

现在验证 "权重侧的比值" 和 "KV 侧的比值" 是不是刚好相等。

**KV 侧，精确成立、跟任何配置都无关**：把 `flops_attn` 除以 `bytes_kv`，
注意 `d = H·dh`，代入直接消元：

```
flops_attn / bytes_kv
  = [batch·L·H·4·ctx_len·dh] / [batch·ctx_len·2·L·(H·dh)·dtype_bytes]
  = 4 / (2·dtype_bytes)
  = 2 / dtype_bytes
```

`batch`、`ctx_len`、`L`、`H`、`dh` **全部约掉了**。KV 侧的算术强度是一个真正的常数，
恒等于 `2/dtype_bytes`，fp32 下就是 `0.5`，跟你用几层、几个头、上下文多长、batch 多大**都无关**。
这条我认为是整篇最值得记住的一步代数——它比"batch=1 时是 0.5"这个表面结论更本质。

**权重侧，batch=1 时近似成立**：`flops_weights/bytes_weights = 2·batch·matmul_params /
[dtype_bytes·(matmul_params + 2·batch·d)]`。当 `batch=1` 且模型不是小到离谱
（`matmul_params ≫ 2d`，任何真实大小的模型都满足），后面那个 `2·batch·d` 可以忽略，
这个比值也逼近 `2/dtype_bytes = 0.5`。

两边都逼近同一个常数 `2/dtype_bytes`，按引理，**加权平均——也就是总的算术强度——
也必然逼近这同一个常数**，不管权重侧和 KV 侧的字节各占多少比例。
这就是为什么 `## 1` 表里 `bs=1` 那一列六行全是 0.50：
**不是因为两侧字节比例没变**（其实变化极大，见下面的实测对照），
**而是因为两侧的"每字节能做几次乘加"本来就相等**，混多少比例都还是那个数。

**拿真实运行数字对照这条"比例剧变、结果不变"**（`_lab/minigpt.py` 默认配置，`analytic_cost()` 实际输出）：

| ctx_len | batch | KV 占总字节 | 算术强度 |
|---:|---:|---:|---:|
| 16 | 1 | 1.9% | 0.500 |
| 16384 | 1 | 95.2% | 0.500 |

同样是 `batch=1`，KV 占访存的比例从 1.9% 暴涨到 95.2%——权重侧和 KV 侧的"混合比例"
天差地别——但算术强度纹丝不动，还是 0.500。这正是引理说的：**当两个待加权平均的比值相等时，
权重占比怎么变都不影响平均值。** 这也是"`bs=1` 恒为 0.5、与 ctx 无关"这句话真正的原因，
而不是碰巧。

**换 dtype 的效果**：这条推导里 dtype 只出现在分母（字节数），FLOPs 的定义（乘加次数）跟精度无关。
所以换成 fp16/bf16（`dtype_bytes=2`）时，这个常数直接变成 `2/2 = 1.0`——不用改 batch、
不用改模型结构，白拿一倍算术强度。这也是为什么推理默认用 fp16/bf16 而不是 fp32（`## 5` 会展开讲）。

**推论（本节最重要的一句话）**：单条请求的解码，从递归生成第一个 token 起，
就已经站在访存瓶颈的地板上了，**没有"更低"可去**。任何试图靠"换更大的模型"
"调整层数/头数"去改善单条请求解码效率的努力，在这个指标上都不会有效果——
因为无论模型多大，`matmul_params` 和它对应的字节数是同比例放大的，比值不变。

### 2.4 只有 batch 能把它抬起来，但两侧抬升的方式不对称

`batch>1` 时重新看两侧：

**权重侧**：`flops_weights = 2·batch·matmul_params` 随 batch **精确线性增长**；
`bytes_weights ≈ dtype_bytes·matmul_params` **几乎不随 batch 变**（权重只读一遍，`batch` 条请求共用同一份）。
所以权重侧的比值 `≈ 0.5·batch`（fp32）——**batch 翻倍，这一侧的强度就翻倍**。
这正是"批处理省下的东西"：把一次昂贵的显存搬运，摊到更多计算上。

**KV 侧**：上面已经证明 `flops_attn/bytes_kv` **恒等于 `2/dtype_bytes`，跟 batch 无关**——
batch 出现在分子也出现在分母，精确约掉。**KV 侧的强度永远抬不动**，
因为 KV 缓存是每条请求私有的历史，不存在"共用一份读一遍"这件事。
这正是"批处理省不掉的东西"。

于是总的算术强度是这两个数的**加权平均**：一个能被 batch 线性抬高（权重侧，
权重是 `bytes_weights`），一个恒定不动（KV 侧，权重是 `bytes_kv`）。
`bytes_kv` 本身随 `batch·ctx_len` 线性增长——**ctx_len 越长，KV 侧在这个加权平均里占的份量越重**，
把总强度往那个恒定不动的 `0.5` 拉回去，不管权重侧被 batch 抬得多高。
这就是 `## 1` 第三条读法（"ctx 越长，batch 抬得越少"）的完整数学解释。

**用真实运行数字看这个"权重侧被抬高、KV 侧纹丝不动、结果被拉回"的全过程**
（默认配置，`analytic_cost()` 输出，`w_ai`/`kv_ai` 是我为讲清楚这一步而手动拆开的两侧子强度，
不是代码直接打印的字段）：

| ctx_len | batch | 权重侧强度 w_ai | KV 侧强度 kv_ai | 总强度 | KV 占总字节 |
|---:|---:|---:|---:|---:|---:|
| 16 | 1 | 0.500 | 0.500 | 0.500 | 1.9% |
| 16 | 64 | 31.396 | 0.500 | 14.496 | 54.7% |
| 16 | 256 | 118.857 | 0.500 | 21.744 | 82.0% |
| 16384 | 1 | 0.500 | 0.500 | 0.500 | 95.2% |
| 16384 | 64 | 31.396 | 0.500 | 0.525 | 99.9% |
| 16384 | 256 | 118.857 | 0.500 | 0.525 | 100.0% |

看最下面三行：`w_ai`（权重侧）在 batch=64/256 时被抬到 31.4 / 118.9，**跟 ctx 长度完全无关**
（横着比 ctx=16 和 ctx=16384 那两行的 `w_ai`，一模一样）——权重侧只认 batch，不认 ctx。
但 `kv_ai` 恒为 0.500，且 ctx=16384 时 KV 已经占了 95%~100% 的字节，
两个数加权平均下来，总强度被死死摁在 0.5 附近，`w_ai` 抬得再高也没用。
**这就是"长上下文杀吞吐"的机制**：不是上下文长了算得慢，
是上下文长了之后，批处理这根唯一的杠杆失去了作用力臂。

（旁注：`w_ai` 没有精确等于 `0.5·batch`——batch=256 时理论值是 128，
实际是 118.857，差了约 7%。这个偏差就来自上面说的"先忽略"的 embedding gather 字节，
batch 越大它越不能忽略。`## 6` 会专门讲这个坑。）

### 2.5 roofline 心智模型：低于机器平衡点就是访存受限

上面算出的是"这段计算本身需要多少强度"，但"访存受限"这个判断还需要另一半——
你的硬件能提供多大强度。roofline 模型把这两半放在一起看：

```
机器平衡点 = 硬件算力峰值(FLOPs/s) / 硬件显存带宽峰值(Bytes/s)
```

判据只有一句话：**如果你这段计算的算术强度低于机器平衡点，你就是访存受限——
算力有富余没用完，因为数据没搬到；如果高于机器平衡点，你是算力受限——
显存有富余没用完，因为算力跟不上。**

⚠️ 这一节故意不给具体硬件的算力/带宽数字——本机没有 GPU，
任何具体数字要么是查资料抄来的、要么是编的，都不符合本库的诚实标准。
**这里只给判据的形式，代入哪块硬件由你自己查那块硬件的规格表。**
方法是：查到你的硬件的 "算力峰值" 和 "带宽峰值"，相除得到机器平衡点，
再拿 `## 2.2`~`## 2.4` 算出的算术强度去跟它比。你会发现：
**decode 阶段的强度通常是 0.5~几十这个量级，而绝大多数现代加速卡的机器平衡点
是几十到几百这个量级**——这就是为什么"decode 是访存受限的"这句话在几乎所有硬件上都成立，
不需要算出具体数字也能得出定性结论；但"具体差多少倍""能不能通过加大 batch 追上"，
必须代入你自己那块硬件的真实规格才能回答，本篇不替你编这个数字。

### 2.6 prefill 与 decode：同一段代码，走到了完全不同的工作点

到目前为止的推导，`batch` 指的是"同时处理几条请求各自的 1 个新 token"。
但 `forward_cached()` 的 `new_tokens` 参数并不要求只传 1 个 token——
**prefill 阶段一次性把整段 prompt（比如 500 个 token）作为 `new_tokens` 传进去，
处理的是同一条请求内部的 T=500 个新位置，而不是 500 条不同的请求。**

关键洞察是：**从矩阵乘的角度看，"同一条请求的 T 个新位置"和
"T 条请求各自的 1 个新位置"，在权重侧是同一件事**——权重矩阵不关心传进来的
`T` 行数据来自哪里，它只是把这 `T` 行都乘一遍，权重只读一次。
所以把 `## 2.4` 里的推导逐字重做一遍，只把"batch"换成"T"（本次前向新处理的 token 数）：

```
flops_weights(prefill) = 2 · T · matmul_params      （权重侧 FLOPs 随 T 线性增长）
bytes_weights(prefill) ≈ dtype_bytes · matmul_params （权重只读一遍，被这 T 个位置共用）
```

**一次 prefill 处理的 T 往往是几十到几千**（整段 prompt 的长度），
而一次 decode 处理的 T 恒为 1。代入权重侧强度 `≈ 0.5·T`（fp32）：
prefill 的 T 大，强度就高，**天然更接近算力受限**；decode 的 T=1，
强度死死卡在 0.5，**天然是访存受限**。

（唯一的差别在注意力部分：decode 场景里"batch 条请求各自定长看 ctx_len 个历史"，
而 prefill 场景里 T 个新位置要满足因果关系——第 i 个新位置只能看到 `p0+i` 个历史，
是一个从短到长的窗口，而不是统一的 `ctx_len`，多出一个新位置之间 `O(T²)` 的自注意力项。
这个细节不改变结论：数量级上，权重侧强度仍随 T 增长，prefill 仍然天然更接近算力受限，
只是精确公式比直接套用 `## 2.4` 的 batch 公式要复杂一点，本篇不展开精确推导。）

**同一段代码、同一个算子，工作点完全不同**：`_lab/minigpt.py:139` 的 `forward_cached()`
不区分"这是 prefill 调用还是 decode 调用"——它只看 `new_tokens` 有几个元素。
`_lab/minigpt.py:139-145` 的函数说明明确写了这一点。这不是简化，
这恰恰是"prefill 和 decode 不是两种算法，是同一个算子在不同 T 下的两个工作点"
这条结论的代码证据。`## 4` 会看真实引擎的调度器如何利用这一点。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang 等，带 `引擎:文件:行`）

`## 2.6` 推出的结论是"prefill 和 decode 是同一个算子在不同 T 下的两个工作点，
不是两种算法"。这不只是本库玩具引擎的设计选择——真实调度器也是这么建模的。

vLLM 的调度器（`vllm:vllm/v1/core/sched/scheduler.py:487`）在源码注释里直接写明：
调度器层面**没有"decode 阶段"或"prefill 阶段"这种区分**，每个请求只有
`num_computed_tokens`（已经算过多少）和 `num_tokens_with_spec`（应该算到多少）两个数，
调度要做的事就是让前者追上后者——这和 `## 2.6` 说的"`forward_cached()` 只关心
`new_tokens` 有几个元素，不关心这是不是 prefill"是同一个设计原则的两种实现。

这条原则直接服务于 `## 2.4` 的结论：**batch（这里更准确地说是"一步里凑进来的 token 总数"）
是唯一能抬高算术强度的杠杆**，所以调度器的核心变量是一个跨请求共享的 token 预算
（`vllm:vllm/v1/core/sched/scheduler.py:504`，`token_budget = self.max_num_scheduled_tokens`），
每一步从多条请求（无论它们各自是在做 prefill 还是 decode）里凑出尽量多的新 token，
一起塞进同一次前向——这正是把 `## 2.4` 里的"T"和"batch"这两个各自能摊薄权重读取的维度，
在调度层面合并成同一个预算来管理。这也是 `[[04-连续批处理]]` 要展开讲的机制，
本篇只点出它和这条式子的关系。

这个统一预算还带来一个直接后果：**一条请求如果需要新算的 token 数太多
（典型情况是一条很长 prompt 的 prefill），会被显式截断，不允许一次吃光整份预算**
（`vllm:vllm/v1/core/sched/scheduler.py:566-572`，`num_new_tokens` 会被
`long_prefill_token_threshold` 和 `token_budget` 两道上限夹住，也就是"分块 prefill"，
chunked prefill）。结合 `## 2.6`：一次处理的 T 越大，这次前向的算术强度越接近算力受限，
如果放任一条几千 token 的 prefill 独占一整步，这一步里其它请求的 decode（本来强度就卡在 0.5，
延迟敏感）就要排队等这个算力受限的大块任务算完——分块 prefill 的作用是让"高强度的大块 T"
和"低强度的 decode token"能在同一个 token 预算里揉在一起调度，而不是让前者饿死后者。
**这里只讲机制，不给具体阈值默认值或吞吐数字**——那些数字属于"真实引擎的实测"，
不是本篇能负责的范围（见 `_PLAN.md` §1 第 4 条的红线）。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：用解析模型（手推公式）而不是直接上 profiler 实测数字来讲这个原理。**
- 为什么这样：解析模型不需要摸到目标硬件就能推出定性正确、可复现、可被读者亲手验算的结论
  （`bs=1` 恒为 0.5 这条断言在任何一台笔记本上都能重新推一遍）；它讲的是"为什么"，
  profiler 数字讲的是"是什么"，教学库要的是前者。
- 不这样会怎样：如果一开始就丢一份具体硬件上的 profiler 截图，读者能记住"decode 慢"，
  但换一块 GPU、换一个模型尺寸，结论是否还成立就说不清楚——因为具体数字背后的结构性原因
  从没被讲过。
- 什么时候可以不这样：当你已经锁定了目标硬件和具体 kernel 实现，需要决定"这个 batch size
  要不要单独写一个 kernel"这类微秒级的工程决策时，解析模型的精度不够，必须上真实 profile
  （`nsight`/`torch.profiler` 之类），本篇的模型只负责告诉你"往哪个方向想"。

**决策二：把 embedding 的查表字节和参与矩阵乘的权重字节分开算，而不是混在一起当"权重"处理。**
- 为什么这样：`wte`/`wpe` 是查表（gather），只读用到的那几行；矩阵乘权重是被完整读入参与运算的。
  两者的"读取量随请求数怎么变"这条规律不同，混在一起算会污染 `## 2` 推出的比值。
- 不这样会怎样：见 `## 6` 第一条踩坑——第一版就是这么算错的，强度曲线呈现出假的"随 ctx 上升"
  趋势，会把"上下文越长越受限"这个错误结论当成真的写进结论里。
- 什么时候可以不这样：当 `vocab` 和 `d_model` 都足够大、`lm_head` 本身的 FLOPs 量级已经不可忽略时
  （比如 `vocab=128k` 级别的真实模型），更需要精细区分而不是更能马虎；本库没找到"可以放心混算"
  的场景，这条决策没有豁免条件，只有"错得明显"和"错得隐蔽"的区别。

**决策三：把"加大 batch"而不是"换更大模型"或"缩短上下文"当成抬高算术强度的手段。**
- 为什么这样：`## 2.3` 证明了权重侧和 KV 侧在 batch=1 时强度都恒为 `2/dtype_bytes`，
  换多大的模型、缩多短的上下文都不改变这个比值——唯一能让权重侧强度脱离这个常数的变量
  只有 batch（`## 2.4`）。
- 不这样会怎样：如果指望"用更大的模型"缓解访存瓶颈，会发现强度纹丝不动
  （模型变大时 FLOPs 和字节数同比例放大，比值不变）；如果指望"缩短上下文"，
  `## 1` 的表已经说明短上下文时强度反而更容易被 batch 抬高，但短上下文本身通常不是能自由选的东西。
- 什么时候可以不这样：单条请求、低延迟优先的场景（本地单用户交互、debug）里，
  `batch=1` 本身就是唯一诉求，此时"抬高算术强度"根本不该是目标——抬高强度是为了吞吐，
  代价是要攒够一批请求再算，会牺牲单条请求的延迟。

**决策四：默认建议用 fp16/bf16 而不是 fp32 做推理这条常数上的选择。**
- 为什么这样：`## 2.3` 推出这个常数是 `2/dtype_bytes`，FLOPs（乘加次数）不随精度变，
  只有字节数随精度变——换成 2 字节的 dtype，常数直接从 0.5 翻倍到 1.0，不需要动 batch
  或架构，是几乎免费的强度提升。
- 不这样会怎样：继续用 fp32，同样的硬件在同样负载下访存字节数always翻倍，
  更容易先撞到 `## 2.5` 说的机器平衡点天花板。
- 什么时候可以不这样：涉及数值敏感的累加（某些 loss 计算、优化器状态）以及训练阶段，
  仍然需要 fp32 或至少 fp32 累加的混合精度，不能无脑把所有环节都砍成 fp16——
  本篇只讨论推理阶段 decode 这一段路径，不代表全流程都该降精度。

## 6. 常见错误与踩坑

**踩坑一（本库真实踩过，不是编的）：算术强度模型第一版算错了。**
第一版的分母把 embedding 的字节算了进去，分子却忘了加 `lm_head` 的 FLOPs——
`lm_head` 和 `wte` 权重共享，很容易被误当成"反正都是 embedding，只算一次字节就行"，
但它在前向里实实在在做了一次 `d×V` 规模的矩阵乘，这次乘法的 FLOPs 必须计入分子。
后果是算出来的强度是 `0.43 → 0.50` 一路爬升，看着非常像"上下文越长越受限"这个
（错误的）定性结论——**曲线形状看起来合理，正是这种错误最危险的地方，
因为它不报错、不崩溃，只是安静地给出一个方向性错误的图。**
教训被写进了 `_lab/minigpt.py:217-219` 的代码注释里：**必须把"参与矩阵乘的权重"
和"只被 gather 的 embedding"分开算**。更一般的教训（也是 `_PLAN.md` §7 第 1 条）：
**任何 roofline 类的解析模型，写完先验证退化情形是否等于理论值**
——这里的退化情形就是"`batch=1` 应该恒等于 `2/dtype_bytes`"，这是一条闭式解，
不需要猜、不需要跑实验就能算出应该是多少。`_lab/minigpt.py:274-280` 的断言
就是把这条"先验证退化情形"的教训焊死成了可执行的护栏，不再靠人眼看曲线顺不顺眼。

**踩坑二：把"decode 是访存受限的"过度推广成"这个模型是访存受限的"。**
`## 2.6` 已经说明 prefill 和 decode 是同一个算子在不同工作点上的表现——
prefill（T 大）通常更接近算力受限，decode（T=1）访存受限。
如果只用某一次 decode 的 profile 结果去判断"要不要给 prefill 也做同样的优化"，
或者反过来拿 prefill 的结论套用到 decode 上，两个方向都会得出错误的优化优先级
（比如给 prefill 做的算力优化，用在 decode 上收益甚微，因为 decode 从来不缺算力）。

**踩坑三：把"抬高算术强度"直接当成"提高了吞吐"，或者把"batch 越大越好"当成免费午餐。**
`## 2.5` 的 roofline 判据说的是"低于机器平衡点就有性能损失的空间"，
抬高强度只是**必要条件**——真正吃到吞吐收益还要看调度器有没有真的把这些请求凑成一批
（这是 `[[04-连续批处理]]` 要解决的工程问题，本篇只算"凑起来能有多大收益"这笔账，
不管"怎么凑起来"）。另外，`## 2.2`~`## 2.4` 算的只是**访存带宽/FLOPs 这条"速度"账**，
完全没算 KV 缓存要占多少块显存这条**"容量"账**——batch 能开多大，
最终会被"KV 缓存能不能装得下"这另一条完全不同的约束卡住，
这是 `[[03-分页KV与块管理]]` 的主题，本篇故意不覆盖，别把两条账混成一条。
