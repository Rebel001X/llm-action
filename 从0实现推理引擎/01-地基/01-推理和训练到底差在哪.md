# 推理和训练到底差在哪

> **一句话**：自回归把"批"拆成了串行的 token。
> **前置**：无——这是全库第 0 课，读完它再进 `02-自回归解码为什么是访存瓶颈.md`。

## 0. 这一篇要解决什么问题

网上最流行的一句话是："推理不就是训练去掉反向传播（backpropagation）嘛"。

这句话在**字面上**没错——推理确实只有前向传播（forward pass），确实不用算梯度、不用更新参数。但如果你带着这个理解去写推理引擎，你会在接下来的每一步都栽跟头：你会以为"批（batch）越大就该越快"，直到显存爆掉才发现批里每条请求长度都不一样；你会以为"没有反向传播，计算应该更轻"，结果发现单条请求跑起来比你想的慢得多、GPU 利用率却低得可怜；你会以为"性能测试对不对靠肉眼看结果像不像"，结果一个悄悄错位的缓存写入让模型输出看起来"通顺"但其实完全变了个人。

这篇要说清楚：**"去掉反向传播"只是表面。真正决定推理引擎长什么样的，是一条更底层的约束——自回归解码（autoregressive decoding）逼着你一个 token 一个 token 地往外吐，而训练完全没有这条约束。**

从这一条根因出发，可以直接推出本库后面几十篇要解决的四个具体差异，这篇先把它们摆出来，后面每一篇再展开一个：

1. **瓶颈不同**：训练是算力受限（compute-bound），推理的解码（decode）阶段是访存受限（memory-bound）——展开见 `02-自回归解码为什么是访存瓶颈.md`。
2. **"批"的含义不同**：训练里的批是同构的（等长、同时开始同时结束），推理里的批天生异构——这是连续批处理（continuous batching）存在的理由，展开见 `04-连续批处理.md`（在 `02-最小可跑引擎/`）。
3. **显存的用途不同**：训练显存被激活值（activations）和优化器状态（optimizer states）吃掉，推理显存被权重和 KV 缓存（KV cache）吃掉——展开见 `03-KV缓存的第一性原理.md`。
4. **正确性判据不同**：训练看 loss 曲线往下走就行，推理必须逐 token 对齐——本库 `_lab/tests` 的每一条测试都建立在这条判据上。

这四条不是四个孤立的知识点，是**同一根因在四个维度上的投影**。看完这篇，你应该能自己把其中任何一条重新推导出来，而不是背下来。

### 1.2 一个不用跑代码、自己就能算的式子

算术强度（arithmetic intensity）的定义是"每读 1 字节数据，能做多少次浮点运算"：`AI = FLOPs / Bytes`。

对一个 fp32（4 字节）权重矩阵里的**每一个参数**，解码一步要做的事永远是同一件事：读这个参数（4 字节），跟激活值做一次乘法、一次加法（2 FLOP，这是"乘加"，multiply-accumulate 的标准计法）。所以：

```
单个参数的算术强度 = 2 FLOP / 4 字节 = 0.50
```

上下文长了、模型深了，这个比值**根本不会变**，因为它是"每个字节配几次运算"这个局部比值，不是总量。这就是 1.1 里那张表第一列恒为 0.50 的原因，`## 2` 会把它从"单个参数"推广到"整个模型"。

### 1.3 另一个现象：生成为什么必须是个循环

打开 `_lab/minigpt.py:178-192` 的 `generate()` 函数，你会看到生成 `n_new` 个新 token 是一个 Python `for` 循环，每轮只喂 1 个 token 进 `forward_cached`。这不是这份教学代码写得"不够并行"——**换成任何框架、任何硬件，这个循环都拿不掉**。第 5 个要生成的 token 是什么，本身就是模型看到第 4 个 token 之后现算出来的；在算出第 4 个之前，第 5 个 token 的输入根本不存在。这条数据依赖（data dependency）是自回归模型的定义本身，不是工程实现的疏忽。

对照着看 `forward_naive(cfg, w, tokens)`（`_lab/minigpt.py:95-116`）：这个函数对一整条**已经完全知道内容**的序列，是一次性把所有位置的 Q/K/V、注意力（attention）、前馈网络（FFN）全部用矩阵乘算完的——序列内部没有循环。**训练对一个 batch 里的每一条样本做的正是这件事**：给定一整句话（比如"猫坐在垫子上"），所有位置的目标 token 都已知（教师强制，teacher forcing），一次前向就能把这句话里每个位置的 loss 全部算出来，然后一次反向传播搞定所有位置的梯度。

对比一下就是核心结论：

| | 训练一步 | 推理生成 n_new 个 token |
|---|---|---|
| 目标 token 是否提前已知 | 是（来自数据集） | 否（要模型自己吐出来） |
| 序列内 T 个位置能否一次算完 | 能（`forward_naive` 那种一次矩阵乘） | 只有 prompt 部分能，新生成的部分不能 |
| 循环发生在哪 | 只在 step 之间（多个 batch） | 在 token 之间（单条请求内部） |

`generate` 里真正体现"逐 token 循环"的就是下面这几行（节选自 `_lab/minigpt.py:181-187`，`use_cache=True` 那条路径）：

```python
if use_cache:
    cache = KVCache(cfg, max_seq=len(prompt) + n_new + 1)
    logits = forward_cached(cfg, w, out, cache)     # 一次性处理整段 prompt（prefill）
    for _ in range(n_new):
        nxt = int(logits.argmax()) if greedy else int(np.argmax(logits))
        out.append(nxt)
        logits = forward_cached(cfg, w, [nxt], cache)  # 每轮只喂 1 个新 token（decode）
```

第一次调用 `forward_cached` 处理的是整段已知的 prompt（这一步叫 prefill，跟训练的"一次算完整段"性质相同）；但从 `for` 循环开始，每一轮都只能喂**刚采样出来的那一个 token**——因为下一轮要喂什么，取决于 `logits.argmax()` 这一行算出的结果，这行代码没跑完，下一轮的输入字面上就不存在。Python 层面这只是个 `for` 循环，但它对应的是数据依赖，不是可以展开成并行的普通迭代。

换算成数字更直观：训练一条长度 512 的序列，`forward_naive` 只需要被调用 1 次，512 个位置的 loss 一起出来；推理如果要生成 512 个新 token，`forward_cached` 要在循环里被调用 512 次，一次只吐 1 个 token。**调用次数从 1 变成 512，不是因为推理"效率低"，是因为这 512 次里，后一次的输入字面上要等前一次的输出算出来才存在。**



## 2. 原理

把 `## 1` 的两个现象串成一条因果链：

**第一步：自回归约束决定了"生成"必须串行。**
语言模型定义的是 `P(token_t | token_1, ..., token_{t-1})`。要采样出 `token_t`，前 `t-1` 个 token（包括模型自己刚生成的那些）必须已经存在。这不是"当前实现算力不够所以串行"，是**这个概率定义本身要求前一个输出是后一个输入的一部分**。训练不需要这个循环，是因为训练时序列的每个位置的"输入前缀"来自数据集里已经写好的句子，不需要模型自己现算——这就是 `## 1.3` 表格里第一行的差别。

**第二步：串行导致解码一步的工作量结构很特殊。**
在 decode 阶段（已经有历史 KV、只算新来的 1 个 token）批量为 1 时，模型要做的事是：为这 1 个 token，把每一层的每一个权重矩阵、以及它要关注的每一个历史 KV，各参与一次乘加。用符号写：

```
FLOPs_权重侧 = 2 × (权重参数总数)          ← 每参数 1 次乘加
Bytes_权重侧 = dtype_bytes × (权重参数总数) ← 每参数读 1 次
FLOPs_KV侧  = 2 × (KV 元素总数)
Bytes_KV侧  = dtype_bytes × (KV 元素总数)
```

两侧分别算算术强度都是 `2 / dtype_bytes`——跟权重有多少个参数、KV 有多长上下文**完全无关**，因为分子分母是同倍数增长的。两侧的强度既然都恒等于同一个常数，加权平均（无论权重和 KV 各占多少比重）自然也还是这个常数。fp32 下 `dtype_bytes=4`，算出来就是 0.50。这正是 `_lab/minigpt.py:197-214` 那段 `analytic_cost` 函数文档字符串（docstring）里写的结论，也是 `_lab/minigpt.py:274-280` 用 4 个不同 ctx 值验证过的断言。

这一步是本篇最容易被误解的地方，专门强调一句：**推理在 batch=1 时不是"因为某个环节没优化好"才卡在访存瓶颈（memory-bound）上，它是数学上一开始就已经在瓶颈的底部，没有更低可去。** 想再往下降，唯一的物理手段是换更小的 `dtype_bytes`（比如 fp16 是 2、fp8 是 1），而不是"优化调度"或"换个框架"。

**第三步：既然分母（batch=1 时）已经到底，唯一能抬高强度的是权重被更多请求共用。**
权重是**共享**资源：不管同时服务 1 条请求还是 64 条，每个权重参数只需要从显存读 1 次，可以让这一批请求都用上这同一次读取的结果。于是权重侧的强度会随 batch 线性抬高（`0.5 × batch`），这正是 `_lab/minigpt.py:282-286` 验证的"batch 越大、强度显著抬高"这条断言。但 KV 是**私有**资源：每条请求的历史 K/V 只属于它自己，不能被别的请求共用，batch 再大也抬不动 KV 侧那部分强度。当上下文很长时 KV 侧字节数远超权重侧，整体强度就被 KV 拖回接近 0.50——这是 `_lab/minigpt.py:288-292` 验证的"长上下文下 batch 收益被稀释"。这就是 `## 1.1` 表格里"ctx 越长，同一 bs 往右抬得越少"背后的完整机制，也是 KV 占访存比重那一列从 54.7% 一路爬到 99.9% 的原因。

**第四步：想拉长 batch，就必须接受推理批与训练批的语义分裂。**
训练要凑一个 batch 很简单：从数据集里随便挑 N 条样本，补齐（pad）到同一长度，一起进、一起出，下一个 batch 再重新挑。这是**同构**的批：形状固定、生命周期一致，天生适合写成一个静态的四维张量（tensor）喂进框架。

推理的"批"完全不是这么回事：请求是用户一条一条发过来的，到达时间不同；每条请求想要生成的长度不知道，可能第 3 步就因为遇到停止符结束，也可能要跑到第 500 步；结束时间自然也不同。画一条时间轴，三条请求的生命周期大概长这样：

```
时间步 →   0    10   20   30   40   50   60   70   80
请求 A     [============================================]   （早到，要生成很长）
请求 B          [==========]                                （比 A 晚到，第 25 步就撞上停止符）
请求 C                    [======================]          （比 B 更晚到，还在生成）
```

如果照搬训练那一套"凑够 N 条同构请求再一起处理、处理完一起放行"：要么 A 必须等 B、C 都到齐了才能开始（早到的请求空等），要么 B 在第 25 步已经结束了，但它占的那个批次槽位既不能立刻交给新来的请求，也不能提前退出——因为同一批里的 A、C 还没算完，槽位要一直空占到这一整批全部结束。这两种情况都要命：**先到的请求要陪后到的请求傻等，跑得快的请求要陪跑得慢的请求继续占着显存和算力槽位**。真实推理引擎因此必须发明连续批处理（continuous batching）——每一步都重新决定这一批里到底装哪些请求：B 在第 25 步一结束，它的槽位立刻空出来，调度器下一步就能把新来的请求填进去，不需要等 A、C 也跑完。训练完全不需要这套机制，因为它的批从一开始就是同构的，没有"某条提前结束、某条还没到"这回事。

**第五步：这条语义分裂进一步逼出显存用途的分裂。**
训练显存的大头是**激活值**（每一层前向的中间结果，要留到反向传播时用来算梯度）和**优化器状态**（比如 Adam 每个参数要额外存动量和二阶矩这两份统计量，混合精度下还要存一份 fp32 主权重副本）。这两块都跟"当前这个 batch 的形状"绑定死了——batch 一结束，激活值就可以释放，下一个 batch 重新申请，是**周期性**的开销。

推理显存的大头是**权重**（固定不变，服务全程只加载一次）和 **KV 缓存**（每条请求在它存活期间持续增长，长度取决于这条请求已经生成了多少 token，跟其他请求无关）。KV 缓存不能像训练激活值那样"这一步用完就扔"——它是这条请求还没结束前必须一直留着的状态，而且每条请求何时结束互不相同。这就是为什么真实推理引擎会把 KV 缓存做成一个独立的、可以动态分配/回收的内存管理系统（分页 KV，展开见 `03-KV缓存的第一性原理.md`），而训练框架不需要为激活值发明这么复杂的东西。

**第六步：没有 loss，正确性判据只能是"逐 token 对齐"。**
训练有一个天然的标量信号——loss，用来判断"训练得好不好"，允许有噪声、允许曲线上下抖动，只要长期趋势往下走就行。推理阶段**不存在**这样一个可以容忍抖动的信号：你给用户展示的就是模型吐出来的具体 token 序列，用户不会去看你的"平均对齐度是 98%"。任何为了提速而做的改动——加 KV 缓存、把 KV 分页、把多条请求拼成一批、换算子实现——都必须让输出的 token 序列跟没做这个优化之前**完全一样**（数值上允许浮点误差，但离散采样出来的 token id 必须一致）。这不是"标准严格"的选择，是因为一旦放松这条标准，你就没有任何客观办法判断一次"优化"到底是让引擎变快了，还是悄悄改变了模型该说的话。

### 3.1 一个真实规模的 KV 缓存估算（解析计算，不是实测）

`_lab/minigpt.py` 默认配置是玩具尺寸（4 层、d_model=128），跑出来 `kv_bytes_per_token` 只有 4096 字节，感受不到 KV 缓存真正的压力。下面换一组**自己设定**的、量级上接近一个中等规模开源模型的参数，纯手算，标清楚假设：

假设：
- 层数 `L = 32`
- `d_model = 4096`
- 精度 fp16，`dtype_bytes = 2`
- 不考虑分组查询注意力（GQA，会显著压缩 KV，本库后面会专门讲）——这里用 `_lab/minigpt.py:38` 里最朴素的公式，即每个头都有自己独立的 K、V

代入 `_lab/minigpt.py:38` 的公式 `2 × L × d_model × dtype_bytes`：

```
每 token KV 字节 = 2 × 32 × 4096 × 2 = 524,288 字节 = 512 KiB
```

一条请求、上下文长度 4096 时的 KV 总量：

```
4096 × 512 KiB = 2,097,152 KiB ≈ 2 GiB
```

如果同时服务 64 条这样的请求（连续批处理希望达到的量级）：

```
64 × 2 GiB = 128 GiB
```

对照一下权重本身的显存占用：一个 7B 参数量级的模型，fp16 下权重是 `7×10⁹ × 2 字节 ≈ 14 GiB`。**64 条中等长度请求的 KV 缓存（128 GiB）比权重本身（14 GiB）大了近 9 倍**，而且远超单张 80 GiB 显卡的容量。这组数字解释了两件事：第一，`## 2` 第五步说"KV 缓存是推理显存的大头"不是夸张;第二，这也是为什么真实引擎一定要上 GQA、量化 KV、分页管理这些手段——它们的机制不在这篇文章的范围内，`03-KV缓存的第一性原理.md` 会展开。

把同一组假设（`L=32, d_model=4096, dtype_bytes=2`）按不同上下文长度、不同并发数摆成一张表，更容易看出"线性增长"这四个字有多不留情面：

| 上下文长度 | 单条请求 KV | 64 条并发合计 KV |
|---:|---:|---:|
| 128 | 0.06 GiB | 4 GiB |
| 1,024 | 0.5 GiB | 32 GiB |
| 4,096 | 2 GiB | 128 GiB |
| 16,384 | 8 GiB | 512 GiB |
| 32,768 | 16 GiB | 1,024 GiB |

每一格都是"每 token KV 字节 × 上下文长度 × 并发数"这一个式子算出来的，没有任何隐藏系数。表里最后一行（32K 上下文、64 路并发）已经是 1 TiB 量级的显存需求——这不是危言耸听，而是长上下文 + 高并发这个组合天然会撞到的量级，也是本库后面要讲分页、量化、GQA 这些手段的现实驱动力。

作为对照，训练侧显存另一个大头——优化器状态——量级是怎样的：Adam 优化器给每个参数额外存动量和二阶矩两份统计量，混合精度训练下还要存一份 fp32 主权重副本，通行的估算是每个参数额外背上 12～16 字节的优化器开销，跟 batch 大小、序列长度**无关**，是参数量的固定倍数。这跟推理里 KV 缓存"随 batch × 上下文线性增长、跟参数量无关"正好是两种不同的增长方式——这也是显存用途分裂的量化体现，不需要跑代码，两个式子摆在一起就能看出来。

### 3.2 手算复核：用公式重新推出表格里的一个数字

`## 1.1` 的表是跑代码打出来的，光看数字容易觉得"反正代码说了算"。这里挑表里 `ctx=256, bs=4` 那一格（印着 `1.17`），完全不跑代码，只用 `_lab/minigpt.py:216-230`（`analytic_cost` 函数体里的公式部分）手算一遍，验证它不是拍出来的。

默认配置 `Config()`（`_lab/minigpt.py:26-27`）是 `n_layer=4, n_head=4, d_model=128, vocab=512`，于是 `d_head = 128 / 4 = 32`。

**第一步，权重侧（对应 `_lab/minigpt.py:220-221, 226`）：**

```
matmul_params = L × (4d² + 8d²) + d × vocab
              = 4 × (4×128² + 8×128²) + 128×512
              = 4 × (65,536 + 131,072) + 65,536
              = 786,432 + 65,536 = 851,968

flops_weights = 2 × batch × matmul_params = 2 × 4 × 851,968 = 6,815,744
bytes_weights = dtype_bytes × (matmul_params + 2×batch×d)
              = 4 × (851,968 + 2×4×128) = 4 × 852,992 = 3,411,968
```

**第二步，KV/注意力侧（对应 `_lab/minigpt.py:223, 228`）：**

```
flops_attn = batch × L × H × 4 × ctx_len × d_head
           = 4 × 4 × 4 × 4 × 256 × 32 = 2,097,152

bytes_kv = batch × ctx_len × (2 × L × d × dtype_bytes)
         = 4 × 256 × (2×4×128×4) = 4 × 256 × 4,096 = 4,194,304
```

**第三步，合起来（对应 `_lab/minigpt.py:229-230, 236`）：**

```
total_flops = 6,815,744 + 2,097,152 = 8,912,896
total_bytes = 3,411,968 + 4,194,304 = 7,606,272

算术强度 = 8,912,896 / 7,606,272 ≈ 1.172
```

保留三位小数是 `1.172`，`## 1.1` 表格用两位小数显示成 `1.17`——对上了。这不是凑出来的：公式里的每一项都能在 `_lab/minigpt.py:216-230` 里找到对应的一行代码，你可以随便换一个 `(ctx, batch)` 组合再手算一次，或者直接在 Python 里跑 `analytic_cost(Config(), 256, batch=4)` 让代码替你算——两条路径必须给出同一个数字。这正是本库"每个原理必须有可跑代码撑腰"这条红线的一次具体示范：不是"信我"，是你自己拿计算器也能核对。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang 等，带 `引擎:文件:行`）

`## 2` 推出的六步里，第三、四、五步在真实引擎里都能找到对应的代码结构。这里只挑三处最直接的证据，机制细节留给后面专门讲调度和 KV 缓存的篇目。

### 4.1 前向确实是唯一路径——但这只是表面

vLLM 里真正在每一步 decode 时被调用、产出 logits 的函数是 `execute_model`，它被 `@torch.inference_mode()` 装饰（`vllm:vllm/v1/worker/gpu_model_runner.py:4283`，函数本体紧跟在 `:4284`）。`inference_mode` 比更常见的 `no_grad` 还要彻底：它连"这个张量将来可能要参与反向传播"这件事本身都不记录，省掉了自动微分（autograd）的簿记开销。这是"推理没有反向传播"这句话在真实代码里最直接的落地——但正如 `## 0` 强调的，这只是表面差异，决定引擎骨架长什么样的是下面两条。

### 4.2 批不是一个定形张量，是两条会动的队列

vLLM 的调度器（`Scheduler`）把"正在跑的请求"和"还在排队的请求"分别放在两个独立、长度可变的容器里：等待队列 `self.waiting`（`vllm:vllm/v1/core/sched/scheduler.py:196`）和运行列表 `self.running: list[Request]`（`vllm:vllm/v1/core/sched/scheduler.py:199`）。注意 `running` 的类型标注是 `list[Request]`——一个可以随时增删元素的 Python 列表，不是训练里那种一旦组好形状就固定到底的 `(batch, seq_len)` 张量。调度器每一步都要重新决定这一步的这一批里到底装哪些请求、有没有请求要被换出去等下一轮——这正是 `## 2` 第四步说的"每一步都重新决定批的构成"，而不是训练那种"batch 组好之后直到这个 step 算完都不会变"的写法。

### 4.3 KV 缓存是一套独立于权重加载路径的动态分配系统

vLLM 把 KV 缓存的管理从模型权重的生命周期里完全拆出来，单独用一个 `KVCacheManager` 类负责（`vllm:vllm/v1/core/kv_cache_manager.py:118`），对外的核心接口是 `allocate_slots`（`vllm:vllm/v1/core/kv_cache_manager.py:347`）——每当调度器决定要给某条请求继续生成新 token，才会向这个管理器申请新的存储块；不像权重那样在服务启动时一次性、整体加载完就不再变化。这个管理器往下就是分页（paging）机制的地基，具体怎么分块、怎么回收留给 `03-KV缓存的第一性原理.md`；这里只需要看到一件事：**真实引擎专门为 KV 缓存写了一整套独立于权重加载路径的分配器，这不是随意的架构偏好，是 `## 2` 第五步说的"显存用途分裂"逼出来的必然结构。**

### 4.4 三条证据放在一起看

把 `4.1`～`4.3` 摆在一起，能看出它们不是三个无关的实现细节，而是同一条因果链在同一份代码库里的三个落点：`inference_mode` 关掉自动微分，只是"没有反向传播"这句大实话最表层的体现；`Scheduler` 里 `waiting`/`running` 两条会动的队列，是"批天生异构"这条结论逼出来的调度结构；`KVCacheManager` 独立于权重的按块分配，是"显存用途分裂"这条结论逼出来的内存管理结构。三条证据分别对应 `## 2` 第一、四、五步——**这也是为什么本篇一直强调"表面差异"和"根因"要分开看：如果只看到 `inference_mode` 就以为理解了推理引擎，会完全漏掉后面两条真正决定引擎复杂度的部分。**

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：用 KV 缓存，而不是每步重算整条前缀。**
- 为什么这样：把每步新增的计算量从"重算全部历史"降到"只算新来的这一小段"，`forward_cached` 只处理 `new_tokens`（`_lab/minigpt.py:139-146`），历史 K/V 直接从缓存读。
- 不这样会怎样：退化成 `generate` 里 `use_cache=False` 那条分支（`_lab/minigpt.py:188-191`），每生成一个 token 就把已生成的全部内容喂给 `forward_naive` 重新算一遍，生成 n 个 token 的总计算量是 O(n²) 量级，越往后越慢。
- 什么时候可以不这样：只需要对一段**已经完整存在**的文本打一次分（比如算困惑度、只要 prompt 部分的 logits），根本不涉及"逐 token 生成"，一次前向就结束了。这种场景下引入 KV 缓存反而多一份实现复杂度和显存占用，没有收益可言。

**决策二：用连续批处理，而不是训练式的同步定长批。**
- 为什么这样：请求的到达时间、期望长度、结束时间三个维度天生异构，同步等批会让先到的请求空等、快请求陪着慢请求继续占显存。
- 不这样会怎样：要么退化成串行处理单条请求——`## 1` 已经证明 batch=1 时算术强度恒卡在瓶颈底部（0.50），吞吐提不上去；要么退化成"凑够 N 条才发车"的静态批，其中最长的那条请求没结束，整批都不能放行，长尾请求拖垮全局延迟。
- 什么时候可以不这样：离线批量评测这类场景——所有输入提前已知、可以按长度预先分桶、不追求低延迟——用接近训练那种同步大批反而实现更简单，连续批处理调度器的复杂度在这里是不必要的开销。

**决策三：把 KV 显存当成独立于权重的、按需增长的资源来管理。**
- 为什么这样：权重是服务全生命周期的固定开销，KV 是随并发请求数和上下文长度实时变化的开销，两者混在一起管理，要么必须按峰值预留（浪费显存），要么用到才发现不够（服务崩溃）。
- 不这样会怎样：退回 `KVCache` 第一版那种做法——为每条请求按 `max_seq` 预分配定长数组（`_lab/minigpt.py:128-132`）——再短的请求也占着按最大长度算出来的显存，并发数怎么都上不去，这正是 `_PLAN.md` §2 里点名"分页 KV 要解决的事"。
- 什么时候可以不这样：单用户、几乎不并发的本地小模型场景（比如本地聊天工具），固定预分配一份够用的 KV 数组反而更简单，省掉分页/回收整套机制的实现和运行时开销。

**决策四：用"逐 token 输出对齐"，而不是"loss/统计指标差不多"，作为推理优化的正确性判据。**
- 为什么这样：服务阶段没有一个可以容忍抖动的标量信号——用户看到的就是具体的 token 序列，任何一次悄悄的语义偏移都是用户能直接感知到的错误。
- 不这样会怎样：bug 会是静默的。本文引用的"第一版 `analytic_cost` 把 embedding 字节算进分母、却漏了 lm_head 的 FLOPs"就是真实发生过的案例（教训记在 `_lab/minigpt.py:217-219` 的注释里）——如果验收标准只是"趋势看着差不多"，这类整体口径错误可以蒙混很久都发现不了。
- 什么时候可以不这样：只有当"优化"本身就显式承诺会改变数值结果时（比如把权重量化到 int8/int4，这类优化的前提就是"近似"而非"相等"），才需要换一套判据——不是逐 token 严格相等，而是效果指标（困惑度、任务准确率）落在容忍范围内。但这属于另一类要显式声明的优化，不能和 KV 缓存、分页、批处理这类"理应零误差"的优化混为一谈。

## 6. 常见错误与踩坑

1. **以为"没反向传播 = 计算更轻"，把瓶颈方向判断反了。** 推理变慢时第一反应是"算力不够、该换更强的卡"，但 `## 2` 第二步已经证明 batch=1 时瓶颈根本在访存带宽，砸算力对这部分基本无效——真正该做的是想办法抬高 batch 或换更小的 dtype。
2. **把训练"batch 越大越好"的直觉直接套到推理上。** `## 1.1` 的表已经摆明：ctx=16384 时哪怕 bs 冲到 256，算术强度也只能抬到 0.53，边际收益微乎其微，而这时候 KV 缓存早就可能把显存吃满、请求根本排不进这么大的批。
3. **用"看起来正常"当验收标准。** 这是本库作者自己踩过的坑：第一版 `analytic_cost` 把 embedding 的字节算进了分母，却没把 lm_head 的 FLOPs 算进分子，算出来的趋势是"ctx 越长强度越高"（从 0.43 一路爬到 0.50），单看数字表面上也说得通，直到写了退化情形检验——`_lab/minigpt.py:274-280` 那条"batch=1 时必须恒等于 0.5"的断言——才发现整个模型的口径从一开始就错了。教训写在 `_lab/minigpt.py:217-219` 的注释里，也记在 `_PLAN.md` §7 的踩坑清单第一条。
4. **以为 KV 缓存"只是个加速 trick，随便实现问题不大"。** `forward_cached` 里 `p0:p0+T` 这几处写入/读取下标（`_lab/minigpt.py:159-165`）只要算错一位，模型依然会吐出语法通顺、"看着正常"的文本，只是内容跟朴素路径已经不一致——这种 bug 人眼几乎不可能发现，只能靠 `_lab/minigpt.py:249-266` 那三条逐位/逐 token 比对的断言抓出来，这也是 `_PLAN.md` §2 里说"推理引擎的 bug 绝大多数是静默的"的具体例子。
5. **只在单条请求的视角下想问题，漏掉批的异构性。** 把"推理"简单等同于"反复调用 `generate()`"，会忽视真实引擎里 decode 一步处理的是**当前这一批**里所有在跑请求各自的下一个 token，而不是让某条请求关起门来自己生成到底——`## 4.2` 里调度器的 `waiting`/`running` 两条队列就是为了处理这层复杂度存在的。
