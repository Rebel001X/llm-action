# 00 · 总览与学习路径（亲笔）

> 这一篇我自己写。它要说清三件事：**这个库和别的库不一样在哪、按什么顺序读、以及"用什么语言"这个问题的答案。**

---

## 1. 这个库要回答什么

**如果你要自己写一个推理引擎，需要懂哪些原理、按什么顺序搭、用什么语言写。**

隔壁 `VLLM-SGlang-研究-推进/` 那个库是**读代码**的——把 12 个真实引擎逐行解剖，
每条断言都钉在别人源码的一行上。这个库是**写代码**的：从一个空文件开始，
一步步搭出一个能连续服务的引擎，并在每一步问"为什么必须有这个部件"。

两个库的红线因此不同：

| | 研究库 | 本库 |
|---|---|---|
| 红线 | 每条断言回到**别人源码**的一行 | 每个原理有**本库自己能跑的代码** |
| 验证 | `_verify.py` 打开引擎源码核行号 | 同左，外加 `_lab/tests` **跑一遍证明优化不改变输出** |
| 性能数字 | 一个都不产（无 GPU） | 本库玩具引擎在 CPU 上的实测**可以有**；外推到真引擎**绝对不行** |

一句话：**别的库教你看懂引擎，这个库教你造一个。**

## 2. 先回答那个最常被问的问题：用什么语言

你大概率是带着这个问题来的，所以我把答案放最前面。

**先看事实，不看意见。** 下面是 12 个主流开源引擎的真实语言构成
（数据由隔壁研究库的 `_lab/repo_stats.py` 从各自源码算出，快照 2026-08-22 前后）：

| 引擎 | 总行 | 主语言 | 占比 | 值得注意的 |
|---|---:|---|---:|---|
| TensorRT-LLM | 2,452,198 | Python | 56% | C/C++ 合计 23% |
| SGLang | 2,317,985 | Python | 80% | Rust 6%、CUDA 4% |
| Dynamo | 2,220,830 | JSON | 34% | **Rust 27%**、Go 6% |
| vLLM | 1,914,984 | Python | 75% | Rust 5%、CUDA 3% |
| llama.cpp | 992,377 | **C++** | 44% | 头文件 22%、C 7% |
| Mooncake | 548,895 | **C++** | 54% | 它不是引擎，是 KV 传输层 |
| KTransformers | 403,076 | Python | 44% | C/C++ 30% |
| LMDeploy | 339,214 | Python | 63% | CUDA 9% |
| TGI | 189,926 | Python | 57% | **Rust 12%**（router） |
| LightLLM | 148,574 | Python | 86% | **0 个 CUDA 文件**、129 个 Triton 文件 |
| MLC-LLM | 100,240 | Python | 70% | C++ 16%（TVM 运行时） |
| Tokasaurus | 13,219 | Python | 95% | 纯 Python 也能跑起来 |

**三条硬事实**：

1. **12 个里 10 个主语言是 Python。** 只有 llama.cpp 与 Mooncake 是 C++，
   而 Mooncake 根本不是推理引擎（是 KV 传输与存储）。
2. **没有一个引擎是「用 Rust 写的」。** Rust 只出现在 4 个项目里，
   而且位置高度一致：**都在"请求进来到交给 GPU 之前"那一段** ——
   Dynamo 的集群路由、TGI 的 router、SGLang 与 vLLM 的可选前端。
   **从不出现在模型执行层。**
3. **纯 Python + Triton 是可行的**：LightLLM 全仓 0 个 CUDA 文件。

**所以正确的问题不是"用什么语言"，是"哪一层用什么语言"。**

| 层 | 12 家的实际选择 | 为什么 |
|---|---|---|
| HTTP / 协议 | 多数 Python（FastAPI）；TGI 与 Dynamo 用 Rust | 这一层是 CPU 密集 + 高并发，Rust 有优势 |
| 调度 / 编排 | 多数 Python | 迭代快最重要；热路径本来就在 GPU 上 |
| 模型执行 | 几乎全是 Python 调 PyTorch；llama.cpp 是 C++ | 模型生态在 Python，重写等于自绝于生态 |
| 算子 | CUDA / Triton；或者**根本不写**，外包给 FlashAttention/FlashInfer | 自研 kernel 的边际收益递减得很快 |

**给从 0 开始的人的建议**（`[[06-选型决策表]]` 有完整版）：

- **学原理** → Python（甚至 numpy）。本库的 `_lab/` 就是这么做的。
- **端侧 / 无 GPU 部署** → C++（llama.cpp 那条路），代价是新模型支持要手写。
- **集群服务** → Python 主体 + 必要时把 router 换成 Rust。
- **想给上游提 PR** → 学 Python，因为 10 家的主体都是 Python。

**最不推荐的做法**：因为"Rust 更快"就用 Rust 从头重写一个引擎。
12 家没有一家这么做，不是因为他们没想到。详见 [[04-Rust在推理栈里到底占了什么位置]]。

## 3. 一个能跑的最小引擎：`_lab/`

这个库的每个原理都配一段能跑的代码。全部纯 numpy、CPU、不装 torch——
目的是让每一步矩阵乘都露在外面，而不是藏在框架的一个算子里。

| 文件 | 是什么 |
|---|---|
| `_lab/minigpt.py` | 最小 Transformer：朴素前向 / KV 缓存前向 / 生成 / **算术强度解析模型** |
| `_lab/paged.py` | 分页 KV：块表、分配器、引用计数、碎片统计 |
| `_lab/engine.py` | 调度器 + 连续批处理 + 前缀缓存，拼成能连续服务的引擎 |
| `_lab/sampling.py` | 采样（temperature/top-k/top-p/重复惩罚）、停止条件、**流式输出的状态机** |
| `_lab/serve.py` | HTTP 服务：两道队列把并发的 HTTP 与单线程的引擎解耦；SSE、背压、断连回收 |
| `_lab/flashattn.py` | 在线 softmax + 分块注意力 + decode 的 split-KV |
| `_lab/parallel.py` | TP / PP / EP —— **等价性与代价都能在单机上验证** |
| `_lab/spec_decode.py` | 投机解码 + 20 万次采样的分布检验 |
| `_lab/structured.py` | 语法约束解码：状态×词表掩码索引 + jump-forward |
| `_lab/quantize.py` | 三档量化的误差、实际位宽、量权重还是量 KV 的访存账 |
| `_lab/tests/` | pytest 共 119 项，判据分四套，见下 |

跑起来（纯 numpy + 标准库，不装 torch、不装 web 框架）：

```bash
cd _lab
python minigpt.py  --selftest && python minigpt.py   # 后者打印算术强度表
python paged.py    --selftest && python paged.py     # 后者打印碎片随块大小的变化
python engine.py   --selftest && python engine.py    # 后者对比开/关前缀缓存
python sampling.py --selftest && python sampling.py  # 后者演示采样对比 + 流式扣留
python serve.py    --selftest                        # 起服务打自己，8 项断言
python serve.py                                      # 前台起服务，再用 curl 打它

python flashattn.py --selftest && python flashattn.py    # 分块等价 + 峰值中间量
python parallel.py  --selftest && python parallel.py     # TP通信量 / PP气泡 / EP负载
python spec_decode.py --selftest && python spec_decode.py # 分布检验 + γ 最优值
python structured.py --selftest && python structured.py   # 掩码索引 + jump-forward
python quantize.py  --selftest && python quantize.py     # 量化误差 + 访存账

python -m pytest tests -q                            # 119 passed
```

**测试哲学要单独说一句，而且它分四套 —— 这个区分本身就是内容。**

| 判据 | 用在哪 | 长什么样 | 抓不到什么 |
|---|---|---|---|
| **输出恒等** | KV 缓存 / 分页 / 批处理 / 前缀缓存 / FlashAttention / TP | 算两遍，逐位比 | **两侧同时犯的错** |
| **分布恒等** | 投机解码 | 大量采样后比全变差 | 低于采样噪声的偏差 |
| **约束恒成立** | 结构化输出 | 每次输出都必须被解析器接受 | 分布层面的偏移（它**故意**改分布） |
| **误差有界且单调** | 量化 | 误差落在解析预测附近 | 特定输入上的灾难性失效 |

第一套的道理是：那几样出错时**几乎不会崩，只会静默给出不一样的结果**，
所以唯一有效的护栏就是*算两遍，逐位比*。

**但它有一个结构性盲区，而且这个盲区是本库最值得看的一处**：
把 `minigpt.py` 里 4 处残差 `x = x + ...` 一起写成 `x = ...`，
**两条前向路径同时被改到**，于是 25 条差分断言**全绿**，
而模型输出的 argmax 已经从 36 变成了 44。
解药是 `tests/test_invariants.py`：**不比"实现和实现"，比"实现和它必须满足的性质"**
—— 把 `wo`/`w2` 置零后每层必须退化成恒等，那个 bug 在这里最大差从 2.4e-07 跳到 3.26。
完整复现与另外五次打脸见 [[01-正确性怎么保证]]。

## 4. 已经算出来的两条硬结论

### 4.1 batch=1 时，算术强度恒为 0.5，与上下文长度无关

跑 `python _lab/minigpt.py` 得到（fp32，解析计算不是实测）：

```
     ctx     bs=1     bs=4    bs=16    bs=64   bs=256    KV占访存(bs=64)
      16     0.50     1.89     6.21    14.50    21.74           54.7%
      64     0.50     1.65     3.85     5.80     6.64           82.8%
     256     0.50     1.17     1.76     2.02     2.10           95.1%
    1024     0.50     0.75     0.86     0.90     0.90           98.7%
    4096     0.50     0.57     0.59     0.60     0.60           99.7%
   16384     0.50     0.52     0.52     0.53     0.53           99.9%
```

三条读法，**整个库后面的内容都从这里长出来**：

- **第一列恒为 0.50。** fp32 下每个权重参数、每个 KV 元素都是「1 次乘加(2 FLOP)、读 4 字节」，
  所以强度必然是 `2/4 = 0.5`。**单条请求的解码一开始就在访存瓶颈的底，没有更低可去。**
  （换 fp16 这个常数变成 1.0——这也是低精度真正省下的东西。）
- **只有增大 batch 能抬高它。** 权重读一遍被整批共用，KV 不能。
  **这就是连续批处理存在的全部理由。**
- **ctx 越长，batch 抬得越少。** ctx=16 时 bs=256 能抬到 21.74；
  ctx=16384 时只能抬到 0.53，因为 KV 占了 99.9% 的访存。
  **"长上下文杀吞吐"的机制就在这一格里。**

> **这个模型我第一版算错过**：把 embedding 的字节算进了分母，却没把 lm_head 的 FLOPs 算进分子，
> 于是强度算出来 0.43 → 0.50 一路上升，看着像"上下文越长越受限"，
> 还编出了一套解释。正确做法是把"矩阵乘用到的权重"和"只被 gather 的 embedding"分开算。
> **教训：任何 roofline 类解析模型，先验证退化情形等于理论值，再看趋势。**

### 4.2 分页把内碎片压到不足一个块

跑 `python _lab/paged.py`：序列长 100 时，块大小 1/4/16/64/256 分别浪费 0%/0%/6%/22%/61%。
**块越大 → 块表越短、kernel 越好写，但内碎片越大。** 这就是 `block_size` 这个旋钮的全部取舍。

## 6. 这个库不做什么

写在前面，免得你抱错期待：

- **不教你写 CUDA kernel。** 那是 `cuda实战，ai实战/` 和 `attention-optimization/` 的活。
  本库把算子当黑盒，讲的是算子**之上**那一层。
- **不产出真实引擎的性能数字。** 本机没有 GPU。
  `_lab` 的耗时是这个 numpy 玩具自己的，**任何往 vLLM/SGLang 身上的外推都是编造**。
- **不追新。** 模型架构和引擎特性变得很快，本库只讲**变化慢的那部分**：
  访存瓶颈、KV 的数学结构、分页、批处理。这些五年内不会变。
- **不替你选。** `[[06-选型决策表]]` 给的是判据，不是答案 ——
  因为答案取决于你的目标，而那个只有你知道。

## 7. 怎么验证这个库没骗你

```bash
python _verify.py          # 全库体检：本库自引用 + 引擎引用 + 双链 + 占位符
cd _lab && python -m pytest tests -q
```

`_verify.py` 会做两件事：
1. 正文里每一个 `` `_lab/minigpt.py:197` `` 这样的引用，**它会真的打开那个文件数到那一行**；
2. 每一个**带引擎前缀**的引用（形如下面这样），
   对着隔壁 `../VLLM-SGlang-研究-推进/_src/` 的真实 clone 核 ——
   那份 clone 不在时会**明说跳过了多少条**，不伪装通过：

   ```
   `vllm:vllm/v1/core/sched/scheduler.py:686`
   ```

**随便挑一条引用打开看。对不上就是本库的 bug，不是你的理解问题。**
