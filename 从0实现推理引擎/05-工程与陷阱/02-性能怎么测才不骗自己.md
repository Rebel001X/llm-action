# 02 · 性能怎么测才不骗自己

> 接着 [[01-正确性怎么保证]] 往下走：正确性问完之后，第二个要问的问题是「这个数字能信吗」——**同一套怀疑精神，换了一个对象**。正确性的敌人是"悄悄改变输出的 bug"；性能的敌人是"悄悄改变含义的数字"，而且后者往往连 bug 都算不上，只是**测的东西和想知道的东西不是一回事**。
>
> **一句话**：测的东西和想知道的东西，常常不是一回事。
> **前置**：`[[07-把它变成一个HTTP服务]]`（本篇要反复用到的 `Job.ttft`/`Job.tpot`/`_metrics()` 都在那一篇里第一次出现）、`[[02-自回归解码为什么是访存瓶颈]]`（本篇讲"工作点"要用到的算术强度表）

---

## 0. 这一篇要解决什么问题

先把这一篇的特殊处境摆在最前面，因为它决定了整篇文章能讲什么、不能讲什么：

> **这台机器没有 GPU。本库从头到尾产不出一个真实推理引擎的性能数字。**

如果这是一篇讲"怎么把 vLLM 的吞吐调上去"的文章，写不下去——没有 GPU，没有真实模型，
甚至连一次可信的真实 benchmark 都跑不了。但这个限制反而逼出了一个更值钱的问题：

**如果我现在拿到一个性能数字——不管是别人发的 benchmark，还是自己压测跑出来的——我凭什么信它？**

这个问题不需要 GPU 就能回答，而且诚实地说，它比"怎么把数字跑高"更重要。
理由很朴素：**推理引擎的性能数字有一半是自己骗自己骗出来的**，不是因为谁在造假，
而是因为下面这几件事几乎每个人第一次做压测都会踩：

1. 把两个受完全不同因素支配的量（排队+prefill、decode 每步）平均成一个"延迟"；
2. 拿一个能刷得很好看的吞吐口径（比如算上 prefill 的总 token/s）当成用户体感；
3. 只看均值不看分位数，而分位数自己在小样本下的方差可以大到把趋势直接吃掉；
4. 报一个吞吐数字却不说模型、精度、上下文长度、batch、硬件——**少任何一项，这个数字就无法被复现，也无法被反驳**；
5. 把客户端瓶颈、没有预热、429/503 处理不当，全都记成了"引擎慢""引擎不稳"。

这一篇要做的不是教你怎么把 `_lab/serve.py` 的吞吐调高——**它是纯 numpy 玩具，调不调都没有工程意义**——
而是拿它当一个**足够小、足够能看清全部细节**的样本，把"测量方法论"这件事过一遍：
指标要怎么分层、平均数什么时候会骗人、一个数字要绑定哪些前提才叫"可比"、
遇到解析模型和实测不一致时该信哪个。这些结论对真实引擎同样成立，
而且**恰恰是因为看不到 GPU 上的数字，才更要把"怎么判断数字可信"这件事想透**——
不然拿到真实硬件的第一天，照样会被自己的第一版压测脚本骗一次。

## 1. 先看现象：同一个引擎，两个方向的延迟

用 `_lab/serve.py` 起一个真实的（虽然是玩具的）HTTP 服务，固定 prompt、固定输出长度、
固定并发请求数，只改一个旋钮——`max_running`，即引擎允许同时在跑的请求数上限——
看 TTFT（Time To First Token）和 TPOT（Time Per Output Token）怎么动。

跑法（脚本不在 `_lab/` 里，是这一篇临时写的实验代码，串起 `serve.py` 的接口）：

```python
import sys, json, threading, time, urllib.request
sys.path.insert(0, "<repo>/_lab")
import serve as S

# 固定：prompt、max_tokens=24、并发请求数=8
# 只改：max_running（引擎里同时能跑的请求数上限）
httpd, loop = S.serve("127.0.0.1", 0, max_queue=64, n_blocks=2048,
                      block_size=16, max_running=max_running)
# ... 8 个线程同时 POST /v1/completions，读回响应里的 timings.ttft_ms / tpot_ms
```

这台机器（Windows、CPU、numpy 玩具引擎，**下同，不再重复标注**）上跑出来的真实数字：

```
max_running   TTFT 均值(ms)   TTFT 范围(ms)    TPOT 均值(ms)   TPOT 范围(ms)
     1            12.10        0.63 – 29.40        0.21         0.19 – 0.23
     2            17.70        1.71 – 32.87        0.48         0.44 – 0.58
     4            11.41        1.83 – 21.70        0.90         0.77 – 0.98
     8             2.53        1.75 –  3.64         1.49         1.45 – 1.54
```

（8 条并发请求，`max_queue=64` 保证没有一条被 503 拒绝，`n_completed` 每行都是 8。）

两端（`max_running=1` 和 `max_running=8`）的对比非常干净：**TTFT 从 12.10ms 降到 2.53ms（↓79%），
TPOT 从 0.21ms 涨到 1.49ms（↑607%）——同一个引擎，同一段代码，两个指标反着走。**
TPOT 这一列尤其规整：0.21 → 0.48 → 0.90 → 1.49，四档严格递增，没有一次例外。

但**中间两档的 TTFT 不单调**（12.10 → 17.70 → 11.41，先涨后跌），先别急着找原因——
这恰好是 `## 2.3` 要讲的东西的活样本：**8 个样本的分位数/均值本来就没那么稳**，
过早从这种波动里读出"故事"，正是这一篇要拆穿的自欺之一。

机制留到 `## 3.6` 结合代码讲清楚，这里先给结论：**这个玩具引擎的"连续批处理"是调度层面的
（多条请求交替被送进单线程的 `step()` 循环），不是内核层面的（把多条请求的输入拼成一次向量化矩阵乘）**。
`max_running` 越大，请求越容易被立刻收进 `running`（TTFT 里的排队部分变短），
但每一步 `step()` 都要把 `running` 里所有请求依次算一遍单请求前向，
你的请求要等的"轮数"变多了（TPOT 变长）。方向是反的，但**原因不是`## 3.1` 那张算术强度表里
"batch 摊薄权重读取"那件事**——真要摊薄权重读取，得把这些请求的矩阵乘拼成一次调用，
这个玩具引擎没有做到那一层，这是它和真实引擎之间**很值得点名**的一处差距。

> **不可外推**：以上数字只是这个 numpy 玩具在这台 CPU 上、这一次运行的结果。
> 不能拿它去说"某某引擎 batch 越大 TPOT 一定越差"——那要看内核是不是真的做了向量化批处理，
> 这个玩具没有做，真实引擎（vLLM/SGLang）做了，机制完全不同。

## 2. 原理

### 2.1 指标分层：合成一个"延迟"等于什么都没测

一次请求的生命周期天然分两段，而且**受完全不同的因素支配**：

- **TTFT**：从请求到达到第一个 token 吐出来，包含**排队时间**（等前面的请求腾位置）和 **prefill 计算时间**（整段 prompt 走一遍前向）。归**调度策略**和**负载水位**管。
- **TPOT**：从第一个 token 到最后一个 token，平均每个 token 的间隔。归 **decode 这一步的访存带宽**管——`[[02-自回归解码为什么是访存瓶颈]]` 已经证明单条请求的 decode 一开始就在访存瓶颈的底（算术强度恒为 0.5，`_PLAN.md` §3.1）。

这条区分不是这一篇发明的，`_lab/serve.py:99-102`（`Job.ttft`）和 `_lab/serve.py:104-115`（`Job.tpot`）
两个属性的 docstring 直接写了它：TTFT "排队 + prefill"，TPOT 归"decode 的访存带宽"管。
**把两者平均成一个"延迟"，等于把两台机器的体温加起来除以二**——
`## 1` 那张表已经演示了后果：同一个引擎在同一次实验里，TTFT 和 TPOT 一个降 79%、一个涨 607%，
如果只报一个合成的"平均延迟"，这两件事会互相抵消成一条看起来毫无变化的曲线。

**排队时间还要再往下拆一层。** 一个引擎"变慢了"，很可能只是**队列变长了**——
和引擎本身的计算速度毫无关系。TTFT 把排队和 prefill 捆在一起报，这是可以接受的
（用户体感上二者确实分不开），但**排查问题时必须能分开看**，否则会把调度问题误判成引擎问题
（反过来也一样）。这一层区分本库的玩具没有做全——`Job` 只记了 `t_arrive` 和 `t_first`
两个时间戳（`_lab/serve.py:93-94`），TTFT 是两者之差，排队和 prefill 各占多少无法从这一个数字里拆出来。
`## 4` 会看到，vLLM 直接把排队时间做成了一个独立的 Prometheus 指标，
而不是任由它隐藏在 TTFT 里——这是本库这个教学简化版和真实引擎之间一处诚实的差距。

不过"队列有多深"这件事本身，`_lab/serve.py` 是有独立观测口的：`EngineLoop.depth()`
（`_lab/serve.py:229-230`）把还没被引擎收下的 `in_q`、已经在等待队列里的、以及正在跑的三部分加总，
`/metrics` 把它和 `running`/`waiting` 两个子项一起原样透出（`_lab/serve.py:450-452`）。
**这是一个和 TTFT/TPOT 完全独立的信号**：队列深度涨了但 TPOT 没涨，说明是负载涌进来了、
调度还没吃力；队列深度没涨但 TPOT 涨了，说明是 decode 本身变慢了——
两个方向的诊断结论截然不同，而能不能分清全靠这两组指标有没有分开报。

### 2.2 吞吐要分两种：输出 token/s 与总 token/s（含 prefill）

"这个引擎吞吐 X token/s" 这句话本身就有歧义，因为 token 有两个来源：
prefill 阶段一次性吃进去的 prompt token，和 decode 阶段一个一个吐出来的输出 token。

- **总 token/s**（(prompt_tokens + output_tokens) / wall_time）：prompt 越长，这个数字天然越大——
  哪怕 decode 一个字没变快。一段 4000 字的长 prompt 配 20 个字的短输出，
  总 token/s 可以刷得非常好看，**而用户在屏幕上一个字都没多拿到**。
- **输出 token/s**（output_tokens / wall_time，或者 `1 / TPOT`）：这才是用户实际感知的"吐字速度"。

`_lab/serve.py` 把这两类 token 分开计数，没有含糊地揉成一个总数：
`prefill_tokens` 在准入阶段按 `len(todo)` 累加（`_lab/serve.py:166`），
`decode_steps` 在 decode 循环里逐步累加（`_lab/serve.py:182`），
两个计数器一起在 `_lab/engine.py:122` 初始化。`/metrics` 把它们原样透出（`_lab/serve.py:456`），
调用方要算哪种吞吐，自己用对应的分子去除以 wall time，**而不是先把两个数加在一起**。

### 2.3 平均数会骗人：必须报分位数，而分位数自己也有方差

延迟分布是长尾的——大多数请求快，少数请求因为排队、GC、或者恰好撞上一次大 prefill 而很慢。
均值会被这条尾巴稀释，看不出"最差的那 10% 用户体验有多差"。
`_lab/serve.py` 的 `_metrics()`（`_lab/serve.py:440-458`）就是按这个原则写的：
不报均值，报 p50 和 p90（`_lab/serve.py:445-446` 的 `p(xs, q)` 辅助函数，
对排序后的数组按分位取值），TTFT 和 TPOT 各自独立报一份分位数。

但**分位数不是免费的午餐**：样本数少的时候，分位数本身的抖动可能比它想反映的趋势还大。
本库自己在这上面栽过一次，写进正文免得下次又犯——

> ⚠️ **隔壁研究库的教训**：`../VLLM-SGlang-研究-推进/_lab/sched_sim.py` 做调度公平性的差分模拟时，
> 第一版只跑了一个随机种子，得到 `aged_T4`/`T2`/`T1` 三档的"公平差"是 136～139，
> 而 `aged_T8` 是 12——一个看起来很整齐的"非单调"结果，差点就当成真实发现写进结论。
> 换成 8 个种子后，这几档的标准差高达 41～51，那个"非单调"完全落在噪声区间里；
> 再加到 24 个种子，趋势才真正稳定下来。**58 个样本上的单点 p90，标准差能到均值的一半。**
>
> **教训很具体，可以直接套用**：任何一次报出来的分位数，先问它自己的抖动有多大
> （多跑几个种子/几次重复，看这个分位数本身的标准差），再谈"是不是有趋势"。
> `## 1` 那张表里中间两档 TTFT 不单调，同一个道理——8 个样本的分位数，本来就不该被过度解读。

### 2.4 工作点：不写清楚的数字等于没有

一个吞吐或延迟数字要能被别人复现、被别人反驳，必须同时带着这些信息：
**模型 / 精度 / 上下文长度 / batch / 输入输出长度分布 / 硬件 / 有没有开前缀缓存 / 有没有开 CUDA Graph**。
少任何一项，这个数字就只是一个孤立的浮点数，没法和任何别的数字比较。

`_PLAN.md` §3.1 那张算术强度表（`analytic_cost()` 的解析结果，见 `## 3.5`）已经算出了
"少写一项能差多少"的具体量级：同一个玩具配置，fp32、batch=1 恒为 0.50，
但把 batch 抬到 64 时，ctx=16 能把强度抬到 21.74（涨 43 倍），ctx=16384 只能抬到 0.53（几乎没涨）。
**只写"batch=64 时强度提升明显"而不写 ctx 是多少，这句话在两种上下文长度下分别对应
43 倍和不到 1.1 倍的真实收益——工作点缺一项，数字的意义能差出一个数量级还不止。**
这不是这个玩具独有的现象：ctx 越长、KV 占访存的比例越高（bs=64 时从 54.7% 一路涨到 99.9%），
batch 能摊薄的只有权重那一部分，KV 摊不薄，是任何用 KV 缓存做自回归解码的引擎都要面对的结构性事实。

### 2.5 什么时候该信解析模型，什么时候该信实测

解析模型（roofline 一类）告诉你**上限在哪**；实测告诉你**离上限有多远**。
两者从来不是二选一，但**两者不一致时，先怀疑测法，不要先怀疑模型**——
如果实测吞吐超过了访存带宽允许的理论上限，那基本可以断定是测错了
（口径不对、算错了模型规模、或者悄悄换了精度），而不是"这个引擎真的突破了物理限制"。

反过来，解析模型自己也可能算错，而且犯的往往不是显眼的错——
`analytic_cost()`（`_lab/minigpt.py:197-238`）第一版就在这上面栽过：
把 embedding 的字节算进了分母，却没把 lm_head 的 FLOPs 算进分子，
算出来的强度是 0.43 一路涨到 0.50，看着像一条自洽的"ctx 越长越受限"的趋势，
连解释都编好了。抓住它的办法不是通读代码，是**先问退化情形该等于几**：
fp32、batch=1 时，权重侧和 KV 侧都是"每元素 1 次乘加（2 FLOP）、读 4 字节"，
强度必须恰好是 `2/dtype_bytes`，与上下文长度**完全无关**——一旦这么问，
那条"上升的趋势"当场站不住。这条规矩现在钉成了断言（`## 3.5` 给出行号），
**任何 roofline 类解析模型，都应该先验证退化情形等于理论值，再看它给出的趋势。**

## 3. 自己动手：`_lab/` 里对应的实现

### 3.1 指标怎么被量出来的：`Job.ttft` / `Job.tpot`

`Job`（`_lab/serve.py:83-97`）是 HTTP 线程和引擎线程之间唯一的通信载体，
只记了三个时间戳：`t_arrive`（构造时打的戳，`_lab/serve.py:93`）、`t_first`（第一个 token 出现的时刻）、
`t_end`（最后一个 token 出现的时刻）。两个属性从这三个戳里派生：

```python
@property
def ttft(self) -> float:
    return self.t_first - self.t_arrive if self.t_first > 0 else -1.0

@property
def tpot(self) -> float:
    if self.n_out <= 1 or self.t_first <= 0:
        return -1.0
    return (self.t_end - self.t_first) / (self.n_out - 1)
```

（原文见 `_lab/serve.py:99-102` 与 `_lab/serve.py:104-115`，后者除法分母是 `n_out - 1`
——只有一个输出 token 时没有"两个 token 之间的间隔"可言，返回哨兵值 `-1.0` 而不是抛异常或除零。）

### 3.2 分位数：`_metrics()` 里的 p50/p90

```python
def _metrics(loop: EngineLoop) -> dict:
    done = list(loop.done)
    ttfts = sorted(j.ttft for j in done if j.ttft > 0)
    tpots = sorted(j.tpot for j in done if j.tpot > 0)

    def p(xs, q):
        return round(xs[min(len(xs) - 1, int(len(xs) * q))] * 1000, 2) if xs else -1

    return {..., "ttft_ms": {"p50": p(ttfts, 0.5), "p90": p(ttfts, 0.9)},
                 "tpot_ms": {"p50": p(tpots, 0.5), "p90": p(tpots, 0.9)}, ...}
```

（`_lab/serve.py:440-458`，取分位数的辅助函数在 `_lab/serve.py:445-446`。）
**注意它排除了 `ttft <= 0` 和 `tpot <= 0` 的样本**——那是 `## 3.1` 里的哨兵值（还没出第一个 token、
或只出了一个 token），把哨兵值混进分位数计算会直接污染结果，这是写分位数统计时很容易漏掉的一步。
`/metrics` 返回值里还焊了一句免责声明（`_lab/serve.py:457`）：
`"note": "numpy toy on CPU; NOT comparable to any real engine"`——
这句话被焊进了返回值本身，而不只是写在文档里，任何拿这份 JSON 做汇报的人都会在原始数据里撞见它。

### 3.3 吞吐拆分：`prefill_tokens` 与 `decode_steps` 两个计数器

`_lab/engine.py:122` 在 `Engine.__init__` 里把统计字典初始化成
`{"prefill_tokens": 0, "decode_steps": 0, "cached_tokens": 0}`——三个计数器从一开始就是分开的。
`ServingEngine._admit()` 在准入一条请求、算完它的 prefill 之后累加 `prefill_tokens`
（`_lab/serve.py:166`：`self.stats["prefill_tokens"] += len(todo)`）；
`ServingEngine.step()` 每推进一步 decode 就累加 `decode_steps`
（`_lab/serve.py:182`：`self.stats["decode_steps"] += 1`）。
`## 2.2` 讲的"总 token/s 会被长 prompt 刷高"，在代码层面对应的就是：
**如果拿 `(prefill_tokens + decode_steps) / wall_time` 当"引擎吞吐"去汇报，
prompt 越长这个数字天然越大，而 `decode_steps`（真正对应用户拿到的输出）可能纹丝不动。**

### 3.4 背压与重试：`post()` 助手 + `max_queue=4` 的并发测试

`serve.py --selftest` 会真的拉起一个 `ThreadingHTTPServer`，用 6 条并发请求打
`max_queue=4` 的服务（`_lab/serve.py:483-484`）。这里有一段专门写进代码注释的踩坑记录：

> 这一段本来没写重试，于是并发那一项有约四成概率挂掉——6 条请求打 `max_queue=4` 的服务，
> 被拒的那两条在工作线程里抛出 `HTTPError`，看起来像"服务坏了"，其实是背压在正常工作。
> （`_lab/serve.py:491-499`，`post()` 辅助函数的 docstring 原文）

现在的 `post()`（`_lab/serve.py:491-513`）内置了退避重试：收到 503 就按
`Retry-After` 头睡一下再重试，最多 60 次，只有真的重试 60 次还失败才当作故障抛出
（`_lab/serve.py:504-513`）。断言里专门留了一句话钉住这条认知（`_lab/serve.py:555-557`）：
**"过程中被背压拒绝并重试了 N 次——503 是正常工作，不是故障"**，
`n_completed == 6` 且块全部归还（`_lab/serve.py:553-554`）才是真正的通过条件，
503 的次数本身不参与判定对错。`## 6.4` 会把这条踩坑单独拿出来当反面教材讲。

### 3.5 解析模型的退化情形检验：`analytic_cost()` + 断言

`analytic_cost()`（`_lab/minigpt.py:197-238`）算的是一步 decode 的解析成本
（FLOPs vs Bytes），docstring 里直接写了 `## 2.5` 讲的那次自我纠错。
钉住这条"先验证退化情形"规矩的断言现在在 `_lab/tests/test_invariants.py:145-159`：

```python
def test_analytic_intensity_hits_the_theoretical_floor_exactly(tiny):
    cfg, _ = tiny
    for db in (1, 2, 4):
        for ctx in (16, 1024, 65536):
            ai = M.analytic_cost(cfg, ctx, batch=1,
                                 dtype_bytes=db)["arithmetic_intensity"]
            assert abs(ai - 2 / db) < 4e-3 * (2 / db), f"dtype={db} ctx={ctx} -> {ai}"
```

三种 dtype 字节数（fp32=4、fp16=2、int8=1）×三种上下文长度全部要落在 `2/dtype_bytes` 附近，
**且和 ctx 无关**——这正是"退化情形等于理论值"这条规矩落到代码里的样子，
比只在一个 ctx 上验一次要硬得多：只验一个点，把公式里 ctx 那一项系数写错了也可能蒙混过关。

### 3.6 我自己实验用到的调度机制：为什么 `max_running` 会让 TPOT 变长

`## 1` 那组数字的机制在 `Engine.step()` 里能看全（`ServingEngine.step()` 覆写的是同一段逻辑，
`_lab/serve.py:175-191`，二者结构一致，下面用基类版本 `_lab/engine.py:190-197`）：

```python
def step(self) -> None:
    self._admit()
    for req in list(self.running):        # <- 单线程 for 循环，逐条请求单独前向
        if req.finished:
            continue
        logits = self._forward(req, [req.out[-1]])
        req.out.append(int(logits.argmax()))
        self.stats["decode_steps"] += 1
```

**`for req in list(self.running)` 是逐条请求各调一次 `_forward`**，不是把 `running` 里所有请求的
输入拼成一次矩阵乘。`max_running` 越大，`running` 里同时挤的请求越多，
每一步 `step()` 要顺序算完的前向次数越多，**你的请求从"轮到你"到下一次"轮到你"之间的间隔就越长**——
这就是 TPOT 随 `max_running` 单调上升的直接原因。同时，`max_running` 越大，
新请求越不容易被压在等待队列里（`_admit()` 的准入条件是
`len(self.running) < self.max_running`，`_lab/engine.py:153`），
排队时间变短，TTFT 跟着降——两条曲线方向相反，但**分别由准入条件和 for 循环两处不同的代码决定**，
不是同一个机制的两面。真实引擎用向量化批处理把 `for req in ...` 这层循环换成了一次矩阵乘，
`max_running`（等价于 batch size）变大时靠的是 `## 2.4` 里那张算术强度表的道理去摊薄权重读取，
和这里"排队变短、循环变长"的道理并不是一回事——**这正是这个玩具没有实现、也不该被拿来外推的那一层**。

### 4.1 一个吞吐数字要报哪些参数：vLLM 自己的参数清单就是证据

vLLM 的服务压测入口现在是 `vllm bench serve`，实现在 `vllm/benchmarks/serve.py` 里
（旧的 `benchmarks/benchmark_serving.py` 已经变成一个提示"改用新命令"的空壳）。
`add_cli_args()` 里列的参数，本身就是 `## 2.4` 那条"工作点必须写清楚"的最好证据——
随手挑几个（`vllm:vllm/benchmarks/serve.py:1548` 是函数入口）：

| 参数 | 对应 `## 2.4` 里的哪一项 | 出处 |

这句话本身就是在提醒使用者：**只报一个"吞吐"数字，不说是被并发上限卡住的还是被到达速率卡住的，

也值得留意：**预热不是自动发生的，是一个要显式打开的旋钮**，这条会在 `## 6.3` 里展开。

### 4.2 指标怎么分层：Prometheus 里三个独立的直方图

`## 2.1` 提到本库的玩具把排队时间和 prefill 时间捆在 TTFT 里报，没有再往下拆——
vLLM 拆得更细，直接在 Prometheus 层面开了三个独立的直方图（`vllm/v1/metrics/loggers.py`）：

- `vllm:time_to_first_token_seconds`（`vllm:vllm/v1/metrics/loggers.py:796-797`）
- `vllm:request_time_per_output_token_seconds`（`vllm:vllm/v1/metrics/loggers.py:859-861`）
- `vllm:request_queue_time_seconds`（`vllm:vllm/v1/metrics/loggers.py:922-923`）

**排队时间是单独的第三个指标，不是并进 TTFT 里就算了**——这正是 `## 2.1` 里那句
"一个引擎变慢了，很可能只是队列变长了"在真实系统里的落地方式：运维要判断"是调度堆了队列
还是 decode 本身变慢了"，看的是这两个直方图有没有同时抬头，而不是盯着一个合成的"延迟"猜。
这也是本库玩具和真实引擎之间一处诚实的差距（`## 2.1` 已提前说明）：
真实引擎值得学的地方之一就是**把可能相互抵消的量，从一开始就做成互不遮挡的独立指标**。

## 5. 设计决策与代价

### 5.1 报分位数（p50/p90），不只报均值

- **为什么这样**：延迟分布长尾，均值会被大多数快请求稀释，看不出"最差 10% 用户"的体验；`_metrics()`（`_lab/serve.py:440-458`）按这个原则实现。
- **不这样会怎样**：一个引擎可能均值很好看，p90 却涨了三倍——只报均值会完全漏掉这种"多数人没事，少数人被恶心到"的情况，而后者往往才是投诉的来源。
- **什么时候可以不这样**：样本量极小（个位数）或者场景本身不存在并发排队（单用户离线脚本、`## 2.1` 末尾提过的例外），这时分位数和均值几乎重合，报均值也不算错，但依然不如分位数细。

### 5.2 排队时间要能单独看，不能只藏在 TTFT 里

- **为什么这样**：排队归调度和负载水位管，prefill 归计算管，两者归因完全不同，`## 4.2` 里 vLLM 把它拆成独立指标就是这个理由。
- **不这样会怎样**：TTFT 涨了，但涨的是排队还是 prefill 分不清——去查 decode kernel 还是去查准入策略，方向完全相反，混在一起报会让排查从一开始就走错路。
- **什么时候可以不这样**：系统里几乎不存在排队（并发极低、`max_queue` 远大于实际负载），TTFT 里排队部分本来就接近零，这时不单独拆问题也不大，但拆出来永远是更细的粒度。

### 5.3 吞吐默认报输出 token/s，不用总 token/s（含 prefill）

- **为什么这样**：用户体感是"多久吐一个字"，不是"引擎一共处理了多少 token"；`## 3.3` 里 `prefill_tokens` 和 `decode_steps` 分开计数就是为了不让这两件事被迫合并。
- **不这样会怎样**：长 prompt 短输出的场景下，总 token/s 可以刷得很漂亮，而用户实际拿到的输出速度可能很差——`## 2.2` 已经算过这个后果。
- **什么时候可以不这样**：如果场景本身就是"处理长文档、几乎不生成新内容"（比如做 embedding、做摘要打分这类以 prefill 为主的任务），总 token/s 反而更贴近这个场景真正在意的东西——但这时候更该做的是给这个指标改个不会引起歧义的名字，而不是继续叫它"吞吐"。

### 5.4 一个吞吐/延迟数字必须绑定完整工作点

- **为什么这样**：`## 2.4` 用 `_PLAN.md` §3.1 那张表算过，同一个引擎、只是 ctx 从 16 变到 16384，batch 带来的收益能差四十几倍——少写 ctx 这一项，数字的意义就已经丢了。
- **不这样会怎样**：两个团队各自报"batch=64 时吞吐提升明显"，谁都没错，但两人说的可能是相差几十倍的两件事，直到对齐 ctx 长度才发现在互相误解。
- **什么时候可以不这样**：内部沟通、双方都清楚默认工作点是什么（比如团队里所有 benchmark 都固定用同一套配置跑），可以省去每次都重复报一遍——但这依赖一个隐含的共同上下文，一旦数字要拿给外部人看，这个前提就不再成立。

### 5.5 解析模型和实测打架时，先怀疑测法

- **为什么这样**：解析模型给的是物理上限，实测超过物理上限只有一种解释——测错了；`## 2.5` 已经说明这不是"模型和实测二选一"的问题。
- **不这样会怎样**：如果先怀疑模型、认定"实测数字才是真的"，很容易把一次口径错误（精度算错、模型规模算错）误当成"发现了一个反常现象"，然后花时间去解释一个不存在的东西。
- **什么时候可以不这样**：解析模型本身还没经过 `## 2.5` 说的退化情形校验时，模型自己的可信度也存疑——这时候矛盾出现了，两边都要查，不能默认实测有问题。这也是为什么 `## 3.5` 那条断言要先于任何"信不信实测"的判断存在。

### 5.6 任何分位数先估计自己的方差，再谈趋势

- **为什么这样**：`## 2.3` 讲的 `sched_sim.py` 教训——8 个种子把"非单调"的假发现从 σ 41～51 的噪声区打回原形，24 个种子才站住;`## 1` 里中间两档 TTFT 的抖动是同一件事在这一篇里的活样本。
- **不这样会怎样**：单次/小样本跑出来的分位数抖动，会被误读成"某个配置就是比另一个好"，据此做出的调优决策实际是在拟合噪声。
- **什么时候可以不这样**：如果分位数之间的差距远大于抖动范围（比如 `## 1` 表里 TPOT 那一列，四档严格递增且没有交叉），这时不需要额外多跑几轮去确认方向；但"差距够不够大"这件事本身还是要先看过至少几次重复才能判断，不能凭直觉认定。

## 6. 常见错误与踩坑

### 6.1 拿 prefill 的吞吐当引擎吞吐

**现象**：压测报告写着"吞吐 X token/s"，数字很亮眼，细看发现测的场景是长 prompt（几千 token）配几十个 token 的短输出。
**为什么错**：`## 2.2` 已经拆过，这类场景里总 token/s 的分子被 prefill 那部分撑大了，`decode_steps`（`_lab/serve.py:182`）真正对应用户体验的那部分可能根本没什么贡献。
**怎么测才对**：报告里明确区分 `输出 token/s` 和 `总 token/s（含 prefill）`，并注明这次测试的输入输出长度分布——`## 4.1` vLLM 的 `--input-len`/`--output-len` 就是把这个区分做成了强制参数。

### 6.2 测的时候客户端是瓶颈

**现象**：并发压测时吞吐怎么都上不去，看起来像是服务端到了极限。
**为什么错**：单线程 Python 客户端本身的请求构造、JSON 序列化、GIL 争抢，都可能先于服务端成为瓶颈——测出来的其实是客户端的天花板，不是引擎的。`## 1` 的实验脚本用的就是多线程 + `urllib`，如果换成单线程顺序发请求，测出来的 TTFT/TPOT 会明显更差，但那反映的是脚本，不是引擎。
**怎么测才对**：客户端要么用异步/多进程把自己的开销压到可忽略，要么先单独测一遍"客户端能达到的最大请求速率"（不经过服务端，比如打一个立即返回的假接口），确认客户端本身不是瓶颈之后再看服务端数字。

### 6.3 没有预热

**现象**：第一次调用的延迟明显比后面几次高一截，被当成"稳态性能"报了出去。
**为什么错**：第一次调用往往含编译、CUDA Graph 捕获、显存分配这类一次性开销——`[[05-GPU执行模型速成]]` 讲过 CUDA Graph 需要按形状提前捕获，第一次遇到某个形状必然要走一次没有捕获过的慢路径。把这次开销摊进"稳态延迟"里，报出来的数字既不代表冷启动、也不代表稳态，是两者含糊的混合物。
**怎么测才对**：显式跑几轮预热请求再开始计时——`## 4.1` 提到 vLLM 的 `--num-warmups` 默认是 `0`（`vllm:vllm/benchmarks/serve.py:1692-1697`），**预热是一个需要主动打开的选项，不会自动发生**，这一点本身就值得在报告里写清楚"这次测试有没有预热、预热了几轮"。

### 6.4 压测脚本不处理 429/503

**现象**：并发压测时一部分请求报错，被记成"引擎不稳定""错误率 X%"。
**为什么错**：**背压是服务端在正常工作，不是故障**——`_lab/serve.py --selftest` 自己就犯过这个错：6 条并发请求打 `max_queue=4` 的服务，被拒的两条抛出 `HTTPError`，看起来像服务坏了，其实是队列满了按设计返回 503（`## 3.4` 已给出原文和行号）。
**怎么测才对**：压测客户端要识别 429/503，做退避重试，只把"重试很多次依然失败"算作真故障——现在 `_lab/serve.py` 的 `post()`（`_lab/serve.py:491-513`）就是这么改的：按 `Retry-After` 睡一下再试，最多 60 次才认输。**背压不是服务端一家的事**：服务端负责及时说不，客户端负责听得懂。

### 6.5 只测稳态不测冷启动

**现象**：报告只给"跑了 10 分钟之后的平均延迟"，对第一次请求、扩容后新实例的表现只字不提。
**为什么错**：冷启动（`## 6.3` 那类一次性开销、缓存还没热身、`## 2.1` 的 `PrefixCache` 一类结构还没积累命中）在真实流量里不是可以忽略的边角情况——扩容、重启、滚动发布都会反复触发它，用户第一次请求踩到冷启动的概率不低。
**怎么测才对**：分别报"冷启动延迟"（服务刚起来时的前几个请求）和"稳态延迟"（预热、跑够久之后），两个数字都要有，不能只挑好看的那一个。

### 6.6 对比两个引擎时用了各自的默认配置

**现象**：报告写"A 引擎比 B 引擎快 X%"，细看两边跑的是各自开箱即用的默认参数。
**为什么错**：默认参数背后往往是完全不同的工作点——`## 2.4` 已经说明 ctx、batch 这类前提差一点，吞吐能差几十倍。**两边默认配置不同，测的是"默认值谁选得好"，不是"引擎谁快"**，这是两个不同的问题，报告如果没说清楚在比哪一个，读者会默认是后者。
**怎么测才对**：对比之前先把 `## 2.4` 那份工作点清单在两边对齐——同模型、同精度、同 ctx、同 batch、同硬件、前缀缓存/CUDA Graph 都统一开或统一关，对不齐的项目要么想办法对齐，要么在结论里明确写出"这个差异有多少来自配置而不是引擎本身"。
