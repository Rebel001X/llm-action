# 分页 KV 与块管理

> **一句话**：把"一条请求的 KV 必须物理连续"这条假设拆掉，像操作系统管虚拟内存一样管 KV。
> **前置**：`02-加上KV缓存.md`

## 0. 这一篇要解决什么问题

`[[03-KV缓存的第一性原理]]` 已经证明了两件事：K/V 可以被安全地缓存（因为它们是只依赖 `token_{1..i}` 的纯函数），代价是"逐位置线性增长、不能像权重一样共享"。那篇的 `## 5.2`、`## 5.3` 顺手点出了朴素实现 `KVCache`（`_lab/minigpt.py:121`）留下的两个窟窿，但没有解决它们，只是把问题甩给了这一篇：

1. **必须按 max_seq 预分配** —— 一条只用 20 个 token 的短请求，也要占住能容纳 2048 个 token 的一整段数组，多余的部分白白占着显存，谁也用不上。这是**内碎片（internal fragmentation）**：分配多了、没用完。
2. **一条请求的 KV 必须是一段连续内存** —— 显存里可能明明有足够的空闲总量，却因为它们零散分布在各处，拼不出一段单独连续的区间来装下一条新的长请求。这是**外碎片（external fragmentation）**：总量够、但拼不成一整块。

这两个窟窿光靠"调小 max_seq"或者"多留点余量"都补不上——它们是**连续分配**这个设计选择本身带来的，不是参数没调好。真正要拆掉的是这条假设本身：**一条请求的 KV 到底要不要在物理上挨在一起？**

答案是不需要。操作系统几十年前就在管理进程的虚拟地址空间时回答过同一个问题：进程眼里的地址空间连续，物理内存不连续，中间靠一张页表做翻译。这一篇要做的就是把这套思想原样搬到 KV 缓存上——`_lab/paged.py` 整个文件的注释（`_lab/paged.py:8-10`）已经把结论写在最前面：**逻辑上连续（token 0..n）、物理上分散（若干固定大小的块），中间用一张块表映射**。`## 2` 会把这个类比拆开、逐条对应；`## 3` 会带你把 `_lab/paged.py` 里对应的每一个部件读一遍；`## 5` 会回过头来算这套机制自己引入的新代价——块表变长、内碎片压到多少、`block_size` 怎么选。

这一篇是"从 0 实现推理引擎"这条主线里**最像操作系统**的一篇——分页、块表、引用计数，跟虚拟内存是同一套思想，只是把"字节"换成了"KV 张量的一个位置"。

顺带交代一下这篇在全局里的位置：它单独看只是"把一条请求的内存管理得更精细"，但它拆掉的这条假设，恰恰是后面 `[[04-连续批处理]]` 能把长短不一的多条请求塞进同一个 batch 的物理前提——如果每条请求还得占一段连续内存，请求一多，`## 0` 那两条碎片债务会直接让"凑出一个 batch"这件事本身变得不可行；也恰恰是 `[[05-前缀缓存]]` 能让不同请求共享同一段历史的物理前提——没有块表这层间接，"两条请求指向同一份 KV"根本无从谈起。这两条线都要等到各自那一篇才会展开，这里先把承重的那部分——块、块表、引用计数——一次性打好。

## 2. 原理：和虚拟内存的类比

这一节按四步走：先看操作系统的原始方案（`## 2.1`），再逐项对应到 `_lab/paged.py`（`## 2.2`），然后讲清楚为什么这条类比不是修辞、而是后面每个部件的根源（`## 2.3`），最后落到一个具体数字上（`## 2.4`）。

### 2.1 操作系统怎么解决"必须连续"这件事

进程看到的地址空间是一段逻辑上连续的编号，从 0 到某个上限；物理内存则由许多个固定大小的**物理页帧（page frame）**拼成，散落分布，哪块空闲、哪块被谁占着，操作系统心里有一本账。进程完全不知道、也不需要知道自己用的第 5000 字节实际落在物理内存的哪个角落——它只管按逻辑地址读写，操作系统在背后维护一张**页表（page table）**，把"逻辑页号"翻译成"物理页帧号"，每次访存都要经过这一次翻译。

三个部件缺一不可：固定大小的物理页帧、外加一个知道哪些页帧空闲的**分配器**；一张逻辑页号到物理页帧号的**页表**；以及**按需分配（demand paging）**——进程第一次真正用到某个逻辑页时才给它分配物理页帧，不是一开始就把整个虚拟地址空间对应的物理页帧全部占满。

### 2.2 一一对应到 `paged.py`

| 虚拟内存里的角色 | KV 分页里对应的东西 | 在 `_lab/paged.py` 里 |
|---|---|---|
| 虚拟地址（进程视角，连续） | 逻辑 token 位置 `0..length-1` | `SeqTable.length`（`_lab/paged.py:86`） |
| 物理页帧（不连续，若干个固定大小） | 物理块（`k`/`v` 数组的最外维，每块 `block_size` 个 token 位） | `PagedKVCache.k`/`v`（`_lab/paged.py:73-74`） |
| 页表（逻辑页号→物理页帧号） | 块表（逻辑块序号→物理块号） | `SeqTable.blocks`（`_lab/paged.py:85`），一个 Python list |
| 地址翻译（页号 + 页内偏移） | `pos // block_size` 找块、`pos % block_size` 找偏移 | `SeqTable.append`/`gather`（`_lab/paged.py:115`、`:131`） |
| 空闲页帧的登记（链表/位图） | 空闲块栈 | `BlockAllocator.free`（`_lab/paged.py:32`） |
| 按需分配（真用到才给物理页） | 写满当前块才要新块 | `SeqTable._ensure`（`_lab/paged.py:89-93`） |
| 多个进程共享同一物理页 | 多条请求的块表指向同一物理块 | `BlockAllocator.incref`/`decref`（`_lab/paged.py:42-50`） |
| 页帧的引用计数 | 块引用计数 | `BlockAllocator.ref`（`_lab/paged.py:33`） |

### 2.3 把这个类比讲透——后面所有机制都从它长出来

这条类比不是一个方便记忆的比喻，它是接下来每一个部件为什么长这样的**根源**：

- 地址翻译这层间接（indirection）一旦存在，"同一段内容被两个不同的逻辑位置映射到同一块物理内存"就成了免费的能力——不用改物理内存布局，只用改块表里的一个条目。这正是块共享、进而是前缀缓存的全部理论基础：两条请求的块表在某个逻辑块序号上指向同一个物理块号，KV 就被共享了，见 `[[05-前缀缓存]]`。
- 因为共享意味着"一块物理内存背后可能站着不止一个逻辑位置"，"释放"就不能是"谁用完了就直接还回去"，而要变成"引用计数归零才真的还"——操作系统的页表项同样要维护类似的账本，不然一个进程 fork 出子进程、子进程先退出时，会把父进程还在用的物理页也一起释放掉。`## 3.2` 会具体讲 `BlockAllocator.decref`（`_lab/paged.py:45-50`）怎么做到这一点。
- 按需分配这条性质直接决定了内碎片的上界：一条请求最多因为"最后一块没写满"浪费掉一块的空间，不会更多——这是 `## 3.6`、`## 5.2` 要量化的核心指标。
- 这个类比也划出了这篇不讲什么。操作系统的按需分页遇到"缺页"时会去磁盘上把对应的页调进来（page-in），对进程本身透明；`_lab/paged.py` 的块分配器遇到"没有空闲块了"时**不会**去哪儿调更多块进来，直接抛 `MemoryError`（`_lab/paged.py:37`），因为它没有"磁盘"这一层可退——`## 6` 会讲这件事在真实引擎里对应什么。操作系统还有页面置换算法（比如 LRU，选出哪个页被换出到磁盘），本篇的分配器完全没有淘汰逻辑，`_lab/paged.py:26-27` 的注释已经写清楚：那是前缀缓存要用的东西，见 `[[05-前缀缓存]]`。

### 2.4 一个具体的地址翻译算例

抽象的映射规则容易看懂，容易看漏的是它在真实数字上到底怎么落地。取 `block_size=4`，一条请求已经写到第 13 个逻辑位置（`pos=13`，从 0 计数）：

```
pos // block_size = 13 // 4 = 3   →  块表第 3 项（第 4 个逻辑块）
pos %  block_size = 13 %  4 = 1   →  块内偏移 1（这个块里的第 2 格）
```

`SeqTable.blocks[3]`（`_lab/paged.py:85`）里存的物理块号可能是任意值，比如 `17`——它不需要跟逻辑块序号 `3` 有任何数值关系，`## 3.2` 的分配器发块号时完全是"栈顶弹出来是几就是几"，不保证连续、不保证有序。`append()`（`_lab/paged.py:113-117`）真正写入的位置是 `self.pool.k[layer][17, 1]`——物理块 17 的第 1 个槽位。如果 `pos=14`（下一个位置），`14 // 4 = 3`、`14 % 4 = 2`，还是块表第 3 项、物理块 17，偏移变成 2；直到 `pos=16`，`16 // 4 = 4`，第一次需要块表第 4 项——如果这一项还不存在，`_ensure()`（`## 3.3`）就会在这一刻触发一次新的 `alloc()`。

这也是为什么"内碎片最多一块"这句话在算例上站得住：只要 `_ensure()` 严格按"当前块数是否够用"来判断，块表第 3 项从 `pos=12` 开始被用到 `pos=15`（四个槽位全部用满）才会去申请第 4 项——不会出现"块表已经有 5 项，但序列长度只有 13"这种提前多要的情况。

再看跨块边界那一刻：`pos=15` 时 `15 // 4 = 3`、`15 % 4 = 3`，仍落在块表第 3 项，是这个块的最后一格；`pos=16` 时 `16 // 4 = 4`，第一次需要块表第 4 项。这两次写入之间，`_ensure()`（`_lab/paged.py:89-93`）里的 `need` 从 `4` 跳到 `5`，`while len(self.blocks) < need` 的循环条件第一次为真，触发一次新的 `alloc()`。**这正是块表变长的唯一时机**——不是按固定节奏预先长出来的，是被"写满了上一块"这个事实精确触发的。

### 3.1 物理池：先把"固定大小的块"摆出来

`PagedKVCache`（`_lab/paged.py:61-77`）是分页版的物理 KV 池，构造函数（`_lab/paged.py:69-74`）里唯一值得多看一眼的是它的形状：

```python
shape = (n_blocks, block_size, cfg.n_head, cfg.d_head)
self.k = [np.zeros(shape, np.float32) for _ in range(cfg.n_layer)]
```

**块被摆在最外维**——不是随手写的，`_lab/paged.py:64-66` 的注释点破了原因：这样一个块在内存里天然连续，真实引擎的 attention kernel 才能按块做 gather（`## 4.2` 会看到 vLLM 的 kernel 真的是这么吃数据的）。`_lab` 用不上这个优势，因为教学代码走的是 `## 3.5` 会讲的另一条路，但物理布局先摆对，是为了让读者的直觉和真实实现对得上。

跟朴素版 `KVCache`（`_lab/minigpt.py:121`）比，`PagedKVCache` 从"每条请求一份、按 max_seq 大小"变成了"整个引擎共享一个池、按 `n_blocks × block_size` 固定大小"——池的总大小从一开始就是有限且已知的，`n_blocks` 数量的物理块，谁来用、怎么分配，全部交给 `## 3.2` 的分配器。

### 3.2 块分配器：一个栈，仅此而已

`BlockAllocator`（`_lab/paged.py:22-58`）的全部状态只有两样：一个空闲块编号的栈 `self.free`（`_lab/paged.py:32`），一个正在被使用的块的引用计数字典 `self.ref`（`_lab/paged.py:33`）。

`alloc()`（`_lab/paged.py:35-40`）：

```python
def alloc(self) -> int:
    if not self.free:
        raise MemoryError("没有空闲块了 —— 真实引擎在这里会触发抢占/回退")
    b = self.free.pop()
    self.ref[b] = 1
    return b
```

`self.free.pop()` 从栈顶弹一个块号——Python `list.pop()` 不带参数默认弹末尾，均摊 O(1)。**为什么用栈而不是别的结构**：分配和释放都只需要在一端操作，不需要遍历、不需要排序，块与块之间没有"先来后到"的语义要求——归还回去的块和新分配出去的块，用哪个物理块号都无所谓，只要没人在用。用队列（`pop(0)`）反而是 O(n)，因为要搬移剩下所有元素；用栈是最简单也最快的选择，不需要引入任何优先级。

`incref()`/`decref()`（`_lab/paged.py:42-50`）：

```python
def incref(self, b: int) -> None:
    self.ref[b] = self.ref.get(b, 0) + 1

def decref(self, b: int) -> None:
    self.ref[b] -= 1
    if self.ref[b] == 0:
        del self.ref[b]
        self.free.append(b)
```

**这是块共享能成立的前提**：`decref` 只有在计数真的归零时才会把块号放回 `self.free`。设想两条请求的块表都指向同一个物理块 `b`（`## 2.3` 已经讲过这为什么能发生）：请求 A 结束、调用 `free()`（`## 3.6`）对 `b` 调一次 `decref`，`self.ref[b]` 从 2 掉到 1，**不会**被放回空闲栈，因为请求 B 还在用它；只有等 B 也结束、再调一次 `decref`，计数才真正归零，块 `b` 才被放回 `self.free`，能被别的请求 `alloc()` 到。`## 3.7` 第 7 条断言会把这条行为实际跑一遍。

### 3.3 块表：地址翻译真正发生的地方

`SeqTable`（`_lab/paged.py:80-145`）是一条请求自己的块表，构造函数（`_lab/paged.py:83-87`）里 `self.blocks: list[int]` 就是"逻辑块序号 → 物理块号"这张页表本身，一个 Python list，下标是逻辑块序号，元素是物理块号。

`_ensure()`（`_lab/paged.py:89-93`）——按需扩容：

```python
def _ensure(self, n_tokens: int) -> None:
    need = (self.length + n_tokens + self.pool.block_size - 1) // self.pool.block_size
    while len(self.blocks) < need:
        self.blocks.append(self.pool.alloc.alloc())
```

`need` 是"写完这批新 token 之后，一共需要多少块"，用的是向上取整的写法（`(x + bs - 1) // bs`）。`while` 循环只在当前块数不够时才继续 `alloc()`——**只在写满当前块时才要新块**，这正是内碎片被压到"最多一块"的直接原因，`_lab/paged.py:90` 的注释把这句话原样写在了代码上方。

`append()`（`_lab/paged.py:109-117`）——把新算出来的 K/V 写进去，做的是地址翻译本身：

```python
for i in range(T):
    pos = self.length + i
    b, off = self.blocks[pos // bs], pos % bs
    self.pool.k[layer][b, off] = kn[:, i, :]
    self.pool.v[layer][b, off] = vn[:, i, :]
```

`pos // bs` 是"逻辑位置属于第几个逻辑块"，拿它去查 `self.blocks` 这张页表，翻出物理块号 `b`；`pos % bs` 是块内偏移 `off`。**这两行就是 `## 2` 类比里"地址翻译"那一步的全部代码**——没有更多机关，一个整除、一个取模。

`gather()`（`_lab/paged.py:119-134`）反过来，把散落在各块里的 K/V 收成一段连续数组供后面矩阵乘用，同一套 `pos // bs`、`pos % bs` 翻译逻辑在 `_lab/paged.py:131` 里重复了一遍，只是方向从写变成了读。`## 3.5` 单独展开讲它，因为它是本篇最容易被误解的一处。

### 3.4 begin/commit：我在这个文件上踩的坑

`SeqTable.begin()`（`_lab/paged.py:95-103`）和 `commit()`（`_lab/paged.py:105-107`）看起来像是能合并成一步的两个函数——`begin(n_new)` 按需扩容、把 `n_new` 标成"待写"（`self._pending`），`commit()` 才真的把 `self.length` 往前推：

```python
def begin(self, n_new: int) -> None:
    self._ensure(n_new)
    self._pending = n_new

def commit(self) -> None:
    self.length += self._pending
    self._pending = 0
```

`_lab/paged.py:98-100` 的 docstring 把这道坎明写了出来——**这是我写这个文件时踩过的坑**：第一版没有分 begin/commit 两步，直接在最后一层结束时把 `tab.length` 往前推。问题出在 `_forward_paged()`（`## 3.5` 完整看）要对**每一层**分别调用 `tab.append(li, ...)` 和 `tab.gather(li)`——每层都要写自己的 K/V、读自己那份历史。如果 `length` 在第一层算完就被推进了，那么从第二层开始，`gather()` 里用到的历史长度会比这一步实际正在处理的 token 数**多算一遍**——因为"序列变长了"这件事被提前发生了，而这一步里其余各层都还没写完。表现出来的症状是 attention 的 `scores` 矩阵形状和 `causal` 掩码形状对不上，直接崩掉，而且是那种一层层往下传的抛错，排查起来要一路倒查到底是哪层的形状先不对。

**根子在于混淆了两件事**：`begin`/`commit` 之间要跨越的是"这一步要写多个层各自的 K/V"，而"序列长度变化"只应该在**这一步全部层都写完之后**发生一次。`_lab/paged.py:100` 的注释把这句话说得最直接：**每一层都要写自己的 K/V，但"序列长了 n 个"这件事只该发生一次。** 分成两步之后，`begin(T)` 先把空间占好（调用 `_ensure`，可能触发 `alloc()`），但 `self.length` 保持不变，让 `gather()` 在每一层看到的历史长度都还是**这一步开始之前**的值，加上这一层刚 `append` 进去的 `T` 个新 token；等所有层都跑完了，最后调一次 `commit()`，`self.length` 才真的往前挪。对照 `_forward_paged()`：`tab.begin(T)`（`_lab/paged.py:226`）在进入层循环之前调一次，`tab.commit()`（`_lab/paged.py:244`）在层循环结束之后调一次，中间每一层各自的 `append`/`gather` 都不碰 `length`。

这类坑属于 `03-KV缓存的第一性原理.md` `## 6` 点名的那种典型模式：**代码不会静默跑出错误答案，而是会因为一个跟本意无关的地方（矩阵形状）先炸掉**——这里比较幸运，属于"至少会报错"的一类；比它更危险的是 `## 6` 会讲到的另一类：形状照样对、值却算错了，程序一声不吭地往下跑。

### 3.5 `gather()` 是教学妥协，不是分页要付的代价

`_lab/paged.py:119-125` 的 docstring 已经把这件事挑明了：真实引擎**不做这一步**——它把块表直接交给 attention kernel，由 kernel 边算边取。这里 gather 是为了让教学代码能复用 numpy 的矩阵乘，代价是多一次拷贝，所以本文件不谈性能。

具体看 `gather()`（`_lab/paged.py:119-134`）在干什么：申请一段全新的连续数组 `ks`/`vs`（`_lab/paged.py:128-129`），然后逐个逻辑位置查块表、把散落在各物理块里的一格格 K/V **拷贝**进这段新数组（`_lab/paged.py:130-133`）。`_forward_paged()` 拿到这段连续数组之后（`_lab/paged.py:236`），才能直接写 `q @ k_all.transpose(0, 2, 1)`（`_lab/paged.py:237`）这种 numpy 矩阵乘——numpy 的矩阵乘要求参与运算的数组本身是（或者能被廉价视图成）连续内存，不能直接对着"散落在若干物理块里的某些格子"做矩阵乘。

**这一步付出的代价是明确的、独立于"分页"本身的**：多申请一段内存、多一次逐位置拷贝。它不是分页机制天生要付的代价，而是"教学代码要复用 numpy 现成的矩阵乘算子"这个选择带来的代价。`## 4.2` 会看到真实引擎怎么绕开它——不做 gather，直接把物理池和块表一起递给 kernel，kernel 内部自己按块表去物理池里取数、边取边乘，从不在显存里再单独开一段临时连续数组。如果读者把 `gather()` 这次拷贝误当成"分页本身比连续 KV 缓存慢"的证据，那是把教学实现的取舍安在了机制头上——`## 5.3` 会把这条决策单独列出来讲。

### 3.6 释放与碎片统计

`free()`（`_lab/paged.py:136-140`）：

```python
def free(self) -> None:
    for b in self.blocks:
        self.pool.alloc.decref(b)
    self.blocks.clear()
    self.length = self._pending = 0
```

对块表里记着的每一个物理块号调一次 `decref`——**不是直接把块号扔回空闲栈**，而是走引用计数那条路：如果这个块没被别的请求共享，计数归零，`BlockAllocator.decref`（`_lab/paged.py:45-50`）会把它放回 `self.free`；如果被共享着，这次 `decref` 只是让计数减一，物理块继续留在别的请求手里。这条路径正是 `## 2.3` 讲的"释放不能是谁用完了就直接还回去"的具体实现。

`fragmentation()`（`_lab/paged.py:142-145`）：

```python
def fragmentation(self) -> dict:
    cap = len(self.blocks) * self.pool.block_size
    return {"capacity": cap, "used": self.length, "internal_waste": cap - self.length}
```

`capacity` 是这条请求名下所有块加起来能装的总槽位，`used` 是实际用掉的 token 数，`internal_waste` 就是内碎片——`_lab/paged.py:143` 的注释把话挑明了："分页的核心卖点就是把它压到 < 1 块"。因为 `_ensure()` 只在写满当前块时才申请新块（`## 3.3`），`internal_waste` 的取值范围严格是 `[0, block_size)`——最坏情况下，最后一个块只写进去 1 个 token，浪费 `block_size - 1` 个槽位，但绝不会更多，`## 5.2` 会拿它对照不同 `block_size` 的取舍。

### 3.7 `selftest()` 的七条断言

`selftest()`（`_lab/paged.py:148-213`）用同一套 `cfg`（`_lab/paged.py:151`）和同一段 `prompt`（`_lab/paged.py:153`）跑了七条断言，一次比一次刁钻：

1. **分页不许改变输出**（`_lab/paged.py:155-162`）：`block_size=4` 故意选小，逼出多个块，比较 `_forward_paged` 和朴素 `forward_naive` 的输出，容差 `atol=1e-4`。
2. **逐 token 增量喂，结果照样要一致**（`_lab/paged.py:164-169`）：每次只喂 1 个 token，缓存从空一路长大，`## 3.4` 讲的 begin/commit 配对如果错了，这条断言第一个失败。
3. **`block_size` 不该影响结果**（`_lab/paged.py:171-176`）：`1/2/8/16` 挨个跑一遍，都要跟 `want` 一致——`block_size` 只是实现细节，不该泄漏到数学结果里。
4. **内碎片必须小于一个块**（`_lab/paged.py:178-181`）：直接调用 `## 3.6` 的 `fragmentation()`。
5. **释放后块要全部归还**（`_lab/paged.py:183-190`）：跑完一段 prompt 之后调 `free()`，`pool.alloc.n_used` 必须归零——不归零就是泄漏，`## 6.3` 会讲这类 bug 有多隐蔽。
6. **块用尽必须明确报错**（`_lab/paged.py:192-199`）：`n_blocks=1, block_size=2` 这种极端小的池子，跑稍长一点的 prompt 必然把块耗尽，断言在 `except MemoryError` 分支里通过，`try` 分支走到底反而是失败——**静默把请求跑"成功"了才是这条测试真正要抓的问题**。
7. **引用计数：两张表共享一个块，只有都释放才归还**（`_lab/paged.py:201-210`）：直接摆弄 `BlockAllocator`，不经过 `SeqTable`——`alloc()` 一次、`incref()` 一次（模拟两个使用者）、`decref()` 一次（第一个使用者走了），这时 `n_used` 该还是 1；再 `decref()` 一次（第二个也走了），`n_used` 才归零。

`## 1` 已经跑过这七条全绿。全部代码只有 260 行，测试却把"分页"这件事从"输出不许变"到"内碎片有多大"到"释放会不会漏"到"用尽会不会静默"到"共享的计数账对不对"，五个维度全部盯住了——这也是 `_lab/tests/test_lab.py` 里同一批断言（`test_paging_is_output_preserving`、`test_internal_fragmentation_below_one_block`、`test_blocks_are_returned_on_free`、`test_out_of_blocks_raises_loudly`、`test_refcount_guards_shared_blocks`）会在 pytest 里被重新组织一遍的原因：`selftest()` 是不依赖任何框架、能单独跑的版本，pytest 版本额外把 `block_size` 参数化到了 1/2/4/8/16 五个值（`_lab/tests/test_lab.py:125-133`）。

### 3.8 逐行对照 `forward_cached` 与 `_forward_paged`：算法一个字没变

`_forward_paged()` 的 docstring（`_lab/paged.py:218-222`）自己点破了这一节要证明的事："和 `minigpt.forward_cached` 逻辑相同，只是 K/V 走块表""对比这两个函数是本篇教学的核心：算法一个字没变，变的只是历史 K/V 从哪儿取"。把两份代码摆在一起看，能验证这句话不是自我表扬：

| 步骤 | `forward_cached`（`_lab/minigpt.py:139-173`） | `_forward_paged`（`_lab/paged.py:216-246`） |
|---|---|---|
| 记录已有历史长度 | `p0 = cache.length`（`_lab/minigpt.py:147`） | `p0 = tab.length`（`_lab/paged.py:225`） |
| 位置编码 | `w["wpe"][p0:p0+T]`（`_lab/minigpt.py:148`） | 同一行写法（`_lab/paged.py:227`） |
| 因果掩码 | `np.triu(...)`（`_lab/minigpt.py:151`） | 同一行写法（`_lab/paged.py:228`） |
| 写入新 K/V | `cache.k[li][:, p0:p0+T] = kn`（`_lab/minigpt.py:159`，数组切片赋值） | `tab.append(li, kn, vn)`（`_lab/paged.py:235`，走块表） |
| 读出全部历史 K/V | `k_all = cache.k[li][:, :p0+T]`（`_lab/minigpt.py:161`，数组切片） | `k_all, v_all = tab.gather(li)`（`_lab/paged.py:236`，走块表） |
| 注意力打分与掩码 | `scores = q @ k_all.T / √d`、`scores[:, :, p0:] += causal`（`_lab/minigpt.py:164-165`） | 同一行写法（`_lab/paged.py:237-238`） |
| 序列长度真正推进 | `cache.length = p0 + T`（`_lab/minigpt.py:171`，层循环结束后一次性做） | `tab.commit()`（`_lab/paged.py:244`，层循环结束后一次性做） |

唯一的区别集中在两处：**写**从"数组切片赋值"变成了"经过块表翻译的 `append`"，**读**从"数组切片"变成了"经过块表翻译再拷贝出来的 `gather`"。除此之外，从位置编码怎么切片、因果掩码怎么打、attention 打分公式怎么写，两份代码逐字相同——**没有因为换成分页就多算一点、少算一点、换一种数学**。这正是 `## 0` 一开始就该立住的底线：分页是一次纯粹的**存储层重构**，不是对算法的修改，`## 3.7` 第 1、2 条断言之所以能通过，根源就在这张表格里"结构完全一致"这件事——不是巧合，是设计上刻意保持的对称。

唯一多出来的是 `tab.begin(T)`（`_lab/paged.py:226`）——`forward_cached` 不需要这一步，因为它按 max_seq 连续预分配，从不会出现"当前空间不够、需要按需申请"这种情况；分页版本引入了这一行，是 `## 3.4` 讲过的 begin/commit 机制存在的直接原因。

## 4. 真实引擎是怎么做的（对照 vLLM、SGLang）

`## 2`、`## 3` 讲的块、块表、引用计数是能想到的最小实现，下面挑四个点跟真实引擎对照：分配和引用计数（`## 4.1`）、gather 这一步是否真的存在（`## 4.2`）、`block_size` 该取多大（`## 4.3`）、块用尽之后怎么办（`## 4.4`）——每一点都对应 `_lab/paged.py` 里已经讲过的某个具体设计。

### 4.1 vLLM：`BlockPool` 的引用计数，和我们的 `incref`/`decref` 是同一件事

`_lab/paged.py:42-50`（`## 3.2`）的 `incref`/`decref` 是这套思想能想到的最小实现。vLLM 的 `BlockPool`（`vllm:vllm/v1/core/block_pool.py:143`）做的是同一件事，只是接的东西更多。

分配对应的是 `get_new_blocks()`（`vllm:vllm/v1/core/block_pool.py:647-677`）：块用尽时的处理和 `_lab/paged.py:36-37` 几乎是同一句话，只是异常类型不同：

```python
# vllm:vllm/v1/core/block_pool.py:658-659（节选）
if num_blocks > self.get_num_free_blocks():
    raise ValueError(f"Cannot get {num_blocks} free blocks from the pool")
```

拿到块之后立即把引用计数置 1（`vllm:vllm/v1/core/block_pool.py:667-668`：`assert block.ref_cnt == 0; block.ref_cnt += 1`），跟 `_lab/paged.py:38-39` 的 `b = self.free.pop(); self.ref[b] = 1` 是同一步操作。

共享块对应的是 `touch()`（`vllm:vllm/v1/core/block_pool.py:702-717`）——"当一个块被另一条有相同前缀的请求命中时调用"，核心逻辑只有一行：`block.ref_cnt += 1`（`vllm:vllm/v1/core/block_pool.py:715`），跟 `_lab/paged.py:42-43` 的 `incref` 一模一样。释放对应 `free_blocks()`（`vllm:vllm/v1/core/block_pool.py:719-743`），每个块先 `ref_cnt -= 1`（`vllm:vllm/v1/core/block_pool.py:731`），只有归零才真正处理归还（`vllm:vllm/v1/core/block_pool.py:732`），跟 `_lab/paged.py:47-50` 同构。

真正的差异在"归零之后去哪儿"：`_lab/paged.py:50` 只有一个空闲栈 `self.free`，块归零就直接 `append` 进去；vLLM 归零之后要看这个块有没有被前缀缓存记住的哈希（`vllm:vllm/v1/core/block_pool.py:733-738`），有哈希的块进一条按 LRU 淘汰的队列末尾，没有哈希的块进另一条按 LIFO 复用的队列开头——归零不等于立刻可回收，先进入"逻辑上还留着、物理上可以被下一次分配顶掉"的状态。这是前缀缓存要用的机制，`_lab/paged.py:25-27` 已经点明这类复杂度留给 `[[05-前缀缓存]]`，这里只讲最朴素的一份空闲栈。

### 4.2 vLLM：`block_table` 直接喂给 kernel，没有 gather 这一步

`## 3.5` 说 `gather()` 是教学妥协，真实引擎把块表直接交给 kernel。vLLM 的 flash attention 后端在真正调用 kernel 时是这样写的：

```python
# vllm:vllm/v1/attention/backends/flash_attn.py:1085-1098（节选）
flash_attn_varlen_func(
    q=query[:num_actual_tokens],
    k=key_cache,
    v=value_cache,
    ...
    block_table=block_table,
    ...
)
```

`k`、`v` 传进去的是**整个物理 KV 池**（`key_cache`/`value_cache`，对应 `_lab/paged.py` 里 `PagedKVCache.k`/`v` 那种全局共享的池），`block_table` 单独作为一个参数传进去——kernel 拿到这两样东西，自己在 CUDA 代码里按块表去物理池里取数、边取边算，从头到尾没有一步"先把这条请求的 K/V 收成一段连续数组"。这跟 `## 3.5` 的结论完全对得上：`gather()` 拷贝出来的那段连续数组，纯粹是 `_lab` 为了复用 numpy 现成的矩阵乘算子而付出的代价，不是"分页"这件事本身要付的代价——真实引擎有专门写的 kernel，压根不需要这一步。

### 4.3 `block_size` 该取多大——vLLM 和 SGLang 给出了不同答案

`## 5.2` 会展开讲这条取舍本身，这里先把两个真实引擎的选择摆出来，作为论证时的实锤。

vLLM 默认块大小是 16：

```python
# vllm:vllm/config/cache.py:79（节选）
DEFAULT_BLOCK_SIZE: ClassVar[int] = 16
```

没有用户显式指定时，`self.block_size = self.DEFAULT_BLOCK_SIZE`（`vllm:vllm/config/cache.py:317`）。

SGLang 默认页大小（等价于 `block_size`，SGLang 管它叫 page）是 1——绝大多数平台走到这一分支：

```python
# sglang:python/sglang/srt/arg_groups/overrides.py:2395-2396（节选）
if not is_musa():
    return {"page_size": 1}
```

`page_size=1` 意味着 SGLang 默认按**token 粒度**做分页，不是**块粒度**——它的分配器 `TokenToKVPoolAllocator`（`sglang:python/sglang/srt/mem_cache/allocator/token.py:28`）管理的直接是"哪些 token 槽位空闲"，`alloc()`（`sglang:python/sglang/srt/mem_cache/allocator/token.py:55-64`）不够时**返回 `None`**（`sglang:python/sglang/srt/mem_cache/allocator/token.py:59-60`）而不是抛异常——跟 `_lab/paged.py:37` 直接抛 `MemoryError`、vLLM 直接抛 `ValueError` 是三种不同的"报告没内存了"的方式，但共同点是**都不会静默**：调用方拿到 `None` 或者捕获到异常，必须显式处理，不能假装什么都没发生。

这条对比直接印证 `## 5.2` 要讲的取舍两端：vLLM 选了较大的固定块（16），换来更短的块表、kernel 更好写；SGLang 默认选了粒度最细的单 token 页，代价是块表（在 SGLang 里等价的结构）要长得多，换来的是碎片几乎为零、共享粒度精确到每个 token。两个工业级引擎在同一条设计决策上给出了不同答案，这不是谁更"对"，是"什么时候可以不这样"的活证据。

值得补一句的是，SGLang 并非只能走 token 粒度——`page_size` 本身是可配的，一旦调大，分配器会切换成另一个专门的类 `PagedTokenToKVPoolAllocator`（`sglang:python/sglang/srt/mem_cache/allocator/paged.py:105`），它的 docstring 直接写着"和 `TokenToKVPoolAllocator` 接口相同，只是一条请求分到的输出总是按页对齐的"（`sglang:python/sglang/srt/mem_cache/allocator/paged.py:106-110`）——跟 `_lab/paged.py` 里 `SeqTable`/`BlockAllocator` 这一套"块粒度"设计是同一件事，只是被实现成了默认关闭、按需打开的一个选项。这说明 `block_size`（或者 `page_size`）从来不是引擎在写代码那一刻就焊死的常数，而是一个特意留出来给部署场景调节的旋钮，`## 5.2` 那三条"为什么/不这样/什么时候不这样"讲的正是这个旋钮该往哪边拧。

### 4.4 块用尽之后：抢占（vLLM）与 retract（SGLang）

`_lab/paged.py:37` 抛出 `MemoryError` 时，函数调用直接中断，调用方要自己接住，`## 3` 的教学代码没有再往下处理。真实引擎接住之后不会让请求就此失败，而是会**抢占**——把某条正在跑的请求的块表整个收回去，腾出空间先满足别的请求，之后再把这条被抢占的请求重新排队。vLLM 管这个动作叫 `_preempt_request`（`vllm:vllm/v1/core/sched/scheduler.py:1347`），SGLang 管它叫 `retract_decode`（`sglang:python/sglang/srt/managers/scheduler.py:3589`）——名字不同，解决的是同一个问题：**块不够用是一个必须显式处理的调度状态，不是异常路径里打个日志就能糊弄过去的事**。这两个函数具体怎么选谁被抢占、怎么恢复，超出了本篇范围，点到为止；`## 6` 会把这条结论落回到 `_lab/paged.py` 自己的行为上。

## 5. 设计决策与代价

`## 3` 逐个部件讲了"是什么"，这一节回过头来讲"为什么这样选、不这样选会怎样、什么时候可以不这样选"——七条决策，从要不要分页这个最上层的问题开始，一路细到物理内存该怎么摆。

### 5.1 要不要分页（vs. 继续用连续预分配）

- **为什么这样**：`## 0` 已经算过，朴素 `KVCache`（`_lab/minigpt.py:121`）同时背着内碎片和外碎片两条债。分页用"逻辑连续、物理分散、中间一张块表"把两条债都还掉：内碎片被 `_ensure()`（`## 3.3`）压到不足一块；外碎片直接被"物理块本来就不要求连续"这个设计消灭——不再需要在一大片物理内存里找出一段单独连续的区间。
- **不这样会怎样**：继续按 max_seq 连续预分配，`## 3` 那种块表、地址翻译、引用计数全都不需要写，`_forward_paged()`（`## 3.4`）可以直接退化成 `03-KV缓存的第一性原理.md` `## 3.1` 里 `forward_cached` 那种更简单的写法。但代价是 `## 0` 列的两条碎片债务原样背着——请求越多、长度差异越大，浪费掉的显存越多。
- **什么时候可以不这样**：只服务单条请求、或者所有请求长度提前已知且彼此接近时——`03-KV缓存的第一性原理.md` `## 5.2` 已经举过这个例子：批量跑一个定长评测集。这些场景下，预分配不会产生"多余空间"（因为提前知道要用多少），上分页反而多了一层块表维护和地址翻译的开销，纯属浪费。

### 5.2 `block_size` 该取多大——用碎片表说话

`## 1` 跑过的那张表是这条决策的直接证据，序列长度固定在 100：

| block_size | 块数 | 容量 | 浪费 | 浪费率 |
|---:|---:|---:|---:|---:|
| 1 | 100 | 100 | 0 | 0.0% |
| 4 | 25 | 100 | 0 | 0.0% |
| 16 | 7 | 112 | 12 | 10.7% |
| 64 | 2 | 128 | 28 | 21.9% |
| 256 | 1 | 256 | 156 | 60.9% |

（本库自己的玩具引擎、CPU 上的解析计算，公式在 `_lab/paged.py:256-259`——不是真实引擎的实测数字。）

块越大，块表（`SeqTable.blocks`，`_lab/paged.py:85`）越短——序列长度不变时，`len(blocks)` 跟 `block_size` 成反比；块表短，`_ensure()`（`## 3.3`）里 `while` 循环触发 `alloc()` 的次数也越少，管理开销小；真实引擎里 kernel 也更好写。但内碎片正比于"最后一块被浪费掉的部分占整块的比例"，块越大，最坏情况下浪费的绝对槽位数越多——`block_size=256` 时单条 100 token 的请求浪费掉 156 个槽位，比实际用量本身还多。

- **为什么这样（取一个折中值，比如 vLLM 的 16）**：`## 4.3` 已经给出实锤，vLLM 默认 `block_size=16`（`vllm:vllm/config/cache.py:79`）——序列长度通常远大于 16，块表长度可控，内碎片上限也就 15 个 token 位，相对长序列可以忽略。
- **不这样会怎样**：块取太大（比如 256），短请求会被内碎片吃掉大半（上表 `60.9%` 就是证据）；块取太小（比如 1，等于不分块），内碎片趋近于零，但块表长度等于序列长度本身，`_ensure()` 每次都要触发 `alloc()`，管理开销、块表本身占的内存都线性增长，真实引擎里 kernel 每次要处理的块数也随之暴涨。
- **什么时候可以不这样**：`## 4.3` 里 SGLang 默认走的就是 `page_size=1`（`sglang:python/sglang/srt/arg_groups/overrides.py:2396`）这条极端——当共享粒度需要精确到每个 token（前缀缓存希望命中越细越好）、或者硬件/kernel 实现本身对"token 粒度页"有专门优化时，块小到 1 反而是对的选择。这条决策不存在"唯一正确的 block_size"，只有"这条引擎在这组约束下选的折中点"。

### 5.3 `gather()` 还是把块表交给 kernel

- **为什么这样（本库选 gather）**：`_lab` 全程只用 numpy（`_PLAN.md` `## 2` 的约束），numpy 的矩阵乘要求参与运算的数组连续，没有"kernel 边算边按块表取数"这种自定义算子。`gather()`（`_lab/paged.py:119-134`）是复用 numpy 现成算子唯一可行的路径。
- **不这样会怎样（本库这样选的代价）**：多一次显式拷贝（`## 3.5`），拷贝的数据量随序列长度线性增长——这是 `_lab/paged.py:12` 早就点明的"这个文件只做机制，不做性能"的具体体现。
- **什么时候可以不这样**：写一个专门的 kernel（哪怕是最朴素的、逐块累加的 CUDA 或 Triton kernel），像 `## 4.2` 的 vLLM 那样，把物理池和块表原样传进去，kernel 内部自己索引——这样连一次拷贝都不用付。`[[01-注意力从朴素到FlashAttention]]` 会展开讲这类 kernel 具体怎么写。

### 5.4 引用计数 vs. 直接归还

- **为什么这样**：`## 2.3` 已经讲过，一旦地址翻译这层间接存在，块共享就是免费的能力——但共享意味着一个物理块背后可能站着不止一个逻辑请求，"谁用完就还"这种朴素释放会把还在用的块提前收回，`## 6.4` 会讲这样出错时症状有多隐蔽。
- **不这样会怎样**：如果 `decref` 直接改成"调一次就还"（不检查计数是否归零），`## 3.7` 第 7 条断言会立刻失败——两张表共享同一个块，第一张表 `free()` 之后，第二张表还在用的这个块已经被塞回空闲栈，下一次 `alloc()` 可能把它分给一条完全不相关的新请求，新请求会往这个块里写入自己的 K/V，而共享它的第二条老请求下一次读到的就是新请求的数据——静默串号。
- **什么时候可以不这样**：从始至终不存在共享（每条请求各用各的块，块表之间没有交集）——这种情况下引用计数恒为 0 或 1，维护它没有额外收益，但也没有额外坏处。多数实现即便当下不需要共享也保留这套机制，是因为共享是随时可能被打开的事（`[[05-前缀缓存]]` 一旦启用，共享就成了常态），不值得为了省掉几行代码在将来重新引入一遍。

### 5.5 begin/commit 分两步 vs. 一步到位

- **为什么这样**：`## 3.4` 完整讲过——多层网络每层都要写自己的 K/V，但序列长度只能变化一次，`begin`/`commit` 把"占位"和"真正生效"拆成两个独立动作，中间留出空间让每一层各自完成读写。
- **不这样会怎样**：`## 3.4` 那道坑本身就是答案——合并成一步、在某一层内部直接推进 `length`，会导致后续层看到的历史长度和实际情况对不上，`## 3.7` 第 1、2 条断言会先炸。
- **什么时候可以不这样**：如果整个前向逻辑本来就不是逐层分开写 K/V、读 K/V（比如一次性把所有层的注意力打包成一个大算子，内部自己保证顺序一致性），这道坎可能被算子内部的实现细节吸收掉，不需要在 `SeqTable` 这一层暴露 `begin`/`commit` 两个方法——但这属于换了一种实现方式来解决同一个问题，不是绕开了问题本身。

### 5.6 块用尽报错 vs. 悄悄扩容

- **为什么这样**：`_lab/paged.py:36-37` 选择直接抛 `MemoryError`，把"没内存了"变成一个调用方必须处理的显式事件——`## 4.4` 已经证明真实引擎在这里接的是抢占/retract 这类调度动作，不是当没看见。
- **不这样会怎样**：如果 `alloc()` 改成"没有空闲块就悄悄扩容物理池"，短期内测试照样能通过（`## 3.7` 的断言不会报错），但代价是显存分配变得不可预测——物理池的大小本该是引擎启动时就按显卡容量算好的一个硬上限（`n_blocks` 这个参数存在的意义），悄悄扩容意味着这个上限形同虚设，某条请求的一次 `alloc()` 调用可能触发一次意料之外的大块显存申请，轻则拖垮延迟，重则直接把显卡剩余显存挤爆导致进程崩溃。
- **什么时候可以不这样**：明确知道物理池永远够用（比如 `n_blocks` 按最坏情况留了很大余量、或者只是本地跑一次性小实验）——这时候 `alloc()` 永远不会走到 `if not self.free` 那个分支，报不报错在实际运行路径里没有区别；但这属于"侥幸没触发"，不是"这条设计原则不适用"。`_lab/paged.py:36-37` 选择报错而不是留一条隐患，正是因为写库的人没法替使用者保证这份侥幸。

### 5.7 物理布局：把块摆在最外维

`## 3.1` 提到 `PagedKVCache` 的形状是 `(n_blocks, block_size, n_head, d_head)`（`_lab/paged.py:72`），块维度摆在最外面，不是随手选的顺序。

- **为什么这样**：让同一个物理块在内存里连续排列——`self.pool.k[layer][b]` 这一次索引取出的是一段连续内存。真实引擎的 attention kernel 按块读取（`## 4.2` 里 `block_table` 的用法）依赖的就是这个前提；如果块维度不是最外维，同一个块的数据会被 `n_head`、`d_head` 这些维度的步长切得七零八落，kernel 每次按块取数都要做一堆不连续的小段读取，效率上不去。
- **不这样会怎样**：比如把形状写成 `(n_head, n_blocks, block_size, d_head)`，`_lab` 这种全走 numpy 索引、不关心内存步长的教学代码不会报错、结果也不会错——`## 3.7` 的断言照样能过，因为 numpy 的高级索引本来就会处理好任意步长；但这个布局如果被一个真实 kernel 拿去用，同一个块的数据在物理内存上就不连续了，`## 4.2` 依赖"块内连续"这条假设的 kernel 会直接读错数据，或者退化成极慢的逐元素访问。
- **什么时候可以不这样**：如果从一开始就认定这套代码永远只在 numpy 里跑、永远不会被一个真实 kernel 直接吃这块内存（就像 `_lab/paged.py` 本身现在这样），布局选哪种在正确性上确实没有差别——`_lab` 选了"跟真实实现对齐"的布局，纯粹是为了不让读者建立错误的直觉，不是因为教学代码本身需要它。

## 6. 常见错误与踩坑

`03-KV缓存的第一性原理.md` `## 6` 的开场白在这篇同样成立："推理引擎的 bug 绝大多数是静默的"——加了分页之后代码照样能跑、不报任何异常，生成出来的文本读起来甚至通顺，但其实从某一步开始就已经算错了。下面六条坑分两类：`## 6.1`、`## 6.2` 属于"形状/下标层面容易露馅"的一类（不一定崩溃，但离真相不算太远）；`## 6.3` 到 `## 6.6` 属于"完全无声、要靠专门设计的测试才能抓到"的一类，`## 3.7` 里对应的断言逐条能对上号，这不是巧合——每一条容易踩的坑背后，都应该有一条专门盯住它的断言，反过来说，一条测试如果抓不住某类坑，这条坑就还没被真正管住。

### 6.1 跨块边界写错

场景：`append()`（`_lab/paged.py:109-117`）里如果 `off = pos % bs` 这一步算错——比如手滑用错了变量、或者块大小从常量改成了每次读配置却读错了字段——某个 token 会被写进错误的块内偏移，覆盖掉同一块里另一个 token 的 K/V。

后果：不会有任何异常（数组下标依然在合法范围内，只是指向了不该指向的格子），被覆盖的那个 token 的历史 K/V 从此错了，后续所有依赖它的 attention 计算全部跟着错，而且因为跨层共享同一套块表，错误会在每一层重复发生一遍。`## 3.7` 第 1、3 条断言（跟朴素版本比对、跨 `block_size` 取值比对）是抓这类 bug 最直接的手段——朴素版本没有"块内偏移"这个概念，天然不会犯这种错，拿它当参照物一比就露馅。

### 6.2 begin/commit 不配对，长度错乱

`## 3.4` 完整讲过原理，这里补一条更容易踩的具体写法：如果在层循环内部某个分支提前 `return`（比如加了一段调试代码，某个条件下跳过了剩余层），会导致 `commit()` 根本没被调用到，`self._pending` 永远停在上一次 `begin()` 设的值，`self.length` 也永远没有真的往前推进。下一次调用 `begin()` 时，`_ensure()`（`_lab/paged.py:89-93`）用的 `self.length` 还是旧值，算出来的 `need` 比实际需要的块数少，可能导致 `append()` 往一个还没申请到的位置写（数组越界）或者往一个逻辑上"已经该被下一条数据占用"的位置写。这类 bug 的症状取决于具体触发路径，可能是数组越界的硬崩溃，也可能是不越界但语义已经错乱的静默错误——这正是"begin/commit 必须严格配对"这条约束比看上去更重要的原因，`_forward_paged()`（`_lab/paged.py:226`、`:244`）里 `begin` 和 `commit` 分别只在函数入口和出口各出现一次，中间没有任何提前返回的分支，就是为了保证这条配对关系不会被破坏。

### 6.3 释放时忘了 decref——泄漏，且不会报错

`SeqTable.free()`（`_lab/paged.py:136-140`）如果实现里漏掉了对 `self.pool.alloc.decref(b)` 的调用（比如手滑只清了 `self.blocks.clear()`，没有先把块号交回分配器），块的引用计数永远不会归零，`BlockAllocator.free`（`_lab/paged.py:32`）那个空闲栈里永远少了这些块。**程序不会报任何错**——`n_used`（`_lab/paged.py:56-58`）会一直增长，物理池会在跑了足够多条请求之后被"用满"（其实是被泄漏干净），下一次 `alloc()` 才会抛出 `MemoryError`（`_lab/paged.py:37`），而这时候排查起来看到的现象是"莫名其妙的池子不够用了"，跟真正的原因（某处忘了 `decref`）隔着好几百次请求的距离，很难直接联想到一起。`## 3.7` 第 5 条断言（释放后 `n_used` 必须归零）就是专门盯住这个坑设计的——它必须紧跟在一次完整的分配-释放之后立刻检查，不能像真实场景那样等池子被耗尽了才发现。

### 6.4 共享块被提前释放——会读到别人的 KV，静默给出错答案

`## 5.4` 已经从"为什么"的角度讲过这条，这里讲具体后果。设想请求 A、B 共享同一个物理块 `b`（块的引用计数是 2），如果某处代码错误地对 `b` 调用了两次 `decref`（比如 `free()` 被意外调用了两遍，或者在共享发生之前错误地把引用计数先减了一次），块 `b` 会在只有一条请求真正结束的情况下被过早放回空闲栈。接下来任何一次 `alloc()` 都可能把 `b` 分给一条完全不相关的第三条请求 C，C 开始往 `b` 里写自己的 K/V，把 A/B 原本共享的那份历史数据覆盖掉。如果这时候 B 还没结束、还在生成，它下一次 `gather()`（`_lab/paged.py:119-134`）读到的会是 C 写进去的数据——**不是 `nan`，不是异常，是别的请求的 KV，形状完全合法**，B 会拿着这段错误的历史继续算 attention、继续生成，产出一个读起来通顺、但已经被另一条请求的内容污染过的错误答案。这是本篇里最危险的一类 bug，因为它连"结果看起来有点奇怪"这种线索都未必留下——`[[05-前缀缓存]]` 会讲真实引擎为了防住这类错误，专门把"块的引用计数"和"块的哈希是否还有效"分开管理，任何一次共享块的复用之前都要先核验哈希链没断。

### 6.5 把「全局池容量」和「这条请求名下的容量」搞混

`fragmentation()`（`_lab/paged.py:142-145`）里 `cap = len(self.blocks) * self.pool.block_size`，用的是**这条请求名下**已经分配到的块数，不是整个 `PagedKVCache` 的 `n_blocks`。一个容易犯的错误是把它写成 `self.pool.alloc.n_blocks * self.pool.block_size`——两个都是"合法"的数字，量纲却完全不同：前者衡量"这条请求自己浪费了多少"，后者衡量"整个引擎的物理池有多大"。写错的后果不是程序崩溃，是 `## 3.7` 第 4 条断言这类"内碎片必须小于一个块"的检查从"验证分页机制本身"变成了一句几乎恒真的废话——只要请求数远小于 `n_blocks`，用全局容量算出来的"浪费率"会小到看不出问题，哪怕 `_ensure()` 真的算错了、某条请求实际占了远超它需要的块数，这条检查也发现不了。

### 6.6 捕获 `MemoryError` 却不做恢复处理，等于把静默错误请回来

`_lab/paged.py:37` 抛 `MemoryError` 的本意，是逼着调用方在这一刻做出一个明确的决定——`## 4.4` 里真实引擎的选择是抢占别的请求腾地方，或者把当前请求退回队列稍后重试。如果调用方图省事，写成 `try: _forward_paged(...) except MemoryError: pass`——异常确实被"处理"了，程序不会崩溃，但这条请求这一步的 K/V 根本没写完整（`## 3.4` 讲过的 `begin`/`commit` 之间，`_ensure()` 半途失败，`commit()` 可能压根没被执行到，或者对应着一批没写全的块），下一次这条请求再被调度到时，`tab.length` 记的位置和物理块里实际写了什么对不上。这类"捕获了异常但没有真正恢复"的写法，表面上看比 `## 6.3` 的资源泄漏更安全（至少显式处理了），实际上把一个**本来会崩溃、容易定位**的错误，转换成了一个**悄悄跑下去、只在后面某处输出乱码或崩溃**的错误——`_lab/paged.py:37` 那句注释"真实引擎在这里会触发抢占/回退"里的"回退"二字，指的是抓到异常之后要有真正的后续动作（把这条请求完整地退回排队、或者清空它这一步已经写了一半的状态重来），不是简单地吞掉异常然后当作什么都没发生。
