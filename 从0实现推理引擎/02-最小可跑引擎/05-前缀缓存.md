# 前缀缓存

> **一句话**：前缀完全相同，K/V 就逐位相同，没理由算两遍、存两份。
> **前置**：`[[04-连续批处理]]`（本篇复用同一个 `Engine`）、`[[03-KV缓存的第一性原理]]`（"K/V 只依赖历史"这条数学事实是本篇存在的全部理由）

## 0. 这一篇要解决什么问题

到 `[[04-连续批处理]]` 为止，引擎已经解决了两类问题：**一条请求内部**怎么管理 KV（分页，`[[03-分页KV与块管理]]`），**多条请求之间**怎么共享计算资源、不让谁等谁（连续批处理）。但还有一类浪费没被碰过：**两条不同请求之间，如果开头一段 token 完全一样，这段计算目前会被各自独立地、老老实实地重新做一遍**——各自 prefill、各自写一份 K/V，互相不知道对方存在。

这不是罕见情况，是真实流量里的常态：同一个 system prompt 被成千上万条请求共享，同一段 few-shot 示例被反复贴在每条 prompt 前面，同一段长文档被多轮追问。`_lab/engine.py` 顶部的模块 docstring 已经点出了这件事的两句话概括（`_lab/engine.py:14-18`）：两条请求如果开头 token 完全一样，那它们前面这段的 K/V 也**逐位相同**（因为 K/V 只依赖该位置及之前的输入），既然一样，就没必要各算一遍、各存一份，做法是按块算内容哈希，哈希相同的块直接复用同一个物理块。

这句话看着简单，动手写的时候却是**整个引擎里最容易写出静默 bug 的一步**——不是因为它牵扯的数学有多复杂（`[[03-KV缓存的第一性原理]]` 已经把"K/V 只依赖历史"证明得很彻底了），而是因为"跨请求共享一份物理内存"这件事，只要有一处引用计数算错、一处哈希算错、一处边界条件漏了，程序**不会崩溃**，只会安安静静地把 A 请求的历史算出来的 K/V，喂给 B 请求去做 attention——B 会得到一个语法通顺、看起来完全正常、但其实答非所问的输出。本篇要把这几处坑一个个挖开看清楚，而不只是把正确代码抄一遍。

先把范围划清楚：本篇要回答四个问题——

1. **为什么可以共享**——这不是新证明，是 `[[03-KV缓存的第一性原理]]` 那条"K/V 只依赖历史"的证明的直接推论，但要把"共享的是物理块本身、不是某种近似"这件事讲实。
2. **为什么必须是链式哈希**——本篇最重要的一节，会构造一个具体例子，把"不链式会怎样"从文字描述变成一次可以亲眼看见的、真实算出不同数字的实验。
3. **引用计数在这里扮演什么角色**——分页那一篇（`[[03-分页KV与块管理]]`）已经讲过"归零才释放"是共享成立的前提，这里要讲清楚前缀缓存具体在哪一步用到它、不用会怎样。
4. **一个容易漏掉的边界情况**——如果整段 prompt 全部命中缓存，引擎要怎么继续往下走。

## 2. 原理

### 2.1 共享的是物理块本身，不是某种近似

`[[03-KV缓存的第一性原理]]` 用归纳法证明过一条结论：对任意层 `l`，位置 `i` 的 `k_i^(l)`、`v_i^(l)` 只依赖 `token_{1..i}`——只依赖这个位置及之前的输入，跟后面还会追加什么完全无关。这条证明当时是在**一条请求内部**用的——用来说明"缓存了之后再读出来，跟当场重新算一遍是完全一样的值"。前缀缓存要做的事只是把这条证明**推广到跨请求**：如果请求 A 和请求 B 在某个位置 `i` 之前的全部 token 完全相同（`A_{1..i} = B_{1..i}`），那么按同一条归纳证明，`k_i` 这个函数在两条请求上吃到的是**完全相同的输入**，算出来的必然是**完全相同的值**——不是"很接近"、不是"语义上差不多"，是同一个纯函数在同一个输入上求值两次，逐位相等。

这句话决定了本篇要强调的一个态度：**前缀缓存不是一种有损优化**。它跟量化（用更低精度存数，天然带来舍入误差）、剪枝、近似注意力这类"拿一点精度换速度"的手段完全不是一回事——量化之后模型的输出理论上就会和不量化时不同，只是差得可以接受；前缀缓存做对了之后，输出必须和完全不用前缀缓存时**逐位相同**，这不是"差得很小可以接受"，是"压根不该有任何差异"。`## 1` 里 `selftest` 那条"开/关前缀缓存输出必须相同"的断言就是在验这件事，不是在验"差得够不够小"。

也正因为它不是近似，前缀缓存能给多少收益完全取决于一件事：**有多少物理块被判定为"内容相同"**，判定错了（判成相同其实不同，或者判成不同其实相同）都是 bug，前者是本篇 `## 2.3` 要讲的静默错误，后者只是少省了一点计算，不影响正确性但影响收益（`## 5` 会讲这条）。

### 2.2 为什么按"块"共享，不是按"整段前缀"共享

`[[03-分页KV与块管理]]` 已经把 KV 拆成了固定大小的物理块，每条请求靠一张块表做逻辑位置到物理块的翻译。前缀缓存要做的事，翻译过来就是：**如果两条请求某几个块的内容相同，就让它们的块表指向同一批物理块**，而不是各自申请新块、各自写一份。

问题来了：为什么要以"块"为单位判断"内容相同"，而不是直接比较"整段前缀有多长一样"？两个理由，一个是工程上的，一个是数据结构决定的：

- **共享的最小单位就是物理块本身**——分页管理下，一条请求的 KV 本来就是按块分配、按块寻址的，"复用一段 K/V"落到实现上，能做的动作只有"把块表里某个位置指向已有的物理块号"，不存在"复用半个块"这种操作——半个块要么整个物理块被你占着不共享，要么共享整个块但内容对不上。所以共享粒度天然就是块大小，不是任意长度。
- **判断"内容相同"需要一个能快速比较的摘要**——如果要比较"两条请求前 300 个 token 是否完全相同"，朴素做法是把 300 个 token 逐个比较，代价随长度线性增长，而且每来一条新请求都要跟缓存里所有已有前缀比一遍。按块算一个哈希值，把"内容是否相同"这个问题转换成"两个哈希值是否相等"，只要块大小选定了，比较代价是常数，跟前缀多长无关。

这就引出了 `## 2.3` 要讲的东西：这个"哈希"具体怎么算，直接决定了前缀缓存是对还是错。

### 2.3 链式哈希：本篇最重要的一节

`_lab/engine.py:36-43` 的 `PrefixCache` 类文档字符串已经把结论写在最前面：**哈希必须是链式的**——`hash(父块哈希, 本块 token)`，不能只 hash 本块自己的 token。这条结论不是"工程上更保险"的建议，是一条不这样做就一定会算错的硬约束，下面把"为什么"和"错了会怎样"都过一遍。

**先把错误的做法摆出来。** 如果你只按"这个块自己的 token 内容"算哈希——`hash(本块token)`——直觉上似乎没问题："内容相同不就该复用吗？"陷阱就藏在这句话里：`## 2.1` 证明的是"**前缀**相同 ⇒ K/V 相同"，不是"**这一块自己**相同 ⇒ K/V 相同"。按 `[[03-KV缓存的第一性原理]]` 的归纳证明，位置 `i` 的 `k_i`、`v_i` 依赖的是 `token_{1..i}` **这一整段**，包括这个块之前所有的历史——两个块**自己的 token 完全一样**，只要**它们前面的历史不完全一样**，块内每个位置算出来的 K/V 就完全不保证相同。只按本块内容算哈希，等于是在断言一件没有被证明过的事：「一个块的 K/V 只取决于这个块自己」——这句话对第 0 层（embedding，还没经过任何 attention）是对的，对第 1 层往后统统不对，因为从第一次 attention 开始，隐藏状态就已经混入了更早的历史。

**具体构造一个例子，让这件事从文字变成可以亲眼看见的数字。** 用 `_lab/minigpt.py` 已经公开的两个函数（`Config`、`init_weights`、`KVCache`、`forward_cached`，都在 `[[03-KV缓存的第一性原理]]` 的 `## 3.1` 里逐行讲过），构造两条请求：

- 请求 A：`[50, 51, 5, 6]`——block_size 取 2，block0 = `(50, 51)`，block1 = `(5, 6)`。
- 请求 C：`[1, 2, 5, 6, 40, 41]`——block0 = `(1, 2)`，block1 = `(5, 6)`，block2 = `(40, 41)`。

两条请求的 block1 **token 内容一模一样**——都是 `(5, 6)`——但它们前面的历史完全不同：A 的历史是 `(50, 51)`，C 的历史是 `(1, 2)`。如果只按本块内容算哈希，两个 block1 会得到相同的哈希值，一个朴素实现会认为"C 的 block1 可以直接复用 A 已经算好的 block1"。这段代码可以直接在 Python 交互环境里跑，不改动 `_lab` 里任何一行：

```python
import numpy as np
from minigpt import Config, init_weights, KVCache, forward_cached

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=64, seed=1)
w = init_weights(cfg)

A = [50, 51, 5, 6]
C = [1, 2, 5, 6, 40, 41]

cacheA = KVCache(cfg, 16)
forward_cached(cfg, w, A, cacheA)          # 先把 A 跑完，block1 的 K/V 被"存进缓存"

cacheC = KVCache(cfg, 32)
forward_cached(cfg, w, C, cacheC)          # C 老老实实按自己的真实历史重算

# 两边 block1（都是 token (5,6)）在 layer1 上的 K，逐位对比
kA = cacheA.k[1][:, 2:4]
kC = cacheC.k[1][:, 2:4]
print(np.abs(kA - kC).max())
```

在这套种子固定的权重下，这个 `max` 的值是 **1.53**——不是浮点噪声量级的 `1e-6`，是和激活值本身同一个数量级的真实差异。`layer0`（还没经过任何 attention，K 只是 token embedding 的线性投影）上两者的差异是精确的 `0.0`——这恰好印证了 `[[03-KV缓存的第一性原理]]` `## 2.2` 归纳证明里"归纳基础"那一步：第 0 层的隐藏状态只由 `token_i` 自己决定，跟历史无关，只有从第一次 attention 混合开始，`k_i` 才真正开始依赖更早的历史。**这也是为什么"只 hash 本块 token"这个错误在浅层网络或者只看 embedding 层时很容易被掩盖过去——差异是从某一层往后才会显现出来的，不是从第一层就看得到。**

再往下走一步：把这个"错误复用"接进一次真正的生成，看它怎么让下游答案变了。构造一个把 C 的 block1 强行换成 A 的 block1 的"坏引擎"（block0、block2 仍然按真实历史正常计算——只有 block1 被替换），跟"完全不复用任何块、老老实实按真实历史算"的正确引擎并排生成 6 步：

```
正确引擎继续生成 6 步：       [58, 58, 58, 58, 58, 58]
非链式哈希引擎继续生成 6 步： [58, 58, 58, 58, 58, 9]
```

前 5 步两边**恰好**给出了相同的 argmax token——这一点本身就是个提醒：**静默 bug 不保证每一步都能被看出来**，被污染的 logits 只是数值上不对（前面已经量出 `layer1` 的 K 差了 1.53），但 argmax 这个离散决策要等误差累积到足够大、或者恰好落在两个候选 token 的决策边界附近，才会真正翻转成一个肉眼可见的错误 token。第 6 步（下标 5）翻转成了 `9`——全程没有任何异常、没有任何报错，`PrefixCache` 如果真的这么写，会在生产环境里安安静静地把一部分请求的输出换成别的东西，而且**具体哪些请求会被换掉，取决于缓存里当前存了哪些块、请求到达的先后顺序**——同样的 prompt，换一批并发的邻居，答案可能就不一样，这种 bug 几乎不可能靠"重跑一遍看看还错不错"来复现和定位。

**链式哈希怎么堵上这个洞。** `_lab/engine.py:51-58` 的 `block_hashes` 方法：

```python
def block_hashes(self, tokens: list[int]) -> list[tuple]:
    bs = self.pool.block_size
    out, parent = [], None
    for i in range(0, len(tokens) - bs + 1, bs):
        parent = (parent, tuple(tokens[i:i + bs]))
        out.append(parent)
    return out
```

第一个块的哈希是 `(None, tuple(第一块token))`；第二个块的哈希是 `(第一个块的哈希, tuple(第二块token))`——**父块的哈希被直接嵌进了子块哈希的结构里**。这样一来，两个块的哈希相等，当且仅当它们各自的父块哈希也相等、且这一块自己的 token 也相等——顺着这条链一路往回推，**两个块哈希相等，当且仅当从序列开头到这个块为止，全部内容都相等**，这正好是 `## 2.1` 证明成立所需要的条件，不多不少。用同样的例子验证一遍：A 的 block1 哈希是 `(hash(block0_A), (5,6))`，C 的 block1 哈希是 `(hash(block0_C), (5,6))`——`block0_A = (50,51)`、`block0_C = (1,2)`，两者的哈希不相等，所以整条链条从第二环开始就已经不相等，两个 block1 的哈希天然不同，不会被误判成可复用。

顺带说一句本库的哈希实现里一个容易被忽略、但其实规避了一类风险的细节：`self.table: dict[tuple, int]`（`_lab/engine.py:47`）直接用嵌套元组当字典的 key，而不是先把这个嵌套元组喂进一个真正的哈希函数（比如 `hash()`、`sha256`）压成一个固定长度的摘要串再当 key。Python 的 `dict` 在两个 key 的哈希值相等时，还会再用 `==` 精确比较一次——所以这里即便发生了哈希数值上的碰撞，`table` 也不会把两个不同内容的块判成同一个 key。这不是白得的好处，是拿内存换的：真实引擎缓存的是几十万甚至上千万个块，没办法把每个块完整的 token 序列都存起来当 key（那样表本身就会占用巨量内存），必须把内容压缩成一个短哈希摘要——一旦压缩，就有了统计意义上非零（但通过选用足够长的哈希位数可以压到可忽略）的哈希碰撞概率。`## 5` 会把这条"要不要用真正的哈希函数压缩 key"当成一条独立的设计决策来看。

### 2.4 只对满块算哈希

`_lab/engine.py:51-58` 的循环范围是 `range(0, len(tokens) - bs + 1, bs)`——只在 `tokens` 长度够一整块时才往前走，最后不满一块的那截尾巴**完全不参与哈希计算**。理由不是"偷懒少算一点"，是这段尾巴的内容**还会变**：一条正在被处理的请求，它当前最后一个不满的块，后面很可能还要继续往这个块里追加新生成的 token（直到写满），如果现在就把这个"半成品"块的内容算成哈希登记进缓存表，此刻算出的哈希对应的其实是"这个块**还没写完时**的内容"——写完之后内容变了，哈希却没有跟着更新，缓存表里就留下了一条描述已经过时的记录。反过来，即便这条请求恰好没有再往这个块写任何东西就结束了，把一个"不知道会不会再变"的东西当成"已经定型、可以放心复用"的东西缓存起来，本身就是在拿一个不确定的前提当结论用。

### 2.5 引用计数：复用不等于免费

`[[03-分页KV与块管理]]` 已经证明过"归零才释放"是块共享成立的前提——两张块表指向同一个物理块时，只有当所有持有者都释放了这个块，它才真的被还给空闲池。前缀缓存是这条规则第一次被真正用上的场景：一旦某个块被两条毫不相干的请求同时指向，"这个块什么时候可以安全地被别人拿去用"这件事，就不再由某一条请求单独决定了。

`_lab/engine.py:60-74` 的 `match` 方法里，每命中一个块就会调用一次 `self.pool.alloc.incref(b)`（`_lab/engine.py:72`）——这行代码在做的事情，翻译成一句话是：**"我也要用这个块，请把它算进有几个人在用里"**。如果漏掉这一行会怎样：假设块 X 目前只有请求 A 的块表指向它，引用计数是 1；请求 B 通过前缀缓存匹配到块 X，把自己的块表也指向它，但没有 incref——块 X 的引用计数依然是 1，账面上"只有一个人在用"，但实际上有两条请求都在读它。等 A 这条请求结束、调用 `SeqTable.free()`（走到 `_lab/paged.py:136-140`）对块 X `decref` 一次，计数从 1 降到 0，块 X 被判定为"没人用了"，还给空闲池——可 B 这时候还没结束，还在往后 decode，块表里依然指着块 X。空闲池随后可能把块 X 分配给一条完全不相关的第三条请求 C，C 开始往块 X 里写自己的 K/V——B 下一步做 attention 时读到的，已经不是它以为在复用的那段前缀，而是 C 刚写进去的、跟 B 毫无关系的数据。这跟经典的 use-after-free 是同一类错误，只是发生在 KV 缓存这个场景里：不会崩溃，只会让 B 读到别人的东西，answer 从此不知道错到哪儿去了。

### 2.6 一个容易漏掉的边界情况：整段 prompt 全部命中怎么办

前面几节都在讲"命中了该怎么复用"，还有一种情况没处理：如果**整段 prompt 的每一块都命中了缓存**，会发生什么？

直觉上这应该是最理想的情况——一个 token 都不用算，直接进入 decode。但这里有个容易被忽略的细节：`## 2.1` 证明的是 K、V 可以被缓存复用，**没有一句话说过 logits 也可以**。回顾 `[[03-KV缓存的第一性原理]]` 的 `## 2.3`：`KVCache` 只存 K、V 两样东西（`_lab/minigpt.py:121-133` 的 `KVCache.__init__` 只分配了 `self.k` 和 `self.v`），连 Q 都不存，logits 更不会被存下来——**logits 是某个位置的隐藏状态过完全部层、再乘上 `lm_head` 之后才有的东西，它从来不是"K/V 缓存"这个概念的一部分**。而生成下一个 token 靠的正是"最后一个位置的 logits"，不是"最后一个位置的 K"。

如果 prompt 的每一块都命中了缓存，意味着**没有任何 token 需要真的跑一次前向**——但没有前向，就没有任何位置的 logits 被算出来过，包括最后一个位置。这时候引擎手里只有一堆缓存好的 K、V，却拿不出"接下来该生成什么"这个问题的答案。`_lab/engine.py:152-188` 的 `_admit` 方法处理这种情况的方式是**回退一个块**（`_lab/engine.py:168-175`）：宁可少复用一整块、把它当成没命中重新算一遍，也要保证至少有一个位置是真正跑过前向的，从而拿得到可用的 logits。`## 3` 会把这段代码逐行拆开看。

### 2.7 一个真实的限制：本库没有淘汰策略

把 `_lab/engine.py` 从头到尾找一遍会发现一件事：`store`（`_lab/engine.py:76-81`）会对登记进表的每个块 `incref`，但**整个文件里没有任何地方对这份引用做过 `decref`**——`self.prefix.table` 只增不减，一个块一旦被存进前缀缓存，就会被这份"缓存自己持有的引用"永远按住，哪怕后来所有真正在用它的请求都已经结束、`SeqTable.free()`（`_lab/paged.py:136-140`）已经把它们那一份引用都还掉了，块的引用计数也不会真正归零——`## 2.5` 讲过"归零才释放"，缓存自己那一份 `incref` 永远不松手，这个块也就永远不会真的回到空闲池。

这不是笔误，是这份教学代码有意留白的一个简化：本篇要讲透的是"跨请求共享要保证正确"这条主线，淘汰策略是另一整套复杂度——什么时候该把哪个块从缓存里挤出去、要不要按最近最少使用排序、挤出去之后原来指着它的请求怎么办——加进来会让 `PrefixCache` 这个类本身的职责从"判断能不能共享"膨胀成"判断能不能共享 + 管理生命周期"两件事，不利于把 `## 2.3` 那条最重要的正确性论证讲清楚。

代价是具体的：物理块池的容量是有限的（`_lab/engine.py:116` 的 `n_blocks`），随着服务运行的时间越长、遇到过的**不同**前缀越多，被缓存永久占住的块只会单调增加，可分配给新请求（不管这条新请求跟已有前缀有没有共享）的块越来越少。`_admit` 遇到分配不出块的情况，处理方式是捕获 `MemoryError` 之后什么都不做、直接 `return`（`_lab/engine.py:178-180`）——这条请求这一步不会被放进来，**不会有任何报错或提示，只会在下一次调度时再试一次**。如果这种情况持续发生，从外部看到的现象只是"吞吐莫名其妙地降下来了、有些请求一直卡在排队"，没有任何异常栈能直接指向"缓存里攒了太多再也不会被淘汰的旧前缀"这个根源——`## 1` 演示的那次运行（8 条请求、1024 个块的池子）远没有触到这条限制，真正会踩到它的是跑得足够久、见过足够多不同前缀的长时间服务。`## 4` 会看真实引擎怎么处理这件事，`## 5` 会把"要不要做淘汰"当成一条单独的设计决策讲清楚。

## 3. 自己动手：`_lab/` 里对应的实现

### 3.1 `PrefixCache` 的三个方法：算哈希、查、存

`PrefixCache` 类（`_lab/engine.py:36-43`）只维护一件事：一张从"块哈希"到"物理块号"的表（`self.table: dict[tuple, int]`），外加两个计数器 `hits`、`lookups` 用来算命中率。围绕这张表，三个方法各司其职：

- `block_hashes`（`_lab/engine.py:51-58`）：把一段 token 序列切成若干满块，对每一块算出链式哈希，`## 2.3`、`## 2.4` 已经逐行讲过它的逻辑。它是纯函数——不读不写 `self.table`，只是把"token 序列"翻译成"这段序列每个满块对应的哈希列表"，`match` 和 `store` 都靠调用它来定位。
- `match`（`_lab/engine.py:60-74`）：从头开始查表，**一旦某块没查到就立刻 `break`**（`_lab/engine.py:69-70` 的 `if b is None: break`）。这一行"提前停止"能安全地成立，前提正是链式哈希——`## 2.3` 已经证明过，某个块的哈希一旦不匹配，它后面所有块的哈希必然也不匹配（因为后面每个块的哈希都把前面的哈希嵌进去了），所以没有必要继续查——继续查也不可能查到。**如果哈希不是链式的，这一行提前停止的优化本身就是错的**：块 2 的哈希跟块 1 匹不匹配没有任何关系，块 1 没查到，块 2 完全可能因为纯粹的内容巧合在表里查到一个属于其他历史的记录——这正是 `## 2.3` 构造的那个例子里，如果不做提前停止检查、放任块 2 单独去查表，会撞上的坑。每查到一块，`match` 立刻对这个物理块 `incref`（`_lab/engine.py:72`）——`## 2.5` 已经讲过漏掉这一步的后果。返回值是"命中的物理块列表"和"命中的 token 数"，两者互相印证：块数乘以 `block_size` 就应该等于 token 数（`_lab/engine.py:74` 的 `len(blocks) * self.pool.block_size`）。
- `store`（`_lab/engine.py:76-81`）：把这条请求处理完之后，自己拥有的满块登记进表里，供后来者复用。留意 `if h not in self.table`（`_lab/engine.py:79`）这个条件——已经登记过的哈希不会被覆盖，**先到先得**，第二条带着同样前缀来的请求即便自己也算完了同一块，也不会去抢已经在表里的那条记录，而是直接在 `match` 阶段查到它、复用它、增加一次引用计数，不会有两份物理内存存着同一段内容。`store` 也会对登记的每个块 `incref` 一次（`_lab/engine.py:81`）——**这次 incref 是缓存表自己持有的一份引用**，跟某条具体请求的块表引用是分开的两件事：即便发起这次 `store` 的请求已经结束、释放了自己的块表引用，只要缓存表这一份引用还在，物理块就不会被回收，后来者依然查得到、复用得到。

### 3.2 `_admit` 里的复用逻辑：从查表到决定要不要真的前向

`_admit`（`_lab/engine.py:152-188`）是每一步调度里"把等待队列的请求放进来跑"的地方，`[[04-连续批处理]]` 已经讲过它的整体结构，这里只看跟前缀缓存相关的那一段：

```python
reuse = 0
if self.prefix is not None:
    blocks, reuse = self.prefix.match(req.prompt)
    if blocks:
        req.tab.blocks = list(blocks)
        req.tab.length = reuse
req.cached_tokens = reuse
self.stats["cached_tokens"] += reuse

todo = req.prompt[reuse:]
```

（`_lab/engine.py:157-167`）先调用 `match`，如果查到了任何命中块，直接把这些物理块号塞进这条请求自己的块表 `req.tab.blocks`（不需要重新分配、不需要拷贝任何 K/V 数据，只是让指针指过去），并把 `req.tab.length` 设成 `reuse`——告诉这张块表"你已经有 `reuse` 个 token 的历史了，尽管你自己一个 token 都还没真正算过"。`todo = req.prompt[reuse:]` 算出真正还需要跑前向的那一段——如果命中了 4 个块、每块 16 个 token，`todo` 就会比 `req.prompt` 短 64 个 token，这正是 `## 1` 表格里"复用 token"数字的来源。

紧接着是 `## 2.6` 讲过的边界情况（`_lab/engine.py:168-175`）：

```python
if not todo:
    back = self.pool.block_size
    req.tab.length -= back
    todo = req.prompt[reuse - back:]
    req.cached_tokens -= back
    self.stats["cached_tokens"] -= back
```

`todo` 是空的，意味着整段 prompt 全部命中——按 `## 2.6` 的分析，这时候手里没有任何真正跑过前向的位置，拿不到 logits。处理方式是**回退整整一个块**：把 `req.tab.length` 往回退 `block_size`，把这个块对应的 token 重新塞回 `todo` 里，同时把 `cached_tokens` 和全局统计的 `stats["cached_tokens"]` 都相应减掉，保持"复用 token 数"这个统计口径不撒谎——这个块虽然刚才在缓存表里查到了、判定为命中，但引擎决定不用这次命中，改成重新真算一遍，统计上就不该再算它是"省下来的"。注意这里退的是**整整一个块**，不是"只退最后一个 token"——原因在 `paged.py` 的分配粒度里：块表按块分配和寻址，"只重算块内最后一个 token"意味着要在一个已经被判定为共享的物理块内部单独改写一个位置，这个物理块可能同时还被表里登记的记录、或者其它请求的块表引用着，往里写就是往共享内存里写——这正是 `## 2.5` 要提防的问题。退一整块，让这个块重新走一遍正常的"分配自己的新物理块、真算、写入"流程，就不会碰共享内存这条红线。之后照常调用 `self._forward(req, todo)`（`_lab/engine.py:176-177`）跑真正的前向，拿到 `logits`，`req.out.append(int(logits.argmax()))`（`_lab/engine.py:182`）append 出第一个生成的 token——至此，即便是"全部命中"这种极端情况，引擎也总能拿到可用的 logits。

最后，`_forward` 跑完、这条请求真正被放进 `running` 列表之前，`_admit` 会调用一次 `self.prefix.store(req.prompt, req.tab)`（`_lab/engine.py:186`）。**这次调用的时机很关键**：一定是在 `_forward` 真正把 K/V 写进物理块（`_lab/engine.py:140` 的 `tab.append`，物理写入发生在 `paged.py` 内部）**之后**才登记进缓存表，不是提前登记。如果反过来，在 `_forward` 开始之前就调用 `store`，把这个块的哈希提前登记进表——后面一步如果另一条请求恰好也命中了这个哈希，会立刻拿到这个物理块号去读，可这个物理块此刻可能还没被写完，甚至这条请求本身还没跑到 `_forward` 那一步。这类"提前发布未完工的东西"式的错误在并发系统里很常见，本库虽然是单线程模拟、不存在真正的竞态，但**代码结构本身有没有把"写完"和"公开"这两件事的顺序保证死**，决定了这类 bug 会不会在未来某次改动（比如给 `_admit` 加上真正的并发或者流水线）中被引入。`## 6` 会把这条单独当一条"常见错误"讲。

### 3.3 引用计数：`BlockAllocator` 的 incref/decref

`_lab/paged.py:22-59` 的 `BlockAllocator` 类文档字符串已经写明了这两个方法是为谁准备的：「块带 hash、带引用计数……那些是**前缀缓存**要用的」。具体实现（`_lab/paged.py:42-50`）：

```python
def incref(self, b: int) -> None:
    self.ref[b] = self.ref.get(b, 0) + 1

def decref(self, b: int) -> None:
    """引用计数归零才真的还回去 —— 这是**块共享**能成立的前提。"""
    self.ref[b] -= 1
    if self.ref[b] == 0:
        del self.ref[b]
        self.free.append(b)
```

`incref` 只是把计数加一；`decref` 减一之后检查是不是归零了，归零才真的把块号塞回空闲栈 `self.free`。这两个方法本身极其简单，简单到容易让人误以为"这里没什么好讲的"——但正是它俩，撑住了 `## 2.5` 讲的那整条"块能不能安全共享"的逻辑。一个物理块此刻的引用计数，就是此刻究竟有多少个不同的持有者正指着它——可能是一条正在跑的请求的块表，也可能是缓存表自己的一份记录（`store` 里的那次 `incref`）。只要这个数字大于零，`decref` 就不会把它放回空闲池，分配器也就不可能把它发给别的、不相关的用途。

### 3.4 `selftest` 里三条专门盯着前缀缓存的断言

`selftest`（`_lab/engine.py:217-294`）第 2、3、6 条断言各自盯着本篇讲过的一条性质：

- **断言 2**（`_lab/engine.py:250-257`）：两条共享 16 个 token 前缀的请求跑完之后，`prefix_hits` 必须大于 0、`cached_tokens` 必须大于 0——光是"没崩"不够，得真的发生了命中，否则前缀缓存这个开关形同虚设。
- **断言 3**（`_lab/engine.py:259-266`）：开着前缀缓存跑出来的 `prefill_tokens`，必须严格小于关闭时跑出来的 `prefill_tokens`——`## 2.1` 说过前缀缓存唯一的收益来源就是少算 prefill token，这条断言直接验证收益真的兑现了，不是只做了表面功夫。
- **断言 6**（`_lab/engine.py:285-291`）：

  ```python

  pc = PrefixCache(pool)

      print("FAIL 链式哈希失效：不同前缀的同内容块撞了 key（会静默给出错答案）")
  ```

  这正是 `## 2.3` 里"AB|CD 和 XY|CD 第二块内容相同、历史不同"那个抽象例子的最小可执行版本——`[1,2,5,6]` 和 `[3,4,5,6]` 的第二块都是 `(5,6)`，第一块不同。这条断言比 `## 2.3` 构造的完整生成实验轻量得多（不用真的跑模型、不用比较数值），却精确地盯住了"会不会撞 key"这一件事本身——是 bug 存在与否的最短路径判据，`_lab/tests/test_lab.py:217-225` 的 `test_chained_hash_prevents_key_collision` 就是把这条断言原样搬进了 pytest。

### 3.5 自己动手：换一个 `block_size`，看命中数字怎么变

`## 2.2` 说过共享的最小单位是物理块，这句话有个直接推论：**块大小本身决定了这次共享能省到多少**——不是"块越小越好、块越大越好"这种单调关系，而是要看共享的那段前缀能不能被块大小整除。用 `## 1` 那组 8 条请求（共享 64-token system prompt）的实验，只改 `_lab/engine.py:311` 里的 `block_size`，其它都不动，自己跑一遍：

```python
for bsz in (8, 16, 32, 63, 64):
    e = Engine(cfg, w, n_blocks=1024, block_size=bsz, max_running=8,
               enable_prefix_cache=True)
    for i in range(8):
        e.add(Request(i, sysp + [200 + i, 201 + i], 8))
    st = e.run()
    print(bsz, st["prefill_tokens"], st["cached_tokens"], e.prefix.hits, e.prefix.lookups)
```

真实跑出来的结果：

```
block_size    prefill_tokens  cached_tokens  hits  lookups
         8               80            448    56       57
        16               80            448    28       29
        32               80            448    14       15
        63               87            441     7        8
        64               80            448     7        8
```

`block_size` 取 8、16、32、64 时，`prefill_tokens` 全部是 80——共享的 64-token 前缀恰好能被这四个数整除，不管切成多少块，能共享的 token 总量（448）是一样的，块数越少（`hits` 越小）只是意味着每块更大、要维护的表项更少，跟省了多少计算无关。`block_size=63` 是唯一的例外：`87 > 80`，多出来的 7 个 token 正好是 `7 条请求 × 1 个 token`——因为 `64` 不能被 `63` 整除，`block_hashes`（`_lab/engine.py:51-58`）只能切出**一个**满块（前 63 个 token），剩下第 64 个 token（虽然内容也是共享的）连同每条请求各自独有的 2 个 token 一起，永远没有资格进入任何一个满块，`## 2.4` 讲过的"只对满块算哈希"这条规则，在这里就是"明明是共享内容，却因为块边界没对齐而白白多算了"的直接原因。

这条实验补全了 `## 4.2` 那句"基数树能做到比固定块大小更细的粒度"的具体含义：换成基数树，`(1..63)` 和 `(1..64)` 这两段前缀之间那 1 个 token 的差异不需要凑够一整块才能被处理——树可以精确地在第 64 个 token 这个位置分叉，第 1-64 个 token 无论如何都能被共享，不会因为块边界没对齐而损失这部分共享。固定块大小的方案要避免这种"没对齐、白算"的情况，只能指望共享的前缀长度凑巧是块大小的整数倍——真实场景里的 system prompt、few-shot 模板不见得会刻意对齐到 16 或 32 这种块大小，`block_size` 选多大、要不要为了对齐去刻意设计 prompt 模板的长度，是这条实验揭示出来的一个实际问题，`## 5.2` 已经把"哈希表 vs 基数树"这条取舍写成了决策，这里补上的是"选定了哈希表方案之后，块大小本身还有一层对齐代价"这个更具体的教训。

## 4. 真实引擎是怎么做的（对照 vLLM 与 SGLang）

`_lab/engine.py` 的 `PrefixCache` 用的是**哈希表**：每个块算一个（链式）哈希，拿它当 key 去查一张扁平的表。这不是唯一的做法——vLLM 和 SGLang 分别代表了两条不同的路子，拿它们跟本库的实现对照，能看清楚"哈希表"这个选择本身其实也是一条设计决策，而不是"前缀缓存天生就该这么写"。

选这两个引擎对照不是随意的：`03-语言选型/` 系列已经用真实仓库统计说过，vLLM 和 SGLang 是这批引擎里 Python 占比最高的两个（分别 75%、80%），核心调度逻辑基本都在纯 Python 里，读起来不需要先跨过一层 C++/Rust 的门槛，跟 `_lab/engine.py` 本身的实现语言也对得上，对照起来最直接。

### 4.1 vLLM：跟本库同构的链式哈希，多几层实际考虑

vLLM 的 `hash_block_tokens`（`vllm:vllm/v1/core/kv_cache_utils.py:620-647`）跟 `_lab/engine.py:51-58` 的 `block_hashes` 在结构上几乎一一对应：

```python
# vllm:vllm/v1/core/kv_cache_utils.py:641-647（节选）
if not parent_block_hash:
    parent_block_hash = NONE_HASH

curr_block_token_ids_tuple = tuple(curr_block_token_ids)
return BlockHash(
    hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
)
```

同一件事：父块哈希嵌进子块哈希的输入。区别是两处：一是 vLLM 用一个真正的哈希函数（`hash_function`）把 `(parent_block_hash, curr_block_token_ids_tuple, extra_keys)` 这个元组压成一个固定长度的摘要值当 key，不是像本库这样直接用嵌套元组本身当 key——`## 2.3` 结尾提过的"内存换碰撞概率"取舍，在这里就是真实存在的（`## 5` 会展开）。二是多了一个 `extra_keys` 参数——同样的 token 内容，如果两条请求用的是不同的 LoRA 适配器、不同的多模态输入、或者带了不同的 `cache_salt`（一种显式声明"这两条请求即使前缀字面相同也不该共享"的机制），会被 `extra_keys` 区分开，不会被误判成可复用——这类场景下"token 内容相同"跟"K/V 真的相同"这条等价关系本身就不成立了（比如换一个 LoRA 适配器，同样的输入权重都变了，`## 2.1` 讲的"纯函数"这个前提就被破坏了），`extra_keys` 是把这类额外的"隐藏输入"也编码进哈希里，逻辑跟本篇讲的完全一致，只是需要考虑的"输入"比本库这个玩具引擎更多。

`## 2.6` 讲的"全部命中要回退"这个边界情况，vLLM 里也有一模一样的处理，而且给出的理由和取的做法跟 `_lab/engine.py:168-175` 几乎逐字对应：

```python
# vllm:vllm/v1/core/kv_cache_manager.py:256-262（节选）
# NOTE: When all tokens hit the cache, we must recompute the last token
# to obtain logits. Thus, set max_cache_hit_length to prompt_length - 1.
# This can trigger recomputation of an entire block, rather than just
# the single last token, because allocate_slots() requires
# num_computed_tokens to be block-size aligned. Removing this limitation
# could slightly improve performance in the future.
max_cache_hit_length = request.num_tokens - 1
```

注释里两句话对应本篇两个结论：第一句"必须重算最后一个 token 才能拿到 logits"就是 `## 2.6` 证明的东西；第二句解释了"为什么退的是一整块，不是一个 token"——`allocate_slots()`（vLLM 的块分配函数）要求已计算的 token 数必须是块大小的整数倍，这跟 `## 3.2` 里"退一整块是为了不在共享物理块内部单独改写"的理由是同一件事的另一种表述：块级分配器天然只能以块为粒度操作，"少退一点、只重算最后一个 token"在这种分配器下根本没有对应的操作可做。注释最后一句"未来也许能把这里优化得更精细"也侧面说明了这不是无关紧要的实现细节，是真实引擎也认了的、块粒度分配带来的固有代价。

### 4.2 SGLang：用基数树，不用哈希表

SGLang 的前缀缓存（`sglang:python/sglang/srt/mem_cache/radix_cache.py`）走的是完全不同的数据结构：**基数树（radix tree）**，不是哈希表。`RadixCache` 类（`sglang:python/sglang/srt/mem_cache/radix_cache.py:303`）维护一棵树，`TreeNode`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:238-260`）是树上的节点，每个节点存一段 token（`node.key`）和这段 token 对应的 KV（`node.value`）。查找前缀命中走的是 `match_prefix`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:377`）——从根节点开始，沿着树往下走，尽可能匹配到最长的公共前缀；写入新前缀走的是 `insert`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:437`）——如果新序列在某个已有节点中途分叉，就把那个节点从分叉点切开，长出一个新分支。

这跟哈希表方案回答的是**同一个问题**——"两条请求前面这段一样吗，一样就共享"——但编码"依赖历史"这条约束的方式完全不同：哈希表方案里，"块 2 依赖块 1"这件事是**人为编码进哈希函数的链式结构**里的（`## 2.3` 证明过，不链式就会出问题）；基数树方案里，"这段依赖前面那段"这件事**是树本身的结构自带的**——一个节点在树里的位置本身就是它的完整前缀，不需要另外算一个哈希去描述"我依赖谁"，父子关系直接就是依赖关系，不可能出现 `## 2.3` 那种"两个无关节点意外撞在一起"的情况，因为树上任何两个不同路径到达的节点，天然对应不同的前缀。

两种方案还有一处实打实的粒度差异：哈希表方案的共享单位被死死钉在"块大小"上——`## 2.4` 讲过，不满一块就不能进缓存；基数树在 `insert` 时可以在**任意 token 边界**把一个节点切开分叉（前提是没有开启按页对齐，SGLang 也支持按 `page_size` 对齐，行为上更接近块方案），共享粒度理论上能做到比固定块大小更细。这个差异不是免费的：基数树要维护父子指针、要在插入时做节点分裂，比"算一个哈希去查一张扁平表"要复杂得多——**两种数据结构在解同一个问题，选择哪一种，是拿"实现复杂度"换"共享粒度和树结构带来的其它能力"的取舍**，`## 5` 会把这条也当一条决策写清楚。

引用计数在这两套方案里也长得不一样。`## 2.5`、`## 3.3` 讲的 `paged.py` 引用计数是"归零就立刻还回空闲池"；SGLang 的 `TreeNode.lock_ref`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:247`）语义不同——`inc_lock_ref`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:623-636`）、`dec_lock_ref`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:638-656`）管理的是"锁定"状态，`lock_ref` 归零之后节点**不会被立刻从树上摘掉**，只是从 `protected_size_`（锁定、不可驱逐）这个桶挪进 `evictable_size_`（可驱逐）这个桶——它依然留在树里，等着要么被后来的请求命中续命，要么在显存紧张、需要驱逐时被某种淘汰策略挑中真正清理掉。这跟 `paged.py` 里"归零立刻释放"的直接后果是：SGLang 的树上会长期挂着大量"当前没人在用、但也没被清理"的历史前缀，只要后面还有新请求命中它们，就不需要重新分配和搬运——代价是这棵树本身要占着一部分本可以立刻腾出来的显存，直到淘汰策略真的把它清理掉。

### 4.3 两个真实引擎都做了淘汰，本库没有

`## 2.7` 讲过 `_lab/engine.py` 的 `PrefixCache` 一个块只要被 `store` 过，就会被永久按住，从不淘汰。两个真实引擎都没有留这个空白。

vLLM 用 `FreeKVCacheBlockQueue`（`vllm:vllm/v1/core/kv_cache_utils.py:228-239`）——一个双向链表，文档字符串直接写明排序规则："The least recent used block is at the front (LRU)"。关键的设计是：一个块的引用计数降到 0 之后，**它不会被立刻从哈希表里摘掉，而是被放进这个空闲队列，按最近最少使用排序**——如果在它被真正挑出来分配给别的用途之前，又有新请求命中了它的哈希，这个块可以直接被捞回来重新使用，不需要重新计算；只有当分配器真的需要一个新块、又找不到从未用过的空闲块时，才会从这个队列最前面（最久未被访问的那个）淘汰一个块，同时清掉它在哈希表里的记录。

`## 4.2` 提到的 SGLang `evictable_size_` / `protected_size_` 桶，本质上是同一个思路的另一种记账方式：`lock_ref` 归零的节点从"受保护"挪进"可驱逐"，但依然留在树里，等着要么被后来的请求命中续命，要么在需要腾地方时被淘汰策略真正清理掉。

两边的共同点是：**"引用计数归零"和"这块内存被回收挪作他用"之间，都插了一层"暂缓、按某种策略排队"的中间状态**，不是归零就立刻处理。`_lab/paged.py:42-50` 的 `decref` 恰恰相反——归零立刻把块塞回空闲栈，没有任何中间状态；`_lab/engine.py` 能这样简化，是因为它压根不打算让一个块的引用计数在"被前缀缓存记住"之后降到 0——`## 2.7` 讲的"缓存自己那份 incref 永不归还"，换个角度看也是一种（更原始的）避免这个问题的方式：既然引用永远不会真的归零，也就不需要"归零之后该怎么处理"这套额外的排队逻辑，代价是完全没有淘汰的能力。

## 5. 设计决策与代价

### 5.1 要不要引入前缀缓存这套机制

- **为什么这样**：`## 1` 的实测已经给出了具体数字——8 条请求共享 64-token system prompt，prefill token 从 528 降到 80，wall time 降到不到一半。只要真实流量里存在"不同请求共享相当一段前缀"这件事，前缀缓存就能把本该重复的计算和存储省下来，而且 `## 2.1` 已经论证过它不是近似，不用担心用了之后输出会变。
- **不这样会怎样**：每条请求各自独立 prefill，代码更简单（不需要维护哈希表、不需要处理引用计数、不需要考虑 `## 2.3`、`## 2.6` 这些边界情况），但完全没有跨请求共享的收益，`[[04-连续批处理]]` 解决的是"调度粒度"问题，前缀缓存解决的是"重复计算"问题，两者互不替代。
- **什么时候可以不这样**：请求之间前缀重合度本来就低——比如每条都是完全独立、彼此毫无关联的单轮问答，没有共享的 system prompt、没有共享的 few-shot 示例——这时候哈希表几乎查不到任何命中，维护它本身反而是纯粹的额外开销（每次 prefill 都要多算一遍哈希、多查一次表），`## 5.7` 会具体算这笔账什么时候是负收益。

### 5.2 按块共享，还是按任意 token 边界共享（哈希表 vs 基数树）

- **为什么这样**（选哈希表）：`_lab/engine.py` 建立在分页 KV 之上，共享的最小单位天然就是物理块，用哈希表查块级别的命中，实现直接对应到现有的分页结构，不需要额外引入一整套树的分裂、合并逻辑。`## 4.2` 讲过，SGLang 的基数树能做到比块更细的粒度，但代价是数据结构本身复杂得多。
- **不这样会怎样**：如果坚持哈希表方案却想要比块更细的共享粒度，只能把块调小——但块越小，`[[03-分页KV与块管理]]` 讲过的块表开销（每条请求要维护的块数）就越大，注意力 kernel 要处理的块数也越多，这是块大小本身的取舍，不是免费能拿到的细粒度。
- **什么时候可以不这样**：如果场景里前缀共享天然就发生在块对齐的边界上（比如固定长度的 system prompt、模板化的 few-shot 结构），哈希表方案已经能拿到几乎全部收益，上基数树换来的细粒度用不上；反过来，如果场景里存在大量**分支型**的共享——比如一次对话在某个点之后走向多个不同分支（beam search、多轮编辑重试同一处），不同分支在非块对齐的位置上分叉，基数树能更自然地表达这种结构，`## 4.2` 的 `insert` 分裂逻辑就是为这种场景准备的。

### 5.3 链式哈希，还是只 hash 本块内容

- **为什么这样**：`## 2.3` 已经用真实跑出来的数字证明过——不链式会把两个历史不同、内容相同的块判成可复用，`layer1` 的 K 差出 1.53，下游生成在第 6 步真的翻转成了错误 token，而且全程没有任何报错。链式哈希是让 `## 2.1` 那条"共享的前提是前缀相同"的证明，精确地落进代码里的唯一方式。
- **不这样会怎样**：`## 2.3` 已经具体演示过；补一句更概括的说法——只 hash 本块内容，本质上是在断言"K/V 只依赖这个块自己"，这条断言只在网络的第 0 层（还没经过任何 attention）成立，对第 1 层往后一律不成立，所以这个错误几乎必然会在真实的多层 Transformer 上发生，不是某种边缘场景才会踩到的坑。
- **什么时候可以不这样**：找不到——只要模型有超过一层 attention（几乎所有真实的 Transformer 都是），链式哈希就是必须的，没有"什么时候可以省略"这个选项。这条决策跟别的决策不一样，不是权衡，是正确性的硬约束。

### 5.4 用真正的哈希函数压缩 key，还是直接用完整结构当 key

- **为什么这样**（vLLM/SGLang 的做法）：真实引擎的缓存表要装下几十万甚至更多个块，如果 key 是完整的、一路链回根节点的 token 序列，内存开销会随缓存的块数线性增长、而且每个 key 本身也会越来越长（链得越深，key 越大），压成一个固定长度（比如 64 位或 128 位）的哈希摘要，查表的内存和比较开销都是常数，跟前缀多长、缓存了多少块无关。
- **不这样会怎样**（本库的做法）：`_lab/engine.py:47` 直接用嵌套元组当 key，`## 2.3` 结尾讲过，这样反而**规避**了哈希碰撞——Python 的 `dict` 在哈希值相等时还会用 `==` 精确比较一次，不会真正把两个不同内容的块误判成同一个 key。代价是每个 key 本身占的内存和它编码的历史长度成正比，块数一多、链条一深，这张表本身就会变得很大。
- **什么时候可以不这样**：本库这种教学场景——块的数量以百为单位、链条最深不超过几十环——完整结构当 key 造成的内存开销完全可以忽略，换来的是不用操心哈希函数选型、不用操心碰撞概率这套额外的复杂度。真到了要缓存几十万个块的生产规模，内存开销就不再是可以忽略的量，必须换成固定长度的哈希摘要，且要选够长的哈希位数把碰撞概率压到可以忽略——这时候"哈希碰撞导致误判两个不同前缀相同"重新变成一个要认真考虑的风险，只是概率极低，跟 `## 2.3` 讲的"哈希函数选对了但结构错了、注定会撞"是两类完全不同性质的风险。

### 5.5 复用时要不要 incref

- **为什么这样**：`## 2.5`、`## 3.3` 已经讲过——一个物理块被跨请求共享之后，"什么时候可以安全释放"这件事不再由单条请求决定，必须靠引用计数知道究竟还有几个持有者。`match` 里的这一次 `incref`（`_lab/engine.py:72`）是让"复用"这个动作在账面上被记录下来的唯一方式。
- **不这样会怎样**：`## 2.5` 已经具体推演过整个过程——原持有者结束时把块交还，复用方还在用，块被分配器发给不相关的第三方，复用方读到别人写的数据，答案跟着错。这条错误不会抛异常，只会在特定的请求到达顺序、特定的调度时机下才会出现，几乎不可能靠简单重跑复现。
- **什么时候可以不这样**：如果引擎从设计上就保证一个物理块永远只被一条请求独占、绝不共享（也就是压根不做前缀缓存），那当然不需要引用计数——`[[03-分页KV与块管理]]` 里最初那个朴素的分配器就是这样。一旦决定要做跨请求共享（本篇的前提），引用计数就不是可选项。

### 5.6 全部命中时要不要回退一个块

- **为什么这样**：`## 2.6` 证明过 logits 从来不是 K/V 缓存的一部分，全部命中意味着没有任何位置真正跑过前向，拿不到可用的 logits，必须至少让一个块重新走一遍真实前向。
- **不这样会怎样**：要么直接崩溃（没有 logits 可以拿来做 argmax，代码层面很可能是一个空数组或者形状不对的索引错误），要么更危险——工程实现里如果没处理好，可能会用某个凑巧存在的、语义不对的值顶上去（比如错拿了 K 而不是 logits），那就是另一种静默错误。
- **什么时候可以不这样**：如果这条请求根本不需要生成任何新 token——比如只是拿它的 prompt 去做一次打分或者算一次困惑度（回顾 `[[03-KV缓存的第一性原理]]` `## 5.1` 提过的这类场景），那么"全部命中之后能不能继续 decode"根本不是这条请求关心的问题，回退这个块换来的"能拿到最后一个 logits"这份收益，对它来说是不需要的开销。

### 5.7 什么时候前缀缓存是负收益

- **为什么这样**（要算清楚这笔账）：前缀缓存不是免费的开关——每条请求进来都要算一遍块哈希（`## 2.3`，哈希本身要走一遍全部块）、查一遍表（`match`）、结束时登记一遍（`store`），这些都是额外的 CPU 开销；被缓存表登记过的块还会一直被引用计数占着，`## 2.5` 讲过这意味着"这些块暂时不能被分配给别的请求"，物理块池里可用的块变少了。
- **不这样会怎样**：如果开着前缀缓存，但请求之间根本没有共享前缀，`match` 每次都在第一块就 `break`（`_lab/engine.py:69-70`），`store` 每次都在登记全新的哈希——花了哈希计算和查表的开销，却一次命中都没拿到，`## 1` 表格里"命中块"那一列会一直是 0，`prefill_tokens` 跟关掉时相比不会有任何减少，纯粹是净亏。
- **什么时候可以不这样**：`## 5.1` 已经点过这条——请求之间前缀重合度本来就低的场景，直接关掉前缀缓存（`_lab/engine.py:114` 的 `enable_prefix_cache=False`）比开着更划算。判断依据不是"理论上有没有共享前缀的可能"，是"实际流量里命中率有多高"——`## 1` 结尾提到 `hits / lookups` 这个比值才是真正该看的数字，但 `run()` 目前只把 `hits`（`_lab/engine.py:211` 的 `prefix_hits`）透出到统计里，`lookups` 得像 `## 1` 那样自己去读 `e.prefix.lookups`。这是本库教学代码留下的一个小接口缺口：真要在生产里做"要不要开前缀缓存"这个决策，命中率应该是一等公民的监控指标，不该需要读私有字段才能拿到。

### 5.8 要不要实现淘汰策略

- **为什么这样**（本库选择不做）：`## 2.7` 讲过，教学库这一步要讲透的是"跨请求共享要保证正确"这条主线——`## 2.3` 的链式哈希、`## 2.5` 的引用计数、`## 2.6` 的全命中回退，这几件事本身已经有足够多细节需要一次讲清楚。淘汰策略是完全独立的一套复杂度：按什么顺序淘汰、淘汰时要不要通知还指着这个块的请求、`decref` 到 0 和"真正被回收"之间要不要留一个缓冲状态——这些问题的答案不影响"共享对不对"，只影响"共享的收益能维持多久"，放进同一篇会稀释掉最重要的那条论证。
- **不这样会怎样**：`## 2.7` 已经具体讲过——物理块池的容量随着遇到过的不同前缀数量单调收缩，长时间运行、前缀多样性持续增长的服务最终会把可用块耗尽，新请求卡在 `_admit` 的 `MemoryError` 分支里反复重试却拿不到块，而且没有任何异常或日志直接指向根源。
- **什么时候可以不这样**：能够预先估计"不同前缀的数量上限不会超过块池容量"的场景——比如 `## 1` 那种跑几步就结束的演示、或者 pytest 里跑几个 tiny 配置的测试——完全不需要淘汰策略，`_lab` 现在的状态就是为这类场景准备的。一旦请求会持续不断地到达、且前缀的多样性没有一个能提前保证的上限（真实生产服务基本都是这种情况），就必须像 `## 4.3` 讲的 vLLM `FreeKVCacheBlockQueue`、SGLang 的 `evictable_size_` / `protected_size_` 那样，在"引用计数归零"和"块被真正回收"之间插入一层按某种策略排队的中间状态，不能再指望"反正永远不会真的归零"这个偷懒的前提。

## 6. 常见错误与踩坑

前缀缓存是本库到目前为止**最容易写出静默 bug 的一步**——不是因为逻辑本身有多绕，是因为"跨请求共享内存"这件事，出错时表现出来的样子跟"写对了"几乎一模一样：程序照常跑完、不报任何异常、生成出来的文本读起来往往还很通顺，只是**内容是错的**。下面五条错误，每一条都点出"错了会看到什么现象"，而不只是"要写对"。

### 6.1 非链式哈希

`## 2.3` 已经用真实数字把这条错误从头到尾走了一遍：`layer1` 上同样内容的块（token 都是 `(5,6)`），历史不同（`(50,51)` vs `(1,2)`）算出来的 K 差了 `max|diff| = 1.53`；接进生成之后，前 5 步 argmax 恰好没被冲开，第 6 步彻底翻转成一个不同的 token，全程没有任何异常。**这是这份清单里最重要的一条**，也是唯一一条本篇专门做了完整数值实验去证明的错误——因为它是最容易写、最不容易在代码审查里被发现的一种错法：`hash(本块token)` 这行代码本身完全不会引起任何人怀疑，形状对、类型对、跑起来也不报错，问题只有真的去比较跨请求的 K/V 数值才能看出来。

### 6.2 忘了 incref

`## 2.5` 已经推演过完整过程：块 X 被请求 B 通过前缀缓存复用，但 `match` 里没有对它 `incref`；请求 A（块 X 原本唯一的持有者）结束时 `decref`，引用计数从 1 掉到 0，块 X 被判定为"没人用了"、还给空闲池；空闲池随后把块 X 分配给不相关的请求 C，C 往里写自己的 K/V；B 下一步做 attention，读到的已经是 C 写的数据。这类错误的典型现象是：**单独跑某一条请求完全正常，只有在特定的并发/调度时序下才会出错**——因为 bug 依赖"另一个持有者恰好在这个时间点释放了这个块"这个条件，孤立地重跑一条请求根本触发不了它，`selftest` 里第 5 条断言（`_lab/engine.py:276-283`，"全部结束后块必须归零"）这类"总量对不对"的检查也未必能抓住它——总量最终可能是对的（块最后确实都还回去了），错的是过程中某一步读到了不该读到的数据。

### 6.3 把不满的块也缓存了

`## 2.4` 讲过理由：不满的块内容还会变。如果 `block_hashes`（`_lab/engine.py:51-58`）的循环范围改成把最后一段不满 `block_size` 的尾巴也算进去、登记进缓存表，会出现两种现象：一种是这条请求后续确实还往这个块里追加了新 token（块被写满或者继续往下一个块写），这时候表里登记的哈希对应的是这个块"半成品"时的内容，跟它最终定型之后的真实内容对不上——如果后来有另一条请求恰好命中了这个过时的哈希，拿到的物理块内容跟哈希本该代表的内容已经不一致；另一种更直接：这个物理块可能因为这条请求最终没有走到那么长，从来没有真正写满过，缓存表里那条哈希记录却一直挂着，指向一个内容不完整、甚至后续被分配器回收挪作他用的块——变成一条悬空的记录。

### 6.4 全部命中时没有回退

`## 2.6` 证明过：logits 不是 K/V 缓存的一部分，全部命中意味着没有任何位置真正跑过前向。如果 `_admit`（`_lab/engine.py:152-188`）漏掉 `## 3.2` 讲的回退逻辑（`_lab/engine.py:168-175`），`todo` 会是一个空列表，`self._forward(req, todo)`（`_lab/engine.py:176-177`）在 `T = len(new_tokens)` 处会拿到 `T = 0`——后续 `causal = np.triu(np.full((T, T), ...))` 会算出一个形状是 `(0, 0)` 的矩阵，矩阵乘和 softmax 在空矩阵上通常不会报错、只会返回一个同样是空的结果，`x[-1]` 这一步（取最后一个位置的 logits）会在空数组上触发一个明确的索引越界异常——这算是本篇讲的错误里少数几个**会真的报错、不会静默**的一种，唯一的坏消息是这个异常离真正的病因（忘了处理全部命中这个边界情况）隔着好几层调用，排查起来不会一眼看出问题出在"忘了回退"这四个字上。

### 6.5 `store` 的时机早于 `_forward` 真正写完

`## 3.2` 结尾讲过正确顺序：`_lab/engine.py:186` 的 `self.prefix.store(req.prompt, req.tab)` 一定发生在 `_forward` 真正把 K/V 写进物理块之后。如果为了"尽早让后面的请求也能复用"这样一个听起来合理的理由，把 `store` 挪到 `_forward` 之前调用，会出现的现象是：另一条请求这时候查表命中了这个还没被真正写完的块，立刻拿去做 attention，读到的要么是分配时初始化的全零数据，要么是这块物理内存上一任持有者留下的旧内容——这跟 `## 6.1` 的现象很像（读到"看起来正常、实际不对"的 K/V），但根源完全不同：`## 6.1` 是哈希算法本身的逻辑错误，这一条是**执行顺序**的错误，代码逻辑本身可能一处都没写错，只是两件必须有先后关系的事被摆反了。本库目前是单线程模拟，`_admit` 一次只处理一条请求、不存在真正的竞态，这条错误现在不会被触发——但只要未来往流水线化、真正并发的方向改（比如把 prefill 和别的请求的 decode 重叠执行），这个顺序假设就必须被显式地保证下来，不能只靠"目前代码碰巧是这么写的"。
