# 连续批处理

> **一句话**：把"攒一批等全部跑完"改成"每一步都重新决定这一步跑谁"。
> **前置**：[[03-分页KV与块管理]]（本篇假定 KV 已经能按块动态申请/归还，只解决"这些块该在哪些请求之间、按什么节奏调度"这一层）

## 0. 这一篇要解决什么问题

`02-自回归解码为什么是访存瓶颈.md` 已经算过一条硬结论：decode 阶段 `batch=1` 时算术强度恒卡在 `0.5`（fp32），**唯一能把它抬起来的杠杆是加大 batch**。那篇文章证明了"批处理值得做"，但它悄悄假设了一件事——"凑出一个 batch"这件事本身是免费的、瞬时的。真实服务场景里它一点都不免费：请求不是同时到达的，输出长度也不是提前知道的（`06-采样-停止条件-流式输出.md` 会展开讲"提前知道"为什么几乎不可能），你不可能像 `_lab/minigpt.py` 的 `generate()` 那样，攒够 N 条请求、对齐好张量形状再一次性喂进模型。

朴素的应对是**静态批处理（static batching）**："攒一批 → 一起跑到全部结束 → 再攒下一批"——这是"能跑单条请求"往前一步最自然的延伸：既然一条能喂进模型，攒几条一起喂不就行了？`_lab/minigpt.py` 到 `_lab/paged.py` 为止，讲的都是"一条请求内部怎么正确、怎么省显存"，从没有出现过"多条请求同时活着、此消彼长"这件事。本篇要引入的东西——`_lab/engine.py`——是本库第一次让多条请求真正互相看得见对方：它们抢同一批物理块、抢同一个 `max_running` 名额、在同一个 `step()` 里此起彼伏地进场和退场。

静态批处理有两个硬伤，`## 2` 会用一个能手算的例子把代价钉死：**最慢的那一条拖着所有人**（输出长度参差不齐时，浪费巨大）；**新请求必须等整批结束才能进来**（排队延迟随批次时长线性增长）。**连续批处理（continuous batching，vLLM 论文与文档里也写作 iteration-level scheduling）** 的解法是把调度粒度从"一批"降到"一步"——每一步都重新决定这一步跑哪些请求，谁结束了立刻让位，新来的立刻能挤进去。`_lab/engine.py` 的 `step()` 就是这套机制能跑、能测的最小版本。本篇顺序：先看它的可观测特征（`## 1`），再讲清楚为什么静态批不够、连续批把什么变成了什么（`## 2`），然后逐行走读代码（`## 3`），最后对照真实引擎、讲设计取舍与踩坑（`## 4`~`## 6`）。

## 1. 先看现象

进入 `_lab/` 目录跑一遍自检：

```bash
cd _lab
python engine.py --selftest
```

输出：

```
selftest: PASS
```

这个 `PASS` 背后压着 6 条断言（`_lab/engine.py:217-294`），其中第 4 条是本篇的题眼——**短请求必须先于长请求结束，不必等长请求跑完**：

```python
# _lab/engine.py:268-274
e = Engine(cfg, w, n_blocks=512, block_size=4, max_running=4)
short, long_ = Request(1, p1, 2), Request(2, p2, 12)
e.add(short); e.add(long_)
e.run()
if not (short.done < long_.done):
    print(f"FAIL 短请求应先结束：short={short.done} long={long_.done}"); ok = False
```

这条断言的镜像版本也在 pytest 里（`_lab/tests/test_lab.py:228-235` 的 `test_short_request_finishes_before_long_one`）。**这正是连续批处理的可观测特征**：如果引擎是静态批处理，`short.done` 和 `long_.done` 永远相等（两条请求同一批进、同一批出）；只要观察到 `short.done < long_.done`，就说明调度粒度已经细到了"步"这一级。

亲手放大这个现象，看看数字长什么样。用一段能直接复制运行的脚本，构造 4 条请求，输出长度分别是 10、10、10、100：

```bash
cd _lab
python -c "
import minigpt as M
from minigpt import Config
from engine import Engine, Request

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=256, seed=1)
w = M.init_weights(cfg)
prompt = [3, 14, 15, 62, 6, 35, 8, 9]

e = Engine(cfg, w, n_blocks=512, block_size=4, max_running=4, enable_prefix_cache=False)
reqs = [Request(i, prompt, n) for i, n in enumerate([10, 10, 10, 100])]
for r in reqs:
    e.add(r)
e.run()
for r in reqs:
    print(f'req {r.rid}: max_new={r.max_new:3d}  start={r.start:3d}  done={r.done:3d}')
"
```

这个 numpy 玩具引擎在 CPU 上的实测输出（不可外推到真实引擎，只说明这套调度逻辑本身的行为）：

```
req 0: max_new= 10  start=  0  done=  8
req 1: max_new= 10  start=  0  done=  8
req 2: max_new= 10  start=  0  done=  8
req 3: max_new=100  start=  0  done= 98
```

三条输出长度 10 的请求在第 8 步就结束了，第四条要跑到第 98 步。（`done` 不精确等于 `max_new - 2` 这件事本身也值得记住：`_admit()` 在准入那一步会顺带产出第一个 token，紧接着 `step()` 的推进循环在同一步里又追加一个，所以每条请求在"进场"那一步就已经拿到 2 个 token，`## 3` 会逐行讲这是怎么发生的。）关键不是这个具体数字，而是**三条短请求确实在第 98 步之前就已经把结果交出去了**——如果这是静态批处理，四条请求会被绑在一起等到第 98 步才能一起返回。`## 2` 把这件事的代价用干净的数字算一遍。

## 2. 原理

### 2.1 静态批处理的两宗罪，用手能算出来

先把"静态批处理"的行为公式化：攒 `B` 条请求为一批，一起跑，直到批内**最长**的那条完成，批才算结束、才能把结果交给调用方、才能开始攒下一批。设批内第 `i` 条请求输出长度为 `n_i`，理想化地假设"生成一个 token 花一步"（`_lab/engine.py` 的实现在这个理想模型上有一个小常数偏移，`## 1` 已经指出，不影响这里的定性结论），批完成需要的步数是：

```
T_static = max(n_1, ..., n_B)
```

**每一条**请求的结果都只能在 `T_static` 这一步之后拿到——哪怕它自己只需要 10 步就写完了。批内平均延迟：

```
avg_latency_static = T_static = max(n_1, ..., n_B)
```

连续批处理让每条请求跑够自己的 `n_i` 步就退场：

```
avg_latency_continuous = (n_1 + n_2 + ... + n_B) / B
```

代入 `## 1` 那组数字（`n = 10, 10, 10, 100`）：

```
静态：avg_latency_static      = max(10,10,10,100)        = 100
连续：avg_latency_continuous  = (10+10+10+100) / 4        = 32.5
```

**同一批请求，连续批处理把平均延迟从 100 步压到 32.5 步，压缩了 67.5%**——纯粹来自"让写完的请求提前离场"，模型本身、算力本身一点没变。这是第一宗罪的代价：**最慢的那条拖着所有人**，具体拖多少，取决于批内输出长度的方差有多大（如果四条都是 10，两种调度完全没区别——这条留到 `## 5` 展开讲"什么时候连续批处理没有收益"）。

第二宗罪更狠，因为它不是"批内"的账，是"批间"的账。设想第 5 条请求 `E`（输出长度 5）在第 1 步就已经提交，此时上面 4 条请求刚开始跑、名额已满：

- **静态批处理**：`E` 必须等当前这批（第 100 步才结束）彻底跑完才能开始，跑完自己的 5 步，绝对完成时刻是 `100 + 5 = 105`。
- **连续批处理**：第 8 步（`## 1` 的实测数字）三条短请求已经让出名额，`E` 立刻被放进来，跑完自己的 5 步，绝对完成时刻是 `8 + 5 = 13`。

**同一条新请求，排队延迟从 105 压到 13，是 8 倍以上的差距**——而且这个差距会随着"批里混进一条特别长的请求"而无限放大：批处理是照顾了"平均吞吐"，但静态批处理把"平均吞吐"建立在了"所有新请求都要给最慢的那条陪绑"这个代价上。**连续批处理的贡献，本质上是把"排队延迟"这个变量，从"取决于当前批里最慢的那条"，改成了"取决于什么时候有名额空出来"**——这正是 `## 0` 说的"调度粒度从批降到步"在数字上的样子。

这条结论反过来也告诉你它什么时候不成立。把 `## 2.1` 开头那组数字换成四条**输出长度全部相同**的请求（`n = 10, 10, 10, 10`）再算一遍：

```
静态：avg_latency_static     = max(10,10,10,10)          = 10
连续：avg_latency_continuous = (10+10+10+10) / 4          = 10
```

两个数字完全相等——**批内输出长度没有方差时，静态批处理的"陪绑代价"本来就是 0，连续批处理无从优化起**。`## 5` 决策四会把这条和"离线批量、提前到齐"这个条件放在一起，正式定成"什么时候可以直接不上连续批处理"。

### 2.2 把"批"从张量维度，搬到调度决策

静态批处理和连续批处理，在模型这一层用的是**同一个矩阵乘**——`## 2.1` 算的收益跟模型内部结构毫无关系，纯粹是"什么时候把结果交出去、什么时候放新请求进来"这个调度决策的产物。这也解释了为什么连续批处理不需要发明新算子：`_lab/engine.py:128-150` 的 `_forward()` 和 `_lab/paged.py:216-246` 的 `_forward_paged()` 几乎是同一段代码（`_lab/engine.py` 走的正是分页路径），批处理的全部机关都在"怎么决定这一步喂给它们的 `new_tokens` 是谁"这一层，不在前向计算本身。

回到 `02-自回归解码为什么是访存瓶颈.md` 的算术强度表——`## 2.1` 证明了"凑批"本身省下的是排队延迟，而"凑出来的批到底能把算术强度抬多高"，答案已经写在那张表里：批越大，权重侧的访存被摊得越薄。但表里还有一条容易被本篇的调度视角掩盖的结论：**ctx 越长，同样的 batch 能抬起的强度越少**（ctx=16 时 `bs=1→256` 能把强度从 0.50 抬到 21.74，ctx=16384 时同样的批量只能抬到 0.53）。这意味着**连续批处理调度得再聪明，也只能把请求尽量凑满调度器允许的名额**——它决定的是"batch 维度能不能撑起来"，撑起来之后这个 batch 到底值多少算术强度收益，是模型结构（尤其是 ctx 长度）说了算，调度层管不了。`## 5` 会把这条并进"什么时候连续批处理没有收益"的讨论里。

### 2.3 静态批处理不是稻草人，是"把 `generate()` 简单地扩成多条"的必然结果

容易把静态批处理当成一个专门用来批判的稻草人，但它是本库前面代码路径最直接的延伸。`_lab/minigpt.py:178-192` 的 `generate()` 每次只服务一条请求，如果只是把它的输入张量在最外面加一维、塞进 `B` 条 prompt 一起跑（`forward_cached` 本身对"新增了几个位置"并不敏感，`03-KV缓存的第一性原理.md` 已经证明过这一点），得到的**正是**静态批处理：所有请求共享同一个 `for _ in range(n_new)` 循环，循环次数取的是 `max(n_new for 各条请求)`，跑得快的请求只能干等着循环转完。**`_lab/engine.py` 的 `Engine` 不是给静态批处理"加了一层调度"，而是把这个 `for` 循环本身换掉**——用 `waiting`/`running` 两个集合和逐步判定的 `finished` 取代了"循环次数由批内最长请求决定"这条硬编码规则，`## 3` 接下来要走读的就是这个替换具体长什么样。

## 3. 自己动手：`_lab/` 里对应的实现

`_lab/engine.py` 的 `Engine` 类（`_lab/engine.py:101-111`）文档字符串把 `step()` 要做的三件事写得很直白：**准入**（在预算允许的前提下把等待队列里的请求放进来）、**推进**（让所有在跑的请求各出一个 token）、**回收**（结束的请求释放块、腾出位置）。逐块看这三件事怎么落到代码里。

### 3.1 一条请求：`Request` 与"结束"的定义

`Request`（`_lab/engine.py:86-98`）的字段不多：`prompt`、`max_new`、已经生成的 `out`、指向分页 KV 的 `tab`、以及 `start`/`done` 这两个记账用的步号——`## 1` 打印的 `start`/`done` 就是从这两个字段读出来的。`finished` 是个属性（`_lab/engine.py:96-98`）：

```python
@property
def finished(self) -> bool:
    return len(self.out) >= self.max_new
```

**"结束"这件事完全是每条请求自己的私有状态**，不依赖它是不是在某个"批"里、批里还有没有别的请求活着——这一句定义就是连续批处理能成立的地基：如果"结束"要靠"批里所有人都结束"来定义，`short.done < long_.done` 这个断言根本无从谈起。

### 3.2 准入：`_admit()` 在多个约束下往里塞请求

`_admit()`（`_lab/engine.py:152-188`）是本篇除了 `step()` 之外最重要的函数。外层循环的守卫条件：

```python
# _lab/engine.py:153
while self.waiting and len(self.running) < self.max_running:
```

**两个条件缺一不可**：队列里还有人排队，且当前 `running` 还没到 `max_running` 这个硬上限。`max_running` 是构造 `Engine` 时传入的参数（`_lab/engine.py:113-114`），教学上刻意做成显式参数——真实引擎里这个数字要么由显存/块数反推、要么由服务方直接配置，本库不替你决定，让你自己传。

拿到队首请求后（`_lab/engine.py:154`，注意是 `self.waiting[0]`，严格 FIFO，不是挑一个"最容易塞进去"的），先尝试前缀缓存复用（`_lab/engine.py:159-165`，命中多少算多少，完整机制留给 `[[05-前缀缓存]]`），算出真正需要重新计算的 `todo`（`_lab/engine.py:167-175`），然后是本节的关键：

```python
# _lab/engine.py:176-180
try:
    logits = self._forward(req, todo)
except MemoryError:
    req.tab.free()
    return                              # 块不够，这一步先不放它进来
```

`self._forward()` 内部会经由 `SeqTable.begin()` → `_ensure()`（`_lab/paged.py:89-93`）向 `BlockAllocator.alloc()`（`_lab/paged.py:35-40`）要块，块不够时 `alloc()` 直接 `raise MemoryError`（`_lab/paged.py:37`）。**这里的 `except` 接住了它，而且是优雅地接住**：先把这条请求已经占用的部分块退回去（`req.tab.free()`），再 `return`——**这是 `return`，不是 `continue`**：一旦队首请求装不下，`_admit()` 当场放弃这一步的全部准入，哪怕队列后面排着一条明明能塞进剩余空间的小请求，也不会被看到。`## 5`、`## 6` 会分别从"为什么这样设计"和"会看到什么现象"两个角度回来讲这个 `return`。

装下之后（`_lab/engine.py:181-188`）：记下第一个 token（`req.out.append(...)`）、标记 `prefilled = True`、记录 `req.start = self.step_id`、把请求从 `waiting` 挪进 `running`。**注意 `req.start` 记的是准入这一步的 `step_id`，不是请求被 `add()` 进队列的时刻**——`Request.arrive` 字段（`_lab/engine.py:88`）虽然存在，但当前调度逻辑完全没有读它，`_admit()` 只认 FIFO 顺序和资源够不够，这个留给 `06-采样-停止条件-流式输出.md` 或未来扩展去用。

亲手验证 `max_running` 这道闸门的效果——3 条请求，`max_running=2`，第 3 条注定要排队：

```bash
cd _lab
python -c "
import minigpt as M
from minigpt import Config

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=256, seed=1)
w = M.init_weights(cfg)
prompt = [3, 14, 15, 62, 6, 35, 8, 9]

e = Engine(cfg, w, n_blocks=512, block_size=4, max_running=2, enable_prefix_cache=False)
reqs = [Request(0, prompt, 3), Request(1, prompt, 3), Request(2, prompt, 2)]
for r in reqs:
    e.add(r)
e.run()
for r in reqs:
    print(f'req {r.rid}: max_new={r.max_new}  start={r.start}  done={r.done}')
"
```

实测输出：

```
req 0: max_new=3  start=0  done=1
req 1: max_new=3  start=0  done=1
req 2: max_new=2  start=2  done=2
```

`req0`、`req1` 第 0 步就进场（`max_running=2` 刚好够两个名额），`req2` 一直在 `waiting` 里等，直到第 2 步——也就是 `req0`/`req1` 结束、名额腾出来的那一步——才被 `_admit()` 挑中。**`start=2` 这个数字就是 `_admit()` 这道闸门产生的排队延迟**，跟 `## 2.1` 手算的"新请求要等名额"是同一件事的最小复现。

### 3.3 head-of-line blocking：FIFO 的代价，眼见为实

`## 3.2` 提到 `_admit()` 遇到装不下就整体 `return`，不会跳过去看队列后面的请求。构造一个场景让这件事的代价可见：`n_blocks=2`、`block_size=16`（池容量 32 token），三条请求——`reqA` 占 1 块、能活好几步；`reqB` 需要 2 块，只要 `reqA` 还活着，`reqB` 永远装不下；`reqC` 只需要 1 块，`reqA` 存活期间池子里明明还空着 1 块，`reqC` 本该能进：

```bash
cd _lab
python -c "
import minigpt as M
from minigpt import Config
from engine import Engine, Request

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=256, seed=1)
w = M.init_weights(cfg)

e = Engine(cfg, w, n_blocks=2, block_size=16, max_running=8, enable_prefix_cache=False)
reqA = Request(0, list(range(10)), 5)
reqB = Request(1, list(range(20)), 2)
reqC = Request(2, list(range(5)), 2)
e.add(reqA); e.add(reqB); e.add(reqC)
for step in range(6):
    e.step()
    print('step=%d running=%s waiting=%s blocks_used=%d/2' %
          (step, [r.rid for r in e.running], [r.rid for r in e.waiting], e.pool.alloc.n_used))
for r in (reqA, reqB, reqC):
    print('req %d: start=%s done=%s' % (r.rid, r.start, r.done))
"
```

实测输出：

```
step=0 running=[0] waiting=[1, 2] blocks_used=1/2
step=1 running=[0] waiting=[1, 2] blocks_used=1/2
step=2 running=[0] waiting=[1, 2] blocks_used=1/2
step=3 running=[]  waiting=[1, 2] blocks_used=0/2
step=4 running=[]  waiting=[2]    blocks_used=0/2
step=5 running=[]  waiting=[]     blocks_used=0/2
req 0: start=0 done=3
req 1: start=4 done=4
req 2: start=5 done=5
```

第 0~2 步，池子里明明有 1 个空块，`reqC` 却纹丝不动地待在 `waiting` 里——因为队首是 `reqB`，`reqB` 需要 2 块而只有 1 块空闲，`_admit()` 在 `reqB` 这里就 `return` 了，`reqC` 连被看一眼的机会都没有。直到第 3 步 `reqA` 结束、两块全部归还，第 4 步 `reqB` 才终于挤进去（顺带在同一步结束），第 5 步 `reqC` 才轮到自己——**比它"本该能进"的第 0 步晚了整整 5 步**。这就是 `## 3.2` 那个 `return` 的具体代价，`## 5` 会讲清楚为什么这个代价被认为是值得付的。

### 3.4 推进与回收：`step()` 的后两件事

回到 `step()`（`_lab/engine.py:190-203`）本身，三件事对应三段代码：

```python
# _lab/engine.py:190-203
def step(self) -> None:
    self._admit()                                        # 1. 准入
    for req in list(self.running):                        # 2. 推进
        if req.finished:
            continue
        logits = self._forward(req, [req.out[-1]])
        req.out.append(int(logits.argmax()))
        self.stats["decode_steps"] += 1
    for req in list(self.running):                        # 3. 回收
        if req.finished:
            req.done = self.step_id
            req.tab.free()
            self.running.remove(req)
    self.step_id += 1
```

**推进循环**（`_lab/engine.py:192-197`）对 `self.running` 里每条未结束的请求各调用一次 `_forward()`，只喂它自己最后生成的那个 token（`[req.out[-1]]`）——这正是 `03-KV缓存的第一性原理.md` 讲过的"decode 阶段 `T=1`"那个工作点，`## 2` 的算术强度账就是在这个循环隐含的 batch 维度上打的：`self.running` 里同时有几条请求，这一步的有效 batch 就是几。**推进循环遍历用的是 `list(self.running)` 的快照，不是 `self.running` 本身**——这是必须的：如果直接遍历 `self.running` 同时在下一段回收循环里 `remove()`，边遍历边改列表会跳过元素或抛异常，这也是 `## 6` 值得单独记一笔的坑。

**回收循环**（`_lab/engine.py:198-202`）单独起一个循环、放在推进循环**之后**，而不是"发现 `finished` 就立刻在推进循环里回收"，原因是**这一步刚推进完的请求，即便已经满足 `finished`，这一步的 token 也已经产出、该被记入 `decode_steps` 统计、该被视为"活到了这一步"**——`req.done = self.step_id` 记的是"这一步结束时它已完成"，如果把回收提前到推进循环内部，逻辑上没有错，但会让"这一步到底跑了几条请求"这个统计和 `_admit()` 下一步能看到的 `len(self.running)` 产生时序上的歧义，两个循环分开写是为了让每一步的"准入用的容量快照"是确定的。

`run()`（`_lab/engine.py:205-212`）只是把 `step()` 循环到队列清空：`while (self.waiting or self.running) and self.step_id < max_steps`。**没有队列清空就不停**——这也是为什么 `## 1` 的实测里，四条请求哪怕三条早早结束，`run()` 依然要把 `step_id` 转到 98：**只要还有一条请求活着，引擎就不能收工**，这是"连续"批处理这个名字里"连续"的字面意思。

### 3.5 正确性：为什么批处理"不改变输出"是需要专门验证的命题

`selftest()`（`_lab/engine.py:217-294`）第 1 条断言（`_lab/engine.py:237-248`）测的是本篇最重要的正确性命题：

```python
# _lab/engine.py:237-248（节选）
for use_pc in (False, True):
    e = Engine(cfg, w, n_blocks=256, block_size=4, max_running=4,
               enable_prefix_cache=use_pc)
    r1, r2 = Request(1, p1, 6), Request(2, p2, 6)
    e.add(r1); e.add(r2)
    e.run()
    if r1.out != want1 or r2.out != want2:
        print(f"FAIL 批处理改变了输出 ...")
```

`want1`/`want2` 是完全不经过 `Engine`、直接调朴素前向 `M.forward_naive`（`_lab/engine.py:226-233`）单独生成出来的参照序列。这条断言（连同 pytest 里参数化两遍前缀缓存开关的 `test_batching_preserves_per_request_output`，`_lab/tests/test_lab.py:186-199`）验证的是：**同一条请求，跟别的请求同批跑 vs 自己单独跑，输出必须一模一样**。

这条命题**极容易被破坏，而且破坏之后不会有任何报错**——`_PLAN.md` §1 第 1 条讲过的"推理引擎的 bug 绝大多数是静默的"，在多请求场景下体现得最明显，因为多出了三条全新的出错路径（`## 6` 会详细展开每一条"错了会看到什么现象"）：**请求之间串了 KV**（A 的注意力算的时候读到了 B 的历史）、**位置编码算错**（`p0`——`_lab/engine.py:132` 的 `tab.length`——本该是这条请求自己的已提交长度，如果偷懒用了全局的 `step_id` 或者别条请求的长度去切 `wpe`，形状照样对得上，不会报错）、**共享的块被提前释放**（`## 3.2` 见过 `PrefixCache` 复用块时要 `incref`，`_lab/engine.py:72`；一条请求 `tab.free()` 时对应 `decref`——`_lab/paged.py:136-140`——如果引用计数记错，物理块可能在还有人用的时候被还回空闲池，被下一条请求写脏）。

`_lab/tests/test_lab.py:238-245` 的 `test_no_block_leak_across_many_requests` 补上另一半：6 条请求轮番进出、`max_running=2` 强制反复挤占，跑完之后 `e.pool.alloc.n_used` 必须精确归零——**块表泄漏和块表串号是一体两面**：一个是"该收回的没收回"，一个是"不该给的给出去了"，这两条断言一起才把 `_admit()`/`step()` 的引用计数和 FIFO 逻辑捂严实。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang，带 `引擎:文件:行`）

`## 3.4` 把 `step()` 归纳成"准入、推进、回收"三件事，这不是本库自己发明的划分——真实调度器的主循环骨架是同一件事，只是每一步里塞进去的细节多得多。

**vLLM**：调度逻辑集中在一个函数里——`schedule()`（`vllm:vllm/v1/core/sched/scheduler.py:484`）。它的文档注释在 `## 3.4`"推进就是喂 `T=1`"这条结论之上，直接把"prefill/decode 不是两个阶段"钉成了实现原则：调度器眼里只有 `num_computed_tokens`（已经算过多少）要追上 `num_tokens_with_spec`（该算到多少）这一件事（`vllm:vllm/v1/core/sched/scheduler.py:486-495`）——这正是 `## 3.4` 里"推进循环无非是再调用一次 `_forward`，只是这次 `T=1`"这句话在生产代码里的样子，`_lab/engine.py` 的 `_admit()` 走的是"整段 `todo`"（`T` 可能很大）、推进走的是"单 token"（`T=1`），两条路径共用同一个 `_forward()`（`_lab/engine.py:128-150`），跟 vLLM 这条设计原则是同一个思路。

调度器每一步维护一个**跨请求共享的 token 预算**：

```python
# vllm:vllm/v1/core/sched/scheduler.py:504（节选）
token_budget = self.max_num_scheduled_tokens
```

`_lab/engine.py` 的 `_admit()` 用的是"请求数"（`max_running`）当预算，vLLM 用的是"token 数"（`token_budget`）——**这个差别正对应 `## 2.2` 讲的"batch 维度到底怎么撑起来"**：token 预算天然能把"一条请求的一大段 prefill"和"很多条请求各自的一个 decode token"揉进同一个预算里统一分配（`vllm:vllm/v1/core/sched/scheduler.py:533-536` 先扫一遍 `self.running`，逐条按预算切出 `num_new_tokens`），而 `_lab/engine.py` 为了让代码保持教学可读，选择了更粗粒度的"按请求数"卡位，代价是没法精细控制"这一步到底喂进模型多少 token"，`## 5` 会把这条差异算进决策里。

vLLM 还专门处理了 `_lab/engine.py` 完全没碰的一个问题——**一条请求如果一次要塞进的新 token 太多（典型情况是一条很长 prompt 的 prefill），会被显式截断，不允许一次吃光整份预算**：

```python
# vllm:vllm/v1/core/sched/scheduler.py:571-575（节选）
if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = self.scheduler_config.long_prefill_token_threshold
num_new_tokens = min(
    num_new_tokens, token_budget, input_budget - draft_slots
)
```

这就是**分块预填充（chunked prefill）**：把一条长 prefill 拆成好几步喂，每步只吃一部分预算，剩下的预算留给同一步里其它请求的 decode——否则一条几千 token 的 prefill 会独占一整步，这一步里所有 decode（延迟敏感）都要陪它等。`## 0` 说过本库刻意不做这件事，这里能看到真实引擎为什么要做。

vLLM 的准入循环也有和 `## 3.2`/`## 3.3` 完全对应的一段，同样是"资源不够就不放行"，只是它多了一条 `_lab/engine.py` 没有的出路：

```python
# vllm:vllm/v1/core/sched/scheduler.py:759-766（节选）
while (self.waiting or self.skipped_waiting) and token_budget > 0:
    ...
    num_running = len(self.running) + self.num_waiting_for_streaming_input
    if num_running >= self.max_num_running_reqs:
        break
```

`max_num_running_reqs`（`vllm:vllm/v1/core/sched/scheduler.py:118`）就是 `_lab/engine.py` 的 `max_running`；这条 `break` 也和 `_lab/engine.py:176-180` 的 `return` 一样，是"资源不够、这一步先不放行"的意思。真正的差别在**已经在跑、后来又装不下的请求**怎么办：`_lab/engine.py` 的推进循环（`## 3.4`）对此毫无防备——`## 6` 会用一个真实崩溃的例子证明这一点；vLLM 对这种情况有专门的**抢占（preemption）**机制：

```python
# vllm:vllm/v1/core/sched/scheduler.py:1347-1366（节选）
def _preempt_request(self, request, timestamp, drop_stale_output=False) -> None:
    """Preempt a request and put it back to the waiting queue."""
    ...
    self._free_request_blocks(request)
    ...
    request.status = RequestStatus.PREEMPTED
    request.num_computed_tokens = 0
    ...
    # 函数末尾把它放回 waiting 队列（vllm:vllm/v1/core/sched/scheduler.py:1387 起）
```

抢占做的事是：挑一条已经在跑的请求，强制释放它的块、把它退回 `waiting` 队列、`num_computed_tokens` 清零（意味着它以后要重新 prefill）——用一条请求的进度换出显存，让别的请求能继续往前推进。**这正是 `_lab/engine.py:37`（`paged.py`）那句报错信息里写的"真实引擎在这里会触发抢占/回退"**：本库选择让它直接崩溃（`## 6` 会展示），vLLM 选择付出"重新 prefill 一条请求"的代价来换资源腾挪的空间。

**SGLang**：调度器的主循环写得更直白，一眼就能看出"准入-推进-回收"这三件事在事件循环里的样子：

```python
# sglang:python/sglang/srt/managers/scheduler.py:1748-1778（节选）
def event_loop_normal(self):
    while True:
        recv_reqs = self.request_receiver.recv_requests()
        self.process_input_requests(recv_reqs)          # 收新请求，进 waiting_queue
        plan = self.get_next_batch_to_run(
            running_batch=self.running_batch, last_batch=self.last_batch)
        self.running_batch = plan.running_batch          # 准入 + 推进：决定这一步跑谁
        batch = plan.batch_to_run
        if batch:
            result = self.run_batch(batch)                # 真正调一次前向
            self.process_batch_result(batch, result)       # 回收：写回输出、判断是否结束
        self.last_batch = batch
```

新请求先进 `self.waiting_queue`（`sglang:python/sglang/srt/managers/scheduler.py:1144`），`get_next_batch_to_run`（`sglang:python/sglang/srt/managers/scheduler.py:3080`）里会把上一步结束的请求从 `running_batch` 过滤掉（`sglang:python/sglang/srt/managers/scheduler.py:3164-3167` 的 `running_batch.filter_batch()`，对应 `## 3.4` 的回收循环），再从 `waiting_queue` 里挑新的 prefill 请求合并进来——**跟 `_lab/engine.py:190-203` 的 `step()` 是同一套骨架：收请求、决定这一步谁上、跑一次、把结束的摘出去**，只是 SGLang 把"这一步跑谁"这个决策（`get_next_batch_to_run` 里合并 prefill 批和 running 批的逻辑）和"实际调用模型"（`run_batch`）拆成了两个显式步骤，`_lab/engine.py` 为了代码量把它们揉在了 `step()` 一个函数里。

**本篇不做的三件事**：抢占（上面已经看到 vLLM 怎么做）、分块预填充（上面也看到了）、以及 SGLang 用 `event_loop_overlap`（`sglang:python/sglang/srt/managers/scheduler.py:1783`）实现的**overlap 调度**（CPU 侧准备下一步的调度决策和 GPU 侧跑当前这一步的前向计算重叠进行，互相不用等对方）。三样本库都刻意不实现——`_lab/engine.py:108-110` 的模块文档字符串已经明说了这一点：**教学库要的是把"准入-推进-回收"这条主干露出来，这三样都是主干之上的工程加固**，加了之后主干反而会被参数、状态机、异常分支淹没。它们分别解决的问题是"资源不够时已经在跑的请求怎么办""一条超大请求怎么不饿死同批的小请求""调度决策本身的开销怎么跟计算重叠掉"——`[[03-从玩具到生产还差什么]]` 会把这三样和其它被本库跳过的东西放在一起，讲清楚"从玩具到能上线，还差多少工程量"。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：把调度粒度从"批"降到"步"（连续批处理本身）。**
- 为什么这样：`## 2.1` 手算过，静态批处理的平均延迟等于批内最长请求的长度（本例 100），连续批处理等于批内平均长度（本例 32.5）；新请求的排队延迟差距更悬殊（105 对 13）。这两条差距的来源完全一致：**结束的请求不必等别人**。
- 不这样会怎样：退化成静态批处理——`## 2.1` 算过的代价照单全收，而且代价会随"批内输出长度方差"和"批的时长"同步放大，长文本生成场景（有的请求几十 token 就停，有的要写几千字）受害最深。
- 什么时候可以不这样：见决策四——输出长度同质、且是离线批量提交时，两种调度几乎等价，上连续批处理反而多付出每步调度的常数开销。

**决策二：用硬上限 `max_running` 卡住同时在跑的请求数，而不是"能塞多少塞多少"。**
- 为什么这样：每条 `running` 请求都要占物理块（显存）、每一步都要参与一次前向；不设上限，`_admit()` 会一直往里塞，直到某一步在 `_forward()` 内部因为块耗尽而失败——`## 3.2` 的 `_admit()` 至少还能优雅接住这个 `MemoryError`，但如果这个爆炸发生在已经进入 `running` 之后的推进阶段，`## 6` 会展示这会直接让整个 `run()` 崩溃退出，不会有任何优雅处理的机会。把上限提前到准入这一步显式卡死，是为了让"这一步最多同时服务多少条"这个决策可控、可预测。
- 不这样会怎样：轻则批越攒越大、每步墙钟时间跟着涨、个体延迟不降反升；重则如上所述，某条已经在跑的请求把池子挤爆，触发 `## 6` 的那种不可恢复崩溃。
- 什么时候可以不这样：吞吐优先、延迟完全不敏感的离线批量场景，可以把 `max_running` 设得很大（甚至等于队列长度），让准入完全由块预算说了算，不再需要一个独立的"请求数"上限；本库把它做成显式参数正是为了让"容量上限从哪来"这件事在教学上可见，而不是藏进一个自动扩缩容的黑盒。

**决策三：`_admit()` 严格按 FIFO 顺序，一旦队首装不下就整体放弃这一步的准入，不去看队列后面还有没有能塞进去的小请求。**
- 为什么这样：实现简单、且天然保序公平——请求永远按提交顺序被服务，不会出现"体积小的请求insert队"这种打乱到达顺序的行为；`_lab/engine.py:176-180` 的 `except MemoryError: req.tab.free(); return` 就是这条策略的全部代码，一行都不用维护"跳过了谁"的额外状态。
- 不这样会怎样：`## 3.3` 已经实测过代价——`reqC` 明明能塞进空出来的那块空间，却要陪着装不下的 `reqB` 一起在 `waiting` 里多等 5 步，这几步的块利用率是白白浪费的（1/2 块空着没人用）。
- 什么时候可以不这样：请求之间体积差异很大、且 `waiting` 队列经常很长时，跳过队首去找"能塞进当前空隙"的请求确实能把利用率抬起来——但这样做需要额外维护"这一步跳过了哪些请求"的状态，还要照顾公平性（不能让一条大请求永远被后面一串小请求插队饿死），复杂度上升不是免费的。`## 4` 里 vLLM 的调度器用 token 预算而不是请求数当门槛，某种程度上已经比严格 FIFO 更精细，但依然没有做"任意重排"这种更激进的优化——真实引擎在这条取舍上也是保守的。

**决策四：什么时候可以直接不上连续批处理。**
- 为什么这样：`## 2.1` 证明连续批处理的收益来自两个条件同时成立——**输出长度异质**（不然静态批处理的"陪绑"代价趋近于 0）**、在线到达**（不然"新请求排队"这件事根本不存在）。当一批任务提前全部到齐、且长度大致相近（比如批量跑一个定长的分类/打分任务，`03-KV缓存的第一性原理.md` §5.1 提到过这类"只需要单次前向"的场景就属于这一类的极端情况），静态批处理和连续批处理在总耗时和平均延迟上几乎没有差别，`_admit()`/`step()` 每一步的准入判断、回收扫描这些常数开销纯属净亏。
- 不这样会怎样：在同质、离线场景硬上连续批处理，多付出的调度开销换不来任何延迟或吞吐上的收益，代码复杂度却实打实地上升了（`Engine` 比 `_lab/minigpt.py` 的 `generate()` 循环多了一整套准入/回收/块管理）。
- 什么时候可以不这样（回到"什么时候必须用"）：在线服务、输出长度不可预知——这是几乎所有真实 LLM 应用的常态，这时候异质性和在线到达同时成立，`## 2.1` 的收益是结构性的。还要叠加 `## 2.2` 的结论：**长上下文场景下，调度调得再好，也调度不出模型结构本身没有的空间**——`02-自回归解码为什么是访存瓶颈.md` 那张表说 ctx=16384 时 batch 从 1 抬到 256 只能把强度从 0.50 抬到 0.53，此时即便连续批处理把 `running` 的名额撑到最满，能兑现的算术强度收益本身也已经很有限；这不是否定连续批处理，而是提醒它解决的是"排队/浪费"这个调度问题，不是"模型结构决定的强度上限"这个更底层的问题。

## 6. 常见错误与踩坑

**错误一：以为块耗尽在哪个阶段都会被优雅接住，实际上只有准入阶段有 `try/except`。**
`## 3.2` 看到的 `except MemoryError` 只包在 `_admit()` 里；`step()` 的推进循环（`_lab/engine.py:192-197`）对已经在 `running` 里的请求毫无防备。真实构造一次：

```bash
cd _lab
python -c "
import minigpt as M
from minigpt import Config
from engine import Engine, Request

cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=256, seed=1)
w = M.init_weights(cfg)
e = Engine(cfg, w, n_blocks=2, block_size=8, max_running=8, enable_prefix_cache=False)
req = Request(0, list(range(16)), 4)   # 16 token 的 prompt 已经吃满 2 个块的全部容量
e.add(req)
e.run()
"
```

**错了会看到什么现象**：不是安静地把这条请求晾在一边等下一轮，而是一条从 `_lab/paged.py:37` 一路上抛、经过 `_lab/engine.py:195` 的 `MemoryError` 直接把整个 `run()` 炸穿，进程带着 traceback 退出——`n_blocks=2`、`block_size=8` 给的池子容量刚好等于 prompt 长度，`_admit()` 阶段能顺利放行（`todo` 用完了全部容量，但没超），可一旦这条请求开始 decode、需要第 17 个 token 的位置时，`SeqTable._ensure()` 又去要一个块，池子里已经一个都不剩。**这正是 `## 4` 里 vLLM 用抢占解决的场景**：本库选择了更简单但更脆弱的做法——只要 `n_blocks`/`block_size`/`max_running` 配得不够宽松，一条正在运行的请求自己长出新 token 就能把整个引擎打崩，这不是 bug，是 `## 0`/`## 4` 反复强调的"本篇刻意不做抢占"的直接后果，配置这三个参数时必须留出请求"自然增长"所需的余量。

**错误二：只看"批全部跑完的总步数"，得出"连续批处理没有用"的结论。**
`## 2.1` 的例子里，静态批和连续批的队列清空时刻都是第 100 步（被最长的那条请求锁死）——如果只拿"最后一条请求什么时候完成"当基准测两种调度，会测出几乎一样的数字。**错了会看到什么现象**：写一个只统计 `max(r.done for r in reqs)` 的评测脚本，两种实现跑出来的数字确实一样，于是错误地下结论"连续批处理没有性能提升"。真正该看的指标是**平均/中位数延迟**（`## 2.1` 是 100 对 32.5）和**新请求排队延迟**（105 对 13）——这两个指标只要评测脚本没算，连续批处理的收益就会被完全遮蔽掉。

**错误三：把 head-of-line blocking 误判成调度器的 bug。**
`## 3.3` 的实测数字：`reqC` 明明有空间却要等到第 5 步才被 `_admit()` 挑中。**错了会看到什么现象**：如果不知道 `_admit()` 严格 FIFO 这条设计（`## 5` 决策三），观察 `e.waiting` 会看到一个"应该能塞进去却迟迟不被服务"的请求，第一反应容易怀疑是准入逻辑写错了、漏判了什么条件——实际上这是 `_lab/engine.py:176-180` 那个 `return` 而不是 `continue` 的直接推论，是设计选择，不是缺陷。

**错误四：批处理改变了单条请求的输出——本篇最容易被忽视、也是后果最严重的一类错误。**
`test_batching_preserves_per_request_output`（`_lab/tests/test_lab.py:186-199`）如果失败，**错了会看到什么现象**：不是任何异常或崩溃，是同一条请求单独跑和跟别的请求同批跑，`argmax` 出来的 token 序列从某一步开始悄悄分叉——两种跑法都会正常退出，程序不报任何错，唯一的信号是这条断言本身。三个具体成因（`## 3.5` 已经列过，这里补上"怎么在实践中发现"）：

1. **请求间共享了不该共享的 K/V**：如果调试时打印某条请求的 `req.tab.blocks`，发现它跟另一条完全不相关的请求指向了同一批物理块编号，而这不是 `PrefixCache` 有意为之的复用（`## 3.2` 见过 `incref`），那就是分配逻辑出了错——现象是两条请求生成到某一步开始，输出会变得诡异地相关（比如一条请求"看到"了另一条的提示词内容）。
2. **位置编码用错了偏移**：`_lab/engine.py:132-133` 的 `p0 = tab.length` 必须是**这条请求自己**的已提交长度。调试时如果发现同一条请求单独跑和批量跑生成出的 token 从"批量跑时前面恰好排了另一条不同长度的请求"这个条件开始才出错，基本可以断定是有代码路径混用了别的请求或全局 `step_id` 的长度去切 `wpe`。
3. **共享块引用计数记错，导致被提前释放**：这是三者中最隐蔽的一种，因为它**不一定马上触发**——某条请求 `tab.free()`（`_lab/paged.py:136-140`）把引用计数降到 0 之后，物理块被还回空闲池，但只有等**下一条**请求恰好申请到同一个块编号、把它写脏，前一条还在用这块 KV 的请求才会读到错误数据。现象是：某次跑测试通过，换一批请求数量或顺序后偶发性地输出不一致——这种"不是每次都错"的间歇性正是引用计数类 bug 的典型指纹，出现这种症状时第一反应应该是去查 `incref`/`decref` 是否配对，而不是怀疑数值精度。
