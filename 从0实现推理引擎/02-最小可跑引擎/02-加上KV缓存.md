# 加上 KV 缓存

> **一句话**：算法没变，变的只是历史 K/V 从哪儿来。
> **前置**：`01-第一版-朴素前向.md`（若尚未成文，先接受一个前提：`forward_naive` 已经能跑，见 `_lab/minigpt.py:95-116`，它每生成一个 token 就把已有的整段历史重新算一遍）。原理层面的前置是 `[[03-KV缓存的第一性原理]]`——那一篇用归纳法证明了"K/V 只依赖过去、算一次就不会再变"，本篇直接拿这条结论当前提用，不重新证明。

## 0. 这一篇要解决什么问题

`forward_naive`（`_lab/minigpt.py:95-116`）能跑，但有一个致命的复杂度问题：它每次调用都要把**当前已有的全部 token**重新过一遍注意力，从第 1 个 token 生成到第 n 个，前后一共要重算 `1+2+...+n = n(n+1)/2` 次"位置 K/V"——`[[03-KV缓存的第一性原理]]` 的 `## 3.2` 已经算过这笔账。这篇要做的事，就是把这刀砍成 `O(n)`。

但"降复杂度"这四个字说起来轻松，真正动手写的时候容易在三个地方翻车：位置编号从哪儿开始数、掩码该盖住哪一段、缓存该写到哪个下标。这些坑不会让程序崩溃，只会让它**安静地算错**——这是 `_PLAN.md` §2 反复强调的那句话："推理引擎的 bug 绝大多数是静默的"。

本篇明确不做的事：不重新证明"为什么可以缓存 K/V"——那件事 `[[03-KV缓存的第一性原理]]` 已经用归纳法从头到尾证过一遍，本篇直接把那条结论（`k_i`、`v_i` 只依赖 `token_{1..i}`，算一次就不会再变）当作已知条件。本篇要做的是三件更"工程"的事：

1. **把"能缓存"这条数学事实翻译成正确的代码**——朴素版要改动哪几处，改错了每一处会是什么后果；
2. **给出一套可以自己动手执行的验证方法**，而不是"跑了一遍 `--selftest` 看到 `PASS` 就算数"；
3. **诚实指出这一版实现留下的问题**——它离能上生产还差多远，为后面几篇（分页、批处理、前缀缓存）打好埋伏。

3. **端到端生成对比**：`use_cache=False` 和 `use_cache=True` 跑 `generate()`（`_lab/minigpt.py:178-192`）各生成 8 个新 token，token 序列必须**逐个相同**（`_lab/minigpt.py:263-266`）。

再看第二件事：这次改写到底图什么？——图的是速度，不是别的。自己动手跑一段计时（用的是 `_lab/minigpt.py` 默认配置：4 层 / 4 头 / `d_model=128` / 词表 512，`generate()` 生成 50 个新 token，prompt 长度 10）：

```python
import time
from minigpt import Config, init_weights, generate

cfg = Config()
w = init_weights(cfg)
prompt = [3, 14, 15, 62, 6, 35, 8, 9, 7, 12]

for use_cache in (False, True):
    t0 = time.perf_counter()

```

在本机实测跑了 4 遍（笔记本 CPU，非 GPU）：

```

use_cache=True    0.0301 ~ 0.0315 秒
加速比            约 11.0 ~ 12.5 倍
```

⚠️ **这是 numpy 玩具引擎在 CPU 上的实测数字，只说明这个玩具自己的行为，不可外推到 vLLM/SGLang 这类真实引擎**——真实引擎在 GPU 上、kernel 是异步发射的、还有分页和批处理这些本篇之后才引入的机制，加速比是完全不同量级的另一件事。这里唯一值得记住的是**方向**：两条路径生成出来的 token 序列末尾完全一样（都收敛到同一个 argmax 循环），但耗时差了一个数量级——**输出没变，只是变快了**，这正是本篇要证明的核心命题的实测版。

## 2. 原理

### 2.1 中心论点：算法一个字没变，变的只是历史 K/V 从哪儿来

把 `forward_naive`（`_lab/minigpt.py:95-116`）和 `forward_cached`（`_lab/minigpt.py:139-173`）并排摆在一起看，会发现一件容易被忽略的事：**两段代码里，`layernorm`、`q/k/v` 投影、`softmax(QK^T/√d)·V`、残差连接、FFN——每一个算子、每一处矩阵形状、每一个数学公式都完全相同。** 没有任何一个算子在"缓存版"里被替换成了别的东西。真正变化的只有一件事：**历史位置的 K、V 从"当场重新算"变成了"从上次算好的地方读出来"。**

这句话值得再翻译一遍：`forward_naive` 可以理解成"每次调用都先把 `KVCache` 清空、重新填满、再读出来算注意力"的一种极端写法；`forward_cached` 只是把"清空重填"这一步省掉了，直接复用上次填进去、且按 `[[03-KV缓存的第一性原理]]` 证明过"不会再变"的那部分。**是同一个函数在同一组权重上被求值，只是求值的方式从"每次全量重算"换成了"增量追加"。** 这是本篇所有讨论的出发点，`## 3` 会把这句话拆成四处具体的代码差异。

### 2.2 prefill 与 decode：同一段代码，两个工作点

`forward_cached(cfg, w, new_tokens, cache)` 的参数 `new_tokens` 没有对"这批新 token 有几个"做任何限制——它可以是一整段 prompt（这叫 **prefill**），也可以是一个 token（这叫 **decode**）。`_lab/minigpt.py:139-145` 的函数说明直接写了这一点。`generate()`（`_lab/minigpt.py:178-192`）里能看到这两种调用各发生一次/多次：第一次调用 `forward_cached(cfg, w, out, cache)`（`_lab/minigpt.py:183`）传入的是整段 `out`（此刻等于 prompt），这是 prefill；之后循环体里每次调用 `forward_cached(cfg, w, [nxt], cache)`（`_lab/minigpt.py:187`）只传一个新 token，这是 decode。

**这不是两套实现凑巧长得像，是同一段代码在两个不同的 `T`（新 token 数）下被调用。** `02-自回归解码为什么是访存瓶颈.md` 的 `## 2.6` 把这件事从代码事实推广成了一条访存/算力的定量结论——权重侧强度约等于 `0.5·T`（fp32），`T` 大（prefill）就更接近算力受限，`T=1`（decode）就死死卡在访存受限的地板上。本篇不重复那条推导，只强调它的代码根源就在这里：`forward_cached` 从来没有一个 `if is_prefill: ... else: ...` 的分支，`T` 是几完全由调用者传进来的 `new_tokens` 长度决定。

### 2.3 复杂度对比：省下来的是计算，不是访存

朴素版每生成一步都要把当前全部历史的 K/V 重算一遍。从空序列生成到长度 `n`，第 `m` 步要重算 `m` 个位置，`n` 步累计：

```
1 + 2 + ... + n = n(n+1) / 2
```

缓存版每步只算新增的那 1 个（或 prefill 时那 `T` 个）位置，`n` 步累计正好 `n` 次。`n=1000` 时是 `500,500` 次 vs `1,000` 次，差 500.5 倍，且这个倍数随 `n` 线性扩大——这条账 `[[03-KV缓存的第一性原理]]` 的 `## 3.2` 已经算过一遍，这里不重复，只请记住结论：**省下来的是"要重新做多少次乘加"，也就是 FLOPs。**

但这里必须诚实地把话说完整：**KV 缓存省的是计算，不是访存。** decode 阶段哪怕开了缓存，每一步依然要把当前全部历史的 K、V 从内存里**读出来**参与这一步的注意力——`forward_cached` 里 `k_all = cache.k[li][:, :p0+T]`（`_lab/minigpt.py:161`）这一行读出来的是**全部**历史，一个位置都不能少读，因为注意力的定义就是要跟全部历史做点积。`02-自回归解码为什么是访存瓶颈.md` 的 `## 2.3` 已经证明过：**只要 batch=1，算术强度恒等于 `2/dtype_bytes`（fp32 下 0.5），跟上下文长度完全无关**——这条结论本身描述的就是"开了 KV 缓存之后"的 decode，它没有假设"没有缓存"，因为没有缓存的朴素版根本不会有人拿去算这条强度（那样算出来的 FLOPs 分子会更大，但架不住它压根不该被当成正常路径讨论）。

把这两件事放在一起才是完整的图景：**KV 缓存把"算不完"变成了"读不完"，它消灭的是 `O(n²)` 的重复计算，但没有、也不可能让 decode 从访存受限变成算力受限**——因为读全部历史 K/V 这件事本身就是决定算术强度的分母主项（`02-自回归解码为什么是访存瓶颈.md` `## 2.3` 里 `bytes_kv` 那一项）。这条边界很重要：如果指望"上了 KV 缓存"就能让 decode 变得像 prefill 一样吃满算力，会发现无论怎么调，`bs=1` 那一列的算术强度永远是 0.500（见 `02-自回归解码为什么是访存瓶颈.md` `## 1` 的表），这不是没调好，是这条路径的物理极限。真正能抬高强度的手段是加大 batch，那是 `[[04-连续批处理]]` 的事，不是本篇能解决的。

## 3. 自己动手：`_lab/` 里对应的实现

### 3.1 先重新看一眼朴素版，作为对照基准

`forward_naive`（`_lab/minigpt.py:95-116`）的关键三行：

```python
T = len(tokens)
x = w["wte"][tokens] + w["wpe"][:T]                      # _lab/minigpt.py:101
mask = np.triu(np.full((T, T), -1e9, np.float32), k=1)   # _lab/minigpt.py:102
```

`T` 就是"到目前为止的全部历史长度"，位置编码从 0 编到 `T-1`，掩码是一个完整的 `T×T` 下三角。**每调用一次，这三行都要重新跑一遍，`T` 每步都在变大。** 这是 `forward_cached` 要动刀的地方。

### 3.2 `KVCache`：缓存住什么、怎么存

`_lab/minigpt.py:121-136`：

```python
class KVCache:
    def __init__(self, cfg: Config, max_seq: int | None = None):
        self.cfg = cfg
        n = max_seq or cfg.max_seq
        self.k = [np.zeros((cfg.n_head, n, cfg.d_head), np.float32) for _ in range(cfg.n_layer)]
        self.v = [np.zeros((cfg.n_head, n, cfg.d_head), np.float32) for _ in range(cfg.n_layer)]
        self.length = 0
```

三个要点，对照 `_lab/minigpt.py:128-133`：

- **每层一对数组**：`self.k`、`self.v` 是长度为 `n_layer` 的 list，每个元素形状 `(n_head, n, d_head)`——`n` 是预留的最大长度。为什么只缓存 K、V 不缓存 Q，`[[03-KV缓存的第一性原理]]` 的 `## 2.3` 已经讲透（Q 只在算出的那一步被读一次，缓存了也没人会再读它），本篇不重复。
- **`self.length` 是唯一的游标**：记录"已经写了多少个位置"，`forward_cached` 每次调用都靠这一个数知道该从哪儿接着写。
- **`n` 必须提前定死**：构造时就要传入 `max_seq`，这是留给 `## 5.1` 讨论的第一个代价。

### 3.3 `forward_cached` 逐行对照：四处差异

`_lab/minigpt.py:139-173` 的签名和说明：

```python
def forward_cached(cfg: Config, w: dict, new_tokens: list[int],
                   cache: KVCache) -> np.ndarray:
```

（`_lab/minigpt.py:139-145`）——注意参数不再是"到目前为止的全部 token"，而是 `new_tokens`：**只传新增的那一部分**，历史已经在 `cache` 里了。逐处对照 `## 3.1` 的朴素版，差异只有四处：

**差异一：位置编码从 `p0` 开始切，不是从 0**（`_lab/minigpt.py:146-148`）：

```python
T = len(new_tokens)
p0 = cache.length                                       # 已有多少历史
x = w["wte"][new_tokens] + w["wpe"][p0:p0 + T]
```

朴素版是 `wpe[:T]`（`_lab/minigpt.py:101`），缓存版是 `wpe[p0:p0+T]`（`_lab/minigpt.py:148`）。这批新 token 在整条序列里的真实位置是 `p0..p0+T-1`，不是 `0..T-1`——`p0` 就是 `cache.length`，即"缓存里已经攒了多少个历史位置"。这一行错了会发生什么，`## 6.1` 专门讲。

**差异二：新算出的 K/V 要写进缓存**（`_lab/minigpt.py:159-160`，在逐层循环内部）：

```python
cache.k[li][:, p0:p0 + T] = kn                      # 追加写
cache.v[li][:, p0:p0 + T] = vn
```

`kn`、`vn` 是这一步新算出来的 K、V（形状 `(n_head, T, d_head)`），写进 `[p0, p0+T)` 这一段。朴素版完全没有这一步——它每次都是从零现算，压根不存。

**差异三：注意力要读"历史 + 新"拼起来的全部 K/V**（`_lab/minigpt.py:161-166`）：

```python
k_all = cache.k[li][:, :p0 + T]
v_all = cache.v[li][:, :p0 + T]

scores = q @ k_all.transpose(0, 2, 1) / np.sqrt(cfg.d_head)
scores[:, :, p0:] += causal                         # 只对新 token 段加因果掩码
```

`k_all`、`v_all` 是"刚写进去的新段 + 之前已经在缓存里的历史段"合在一起的视图，形状 `(n_head, p0+T, d_head)`。新 token 的 `q`（只有 `T` 个）要对全部 `p0+T` 个位置的 `k` 做点积，`scores` 形状是 `(n_head, T, p0+T)`。

**差异四（最容易写错的一处）：因果掩码只加在新 token 那一段上**。对照 `_lab/minigpt.py:151` 的掩码定义：

```python
causal = np.triu(np.full((T, T), -1e9, np.float32), k=1)
```

这是一个 `T×T` 的小矩阵，只覆盖"新 token 对新 token"这部分；`scores[:, :, p0:] += causal`（`_lab/minigpt.py:165`）把它加到 `scores` 里列下标从 `p0` 开始的那一段——也就是新 token 对应的那部分。**列下标 `0..p0-1`（对应历史）完全不加任何掩码。** 这是因为新 token 相对于历史天然全部可见（历史一定在新 token 前面），只有新 token 彼此之间还需要遵守"看不到后面"的规则。朴素版的 `mask`（`_lab/minigpt.py:102`）是完整的 `T×T` 下三角、盖住整个 `scores`；缓存版是"历史段不盖、新段盖一个小的下三角"，这两种写法必须在数学上等价——`## 6.2` 会讲写错这一处会有什么后果。

收尾：`cache.length = p0 + T`（`_lab/minigpt.py:171`）——更新游标，供下一次调用当作新的 `p0`。整段函数里，`layernorm`、`q/k/v` 投影公式（`_lab/minigpt.py:154-157`）、`softmax`、`o @ wo`、FFN（`_lab/minigpt.py:167-169`）跟朴素版逐字相同——回应 `## 2.1` 的中心论点：**变化只集中在这四处，其余的算子代码是复制粘贴过来的。**

### 3.4 `generate()`：两条路径怎么接起来

`_lab/minigpt.py:178-192`：

```python
def generate(cfg: Config, w: dict, prompt: list[int], n_new: int,
             use_cache: bool = True, greedy: bool = True) -> list[int]:
    out = list(prompt)
    if use_cache:
        cache = KVCache(cfg, max_seq=len(prompt) + n_new + 1)
        logits = forward_cached(cfg, w, out, cache)
        for _ in range(n_new):
            nxt = int(logits.argmax()) if greedy else int(np.argmax(logits))
            out.append(nxt)
            logits = forward_cached(cfg, w, [nxt], cache)
    else:
        for _ in range(n_new):
            logits = forward_naive(cfg, w, out)
            out.append(int(logits.argmax()))
    return out
```

`use_cache=True` 分支（`_lab/minigpt.py:181-187`）里，`KVCache` 的 `max_seq` 被设成 `len(prompt) + n_new + 1`（`_lab/minigpt.py:182`）——这条请求这辈子能达到的最大长度，`## 5.1` 会讲这是个代价而不是免费的设计。第一次调用 `forward_cached(cfg, w, out, cache)`（`_lab/minigpt.py:183`）传的是整段 `out`（此刻等于 prompt），这是 prefill；循环体里 `forward_cached(cfg, w, [nxt], cache)`（`_lab/minigpt.py:187`）每次只传 1 个新 token，这是 decode——同一个函数，`## 2.2` 讲过的两个工作点在这里被完整地接成了一个生成循环。`use_cache=False` 分支（`_lab/minigpt.py:189-191`）每步都调用 `forward_naive(cfg, w, out)`，`out` 每步都在变长，这就是本篇要消灭的 `O(n²)`。

### 3.5 `selftest`：三条断言到底在测什么

回到 `## 1` 提过的三条断言，这里逐条看它们的代码（`_lab/minigpt.py:241-266`）：

```python
# 1) prefill 一致性（_lab/minigpt.py:249-253）
a = forward_naive(cfg, w, prompt)
c = KVCache(cfg)
b = forward_cached(cfg, w, prompt, c)
if not np.allclose(a, b, atol=1e-4): ...
```

一次性把整段 `prompt` 分别喂给两条路径。**这条测试有个盲区**：因为是空缓存、一次性喂完，`p0` 全程为 0，`## 3.3` 差异一里的 `wpe[p0:p0+T]` 和朴素版的 `wpe[:T]` 在 `p0=0` 时**恰好写法等价**——如果只有这一条断言，`## 6.1` 那类"位置编码没跟着偏移"的 bug 是测不出来的。

```python
# 2) 逐 token 增量一致性（_lab/minigpt.py:256-260）
c2 = KVCache(cfg)
for t in prompt:
    b2 = forward_cached(cfg, w, [t], c2)
if not np.allclose(a, b2, atol=1e-4): ...
```

这条把 `prompt` 拆成一个个 token 喂，缓存从空一路长大，`p0` 会依次取到 `0, 1, 2, ...`——**专门用来堵上第 1 条留下的盲区**，位置编码只要没跟着 `p0` 偏移，这里就会失败。

```python
# 3) 端到端生成一致性（_lab/minigpt.py:263-266）
g1 = generate(cfg, w, prompt, 8, use_cache=False)
g2 = generate(cfg, w, prompt, 8, use_cache=True)
if g1 != g2: ...
```

这条最敏感：greedy decode 每步都把上一步的 argmax 结果喂回去当下一步输入，一旦中途某一步 logits 算错，argmax 大概率会选到不同的 token，后面全部分叉。三条断言合起来才是完整的护栏——**任何一条单独存在都留有盲区，是三条叠在一起才把 `## 6` 要讲的几类 bug 全部堵死。**

### 3.6 一套可操作的验证清单：自己写完一份 KV 缓存，怎么知道写对了

`## 3.5` 拆过的三条 `selftest` 断言，本质上是下面这份清单的前两条。把清单完整列出来，是因为**只测这两条仍然会留下两个盲区**——不同起始长度没测全，而且从头到尾都是"正向"验证（两条路径应该相同的地方，验证它们确实相同），缺一条"负向"验证（不同的地方，验证它们确实不同）。四条凑齐才算完整：

1. **逐位对比**：`forward_naive(prompt)` 与 `forward_cached(prompt, 空缓存)` 的输出必须在 `atol=1e-4` 内相等（`_lab/minigpt.py:249-253`）。
2. **逐 token 增量喂 vs 一次喂整段**：把同一段 prompt 拆成单 token 依次喂给 `forward_cached`，最终结果要跟一次性喂给 `forward_naive` 一致（`_lab/minigpt.py:256-260`）。
3. **不同起始长度都要测，不能只测从空缓存开始**：前两条测试的缓存起点都是 `p0=0`（要么全程空缓存，要么从零一路长大），但 `## 6.1`、`## 6.3` 的坑恰恰只在 `p0>0` 之后才会露出来。自己动手补一段更狠的参数化测试——固定住"已有的历史"，只改"从哪个 `p0` 开始追加"，验证结果始终跟朴素版一致：

   ```python
   import numpy as np
   from minigpt import Config, init_weights, KVCache, forward_cached, forward_naive

   cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=64, seed=1)
   w = init_weights(cfg)
   full = [3, 14, 15, 62, 6, 35, 8, 9, 7, 12]

   for split in range(1, len(full)):          # 在每一个可能的位置切开来试
       cache = KVCache(cfg)
       forward_cached(cfg, w, full[:split], cache)      # 先攒到 p0 = split
       got = forward_cached(cfg, w, full[split:], cache) # 再从这个 p0 继续追加
       want = forward_naive(cfg, w, full)
       assert np.allclose(want, got, atol=1e-4), f"split={split} 处不一致"
   ```

   这段代码只用到本文已经引用过的公开接口，思路是"同一段历史，从任意一个 `p0` 切开重新起步，结果都必须跟一次性跑完的朴素版一致"——`## 3.5` 的第 2 条只验证了"每次只追加 1 个 token"这一种切法，这里把切法扩展成"任意位置切一刀，前后两段分两次喂"，能测到的 `p0` 取值比原来的 `selftest` 更全。

4. **反向测试：改一个历史 token，结果必须变**——前三条清一色是"正向"验证：两条应该相同的路径，验证确实相同。这类测试有一个共同的盲区：如果 `forward_cached` 有一个 bug，导致它压根没有真正读到缓存里写进去的历史 K/V（比如某处手滑读成了 `KVCache.__init__`（`_lab/minigpt.py:128-133`）里初始化的那片全零数组，而不是真正写入过的那一段），只要这个"读错的值"在两条路径里读法一致，`## 3.5` 那类对比测试完全抓不出来。能抓住这类 bug 的只有一种测试：**故意改动历史里的某一个 token，验证后面的输出必须跟着变**——如果没变，说明这段历史压根没被真正用上，缓存形同虚设：

   ```python
   from minigpt import Config, init_weights, KVCache, forward_cached
   import numpy as np

   cfg = Config(n_layer=2, n_head=2, d_model=32, vocab=64, max_seq=64, seed=1)
   w = init_weights(cfg)

   def logits_after(history, extra):
       cache = KVCache(cfg)
       forward_cached(cfg, w, history, cache)   # 先把历史攒进缓存
       return forward_cached(cfg, w, [extra], cache)  # 再追加同一个新 token

   base    = logits_after([3, 14, 15, 62, 6], 8)
   changed = logits_after([3, 50, 15, 62, 6], 8)   # 只改了历史里第 2 个 token（注意 token id 必须小于 vocab=64）

   print(np.allclose(base, changed))   # 必须是 False —— 改了历史，输出纹丝不动就是历史没被用上
   ```

   在真正的 `_lab/minigpt.py` 实现上跑这一段，`np.allclose` 会打印 `False`——历史第 2 个 token 变了，第 2 层往后所有依赖它的 `k`、`v` 全部不同，最终 logits 自然跟着变。这条测试反过来验证的是 `[[03-KV缓存的第一性原理]]` `## 2.2` 证明的那件事在实现里没被破坏：`k_i`、`v_i` **确实**依赖它左边的历史，而不是一段读了跟没读一样的摆设代码。

## 4. 真实引擎是怎么做的（对照 vLLM）

`_lab/minigpt.py` 的 `KVCache`（`_lab/minigpt.py:121-136`）是"每层一个大数组，按绝对位置连续索引"——`cache.k[li][:, p0:p0+T]` 这种写法要求整条请求的 K/V 是一段物理连续的内存。真实引擎的 KV 缓存物理布局完全不是这样。

vLLM 的 attention kernel 接收的 `kv_cache` 张量形状，docstring 写得很直接：

```python
# vllm:vllm/v1/attention/backends/flash_attn.py:897-898
kv_cache: shape =
    [num_blocks, num_kv_heads, block_size, 2 * head_size]
```

第一维不是"绝对位置"，是 `num_blocks`——**一整块显存被切成 `num_blocks` 个固定大小（`block_size`）的物理块，K/V 存在哪个块、块内哪个位置，跟这条请求在逻辑序列里的位置是两回事，中间要有一层翻译。** 这层翻译由 `BlockTable` 负责：

```python
# vllm:vllm/v1/worker/block_table.py:57
class BlockTable:
```

`BlockTable` 维护的是"这条请求逻辑上的第几个块，对应物理上的第几个块"这张表，而不是像 `_lab/minigpt.py` 的 `KVCache` 那样直接用一个连续下标 `p0:p0+T` 定位。真正把"新 token 的位置"翻译成"该写进哪个物理块的哪个槽位"的，是 `compute_slot_mapping`：

```python
# vllm:vllm/v1/worker/block_table.py:201-229（节选）
def compute_slot_mapping(
    self, num_reqs, query_start_loc, positions,
) -> None:
    ...
    _COMPUTE_SLOT_MAPPING_KERNEL(
        num_reqs, num_tokens, self.max_num_batched_tokens,
        query_start_loc, positions,
        self.block_table.gpu, self.block_table.gpu.stride(0),
        self.block_size, self.slot_mapping.gpu, ...
    )
```

对照 `## 3.3` 差异二里的那一行 `cache.k[li][:, p0:p0 + T] = kn`（`_lab/minigpt.py:159`）——我们的写法是"我自己知道 `p0` 在哪，直接切片写"；vLLM 的写法是"把每个 token 的逻辑 `positions` 和这条请求的 `block_table` 一起喂给一个专门的 kernel，由它算出每个 token该写进物理显存的哪个槽位（`slot_mapping`）"。**核心算法——`forward_cached` 那四处差异体现的"新 token 只算一次、写一次、历史只读不重算、掩码只盖新段"——vLLM 一个字都没有变，变的是这些读写操作底下多了一层"逻辑位置 → 物理槽位"的地址翻译。**

这层翻译存在的理由，直接对应 `_lab/minigpt.py` 的 `KVCache` 构造函数里那句自嘲式的注释——它必须按 `max_seq` 预分配一整段连续内存（`_lab/minigpt.py:128-133`）。`## 5.1` 会把这件事拆成决策讲，这里先点出结论：**只要坚持"一条请求的 K/V 必须是一段连续内存"，就必须预分配到可能用到的最大长度**，而 vLLM 用固定大小的块 + 块表，恰恰是为了不做这个预分配。`[[03-分页KV与块管理]]` 会把 `BlockTable`、`compute_slot_mapping` 这套机制在本库自己的 `paged.py` 里对应地实现一遍。

## 5. 设计决策与代价

### 5.1 要不要给 `forward_cached` 和 `forward_naive` 用同一套 `T` 可变的接口，而不是分别写 prefill 版和 decode 版

- **为什么这样**：`## 2.2` 已经指出，prefill 和 decode 在数学上是同一个函数在不同 `T` 下的两次求值，`generate()`（`_lab/minigpt.py:178-192`）也确实是这么调的——用同一个签名承载两种调用，直接把"它们是同一件事"这条结论体现在接口设计里，不需要读者去猜两个函数是不是暗中不一致。
- **不这样会怎样**：如果分别写 `forward_prefill` 和 `forward_decode` 两个函数，核心逻辑（q/k/v 投影、掩码规则、缓存读写）要各自实现一遍，测试也要覆盖两遍——`## 3.3` 拆出来的四处差异，任何一处如果只在一个函数里改对、另一个函数里忘了改，就会产生两条路径悄悄不一致的 bug，而且很可能只在极端 `T` 值下才会暴露。
- **什么时候可以不这样**：当 prefill 和 decode 的性能特征差异大到必须用完全不同的 kernel 实现时（真实引擎里很常见——prefill 用适合大矩阵乘的 kernel，decode 用针对"新增 1 行"优化过的 kernel），**接口层面仍然可以统一**（`## 4` 里 vLLM 的 `kv_cache` 张量形状对 prefill、decode 是同一套约定），但底层可以按 `T` 的大小分派到不同实现——这是"接口统一、实现可以分叉"，跟"接口本身就分叉成两套"是两回事。

### 5.2 要不要用"追加写"而不是"每次整体重建缓存再读"

- **为什么这样**：`## 3.3` 差异二里 `cache.k[li][:, p0:p0+T] = kn` 只写新增的这一小段，历史那部分内存完全不碰——这正是"只算新增、不重算历史"这件事在代码层面落地的方式，也是 `## 2.3` 里那笔复杂度账（`n(n+1)/2` 降到 `n`）成立的前提。
- **不这样会怎样**：如果每次调用 `forward_cached` 都新建一个空的 `KVCache`、把历史 token 连同新 token 一起重新算一遍再整体写进去，表面上函数签名没变、`selftest` 甚至可能还是能过（因为结果确实一致），但复杂度已经退化回了 `O(n²)`——**这是一种"伪缓存"：形式上有 `KVCache` 这个类，实际上什么都没省。** 这个坑不会被 `## 3.5` 那三条正确性断言抓到，因为它们只测输出对不对，不测有没有真的省计算，这也是为什么 `_PLAN.md` 强调"正确性优先于性能"的同时，性能这件事仍然需要单独去看（`## 1` 的计时实验就是干这个的）。
- **什么时候可以不这样**：当支撑缓存正确性的前提被打破时——`[[03-KV缓存的第一性原理]]` `## 2.4` 提到的"权重变了（比如推理中途切换 LoRA 适配器）"——旧缓存里的 K/V 已经不是用当前权重算出来的，此时必须清空重算，不能再"追加"。但这已经不是"选择用不用追加写"的问题，是"这批数据的缓存前提已经失效，必须整体作废"，跟 `## 5.2` 讨论的默认路径是两回事。

### 5.3 要不要让因果掩码只覆盖新增段，而不是对整个 `scores` 套用同一个下三角

- **为什么这样**：`## 3.3` 差异四已经讲过语义——新 token 对全部历史天然可见，只有新 token 之间才需要遵守"看不到后面"。只在 `scores[:, :, p0:]` 这一小段（`T×T`）加掩码，而不是对整个 `(p0+T)×(p0+T)` 套用下三角，**既是语义上唯一正确的写法，顺带也省了构造一个更大掩码矩阵的开销**——`_lab/minigpt.py:151` 的 `causal` 全程只是一个 `T×T` 的小矩阵，不随 `p0` 增长。
- **不这样会怎样**：见 `## 6.2`——把掩码套用到整个 `scores` 上，等于用"新 token 在这批新 token 内部的相对位置"去决定它能看见多远的历史，而不是用它在整条序列里的真实绝对位置，会把不该被遮住的历史错误地挡住。
- **什么时候可以不这样**：如果一个实现选择放弃增量缓存、每步都把全部历史和新 token 拼起来重新整体跑一遍完整的 `forward_naive` 式前向，那确实可以对整个序列套用统一的下三角掩码——但那已经不是 `forward_cached` 要做的事，是 `## 5.2` 里说的"伪缓存"退化路径。

### 5.4 要不要用 `np.allclose(atol=1e-4)` 而不是精确相等去验证"改写前后输出不变"

- **为什么这样**：`forward_naive` 和 `forward_cached` 虽然算的是同一个数学函数，但两条代码路径里矩阵乘、加法的**执行顺序不完全相同**（比如 `forward_cached` 是先算新 token 的 K/V 再和历史拼接，`forward_naive` 是整段一起算），浮点加法不满足结合律，顺序不同、累积的舍入误差量级就不同，不能要求逐位精确相等。`atol=1e-4` 是"能吸收正常浮点噪声、又能抓住真实逻辑错误"之间的一个刻意选定的平衡点——`## 6.1`、`## 6.2` 这类真实 bug 造成的偏差通常是数量级上的（argmax 会直接选到不同的 token），远大于 `1e-4`。
- **不这样会怎样**：要求 `a == b` 精确相等，本来正确的实现会被误判成 `FAIL`（过严，`_lab/minigpt.py:249-253` 这类断言会一直红，逼着你去"修"一个根本没坏的东西）；把容差调得更宽比如 `1e-2`，真正的逻辑 bug 造成的偏差有可能被容差吸收掉，测试形同虚设（过松，`## 6` 里几类 bug 反而测不出来）。
- **什么时候可以不这样**：如果存在一种实现方式，能保证两条路径按**完全相同**的顺序做**完全相同次数**的浮点运算（比如强行把 `forward_naive` 也改写成"每步都从空缓存开始追加拼接一遍再整体读出"），理论上有可能做到位级相等——但这样改写没有意义，`forward_naive` 存在的目的就是提供一个独立写法的参照物，两条路径本该是不同的实现路径，用容差比较才是这里的标准实践。

## 6. 常见错误与踩坑

`## 3.5` 已经说明：`selftest` 的三条断言合起来才堵得住下面这几类 bug，任何一条单独存在都留有盲区。这里逐条讲清楚"写错了会在什么现象上露馅"。

### 6.1 位置编码没跟着 `p0` 偏移

正确写法是 `wpe[p0:p0+T]`（`_lab/minigpt.py:148`），错误写法是照抄朴素版的 `wpe[:T]`——只看这批新 token 自己有几个，永远从位置 0 开始编号。

**现象：不报任何异常，形状完全对得上（都是 `(T, d_model)`），矩阵乘、加法照常跑完。** 但语义已经错了：假设 prompt 长度是 5，第 6 步 decode 一个新 token 时 `p0=5`，正确做法是让模型知道"这是序列里第 5 个位置"；如果写成 `wpe[:1]`，模型会以为自己在处理"第 0 个位置"——跟 prefill 阶段处理 prompt 第一个 token 时用的是同一份位置编码。连续生成多个 token 时，每一步的位置信息全部错位，模型会输出一些语法上不出错、但读起来越来越不连贯的内容。**`## 3.5` 里第 1 条断言（一次性 prefill 对比）抓不住这个 bug**——因为那条测试的 `p0` 全程为 0，`wpe[:T]` 和 `wpe[p0:p0+T]` 在 `p0=0` 时恰好写法等价；能抓住它的是第 2 条断言（`_lab/minigpt.py:256-260`，逐 token 增量对比），因为它会让 `p0` 依次取到非零值。

### 6.2 因果掩码加到了历史那一段上

正确写法是 `scores[:, :, p0:] += causal`（`_lab/minigpt.py:165`），只对列下标从 `p0` 开始（对应新 token）的那一段加掩码。容易犯的错误是构造一个覆盖整个 `(p0+T)×(p0+T)` 的下三角矩阵，直接加到整个 `scores` 上。

**现象：同样不会报异常**（`np.triu` 构造一个更大的矩阵、加到 `scores` 上，形状运算完全合法）。但后果是模型会看不见一部分本该看得见的历史——因为一个从下标 0 重新数起的下三角矩阵，会把"新 token 相对于它在这批新 token 内部的相对位置"当成可见范围，而不是它在整条序列里的绝对位置。生成出来的内容会表现得像是**忘记了较早的上下文**，只对最近几个 token 有反应，而且这种"失忆"往往要生成好几步之后才会明显看出来，因为刚开始几步被误挡住的历史信息可能恰好不影响当时的输出。

### 6.3 缓存写入的位置算错

正确写法是 `cache.k[li][:, p0:p0+T] = kn`（`_lab/minigpt.py:159`），一个容易犯的错误是写成 `cache.k[li][:, :T] = kn`——漏掉了 `p0` 偏移，每次都从下标 0 开始写。

**现象：第一次调用（prefill，此时 `p0=0`）碰巧是对的，因为 `[:T]` 和 `[p0:p0+T]` 在 `p0=0` 时一样。** 但从第二次调用（第一次 decode）开始，新算出的 K/V 会覆盖掉缓存里**下标 0 开始**的那一段——也就是历史里最早的几个 token 的 K/V 被新 token 的 K/V 覆盖掉了，而 `cache.length` 依然正常按 `p0+T` 递增。之后 `k_all = cache.k[li][:, :p0+T]`（`_lab/minigpt.py:161`）读出来的这段内存里，开头几个位置存的已经不是原来那几个 token 的 K/V，而是被后来的新 token "写脏"了的数据。这类 bug 的诡异之处在于：**它不会让生成立刻崩掉，而是让模型的注意力开始"重复"或者"张冠李戴"**——比如后面生成的内容莫名其妙地像是在响应一个更早输入过的、但其实已经被覆盖掉的 token，因为存储那个 token 位置的内存已经被别的内容顶替了。

### 6.4 最隐蔽的一种：只在 batch=1 时对，多条请求同批跑时串了

`_lab/minigpt.py` 里的 `KVCache`（`_lab/minigpt.py:121-136`）从头到尾只服务一条请求，`selftest`（`_lab/minigpt.py:241-295`）的全部断言也都是单条请求跑到底——**这意味着这份 `selftest` 天生保证不了"多条请求同时用缓存会不会互相串"这件事，因为它压根没有制造出第二条请求来验证。**

真正会暴露这类 bug 的场景是把 `KVCache` 这套机制扩展成同时服务多条请求：如果不小心让两条请求共用同一段连续内存（比如把 `p0`/`cache.length` 这类游标写成了跨请求共享的全局或类级状态，而不是每条请求各自独立），或者在批处理时把张量的 batch 维和序列维搞混，会出现"请求 A 的注意力读到了请求 B 写进去的 K/V"这种串话。**现象是：单条请求测试永远是绿的（因为没有第二条请求来打架），但一旦真的并发跑两条内容不同的请求，其中一条（甚至两条）会开始生成一些跟自己输入完全对不上、却神似另一条请求内容的输出——而且往往只在某些请求长度组合、某些并发时机下才会复现，不稳定，比前三类 bug 难抓得多。**

本库 `engine.py` 里能看到"不串"这件事具体是怎么做对的：每条请求准入时都会拿到一个**独立的** `SeqTable` 对象（`req.tab = SeqTable(self.pool)`，`_lab/engine.py:155`），而不是共用同一份缓存状态；专门验证"这件事没做错"的测试是 `test_batching_preserves_per_request_output`（`_lab/tests/test_lab.py:187-199`）——它特意构造了两条**共享前缀、后缀不同**的请求同批跑，断言每条各自的输出必须跟它单独跑时完全一致。**这条测试存在的意义，正是本节要强调的这句话的反面：`_lab/minigpt.py` 自己的 `selftest` 测不出批处理串没串，必须专门在有并发请求的场景下才能验证。** `[[04-连续批处理]]` 会展开讲这套隔离机制的完整设计。

### 6.5（附加）把 `atol=1e-4` 之内的正常浮点误差当成 bug 去"修"

这不是缓存本身写错，而是验证方式出的偏差：看到两条路径的 logits 差了 `1e-6`、`1e-5` 这个量级，就怀疑代码哪里没写对——`## 5.4` 已经解释过，这是浮点运算顺序不同导致的正常舍入误差，不是逻辑错误。**现象是**：如果因此把代码改成强行让两条路径按相同顺序计算（比如让 `forward_naive` 也去模拟"追加拼接"的计算顺序），代码会变得又绕又难维护，却对正确性毫无实质帮助——真正该做的是确认容差量级选得对不对（`## 5.4`），而不是消灭噪声本身。
