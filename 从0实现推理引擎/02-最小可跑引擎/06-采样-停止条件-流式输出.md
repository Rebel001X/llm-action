# 采样、停止条件与流式输出

> **一句话**：贪心是采样的退化情形，流式输出是状态机，不是切碎发送。
> **前置**：`[[05-前缀缓存]]`（本篇复用同一个 `_lab/minigpt.py` 的 `forward_cached`，只是不再假设每一步都取 `argmax`）

## 0. 这一篇要解决什么问题

到 `[[05-前缀缓存]]` 为止，五篇文章把"喂 prompt 进去、吐 token 序列出来"这件事从朴素前向一路做到了能连续批处理、能跨请求共享前缀。但这五篇有一个从没被挑明、却贯穿始终的假设：**每一步拿到 logits 之后都取 `argmax`**——`_lab/minigpt.py` 的 `generate()`、`_lab/engine.py` 的推进循环，做的都是同一件事。这不是偷懒，是刻意的：正因为 `argmax` 是确定性的，前面几篇"优化不许改变输出"那一整套逐位比较的测试才立得住——KV 缓存、分页、连续批处理、前缀缓存，每一项优化都拿"跟朴素路径的 token 序列逐位相同"当护栏。一旦引入随机采样，这句护栏本身就要换一套判据：同一个 prompt 跑两次得到两个不同的 token 序列，是**预期行为**，不是 bug。

一个真能用的服务必须再补三件事，而且——这是本篇区别于前五篇最大的一点——**这三件事全都不是数学问题，是工程问题，几乎每一个坑都是静默的**：跑起来不报错、不崩溃，只是结果不对，或者晚一点才发现不对。`_lab/sampling.py` 顶部的模块文档把这三件事和各自的难点摆得很直白（`_lab/sampling.py:1-23`）：

1. **采样**：temperature / top-k / top-p / 重复惩罚。公式都不难，难的是**算子的施加顺序**会改变候选集，以及**重复惩罚在负 logit 上很容易把符号写反**。
2. **停止条件**：`max_new` 和 EOS 是整数比较，一眼能看对；停止字符串难，因为**停止串可能横跨两个 token 的边界**，逐 token 判断会漏检。
3. **流式输出**：不能一拿到 token 就往外发。两个原因逼你缓一手——**UTF-8 多字节字符会跨 token 边界**（字节级 BPE 的 token 可以是半个汉字），以及**已经发给用户的字符收不回来**，所以任何可能构成停止串前缀的尾巴都得先扣住再看。

本文件的立场写在模块文档里，值得先立在这里当全篇的纲：**贪心不是"采样的对立面"，是 `temperature → 0` 的退化情形；流式不是"把结果切碎发出去"，是一个需要显式状态机的增量协议。** `## 1` 先看这套机制跑起来是什么样子，`## 2` 讲清楚背后的机制为什么必须这样设计，`## 3` 逐行对照 `_lab/sampling.py`，`## 4` 看真实引擎怎么做同一件事，`## 5`~`## 7` 收尾。

## 2. 原理

### 2.1 贪心是采样的一个端点，不是它的对立面

`apply_temperature()`（`_lab/sampling.py:89-97`）做的事只有一行：`logits / t`。这一行为什么能连到"贪心"上，是个可以直接算的极限：`t → 0` 时，最大的那个 logit 除以一个趋近于 0 的正数，会被放大到远超其它所有值，softmax 之后这个位置的概率趋近于 1，其余趋近于 0——等价于直接取 `argmax`。`t → ∞` 时所有 logit 都被压缩到接近 0，softmax 退化成均匀分布——等价于纯随机。**贪心和纯随机是同一条参数曲线的两个端点，中间是连续过渡的**，不是两套互斥的机制。`top_k=1` 是这条结论的另一个入口：无论温度多高，只保留 1 个候选之后采样就没有第二个选项可选，同样退化成 `argmax`——`SamplingParams.is_greedy`（`_lab/sampling.py:48-50`）把这两条路径都判定为贪心，正是这个数学事实在代码里的样子。

这条结论决定了 `## 0` 说的判据切换：贪心分支下"逐位比较"依然是判据（前五篇的全部测试对贪心路径完全成立，因为 `_lab/sampling.py` 本身没有改变 `argmax` 这条路径的语义）；一旦 `temperature>0` 或者需要真正采样，判据必须换成**同 seed 可复现**与**批不变性**——这两条不是退而求其次，是随机性场景下唯一还站得住的护栏，`## 3.3` 落到具体代码时会讲清楚。

### 2.2 施加顺序为什么会改变候选集

`## 1` 第一张表背后有一条更细的机制，值得手算一遍再看代码。用 `_lab/sampling.py:313` 里 selftest 自带的分布：概率 `[0.87, 0.08, 0.05]`，取 `k=2, p=0.9`。

**先 top-k 后 top-p**：top-k=2 先把最小的 0.05 砍成 `-inf`，剩下 `{0.87, 0.08}`。`top_p_filter()`（`_lab/sampling.py:109-129`）内部会重新对**当前传入的 logits**做一次 softmax（`_lab/sampling.py:123`），而这时候只剩两个有限值——重新归一化后变成 `0.87/0.95 ≈ 0.916`、`0.08/0.95 ≈ 0.084`。按累计概率排序：第一个候选"它之前的累计" `= 0 < 0.9`，保留；第二个候选"它之前的累计" `= 0.916`，已经**不小于** `0.9`，被排除。结果：只剩 1 个候选。

**先 top-p 后 top-k**：`top_p_filter()` 先在原始三元分布上工作，累计概率对第一个候选是 `0 < 0.9`，保留；对第二个候选是 `0.87 < 0.9`，保留；对第三个候选是 `0.87+0.08=0.95`，不小于 `0.9`，排除。结果：`top_p` 单独已经保留了 2 个候选 `{0.87, 0.08}`。后续再套 `top_k=2`，这两个恰好就是最大的两个，不再有变化。结果：2 个候选。

同一个 `(k=2, p=0.9)`，顺序一换，候选集从 1 个变成 2 个——**根因是 top-k 砍掉尾巴之后，剩下概率被重新归一化，分母变小，累计和天然涨得更快，top-p 的截断点就提前了**。`filter_order_matters()`（`_lab/sampling.py:132-144`）把这两种顺序做成了一对可以直接调用、直接对比的函数，`## 3.2` 会展开讲它的实现。这不是学术细节：**不同引擎的默认顺序不一样，同样的 `(k, p)` 配置在两个引擎上可以合法地给出不同的候选集**，`## 4.1` 会看到真实引擎选的是哪种顺序、为什么。

### 2.3 UTF-8 增量解码：为什么不能用 `bytes.decode()`

真实 BPE 词表的 token 是**字节串**，不是字符串。一个 token 完全可以只是某个多字节字符的一部分——`_lab/sampling.py` 用 12 个 token 的玩具词表（`TOY_VOCAB`，`_lab/sampling.py:182-195`）把这个真实难点复现出来：id 4 是 `b"\xe4\xbd"`、id 5 是 `b"\xa0"`，两个拼在一起才是 "你" 的合法 UTF-8 编码（`E4 BD A0`）。如果流式输出的实现是"每收到一个 token 就 `token_bytes.decode("utf-8")`"，id 4 单独解码会直接抛出 `UnicodeDecodeError`——这种错法至少会崩溃、容易被发现。**真正危险的是把异常处理成 `errors="replace"`**：`b"\xe4\xbd".decode("utf-8", errors="replace")` 不会抛异常，会安静地给出一个 `U+FFFD`（替换字符）。等 id 5 的字节到达，为时已晚——**已经发给用户的 `U+FFFD` 是永久的，没有"回滚重发"这回事**，哪怕后续字节把这个字符补全了，用户看到的这一位置已经定格成了乱码。

正确做法是用 `codecs.getincrementaldecoder("utf-8")()`（Python 标准库自带）：喂进去不完整的字节序列，它会自己判断"这是不是一个完整字符的开头"，不完整就内部缓存、返回空字符串，不抛异常也不猜测；等后续字节补齐，才把这个字符正常吐出来。这不是"多包一层 try/except"能替代的——try/except 只能决定"报不报错"，改变不了"半个字符已经不可逆地进了 decode 结果"这个事实；只有一个真正维护内部字节缓冲区的增量解码器,才能把"这个字符还没攒够"和"已经攒够可以吐出"这两个状态显式分开。

### 2.4 停止串跨 token 边界：为什么要扣住 `max(len(stop))-1` 个字符

停止串 "STOP" 由两个 token 拼出来：id 7 是 `b"ST"`、id 8 是 `b"OP"`。如果检测逻辑是"每来一个 token 就单独看这个 token 里有没有停止串"，两个 token 各自都不包含 "STOP"，检测会彻底漏掉这次命中。正确做法是维护一段**已解码但还没确认安全的文本**，每次新增内容后在这段文本里整体查找停止串——但这样一来又引出下一个问题：**文本一旦发给用户就收不回来了**，如果把新解码出来的字符立刻全部发出去，等真的凑出停止串时,已经发出去的那部分文本已经包含了停止串的前缀（比如已经发出了 "ST"），没法撤回。

解法是显式留一段安全缓冲：停止串最长是 `L` 个字符，那么**任何还没被确认"不可能构成某个停止串前缀"的尾巴，长度不会超过 `L-1` 个字符**（因为一旦达到 `L` 个字符还没匹配上，就说明这段尾巴已经不可能是任何停止串的前缀）。所以每次只发出"已解码文本"去掉最后 `L-1` 个字符的那一部分，`## 1` 里 token 1 只发出 `'He'`（`'Hello'` 去掉最后 3 个字符）就是这条规则的直接体现——`hold = max(len(s) for s in stop) - 1`，`## 3.5` 会看到这一行代码。**代价很直白：流式输出天然带一点延迟，延迟长度等于最长停止串减一，这是协议要求，不是实现写得不好。**

### 2.5 `finish_reason` 的优先级

一次生成可能同时满足多个停止条件——比如停止串恰好在最后一个允许生成的 token 上命中，`stop` 和 `length` 同时成立。客户端要靠 `finish_reason` 决定要不要自动续写、要不要报错重试，这两种情况的处理策略完全不同，所以**必须有一个明确的优先级，不能返回"随便一个成立的原因"**。`_lab/sampling.py` 的顺序是：先看 `StreamGuard` 是不是已经命中停止串（`stop`），再看最后一个 token 是不是 EOS（`eos`），最后才看长度是不是到顶（`length`）——`stop` 优先级最高的原因很直接：它代表"模型自己知道该停了、而且是按用户要求停的"，比"凑巧撞上了长度上限"这种信息量更大，值得客户端优先采信。

## 3. 自己动手：`_lab/` 里对应的实现

### 3.1 `SamplingParams`：默认值就是贪心

```python
# _lab/sampling.py:37-50
@dataclass
class SamplingParams:
    """一次请求的采样配置。**默认值刻意等价于贪心**，方便和前面的测试对齐。"""
    temperature: float = 0.0         # 0 = 贪心（argmax）
    top_k: int = 0                   # 0 = 关闭
    top_p: float = 1.0               # 1.0 = 关闭
    repetition_penalty: float = 1.0  # 1.0 = 关闭
    seed: int | None = None
    max_new: int = 32
    eos: int | None = None
    stop: tuple[str, ...] = field(default_factory=tuple)

    @property
    def is_greedy(self) -> bool:
        return self.temperature <= 0.0 or self.top_k == 1
```

（`_lab/sampling.py:37`、`is_greedy` 属性在 `_lab/sampling.py:48-50`）每个字段的默认值都是"关闭这个算子"的那个值，这不是巧合——这样构造出的默认 `SamplingParams()` 恰好复现了前五篇一直在用的 `argmax` 路径，`## 2.1` 的数学事实在这里落成了一行代码判据：`temperature<=0.0 or top_k==1`。

### 3.2 四个采样算子

**重复惩罚**（`_lab/sampling.py:55-72`）是全文件最容易写错的一处：

```python
# _lab/sampling.py:55-72
def apply_repetition_penalty(logits: np.ndarray, prev: list[int],
                             penalty: float) -> np.ndarray:
    if penalty == 1.0 or not prev:
        return logits
    out = logits.copy()
    idx = np.unique(np.asarray(prev, dtype=np.int64))
    v = out[idx]
    out[idx] = np.where(v > 0, v / penalty, v * penalty)
    return out
```

关键在最后一行的 `np.where`：正的 logit 除以 `penalty`（变小），负的 logit 乘以 `penalty`（`penalty>1` 时同样变小，因为负数乘大于 1 的数会更负）。两个分支都朝着"变小"走，惩罚才是惩罚。旁边故意留了一个错误版本当反例，**只在自检里当靶子用，不会被别处调用**：

```python
# _lab/sampling.py:75-86（故意写错的反例，不要在别处调用）
def apply_repetition_penalty_naive(logits: np.ndarray, prev: list[int],
                                   penalty: float) -> np.ndarray:
    if penalty == 1.0 or not prev:
        return logits
    out = logits.copy()
    idx = np.unique(np.asarray(prev, dtype=np.int64))
    out[idx] = out[idx] / penalty       # 负 logit 除以 penalty 会变大！
    return out
```

`selftest()` 里用 `-2.0` 这个负 logit 钉死两者的差异（`_lab/sampling.py:319-324`）：正确实现给出的结果比 `-2.0` 更小；朴素实现给出 `-2.0 / 1.2 ≈ -1.667`，比 `-2.0` 更大——**惩罚把这个 token 的概率抬高了，而且没有任何异常提示这件事发生了**。

`apply_temperature()`（`_lab/sampling.py:89-97`）只有一行核心逻辑 `logits / t`，`## 2.1` 已经讲过它的极限行为，这里补一条实现细节：函数对 `t<=0` 会主动 `raise ValueError`（`_lab/sampling.py:95-96`），不允许调用方在这个分支里意外除零——贪心必须走 `is_greedy` 那条独立路径，不能指望 `apply_temperature` 兜底。

`top_k_filter()`（`_lab/sampling.py:100-106`）用 `np.partition` 找到第 k 大的阈值，小于阈值的位置全部置 `-inf`；`k<=0` 或 `k>=vocab` 时是空操作，这两个边界条件不是可有可无的判断——如果漏掉 `k>=n` 这条，`np.partition(logits, n-k)` 在 `k>n` 时会直接越界。

`top_p_filter()`（`_lab/sampling.py:109-129`）是四个算子里最容易在边界条件上写错的一个，函数文档里专门点出了这条：

```python
# _lab/sampling.py:112-118
两个必须注意的点：
  * **永远保留至少一个 token**。判据写成「它*之前*的累计 < p」而不是
    「含它的累计 <= p」，第一个 token 的"之前累计"恒为 0，所以必然留下。
    写成后者时，只要 top-1 概率本身就大于 p，集合就空了，采样直接崩。
```

对应到实现是 `cum_before = np.cumsum(probs) - probs`（先算出"这个位置之前"的累计，`_lab/sampling.py:124`）和紧接着的 `keep_sorted[0] = True`（`_lab/sampling.py:126`，显式兜底）。`test_top_p_never_empties_the_candidate_set`（`_lab/tests/test_serving.py:56-60`）用 `p` 从 `1e-9` 到 `0.5` 扫了一遍，确认候选集永远至少有 1 个。

`filter_order_matters()`（`_lab/sampling.py:132-144`）把 `## 2.2` 手算的两种顺序包成一对能直接对比的调用：

```python
# _lab/sampling.py:142-144
kp = np.isfinite(top_p_filter(top_k_filter(logits, k), p)).sum()
pk = np.isfinite(top_k_filter(top_p_filter(logits, p), k)).sum()
return int(kp), int(pk)
```

`test_filter_order_changes_the_candidate_set`（`_lab/tests/test_serving.py:63-71`）直接断言 `(kp, pk) == (1, 2)`，把 `## 2.2` 手算的结果钉成了一条可回归的测试，不是"讲完就完"的口头结论。

### 3.3 `Sampler`：每条请求自己的随机数发生器

```python
# _lab/sampling.py:149-173
class Sampler:
    def __init__(self, params: SamplingParams):
        self.p = params
        self.rng = np.random.default_rng(params.seed)

    def __call__(self, logits: np.ndarray, prev: list[int]) -> int:
        p = self.p
        logits = apply_repetition_penalty(logits, prev, p.repetition_penalty)
        if p.is_greedy:
            return int(np.argmax(logits))
        logits = apply_temperature(logits, p.temperature)
        logits = top_k_filter(logits, p.top_k)
        logits = top_p_filter(logits, p.top_p)
        probs = M.softmax(logits[None, :].astype(np.float32))[0]
        probs = probs / probs.sum()            # rng.choice 对归一化很敏感
        return int(self.rng.choice(len(probs), p=probs))
```

（`_lab/sampling.py:149`，`__call__` 在 `_lab/sampling.py:163-173`）两条设计值得单独拎出来：第一，**重复惩罚永远先做**，连贪心分支都不例外（`_lab/sampling.py:165` 在 `if p.is_greedy` 判断之前），这正是 `## 1` 表格里"贪心 + 重复惩罚"那一行能生效的原因——重复惩罚在这里被当成"改变 logits 本身"的一步，而不是"采样算子"的一部分。第二，`self.rng = np.random.default_rng(params.seed)`（`_lab/sampling.py:161`）是**每个 `Sampler` 实例自己的随机数发生器**，不是从某个全局单例借来的。这不是洁癖：如果整个引擎共用一个全局 `rng`，某条请求这一步抽到什么就取决于"同一批里还有谁、按什么顺序被处理"，于是同样的 prompt、同样的 `seed`，在不同负载下给出不同结果，而且不会有任何报错提示这件事发生了。`selftest()` 用一对对照实验把这条钉死（`_lab/sampling.py:326-346`）：`s1`/`s2` 两个独立 `Sampler` 用同一个 `seed=42`，`s2` 在每次调用之间被另一个 `seed=999` 的 `Sampler` "打断"，结果依然和不受打断的 `s1` 完全一致（`_lab/sampling.py:335-336`）；紧接着用两个共享同一个 `np.random.default_rng(42)` 的裸 rng 做反例，"打断"之后序列立刻不一致（`_lab/sampling.py:345-346`）。这条测试的镜像版本在 `test_per_request_rng_is_batch_invariant`（`_lab/tests/test_serving.py:95-110`）。

### 3.5 `StreamGuard`：流式输出的全部难点都在这一个类里

```python
# _lab/sampling.py:223-230
def __init__(self, stop: tuple[str, ...] = ()):
    self.stop = tuple(s for s in stop if s)
    self.hold = max((len(s) for s in self.stop), default=1) - 1
    self.dec = codecs.getincrementaldecoder("utf-8")()
    self.text = ""       # 已解码出的全部文本（含扣住没发的尾巴）
    self.emitted = 0     # 已经发给用户的字符数
    self.stopped = False
    self.stop_hit: str | None = None
```

`hold`（`_lab/sampling.py:225`）就是 `## 2.4` 推出的 `max(len(stop))-1`；`self.dec` 是 `## 2.3` 讲的增量 UTF-8 解码器；`self.text`/`self.emitted` 是这个状态机的核心——`text` 永远是"已经解码出的全部文本"（包括还没发出去的尾巴），`emitted` 是这段文本里已经确认安全、真正发给用户的边界。`push()`（`_lab/sampling.py:232-249`）每喂一个 token 更新一次这两个状态：

```python
# _lab/sampling.py:232-249
def push(self, token_id: int) -> str:
    if self.stopped:
        return ""
    self.text += self.dec.decode(TOY_VOCAB[token_id])
    for s in self.stop:
        i = self.text.find(s)
        if i >= 0:
            out = self.text[self.emitted:i]
            self.emitted = max(i, self.emitted)
            self.stopped, self.stop_hit = True, s
            return out
    safe = len(self.text) - self.hold
    if safe <= self.emitted:
        return ""
    out = self.text[self.emitted:safe]
    self.emitted = safe
    return out
```

三步顺序不能换：先用增量解码器追加解码（可能什么都追加不上，`self.dec.decode()` 内部有自己的字节缓冲区，`## 2.3` 讲过这一点）；再检查有没有命中停止串，命中就把命中点**之前**的部分发出去、之后的全部丢弃并停止；都没命中，才按 `## 2.4` 的公式算出这一刻的安全边界 `safe`，发出 `emitted` 到 `safe` 之间的新增部分。`## 1` 里 token 1 只发出 `'He'`，正是这最后四行代码在 `hold=3` 时算出来的结果。

`flush()`（`_lab/sampling.py:251-261`）在生成正常结束（EOS 或 `max_new` 用完）时调用，把最后还扣着的尾巴放出来：

```python
# _lab/sampling.py:251-261
def flush(self) -> str:
    if self.stopped:
        return ""
    out = self.text[self.emitted:]
    self.emitted = len(self.text)
    return out
```

文档字符串把这条踩坑写在了代码旁边（`_lab/sampling.py:255-256`）：**忘了调用它是流式实现最常见的 bug**——输出总是少最后一两个字，而且短输出比长输出更容易暴露，因为扣住的比例更大。`test_flush_releases_the_held_tail`（`_lab/tests/test_serving.py:150-155`）直接构造了一个 `hold=3` 的例子：只 `push` 两个 token，拼出来的字符串**必须**跟 `"Hello!"` 不相等（尾巴被扣着），加上 `flush()` 之后才相等——这条测试是"忘了 flush"这个静默 bug 唯一能被抓住的地方。

`test_streaming_concatenation_equals_bulk_decode`（`_lab/tests/test_serving.py:115-120`）把 `## 3.4` 提到的判据落成代码：`push` 每个 token 拼出的片段，加上最后的 `flush()`，必须逐字符等于 `toy_decode()` 一次性解码的结果——这是流式实现**唯一**的正确性标准，其它一切都是这条标准的推论。`test_partial_utf8_is_held_back_not_mangled`（`_lab/tests/test_serving.py:123-133`）和 `test_stop_string_straddling_token_boundary_is_caught`（`_lab/tests/test_serving.py:136-141`）分别单独钉住 `## 2.3` 和 `## 2.4` 讲的两条机制。

### 3.7 自检怎么把上面每一条都钉成了断言

`selftest()`（`_lab/sampling.py:285-367`）不是简单地把每个函数跑一遍看不报错，而是针对 `## 2` 每一条机制**专门构造能暴露对错的输入**：`## 3.2` 的重复惩罚符号反例用的是精心选的负 logit `-2.0`（`_lab/sampling.py:319`）；`## 3.3` 的批不变性反例特意让另一个 `Sampler` 在中间"打断"（`_lab/sampling.py:332-334`）；`## 3.5` 的 UTF-8 反例特意在两次 `push` 之间断开一个多字节字符（`_lab/sampling.py:350`，token 4 和 5 分两次喂）。这不是覆盖率意义上的"跑到了这一行"，是**专门为每一类静默 bug 设计的对抗性输入**——`## 6` 会反过来，把这些输入当成"如果代码写错了会看到什么现象"的示范。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang，带 `引擎:文件:行`）

### 4.1 采样施加顺序与重复惩罚的符号，真实引擎是同一套答案

vLLM 的 `Sampler` 把整条流水线的顺序写进了类文档字符串本身，而不是散落在代码各处让人自己拼——顺序是先罚分（含重复惩罚）、再温度、再 top-k/top-p：

```python
# vllm:vllm/v1/sample/sampler.py:21-60（节选）
class Sampler(nn.Module):
    """
    ...
    6. Apply penalties
        a) Repetition penalty
        b) Frequency penalty
        c) Presence penalty
    7. Sample the next tokens. `sample` method performs the following steps:
        a) If not `all_random`, perform greedy sampling. ...
        b) Apply temperature.
        c) Apply logit processors which are argmax-invariant, by default
           the min_p processor.
        d) Apply top_k and/or top_p.
        e) Sample the next tokens with the probability distribution.
    ...
    """
```

这跟 `_lab/sampling.py:163-173` 的 `Sampler.__call__` 是同一个顺序——先罚分、再判断是否贪心、再温度、再 top-k/top-p——不是巧合。**罚分作用在原始 logit 上、跟温度和截断算子解耦**，是这套顺序背后共同的道理：如果先做温度缩放再罚分，罚分的"力度"会随温度变化而变化，两个本该独立的旋钮就绞在一起了。

**top-k 先于 top-p** 这条 `## 2.2` 手算过的顺序，vLLM 的实现是逐字对应：

```python
# vllm:vllm/v1/sample/ops/topk_topp_sampler.py:367-406（节选）
def apply_top_k_top_p_pytorch(logits, k, p, allow_cpu_sync=False):
    logits_sort, logits_idx = logits.sort(dim=-1, descending=False)
    if k is not None:
        # Apply top-k.
        top_k_mask = logits_sort.size(1) - k.to(torch.long)
        top_k_mask = logits_sort.gather(1, top_k_mask.unsqueeze(dim=1))
        top_k_mask = logits_sort < top_k_mask
        logits_sort.masked_fill_(top_k_mask, -float("inf"))
    if p is not None:
        # Apply top-p.
        probs_sort = logits_sort.softmax(dim=-1)
        probs_sum = torch.cumsum(probs_sort, dim=-1, out=probs_sort)
        top_p_mask = probs_sum <= 1 - p.unsqueeze(dim=1)
        top_p_mask[:, -1] = False   # at least one
        logits_sort.masked_fill_(top_p_mask, -float("inf"))
    return logits.scatter_(dim=-1, index=logits_idx, src=logits_sort)
```

top-k 的 `masked_fill_(-inf)`（`vllm:vllm/v1/sample/ops/topk_topp_sampler.py:392-396`）先执行，softmax（`vllm:vllm/v1/sample/ops/topk_topp_sampler.py:398`）是在**已经被 top-k 截断过的** `logits_sort` 上重新做的——这正是 `## 2.2` 手算里"top-k 砍掉尾巴后概率被重新归一化"那一步在生产代码里的样子。`top_p_mask[:, -1] = False`（`vllm:vllm/v1/sample/ops/topk_topp_sampler.py:404`）跟 `_lab/sampling.py:126` 的 `keep_sorted[0] = True` 是同一条"永远保留至少一个"的兜底，只是排序方向相反（vLLM 升序排、`_lab/sampling.py` 降序排，兜底的位置因此一个在末尾一个在开头）。

重复惩罚的符号分支，vLLM 也不是从头造了一套逻辑，是同一个 `torch.where` 两路分支：

```python
# vllm:vllm/_custom_ops.py:309-321（节选，apply_repetition_penalties_torch）
def apply_repetition_penalties_torch(logits, prompt_mask, output_mask, repetition_penalties):
    repetition_penalties = repetition_penalties.unsqueeze(dim=1).repeat(1, logits.size(1))
    penalties = torch.where(prompt_mask | output_mask, repetition_penalties, 1.0)
    # If logits are positive, divide by penalty, otherwise multiply by penalty.
    scaling = torch.where(logits > 0, 1.0 / penalties, penalties)
    logits *= scaling
```

`torch.where(logits > 0, 1.0 / penalties, penalties)`（`vllm:vllm/_custom_ops.py:320`）跟 `_lab/sampling.py:71` 的 `np.where(v > 0, v / penalty, v * penalty)` 是完全同构的两行代码——正 logit 除、负 logit 乘。**这不是本库为了教学简化出来的特例，是生产引擎的真实做法**：`## 3.2` 那个"朴素实现"反例，如果原样搬进 vLLM 会犯一模一样的错误。

### 4.2 停止串的 hold-back 缓冲：同一个公式 `max(len(stop)) - 1`

`## 2.4` 推出的这条公式，vLLM 的增量解码器（`IncrementalDetokenizer`）是原样实现的，甚至变量名的意图都一样：

`get_next_output_text()` 用这个缓冲长度切出"这一刻能安全发出去"的文本，跟 `_lab/sampling.py:244-249` 的 `safe = len(self.text) - self.hold` 是同一个思路：

### 4.3 增量 UTF-8 解码器：真实引擎也不用手写 `bytes.decode()`

`## 2.3` 讲过手写解码在半个字符上会出问题，vLLM 的 `FastIncrementalDetokenizer` 走的是标准 `tokenizers` 库自带的流式解码对象，跟 `_lab/sampling.py:226` 用 `codecs.getincrementaldecoder("utf-8")()` 是同一个层级的选择——**都不自己维护字节缓冲区，把这件事交给一个专门写好、测过边界情况的组件**：

```python
# vllm:vllm/v1/engine/detokenizer.py:184-187（节选）
self.stream = tokenizers.decoders.DecodeStream(
    ids=request.prompt_token_ids,
    skip_special_tokens=self.skip_special_tokens,
)
```

每来一个新 token，调用的是这个流对象的 `step()`，而不是对 token 的原始字节做任何手工拼接：

```python
# vllm:vllm/v1/engine/detokenizer.py:224-226（节选，_protected_step）
def _protected_step(self, next_token_id: int) -> str | None:
    try:
        token = self.stream.step(self.tokenizer, next_token_id)
    except (OverflowError, TypeError):
        ...
```

值得留意的一点是：即便用了这样一个专门写好的增量解码器，vLLM 还是在 `_protected_step` 里包了一层 `try/except`（`vllm:vllm/v1/engine/detokenizer.py:224-250`），处理的是分词器在极少数情况下产生非单调、无效 UTF-8 输出、把 `DecodeStream` 内部状态搞坏的边界情况——**"用了正确的组件"不等于"从此不用再考虑边界情况"，只是把大部分边界情况的复杂度封装掉了，剩下的极端情况仍然需要显式处理**，`_lab/sampling.py` 的玩具词表足够小、不会撞上这类分词器实现细节的坑，但这提醒了一件事：真实系统里"增量解码"这个组件本身也不是绝对可靠的黑盒。

### 4.4 SGLang：detokenize 是独立进程，因为它是 CPU 活会阻塞引擎循环

前三点讲的是"同一件事真实引擎怎么做"，这一点讲一个 `_lab/sampling.py` 完全没有涉及、但对生产系统很关键的架构决策：**detokenize 不在做前向计算的那个进程里做**。SGLang 的模块文档字符串开门见山：

```python
# sglang:python/sglang/srt/managers/detokenizer_manager.py:14
"""DetokenizerManager is a process that detokenizes the token ids."""
```

它是真的用 `multiprocessing.Process` 启动出来的独立进程，不是同进程里的一个类：

```python
# sglang:python/sglang/srt/entrypoints/engine.py:993-998（节选）
if get_serving().detokenizer_worker_num <= 1:
    proc = mp.Process(
        target=run_detokenizer_process_func,
        args=(server_args, port_args),
    )
    proc.start()
```

原因跟 `## 0` 说的"这一整段全是工程问题"直接呼应：detokenize——把 token id 转文本、判断增量、扫停止串——是纯 CPU 活，字符串操作、正则/子串查找不会用到 GPU；如果这些工作跟负责调度和前向计算的主循环挤在同一个进程、同一条控制流里，每一步 decode 都要先等这段 CPU 处理完才能进入下一次调度决策，等于让 GPU 空转等 CPU。**独立进程把这段延迟从"引擎主循环的关键路径"里挪了出去，跟 GPU 的前向计算天然并行**——这是 `## 0` 说"从 token 到用户"这一段全是工程问题的一个直接推论：解决方案不总是"算法层面把逻辑写对"，有时候是"把这件事搬到不会卡住别人的地方去做"。

SGLang 判断"这段解码是不是不完整"用的思路跟 `codecs` 增量解码器不同，是一种更轻量的事后启发式——检查解码结果**是否以替换字符结尾**：

```python
# sglang:python/sglang/srt/managers/detokenizer_manager.py:380-393（节选）
pending = s.sent_offset - s.decoded_text_len
if new_text and not new_text.endswith("�"):
    # Clean text: commit to decoded_text and advance offsets.
    s.append_decoded_text(new_text)
    ...
else:
    # Incomplete UTF-8: emit the printable prefix only; do not
    # commit (token offsets stay so the next iteration retries
    # with more tokens).
    printable = find_printable_text(new_text)
    ...
```

这里的逻辑是：先用底层分词器的 `decode()` 正常解码（分词器内部对不完整字节默认会产出 `�`），再检查结果**是不是以 `�` 收尾**——如果是，就认定这是"半个字符"，只发出更早之前已经确认完整的那部分，把这一段的 offset 原地不动，等下一个 token 到来再重试。这跟 `codecs` 增量解码器"内部维护字节缓冲区、天然知道自己攒了几个字节"的做法在机制上完全不同——**一个是显式状态机（知道自己在等什么），一个是事后从解码结果的表面特征反推（猜测这大概率是不完整）**——两者能达到同样的效果，是因为 `�` 在这个场景下几乎只会由不完整字节产生；但这也意味着如果某个真实模型合法生成了 `�` 这个字符本身（它确实是 Unicode 里一个真实存在的码位），SGLang 这条启发式会误判成"还没解码完整"而多扣一轮——这是"轻量启发式"相对"显式状态机"要付出的代价，`## 5` 会把这条取舍归纳成一条决策。

**本篇跟这四点对照没有覆盖到的东西**：`min_p`/`logit_bias`/`bad_words` 这类更多的 logits processor（vLLM 文档字符串第 5 步提到）、批量场景下罚分张量化的实现细节（`vllm:vllm/v1/sample/ops/penalties.py:10-38` 的 `apply_all_penalties`，本篇只讲了单条请求）、以及 SGLang 多个停止串同时命中时"选择在文本里最先出现的那个"这条规则（`sglang:python/sglang/srt/managers/detokenizer_manager.py:177-198` 的 `trim_matched_stop` 文档里写了一句 `# TODO(lmzheng): handle the case where multiple stop strs are hit`，说明这条规则连生产引擎自己都还留了一个已知的未尽之处）——这些都不是本篇要讲的核心机制，`_lab/sampling.py` 刻意只做单条请求、单一 stop 匹配这层最小实现，留出的复杂度会在 `[[04-结构化输出]]`（更强的约束采样）和 `[[03-从玩具到生产还差什么]]` 里再谈。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：采样算子顺序写死（罚分 → 贪心判断 → 温度 → top-k → top-p），不做成可配置的流水线。**
- 为什么这样：`## 2.2` 证明了顺序会改变候选集——如果顺序本身是用户可调的自由度，两个用户填了同样的 `(k, p)` 却因为顺序不同拿到不同的候选集，这是一种很难在 API 文档里讲清楚、极容易引发困惑的隐藏参数；固定顺序换来的是"给定 `(temperature, top_k, top_p, repetition_penalty)`，输出分布是唯一确定的"，`## 4.1` 也看到 vLLM 把顺序钉进了类文档字符串本身，不作为运行时可调项。
- 不这样会怎样：要么需要额外暴露一个"顺序"参数并在文档里讲清楚它对结果的影响（`## 2.2` 那种手算的复杂度会转嫁给每一个使用者），要么各处理由自己隐式决定顺序、不同代码路径之间互相不一致——这比"没有配置顺序"更糟，是"顺序不可预测"。
- 什么时候可以不这样：在研究/调参场景（不是稳定对外服务）里，把每个算子做成可插拔、可重排的 pipeline（类似 vLLM 的 `logits_processor` 列表机制，`## 4.1` 提过第 5 步"Apply logit processors"就是这样一层可扩展的挂载点）反而有价值——探索新采样策略时，锁死顺序反而是束缚。`_lab/sampling.py` 没有做这层抽象，是教学场景下"少一个变量、多一分清晰"的取舍。

**决策二：每条请求持有独立的 `np.random.default_rng(seed)`，不共用引擎级别的全局 rng。**
- 为什么这样：`## 3.3` 的对照实验已经证明——共用全局 rng 时，一条请求这一步抽到什么取决于同批里还有谁、按什么顺序被处理；每请求独立 rng 换来的是**批不变性**：同一个 `seed` 在任何负载下都复现同样的输出序列，这是"可复现"这条判据（`## 2.1` 提过的、替代逐位比较的新护栏）能够成立的前提。
- 不这样会怎样：某条请求的输出会随着"同批里恰好有谁"发生变化，而且这个变化不会有任何报错提示——调试时想复现一个线上 bug，同样的 prompt、同样的 seed，跑出来的结果对不上，因为负载（同批的其它请求）没法在本地精确重放。
- 什么时候可以不这样：如果整个系统压根不承诺"同 seed 可复现"（比如生产环境干脆不接受用户传 `seed`，或者接受但明确告知不保证跨批次复现），全局 rng 能省下每条请求构造一个独立 rng 对象的开销——但这个开销在真实系统里通常小到可以忽略，`## 4` 也没有看到任何一个真实引擎选择这条路径，这基本是一条没有真正理由不做的决策。

**决策三：`StreamGuard` 用"扣住最后 `max(len(stop))-1` 个字符"这种显式缓冲，而不是"生成全部结束后再统一处理"。**
- 为什么这样：流式接口存在的意义就是尽早把内容展示给用户（降低首字延迟），如果等全部生成结束才处理停止串和输出，等于放弃了流式的核心价值，接口即使叫"流式"，行为上跟非流式没有区别；显式缓冲把"不确定能不能发"的范围限制到最小——只有最后 `L-1` 个字符处于待定状态，其余已经解码出的内容都能立刻确认安全、尽早发出。
- 不这样会怎样：两个极端都不好——完全不流式，首字延迟等于整个生成耗时；或者反过来，激进地"拿到字符立刻发"、不做任何缓冲，`## 6` 会展示这样做的后果是命中停止串时已经把停止串本身的一部分发给用户了，而这部分内容根本收不回来。
- 什么时候可以不这样：如果协议约定服务端"宁可多发"、把停止串裁剪的责任转交给客户端自己再做一次（客户端拿到完整流之后自己找停止串截断），服务端这层缓冲确实可以省掉——但这只是把复杂度转嫁给了每一个调用方，不是让它消失，而且要求所有客户端都正确实现这层裁剪逻辑，这个假设在真实生态里通常不成立。

**决策四：用标准库的增量解码器（`codecs.getincrementaldecoder`），不手写字节缓冲状态机。**
- 为什么这样：UTF-8 的合法性判断——一个前导字节后面该跟几个续接字节、怎么识别一段字节是不是"合法但不完整"——本身是一套边界情况繁多的规则，标准库的实现经过广泛测试；`## 4.3` 看到即便是生产级的 vLLM，也是复用 `tokenizers` 库自带的 `DecodeStream`，而不是自己在 detokenizer 里重新写一遍字节判断逻辑。
- 不这样会怎样：`## 6` 会展示两种自己动手容易犯的错——要么直接 `bytes.decode()` 在半个字符上崩溃，要么用 `errors="replace"` 产生不可逆的乱码；即便侥幸把状态机写对了，也要为一堆 UTF-8 边界情况（4 字节字符、代理对之类）单独写测试，这些测试标准库已经替你写过一遍了。
- 什么时候可以不这样：如果确定分词器本身保证每个 token 都解码成完整字符（存在这样的分词器，比如某些纯字符级/词级的方案），这层增量解码器确实是多余的开销——但这依赖对具体分词器实现细节的假设，一旦换成字节级 BPE（GPT 系、LLaMA 系目前普遍如此，`_lab/sampling.py` 的玩具词表也是在模拟这一点），这条假设立刻不成立，省下来的这层保护网也就没有了。

**决策五：`finish_reason` 是单一字符串、按固定优先级（`stop` > `eos` > `length`）返回，不是多值集合。**
- 为什么这样：客户端的重试/续写逻辑通常是一个简单的分支判断，单一、有明确优先级的字符串能直接映射到一个动作；`## 2.5` 讲过 `stop` 优先的语义理由——"模型按用户要求主动停"比"凑巧撞上长度上限"信息量更大，值得优先采信。
- 不这样会怎样：如果三个条件都上报（比如返回一个集合），每一个客户端都要各自实现一套"到底该信哪个"的优先级逻辑，等于把这个决策重新下放了一遍，不同客户端很可能实现出互相不一致的行为——这正是 `## 3.6` 强调"这三个 `if` 的顺序不能随便换"背后的动机在系统层面的放大。
- 什么时候可以不这样：调试或离线分析场景确实需要知道"这次是不是好几个条件同时触发的"（比如判断某个停止串设得是不是太短，导致几乎每次都会和 `length` 同时命中，这是配置本身有问题的信号）——这种情况下可以在对外的单一 `finish_reason` 字段之外，另外挂一个诊断性质的多值字段供内部排查用，但对外暴露给客户端做决策的字段，仍然应该保持单一优先级，不能让"多个原因同时成立"变成客户端自己要处理的分支。

## 6. 常见错误与踩坑

本篇开头就说过：这一段的坑几乎全是**静默**的——程序不崩溃、不报异常，只是结果不对，或者要凑巧的条件才会暴露。下面六条每一条都点出"错了会看到什么现象"。

**错误一：忘了调用 `flush()`。**
`_lab/sampling.py:255-256` 的文档字符串里专门写了这条："忘了调用它是流式实现最常见的 bug"。**错了会看到什么现象**：输出总是少最后一两个字，而且**短输出比长输出更容易暴露**——因为扣住的 `hold` 个字符占输出总长度的比例更高，一段只有 6 个字符的回复被扣掉最后 3 个，用户能明显看出"话没说完"；一段几百字的长回复少最后 3 个字反而容易被忽略过去。`test_flush_releases_the_held_tail`（`_lab/tests/test_serving.py:150-155`）是抓这个 bug 的唯一测试：只 `push` 两个 token 不 `flush`，断言拼出来的字符串**必须**跟完整结果不相等——如果这条断言被删掉或者弱化成"结果included在完整结果里"这种更宽松的判据，这类 bug 会在测试里也变成静默的。

**错误二：用 `errors="replace"` 兜底 UTF-8 解码失败。**
`## 2.3` 讲过原理，这里补一句现象描述：**错了会看到什么现象**——不是异常，是文本流里冒出一个或几个 `�`（U+FFFD），而且这个乱码是**永久的**：即便后续 token 把这个字符真正需要的字节全部补齐了，用户屏幕上已经定格的 `�` 也不会被替换或更正，因为这段文本早已经发出去了。`selftest()` 用 `chk(all(chr(0xFFFD) not in x for x in parts), ...)`（`_lab/sampling.py:355-356`）在全部片段里显式扫描有没有 `U+FFFD`——这是专门为这一类错误设计的检查，如果代码里悄悄把 `codecs` 增量解码器换成了带 `errors="replace"` 的普通 `decode()`，这条断言会立刻变红。

**错误三：共用一个全局 `rng`，不给每条请求独立的随机数发生器。**
`## 3.3`/`## 5` 决策二已经讲过机制。**错了会看到什么现象**：单独测试一条请求（同 prompt、同 seed）时结果完全正常、可复现；一旦放进真实的并发/批处理环境，同样的 prompt、同样的 seed，只因为同批里多了或少了别的请求，输出就变了——这种"孤立测试通过、放进真实负载就复现不了"的症状是这类 bug 的典型指纹，`_lab/sampling.py:338-346` 用一对最小反例把它复现了出来：两个共享同一个 `np.random.default_rng(42)` 的调用序列，只要中间被另一次 `integers()` 调用"打断"过一次，后续结果就跟没被打断时完全不同。

**错误四：`top_p_filter` 的判据写成"含它的累计 `<= p`"而不是"它*之前*的累计 `< p`"。**
`## 2.1`/`## 3.2` 讲过这条边界条件。**错了会看到什么现象**：多数情况下看不出问题（大部分分布的 top-1 概率不会大到超过 `p`），但只要遇到一个**尖锐分布**——top-1 概率本身就大于 `p`（比如模型对下一个 token 非常确定，给出 `0.95` 的概率，而 `p=0.9`）——错误判据会把这唯一一个候选也筛掉，候选集变成空集，后续 `rng.choice(len(probs), p=probs)` 在一个全零（或者因为浮点误差变成负数）的概率数组上要么直接抛异常，要么在没有异常保护的实现里悄悄产出 `NaN` 进而让整个生成过程崩掉。这个 bug 的隐蔽之处在于：只要开发时测试用的分布不够尖锐（比较"平"的分布不会触发它），这个边界条件错误可以在测试环境里长期不被发现，直到线上遇到模型给出高置信度输出的那一刻才炸。

**错误五：重复惩罚符号写反——`apply_repetition_penalty_naive` 那种写法。**
`## 3.2` 已经用真实数字过了一遍：`-2.0 / 1.2 ≈ -1.667`，比原值更大。**错了会看到什么现象**：不是崩溃，是模型**变得更爱重复**——本来是想通过惩罚抑制重复，结果对已经出现过的负 logit token，惩罚反而把它的分数抬高了，越生成越倾向于把之前出现过的内容再说一遍，而且这个方向性错误不会有任何异常或警告，只有对照"重复惩罚开启前后，重复率是变高还是变低"这样一个具体的指标才能发现——`## 1` 第一张表如果这里的实现是反的，"贪心 + 重复惩罚 1.3"这一行的"最长连续重复"不会从 6 降到 1，反而可能比不加惩罚的贪心基线更差。

**错误六：停止串检测只看"当前这一个 token 解码出的文本"，不维护跨 token 的完整上下文。**
`## 2.4` 讲过停止串可能横跨 token 边界这件事本身；这里补一条具体的错误实现方式：如果代码逻辑是"每来一个 token，把这个 token 单独 decode 之后检查里面有没有停止串"，那么停止串 "STOP" 由 `b"ST"`（id 7）和 `b"OP"`（id 8）两个 token 分别贡献一半时，两次检查都不会命中——**错了会看到什么现象**：这个停止串会被彻底漏检，生成一直跑到 `max_new` 或 EOS 才停，`finish_reason` 报的是 `"length"` 或 `"eos"`，而不是本该报的 `"stop"`，用户设置的停止条件形同虚设，而系统不会有任何提示告诉你这条规则没生效。`test_stop_string_straddling_token_boundary_is_caught`（`_lab/tests/test_serving.py:136-141`）是专门为这类错误设计的：它构造的输入序列（`[1, 2, 7, 8, 10]`）保证停止串恰好被切在两个 token 之间，如果检测逻辑退化成"只看单 token"，这条测试会直接失败。

- `[[04-结构化输出]]`——本篇的停止条件是"匹配到某个字符串就停"，结构化输出是这件事的一个更强版本：不是等生成完再检查，是**每一步都提前把候选集限制在语法允许的范围内**，跟 `## 3.2` 讲的 top-k/top-p 是同一层"过滤候选集"的机制，只是过滤依据从概率排名换成了语法约束。
- `[[01-正确性怎么保证]]`——本篇几乎所有测试（`## 3.7`）都不是"跑一遍看不报错"，是专门针对某一类静默 bug 设计的对抗性输入；那一篇会把这套"怎么为静默 bug 设计测试"的方法论从本篇这个具体案例里抽出来，讲成可以复用到别处的一般原则。
