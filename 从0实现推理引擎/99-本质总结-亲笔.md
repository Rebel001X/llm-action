# 99 · 本质总结（亲笔）

> 这一篇我自己写。前面二十多篇是过程，这一篇是**我写完之后真正相信的东西**。
> 它不复述细节 —— 细节在各章里，而且每一条都能跑。
> 这里只留那些**五年后还成立**的部分。

---

## 1. 如果只能记住三句话

> **一、单条请求的解码，从第一步起就在访存瓶颈的最底部，没有更低可去。**
> 引擎里几乎每一个设计，都是这一条的推论。
>
> **二、引擎里的优化几乎全是「等价变换」，所以它们出错时不崩，只是悄悄换个答案。**
> 唯一有效的护栏是「算两遍，逐位比」—— 但这个护栏有一个结构性盲区。
>
> **三、「用什么语言」是个错问题。** 正确的问题是「哪一层用什么语言」。

下面把这三句各自展开一次。

## 2. 一条物理事实，解释了六件看起来无关的事

`_lab/minigpt.py:197` 的 `analytic_cost()` 算出来的那张表，是这个库的地基：

```
     ctx     bs=1     bs=4    bs=16    bs=64   bs=256    KV占访存(bs=64)
      16     0.50     1.89     6.21    14.50    21.74           54.7%
     256     0.50     1.17     1.76     2.02     2.10           95.1%
    1024     0.50     0.75     0.86     0.90     0.90           98.7%
   16384     0.50     0.52     0.52     0.53     0.53           99.9%
```

**第一列恒为 0.50，与上下文长度完全无关。** 原因朴素到近乎乏味：
fp32 下每个权重参数、每个 KV 元素都是"做 1 次乘加（2 FLOP）、读 4 字节"，
所以强度必然是 `2/4`。换 fp16 就是 1.0。**这是个下界，不是个测量值。**

我原以为这里会看到一条"上下文越长越受限"的下降曲线，还为它编好了解释。
**真相是它一开始就在底部，压根没得降。**（这个错误的完整经过在
[[01-正确性怎么保证]] 的打脸清单第 1 条。）

现在看这一条能解释多少件事：

| 现象 | 它其实是同一条事实的哪一面 |
|---|---|
| **连续批处理为什么必须有** | 权重读一遍被整批共用，**只有增大 batch 能抬高强度**；KV 是每条请求私有的，抬不动 |
| **长上下文为什么杀吞吐** | ctx=16384 时 KV 占了 99.9% 的访存，batch 从 1 加到 256 只把强度抬了 0.03 |
| **KV 缓存到底省了什么** | 省的是计算（O(n²) → O(n)），**不是访存**。它把"算不完"变成"读不完"，decode 仍然在底部 |
| **FlashAttention 为什么有用** | 它**一个 FLOP 都没省**，省的是那张 T×T 矩阵的搬运。T=32768 时朴素要同时持有 10.7 亿个数，分块恒为 1024 个 |
| **量化为什么有用** | weight-only 量化**一次乘法都没省**，甚至多了反量化。它省的是读权重的字节数 |
| **投机解码为什么划算** | 验 5 个 token vs 验 1 个：**FLOPs ×5.00，访存仅 ×1.000** —— 因为这几个 token 同属一条请求、共用一份 KV |

六件事，一个原因。

**推论也跟着来**：凡是"多算一点、少读一点"的交换，在 decode 上都是赚的；
凡是"少算一点、多读一点"的交换，都是亏的。
这一条能替你判断绝大多数没见过的新技巧值不值得看。

**但它有个边界，而且这个边界是我被自己的代码纠正过的**：
上面这些"省访存"的手段，**收益上限就是它占的那一份，一分不多**。
权重 int8 在 batch=1 时省 74.6% 访存，在 batch=256 时只省 32.5%；
KV int8 在 ctx=16384/batch=64 时省 73.2%，在 ctx=128/batch=1 时只省 0.38%。
而且 **KV 要成为主项，需要"长上下文"和"大 batch"两个条件同时成立** ——
我原本以为长上下文一个条件就够，实测 ctx=16384 但 batch=1 时 KV 只占 39.5%，
权重仍是主项。**单条请求的 KV 再长也只有一份，而权重是固定的一大坨。**
（`_lab/tests/test_advanced.py:293`）

## 3. 引擎的 bug 不崩，只换答案

这是我写完这个库之后感受最深的一条，而且它和普通业务系统正好相反。

业务系统的 bug 大多会显形：异常、错误码、数据对不上。
推理引擎的 bug 被模型本身的"合理性"掩盖了 ——
**模型总能给你一段像模像样的话，无论它中间读到的是不是别人的 KV。**

具体点名一下这个库里那些"错了也不会响"的地方：

- **前缀缓存的块哈希不做链式**：`"1,2|5,6"` 和 `"3,4|5,6"` 的第二块撞成同一个 key，
  两条请求的历史完全不同却共用了 K/V。没有异常，只是答案错了。
- **引用计数漏一次 decref**：块被提前还回空闲池，第三条请求分到它并覆写，
  原持有者下一次 `gather()` 读到的是别人的 KV。形状合法、没有 nan。
- **重复惩罚忘了分正负**：`-2.0 / 1.2 = -1.667` **比原来更大**，
  于是"惩罚"把重复 token 的概率推高了 —— 越惩罚越复读。
- **投机解码的验收规则写成"`p(x) ≥ q(x)` 就收"**：跑起来完全正常，文本通顺，
  只是输出分布不是目标模型的。实测全变差 0.129，是正确实现的 **56 倍**。
- **流式输出用 `errors="replace"` 处理半个汉字**：不崩，只是往已经发出去的文本里
  永久钉了一个 U+FFFD，后半截字节到了也补不回来。

所以本库的测试主力是"算两遍，逐位比"。它极其有效 —— 25 条差分断言在 0.14 秒内跑完。

**但它有一个结构性盲区，而这是整个库我最想让人记住的一个发现。**

把 `minigpt.py` 里 4 处残差 `x = x + ...` 一起写成 `x = ...`，
**两条前向路径同时被改到** ——

```
正常：  差分测试 allclose=True   argmax=36
两侧同错：差分测试 allclose=True   argmax=44     ← 25 条断言全绿，模型已经错了
只错一侧：差分测试 allclose=False               ← 立刻抓到
```

这不是测试写得不够仔细，是**差分测试的定义决定的**：
它比的是"两个实现是否一致"，而**两侧一起错，就是一致的**。

解药只有一条，而且很好记：

> **不比"实现和实现"，比"实现和它必须满足的性质"。**

性质来自数学，不来自另一份代码，所以两侧同错也躲不掉。
`_lab/tests/test_invariants.py:43` 那条断言就是：把每层的 `wo` 与 `w2` 置零后，
两个子层输出都是 0，`x = x + 0` **必须**是恒等，整个模型必须退化成
`lm_head(LayerNorm(embedding))`。那个 bug 在这里最大差从 2.4e-07 跳到 3.26。

**这条方法论对算式同样适用，而且更重要**：
任何 roofline / 成本模型，**先验证退化情形等于理论值，再看趋势**。
趋势是最容易自圆其说的东西，退化情形是硬的。
第 2 节那个 0.50 就是这么被找回来的。

### 3.1 判据必须跟着意图走

写完这个库我才把这件事想清楚：**测试判据不是风格问题，是"这个变换想干什么"的直接映射。**

| 变换想干什么 | 判据 | 用错了会怎样 |
|---|---|---|
| **等价重写**（KV 缓存、分页、批处理、FlashAttention、TP、投机解码） | 输出恒等 / 分布恒等 | 用"跑起来没报错"测 → 永远通过 |
| **有意干预**（结构化输出） | 约束恒成立 | 用"分布恒等"测 → 问错了问题，它就是要改分布 |
| **有损近似**（量化） | 误差有界且单调 | 用"输出恒等"测 → 永远失败 |

三种搞错任何一种，得到的都是一条**没有信息量**的测试。

还有一条附带的：**一条从未见过红灯的断言，和 `assert True` 是同一个东西。**
所以这个库里故意留了两个错误实现当反例
（`_lab/sampling.py:75` 的符号反了的重复惩罚、`_lab/spec_decode.py:65` 的朴素验收），
只被自检调用。**证明一条断言有意义的唯一办法，是给出一个能让它失败的实现。**

## 4. 「用什么语言」问错了

这是最初那个问题。写完 `03-语言选型/` 六篇之后，我的答案是：**这个问题问错了。**

先看事实（12 个主流引擎的真实语言构成，见 `_PLAN.md` §3.2）：

- **12 个里 10 个主语言是 Python。** 只有 llama.cpp 与 Mooncake 是 C++，
  而 Mooncake 根本不是推理引擎（是 KV 传输与存储）。
- **没有一个引擎是"用 Rust 写的"。** Rust 只出现在 4 个项目里，位置高度一致：
  **都在"请求进来到交给 GPU 之前"那一段**，从不出现在模型执行层。
- **纯 Python + Triton 是可行的**：LightLLM 全仓 0 个 CUDA 文件。

所以正确的问题是**「哪一层用什么语言」**。而各层的判据不一样：

- **模型执行层用 Python，不是因为它快，是因为模型生态在 Python。**
  离开它等于永远在追新架构。
- **"更快"几乎从来不是选语言的正当理由** —— 引擎热路径在 GPU 上，
  decode 一步的瓶颈是显存带宽，不是解释器。这一条直接由第 2 节那张表支撑。
- **C++ 在 llama.cpp 里的价值不是"更快"，是"不需要那一整套运行时"** ——
  一个可执行文件就能分发到没有 Python、没有 CUDA 的机器上。
  代价是新模型支持要手写，**滞后是结构性的，不是团队不努力**。
- **Rust 的真实价值不在快，在高并发下的可预测性** ——
  它替换的是那些 CPU 密集、请求粒度细的层。

一句话版本：**语言不是按"快慢"选的，是按"这一层的约束是什么"选的。**

## 5. 推理引擎本质上是一个内存分配器加一个调度器

把模型执行当黑盒之后，剩下的部分长得非常眼熟 —— **它就是一个小型操作系统。**

| 引擎里的东西 | 它其实是 |
|---|---|
| 分页 KV + 块表 | 虚拟内存：逻辑连续、物理分散、中间一张页表 |
| 块的引用计数 | 共享内存的生命周期管理，**块共享能成立的唯一前提** |
| 前缀缓存 | 内容寻址的缓存，外加一个淘汰策略 |
| 连续批处理 | 把调度粒度从"一批"降到"一步"的抢占式调度 |
| 块耗尽时的抢占/回退 | 换页 |
| 背压（503） | 准入控制 |

**这个视角很有用**，因为它告诉你哪些经验可以直接搬过来：
分配器的碎片问题、缓存的淘汰策略、调度的公平性与饥饿、准入控制的必要性 ——
这些都有几十年的成熟答案，不需要在推理这个语境里重新发明。

而它也告诉你**什么是这个领域特有的**：
只有一件 —— **KV 缓存的数学结构**（每个位置的 K/V 只依赖它自己和它之前的输入）。
分页能成立、前缀能共享、缓存不改变输出，全都是这一条的推论。
**这一条是推理引擎唯一真正"自己的"东西**，其余都是借来的。

## 6. 我被自己打脸八次

写这个库和它的姊妹库时，我记录了八次"我先写下了一个结论，然后被自己的代码证伪"。
完整清单在 [[01-正确性怎么保证]] §6.1，这里只说共同点：

> **八次里，错的都不是代码，是我对代码应该产出什么的预期。**

而且它们的形状惊人地一致：**我先有了一个说得通的故事，然后去看数据，
数据看起来支持这个故事，于是就写下了。**

- 算术强度"随上下文下降" —— 因为我先相信了"长上下文更受限"；
- "长上下文时 KV 主导访存" —— 因为听起来太顺了，我没去看 batch=1 的情形；
- 量化误差阈值随手写成 `< 0.01` —— 因为 0.01 是个好看的数字，
  而正确做法是**先算出解析预测（0.01076）再断言**；
- 建模 vLLM 的块淘汰时当成"插入序 FIFO"，得出"SGLang 领先 8.72 个百分点"的假结论
  —— 真相是 `touch()` 让命中块离开空闲队列，实际是**近期使用序**，修正后结论反了；
- 调度模拟只跑一个随机种子，p90 的标准差约等于均值的一半，
  差点发表一个"非单调"的假发现。

**唯一救回来的办法，每一次都是同一个动作**：先算出这个数**应该**是多少，再去对。
不是"跑一下看看"，是"先写下预测，再跑"。

顺带一条同源的：**空结果是 bug，不是事实。** 工具返回 0 条时，
第一反应必须是怀疑工具，而不是宣布"这个引擎没有这个东西"。

## 7. 这个库的边界（说在最后，免得被误用）

- **本机没有 GPU。** 所以这个库**一个真实引擎的性能数字都没有**。
  玩具引擎在 CPU 上的实测可以有，解析模型算出来的比值可以有，
  但每一处都标了适用条件。**任何往 vLLM/SGLang 身上的外推都是编造。**
- **`_lab/` 的"连续批处理"是调度语义，不是 kernel 级的批。**
  它演示的是"每一步重新决定跑哪些请求"，不是"把一批请求拼成一个大矩阵一次算"。
  **它证明的是正确性结构，不是性能。**
- **本库的断言覆盖逻辑正确性，不覆盖并发正确性。** 竞态、重入、GIL 下的真实并发行为，
  一条都没测。这一层的差距见 [[03-从玩具到生产还差什么]]。
- **不追新。** 模型架构和引擎特性变得很快，这个库只讲变化慢的部分：
  访存瓶颈、KV 的数学结构、分页、批处理、测试判据。这些五年内不会变。

## 8. 那么，要不要真的从 0 写一个

**如果目的是学** —— 值得，而且这条路是有尽头的。
`_lab/` 十个文件、不到三千行纯 numpy，就把一个引擎的主干走完了：
朴素前向 → KV 缓存 → 分页 → 连续批处理 → 前缀缓存 → 采样与流式 → HTTP 服务。
**每一步都有一条测试证明"它没有改变输出"** —— 这件事本身比代码更值钱。

**如果目的是上线** —— 不要从空文件开始。

先老实回答一个问题：**为什么不用现成的？**
"想学"是好答案。"觉得它们太重"通常不是 —— 那份"重"里有很大一块是失败路径，
而失败路径没法从教程里学，只能从事故里学。
真要动手，**从改造现有引擎开始**：隔壁 `../VLLM-SGlang-研究-推进/` 那个库
就是干这个的（`05-改进机会/`、`06-拓展方向/`）。

最后留一句我自己会记住的：

> **推理引擎里最难的不是让它变快，是让你有把握它还是对的。**
> 快慢有解析模型可以预估，而"对不对"只有一个办法 —— 算两遍，逐位比；
> 再补一层退化情形，防两侧同错。
