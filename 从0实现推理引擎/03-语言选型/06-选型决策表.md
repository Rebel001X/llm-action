# 选型决策表

> **一句话**：这一篇不替你选，只给判据和一条你能自己走一遍的决策树。
> **前置**：先读完前五篇——`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` 给事实基础，`[[02-Python为什么还没被淘汰]]`、`[[03-C++路线-llama.cpp的取舍]]`、`[[04-Rust在推理栈里到底占了什么位置]]`、`[[05-编译器路线-TVM与MLIR]]` 分头给出四条路各自的判据。本篇不重新论证任何一条，只把它们收拢成一张能走的图。

## 0. 这一篇要解决什么问题

`[[00-总览与学习路径]]` 第 2 节写过一句话，本篇就是把它兑现：

> **不替你选。这一篇给的是判据，不是答案，因为答案取决于你的目标，而那个只有你知道。**

用户带着这个库来的时候，问的往往是一个具体但问错了的问题：**"用什么语言写推理引擎好，Rust、C++ 还是其他？"** 前五篇已经把这个问题拆穿了——`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` 用 12 个真实引擎的语言构成表证明了它是个假二选一：10 个引擎主语言是 Python，Rust 从没当过任何一个引擎的主语言，却出现在 4 个项目里、位置高度一致；`[[03-C++路线-llama.cpp的取舍]]` 证明 C++ 那条路解决的根本不是"哪个语言快"，是"要不要背一整套运行时"；`[[05-编译器路线-TVM与MLIR]]` 证明"编译器路线"本身也不是一个选项，是三层完全不同的技术方案。

四篇分头论证之后，本篇要做三件事，缺一不可：

1. **把"用什么语言"这个问题重新问对**——正确的问题是"哪一层用什么语言"，这句话本篇不是第一次说，但本篇是第一次把它变成一张能真的填的表（`## 2`）。
2. **给一棵能走的决策树**——不是一张排行榜，是从"你的目标是什么"出发、一路问下去、走到一个具体建议的路径图，覆盖至少六条真实存在的目标（`## 3`）。
3. **把前四篇最容易被单独抽出来当成口号、却经不起推敲的几句话，钉死成反直觉判据和红灯清单**——"Rust 更快所以该用 Rust"、"C++ 没有 GC 所以延迟更稳"这类话，本篇要说清楚它们错在哪一步（`## 2.3`、`## 6`）。

读完本篇，你应该能做到：把自己正在纠结的场景代入 `## 3` 的决策树，走出一条具体的建议路径；如果这条路径让你意外（比如你以为该用 Rust，走出来却是"继续用 Python"），你应该能在 `## 2` 的判据表和 `## 5` 的代价清单里找到"为什么"，而不是把这篇文章的结论当成新的意见去信。

## 2. 原理

### 2.1 把问题重新问对

"用什么语言写推理引擎"这句话默认了一个前提：**一个引擎从头到尾该用同一种语言写。** 这个前提在 12 个真实项目里没有一个成立——哪怕是"C++阵营"的 llama.cpp，也有 7% 是 Python（离线权重转换脚本，`[[03-C++路线-llama.cpp的取舍]]` 已经讲过它不在服务请求的热路径上）；哪怕是"Python阵营"最纯粹的 Tokasaurus，也要靠 `torch.compile` 把 Python 侧发指令的开销压下去（`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` 第 6 节的例子）。

一个能对外提供服务的推理引擎，不管最终用什么语言写，都要做四件事（`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` §2.1 已经拆过）：

1. **接收请求**：HTTP/gRPC 协议解析、鉴权、把请求包装成内部对象；
2. **决定这一步谁上**：调度/编排——continuous batching 排队、抢占、prefix cache 查找、（如果是集群）路由到哪台机器；
3. **执行模型**：把 token 组织成张量、跑一遍前向、从 logits 采样；
4. **算子本身**：矩阵乘、attention、norm 这些真正吃浮点运算的 kernel。

**正确的问题不是"用什么语言"，是"这四层里，每一层分别用什么语言"**——因为这四层对语言的真实要求完全不同：第 1、2 层是 CPU 密集、请求粒度的决策，跟模型有多大无关；第 3、4 层的"计算"早就外包给了 GPU/BLAS/CUDA，语言在这里承担的是编排而不是算数。把四层混成一个问题去问，答案必然是一个笼统的意见；把四层拆开问，答案才会落到"这一层的瓶颈到底是什么"这个能回答的问题上——`## 2.2` 把这条拆解变成一张表。

### 2.2 四层 × 候选语言的判据表

这张表是本篇的核心资产。每一格给的是**判据**，不是"看情况"——判据的意思是：给你一条能自己核实的规则，代进你的场景，能得出一个具体结论。

| 层 | 候选 | 选它的判据 | 不选它的判据 |
|---|---|---|---|
| HTTP / 协议 | **Python**（FastAPI 等） | 请求条数不大、序列不短到让调度开销显性化——`[[02-Python为什么还没被淘汰]]` §5.2 判据表的"大模型/任意并发"和"小模型/低并发"两行；vLLM/SGLang/TensorRT-LLM/LightLLM/Tokasaurus 五家默认选择都是它 | 单纯"想要更快"不是理由——`[[02-Python为什么还没被淘汰]]` 的 `T_py < T_gpu` 判据已经说明，多数场景下这一层的开销会被 GPU 计算掩盖，换语言换不来可感知的收益 |
| HTTP / 协议 | **Rust**（axum/Tokio 等） | 要同时扛住成千上万条长连接（SSE 流式响应），且已经**测出**（不是猜）请求粒度的调度开销追上或超过了模型前向时间——`[[04-Rust在推理栈里到底占了什么位置]]` §2.1(a)(b) 的 CPU 密集 + 高并发两条共性；TGI、Dynamo 的做法 | 没有实测数据支撑"这一层是瓶颈"这个判断——vLLM、SGLang 的 Rust 前端默认都是关闭的（`vllm:vllm/envs.py:165`），说明连头部团队都认为这是工作点相关的可选项，不是普适基石 |
| 调度 / 编排 | **Python** | 策略要高频迭代（continuous batching 排队规则、prefix cache 驱逐策略）——改一行不用重新编译；单机内决策频率跟模型前向频率是同一个量级——`[[02-Python为什么还没被淘汰]]` §2.2(b) | 决策频率远高于模型前向频率、且逻辑已经稳定不常改——这时候迭代速度这条理由不再成立，见下一行 |
| 调度 / 编排 | **Rust**（仅限单独抽出的一小层） | 请求粒度、高频、CPU-bound 的那一小段——TGI 的 `Queue`/`next_batch`、Dynamo 的集群路由——决策频率可能远高于模型前向频率，且这段逻辑已经稳定；只抽这一小层，不是重写整个调度系统 | 调度逻辑还在频繁变动、稳定不下来——重写成本可能超过省下的调度开销，`[[04-Rust在推理栈里到底占了什么位置]]` 决策二"什么时候可以不这样" |
| 调度 / 编排 | **C++**（经 bindings 调用） | 已经有一个独立的编译期产物（TensorRT engine、TVM 编译模块），调度逻辑顺理成章拉进同一个编译单元——TensorRT-LLM 的 `CapacityScheduler`、MLC-LLM 的 `EngineImpl`，`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` §4.2 | 没有这样一个编译期产物做地基——平白无故把调度逻辑塞进 C++，只是把决策一（Python 迭代快）的收益扔掉，换不来任何编译期产物本来就有的好处 |
| 模型执行 | **Python + PyTorch** | 要复用 HF `transformers` 的模型定义/权重生态、要追新模型——这是 11/12 家真正的推理引擎的选择（除 llama.cpp）；真正的计算已经外包给 PyTorch 的 C++/CUDA 内核，Python 在这里不吃亏 | 目标环境没有 Python 解释器、没有 GPU、要求单二进制离线分发——这是唯一一条能推翻"默认选 Python"的路 |
| 模型执行 | **C++** | 无运行时依赖是硬约束——端侧/嵌入式/无 GPU 场景，`[[03-C++路线-llama.cpp的取舍]]` §2.1；愿意为每个新模型付两道手写工序的代价（`conversion/*.py` + `src/models/*.cpp`） | 要跟上不断发布的新模型——这条路每个新架构都要重新手写一遍图构建，`[[03-C++路线-llama.cpp的取舍]]` §4.1 已经量化过这个代价 |
| 算子 | **CUDA / 外包给专家库**（FlashAttention/FlashInfer） | 算子是标准的、有成熟实现——自己维护一份等价实现的边际收益递减得很快；vLLM 的 FlashAttention 后端就是直接 `import` 外部实现 | 这个算子是团队的核心差异化能力、或者是一个没人实现过的冷门格式——这时候外包没有对象可包 |
| 算子 | **Triton** | 想要 GPU 机器码的性能、但不想引入 CUDA C 工具链，且写 Python 语法就能表达算法——LightLLM 全仓 0 个 CUDA 文件的证据 | 需要极致的手工调优、或者要触达 Triton 编译器覆盖不到的硬件特性（比如 llama.cpp 的 AVX512/NEON 手写内层循环） |
| 算子 | **自写 CUDA/C++** | 遇到没有通用库覆盖的冷门算子/格式——KTransformers 的 GGUF 反量化 kernel；或者目标就是没有 GPU 只能靠 CPU SIMD 出算力——llama.cpp 的路 | 标准算子——自己写只是在重复造一个别人已经打磨了数百人年的轮子 |

**这张表最重要的读法**：横着看每一层都不是唯一答案，是"这一层在什么条件下选哪个"；竖着看会发现**同一门语言在不同层出现的理由完全不同**——Python 在 HTTP 层是因为够用，在调度层是因为要快速迭代，在模型执行层是因为生态锁死在那里，三个理由互不替代。这正是 `## 2.1` 那句话的具体展开：语言选型是逐层做的决定，不是整体做的决定。

### 2.3 五条反直觉的判据

前四篇分头证明过这五条，这里把它们收成判据、并标注each条能在哪一篇找到完整论证——这是本篇最容易被单独摘出来用的部分，也是最容易被误用成半句话口号的部分，所以每条都要连着"为什么"一起记，不能只记结论。

**1. "更快"几乎从来不是选语言的正当理由。**

引擎的热路径在 GPU 上，Python 只负责发起调用；decode 一步的瓶颈是显存带宽，不是解释器（`[[02-自回归解码为什么是访存瓶颈]]`）。`[[02-Python为什么还没被淘汰]]` 给出的判据是 `T_py < T_gpu` 时 Python 完全被 GPU 的异步执行掩盖——这条判据对 Python 成立，对 llama.cpp 在 GPU 后端上执行 decode 同样成立，因为真正做浮点运算的仍然是 GPU kernel，跟发起调用的语言无关（`[[03-C++路线-llama.cpp的取舍]]` §2.5）。**"更快"这个理由只在没有 GPU 打掩护的场景里才成立**——纯 CPU 推理、或者请求粒度的路由/排队层（`[[04-Rust在推理栈里到底占了什么位置]]` §2.1a）。判断自己的场景属不属于这个例外，比记住"某语言更快"这句话本身更重要。

**2. 生态惯性 > 语言性能。**

新模型第一时间能跑起来的实现几乎总是 HuggingFace `transformers` 的 Python 代码——权重格式、config schema、tokenizer 全部围绕这套生态定义（`[[02-Python为什么还没被淘汰]]` §2.2a）。vLLM 和 SGLang 都直接 `from transformers import LlamaConfig`（`vllm:vllm/model_executor/models/llama.py:32`）——两个互相竞争的头部引擎独立做出了同一个选择：不是因为 Python 快，是因为**离开这个生态，就等于每次新模型发布都要重新手写一遍权重加载和 config 解析**，永远在追。llama.cpp 选择付这份代价（`conversion/*.py` + `src/models/*.cpp` 两道手写工序），换来的是无依赖分发（`[[03-C++路线-llama.cpp的取舍]]` §4.1）——这是一笔明确的交易，不是意外。

**3. 团队能力是硬约束，比技术判据权重更高。**

`## 2.2` 那张表给的是"这一层适合什么语言"，但这个判据有一个从未明说的前提：**团队真的会写、会调试、会维护这门语言。** `[[03-C++路线-llama.cpp的取舍]]` §5.1 决策二说得很直白："团队没有 C++ 工程能力，或团队本来就在 Python/PyTorch 生态里"是"不该走 C++ 这条路"的判据之一，跟目标环境无关；`[[04-Rust在推理栈里到底占了什么位置]]` 决策四同样说，重写模型执行层这件事"跟能不能写 Rust 无关",是工程量本身就不现实。技术判据告诉你"哪一层理论上适合哪种语言"，团队能力告诉你"这个理论上的最优解你们真的实现得出来吗"——后一个问题不回答，前一个判据只是纸上谈兵。

**4. "以后可能需要多后端"不是现在上编译栈的理由。**

`[[05-编译器路线-TVM与MLIR]]` 决策三给出的判据非常具体："能不能现在就写出两个以上、具体到型号的目标硬件清单？写不出来，就不是'现在'该上图级编译器的时机。" MLC-LLM 式的架构换来的是"一份模型描述、多种硬件后端"这份真实收益（`README.md:22-58` 那张覆盖 NVIDIA/AMD/Intel/WebGPU/手机 GPU 的矩阵），但代价（每个新模型要用编译器自己的前端重写一遍、动态形状要预先枚举、编译时间本身是一项要测量的成本）从第一天就要背上，不管你最终用不用得上那份收益。**"以后可能"是一个用不上的期权，代价却是现在就要付的**——这条判据的价值恰恰在于它把一个含糊的"以后"变成了一个能现在就回答的是非题。

**5. Rust 的真实价值不在快，在"高并发下的可预测性"——它替换的是那些 CPU 密集且请求粒度细的层，不是模型执行层。**

12 个真实项目、0 个例外——没有一家把模型执行层换成 Rust（`[[04-Rust在推理栈里到底占了什么位置]]` §2.2）。Rust 进模型执行层要么走 FFI 绑 CUDA（内存安全的核心卖点在 `unsafe` 边界内失效），要么另起一套算子库（工程量要对齐 cuBLAS/FlashAttention，不现实）。Rust 真正落地的四处代码——vLLM 的 `rust/`、SGLang 的 `rust_server.py`/`sgl-model-gateway`、TGI 的 `router`/`backends`、Dynamo 的 `kv-router`——全部在"请求进来到交给 GPU 之前"这一段：这一段没有 GPU 打掩护，CPU 开销是真实的串行瓶颈；这一段又是高并发长连接的场景，Rust 的异步运行时（Tokio）没有 GIL 那种全局锁的天花板。**它换来的是"这一层在高 QPS、长连接场景下的延迟可预测性"，不是"矩阵乘算得更快"**——这条区分决定了 Rust 该被放进哪一层，也决定了它绝不该被放进哪一层。

## 4. 真实引擎是怎么做的（对照 12 家源码，带 `引擎:文件:行`）

`## 3` 的每一条路径都不是抽象推演，是真实项目的现状。这一节逐条给证据——**读法不是"这个引擎证明了这条路径最优"，是"这个引擎证明了这条路径真的有人走通过、能跑、值得参考"**。

### 4.1 路径 A（学原理）：本库自己就是这条路的实现，没有一个生产级引擎走这条路——这是故意的

12 个真实引擎里，没有一家的模型执行是用"纯 Python + 解释执行"实现的——即便是 Tokasaurus 那种 95% Python 的引擎，矩阵乘也是通过 `torch` 张量调用底层 C++/CUDA 内核完成的（`[[01-用什么语言写推理引擎-12个真实引擎的证据]]` 第 6 节）。这不是路径 A 的反例，是路径 A 的边界说明：**"学原理"这个目标要的是"每一步矩阵乘露在外面、能改一行立刻验证"，不是"生产级吞吐"**，两个目标对语言的要求本来就不一样，不需要在 12 家里找一个先例。

本库 `_lab/minigpt.py` 就是这条路径落地的样子：朴素前向 `_lab/minigpt.py:95`（`forward_naive`）、生成循环与 selftest 从 `_lab/minigpt.py:241` 开始（`selftest`），全部纯 numpy、不装 torch。`_lab/serve.py` 一路走到 577 行，把 HTTP 服务这一层也用同一套约束实现了一遍（`_lab/serve.py`），证明"学原理"这个目标下，四层全部可以用 Python 实现，不需要在某一层临时改用别的语言——这跟路径 F（生产级在线服务）形成直接对照：同样是四层，目标不同，`## 3` Q6a 那条"要不要换 Rust"的判据在这里根本不适用，因为判据的前提（高并发、长连接、请求条数主导时间）在一个单用户学习项目里不成立。

### 4.2 路径 B（团队小，改造现有引擎）：Dynamo 本身就是这条思路的产品化

路径 B 说的是"别自研"，但"别自研"不是一句空话，12 家里恰好有一个真实项目，把"站在已有引擎之上而不是重写"当成了自己的核心产品定位——Dynamo。它的 README 说得非常直接：

> "Dynamo is the orchestration layer above inference engines — it doesn't replace SGLang, TensorRT-LLM, or vLLM, it turns them into a coordinated multi-node inference system."（`dynamo:README.md:36`）

这句话是路径 B 的一个精确类比：一个团队面对"要不要自己重写一个推理引擎"这个问题时，Dynamo 团队选择的答案是"不重写模型执行层，在已有的 vLLM/SGLang/TensorRT-LLM 之上加一层编排"——把自己的工程投入放在"路由/编排"这一层（`[[04-Rust在推理栈里到底占了什么位置]]` §4.4 已经拆过 `dynamo:lib/kv-router/` 具体在做什么），而不是重新实现 attention、重新写一遍权重加载。**这不是"Dynamo 团队能力不够"，是一个理性的工程决策：模型执行层的存量优势（HF 生态、CUDA 算子生态）已经被别人（vLLM/SGLang）打磨过，重新做一遍的边际收益低到不值得**——这正是路径 B 想让团队小的读者提前想清楚的事：你缺的可能不是"重新实现调度器"的能力，而是"重新实现调度器"这件事本身值不值得做。

### 4.3 路径 C（端侧/无 GPU）：llama.cpp 的分发方式就是答案

`[[03-C++路线-llama.cpp的取舍]]` 整篇已经把这条路径的收益/代价讲透了，这里只钉两条最直接的证据。分发方式上，README 给出的第一条上手路径是下载一个可执行文件直接跑：

```
llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF
```
（`llama.cpp:README.md:32-34`）

不需要 Python 解释器、不需要 pip 依赖树、不需要 CUDA。架构上，HTTP 层、调度层、模型执行层全部揉进同一个 C++ 二进制——路由注册的入口在 `llama.cpp:tools/server/server-http.cpp:604`（`pimpl->srv->Post(...)`），跟前面 `## 2.2` 判据表里"模型执行层选 C++"那一格的判据（无运行时依赖是硬约束）严丝合缝对上。这条路径唯一要事先想清楚的代价是：新模型支持要走两道手写工序（Python 权重转换 + C++ 图构建），`[[03-C++路线-llama.cpp的取舍]]` §4.1 已经给出具体数字对比，本篇不重复。

### 4.4 路径 D（多硬件/编译器路线）：MLC-LLM 的编译入口就是"代价从这里开始"的分界线

`[[05-编译器路线-TVM与MLIR]]` §4.2 已经详细拆过 MLC-LLM 的取舍，这里钉住决定性的一行代码——模型对象必须先"导出"成一张 TVM 的 Relax 图，才谈得上执行：

```python
mod, named_params, ext_mods = model.export_tvm(
    spec=model.get_default_spec(),
    allow_extern=True,
)
```
（`mlc-llm:python/mlc_llm/interface/compile.py:163`）

这一行是路径 D 代价的具体落点：**不是"可选加速"，是模型能不能跑起来的必经步骤**——`## 2.3` 判据四说的"以后可能需要多后端不是现在上编译栈的理由"，落到代码层面就是这一行：一旦走这条路，新模型接入就必须先过这道 `export_tvm` + 完整 Relax 流水线的门槛，不像 vLLM 那样改一份 PyTorch eager 代码就能跑。这条代价只有在你能现在就写出两个以上具体硬件型号（比如 MLC-LLM 自己覆盖的 WebGPU/手机 Adreno/Apple Metal，`mlc-llm:README.md:22-58`）时才值得付。

### 4.5 路径 E（给上游提 PR / 找工作）：门槛由生态决定，不是由"哪个语言更好"决定

vLLM 支持一个新模型架构的核心动作是往一个注册表字典里加一行——`_TEXT_GENERATION_MODELS` 定义在 `vllm:vllm/model_executor/models/registry.py:72`，这是普通的 Python 字典，贡献者要读懂、能改、能跑测试的门槛就是"会 Python + 熟悉 PyTorch `nn.Module`"，跟 C++/Rust 完全无关。反过来，想往 LightLLM 的自定义 Triton kernel 提性能优化 PR，门槛换成了"会 Triton"——`lightllm:lightllm/common/basemodel/triton_kernel/add_in_place.py:7` 那个 `@triton.jit` 装饰器下面的函数，是 Python 语法但要按 GPU tile 思路去写、去调优。**这两个门槛是同一个仓库里两种完全不同的能力要求**，路径 E 真正要回答的问题从来不是"这个引擎是不是 Python 写的"，是"我想改的具体是哪一层"——这跟 `## 2.1` "把问题重新问对"是同一条方法论，只是换成了"贡献代码"这个具体场景。

### 4.6 路径 F（在线多租户服务）：Python 调度器主体，Q6a 分叉点的两侧都有真实项目

vLLM 的调度器是一个普通的 Python 类，`class Scheduler(SchedulerInterface):` 定义在 `vllm:vllm/v1/core/sched/scheduler.py:73`；SGLang 同样，`class Scheduler(` 定义在 `sglang:python/sglang/srt/managers/scheduler.py:384`。这是 Q6 分叉之后、Q6a 判定为"否"时的默认落点——两个互相竞争的头部引擎，在"单机内调度决策用 Python 写"这件事上做了同一个选择,因为决策频率跟模型前向频率是同一个量级（`[[02-Python为什么还没被淘汰]]` §2.2b）。

Q6a 判定为"是"（实测出请求粒度开销追上模型前向）时的落点，TGI 是最直接的证据——它的连续批处理排队逻辑整段是 Rust：

```rust
pub(crate) struct Queue {
    queue_sender: mpsc::UnboundedSender<QueueCommand>,
}
```
（`tgi:backends/v3/src/queue.rs:41`）

`next_batch` 方法（`## 3.2` 已给出核查命令）就是决定"这一步该往 batch 里塞哪些新请求"的入口——这段决策逻辑跟 vLLM/SGLang 的 `Scheduler` 类解决的是同一个问题，选了不同语言，区别在于 TGI 判断这一层的决策频率已经高到值得单独抽出来重写（`[[04-Rust在推理栈里到底占了什么位置]]` §2.1）。

**这里必须补一个反例，防止 Q6a 被简化成"主语言 Python 就意味着调度也是 Python"**：TensorRT-LLM 主语言是 Python，占 56%，但真正做"这一步该放行哪些请求"判断的 `CapacityScheduler::operator()` 是 C++，定义在 `tensorrt-llm:cpp/tensorrt_llm/batch_manager/capacityScheduler.cpp:708`——`## 2.2` 判据表里"调度/编排层选 C++（经 bindings 调用）"那一格的判据（已经有独立编译期产物做地基）在这里成立，因为 TensorRT-LLM 整个模型执行层就架在 TensorRT 编译产物之上。这条反例提醒的是：Q6a 那个"是/否"判断给出的是"要不要单独抽出一层重写"，不是"整个引擎的主语言是什么"——两个问题的答案可以完全不相关。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

`## 3` 的决策树给出的是路径，这一节把路径背后真正在做的**决定**摊开——每条决定配三样。

**决策一：把"哪一层用什么语言"当成默认要问的问题，而不是"整个引擎用什么语言"**

- **为什么这样**：`## 2.1` 已经论证过，12 个真实项目没有一家是单一语言写到底的（哪怕 llama.cpp 也有 7% Python 的离线转换脚本）；四层对语言的真实要求完全不同——HTTP/调度是请求粒度的 CPU 决策，模型执行/算子的计算早就外包给 GPU/BLAS。
- **不这样会怎样**：把问题问成"整个引擎用什么语言"，答案必然是一个笼统的意见（"Rust 更安全"、"C++ 更快"），这类意见套不进任何一层的真实判据，最终要么全盘照抄某个团队的选择（忽略自己的约束跟那个团队不一样），要么因为找不到"标准答案"而迟迟不动笔。
- **什么时候可以不这样**：目标本身就是极简单的单一场景（比如路径 A 的学习项目、路径 C 的端侧单二进制），四层里有的层根本不存在（学习项目没有跨机路由，端侧单用户场景不需要复杂调度）——这时候"整个用一种语言写"不是偷懒，是因为拆出来的层数本来就少，拆不拆的差异不大。

**决策二：团队规模先于技术判据，决定要不要自研**

- **为什么这样**：`## 2.3` 判据三说得很直接——技术判据告诉你"哪一层理论上适合哪种语言"，团队能力告诉你"这个理论上的最优解你们真的能实现出来吗"。一个 3 人团队即便选对了每一层的语言，也未必扛得住"自己维护一个调度器 + 自己维护一套模型接入层 + 自己维护 HTTP 服务"这三件事的长期工程量——Dynamo 选择把精力放在编排层、不重写模型执行层（`## 4.2`），是同一条逻辑在头部团队身上的体现。
- **不这样会怎样**：跳过团队规模这一问、直接按"理论最优"去选语言组合，很可能选出一套没人有精力长期维护的架构——短期内能跑起来一个 demo，长期在"新模型接入""安全补丁""性能调优"这些持续性工作上会被拖垮，这类拖垮往往是渐进的，不会在项目初期就暴露。
- **什么时候可以不这样**：目标从一开始就是"造引擎本身"，不是"用推理服务支撑别的产品"——比如研究团队想验证一种新的调度算法、教学项目想讲清楚引擎的骨架（本库就是这类）。这时候"自己写"才是目标本身，不是达成目标的手段，团队规模这一问就不适用。

**决策三：端侧/无 GPU 目标，从一开始就锁定单一语言、单一二进制**

- **为什么这样**：`[[03-C++路线-llama.cpp的取舍]]` 已经证明这条选择换来的不是速度，是"不需要那一整套运行时"——目标设备装不下 Python + torch，这是一个物理约束，不是偏好。
- **不这样会怎样**：照搬"Python 编排 + CUDA 算子"这套主流架构去做端侧部署，等于把 Python 解释器、pip 依赖树也一起打包进目标设备，在资源受限的端侧环境里往往行不通或代价过高（`[[03-C++路线-llama.cpp的取舍]]` §5.1 决策三）。
- **什么时候可以不这样**：目标设备资源充裕（服务器级 GPU）、且需要快速接入新模型——这时候主流架构的接入速度优势远大于单二进制的部署优势，`## 2.2` 判据表里"模型执行层选 Python"那一格的判据重新占优。

**决策四：编译器路线只在能写出具体硬件清单时才上，而且从 Triton 这一层开始，不是从图级编译器开始**

- **为什么这样**：`[[05-编译器路线-TVM与MLIR]]` 决策二、决策三已经给出完整判据——Triton 的失败模式是局部的（一个 kernel 写错不影响其他算子），图级编译器的失败模式是全局的（一次编译失败整个模型编不出来）；多后端这份真实收益，只有在硬件目标真的不止一种时才能兑现，代价却是从第一天就要背上的固定成本。
- **不这样会怎样**：为一个假设存在的"以后可能要支持的硬件"提前上图级编译栈，会长期背负"新模型接入变慢、调试难度上升、编译时间成本"这些代价，却从来没有兑现那份"多后端"的收益——这类选型的成本经常是隐性的，团队容易把它误判成"团队能力问题"而不是"架构选型的代价"（`[[05-编译器路线-TVM与MLIR]]` §5 决策三）。
- **什么时候可以不这样**：目标硬件从一开始就明确不止一种，且能写出具体到型号的清单（比如"同一个模型要能在服务器和用户手机上都跑起来"）——这时候 MLC-LLM 式的架构才是在为一个真实存在的需求付费，不是为一个假设付费。

**决策五：请求粒度的调度/路由层，只在实测证明它已经追上模型前向时间时才单独换 Rust**

- **为什么这样**：`[[02-Python为什么还没被淘汰]]` 的 `T_py < T_gpu` 判据说明这一层的开销大多数场景下会被 GPU 计算掩盖；`[[04-Rust在推理栈里到底占了什么位置]]` §5.3 明确说"先能跑、再谈性能层的语言选型"——vLLM、SGLang 都是先有成熟的 Python 引擎，Rust 前端后来才作为可选层加上去，只有 TGI 是个例外（从早期就是 Rust）。
- **不这样会怎样**：在需求还不清楚的时候就为一个可能根本不存在的瓶颈预先花掉 Rust 的学习/维护成本——这是决策四同一个逻辑在另一层上的重复：**代价现在付、收益以后可能兑现的赌注,先问清楚"以后"是不是已经能被证明存在**。
- **什么时候可以不这样**：路由逻辑从项目一开始就注定要面对海量请求、长连接的场景（比如从零设计一个多租户网关产品，不是从零设计一个推理引擎）——这是 TGI 的真实历史（`[[04-Rust在推理栈里到底占了什么位置]]` §5.3），"从一开始就是 Rust"在这种场景下是设计要求，不是过早优化。

**决策六：决策树问问题的顺序本身是一项设计决策，不能任意打乱**

- **为什么这样**：`## 3.1` 末尾已经说明——团队规模（Q2）比目标硬件（Q3）更早决定"要不要自己造轮子"，目标硬件（Q3）又比"要不要多后端"（Q4）更早决定"有没有 GPU 这个选项"。这个顺序反映的是约束之间的真实依赖关系：没有 GPU 这件事，会直接让"多后端编译器路线"这个选项失去意义（编译器路线要解决的是"同一份描述、多种硬件"，但如果连基本的推理都跑不起来，谈多后端没有意义）。
- **不这样会怎样**：颠倒问题顺序会导向错误的建议——比如先问"要不要多后端"再问"有没有 GPU"，会让一个本来该走 C++ 端侧路线的团队，误以为编译器路线是首选,而 MLC-LLM 那类多后端能力解决的其实是另一类问题（浏览器/手机上也要能跑，`## 4.4` 已经讲过）。
- **什么时候可以不这样**：如果读者自己非常清楚哪几条约束对自己最先起决定作用（比如已经确定死了目标硬件、团队规模都不是问题，唯一悬而未决的只有"要不要给上游提 PR"），可以直接跳到对应的问题去回答，不需要机械地从 Q1 走到底——这棵树是给"还没想清楚"的人用的排查顺序，不是"必须逐题作答"的强制流程。

## 6. 常见错误与踩坑（红灯清单：看到这些说法就该警惕）

四条选型误判，每条给一句为什么——这是本篇最容易被单独截图传播、也最容易被断章取义的部分，所以每条都配了能自己核实的证据，不是只给结论。

**红灯一："Rust 比 Python 快 100 倍，所以引擎该用 Rust"**

任何具体倍数都是编的——本库红线不允许给这类未经查证的性能对比数字（`_PLAN.md` §1 第 4 条），这句话本身的可疑之处不在数字准不准，在于它默认了"引擎变快的杠杆在语言执行速度上"。`## 2.3` 判据一已经拆穿：decode 的瓶颈是显存带宽，Python 只负责发指令，`T_py < T_gpu` 时语言执行速度根本不在关键路径上（`[[02-Python为什么还没被淘汰]]`）。12 个真实项目、0 个例外——没有一家把模型执行层换成 Rust（`[[04-Rust在推理栈里到底占了什么位置]]` §2.2），如果"更快"这个理由真的成立，这条空缺不该存在。

**红灯二："C++ 没有 GC，所以延迟更稳"**

这句话把"这个场景里的主要延迟来源"想错了。GC 停顿确实是一类真实的延迟不稳定来源，但在推理引擎的模型执行层，主要延迟来源是显存带宽和 kernel 调度，不是内存回收——`[[03-C++路线-llama.cpp的取舍]]` §2.5 明确说过，llama.cpp 在 GPU 后端上执行 decode，真正做浮点运算的仍然是同一批 CUDA/Metal kernel，C++ 语言本身没有让这些 kernel 算得更快。**"没有 GC"这个优点在 Rust 真正落地的那一层（请求路由/网关,`[[04-Rust在推理栈里到底占了什么位置]]` 决策三）才是实打实的收益——高 QPS、长连接（SSE 流式响应）场景下,GC 停顿确实会打断正在流式返回的连接**——但这是"这一层"的优势，不是"整个引擎"的优势，把它挪用到模型执行层就是张冠李戴。

**红灯三："全部重写就能解决性能问题"**

这句话的错误在于跳过了"性能问题具体出在哪一层"这个必答题。`## 2.1` 已经论证过，一个引擎的性能瓶颈可能落在四层里的任何一层，甚至可能根本不是语言选型的问题——`[[02-Python为什么还没被淘汰]]` §5.2 判据表第四行专门提醒："调度器的**算法复杂度**可能先于**语言选型**成为瓶颈——换语言之前先检查调度算法本身是不是随请求数超线性增长"。vLLM 的 Rust 前端自己承认"experimental, and is not feature-complete"（`vllm:rust/README.md:5`）——这不是"重写没做完"，是渐进式迁移项目正常的状态，反过来也说明"全部重写"从来不是这两家头部团队的选择,他们做的是把一层单独抽出来,不是推倒重来。

**红灯四："先用编译器路线，以后好扩展"**

`## 2.3` 判据四、`## 5` 决策四已经把这句话的账算清楚了——"以后好扩展"是一个含糊的期权，代价（每个新模型要用编译器自己的前端重写一遍、动态形状要预先枚举、编译时间本身是要测量的成本，`vllm:vllm/config/compilation.py:648` 的 `cudagraph_capture_sizes: list[int]` 就是这份代价在真实代码里的样子——想用哪些形状就得为每一个单独付一次捕获成本）却是现在就要付的。判据很具体：**能不能现在就写出两个以上、具体到型号的目标硬件清单？写不出来，"以后好扩展"就只是一句还没兑现、也不知道什么时候会兑现的承诺。**

## 7. 自测题与延伸阅读

**自测题（闭卷回答，答案都在本篇里）**：

1. "用什么语言写推理引擎"为什么是一个问错了的问题？正确的问法是什么，为什么四层对语言的真实要求完全不同？
2. `## 3` 的决策树里，Q2（团队规模）为什么排在 Q3（目标硬件）之前？如果颠倒这两问的顺序，一个 3 人团队、目标是端侧部署的场景会得出什么样错误的建议？
3. `## 2.2` 判据表里，"调度/编排层"这一格给了三个候选（Python、Rust、C++经bindings），分别对应什么条件？TensorRT-LLM 的 `CapacityScheduler` 落在哪一个，为什么它的主语言统计（Python 56%）不能直接推出这个答案？
4. 红灯二说"C++ 没有 GC 所以延迟更稳"这句话"张冠李戴"，具体是把哪一层的优势错误地挪用到了哪一层？
5. Dynamo 的 README 说自己是"orchestration layer above inference engines"，这句话怎么支持 `## 3` 路径 B（团队小，改造现有引擎）这条建议？如果一个团队反过来说"我们要做 Dynamo 那样的编排层，所以得重写一个 vLLM"，这个推理错在哪一步？
6. `## 5` 决策四和决策五说的是两个不同层（编译器路线 vs 请求粒度调度层）的"先别急"判据，两条判据的共同结构是什么？各自的"什么时候可以不这样"分别对应什么场景？
7. 如果你要把自己在 `[[07-把它变成一个HTTP服务]]` 里搭出来的玩具引擎，改造成一个真正对外提供服务的产品，代入 `## 3` 的决策树，你会从 Q1 走到哪一条路径？如果中途某个问题的答案会随着产品发展变化（比如从"团队 3 人"变成"团队 20 人"），你觉得决策树给出的建议应该在哪一步重新走一遍？
