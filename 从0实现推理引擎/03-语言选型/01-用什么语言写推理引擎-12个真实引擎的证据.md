# 用什么语言写推理引擎——12个真实引擎的证据

> **一句话**：别问"用什么语言"，问"哪一层用什么语言"。
> **前置**：无——本篇是 `03-语言选型/` 的入口。`00-总览与学习路径.md` 第 2 节写了一版简版结论，本篇把它展开、给出源码证据；深入的 Python 侧论证见 [[02-Python为什么还没被淘汰]]。

## 0. 这一篇要解决什么问题

这是本库读者最常问的问题，没有之一：**我要自己写一个推理引擎，该用 Rust、C++ 还是 Python？**

网上关于这个问题的讨论大多是意见——"Rust 更安全更快"、"Python 太慢担不起推理引擎的延迟要求"、"C++ 才是系统软件的正道"。这些话听起来都有道理，但没有一句是从**真实存在、有人在生产里用**的引擎里长出来的。

本篇不给意见。做法是把 12 个真实开源推理引擎的源码摆在桌面上，数它们的语言构成，再打开代码看它们把哪种语言放在哪一层、为什么。结论不是我说的，是这 12 份仓库自己说的。

三件事本篇要做到:

1. 给出 12 个引擎的完整语言构成表，讲清楚这张表怎么读、读出什么。
2. 把推理引擎拆成四层（HTTP/协议、调度/编排、模型执行、算子），逐层给出 12 家的真实选择，每一层至少一条带文件名和行号的源码证据。
3. 给一张"从 0 开始写，目标不同该怎么选"的分叉表——不给单一答案，因为答案取决于你的目标。

读完本篇你能自己回答的问题：为什么 10 个引擎的主语言都是 Python 而没人觉得这是笑话；Rust 在这些引擎里到底出现在哪、为什么偏偏是那几个位置；以及你自己动手写一个引擎时，语言这件事该在什么时候纠结、什么时候完全不用管。

## 2. 原理

### 2.1 把引擎拆成四层，语言选型是逐层做的决定，不是整体做的决定

一个能对外提供服务的推理引擎，不管用什么语言写，都要做这四件事：

1. **接收请求**：HTTP/gRPC 协议解析、鉴权、把请求包装成内部对象。
2. **决定这一步谁上**：调度/编排——continuous batching 排队、抢占、prefix cache 查找、（如果是集群）把请求路由到哪台机器上的哪个副本。
3. **执行模型**：把 token 组织成张量、跑一遍 Transformer 的前向、从 logits 采样。
4. **算子本身**：矩阵乘、attention、norm 这些真正吃浮点运算的 kernel。

把 12 家的真实选择填进这张表（第 4 节逐条给源码证据）：

| 层 | 12 家的实际选择 | 这一层对语言的真实要求 |
|---|---|---|
| HTTP / 协议 | 多数 Python（FastAPI）；**TGI 与 Dynamo 用 Rust** | CPU 密集、req/s 可能很高、和模型本身的计算量无关 |
| 调度 / 编排 | 多数 Python；**TGI 的 router、Dynamo 的集群路由用 Rust** | 请求粒度的决策逻辑，复杂但不涉及浮点运算；决策频率可能远高于模型前向频率 |
| 模型执行 | 几乎全是 Python 调用 PyTorch；**llama.cpp 是 C++ 全家桶** | 要复用模型定义/权重生态；真正的计算已经外包给下一层 |
| 算子 | CUDA / Triton；或者**根本不写**，外包给 FlashAttention / FlashInfer 这类专门库 | 纯浮点吞吐，跟"用什么语言写调度逻辑"是两个问题 |

**这张表的读法**：Rust 出现的两个位置（HTTP 层、调度/编排层的一部分）恰好是"请求粒度、和模型计算量无关"的那两层；模型执行层和算子层——真正跟"这个模型有多大"绑定的两层——几乎没有人往这两层里塞 Rust。这不是巧合，第 2.2、2.3 节分别讲这两层为什么会这样选。

**顺带说清楚 Mooncake 为什么不该被拿来类比**：Mooncake 主语言是 C++、占 54%（`_PLAN.md:124`），乍看跟 llama.cpp 是同一类"C++ 引擎"，但它压根不做上面四层里的任何一层——它不接收推理请求、不做调度决策、不执行模型前向、不算 attention。

它做的是另一件事：把 KV 缓存在多台机器之间搬运和落盘（`_PLAN.md:124` 标注"它不是引擎，是 KV 传输层"）,是 vLLM/SGLang 这类真正的推理引擎在做分布式 KV 缓存复用时会依赖的一个基础设施组件，不是一个独立能对外提供推理服务的引擎。

它选 C++ 的理由——搬运大块内存、对接 RDMA 这类网络硬件——是数据搬运层的考量，跟"要不要接入 HF 模型生态"（2.2a）、"调度策略要不要快速迭代"（2.2b）这些决定推理引擎主语言的理由完全不是一回事。把 Mooncake 的语言选择当成"推理引擎该用 C++"的证据，等于拿一个搬运工具的选型去证明厨师该怎么切菜——问的不是同一个问题。

### 2.2 为什么主语言几乎一定是 Python

三个理由,合在一起解释了为什么 10/12 家选了同一个默认项:

**(a) 模型定义与权重生态锁死在 Python 里。** 新模型发布时，第一时间能跑起来的实现几乎总是 HuggingFace `transformers` 的 Python 代码——权重格式（safetensors）、config schema、tokenizer 全部围绕这套生态定义。

推理引擎要在新模型发布后尽快支持它，最短路径就是直接依赖这套生态，而不是每次重新在另一门语言里手写一份权重加载器和 config 解析器。这条路径依赖一旦形成，主语言选 Python 就不是"喜好"，是"接入成本最低"。

**(b) 迭代速度。** 调度策略——continuous batching 的排队规则、prefix cache 的驱逐策略、投机解码的接受率反馈——是引擎里改动最频繁的一层，改动者往往是做研究的人而不是做系统的人。这层如果用 C++/Rust 写，改一行策略要走"改代码 → 重新编译 → 重新链接 → 重启"的完整流程；用 Python 写，改一行、保存、重启进程就生效，编译器完全不参与。

研究和生产之间的反复拉扯发生在这层，这层就该用能让这种拉扯代价最低的语言。

**(c) 热路径本来就在 GPU 上，Python 只负责发指令。** GPU 的 kernel launch 是异步的：Python 调用一次矩阵乘，CPU 侧做的事情只是把"执行这个 kernel"这条指令塞进一个队列（CUDA stream），然后立刻返回去执行下一行代码——它不等 GPU 真的算完。只要 Python 把指令塞进队列的速度跟得上 GPU 消费指令的速度，Python 的存在感就等于零，因为它的时间被 GPU 的计算时间盖住了。

**Python 不在热路径上算数，它在发指令。** 这条原理是本节和下一节共同的地基，完整的形式化判据和源码证据见 [[02-Python为什么还没被淘汰]] 第 1、2 节。

三条理由指向同一个结论：模型执行层的"计算"外包给了 GPU/BLAS，Python 在这一层承担的是编排而不是算数，而编排恰好是 Python 最不吃亏、生态最完整、迭代最快的工作。

### 2.3 Python 什么时候真的成为瓶颈

上一节的判据里藏着一个前提：**Python 塞指令的速度要跟得上 GPU 算的速度。** 这个前提不是恒成立的。

模型越大，GPU 一步前向要算的时间越长，Python 侧固定的调度/编排开销占比就越小,可以忽略。但反过来：**模型越小、并发请求数越多、序列越短，GPU 一步前向的时间本身就短，而 Python 侧要处理的请求条数（不是模型大小）却在涨。** 到某个点上，Python 侧为下一步做准备所需的时间会追上甚至超过 GPU 算完当前步所需的时间——这时候 GPU 算完就在等 Python，Python 从"免费的编排层"变成了实打实的瓶颈。

**这不是一句空话，是 12 家里两家真实做过的架构决定：** TGI 把整个 router（接请求、排队、决定下一批喂给模型执行进程哪些请求）用 Rust 写；Dynamo 把集群级别的请求路由——把一条请求发到哪台机器上的哪个 KV 缓存命中率最高的副本——整层放进 Rust。

这两处恰好都是"请求粒度的决策，且决策频率可能很高"的场景：router 要在每一条新请求进来时都做一次决策，集群路由要在多机负载均衡的场景下对海量请求做路由判断。

这类场景下，请求条数才是主导时间的量，而不是模型算了多久——这正是 Python 解释器逐次函数调用/对象创建的固定开销最容易被放大的地方。第 4.2 节会打开 `tgi:backends/v3/src/queue.rs` 和 `dynamo:lib/llm/src/kv_router.rs` 给出具体的类型定义和方法签名；判据的完整形式化版本、以及"多大算大、多短算短"的判据表在 [[02-Python为什么还没被淘汰]] 第 5.2 节。

## 3. 自己动手：你可以自己复算这张表

第 1 节的表不是拍脑袋抄来的，是隔壁研究库 `../VLLM-SGlang-研究-推进/_lab/repo_stats.py` 跑出来的确定性结果。这一节讲这个脚本在做什么、以及**你应该自己跑一遍，而不是相信我给的数字**。

`repo_stats.py` 做的事情很朴素：遍历每个引擎已经 clone 下来的源码目录，按文件后缀分类计数行数（`.py`/`.pyi` 记 Python，`.rs` 记 Rust，`.cu`/`.cuh` 记 CUDA，`.cc`/`.cpp` 记 C++，等等），再单独扫一遍每个 Python 文件里有没有 `@triton.jit` 装饰器或者 `triton.jit(...)` 这种函数调用形式——这是判断"这个文件是不是自研 Triton kernel"的规则。跑法：

```bash
cd "../VLLM-SGlang-研究-推进/_lab"
python repo_stats.py              # 跑全部已 clone 的引擎，写出 out/repo_stats.json
python repo_stats.py vllm sglang  # 只跑指定的几个，调试用
python repo_stats.py --selftest   # 先确认脚本本身逻辑没错
```

**为什么值得自己跑一遍而不是照抄本篇的表**：这类"数代码行数"的脚本，判定规则本身就是需要被审计的东西,而不是拿到结果就完事。`repo_stats.py` 里有一条真实踩过的坑值得知道——第一版 Triton 判定只认 `@triton.jit` 装饰器语法，结果把 MLC-LLM 里用 `triton.jit(triton_kernel)` 函数调用形式手写的 kernel 判成了 0 个 Triton 文件,这是假阴性,因为那些代码语义上就是手写 Triton kernel,只是没用装饰器写法。

教训是**"用某种字符串模式在仓库里搜不到"和"这个仓库没有这个东西"是两件事**——数字背后的判定规则跟数字本身一样重要,而判定规则会随仓库版本、写法风格变化而失效。仓库是活的，今天的语言构成三个月后可能已经不是这张表的样子——**这本身也是"跑代码验证，而不是记住一个数字"这条本库红线的具体体现**（`_PLAN.md:34-37` 那条诚实标准）。

跑完以后，`out/repo_stats.json` 里每个引擎会有一份按语言、按子目录的详细统计——比本篇表格里的"前四语言"更细，可以自己深挖某个引擎的某个子目录到底是什么语言写的，这是第 4 节逐层举证据的方法论来源。

## 4. 真实引擎是怎么做的（对照 12 家源码，带 `引擎:文件:行`）

第 2.1 节给的四层表是结构性的判断，这一节把每一格钉在真实文件的真实行号上。

### 4.1 HTTP / 协议层：多数 Python + FastAPI，两家用 Rust

**Python 阵营**——vLLM 和 SGLang 都用 FastAPI 挂路由。vLLM 构建应用对象的地方是 `vllm:vllm/entrypoints/launchers/app.py:35`，一行 `app = FastAPI(...)`；SGLang 在 `sglang:python/sglang/srt/entrypoints/http_server.py:456` 同样是 `app = FastAPI(`，往下在 `sglang:python/sglang/srt/entrypoints/http_server.py:1714` 能看到 `@app.post("/v1/completions", ...)` 这样的路由装饰器——两个互相竞争的头部引擎，在"HTTP 层用什么框架"这件事上做了同样的选择。

这不是 vLLM/SGLang 两家的巧合。同样的 `app = FastAPI(...)` 模式在另外两家主语言是 Python 的引擎里也能原样找到：TensorRT-LLM 在 `tensorrt-llm:tensorrt_llm/serve/openai_server.py:562`，`self.app = FastAPI(lifespan=lifespan)`；LightLLM 在 `lightllm:lightllm/server/api_http.py:119`，`app = FastAPI()`。四家互相之间在模型架构、调度策略上有明显的技术分歧,但在"HTTP 层用 FastAPI"这一点上没有分歧——这层几乎不涉及推理引擎的核心技术难点,选型早就收敛了。

**Rust 阵营**——TGI 的 HTTP 路由表整段是 Rust 写的，`tgi:router/src/server.rs:2203-2211`：

```rust
let mut base_routes = Router::new()
    .route("/", post(compat_generate))
    .route("/generate", post(generate))
    .route("/generate_stream", post(generate_stream))
    .route("/v1/chat/completions", post(chat_completions))
    .route("/v1/completions", post(completions))
    .route("/vertex", post(vertex_compatibility))
    .route("/invocations", post(sagemaker_compatibility))
    .route("/tokenize", post(tokenize));
```

这是 Rust 的 axum web 框架，跟 FastAPI 是同一类工具在不同语言里的对应物。Dynamo 走的是同一条路：它的 OpenAI 兼容前端同样用 axum 挂路由，`dynamo:lib/llm/src/http/service/openai.rs:3881` 是其中一处 `let router = Router::new()`（同一个文件里这样的挂载点出现了十几次，对应 `/v1/chat/completions`、`/v1/completions`、`/v1/responses` 等不同的 OpenAI 兼容端点）。

**C++ 阵营（llama.cpp）**：llama.cpp 走的是第三条路——HTTP 层也不用另一门语言，直接用 `cpp-httplib` 在 C++ 里挂路由。`llama.cpp:tools/server/server-http.cpp:604` 的 `pimpl->srv->Post(path_prefix + path, [handler](const httplib::Request & req, httplib::Response & res) { ... })` 就是路由注册的地方。这一点在第 4.3 节还会再提到——llama.cpp 的特别之处不是"C++ 比别人快"，是它**压根没有一个独立的 Python 编排层**，四层全部揉进同一个 C++ 二进制。

### 4.2 调度 / 编排层：多数 Python，两家把请求粒度的路由/排队单独抽成 Rust

**Python 阵营**——vLLM 的调度器类定义在 `vllm:vllm/v1/core/sched/scheduler.py:73`，一行 `class Scheduler(SchedulerInterface):`；SGLang 的调度器类定义在 `sglang:python/sglang/srt/managers/scheduler.py:384`，`class Scheduler(`。两个类里装的都是"这一步该给哪些请求分配算力"这种业务逻辑——continuous batching 的排队、抢占、prefix cache 命中判断——这正是 2.2(b) 讲的"研究人员每周都会碰、需要快速迭代"的那层代码。

**llama.cpp 的请求队列同样是 C++**，跟 4.1 节它的 HTTP 层是同一个二进制、同一种语言。`llama.cpp:tools/server/server-queue.cpp:515` 的 `void server_response_reader::post_task(server_task && task, bool front) {` 是往队列里放一个新任务的入口。

**一个会打乱"主语言 = 决策语言"这个简单假设的例外：TensorRT-LLM**。第 1 节表里 TensorRT-LLM 的主语言是 Python，占 56%（`_PLAN.md:119`），如果只看这个数字，很容易猜它的调度决策也在 Python 里——但打开代码会发现不是这样。

这个例外恰好证明了本篇开头那句话："10/12 家主语言是 Python"这个统计,回答的是"这个仓库总共写了多少行 Python",不直接回答"决定这一步谁上 GPU 这件事是哪门语言做的"。

TensorRT-LLM 把这个决策放进了 C++,但整体代码量上 Python 依然占多数——因为 Python 层要做的模型接入、config 解析、LLM API 封装这些工作（2.2a、2.2b）本身就比一段调度算法的代码量大得多。**统计一个仓库总行数里哪种语言最多，和"关键路径上是哪种语言在做决定"，是两个不能互相替代的问题**——这正是本篇坚持要下沉到第 4 节文件行号级别、而不是停在第 1 节那张表就收工的原因。

两个独立的例子（TensorRT-LLM、MLC-LLM）说明这不是巧合,是**"高性能编译型运行时 + Python 高层 API"这一类架构的共同特征**——这类引擎往往本来就依赖一个独立的编译期产物（TensorRT 的 engine 文件、TVM 编译出的模块），调度逻辑顺理成章地被拉进了同一个编译单元里,而不是留在 Python 里跟解释器的调用开销较劲。

**这一节最该记住的对比**：vLLM/SGLang 的调度器是"单机内决定哪些请求进这一步的 batch"，Python 写没问题，因为决策频率跟模型前向频率是同一个数量级；TGI 的 router、Dynamo 的集群路由是"网络入口处对海量请求做逐条决策"，决策频率可能远高于模型前向频率——这才是两家选 Rust 的真实原因，而不是"Rust 总体上更适合写调度器"。

TensorRT-LLM、MLC-LLM 选了第三条路——决策逻辑本身用 C++ 写、编译进引擎，Python 完全不参与这一步的判断,只负责把结果之上的一切都包装成好用的 API。三种选择服务的都是同一个目的：让"决定这一步谁上"这件事,跑在一个不会拖慢它的语言里,只是"不会拖慢"在不同架构里落地成了不同的具体形式。

### 4.3 模型执行层：几乎全是 Python 调 PyTorch，llama.cpp 是 C++ 到底

**Python 调 PyTorch 是绝对主流**：vLLM 把一步前向的入口封装在 `vllm:vllm/v1/worker/gpu_model_runner.py:4284` 的 `def execute_model(` 方法里——这个方法内部把 token id、KV 位置组织成张量,调用一次 `self.model(...)`，这一行 Python 代码触发的是 PyTorch 底层 C++/CUDA 的真正计算，Python 自己不参与任何一次浮点运算。

同一个文件里 `vllm:vllm/v1/worker/gpu_model_runner.py:6937` 的 `def capture_model(self) -> int:` 是 CUDA Graph 录制的触发点——即便是这种把整串 kernel launch 录成一张图、绕开逐条调度开销的激进优化，触发录制的动作本身依然是从 Python 里发起的，因为"什么时候该录、录哪些 shape"仍然是编排决策,不是浮点运算。

**llama.cpp 是唯一一个把模型执行层也写成 C++ 的**：`llama.cpp:src/llama-context.cpp:1635` 的 `int llama_context::decode(const llama_batch & batch_inp) {` 是一步 decode 的核心入口——这个函数在 C++ 里完成"组织 batch → 调用计算图 → 采样"整条链路，没有独立的 Python 进程/线程参与这一步的编排决策。

这跟 4.1 节的 HTTP 层证据、4.2 节隐含的"llama.cpp 没有单独的调度器语言"合起来说明一件事：**llama.cpp 不是"把 vLLM 的架构翻译成 C++"，是从设计上就没有分出一个独立的 Python 编排层**——单进程、单语言、从接请求到吐 token 全在一个 C++ 二进制里。这是它 44% 主语言占比、以及能在没有 Python 解释器的设备上运行的根本原因。

顺带说一句 llama.cpp 表格里那 7% Python（`_PLAN.md:123`）是什么：不是运行时代码，是离线的权重格式转换脚本——`llama.cpp:convert_hf_to_gguf.py:175` 的 `def main() -> None:` 就是其中一个，负责把 HuggingFace safetensors 转成 llama.cpp 自己的 GGUF 格式。

这一步跑在"发布模型之前"，不跑在服务请求的热路径上，跟 4.2 节 TGI/Dynamo 的 Rust router 处于完全不同的性质——一个是运行时编排代码，一个是离线工具脚本，两者都不参与推理请求的实时处理，但原因南辕北辙。

**第三条路：Python 只是壳，模型执行完全外包给一个预编译的引擎（LMDeploy）**。LMDeploy 的做法跟 vLLM/SGLang 又不一样——它不是"Python 组织张量、调用 PyTorch 的 op"，而是把整个模型执行引擎（TurboMind）编译成一个独立的 C++/CUDA 共享库，Python 侧只做一件事：把它 `import` 进来当成一个黑盒调用。证据在 `lmdeploy:lmdeploy/turbomind/turbomind.py:31`：

```python

```

`_turbomind` 不是一个 Python 模块，是编译出来的扩展模块（`.pyd`/`.so`），真正的 attention、KV cache 管理、批处理执行全部在这个编译产物内部完成，Python 这一层能看到的只是它暴露出来的接口。

这跟 vLLM/SGLang"Python 逐层组织张量、每一层单独调用一次 PyTorch 算子"的做法在颗粒度上完全不同——TurboMind 把整个前向过程当成一个黑盒，Python 边界画在"进模型之前/出模型之后"，而不是"每个算子调用之前/之后"。

三种模型执行层的做法（vLLM/SGLang 细粒度调用 PyTorch、llama.cpp 全 C++、LMDeploy 粗粒度调用一个预编译引擎）殊途同归：**真正的浮点计算，没有一家指望 Python 解释器自己去做**，区别只在于 Python 和"干活的那部分"之间的边界画在哪个粒度上。

### 4.5 补完 SGLang 6% 和 vLLM 5% 那部分 Rust 到底是什么

第 1 节的表提到 SGLang 有 6% Rust、vLLM 有 5% Rust（`_PLAN.md:120-122`），但 4.1、4.2 节只举了 TGI 和 Dynamo 的例子——这两家的 Rust 占比恰好也留在同一层，值得把证据补全，不然"四个项目都把 Rust 放在同一层"这句话就只验证了一半。

**SGLang 有自己的 Rust 网关，独立于 4.2 节讲的 Python `Scheduler`**。`sglang:sgl-model-gateway/README.md:3` 是这个组件自己的定位说明："High-performance model routing control and data plane for large-scale LLM deployments. ```rust

具体的多路由管理逻辑在 `sglang:sgl-model-gateway/src/routers/router_manager.rs:62`，`pub struct RouterManager {`。这套东西跟 4.2 节引用的 `sglang:python/sglang/srt/managers/scheduler.py:384` 那个 Python `Scheduler` 类**不是同一层**——`Scheduler` 决定单机内这一步 batch 里放哪些请求，`sgl-model-gateway` 决定多副本场景下一条请求该先落到哪个 worker。SGLang 的做法跟 Dynamo 几乎是同一个思路：单机决策留 Python，跨机/大规模路由决策换 Rust。

**vLLM 的 5% Rust 是一个明确标注为实验性的替代前端**，仓库自己的说明写在 `vllm:rust/README.md:3`："This is a Rust drop-in alternative frontend for vLLM. 代码层面，`vllm:rust/src/server/src/lib.rs:4` 的文档注释是"Minimal OpenAI-compatible HTTP server above `vllm_chat`"，往下 `vllm:rust/src/server/src/lib.rs:158` 的 `pub async fn serve(config: Config, shutdown: CancellationToken) -> Result<()> {` 是它的服务入口，用的同样是 axum——跟 4.1 节 TGI、Dynamo 用的是同一个 Rust web 框架。

**这一节补的证据把"哪一层"这条主线扎得更实**：四个出现 Rust 的引擎——Dynamo（集群路由，27%）、TGI（router,12%）、SGLang（model gateway,6%）、vLLM（northbound serving layer,5%）——没有一个例外,全部落在"HTTP/协议层"或"跨请求/跨机路由决策层"，且四家里至少两家（Dynamo、SGLang）的官方自我描述原文里直接用了"routing"这个词。

占比数字从 27% 到 5% 跨度很大,但落点位置的一致性远比占比数字本身更能说明问题——这也是为什么本篇从第 1 节开始就强调"别只看占比,看它落在哪"。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

### 5.1 四条核心决策

**决策一：主体语言选 Python**

- **为什么这样**：模型定义/权重生态锁在 Python 里（2.2a），调度策略需要高频迭代（2.2b），而真正的浮点计算已经外包给 GPU/BLAS，Python 在编排这个位置不吃亏（2.2c、4.3、4.4）。
- **不这样会怎样**：新模型接入要重写一遍权重加载和 config 解析，追不上模型发布的速度；调度策略每改一行都要走"改代码 → 编译 → 链接 → 重启"，研究和生产之间的迭代速度会被拖垮，这正是为什么 10/12 家用同一个默认项（第 1 节表）。
- **什么时候可以不这样**：目标从一开始就不是"接入 HF 生态里的任意新模型"，而是"极少数固定模型、极致的端侧/离线部署"——这时候 Python 解释器本身的启动开销、依赖体积、对操作系统的要求都变成负资产，第 5.2 节的"端侧部署"这一行给的就是这种取舍，llama.cpp 是这条路径唯一的头部代表。

**决策二：把请求粒度、高频调用的那一小层单独抽出来用 Rust 重写，而不是重写整个引擎**

- **为什么这样**：2.3 节的判据翻转只发生在"决策频率可能远高于模型前向频率"的场景——TGI 的 router 要在每条新请求进来时做一次决策，Dynamo 的集群路由要在多机负载均衡下对海量请求逐条路由（4.2 节）。这个场景里请求条数、而不是模型算了多久,主导时间，Python 解释器的固定开销此时是实打实的成本。
- **不这样会怎样**：留在 Python 里，随着并发请求数上涨，router/路由层的调度开销会先于模型计算成为瓶颈——尤其是小模型、高并发、短序列的场景，GPU 一步前向本身就短，追上它的门槛更低。
- **什么时候可以不这样**：请求粒度的决策频率本来就不高（并发量不大、批处理窗口本身较长），或者这一层的决策逻辑还在频繁变动、稳定不下来——这时候把它单独抽出来重写的工程成本，可能超过它省下来的调度开销。TGI 和 Dynamo 的调度决策**主体逻辑仍然留在 Python 里**（TGI 主语言仍是 Python 57%，`_PLAN.md:127`），被抽走的只是"接请求 + 排队 + 路由"这一小段最高频的路径，不是整个决策系统。

**决策三：端侧/无 GPU 部署目标，从一开始就选单一语言、单一二进制**

- **为什么这样**：llama.cpp 的四层（4.1-4.4 节）全部揉进同一个 C++ 二进制，没有独立的 Python 编排进程，也就没有"要不要装 Python 解释器"这个前置依赖——这对跑在手机、笔记本、嵌入式设备上的场景是刚需,而不是可选项。
- **不这样会怎样**：如果照搬"Python 编排 + C++/CUDA 算子"这套主流架构去做端侧部署，等于把 Python 解释器、pip 依赖、动态链接这些东西也一起打包进目标设备,这在资源受限的端侧环境里往往行不通或代价过高。
- **什么时候可以不这样**：目标设备本身资源充裕（服务器级 GPU、不缺内存和存储）、且需要快速接入新发布的模型——这时候主流架构（决策一）的接入速度优势远大于单二进制的部署优势,不值得为了"单一二进制"这个好处放弃 Python 生态的接入速度。

**决策四：算子层能不写就不写，外包给专门维护的 kernel 库或用 Triton 而不是手写 CUDA C**

- **为什么这样**：attention 这类核心算子的性能工程需要专门团队长期投入（4.4 节 FlashAttention 的例子），推理引擎项目自己维护一份等价实现的边际收益递减得很快；Triton 用 Python 语法写 kernel，能在不引入 CUDA C 工具链的情况下拿到接近手写 CUDA 的性能（LightLLM 的例子）。
- **不这样会怎样**：自己维护一份 CUDA 实现，意味着上游 kernel 库每一次性能优化、每一次新硬件适配，都要自己重新做一遍；对精力有限的团队/个人项目，这是持续的维护税。
- **什么时候可以不这样**：算子本身是这个引擎的核心差异化能力、或者现有的通用 kernel 库不支持你的模型架构里某个特殊算子（比如某种新的 attention 变体、自定义的量化格式）——这时候手写 CUDA/Triton kernel 不是可选项，是不得不做的事,第 4 节里所有引擎自己维护的那些非 attention 算子（比如 LightLLM 129 个 Triton 文件里的大部分）就是这种情况。

### 5.2 从 0 开始写，按目标分叉的选型表

第 5.1 节的四条决策服务于不同目标。把它们收进一张表，先问自己"我写这个引擎是为了什么"，再对照选：

| 你的目标 | 主体语言 | 理由 | 对应 12 家的参照 |
|---|---|---|---|
| **学原理**：搞懂自回归解码、KV 缓存、分页、批处理这些第一性原理 | Python（甚至纯 numpy） | 不需要生产级性能，需要的是"每一步矩阵乘都露在外面、改一行立刻能验证"——这正是本库 `_lab/` 的做法（`_PLAN.md:53-64`）。语言的执行速度在这个目标下完全不重要，重要的是你能不能改代码验证自己的理解。 | 无直接参照——12 家都是生产级项目，但它们的调度器代码（4.2 节）证明了"用 Python 表达调度算法"这件事本身没有任何门槛 |
| **端侧 / 无 GPU 部署**：让引擎跑在手机、笔记本、嵌入式设备上 | C++ | 单一二进制、无解释器依赖、可控的内存占用（决策三） | llama.cpp——唯一的头部代表，代价是新模型支持要手写适配，不能直接吃 HF 生态的红利 |
| **集群服务**：多机、高并发、要接入不断更新的开源模型 | Python 主体 + 视瓶颈把 router/路由层换成 Rust | 需要 HF 生态的接入速度（决策一），高并发场景下网络入口处的请求粒度开销可能需要单独优化（决策二） | vLLM/SGLang（Python 主体）、TGI/Dynamo（Python 主体 + Rust router/路由层），四家目前的生产实践都是这个组合 |
| **想给某个上游引擎提 PR** | 学那个引擎的主语言 | 10/12 家主体是 Python，贡献代码要先能读懂、能编译、能跑测试——用引擎自己的语言最快达到这个门槛 | 直接对照第 1 节的表：想往 vLLM/SGLang/TGI（调度器部分）提 PR，学 Python；想往 llama.cpp 提 PR，学 C++；想往 TGI 的 router 或 Dynamo 的路由层提 PR，学 Rust |

**这张表最重要的读法**：横着看每一行都不是"这个语言全面碾压"，是"这个目标下,这门语言在这一层的代价最小"。竖着看会发现同一个引擎（比如 TGI）可能同时出现在"集群服务"和"想提 PR"两行里,但给出的建议不完全一样——因为"用什么语言写"和"贡献代码要会什么语言"是两个相关但不相同的问题,前者取决于你在造什么,后者取决于你在改谁的代码。

### 5.3 一个具体的成长路径：语言决定不需要一次做完

第 5.2 节的表是按"最终目标"分叉的静态判断，但真实的成长路径往往是**渐进的**——本库 `02-最小可跑引擎/` 那一串篇目本身就是一条这样的路径（`01-第一版-朴素前向` → `02-加上KV缓存` → `03-分页KV与块管理` → `04-连续批处理` → `05-前缀缓存` → `06-采样-停止条件-流式输出` → `07-把它变成一个HTTP服务`，`_PLAN.md:154-161`），语言决定完全可以跟着这条路径分阶段做,不需要在第一行代码之前就想清楚终局：

1. **第一阶段——只有模型执行层和算子层，其他两层不存在**：`02-最小可跑引擎/01` 到 `05` 这几篇，做的事情是朴素前向、KV 缓存、分页、批处理——全部是"给定一批 token，怎么算出下一批 token"，根本没有 HTTP 请求、没有跨请求调度。这个阶段选 Python（甚至纯 numpy，本库 `_lab/minigpt.py` 就是这么做的）没有任何争议——4 层里还只存在 2 层,2.2、4.3、4.4 节讲的"计算外包给 BLAS/PyTorch，Python 只编排"这条理由从一开始就适用。
2. **第二阶段——补上调度/编排层**：`02-最小可跑引擎/04-连续批处理` 开始，出现"这一步该给哪些请求分配算力"这种决策，对应 4.2 节的 vLLM/SGLang `Scheduler`。这一步大概率仍然留在 Python 里——单机内的调度决策频率跟模型前向频率是同一个量级（4.2 节"这一节最该记住的对比"），2.3 节讲的判据翻转在这个阶段通常还不会发生。
3. **第三阶段——补上 HTTP/协议层**：`02-最小可跑引擎/07-把它变成一个HTTP服务`，这时候才第一次需要考虑"要不要用 Rust"——但即便到了这一步，4.1 节的证据显示默认选项仍然是 Python/FastAPI（vLLM、SGLang、TensorRT-LLM、LightLLM、Tokasaurus 五家都是），只有当这一层真正开始承受第 2.3 节讲的那种"请求条数远超模型前向频率"的压力时，才轮到考虑把这一层单独换成 Rust——而且如决策二所说，换的是这一层，不是回头重写前两个阶段已经写好的 Python 调度/模型代码。
4. **第四阶段（可选）——只有真的要接入不断更新的开源模型生态,才需要认真考虑要不要复用 HF `transformers` 的 config/权重加载**（2.2a）。如果你的引擎从一开始就只服务少数几个你自己训练或手工适配的模型，这一条理由的分量会小很多——这也是为什么"目标"必须先问清楚：**同一套四层框架，理由的权重会因为你要不要接入开源模型生态而完全不同**。

这条路径最重要的启示是：**语言选型不是一次性的架构决定，是随着引擎长出新的一层，逐层去问"这一层现在需不需要换语言"**。本库自己的篇目顺序——先讲原理（01-地基）、再一层层搭引擎（02-最小可跑引擎）、最后才讨论语言（03-语言选型，也就是本篇）——不是随意安排的目录结构，是这条成长路径本身的直接体现。

## 6. 常见错误与踩坑

**误区一："Rust 更快，所以推理引擎该用 Rust 重写"**

12 家没有一家这么做，不是因为团队没想到 Rust,恰恰是四家都用了 Rust（Dynamo、TGI、SGLang、vLLM，第 1 节表），只是都只用在一层，且都是同一类层——请求粒度、和模型计算量无关的那一层（HTTP、router、集群路由,4.1、4.2 节）。没有一家把模型执行层或算子层换成 Rust,因为那两层的"计算"本来就已经外包给了 GPU/BLAS/FlashAttention（2.2c、4.3、4.4 节）——语言换了也换不动已经外包出去的浮点运算。

"用 Rust 重写"这句话默认了"整个引擎的瓶颈都在语言执行速度上",但 4 层里有 2 层的瓶颈根本不在这里,重写这两层不会带来这个默认所期待的收益,只会带来失去 Python 生态接入速度的代价（决策一）。

**误区二："Python 慢，所以不能写引擎"**

两个真实存在、能跑的引擎直接反驳这句话：Tokasaurus 95% 是 Python（`_PLAN.md:130`），LightLLM 86% 是 Python 且 **0 个 CUDA 文件、129 个 Triton 文件**（`_PLAN.md:136`，4.4 节给了具体行号）。

这条误区错在把"用 Python 写"等同于"用 Python 解释器去执行浮点运算"——但 4.3、4.4 节已经拆穿了这个默认：模型执行层的"计算"是 PyTorch 的 C++/CUDA 内核在做，算子层的"计算"是 Triton JIT 编译出的 GPU 机器码或者外部 FlashAttention 库在做，Python 解释器本身从头到尾没有算过一次浮点乘加。

判断一个引擎是不是"用 Python 写的",要看 Python 在架构里承担的是编排还是计算,不是看源文件后缀占比。

Tokasaurus 是这条误区最彻底的反例——它连 HTTP 层、调度层都没有换语言，四层里能留在 Python 的全留在 Python：HTTP 层的 `app = FastAPI(lifespan=lifespan)` 在 `tokasaurus:tokasaurus/server/endpoints.py:56`；调度决策函数在 `tokasaurus:tokasaurus/manager/scheduler.py:576`，`def schedule(`。

模型前向在 `tokasaurus:tokasaurus/model/llama.py:356`，`def forward(self, batch_state: BatchState):`——连 Llama 的前向实现都是自己手写的 Python 类，没有像 vLLM/SGLang 那样接一层 HF `transformers` 的 config。2.2a 讲的路径依赖在这里没有出现,这是它代码量小、能做到 95% Python 的原因之一。

真正让它在这种"全 Python"架构下还能喂饱 GPU 的，是 `tokasaurus:tokasaurus/model/llama.py:63` 那一行 `if extra_config.torch_compile:`——`torch.compile` 是另一种"压缩 Python 发指令开销"的手段（和 4.5 节提到的 CUDA Graph 是同一类思路,但做法不同）：CUDA Graph 录的是已经发出的 kernel launch 序列,`torch.compile` 是在模型前向执行前,把 Python 里逐层调用的一串算子编译融合成更少的调用。

这进一步印证 2.2(c)、2.3 节的判据：只要有办法把"发指令"这一步的开销压下去，Python 解释器本身的存在从来不是理论上的性能天花板。

**误区三："必须自己写 CUDA 才能有性能"**

反例就是 LightLLM——0 个 CUDA 文件，靠 Triton kernel（4.4 节 `lightllm:lightllm/common/basemodel/triton_kernel/add_in_place.py:7`）撑起自定义算子，同时是真实能跑、被使用的推理引擎。

更进一步，vLLM 在能用现成 FlashAttention 的场景下,连 Triton 都不写,直接 `import` 外部库的函数（4.4 节 `vllm:vllm/v1/attention/backends/flash_attn.py:44-47`）。这条误区把"自己动手写底层 kernel"当成了性能的必要条件,但 12 家的真实做法说明性能工程可以是"选对现成的专门库",不一定是"亲手实现一遍"——写不写 CUDA 是一个工程分工问题,不是一个能力门槛问题。

**误区四：把"哪一层"和"整个引擎"混为一谈**

第 4 节反复出现的模式是：**同一个引擎在不同层用不同语言**，TGI 是 Python 调度器主体 + Rust router（4.1、4.2 节），vLLM 是 Python 主体 + 依赖外部 FlashAttention/CUDA 算子（4.3、4.4 节）。看到"TGI 有 12% Rust"就下结论"TGI 是个 Rust 项目"，或者看到"vLLM 主语言是 Python"就下结论"vLLM 里没有 C++/CUDA 代码"，都是把第 1 节那张粗粒度的表当成了引擎架构的全部。

粗粒度的语言占比表只能回答"整体上哪种语言的代码行数多"，回答不了"关键路径上真正跑在哪层的是什么"，这正是本篇要拆到第 4 节文件行号级别的原因。

**误区五：把"主语言占比"直接当成"关键决策所在的语言"**

这是误区四的一个更隐蔽的变体，专门被 TensorRT-LLM 打脸（4.2 节）：它的主语言是 Python、占 56%，如果止步于第 1 节的表，很自然会以为它跟 vLLM/SGLang 一样,调度决策也在 Python 里——但真正做"这一步该放行哪些请求"这个判断的 `CapacityScheduler::operator()`（`tensorrt-llm:cpp/tensorrt_llm/batch_manager/capacityScheduler.cpp:708`）是 C++。

Python 层只是通过 `tensorrt_llm.bindings` 这层编译产物去调用它（`tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:48`）。"总行数里哪种语言最多"统计的是仓库里所有代码——包括 API 封装、参数校验、config 解析、测试代码——这些工作量本身就可能远大于一段调度算法。

"关键路径的决策在哪种语言里"问的是完全不同的问题。

这条误区提醒的是本篇通篇的方法论：**统计数字能告诉你从哪里开始看，不能替你看完**，真要确认"这一层是什么语言"，唯一靠得住的办法是打开那份源码，找到那个具体做决策的函数，这也是第 3 节反复强调"自己跑一遍、别信抄来的数字"的另一层含义。

## 7. 自测题与延伸阅读

**自测题（闭卷回答，答案都在本篇里）**：

1. 第 1 节的表里，12 个引擎有 10 个主语言是 Python，但 Rust 出现在 4 个项目里。这 4 个项目里 Rust 出现的位置有什么共同点？为什么模型执行层和算子层几乎没有 Rust？
2. 为什么"Mooncake 是 C++ 写的"这个事实不能直接类比到"推理引擎该用 C++ 写"这个结论上？（提示：它到底是不是推理引擎）
3. TGI 和 Dynamo 都用 Rust 重写了请求粒度的那一层，但两家 Rust 代码解决的具体问题不完全一样——TGI 的 `queue.rs` 和 Dynamo 的 `kv_router.rs` 各自的核心方法叫什么、分别做什么决策？
4. llama.cpp 的 7% Python 代码是干什么用的？它跑在服务请求的热路径上吗？这跟 TGI 的 12% Rust 代码在"是否参与实时请求处理"这一点上有什么本质区别？
5. LightLLM "0 个 CUDA 文件"这个事实，反驳的是哪一句常见的错误论断？它是怎么在不写 CUDA C 的情况下让自定义算子跑在 GPU 上的？
6. 第 5.2 节的判据表里，如果你的目标是"给 SGLang 的调度逻辑提一个 PR"，该学什么语言？如果目标是"给 SGLang 的某个 CUDA kernel 提性能优化 PR"呢？两个答案为什么不一样？
7. 把你自己想写的推理引擎代入第 5.2 节的四行判据表——你的目标最接近哪一行？如果你的目标同时沾一点"学原理"又沾一点"集群服务"，你会先做哪一层的语言决定，为什么？
8. TensorRT-LLM 的主语言统计是 Python 56%，但它真正做批处理决策的代码是什么语言写的？这个例子说明"仓库总行数里哪种语言最多"和"关键路径的决策在哪种语言里"是不是同一个问题？
9. LMDeploy 的 TurboMind、KTransformers 的 `KTransformersOps`、vLLM 的 `flash_attn_varlen_func` 都是 Python 代码里 `import` 进来的东西，但三者被外包出去的边界粒度不一样——分别是"整个模型前向"、"某一类冷门算子"，还是"某个标准算子"？这跟第 5.1 节决策四"什么时候不得不自己写 kernel"是什么关系？
