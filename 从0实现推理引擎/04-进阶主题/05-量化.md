# 量化

> **一句话**：量化省的是读权重/KV 的字节数，不是乘法的次数。
> **前置**：`02-自回归解码为什么是访存瓶颈.md`

## 0. 这一篇要解决什么问题

先把最容易被说反的一条摆在最前面，后面所有内容都是在证明它、量化它、给它划边界：

> **权重量化省的是「读权重的字节数」，不是「乘法的次数」。**
> weight-only 量化下，权重按 int8/int4 存，**算的时候还要反量化回浮点**，
> FLOPs 一点没少，甚至还多了反量化那几下。
> 它有用，纯粹是因为 decode 本来就访存受限——**分母小了，分子没动。**

`02-自回归解码为什么是访存瓶颈.md` 已经算过一张表：fp32、`bs=1` 时算术强度恒为 0.50，跟上下文长度无关，因为每个参数、每个 KV 元素都是"一次乘加（2 FLOP）读 4 字节"。那篇文章证明了 decode 的瓶颈在分母（字节数），不在分子（FLOPs）。这一篇接着往下问：**既然瓶颈在分母，那把分母的每个元素从 4 字节压到 1 字节甚至半字节，会发生什么？**

三个问题，对应下面三节的重点：

1. **误差能不能先算出来，而不是跑出来才知道？**（`## 2.2`、`## 3`）——能。对称量化的噪声近似均匀分布，误差有解析预测公式，这条方法论比任何一个具体的量化方案都更值得记住。
2. **量化谁——权重还是 KV——取决于什么？**（`## 2.5`、`## 5.2`）——取决于工作点（上下文长度 × batch），没有通用答案，而且这条结论比看上去更容易被写窄——`## 2.5` 会把我自己第一版写窄、又被自检打脸的过程原样摆出来。
3. **真实引擎接住"量化"这件事之后，会碎成什么样子？**（`## 4`）——vLLM 一个目录下挂了几十种方案，这个数字本身就是答案的一部分。

## 2. 原理

### 2.1 量化省的到底是哪一步

一次矩阵乘 `y = x @ W` 分两件事：**读 `W`**（访存）和**做乘加**（计算）。weight-only 量化改的是 `W` 在显存里怎么存——int8/int4——但矩阵乘本身要求两个操作数类型一致（或者硬件有专门的低精度 GEMM kernel），大多数朴素实现的路径是"读出低比特权重 → 反量化回 fp16/fp32 → 跟激活做乘加"。反量化本身也是计算（`## 4.3` 会看到真实引擎里这一步长什么样），**乘加的次数一点没少，还多出反量化那几下**——`intensity_with_quant()`（`_lab/quantize.py:102-123`）的注释把这句话直接写在了代码上方：`w_bytes`、`kv_bytes` 两个旋钮改变的只是 `bytes` 这一项，`flops` 那一行的计算式里根本不出现这两个旋钮。

省的是访存这一步：字节数从 `4 × 元素个数`（fp32）降到 `1 × 元素个数`（int8）甚至更低。`02-自回归解码为什么是访存瓶颈.md` 证明了 decode 阶段瓶颈就在访存，所以**分母变小，耗时跟着降**——但前提是分母真的是瓶颈。`## 2.5` 会把"什么时候分母不是瓶颈"讲清楚。

### 2.2 误差不用拍脑袋，先算出来再对

对称量化把权重矩阵按 `scale = amax / qmax` 缩放、取整、截断，再乘回 `scale`（`_qdq()`，`_lab/quantize.py:42-47`）。这个过程引入的量化噪声，在权重分布不是病态的情况下，近似**均匀分布**在 `[-scale/2, scale/2]` 之间——因为取整误差 `round(w/scale) - w/scale` 本身就是均匀分布在 `[-0.5, 0.5]`。均匀分布的标准差是区间半宽除以 `√12`，所以：

```
噪声标准差 ≈ (scale / 2) / (√12 / 2) = scale / √12
相对误差   ≈ (scale / √12) / std(w)
           = (amax / qmax / √12) / std(w)
```

`selftest()`（`_lab/quantize.py:187`）把这条公式直接写成代码算出 `pred`，再跟实测的 `e8t` 比：0.01079 对 0.01076，差 0.3%。**这条方法论值得单独拎出来讲**：它不是"验证量化实现对不对"的众多手段之一，而应该是**第一步**——任何量化实现，动笔之前先按这条公式估出应有的误差量级，实现完了拿实测一比，对不上就是实现有问题（最常见的是 scale 算法算偏了，比如该取绝对值最大值却漏了负数、该按某个轴取 max 却按错了轴）。反过来，如果一上来就凭感觉设一个"误差应该小于 0.05 吧"这样的阈值，量化实现哪怕算错了 scale，只要凑巧落在这个随手设的阈值以内，bug 照样能蒙混过关。

### 2.3 一个离群值为什么能毁掉整个矩阵

`qdq_per_tensor()`（`_lab/quantize.py:50-57`）用整个矩阵共享一个 `scale`，由 `abs(w).max()` 决定。问题在于**这个 scale 同时决定了全部权重的量化步长**：如果矩阵里有一个异常大的权重（比如 50，而其余权重的量级是 0.05），`scale = 50 / 127 ≈ 0.394`，其余那些量级只有 0.05 的权重相对这个步长几乎全部被量化到 0 附近的极少几个格点上——**离群值把量化步长撑大了几十倍，其余权重的有效位数被这一个数吃光了**。`selftest()` 注入一个离群值（`_lab/quantize.py:207-215`）后，per-tensor 误差从 0.01079 直接跳到 0.24782，23 倍。

`qdq_per_channel()`（`_lab/quantize.py:60-66`）把 `scale` 从"整个矩阵一个"改成"每个输出通道一个"，代价只是每个通道多存一个 scale（相对成千上万个权重可以忽略）。同样注入离群值，误差只有 0.01556——仅为 per-tensor 的 6.3%，因为离群值只撑大了**它所在那一列**的 scale，其余列的量化精度完全不受影响。**这就是 per-channel 是工程默认选择的全部理由**：不是它误差天生更低（正常权重下 per-channel 也确实略低，`## 1` 第一张表隐含地能看出来），而是它把"一个离群值"这种真实权重分布里几乎必然存在的现象，从"摧毁整个矩阵"降级成"损失一列"。

### 2.4 所谓 int4，不是 4 bit

`qdq_group()`（`_lab/quantize.py:69-81`）把 scale 的粒度进一步细分到"每 `group` 个输入维一个"，常用于 int4——分组越细，每组内部的数值范围越窄，量化步长越小，误差越低（`selftest()` `_lab/quantize.py:191-192`：int4/group=64 的误差比 int8/per-channel 还大，位宽仍是主导项，但分组本身在朝着更细的方向努力减小误差）。

代价是**每一组都要单独存一个 scale**，`bytes_per_weight()`（`_lab/quantize.py:84-92`）把这笔账算清楚：

```
实际每权重字节数 = bits / 8 + scale_bytes / group
```

`group=32`、`scale_bytes=2`（fp16 scale）时：`4/8 + 2/32 = 0.5 + 0.0625 = 0.5625` 字节 = **4.50 bit**；`group=128` 时：`4/8 + 2/128 = 0.515625` 字节 = **4.125 bit**（`_lab/quantize.py:218-222`）。**group 越小，误差越低，但"int4"这个名字越名不副实**——宣传口径说的是 bit 数本身，真实口径是 bit 数加上摊到每个权重头上的 scale。这不是量化特有的现象，是所有"分组换精度"的方案共同要付的账：分得越细，metadata 开销占比越高。

### 2.5 量化谁取决于工作点——以及我自己在这条上写窄过一次

`intensity_with_quant()`（`_lab/quantize.py:102-123`）把"权重占访存多少""KV 占访存多少"分开算，口径跟 `02-自回归解码为什么是访存瓶颈.md` 的 `analytic_cost` 一致，只是把权重和 KV 的每元素字节数拆成了两个独立旋钮：

```
b_w  = w_bytes  × (mm + 2 × batch × d_model)
b_kv = kv_bytes × batch × ctx × 2 × n_layer × d_model
```

`mm` 是固定的一大坨——跟 `ctx`、`batch` 都无关，是模型权重本身的大小；`b_kv` 里 `batch` 和 `ctx` 都在乘法里，**KV 的字节数随两者线性增长，权重的字节数几乎不随它们变**（`2 × batch × d_model` 那一小项是每步新增的 Q/K/V 投影输入，量级远小于 `mm`）。`## 1` 第二张表 `ctx=128, batch=1` 那一行权重占 99.5%，就是这条结构性差异最极端的体现。

**这一条我第一版写窄过，被自己的自检打脸**：原以为"上下文一长，KV 自然就占主导"，于是想当然地断言 `ctx=16384` 时 `kv_share > 0.5`。实测 `ctx=16384、batch=1` 时 KV 只占访存的 39.5%（`_lab/quantize.py:231-238` 的注释和断言把这段自我纠正原样保留了下来）——权重仍然是主项。真相是：**单条请求的 KV 再长，也只有一份；权重却是固定的一大坨，不会因为某条请求短就变小**。KV 要反超权重，需要**长上下文和大 batch 两个条件同时成立**——`batch=64` 时 `ctx=16384` 的 KV 占比才涨到 97.7%，因为这时候 KV 的字节数被 64 条请求各自的一份 KV 乘出来了，而权重只读一遍就被 64 条请求共用。

**结论直接决定了该量化谁**：短上下文小 batch（比如典型的对话场景，单用户、几百 token 上下文）应该量权重；长上下文大 batch（比如高并发的长文档服务）应该量 KV。没有"量化就该量权重"或者"量化就该量 KV"这种通用答案，只有"先算出这次服务的工作点落在哪，再决定量哪一项"。

把 `ctx=16384、batch=1` 和 `ctx=16384、batch=64` 这两行拆开算一遍，能看清"两个条件同时成立"具体指什么。`mm`（固定权重字节基数）在两种 batch 下完全相同，`b_kv` 却随 batch 线性放大：

```
                          batch=1           batch=64
b_w  = 4×(mm+2×batch×d_model)   ≈ 2.629×10¹⁰   ≈ 2.630×10¹⁰   （几乎不变）
b_kv = 4×batch×ctx×2×n_layer×d_model
                                 ≈ 1.718×10¹⁰   ≈ 1.100×10¹²   （× 64 倍）
kv_share = b_kv / (b_w+b_kv)       39.5%           97.7%
```

`b_w` 那一行两个 batch 下几乎没变（唯一随 batch 变化的 `2×batch×d_model` 项本来就比 `mm` 小好几个数量级），`b_kv` 那一行被 `batch` 直接乘了 64 倍——这就是"长上下文不够、还要大 batch"这句话在算式层面的来源：**只有 `batch` 这个乘数够大，`b_kv` 才能追上原本占绝对多数的 `b_w`**。如果只看 `ctx` 变大这一件事（`batch` 固定为 1），`b_kv` 确实也在涨（`ctx` 本身就在 `b_kv` 的乘法链里），但 `b_w` 纹丝不动，两者的比值涨得远没有直觉预期的那么快——`## 1` 表格里 `ctx=16384, batch=1` 那一行 60.5%/39.5% 就是"只让 `ctx` 一个变量变大"能达到的上限附近，离反超还差得远。

再多说一层：`## 1` 第二张表里"权重占访存"和"权重 int8 省"这两列的比值几乎恒定——`99.5% × 75% ≈ 74.6%`，`60.5% × 75% ≈ 45.4%`，`2.3% × 75% ≈ 1.8%`（这里 `75%` 是 fp32→int8 的字节缩减比例，`4→1` 字节）。**这不是巧合，是量化收益的通用公式**：

```
总访存节省比例 ≈ 该项占总访存的份额 × 该项位宽的相对下降幅度
```

`## 5` 会把这条公式落回到"量化只能省它占的那部分"这条决策原则上。

## 3. 自己动手：`_lab/quantize.py` 里对应的实现

### 3.1 `_qdq()`：对称量化再反量化，一处兜底

`_qdq()`（`_lab/quantize.py:42-47`）是全文件唯一真正做量化-反量化的函数，其它三个量化函数都是围着它包了一层"怎么算 `amax`"：

```python
def _qdq(w, amax, bits):
    qmax = 2 ** (bits - 1) - 1
    scale = np.where(amax == 0, 1.0, amax / qmax)
    q = np.clip(np.rint(w / scale), -qmax - 1, qmax)
    return (q * scale).astype(np.float32)
```

`np.where(amax == 0, 1.0, ...)`（`_lab/quantize.py:45`）是唯一的兜底：如果某一列（或某一组）全为 0，`amax` 也是 0，直接用它做除数会产生 `nan`。`selftest()` 专门造了一个全零矩阵验证这一点不会出错（`_lab/quantize.py:202-204`）。`np.clip(..., -qmax-1, qmax)`（`_lab/quantize.py:46`）处理的是对称量化天生的不对称：`int8` 的可表示范围是 `[-128, 127]`，但 `qmax` 取 127（对称设计，正负各留 127 档，`-128` 那一档理论上可用但没被 `scale` 覆盖到，`clip` 负责把它接住）。

### 3.2 `qdq_per_tensor()` / `qdq_per_channel()`：`amax` 怎么取决定了粒度

```python
def qdq_per_tensor(w, bits=8):
    return _qdq(w, np.abs(w).max(), bits)

def qdq_per_channel(w, bits=8, axis=0):
    return _qdq(w, np.abs(w).max(axis=axis, keepdims=True), bits)
```

（`_lab/quantize.py:50-66`）两个函数除了 `amax` 的取法，逻辑完全一样——`per_tensor` 是一个标量，`per_channel` 是一个沿 `axis=0` 取 max 后 `keepdims=True` 的向量，靠 numpy 的广播机制自动把每一列的 scale 应用到那一列的所有元素上。**这两个函数的全部区别就是 `amax` 这一个参数的形状**，`## 2.3` 讲的误差差异全部由这一处形状差异导致。

### 3.3 `qdq_group()`：先 reshape 出分组维度，再复用 `_qdq`

```python
def qdq_group(w, bits=4, group=64):
    n_in, n_out = w.shape
    pad = (-n_in) % group
    if pad:
        w = np.concatenate([w, np.zeros((pad, n_out), w.dtype)], 0)
    g = w.reshape(-1, group, n_out)
    out = _qdq(g, np.abs(g).max(axis=1, keepdims=True), bits)
    return out.reshape(-1, n_out)[:n_in]
```

（`_lab/quantize.py:69-81`）`(-n_in) % group`（`_lab/quantize.py:76`）是 Python 里对负数取模的一个常见技巧，用来算"填到 `group` 的整数倍还差多少"——比 `group - n_in % group` 更简洁，因为它天然处理了"刚好整除、不需要填充"的情况（此时结果是 0，而后一种写法会算出 `group`，还得再判断一次）。补零之后 `reshape(-1, group, n_out)`（`_lab/quantize.py:79`）把输入维拆成"组数 × 组内位置 × 输出维"三维，对中间那一维（`axis=1`）取 `max`，就是"每组一个 scale"。最后 `[:n_in]`（`_lab/quantize.py:81`）把补的零切掉，保证输出形状跟输入一致。

### 3.4 `bytes_per_weight()`：把宣传口径换算成真实口径

```python
def bytes_per_weight(bits, group, scale_bytes=2):
    base = bits / 8.0
    return base if group is None else base + scale_bytes / group
```

（`_lab/quantize.py:84-92`）`group=None` 时就是位宽本身除以 8（比如 int8 恒为 1.0 字节）；有分组时加上摊到每个权重头上的 scale 开销。`## 2.4` 已经用这个函数算出了 int4 的两个真实位宽，这里只强调一点：**这个函数不做任何量化计算，只做算术**，它存在的唯一目的就是把"位宽标称值"和"真实存储成本"这两个经常被混为一谈的数字分开算清楚。

### 3.5 `rel_err()`：统一的误差量尺

```python
def rel_err(a, b):
    return float(np.linalg.norm(a - b) / np.linalg.norm(a))
```

（`_lab/quantize.py:95-97`）相对 Frobenius 误差——分子是量化前后矩阵的差的范数，分母是原矩阵自己的范数。用相对误差而不是绝对误差，是因为不同层、不同矩阵的权重量级本身差异很大（有的层权重标准差 0.02，有的 0.1），绝对误差没法跨层比较，相对误差才有可比性。`## 2.3` 讨论离群值时能看出这个指标的一个副作用：分母（`np.linalg.norm(a)`）本身也会被离群值显著拉大，所以"误差涨了多少倍"这个结论要连着分子分母一起看，不能只盯着分子。

### 3.6 `intensity_with_quant()`：访存账的核心，FLOPs 那一行完全不含位宽

```python
mm = n_layer * (4 * d_model ** 2 + 8 * d_model ** 2) + d_model * vocab
flops = 2 * batch * mm + batch * n_layer * n_head * 4 * ctx * d_head
b_w = w_bytes * (mm + 2 * batch * d_model)
b_kv = kv_bytes * batch * ctx * 2 * n_layer * d_model
total = b_w + b_kv
```

（`_lab/quantize.py:115-119`）`## 2.1` 已经点出这个函数结构本身就是论证：`flops` 那一行的计算式里，`w_bytes`、`kv_bytes` 两个变量根本不出现——**不是因为省略了，是因为量化物理上就不该出现在这一行**。`b_w`、`b_kv` 两行则完全由这两个旋钮线性缩放。返回字典里的 `weight_share`、`kv_share`（`_lab/quantize.py:121-123`）就是 `## 1` 第二张表里那两列的直接来源。

### 3.7 `quantize_model()`：量化只覆盖大矩阵

```python
MATS = ("wq", "wk", "wv", "wo", "w1", "w2")

def quantize_model(w, fn):
    out = {k: (v.copy() if isinstance(v, np.ndarray) else v)
           for k, v in w.items() if k != "layers"}
    out["layers"] = []
    for lw in w["layers"]:
        nl = dict(lw)
        for k in MATS:
            nl[k] = fn(lw[k])
        out["layers"].append(nl)
    return out
```

（`_lab/quantize.py:128-145`）只对 `MATS` 里列出的六个矩阵（Q/K/V/O 投影 + 两个 FFN 矩阵）应用量化函数 `fn`，LayerNorm 的 gain/bias 和 embedding 完全不碰——它们直接从原字典拷贝过去（`v.copy()`）。`_lab/quantize.py:132-135` 的注释给了理由：这些参数量小、对误差敏感，量化收益微乎其微而风险不小。**真实引擎也是这么做的**，`## 4` 会看到 vLLM 的量化配置同样只覆盖 Linear 层。

### 3.8 `top1_agreement()`：一个必须讲清边界的指标

```python
def top1_agreement(cfg, w_ref, w_q, n_prompt=60, seed=0):
    rng = np.random.default_rng(seed)
    same = 0
    for _ in range(n_prompt):
        p = [int(x) for x in rng.integers(0, cfg.vocab, 6)]
        a = int(M.forward_naive(cfg, w_ref, p).argmax())
        b = int(M.forward_naive(cfg, w_q, p).argmax())
        same += (a == b)
    return same / n_prompt
```

（`_lab/quantize.py:148-164`）随机生成 60 个 prompt，比较量化前后模型对下一个 token 的 top-1 预测是否一致。`_lab/quantize.py:152-156` 的文档字符串把边界写得很直接：**这是本文件唯一的"质量"指标，而且它衡量的是"和未量化的自己有多像"，不是"答得对不对"**。本库的权重是随机初始化的（`M.init_weights`），没有语言学意义上的对错可言。`## 6` 会把"拿这张表谈精度损失"列为一条明确的错误用法。

### 3.9 `selftest()`：15 条断言里最值得记住的三条

`selftest()`（`_lab/quantize.py:169-272`）从基本性质一路加码到端到端指标，这里挑三条讲清楚它们在验证什么，而不是逐条复述：

- **解析预测 vs 实测**（`_lab/quantize.py:187-190`）：`## 2.2` 讲过的方法论，这条断言的容差是 15%（`abs(e8t - pred) / pred < 0.15`），不是要求分毫不差——量化噪声"近似"均匀分布是一个近似模型，真实权重不是严格均匀采样，允许一定偏差，但偏差应该在一个数量级以内，15% 是一个宽松但能抓住"scale 算法算偏了"这类实现错误的阈值。
- **幂等性**（`_lab/quantize.py:194-197`）：对已经量化过的权重再量化一次，结果应该不变（`np.allclose(q1, q2, atol=1e-7)`）。这条断言抓的是另一类实现错误：如果 scale 的计算依赖了某种"历史状态"（比如不小心用了移动平均），同一份数据量两次会得到不同结果，说明 scale 算法有偏。
- **块用尽/离群值这类"退化情形"必须先验证等于已知值**（`_lab/quantize.py:199-200`，位宽给到 32 时应退化为恒等）：这是 `_PLAN.md` §7 第 1 条踩坑教训的直接应用——**任何解析模型，先验证退化情形下等于理论值，再看趋势**。这里的退化情形是"量化位宽给得足够大"，理论值是"量化应该等价于不量化"。

## 4. 真实引擎是怎么做的（对照 vLLM）

### 4.1 量化方案有多碎——一个目录，30 个注册名字，20 个实现类

`## 0` 说过这一节要讲"真实引擎接住量化之后碎成什么样"，先给一个直接数出来的数字。vLLM 的 `QuantizationMethods`（`vllm:vllm/model_executor/layers/quantization/__init__.py:12-46`）是一个 `Literal` 类型，列出了所有合法的 `--quantization` 取值：

```python

    "awq", "auto_awq", "fp8", "fbgemm_fp8", "fp_quant",

    "compressed-tensors", "experts_int8", "quark", "moe_wna16",

    # 以下是 online 量化的简写名（fp8_per_tensor 等）

    "int8_per_channel_weight_only", "nvfp4_per_token", "mxfp8",

```

数一遍——**30 个字符串**。往下翻到 `method_to_config` 映射表（`vllm:vllm/model_executor/layers/quantization/__init__.py:139-168`），这 30 个名字背后是 **20 个不同的 Python 配置类**（`AutoAWQConfig` 一个类接了 `awq`/`awq_marlin`/`auto_awq` 三个名字，`AutoGPTQConfig` 接了 `auto_gptq`/`gptq`/`gptq_marlin` 三个，其余大多一对一）。对应到源码目录本身，`vllm/model_executor/layers/quantization/` 下平铺着 `auto_awq.py`、`auto_gptq.py`、`fp8.py`、`fp_quant.py`、`humming.py`、`modelopt.py`、`moe_wna16.py`、`mxfp4.py`、`torchao.py` 等十几个独立文件，外加 `compressed_tensors/`、`quark/`、`turboquant/`、`online/`、`inc/` 五个子目录，每个子目录内部还有自己的一整套 scheme 分类。

**这个数字本身就是答案**：量化不是一个"要不要用"的二选一，是一整片碎片化的工程现实——不同硬件（NVIDIA/AMD/Intel Gaudi）、不同格式（AWQ/GPTQ/FP8/MXFP4/NVFP4）、不同粒度（per-tensor/per-channel/per-block/per-token-head）交叉组合出来的结果。`## 2` 里 `qdq_per_tensor`/`qdq_per_channel`/`qdq_group` 三个函数，只是这一整片现实里最基础的三个坐标点。

### 4.2 KV 缓存量化：一个独立的开关，17 个取值

`## 2.5` 讲过量化权重和量化 KV 是两件独立的事，vLLM 的配置也确实把它们分开——`CacheDType`（`vllm:vllm/config/cache.py:39-57`）是专门给 KV 缓存用的类型开关，跟模型权重的量化方案完全无关：

```python
CacheDType = Literal[
    "auto", "float16", "bfloat16",
    "fp8", "fp8_e4m3", "fp8_e5m2", "fp8_inc", "fp8_ds_mla",
    "turboquant_k8v4", "turboquant_4bit_nc",
    "turboquant_k3v4_nc", "turboquant_3bit_nc",
    "int4_per_token_head", "int8_per_token_head", "fp8_per_token_head",
    "nvfp4", "nvfp4_4over6",
]
```

默认值是 `"auto"`（`vllm:vllm/config/cache.py:119`：`cache_dtype: CacheDType = "auto"`），意味着**默认不量化 KV，用模型自身的数据类型**——跟 `## 2.5` 的结论对得上：KV 量化只在长上下文 + 大 batch 这种特定工作点下才划算，不该是默认打开的选项。`is_quantized_kv_cache()`（`vllm:vllm/utils/torch_utils.py:77-82`）判断一个 `cache_dtype` 是否真的启用了量化：

```python
def is_quantized_kv_cache(kv_cache_dtype):
    return (kv_cache_dtype.startswith("fp8")
            or kv_cache_dtype.endswith("per_token_head")
            or kv_cache_dtype.startswith("nvfp4"))
```

`"auto"`、`"float16"`、`"bfloat16"` 都不满足这三个条件，说明它们被明确算作"未量化"。这跟本库 `intensity_with_quant()` 用 `w_bytes`/`kv_bytes` 两个独立旋钮建模是同一个设计思路——KV 是不是要量化，取决于当前部署的工作点，跟权重那边选了哪种量化方案没有必然联系。

### 4.3 weight-only 量化在大 batch 下真的会切回反量化+matmul——AWQ 的例子

`## 0` 立的论点里最容易被怀疑的一句是"weight-only 量化算的时候还要反量化回浮点"。vLLM 的 AWQ 实现把这件事直接写成了一个运行时分支，`AWQLinearMethod.apply()`（`vllm:vllm/model_executor/layers/quantization/auto_awq.py:913-937`）：

```python
FP16_MATMUL_HEURISTIC_CONDITION = x.shape[:-1].numel() >= 256
if FP16_MATMUL_HEURISTIC_CONDITION or envs.VLLM_BATCH_INVARIANT:
    out = ops.awq_dequantize(qweight, scales, qzeros, 0, 0, 0)
    out = torch.matmul(reshaped_x, out)
else:
    out = ops.awq_gemm(reshaped_x, qweight, scales, qzeros, pack_factor)
```

`x.shape[:-1].numel()` 就是这一步要处理的 token 数（近似等于 batch）。**token 数少于 256 时**，走 `ops.awq_gemm`——一个直接吃 int4 权重的融合 kernel，不需要先展开成 fp16。**token 数达到或超过 256 时**，vLLM 反而主动**先用 `awq_dequantize()` 把权重整个反量化回 fp16，再调用普通的 `torch.matmul`**——跟 `_lab` 里 `_qdq()` 做的事情性质完全一样，只是在真实 kernel 里发生。

这条分支存在的原因跟 `## 1` 第二张表、`## 2.5` 结尾的公式讲的是同一件事：**batch 越大，权重量化的收益越小**，因为权重字节数被摊薄、瓶颈从访存转移向计算。当 token 数足够多，融合的低比特 GEMM kernel 反而不如"老老实实反量化成 fp16 再用高度优化的标准 matmul"划算——这正是 `## 3` 里 `selftest()` 那条断言（`_lab/quantize.py:253-259`：batch=1 时权重量化省 74.6% 访存，batch=256 时只省 32.5%）在真实引擎里的对应物：不是"batch 大了量化就没用了"，而是"batch 大了之后，连该不该用融合低比特 kernel 都要重新权衡，AWQ 选择在这个点上切换成先反量化"。

### 4.4 MoE 专属方案：量化只在参数集中的地方发生

`## 3.7` 讲过 `quantize_model()` 只碰 `MATS` 六个矩阵、不碰 LayerNorm 和 embedding，理由是"量化收益要花在参数量真正集中的地方"。vLLM 的 `ExpertsInt8Config`（`vllm:vllm/model_executor/layers/quantization/experts_int8.py:22-24`）把这条原则用在了另一个更极端的场景上，docstring 只有一句话说清楚它干什么：

```python
class ExpertsInt8Config(QuantizationConfig):
    """Online int8 quantization for MoE expert weights.
    Linear layers are left unquantized.
    """
```

MoE 模型的参数量绝大多数集中在专家（expert）的 FFN 矩阵上——一个 64 专家的 MoE 层，专家部分的参数量可以是普通 attention 投影层的几十倍。`ExpertsInt8Config` 只量化专家权重，其余的 Linear 层（包括路由门控本身）**保持不量化**——跟 `MATS` 只挑六个大矩阵是同一个判断标准：**参数量占比小的地方，量化收益追不上它带来的精度风险，干脆不碰**。`__init__.py` 的注册表（`## 4.1`）里 `moe_wna16`、`compressed_tensors/schemes/` 下也有好几个专门给 MoE 权重用的 scheme——这不是巧合式的功能重复，是"权重占访存的份额决定量化优先级"这条原则在 MoE 架构下的必然推论：模型结构一旦把参数量高度集中到某个部件（这里是专家 FFN），量化方案就会跟着长出一个专门覆盖那个部件的分支。

## 5. 设计决策与代价

### 5.1 per-tensor / per-channel / group：粒度三选一

- **为什么这样（工程默认选 per-channel）**：`## 2.3` 已经用实测数字证明——同样注入一个离群值，per-tensor 误差涨 23 倍，per-channel 只涨到 per-tensor 的 6.3%。代价只是每个输出通道多存一个 scale，相对成千上万个权重可以忽略。这是"额外开销几乎为零、收益巨大"的那种决策，工程上没有理由不选。
- **不这样会怎样**：继续用 per-tensor，正常情况下（权重分布没有离群值）误差跟 per-channel 差不多（`## 1` 第一张表能看出差距不算大），但只要真实权重里出现哪怕一个异常值——而大模型权重里出现离群值几乎是常态，尤其是某些激活值经过 LayerNorm 之后会诱导出权重里的离群通道——per-tensor 的精度会断崖式下跌，且这种下跌没有任何预警信号（不报错、不崩溃，只是模型输出变差）。
- **什么时候可以不这样（更细的 group，甚至比 per-channel 还细）**：位宽已经压到 int4 甚至更低时，per-channel 那一级的粒度往往还不够——`## 2.4` 的 `qdq_group()` 就是为了在 int4 场景下进一步压低误差。什么时候不需要比 per-channel 更细：位宽还在 int8 或以上、且不打算再往下压时，per-channel 已经能把离群值的损害控制住，再往下分组只是增加 scale 的存储开销（`## 2.4`），收益边际递减。

### 5.2 量权重还是量 KV：工作点说了算

- **为什么这样（按工作点二选一，而不是都量或都不量）**：`## 2.5` 的公式已经给出依据——总访存节省比例约等于该项占访存的份额乘以该项位宽的相对下降。短上下文小 batch 时权重占比接近 100%，量 KV 几乎不产生任何收益（`## 1` 表里 `ctx=128, batch=1` 那一行 KV 只省 0.4%）；长上下文大 batch 时反过来。把有限的工程精力和精度预算花在占比小的那一项上，是纯粹的浪费。
- **不这样会怎样**：如果不看工作点、拍脑袋决定"我们上量化就把权重和 KV 都量了"，短上下文场景下 KV 量化那部分工作几乎是白做——`0.38%` 的访存节省不足以抵消它带来的额外精度风险和实现复杂度（KV 量化通常还需要在线统计 K/V 的动态范围，比权重量化更麻烦，因为 KV 是运行时产生的，不能像权重那样离线算好 scale）。
- **什么时候可以不这样（两者都量，或者干脆都不量）**：服务的工作点本身就会大幅波动（既有短对话又有长文档批处理），且愿意付出两套量化流水线的维护成本时，两者都支持是合理的——`vllm:vllm/config/cache.py:39-57` 的 `CacheDType` 和 `vllm:vllm/model_executor/layers/quantization/__init__.py` 的权重量化方案本来就是两个独立的开关，同时打开没有互斥问题，只是收益要分别核算，不能假设"反正都量了，收益肯定叠加"。

### 5.3 group size 该取多大：精度换存储

- **为什么这样（折中，比如 group=128）**：`## 2.4` 的数字已经摆出来——`group=32` 实际 4.50 bit，`group=128` 实际 4.125 bit，分组越细误差越低但存储成本越接近 int8。取一个折中值，是在"这次量化到底图什么"（图存储省到底，还是图尽量不掉精度）两端之间找平衡点，跟 `02-最小可跑引擎/03-分页KV与块管理.md` `## 5.2` 里 `block_size` 的取舍是同一种结构的决策——一个旋钮，两头都有真实代价，中间没有免费的最优解。
- **不这样会怎样**：group 取得极小（比如 8），"int4"的真实位宽会逼近甚至超过 int8（`4/8 + 2/8 = 1.0` 字节，跟不分组的 int8 一样贵），量化到 int4 这件事本身就失去了意义——花了实现复杂度的成本，却没拿到存储节省的收益。group 取得极大（比如整行共用一个 scale，退化成 per-channel），误差会显著上升，`## 1` 第一张表里 group=128 相对更粗糙的误差已经能看出这个趋势的起点。
- **什么时候可以不这样**：存储本来就不紧张（模型不大、显存够）时，直接用 per-channel int8 而不是更省字节但更费心思调参的 group-wise int4，工程上更简单，出错的地方更少——`group` 这个参数存在的意义仅仅是"当 int8 都不够省的时候，多一级可以调的旋钮"，不是所有场景都必须调到底。

### 5.4 只量大矩阵，不碰 LayerNorm 和 embedding

- **为什么这样**：`quantize_model()`（`## 3.7`）只对 `MATS` 六个矩阵动手。这些矩阵占了模型绝大多数参数量，量化它们才能拿到访存节省；LayerNorm 的 gain/bias 通常只有 `d_model` 量级的参数（相对 `d_model²` 量级的投影矩阵可以忽略），量化它们省不下多少字节，却因为 LayerNorm 直接控制激活值的尺度，对误差格外敏感，一旦量偏容易让整个网络的数值范围跟着漂移。
- **不这样会怎样**：如果连 LayerNorm 和 embedding 也量化，访存节省的边际收益极小（参数量占比太小），但精度风险不成比例地放大——`embedding` 直接决定每个 token 最初的表示，量化误差会被后续每一层放大，而不像大矩阵的量化误差那样有机会在多层累积中被部分抵消。
- **什么时候可以不这样**：显存极度紧张、连这几个小矩阵的字节数都要计较的场景（比如把模型塞进极小的边缘设备）——这时候可能需要对 embedding 做量化，但通常会用比大矩阵更保守的方案（更高位宽、更细的粒度），而不是套用同一套激进的量化配置。这类场景不在本库讨论范围内，`_PLAN.md` §1.4 已经划了红线：本库不做真实模型的精度损失外推。

### 5.5 什么时候根本不该量化

- **为什么要单独列这一条**：`## 0` 的立论是"量化省的是访存的字节数"，这句话反过来读就是一条否决条件——**如果访存本来就不是瓶颈，量化就没有它声称的那个收益**。`## 4.3` 的 AWQ 例子已经证明真实引擎自己也这么想：batch 大到一定程度，连用不用融合低比特 kernel 都要重新权衡。
- **不看这条会怎样**：在一个已经算力受限的工作点上（大 batch、短序列、显存本就充裕）硬上权重量化，`## 1` 表里 `batch=256` 那一行的 32.5% 收益还在，但那是"总访存"的节省比例，而这个工作点下瓶颈根本不在访存——`02-自回归解码为什么是访存瓶颈.md` 的算术强度表证明了大 batch、短上下文时算术强度已经抬得很高，接近甚至超过硬件的计算/带宽平衡点，这时候访存字节数再降，端到端延迟也不会跟着线性下降，因为限制吞吐的已经是乘加单元的算力上限。这正是 `## 6.4` 要讲的常见错误的根源。
- **什么时候可以不这样（即什么时候该量化）**：显存吃紧（模型放不下、或者要给更大 batch/更长上下文腾空间）、或者确认当前工作点确实访存受限（小 batch、或者长上下文单请求）——这两种情况下量化要么是刚需（放不下就是放不下），要么是能兑现的收益（`## 1` 表格里那些高占比、高收益的行）。判断"该不该量化"的第一步，永远是先按 `intensity_with_quant()` 这样的模型把工作点的瓶颈算出来，而不是默认"量化总是好的"。

## 6. 常见错误与踩坑

### 6.1 以为量化省的是算力

这是最容易犯、也是本篇开篇就要纠正的误解。`## 2.1`、`## 3.6` 已经从代码层面证明：`intensity_with_quant()` 的 `flops` 那一行不含任何跟位宽相关的变量，`selftest()`（`_lab/quantize.py:240-243`）直接断言"权重量化到 int8，FLOPs 一点没变"。如果抱着"量化了应该算得更快"的预期去测一个纯算力受限的工作负载（比如 `## 5.5` 讲的大 batch 短序列场景），会观察到延迟几乎不变甚至因为反量化开销略微变差，然后错误地得出"这个量化实现有 bug"的结论——真正的问题是预期本身就错了。

### 6.2 拿"输出恒等"去测量化，这个测试永远会挂

`_PLAN.md` §2 强调本库大多数机制（KV 缓存、分页、连续批处理）的判据是"算两遍，逐位比对，必须完全一致"。量化不适用这套判据——它**本来就是有损的**，`qdq_per_tensor(w, 8)` 跟原始 `w` 逐位比对必然不相等。如果沿用别的章节那套"输出必须逐位恒等"的测试思路去写量化的测试，得到的结果只能是"永远失败"，而失败本身不代表实现有 bug。`## 2.2`、`## 3.9` 讲的解析预测误差才是量化该用的判据：不是"误差是不是零"，而是"误差是不是落在解析预测的合理范围内"。`selftest()` 里没有一条断言要求量化前后输出相等（`_lab/quantize.py:199-200` 那条恒等断言测的是位宽给到 32 这种退化情形，不是常规量化位宽），这个区分是刻意的。

### 6.3 忽略 scale 的存储开销就说"压缩 8 倍"

fp32 到 int4，位宽上看是 `32/4 = 8` 倍压缩，但这个数字没算 scale。`## 2.4` 已经算过，`group=32` 时真实位宽是 4.5 bit，相对 fp32 的 32 bit，真实压缩比是 `32/4.5 ≈ 7.1` 倍，不是 8 倍；`group=8` 这种更激进的分组，真实位宽会逼近甚至超过 int8，压缩比进一步缩水。宣传材料里常见"4-bit 量化，模型体积缩小 8 倍"这类说法，默认假设了 `group=None`（不分组、per-tensor 或 per-channel），一旦换成更细的分组来换取精度，压缩比要用 `bytes_per_weight()` 重新算，不能直接套 `位宽比例`。

### 6.4 在大 batch 场景上量化权重，然后奇怪为什么没变快

`## 1` 表格已经量化地证明了这条：batch=1 时权重量化省 74.6% 访存，batch=256 时只省 32.5%——而且这只是"访存字节数"的节省比例，不等于端到端延迟的节省比例，因为 `## 5.5` 讲过大 batch 场景访存本来就未必是瓶颈。`## 4.3` 的 AWQ 例子是这条错误在真实引擎里的镜像：如果开发者手动强制走融合低比特 kernel（跳过 vLLM 自己那套按 token 数切换的启发式），在大 batch 下反而可能比"直接用 fp16 权重"更慢——因为融合 kernel 针对小 batch 优化，大 batch 下不如反量化后交给高度调优的标准 GEMM。**量化不是无条件的性能优化开关，它的收益曲线随 batch 单调递减**，上线前应该先用类似 `## 1` 表格的方式把当前服务的典型工作点标出来，再决定量不量、量什么。

### 6.5 拿端到端 top-1 一致率谈精度损失，这是越界的

`## 3.8` 已经把边界写清楚，这里再强调一次因为这个错误极容易在写报告、做汇报时不小心犯：`top1_agreement()` 衡量的是"量化后的模型和量化前的自己有多像"，不是"量化后的模型答得对不对"。`## 1` 第三张表里 int8 per-tensor 甚至到达 100%——这不代表 int8 per-tensor 没有精度损失（`## 2.3` 已经证明它对离群值极度敏感），只是恰好在这批玩具模型、这批随机 prompt 上，量化引入的误差没有大到足以改变 argmax 的结果。本库权重是随机初始化的，没有语言学意义上的对错，真实精度评估必须在真实任务、真实数据集上进行，`_PLAN.md` §1.4 的红线在这里再次适用：**不许把玩具模型的数字外推到真实精度损失**。

### 6.6 把权重量化方案和 KV 缓存量化当成同一个开关

`## 4.2` 已经证明这是两件独立配置的事：vLLM 的权重量化方案通过 `QuantizationMethods`（`## 4.1`，30 个取值）选择，KV 缓存的数据类型通过完全独立的 `CacheDType`（`vllm:vllm/config/cache.py:39-57`，17 个取值）选择，默认值 `"auto"` 意味着**权重可能已经量化了，KV 缓存却依然是原始精度**。容易踩的坑是看到"模型开了 int8 量化"就默认 KV 也一起降精度了，然后拿显存占用去核对，发现跟预期对不上——`## 2.5` 已经算过两者的收益曲线在工作点上完全不同，配置上把它们分开正是因为收益曲线不同，混为一谈会导致要么该量的没量（长上下文大 batch 却没开 KV 量化），要么产生"量化选项都点开了显存却没降多少"这种误判（`## 2.5` 结尾公式已经说明白：不该量的那一项，量了也白量）。

### 延伸阅读
