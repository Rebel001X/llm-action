# 投机解码

> **一句话**：分布不变，靠的是访存空档，不是算力便宜。
> **前置**：[[02-自回归解码为什么是访存瓶颈]]（decode 阶段恒定访存受限，是投机解码整套账能算得通的地基）

> **两句立论，贯穿全篇**：
> 1. **投机解码不是近似 —— 输出分布逐点等于原模型。**
> 2. **它之所以划算，是因为 decode 访存受限；一旦目标模型转为算力受限，它会变慢。**

## 0. 这一篇要解决什么问题

`02-自回归解码为什么是访存瓶颈.md` 已经把账算死了：decode 阶段 `batch=1` 时，算术强度恒等于 `2/dtype_bytes`（fp32 下是 0.5 FLOP/字节），跟上下文长度完全无关——因为无论权重还是 KV，每个元素都只做一次乘加、读一次字节，两边天生就在同一个瓶颈上，没有更低可去。`[[04-连续批处理]]` 给出的解法是横向拓宽：凑更多条请求一起跑，让权重那一次读被更多请求分摊。但连续批处理拓宽不了**单条请求内部**这一步——`_lab/minigpt.py:178-192` 的 `generate()` 每一步依然只产出 1 个 token，权重和 KV 依然要整套读一遍，而对面只换来 1 个 token 的产出。如果这条请求当前是唯一在跑的（batch=1，最坏情况，也是延迟敏感场景下最常见的情况），连续批处理帮不上任何忙。

问题就摆在这里：**这一次前向读了一整套权重和 KV，能不能不要只换 1 个 token？** 投机解码的想法很直接——先用一个便宜得多的**draft**模型或方法，猜出接下来 γ 个 token；再让**target**（原模型）**一次前向**同时验证这 γ 个位置对不对。猜对的白赚，猜错的从错的地方重来。如果验证这 γ 个位置的代价接近验证 1 个位置的代价（`## 2.4` 会证明这一点），那么这一次昂贵的权重+KV读取，就有机会换回不止 1 个 token。

但这条路必须先回答两个问题，回答不了就不能用：

1. **验证完之后，输出还是不是原模型的分布？** 如果只是"draft 猜的大概率对就用、大概率不对就丢"，那产出的是一个新的、偏离原模型的分布——这是有损压缩，不是投机解码。**这一篇要证明它不是**：接受-拒绝规则算出来的输出分布，逐点精确等于 target 的分布 `p`，跟 draft 的分布 `q` 完全无关。`## 2.1` 给出一行数学证明，`## 1`/`## 3` 用代码把它测出来。
2. **"验 γ 个位置"真的接近"验 1 个位置"的代价吗？** 这不是显然的——直觉上验证的 token 越多，算力开销就该越大。答案是**分情况的**：只要 target 还在访存受限区间，验证宽度几乎不影响访存字节数（`## 2.4`），代价确实接近白送；但 target 一旦转为算力受限，这笔"几乎白送"的账就不成立了，投机解码反而可能拖慢整体（`## 2.5`，这正是立论第二句）。

本篇顺序：`## 1` 先跑一遍自检，把关键数字摆出来；`## 2` 把这些数字背后的原理和证明讲透；`## 3` 逐行走读 `_lab/spec_decode.py`，把 `## 2` 的每一条结论对应到能跑的代码上；`## 4` 对照 vLLM/SGLang 的真实实现；`## 5`/`## 6` 讲设计取舍和踩坑；`## 7` 收尾。**红线先声明一遍**：本机没有 GPU，本篇出现的所有"加速比"都是按 `_lab/spec_decode.py` 的解析成本模型算出来的**估计**，不是任何真实引擎的实测数字，`## 2.5`/`## 5` 会反复标出它在什么条件下不成立。

## 2. 原理

### 2.1 接受-拒绝规则：一行证明

规则本身（Leviathan 等人的形式，`_lab/spec_decode.py:18-24` 的模块文档字符串已经写过一遍，这里逐步展开证明）：

> 从 draft 分布 `q` 里采一个 `x`；以概率 `min(1, p(x)/q(x))` 接受它；
> 否则，从 **残差分布 `residual(p,q) = norm(max(0, p-q))`** 里重新采一个，并就此打住。

**先证明一个逐点等式**：对任意 `x`，

```
min(p(x), q(x)) + max(0, p(x) - q(x)) = p(x)
```

分两种情况看就是恒等式：若 `p(x) >= q(x)`，左边 = `q(x) + (p(x)-q(x))` = `p(x)`；若 `p(x) < q(x)`，左边 = `p(x) + 0` = `p(x)`。**跟 `q` 具体是什么无关，纯粹是 `min`/`max` 的代数事实。**

**再证明接受路径贡献的恰好是 `min(p,q)`**：`x` 以概率 `q(x)` 被抽到，抽到后以概率 `min(1, p(x)/q(x))` 被接受，两步相乘：

```
q(x) · min(1, p(x)/q(x)) = min(q(x), p(x))
```

同样分两种情况验证：`p(x) >= q(x)` 时，`min(1,p/q)=1`，乘积 `= q(x) = min(p,q)(x)`；`p(x) < q(x)` 时，`min(1,p/q)=p(x)/q(x)`，乘积 `= q(x)·p(x)/q(x) = p(x) = min(p,q)(x)`。**两种情况都精确落在 `min(p(x),q(x))` 上。**

**拒绝概率**是对全体 `x` 求和后的余量：`1 - Σ_x min(p(x),q(x)) = Σ_x max(0, p(x)-q(x))`——记这个和为 `Z`（`_lab/spec_decode.py:47` 就是这个 `s = r.sum()`）。拒绝发生时，从 `residual(x) = max(0,p(x)-q(x))/Z` 里重采，这一支贡献的质量是 `Z · residual(x) = max(0, p(x)-q(x))`。

**两支相加**：

```
P(输出 = x) = min(p(x), q(x)) + max(0, p(x) - q(x)) = p(x)
```

正是开头证明的那条逐点恒等式——**`q` 在推导的每一步都在场，但最终答案里完全不出现**。这不是巧合，是这套规则的设计目标：无论 draft 是什么分布（只要它在 `p(x)>0` 的地方也 `>0`），输出永远精确等于 `p`。

拿一组能手算的数字把这条证明走一遍（对应 `_lab/spec_decode.py:40` 的 `residual()`）：

```
p = [0.50, 0.30, 0.15, 0.05]
q = [0.20, 0.20, 0.30, 0.30]

min(p,q)     = [0.20, 0.20, 0.15, 0.05]   求和 = 0.60   ← 整体接受率 α
max(0,p-q)   = [0.30, 0.10, 0.00, 0.00]   求和 = 0.40   ← Z，整体拒绝概率
residual(归一化后) = [0.75, 0.25, 0.00, 0.00]           ← max(0,p-q) / Z

min(p,q) + Z·residual = [0.20+0.4·0.75, 0.20+0.4·0.25, 0.15+0.4·0, 0.05+0.4·0]
                       = [0.50, 0.30, 0.15, 0.05]
                       = p   ✓ 精确相等
```

这组数字不是随手编的，是 `_lab/spec_decode.py` 自带的 `residual()` 在这组 `p`、`q` 上跑出来的真实结果（`## 3.1` 会给出可复制运行的命令）。**注意 `residual` 只有两个位置非零**——那正是 `p(x) > q(x)` 的两个位置（`x=0,1`），`p(x) <= q(x)` 的位置（`x=2,3`）残差恒为 0，因为那里的质量已经在接受路径里被 `min(p,q)` 完全覆盖了，没有"欠"target 什么。

### 2.2 接受率 = 两个分布的重叠面积

`## 2.1` 顺带证明了一个很直观的几何结论：整体接受率

```
α = Σ_x min(p(x), q(x))
```

**就是 `p` 和 `q` 这两条分布曲线的重叠面积**——想象把 `p`、`q` 画成两条直方图，`min(p,q)` 逐格取较矮的那根柱子，加起来就是两块面积重叠的部分。`## 2.1` 的例子里 `α=0.60`；`draft` 越像 `target`，两条直方图撞得越严实，`α` 越接近 1（`draft==target` 时完全重合，`α=1`，永不拒绝——`_lab/spec_decode.py:206-207` 的自检断言就是这句话）；draft 越离谱，重叠面积越小，`α` 越接近 0。

实测的一组数字（`_lab/spec_decode.py:263-275` 的 `_demo()`，把 target 温度固定、draft 温度逐渐拉高来制造"越来越不像"）：

```
  draft 温度      重叠面积 α     γ=4 期望产出     γ=8 期望产出
      2.0         0.279            1.38            1.39
      2.5         0.241            1.32            1.32
      3.0         0.200            1.25            1.25
      4.0         0.125            1.14            1.14
      6.0         0.059            1.06            1.06
```

温度越高，分布越平（越接近均匀分布），跟固定的 target 重叠得越少，`α` 单调下降——`draft` 选型的核心指标就是这一列，`## 4`/`## 5` 会讲真实引擎具体怎么选 draft。

### 2.3 期望产出的次线性，对上 draft 成本的线性——γ 有最优值

一轮完整流程（`_lab/spec_decode.py:79-102` 的 `spec_step()`）里，γ 个 draft 位置逐个验证，第一次被拒就停（后面猜的全丢，`_lab/spec_decode.py:99` 那行注释写得很直白）；如果 γ 个全部通过，**免费**再采一个第 γ+1 位的 token（因为验证 target 已经把这个位置的分布算出来了）。

**推导期望产出**：设每一步的接受事件是独立同分布的（每步都重新从 `q` 采样，接受概率的边际是 `## 2.2` 的 `α`），记 `N` 为"连续接受的 draft 个数"（0 到 γ 之间）。用一个常见技巧算 `E[N]`：

```
E[N] = Σ_{k=1}^{γ} P(前 k 步全部接受) = Σ_{k=1}^{γ} α^k = α(1-α^γ)/(1-α)
```

总产出 token 数是 `N` 再加 1（要么是拒绝后残差补的那个，要么是全接受后白送的那个）：

```
E[总产出] = 1 + α(1-α^γ)/(1-α) = (1-α^(γ+1)) / (1-α)
```

这正是 `_lab/spec_decode.py:107-116` 的 `expected_tokens(alpha, gamma)`。拿 `## 2.1` 那组 `p, q` 算出的 `α=0.60`、`γ=3` 代进去验证一遍：

```
公式：expected_tokens(0.6, 3) = (1 - 0.6^4) / (1 - 0.6) = (1 - 0.1296) / 0.4 = 2.1760
实测：5 万次 spec_step() 平均产出 token 数 = 2.1772（同一组 p, q，γ=3）
      5 万次平均"接受的 draft 个数" N       = 1.1772
公式：E[N] = 0.6·(1-0.6^3)/(1-0.6) = 0.6·0.784/0.4 = 1.1760
```

公式和 5 万次模拟对得上（差距在采样噪声范围内），`## 3.2` 给出可复制运行的命令。

**这条公式的关键性质是它对 γ 次线性**：`α` 固定时，`α^γ` 随 γ 指数衰减，`expected_tokens` 趋向一个上限 `1/(1-α)`，γ 越大边际收益越薄。而 draft 的成本是**线性**的——猜 γ 个就要跑 draft γ 步。一个次线性的收益去追一个线性的成本，两条曲线必然在某处交叉，交叉点右边继续加大 γ 就是净亏——**这就是"γ 不是越大越好"的全部数学**。`_lab/spec_decode.py:141-154` 的 `speedup_estimate()` 把这两条曲线直接相除，`_demo()` 扫出一张 γ 的最优值表（draft 成本设为 target 的 5%，小 batch、访存受限，`verify_overhead=0`）：

```
   γ    α=0.5    α=0.7    α=0.8    α=0.9
   1    1.43     1.62     1.71     1.81
   2    1.59     1.99     2.22     2.46
   4    1.61     2.31     2.80     3.41
   6    1.53     2.35     3.04     4.01
   8    1.43     2.28     3.09     4.38
  12    1.25     2.06     2.95     4.66
  16    1.11     1.85     2.72     4.63

各列最优 γ：α=0.5 → γ=4（x1.61）　α=0.7 → γ=6（x2.35）
           α=0.8 → γ=8（x3.09）　α=0.9 → γ=12（x4.66）
```

**每一列都存在一个最高点，过了这个点继续加 γ 反而掉头向下**——`α=0.5` 那一列在 `γ=4` 见顶（1.61x），`γ=16` 时已经跌回 1.11x，比 `γ=1` 的 1.43x 还差；`α` 越高，最优 γ 越靠右（draft 越准，能多猜几步再验证）。`## 3.3` 会再跑一组更贵的 draft（成本比例从 5% 提到 20%）看这张表怎么整体左移。

### 2.4 验证为什么几乎白送：同请求共享 KV，不是多请求各有 KV

这是本篇第二硬的一条，直接决定投机解码划不划算。`_lab/spec_decode.py:119-138` 的 `verify_cost(d_model, n_layer, n_head, d_head, vocab, ctx, n_tok)` 算的是"一次前向验证 `n_tok` 个 token"的解析成本：

```python
# _lab/spec_decode.py:132-136
matmul_params = n_layer * (4 * d_model ** 2 + 8 * d_model ** 2) + d_model * vocab
flops = 2 * n_tok * matmul_params + n_tok * n_layer * n_head * 4 * ctx * d_head
bytes_w = dtype_bytes * (matmul_params + 2 * n_tok * d_model)
bytes_kv = ctx * 2 * n_layer * d_model * dtype_bytes      # <- 不乘 n_tok
```

**FLOPs 的两项都乘了 `n_tok`**——`n_tok` 个位置各自要做一遍矩阵乘、各自要跟 `ctx` 长度的历史做一遍注意力，算力天然是线性的。**但 `bytes_kv` 这一行没有 `n_tok`**：这 `n_tok` 个位置（对应 `γ+1` 个待验证 token）**属于同一条请求**，历史 KV 只有一份，矩阵乘把这份 KV 读进片上内存后，可以被 `n_tok` 个 query 位置反复复用——读一遍就够，不需要为每个位置各读一份。真实数字（`_lab/spec_decode.py:294-301` 的 `_demo()`，一组接近 7B 模型的配置）：

```
  验几个     FLOPs 倍数     访存倍数     算术强度
    1          1.00         1.000        0.50
    2          2.00         1.000        1.00
    4          4.00         1.000        2.00
    8          8.00         1.000        4.00
   16         16.00         1.000        8.00
```

**FLOPs 老老实实地线性涨，访存倍数死死钉在 1.000 不动**——这就是"验证几乎白送"的字面意思：多验证的算力，如果这条请求本来就在访存受限区间里排队等着（`0.50` 的算术强度意味着硬件的算力单元本来就有大量空闲），那这部分多出来的 FLOPs 就是拿硬件本来就没用满的算力去换，几乎不占用额外的墙钟时间。

**这条结论和"多请求批处理"是两回事，必须分清楚**——`_lab/minigpt.py:197-238` 的 `analytic_cost(cfg, ctx_len, batch)` 算的是另一种情形：

```python
# _lab/minigpt.py:226-228
bytes_weights = dtype_bytes * (matmul_params + 2 * batch * d)
# KV 每条请求私有，随 batch 线性增长 —— 这是批处理省不掉的东西
bytes_kv = batch * ctx_len * (2 * L * d * dtype_bytes)
```

这里的 `bytes_kv` **乘了 `batch`**——因为 `[[04-连续批处理]]` 讲的多请求批处理里，每条请求有自己独立的一段历史，`batch` 条请求的 KV 互不相同，各自的那份都要单独读一遍，省不掉。**两个函数长得像，乘的对象却完全不同**：`verify_cost` 里 `n_tok` 个位置是"同一条请求内部的 γ+1 个候选"，KV 只读一遍；`analytic_cost` 里 `batch` 个位置是"不同请求各自的 1 个 decode token"，KV 各读各的。投机解码占的便宜，正是"验证宽度"这个维度天生免费，而"批大小"这个维度天生不免费——`_lab/spec_decode.py:126-127` 的函数文档字符串把这句话直接写进了代码注释里。

### 2.5 什么时候反而变慢：verify_overhead 这个开关

`## 2.4` 的"几乎白送"有一个隐含前提：**target 还在访存受限区间**，硬件的算力单元本就闲着，多算的 FLOPs 不占用额外时间。这个前提不是恒成立的——`## 0` 提过，`[[04-连续批处理]]` 讲过 batch 越大算术强度越高，当 batch 大到一定程度、算术强度跨过硬件的"拐点"，target 就从访存受限转为**算力受限**：这时硬件的算力单元已经是瓶颈本身，`## 2.4` 那"多算的 FLOPs 几乎不占时间"的假设直接失效——多算的每一份 FLOPs 都要真金白银地花时间。

`_lab/spec_decode.py:141-154` 的 `speedup_estimate()` 把这件事显式建模成一个参数：

```python
# _lab/spec_decode.py:141-154（节选）
def speedup_estimate(alpha, gamma, draft_ratio, verify_overhead=0.0):
    return expected_tokens(alpha, gamma) / (1.0 + gamma * draft_ratio + verify_overhead)
```

分母的三项分别是：target 验证一次（`1`）、draft 跑 γ 步（`gamma * draft_ratio`）、**验证 γ+1 个位置比验证 1 个位置多付出的那一点点算力时间**（`verify_overhead`）。`## 2.4` 证明了小 batch、访存受限时 `verify_overhead ≈ 0`；大 batch、算力受限时它会显著大于 0。拿 `α=0.8, γ=4, draft_ratio=0.05` 这一组固定参数，只改 `verify_overhead`：

```
verify_overhead = 0（小 batch，访存受限）：
  speedup = expected_tokens(0.8,4) / (1 + 4·0.05 + 0) = 3.3616 / 1.20 = 2.80x

verify_overhead = 4（大 batch，target 已算力受限）：
  speedup = expected_tokens(0.8,4) / (1 + 4·0.05 + 4) = 3.3616 / 5.20 = 0.65x
```

**同一组 α、γ、draft 成本比例，仅仅因为 target 从访存受限变成算力受限，估计加速比从 2.80 倍直接翻成 0.65 倍——从"划算"翻成"净亏"。** 这正是立论第二句的数学出处，也是 `## 1` 那第四条数字的来源。`## 5` 决策三会把这条结论落到"高负载时要不要动态关掉投机解码"这个真实工程决策上。

**红线重申**：以上所有倍数都是 `speedup_estimate()` 这个解析成本模型算出来的估计，本机没有 GPU，`verify_overhead` 具体等于多少要看真实硬件的算力/带宽拐点在哪、当前 batch 有多大——`## 2.4`/`## 2.5` 只证明了"存在一个从白送到不白送的转折"，不给出任何真实引擎在真实硬件上的实测加速比。

### 3.1 `residual()` 与两个采样函数：正确版与反例

`residual(p, q)`（`_lab/spec_decode.py:40-50`）就是 `## 2.1` 证明里的 `norm(max(0,p-q))`：

```python
# _lab/spec_decode.py:40-50
def residual(p, q):
    r = np.maximum(p - q, 0.0)
    s = r.sum()
    if s <= 0:                      # p 完全被 q 覆盖（例如 p == q），理论上到不了这里
        return p / p.sum()
    return r / s
```

`spec_sample_one(p, q, rng)`（`_lab/spec_decode.py:53-62`）是 `## 2.1` 规则的直接翻译——**注意接受概率用的是 `p[x]/q[x]`，分母是 draft 的概率**：

```python
# _lab/spec_decode.py:53-62
def spec_sample_one(p, q, rng):
    x = int(rng.choice(len(q), p=q))
    if rng.random() < min(1.0, float(p[x] / q[x])):
        return x
    return int(rng.choice(len(p), p=residual(p, q)))
```

亲手用 `## 2.1` 那组 `p, q` 验证一遍（可直接复制运行）：

**怎么自己设计这类分布检验**：全变差 `_tv(a,b)`（`_lab/spec_decode.py:165-167`）就是 `0.5 * Σ|a-b|`，一行代码；难的不是算它，是**样本量怎么定、阈值定多少才不会把采样噪声当成 bug**。经验分布本身带噪声，量级大致随 `1/√N` 衰减，`V` 越大（要覆盖的格子越多）同样 `N` 下噪声通常越大——这里没有一个万能公式能直接给出"要跑多少次"，`_lab/spec_decode.py` 的做法是先拿一个已知正确的实现把噪声量级实测出来，再决定阈值：

```python
# _lab/spec_decode.py:186-195（selftest 里两条判据，性质完全不同）
chk(tv < 0.005, ...)         # 对正确实现：绝对阈值——先用大 N 把噪声上限跑出来，再留安全余量
chk(tv_n > 20 * tv, ...)     # 对可疑实现：相对阈值——不跟固定数字比，跟同一次运行里"正确版本自己的噪声"比
```

**第二条是更值得学的做法**：`tv_n > 20 * tv` 不是拍脑袋定的"朴素版全变差必须大于 0.1"这种绝对数字——`N`、`V` 一换，噪声量级就变了，绝对阈值也得跟着重新猜。它比的是**同一次运行里，可疑实现的偏差是不是正确实现噪声的一个数量级以上**——`tv` 本身就是当次运行测出来的噪声真实水平，`tv_n` 只要显著超过它（这里选了 20 倍这个很宽松的安全系数），就能确信"这不是采样噪声，是分布真的错了"，而且这条判据不需要因为换了词表大小或采样次数而重新调参。`## 3.6` 的 `test_naive_verifier_is_biased`（`_lab/tests/test_advanced.py:158-165`）沿用的是同一套相对阈值思路（`S._tv(emp, p) > 0.05`，阈值定在比 `test_output_distribution_equals_target` 用的 `< 0.01` 高出 5 倍以上）。

### 3.2 `spec_step()`：完整一轮，及"至少产出 1 个"的兜底

`spec_step(p_rows, q_rows, rng)`（`_lab/spec_decode.py:79-102`）把 `## 2.1`/`## 2.3` 的单步规则接成一整轮：

```python
# _lab/spec_decode.py:91-102
gamma = len(q_rows)
out = []
for i in range(gamma):
    x = int(rng.choice(q_rows.shape[1], p=q_rows[i]))
    if rng.random() < min(1.0, float(p_rows[i][x] / q_rows[i][x])):
        out.append(x)
        continue
    out.append(int(rng.choice(p_rows.shape[1], p=residual(p_rows[i], q_rows[i]))))
    return out, i                     # 拒了就停，后面猜的全丢
out.append(int(rng.choice(p_rows.shape[1], p=p_rows[gamma])))
return out, gamma
```

**`return out, i` 这一行是整个函数除了接受-拒绝规则本身之外最重要的一行**：一旦某个位置被拒绝，循环立刻 `return`，不会继续检查后面已经猜好的位置。`## 6` 错误三会讲清楚为什么不能改成 `continue`。**循环走完（γ 个全接受）之后还有一行**（`_lab/spec_decode.py:101`）：从第 `γ+1` 位的 target 分布 `p_rows[gamma]` 里再采一个——这个位置的 logits 反正在这次前向里已经算出来了，白拿。

用 `## 2.3` 那组数字（`p, q` 同 `## 2.1`，`γ=3`）验证期望产出公式：

### 3.5 `speedup_estimate()`：把 2.80x 和 0.65x 手算一遍

### 3.6 `selftest()`：本篇用的是第三种判据——分布恒等

这和 `[[04-连续批处理]]` 用的"输出恒等"（`_lab/tests/test_lab.py` 的判据）是不同的哲学——**投机解码单次调用的输出本身就是随机的**，同一组 `p, q`、不换随机种子会得到同一个 token，换种子会得到不同 token，逐次比对没有意义；唯一能验证正确性的方式是**跑够多次，比较经验分布跟理论分布的距离**。`_lab/tests/test_advanced.py:37-41` 的 `test_all_advanced_selftests_pass` 先把 `spec_decode.selftest()`（连同另外四个进阶模块的自检）在 pytest 里跑一遍兜底，之后 `_lab/tests/test_advanced.py:142-190` 这几条断言（`## 3.1`~`## 3.4` 引用过的那几条）逐条把"分布恒等""朴素版有偏""验证几乎白送"这三件事钉成回归测试：

| `test_expected_tokens_endpoints` | `_lab/tests/test_advanced.py:177` | `## 2.3`：`expected_tokens(1.0,γ)=γ+1`、`expected_tokens(0,γ)≈1` 两个端点算对 |
| `test_verification_is_nearly_free_in_bytes` | `_lab/tests/test_advanced.py:182` | `## 2.4`/`## 3.4`：验 8 个 token 的 `bytes` 涨不到 5%，`flops` 涨 7.9 倍以上 |

**六条断言合在一起，覆盖了 `## 2` 五节原理里除 `## 2.5`（`verify_overhead`）之外的全部**——`## 2.5` 那条"何时反而变慢"的断言（`fast > 2.0 > slow`）在 `_lab/spec_decode.py:250-255` 的 `selftest()` 里单独测，没有进 pytest 的 6 条清单，因为它验证的是 `speedup_estimate()` 这一个纯函数、不涉及采样随机性，用不着分布检验这一整套机制，`selftest()` 里的普通断言（`## 3.5` 已经手算过）就够了。**一节原理配一条能跑的检验，不允许有只讲道理不给验证的地方。**

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang，带 `引擎:文件:行`）

### 4.1 draft 从哪来：三条代价完全不同的路

vLLM 把所有支持的投机方法收进一个字面量类型（`vllm:vllm/config/speculative.py:69-79`）：

```python
# vllm:vllm/config/speculative.py:69-79（节选）
SpeculativeMethod = Literal[
    "ngram", "medusa", "mlp_speculator", "draft_model", "suffix",
    "custom_class", EagleModelTypes, NgramGPUTypes, DSparkModelTypes,
]
```

`EagleModelTypes`（`vllm:vllm/config/speculative.py:66-68`）本身又包含一长串 `MTPModelTypes`（`vllm:vllm/config/speculative.py:37-62`，deepseek_mtp、glm4_moe_mtp、qwen3_next_mtp 等二十多个模型各自的 MTP 头命名）。**这份清单印证了 `## 0` 提过的判断：draft 的来源不是"哪种更主流"的问题，是三条代价结构完全不同的路，选哪条取决于手头有什么资源**：

**路径一：n-gram / prompt lookup，不需要任何模型。** `vllm:vllm/v1/spec_decode/ngram_proposer.py:12` 的 `NgramProposer` 纯粹是字符串匹配——在已经出现过的 token 序列里找一段长度 `min_n`~`max_n` 的后缀，看它之前在上下文里出现过之后接的是什么，直接照抄。整个 `propose()` 路径跑在 CPU 上，用 numba JIT 加速（`vllm:vllm/v1/spec_decode/ngram_proposer.py:55-62` 初始化时就先触发一次 JIT 编译），完全不占 GPU 算力，`draft_ratio`（`## 2.3`/`## 3.3` 用到的那个参数）趋近于 0。代价是它只能"抄自己讲过的话"——SGLang 这边的等价实现是 `sglang:python/sglang/srt/speculative/ngram_worker.py:71` 的 `NGRAMWorker`。这条路在代码补全、检索增强这类"接下来大概率是重复内容"的场景里 `α`（`## 2.2` 的重叠面积）很高，遇到从没在上下文出现过的新内容时 `α` 会塌下去。

**路径二：独立的小模型，能自己完整跑一次前向。** `vllm:vllm/v1/spec_decode/draft_model.py:19` 的 `DraftModelProposer` 是另一个完整的、可以自己独立 decode 的因果语言模型——甚至可以跟 target 用不同的分词器（`use_heterogeneous_vocab`，`vllm:vllm/v1/spec_decode/draft_model.py:34-58`）：这种情况下 vLLM 会构建一个 `VocabMapping`，把 draft 的 logits 约束到两个词表的交集 token 上，保证 `## 2.1` 那套接受-拒绝证明依然成立（`## 2.1` 的推导对 `p`、`q` 的词表没有隐含假设，但代码实现要求两边真的能在同一个 `x` 上对齐）。代价也最实打实：draft 要自己维护一份 KV cache、自己 prefill、自己 decode，`draft_tensor_parallel_size` 还要求跟 target 的 TP 度一致（`vllm:vllm/v1/spec_decode/draft_model.py:63-78`，否则直接报错）——这条路的 `draft_ratio` 通常是三条里最高的，但适用面最广，只要选个足够小、足够像 target 的模型就能上。

**路径三：模型自带的 MTP 头 / EAGLE，复用 target 算出来的隐藏状态。** `vllm:vllm/v1/spec_decode/eagle.py:10-21` 的 `EagleProposer` 和上面两条路径共用同一个基类 `SpecDecodeBaseProposer`（`vllm:vllm/v1/spec_decode/llm_base_proposer.py:71`），区别只在 `pass_hidden_states_to_model=True`：EAGLE/MTP 头不是从零跑一遍前向，而是直接吃 target 这次前向已经算出来的隐藏状态，接一个小得多的头预测下一个 token。基类初始化那句注释写得很直白（`vllm:vllm/v1/spec_decode/llm_base_proposer.py:109`）：

```python
# vllm:vllm/v1/spec_decode/llm_base_proposer.py:109-111
# Unifying eagle, draft model, and parallel drafting support.
```

SGLang 这边把"MTP 头不需要自己的 KV"这件事写得更直接：`sglang:python/sglang/srt/speculative/frozen_kv_mtp_worker_v2.py:676` 的 `FrozenKVMTPWorkerV2` 直接继承 `EAGLEWorkerV2`（`sglang:python/sglang/srt/speculative/eagle_worker_v2.py:1050`），类文档字符串写道（`sglang:python/sglang/srt/speculative/frozen_kv_mtp_worker_v2.py:677-681`）：

```
Reuses `EAGLEWorkerV2`'s verify / `move_accept_tokens` / forward
skeleton verbatim; only the draft worker and the seed-based draft-extend
are frozen-specific.
```

以及初始化处的注释（`sglang:python/sglang/srt/speculative/frozen_kv_mtp_worker_v2.py:694-696`）：**"frozen draft owns no KV"**——这正是和路径二的关键代价差异：独立小模型是另一个完整的模型，要为它单开一份 KV；MTP 头没有自己的 KV，它活在 target 的计算图内部，直接读 target 算好的隐藏状态。三条路径的代价谱因此是：**n-gram（几乎零成本，但只能抄原文）< MTP 头（不需要独立前向/独立 KV，但要求 target 本身训练过这个头）< 独立小模型（代价最大，但对任意 target 都适用）。**

### 4.2 rejection sampler：`## 2.1` 那行证明在生产代码里长什么样

`## 2.1` 证明的接受概率 `min(1, p(x)/q(x))`，在 vLLM 的 Triton kernel 里就是这一行（`vllm:vllm/v1/sample/rejection_sampler.py:829`）：

```python
# vllm:vllm/v1/sample/rejection_sampler.py:829
accepted = draft_prob > 0 and target_prob / draft_prob >= uniform_prob
```

跟 `_lab/spec_decode.py:60` 的 `rng.random() < min(1.0, float(p[x]/q[x]))` 是同一件事，只是不等号方向换了个写法（`uniform < p/q` 等价于 `p/q >= uniform`）。`residual()`（`_lab/spec_decode.py:40-50`）在 vLLM 里对应 `sample_recovered_tokens_kernel`（`vllm:vllm/v1/sample/rejection_sampler.py:930`）：

```python
# vllm:vllm/v1/sample/rejection_sampler.py:930-932
prob = tl.maximum(target_prob - draft_prob, 0.0)
# NOTE(woosuk): We don't need `prob = prob / tl.sum(prob)` here because
# `tl.argmax` will select the maximum value.
```

`tl.maximum(target_prob - draft_prob, 0.0)` 就是 `max(0, p-q)`，跟 `_lab/spec_decode.py:46` 的 `np.maximum(p - q, 0.0)` 一字不差。但**归一化那一步被省掉了**——`_lab/spec_decode.py:47-50` 的教学版老老实实除以 `s = r.sum()` 再采样；vLLM 的生产实现用的是 Gumbel-max 技巧（`vllm:vllm/v1/sample/rejection_sampler.py:679-687` 的 `q.exponential_()` 和 `inv_q = q.reciprocal()`）：给每个 token 配一个独立的指数分布随机数，用 `未归一化概率 × inv_q` 取 `argmax`，等价于按 `residual` 的（未归一化）概率采样，却不需要真的算出分母 `s` 再除——词表几万到十几万时，这一步省下的是一次全词表规约。**公式跟 `_lab/spec_decode.py` 完全一样，工程实现上多做了一个"绕开归一化"的优化。**

SGLang 走的是另一条实现路线——`sglang:python/sglang/kernels/ops/speculative/reject_sampling.py:71` 的接受判断：

```python
# sglang:python/sglang/kernels/ops/speculative/reject_sampling.py:71
if coin * q < p:
```

同样是 `min(1,p/q)` 规则的等价写法（`coin < p/q` 两边乘 `q`），只是用乘法代替除法，避免了 `q` 接近 0 时的数值问题。残差部分（`sglang:python/sglang/kernels/ops/speculative/reject_sampling.py:116-117`）：

```python
diff = p_val - q_val
val = tl.where(diff > 0.0, diff, 0.0)
```

跟 vLLM 那行是同一个 `max(0,p-q)`，但 SGLang 选择老老实实扫两遍词表（第一遍求归一化常数 `norm_sum`，第二遍找累积分布落点，`sglang:python/sglang/kernels/ops/speculative/reject_sampling.py:101-158`），没有用 Gumbel 技巧——**两个引擎对同一条数学证明，选了两种不同的工程实现**：vLLM 用随机数技巧换掉一次归一化，SGLang 用两遍朴素扫描把逻辑写得更直白。公式本身，跟 `_lab/spec_decode.py` 一样，一步都没有变通。

**本篇没建模的一个真实扩展**：SGLang 除了这条"链式"验证（`chain_speculative_sampling_triton`），还有一条"树形"验证 `tree_speculative_sampling_target_only`（两者的选择逻辑在 `sglang:python/sglang/srt/speculative/eagle_utils.py:772-776`）——树形验证允许 draft 在同一步猜出多条分支候选，一次性全部验证，比 `_lab/spec_decode.py:79` 的 `spec_step()` 只验一条 `γ+1` 长的链更进一步。`## 3` 的代码只覆盖链式这一种，树形验证的接受-拒绝数学本质相同（仍然是 `## 2.1` 那条证明，只是要在树上按父子关系逐层跑），但工程复杂度显著更高，留给读者自己去读 `sglang:python/sglang/srt/speculative/eagle_utils.py` 的 `verify` 路径。

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：γ 按 batch size 动态调整，而不是写死一个常数。**
- 为什么这样：`## 2.3` 证明了产出对 γ 次线性、draft 成本对 γ 线性，最优 γ 同时依赖 `α`（draft 有多准）和 `draft_ratio`（draft 有多贵）——`## 3.3` 实测过，同样的 `α`，draft 成本从 5% 涨到 20%，最优 γ 就从 4~12 整体收缩到 1~6。这两个量在真实服务里都不是常数：`α` 随请求内容变（`## 2.2` 的重叠面积取决于当前生成的内容跟 draft 擅长的模式像不像），`draft_ratio` 隐含依赖当前 batch 大小（batch 越大，target 那次前向摊薄后的相对成本越低，draft 相对变"贵"）。vLLM 直接把这个依赖关系做成配置项——`num_speculative_tokens_per_batch_size`（`vllm:vllm/config/speculative.py:181-186`）：按 `(range_start, range_end, num_speculative_tokens)` 的 batch size 区间表动态选 γ。
- 不这样会怎样：γ 定太大，`## 2.3` 的表格显示 `α=0.5` 时 `γ=16` 只有 1.11x，远不如 `γ=4` 的 1.61x——多猜的那些位置大概率白猜，draft 成本白花；γ 定太小，则错过次线性收益最陡的那一段区间，`## 3.3` 显示便宜 draft（5%）时最优 γ 通常在 4~12 之间，定死在 1 或 2 会漏掉大半收益。
- 什么时候可以不这样：`α` 和 batch 规模都稳定的场景（比如固定负载的离线批处理、同一类任务反复跑）可以手工调好一个 γ 用到底，不需要 vLLM 那种按区间动态切换的机制——这本身就是"什么时候可以不做动态负载感知"的一个特例，跟决策三是同一类判断。

**决策二：draft 来源三选一，不存在一个绝对更优的选项。**
- 为什么这样：`## 4.1` 证明三条路径的代价结构完全不同——n-gram 几乎零成本但只能"抄原文"、独立小模型代价最大但对任意 target 都适用、MTP 头介于两者之间但要求 target 本身训练过这个头。选哪条本质是"能不能便宜地拿到一个 `α` 足够高的 `q`"这个约束下的工程决策，不是有一个放之四海而皆准的答案。
- 不这样会怎样：选错会导致 `α` 太低——`## 2.2` 证明 `α` 就是重叠面积，如果强行用 n-gram 去猜从没在上下文出现过的创造性内容，重叠面积会塌到接近 0，`## 2.3` 的 `expected_tokens` 在 `α→0` 时退化到 1（纯靠残差兜底，等价于没有加速），`## 2.5` 的 `speedup_estimate` 因为分子几乎不涨、分母还要多算 `γ·draft_ratio`，会直接跌破 1（变慢）。
- 什么时候可以不这样（可以不用某条路径）：重复性强的场景（检索增强生成、代码补全、编辑草稿）n-gram 就够，不需要额外训练或部署一个 draft 模型；target 本身原生带 MTP 头的模型（`vllm:vllm/config/speculative.py:37-61` 那份清单里的模型）不需要再找一个独立 draft 模型；反过来，通用创造性生成任务如果 target 没有 MTP 头、内容重复性也不够支撑 n-gram，独立小模型可能是唯一能落地的选项。

**决策三：高负载时要不要动态关掉投机解码。**
- 为什么这样：`## 2.5` 证明了同一组 `α`、`γ`、`draft_ratio`，仅仅因为 `verify_overhead` 从 0 涨到 4（target 从访存受限转为算力受限），估计加速比从 2.80x 直接跌到 0.65x——**从划算翻成净亏**，`_lab/spec_decode.py:250-255` 的自检断言把这条数字直接钉进了回归测试。`verify_overhead` 升高的物理原因是 `## 2.4` 证明的"验证几乎白送"这个前提本身建立在"target 还有空闲算力"之上，高并发/大 batch 下这个前提会失效。
- 不这样会怎样：投机解码一直开着，在高负载时段反而拖慢整体吞吐——这不是理论推测，是 `## 2.5`/`## 3.5` 那条断言实打实算出来的数字。更隐蔽的代价是 draft 本身也要占用一部分算力/显存/调度资源（尤其 `## 4.1` 路径二的独立小模型），高负载下这部分开销是纯粹的机会成本，挤占的是本可以留给 target 处理更多并发请求的资源。
- 什么时候可以不这样（可以不做动态开关，一直开着）：离线、低并发、延迟敏感、target 本身很少打满算力上限的服务场景（比如单用户交互式应用，batch 常年个位数），`## 2.4` 的"访存受限"前提基本恒成立，不需要专门做负载探测和运行时开关——这也是很多部署直接静态配置一份 `speculative_config` 而不做动态调度的原因。真正需要这道开关的，是 `α`、batch 规模、`verify_overhead` 都可能随时间剧烈波动的在线多租户服务，这正是决策一那份"按 batch size 区间选 γ"配置表想解决的同一类问题（γ 选到 0 就等价于关闭）。

## 6. 常见错误与踩坑

**错误一：接受概率的分子分母写反——`min(1, q(x)/p(x))`，不是 `min(1, p(x)/q(x))`。**
`_lab/spec_decode.py:56-58` 的文档字符串已经把这条坑标出来了：**写反不会崩，只会让分布悄悄偏掉**。用 `## 2.1` 那组 `p, q` 实测（20 万次采样）：

```
p                                   = [0.50, 0.30, 0.15, 0.05]
写反后（accept = min(1,q/p)）经验分布 = [0.2188, 0.18, 0.3003, 0.3009]   TV = 0.40115
```

**错了会看到什么现象**：经验分布不是随机地偏离 `p`，而是系统性地滑向 `q`（这里 `q=[0.20,0.20,0.30,0.30]`，写反后的经验分布几乎就是 `q` 本身）——分子分母写反之后，"谁更可能被接受"这件事的方向被整体颠倒，程序完全不报错，生成的文本依然通顺，只是长期跑下去输出的口味会悄悄向 draft 靠拢而不是 target。

**错误二：拒绝之后从 `p` 直接重采，而不是从残差 `residual(p,q)` 重采。**
接受概率本身写对了，但 `## 2.1` 证明链条的后半段被跳过：拒绝发生时直接 `rng.choice(len(p), p=p)`，而不是 `rng.choice(len(p), p=residual(p,q))`。这正是 `## 3.1` 提到的 `spec_sample_one_naive` 犯的第二个错误（它同时还改了接受规则本身）。单独测这一个错误（接受规则保持正确）：

```
理论：min(p,q) + Z·p = [0.2+0.4·0.50, 0.2+0.4·0.30, 0.15+0.4·0.15, 0.05+0.4·0.05]
                     = [0.40, 0.32, 0.21, 0.07]
实测（20 万次）经验分布 = [0.399, 0.3208, 0.2096, 0.0705]   TV = 0.10095
```

**错了会看到什么现象**：偏差比错误一小得多（TV 0.10 对 0.40），因为接受路径依然对，只有拒绝之后那一小份质量（`Z=0.4`）算错了方向——这种"局部对、局部错"的偏差比错误一更难从直觉上发现，因为大部分采样结果确实符合 `p`，只有"拒绝之后补的那个token"这一条支路悄悄跑偏，抽样量不够大的时候很容易被当成正常的采样噪声放过去。

**错误三：拒绝后没有丢掉后面已经猜好的 token。**
`_lab/spec_decode.py:99` 的 `return out, i` 一旦被改成 `continue`（拒绝了继续检查下一个位置），就会犯这个错误。**问题不在概率公式本身，在"条件"上**：`spec_step()` 里 `p_rows[i+1]` 是 target 在"draft 到 `i` 位置为止全部被接受"这个前提下算出来的分布——一旦位置 `i` 被拒绝、换成了从残差里重采的 token，`i` 之后的历史已经和 target 算 `p_rows[i+1]` 时假设的历史不一样了，继续用 `p_rows[i+1]` 去验证第 `i+1` 位，验证的是一个跟实际前缀不匹配的条件分布。**错了会看到什么现象**：不会报错，也不会像错误一那样在整体分布上留下明显痕迹（因为出错的只是"某次拒绝之后紧跟着的那一小段"），但生成出来的这一小段内容是在错误的条件下采样出来的，统计意义上不再是 target 在真实前缀下会给出的分布——这类 bug 几乎只能靠"拒绝点之后是否还在继续验证"这种代码审查方式抓，统计检验能测出"分布不对"，但很难精确定位到"错在拒绝后没有及时停止"这一步。

**错误四：只用"生成的文本读起来正常"当作验证手段。**
`## 1`/`## 3.1` 反复出现的那句话——`spec_sample_one_naive` **跑得完全正常，生成的文本也通顺，只是分布错了**——是本篇分量最重的一条教训。全变差 0.12940（是正确版的 56 倍）这种量级的偏差，人眼读几段生成文本完全看不出来：语法通顺、语义连贯，唯一能暴露它的是把同一组 `p, q` 跑几万次、统计经验分布再跟理论分布比对（`## 3.1`/`## 3.6` 的做法）。**这正是 `_PLAN.md` §1 第 1 条"推理引擎的 bug 绝大多数是静默的"在投机解码这个场景下最典型的体现**——错误一、二、三都不会让程序崩溃或报错，能抓住它们的只有像 `_lab/tests/test_advanced.py:149-165` 这样专门针对分布做的统计检验，而不是"跑起来看看输出像不像话"。
