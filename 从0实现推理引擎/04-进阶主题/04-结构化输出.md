# 结构化输出

> **一句话**：合法性来自掩码，不来自模型。
> **前置**：`[[06-采样-停止条件-流式输出]]`（复用同一层"过滤候选集"的机制，只是过滤依据从概率排名换成了语法约束）

## 0. 这一篇要解决什么问题

"让大模型输出合法 JSON"是一个被讲烂的需求，也是一个被讲烂的假答案。假答案是这样的：在 system prompt 里写"请务必只输出合法的 JSON，不要有任何多余文字"，然后祈祷。这套做法的问题不是"效果不好"——很多时候效果确实不错——问题是它给不出**保证**。模型是一个概率分布采样器，prompt 只能改变分布的形状，不能给分布的支撑集设边界；只要"输出一个不闭合的花括号"这个事件的概率不严格为零，跑够多次就一定会撞上它，而"够多次"在一个每天处理几百万请求的生产服务里根本不是什么大数字。

真正能给出保证的做法只有一句话：**每一步，把当前语法状态下不合法的 token 全部置成 `-inf`，然后照常采样。** 模型本身没有被改动一分——它仍然在输出它想输出的分布——改的只是喂给它的候选集。所以结果**一定**合法，不是"prompt 写得好所以通常合法"，是数学上不可能不合法：既然不合法的选项已经被排除在候选集之外，采样这个动作本身就没有办法选中它们。这句话是 `_lab/structured.py` 整个文件的立论（`_lab/structured.py:1-9`），也是这一篇要讲透的第一件事。

但这一篇真正的重心不在"给出保证"这个结论本身——结论说出来很直白，几乎没有技术含量。重心在**为什么这件事在工程上比听起来难得多**：难点不在语法（JSON 的语法用 EBNF 写出来不超过十行），难点在**token 边界和语法边界从来不对齐**。真实分词器的一个 token 完全可能横跨两个语法元素——`_lab/structured.py` 用一个刻意构造的小词表把这件事变得可以摸到，词表里 `":` 这个 token 同时横跨"字符串收尾引号"和"冒号"两个语法元素，`,"` 同时横跨"逗号"和"下一个键名的开头引号"（`_lab/structured.py:11-15`）。这意味着**不能按 token 写规则**——"这个 token 在语法上合不合法"根本不是这个 token 自身能回答的问题，必须先在字符层面写清楚文法，再把每个 token 拆成字符逐个喂给这套文法走一遍，才能知道它合不合法。这条题眼句会在 `## 2.2`/`## 2.3` 被数字钉死。

`## 1` 先把 `_lab/structured.py` 的自检和演示跑一遍，把"合法性来自掩码"这句话变成一组可以自己复现的数字；`## 2` 把背后的机制逐条讲清楚，包括一个我自己踩过、被自检当场打脸的坑；`## 3` 逐行对照 `_lab/structured.py` 里的实现；`## 4` 看 SGLang 与 vLLM 这两个真实引擎怎么做同一件事（把 jump-forward 当卖点讲的正是 SGLang）；`## 5`~`## 7` 收尾。

## 2. 原理

### 2.1 三条路线的对照：prompt、拒绝采样、掩码

在讲掩码怎么实现之前，值得先把"让输出合法"这件事的三条常见路线摆在一起比一比，因为它们的失败模式完全不同：

1. **纯 prompt 工程**——`## 0` 已经说过，它改变的是分布的形状，不是分布的支撑集。只要"生成非法输出"这个事件的概率不是数学上的零，就有非零概率触发，而且不会有任何信号告诉你这次触发了（下游拿到字符串直接喂 `json.loads()`，炸的是调用方）。
2. **先生成再拒绝采样**（生成完整输出，`json.loads()` 失败就整段重新生成）——比纯 prompt 多了一层校验，但代价是重新生成的整段成本，而且**没有终止保证**：如果模型在这个 prompt 下生成合法输出的概率本身很低，重试次数的期望值可能高到不可接受，理论上甚至可以不收敛。
3. **掩码**——`## 0` 的做法，每一步把不合法的候选置为 `-inf`。这条路线的正确性证明只需要一句话：**采样的定义域已经不包含非法值，采样结果自然不可能是非法值。** 不依赖"模型学得好不好"，是纯粹的集合论断言。

`## 1` 的第二组对照实验就是把方案 1（不加约束）和方案 3（掩码）并排跑：同一个词表、同一套（纯噪声的）`logits_fn`，不加约束随机吐 6 个 token 时 499/500 无法解析（`_lab/structured.py:278-288`），加了掩码之后 500 次全部能解析、500 次全部走到终态（`_lab/structured.py:260-276`）。这组对照之所以有说服力，恰恰是因为它**刻意选用了最差的模型**——纯噪声，不携带任何"这个模型学过 JSON 长什么样"的信息。如果连纯噪声都能被掩码逼成 100% 合法，这条保证就跟模型本身的能力毫无关系，是掩码这个机制单方面提供的。

### 2.2 token 边界与语法边界为什么会错位

`_lab/structured.py` 的 `VOCAB`（`_lab/structured.py:41-55`）故意在两个地方埋了雷：

```python
# _lab/structured.py:41-55
VOCAB: list[str] = [
    "",        # 0  EOS
    "{",       # 1
    "}",       # 2
    '"',       # 3
    ":",       # 4
    ",",       # 5
    '":',      # 6  <- 横跨：字符串收尾 + 冒号
    ',"',      # 7  <- 横跨：逗号 + 下一个键的开头引号
    "name",    # 8
    "age",     # 9
    "Ada",     # 10
    "42",      # 11
    "x",       # 12
]
```

`'":'`（id 6）和 `',"'`（id 7）不是凑数的怪 token，它们复现了真实 BPE 分词器一个非常普遍的现象：合并规则只看字节共现频率，不看语法结构。"引号紧跟冒号"或者"逗号紧跟引号"这种组合在训练语料里出现得足够频繁，BPE 就会把它们合并成一个 token，完全不管这两个字符分别属于哪个语法元素。这不是本库编出来的极端情形——真实分词器里类似的横跨现象比比皆是（标点与紧邻词的合并、驼峰命名内部的合并等等）。

这条现象直接推出一个后果：**规则不能写在 token 层面。** 如果规则是"检查这个 token 是不是当前语法允许出现的 token 之一"，第一个问题就是"允许出现的 token"这个概念本身依赖你已经把语法精确到了字符——而字符层面的语法，只需要知道"下一个字符能不能接在当前状态后面"，根本不需要关心分词器切出来的边界在哪里。`_lab/structured.py` 的做法是把这两层显式分开：

- `step_char()`（`_lab/structured.py:72-117`）只回答"一个字符能不能走"，这是**语法本身**，与分词器无关；
- `step_token()`（`_lab/structured.py:120-133`）把一个 token 拆成字符，逐个喂给 `step_char()`，全部走通才算这个 token 合法——**token 层面的合法性是从字符层面推出来的结果，不是可以独立定义的东西。**

```python
# _lab/structured.py:120-133
def step_token(st: tuple, tok: str) -> tuple | None:
    if tok == "":
        return st if st[0] == "done" else None    # EOS 只在终态合法
    cur: tuple | None = st
    for ch in tok:
        cur = step_char(cur, ch)
        if cur is None:
            return None
    return cur
```

`for ch in tok` 这一行就是"把 token 拆开逐字符走一遍"的全部代码——没有任何特殊处理横跨边界 token 的分支，因为**根本不需要特殊处理**：只要字符层面的规则是完整的，横跨边界的 token 自动就能被正确判定，不需要为 `'":'`、`',"'` 这类 token 单独写一条 if。这是"在字符层面写规则"这条设计换来的直接好处。

### 2.3 合法性是状态的属性，不是 token 的属性

`## 2.2` 只回答了"横跨边界的 token 怎么判定"，还没回答一个更根本的问题：同一个 token，换一个语法状态，合法性会不会变？`selftest()` 用 `'":'` 这一个 token 在两个状态下的行为把这件事钉死（`_lab/structured.py:253-256`）：

```python
chk(step_token(("kb", 1, 0), '":') == ("val", 0, 0),
    "token '\":' 在键名内部合法，逐字符走后落在 val")
chk(step_token(("kq", 0, 0), '":') is None,
    "**同一个 token 换个状态就不合法** —— 合法性是状态的属性，不是 token 的属性")
```

`("kb", 1, 0)` 是"已经在键名内部吃了 1 个字母"的状态——这时候 `'":'` 里的引号能收尾键名、冒号能顺理成章地进入 `val` 状态，整个 token 合法。`("kq", 0, 0)` 是"正在等键名的开头引号"的状态——这时候 `'":'` 的第一个字符 `"` 确实能走通（进入 `kb`），但第二个字符 `:` 在 `kb` 状态下不是字母也不是收尾引号，`step_char` 直接返回 `None`，整个 token 判定失败。

这是本篇的题眼：**一张"token → 是否合法"的表根本不存在，能存在的只有"状态 × token → 是否合法"这张表。** `## 3.6` 会看到 `build_index()` 正是按这个形状建的——键是状态，不是空空如也地只按 token 建一份全局表。这条结论直接决定了 `## 6` 要点名的一类错误：如果实现里把某个状态算出来的合法 token 集合缓存下来、复用到另一个状态上，看起来是"性能优化"，实际上是让模型在不该合法的地方合法地吐出了不该出现的 token。

### 2.4 索引是怎么建的：BFS 枚举 + 全量试走

有了"状态相关"这条结论，剩下的问题是怎么把这张表建出来，让**推理时**不需要对每个候选 token 现场跑一遍 `step_token`（那样每一步采样都要付出 O(词表 × token 长度) 的代价，等于把编译时的活干到了热路径上）。做法是提前把它算好：

1. **BFS 枚举所有可达状态**——`all_states()`（`_lab/structured.py:138-151`）从起始状态出发，对每个已发现的状态尝试字母表里的每个字符，把新状态收进队列，直到无法再发现新状态为止。这正是`## 1` 里"41 个可达状态"这个数字的来源，也是任何一个真实的语法编译器在做的事——BFS/DFS 遍历状态机不是本库的教学简化,是构建确定性有限自动机（DFA）的标准做法。
2. **为每个状态 × 每个 token 试走一遍**——`build_index()`（`_lab/structured.py:154-161`）：

```python
# _lab/structured.py:154-161
def build_index(vocab: list[str] = VOCAB) -> dict[tuple, np.ndarray]:
    return {st: np.array([step_token(st, t) is not None for t in vocab])
            for st in all_states()}
```

这张表的成本是 **O(状态数 × 词表大小 × 平均 token 长度)**，但只需要**做一次**——语法和分词器一旦固定，这张表就固定了，推理时只是一次字典查找加一次布尔数组索引。本库的玩具规模是 41 × 13 × (≤4)，眨眼就能建完；**真实系统的词表是几万到几十万、状态数可能上千**，这张表的构建时间和内存占用就不再是可以忽略的常数了——这正是"结构化输出换一个语法（或者换一个 JSON Schema）就要重新编译一次索引"这句话的来源，`## 5` 会把这点落成一条设计决策，`## 4` 会看到真实引擎为什么要专门为编译结果加一层缓存。

### 2.5 有界文法：为什么随机采样需要三个上界

`_lab/structured.py` 的文法带着三个显式上界（`_lab/structured.py:64`）：

```python
# _lab/structured.py:64
MAX_WORD, MAX_DIGIT, MAX_PAIR = 5, 3, 2
```

分别限制"一个字母串最长几个字符"、"一个数字串最长几位"、"最多几个键值对"。这三个数字不是随便拍的，它们是 `## 2.4` 的 BFS 能够终止的前提：如果字母串长度没有上界，`("kb", n, p)` 这样的状态会随着 `n` 无限增长，`all_states()` 永远枚举不完，`build_index()` 也就永远建不出来。**有界文法不是可选项,是"状态数有限"这条前提的必要条件。**

有界这件事还有第二层意义,`## 1` 的对照实验其实已经用到了它:如果生成过程允许无限长(比如字母串长度没有上界),纯噪声驱动的采样有非零概率永远不吐出收尾引号,`selftest()` 里"500 次全部走到终态"这条断言就没有理论保证成立——是有限状态、有限步数的 `max_tokens` 上限,以及文法本身的有界性,共同保证了这条实验能够稳定复现。

这条限制不是玩具专属的简化。**真实场景里这些上界通常就是 JSON Schema 本身在提供**——`maxLength`、`minimum`/`maximum` 的位数、数组的 `maxItems`、对象的必需字段数——一份 JSON Schema 描述的本来就是一个有界文法,`_lab/structured.py` 的 `MAX_WORD`/`MAX_DIGIT`/`MAX_PAIR` 只是把这件事从 schema 的字段直接搬成了代码里的三个整数常量。`## 4` 会看到真实引擎(SGLang、vLLM)确实是把用户传入的 JSON Schema 编译成语法对象,而不是凭空发明一套语法。

### 2.6 空合法集合必须炸

`apply_mask()`（`_lab/structured.py:164-174`）做的事情看起来只有一行：

```python
# _lab/structured.py:164-174
def apply_mask(logits: np.ndarray, allowed: np.ndarray) -> np.ndarray:
    if not allowed.any():
        raise ValueError("当前状态没有任何合法 token —— 语法或索引有 bug")
    return np.where(allowed, logits, -np.inf)
```

`if not allowed.any(): raise` 这一行看起来像是防御性编程的老套路，但它在这里不是可有可无的装饰——**如果没有这一行，`allowed` 全 `False` 时 `np.where` 会把所有位置都置成 `-inf`，紧接着的 softmax 计算 `exp(lg - lg.max())` 里 `lg.max()` 本身就是 `-inf`，`lg - lg.max()` 变成 `-inf - (-inf) = nan`，`exp(nan) = nan`，归一化之后概率分布整个是 `nan`。** 到了这一步，`np.random.choice` 或者 `argmax` 面对全 `nan` 的输入，行为是未定义的——多数实现会退化成取第 0 个位置，也就是本库词表里的 EOS，或者别的什么无意义的默认值。**全程没有任何异常、没有任何警告，模型开始吐垃圾，唯一的信号是下游某个环节的输出突然不对了，而这时候现场早就丢了。**

这条防线之所以值得单独拎出来讲，是因为它对应着一类**语法本身设计有 bug**的情况——比如某个状态在 `step_char` 里被写漏了一条转移，导致从这个状态出发没有任何字符能走。这种 bug 不该被"优雅地兜住"，恰恰相反，它必须以最刺耳的方式炸出来，因为它意味着**语法或者索引这一层的代码本身是错的**，任何静默处理都是在把这个 bug 一路掩盖到用户看到乱码为止。`test_empty_allowed_set_raises_loudly`（`_lab/tests/test_advanced.py:227-230`）把这条要求钉成了一条可回归的断言。

### 2.7 jump-forward：只剩一条路时不用问模型

`## 1` 状态表里能看到不少状态只有 1 个合法 token（比如 `('start', 0, 0)` 只有 `'{'` 合法，`('colon', 0, 0)` 只有 `':'` 合法）——这类状态在语法上叫"确定性路径"：不管模型想输出什么，下一个 token 已经被语法钉死了。既然结果已经确定，**问模型这一步的 logits 纯属浪费一次前向计算**，`forced_token()`（`_lab/structured.py:177-185`）把这件事变成一次直接的判定：

```python
# _lab/structured.py:177-185
def forced_token(allowed: np.ndarray) -> int | None:
    ids = np.flatnonzero(allowed)
    return int(ids[0]) if len(ids) == 1 else None
```

`## 1` 里"41 个状态里 12 个只有唯一选择"和"jump-forward 平均省 31% 的调用"这两个数字就是这个函数在批量场景下的效果。代价要说清楚——`forced_token()` 的文档字符串专门点出这条（`_lab/structured.py:180-182`）：这样吐出去的 token **未必是模型自己会选的切分**。举个例子，语法钉死下一步必须是引号加冒号，如果词表里同时有 `'"'`+`':'`（两个独立 token）和 `'":'`（一个合并 token）两种切法都能走通语法，`forced_token()` 只会在"合法集合恰好只剩一个 token"的那一刻触发，如果两种切法都合法，这一步就不会被跳过，会正常问模型；但一旦真的触发了跳步，跳过去的这个具体 token id 是语法逼出来的，不是模型采样出来的——这跟真实分词器场景下的 **token healing** 问题是同一件事：模型自己训练时"看到"的边界切法，未必和推理时被语法强制吐出来的切法一致。多数场景这个差异无所谓（下游只关心最终字符串），但**要拿这一步的 logprob 去做打分或者对齐训练时，这里会咬人**——logprob 对应的是"模型给这个具体 token 的概率"，而这个 token 根本没有真的被采样过，它的 logprob 在语义上是缺失的。

### 2.8 我踩的坑：从头到尾共享一个 rng，会让"跳步"和"不跳步"走上两条不同的轨迹

这一段是本篇唯一要展开讲"错误的第一版长什么样"的地方，因为它是一个非常容易在类似场景里重犯的错误。`generate()`（`_lab/structured.py:190-231`）的文档字符串把这件事讲得很直白（`_lab/structured.py:198-204`）：

```python
# _lab/structured.py:198-204
⚠️ **随机性按「(seed, 已生成文本)」派生，而不是一个从头走到尾的 Generator。**
这不是洁癖，是被 jump-forward 逼出来的：被跳过的那些步**不消耗随机数**，
共用一个有状态的 rng 时，开关 jump-forward 会让两条轨迹从第一次跳过之后
彻底发散 —— 于是根本没法验证"跳过的都是没得选的步"。
**我第一版就是这么写的，自检直接打脸：产出文本不同、调用次数反而更多。**
派生式随机让"同 seed ⇒ 同轨迹"成立，两者才可比。
```

第一版的错误做法是这样的：在 `generate()` 开头建一个 `rng = np.random.default_rng(seed)`，每次真正需要采样时调用 `rng.choice(...)`，jump-forward 跳过的步完全不碰这个 rng。乍看没什么问题——jump-forward 本来就不需要采样。但破绽在于：**"这一步该不该消耗一次随机数"这件事，本身取决于开没开 jump-forward。** 假设关掉 jump-forward 跑一条轨迹：第 3 步、第 5 步、第 7 步都要真的采样，`rng` 依次被调用第 1、2、3 次。再打开 jump-forward 跑同一个 `seed`：第 3 步被判定成唯一选择，直接跳过，不碰 `rng`；到了第 5 步才第一次调用 `rng`——但这是同一个共享 `rng` 对象的**第 1 次**调用，而关闭版本里第 5 步用的是 `rng` 的**第 2 次**调用。同一个 `rng` 对象的调用序列一旦错位，从第一次跳步开始，两条轨迹拿到的随机数完全对不上——于是"开关 jump-forward 应该产出同一段文本，只是少问几次模型"这条本该成立的性质，在第一版代码里直接不成立：`selftest()` 一跑，产出文本不同，而且更荒谬的是**调用次数反而变多了**（因为随机数错位导致某些分支走向了原本不会走的、更长的路径）。

修复方式是把随机性从"一个从头跑到尾的有状态对象"换成"按 `(seed, 已生成文本, 已生成的 token 数)` 现场派生"（`_lab/structured.py:223-225`）：

```python
# _lab/structured.py:223-225
# **必须用确定性哈希。** Python 的内置 `hash()` 对字符串是逐进程加盐的，
# 用它会让"同 seed ⇒ 同轨迹"只在单次进程内成立，换个进程就不一样。
srng = np.random.default_rng([seed, zlib.crc32(text.encode()), len(toks)])
```

这样一来，"这一步会不会被跳过"完全不影响"下一次真正采样时会拿到哪个 rng"——每次采样都是独立地根据"到目前为止已经生成的文本"重新计算出一个专属的 rng，被跳过的步完全不在这条计算路径上，两条轨迹在共同经过的每一步上必然拿到完全相同的随机数。`## 3.9` 会展开讲这行代码的另一处隐藏坑：**为什么必须显式用 `zlib.crc32`，而不能用 Python 内置的 `hash()`。**

### 2.9 和投机解码的关键区别：等价重写 vs 有意干预

这两件事经常被放在一起讨论，因为它们都涉及"在采样之前对候选做点什么"，但它们的目标是相反的。`_lab/tests/test_advanced.py` 文件头（`_lab/tests/test_advanced.py:1-17`）把本库四个进阶模块各自的测试判据列成了一张表，其中投机解码和结构化输出这两行放在一起看最能说明问题：

| 模块 | 判据 | 为什么 |
|---|---|---|
| `spec_decode` | **分布恒等**（统计检验） | 单次输出本来就是随机的，只能测分布 |
| `structured` | **约束恒成立** | 它**故意**改变分布，恒等测试没有意义 |

`[[03-投机解码]]` 的核心恒等式在 `_lab/spec_decode.py:24` 写得很直白：`P(输出 x) = min(q(x), p(x)) + max(0, p(x)-q(x)) = p(x)`——不管草稿分布 `q` 是什么，验收之后的输出分布**精确**等于目标模型自己的分布 `p`。投机解码的全部正确性要求就是这一条：它换了一种更便宜的**采样过程**，但过程的终点——输出的分布——必须跟"老老实实一步步问目标模型"完全一样，一个字节的偏差都不许有。这是**等价重写**：看起来走了近道，落地效果必须证明和不走近道完全相同。

结构化输出反过来：`selftest()` 里专门有一条断言验证掩码之后的概率分布（`_lab/structured.py:303-312`）——

```python
# _lab/structured.py:306-312（节选）
masked = apply_mask(lg, idx[probs_state])
e = np.exp(masked - masked.max())
probs = e / e.sum()
chk(abs(probs[idx[probs_state]].sum() - 1.0) < 1e-12
    and probs[~idx[probs_state]].sum() == 0.0, ...)
```

掩码之后，不合法位置的概率**恒为零**，合法位置的概率被重新归一化到总和为 1——这不是"意外的副作用"，是掩码存在的**目的本身**：结构化输出就是要把不合法那部分概率密度直接剪掉，让合法子集在被剪掉之后重新构成一个合法的概率分布。这是**有意的干预**：模型原本会给非法 token 分配的那部分概率，被有意地、不加掩饰地重新分配给了合法 token；分布因此改变了，改变的方向和幅度都是设计者要的结果，不是需要被消除的误差。

**把这两套判据用反是这个领域最常见的测试错误之一。** 拿"输出分布必须和不加约束时完全一致"去测结构化输出，这条测试永远不可能通过，因为约束生效的意义就在于分布必须变；反过来拿"跑起来不报错"去测投机解码，这类 bug 最危险——`_lab/tests/test_advanced.py` 里专门留了一个 `test_naive_verifier_is_biased` 的反例（在 `[[03-投机解码]]` 那一篇会展开），一个看起来合理的朴素验收实现完全能够正常运行、不抛任何异常，只是采样出来的分布已经悄悄偏了，这种 bug 只有靠对分布做统计检验才能抓到。**测试判据要和"这个组件的正确性到底意味着什么"对齐，不能图省事套用同一套模板。**

`n >= 1` 这个判据（`_lab/structured.py:86`）是"键名不能是空字符串"这条 JSON 语法要求的直接落地——如果去掉这个条件，`{""：""}`（空键名）会被判定为合法，这不是本库刻意留的教学彩蛋，是编写字符级文法时必须显式处理的一条边界。这整个函数的注释里点明了它的地位（`_lab/structured.py:75-77`）：**只有字符层面的规则才是文法本身，token 层面的合法性是由它推出来的结果**——这句话是 `## 2.2`/`## 2.3` 两节结论共同的出发点。

### 3.4 `step_token`：把 token 拆开逐字符走一遍

`step_token()`（`_lab/structured.py:120-133`）的完整实现已经在 `## 2.2` 展示过。这里强调一点：这个函数**没有为任何具体的 token 写特殊分支**，包括横跨边界的 `'":'`、`',"'`。它对所有 token 一视同仁地拆成字符、逐个喂给 `step_char`——这正是"横跨边界的 token 问题不需要单独解决"这条结论在代码层面的样子：解法不是"针对横跨边界的情形打个补丁"，而是从一开始就用一种不区分 token 边界的方式定义合法性。

### 3.5 `all_states`：BFS 枚举可达状态

```python
# _lab/structured.py:138-151
def all_states() -> list[tuple]:
    seen, frontier, order = {Start}, [Start], [Start]
    while frontier:
        nxt = []
        for st in frontier:
            for ch in ALPHABET:
                to = step_char(st, ch)
                if to is not None and to not in seen:
                    seen.add(to)
                    order.append(to)
                    nxt.append(to)
        frontier = nxt
    return order
```

这是一个标准的层序 BFS：`frontier` 是本轮待扩展的状态集合，对每个状态尝试字母表里的每个字符（不是尝试词表里的每个 token——枚举状态这一步只需要字符级文法，`## 3.1` 的 `ALPHABET` 在这里被用到），把新发现的状态收进 `seen`/`order`，直到某一轮扩展不出任何新状态、`frontier` 变空为止。`order` 保留了状态被首次发现的顺序，这个顺序本身没有特殊含义，只是让 `## 1` 的状态表打印出来时相对稳定、可复现。

### 3.6 `build_index`：状态是索引的键，不是 token

`build_index()`（`_lab/structured.py:154-161`）的完整实现在 `## 2.4` 已经展示过。这里补一条从 `## 2.3` 延伸出来的实现细节：返回的字典 `{st: np.array([...]) for st in all_states()}` 的键是**状态**，值是一个长度等于词表大小的布尔数组——这个数据结构的形状本身就是"合法性是状态的属性"这条结论的直接翻译：如果不小心把索引结构写成 `{token: 是否总是合法}` 这种忽略状态的形状，`## 6` 会讲这类错误会造成什么后果。

### 3.7 `apply_mask`：先炸后归一化

`_lab/structured.py:164-174` 的完整代码已经在 `## 2.6` 展示过。补一句实现顺序上的细节：`apply_mask()` 本身**不做 softmax**，只负责把非法位置置为 `-inf`——真正的 softmax 和归一化是 `generate()` 调用完 `apply_mask()` 之后另外做的（`_lab/structured.py:222`，`e = np.exp(lg - lg.max())`）。这个职责划分是有意的：`apply_mask()` 只对"给定 logits 和合法性掩码，输出被掩码过的 logits"这一件事负责，不掺杂采样策略——这样它可以被独立测试（`test_mask_renormalizes_onto_allowed_set`，`_lab/tests/test_advanced.py:233-241`），不需要连带测试整条采样管线。

### 3.8 `forced_token`：唯一合法 token 时的直接判定

`_lab/structured.py:177-185` 的完整代码已经在 `## 2.7` 展示过。这里补一句边界条件：`len(ids) == 1` 这个判据只在**恰好**一个合法 token 时触发，如果合法集合是空的（`## 2.6` 讨论的 bug 场景），`np.flatnonzero(allowed)` 返回空数组，`forced_token()` 会返回 `None`——也就是说 `forced_token()` 本身并不会在空集合场景下报错，它只是老实回答"没有唯一选择"，真正负责报错的是 `## 3.7` 的 `apply_mask()`（因为一旦 `forced_token` 判定不是唯一选择，`generate()` 就会走到 `apply_mask()` 那一步，`## 3.9` 会看到这个调用顺序）。**报错的职责被放在 `apply_mask()` 而不是 `forced_token()`，是因为空集合是"语法或索引写错了"的信号，而这个信号只有在真正要采样的那一刻才有意义去检查。**

### 3.9 `generate`：调度 jump-forward 与派生式随机数

`generate()`（`_lab/structured.py:190-231`）的主循环把前面几节的构件拼在一起：

```python
# _lab/structured.py:208-229（节选，循环体）
for _ in range(max_tokens):
    if st[0] == "done":
        break
    allowed = idx[st]
    if jump_forward:
        f = forced_token(allowed)
        if f is not None:
            jumped += 1
            toks.append(f)
            text += vocab[f]
            st = step_token(st, vocab[f])
            continue
    calls += 1
    lg = apply_mask(np.asarray(logits_fn(st, text), np.float64), allowed)
    e = np.exp(lg - lg.max())
    srng = np.random.default_rng([seed, zlib.crc32(text.encode()), len(toks)])
    t = int(srng.choice(len(lg), p=e / e.sum()))
    toks.append(t)
    text += vocab[t]
    st = step_token(st, vocab[t])
```

每一步先查索引拿到 `allowed`（`## 3.6`），再看是否开启 jump-forward、这一步是否只有唯一选择（`## 3.8`）——如果是，直接吃掉这个 token、更新状态、`continue`，**完全不调用 `logits_fn`**，`calls` 计数器不增加；如果不是，才真正调用一次模型、走 `apply_mask` → softmax → 派生式随机数采样这条链路，`calls` 计数器加一。`## 2.8` 讲过的坑就藏在这最后三行：`srng` 是**每次采样现场重新构造**的，用的是 `[seed, zlib.crc32(text.encode()), len(toks)]` 这三个数拼成的种子，而不是一个在循环外部建好、循环体内反复调用的共享对象。

`_lab/structured.py:223-224` 那两行注释点出了另一处隐藏坑：**为什么必须用 `zlib.crc32` 而不是 Python 内置的 `hash()`。** Python 出于安全考虑，对字符串的 `hash()` 从 3.3 版本起默认启用了随机加盐（`PYTHONHASHSEED`），同一段代码在同一个进程内多次调用 `hash("some text")` 会得到一致的结果，但**换一个进程运行，同样的字符串会得到不同的哈希值**——这意味着如果 `generate()` 用内置 `hash()` 派生种子，"同 seed 复现同轨迹"这个承诺只在单次进程运行内成立，写进测试报告的复现步骤，换一台机器、甚至同一台机器重新起一次 Python 进程，就对不上了。`zlib.crc32` 是一个不带随机盐的确定性哈希函数，同样的输入永远给出同样的输出，不依赖进程状态——这是"确定性"这个词在这里的准确含义：不是"看起来随机但固定"，是"任何时候、任何进程里重算都一样"。

### 3.10 `selftest`：12 项断言怎么覆盖前面每一条机制

`selftest()`（`_lab/structured.py:236-321`）不是把每个函数各跑一遍看看报不报错，而是针对 `## 2` 的每一条机制专门构造了能暴露对错的输入——`## 1` 打印的 12 行输出，每一行背后都对应着一个具体的断言：状态数与起始状态（`_lab/structured.py:247-250`，对应 `## 2.5`/`## 2.7`）、横跨边界 token 的状态相关合法性（`_lab/structured.py:253-258`，对应 `## 2.3`）、约束生成 500 次全部合法与不加约束的对照（`_lab/structured.py:260-288`，对应 `## 2.1`）、jump-forward 的调用数与文本一致性（`_lab/structured.py:291-301`，对应 `## 2.7`/`## 2.8`）、掩码的概率语义（`_lab/structured.py:304-312`，对应 `## 2.9`）、空集合报错（`_lab/structured.py:314-318`，对应 `## 2.6`）。**这些断言不是覆盖率意义上的"跑到了这一行"，是专门为每一类可能的静默 bug 设计的对抗性输入**——`## 6` 会反过来，把每一类输入当成"如果代码写错了会看到什么现象"的示范。

### 3.11 五项 pytest 回归测试：把手动验证钉成可回归的断言

`_lab/tests/test_advanced.py` 里专门给结构化输出留了五个测试函数，与 `selftest()` 的关系是**互补而非重复**——`selftest()` 跑的是固定的少数几个种子，pytest 这五项把关键性质铺开在更大范围的输入上验证：

- `test_constrained_output_is_always_parseable`（`_lab/tests/test_advanced.py:204-208`）用 `@pytest.mark.parametrize("seed", range(20))` 把 `## 2.1` 的"500 次全部合法"这条断言换成 20 个独立种子逐个跑、逐个断言，任何一个种子失败都会被 pytest 精确定位到具体的种子值，比 `selftest()` 里"500 次一起过或一起不过"的粗粒度报告更适合调试。
- `test_token_legality_is_state_dependent`（`_lab/tests/test_advanced.py:211-214`）单独把 `## 2.3` 的核心断言拎出来，不依赖 `index` fixture，是这五项里最快、最该在改动 `step_char`/`step_token` 之后第一个跑的测试。
- `test_jump_forward_changes_cost_not_output`（`_lab/tests/test_advanced.py:217-223`）把 `## 2.8` 那条"开关 jump-forward 产出必须完全相同"的性质铺开在 10 个种子上，同时断言 `a["model_calls"] + a["jumped"] == b["model_calls"]`——这条等式本身就是在验证"跳过的步不多不少，全部是被省下的模型调用"，如果 `## 2.8` 的坑复发（rng 从头到尾共享），这条等式和文本相等两条断言会同时失败。
- `test_empty_allowed_set_raises_loudly`（`_lab/tests/test_advanced.py:227-230`）直接构造一个全 `False` 的合法性数组喂给 `apply_mask`，断言必须抛出 `ValueError`——这是 `## 2.6` 那条"空集合必须炸"的护栏。
- `test_mask_renormalizes_onto_allowed_set`（`_lab/tests/test_advanced.py:233-241`）验证掩码之后概率恰好落在合法集合上、恰好归一化到 1——`## 2.9` 用来跟投机解码做对比的那条性质。

### 3.12 `_demo`：状态表、约束生成、jump-forward 对比

`_demo()`（`_lab/structured.py:326-369`）就是 `## 1` 打印出来的那三段输出的来源，不是另外写的展示代码——它直接调用 `build_index()`/`all_states()`/`generate()`，跟 `selftest()` 用的是同一套函数，只是把断言换成了打印。这一点值得单独说一句：本库的"演示"和"自检"从不使用两套互相独立的实现，`_demo()` 打印出来的每一个数字都能在 `selftest()` 的某条断言里找到对应，这也是为什么 `## 1` 能放心地直接引用 `_demo()` 的输出作为"可复现的现象"——它背后有断言在守着，不是一次性演示脚本随缘打印出来的数字。

## 4. 真实引擎是怎么做的（对照 vLLM/SGLang，带 `引擎:文件:行`）

### 4.1 SGLang：三种约束形式，dispatch 到不同后端

SGLang 的语法后端接口在 `base_grammar_backend.py` 里定义了统一的 dispatch 入口，接收的约束形式不止 JSON 一种：

```python
# sglang:python/sglang/srt/constrained/base_grammar_backend.py:128-138（节选）
def dispatch_json(self, key_string: str) -> BaseGrammarObject:
    return self._not_supported("json", key_string)

def dispatch_regex(self, key_string: str) -> BaseGrammarObject:
    return self._not_supported("regex", key_string)

def dispatch_ebnf(self, key_string: str) -> BaseGrammarObject:
    return self._not_supported("ebnf", key_string)

def dispatch_structural_tag(self, key_string: str) -> BaseGrammarObject:
    return self._not_supported("structural_tag", key_string)
```

四个 `dispatch_*` 方法对应四种约束形式：**JSON Schema、正则表达式、EBNF 文法、结构化标签（structural tag，一种更细粒度的"标签内是某种 schema"约束）**。基类里每一个默认实现都是"不支持"（`_not_supported`），具体支持哪些由子类（`XGrammarGrammarBackend`、`OutlinesBackend`、`LLGuidanceBackend` 等）覆写——这跟 `_lab/structured.py` 只写死一种 JSON 子集语法的做法形成直接对照：真实系统里"语法"不是一份写死的代码，是一个可插拔的编译目标，`## 2.5` 讲过的"上界通常来自 JSON Schema"在这里对应的正是 `dispatch_json`。

### 4.2 SGLang：编译结果的缓存字典，键是 `(约束类型, 约束内容)`

`## 2.4` 讲过索引/编译只需要做一次、但成本不小。SGLang 把编译出来的语法对象缓存在一个字典里，键是约束类型和约束内容组成的元组：

```python
# sglang:python/sglang/srt/constrained/base_grammar_backend.py:205-207
def __init__(self):
    self.executor = ThreadPoolExecutor()
    self.cache: Dict[Tuple[str, str], BaseGrammarObject] = {}
```

取用这份缓存的逻辑把"缓存命中直接返回"和"缓存未命中提交异步编译任务"分得很清楚：

```python
# sglang:python/sglang/srt/constrained/base_grammar_backend.py:284-293
def get_cached_or_future_value(
    self, key: Tuple[str, str], require_reasoning: bool
) -> Tuple[BaseGrammarObject | Future[BaseGrammarObject], bool]:
    value = self.cache.get(key)
    if value:
        copied_value = value.copy()
        copied_value.maybe_init_reasoning(require_reasoning)
        return copied_value, True
    value = self.executor.submit(self._init_value_dispatch, key, require_reasoning)
    return value, False
```

命中时返回的是 `value.copy()`，不是共享的同一个对象——`## 2.3` 讲过语法状态是可变的（每接受一个 token 状态就会推进），如果两条不同的请求共享同一个语法对象实例，一条请求的状态推进会污染另一条请求；`copy()` 保证每条请求拿到的是**独立的状态副本**，共享的只是编译产出的静态部分（`GrammarMatcher` 之外的编译结果，`## 4.3` 会看到 xgrammar 后端 `copy()` 具体复用了哪些字段）。未命中时不是同步阻塞编译，是 `self.executor.submit(...)` 提交到线程池异步编译——`## 2.4` 说过编译成本在真实系统里不是常数，如果同步编译，第一个用某个新 schema 的请求会让整条调度主循环卡住等编译完成；异步提交把这段延迟挪出了关键路径，跟 `[[06-采样-停止条件-流式输出]]` `## 4.4` 讲的"detokenize 独立进程"是同一种思路的不同应用——**把慢的 CPU 活搬到不会卡住主循环的地方去做**。

### 4.3 SGLang：xgrammar 后端把掩码做成一次批量 bitmask 操作

`## 2.6` 的 `apply_mask()` 是单条请求、单次调用的 numpy 操作。真实系统需要在一个批次的多条请求上同时应用各自的掩码，SGLang 的 xgrammar 后端把这件事编码成一个批量的 token bitmask：

```python
# sglang:python/sglang/srt/constrained/xgrammar_backend.py:114-120
def allocate_vocab_mask(
    self, vocab_size: int, batch_size: int, device
) -> torch.Tensor:
    return _allocate_token_bitmask(vocab_size, batch_size)

def fill_vocab_mask(self, vocab_mask: torch.Tensor, idx: int) -> None:
    self.matcher.fill_next_token_bitmask(vocab_mask, idx)
```

`fill_next_token_bitmask` 直接由 xgrammar 库（一个专门做语法约束解码的 C++/CUDA 库）提供，把"给定当前语法状态、填出这一行的合法性位图"这件事下沉到了编译好的原生代码里，而不是像 `_lab/structured.py` 那样用 Python 的 `np.array([step_token(st, t) is not None for t in vocab])` 现场算——**这正是 `## 2.4` 说的"这张表只需要建一次"在真实系统里的另一种实现方式：不是把整张状态×词表的表提前全部枚举好存起来（词表几万到几十万、状态上千时这张表会大到不实际），而是维护一个能在当前状态下快速算出这一行掩码的匹配器（`GrammarMatcher`），需要哪一行现算哪一行**，用编译好的自动机结构换取现算的速度。应用掩码这一步也走了专门的 kernel，不是一次 `np.where`：

```python
# sglang:python/sglang/srt/constrained/xgrammar_backend.py:126-131（节选）
def apply_vocab_mask(self, logits: torch.Tensor, vocab_mask: torch.Tensor) -> None:
    if logits.device.type in {"cuda", "xpu", "musa"}:
        if _is_hip:
            apply_token_bitmask_inplace_cuda(logits, vocab_mask)
        else:
            apply_token_bitmask_inplace_triton(logits, vocab_mask)
```

原理跟 `_lab/structured.py:174` 的 `np.where(allowed, logits, -np.inf)`完全一样——把不合法位置置为一个极小值，让 softmax 之后这些位置的概率归零——只是换成了一个按设备类型分派的原地 kernel（CUDA 版本或者 Triton 版本），这是"同一个数学操作，在数十万词表 × 数百并发请求的规模下需要专门的 kernel 而不是通用张量操作"的一个具体例子，本篇不涉及性能数字，只指出这个操作在真实系统里已经不是一行 `np.where` 能打发的了。

### 4.4 SGLang：xgrammar 的 jump-forward 是"问匹配器要一段确定的字符串"

`## 2.7` 的 `forced_token()` 只回答"当前是不是恰好一个合法 token"。SGLang 的 xgrammar 后端把 jump-forward 实现成直接向底层匹配器要一段"接下来必然会出现的字符串"：

```python
# sglang:python/sglang/srt/constrained/xgrammar_backend.py:164-168
def try_jump_forward(self, tokenizer) -> Optional[Tuple[List[int], str]]:
    s = self.matcher.find_jump_forward_string()
    if s:
        return [], s
    return None
```

`find_jump_forward_string()` 做的是同一件事的加强版：不只是"下一个 token 是不是唯一的"，而是"从当前状态出发，沿着确定性路径能一口气走多远"——如果语法在接下来连续好几步都只有一条路可走（比如 JSON 里某个字段名被固定死之后紧跟的引号、冒号、下一个固定字段名），这里会一次性把这整段确定的字符串取出来，而不是像 `_lab/structured.py` 的 `forced_token()` 那样每步单独判断一次。**这是同一个"确定性路径不用问模型"的想法，被做成了批量版本**：`_lab/structured.py` 的 `generate()` 主循环里 jump-forward 命中之后还是 `continue` 回到循环顶部逐 token 判断，SGLang 这里是一次调用拿到一整段字符串。SGLang 更早期的 `outlines` 后端（在 xgrammar 成为默认后端之前）实现的是同一个想法的另一版本，模块文档字符串直接引用了这个技术最初发表的博客（`sglang:python/sglang/srt/constrained/outlines_jump_forward.py:14-16`）：

```
Faster constrained decoding with jump forward decoding / compressed finite state machine.
Reference: https://lmsys.org/blog/2024-02-05-compressed-fsm/
```

这份 outlines 后端的实现思路和 `_lab/structured.py` 的 `forced_token()` 更接近：`init_state_to_jump_forward()`（`sglang:python/sglang/srt/constrained/outlines_jump_forward.py:62-139`）遍历正则对应的确定性有限自动机的每条转移，统计每个状态的出边数（`outgoings_ct`），**只有出边数恰好为 1 的状态才会被记进跳转表**——跟 `_lab/structured.py:184-185` 的 `len(ids) == 1` 判据是同一条逻辑，只是这里是在编译期把所有"唯一出边"的状态提前找出来存成一张表，而不是在生成时现场对合法性数组数有几个 `True`。

### 4.5 vLLM：一个 `StructuredOutputOptions` 枚举定义了支持的约束形式

vLLM 的结构化输出后端接口用一个枚举明确列出了它支持的约束形式：

```python
# vllm:vllm/v1/structured_output/backend_types.py:19-25
class StructuredOutputOptions(enum.Enum):
    JSON = enum.auto()
    JSON_OBJECT = enum.auto()
    REGEX = enum.auto()
    GRAMMAR = enum.auto()
    CHOICE = enum.auto()
    STRUCTURAL_TAG = enum.auto()
```

`JSON`（按 JSON Schema 约束）、`REGEX`（正则表达式）、`GRAMMAR`（EBNF 文法）、`STRUCTURAL_TAG`（结构化标签），再加上两个更具体的便利形式 `JSON_OBJECT`（任意合法 JSON 对象，不绑定具体 schema）和 `CHOICE`（从一组给定字符串里选一个）——跟 `## 4.1` SGLang 的四个 `dispatch_*` 基本是同一套支持面（JSON Schema / 正则 / EBNF 三种核心形式两边都有，只是 vLLM 用一个枚举把它们统一在一个抽象接口下）。这个抽象接口本身定义在同一个文件里：

```python
# vllm:vllm/v1/structured_output/backend_types.py:31-70（节选）
class StructuredOutputGrammar(ABC):
    """Request-level backend for structured output requests."""

    @abstractmethod
    def accept_tokens(self, request_id: str, tokens: list[int]) -> bool: ...

    @abstractmethod
    def validate_tokens(self, tokens: list[int]) -> list[int]: ...

    @abstractmethod
    def rollback(self, num_tokens: int) -> None: ...

    @abstractmethod
    def fill_bitmask(self, bitmask: "torch.Tensor", batch_index: int) -> None: ...
```

`fill_bitmask` 对应 `## 2.6`/`## 3.6` 讲的"填一行合法性掩码"；`accept_tokens`/`rollback` 是 `_lab/structured.py` 里 `generate()` 主循环隐式做的事（接受一个 token 之后推进状态、`## 4.4` 的 jump-forward 场景需要能回滚状态）在真实系统里被显式暴露成接口方法——`rollback` 存在的原因正是 `## 4.4` 的 jump-forward：一次性吐出一段字符串之后，如果这段字符串跟原本按 token 走的路径在某处对不上（真实分词器的切分可能跟语法期望的切分不完全一致），需要能回退到分叉点重新走，这是 `_lab/structured.py` 的玩具实现没有涉及、但真实系统必须处理的复杂度。

### 4.6 vLLM：编译缓存是 xgrammar 库自带的能力，用一个环境变量控制上限

vLLM 默认的结构化输出后端同样是 xgrammar，但它不像 SGLang 那样在自己的代码里维护一个 `Dict` 缓存，而是直接把缓存开关和容量上限交给 xgrammar 库自己的 `GrammarCompiler`：

```python
# vllm:vllm/v1/structured_output/backend_xgrammar.py:66-71
self.compiler = xgr.GrammarCompiler(
    tokenizer_info,
    max_threads=8,
    cache_enabled=True,
    cache_limit_bytes=vllm.envs.VLLM_XGRAMMAR_CACHE_MB * 1024 * 1024,
)
```

`cache_enabled=True` 打开的正是 `## 2.4`/`## 4.2` 讲的"同一个语法只编译一次"这条优化，`cache_limit_bytes` 给这份缓存设了一个按字节数算的硬上限（由环境变量 `VLLM_XGRAMMAR_CACHE_MB` 配置）——**这条细节印证了 `## 2.4` 那句"这张表在真实系统里不是可以忽略的常数"：如果编译缓存没有容量上限，一个会持续收到大量不同 schema（比如每个用户各自定义结构）的服务，缓存会无限增长直到吃光内存**，这不是危言耸听，是编译产物本身随语法复杂度和词表大小线性增长的直接后果。具体某种约束形式怎么被送进这个带缓存的编译器：

```python
# vllm:vllm/v1/structured_output/backend_xgrammar.py:79-96（节选）
def compile_grammar(
    self,
    request_type: StructuredOutputOptions,
    grammar_spec: str,
    stop_token_ids: set[int] | None = None,
) -> StructuredOutputGrammar:
    if request_type == StructuredOutputOptions.JSON:
        ctx = self.compiler.compile_json_schema(
            grammar_spec, any_whitespace=not self.disable_any_whitespace
        )
    elif request_type == StructuredOutputOptions.JSON_OBJECT:
        ctx = self.compiler.compile_json_schema(
            '{"type": "object"}', any_whitespace=not self.disable_any_whitespace
        )
    elif request_type == StructuredOutputOptions.GRAMMAR:
        ctx = self.compiler.compile_grammar(grammar_spec)
    elif request_type == StructuredOutputOptions.REGEX:
        ctx = compile_regex_with_timeout(
            self.compiler.compile_regex,
            grammar_spec,
        )
```

`compile_json_schema`/`compile_grammar`/`compile_regex` 三个独立的编译入口，分别对应 `## 4.5` 枚举里的三种核心约束形式——这跟 `_lab/structured.py` 只有一种写死的语法（`## 2.5` 的 `step_char`）形成的对照是：**真实系统的"语法"不是一份代码，是编译器的输入**，`_lab/structured.py` 相当于手写了一份已经编译好的语法（`step_char` 本身就是这份语法的直接实现），真实系统需要一层额外的编译器把 JSON Schema / 正则 / EBNF 这些**描述**转换成能在 `## 4.3` 那种匹配器里跑起来的自动机。

### 本篇对照没有覆盖到的东西

vLLM 除了 xgrammar 后端还挂了 `backend_guidance.py`（guidance 库）和 `backend_lm_format_enforcer.py`（lm-format-enforcer 库）两种可切换的后端、`backend_outlines.py`（早期默认后端），本篇只深入看了 xgrammar 这一条路径；SGLang 的 `llguidance_backend.py` 同样没有展开。**这不是因为它们不重要，是因为它们各自的编译器实现细节（不同的自动机表示、不同的批量 kernel 写法）需要单独一篇才能讲清楚，本篇的重点是"掩码是保证的来源"和"token 边界要在字符层面处理"这两条核心机制，这两条在所有后端上都成立，具体某个后端怎么把自动机编译得更快、批量 kernel 怎么写，属于 `[[05-量化]]`/`[[03-从玩具到生产还差什么]]` 讨论"从玩具到生产还差什么细节"的范畴，不属于本篇要讲的原理层面。**

## 5. 设计决策与代价（为什么这样 / 不这样会怎样 / 什么时候可以不这样）

**决策一：用掩码（提前限制候选集），不用"先生成再拒绝重试"。**
- 为什么这样：`## 2.1` 已经证明——掩码给出的是数学意义上的保证（非法值根本不在采样的定义域里），拒绝重试给出的是概率意义上的期望，没有终止保证。对外提供 API 承诺"输出一定合法"时，只有掩码这条路线站得住。
- 不这样会怎样：拒绝重试在合法输出概率高的场景下"看起来"也能用，但每次失败都要重新付出一整段生成的成本，而且这个成本在合法输出概率低的场景下（比如约束特别严苛、模型没见过类似格式）可能爆炸性增长；更麻烦的是它没有一个干净的"什么时候该放弃"的边界，工程上通常要另外加一个重试次数上限，而这个上限本身就是在承认"这条路线不保证成功"。
- 什么时候可以不这样：如果约束很宽松（比如只要求"输出看起来像一段话，不要求严格格式"）、且失败代价很低（前端能优雅降级），拒绝重试的实现成本远低于维护一整套语法编译器，这种场景下"先生成再校验"是合理的工程取舍——`## 4` 提到的这些引擎级别的语法后端，本身就是为"约束必须严格保证"这类场景存在的重型基础设施，杀鸡不必用它。

**决策二：要不要开 jump-forward。**
- 为什么开：`## 1` 的实测数字——200 条种子平均省 31% 的模型调用——在有大段确定性文本的语法里（固定字段名、固定分隔符）这不是小数目；`## 2.7` 讲过它的正确性是有保证的，跳过的步本来就没有第二个选择，不会改变最终产出。
- 不这样会怎样（关掉）：省不到这部分调用次数，但换来的是**每一步产出的 token 都真的经过了模型采样**，`logprob` 这类需要对齐"模型真的选过这个 token"的下游用途不会遇到 `## 2.7` 讲的口径差问题。
- 什么时候可以不开：任何需要精确 token 级 `logprob`（打分、强化学习里的重要性采样、跟训练时的 teacher forcing 对齐做逐 token 对比）的场景，jump-forward 跳过的那些步没有真实的模型 logprob 可用，这时候应该关掉——`## 4.5` vLLM 的 `StructuredOutputGrammar.rollback` 接口某种程度上就是在为"jump-forward 之后可能需要退回来重新走"这类精细场景兜底，但最干净的做法还是在明确需要精确 logprob 时直接不开这项优化。

**决策三：索引/编译什么时候做——请求到来时现编现用，还是提前批量编译好。**
- 为什么倾向"编译一次、缓存复用"（`## 2.4`/`## 4.2`/`## 4.6` 共同的做法）：编译成本是 O(状态数 × 词表大小 × token 长度) 量级，真实词表和 schema 复杂度下这个成本不小；同一个 schema 大概率会被多条请求复用（同一个 API 端点、同一份结构化输出格式）,缓存命中之后几乎是零成本。
- 不这样会怎样（每条请求都现编）：如果服务收到的 schema 五花八门、彼此互不重复，缓存命中率趋近于零，缓存本身反而变成一份纯粹的内存开销（存了一堆永远不会被再次命中的编译产物）——这时候"缓存"这个词已经名不副实，退化成了"每条请求各编各的，只是多占了内存"。
- 什么时候可以不建索引、不做编译（回到"现算合法性"）：约束足够简单、状态数极小（比如只是"从 5 个候选字符串里选一个"这种 `CHOICE` 类型），编译一整张状态表的固定开销可能比直接在生成时对候选逐个字符串匹配还大——`## 4.5` vLLM 单独给 `CHOICE` 留了一个枚举值，很可能就是因为这类极简单的约束不值得走一整套语法编译流程,用更直接的实现反而更划算（本篇没有深入 `CHOICE` 具体怎么实现，标注"未查证具体实现细节"）。

**决策四：文法规则写在字符层面，不写在 token 层面。**
- 为什么这样：`## 2.2`/`## 2.3` 已经用横跨边界的 token 证明了 token 层面根本无法独立定义合法性——除非退化成"对每个状态、每个 token 各自穷举一遍"，而那正是字符级规则加上 `step_token()` 在做的事，只是绕了个更直接的弯路。
- 不这样会怎样：如果试图直接手写"token 级规则表"（比如为每个状态手工列出这个状态下允许哪些 token），横跨边界的 token 极容易被漏掉——`## 6` 会把这个错误单独列成一条常见错误。
- 什么时候可以不这样：如果能够严格保证分词器的每个 token 都不会跨语法元素边界（比如约束场景本身就是字符级/字节级生成，不经过 BPE 这类会合并任意字节序列的分词器），token 边界和语法边界天然对齐,这时候直接在 token 层面写规则不会漏检——但这个前提在几乎所有真实 LLM 场景下都不成立，`## 2.2` 已经说过 BPE 合并跨语法元素边界是常态而非例外。

## 6. 常见错误与踩坑

**错误一：按 token 写合法性规则，而不是在字符层面写规则再逐字符走。**
`## 2.2`/`## 2.3` 已经讲过这条的机制。**错了会看到什么现象**：大部分时候看不出问题——因为大部分 token 不横跨语法边界，规则表对它们判断正确；只有当输出恰好用到了横跨边界的那个 token（比如本文的 `'":'`、`',"'`）时，规则表要么把它错误地标成非法（模型明明可以合法地用这个 token 收尾，却被强制拆成两步），要么错误地标成合法（在不该合法的状态下把它放行，生成出语法上不完整的字符串）。这类 bug 的隐蔽之处在于：**测试用例如果覆盖不到这些"巧合"token，可以在测试环境里长期不暴露**，直到线上遇到分词器切出这个具体切法才炸。

**错误二：空合法集合不报错，静默地继续跑下去。**
`## 2.6` 已经讲过这条的完整机制。**错了会看到什么现象**：不是异常，是 `softmax` 变成 `nan`、后续 `argmax` 或 `choice` 退化成某个默认值（往往是索引 0），模型开始吐出跟语法完全无关的内容，而**全程没有任何报错**——`test_empty_allowed_set_raises_loudly`（`_lab/tests/test_advanced.py:227-230`）是唯一能抓住这类错误的地方：如果 `apply_mask()` 里 `## 2.6` 那个 `if not allowed.any(): raise` 被删掉或者改成 `try/except` 悄悄吞掉，这条测试会立刻失败。

**错误三：忘了索引是"状态相关"的，把某个状态算出来的合法 token 集合当成全局通用的规则缓存。**
`## 2.3` 已经证明"同一个 token 换个状态就不合法"——如果实现里图省事,把第一次遇到某个 token 时算出来的"是否合法"结果直接缓存下来,下次遇到同一个 token（哪怕是在完全不同的语法状态下）直接复用这个缓存结果,就会在"这个 token 曾经在别的状态下合法"的场景下错误地放行。**错了会看到什么现象**：生成过程在某个特定的历史路径下突然吐出一个语法上说不通的 token,而且这个 bug 极难复现——它只在"曾经处于过让这个 token 合法的状态、后来又转移到了让它非法的状态"这种特定的历史序列下才会触发,单独测试某个状态本身完全正常。`## 3.6` 强调过 `build_index()` 返回的字典键是**状态**而不是 token,正是为了从数据结构层面杜绝这类缓存串味的可能性。

**错误四：以为把要求写进 prompt 就能保证格式合法。**
`## 0`/`## 2.1` 已经讲过这条的完整论证——prompt 只能改变分布形状,不能给分布的支撑集设边界,只要非法输出的概率不严格为零,总有一天会撞上它。**错了会看到什么现象**：开发和测试阶段几乎全部正常(模型在大多数输入上确实倾向于遵守 prompt 里的格式要求),上线之后在某个边缘输入、某次采样的巧合下突然吐出一段多余的解释文字或者不闭合的 JSON,下游 `json.loads()` 直接抛异常——**这类故障的典型特征是"复现率极低、报告频率却不为零"**,排查时如果只盯着 prompt 措辞改来改去,永远堵不住这个口子,因为问题根本不在 prompt 措辞,在于这条路线从数学上就没有给出保证。

**错误五（`## 2.8` 的坑，值得单独再列一条）：在一个支持"跳步"的生成循环里，用一个从头到尾共享的有状态随机数生成器。**
**错了会看到什么现象**：单独跑"不开跳步优化"的版本完全正常、可复现；一旦打开跳步优化，产出的文本和调用次数都跟预期的"应该完全一致，只是少几次调用"对不上——更具体地说，`## 2.8` 描述过的现象是**调用次数反而会变多**，这个反直觉的结果往往会让人误以为是跳步逻辑本身写错了、去检查 `forced_token()` 的判据，而真正的问题出在随机数生成器的调用序列错位上，跟跳步逻辑本身是否正确毫无关系——这是这类 bug 特别容易把人带偏排查方向的地方。

**错误六：确定性哈希用了 Python 内置的 `hash()`，而不是 `zlib.crc32` 这类不加盐的哈希函数。**
`## 2.8`/`## 3.9` 已经讲过原理。**错了会看到什么现象**：同一次 Python 进程运行内,"同 seed 复现同轨迹"完全成立,自己测试的时候怎么跑都对得上；一旦换一个进程重新运行（哪怕是同一台机器上重新执行一次 `python xxx.py`），同样的 seed 给出不同的结果——这类 bug 极难在本地开发时发现,因为本地反复调试往往就在同一个进程里跑来跑去,只有在"两次独立运行需要产出一致结果"这个要求被真正测试到时（比如 CI 里两次独立进程运行同一个种子做对比）才会暴露。
