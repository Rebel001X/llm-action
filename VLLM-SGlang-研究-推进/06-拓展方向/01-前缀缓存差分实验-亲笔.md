# 06-01 · 前缀缓存差分实验（亲笔）

## 0. 结论先行

四条，按可信度排序：

1. **在共享前缀充裕、容量充裕的工作负载上，两家的命中率几乎完全一样**（差 0.00–0.01 个百分点）。
   "块哈希表 vs 基数树"这个被讲了很久的分类，**在命中率这个指标上几乎不产生差异**。
2. **唯一可测的匹配差异，只出现在共享前缀长度不是 block_size 整数倍时** —— 本实验里 0.91 个百分点。
   而且 **vLLM 自己就有旋钮能把它抹平**：把 hash 单元调到 1，差距归零。
3. **容量吃紧时的差异来自驱逐，不来自匹配** —— 而且方向和我预期的相反：
   在最紧的容量下 **vLLM 反而略胜 0.56 个百分点**。
4. **我第一版实验得出了完全相反的结论，那是我建模错了。** 详见 `## 7`。

**这四条都不涉及"谁更快"。** 本实验没有显存、没有 kernel、没有拷贝，
它只回答"同一条 token 序列进来，谁能命中多少、谁被淘汰"。

## 3. 实验设计

**自变量**只有一个真正重要：**共享前缀的形态**。围绕它造了五种工作负载：

| 工作负载 | 构造 | 对应现实 |
|---|---|---|
| `shared_system` | 512 token 完全共享的 system prompt + 短问题 | 企业内部对话服务 |
| `misaligned_share` | **517** token 共享前缀（**故意不是 16 的倍数**） | 同上，但模板长度没对齐 |
| `tree_branch` | 128 根 + 4 选 1 中段 + 随机尾 | Agent / 搜索 / best-of-k |
| `no_share` | 每条全随机 | 对照组，前缀缓存应当零收益 |
| `hot_cold` | 1/3 命中热前缀 + 2/3 冷流量冲刷 | 真实线上流量 |

**四个对照臂**（这是本实验设计上最关键的部分）：

- **vLLM 真实** —— `evict="freequeue"`，按上表建模；
- **稻草人 FIFO** —— `evict="insert_fifo"`，按首次插入排序、命中不改顺序。
  **这不是 vLLM 的行为**，保留它只为量化"把 vLLM 误建模会高估多少"；
- **vLLM + LRU** —— 只把驱逐换成按最近访问，匹配完全不动。
  它与"vLLM 真实"的差 = **驱逐策略贡献**；它与 SGLang 的差 = **匹配方式贡献**；
- **SGLang** —— 基数树 + 叶子 LRU。

有了第三臂，"总差"才能被拆成"驱逐贡献 + 匹配贡献"，而不是笼统地说"SGLang 更好"。

## 4. 结果

```

misaligned_share      16    1   16    65536   0.9223     0.9223    0.9223  0.9314    0.91     0.00     0.91
misaligned_share      16    1    4    65536   0.9295     0.9295    0.9295  0.9314    0.19     0.00     0.19
misaligned_share      16    1    1    65536   0.9314     0.9314    0.9314  0.9314    0.00     0.00     0.00
shared_system         16    1   16    65536   0.9307     0.9307    0.9307  0.9308    0.01     0.00     0.01
shared_system         16   16   16    65536   0.9307     0.9307    0.9307  0.9307    0.00     0.00     0.00
tree_branch           16    1   16    65536   0.8842     0.8842    0.8842  0.8842    0.01     0.00     0.01
no_share              16    1   16    65536   0.0000     0.0000    0.0000  0.0000    0.00     0.00     0.00
hot_cold              16    1   16    16384   0.2986     0.2740    0.2986  0.2986    0.00     0.00     0.00
hot_cold              16    1   16     4096   0.2765     0.1838    0.2709  0.2709   -0.56    -0.56     0.00
```

逐条读：

**① 共享前缀充裕时，两家几乎没区别。**
`shared_system` 与 `tree_branch` 上总差 0.00–0.01 个百分点。
`shared_system` 的共享段是 512 token，恰好是 16 的整数倍，块粒度不吃亏；
`tree_branch` 的 128 与 96 同样对齐。**现实中的模板长度当然不会总是对齐**，这引出第②条。

**② 不对齐时，匹配方式的差异才现身 —— 但很小，且 vLLM 自己能补。**
`misaligned_share` 的共享前缀是 517 token。块粒度只能命中 512，
每条请求白丢 5 个 token，累计成 0.91 个百分点。
把 vLLM 的 hash 单元从 16 调到 4，差距降到 0.19；调到 1，**完全归零**。
代价在 `## 5` 讲。

**③ 容量吃紧时，差异全部来自驱逐，且方向和直觉相反。**
`hot_cold` @16K：两家命中率**一模一样**（0.2986）。
`hot_cold` @4K：**vLLM 真实 0.2765 反而高于 SGLang 的 0.2709**。
而"vLLM + LRU"对照臂是 0.2709，与 SGLang 分毫不差 ——
这说明 **SGLang 的叶子 LRU 与朴素 LRU 在这个负载上等价**，
而 **vLLM 的策略比朴素 LRU 更强**。为什么？见 `## 7` 第 2 条。

**④ 无共享前缀时两家都是 0。** 这是模拟器的健全性检查：
如果这一格不是 0，说明模拟器在自己制造命中。

## 5. 设计决策与代价

### 决策一 · vLLM 用链式块哈希，而不是树

- **为什么这么设计**：`hash((parent, tokens))` 让"查一个块"退化成一次字典查询，
  O(1)，且天然是内容寻址 —— 不同请求只要前缀字节相同就落到同一个 key，不需要维护任何树结构。
- **不这样会怎样**：就得维护一棵树，插入要分裂、驱逐要维护父子关系。
  本实验里 SGLang 侧在 `misaligned_share` 上发生了 **15 次节点分裂**，
  在 `hot_cold` @4K 上 13 次 —— 这些是基数树独有的、块哈希表完全没有的维护动作。
- **什么时候可以不这样**：当你需要**任意长度**前缀命中、且共享前缀长度天然不对齐时。
  但要注意第②条已经证明：vLLM 用细粒度 hash 就能达到同样效果，未必要换数据结构。

### 决策二 · 细粒度 hash 单元：用查询次数换命中率

- **为什么**：把 hash 单元从 block_size 调小，就能在最后一个不满块内部回探，补回不对齐的尾巴。
- **不这样会怎样**：共享前缀不对齐时，每条请求白丢最多 `block_size - 1` 个 token。
- **什么时候可以不这样**：**代价是查询次数。** 本实验 `misaligned_share` 上：
  hash 单元 16 → 6,556 次查表；单元 4 → 7,156 次（+9%）；单元 1 → **8,739 次（+33%）**。
  换来的是 0.91 个百分点的命中率。
  **共享前缀本来就对齐的场景（512、1024 这种模板长度），这 33% 是纯亏。**

### 决策三 · vLLM 释放块时把列表倒序

- **为什么**：尾部的块是这条请求特有的、最不可能被别人共享的；
  倒序追加让它们排在驱逐队列更靠前的位置，先死。
- **不这样会怎样**：按正序释放，靠前的（最可能被共享的）块反而排在前面等着被驱逐。
- **什么时候可以不这样**：当请求之间几乎无共享（`no_share` 那种），
  谁先死都一样，这个排序纯属做无用功。

### 决策四 · SGLang 的 page_size

- **为什么**：page_size > 1 时按页对齐，可以让 KV 的物理布局按页连续，利于 kernel 访存。
- **不这样会怎样**：page_size=1 才是真 token 粒度，但每个 token 一个槽位。
- **什么时候可以不这样**：**注意本实验第 5 行** —— page_size 拉到 16 之后，
  SGLang 的命中率与 vLLM 完全相同（0.9307）。
  **"基数树 = token 粒度"是错的：粒度来自 page_size，不来自树。**

## 6. 同位对照：这个实验能替代什么、不能替代什么

**能替代的**：过去只能定性讨论的"块 vs 树"取舍，现在有了同 trace 下的数字，
而且是可复算的（同 seed 逐位可复现，`_lab/tests/test_lab.py` 里有回归测试锁着）。

**不能替代的**（必须说清楚，否则这篇就成了它自己批判的那种东西）：

- **不能回答"谁更快"。** 没有显存、没有 kernel、没有 H2D 拷贝、没有并发。
  命中率相同不代表吞吐相同 —— 树的指针追逐与哈希表的随机访问对 CPU 缓存完全不同，
  这一层本实验完全没建模。
- **不能回答"生产上谁的命中率更高"。** 我的五种工作负载是构造的，不是采样的真实流量。
  真实流量的共享前缀分布、到达顺序、请求生命周期重叠，都会改变结论。
- **不能覆盖 lock_ref / 在跑请求的保护。** 模拟器把请求当作原子处理，
  没有"多个请求同时在跑、各自锁住一段前缀"这个真实情形。
  这会低估 SGLang `lock_ref` 机制的价值。

## 7. 踩坑与反直觉

### 坑一 · 我第一版实验的结论是完全错的，错在把 vLLM 建模成了 FIFO

第一版我读到 `vllm/v1/core/block_pool.py:737` 的注释 "FIFO reuse of cached blocks"，
就把 vLLM 的驱逐建成了"按首次插入排序的 FIFO"。跑出来的结果是：

> `hot_cold` @4K：vLLM 0.1838，SGLang 0.2709 —— **SGLang 领先 8.72 个百分点**。

看着像个很有价值的发现，我差点就写进结论了。

真相是那句注释的后半截：**"for LRU eviction behavior"**。
`touch()`（`vllm/v1/core/block_pool.py:702`）在命中时把块从空闲队列**摘掉**
（`:714` 的 `self.free_block_queue.remove(block)`），释放时再追加到队尾。
所以队列顺序是**按最近一次释放**，而不是按首次插入 —— 它本来就是 LRU 的一种实现，
"FIFO" 说的是队列这个数据结构的用法，不是淘汰策略的语义。

改对之后：vLLM 0.2765，SGLang 0.2709，**vLLM 反而略胜**。
**我的建模误差是 9.27 个百分点，比我原本想报告的"发现"还大。**

这个稻草人臂我**故意留在代码里**（`evict="insert_fifo"`），
并在 `_lab/tests/test_lab.py` 里用一条构造 trace 钉死了真实策略必须优于它 ——
让这个错误以后不可能被悄悄改回来。

### 坑二 · vLLM 的驱逐不只是"近似 LRU"，它比 LRU 更强

对照臂里"vLLM + 纯 LRU"是 0.2709，而 vLLM 真实策略是 0.2765。
差的这 0.56 个百分点来自**倒序释放**：它编码了一条 LRU 不知道的先验 ——
**同一条请求里，越靠后的块越不可能被别人共享**。
纯 LRU 只看时间，看不到这个结构信息。

所以把 vLLM 的驱逐描述成"LRU 的廉价近似"是**低估**了它。
它是"LRU + 请求内位置先验"，在共享前缀主导的负载上比纯 LRU 更好。

### 坑三 · "基数树天然 token 粒度"是个流传很广的错觉

`RadixKey.match` 的 docstring 白纸黑字写着
"Result is rounded down to `page_size`"（`sglang:python/sglang/srt/mem_cache/radix_cache.py:181`）。
page_size=16 时，基数树和块哈希表的命中粒度**完全一样**（本实验第 5 行，两边都是 0.9307）。
粒度是 page_size 决定的，跟用不用树没关系。

### 坑四 · 两边的"操作次数"不可直接比

我在产物里同时记了 vLLM 的 `lookups` 和 SGLang 的 `descends`/`splits`，
但**它们不是同一种东西**：一次哈希查表和一次树节点下行的开销完全不同。
`misaligned_share` 上 vLLM 6,556 次查表 vs SGLang 213 次下行 ——
**不能据此说"SGLang 少做 30 倍工作"**。要比这个得测真实耗时，而本机做不到。
这一栏只能用来看**同一引擎在不同配置下的相对变化**（比如 hash 单元 16→1 让查询涨 33%）。

## 8. 可改进点

1. **给 vLLM 提一个"共享前缀对齐度"指标**。第②条说明：
   模板长度是不是 block_size 的整数倍，直接决定要不要开细粒度 hash。
   现在用户没有任何办法知道自己的流量对齐得好不好。
   一个 `prefix_alignment_waste_tokens` 计数器就够了，A 档难度。
2. **把细粒度 hash 的开关做成自适应**。现在 `prefix_match_unit` 是静态配置。
   既然对齐度可测，就可以在对齐良好时自动退回块粒度，省掉那 33% 的查询。
   需要设计讨论，B 档。
3. **SGLang 的 page_size 文档应当明说它决定命中粒度**。
   坑三那个错觉很大程度上是文档没讲清造成的。
4. **把这个差分模拟器扩成两家的共享回归测试**。
   两个引擎都在改前缀缓存，但没有任何跨引擎的行为一致性检查。
   一套公共 trace + 期望命中数，能当"策略回归"的护栏 —— 见 [[05-拓展优先级-亲笔]]。
