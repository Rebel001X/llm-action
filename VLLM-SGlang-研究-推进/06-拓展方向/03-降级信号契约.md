# 06-03 · 降级信号契约

> **本篇取证基准**：`vllm` @ `7ca49fbe`（2026-08-22）；跨引擎引用带 `sglang:` 前缀，SGLang 快照见 `_lab/out/repo_stats.json`。
> **一句话**：把"我要的东西没给成"从只能读日志，变成可编程发现。

## 0. 结论先行

[[03-跨引擎共性缺口]] 的缺口①已经证明：CUDA Graph 掉回 eager、配置被无条件覆盖、招牌特性零调用点、KV 传输判死、观测两极分化——这些看起来分散在不同子系统的问题，本质是同一件事的不同变形：**引擎决定"不给你你要的东西"这个瞬间，没有一条统一的、可编程发现的信号通路**。用户能看见的只有日志（如果恰好打了的话），而日志既不是稳定标识、也不能被程序订阅、还默认关着。

本篇不再重复举证"这是共性"——那件事 `03-跨引擎共性缺口` 已经做完，本篇要做的是**把这条共性缺口从"发现问题"推进到"能实施的设计"**。核心结论四条：

1. **"降级"不是一件事，是五件不同的事**（`## 1` 展开的 A-E 分类），每一类"该不该报警"的答案都不一样——把它们塞进同一套报警策略，要么吵得没法用，要么漏掉真正致命的那类。
2. **今天两家引擎在"发生了什么"和"发生了没有"之间几乎只有日志一层**——`## 2` 的矩阵显示，metrics/响应字段/专用端点这三种更适合被程序消费的出口，目前没有一格被降级事件占用；两家却都已经有能力相当的**同类基础设施**（Prometheus 计数器、KV 事件发布/订阅）在服务别的目的。
3. **契约本身要分两档默认值，不能一刀切**（`## 3`/`## 5` 详细论证）：便宜到可以忽略开销的"发生过没有"用计数器，默认开；带内容、带 IPC、带序列化成本的"发生了什么/为什么"，默认关，和 vLLM 现有的 `--cudagraph-metrics`、`enable_kv_cache_events` 保持同一条默认值哲学。
4. **上游没做这件事，不是没想到**——`## 5` 给出至少三条真实、可反驳的理由：热路径埋点的真实开销、枚举一旦公开就是要长期维护的 API 表面、跨进程/跨语言回传的工程成本。本篇的落地方案（`## 8`）刻意从成本最低的一档开始，不要求一次性解决全部三条阻力。

**边界声明**：本篇提出的类型名、字段名、契约形状全部是**本库的设计提议**，不是上游 vLLM/SGLang 已经存在或计划实现的 API——正文里任何 Python 代码块只要不是直接引自 `_src/` 的真实文件，一律在块内注明"本库提议"。

## 1. 它在系统里的位置

本篇坐标：`06-拓展方向/` 目录第三篇，直接展开 [[03-跨引擎共性缺口]] `## 8` 缺口①（静默降级）与缺口⑤（观测两极分化）——那篇给出的判断是"这两条建议合并成一个改进项目一起推进"（该篇 `## 8` 优先级表原话），本篇就是那个合并后的项目。原材料另外来自 [[01-vLLM可改进点]] `## 8.1`-`## 8.3`（鉴权、CUDA Graph、配置覆盖三条）与 [[02-SGLang可改进点]] 里约束解码/PD 分离相关的可改进点，以及 [[06-vLLM-模型执行与CUDA-Graph]]、[[06-SGLang-约束解码与语法后端]] 两篇精读正文的原始证据。

**和 `03-跨引擎共性缺口` 的分工边界**：那篇回答"这是不是共性、有多普遍"，用的是横向证据（12 个引擎各找几个例子）；本篇回答"如果要修，修成什么样"，用的是纵向深挖（把 vLLM/SGLang 两家的证据链走到底，给出一个可以写进 RFC 的具体形状）。本篇不重新论证"这是共性"，直接引用该篇 `## 8` 缺口①②⑤ 的结论作为前提。

### 1.1 先把"降级"拆成五个互斥的桶

任务书给出的分类框架，本篇复核后保留，因为五个桶在"该不该报警"这件事上给出的答案确实互斥：

| 类别 | 定义 | 真实例子（源码为证） | 该不该报警 |
|---|---|---|---|
| **A 静默 fallback** | 走了另一条更慢/更弱的路径，用户无感 | vLLM CUDA Graph → eager，`vllm:vllm/compilation/cuda_graph.py:244-254` | **应该**——用户显式要的能力（`cudagraph_mode=FULL`）在运行时被换成另一条路径，触发条件（cascade attention、encoder 输出）是确定性的，可以标注 |
| **B 配置被覆盖** | 用户设了 X，引擎改成 Y | `enforce_eager=True` 清空 `compilation_config.mode`（有 `warning_once`，`vllm:vllm/config/vllm.py:1387-1393`）；贪心采样清空 `top_p`/`top_k`/`min_p`（零日志，`vllm:vllm/sampling_params.py:529-534`） | **要看粒度**——启动期/全局配置覆盖一次性发生，打日志成本几乎为零，应该做；请求级覆盖（`SamplingParams`）如果每个请求都打日志，高 QPS 下自己就是噪音源，更适合做成响应里的可选字段 |
| **C 功能未生效** | 开关存在、代码存在，但从没被调用 | SGLang jump-forward 四后端全实现、调度器零调用点，`sglang:python/sglang/srt/constrained/outlines_backend.py:157` | **不该**塞进运行时契约——这是一个**静态**属性（这段代码从不随请求变化），不需要每次请求都发一个事件；`03-跨引擎共性缺口` `## 8` 缺口②已经给出正确的应对方式（CI 阶段的"可达性测试"），本篇 `## 3.4` 会说明为什么故意不把它纳入本契约 |
| **D 能力不支持** | 请求了引擎做不到的组合，被静默忽略或降级 | LMDeploy `QuantPolicy.TURBO_QUANT = 42`（`lmdeploy:lmdeploy/messages.py:27`）被 `TurbomindEngineConfig.__post_init__` 放行（`lmdeploy:lmdeploy/messages.py:351-358`），但 `src/turbomind/` 全目录零实现 | **应该，且比 A 更紧迫**——用户传了一个具体、有名字的能力请求，配置层甚至没有拒绝它；A 至少可能被"变慢了"这种自然信号泄漏出来，D 是纯语义错误，没有任何自然信号会让用户怀疑 |
| **E 资源性降级** | 抢占/回退/KV 传输失败 | vLLM 抢占计数器已存在（`vllm:vllm/v1/metrics/loggers.py:661-667`）；SGLang 回退/PD 传输失败计数器已存在（`sglang:python/sglang/srt/observability/metrics_collector.py:456-461,528-534`）；KV 加载失败默认判死（`vllm:vllm/config/kv_transfer.py:69`） | **全局聚合层面不是缺口**——两家都已经做了；真正的窟窿在**请求级归因**：一个被抢占/被判死的具体 `request_id`，它自己能不能拿到一个机器可读的原因码，区分"KV 传输失败"和"模型抛异常"和"客户端断连"？本篇没有在响应协议里找到这类字段 |

**C 类被排除在契约之外**这件事本身值得强调——不是遗漏，是判断"运行时事件流"这个工具形状不适合它。这个判断在 `## 3.4` 单独论证。

### 1.2 一个横跨 A/D 两类的边界案例

`## 1.1` 的表格把五类分开讨论，是为了让"该不该报警"这件事有清晰答案，但至少有一个真实例子提醒我们**真实代码不总是配合这种分类**。

`dispatch_cudagraph()`（`vllm:vllm/v1/worker/gpu_model_runner.py:4105`）在检测到 cascade attention 或有 encoder 输出时传入 `disable_full=True`，让本步放弃 FULL 图——这一个动作同时符合两类判断标准：

- **按 A 类看**：用户配置了 `cudagraph_mode=FULL`，实际这一步走的是弱化路径，触发点和 `## 2` 已核实的 `vllm:vllm/compilation/cuda_graph.py:244-254` 是同一条静默降级链路的上游。
- **按 D 类看**：cascade attention（长共享前缀命中）和"FULL 图"这两个能力，引擎目前做不到同时满足，只能二选一——这正是 D 类定义"请求了引擎做不到的组合"的字面意思。

区分它到底属于哪一类不是学术意义上的分类癖好——`## 1.1` 给 A 类和 D 类分别给出的"该报警"理由并不相同（A 类是"路径被静默换掉"，D 类是"配置层没有拒绝一个做不到的组合"）。这个边界例子同时踩中两条理由，说明**契约不该强迫每个触发点只归一类**：`## 3.5` 的 `DegradationEvent.cls` 字段允许同一个 `reason` 在文档里同时标注"也符合 D 类判断标准"，消费者按自己关心的维度过滤即可，不需要本篇替每一个真实触发点做一次非黑即白的裁决。

### 1.3 五类之间怎么排优先级

`03-跨引擎共性缺口` `## 8` 给六条共性缺口排过序，判据是"触发条件"（要不要用户先做点什么特殊操作）和"改进成本"两个维度。本篇的 A-E 五类（把 B/E 各自拆成全局/请求级两档，呼应 `## 1.1` 的判断）可以套用同一对判据：

| 类别 | 触发条件 | 改进成本（对照 `## 8` 三阶段） | 本篇判断的优先级 |
|---|---|---|---|
| A 静默 fallback | 中——需要撞上特定配置组合（cascade attention 等） | 低（第一阶段） | 高——`## 4` 已给出完整走读，试点成本最低 |
| B 配置覆盖（全局） | 低——多数用户会在启动期就触发（如 `enforce_eager`） | 低（第一阶段） | 高——已有 `warning_once` 先例，只差接上 Counter |
| B 配置覆盖（请求级） | 高——需要特定采样参数组合 | 中（第二阶段） | 中——影响面随 API 使用方式变化 |
| D 能力不支持 | 低——只要传了一个具体的、不受支持的枚举值就触发 | 未详细设计 | 高但**未纳入落地路线图**——`## 2.1` 已承认 vLLM/SGLang 两家的 D 类证据不足，`## 8` 没有为它单独排阶段 |
| E 资源性降级（全局） | 低——生产环境几乎必然发生抢占/回退 | 已完成（两家都有） | 不需要再投入——`## 7` 第 1 条已论证 |
| E 资源性降级（请求级） | 中——只在 PD 分离等特定部署下触发 | 高（第三阶段） | 中——`## 8` 第三阶段已覆盖，但改动量级最大 |

这张表和 `## 8` 三阶段路线图对得上：A 类和 B 类（全局）进第一阶段，是因为它们同时满足"触发门槛不高"和"改进成本低"。D 类虽然优先级判断上"高"，但本篇没有把它纳入任何一个阶段——不是判断它不重要，是**证据不够扎实、不敢排进施工计划**，这条留给未来的续写或 [[04-可落地贡献清单]] 补齐。

### 2.1 暴露方式矩阵

`✓ + 具体方式` 表示本篇找到了直接证据；`未查证` 表示本篇没有为这个格子单独取证，不代表这个引擎在这一类上没有信号——这条区分沿用 `03-跨引擎共性缺口` `## 2` 的诚实标准。

| 引擎 | A 静默 fallback | B 配置覆盖 | C 功能未生效 | D 能力不支持 | E 资源性降级（全局） | E 资源性降级（请求级归因） |
|---|---|---|---|---|---|---|
| vLLM | 日志（`--cudagraph-metrics` 默认关）| 日志(全局,有)／无(请求级,`vllm/sampling_params.py:529`) | 无 | 未查证 | **metrics**(`num_preemptions`) | 无 |
| SGLang | 日志（同文件内不一致，`sglang:python/sglang/srt/server_args.py:4649` vs `:6009`）| 同左 | 无 | 未查证 | **metrics**(`num_retracted_reqs`/`num_bootstrap_failed_reqs`) | 无 |

**没有一格是"metrics/响应字段/专用端点"用于 A/B/C/D 类降级事件本身**——这四家里能查到的"专用端点"（SGLang `/server_info`）和"响应字段"（vLLM `kv_transfer_params`）都是为别的目的建的，唯二两处**降级相关**的 metrics 命中（vLLM `num_preemptions`、SGLang 三个失败计数器）全部落在 **E 类的全局聚合**，没有一个具体请求能从自己的响应里读到"我这次被抢占了/被判死了"。这两条观察合在一起，就是 `## 0` 结论 2 的证据。

## 3. 契约的形式化

### 3.1 为什么是"契约"而不是"再加几个 Counter"

`03-跨引擎共性缺口` `## 8` 缺口①给出的改进方向已经提到"把降级事件从日志升级成计数器"，本篇要做的不是重复这句话，而是回答三个那篇没展开的问题：**用什么标识一个降级事件**（不能是自由文本，见 `## 3.2`）、**这个事件属于谁**（全局还是某个 `request_id`，见 `## 3.2`）、**默认该开多少**（不是全开也不是全关，见 `## 3.3`）。这三个问题任何一个答不清楚，"加计数器"就会变成又一批各写各的、无法跨引擎对比、甚至无法跨版本兼容的散装信号——正是 `03-跨引擎共性缺口` `## 3` 形状一描述的那种"三段式"重复出现的根源。

### 3.2 契约的四个要素

**要素一：稳定标识（枚举，不是自由文本）。** 一个降级事件必须有一个不随日志措辞变化的 ID。vLLM 现有的 `logger.warning_once` 传的是一整句英文话（`vllm:vllm/config/vllm.py:1388-1390` 那句 "Enforce eager set, disabling torch.compile and CUDAGraphs..."），下游想按"这类事件发生了几次"做统计，只能用字符串匹配去解析日志文本——这本身就是不稳定契约的反面教材：日志文案改一个词，下游的解析脚本就断。

**要素二：归属（全局的还是某条请求的）。** `## 1` 的分类已经暗示了这一点：A/C 类多数是**全局**属性（这个 worker 进程接下来一段时间都会走 eager，不是"这一个请求"的属性）；B/D/E 类里至少有一部分是**请求级**的（贪心采样覆盖、KV 传输失败），必须能回到具体的 `request_id`，否则运维只能知道"发生过"，定位不到"是谁的请求受影响"。

**要素三：可编程出口。** 至少三种形状，对应不同的成本与延迟特征：
- **metrics counter**——一次原子自增，按 `reason` 打标签，复用现有 `/metrics` 端点；只能回答"发生了多少次"，回答不了"是哪个请求"。
- **响应里的可选字段**——只有 `scope="request"` 的事件才有意义，成本是每个响应多几十字节的序列化开销；`vllm:vllm/entrypoints/openai/chat_completion/protocol.py:480-483` 的 `kv_transfer_params` 已经是这个形状的先例。
- **事件流**——每个事件独立发布，可以带任意详情（`batch_descriptor`、触发条件），成本最高（消息总线、跨进程 IPC）；vLLM 的 `vllm:vllm/distributed/kv_events.py` 和 SGLang 的 `sglang:python/sglang/srt/server_args.py:1665-1669`（`kv_events_config`）已经是这个形状的两个独立先例，`## 6` 详细展开。

**要素四：默认行为。** 见 `## 3.3`，独立成节因为这条最容易被简化成"全开"或"全关"，两者都错。

### 3.3 默认行为：分两档，不是全开也不是全关

这是任务书要求"认真论证"的一条，先给结论：**"发生了没有/发生了多少次"这一档默认开，"发生了什么/为什么/带什么上下文"这一档默认关。**

论证不是凭空定的，是从已有先例反推的：

- vLLM 现有的 `num_preemptions`（`vllm:vllm/v1/metrics/loggers.py:661-667`）、`prefix_cache_hits`（`vllm:vllm/v1/metrics/loggers.py:595-601`）都是**默认开**的 Counter/Gauge——它们证明"一个原子自增 + 一个已经在运行的 Prometheus 抓取循环"这个组合的边际成本低到从来没有人认为需要一个开关去关掉它。
- vLLM 现有的 `cudagraph_metrics`（`vllm:vllm/config/observability.py:68`）、`enable_kv_cache_events`（`vllm:vllm/config/kv_events.py:14`），以及 SGLang 独立收敛到的 `kv_events_config`（`sglang:python/sglang/srt/server_args.py:1665-1669`，默认 `None`）都是**默认关**的——这三个开关的共同点是：打开后要么构造额外的统计结构（`CUDAGraphStat`，`vllm:vllm/v1/worker/gpu_model_runner.py:4147-4154`，`06-vLLM-模型执行与CUDA-Graph` `## 7` 已指出），要么起一整条 ZMQ 发布线程（`vllm:vllm/distributed/kv_events.py` 的 `queue.Queue` + `threading.Thread`），成本不是一次原子自增能比的。

两组先例已经在"该开的开、该关的关"这件事上给出了一致的判断，本契约的两档默认值就是把这个已经存在的判断**显式地、一致地**应用到降级事件这个新维度上，不是发明新哲学：

| 出口 | 成本量级 | 默认值 | 理由 |
|---|---|---|---|
| Counter（`reason` 标签，无详情） | 一次原子自增，与现有 `num_preemptions` 同量级 | **默认开** | 成本可忽略，且这正是当前唯一完全空缺的一格（`## 2.1` 矩阵） |
| 响应字段（仅 `scope="request"`） | 每响应几十字节序列化 | **默认关**，按端点/客户端可选开启 | 并非所有客户端都需要，默认开会让所有现有集成的响应体积悄悄变化——这是一次隐性的协议变更 |
| 事件流（带 `detail`） | 消息总线 + 序列化 + 跨进程 IPC | **默认关**，与 `enable_kv_cache_events` 同一开关哲学 | 与现有两个同类机制保持一致，运维已经熟悉"要看详情就单独开一条流"这套心智模型 |

**什么时候可以不这样**：如果一个具体的降级类别被证明触发频率极低（比如 D 类里"配置层放行了根本不存在的能力"这种，正常运行中一旦被踩到就应该是个位数级别的事件），响应字段这一档也可以论证默认开——因为触发频率低，序列化开销的总量本身就可以忽略；这属于"个例例外"，不属于契约本身的默认值，`## 8` 第二阶段会展开这个判断怎么落地。

### 3.4 为什么 C 类（功能未生效）被排除在契约之外

`## 1` 表格已经给出结论，这里补完论证：本契约的四个要素里，"归属"（要素二）预设了一个前提——降级事件是**随时间发生的**，有一个明确的触发时刻（这一步、这个请求、这次调用）。C 类恰恰不满足这个前提：`jump_forward_map = None`（`sglang:python/sglang/srt/constrained/outlines_backend.py:157`）不是"在某次请求处理时被触发的降级"，它是这份代码从编译/加载的那一刻起就恒定为真的属性，不随请求变化，也不需要每次调度都重新判断一遍。给一个静态属性配一个运行时事件契约，等于每次都发布同一个事件——这不是浪费资源的问题，是**契约用错了工具**：静态可达性问题该用静态分析（`03-跨引擎共性缺口` `## 8` 缺口②提议的"可达性测试"，遍历声明的接口成员断言存在可达路径）解决，用运行时信号解决只会把一个 CI 阶段就能抓到的问题，拖到线上才被某个不走运的用户撞见。

### 3.5 示意性接口定义（本库提议，非上游 API）

```python
# ⚠️ 以下全部是本库的设计提议，vLLM/SGLang 当前均不存在这套 API。
# 命名风格参照 vllm/distributed/kv_events.py 的既有约定（本篇 ## 2 已核实该文件存在）。

from dataclasses import dataclass, field
from enum import Enum
from typing import Any


class DegradationClass(str, Enum):
    """对应 `## 1` 的 A/B/D/E 四类——C 类（功能未生效）不进这个枚举，
    理由见 `## 3.4`：那是静态可达性问题，不是运行时事件。"""
    SILENT_FALLBACK = "silent_fallback"       # A
    CONFIG_OVERRIDDEN = "config_overridden"   # B
    CAPABILITY_UNSUPPORTED = "capability_unsupported"  # D
    RESOURCE_DEGRADED = "resource_degraded"   # E


class DegradationReason(str, Enum):
    """稳定标识——蛇形命名、一旦发布视为长期 API 承诺（`## 4` 论证之一）。
    每个取值对应 `## 2` 证据地图里的一行真实代码。"""
    CUDAGRAPH_FALLBACK_MODE_MISMATCH = "cudagraph.fallback.mode_mismatch"
    SAMPLING_GREEDY_OVERRIDE = "sampling.greedy_override"
    KV_LOAD_FAILED_NO_RECOMPUTE = "kv_transfer.load_failed.no_recompute"
    QUANT_POLICY_UNIMPLEMENTED = "capability.quant_policy_unimplemented"


@dataclass(frozen=True)
class DegradationEvent:
    reason: DegradationReason
    cls: DegradationClass
    scope: str  # "global" | "request" —— `## 3.2` 要素二
    request_id: str | None = None  # scope == "request" 时必须非空
    # detail 允许携带 batch_descriptor 之类的上下文，但**不参与**稳定标识，
    # 消费者不应该依赖 detail 的字段名/结构长期不变（`## 4` 论证之二）。
    detail: dict[str, Any] = field(default_factory=dict)
    ts: float = 0.0


class DegradationSink:
    """出口的最小接口，`## 3.2` 要素三三种形状各实现一个子类。"""
    def emit(self, ev: DegradationEvent) -> None:
        raise NotImplementedError


class CounterSink(DegradationSink):
    """Tier 1：默认开启（`## 3.3`）。等价成本：一次
    `Counter.labels(reason=..., cls=...).inc()`，与现有
    `vllm:num_preemptions` 同量级。"""


class ResponseFieldSink(DegradationSink):
    """Tier 2：默认关闭。仅当 ev.scope == "request" 时有意义；
    参照 `vllm:vllm/entrypoints/openai/chat_completion/protocol.py:480-483`
    的 kv_transfer_params 先例，加一个同级的可选字段。"""


class EventStreamSink(DegradationSink):
    """Tier 2：默认关闭。复用 `vllm:vllm/distributed/kv_events.py` 同款
    ZMQ pub/sub，或 SGLang `kv_events_config` 同款配置形状（`## 6`）。"""
```

这段接口刻意保持短——它不是要给出一份可以直接合并的补丁，是要把 `## 3.2`-`## 3.3` 的四个要素落成一眼能看出彼此关系的形状：`DegradationReason` 是稳定标识，`scope`/`request_id` 是归属，三个 `Sink` 子类是三种出口，`Sink` 的默认注册与否（本示意代码没有展开这部分装配逻辑）体现 `## 3.3` 的两档默认值。

### 3.6 三种出口横向对比

`## 3.2` 分别介绍了三种出口的形状，这里把它们并排放在一张表里，方便对照 `## 8` 分阶段落地时"先做哪个"的判断：

| 维度 | `CounterSink` | `ResponseFieldSink` | `EventStreamSink` |
|---|---|---|---|
| 能回答的问题 | 发生了多少次 | 我这次请求受影响了吗 | 具体发生过什么、带什么上下文 |
| 归属要求 | `scope="global"` 或 `"request"` 均可（聚合时不分） | 仅 `scope="request"` 有意义 | 均可，`detail` 只在这一档才有意义 |
| 单次调用成本 | 一次原子自增 | 一次字段赋值 + 响应体多几十字节序列化 | 构造对象 + 跨进程发布（`5.1` 理由四） |
| `## 3.3` 默认值 | 默认开 | 默认关 | 默认关 |
| 已有先例 | `vllm:num_preemptions`（`## 2`） | `vllm:kv_transfer_params`（`## 2`） | `vllm:kv_events.py`／`sglang:kv_events_config`（`## 2`/`## 6`） |
| 覆盖不到的场景 | 定位不到具体哪个请求 | 覆盖不了 `scope="global"` 的事件（`## 1.1` A 类多数如此） | 成本最高，不适合默认全开 |

**"响应字段覆盖不了全局事件"这一行值得单独强调**：`## 4` 走读的 CUDA Graph 例子里 `ResponseFieldSink` 之所以不生效，不是实现疏漏，是这个降级事件本身不属于任何单一请求——三种出口不是互相替代的三个选项，是覆盖不同归属维度的三个答案，`## 7` 第三条会继续展开这一点。

### 3.7 契约的版本化：`DegradationReason` 怎么废弃一个取值而不破坏消费者

`## 5.1` 理由二已经指出枚举一旦公开就是 API 承诺，这里补上一个具体机制，避免这条顾虑变成"所以永远不能改"的借口：

1. **只增不删**——已发布的 `DegradationReason` 取值永远不删除、不改语义，即使对应的触发条件在未来某个版本里消失（比如某个 fallback 分支被彻底修好了），这个取值继续存在，只是从此不再被 `emit`，消费者的历史统计不会因此出现"这个 reason 突然找不到了"的解析错误。
2. **拆分用新增，不用改写**——`## 5.2` 决策一提到"mode mismatch"未来可能拆成两个更精细的原因，做法是新增 `CUDAGRAPH_FALLBACK_CASCADE_ATTN`/`CUDAGRAPH_FALLBACK_ENCODER_OUTPUT` 两个新取值，旧的 `CUDAGRAPH_FALLBACK_MODE_MISMATCH` 保留但停止使用，文档标注"自 vX 起被下列取值取代"，消费者按自己的节奏迁移过滤规则。
3. **`detail` 字段不受这条约束**——`## 5.2` 决策三已经论证，这是为什么 `detail` 要单独排除在稳定标识之外的直接原因：如果契约不区分"稳定标识"和"辅助上下文"，上面两条规则就得同时套用在 `detail` 的每一个字段上，维护成本会失控。

这三条规则本身没有任何一条是本篇发明的新技巧——它们是 Prometheus 指标废弃、Protobuf 字段废弃这类成熟实践里通用的"只增不删 + 语义标注"套路，本篇只是确认这套通用套路可以直接套用在 `DegradationReason` 上，不需要为它单独发明一套版本化机制。

### 3.8 一个常见的替代方案："干脆把日志都改成结构化 JSON"，为什么不够

这是写作过程中权衡过、最终没有采纳为主方案的一条路线，记录下来避免读者觉得本篇忽略了它。

把 `logger.warning("Enforce eager set, disabling torch.compile and CUDAGraphs...")` 这类自由文本日志，统一换成带 `extra={"reason": "config.enforce_eager_override", ...}` 的结构化字段，确实能部分解决 `## 3.2` 要素一"稳定标识"的问题——下游可以按字段过滤，不用解析自由文本。

但它解决不了另外两个要素。**归属**：结构化日志本身不强制要求携带 `request_id`，仍然要靠每个调用点自觉去传，和自由文本日志的现状没有本质差别。**默认行为分层**：`## 3.3` 两档默认值的核心是"发生了没有"这一档要比"发生了什么"便宜得多——结构化日志的每一条仍然是一次完整的日志写入，字符串化 + I/O 成本和普通日志基本没有差别，提供不了 Counter 那一档几乎可忽略的开销。

更根本的问题是**渠道单一**：结构化日志解决的是"日志内容变得可解析"，但仍然只有"日志"这一条通路。`## 3.6` 已经论证三种出口覆盖的是不同问题（"发生了多少次"/"我这次请求受影响了吗"/"具体发生了什么"），把它们全塞进一条日志流，等于强迫所有消费者都去订阅并解析日志，即便他们只关心一个聚合计数。

**结构化日志值得作为 `EventStreamSink` 的一种简化实现**（`## 3.5` 没有排除这种可能性），但不能替代整个契约——这是"实现细节"和"契约形状"的区别：契约规定的是要素和出口的种类，不规定每种出口内部具体用什么技术实现。

## 4. 主流程走读：一次 CUDA Graph 降级如果接上契约会怎么走

### 4.1 vLLM 侧：CUDA Graph fallback

用 `## 2` 已经核实过的真实触发点走一遍——不是虚构场景，是 `vllm:vllm/compilation/cuda_graph.py:244-254` 这条已经在生产代码里存在的分支，只是现在换成"如果接上了 `## 3.5` 的契约会怎样"。

**触发条件**：一个请求命中了 cascade attention（长共享前缀的 batch），`06-vLLM-模型执行与CUDA-Graph` `## 7` 已经指出这会让 `dispatch_cudagraph()` 强制 `disable_full=True`（`vllm:vllm/v1/worker/gpu_model_runner.py:4105`），本步的 `cudagraph_runtime_mode` 因此和 `CUDAGraphWrapper` 捕获时的 `runtime_mode` 不一致。

**第一跳——判断分支命中**：`CUDAGraphWrapper.__call__`（`vllm:vllm/compilation/cuda_graph.py:233`）走到 `:244-254` 的 `if` 分支，**今天**这里直接 `return self.runnable(*args, **kwargs)`，函数调用结束，没有任何人知道这件事发生过。

**第二跳（契约介入点）——发一次事件而不是默默转发**：在同一个分支里，转发之前插一行 `emit(DegradationEvent(reason=CUDAGRAPH_FALLBACK_MODE_MISMATCH, cls=SILENT_FALLBACK, scope="global", detail={"batch_descriptor": str(batch_descriptor)}))`。这一步的成本边界很关键——`CUDAGraphWrapper.__call__` 是逐 step 都可能命中的热路径，`## 5` 决策一会证明为什么这一跳必须只做"记一次"而不是"记下这一次的完整上下文"。

**第三跳——三个出口各自做自己的事**：
- `CounterSink`（默认开）把 `(reason="cudagraph.fallback.mode_mismatch")` 对应的 Counter 自增 1，供 `/metrics` 抓取——运维在 Grafana 上能看到这条曲线从 0 开始爬升，不需要改动任何现有的抓取配置。
- `EventStreamSink`（默认关，需要显式开启，`## 3.3`）如果开着，把包含 `batch_descriptor` 的完整 `DegradationEvent` 发布到既有的 ZMQ 通道——想做"这次降级具体发生在哪个 batch 形状上"这类离线分析的人，订阅这条流。
- 因为这个事件的 `scope="global"`（不属于某个具体请求），`ResponseFieldSink` 不生效——这正是 `## 1` A 类判断"该报警但归属是全局"在流程上的体现。

**和现状的对比**：今天唯一能看见这件事的路径是打开 `--cudagraph-metrics`（`vllm:vllm/config/observability.py:68`），然后翻 `CUDAGraphLogging.generate_metric_table()`（`06-vLLM-模型执行与CUDA-Graph` `## 7` 已指出该方法位于 `vllm:vllm/compilation/cuda_graph.py:71-118`）打印出的 Markdown 表格，人工去读某一行 `Runtime Mode` 是不是 `NONE`。接上契约之后，这件事从"人工翻日志表格"变成"一条可以直接设置告警阈值的 Prometheus 曲线"——**表格本身不需要删除**，`## 6` 会说明这条既有机制在新契约下扮演什么角色。

### 4.2 换一个引擎走一遍：SGLang 的 18 条规则

只用 vLLM 举例容易让人误以为这套契约是为 vLLM 一家的代码结构量身定做的，这里换成 SGLang 侧 `## 2` 已核实的另一条真实证据，确认契约在结构完全不同的代码里同样能落地。

**触发条件**：某次启动，`resolved_view(self).moe_a2a_backend != "none"`（`sglang:python/sglang/srt/server_args.py:4649-4722` 那 18 条规则之一）判定为真，说明当前的 MoE all-to-all 后端配置和 `TcPiecewise` 图捕获模式不兼容。

**第一跳——判断分支命中**：`for _name, predicate in rules:` 循环（`:4720-4722`）走到 `if predicate():` 为真的分支，`self.cuda_graph_config.prefill.backend = Backend.DISABLED`，`_name`（这里是字符串 `"MoE A2A backend"`）被丢弃，函数返回，调用方不知道刚才关掉了 prefill 阶段的图捕获，也不知道是因为哪一条规则。

**第二跳（契约介入点）——`_name` 不再被丢弃**：把 `if predicate(): self.cuda_graph_config.prefill.backend = Backend.DISABLED` 改成 `if predicate(): self.cuda_graph_config.prefill.backend = Backend.DISABLED; emit(DegradationEvent(reason=_rule_name_to_reason(_name), cls=SILENT_FALLBACK, scope="global"))`——这一步的关键不是新写判断逻辑（判断逻辑 18 条规则早就写好了），是把已经存在的 `_name` 字符串接进契约的稳定标识（`_rule_name_to_reason` 是一个把人类可读字符串映射到 `## 3.5` 定义的稳定枚举取值的查表函数，不是直接把 `_name` 当成 `reason` 用——`## 5.1` 理由二已经论证过为什么稳定标识不能直接绑定到会变的英文描述文本上）。

**第三跳——出口**：这是配置解析期（启动阶段）的事件，不是逐 step 热路径，`## 3.6` 的成本对比表里"单次调用成本"这一档对这条触发点几乎不构成顾虑——`CounterSink` 默认开可以直接生效，甚至不需要等到 `## 5.2` 决策四关于"要不要采样"的讨论，因为这条路径的触发频率上限就是"每次进程启动最多 18 次"，天然远低于需要考虑采样的量级。

**和 vLLM 例子的对比**：两条证据分别代表契约要覆盖的两种触发节奏——vLLM 的 CUDA Graph fallback 是**逐请求/逐 step**的热路径，SGLang 的 18 条规则是**逐进程启动一次**的冷路径。`## 5.2` 决策四"默认不采样"的论证对后者天然成立（触发频率本来就低），对前者才是真正需要认真权衡的地方——这也是为什么 `## 8` 第一阶段刻意同时选中这两条证据作为试点：一条验证"热路径埋点的开销可接受"，一条验证"冷路径埋点几乎零风险"，覆盖两种最有代表性的成本场景。

## 5. 设计决策与代价

### 5.1 为什么上游至今没做这件事（不是没想到）

这一节按任务要求单独展开，每条都要能从真实代码结构里读出来，不是猜测维护者的想法。

**理由一：降级往往是性能优化的正常路径的一部分，无差别报警会把"正常"和"异常"混成一锅噪音。**
`vllm:vllm/compilation/cuda_graph.py:248-249` 那两行注释原话是 "`CUDAGraphMode.NONE` could mean the profile run, a warmup run, or running without cudagraphs"——**这条分支本身故意把"真正的降级"和"完全正常的 profile/warmup 阶段"合并处理**。如果不加区分地把这条分支的每次命中都算作一次降级事件，进程启动阶段的 warmup/profile run（这是正常流程，每次启动都会发生）会先制造一大批"降级事件"，把真正值得关注的信号淹没在启动噪音里。这不是"没想到该报警"，是**当前的代码结构本身没有把"降级"和"正常但走了同一条代码路径"分开**，接契约之前必须先解决这个区分，本篇 `## 8` 第一阶段会说明为什么这恰好是选择试点范围时要认真核实的一步。

**理由二：事件枚举一旦公开就是 API 承诺，以后不好改。**
`## 3.5` 的 `DegradationReason` 一旦发布给下游消费（Grafana 面板配置了按这个枚举值过滤的告警规则、某个 router 按这个字符串做分支判断），团队想重新组织判断逻辑——比如把"mode mismatch"这单一原因拆成"cascade attention 触发"和"encoder 输出触发"两个更精细的原因——就要面对"新老两个枚举取值同时存在一段时间"的兼容性负担。`03-跨引擎共性缺口` `## 8` 缺口②已经指出接口层（枚举/协议字段）的变更成本天然低、实现层的变更成本天然高，这条规律反过来也成立：**一旦枚举对外公开，它的变更成本就从"低"变成了"高"**，因为下游消费者的存在本身让它变重了。这是本篇 `## 8` 建议"先小范围试点、不要一次性定义完整枚举"的直接原因。

**理由三：热路径上加计数器本身有开销，且标签基数需要提前设计。**
`03-跨引擎共性缺口` `## 5` 取舍一已经论证过日志的 I/O 开销，本篇要补的是 Counter 这一档也不是零成本——`vllm:vllm/compilation/cuda_graph.py:244-254` 是逐 step 都可能命中的路径，如果给 `reason` 标签配上高基数的维度（比如把 `batch_descriptor` 直接塞进标签而不是 `detail`），Prometheus 时间序列基数会随 batch 形状组合数增长，抓取和存储成本随之上升。这正是 `03-跨引擎共性缺口` `## 8` 缺口①"代价与反驳"提到的"需要提前设计好指标命名空间和基数控制"，本篇 `## 3.5` 把 `detail` 从稳定标识里剥离出去，正是为了不让这条顾虑落到 Counter 这一档头上。

**理由四：降级往往发生在 worker 进程，回传到能响应请求的前端进程要跨 IPC。**
vLLM 是多进程架构，CUDA Graph fallback 发生在 GPU worker 进程内部的 `gpu_model_runner.py` 前向路径里，而 HTTP 前端在另一个进程（scale-out 场景下甚至在另一台机器）。要让"worker 内部发生的降级"能被前端进程的 `/metrics` 端点或 HTTP 响应看到，需要一条现成的跨进程通道——这不是"记一行日志"那么简单：Prometheus 的多进程模式本身需要额外的共享目录配置才能跨进程聚合计数器，vLLM 现有的 `vllm:vllm/distributed/kv_events.py` 之所以选择 ZMQ pub/sub 而不是直接共享内存计数器，正是因为这条通道要同时跨越进程边界和潜在的网络边界。`## 6` 会说明本契约为什么优先复用这条已经解决过这个问题的通道，而不是重新发明一条。

**这四条理由本身回应了任务书的要求**：本篇没有找到、也不编造任何一条"上游 issue/PR/RFC 讨论"作为证据——四条理由全部从 `## 2` 已经核实过的真实代码结构（一段注释、一个多进程架构、一份已有的标签设计顾虑）反推出来，标注为**本库推断**，不是转述维护者的原话。

### 5.2 契约自身的六条设计决策

**决策一：现在只锁一个小的 `DegradationReason` 子集，不追求覆盖 `## 1` 五类降级的全部真实触发点。**
- 为什么这样：呼应 `5.1` 理由二——枚举一旦公开就变重，本篇 `## 8` 第一阶段只选 2-3 个已经在 `## 2` 证据地图里核实过、触发点单一、不需要跨模块联动的降级点起步。
- 不这样会怎样：如果一次性把 `## 2` 表格里 23 条证据全部映射成 `DegradationReason` 取值，会在还没有任何真实消费者验证过这套契约形状好不好用之前，就先背上几十条"以后不好改"的公开 API 负担——这是自己给自己制造 `5.1` 理由二描述的那种压力，没有任何收益对冲。
- 什么时候可以不这样：如果某个降级类别的取值空间本身很小且天然稳定（比如 D 类"这个能力枚举值在这个后端未实现"，取值集合基本等于配置层已经声明过的枚举，不会随时间膨胀），可以为这一类别一次性定义完整，不需要来回小步扩展。

**决策二：`scope="request"` 不强制所有事件都必须带 `request_id`，允许 `scope="global"` 存在。**
- 为什么这样：`## 1` 已经论证 A/C 类多数是全局属性，`sglang:python/sglang/srt/server_args.py:4649-4722` 这类判断发生在配置解析期——这个阶段根本没有任何具体请求存在。契约把 `scope` 设计成显式二选一，由每个触发点自己声明，而不是替所有触发点强行安一个 `request_id`。
- 不这样会怎样：如果强制所有事件都带 `request_id`，配置解析期/启动期这类天然无请求上下文的降级点要么被迫伪造一个 `request_id`（污染下游对"这条事件属于哪个真实请求"的判断），要么被整体排除在契约之外——两者都比"显式允许 `scope=global`"更糟。
- 什么时候可以不这样：如果某个引擎的架构把"配置解析"和"请求处理"完全分离到不共享任何数据结构的两个阶段（多数引擎确实如此），这个区分几乎是免费的，谈不上"什么时候可以不这样"——它几乎总该有，除非配置解析本身发生在 per-request 路径上（本篇没有找到这样的反例）。

**决策三：`DegradationEvent.detail` 不参与稳定标识，不承诺序列化结构长期不变。**
- 为什么这样：`batch_descriptor` 这类上下文信息的具体字段会随引擎内部实现演进（`06-vLLM-模型执行与CUDA-Graph` 已经在讲 `BatchDescriptor` 相关字段），如果把 `detail` 的字段名/类型也纳入公开契约，等于把整个内部数据结构的稳定性绑死给外部消费者——这是 `5.1` 理由二的加强版：不仅 `reason` 不好改，连"降级发生时附带哪些辅助信息"都不好改了。
- 不这样会怎样：vLLM 未来任何一次纯内部重构（比如给 `BatchDescriptor` 加一个字段、改一个字段名）都要先过一遍"会不会破坏 `DegradationEvent.detail` 的下游消费者"这道检查，大幅拖慢正常的内部重构节奏，等于把契约的稳定性代价转嫁给了完全不相关的内部代码演进。
- 什么时候可以不这样：如果某个 `detail` 字段被证明长期稳定且有大量下游依赖（比如"触发时刻批次里的请求数量"这种几乎不会变的量），可以单独把它提升成 `DegradationEvent` 的一等字段——这是契约正常的演进路径：先在 `detail` 里跑一段时间证明有用且稳定，再"转正"。

**决策四：Counter 出口默认对每次命中都直接 `inc()`，不做采样。**
- 为什么这样：`## 4` 第二跳指出 CUDA Graph fallback 是逐 step 命中的热路径，直接 `inc()` 虽然不是零成本，但已有的 `num_preemptions`（`vllm:vllm/v1/metrics/loggers.py:661-667`）从来不是采样计数——统一到同一套心智模型下，运维不需要额外记住"这个数字是精确的还是估计的"。
- 不这样会怎样：如果做采样，触发频率极高的降级原因能显著降低开销，但计数本身会失真，且不同降级原因的触发频率天差地别，很难选出一个对所有 `reason` 都合适的统一采样率——这本身会制造新的认知负担（"哪些指标是精确的，哪些是估计的"）。
- 什么时候可以不这样：如果某一类具体降级事件被证明触发频率高到"直接 `inc()`" 本身造成了可测的开销回归，才应该考虑给那一个具体 `reason` 单独配置采样，而不是给整个契约默认加采样——本库不产出实测性能数字（`00-总览与阅读地图` `## 1` 已声明这条能力边界），这一条的判据只能留给真正部署过这套契约的人用真实压测验证。

**决策五：先在各引擎内部各自实现契约的具体埋点，不强求一套跨引擎共享的代码库。**
- 为什么这样：`## 6` 会展开 vLLM 和 SGLang 各自独立造出了同构的 KV 事件基础设施（`kv_events.py` 与 `kv_events_config`），两者互不依赖对方的代码，只是**设计形状**一致——这说明"跨引擎统一"这件事历史上已经通过"各自实现、事后发现形状相同"而不是"先共享一个库、两家一起接入"的路径达成过一次。契约的 `DegradationReason`/`DegradationEvent`（`## 3.5`）是一份**文档级**的共享规范（字段名、语义、默认值哲学一致），不要求 vLLM 和 SGLang 引入对方的 Python 包依赖。
- 不这样会怎样：如果坚持先建一个两家都要依赖的共享库，光是"这个库归谁维护、版本怎么发布、两家的发布节奏本来就不同步"这类协调成本，就可能拖慢第一阶段的落地——`## 8` 第一阶段本来是几个文件的小改动，一旦绑上跨仓库依赖协调，复杂度会跳一个量级，不成比例。
- 什么时候可以不这样：如果两家已经在共享某个更底层的通用库（比如都依赖同一个 Prometheus client 封装），且这个库本来就承担"两家共同维护的基础设施"角色，那么把 `DegradationReason` 这类纯数据定义放进那个已经存在协调机制的共享库里是合理的——本篇没有找到这样一个现成的、双方都已经依赖的公共 Python 包，所以现阶段按"各自实现、形状对齐"处理。

**决策六：契约只负责"发出信号"，不改变引擎遇到降级时默认选择静默继续还是报错中止的行为。**
- 为什么这样：`03-跨引擎共性缺口` `## 7` 第 1 条已经论证过 `kv_load_failure_policy` 默认 `"fail"` 是评估过正确性风险后的取舍，不是缺口；反过来，A 类 CUDA Graph fallback 默认"静默继续"也是经过 `5.1` 理由一论证过的、故意把降级和 warmup/profile 正常路径合并处理的结果。契约要解决的是"发生了没有、能不能被发现"，不是"发生了之后该不该让请求失败"——这是两个独立的问题，本库 `05-改进机会` 系列已经反复论证过"该报错还是该降级"要逐案例判断，契约不该替所有触发点做这个判断。
- 不这样会怎样：如果契约本身还规定"只要触发了 A/B/D 类事件就必须让请求失败"，会把一个纯粹的可观测性改动，变成一次影响生产可用性的行为变更——`5.1` 理由一已经说明 warmup/profile 阶段本来就会大量走同一条分支，如果这条分支从此导致请求失败，会是一场灾难性的回归。
- 什么时候可以不这样：`## 8` 第三阶段涉及的 E 类 KV 传输失败，恰恰是一个"发生即应该失败"已经是既有共识的类别（`kv_load_failure_policy` 默认 `fail`）——契约在这类场景里不需要"新增"报错行为，只需要在已经决定要失败的那一刻，顺带发布一次带 `request_id` 的事件，报错这件事本身的默认值完全不受契约影响。

## 6. 与各家已有机制的关系

本篇的契约刻意不是另起炉灶——`## 2` 证据地图已经列出四处两家引擎独立收敛到的**同类基础设施**，本节说明契约怎么把它们收口，而不是绕开它们重新造一遍。

**vLLM 的 `--cudagraph-metrics`（`vllm:vllm/config/observability.py:68`）**：这是今天唯一一处"至少能看见"CUDA Graph 降级的机制，但它是**批量导出**（打开后每一步累积统计，周期性生成一整张 Markdown 表格）而不是**逐事件**的。契约不要求废弃这张表——`## 4` 已经说明表格本身可以继续存在，`CounterSink` 只是把"这一步降级了没有"这个信号从"要人工翻表格"升级成"可以直接设阈值告警的一条曲线"，两者服务的场景不同：表格适合排障时做整体分布分析（"过去这段时间有百分之多少的 step 落在 `NONE`"），Counter 适合值班场景（"现在这一刻曲线有没有异常跳变"）。

**vLLM 的 KV 事件（`vllm:vllm/distributed/kv_events.py`，`vllm:vllm/config/kv_events.py:14`）**：这是目前唯一一套已经解决了 `5.1` 理由四（跨进程回传）的通路——`EventBatch`/`KVCacheEvent`（`vllm:vllm/distributed/kv_events.py:24-32`）已经定义了"批次时间戳 + 事件列表"的通用外壳，`## 3.5` 的 `EventStreamSink` 建议直接复用这条 ZMQ 发布通道，而不是新起一条——差别只在于把 `KVCacheEvent` 这个**只服务 KV 缓存生命周期**的窄基类，替换/扩展成能承载 `DegradationEvent` 的更通用外壳。`enable_kv_cache_events` 默认 `False` 这个先例也是 `## 3.3` 两档默认值论证的直接依据之一。

**SGLang 的 `kv_events_config`（`sglang:python/sglang/srt/server_args.py:1665-1669`）与 `describe_kv_events_publisher()`（`sglang:python/sglang/srt/server_args.py:9776`）**：SGLang 独立于 vLLM，收敛到了几乎同构的设计——一个默认 `None`（关闭）的配置项，一个"发布器描述符"方法把 ZMQ 端点信息暴露在 `/server_info` 里供路由层订阅。两家互不参考对方代码库，却各自造出了同一种形状的基础设施，这本身是本篇 `## 0` 结论"契约不是凭空发明"的最强证据——**两条独立的收敛路径已经把"跨进程发布结构化事件"这件事的技术方案趟出来了，缺的只是把它的适用范围从"KV 缓存生命周期"扩展到"降级事件"这一步**。

**SGLang 的 `/get_server_info`（`sglang:python/sglang/srt/entrypoints/http_server.py:786-822`）**：`## 2.1` 矩阵已经指出，这类专用端点今天暴露的是**状态快照**（启动配置 + `internal_states`），不是**事件历史**——这个区分本身是 `## 7` 会展开的一个反直觉发现。契约不需要这个端点承担新的职责，`ResponseFieldSink`/`EventStreamSink` 走的是另外两条独立通路。

**vLLM 响应协议里的 `kv_transfer_params`（`vllm:vllm/entrypoints/openai/chat_completion/protocol.py:480-483`）**：这是"给响应对象加一个可选、默认 `None` 的字段"这个模式在协议层已经落地过的先例——`## 3.5` 的 `ResponseFieldSink` 沿用的正是这个模式，不是发明一种新的协议扩展方式。

一句话总结这一节：**契约要新建的东西只有"一个跨引擎共享的降级事件数据模型和归属规则"（`## 3`），三种出口本身在两家引擎里都已经有对应的、独立造过的基础设施可以直接挂载。**

### 6.1 收口关系一览

| 已有机制 | 引擎 | 今天服务的目的 | 在契约里扮演的角色 | 默认值 |
|---|---|---|---|---|
| `--cudagraph-metrics` | vLLM | 批量导出 CUDA Graph 命中分布表 | 排障用的整体视图，与 `CounterSink` 并存不冲突 | 关（`vllm/config/observability.py:68`） |
| KV 事件（ZMQ pub/sub） | vLLM | 发布 KV 块存取/驱逐事件 | `EventStreamSink` 直接复用的发布通道 | 关（`vllm/distributed/kv_events.py:14`） |

## 7. 踩坑与反直觉

1. **以为 E 类是缺口最深的一类，深挖后发现它是两家投入最多的一类——真正的窟窿在一个更窄的地方。** 动笔前的直觉是"抢占/回退/KV 传输失败"这类资源性降级应该和 CUDA Graph fallback 一样几乎没有信号，`## 2` 证据地图核实下来发现恰恰相反：`vllm:num_preemptions`、`sglang:num_retracted_reqs`、`sglang:num_bootstrap_failed_reqs`/`num_transfer_failed_reqs` 全部是已经存在、默认开启的 Counter。真正没解决的不是"E 类整体没人管"，是一个远比"E 类整体"窄的问题——**全局计数**已经做得不错，**请求级归因**（某个具体 `request_id` 能不能拿到"我是因为 KV 传输失败才死的"这个原因码）完全没有。把这条判断笼统地写成"E 类是缺口"会误导读者去重复造一遍已经存在的轮子。

2. **`sglang:python/sglang/srt/server_args.py:4649-4722` 不是"没有素材可用"，是"素材写好了但没人接出去"。** 通常会假设"没打日志"是因为触发条件本身不好描述、需要额外开发成本才能生成人类可读的原因文本。这段代码推翻了这个假设——18 条规则的每一条都自带一个描述性字符串（`"model-arch blacklist"`、`"DP attention"`……），`for _name, predicate in rules:` 这行代码里 `_name` 前缀的下划线甚至像是在明示"这个变量故意不用"。素材已经到手，缺的只是把它接进 `logger.warning` 或者本篇提议的 `CounterSink.labels(reason=_name)` 这一步——这比"完全没有素材、需要额外开发"要便宜得多，也让 `## 8` 第一阶段选中这段代码作为试点候选时更有信心：这不是要新写一段判断逻辑，只是给已经存在的判断结果接一根线。

3. **以为"专用端点"是最容易補的一档，深挖后发现两家现有的专用端点回答的是完全不同的问题。** `sglang:/get_server_info`（转发到 `/server_info`）看起来像是一个现成的、只需要往里加字段的落点，但 `## 2` 核实后发现它返回的是 `dataclasses.asdict(server_args)` + `internal_states`——本质是"现在的状态是什么"的快照，不是"过去发生过什么"的事件流。把降级事件塞进这类端点，语义上是不匹配的（下一次调用这个端点，之前发生过的降级事件就已经不在返回值里了，除非额外维护一份历史缓冲区，这又变成了事件流的另一种实现）。这个反直觉之处提醒本篇的三种出口不是可以互相替代的选项，而是覆盖不同问题的三个答案：Counter 答"发生了多少次"，响应字段答"我这次请求受影响了吗"，事件流答"具体发生过什么"——专用端点这个第四种形状，天然更适合回答"状态快照"，不适合替代前三者。

4. **以为两家的"同一份文件内部不一致"是各写各的偶然结果，深挖后发现两处不一致的性质完全不同。** vLLM 的 `enforce_eager` 覆盖（有 `warning_once`）和 `SamplingParams` 覆盖（零日志）看似同一种"不一致"，但前者是**全局/启动期**事件、后者是**请求级**事件——`## 1.1` B 类的判断已经说明这两档"该不该报警"的答案本来就不同，"不一致"这个词第一眼看像是缺陷，细看后其实是"两件性质不同的事恰好都叫'配置覆盖'，被同一个词捆在一起讨论"。SGLang 的 `sglang:python/sglang/srt/server_args.py:4649-4722`（零日志）与 `:6009-6011`（有日志）则是另一种性质：两条都是**同一类事件**（配置解析期的 CUDA Graph 禁用），触发时机、归属维度完全一样，只是有没有人记得写这行日志的差异——这才是真正"纯属疏漏、该统一"的不一致。同一个词"不一致"，在 vLLM 那边掩盖了一个真实的分类差异，在 SGLang 这边才是名副其实的疏漏，写作过程中如果不逐条回到源码核实触发时机，很容易把这两种性质不同的"不一致"混为一谈，得出"两家都一样马虎"这种过粗的结论。

## 8. 分阶段落地：三步走

每一步都刻意选择"改动范围小、能独立验证、有明确的第一批受益者"的切入点，不要求一次性把 `## 1` 五类降级全部接完。

**第一阶段——只做 Counter，只选两个已核实、触发点单一的降级点试点。**
- 改哪些文件：vLLM 侧改 `vllm/compilation/cuda_graph.py`（在 `:244-254` 分支转发前插入一次 `CounterSink.emit`）+ `vllm/v1/metrics/loggers.py`（参照 `num_preemptions` 的写法注册一个新 Counter，`## 2` 已核实其定义在 `:655-667`）；SGLang 侧改 `python/sglang/srt/server_args.py`（把 `:4649-4722` 那段循环里被丢弃的 `_name` 接到一个按 `reason=_name` 打标签的 Counter）+ `python/sglang/srt/observability/metrics_collector.py`（新增计数器，参照 `num_retracted_reqs` 的写法，`## 2` 已核实其定义在 `:456-461`）。
- 怎么验证：不需要真实 GPU——CUDA Graph fallback 分支和 SGLang 的规则判断都是纯 Python 逻辑，可以用 mock/monkeypatch 单独触发（`forward_context.cudagraph_runtime_mode` 或某条 `predicate()` 强制返回 `True`），断言对应 Counter 的值增加了 1 且标签正确；这类"造假状态验证解析/判断逻辑"的测试模式，本库 `_lab/*.py` 的 `--selftest` 已经在用同样的思路（不依赖 `_src` 也能验证正确性），可以直接复用。
- 能被谁先用起来：已经在生产环境打开 `--cudagraph-metrics` 的运维——他们已经在主动寻找这类信号，是天然的第一批种子用户，不需要等响应字段/事件流基础设施到位就能立刻从 Grafana 面板上看到一条新曲线。

**第二阶段——把请求级的 B 类配置覆盖接到响应字段，只选一个 API family 先试点。**
- 改哪些文件：`vllm/sampling_params.py`（贪心覆盖发生处 `:529-534`，在覆盖发生时把标记写入请求对象上的一个瞬时字段）+ `vllm/entrypoints/openai/chat_completion/protocol.py`（参照 `kv_transfer_params` 的写法，`## 2` 已核实其定义在 `:480-483`，加一个同级的可选字段，比如响应里的 `sampling_overrides: list[str] | None`）。
- 怎么验证：构造一个 `temperature=0` 且显式传了 `top_p != 1` 的请求，跑一次单元测试断言响应里出现这个字段且内容是 `["sampling.greedy_override"]`；同时验证未触发覆盖时字段省略/为 `None`，不改变现有客户端能解析到的字段集合——这是向后兼容性的硬约束，`kv_transfer_params` 已经证明"可选字段默认 `None`"这个模式不会破坏存量客户端。
- 能被谁先用起来：自己写客户端库、需要精确知道"这次请求实际生效的采样参数是什么"的重度 API 使用者（比如做批量评测/可复现性研究的团队）——他们目前唯一的办法是自己在客户端重新实现一遍 vLLM 内部的覆盖判断逻辑去猜。

**第三阶段——事件流，覆盖 E 类的请求级归因，复用 KV 事件基础设施。**
- 改哪些文件：`vllm/distributed/kv_events.py`（把 `KVCacheEvent`（`## 2` 核实定义在 `:24-32` 附近）的能力扩展成能承载 `DegradationEvent`，或者新增一个复用同一套 ZMQ publisher 的独立 sink）+ vLLM 的 KV 连接器失败处理路径（`vllm/config/kv_transfer.py:69` 附近，在判死之前先发布一次事件）；SGLang 侧对应改 `python/sglang/srt/disaggregation/decode.py`（`:2256-2270` 判死之前）+ 复用已有的 `kv_events_config`/`describe_kv_events_publisher()`（`## 2` 核实定义在 `:1665-1669`、`:9776`）。
- 怎么验证：集成测试起一个 mock ZMQ 订阅者，用测试桩模拟一次 KV 连接器传输失败（不需要真实网络传输，`KVPoll.Failed` 本身就是一个可以直接构造的状态），断言订阅者收到了带正确 `request_id` 和 `reason=kv_transfer.load_failed.no_recompute` 的事件。
- 能被谁先用起来：做 PD 分离部署、需要区分"这次失败是不是因为 KV 传输"从而决定要不要在客户端自动重试的网关/路由层——`sglang:python/sglang/srt/server_args.py:9776` 附近的注释已经明确提到"KV-aware routers"这类消费者的存在（"so KV-aware routers ... can subscribe per-worker"），说明这条通道服务的下游角色已经在代码注释里被点名，不是本篇凭空设想出来的需求。

### 8.1 三阶段一览

| 阶段 | 出口 | 覆盖类别 | 改动量级 | 依赖的既有基础设施 |
|---|---|---|---|---|
| 一 | `CounterSink` | A/B（全局部分） | 小——两处分支各插一行 `emit` + 注册两个新 Counter | `vllm:num_preemptions`／`sglang:num_retracted_reqs` 同款指标体系 |
| 二 | `ResponseFieldSink` | B（请求级部分） | 中——协议对象加字段 + 兼容性测试 | `vllm:kv_transfer_params` 字段模式 |
| 三 | `EventStreamSink` | E（请求级归因） | 大——扩展事件外壳 + 跨进程发布 + 集成测试 | `vllm:kv_events.py`／`sglang:kv_events_config` |

三个阶段之间**没有强制的先后依赖**——`## 5.2` 决策五已经论证契约是文档级的共享规范，不是必须整体部署的单一系统，一个只关心 A 类的团队完全可以只做第一阶段就停下，不需要为了"契约完整性"被迫做完三个阶段。
