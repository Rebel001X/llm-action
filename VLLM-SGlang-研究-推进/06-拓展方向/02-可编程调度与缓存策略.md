# 06-02 · 可编程调度与缓存策略

> **本篇取证基准**：`vllm` @ `7ca49fbe`（2026-08-22）；跨引擎引用带 `sglang:` 前缀，SGLang 快照见 `_lab/out/repo_stats.json`。
> **一句话**：SGLang 已经把"选策略"焊进了 ABC，但两家都没做到"插策略"。

## 0. 结论先行

这是一篇拓展文章，不是找 bug。问题不是"vLLM/SGLang 哪里写错了"，而是：
**如果一个用户想按自己的流量特征换一套调度/驱逐策略，今天的代码离"能换"还差多少？**

六条结论，按证据强度排序：

1. **vLLM 的驱逐策略是全库里最硬编码的一处，零抽象。** `BlockPool.free_blocks()`（`vllm/v1/core/block_pool.py:719`-`740`）用一段内联 `if/else` 把释放的块分进 LIFO 或 FIFO 两条链表，没有类、没有配置参数、没有可覆写的方法——这段逻辑不是"没抽象好"，是从设计上就没打算被替换。
2. **但"调度顺序"和"驱逐策略"在 vLLM 里是两件可编程程度完全不同的事。** 调度顺序（`request_queue.py`）虽然只有 FCFS/PRIORITY 两个内置选项，却有一条**理论上的档三通道**——`scheduler_cls` 配置项（`vllm/config/scheduler.py:117`）可以把整个 `Scheduler` 换成任意实现了 `SchedulerInterface`（17 个 `@abstractmethod`）的自定义类。这条通道是真的，但粒度是"换掉整个调度器"，不是"只换排序策略"——`## 4` 会展开这个粒度错配。
3. **SGLang 的驱逐策略已经是标准 ABC + 工厂模式，7 个内置实现，比 vLLM 领先一整个台阶**——`EvictionStrategy`（`sglang:python/sglang/srt/mem_cache/evict_policy.py:10`）定义 `get_priority(node)`，LRU/LFU/FIFO/MRU/FILO/Priority/SLRU 七个子类各自实现一行到十几行。但**这不等于"用户可以插自己的策略"**：调度到具体实现是靠一个模块级私有字典（`_EVICTION_POLICY_FACTORIES`，`sglang:python/sglang/srt/mem_cache/utils.py:56`），没有导出的注册函数；更细的是，CLI 的 `--radix-eviction-policy` 只暴露了 7 个里的 4 个（`sglang:python/sglang/srt/server_args.py:328`）——**FIFO/MRU/FILO 三个策略已经写好、能跑，但用户从命令行根本够不着**。
4. **SGLang 的调度顺序策略同样是"选"而不是"插"。** `SchedulePolicy.calc_priority()`（`sglang:python/sglang/srt/managers/schedule_policy.py:237`）是一段 `if/elif` 硬分发，未知策略名直接 `raise ValueError`（`:283` 附近）——6 个命名策略（LPM/DFS-WEIGHT/FCFS/LOF/RANDOM/ROUTING_KEY）齐全，但新增第 7 个必须改 SGLang 自己的源码。
5. **[[01-前缀缓存差分实验-亲笔]] 证明了这件事为什么值得做**：容量吃紧时命中率的差异 100% 来自驱逐策略，跟用哪种数据结构（块哈希表 vs 基数树）没关系——`hot_cold` @4K 那组数据里，"vLLM+纯LRU"和 SGLang 完全打平（0.2709），真正让 vLLM 反超的 0.56 个百分点纯粹来自它驱逐顺序里编码的一条先验。**策略比数据结构更值钱，这句话现在有实验支持，不再是直觉。**
6. **风险不是空对空的担忧，本库自己的调研已经撞见过一次活生生的先例**：SGLang 的语法编译就绪检查跑在调度主循环里，最长 5ms 的忙等能拖慢**整批**请求（[[02-SGLang可改进点]] `## 8` 第 2 条）——这是"往主循环里插用户可控的代码"这件事，工程上已经真实付过的代价，不是本篇臆想出来的风险。

**本篇不产出任何实测性能数字**——凡引用 [[01-前缀缓存差分实验-亲笔]] 的命中率数字，都是策略模拟结果，不是吞吐/延迟实测。凡涉及"上游打算怎么做"，一律标「未查证」，本库没有编造过任何 issue/PR/RFC。

## 1. 它在系统里的位置

这篇是"拓展方向"组的第二篇，直接站在 [[01-前缀缓存差分实验-亲笔]] 的结论上往前走一步。那一篇回答了"两家的策略在数字上差多少"，本篇回答"这些策略今天能不能被换掉"——这是两个独立的问题：一个策略即使在数字上被证明更差，只要它是硬编码的，用户就没有绕开它的办法；反过来一个策略数字上打平，只要它可插拔，用户就能按自己的流量特征去调。

和已有篇目的边界划清楚：

- [[03-vLLM-调度器解剖]]、[[02-SGLang-Scheduler事件循环]] 讲的是"调度器今天怎么跑"——本篇复用它们已经核实过的行号，不重新走读主流程，只挑"策略在哪个位置被决定、有没有缝可插"这一件事。
- [[02-调度策略横向对比]] 讲的是"八个引擎的调度策略选了哪些不同的点"——那是**结果**的对比；本篇讲的是**机制**的对比：不是"vLLM 选 FCFS、SGLang 选 LPM"，而是"如果用户想加一个新选项，today's code 要改几个文件"。
- [[01-vLLM可改进点]]、[[02-SGLang可改进点]] 讲的是"哪里有具体缺口"——本篇会引用它们已核实的 5ms 忙等作为风险论据，但本篇的主题不是找 bug，是评估"可编程化"这条路值不值得走、走到哪一步。

本篇要看的是三个子系统的可编程程度，且必须分开看，因为它们在两家引擎里的耦合方式完全不同：

1. **等待队列的出队顺序**（谁先被调度）——vLLM 是 `request_queue.py` 里独立的一层；SGLang 是 `schedule_policy.py`，且直接读前缀缓存树的内容（[[02-SGLang-Scheduler事件循环]] `## 5` 决策二）。
2. **KV 块/节点的驱逐顺序**（容量不够时先牺牲谁）——vLLM 是 `block_pool.py` 内联逻辑；SGLang 是独立的 `EvictionStrategy` 类族。
3. **二者的耦合方式**——vLLM 的调度队列完全不看前缀缓存内容（两个子系统解耦），SGLang 的 LPM 策略直接查询基数树（两个子系统耦合）。耦合方式本身也是"可编程性"要考虑的一个维度：耦合越紧，换一套调度策略需要连带理解的东西就越多。

## 3. 可编程性的三档定义

任务给了三档框架，本节先把每一档在**今天的代码里长什么样**钉死，不谈假设。

### 档一 · 选：从内置枚举里选一个

**形状**：一个 `Enum` + 一个工厂函数（`if/elif` 或字典查表），未登记的名字直接报错。

**今天谁在这一档**：

- vLLM 调度顺序——`SchedulingPolicy`（`vllm/v1/core/sched/request_queue.py:13`-`17`），2 项。
- SGLang 调度顺序——`CacheAwarePolicy`+`CacheAgnosticPolicy`（`sglang:python/sglang/srt/managers/schedule_policy.py:200`-`213`），6 项。
- SGLang 驱逐策略（CLI 层）——`RADIX_EVICTION_POLICY_CHOICES`（`sglang:python/sglang/srt/server_args.py:328`），4 项（低于其内部实际实现的 7 项）。

**能解决什么用户问题**：覆盖了"已知的常见取舍之间二选一/几选一"——比如"我要不要按前缀命中排序""要不要按剩余生成长度排序"。用户不需要写代码，改一个命令行参数。

**实现要动哪些文件**：新增一项，要动**枚举定义 + 工厂分发 + 具体实现函数**三处，全部在引擎自己的源码里。以 SGLang 为例，新增第 7 种调度策略要碰 `schedule_policy.py` 的三个位置（`## 2` 表格里 `:200`-`213`、`:237`-`283`，加一个新的 `_sort_by_xxx()` 静态方法）。

**风险**：几乎没有——每个选项都经过引擎自己的测试，用户只是切换已验证过的路径。**这一档的代价是"选项永远不够用"**，用户的真实流量往往落在两个内置策略之间，档一给不出中间态。

### 档二 · 配：用配置表达组合策略

**形状**：不是从命名策略里选一个，而是让用户用配置（权重/公式/阈值）**组合**出一个新策略，不用写代码，也不用引擎团队预先给这个组合起名字。任务举的例子是"前缀命中权重 × 等待时长 × 优先级"。

**今天谁在这一档：没有，两家都不在**——这是本篇核实后要明说的一条空白，不是找不到就跳过。

最接近的两个案例都不够格：

- vLLM `PRIORITY` 策略的排序键是 `(priority, arrival_time)`（`vllm/v1/request.py:350`-`361`，[[03-vLLM-调度器解剖]] `## 3.3` 已走读）——这是两级字典序，`priority` 由用户填数字，但**组合方式（先比谁、怎么合成一个数）是写死的字典序，用户不能改成加权和**。
- SGLang 的 `NewTokenRatioTracker`（`sglang:python/sglang/srt/managers/scheduler_components/new_token_ratio_tracker.py:14`，[[02-SGLang-Scheduler事件循环]] `## 5` 决策六）是一个**自适应系数**，不是"多个信号的可配置组合"——它只调节一个数（预留比例），不是把前缀命中/等待时长/优先级这类异质信号揉进一个可调公式。

**如果要做，实现要动哪些文件**：这是本档唯一需要"设计"而非"抄现成模式"的部分——

1. **定义信号提取层**：把"前缀命中长度""等待时长""用户优先级"三个数分别暴露成可读字段。SGLang 这三个信号已经分别存在（`Req.num_matched_prefix_tokens`、隐含在 `arrival_time`、`Req.priority`），但目前只在各自的排序函数内部被单独使用，没有统一的"打分向量"抽象。
2. **定义组合层**：一个从配置解析出来的表达式或加权公式，替换 `calc_priority()`（`sglang:python/sglang/srt/managers/schedule_policy.py:237`）里的 `if/elif` 分发，改成"对每个候选请求算出一个标量分数，按分数排序"。
3. **暴露配置格式**：可以是一个简单的 YAML/TOML 权重表，也可以是一个受限表达式语言（避免档三的安全问题，见下）。

一个纯示意的配置格式长什么样（不是任何引擎的真实语法，只是把"组合"这个抽象概念钉成具体形状）：

```yaml
# 假想的 schedule_policy.yaml —— 用配置表达档一给不出的中间态
scoring:
  - signal: prefix_match_tokens   # 对应 Req.num_matched_prefix_tokens
    weight: 1.0
    normalize: by_max_in_batch
  - signal: wait_time_seconds     # 对应 arrival_time 派生
    weight: 0.3
    normalize: none
    cap: 5.0                      # 等待超过 5 秒之后不再继续加权，避免公式失控
  - signal: user_priority         # 对应 Req.priority
    weight: 2.0
    normalize: none
tie_break: fcfs                   # 分数相同时的兜底规则，仍然是档一
```

这份草图故意暴露了档二真正的难点：`cap`、`normalize`、`tie_break` 这些字段本身就是在**用配置语言重新发明一个迷你 DSL**——一旦权重表复杂到需要条件分支（"等待超过 X 秒后权重翻倍，但仅当队列长度超过 Y"），它就已经在滑向档三，只是载体还是声明式配置而不是任意代码。**档二和档三之间没有一条清晰的分界线，只有"配置表达能力"这一个连续谱**——本篇把它们分成两档，是为了讨论方便，不代表现实中存在一个非黑即白的切换点。

**能解决什么用户问题**：档一解决不了的"我的流量介于 LPM 和 FCFS 之间"——比如"前缀命中率高的请求优先，但等待超过 2 秒的请求要开始被提权，避免饿死"（正是 [[02-SGLang-Scheduler事件循环]] `## 7` 反直觉一指出的 LPM 无防饥饿机制的真实解药）。

**风险**：组合公式的正确性边界不好测——权重组合出的排序在某些边界条件下可能不满足任何单一策略都满足的不变量（比如"至少不会无限期饿死"），需要为组合层单独写不变量测试,而不是复用单一策略的测试。

### 档三 · 插：用户注册自己的类/回调

**形状**：一个抽象接口（ABC/trait/Protocol）+ 一个对外暴露的注册机制，用户在自己的代码里实现接口、注册进引擎，**不改引擎源码**。

**今天谁在这一档，要分两半说**：

- **接口形状已经具备，但注册机制没打通**：SGLang 的 `EvictionStrategy`（`sglang:python/sglang/srt/mem_cache/evict_policy.py:10`）是标准 ABC，`get_priority(node)` 是唯一契约，7 个内置实现平均代码量个位数到十几行——**这个接口本身简单到用户完全有能力自己写一个**。卡住的不是接口设计，是 `_EVICTION_POLICY_FACTORIES`（`sglang:python/sglang/srt/mem_cache/utils.py:56`）是模块级私有字典，没有导出等价于 `register_eviction_strategy(name, cls)` 的函数。
- **接口存在但粒度错配**：vLLM 的 `scheduler_cls`（`vllm/config/scheduler.py:117`）是真正意义上"用户传入任意类、引擎实例化并使用"的机制，但粒度是**整个调度器**——`SchedulerInterface` 有 17 个 `@abstractmethod`（`vllm/v1/core/sched/interface.py:38` 起），覆盖 `schedule()`、`update_from_output()`、`get_grammar_bitmask()`、`finish_requests()` 等等。用户想只换"抢占选谁"这一个决策点，也必须重新实现全部 17 个方法——等于重写一遍 `scheduler.py` 的 3037 行等价逻辑（[[03-vLLM-调度器解剖]] `## 2` 已核实这个文件行数）。
- **唯一名副其实的先例在集群路由层，不在单机调度器里**：Dynamo 的 `WorkerSelector` trait（`dynamo:lib/kv-router/src/scheduling/selector/mod.rs:34`）不仅接口存在，还有真实的独立 crate 示例（`dynamo:examples/router/custom-policy-example/`）演示怎么实现一个自定义打分策略并接入——但这解决的是"把请求路由到集群里哪个 worker"，不是"单个引擎进程内部怎么调度/驱逐"，是完全不同的一层。`## 6` 展开这个区别为什么重要。

**能解决什么用户问题**：档二解决不了的"我的排序逻辑依赖外部系统状态"——比如"按一个实时更新的业务 SLA 打分表决定谁先跑"，这种逻辑没法用静态权重公式表达，只能是任意代码。

**实现要动哪些文件（以"给驱逐策略补一个真正的档三"为例）**：

1. `sglang:python/sglang/srt/mem_cache/utils.py:56`-`75`——把私有字典换成一个模块级注册表 + 一个导出的 `register_eviction_strategy(name: str, factory: Callable[[], EvictionStrategy])` 函数。
2. `sglang:python/sglang/srt/server_args.py:460`-`461`——`add_radix_eviction_policy_choices()` 已经是"扩展 CLI 可选项"的先例，注册函数要和它配套，否则用户注册了类却过不了 `choices=` 校验（`## 7` 会展开这条"半成品"证据）。
3. 用户侧：`entry_points` 或显式 `import` 触发注册——这一步引擎团队管不到，属于插件生态设计,vLLM 的 `resolve_obj_by_qualname()`（`vllm/config/scheduler.py:191`）是另一种做法：不预注册，运行时按字符串路径动态 `import`，两种机制各有取舍（`## 5` 展开）。

**风险**：见 `## 4` 第 5 条——用户代码一旦跑进调度主循环，出错模式从"配置错误、启动时报错"变成"运行时任意异常/任意耗时"，且上游没法为用户代码的正确性和性能背书。这是三档里风险最高的一档，也是本篇 `## 4` 要重点展开的部分。

## 4. 改造路线图：今天想换一套策略，要碰哪些文件

这一节把 `## 3` 的框架落回具体路径——分别推演"今天就想做"这四件事，每件事要改几处、卡在哪。

### 换 vLLM 的驱逐策略

1. `vllm/v1/core/block_pool.py:162`-`186`——`BlockPool.__init__` 加一个 `eviction_policy` 参数，默认值复刻现有的 LIFO/FIFO 分流逻辑（保证不改默认行为）。
2. `vllm/v1/core/block_pool.py:719`-`740`——把 `free_blocks()` 内联的 `if block.block_hash is None or not self.enable_caching: ... else: ...` 抽成对策略对象的调用。
3. `vllm/v1/core/sched/scheduler.py:285`——`KVCacheManager(...)` 的构造点要多传一个参数，一路继续往上追（`Scheduler.__init__` 的调用方，即 `EngineCore` 构造 `Scheduler` 的地方）——**这是"改一个私有实现细节，但要打穿至少 3 层调用栈"**，因为 `BlockPool` 没有独立的配置对象，策略只能跟着 `KVCacheManager`/`Scheduler` 的构造参数一路透传。
4. 若要走配置文件/CLI 暴露，还要在 `vllm/config/` 下找一个恰当的位置加字段——`SchedulerConfig`（`vllm/config/scheduler.py`）目前没有任何和"驱逐"直接相关的字段（`watermark` 是准入闸门，不是驱逐排序）。

**结论**：这条路径今天完全没有开始——不是"差最后一公里"，是"连第一公里的接口都没有"。

### 换 vLLM 的调度顺序

技术上**今天就能做**，走 `scheduler_cls`：

1. 用户在自己的包里定义一个类，继承或独立实现 `SchedulerInterface`（`vllm/v1/core/sched/interface.py:38`）的全部 17 个抽象方法。
2. 把这个类的 qualname 字符串传给 `scheduler_cls`（`vllm/config/scheduler.py:117`），`get_scheduler_cls()`（`:170`-`191`）在启动期用 `resolve_obj_by_qualname()` 解析并实例化。

**但这条路径的现实代价极高**：`SchedulerInterface` 的 17 个方法里，真正和"排序"相关的可能只有一两个（`schedule()` 内部决定谁先出队），其余 15 个（`update_from_output`、`get_grammar_bitmask`、`finish_requests`、`make_stats` 等等）和排序策略毫无关系，但接口要求全部实现——**这是典型的"接口存在但颗粒度错配"**：用户为了改一件小事，被迫理解和重新实现一整个子系统。`vllm/config/scheduler.py:120`-`124` 的 docstring 附近日志（`get_scheduler_cls()` 里 `logger.warning_once(...)`，见 `vllm/config/scheduler.py:173`-`180`）本身也在提醒用户"这个接口不是公开稳定 API，兼容性不保证"——这不是本库推断，是上游自己在警告文案里承认的。

### 换 SGLang 的调度顺序

相对最省事的一条路径，但仍然要改源码，不是插件：

1. `sglang:python/sglang/srt/managers/schedule_policy.py:200`-`213`——`CacheAwarePolicy` 或 `CacheAgnosticPolicy` 枚举加一个新成员。
2. `sglang:python/sglang/srt/managers/schedule_policy.py:237`-`283`——`calc_priority()` 加一个 `elif` 分支。
3. 新写一个 `_sort_by_xxx()` 静态方法（参照 `_sort_by_longest_prefix()`，`:381`）。

三处改动全部集中在同一个 700 行左右的文件里，改动面比 vLLM 那条路径小一个数量级——**但这依然是 fork 引擎源码，不是往一个稳定接口里注册**。

### 换 SGLang 的驱逐策略——本篇找到的唯一一处"事故性档三"

理论上，用户可以在 Python 运行期做这件事而**不改一行 SGLang 源码**：

```python
from sglang.srt.mem_cache import utils as sgl_utils
sgl_utils._EVICTION_POLICY_FACTORIES["my_policy"] = MyEvictionStrategy
```

因为 `EvictionStrategy` 接口极简（`## 3` 已指出，只有一个 `get_priority(node)` 方法），且 `_EVICTION_POLICY_FACTORIES`（`sglang:python/sglang/srt/mem_cache/utils.py:56`）是模块级字典而非类内私有属性，Python 没有真正的访问控制，这个 monkeypatch 完全可行。再配合 `add_radix_eviction_policy_choices(["my_policy"])`（`sglang:python/sglang/srt/server_args.py:460`-`461`）把新名字塞进 CLI 的 `choices=` 校验列表，理论上能做到"注册一个新驱逐策略、CLI 能选、跑得起来"。

**但这不能算作 SGLang 团队设计出来的档三能力**——`_EVICTION_POLICY_FACTORIES` 前缀下划线明示这是私有实现细节，没有文档说明这是可扩展点，也没有测试覆盖"外部注册的策略能否正确工作"。用户能做到，只是因为 Python 缺乏真正的私有性，不是因为 SGLang 开了这扇门。`## 7` 会展开为什么这条"意外可行"的路径不应该被当成生产可用的方案。

### 用现有工具评估一个新策略：不需要真的改引擎源码就能先问"值不值得"

`## 3` 档二给出的例子（"前缀命中权重 × 等待时长 × 优先级"）在真的动手改 `schedule_policy.py` 之前，其实有一条更便宜的路：先在 [[01-前缀缓存差分实验-亲笔]] 的模拟器（`_lab/prefix_sim.py`）里把它实现一遍，跑一遍现成的五种工作负载，看它相对 SGLang 真实 LPM、vLLM 真实驱逐策略的差距量级——**这是本篇想强调的一个方法论**：档二/档三这类"要不要投入工程去做可插拔"的决策，不需要先把接口焊进引擎主干才能验证收益，`_lab/prefix_sim.py` 已经把 vLLM 和 SGLang 的策略行为抽成了独立的 Python 类（`## 8` 改进点 1 会具体引用），加一个新的候选类、跑一遍模拟器，就能在合入任何真实代码之前先估计"这个新策略在 `hot_cold`/`tree_branch` 这类构造出的工作负载上，相对现有两家策略的命中率差距大致是什么量级"。

这条路径本身有边界，必须重复 [[01-前缀缓存差分实验-亲笔]] `## 6` 已经说清楚的话：**模拟器只回答命中率差异，不回答性能差异**——一个组合公式即便命中率更高，它每次调度都要对候选队列里的每个请求算一遍加权分数，这个计算开销本身要不要紧，模拟器给不出答案，需要在真实调度主循环里测（这正是 `## 5` 决策五风险 A 担心的那类"用户代码拖慢主循环"的场景，档二的公式复杂度越高，这条风险就越接近档三）。**先用模拟器验证"值不值得"，再决定要不要真的动工程**——这比直接在生产代码上试错更便宜，也更符合本库"不产出实测性能数字、但可以用确定性模拟器验证行为差异"的红线（`_PLAN.md` §1 第 4 条）。

## 5. 设计决策与代价

### 决策一 · vLLM 把驱逐策略焊死在 `BlockPool` 内部,不留接口

- **为什么这样**：驱逐逻辑只有两条分支（有 hash 走 FIFO、无 hash 走 LIFO），且这两条分支背后的物理原因（GPU 局部性 vs 缓存寿命）是 vLLM 分页 KV cache 设计本身决定的，不是"可能会变"的业务规则——[[01-前缀缓存差分实验-亲笔]] `## 5` 决策三已经指出这段逻辑编码了"同一请求里越靠后的块越不可能被共享"这条先验，这条先验来自 vLLM 的**请求生命周期语义**，不是可以脱离上下文任意替换的策略参数。硬编码换来的是：这段 20 行代码不需要任何抽象开销,可以被编译器/解释器直接内联,且没有虚函数调用的性能损耗（本库推断,未实测,依据是这是一段每次块释放都会执行的高频路径代码）。
- **不这样会怎样**：如果开放接口,`BlockPool` 就要多维护一层"策略对象是否满足不变量"的校验——比如用户的策略如果让某个块永远不进驻逐队列,会造成显存泄漏且没有任何报错,这类错误在运行时才会表现为 OOM,且排查链路要跨越"用户策略代码"和"vLLM 核心代码"两个信任边界。
- **什么时候可以不这样**：当 [[01-前缀缓存差分实验-亲笔]] 这类实验证明"策略差异是命中率差异的主要来源"这件事被反复验证、且用户有真实的、和默认策略不同的先验知识时（比如某些业务场景里"最近插入的块"反而比"最近命中的块"更值钱,这与 vLLM 当前假设相反）——这时候硬编码的代价就从"从没被使用过的灵活性"变成"真实losses累积"。`## 8` 的最小可行提案就是为这种场景准备的。

### 决策二 · SGLang 把驱逐策略做成 ABC,但注册表私有

- **为什么这样**：`EvictionStrategy`（`sglang:python/sglang/srt/mem_cache/evict_policy.py:10`）的 7 个实现平均只有几行,说明 SGLang 团队本身经常需要在几种驱逐语义之间切换做实验（LRU/LFU/FIFO/MRU/FILO/Priority/SLRU 覆盖了缓存系统里几乎所有经典策略族）——**做成 ABC 首先是为了自己方便对拍,不一定是为了给外部开放**。私有字典 + CLI 只暴露 4/7 项,符合"内部实验充分、对外暴露保守"的产品化节奏:先把能想到的策略都实现出来做内部验证,再决定哪些值得作为正式承诺的公开选项。
- **不这样会怎样**：如果一开始就把全部 7 项和注册接口都公开,一旦某个策略（比如 SLRU 的 `protected_threshold` 参数在极端 workload 下表现异常）被发现有问题,团队要么背负"向后兼容"的包袱继续支持它,要么破坏性地移除——保守暴露给了团队"先内部验证、后决定要不要承诺"的余地。
- **什么时候可以不这样**：当某个未暴露的策略（比如 MRU,`sglang:python/sglang/srt/mem_cache/evict_policy.py:31`-`33`,"最近使用的先淘汰",适合一次性扫描型工作负载）已经有明确的、可复现的适用场景,且团队愿意为它写文档和维护承诺时,把它加进 `RADIX_EVICTION_POLICY_CHOICES`（`sglang:python/sglang/srt/server_args.py:328`）只是一行代码的事——**这不是本篇找到的空白,这是最容易补的空白**,`## 8` 会把它列进可改进点。

### 决策三 · vLLM 用 `scheduler_cls` 做粗粒度插槽,而不是给 `schedule()` 内部拆细粒度 hook

- **为什么这样**：`schedule()` 本身（`vllm/v1/core/sched/scheduler.py:484`）是一个 800 多行的单一函数,[[03-vLLM-调度器解剖]] `## 0` 已经指出它"没有阶段划分,只按 token 预算追赶目标"——这种设计里,排序、抢占、预算裁剪三件事在逻辑上是互相纠缠的（比如"选谁抢占"直接影响下一步"预算还剩多少"）,给单一决策点开 hook 意味着要在一个已经很长的函数内部找一个干净的切面,而这个切面目前不存在。**整体替换反而是更诚实的做法**：与其假装某个子决策可以被"干净地"抽出来单独 hook,不如坦白告诉用户"你要换,就要理解全部"。
- **不这样会怎样**：如果强行在 `schedule()` 内部某个位置插一个"排序回调"hook,而排序决策实际上和预算裁剪、抢占逻辑共享大量隐式状态（比如 `token_budget`/`input_budget` 两个局部变量,[[03-vLLM-调度器解剖]] `## 7` 踩坑 2 已指出这是两把独立的尺子）,回调函数很容易在不知情的情况下破坏这些隐式不变量,产生比"完全不给 hook"更难排查的 bug。
- **什么时候可以不这样**：如果 vLLM 未来把 `schedule()` 重构成更清晰的阶段化管线（比如显式拆出"候选筛选 → 排序 → 预算分配 → 抢占裁决"四个独立步骤,类似 SGLang 的 `PrefillAdder`（`sglang:python/sglang/srt/managers/schedule_policy.py:511`）把"批构造"独立封装成一个可单独测试的对象,[[02-SGLang-Scheduler事件循环]] `## 6` 已指出这是两家在"记账方式"上的关键差异）,细粒度 hook 才有干净的切面可插。**这是一个架构前提,不是配置项能绕过的**。

### 决策四 · SGLang 把调度策略和前缀缓存树耦合（LPM 直接查 `tree_cache`）

- **为什么这样**：[[02-SGLang-Scheduler事件循环]] `## 5` 决策二已经指出,这是 RadixAttention 作为核心设计的自然延伸——树既是缓存结构也是调度输入,不耦合反而要额外维护一份"影子索引"。
- **不这样会怎样**：耦合的代价是"想换调度策略必须理解基数树的内部状态"——`## 4` 已经展示,SGLang 换调度策略只需要碰 `schedule_policy.py` 一个文件,这看似成本低,但前提是新策略如果要用到前缀信息（比如 `## 3` 档二举的"前缀命中权重 × 等待时长"例子）,必须理解 `tree_cache.match_prefix()`（`sglang:python/sglang/srt/managers/schedule_policy.py:138` 附近的 `match_prefix_for_req()`）这套接口——耦合把复杂度**转嫁**给了想写新策略的人,而不是消除了复杂度。
- **什么时候可以不这样**：vLLM 走的是反例——调度队列完全不看前缀缓存内容（[[03-vLLM-调度器解剖]] `## 6` 已指出这不是疏漏而是架构选择）,代价是没法用前缀命中信息做排序,但好处是想写一个新调度策略,完全不需要理解 KV cache 内部实现——**耦合与否本身是"复杂度放在哪一侧"的取舍**,不是有没有技术能力做到的问题。

### 决策五 · 本篇不建议把档三做成"默认路径",三条风险逐条摊开

任务要求把风险写透，这是本篇最容易写空的一节，所以逐条钉证据，不写空话。

**风险 A · 用户代码跑在调度主循环里，一慢就拖垮整批——这不是假设，是已经发生过的事。**
SGLang 的语法编译就绪检查 `get_ready_grammar_requests()`（`sglang:python/sglang/srt/constrained/grammar_manager.py:184`-`240`）今天就跑在 `get_next_batch_to_run()` 内部（`sglang:python/sglang/srt/managers/scheduler.py:3080`），每轮调度都要先过一道最长 5ms 的忙等（默认间隔 `sglang:python/sglang/srt/environ.py:377`），受影响的不只是等语法的那个请求，是**同一轮里所有请求**（[[02-SGLang可改进点]] `## 8` 第 2 条已核实这条因果链）。语法编译逻辑是 SGLang 团队自己写的、经过审查的代码，尚且踩了"忙等拖累整批"这个坑——**如果把这个位置换成用户提交的任意排序/打分函数，同样的坑复现的概率只会更高，而且上游没有代码审查这道关卡去提前拦下它**。档二比档三在这一条上更安全：一个加权公式的最坏情况耗时是可以静态估计的（几次乘加），一段任意 Python 代码的最坏情况耗时没有上界。

**风险 B · 支持面爆炸——vLLM 自己已经在 `scheduler_cls` 的日志文案里认了这笔账。**
`get_scheduler_cls()` 在检测到用户传了自定义 `scheduler_cls` 时打的 `logger.warning_once`（`vllm/config/scheduler.py:173`-`180`）原话包含"this scheduler interface is not public and compatibility may not be maintained"——**这句话就是"支持面爆炸"这个抽象风险在源码里的具体落地**：上游团队已经预判到，一旦把核心决策组件的替换权交给用户，下一次重构 `SchedulerInterface`（比如给 17 个抽象方法里加一个新的）就必然会破坏所有自定义子类，而上游没有能力、也没有义务替每一个用户的自定义实现背兼容性。这条风险不是"可能会发生"，是 vLLM 团队在**唯一已经开放的档三通道**上，主动写进日志里的免责声明。

**风险 C · 与 CUDA Graph / overlap 调度的交互——批组成变了，图未必跟着变，但更容易掉出已捕获尺寸。**
`## 7` 坑四已经展开机制：CUDA Graph 关心的是 padding 后的 `num_tokens` 落在哪个已捕获尺寸桶里（`vllm/v1/cudagraph_dispatcher.py:72`-`91`），不关心批里具体是哪些请求——这意味着"策略改变了谁在批里"本身不直接破坏图捕获假设。真正的风险是**波动性**：一个偏向极端打分（比如硬优先级压过所有其它信号）的自定义策略，容易让批大小在"只剩高优先级请求的小批"和"预算打满的大批"之间剧烈摆动，比默认 FCFS/PRIORITY 更频繁地把某一步的 `num_tokens` 推到 `cudagraph_capture_sizes` 之外，触发 `## 0` 已确认的静默降级（[[00-总览与阅读地图]] `## 4`"CUDA Graph 掉回 eager 是完全静默的"这条硬结论）。SGLang 的 overlap 调度还多一层：`future_map`（`sglang:python/sglang/srt/managers/scheduler.py:3746`、`:3767`，[[02-SGLang-Scheduler事件循环]] `## 5` 决策三已核实）依赖"下一批的构造能引用上一批还没跑完的输出占位符"，如果自定义策略让批与批之间的请求集合变化过于剧烈（比如频繁地整批换人），这层占位符复用的收益会被稀释，但不会破坏正确性——`record_batch_in_overlap()`（`sglang:python/sglang/srt/managers/scheduler.py:3651`）的注释已经把跨 stream 张量生命周期的约束写清楚，这套机制本身是为应对"批会变化"设计的,只是没有为"批以策略允许的任意方式剧烈变化"这件事做过压力测试（本库推断，未查证是否有专门的模糊测试覆盖极端策略场景）。

**三条风险放在一起的结论**：档三不是不能做，是**不该把"用户代码跑在热路径"和"接口稳定性"这两件事都轻描淡写**。`## 8` 的最小可行提案刻意避开了这两个雷区——它给的是一个默认行为不变的**内部重构**（先把"可替换"这个能力做出来，但不承诺公开稳定接口），而不是立刻开放一个用户可以随意替换的公开插件系统。

## 6. 其他引擎的先例

任务要求点名有先例就给行号,没有就明说。逐家过一遍调研范围内的引擎:

**TensorRT-LLM——档一 + 一条完全体逃生舱,但逃生舱换的是"语言",不是"策略颗粒度"。** 默认调度器是 C++ 绑定的 `BindCapacityScheduler`（`tensorrt-llm:tensorrt_llm/_torch/pyexecutor/_util.py:3082`-`3094`）,策略本身是 `CapacitySchedulerPolicy` 枚举（`MAX_UTILIZATION`/`GUARANTEED_NO_EVICT` 等,[[01-TensorRT-LLM]] `## 3.5` 已核实）——典型档一。但存在 `use_python_scheduler` 开关（`tensorrt-llm:tensorrt_llm/_torch/pyexecutor/_util.py:3059`-`3075`）可以切到纯 Python 实现的 `PyCapacityScheduler`（`tensorrt-llm:tensorrt_llm/_torch/pyexecutor/scheduler/scheduler.py:1909`）——这条路径和 vLLM 的 `scheduler_cls` 犯了同一个"粒度错配"的毛病:换的是整套调度器的实现语言,不是某个具体策略维度。

**LMDeploy——ABC 已经搭好,但只有一个居民。** `BaseEvictionHelper`（`lmdeploy:lmdeploy/pytorch/paging/eviction_helper/base_eviction_helper.py:9`-`24`）定义了 `need_swap_in`/`evict_for_seq` 两个抽象方法,`build_eviction_helper()` 工厂（`lmdeploy:lmdeploy/pytorch/paging/eviction_helper/__init__.py:7`-`17`）按名字分发——但生产代码里只有 `RecomputeEvictionHelper` 一个子类,`'copy'` 这个历史选项已经被折叠进 `'recompute'` 并打了废弃警告。**这是"架构上预留了插槽,产品上从未用满"的又一个例子**,和 SGLang 驱逐策略"实现了 7 个但只暴露 4 个"是同一类现象的不同表现形式:工程团队倾向于先把接口做成可扩展的形状,再决定要不要真的填满它。

**Dynamo——本库调研范围内唯一的真档三,但在集群路由层,不在单机调度器里。** `WorkerSelector` trait（`dynamo:lib/kv-router/src/scheduling/selector/mod.rs:34`）不只是接口存在,还有配套的独立 Cargo crate 示例（`dynamo:examples/router/custom-policy-example/`,[[09-NVIDIA-Dynamo]] `## 5` 已核实其"文档注释写`Default implementation matching the Python _cost_function`""说明这是从 Python 原型移植的算法"两条证据）,证明这条接口真的被用来插过至少一次自定义实现。默认实现 `DefaultWorkerSelector::worker_cost()`（`dynamo:lib/kv-router/src/scheduling/selector/default.rs:333`）和自定义实现是**平等的**——用户的 crate 不需要理解或重写 KV 索引、事件订阅这些配套系统,只需要实现一个"给定候选 worker 列表,打一个代价分数"的函数。

**这个对比本身就是本篇最重要的发现之一**：Dynamo 能做到干净的档三,恰恰因为它选的切面是"选哪个 worker"——这是一个天然独立、输入输出边界清晰的决策点（候选列表进,一个 worker 选择出）。vLLM/SGLang 单机调度器里的排序/驱逐决策,天然和"预算裁剪""前缀树状态""抢占逻辑"这些相邻决策纠缠在一起（`## 5` 决策三已展开）——**同样是"插策略",在决策边界天然清晰的地方（跨 worker 路由）比在决策边界天然模糊的地方（单进程内部排序）容易做得多**。这不是 Dynamo 团队比 vLLM/SGLang 团队更懂插件设计,是问题本身的形状不同。

**结论**：**12 家引擎里,在"单引擎进程内部的调度顺序/驱逐策略"这一层,没有一家做到档三**——SGLang 的 `EvictionStrategy` ABC 形状上最接近,但注册表私有,不构成生产可用的档三;vLLM 的 `scheduler_cls` 是真档三,但粒度错配到"整个调度器"而非"具体策略维度"。真正干净的档三先例出现在集群路由这一层（Dynamo）,不是本篇讨论的引擎内部这一层。

其余四家（LightLLM/llama.cpp/TGI/Tokasaurus）本篇不重新走读——[[02-调度策略横向对比]] 已经逐一核实过它们的调度顺序策略，结论收在一张表里可以直接借用：LightLLM 是"FCFS 端（不重排，只做准入门禁）"、llama.cpp 是"中间偏前缀感知（slot 选择用 LCP 相似度，但不重排队列）"、TGI 是"FCFS 端（前缀缓存只减重算量）"、Tokasaurus 是"FCFS 端（`greedy_prefill` 默认关闭重排）"（[[02-调度策略横向对比]] `## 6` 对照表原文）——**四家全部停在档一都不到的水平：连一个命名策略的选项都没有，只有唯一一条硬编码路径**。这进一步收紧 `## 6` 的结论：不是"vLLM/SGLang 落后于同行"，是**这一层的可编程化在全行业范围内都还没起步**，SGLang 的 6 种调度策略 + 7 种驱逐策略反而是本库调研范围内已知的最高水位。

## 7. 踩坑与反直觉

**坑一 · "SGLang 的驱逐策略已经可插拔"是一句一半对一半错的话。** `EvictionStrategy` ABC 形状齐全、7 个实现齐全,乍看已经是档三——但 `_EVICTION_POLICY_FACTORIES`（`sglang:python/sglang/srt/mem_cache/utils.py:56`）是私有字典,CLI 只暴露 4/7,`add_radix_eviction_policy_choices()`（`sglang:python/sglang/srt/server_args.py:460`）在全仓零调用（`## 2` 已列出）。三件事叠在一起说明:**"接口长得像插件"和"这是一个被支持的插件系统"是两回事**——前者是代码形状,后者需要文档、注册 API、测试覆盖三样都到位。`## 4` 演示的 monkeypatch 路径能跑,但那是钻了 Python 没有真正私有性的空子,不是 SGLang 团队交付的能力。

**坑二 · vLLM 的 `scheduler_cls` 是本篇读到的、上游自己在文档字符串里承认"不是公开 API"的扩展点。** `get_scheduler_cls()` 在使用自定义类时打的 `logger.warning_once`（`vllm/config/scheduler.py:173`-`180`）原文提到"scheduler interface is not public and compatibility may not be maintained"——**这条能力真实存在、技术上今天就能用,但上游自己没有承诺维护它的兼容性**。这和"档三不存在"不同,是"档三存在但没有稳定性保证",对生产用户的意义几乎一样危险:今天写的自定义 `Scheduler` 子类,下一个 vLLM 版本可能因为 `SchedulerInterface` 新增/修改抽象方法而直接跑不起来。

**坑三 · SGLang 调度策略的"档一"比 vLLM 丰富,容易被误读成"SGLang 更可插拔",但改动源码的成本几乎一样。** `## 4` 已经推演过:vLLM 新增一个调度策略要打穿 `request_queue.py` + 上层调用方（结构性障碍更大),SGLang 新增一个调度策略只碰 `schedule_policy.py` 一个文件（结构性障碍更小)——**但两者都是"改引擎源码后重新构建",不是"用户在自己的包里写代码"**。SGLang 选项更多,只是说明它的档一覆盖面更宽,不代表它离档三更近一步——档一和档三是两个独立的维度,不是同一条路上的两个里程碑。

**坑四 · CUDA Graph 对"批组成"的敏感点不是身份,是数量。** 本库已经确立的一条硬结论（[[00-总览与阅读地图]] `## 4`)指出"CUDA Graph 掉回 eager 是完全静默的"——`cudagraph_capture_sizes`（调用点 `vllm/v1/cudagraph_dispatcher.py:72`-`91`）是一个预先算好的**尺寸**子集,运行时把真实 `num_tokens` 向上填充到最近的已捕获尺寸,`capture_model()`（`vllm/v1/worker/gpu_model_runner.py:6937`-`7041`）不关心这一步具体是哪些请求组成的批,只关心 padding 后的 token 数落在哪个桶。**这意味着可插拔调度策略只要不系统性地把批大小分布推出已捕获尺寸集合之外,就不会触发这条静默降级**——风险不是"策略换了 CUDA Graph 就会坏",而是"一个让批大小波动性显著变大的自定义策略(比如极端偏向优先级、导致批大小在 1 和 max_num_seqs 之间剧烈摆动),会让更多步落进未捕获尺寸,进而更频繁地静默走 eager"——这条因果链目前没有任何监控默认打开(`--cudagraph-metrics` 默认关闭,`vllm/config/observability.py:68`),用户几乎不可能在不主动排查的情况下发现自己的自定义调度策略正在拖慢 CUDA Graph 命中率。

**坑五 · SGLang 的 7 个驱逐策略名字，是通用缓存系统的教科书术语，不是推理引擎自创的概念。** `LRUStrategy`/`LFUStrategy`/`FIFOStrategy`/`MRUStrategy`/`FILOStrategy`/`SLRUStrategy`（`sglang:python/sglang/srt/mem_cache/evict_policy.py:16`-`65`）逐一对应操作系统页面置换、数据库缓冲池、CDN 边缘缓存里几十年前就有的经典策略——`SLRUStrategy` 的 Segmented LRU（分段保护）尤其是 Web 缓存领域的老技术（`sglang:python/sglang/srt/mem_cache/evict_policy.py:49`-`65` 的 docstring 原文用"Probationary"/"Protected"两段式命名，这是 SLRU 的标准叫法）。这说明 KV 前缀缓存的驱逐问题，本质上就是通用缓存置换问题的一个特例——**没有理由认为 LLM 推理场景需要发明全新的驱逐算法族，真正 LLM 特有的是"请求内位置先验"这类结构信息**（[[01-前缀缓存差分实验-亲笔]] `## 7` 坑二已指出 vLLM 的倒序释放正是这类特有先验的例子，而它并不在 SGLang 这 7 个通用策略的覆盖范围内——`## 3` 档二想解决的"多因子组合"，本质就是想把"通用缓存置换算法"和"LLM 请求结构先验"这两类不同来源的信号揉进同一个排序函数）。

## 8. 可改进点

**改进点 1（最小可行提案）· 给 `BlockPool.free_blocks()` 补一个可插拔的驱逐排序接口,以 SGLang 的 `EvictionStrategy` 为形状参照。**

- **现状**：`vllm/v1/core/block_pool.py:719`-`740` 的驱逐排序 100% 硬编码,`__init__`（`:162`-`186`）不接受任何策略参数——这是本篇 `## 2` 找到的、全库范围内可编程程度最低的一个决策点,同时又是 [[01-前缀缓存差分实验-亲笔]] 证明"策略差异是命中率差异主要来源"的那个决策点。两件事叠在一起,是本篇认为收益/改动比最高的一处。
- **改哪里**：
  1. 新增一个小接口（可以直接照抄 `sglang:python/sglang/srt/mem_cache/evict_policy.py:10`-`13` 的 `EvictionStrategy` 形状,一个方法、返回一个可比较的排序键）。
  2. `BlockPool.__init__`（`vllm/v1/core/block_pool.py:162`）加一个可选参数,默认值复刻现有逻辑(保证零行为变化)。
  3. `free_blocks()`（`:719`-`740`）把内联 if/else 换成对策略对象的调用。
  4. `Scheduler.__init__`（`vllm/v1/core/sched/scheduler.py:285` 附近）透传新参数——`## 4` 已指出这一步要打穿至少 3 层调用栈,是本提案里工作量最大的部分,但机械、低风险。

接口形状的具体样子（伪代码,不是真实 vLLM 源码,仅示意最小改动面）：

```python
# 新文件，参照 sglang:python/sglang/srt/mem_cache/evict_policy.py:10-13 的 ABC 形状
class BlockEvictionOrdering(ABC):
    """决定一个刚释放的块，应当被优先驱逐还是最后驱逐。"""

    @abstractmethod
    def classify(self, block: "KVCacheBlock") -> Literal["evict_first", "evict_last"]:
        ...


class DefaultV1EvictionOrdering(BlockEvictionOrdering):
    """今天 free_blocks() 里内联的逻辑，原样搬进来，零行为变化。"""

    def classify(self, block: "KVCacheBlock") -> Literal["evict_first", "evict_last"]:
        # 对照 vllm/v1/core/block_pool.py:729-736 的现有 if/else
        if block.block_hash is None:
            return "evict_first"   # LIFO：无 hash 的块，为 GPU 局部性优先复用
        return "evict_last"        # FIFO：有 hash 的块，为缓存寿命最后复用


class BlockPool:
    def __init__(self, ..., eviction_ordering: BlockEvictionOrdering | None = None):
        self.eviction_ordering = eviction_ordering or DefaultV1EvictionOrdering()

    def free_blocks(self, ordered_blocks):
        blocks_to_evict_last, blocks_to_evict_first = [], []
        for block in ordered_blocks:
            block.ref_cnt -= 1
            if block.ref_cnt == 0 and not block.is_null:
                bucket = self.eviction_ordering.classify(block)
                (blocks_to_evict_first if bucket == "evict_first"
                 else blocks_to_evict_last).append(block)
        self.free_block_queue.prepend_n(blocks_to_evict_first)
        self.free_block_queue.append_n(blocks_to_evict_last)
```

这个草图刻意**不**引入"配置字符串 + 工厂 + CLI choices"这一整套 SGLang 式的公开选项机制——那是下一步的事，且要先解决 `## 5` 决策五指出的支持面问题。第一步只做"把决策点从内联逻辑挖出来变成一个可注入的对象"，`eviction_ordering` 参数默认 `None` 意味着不传就是今天的行为，这是一个**纯重构**，不改变任何默认路径的输出。

- **为什么是这一处而不是调度顺序**：调度顺序（`request_queue.py`）已经有干净的工厂函数（`create_request_queue()`,`:201`-`208`),结构性障碍主要是"选项少",不是"没有可插拔的形状"——补齐它只是加枚举值的工作量。驱逐策略是**结构性障碍**:今天连"传一个策略对象进去"这件事本身都做不到。优先修结构性障碍,而不是优先加选项。
- **怎么验证不退化**：[[01-前缀缓存差分实验-亲笔]] 已经有现成的回归测试基础设施——`_lab/tests/test_lab.py:329` 的 `test_vllm_eviction_is_recency_based_not_insertion_fifo` 就是专门锁死"vLLM 真实驱逐策略优于稻草人 FIFO"这条不变量的测试(那篇 `## 7` 坑一记录的、作者自己第一次建模出错又改对的教训)。给 `free_blocks()` 做接口重构后,应该新增一条等价测试:**默认策略对象跑出来的结果,必须和重构前的硬编码逻辑在 `_lab/prefix_sim.py` 的全部五种工作负载上逐位相同**——这是纯重构(不改变默认行为)的标准验证方法,不需要等真实 GPU 环境,`_lab/prefix_sim.py` 的模拟器已经把 vLLM 的驱逐逻辑抽象成了独立的 Python 类（`VllmBlockCache`,`_lab/prefix_sim.py:138`-`160`),可以直接在合入 vLLM 之前用它验证接口设计本身是否自洽。

**改进点 2 · 把 SGLang 未暴露的 3 个驱逐策略（FIFO/MRU/FILO）补进 CLI `choices`。**

- **现状**：`sglang:python/sglang/srt/mem_cache/evict_policy.py` 已经实现了全部 7 个策略,`RADIX_EVICTION_POLICY_CHOICES`（`sglang:python/sglang/srt/server_args.py:328`）只暴露 4 个。
- **风险**：几乎没有——这三个策略已经有完整实现和统一接口,补充暴露只是把已经跑得起来的代码接上 CLI 校验,不引入新的正确性面。**这是本篇找到的、改动成本和收益比最悬殊的一条**,但正因为它太容易,更可能是"团队还没来得及决定要不要为它们承诺文档和兼容性",而不是遗漏——本库未查证是否已有内部计划,标「未查证」。

**改进点 3 · 把 `add_radix_eviction_policy_choices()` 从"零调用的函数"变成"有文档的扩展点",或者干脆删掉。**

- **现状**：`sglang:python/sglang/srt/server_args.py:460`-`461` 定义了这个函数,全仓零调用（`## 2` 已核实)——它和 `add_grammar_backend_choices()` 等一族函数结构相同,大概率是留给下游打包/插件项目在导入期调用的钩子,但没有任何文档说明这个用法,也没有配套的"如何注册对应的策略实现"的说明。
- **改进方向**：如果这确实是有意为之的扩展点,应该在其附近补一条注释,说明"扩展 choices 列表之后,还需要往 `_EVICTION_POLICY_FACTORIES`（或未来的公开注册表）里补对应实现,否则会在选中这个选项时于 `get_eviction_strategy()`（`sglang:python/sglang/srt/mem_cache/utils.py:67`）抛 `ValueError`"——现状是这条依赖关系完全隐式,新读者(甚至新加入的 SGLang 贡献者)不看两个文件的源码不会知道这两处需要配对修改。**这是本篇 `## 7` 坑一诊断出的具体病灶**,修复成本是补一段注释或者一个校验断言,不需要改变行为。

**改进点 4 · 给 vLLM 的 `scheduler_cls` 补一份"允许覆写哪些方法、哪些方法改了会破坏契约"的文档，而不是只有一句笼统的兼容性免责声明。**

- **现状**：`get_scheduler_cls()`（`vllm/config/scheduler.py:170`-`191`）目前给自定义调度器类的唯一反馈是一句 `logger.warning_once`（`:173`-`180`），内容是"这个接口不是公开的，兼容性可能不维护"——这是一句**面向全体的免责声明**，没有区分 `SchedulerInterface`（`vllm/v1/core/sched/interface.py:38`）17 个抽象方法里哪些是"大概率跨版本稳定"（比如 `add_request()` 这类只处理接入的方法），哪些是"每次调度器重构最先动刀"（比如 `schedule()` 本体，[[03-vLLM-调度器解剖]] 已经指出这是全库最大的单一函数，3037 行，历史上显然是持续被修改的高频区域）。
- **改进方向**：不需要承诺"公开 API"这么重的事，只需要在 `SchedulerInterface` 的类文档字符串（`vllm/v1/core/sched/interface.py:38` 附近）里补一张"每个抽象方法的历史变更频率/耦合面"的简表，让用户在决定要不要走 `scheduler_cls` 这条路时，能预判自己的自定义类大概率会在哪个版本升级点上坏掉，而不是完全等到运行时 `AttributeError`/`TypeError` 才发现。
- **代价与反驳**：维护这张表本身需要持续跟踪 `SchedulerInterface` 的变更历史，如果没人认领这项工作，表会比代码更快过时，反而制造虚假的稳定性预期——这也是为什么 `## 5` 决策五认为"用文档管理支持面爆炸的风险"本身就是一个需要持续投入的承诺，不是写一次就完事的工作。**这条改进点的优先级本篇认为低于改进点 1**：改进点 1 是纯代码重构、验证方法明确；这一条是文档 + 长期维护承诺，落地难度更高、更依赖上游团队的意愿，本库未查证上游是否已有相关讨论。
