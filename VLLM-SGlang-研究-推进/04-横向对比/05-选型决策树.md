> **本篇取证基准**：`vllm` @ `7ca49fbe`（2026-08-22）；其余 11 个引擎的 sha 见 `_lab/out/repo_stats.json` 的 `ref` 字段（`sglang` `15a43983`/2026-08-22、`tensorrt-llm` `75b023cd`/2026-08-22、`lmdeploy` `1263d5cd`/2026-08-21、`lightllm` `87881ae7`/2026-08-21、`mlc-llm` `9fa644f5`/2026-08-17、`llama.cpp` `2c6b141e`/2026-08-22、`tgi` `b4adbf2f`/2026-03-21、`dynamo` `2a6da14c`/2026-08-22、`ktransformers` `95009ea6`/2026-08-21、`mooncake` `3b5a5941`/2026-08-22、`tokasaurus` `72689052`/2025-08-19）。本篇引用跨引擎源码时一律加 `引擎名:` 前缀；不带前缀的引用默认指 `vllm`。
> **本篇不含实测性能数字**，所有判据都是**机制性**的：某个引擎有没有某个能力、某个能力在什么条件下失效。

## 0. 结论先行

- **这篇不给排名，给判据。** `03-其他引擎/11-开源推理引擎谱系图.md` 的决策四已经把理由讲透：任何"综合最强"的结论都是替读者的具体场景做了一次未经同意的加权。本篇往前再走一步——谱系图止步于"画出问题族和技术路线两个维度"，本篇要做的是把这两个维度收窄成**可以被一个具体项目直接拿去用的分叉序列**：每一叉问的都是"你的场景里这个数字/布尔值是什么"，不是"你追求什么"。
- **决策树的根不是"选哪个引擎"，是"你的负载是什么形态"。** 在线多租户服务、单用户端侧、大批量离线生成三种形态，各自默认了完全不同的资源假设（`03-其他引擎/11` `## 3.1` 已按问题族分过一次，本篇把这条分类直接当成决策树的第一层，因为它是本篇找到的**最先能排除掉多数引擎**的一个分叉）。不先回答这一问，后面"要不要前缀缓存""要不要投机解码"这些问题全部没有意义——一个端侧单用户助手根本不会遇到"请求排队"这件事，讨论它的调度策略是文不对题。
- **能力矩阵（`## 2`）132 个格子里，21 个标了「未查证」，2 个标了「不适用」（Mooncake/Dynamo 本身不是推理引擎，绝大多数格子对它们不构成有意义的问题）。** 这不是偷懒——是诚实地承认本库这一轮手工 grep 覆盖不到的地方，比瞎猜一个"有"或"无"更负责任。查不到的下一步该去哪核实，`## 2` 每一条都留了路径。
- **三个具体场景（`## 4.4`）从根走到叶，每一步都写清楚为什么这么分叉——包括一步"分叉之后发现原来的判据不够用，必须再追问一个新判据"的真实案例（场景 B，RL rollout 引擎）。** 这条留在这里提前说：决策树不是一次性把所有判据列全就能机械套用的表格，走到某个节点才会发现"原来这里还该问一句"是正常现象，本篇如实记录了这一次。
- **`## 6`「这些情况下别听我的」是硬性的一节，不是免责声明式的客套。** 本篇明确回答不了"哪个更快""哪个生态更成熟""你的团队能不能撑住"这类问题——不是本篇偷懒不答，是这几类问题本身需要的证据（实测数据、活跃度长期观测、你自己团队的技能盘点）超出了本库"读源码"这个方法论能产出的范围。

## 1. 它在系统里的位置

`00-总览与阅读地图.md` §5 路线 B「我要在 vLLM 和 SGLang 之间选一个」把本篇列为收束——但本篇的范围比路线 B 描述的更宽：读完 `03-其他引擎/11-开源推理引擎谱系图.md` 会发现"在 vLLM 和 SGLang 之间选"这个问题本身经常问错了对象，真正的第一个问题往往是"你需不需要一个能扛并发的集群引擎"。本篇因此覆盖全部 12 个引擎，不只是 vLLM/SGLang 两家。

和 `[[04-工程规模与代码结构对比]]`、`[[01-API兼容性横向对比]]`、`[[02-调度策略横向对比]]`、`[[03-KV缓存与前缀复用横向对比]]` 的分工：那几篇（部分规划中）回答的是"这两个引擎在某个具体子系统上分别怎么做、代价是什么"；本篇不重复它们的机制细节，只做一件事——**把那些机制细节收束成一组能直接拿去用的判定问题**，指向对应篇目让读者去查证细节。和 `[[11-开源推理引擎谱系图]]` 的分工最需要说清：谱系图回答"这 12 个项目分别落在技术空间的哪里"，是一张地图；本篇回答"给定你的坐标，你该走去地图上的哪一点"，是一条路线，不重复谱系图已经画好的两维矩阵，只复用它的结论作为判据的输入。

本篇不产出任何新的性能数字，也不重新做取证——`## 2` 的代码地图里，能追到已有篇目的优先追已有篇目，本篇自己新增的引用只覆盖已有篇目没有直接给出、但能力矩阵需要的空白格。

## 3. 判据的定义

决策树只能用下面这 8 个判据分叉，每一个都要求"能用一个数字、一个比例或一个布尔值回答"，不允许"你追求 XX 吗"这种形容词式提问。

| # | 判据 | 怎么测量 | 典型阈值/判法 |
|---|---|---|---|
| Q1 | 负载形态 | 问自己：下一步该处理哪个请求，是由外部客户端并发实时决定的（多个陌生请求方，随时可能有新请求）、还是由你一个人交互式决定的（一次只有一个人在等）、还是你提交任务前就已经拥有完整输入列表的？ | 三选一：在线多租户 / 单用户端侧 / 离线批量 |
| Q2 | GPU 可用性与显存充裕度 | 有没有独立显卡；若有，"模型参数量 × 每参数字节数（FP16 通常 2 字节，量化后更低）+ 并发数 × 单请求 KV cache 占用" 是否 ≤ 显存容量 | 装得下 / 装不下但差距在 1~3 倍（可能靠异构卸载补） / 完全没有独显 |
| Q3 | 共享前缀比例 | 抽样最近一批请求的 prompt，算"和最常见公共开头（system prompt/few-shot 模板）重合的 token 数" ÷ "平均 prompt token 数" | 经验上 >30% 算"高"，<10% 算"低/无"，中间地带按 `[[03-SGLang-RadixAttention与前缀缓存]]` `[[04-vLLM-KV缓存与前缀缓存]]` 的实现细节自行判断 |
| Q4 | 输出长度同质/异质 | 统计一批请求输出 token 数的变异系数 CV = 标准差 / 均值 | CV 明显偏离 0（比如 >0.5）算"异质"；CV 接近 0（定长输出，如固定长度摘要/embedding）算"同质" |
| Q5 | 结构化输出/Agent 负载占比 | 这批请求里，需要 JSON Schema 约束、工具调用、多轮规划（Agent）的请求占比 | 高（这类请求是主要负载）/ 低（偶尔用一下，不是架构设计的中心） |
| Q6 | 是否需要跨机 | 用 Q2 的"装得下"标准重算一遍，但把"模型权重"换成"你要的总 QPS × 每请求资源"——单机 GPU 数量能不能顶住 | 顶得住 / 顶不住，需要多机 |
| Q7 | 团队运维能力 | 团队里有没有人能读、能改 C++/CUDA/nanobind 代码；有没有现成的 K8s 集群与运维经验；能不能接受核心依赖是一个非官方 fork | 三个子问题各自是/否，任一为否都会排除对应的叶子 |
| Q8 | 模型架构白名单匹配度 | 你要跑的模型架构，是否在目标引擎当前快照公开声明支持（或已验证）的架构列表里 | 在 / 不在——这条判据的答案**会随时间变化**，必须现查，本篇给不出静态答案 |

### 4.5 三个具体场景的完整走查

**场景 A · 企业内部多租户对话服务，长 system prompt，输出长度差异大**

1. Q1：外部（内部员工/客户）持续提交对话请求，有并发排队 → **在线多租户**（分支 A）。
2. Q2'：假设企业已有 A100/H100 级别集群，能装下常见的 7B~70B 模型权重与并发 KV cache → **装得下**，继续往下。
3. Q7：假设团队以 Python 为主，没有专职维护 C++/CUDA 构建链的能力，也不追求 NVIDIA 全家桶量化矩阵 → **否**，跳过 TurboMind/TensorRT-LLM 这条支线。
4. Q3：题目直接给出"长 system prompt" → 每个请求的公共开头占比通常显著超过 30% → **高**。
5. Q5：题目没直接说，取决于这个对话服务是否要接工具调用/Agent 编排。若是纯问答场景 → **否** → 落到"vLLM 或 SGLang 均可"这一格，留给 `## 6` 的运维/生态判据；若还要接结构化 JSON 输出、工具调用较多 → **是** → 【叶 A3】SGLang。
6. Q4：题目给出"输出长度差异大" → CV 明显偏离 0 → **异质** → 反过来印证连续批处理在这个场景里收益显著（不是走到静态批处理那条死路），确认前面选的引擎家族是对的，不需要回头。
7. 结论：这个场景落在 **【叶 A3】SGLang**（若结构化输出/Agent 负载重）或 **【叶 A3/A4】vLLM/SGLang 均可**（若是纯问答）——本篇不替读者在两者之间做最后一步选择，理由见 `## 6` 第 2 条。

**场景 B · RL 训练的 rollout 引擎，大批量、小模型、离线、要频繁更新权重**

1. Q1：提交前已有完整一批 rollout prompt，不追求单条请求的低延迟，追求总吞吐 → **离线批量**（分支 C）。
2. 分支 C 的第一问：小模型 + 超高 QPS + 高度重复采样 → 题目里的"大批量、小模型"直接命中，看起来应该直接落到【叶 C1】Tokasaurus。
3. **但这里必须先停下来追问一个分支 C 原本没有显式列出的判据**：RL rollout 有一个分支 A/B/C 三选一时没考虑到的特殊约束——"要频繁更新权重"（策略每轮迭代都要把新参数同步给推理侧）。这正是 `## 7` 要记录的一次真实"走到节点才发现该多问一句"的案例。检查现有证据：`00-总览与阅读地图.md` §4 已经查实 vLLM 有 `enable_sleep_mode` 这类支持权重换入换出的机制，SGLang 有 `/init_weights_update_group` 这个专门给 RLHF 场景热更新权重的端点（`sglang:python/sglang/srt/entrypoints/http_server.py:1339`，`[[01-API兼容性横向对比]]` `## 2` 已引用）。本库现有篇目里**没有找到 Tokasaurus 支持"服务运行期间热替换模型权重"的证据**——它的设计重心是"同一批权重上跑大量重复采样"，不是"权重本身要频繁变"。
4. 新判据：需要频繁热更新权重吗？
   - **是**（典型 RL 训练循环，每几十到几百步同步一次策略权重）→ 优先 **vLLM 或 SGLang**，用它们的离线批量调用模式 + 权重热更新接口，而不是 Tokasaurus——即使 Tokasaurus 在"大批量小模型"这一条上分数更高，"频繁换权重"这一条它没有对应机制，选它会在这条约束上直接卡住。
   - **否**（策略权重相对稳定，比如做一次性大规模合成数据生成，模型不换）→ 可以考虑 **【叶 C1】Tokasaurus**，换取比 vLLM/SGLang 更低的调度开销（13,219 行骨架，专为这一个工作点做过裁剪），但要接受协议层的收窄（E39）。
5. 结论：这个场景的正确走法不是"三条都满足就选 Tokasaurus"，是**在分支 C 的第一问之后，追加"权重更新频率"这一问，且这一问的答案能推翻第一问给出的初步结论**——这正是本篇标题强调"每个分叉必须可判定"背后想避免的反面教材：可判定不等于判据齐全，遗漏一个关键判据一样会导向错误的叶子。

**场景 C · 笔记本上给单个用户跑一个本地助手，无独显**

1. Q1：一次只有一个人在交互式使用 → **单用户/端侧**（分支 B）。
2. Q2：题目直接给出"无独显" → **无独立显卡**。
3. 分支 B 的下一问：需要跨 iOS/Android/浏览器多平台用同一份代码部署吗？题目场景是"笔记本"，没有提到移动端/浏览器打包需求 → **否**。
4. 结论：落到 **【叶 B1】llama.cpp**——GGUF 量化模型 + CPU 后端（若笔记本有集成显卡，还能用 Vulkan/Metal 这类后端，`[[05-llama.cpp-server]]` `## 1.1` 已列出 16 条 `register_backend()`），固定 slot 单机部署已经够用，不需要 MLC-LLM 那套面向多平台 AOT 编译的复杂度。
5. **什么时候这个推荐是错的**：如果这个"本地助手"以后要打包成 iOS/Android App 或者要跑进浏览器（WebGPU），从项目一开始就该选 MLC-LLM——llama.cpp 也有 `ggml-webgpu/`（55 文件/20,394 行，`[[05-llama.cpp-server]]` `## 1.1`）,但 MLC-LLM 的"一份 Relax IR、多平台 `Target`+`BuildFunc` 打包"（`[[06-MLC-LLM]]` `## 5` 决策一）是为这个需求专门设计的架构核心，llama.cpp 的跨平台是"16 条后端各自独立实现"（`[[05-llama.cpp-server]]` `## 4.2` 已指出 CPU 后端代码量比 CUDA 后端还大，因为没有库可借力），两种"跨平台"的工程代价结构不同。

## 5. 判据的设计决策与代价

每条判据都是一次"用什么来代表现实"的取舍。按 `## 3` 的编号逐条给出三样：为什么这样判 / 判错会怎样 / 什么时候这个判据本身失效。

### Q1 · 负载形态（在线多租户 / 单用户端侧 / 离线批量）

- **为什么这样判**：这是三个问题族里唯一一个能在**动手写任何代码之前**就回答的问题，而且它直接决定了后面所有判据是否有意义——族 B（端侧）根本不会遇到"请求排队"，讨论 Q3 共享前缀比例对它没有意义；族 C（离线批量）不需要"延迟 SLA"，讨论投机解码的"GPU 有没有吃饱"这个前提本身就要重新定义（离线场景 GPU 利用率的目标本来就是打满，投机解码在这里的价值判断和在线场景不同，见 `99-本质总结-亲笔.md` 原理 5 第三行"高并发把 GPU 喂饱后，草稿是纯浪费"——离线批量场景常年处在这个"喂饱"状态）。
- **判错会怎样**：把一个实际是"端侧单用户"的场景误判成"在线多租户"，会选出 vLLM/SGLang 这类为集群并发设计的引擎，装起来发现调度器、前缀缓存这些复杂度在单用户场景下完全用不上，纯是维护负担；反过来把"在线多租户"误判成"离线批量"去选 Tokasaurus，会在它主动拒绝 streaming（E39）的地方直接卡死交互式产品。
- **什么时候这个判据本身失效**：负载形态不是恒定的——很多产品白天是"在线多租户"（用户交互），夜间批量跑"离线批量"任务（比如夜间生成第二天的推荐文案）。这种双峰负载下，Q1 的答案是"两个都是"，意味着可能需要两套部署（甚至两个引擎），而不是从决策树上只走一条分支到底；本篇的决策树默认负载形态单一，双峰场景需要读者自己把两条分支都走一遍。

### Q2 · GPU 可用性与显存充裕度

- **为什么这样判**：显存装不装得下是一道纯算术题（参数量 × 每参数字节数 + KV cache 预留 vs 显存容量），是所有判据里**误差最小**的一个——不像"共享前缀比例"那样需要抽样估计，这个数字理论上能精确算出来（当然实际还要留 buffer 给激活值、CUDA context 开销等，本篇给的是主项，不是精确公式）。
- **判错会怎样**：低估了 KV cache 的占用（只算了权重，忘了乘并发数和序列长度），会在生产环境里遇到"模型能加载但一有并发就 OOM"这种上线后才暴露的故障——这类错误比"一开始就装不下"更隐蔽，因为单请求测试时完全不会触发。
- **什么时候这个判据本身失效**：量化会显著改变这道算术题的系数（FP16 的 2 字节/参数在 INT4 量化后变成 0.5 字节/参数，四倍差距），如果读者在做这道算术题时用的是权重的原始精度而不是实际部署精度，算出来的"装不下"结论可能是假的——这正是 KTransformers、llama.cpp 这类引擎存在的意义：把"装不下"这件事往后推。

### Q3 · 共享前缀比例

- **为什么这样判**：前缀缓存/RadixAttention 的收益来源就是"请求间共享前缀"（`99-本质总结-亲笔.md` 原理 5 第二行），用实际测量的比例而不是"我觉得应该有共享"这种直觉去判断，是因为直觉在这里经常错——比如"多轮对话"直觉上像是高共享（同一个用户反复带着历史），但如果每轮历史都在增长且很少有两个用户问出相同的历史,共享的可能只是一个很短的 system prompt,占比未必高。
- **判错会怎样**：高估共享比例会让团队为一个几乎用不上的前缀缓存机制付维护成本（`[[04-vLLM-KV缓存与前缀缓存]]` `## 5.1` 已指出块哈希要混入 LoRA/多模态/`cache_salt` 等额外键，这本身有正确性代价）；低估共享比例则会选一个没有前缀复用机制的引擎（比如按 Q3=低走到 TGI/LightLLM 这条支线），错过本可以拿到的显存/吞吐收益。
- **什么时候这个判据本身失效**：如果请求量本身很小（比如内部工具，日请求量几十条），共享比例算出来再高，前缀缓存的绝对收益也小到可以忽略——这条判据在"负载规模本身不大"的场景下参考价值有限，此时更该问"要不要引擎"而不是"要不要前缀缓存"。

### Q4 · 输出长度同质/异质（CV 变异系数）

- **为什么这样判**：连续批处理的核心收益来自"允许提前完成的请求腾出位置给新请求，而不是等批次里最慢的那个"，这个收益的大小直接取决于批内输出长度的离散程度——`99-本质总结-亲笔.md` 原理 5 第一行已经把这条写死："同质输入 + 离线批量时收益接近 0"。CV 是离散程度最直接的统计量，比"看起来长短不一"这种描述更可复核。
- **判错会怎样**：把异质负载误判成同质，会低估连续批处理的价值，可能选了一个更简单但吞吐更差的静态批处理方案；反过来把同质负载（比如批量生成固定长度的 embedding）误判成异质，会为一个用不上的复杂调度器付维护成本——这个方向的错误尤其容易发生在"该用离线批量框架的场景，却因为路径依赖选了在线服务引擎"。
- **什么时候这个判据本身失效**：CV 是一个静态统计量,但线上负载的输出长度分布会随产品功能变化而变化(比如新增了一个"生成长报告"的功能,原本 CV 很低的产品突然变得异质)——这条判据需要定期重新测量,不是选型时算一次就一劳永逸。

### Q5 · 结构化输出/Agent 负载占比

- **为什么这样判**：这条判据不是"要不要支持结构化输出"（`## 2` 能力矩阵显示 vLLM/SGLang 都支持），是"结构化输出/Agent 这类工作负载在你的请求总量里占多大比例"，因为占比高低会影响你对"这个能力做得多深"的容忍度——`[[06-SGLang-约束解码与语法后端]]` 记录的 xgrammar/llguidance/outlines 四个语法后端，以及 SGLang 前端 DSL（`sgl.gen()`，尽管 `[[11-开源推理引擎谱系图]]` `## 4.1` 指出它"几乎不被生产使用"）这类投入，只有在这类负载确实是主要负载时才划算。
- **判错会怎样**：低估这类负载占比会选一个结构化输出支持相对基础的引擎，后续接 Agent 框架时发现约束解码的性能/覆盖面不够，需要中途迁移；高估则可能为了一个用不上的能力（比如 SGLang 的前端 DSL）多背负 476 个 `ServerArgs` 字段（`00-总览与阅读地图.md` §4 已指出）里那些和你无关的复杂度。
- **什么时候这个判据本身失效**：结构化输出的"支持程度"本身在快速变化——`99-本质总结-亲笔.md` 原理 2 已经指出 SGLang 的招牌优化 jump-forward decoding 在当前快照里是死代码（四个语法后端都实现了但调度器零调用点），"这个引擎支持结构化输出"这句话背后可能藏着"支持"和"生效"之间的落差,查这条判据时不能只看有没有这个功能入口,要像 `99-本质总结-亲笔.md` 原理 2 那样去查它有没有真的被调用。

### Q6 · 是否需要跨机

- **为什么这样判**：单机 GPU 数量能不能顶住目标 QPS，决定了要不要在引擎自带的 PD 分离抽象（如 vLLM `KVConnectorBase_V1`/E4）之上再接一层真实的跨机传输（Mooncake/E33）甚至跨实例路由编排（Dynamo）——这是一条纯粹由资源规模决定的判据，不涉及"想不想要"。
- **判错会怎样**：低估所需机器数会导致上线后被迫在生产环境临时改造成多机部署，PD 分离这类跨进程/跨机的抽象如果不是从设计初期就考虑，后期改造成本很高（`[[12-vLLM-PD分离与KV-Connector]]`、`[[11-SGLang-PD分离与HiCache分层]]` 涉及的连接器协议、KV 传输握手都是需要提前设计的接口）；高估则会为不需要的一层基础设施（`[[08-Mooncake传输引擎]]` `## 5` 决策五已指出"单机单进程场景下这层纯是负担——多一层要装的库、多一份要跟版本的依赖"）付出不必要的运维成本。
- **什么时候这个判据本身失效**：如果目标 QPS 会随时间大幅波动（比如促销期间流量翻十倍），"当前需不需要跨机"这个判据的答案会在同一个产品生命周期里反复变化——这种场景下更该提前设计成"支持跨机但默认单机部署"，而不是按当前流量的静态快照做二选一决策。

### Q7 · 团队运维能力

- **为什么这样判**：`[[11-开源推理引擎谱系图]]` `## 5` 决策一已经承认——这条判据本篇给不出答案，只能提出问题，因为"团队能不能维护 C++/CUDA 构建链"是一个关于读者自己团队的事实，不是关于源码的事实，超出了本库"读源码"的方法论范围。放进决策树是因为这条判据的**权重经常被低估**——LMDeploy TurboMind、TensorRT-LLM 这类深度依赖 C++/nanobind 的引擎（`[[02-LMDeploy与TurboMind]]` `## 6.3`、`[[01-TensorRT-LLM]]` `## 5` 决策三都已指出调度决策下沉到 C++ 的设计），出问题时排查成本显著高于纯 Python 引擎。
- **判错会怎样**：高估团队的 C++ debug 能力，选了一个调度器在 C++ 里的引擎，遇到调度相关的诡异 bug 时会卡在"看不懂 nanobind 绑定" 这一步；低估则会放弃 TurboMind/TensorRT-LLM 能带来的极致时延收益，选一个团队更熟悉但性能天花板更低的方案。
- **什么时候这个判据本身失效**：团队能力不是静态的——如果这次选型本身就是"借这个项目学 C++ 系统编程"这类有意投资团队能力的决策，Q7 当前的"否"不该直接否决 TurboMind/TensorRT-LLM 这条支线,这类"刻意投资学习曲线"的场景本篇给不出通用建议,取决于项目的时间预算。

### Q8 · 模型架构白名单匹配度

- **为什么这样判**：不是所有引擎都支持所有模型架构——`[[02-LMDeploy与TurboMind]]` 已经查实 TurboMind 白名单仅约 15 个架构（无 DeepSeek 系列），新模型会静默降级到 pytorch backend（`99-本质总结-亲笔.md` 原理 2 已把这条列为"静默降级"的一个样本）。这条判据必须放在决策树里,否则前面所有判据都选对了,最后卡在"这个引擎根本不支持我要用的模型"这种最基础的问题上。
- **判错会怎样**：如果没有检查模型架构是否在白名单里就部署，轻则遇到显式报错（容易发现），重则像 TurboMind 那样静默降级到另一个执行路径——用户以为自己在用极致优化的后端，实际吞吐/时延特征完全是另一套代码在跑,这正是"静默降级"最危险的地方（`99-本质总结-亲笔.md` 原理 2）。
- **什么时候这个判据本身失效**：这条判据的答案**保证会过期**——模型支持矩阵几乎每周都在变，本篇给不出任何"现在支持"的静态清单,唯一正确的做法是在每次选型时重新去对应引擎的官方文档/issue 查当前支持情况,`## 6` 第 3 条会重申这一点。
