# KV 缓存与前缀复用横向对比

> **本篇取证基准**：`vllm` @ `7ca49fbe`（2026-08-22）；其余引擎 sha 见 `_lab/out/repo_stats.json` 的 `ref` 字段（`sglang` @ `15a43983`、`tensorrt-llm` @ `75b023cd`、`lmdeploy` @ `1263d5cd`、`lightllm` @ `87881ae7`、`llama.cpp` @ `2c6b141e`），跨引擎引用一律加 `引擎名:` 前缀。
> **一句话**：同一个问题两种教科书答案，代码里还有第三种。

## 0. 结论先行

六个引擎都管自己叫"前缀缓存"，但落到代码里，"缓存"到底是什么数据结构、命中判定要付多少代价、驱逐时怎么决定该扔谁——这三件事六家给出的答案互不相同，而且不是"哈希表 vs 基数树"两派简单对垒。

1. **不是两派，是两条互相独立的轴**：一条轴是"提交单位定长还是变长"（vLLM/TensorRT-LLM/LMDeploy 用定长块，SGLang/LightLLM 默认按 token 变长）；另一条轴是"索引结构是扁平表还是树"（vLLM 用扁平哈希表，其余五家全部是树/trie）。两条轴叉开是四格，vLLM 占一格，SGLang 与 LightLLM 占对角另一格，TensorRT-LLM 与 LMDeploy 占了"哈希表 vs 基数树"这个二元框架根本没预留位置的第三格——**定长块 + 树**。第 4 节把这四格逐一拆开。
2. **没有一家的驱逐是教科书 LRU**：vLLM 没有任何时间戳，靠"释放顺序"近似最近性；SGLang/LightLLM 有真实时间戳但只把叶子节点当候选，非叶子节点无论多久没被访问都不能被淘汰；TensorRT-LLM 的 `LRUEvictionPolicy` 用一个布尔参数 `toFront` 复刻了和 vLLM 同构的"两条队列"结构。第 5 节给出这几种"近似"在什么请求模式下会给出不同答案。
3. **哈希/键里混什么，是本篇最该较真的一节，因为答案错了不是变慢，是答错**——LoRA id、多模态哈希、cache_salt 这三样，vLLM、SGLang、TensorRT-LLM 各自独立实现了几乎同构的隔离机制，LMDeploy 走的是另一条路（树根隔离），LightLLM 与 llama.cpp 在这条维度上是本篇查到的两处真实空白。第 5.1 节逐引擎核对，缺一个具体导致什么错答案。
4. **LightLLM 的基数树代码开头第一行注释就写着"Adapted from sgl-project/sglang"**——两家不是分别发明了同一个轮子，是字面意义上的同一份设计基因；但 LightLLM 在驱逐候选的排序结构（全局 `SortedSet` vs SGLang 每次驱逐现建的堆）和"父节点唯一子节点时反向合并收缩"这两点上做了不同选择，第 7 节展开。
5. **llama.cpp 根本不在"共享索引结构"这个游戏里**——它的"前缀复用"是给每个并发 slot 独立维护一段上下文，来了新请求就对着所有空闲 slot 各算一次最长公共前缀、选相似度最高的那个，复杂度是 `O(slot 数 × prompt 长度)` 的线性扫描，没有哈希也没有树。这不是"更差的实现"，是完全不同的设计目标：slot 解决的是"多用户各自长会话"的路由问题，不是"任意请求间共享前缀"的索引问题。
6. **前缀缓存不是免费开关，命中率低的工作负载会让它变成纯负担**——第 5.3 节给出各家"关掉它"的真实参数名，以及关掉之后省下的具体是哪部分开销。
7. **分层缓存（KV 落到 CPU/SSD 再取回）值不值，本质是一道"传输 vs 重算"的过账题，不是"能省显存就该开"**——第 5.4 节给出解析判据公式，明确标注是演算不是实测。

## 1. 它在系统里的位置

六家引擎把"前缀缓存"放在同一个位置：调度器和物理 KV 存储之间的一层纯簿记，本身不持有真实张量，只回答"这段 token 序列算过没有、算过的话数据在哪个槽位"。这是一个跨引擎的不变量，值得先摆出来，再看各家怎么实现这一层：

```
                 调度器 / 请求批处理
                        │  每步：查前缀命中 → 分配槽位 → （写满即登记新缓存）
                        ▼
     ┌──────────────────────────────────────────────────┐
     │            前缀缓存索引层（本篇主题，纯 CPU 簿记）        │
     │  vLLM       BlockHashToBlockMap  （扁平哈希表）        │
     │  SGLang     RadixCache/UnifiedRadixCache（基数树）    │
     │  LightLLM   RadixCache（基数树，脱胎于 SGLang）        │
     │  TRT-LLM    UnifiedBlockTree（定长块 + 树）           │
     │  LMDeploy   BlockTrie（定长块 + 树）                  │
     │  llama.cpp  无共享索引——按 slot 各自比对 LCP           │
     └──────────────────────────────────────────────────┘
                        │  只搬"逻辑位置"指针，不搬数据
                        ▼
              物理 KV 存储（GPU 显存 / 分层则含 CPU、SSD）
```

本篇不重复三篇兄弟篇已经逐行核对过的单引擎细节——`vllm/v1/core/` 的块池实现见 [[04-vLLM-KV缓存与前缀缓存]]，`radix_cache.py` 的匹配/分裂/驱逐算法见 [[03-SGLang-RadixAttention与前缀缓存]]，`ReqToTokenPool`/`TokenToKVPool` 两级映射见 [[04-SGLang-内存池与KV布局]]。本篇做的是那三篇之上的一层：把六家的索引结构摆在同一张表里，回答"选哪个数据结构、什么时候该选另一个"，以及"哈希里到底该混什么"这两个跨引擎问题。

## 3. 核心数据结构

六家的索引结构可以先归成"扁平表 vs 树"两个物理形状，再叠加"提交单位定长还是变长"这第二个维度——这两点合起来才是本篇 §4 要拆的四格矩阵。这里先用同一份数据，把两种最有代表性的形状（vLLM 的扁平哈希表、SGLang/LightLLM 代表的变长基数树）画成文字图，看它们把**同一串 token** 存成什么样。

### 3.1 场景设定

两个请求：

- 请求 1：`prompt = "ABCDEFGH"`（8 个 token）
- 请求 2：`prompt = "ABCDEXYZ"`（前 5 个 token 与请求 1 完全相同，第 6 个开始分叉：`F` vs `X`）

vLLM 一侧取 `block_size=4`（真实默认是 16，这里调小只是为了让图能画下，不影响结论）；SGLang/LightLLM 一侧取 `page_size=1`（这是两家真实的默认值，见 [[04-SGLang-内存池与KV布局]] §0 第 4 条）。

### 3.2 vLLM：扁平哈希表存出来的样子

```
请求 1 "ABCDEFGH" 按 block_size=4 切块：
  Block#1 = [A,B,C,D]   （满块，登记）
  Block#2 = [E,F,G,H]   （满块，登记）

cached_block_hash_to_block = {
    hash(NONE_HASH, "ABCD")        : Block#1,
    hash(hash(NONE_HASH,"ABCD"), "EFGH") : Block#2,   # 父哈希链到 Block#1
}

请求 2 "ABCDEXYZ" 查命中：
  查 hash(NONE_HASH,"ABCD")               → 命中 Block#1     （4 个 token）
  查 hash(hash(...,"ABCD"), "EXYZ")       → 表里没有这个键     （因为请求 2 的第二块内容是
                                                                E,X,Y,Z，不是 E,F,G,H，
                                                                哈希完全不同）
  → 命中长度 = 4，止步于此
```

**关键点**：token `E` 本身和请求 1 完全相同，理应可以复用，但它被"锁"在第二个块里，这个块要求 `E,F,G,H` 四个 token **同时**匹配才算数。请求 2 的第 6 个 token 是 `X` 不是 `F`，整块判失败，`E` 这一个本来能省的 token 也要重新计算。

### 3.3 SGLang/LightLLM：基数树存出来的样子（page_size=1）

```
插入请求 1 "ABCDEFGH"（空树，直接挂一个叶子，不需要分裂）：

  root
  └── [A,B,C,D,E,F,G,H]  (单节点，8 个 token 全部压在一条边上)

请求 2 "ABCDEXYZ" 到达，沿树下行：
  root.children['A'] 命中上面这个节点，RadixKey.match() 做指数搜索：
    公共前缀长度 = 5 （"ABCDE" 相同，第 6 位 F≠X 分叉）
    5 < 节点长度 8  →  触发 _split_node(split_len=5)：

  root
  └── [A,B,C,D,E]  (P，新的共享父节点，只拷贝分裂点之前这一段)
      └── [F,G,H]  (原节点收缩成私有尾部，仍属于请求 1)

  再把请求 2 剩余的 key [X,Y,Z] 挂到 P 下面：

  root
  └── [A,B,C,D,E]  (P，请求 1、请求 2 共享)
      ├── [F,G,H]   (请求 1 的私有尾部)
      └── [X,Y,Z]   (请求 2 的私有尾部)

  → 命中长度 = 5
```

**关键点**：分裂点精确落在两个序列真正开始不同的位置（token 6），`E` 不需要和 `F,G,H` 捆绑判断，命中长度比 vLLM 的扁平哈希表多出恰好 1 个 token（5 vs 4）——这一个 token 的差距，正是"提交单位定长"在块内部发生非对齐分叉时必须付出的代价，第 4 节会证明这个代价不是常数，而是随"分叉点在块内的相对位置"在 0 到 `block_size-1` 之间波动。

### 3.4 第三种形状：定长块 + 树（TensorRT-LLM / LMDeploy）

把 3.2 的"块"边界继续沿用（block_size=4），但用树而不是扁平表组织：

```
请求 1 "ABCDEFGH" 按块插入树（block_size=4）：
  root
  └── [ABCD] (Block#1)
      └── [EFGH] (Block#2)

请求 2 "ABCDEXYZ" 沿树下行：
  root.children[hash("ABCD")] 命中 Block#1（4 个 token，整块匹配）
  Block#1.children[hash("EXYZ")]  →  没有这个键（Block#1 下面只有 hash("EFGH") 这一个孩子）
  → 命中长度 = 4，和 3.2 的扁平哈希表结果完全相同
```

这印证了 §0 第 1 条的论点：**组织成树本身不会自动带来 token 级精度**，精度来自"边的长度是否可变"。TensorRT-LLM 和 LMDeploy 换来的是"驱逐可以沿子树坍缩、匹配可以提前在树的浅层终止"，不是"块内部的部分匹配"——3.4 和 3.2 在命中长度这一点上是等价的，差异只在维护结构的方式，第 4 节的判据 2 会把这一点用作核心论据。

### 3.5 同一份数据，驱逐时又分别发生什么

§3.2/§3.3 只演示到"插入完成"，接下来把请求 1、请求 2 都跑完、KV 都不再需要时，两边的驱逐机制会做出不同的保护决策——这个对照直接为 §5.2 的"驱逐真相"提供素材。

**vLLM 侧**（沿用 §3.2 的两个块）：假设请求 1 先结束，释放它私有的 `Block#2`（`[E,F,G,H]`，有哈希）——按 `free_blocks` 的分流规则（`vllm:vllm/v1/core/block_pool.py:719`），这个块进 FIFO 队列尾部；`Block#1`（`[A,B,C,D]`，此时仍被请求 2 引用，`ref_cnt=1`）不受影响，继续留在池中不进队列。稍后请求 2 结束，`Block#1` 的 `ref_cnt` 才归零，也进 FIFO 队列尾部——因为它是后释放的，队列里排在 `Block#2` 之后，理应更晚被驱逐。这个结果"恰好正确"（共享块确实应该比私有块活得更久），但**保护它的机制只是"释放时间更晚"这一条**，不是"这个块被两个请求共享过"这个结构信息本身——如果两个请求恰好在同一个调度步内几乎同时结束（`Block#1` 和 `Block#2` 落进同一次 `free_blocks` 调用），它们在队列里的相对顺序就只取决于调用方传入 `ordered_blocks` 时的遍历顺序，不再有任何信号能区分"这个块被共享过"。

**SGLang 侧**（沿用 §3.3 的树，`P=[A,B,C,D,E]` 有两个子节点 `[F,G,H]` 与 `[X,Y,Z]`）：请求 1 结束，`dec_lock_ref` 沿路径释放，`[F,G,H]` 的 `lock_ref` 归零、成为叶子，进入 `evictable_leaves`；但 `P` 此时仍有 `[X,Y,Z]` 这个存活的子节点，**`P` 的 `len(children)` 不为零，结构上就不是叶子，无论 `P.last_access_time` 多旧，`evict` 都不会考虑它**（`sglang:python/sglang/srt/mem_cache/radix_cache.py:593`）。请求 2 结束后 `[X,Y,Z]` 也成为叶子，`_delete_leaf` 把它从 `P.children` 摘除，`P` 此时才第一次满足"零子节点"，被检测为新叶子推入堆（同一函数里 `if len(x.parent.children)==0 and x.parent.lock_ref==0` 的判断，见 §4.4 已引用的 `evict` 代码）——`P` 能不能被驱逐，取决于**它是否还有任何一个活着的后代**，这是结构上的硬约束，不依赖任何时间戳或释放顺序的巧合。

两边最终都"正确"地把共享前缀留到最后驱逐，但 vLLM 靠的是"共享块通常释放得晚"这个统计规律，SGLang 靠的是"父节点结构上不可能在子节点还活着时被判定为叶子"这个不变式——前者可以被反例打破（两个请求同批结束、或释放顺序被上层调用方打乱），后者不能。

## 4. 主流程走读：块哈希表 vs 基数树，谁在什么负载下更划算

### 4.1 一张矩阵，替代"哈希表 vs 基数树"这个二元框架

把"提交单位定长/变长"和"索引结构扁平/树形"两条轴叉开：

| | **扁平索引**（一次查表拿结果） | **树形索引**（沿路径逐层下降） |
|---|---|---|
| **定长块**（提交粒度=`block_size`/`tokensPerBlock` 的整数倍） | **vLLM**：`BlockHashToBlockMap` | **TensorRT-LLM**：`UnifiedBlockTree`；**LMDeploy**：`BlockTrie` |
| **变长/token 级**（提交粒度=实际分叉点） | 本库在六个引擎里没有找到这一格的生产实现——扁平表要支持变长键，意味着放弃"一次哈希直接定位"的优势（变长键本身就得先知道匹配到哪，等于要先做树才能查表），这一格在结构上接近自相矛盾，见判据 2 | **SGLang**：`RadixCache`/`UnifiedRadixCache`；**LightLLM**：`RadixCache`（脱胎于 SGLang） |

llama.cpp 不在这张矩阵里——它没有跨请求共享的索引结构，见 §2.1 最后一行。

### 4.2 判据 1：共享前缀相对块边界的分布

如果实际分叉点密集地卡在块/页边界附近（模板化 system prompt + 结尾差异化，比如同一个 agent 骨架反复调用，差异只出现在最后追加的一小段），定长块"整块才算命中"的代价趋近于零，此时扁平哈希表（vLLM）用最省的实现代价拿到几乎全部收益——不需要维护树、不需要 `.clone()` 分裂、不需要为每次分叉新建 Python/C++ 对象。

如果分叉点在 token 级别到处都有且不对齐（多轮对话在历史任意位置被编辑重发、多份 few-shot 样例被打乱顺序拼接、agent 树搜索的分支点是运行时决定的），定长块每次都可能因为"块内一个 token 不同"损失一整块本该命中的长度（§3.2 的 `E` 就是具体例子），这时候变长节点（SGLang/LightLLM）才能把这部分损失捞回来。

### 4.3 判据 2："边压缩"是否成立，决定"上树"是否划算

§3.4 已经证明：只搭一个树壳子（TensorRT-LLM/LMDeploy 的定长块+树）不会自动换来 token 级精度。SGLang 决策 6（[[03-SGLang-RadixAttention与前缀缓存]] §5）里写得很清楚：只有边的长度本身可变，才能让"连续无分叉的 token 全部压进一条边"，节点数只随实际分叉次数增长，不随序列长度增长。

这意味着：TensorRT-LLM/LMDeploy 如果想追求更细的命中粒度，只能靠调小 `tokensPerBlock`/`block_size`，付出的代价和 vLLM 调小 `block_size`完全同款——更多块/节点对象、更高簿记开销、更频繁的哈希计算；只有 SGLang/LightLLM 把 `page_size` 调到 1 时，这份代价被"边压缩"机制本身吸收掉了大半（本库推断：吸收程度取决于真实流量的分叉密度，分叉越稀疏，压缩效果越好；本库没有真实流量分布可以量化这条曲线）。

一句话总结判据 2：**"上树"买的是"驱逐可以沿子树坍缩、匹配可以提前在浅层终止"这个好处，不是"块内部分匹配不要钱"这个好处**——后者只有同时把边变长才能拿到。

### 4.4 判据 3：请求到达的时间局部性

如果同一批共享前缀的请求几乎同时到达（一次性批量下发的 agent 树搜索、投机解码的多分支候选），分叉点集中出现，树深不会失控，树结构额外的对象创建成本被"一次分裂服务后续大量请求"摊薄——这是树形索引最舒服的工作负载。

如果请求到达稀疏、彼此之间隔着大量其他请求（分叉点被历史上其他请求的插入打散在树的各个角落，中间还夹杂了大量的驱逐/坍缩），树的深度和节点数会随时间波动而没有稳定的命中收益抵消；此时定长块+扁平表固定的簿记成本（不随树深增长，只随前缀长度线性增长）反而更可预测——这是 vLLM 式设计在长期运行、流量模式多变的生产环境里更"皮实"的原因之一（本库推断，基于结构性论证，非实测对比）。

### 4.5 llama.cpp 不参与这场判据讨论，因为它的成本函数完全是另一种

§4.1-4.4 的三条判据都建立在"存在一个跨请求共享的索引结构，判据决定往哪个方向调"这个前提上——llama.cpp 从设计上就不满足这个前提，它的"匹配"是逐 slot 现算，没有可调的数据结构参数：

```cpp
// tools/server/server-context.cpp:1514-1546（节选，变量名与原文一致）
for (server_slot & slot : slots) {
    if (task.id_slot != -1 && slot.id != task.id_slot) continue;
    if (slot.is_processing()) continue;               // 跳过正忙的 slot
    if (tokens.empty()) continue;                      // 跳过空 slot

    // 与输入 prompt 的最长公共前缀长度，除以输入长度 = 相似度
    const size_t lcp_len = tokens.get_common_prefix(task.tokens);
    const float f_sim_cur = float(lcp_len) / task.tokens.size();

    if (f_sim_cur > f_sim_best && f_sim_cur > slot_prompt_similarity) {
        f_sim_best = f_sim_cur;
        ret = &slot;
    }
}
```

这段循环对**每一个**空闲 slot 都要重新算一次 `get_common_prefix`（`llama.cpp:tools/server/server-common.cpp:680`，§2.1 已引用），复杂度是 `O(slot 数 × prompt 长度)`，且没有任何"块大小"或"page_size"类的旋钮可调——因为压根不存在一个跨请求持久化的索引结构去调整粒度。`--slot-prompt-similarity`（`llama.cpp:common/arg.cpp:3757`）调的是"相似度阈值"，即"要不要采用这个 slot"的判定门槛，不是命中粒度。这解释了为什么 §2.1 的主表把 llama.cpp 排除在四格矩阵之外：判据 1/2/3 讨论的是"给定一个共享索引结构，该往哪个方向调"，llama.cpp 从起点上就没有走上这条路——它用"路由到对的 slot"取代了"维护一个共享索引"，是完全不同的成本模型，不是矩阵里缺的第五格。

### 4.6 一个共同的边界情形：块大小的选择本身也是一种判据

不管选哪一格，`block_size`/`page_size` 都不是越小越好：

- 定长块阵营（vLLM/TensorRT-LLM/LMDeploy）调小块，命中粒度变细，但块数量线性增长，每个块对应一份簿记对象（vLLM 是预建数组里的一个 `KVCacheBlock`，TensorRT-LLM/LMDeploy 是树里的一个节点），大部分收益会在"分叉本来就稀疏"的负载下打水漂——多出来的块从未参与过任何一次真正的跨请求命中。
- 变长阵营（SGLang/LightLLM）调小 `page_size` 到 1（两家的真实默认值），因为有边压缩兜底，节点数不会跟着 `page_size` 线性增长，但会跟着**实际分叉次数**增长——一个从不与任何其他请求共享前缀的孤立长请求，在 `page_size=1` 下仍然只占一个节点（§3.3 的第一步就是证据：8 个 token 插入空树只产生一个节点，不是 8 个）。

## 5. 设计决策与代价

### 5.1 哈希/键里必须混什么——本篇最该较真的一节

这不是性能问题，是正确性/隐私问题：两个请求 token 完全相同，但语义不同（不同 LoRA、不同图片、不同租户），如果索引结构判它们"前缀相同"，会把 A 请求算出的 KV 喂给 B 请求，模型在错误的 KV 上继续生成，**没有任何报错信号**。

| 引擎 | LoRA/adapter 隔离方式 | 多模态隔离 | 隐私盐（cache_salt 等价物） | 隔离失败时的具体行为 |
|---|---|---|---|---|
| vLLM | 混入哈希链（`_gen_lora_extra_hash_keys`） | 混入哈希链（`_gen_mm_extra_hash_keys`，含块内偏移） | 混入哈希链，仅块起点（`cache_salt`） | `generate_block_hash_extra_keys`（`vllm:vllm/v1/core/kv_cache_utils.py:582`）返回值为空则不影响哈希；缺失时表现为"偶尔这个请求答非所问"，见 [[04-vLLM-KV缓存与前缀缓存]] §5.1 |
| SGLang | 混入 `RadixKey.extra_key` | 与 LoRA 共用 `extra_key` 字段统一编码（本库未逐字段核实是否与 LoRA 分开存储，**未查证**） | `RadixKey.cache_salt` | `_check_compatible`（`sglang:python/sglang/srt/mem_cache/radix_cache.py:169`）不一致时直接抛异常——**拒绝共享**，是"快速失败"设计 |
| TensorRT-LLM | 混入 `BlockKey.loraTaskId`，逐字段比较 | 混入 `BlockKey.extraKeys`（头文件注释原文"similar to VLLM's approach"） | `BlockKey.cacheSalt` | `numMatchingTokens`（`tensorrt-llm:cpp/include/tensorrt_llm/batch_manager/blockKey.h:96`）任一字段不等直接返回 0 个匹配 token——**静默返回未命中**，不抛异常，是和 SGLang 相反的"静默降级"设计 |
| LMDeploy | **树根隔离**——不同 adapter 从根节点起就不共享任何节点（`self._roots[adapter_name]`），不是混进哈希 | 混入 `extra_identity`（`PrefixCacheExtraIdentity`，多模态 span 元组） | 全仓 `grep -rl cache_salt lmdeploy/` **零命中**——本库在这次核对范围内没有找到等价机制，这是一处真实空白 | LoRA 隔离靠架构（不同根不可能碰头）；多模态靠 `_node_matches_block` 二次校验（`lmdeploy:lmdeploy/pytorch/paging/block_trie/trie.py:204`）；隐私盐缺位意味着 vLLM 安全文档警告的"通过 TTFT 探测别的租户是否问过某个前缀"这类计时旁路，本库未确认 LMDeploy 有对应缓解措施 |
| LightLLM | 全文件 `grep lora\|adapter` **零命中** | 未查证 | 未查证 | 本库推断：可能是因为 LightLLM 的多 LoRA 支持走的是权重层面的适配器切换，不经过这条 `radix_cache.py` 路径；也可能是真实缺口。需要单独一篇核对多 LoRA 场景下 LightLLM 的前缀缓存是否会串味，本篇不下结论 |
| llama.cpp | 不适用 | 不适用 | 不适用 | 架构性回避——slot 之间本来就没有共享索引，LoRA/多模态隔离问题在"有没有共享结构"这一层就不存在，不是"忘了做"而是"设计上问题不存在" |

TensorRT-LLM 的隔离判定直接写在比较函数里（`tensorrt-llm:cpp/include/tensorrt_llm/batch_manager/blockKey.h:93`-`104`）：

```cpp
// cpp/include/tensorrt_llm/batch_manager/blockKey.h:93-104
int numMatchingTokens(BlockKey const& other) const noexcept
{
    SizeType32 numMatched{0};
    if (usesExtraIds == other.usesExtraIds && loraTaskId == other.loraTaskId && extraKeys == other.extraKeys
        && cacheSalt == other.cacheSalt)
    {
        auto [matchEnd, otherMatchEnd] = std::mismatch(
            uniqueTokens.begin(), uniqueTokens.end(), other.uniqueTokens.begin(), other.uniqueTokens.end());
        numMatched = std::distance(uniqueTokens.begin(), matchEnd);
    }
    return numMatched;
}
```

`loraTaskId`/`extraKeys`/`cacheSalt` 任一不等，`if` 直接短路，`numMatched` 保持初值 `0`——**函数不抛异常，正常返回**，调用方看到的是"匹配了 0 个 token"，和"这个块本来就没有任何前缀重叠"在返回值层面完全无法区分。这是和 SGLang 的 `_check_compatible`（不一致直接抛异常）相反的设计：TensorRT-LLM 选择"静默当作未命中"，SGLang 选择"快速失败"——两种设计都能保证不发生跨语义共享，区别在于排障时前者看不出"本来有前缀重叠但因为隔离键不同被拦下了"，后者会在日志里留下一次异常。

LMDeploy 的隔离判定分成两处：LoRA 靠树根级别的物理隔离，多模态靠节点匹配时的字段比较（`lmdeploy:lmdeploy/pytorch/paging/block_trie/trie.py:199`-`206`）：

```python
# lmdeploy/pytorch/paging/block_trie/trie.py:199-206
@staticmethod
def _hash_block(token_ids: np.ndarray, extra_identity: PrefixCacheExtraIdentity):
    return hash(('random', tuple(token_ids), extra_identity))

@staticmethod
def _node_matches_block(node: Node, token_ids: np.ndarray, extra_identity: PrefixCacheExtraIdentity):
    return np.array_equal(token_ids, node.token_ids) and extra_identity == node.extra_identity
```

`extra_identity` 参与哈希（决定落在哪个 `children` 键下），`_node_matches_block` 又在哈希碰撞之外做了一次显式的二次校验——`token_ids` 和 `extra_identity` 必须**同时**相等才算真正匹配到同一个节点，这是"哈希只用来快速定位候选、真正的相等判断另外做一次"的常见防碰撞模式，和 vLLM 的块哈希（只信哈希、不做二次内容比对，见 [[04-vLLM-KV缓存与前缀缓存]] §3.4 关于哈希碰撞的空间优化讨论）形成对照。

**为什么这样设计**：token id 相同不代表语义相同——LoRA 改的是权重不改 token，多模态填充位 token id 对不同图片是相同的（真正信息在嵌入里），多租户场景下 token 内容相同但"是否该让对方知道我问过这个"是隐私问题不是内容问题。三个维度分别对应三种不同的"看起来一样但其实不一样"，缺任何一个都会把不该共享的 KV 判定成共享。

**不这样会怎样**：LoRA/多模态维度不隔离 → 缓存污染导致模型输出错误，且表现为"偶尔答非所问"，复现依赖并发时序，是最难排查的一类 bug；隐私盐不隔离 → 多租户场景下存在可通过计时旁路探测的信息泄露（vLLM 安全文档给出过 8 token 前缀下 ROC AUC 达 0.99 的研究引用，见 [[04-vLLM-KV缓存与前缀缓存]] §5.1）。

**什么时候可以不这样**：单租户、单 LoRA（或不用 LoRA）、纯文本、不关心计时旁路的场景（离线批量跑分、内部工具单用户使用）——这时候额外键天然为空，代码路径本身也这么写（vLLM 的 `extra_keys` 为空直接返回 `None`），不产生额外开销；llama.cpp 的"不适用"就是这条的极端版本——架构上从不共享，问题从根上不存在。

### 5.2 驱逐策略的真相：近似 LRU、leaf-LRU、真排序，三种给出不同答案的场景

**为什么这样设计**：三种策略都是"完全精确的 LRU 需要给每次访问打时间戳并支持任意位置的 O(1) 重排"这一目标在不同工程约束下的妥协——vLLM 甚至不打时间戳，只用"释放顺序"近似；SGLang/LightLLM 打真时间戳，但只让叶子节点参与排序（非叶子节点可能持有仍在使用的子孙，不能贸然淘汰）；TensorRT-LLM 用一个布尔参数复刻了和 vLLM 同构的双队列。

具体机制对照：

| 引擎 | 有没有时间戳 | 候选集合 | 近似方式 |
|---|---|---|---|
| vLLM | 无 | 空闲队列里的所有块 | 释放顺序代替访问顺序：有 hash 走 FIFO 尾部（`vllm:vllm/v1/core/block_pool.py:719` 的 `blocks_to_evict_last`），无 hash 走 LIFO 头部 |
| SGLang | 有（`last_access_time`，`sglang:python/sglang/srt/mem_cache/radix_cache.py:238`） | 仅叶子节点（`evictable_leaves` 增量维护） | 叶子间按真实时间戳排序；驱逐后父节点若坍缩成新叶子，继续参与下一轮排序 |
| LightLLM | 有（`time_id`，单调计数器，见 `lightllm:lightllm/server/router/dynamic_prompt/radix_cache.py:29`） | 仅叶子节点（`SortedSet`，`get_compare_key` 优先按 `ref_counter==0`、再按 `len(children)`、最后按 `time_id`） | 与 SGLang 结构相同（叶子优先），但用增量维护的全局有序集合代替"每次驱逐现建堆" |
| TensorRT-LLM | 无独立时间戳，用队列位置 | `mFreeQueues[cacheLevel]` 里的叶子块 | `releaseBlock(block, toFront)`：正常完成走 `toFront=false`（尾插，FIFO，长期保留）；子树失效/投机解码回退等场景走 `toFront=true`（头插，优先淘汰）——和 vLLM 的 LIFO/FIFO 分流是同一个设计动机的不同实现 |
| LMDeploy | 无独立时间戳，用释放顺序 | `KVBlockLifecycle` 管理的叶子块 | 叶子驱逐之外还叠了一层"冻结检查点优先"（`StateCheckpointLifecycle`，`lmdeploy:lmdeploy/pytorch/paging/block_trie/trie.py:634` 起的 `evict` 注释原文"Frozen partial blocks are cheaper to release because their trie anchor remains cached"）——先处理冻结态、更便宜释放的部分块，剩余额度才交给和 SGLang 同构的叶子驱逐 |
| llama.cpp | 有，但粒度是**整个 slot**（`t_last_used`） | 所有空闲 slot | 只有在没有任何 slot 通过 LCP 相似度匹配上时，才退化成"选 `t_last_used` 最小的空闲 slot"（`llama.cpp:tools/server/server-context.cpp:1565`）——这是六家里唯一一处**真正的时间戳驱动 LRU**，代价是粒度粗到极限：一次驱逐决策覆盖一个 slot 里的全部上下文，不是一个块或一个节点 |

llama.cpp 还有一处值得单独一提的"驱逐前置判断"：即便某个 slot 通过 LCP 相似度选中，如果新请求只能保住旧上下文的不到一半（`f_keep < 0.5f`，`llama.cpp:tools/server/server-context.cpp:1559`），会先触发 `prompt_save`（`llama.cpp:tools/server/server-context.cpp:255`、`1600`）把即将被覆盖的旧上下文整体落盘成 prompt cache 文件，再复用这个 slot——这不是"驱逐"，是"驱逐前先备份"，六家里独此一份，因为只有 llama.cpp 的复用粒度粗到"整个 slot 的上下文"，备份的性价比才成立；vLLM/SGLang 这类块/节点级别的驱逐如果也要做"驱逐前备份"，就是本篇 §5.4 讨论的分层缓存本身，不是一个 if 分支能解决的事。

**不这样会怎样**（vLLM 的近似何时给出错误答案）：一个块被单个长请求持有很长时间（`ref_cnt>0`，不在空闲队列里，vLLM 全程不记录它在此期间被多少个后续请求"路过命中"），一旦这个长请求结束、块被释放，它会被放到 FIFO 队列的尾部——**等同于宣布它是"最新鲜"的**，即便它自己从被创建到现在只被真正命中过一次，且那次命中发生在很久以前。与此同时，另一批块可能在这段时间里被多个短请求反复命中-释放，每次释放都刷新到队尾——如果这批块恰好在长请求释放的**前一刻**被释放（进入队列位置更靠前），它们会比刚释放的长请求块更早被淘汰，尽管按真实访问时间线，它们其实更"热"。**vLLM 的近似依赖一个隐含假设：块被释放的那一刻，大致就是它最后一次真正有用的时刻**——这个假设对短生命周期请求成立得很好，对被单个长请求长期占用的块会系统性失真（本库推断，基于 §5.3/§5.4 已核实的机制推理，非实测对比）。SGLang/LightLLM 因为时间戳打在每次 `match_prefix` 命中时而不是释放时，不会有这个"释放即刷新"的假象——一个只被访问过一次、之后被某个长请求长期持有的节点，`lock_ref` 归零时它的 `last_access_time` 仍然停留在很久以前，会被正确地排到淘汰候选的前列。

**什么时候可以不这样**：如果部署场景里请求生命周期普遍短且均匀（没有长尾的超长生成任务），"释放顺序≈访问顺序"这个假设基本成立，vLLM 的零时间戳设计几乎不会给出错误答案，反而省掉了每次命中都要写时间戳的开销；如果流量里混杂了大量长生成任务和短请求，SGLang/LightLLM 式的真实时间戳能提供更准确的近似，代价是每次命中都要多写一次时间戳（对 SGLang/LightLLM 而言这个开销已经内含在树遍历里，不是额外成本）。

### 5.3 前缀缓存什么时候是负收益，以及各家关掉它的真实参数名

命中率低的工作负载下，前缀缓存三类开销都不产生任何抵消收益：

1. **索引维护开销**：vLLM 每个请求仍要计算 `O(prefix_len/block_size)` 次哈希；SGLang/LightLLM 每个请求仍要走一次 `O(树深)` 的树遍历（哪怕大概率一步就在根节点 miss）；TensorRT-LLM/LMDeploy 同理要走一次 trie 下降；llama.cpp 仍要对每个空闲 slot 算一次 `O(n)` 的 LCP。这些操作单次都不贵，但在高 QPS、短请求、且请求间几乎不共享前缀的场景下会累积成不可忽视的 CPU 侧调度开销，且完全没有对应的命中收益。
2. **块内部碎片**：vLLM/TensorRT-LLM/LMDeploy 的"只精确缓存整块 + 尾部一个部分块"策略（见 [[04-vLLM-KV缓存与前缀缓存]] §5.7）意味着每个请求的最后一个不满块永远无法被复用，命中率低时这部分碎片纯粹是浪费，没有任何摊薄。
3. **"开着但没用上"的显存/对象占用**：vLLM 恒定预留一个 `null_block`；SGLang/LightLLM 每次分叉都新建一个树节点对象，命中率低但分叉密集的负载（比如每个请求内容都近乎随机）下，树的对象数量甚至可能比扁平哈希表的条目数更多——因为每个从未被复用过的孤立分支仍然占一个节点，而哈希表至少不需要为"从未命中过的块"维护父子指针这类额外字段。

关掉它的真实参数名（逐条 grep 核实，非官方文档转述）：

| 引擎 | 参数名 | 默认值 | 引用 |
|---|---|---|---|
| vLLM | `enable_prefix_caching` | `True` | `vllm:vllm/config/cache.py:138` |
| SGLang | `--disable-radix-cache` | 关闭标志默认 `False`（即默认开启前缀缓存） | `sglang:python/sglang/srt/server_args.py:967` |
| TensorRT-LLM | `enable_block_reuse`（`KvCacheConfig` 字段） | `True` | `tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:3862` |
| LMDeploy | `enable_prefix_caching` | **`False`**——六家里唯一默认关闭前缀缓存的引擎 | `lmdeploy:lmdeploy/messages.py:324`（PytorchEngineConfig）/`lmdeploy:lmdeploy/messages.py:478`（TurbomindEngineConfig） |
| LightLLM | `--disable_dynamic_prompt_cache` | 关闭标志默认 `False`（即默认开启） | `lightllm:lightllm/server/api_cli.py:338` |
| llama.cpp | `--no-cache-prompt`（整体关闭）/ `--cache-reuse N`（部分复用的最小长度阈值） | 默认开启缓存复用 | `llama.cpp:common/arg.cpp:3537`、`llama.cpp:common/arg.cpp:3544` |

**为什么这样设计**：五家默认开启，是因为大多数真实服务流量（多轮对话、共享 system prompt、agent 反复调用同一骨架）本身就有可观的前缀重叠，默认开启的期望收益大于维护成本；LMDeploy 默认关闭是本篇发现的六家里唯一的例外。

**不这样会怎样**：默认开启但实际流量零命中的场景下，白白支付 §5.3 前三条列出的所有开销；LMDeploy 默认关闭但实际流量高度重叠的场景下，白白放弃本可以省下的重算——这是一个纯粹的"默认值赌注"，赌的是"典型用户的流量分布长什么样"，六家给出了不完全一致的赌注方向。

**什么时候可以不这样（即什么时候该真的调整默认值）**：纯粹的一次性 embedding/scoring 服务、每个请求输入都不重叠的压测基线测量（想单独测"不算前缀缓存"时的吞吐上限）、或者显存本身就紧张到连一个最小可用的索引结构都嫌贵的极端部署——这几类场景下应该主动关闭（vLLM/SGLang/TensorRT-LLM/LightLLM/llama.cpp）；反过来，多轮对话、agent、共享模板这类天然高重叠场景下，LMDeploy 用户需要主动打开 `enable_prefix_caching`，因为默认值不会帮你打开。

### 5.4 分层缓存的盈亏：一道"传输 vs 重算"的过账题（解析计算，非实测）

SGLang 的 HiCache（GPU→CPU→远端）、vLLM 的 offloading connector、TensorRT-LLM 的 `kSecondaryLevel`，本质都在回答同一个问题：一段 KV 已经不在 GPU 上了，是**去更慢的存储层取回来**，还是**干脆重新跑一遍前向算出来**？

vLLM 把这个问题的接口做得最直白——`KVConnectorBase_V1.get_num_new_matched_tokens`（`vllm:vllm/distributed/kv_transfer/kv_connector/v1/base.py:450`）：

```python
# vllm/distributed/kv_transfer/kv_connector/v1/base.py:450-454
def get_num_new_matched_tokens(
    self,
    request: "Request",
    num_computed_tokens: int,
) -> tuple[int | None, bool]:
    ...
```

返回值第一项是"这个外部存储层还能再提供多少个 token 的 KV"，调度器拿到这个数字之后，走的是和 §3.2 完全相同的"命中即分配槽位"逻辑——**从调度器的视角，外部分层存储和本地前缀缓存命中是同一种事件，唯一的区别是"要不要异步等一下"（返回值第二项）**。这正是"把外部 KV 伪装成前缀缓存命中"这句话的字面含义：调用方不需要知道数据是从 GPU 显存里另一个块拿来的，还是跨进程从 CPU/远端传来的，两者共用同一条"分配槽位→标记已计算"的下游路径。下面的判据公式要回答的，正是"连接器该不该在这次调用里返回一个非零命中数"这件事背后的经济账。

**判据公式**（记号与假设都显式给出）：

- `N`：需要复用的 token 数
- `S`：每 token 需要搬运的 KV 字节数——与 [[04-vLLM-KV缓存与前缀缓存]] §4.4 算过的是同一个量：`S = num_layers × page_size_bytes(单层,每token)`，该篇算例里 32 层、`block_size=16` 时给出 `page_size_bytes(单层)=65536` 字节/块，换算成每 token 每层 4096 字节，32 层合计 `S=131072` 字节 = 128 KiB/token（**沿用该篇的假设值，不是本篇新实测**）
- `BW`：目标层级到 GPU 的有效传输带宽（PCIe/NVLink/跨机网络，取决于分层介质，本篇不假设具体数值）
- `L`：一次传输的固有延迟（发起请求、排队、跨进程/跨机开销），与 `N` 无关的常数项
- `C`：该硬件上"重算一个 token 前向"的有效时间成本，常见一阶近似 `C ≈ 2P / (峰值算力 × 利用率)`（`P` 为模型参数量，忽略 attention 的二次项，这是标准的 FLOPs 估算近似，非本库发明，也不是针对具体硬件的实测）

传输划算当且仅当：

```
L + N·S/BW  <  N·C
```

整理成关于 `N` 的判据：

```
N > L / (C − S/BW)        （前提：C > S/BW）
```

**含义**：

1. 如果 `C ≤ S/BW`（该层级带宽低到连"不算固有延迟"的情况下传输都比重算慢），那么**无论 `N` 多大，重算恒划算，传输永远不该发生**——这是分层缓存只在"GPU↔CPU（高 PCIe/NVLink 带宽）"这类高带宽层级才有意义，而不轻易伸到"GPU↔冷对象存储"的根本原因：慢层级的 `S/BW` 项会直接吃掉传输相对重算的全部优势。
2. 如果 `C > S/BW`，存在一个盈亏平衡点 `N* = L/(C-S/BW)`——复用长度短于这个阈值时重算更划算（固定延迟 `L` 摊不平），复用长度长于阈值时传输更划算。**注意**：调度层面的排队/竞争会让 `C` 在高负载时段实际抬高（同一块 GPU 既要跑重算的前向，也要跑其他请求的解码），从而降低盈亏平衡点、让传输在忙时段相对更有利——这是一个方向性的定性结论，本篇不给出量化曲线。

**为什么要用公式而不是直接说"分层缓存值得开"**：三个引擎的分层机制（HiCache/offloading connector/`kSecondaryLevel`）都是可插拔的策略层，真正决定值不值的是硬件带宽、模型规模、复用长度分布这几个因人而异的输入——把结论写死成"值得"或"不值得"会在下一次硬件/模型组合变化时直接过期，公式本身才是可以复用的资产。

**什么时候可以不用这套公式**：如果硬件层级之间的速度差异极端到肉眼可判（比如目标层级是同一张卡的显存本身，`BW` 接近无穷大、`L` 接近 0，传输显然永远划算；或者目标层级是磁带库，`BW` 低到几个数量级之外，传输显然永远不划算），不需要真的代入公式算——公式的价值在"不那么悬殊"的中间地带，比如 GPU↔CPU 内存这类真实分层场景里的判断。

## 7. 踩坑与反直觉

1. **"哈希表 vs 基数树"这个二元框架在真实代码面前站不住**。TensorRT-LLM 的 `radix_block_tree::UnifiedBlockTree` 和 LMDeploy 的 `BlockTrie` 都是"定长块 + 树"——本篇任务提纲最初也是按这个二元框架来的，读完六家源码之后才发现它遗漏了一整格（§4.1 的四格矩阵），这是本篇写作过程中被代码本身推翻的一个预设。
2. **LightLLM 的基数树不是独立设计，是字面意义上的移植**。`lightllm/server/router/dynamic_prompt/radix_cache.py` 第 1 行就是 `# Adapted from https://github.com/sgl-project/sglang/...`——这不是本库的类比或推断，是源码作者自己写的出处声明。两家的收敛不是"英雄所见略同"，是真实的代码血缘。但"移植"不等于"逐行照抄"，LightLLM 在驱逐候选的排序键上做了自己的选择（`lightllm:lightllm/server/router/dynamic_prompt/radix_cache.py:34`-`35`）：

   ```python
   # lightllm/server/router/dynamic_prompt/radix_cache.py:34-35
   def get_compare_key(self):
       return (0 if self.ref_counter == 0 else 1, len(self.children), self.time_id)
   ```

   排序元组第二项 `len(self.children)`（子节点数）排在 `time_id`（真实的访问时间信号）**前面**——意味着"子节点更少的节点"总是比"子节点更多的节点"更优先被考虑驱逐，哪怕后者的 `time_id` 更旧。结合 LightLLM 独有的 `_try_merge`（父节点唯一子节点时把父子合并成一个节点，`lightllm:lightllm/server/router/dynamic_prompt/radix_cache.py:347`，本篇 §2.1 表格已引用其收缩节点数的效果），这套组合拳的净效果是：LightLLM 比 SGLang 更主动地把"结构简单（子节点少）"当成驱逐优先级的一部分，不是单纯按最近访问时间排序——这是移植之后的独立演化，不是单纯的重复实现。
3. **TensorRT-LLM 的 `BlockKey` 注释也直接承认了对 vLLM 的借鉴**：`cpp/include/tensorrt_llm/batch_manager/blockKey.h` 里 `extraKeys` 字段的注释原文是 "similar to VLLM's approach"（`tensorrt-llm:cpp/include/tensorrt_llm/batch_manager/blockKey.h:47` 附近）。跨引擎"抄作业"比想象中更常见，而且是被开发者公开写进注释、不避讳的那种。
4. **LMDeploy 是六家里唯一默认关闭前缀缓存的引擎**（`enable_prefix_caching` 默认 `False`，`lmdeploy:lmdeploy/messages.py:324`/`478`）——与"前缀缓存显然该默认开着"的直觉相反，且这个反直觉的默认值本篇没有找到代码注释解释原因（未查证具体动机，只确认了这个默认值的存在）。
5. **各家的 `page_size`/`block_size` 默认值横跨 64 倍**：SGLang/LightLLM 默认 1 token（`sglang:python/sglang/srt/arg_groups/overrides.py:2396`，见 [[04-SGLang-内存池与KV布局]] §0 第 4 条），vLLM 默认 16（`vllm:vllm/config/cache.py:79`），TensorRT-LLM 默认 32（`tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:3988`），LMDeploy 默认 **64**（`lmdeploy:lmdeploy/messages.py:470`）——同样叫"块大小"，六家的默认值从 1 到 64 横跨六十四倍，直接决定了各自在 §4.2 判据 1 下的实际表现，"块哈希表命中粒度粗"这句话对 LMDeploy（64）成立的程度，比对 vLLM（16）严重得多。
6. **TensorRT-LLM 的 `toFront=true` 触发条件和 vLLM 的 LIFO/FIFO 分野不是同一件事，不能直接类比过去**。vLLM 按"块有没有哈希"二分；TensorRT-LLM 按"子树整体失效（比如上层被驱逐导致子树脱离查找树）/投机解码回退释放占位块"这类特殊场景触发 `toFront=true`（`tensorrt-llm:cpp/tensorrt_llm/batch_manager/kvCacheManager.cpp:1312`、`2908`、`2931`），正常完成的块走默认的 `toFront=false`。两边"队列结构"同构，但"谁该被优先淘汰"的判定依据完全不同——结构收敛不等于语义收敛。
7. **LMDeploy 全仓搜不到 `cache_salt` 或等价字段**：`grep -rl cache_salt lmdeploy/` 零命中。vLLM/SGLang/TensorRT-LLM 都为多租户计时旁路专门留了一个混入哈希/键的隐私盐，LMDeploy 目前在本篇搜索范围内没有对应机制——这是一处真实的、可以直接验证的空白，不是本库编造的批评。

## 8. 可改进点

1. **跨引擎缺一份"隔离维度对撞测试矩阵"**。LoRA/多模态/cache_salt 三个维度，六家各自独立实现、各自独立测试，没有一份公共的"故意构造 token 相同但语义不同的两个请求，断言绝不共享 KV"的跨引擎对撞测试。**本库推断**：如果这类测试以统一格式存在，LMDeploy 缺 `cache_salt` 这类空白会在 CI 层面直接被抓出来，而不是靠人工 `grep` 发现——这是一个具体、可落地的跨仓库贡献方向（给每家的测试目录提一个通用的隔离覆盖率检查清单），但本库没有去核实社区是否已经在讨论类似提案。
2. **TensorRT-LLM 的 `radix_block_tree` 和 LMDeploy 的 `BlockTrie` 各自独立发明了"定长块 + 树"这个模式，互相之间没有引用或参照**。**本库推断**：如果能把这个模式（连同它相对纯基数树"不享受边压缩"、相对扁平哈希表"能沿子树坍缩驱逐"的取舍）写成一份跨引擎的设计参考，能减少下一个想做类似设计的引擎重复踩坑——但这需要先确认两家维护者是否愿意共享设计文档这类跨项目协作，本库未核实。
3. **`_lab/struct_map.py` 目前只做单引擎内的结构统计，不做跨引擎的"哪个类是默认生产路径"静态可达性分析**。本篇 §6 第 2 条（TensorRT-LLM V1/V2）和兄弟篇 [[03-SGLang-RadixAttention与前缀缓存]] 里 RadixCache/UnifiedRadixCache 的判断，全靠人工 `grep` 追工厂函数得出。如果 `_lab` 能补一个通用的"从入口点开始的可达性分析"（哪些类可以通过默认参数组合被真正构造出来），后续每一篇涉及"哪个实现是默认值"的文章都能省掉这一步人工核对，也能在源码演进后自动发现"某条判断已经过期"这类漂移。
4. **LightLLM 多 LoRA 场景下的前缀缓存隔离是本篇明确标注的未查证点**，值得单独开一个小任务专门核实：`radix_cache.py` 全文件搜不到 LoRA/adapter 相关字段，这到底是因为 LightLLM 的多 LoRA 走了另一套不经过这条路径的机制，还是一个真实的隔离缺口——目前两种可能性本篇都没有排除。

## 9. 自测题与延伸阅读

**自测题**（闭卷）：

1. TensorRT-LLM 的 `radix_block_tree::UnifiedBlockTree` 和 LMDeploy 的 `BlockTrie` 都组织成了树，为什么它们仍然享受不到 SGLang/LightLLM 那种"节点数只随分叉次数增长、不随序列长度增长"的边压缩优势？决定这件事的是哪个设计选择？
2. 用 §3.2/§3.3 的例子（请求 1 `"ABCDEFGH"`、请求 2 `"ABCDEXYZ"`）：如果把 vLLM 一侧的 `block_size` 从 4 改成 8，命中长度会变成多少？如果改成 1，又会变成多少？这说明了什么？
3. vLLM 的空闲块驱逐完全不打时间戳，为什么在"请求生命周期普遍短且均匀"的场景下这个近似依然接近正确？举一个会让这个近似明显失真的具体请求模式。
4. 一个块的哈希/键如果不混入 LoRA id，会导致什么具体的错误现象？这个现象在日志里会长什么样（会报错吗）？
5. 分层缓存的判据公式 `N > L/(C-S/BW)` 里，如果某个存储层级的 `C ≤ S/BW`，说明了什么？这对"要不要把 offloading connector 接到这一层"这个工程决策意味着什么？
6. LMDeploy 用"树根按 adapter 分开"而不是"把 adapter id 混进每个节点的哈希"来隔离 LoRA，这两种做法在"新增一个 LoRA 适配器"这个操作的开销上会有什么不同？
7. 为什么本篇认为"哈希表 vs 基数树"是一个不完整的二元框架？用 §4.1 的四格矩阵，TensorRT-LLM 和 LMDeploy 应该填在哪一格？
8. §3.5 里，vLLM 的共享块 `Block#1`（`[A,B,C,D]`）能活到最后才被驱逐，靠的是什么机制？这个机制在"两个请求几乎同批结束"时会不会失灵？SGLang 的 `P` 节点呢？
9. llama.cpp 的 `t_last_used` 是六家里唯一的"真时间戳 LRU"，但为什么它只在"没有任何 slot 匹配上 LCP 相似度"时才生效？这说明 llama.cpp 把"匹配"和"驱逐"这两件事的优先级排序，与 vLLM/SGLang 有什么本质不同？
