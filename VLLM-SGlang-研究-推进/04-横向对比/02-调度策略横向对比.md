# 调度策略横向对比

> **本篇取证基准**：`vllm` @ `7ca49fbe`（2026-08-22）；其余引擎 sha 见 `_lab/out/repo_stats.json` 的 `ref` 字段，跨引擎引用一律加 `引擎名:` 前缀。
> **一句话**：同一件事，八个引擎给出八种取舍

## 0. 结论先行

- **"连续批处理"这个词掩盖了三个独立子问题，每家引擎在这三个问题上分别选边站**：① 等待队列按什么顺序出队（排序策略）；② 显存/槽位不够时牺牲谁（让位机制）；③ 这一步给谁分多少 token（预算模型）。八个引擎在这三条轴上组合出的答案几乎两两不同，但没有一家在全部三条轴上都是异类——这才是横向对比真正有意思的地方。
- **排序策略上，FCFS 是默认多数派，前缀感知排序是少数派特性，不是行业共识**：vLLM/LMDeploy/LightLLM/llama.cpp/TGI/Tokasaurus 默认或事实上都按到达顺序处理；SGLang 的 LPM 和 TensorRT-LLM 的 `enablePrefixAwareScheduling`（默认开，`tensorrt-llm:cpp/include/tensorrt_llm/batch_manager/capacityScheduler.h:110`）是仅有的两处"排序/准入决策直接读前缀缓存命中率"的地方，但做法完全不同——SGLang 重排整个等待队列，TRT-LLM 只用它做"这个请求现在跳过是否划算"的二元判断。
- **让位机制上，"要不要允许抢占"本身是一条分水岭**：vLLM、SGLang、LMDeploy、Tokasaurus 默认允许牺牲已在跑的请求腾资源（叫法各不相同：preempt / retract / evict / bump）；TensorRT-LLM 默认策略 `GUARANTEED_NO_EVICT`（`tensorrt-llm:cpp/include/tensorrt_llm/executor/types.h:228`）、TGI、LightLLM、llama.cpp 则默认或架构性地**不**允许——它们靠更保守的准入控制（worst-case 预留、`GUARANTEED_NO_EVICT`、固定 slot）从源头避免走到"资源不够只能牺牲人"这一步。
- **一个独立收敛的反直觉现象**：在允许抢占的四家引擎里，vLLM（`self.running.pop()`）、LMDeploy（`running.pop(-1)`）、Tokasaurus（`running_seqs.pop()`）都选择了"牺牲最后加入 running 的请求"（LIFO 倾向），LightLLM 的迭代耗尽式实现在效果上也偏向新请求——只有 SGLang 反过来选"已生成 token 数最少者"。四个互不知情的工程团队分别收敛到近似 LIFO，这不是巧合，`## 7` 会给出机制解释。
- **收束判据（本篇不产出实测数字，只讲机制因果）**：连续批处理相对静态批处理的全部收益，来自两件独立的事同时发生——**输出长度异质**（否则没有人会提前结束、腾出名额）和**在线到达**（否则准入/抢占分支永远不会被触发）。这条判据在 [[03-vLLM-调度器解剖]] `## 5` 决策 5 里已用源码证据展开；本篇跨引擎复核后发现，**这条判据对全部八家引擎都成立，是唯一一条不因实现差异而改变结论的规律**——同质离线批量场景下，本篇讨论的全部排序/让位/预算差异都会退化成无意义的开销，这也是为什么本篇拒绝比较任何吞吐/延迟数字：机制差异只在异质+在线的流量下才产生可观测后果，脱离流量形状谈"谁的调度器更好"没有意义。

## 1. 它在系统里的位置

八家引擎的调度器都在解同一个三段式问题，只是把它拆分到不同的进程/线程边界里：

```
新请求进来 ──▶ [准入/排序]：谁先被考虑？看不看前缀缓存？
                    │
                    ▼
              [预算分配]：这一步谁能上场？吃几个 token？
                    │
                    ▼
              [资源不够时]：要不要牺牲已在跑的请求？牺牲谁？
```

这三段在源码里对应的位置，跨引擎差异很大——**这本身就是横向对比要先讲清楚的一层**，因为后面每一节的"实现位置"栏，读者需要知道自己在哪个进程/语言层里找：

| 引擎 | 调度决策跑在哪 | 与模型执行是否同进程 |
|---|---|---|
| vLLM | `EngineCore` 进程，纯 Python | 否，`AsyncLLM`/API 是另一进程（[[03-vLLM-调度器解剖]] `## 1`） |
| SGLang | `Scheduler` 进程，纯 Python | 否，三进程各自独立（[[02-SGLang-Scheduler事件循环]] `## 1`） |
| TensorRT-LLM | worker 进程内，C++（经 nanobind 暴露给 Python） | 是，Python 只转发调用（[[01-TensorRT-LLM]] `## 3.2`-`## 3.3`） |
| LMDeploy（PyTorch 后端） | 单进程，Python asyncio 事件循环（`lmdeploy:lmdeploy/pytorch/engine/engine.py:604`） | 是 |
| LMDeploy（TurboMind 后端） | 同进程内独立 C++ 线程（`lmdeploy:src/turbomind/engine/engine.cc:113`） | 是 |
| LightLLM | `RouterManager` 进程，纯 Python，ZMQ 与模型 TP worker 通信 | 否 |
| llama.cpp | 单进程，无独立调度线程——`update_slots()` 在主 HTTP 服务循环里跑 | 是 |
| TGI | Rust `router` 进程（tokio 异步任务） | 否，模型是独立 Python shard 进程（gRPC） |
| Tokasaurus | `manager` 进程，纯 Python | 否，模型 worker 是独立进程（`torch.multiprocessing`） |

三种典型形态：**调度与执行分进程**（vLLM/SGLang/LightLLM/TGI/Tokasaurus，好处是调度器崩溃不拖累 GPU 状态，坏处是每步都要跨进程/跨语言传结果）；**调度下沉到执行进程内的另一种语言**（TensorRT-LLM 的 C++、LMDeploy TurboMind 的 C++ 线程，好处是免掉跨进程序列化开销，坏处是改调度策略要走编译/绑定链路）；**调度与执行完全同进程同语言**（LMDeploy PyTorch 后端、llama.cpp，最简单但也最难做流水线重叠）。这条分类和 `## 2` 表格最后一列"并发模型"一一对应。

**还有一层容易被忽略的划分：谁决定"准入"（新请求何时从 waiting 变成 running），谁决定"续跑"（已在 running 的请求这一步该分多少 token）——这两件事不是所有引擎都放在同一个调用里做的。**

| 引擎 | 准入决策在哪 | 续跑决策在哪 | 是否同一次调用/同一进程 |
|---|---|---|---|
| vLLM | `schedule()` 的 WAITING 循环 | `schedule()` 的 RUNNING 循环 | 同一次 `schedule()` 调用 |
| SGLang | `get_new_batch_prefill()` | `update_running_batch()` | 同一次 `get_next_batch_to_run()` 调用，但两者互斥（`## 4.1`） |
| LightLLM | `req_queue.generate_new_batch()`，跑在 **router 进程**（`lightllm:lightllm/server/router/manager.py:429`-`431`） | `_get_classified_reqs()`，跑在**独立的模型 TP worker 进程**（经 `mp.Process` 启动，`lightllm:lightllm/server/router/model_infer/model_rpc.py:208`） | **不是**——是本篇覆盖的引擎里唯一把准入和续跑拆到两个不同 OS 进程的 |
| 其余五家 | 同一调度对象内部 | 同一调度对象内部 | 同进程/同调用 |

LightLLM 这个分工不是偶然的：`ChunkedPrefillQueue` 的最坏情况模拟（`## 5` 决策 4）只需要请求的元数据（预测输出长度、当前占用），不需要访问 GPU 状态，天然可以放在轻量的 router 进程里；而"这一步具体分几个 token、要不要 pause"需要读 KV 分配器的实时状态，只能放在持有显存的 TP worker 进程里。代价是准入决策用的"能不能放下"判断和续跑进程实际看到的显存状态之间存在一个时间差（router 算完 `generate_new_batch` 到 TP worker 真正执行之间），理论上可能出现准入时判断可行、执行时因为其它并发变化而事实上吃紧的情况——这也是为什么 LightLLM 需要 `## 5` 决策 2 的最坏情况模拟必须足够保守，以及为什么 `pause` 机制作为兜底依然存在。

## 3. 核心数据结构：跨引擎术语翻译表

单引擎解剖篇的 `## 3` 讲的是一个引擎内部的类；本篇是跨引擎横向对比，"核心数据结构"改讲一件更有用的事——**同一个概念在八家引擎里叫什么名字、对应哪个类/函数**，避免读者在切换源码时被术语绊倒。

### 3.1 "牺牲一个正在跑的请求"这件事的八种叫法、八套细节

这是本篇必须回答的第 3 项——不能只讲两家（vLLM/SGLang）就收尾，下表把八家引擎的让位机制拆成五个可比较的维度：叫什么、谁选受害者、放回队列哪个位置、KV 怎么处理、有没有安全阀。

| 引擎 | 术语 | 选谁（victim 规则） | 放回队列哪里 | KV 怎么处理 | 安全阀 |
|---|---|---|---|---|---|
| vLLM | preemption | FCFS 下 `running.pop()`（LIFO）；PRIORITY 下 `(priority, arrival_time)` 最大者 | **队头**（`prepend_request`） | 丢弃重算，V1 无 swap 路径 | 无显式上限，理论上会一直抢占到评估中的请求自己被抢占为止 |
| SGLang | retraction | `_get_decode_retraction_order`：已生成 token 数最少者优先 | **队尾**（与新请求同等竞争） | 单机丢弃重算；`decode disaggregation` 模式下 host 备份（`sglang:python/sglang/srt/managers/schedule_batch.py:1932`-`1940`） | 有：至少保留一个请求（`if len(sorted_indices) == 1: break`）；若最后一个仍放不下则直接 `FINISH_ABORT` |
| TensorRT-LLM | pause（仅 `MAX_UTILIZATION`） | 从活跃列表末尾反向查找最近启动者 | 不入队列，留在 active 列表里等下次被重新纳入调度 | 丢弃重算（`schedulingRemoveSequence`），未见 host 备份分支 | 反向查找到 `reqIt`（评估中的请求）为止，找不到就整体 `break` |
| LMDeploy | 无专名，代码里叫 `evict` | `running.pop(-1)`（running 已按 arrive_time 排序，取最新） | 回到 `WaitingState`，按 arrive_time 重新参与排序（结构上接近队尾） | 丢弃重算；`swap_in_map`/`swap_out_map` 字段声明但从未填充（`## 7`） | 循环驱逐至 `running` 空；若仍不够，评估中的 `seq` 自身被 evict（`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:832`-`834`） |
| LightLLM | pause | 迭代 `ready_reqs`（插入序）预算耗尽处触发，偏向更晚加入者 | 保留在 `paused` 状态，同一进程内按 `can_alloc_token_num` 恢复（不入等待队列） | 丢弃重算（`free_a_req_mem`），恢复时 `_match_radix_cache` 可命中前缀 | 每轮限流 `pause_max_req_num=2`（`lightllm:.../base_backend.py:686`），避免一次性暂停过多 |
| llama.cpp | 不存在 | — | — | — | 不适用，架构上没有这个操作 |
| TGI | 不存在（请求级） | — | — | — | 不适用；`evict()` 只作用于无引用的前缀缓存 block |
| Tokasaurus | bump | `running_seqs.pop()`（LIFO） | **队头**（`insert_at_head_of_queued`） | 新建 id 丢弃原 KV，注释明写不做增量续算（纯重算） | 循环驱逐至满足 `num_needed_blocks <= num_free_blocks`，无显式上限 |

**读这张表要避免的误解**：不要把"术语不同"等同于"行为随意"。八个名字背后只有两种真实语义——**允许丢弃重算**（vLLM/SGLang/TRT-LLM/LMDeploy/LightLLM/Tokasaurus 六家，只是谁来选、选谁、放回哪里各不相同，见 `## 5` 决策 2/3）和**架构上不存在这个操作**（llama.cpp/TGI 两家，靠更保守的准入控制回避这个问题）。

**放回队列的位置这一列值得单独强调**：vLLM 和 Tokasaurus 都选择插回**队头**（受害请求下一步优先重试），SGLang 选择插回**队尾**（与新请求平等竞争，`## 5` 决策 2 已在 [[02-SGLang-Scheduler事件循环]] 里指出这是它"没有插队特权"的设计），LMDeploy 的效果接近队尾（按 arrive_time 重新排，不获得特殊优待）。**放回队头 vs 队尾直接决定了受害请求的恢复延迟是否有上界**——队头意味着"下一步大概率被优先捡起"，队尾意味着"恢复时间不确定，取决于新请求到达速率"，这条差异比"用什么词描述这个操作"更值得工程师关心。

### 3.2 每家引擎"一次调度决策"的核心返回类型

这组类型决定了调度器与执行层之间的契约边界，横向看能发现一个共性：**返回类型越丰富，说明这个调度器承担的职责越多**。

| 引擎 | 类型 | 字段数量级 | 备注 |
|---|---|---|---|
| vLLM | `SchedulerOutput`（`vllm:vllm/v1/core/sched/output.py:206`） | 14 个顶层字段 | 见 [[03-vLLM-调度器解剖]] `## 3.2`，多数字段服务 KV connector/投机解码等旁路系统 |
| SGLang | `NextBatchPlan`（`sglang:python/sglang/srt/managers/schedule_batch.py:3429`） | 2 个字段 | 只有 `batch_to_run`/`running_batch`，调度决策与状态更新显式分离 |
| TensorRT-LLM | 三元组 `(scheduled, paused, fitting_disagg_gen_init)` | 3 个 | 原始 C++ 返回签名，Python 只转发，不是 dataclass 契约 |
| LMDeploy | `SchedulerOutput`（`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:67`） | 4 个字段 | `running`/`swap_in_map`/`swap_out_map`/`copy_map`——后两个字段是 `## 7` 要讲的死代码 |
| LightLLM | `Batch`（新建的请求列表对象） | 1 个（请求列表） | 无独立"本步决策"结构，`generate_new_batch` 直接返回可跑的 `Batch` |
| llama.cpp | 无——直接操作 `slots` 数组 | — | 没有把"这一步决策"物化成独立对象，`update_slots()` 就地改状态 |
| TGI | `(entries, batch, span)` 元组 | 3 个 | Rust 侧同样是元组而非结构体 |
| Tokasaurus | `ScheduleDecision`（`tokasaurus:tokasaurus/manager/types.py` 附近） | 3 个字段 | `decoding_seqs`/`prefill_seqs`/`id` |

vLLM 和 SGLang 的字段数量差异（14 vs 2）不是"谁设计得更好"，而是 **vLLM 把 KV connector、投机解码、结构化输出等旁路系统的通信也塞进了同一个契约对象**；SGLang 把这些旁路信息通过其它通道（比如直连 ZMQ socket）传递，`NextBatchPlan` 只承载最核心的批次决策。两种做法在 [[03-vLLM-调度器解剖]] `## 5` 决策 6 与 [[02-SGLang-Scheduler事件循环]] `## 5` 决策三分别有更深的讨论。

## 4. 主流程走读：prefill/decode 怎么二选一，固定 slot vs 动态调度

### 4.1 判据对照：这一步是 prefill 还是 decode，谁来决定

八家引擎在这个问题上分两大阵营：**无阶段区分**（一个批次天然是 prefill 和 decode 的混合体，由 token 预算决定谁能进批）和**批类型互斥**（一轮迭代要么是纯 prefill 批要么是纯 decode 批，由"是否存在可调度的新 prefill"这个布尔判据决定）。

| 引擎 | 阵营 | 判据位置 | 混部 prefill/decode 的方式 |
|---|---|---|---|
| vLLM | 无阶段区分 | `vllm:vllm/v1/core/sched/scheduler.py:487`-`495`（源码注释原话："There's no 'decoding phase' nor 'prefill phase'"） | 天然混部，每请求独立追赶 `num_computed_tokens` |
| SGLang | 批类型互斥（默认） | `sglang:python/sglang/srt/managers/scheduler.py:3191`-`3200`（"Run prefill first if possible"） | 仅 `enable_mixed_chunk=True` 时通过 `ForwardMode.MIXED` 混部，默认关闭 |
| TensorRT-LLM | 两级调度：`CapacityScheduler` 决定谁能进，`MicroBatchScheduler` 再拆 context/generation 批 | `tensorrt-llm:tensorrt_llm/_torch/pyexecutor/_util.py:3082`-`3094` | in-flight batching 允许同批混部，具体由 C++ 两级调度器共同决定 |
| LMDeploy | 批类型互斥 | `lmdeploy:lmdeploy/pytorch/paging/scheduler.py:841`-`850`（`schedule(is_prefill: bool, ...)` 显式传入布尔） | 上层 engine 循环显式在 prefill/decode 两个调用之间切换，不在调度器内部混部 |
| LightLLM | 无阶段区分 | `lightllm:lightllm/server/router/model_infer/mode_backend/base_backend.py:718`（`is_decode = req_obj.cur_kv_len + 1 == req_obj.get_cur_total_len()`） | 天然混部，同一轮 `prefill_reqs`/`decode_reqs` 两个列表可以同时非空 |
| llama.cpp | 无阶段区分（slot 级） | `llama.cpp:tools/server/server-context.cpp:2723`（`update_slots()`） | 同一次 `llama_decode` 调用里不同 slot 可以分别处于 prefill/decode 状态，物理上混部在一个 batch 里 |
| TGI | 无阶段区分（chunked 时） | `tgi:backends/v3/src/backend.rs:221`-`231`（`support_chunking` 分支：`entries.extend(new_entries)` 后一起 `prefill()`） | 支持 chunking 时新 prefill 与旧 cached batch 拼接一起跑；不支持时退化为"先等新 batch 跑完首 token 再拼" |
| Tokasaurus | 无阶段区分（预算共享） | `tokasaurus:tokasaurus/manager/scheduler.py:600`-`605`（`max_prefill = max_tokens_per_forward - len(decoding_seqs)`） | decode 先扣预算，剩余预算给 prefill，同批天然混部 |

**规律**：把执行状态放在**单请求**粒度追踪的引擎（vLLM、LightLLM、Tokasaurus、TGI-chunking、llama.cpp 的 slot 级）天然支持混部；把执行状态放在**批**粒度追踪的引擎（SGLang 默认、LMDeploy）需要显式的"是否混部"开关才能打破互斥，这不是谁更先进，而是数据结构的选择决定了混部是不是"顺手"的事——批粒度状态机的代码更好读（`ForwardMode` 一个枚举说清楚这一步是什么），代价是要多写一条 `MIXED` 分支才能拿到混部的吞吐收益。

### 4.2 chunked prefill 默认开关与块大小对照

| 引擎 | 默认开关 | 块大小怎么定 |
|---|---|---|
| vLLM | 开（`enable_chunked_prefill`） | 无固定值——当步共享 `token_budget` 剩多少切多少，`long_prefill_token_threshold` 默认 `0`=不额外限制 |
| SGLang | 开（`chunked_prefill_size` 默认非 -1） | `chunk_tokens_limit`，超出截断到页对齐的 `trunc_len` |
| TensorRT-LLM | 由 `ContextChunkingPolicy` 决定顺序而非开关；具体块大小受 KV/token 约束联合决定 | 未在本篇深挖单块大小公式（未查证具体默认字节数） |
| LMDeploy | 无独立开关，架构性地总是按预算切 | `cache_config.max_prefill_token_num`（默认 8192），多模态场景可能更大 |
| LightLLM | 开（`disable_chunked_prefill` 默认 `False`） | 由 `batch_max_tokens` 与预算模拟共同决定，无固定块大小常量 |
| llama.cpp | 无独立特性——`n_ubatch` 本身就是每次物理前向的粒度 | `n_ubatch`（默认 512） |
| TGI | `support_chunking` 由部署方模型决定是否开启 | `prefill_token_budget - prefill_tokens`（动态，剩多少切多少，类似 vLLM） |
| Tokasaurus | 隐含，无独立开关 | 由 `calc_prefill_per_forward` 算出的 `num_prefill` 逐请求分配，`prefill_round_up_multiple`（默认 16）对齐 |

**共性**：除 llama.cpp（块大小=物理批大小，与"避免长 prompt 独占一步"的动机无关）之外，**所有支持 chunked prefill 的引擎都把"避免一个长 prompt 独占一整步、拖慢并发 decode 请求的 token 间延迟"作为唯一动机**——这条动机在 vLLM/SGLang/TGI 三家的源码注释里都有直接或间接的表述，llama.cpp 没有这个概念是因为它的并发上限被固定 slot 数原生限制住了，本来就不存在"一个请求占满一整步预算"这种情况。

**TensorRT-LLM 的 `ContextChunkingPolicy` 值得单独展开**，因为它是本篇覆盖的引擎里唯一把"多个长 prompt 同时排队时，先紧着谁的 chunk 切"做成显式可选策略的：`kFIRST_COME_FIRST_SERVED`（`tensorrt-llm:cpp/include/tensorrt_llm/executor/types.h:239`-`240`，docstring 原话"Sequential chunking, complete the unfinished context phase first"）会把预算集中喂给队首那一个长 prompt，让它尽快切完；`kEQUAL_PROGRESS`（`tensorrt-llm:cpp/include/tensorrt_llm/executor/types.h:241`-`243`，"Iterate through each context request in sequence and attempt to increase its chunk count until the constraint is exceeded"）反过来把预算雨露均沾地摊给所有排队的长 prompt，让它们的 TTFT 大致同步推进而不是一个接一个地"谁先来谁先吃完"。vLLM/SGLang/TGI 的 chunked prefill 都没有这个"多个长请求之间怎么分预算"的二级策略——本篇通读代码确认它们默认行为等价于 `FIRST_COME_FIRST_SERVED`（谁在预算循环里先被遍历到，谁先吃满这一步的份额），但没有把"要不要换成雨露均沾"做成可配置项。

### 4.3 固定 slot（llama.cpp）vs 动态调度（其余七家）

llama.cpp 是本篇八家引擎里唯一一个不做"动态调度"的：

- **动态调度七家**的共同前提是"KV cache 是一个可以按 block/page 细粒度分配的池子"，调度器每步决定这个池子怎么在请求间重新分配。
- **llama.cpp** 反过来：先按 `--parallel`/`-np`（server 默认 `-1`→自动 `4`，`llama.cpp:tools/server/server.cpp:152`-`156`）固定切出 N 个 slot，每个 slot 独立持有自己的 KV 状态，调度问题退化成"选一个空闲/前缀相似的 slot"（`llama.cpp:tools/server/server-context.cpp:1500`），不存在跨 slot 的资源重新分配。

两种模型的根本差别是**内存管理粒度**：动态调度以 block/page（通常 16-256 token）为单位管理显存，允许并发数随请求实际显存占用弹性伸缩；固定 slot 以"整条序列的最大长度"为单位预留显存（每个 slot 预留 `n_ctx / n_parallel`），并发数在启动时就写死，与实际请求长度分布无关。`## 5` 决策 5 用三样法则展开这个选择的代价。

### 4.4 一步之内，谁先花预算——八家引擎的消耗顺序

`## 4.1` 讲的是"这一步整体算 prefill 还是 decode"，这里更进一步：**在同一步预算够但不够所有人的情况下，谁先拿到份额**。这条顺序决定了"预算紧张时，decode 的 token 间延迟和新请求的 TTFT 哪个先被牺牲"。

| 引擎 | 预算消耗顺序 | 后果 |
|---|---|---|
| vLLM | RUNNING（含 decode 与未完成 chunked prefill）全部先扫一遍，剩余预算才轮到 WAITING（`vllm:vllm/v1/core/sched/scheduler.py:531`-`753` 先于 `:755`-`1176`） | 已在跑的请求（含 decode）优先，新请求 TTFT 可能因老请求占满预算而变长（[[03-vLLM-调度器解剖]] `## 5` 决策 1） |
| SGLang | 有新 prefill 批可组就无条件先跑它，decode 只在"没有新 prefill 可跑"时兜底（`sglang:python/sglang/srt/managers/scheduler.py:3191`-`3200`） | 与 vLLM 完全相反：新请求 TTFT 优先，decode 的 token 间隔可能被持续到达的新 prefill 无限期推迟（`prefill_decode_interval` 默认 `0`=不设限） |
| TensorRT-LLM | 两级调度：`CapacityScheduler` 先决定谁能进这一步的活跃集合，`MicroBatchScheduler` 再按 `ContextChunkingPolicy` 分配 context（prefill）份额，generation（decode）请求通常独立成批 | 具体优先级取决于两级调度器的策略组合，本篇未追踪全部组合下的确定性顺序（未查证） |
| LMDeploy | 外层 engine 循环显式传入 `is_prefill` 布尔，`_schedule_prefill`/`_schedule_decoding` 二选一执行，不在同一步内竞争同一份预算 | prefill 和 decode 完全分属不同的调度调用，谁先谁后由上层引擎循环的调用顺序决定，调度器本身不做取舍 |
| LightLLM | 单次遍历 `ready_reqs`（插入序），逐请求判断 `is_decode` 后立即扣减共享的 `can_alloc_token_num`——**没有"decode 全部先来"或"prefill 全部先来"的整体阶段**，谁在列表里靠前谁先拿 | 效果上偏向"先加入 running 的请求"（不分 prefill/decode），与到达顺序绑定 |
| llama.cpp | 无共享预算——每个 slot 独立更新，`update_slots()` 在一次 `llama_decode` 调用里把所有活跃 slot 的 token 一起提交 | 不存在"谁先花预算"的问题，slot 数量本身就是硬上限 |
| TGI | 已有的 cached batch（decode）总是继续；新 prefill 能否追加取决于 `support_chunking`——开启时与当前 batch 拼接一起跑，关闭时新 prefill 要等当前批处理完 | 默认（`support_chunking` 视模型支持而定）行为接近 vLLM：已在跑的优先，新请求排队 |
| Tokasaurus | 显式公式 `max_prefill = max_tokens_per_forward - len(queue.decoding_seqs)`（`tokasaurus:tokasaurus/manager/scheduler.py:598`）——**decode 先无条件拿到 1 个名额/请求，剩余预算才给 prefill** | 与 vLLM 同向：decode 优先，且是本篇里唯一把这条优先级写成一行显式算术公式（而不是隐含在循环顺序里）的引擎 |

八家里，**vLLM/Tokasaurus/TGI（默认）站"decode 优先"一边，SGLang 站"prefill 优先"一边，LightLLM 不分阵营（按到达顺序统一竞争），LMDeploy/llama.cpp 因为架构原因不存在这个竞争**。这条分野和 `## 4.1` 的"批类型是否互斥"高度相关但不是同一回事——TGI 支持 chunking 时批类型不互斥，但优先级依然明确偏向已在跑的 decode 请求。

## 5. 设计决策与代价

### 决策 1：排序要不要读前缀缓存——FCFS vs LPM，以及 LPM 会不会饿死请求

- **为什么这么设计**：FCFS（vLLM/LMDeploy/LightLLM/TGI/Tokasaurus 默认）的理由是可预测性——运营者能对"一个请求最多等多久"给出上界估计，实现也最简单（`deque`/`VecDeque`/list 直接够用）。SGLang 的 LPM（`sglang:python/sglang/srt/managers/schedule_policy.py:381`-`391`，`_sort_by_longest_prefix`，排序键是 `-num_matched_prefix_tokens`）反过来押注"命中共享前缀的收益，大于打乱到达顺序的代价"——这在大量请求共享长 system prompt/few-shot 模板的场景下能显著减少前缀 block 被中间请求挤出 LRU 的概率。
- **不这样会怎样**：FCFS 场景下，如果客户端把共享前缀的请求打散发送，批次内几乎没有前缀复用，前缀缓存退化成"每请求独立 KV cache"；LPM 场景下，一个前缀完全不匹配（`num_matched_prefix_tokens=0`）的请求会被排到队尾——**本篇核实过 SGLang 源码，`schedule_policy.py` 通篇没有基于等待时长的加权或老化（aging）机制**，唯一的兜底是等待队列长度超过 128 时自动退化回 FCFS（`sglang:python/sglang/srt/managers/schedule_policy.py:290`-`294`，函数 `_determine_active_policy`），但这条判据的注释写的是"关掉昂贵的前缀匹配和排序计算"（性能考虑），公平性只是这条性能优化的副作用，不能当成显式防饥饿设计来依赖。跨引擎看，**TensorRT-LLM 的 `enablePrefixAwareScheduling`（默认开）不会有这个问题**，因为它只做"这个请求现在跳过是否划算"的二元判断（`tensorrt-llm:cpp/tensorrt_llm/batch_manager/capacityScheduler.cpp:544`-`551`），不重排整个队列，一个请求最多被跳过若干次而不会被无限期挤到队尾——这是两种"前缀感知"设计在饥饿风险上的实质差异，不是名字接近就等价。
- **什么时候可以不这样**：等待队列很短、或请求间本来就没有前缀重叠时，LPM 相对 FCFS 几乎不产生收益（`## 5` 只讲机制因果，不给具体数字）；`tree_cache.disable=True`（未启用前缀缓存）时 SGLang 会自动把 LPM 降级为 FCFS（`sglang:python/sglang/srt/managers/schedule_policy.py:311` 附近）。反过来，如果流量里长尾请求（长时间等不到共享前缀命中）比例不可忽视，运营者应该考虑改用 vLLM 式的 `PRIORITY` 二级排序（`priority` + `arrival_time` 兜底）而不是 LPM——`PRIORITY` 策略结构性地保证了"到达时间"永远是排序的一个维度，不会出现"某个特征值一直不利就永远排不上"的情况。

### 决策 2：允许抢占 vs 架构性不允许——这是比"选谁被抢占"更上游的一层决策

- **为什么这么设计**：允许抢占（vLLM/SGLang/LMDeploy/Tokasaurus）的理由是"准入要尽量激进，把决定权留到真正扛不住的那一刻"——这样能让 KV cache 利用率逼近上限，代价是需要一套让位机制兜底。不允许抢占（TRT-LLM 默认 `GUARANTEED_NO_EVICT`、TGI、LightLLM、llama.cpp）的理由反过来：**在准入的那一刻就用保守估计把"未来会不会撑爆"算清楚**，一旦通过准入就不再有被中途打断的风险。LightLLM 的 `ChunkedPrefillQueue._can_add_new_req`（`lightllm:lightllm/server/router/req_queue/chunked_prefill/impl.py:24`-`51`）是这条思路最直白的实现：假设所有在跑请求都跑到各自的（预测或最大）输出长度，模拟出未来任意时刻的 KV 峰值占用，`need_max_token_num < max_total_tokens` 才放行——只要这个不等式在准入时成立，理论上运行阶段就不需要再牺牲任何人。TRT-LLM 的类名 `GuaranteedNoEvictScheduler`（`tensorrt-llm:cpp/include/tensorrt_llm/executor/types.h:225`-`227`，文档字符串原话"a request, once started, will run to completion without eviction"）把这个承诺写进了名字本身。
- **不这样会怎样**：保守准入的代价是**并发度天花板更低**——LightLLM 假设最坏情况（所有请求都跑到预测/最大长度），比实际发生的情况更悲观，能同时接纳的请求数会少于"边跑边看"的激进准入策略；TRT-LLM `GUARANTEED_NO_EVICT` 同理，用 KV 更保守换取零中断。激进抢占的代价则是运行时抖动——一个后来的大请求可能把已经跑了很久的请求连本带利地打断重算（`## 5` 决策 3 展开"打断谁"）。
- **什么时候可以不这样**：延迟 SLA 极度敏感、且宁可拒绝新请求也不愿意任何已在跑请求被打断的场景，`GUARANTEED_NO_EVICT`/TGI/LightLLM/llama.cpp 这类保守路线是更安全的默认；追求 KV cache 利用率最大化、能容忍偶发重算开销的吞吐优先场景，vLLM/SGLang/LMDeploy/Tokasaurus 的激进准入 + 让位兜底更合适。TRT-LLM 把两条路线都做成了可切换的策略（`MAX_UTILIZATION` vs `GUARANTEED_NO_EVICT`），这本身就是"没有一个答案通吃所有工作点"的证据。

### 决策 3：让位受害者选谁——四个团队为什么都独立收敛到近似 LIFO

- **为什么这么设计**：vLLM（`vllm:vllm/v1/core/sched/scheduler.py:686`，`self.running.pop()`）、LMDeploy（`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:829`，`running.pop(-1)`）、Tokasaurus（`tokasaurus:tokasaurus/manager/manager.py:764`，`running_seqs.pop()`）三家显式选择"牺牲最后加入 running 的请求"；TRT-LLM 的 `MAX_UTILIZATION` 从活跃列表末尾反向查找最近启动者（`tensorrt-llm:cpp/tensorrt_llm/batch_manager/capacityScheduler.cpp:562`-`565`）；LightLLM 的迭代耗尽式实现（`lightllm:lightllm/server/router/model_infer/mode_backend/base_backend.py:692`-`748`，`ready_reqs` 按插入序遍历，预算耗尽处触发 `wait_pause`）在效果上也偏向更晚加入的请求。**本库推断**这五家收敛的共同直觉是"沉没成本最小化"——最近加入 running 的请求，无论是刚开始 chunked prefill 还是刚从 waiting 转正，它已经消耗的计算相对更少，牺牲它损失的"已经白算的工作"最小；牺牲一个跑了很久的请求，等于把它已经产出的大量 decode token 对应的计算全部作废。只有 SGLang 反过来选"已生成 token 数最少者"（`sglang:python/sglang/srt/managers/schedule_batch.py:2825`-`2860` 附近，`_get_decode_retraction_order`）——这条规则表面上和"沉没成本最小化"的直觉相反，但本质是同一个目标的另一种度量：SGLang 直接量化"这个请求已经产出了多少 token"，而不是用"何时加入 running"做代理指标，在请求生成速度不均匀（比如有的请求刚加入就秒出很多 token）时，SGLang 的度量更精确，代价是需要额外维护一个按生成量排序的结构，不像"pop 列表末尾"那样零成本。
- **不这样会怎样**：如果反过来选"牺牲资历最老的请求"（没有引擎这么做），会把已经投入最多计算的请求作废，浪费最大，且该请求可能因为反复排在队伍前面而反复被优先执行、反复被打断，形成恶性循环。
- **什么时候可以不这样**：新加入 running 的请求恰好是一个刚开始的巨型 chunked prefill（还没产出任何 decode token，但即将占用大量后续预算）时，"最近加入=沉没成本最小"这条经验规则会失真——打断它损失确实最小，但如果频繁出现"大请求一进来就被自己触发的资源紧张打断"，会导致这类大请求系统性地难以推进（一种隐性的饥饿）。这是本库通读源码后没有在任何一家引擎里发现专门处理的边界情形，值得作为可改进点看待（见 `## 8`）。

### 决策 4：token 预算模型——共享标量 vs 逐请求最坏情况模拟 vs 固定 slot

- **为什么这么设计**：vLLM/TGI 用**共享标量**（`token_budget`/`prefill_token_budget`，每步从满额往下扣，扣完就停），实现最简单，天然支持 chunked prefill 的"这一步预算够多少算多少"。LightLLM/Tokasaurus 用**逐请求最坏情况模拟**（`lightllm:lightllm/server/router/req_queue/chunked_prefill/impl.py:35`-`36` 的 `need_max_token_num`；`tokasaurus:tokasaurus/manager/scheduler.py:434`-`530` 的 `calc_prefill_per_forward`），把"未来会不会撑爆"提前算进当前这一步的决策里，代价是每步都要跑一遍模拟（Tokasaurus 甚至要在多个时间点上滚动模拟 KV 占用曲线）。llama.cpp 用**固定 slot**，压根不做逐 token 的预算计算，只有"这个 slot 空不空"一个二元判断。
- **不这样会怎样**：纯共享标量模型不主动预判未来，可能在某一步准入的请求，几步之后因为大家都在稳定 decode 而集体撑爆 KV cache，触发让位机制（`## 5` 决策 2/3）；最坏情况模拟模型如果估计过于悲观（比如所有请求的 `max_new_tokens` 都设得很大但实际很快就停），会系统性地低估可用并发度，浪费本可以用上的显存。
- **什么时候可以不这样**：请求的输出长度分布本身很好预测（比如固定长度的分类/打分任务）时，最坏情况模拟的悲观代价很小，共享标量和最坏情况模拟在实际效果上会趋同；输出长度高度不可预测（开放式长文生成）时，最坏情况模拟的保守代价会被放大，共享标量+让位兜底反而更划算——这正好解释了为什么"要不要允许抢占"（决策 2）和"用什么预算模型"（决策 4）在各引擎里高度相关：LightLLM/Tokasaurus 选了保守预算模型，自然也倾向不依赖激进的抢占来兜底（Tokasaurus 虽然有 bump，但 `greedy_prefill=True` 的默认路径本来就很少触发它）。

### 决策 5：固定 slot（llama.cpp）vs 动态调度（其余七家）

- **为什么这么设计**：固定 slot 把"并发数"这个决策提前到启动时做一次性决定，运行时不再需要任何跨请求的资源仲裁逻辑——`get_available_slot()` 的复杂度只来自"选哪个空 slot"，不涉及"要不要为了新请求牺牲旧请求"。这是一种用**部署时的确定性**换**运行时的简单性**的设计：管理员知道这台机器最多同时服务 N 个请求，不会有任何请求因为资源竞争被打断或拒绝额外的推理开销。
- **不这样会怎样**：固定 slot 的显存利用率上限由"最坏情况下每个 slot 需要多少 KV"决定（`n_ctx / n_parallel`），如果实际请求普遍比 `n_ctx` 短很多，这部分预留显存是浪费的；动态调度按 block/page 粒度分配，能把这部分浪费降到更低，代价是需要完整的一套准入/让位逻辑（本篇 `## 2`-`## 5` 讨论的全部内容）。
- **什么时候可以不这样**：单机部署、请求长度分布已知且波动不大、更看重"行为完全可预测、没有任何隐性调度开销"的场景（比如本地开发、边缘设备、小规模自托管），固定 slot 模型的简单性本身就是优点，不需要为了榨取理论上限的显存利用率去承担动态调度的实现与运维复杂度。反过来，多租户、请求长度差异大、需要把显存利用率压到极限的生产服务场景，动态调度是几乎必然的选择——这也是为什么本篇覆盖的另外七家引擎全部走了动态调度这条路。

## 6. 口径差异与本篇不能回答什么

本篇是跨八个代码库的横向对比，比单引擎解剖篇更容易掉进"表面相似、口径不同"的陷阱，以下几点是本库诚实标注的边界：

1. **"token 预算"这个词在不同引擎里不是同一个物理量**。vLLM/TGI 的预算是纯 token 计数；TRT-LLM 的准入约束本质是 KV block 可用量（`maxNumRequests` 只是请求数上限，真正的资源约束在 `kvCacheManager` 侧，本篇 `## 2` 表格为了可比性把它归类到"token 预算参数"这一列，但读者需要知道这是一次概念上的近似对齐，不是同一个数字）；LightLLM/Tokasaurus 的"预算"是滚动模拟出来的动态曲线，不是一个静态常量。逐字对比"谁的预算数值更大"没有意义。
2. **本篇不产出、也不比较任何实测吞吐/延迟数字**——这是 `_PLAN.md` 的红线，也是本篇任务书的硬性要求。凡是"哪种策略更快"的问题，本篇只回答机制上的因果链条（比如"LPM 命中前缀能减少重复计算"），不回答"快多少"，因为这个数字依赖硬件、模型、流量形状，脱离这些前提给数字就是编造。
3. **本篇没有覆盖 LMDeploy 的 TurboMind（C++）后端的完整调度逻辑**。TurboMind 的准入/驱逐是基于时间戳的 LRU cutoff 迭代器（`lmdeploy:src/turbomind/engine/scheduler.cc:73`-`77` 一带的 `EvictingIterator`），和本篇主表所有条目的"请求级排序+让位"模型不是同一套抽象，本库判断需要独立成篇才能讲清楚，此处只在 `## 2`/`## 7` 提及其存在，不展开机制细节。
4. **TensorRT-LLM 的 `ContextChunkingPolicy` 默认解析路径未完全追踪**——`context_chunking_policy` 字段默认是 `None`（`tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:3494`-`3495`），C++ 侧在未显式设置时具体走哪条分支，本库没有继续深挖调用链条确认，`## 2` 表格里"首值 FIRST_COME_FIRST_SERVED"只是枚举声明顺序，不代表已核实为运行时默认值——这一点明确标注为**未查证**，不拿枚举声明顺序冒充确认过的默认行为。
5. **多个配置项组合后的交互效应超出本篇范围**。比如 vLLM 的 `PRIORITY` 策略叠加自定义 `priority` 与前缀缓存命中率会怎么互相影响、SGLang 的 `enable_mixed_chunk` 打开后与 LPM 排序同时生效会是什么效果——本篇只逐个讲清楚单一机制，没有做组合场景的推演，需要哪种组合就去读对应引擎的解剖篇（[[03-vLLM-调度器解剖]]/[[02-SGLang-Scheduler事件循环]]）。
6. **本篇的证据全部来自静态代码走读，不包含任何运行时观测**。所有"victim 选择偏向新请求"这类结论，是读代码得出的必然逻辑推导（比如 `list.pop()` 的语义是确定的），不是靠插桩或 profiling 验证过的运行时行为——这两者在本库的证据等级体系里都算"源码为证"，但读者不应把它和"我们跑过测试观察到"混为一谈。

## 7. 踩坑与反直觉

1. **LMDeploy 的 `swap_in_map`/`swap_out_map` 是贯穿三层调用链的死代码**。`SchedulerOutput`（`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:66`-`73`）声明了这两个字段，一路透传到 `InputsMaker`（`lmdeploy:lmdeploy/pytorch/engine/inputs_maker.py:263`-`264`）、再到 `cache_engine.swap_in`/`swap_out`（`lmdeploy:lmdeploy/pytorch/engine/model_agent/agent.py:157`-`161`）——整套 swap-to-host 的管线都还在，但 `_schedule_prefill`/`_schedule_decoding` 里这两个字典自始至终只被初始化为空 `dict()`（`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:738`-`739`、`:799`-`800`），本库通读全部调度代码没有发现任何一处对它们赋值。佐证是 `eviction_helper` 目录下**只有一个实现**（`recompute_eviction_helper.py`），`eviction_type` 配置默认值也是 `'recompute'`（`lmdeploy:lmdeploy/pytorch/config.py:102`）——这套 swap 管线更像是历史遗留或为将来预留的接口，不是当前生效的代码路径。
2. **TensorRT-LLM 的默认策略根本不会 pause 任何请求**。`GUARANTEED_NO_EVICT` 是默认值（`tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:3490`-`3491`），只有显式切到 `MAX_UTILIZATION` 才会触发 `## 5` 决策 3 讨论的"反向查找最近启动者"逻辑。第一次读 TRT-LLM 调度代码容易把 `capacityScheduler.cpp` 里的 pause 逻辑当成默认行为来理解，但实际上开箱即用的 TRT-LLM 服务在默认配置下和 TGI/LightLLM 一样是"零请求级中断"的。
3. **TGI 压根没有请求级抢占，"evict" 这个词在它的代码里只指前缀缓存 block 的驱逐**。`tgi:backends/v3/src/radix.rs:363`（`pub fn evict`）操作的对象是 radix trie 里未被任何在跑请求引用的缓存 block，和"牺牲一个正在生成的请求"完全是两回事；请求级别的资源冲突处理方式是简单地把请求 `push_front` 退回队列（`tgi:backends/v3/src/queue.rs:301`/`:326`/`:357`/`:371` 反复出现同一模式），已在跑的批次从未被打断。
4. **llama.cpp 并不是"完全无脑轮询"的固定 slot——它默认就有前缀感知的 slot 选择**。`slot_prompt_similarity` 默认值是 `0.1`（`llama.cpp:common/common.h:678`），不是 `0.0`（关闭），意味着开箱即用的 llama.cpp server 会优先把请求路由到"最长公共前缀相似度最高"的 slot（`llama.cpp:tools/server/server-context.cpp:1514`-`1548`），只有相似度都低于阈值才退化到 LRU 选择。这条机制的效果和 SGLang 的 LPM 神似（都是"利用前缀相似度做放置决策"），但作用域完全不同——llama.cpp 只是在几个固定 slot 之间选一个，不是对整个等待队列重排序，本库认为把两者简单类比为"都支持 LPM"是错误的。
5. **Tokasaurus 的默认行为其实是"prefill 优先"，和它 684 行的"极简"名声不太符合直觉**。`greedy_prefill` 默认 `True`（`tokasaurus:tokasaurus/common_types.py:109`），这条路径下 `schedule()`（`tokasaurus:tokasaurus/manager/scheduler.py:576`）遇到非空 `queue.queued_seqs` 就直接 `make_decision(float("inf"))`（尽快榨干所有排队/在跑的 prefill），效果上接近 SGLang 的"prefill 严格优先"。684 行文件里真正独特的部分——`calc_prefill_per_forward` 的 KV 占用曲线模拟——只有在 `greedy_prefill=False` 时才会被调用到，这是本篇任务书专门点名"这个体量差是好抓手"的地方，但读者需要知道：**默认配置下，这份"好抓手"代码其实没有被执行**。
6. **SGLang 的 LPM 没有防饥饿机制，这条已经被 [[02-SGLang-Scheduler事件循环]] 核实过，本篇跨引擎复核后要补一句更完整的对比**：TRT-LLM 的 `enablePrefixAwareScheduling` 默认开，但它做的是"跳过是否划算"的二元判断而非重排序，所以不存在"排到队尾出不来"的风险；llama.cpp 的前缀相似度只影响 slot 选择，同样不存在请求被无限期挤到队尾的问题。**在本篇覆盖的三种"前缀感知调度"里，只有 SGLang 的 LPM 有理论上的饥饿风险**，这是 SGLang 用"重排整个队列"换取更高前缀命中率所付出的、目前源码里没有兜底的代价。

## 8. 可改进点

以下均为本库基于跨引擎源码对比给出的推断，标注证据依据；未核实是否已有对应引擎的官方 issue 在跟踪。

1. **保守准入路线（TGI/LightLLM/TRT-LLM `GUARANTEED_NO_EVICT`/llama.cpp）在预测失准时缺少兜底**。LightLLM 的最坏情况模拟依赖 `ema_req_out_len` 这类预测值（`lightllm:lightllm/server/router/req_queue/chunked_prefill/impl.py:15`），如果实际输出长度系统性偏离预测（比如模型突然开始生成异常长的重复内容），准入时的"安全"判断可能变得不再安全；TGI/llama.cpp/`GUARANTEED_NO_EVICT` 则完全依赖固定预算/固定 slot，对这类分布漂移没有任何自适应能力。可以考虑借鉴 SGLang `new_token_ratio` 的自适应校准思路（`sglang:python/sglang/srt/managers/scheduler_components/new_token_ratio_tracker.py:14`）：观测到实际输出长度与预测持续偏离时，动态收紧准入阈值，而不是依赖一次性算好的静态预算。风险：这类自适应机制本身可能引入新的调参负担和震荡风险，需要用真实流量验证收敛性（本库不产出这类实测数字）。
2. **让位受害者选择普遍缺少"大请求刚加入即被打断"的特殊处理**（`## 5` 决策 3 提到的边界情形）。vLLM/LMDeploy/Tokasaurus 的 LIFO 式选择，在"新加入的是一个尚未产出任何 token 的巨型 chunked prefill 请求"场景下，可能反复打断同一类请求。可以考虑给"投入的 sunk cost"加一个更精确的度量（比如已计算 token 数，而不是简单的加入时间先后），SGLang 的 `_get_decode_retraction_order` 已经这么做了（虽然只覆盖 decode 阶段），vLLM/LMDeploy/Tokasaurus 可以评估类似思路是否值得引入。风险：更精确的度量需要额外维护排序结构，牺牲当前"pop 列表末尾"零成本的实现简洁性。
3. **跨引擎术语不统一本身是一种可改进的生态问题**（本库推断，非任何单引擎的代码缺陷）。`## 3.1` 列出的八个名字（preempt/retract/pause/evict/bump/…）指向两三种真实语义，但没有统一词汇表——运维团队从一个引擎切换到另一个引擎时，容易因为望文生义而误判行为（比如把 TGI 的 `evict` 当成请求级抢占）。这不是任何单个开源项目能单方面解决的问题，但社区如果能就"连续批处理"相关的核心术语（排序/让位/预算/chunking）达成一份跨项目对照表，能显著降低这类误判——本篇 `## 3.1`/`## 2` 的两张表本质上就是在尝试做这件事。
4. **llama.cpp 的 `slot_prompt_similarity` 只在"选 slot"层面利用前缀信息，没有反过来影响准入顺序**。`get_available_slot()` 目前的逻辑是"有相似 slot 就用，没有就 LRU"（`llama.cpp:tools/server/server-context.cpp:1500`-`1567`），不会因为"某个排队中的请求即将有一个高相似度 slot 空出来"而调整处理顺序。理论上可以让 `defer` 回队列的任务在下次调度时优先匹配到刚变空的高相似度 slot，但这需要给"任务-slot 亲和性"加一层持久化的排队优先级，目前的实现里没有这个结构（本库推断，未核实是否已有上游讨论）。

读完本篇应该能回答的一句话总结：**"连续批处理"不是一个统一的算法，是同一个三问题（怎么排序、资源不够牺牲谁、这一步谁吃多少 token）的八份不同答卷**——FCFS 是默认多数派、前缀感知排序是少数派、允许抢占与否是一条比"选谁被抢占"更上游的架构分水岭，而四个互不知情的团队在"选谁被抢占"这个子问题上独立收敛到近似 LIFO，这比任何单一引擎的设计选择本身更能说明"沉没成本最小化"是这个问题的自然解。所有这些差异只在输出长度异质、请求在线到达的流量下才产生真实后果——脱离这个前提，本篇讨论的一切机制差异都不重要。
