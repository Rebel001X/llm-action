## 0. 结论先行

- **总行数排行本身不难记**：TensorRT-LLM（2,452,198）> SGLang（2,317,985）> Dynamo（2,220,830）
  > vLLM（1,914,984）> llama.cpp（992,377）> Mooncake（548,895）> KTransformers（403,076）
  > LMDeploy（339,214）> TGI（189,926）> LightLLM（148,574）> MLC-LLM（100,240）> Tokasaurus（13,219）。
  难的是下一步。
- **"大"不是同一种大。** vLLM 最大的目录 `model_executor`（424,532 行）几乎全是手写的模型架构与算子层，
  是"广度"；Dynamo 最大的目录 `container/compliance`（652,930 行）里 98.5% 是机器生成的 SBOM 依赖清单
  （`base_sboms/` 一个子目录就是 640,241 行 CycloneDX JSON），跟推理逻辑毫无关系；llama.cpp 最大的目录
  `ggml/src`（364,133 行）是手写的张量库，横跨 CUDA/CPU/Vulkan/SYCL/Metal/RPC/BLAS/OpenCL/Hexagon/
  WebGPU/zDNN/CANN 十几个硬件后端的**独立实现**，是"深度"。三个"大"字面上是同一个词，指向完全不同的东西。
- **SGLang 比 vLLM 大这件事，拆开看才有意义。** SGLang 总行数 2,317,985 确实超过 vLLM 的
  1,914,984，但 SGLang 的 `python/sglang`（1,543,126 行）里，真正对标 vLLM 核心引擎的
  `srt/` 子树只有 763,754 行；差出来的部分主要是 `kernels/`（381,213 行，自带 AOT 编译的算子仓库）
  和 `multimodal_gen/`（324,928 行，图像/视频生成，跟 LLM serving 是两个产品）。见 `## 5` 决策 2。
- **测试/产品比这把尺子对非 Python 项目基本失效。** 它只数 `.py` 文件；Dynamo 的核心引擎是
  608,542 行 Rust，`test_to_src_ratio`（1.114）却是从 193,827 行 Python 胶水层算出来的——完全没提到
  Rust 那一侧；Rust 里光是含 `#[cfg(test)]` 内联测试的文件就有 567 个，一个都没被计入。见 `## 7`。
- **struct_map 的"复杂度落点"是关键词命中，不是语义理解，会撞上离谱的假阳性。** 最夸张的例子是
  Mooncake：它的 `disagg` 桶报了 268,180 行、650 个文件——但 Mooncake 全仓 `files_scanned` 也是 650。
  也就是说这个桶**命中了 100% 的文件**，因为分类关键词表里"mooncake"本身就是一个 disagg 关键词，
  而 Mooncake 的两个包根目录（`mooncake-transfer-engine`、`mooncake-store`）字面上都带"mooncake"。
  见 `## 7`。
- **代码健康度指标是三轮过滤后的产物，过滤本身也会漏网。** "热路径静默 except"密度
  （LMDeploy 1.2 到 Dynamo 21.8）已经排除了探测型文件和 `ImportError`，但 `vllm:vllm/distributed/kv_transfer/kv_connector/v1/hf3fs/hf3fs_connector.py:82`
  这种"用 `except Exception` 写的可选依赖导入守卫"照样会被计入——因为过滤规则认的是异常类型
  写的是不是字面上的 `ImportError`，不是语义。见 `## 6`。
- **重申红线**：本篇不产出任何实测吞吐/延迟数字，行数多少不代表"更强"，也不代表"更臃肿"——
  它只回答"复杂度堆在什么地方"，回答不了"这堆复杂度值不值"。

## 1. 它在系统里的位置

这是 04-横向对比系列的第 4 篇。前三篇（`01-API兼容性横向对比`、`02-调度策略横向对比`、
`03-KV缓存与前缀复用横向对比`，均 ⬜ 待写）讲的是"这些引擎在做同一件事时选择不同"；
本篇讲的是更底层的一件事——**这些引擎的工程体量本身长什么样，复杂度堆在哪个目录，
以及"堆在哪"这个说法能不能站得住脚**。

它和 [[00-总览与阅读地图]] 的关系：00 篇 §4 已经"剧透"了本篇最核心的两条结论
（SGLang 比 vLLM 大、静默 except 密度可以横向比），本篇要做的是把这两条结论从"一句话"
展开成"构成是什么、口径边界在哪、复查过没有假阳性"。00 篇的读者如果只信一句话结论，
本篇存在的理由就是逼自己（也逼读者）把这句话拆开验一遍。

它和后面 `05-选型决策树`（⬜）的关系：选型决策树会引用本篇的口径限制章节——
**行数不能当选型依据**，但"代码量集中在哪个子系统"可以提示"这个引擎的维护重心在哪、
换句话说它更可能优先修哪类 bug"。

## 3. 核心数据结构

本篇不解剖某个引擎的类，解剖的是**产出这些数字的三份 JSON 本身的结构**——
读懂它们的字段，才知道数字的边界在哪。

**`_lab/out/repo_stats.json`**：`engines.<name>` 下四块：
- `totals`：`files_counted`/`lines_counted`（全仓，登记语言）、`python_src_lines`/`python_test_lines`
  （只数 `.py`，路径含 `test` 记为 test）、`test_to_src_ratio`；
- `languages`：按后缀分语言的 `{files, lines, code}`（`code` = 非空非纯注释行）；
- `kernels`：CUDA 文件数、Triton JIT 文件数（判定标准是文件里同时有 `@triton.jit`）、
  提到 `cutlass` 的文件数；
- `top_dirs`：**路径深度 2** 分桶（`_subdir_key` 的 `depth=2`），取行数最大的 20 个目录。

**`_lab/out/struct_map.json`**：`engines.<name>` 下：
- `pkg_roots`：每个引擎认定的"产品代码根"，扫描只在这些子树里进行，`tests/`、`benchmarks/`、
  `docs/` 等目录本身也可能被 `EXCLUDE_PARTS` 二次排除；
- `subsystems`：10 个固定桶（`entrypoint`/`scheduler`/`kv_cache`/`attention`/`model_exec`/
  `distributed`/`quantization`/`speculative`/`structured_output`/`disagg`），每桶按**文件路径关键词
  子串匹配**归类，一个文件可能同时命中多个桶；
- `dir_tree`：**路径深度 3** 分桶，且用的扫描口径跟 `top_dirs`不同（见 `## 7`）。

子系统分类用的关键词表（节选，完整见 `_lab/struct_map.py` 的 `SUBSYSTEMS` 字典）：
`kv_cache` 命中 `kv_cache`/`block_manager`/`cache_engine`/`memory_pool`/`radix_cache`/
`prefix_cache`/`block_pool`/`kv_pool`/`paged`；`disagg` 命中 `disagg`/`kv_connector`/
`kv_transfer`/`pd_`/`prefill_decode`/`nixl`/`mooncake`——**最后这个"mooncake"就是
`## 7` 那个 100% 命中假阳性的根源**。

**`_lab/out/improve.json`**：`engines.<name>` 下 `summary`（各项密度指标）、`god_files`
（≥3000 行的文件清单）、`samples`/`samples_silent_except_hot_path`（抽样，带 `role` 字段
标注 `probe`/`hot`/`other`）。角色判定逻辑见 `## 6`。

**逐个走一遍"大在哪"**（`top_dirs` 前 1-2 名，depth=2 口径）：

- **TensorRT-LLM**（`## 2` 锚点 6/7）：没有单一巨头目录，是三份体量相当的东西叠起来——

  `lib/llm`（359,818 行/497 文件）才是 Dynamo 自己的 Rust 服务层核心（KV 路由、块管理、

- **vLLM**（`## 2` 锚点 1/2）：`model_executor`（424,532 行/1,339 文件）——展开一层，

  `model_executor/layers`（199,768 行/897 文件，attention/量化/MoE 等层实现）
  占了 93%。这是"支持的模型和算子变体多"堆出来的广度，不是某个单一算法的深度。
- **llama.cpp**：`ggml/src`（364,133 行/819 文件）分给十几个硬件后端各自独立实现——
  CUDA 43,963 行、CPU 90,580 行、SYCL 44,494 行、OpenCL 26,170 行、Hexagon 33,867 行、
  Vulkan 21,115 行、Metal 10,875 行……**同一组算子在这里被重写了十几遍**，这是深度（每个后端
  都要从头适配一套硬件模型），跟 vLLM 那种"广度"性质不同。
- **Mooncake**：`mooncake-transfer-engine/tent`（85,136 行/219 文件，含厂商内置的
  第三方依赖，见 `## 7`）与 `mooncake-store/tests`（82,187 行/140 文件）并列前二——
  注意第二名本身就是测试代码，depth=2 分桶并不排除 `tests` 路径。
- **KTransformers**：`archive/kt-sft`（105,925 行/342 文件）和 `archive/ktransformers`
  （81,039 行/244 文件）合计占了近一半——**这两个都是 `archive/` 前缀**，2026 版把老
  Python 包整体挪进了归档目录，当前主力是新增的 `kt-kernel/`（C++/CUDA 算子，
  operators 61,576 + python 32,449 ≈ 94,025 行）。字面上最大的两块反而是历史遗留代码。
- **LMDeploy**：`lmdeploy/pytorch`（101,330 行/444 文件）与 `src/turbomind`
  （99,732 行/501 文件）体量接近，对应它双引擎架构里的 Python 后端与 C++ 后端——
  这不是巧合，是产品定位决定的：两条路线都要维护到能打平的程度。
- **TGI**：`server/text_generation_server`（54,458 行/143 文件，worker 主体）领先，
  第二名 `integration-tests/models`（43,895 行/273 文件）已经是测试。
- **LightLLM**：`lightllm/common`（37,915 行/453 文件）最大，内容是各类基础算子和工具，
  没有一个单独目录能占到总量的三分之一——LightLLM 是这份榜单里目录分布最均匀的引擎之一。
- **MLC-LLM**：`python/mlc_llm`（59,274 行/322 文件）占了近六成，`cpp/serve`
  （17,101 行/50 文件）是编译产物的运行时载体——这是编译器路线的典型形状：
  Python 侧做图变换和代码生成，C++ 侧只需要一个瘦的执行器。
- **Tokasaurus**：`tokasaurus/manager`（3,823 行/9 文件）最大，全库 13,219 行——
  这个量级下"大在哪"这个问题本身意义有限，12 家里唯一一个能被人在一天内通读完的引擎。

## 5. 设计决策与代价

### 决策 1：语言组合怎么选，门槛差在哪

12 家可以归进六类组合（代表引擎选取该组合里体量最大或最典型的一家）：

| 组合 | 代表引擎 | 判据（语言行数） | 工程取舍 |
|---|---|---|---|
| 纯 Python | Tokasaurus | Python 12,656 行，无 CUDA/Rust/C++ | 门槛最低，一天能读完；但性能关键路径完全靠 PyTorch 算子间接给，自己没有 kernel 话语权 |
| 近似纯 Python（Triton 代替 CUDA） | LightLLM | Python 128,043 行，0 个 CUDA 文件，129 个 Triton JIT 文件 | 用 Triton 写热点算子而不碰 CUDA C++，既保留"只需要会 Python"的贡献门槛，又不依赖厂商编译器工具链 |
| Python + CUDA | vLLM / TensorRT-LLM / LMDeploy | Python 产品码 79 万～93 万级，CUDA 文件 130～429 个 | 贡献分层：改模型/调度只需要 Python，碰性能关键 kernel 需要 C++/CUDA 背景，两类贡献者门槛完全不同 |
| Python + Rust（路由/传输层分离） | SGLang / TGI | Rust 分别 156,078 / 23,443 行，各自是独立 crate（SGLang 的 `sgl-router`/`sgl-model-gateway`，TGI 的 `router`） | Rust 通常用在"不能有 GC 停顿"的位置（HTTP 路由/负载均衡），不是拿来写 kernel；要改全链路必须同时懂 Python 服务逻辑和 Rust 路由实现 |
| C++ 单体 | llama.cpp / Mooncake | C/C++ 663,024 / 420,627 行，Python 分别只有 58,859 / 30,573 行且只是脚本/绑定 | 贡献门槛最高——改核心逻辑必须懂 C++；换来的是不依赖 Python 运行时，能跑在嵌入式/边缘设备上 |
| Rust 为主体 | Dynamo | Rust 608,542 行 vs Python 产品码 193,827 行 | 核心传输/路由层用 Rust 换内存安全与低延迟，Python 层只是给 vLLM/SGLang/TensorRT-LLM 三家套壳的适配代码，贡献门槛集中在 Rust 一侧 |
| 编译器路线 | MLC-LLM | Python 59,516 行（图变换/codegen）+ C++ 22,690 行（TVM/Relax 运行时） | 不是"写算子"而是"写编译 pass"，贡献门槛是懂 TVM/Relax IR，跟其余组合的技能树几乎不重叠 |

（KTransformers 介于 Python+CUDA 和 C++ 单体之间：Python 152,237 行、C/C++ 127,399 行体量相当，
异构 CPU/GPU 卸载让它两边都不能偏废。）

- **为什么会分出这六种组合**：LLM 推理引擎有两类完全不同的开发活动——
  "编排请求怎么流转"（调度、批处理、KV 管理）天然适合 Python 的开发速度，
  "把矩阵乘法跑到硬件峰值"天然需要更贴近硬件的语言。选哪种组合，本质是在
  "编排层迭代速度"和"性能关键路径的可控性"之间选一个配比。
- **不这样会怎样**：如果强行用一种语言通吃两类活动——比如纯 Python 不写任何 Triton/CUDA
  （类似 Tokasaurus 这种研究级引擎），性能关键路径就只能依赖 PyTorch 算子库本身，
  没法针对自己的 batching/量化策略定制 kernel；反过来如果像老版 TensorRT-LLM 编译路线
  那样把一切都下沉到 C++/CUDA 编译产物，编排层的每一次小改动都要重新走一遍编译流程，
  新模型接入速度会被拖慢（这也是 [[01-TensorRT-LLM]] 篇记录的"编译式引擎已经不编译了"这条演进的部分动因）。
- **什么时候可以不这样**：如果目标从一开始就是"验证一个新调度算法"而不是"服务生产流量"，
  纯 Python（Tokasaurus）反而是对的选择——不需要 Rust/CUDA 带来的构建复杂度，
  改一行调度逻辑不用重新编译任何东西，迭代速度本身就是目的。

  就是相关的事实，不需要拆——拆分口径只在讨论"哪家的 LLM serving 引擎本身更复杂"时才必要。

### 决策 3："一个模型一个大文件" vs 统一 IR

vLLM（`model_executor/models` 311 文件）、SGLang（`srt/models` 类似规模）、
TensorRT-LLM（`_torch/models` 类似规模）都选择"每接入一个新模型架构，就新增一个 Python 文件"；
llama.cpp（`src/models` 151 文件/38,382 行，体量小一个数量级）和 MLC-LLM
（靠 TVM Relax IR 统一表达计算图）走的是更统一的路线。

- **为什么大多数引擎选"一个模型一个文件"**：LLM 模型架构之间的共享度并不像看上去那么高——
  attention 变体（MHA/GQA/MLA/滑动窗口）、MoE 路由策略、位置编码方案各家都不同，
  硬套一层统一抽象意味着每接入一个新模型都要先改抽象层本身，而这个行业新模型发布
  以周为单位，接入速度是硬指标。
- **不这样会怎样**：走统一 IR 路线（MLC-LLM）或统一计算图（llama.cpp 的 `ggml`）
  能换来"同一套优化 pass 自动应用到所有模型"，但代价是新模型必须先被表达成这套 IR/图语言，
  门槛更高、能贡献新模型支持的人更少——这也是为什么 llama.cpp/MLC-LLM 支持新模型的速度
  经常滞后于 vLLM/SGLang 这类"一个模型一个文件"的引擎。
- **什么时候统一 IR 反而更划算**：当目标不是"覆盖尽可能多的模型"而是"把少数几个模型
  跑到极致"，统一 IR/更少的模型专属文件是对的选择，因为收益（跨模型自动复用的优化）
  大于成本（新模型接入慢）——MLC-LLM 和老版 TensorRT-LLM 编译路线都是这个逻辑。

### 决策 4：≥3,000 行的巨石文件该不该当代码异味

`improve.json` 的 `god_files`（≥3,000 行）计数：TensorRT-LLM 25、SGLang 23、vLLM 7、
Dynamo 2，其余引擎 0。但这份清单里至少混着两种性质完全不同的"大"：

- **纯配置罗列型**：`sglang:python/sglang/srt/server_args.py:1`（10,143 行）、
  `tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:1`（6,483 行）——行数增长是"旋钮数量"的
  函数，不是"逻辑复杂度"的函数。
- **真热路径主循环型**：`vllm:vllm/v1/worker/gpu_model_runner.py:1`（7,753 行）、
  `tensorrt-llm:tensorrt_llm/_torch/pyexecutor/py_executor.py:1`（8,828 行）——
  行数增长对应的是要处理的分支/特殊情况数量。

- **为什么会长这么大**：配置类文件长，是因为旋钮本身就多（00 篇已记录 SGLang `ServerArgs`
  476 个字段），而且很多是自动生成 CLI（dataclass → argparse），线性堆叠字段是这套生成
  机制最省事的写法；主循环类文件长，是因为要在一个函数调用栈里处理 prefill/decode、
  投机解码、CUDA Graph 捕获、多种 attention 后端等一长串分支。
- **不这样会怎样**：强行拆分配置类大文件，唯一收益是"git diff 更干净"，代价是"改一个新
  旋钮要跳几个文件"——读者本来就该用 Ctrl+F 定位字段而不是从头读到尾，拆分对这种用法没有
  帮助反而增加认知负担；但如果不拆热路径主循环型大文件，新增一个分支的人往往看不清
  自己改动会不会踩中另一条分支的隐含假设，bug 密度会随行数非线性上升。
- **什么时候可以不拆**：配置类大文件几乎总是可以不拆（前提是字段有良好的分组注释）；
  热路径大文件里，如果确实只是"同一段逻辑对不同硬件/精度的平铺重复"（比如
  `sglang:python/sglang/kernels/ops/attention/flash_attn/cute/flash_fwd_sm100.py:1`
  这类为单个 SM 架构生成的 kernel 文件，5,610 行但内部结构高度模板化），拆分收益也有限；
  真正该拆的是"多条不相关职责被拼进同一个函数调用链"的类型，`## 2` 锚点 1 的
  `gpu_model_runner.py` 属于这一类，[[06-vLLM-模型执行与CUDA-Graph]] 对它的内部结构有更细的走读。

### 代码健康度怎么读：三轮过滤，以及过滤之后还剩什么

`_lab/improve.py` 的"静默 except"密度不是对全仓 `except` 语句直接计数，
中间做了两轮过滤（`_lab/improve.py:48`-`66` 的 `path_role()`）：

1. **第一轮（全仓密度）**：第一版按全仓密度排名，结果前几名全是 `check_env.py`/
   `collect_env.py`/`platforms/cuda.py` 这类**探测型**文件——吞异常在这里是正当的
   （探测硬件/可选依赖本来就该失败即跳过），这个版本的排名毫无意义。
2. **第二轮（排除探测文件 + `ImportError`）**：凡是路径命中 `PROBE_PATTERNS`
   （`check_env`/`collect_env`/`/platforms/`/`_ops.py`/`/utils/`/`utils.py`/
   `env_override`/`version`/`/compat`/`import_utils`/`device_utils`/`/logger`/
   `diagnos`/`_probe`/`capability`），或者捕获的异常类型字面上是 `ImportError`/
   `ModuleNotFoundError`（Python 处理可选依赖的标准写法），一律标 `role=probe`，
   不计入危险密度。
3. **第三轮（分热路径/其他）**：剩下的按文件是否命中 `HOT_SUBSYSTEMS`
   （`scheduler`/`kv_cache`/`attention`/`model_exec`/`disagg`/`speculative`/
   `structured_output`）分成 `hot`（用户看不见的降级或错答案）和 `other`。

`## 0`/`## 4` 表里的密度数字，用的就是第三轮之后的 `silent_except_hot_per_10k_hot_lines`：
LMDeploy 1.2 · vLLM 1.9 · SGLang 4.9 · TensorRT-LLM 5.7 · LightLLM 8.0 · MLC-LLM 8.6 ·
KTransformers 9.5 · TGI 11.5 · Mooncake 15.5 · Dynamo 21.8 · llama.cpp 无 Python 热路径命中 ·
Tokasaurus 0。

**但三轮过滤仍然会漏网**，需要逐条打开看上下文。两个真实例子都在同一个文件里：

- `vllm:vllm/distributed/kv_transfer/kv_connector/v1/hf3fs/hf3fs_connector.py:82`：
  `try: from hf3fs_fuse.io import deregister_fd ... except Exception: HF3FS_AVAILABLE = False`——
  语义上这是一个可选依赖导入守卫（跟 `except ImportError` 想做的事一样），但代码写的是
  `except Exception`，字面上不含"ImportError"，第二轮的 `ImportError` 文本过滤抓不到它；
  文件路径又命中 `kv_connector`/`kv_transfer`（`disagg` 关键词），第三轮被分进 `hot`。
  结果：一个正当的导入守卫被计入了"热路径危险静默降级"。
- 同文件 `vllm:vllm/distributed/kv_transfer/kv_connector/v1/hf3fs/hf3fs_connector.py:251`
  与 `:263`：`task = self._save_queue.get(block=True, timeout=1); except Empty: continue`——
  这是标准的超时轮询模式（拿不到任务就继续下一轮循环，紧接着下面还有一句正常
  `except Exception as e: logger.error(...)` 处理真正的异常），完全正当，同样因为
  `role=hot` 而被计入。

**这条指标能说明什么、不能说明什么**：能说明"如果要去人工审查一个引擎的异常处理纪律，
按这个排名从高到低查性价比更高"；**不能**说明"密度高的引擎 bug 更多"（两个上面的例子
证明即便是排在前列的分数，命中项里也混着完全正当的写法，逐条复核是必须的一步，不是可选项）；
更不能拿来跟别的引擎直接做"谁更烂"的定性判断——密度指标对代码规模、pkg_root
划分方式、乃至某个开发者的异常处理风格都很敏感。

作为补充信号，`TODO 认领率`（带具体人名/issue 号的 TODO 占比）也可以横向看：
vLLM 205/603（34%）、SGLang 167/706（24%）、TensorRT-LLM 49/418（12%）、
LightLLM 0/33（0%）——这条和静默 except 密度是两个独立维度：前者反映"欠下的技术债有没有
一个负责人"，后者反映"运行时异常处理有没有被认真对待"，两者都高或都低的引擎值得多看一眼，
但不构成因果关系。

## 7. 踩坑与反直觉

### 口径限制（必读，写在这里因为它决定了上面所有数字能不能直接比）

**1. 所有行数统计都含空行与注释。** `_lab/common.py` 的 `count_lines()` 返回
`len(text.splitlines())`，不区分空行、纯注释行和真正的逻辑代码行。`_PLAN.md` 定义的
"Python 产品码"口径明确写了这么算是故意的——"读这个文件要翻多少屏"才是这里想表达的量，
不是"圈复杂度"。这意味着一个注释详尽、格式舒展的文件会比一个挤在一起写的等价逻辑文件
"看起来更大"，本篇所有的行数排行都不应该被读成"逻辑复杂度排行"。

**2. `test_to_src_ratio` 只数 `.py` 文件，对 Rust/C++ 为主体的引擎基本失效。**
`_lab/repo_stats.py` 的测试/产品拆分逻辑只在 `suffix == ".py"` 分支里跑（路径含
`test`/`tests` 记作测试，其余记作产品），Rust/C++/CUDA 文件完全不参与这次拆分——
它们的行数被计入总量，但不参与测试覆盖率的分子分母。这带来两类真实的盲区，
本篇用 `#[cfg(test)]` 内联测试模块（Rust 里最常见的测试写法，直接写在被测代码同一个
文件里）实测过：TGI 的 `router/src` 有 6 个文件含 `#[cfg(test)]`，vLLM 的 `rust/src`
有 154 个，SGLang 的 `experimental/sgl-router` + `sgl-model-gateway/src` 合计 78 个，
Dynamo 的 `lib` 下**有 567 个**——这些文件里的测试代码行数，一行都没有计入对应引擎
的 `test_to_src_ratio`。

对 Dynamo 而言这个盲区尤其致命：它的 `test_to_src_ratio`（1.114，12 家里第二高）
完全是从 193,827 行 Python 胶水层算出来的，而 Dynamo 真正的核心引擎是 608,542 行
Rust——**这个指标对 Dynamo 核心代码的测试覆盖情况只字未提**，1.114 这个"看起来
测试很充分"的数字描述的只是一层薄薄的适配代码。同理，TGI 的 0.108（12 家最低）
和 Tokasaurus 的 0.11 表面上接近，但性质不同：Tokasaurus 是纯 Python 项目，这个数字
是它测试覆盖的真实写照；TGI 是 Python worker + Rust router 的分层架构，0.108 只反映了
Python 一侧，Rust router 侧另有独立的测试（含上面提到的 6 个内联测试文件，以及
`router/src` 目录本身 9,921 行里没有细分出的集成测试）没有被这个数字看见。
**C/C++ 项目也是同样的盲区**：llama.cpp 的 `tests/` 目录有 45,555 行 C/C++ 测试代码，
Mooncake 的 `mooncake-store/tests` + `mooncake-transfer-engine/tests` 合计超过 10 万行，
两者都不出现在各自的 `python_test_lines` 里，因为那个字段只认 `.py`。
**结论：这把尺子只对纯 Python 或以 Python 为绝对主体的引擎可比，混合语言引擎之间不能直接比这一列。**

**3. `struct_map.json` 的子系统分类是纯文件路径关键词子串匹配，会有假阳性。**
`_lab/struct_map.py:22`-`24` 的注释自己写明了这条：这是**导航线索**，不是结论，
写进正文前必须回源码复核。本篇复核到的三个真实例子：

- **vLLM `scheduler` 桶报 20 文件/8,424 行，真正的连续批处理调度器只有 6 文件/4,012 行**：
  `vllm:vllm/v1/core/sched/scheduler.py:1`（3,037 行）+
  `vllm:vllm/v1/core/sched/output.py:1`（305 行）+
  `vllm:vllm/v1/core/sched/interface.py:1`（262 行）+
  `vllm:vllm/v1/core/sched/request_queue.py:1`（208 行）+
  `vllm:vllm/v1/core/sched/utils.py:1`（130 行）+
  `vllm:vllm/v1/core/sched/async_scheduler.py:1`（70 行）= 4,012 行，这才是真正对标
  SGLang `sglang:python/sglang/srt/managers/scheduler.py:1`（5,229 行）的部分。
  多出来的 14 个文件是 KV-connector 的 offloading 调度器（如
  `vllm:vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py:1`，
  1,698 行）和 EPLB（专家并行负载均衡）策略文件——因为它们文件名里带"scheduler"或路径
  里带"policy"，被 `scheduler` 关键词组（`sched`/`scheduler`/`batch_sched`/`policy`/
  `waiting`）命中，但语义上跟连续批处理调度器是两个系统。
- **Mooncake `disagg` 桶 100% 命中全仓扫描文件**：`## 3`/`## 6` 已经讲过机制——
  `disagg` 的关键词表里包含"mooncake"，而 Mooncake 的两个包根目录名字本身就带
  "mooncake"，导致这个分类器对 Mooncake 必然给出 100% 命中，不管代码内容是什么。
- **TGI `entrypoint` 桶混进了模型执行文件**：`entrypoint` 关键词组里有"server"，
  而 TGI 的 Python 包整个叫 `text_generation_server`，于是
  `tgi:server/text_generation_server/models/flash_causal_lm.py:1`（2,478 行，真正的
  worker 端模型前向执行代码）因为路径前缀含"server"字样被算进了 `entrypoint`
  （HTTP 服务层）桶，实际上它离 HTTP 层很远。

**4. `repo_stats.json` 的 `top_dirs` 和 `struct_map.json` 的 `dir_tree` 不是同一把尺，
不能拼在一张表里冒充同一口径。** 前者按路径深度 2 分桶（`_lab/repo_stats.py` 的
`_subdir_key(depth=2)`），扫描全部登记语言、不排除任何子目录；后者按路径深度 3 分桶，
且用 `EXCLUDE_PARTS`（`/test`/`/tests/`/`/benchmark`/`/docs/`/`/examples/`/`/third_party/`）
排除了这些路径，扫描的后缀集合也窄得多（只有 `.py`/`.rs`/`.cpp`/`.cc`/`.cu`/`.h`/`.hpp`
七种，`.cuh`、`.json`、`.yaml` 都不算）。`## 5` 决策 2 那份 SGLang 三级目录拆解之所以
没有直接摘抄这两份 JSON 的数字，就是因为深度和排除规则都不一致，本篇改为对 `_src/`
用统一方法重新直接测量，可复现。

### 反直觉

- **"SGLang 比 vLLM 大"本身就是反直觉的**——`## 0`/`## 5` 决策 2 已经用两种口径给出了
  相反的答案（含 kernel 库口径下 SGLang 大 14.7%，不含口径下反而小 17.4%），这条本身
  已经足够反直觉，不需要额外加工。
- **Tokasaurus 的健康度得分是 0，但这不代表它是 12 家里代码纪律最好的。**
  `hot_path_lines_scanned` 只有 1,355 行——分母小到任何密度指标在这个量级都不稳定，
  0 更可能是"样本太小碰巧没撞上"而不是"真的一个隐患都没有"。同理 Mooncake 的
  1,291 行热路径样本、MLC-LLM 的 1,162 行也偏小，这三家的健康度数字都应该配上
  "样本量小，结论弱"的标签，不能跟 vLLM（471,206 行热路径样本）、SGLang（352,420 行）
  这种大样本引擎的分数直接排到同一张榜单上比高低。
- **TGI 的静默 except 密度最低（TGI 排第七，11.5，中等偏低），但它也是 12 家里
  唯一一个 5 个月没有新提交的引擎**（快照 sha 停在 2026-03-21）。密度低有两种完全不同
  的可能原因——"代码写得干净"和"没人再往里面写新代码，自然也没有新的 bug 被引入"——
  单看这一个数字分不清是哪一种，需要配合 `git log` 的活跃度一起读，这也是
  [[00-总览与阅读地图]] §3 特意把 TGI 和 Tokasaurus 的陈旧日期单独列出来的原因。
- **MLC-LLM 的 Triton 计数（`## 4` 表脚注）反过来提醒一件事**：`struct_map` 的问题
  是关键词匹配抓多了（假阳性），`repo_stats` 早期版本对 Triton 的判定则是抓少了
  （假阴性）——只认 `@triton.jit` 装饰器语法，漏掉了 `triton.jit(fn)` 函数调用语法。
  "全仓搜不到某个模式"和"这个仓库没有这个功能"是两回事，两种方向的判定错误本篇都遇到了。

本篇是横向对比篇，不对单个引擎做深挖（那是 `05-改进机会/` 系列的工作），
这里只标出几个从本篇数据里能看到、值得后续篇目跟进的候选：

  `sglang:python/sglang/srt/server_args.py:1` 这种配置文件也列进"待重构"清单。
- **`hf3fs_connector.py` 这类"role=hot 但语义上是正当写法"的案例**（`## 6`），
  在 vLLM 的 KV-connector 目录下大概率不止这一个，值得 `05-改进机会/01-vLLM可改进点`

- **`_lab/struct_map.py` 的 `SUBSYSTEMS` 关键词表本身有改进空间**：Mooncake 的
  100% 命中和 TGI 的 `flash_causal_lm.py` 误分类，根源都是关键词粒度太粗（用整个引擎名
  当关键词、用"server"这种在很多项目里当作路径前缀的词当关键词）。如果要让这份工具
  对 Mooncake/TGI 这类项目也给出有意义的子系统分类，需要给关键词表加一层"排除本引擎
  自己的包名"和"要求关键词出现在路径的目录层级而不是任意子串"的规则，这个改动会影响
  全部 12 个引擎的 `struct_map.json`，改之前要先跑 `struct_map.py --selftest` 加新用例锁定行为。
