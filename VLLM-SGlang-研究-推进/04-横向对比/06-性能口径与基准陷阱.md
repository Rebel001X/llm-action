## 0. 结论先行

一句话说完本篇的论点：**"吞吐/延迟数字"从来不是引擎的属性，是（引擎实现, 工作负载, 测试脚本实现,
硬件）四元组的属性。前三样都能从源码里查到，本篇把它们查完了。**

四条最反直觉、且都能用文件行号核实的发现摆在最前面：

1. **"ITL"这个词，在 SGLang 自己的同一个文件里就有三种互不等价的算法。** 它的原生
   `/generate` backend 把一次 SSE 事件的时间差除以这次事件里新增的 token 数再展开
   （`sglang:python/sglang/benchmark/serving.py:758-760`）；它自己实现的 OpenAI 兼容
   backend 却直接把整个事件的时间差记成一条 ITL，完全不管这次事件里装了几个 token
   （`sglang:python/sglang/benchmark/serving.py:348`）；遇到投机解码还有第三种"重新
   tokenize 摊薄"算法（`sglang:python/sglang/benchmark/serving.py:1116-1144`）。选
   `--backend sglang` 还是 `--backend sglang-oai` 打同一个 server、跑同一批请求，报出来的
   ITL 分布形状就不是同一个统计量。
2. **vLLM 和 SGLang 的官方随机数据集，默认都是定长、且强制忽略 EOS。** 两家的
   `--random-range-ratio` 默认都是 `0.0`（`vllm:vllm/benchmarks/datasets/datasets.py:574-577`、
   `sglang:python/sglang/benchmark/serving.py:2325-2328`），意味着每条请求的输入/输出长度
   完全相同，没有任何方差；random 数据集在 OpenAI 兼容 backend 上还会被自动打开
   `ignore_eos`（`vllm:vllm/benchmarks/serve.py:2093-2097`）。也就是说：这两家最常被拿来
   跑分的默认工作负载，恰好抹掉了连续批处理最大的收益来源——输出长度异质性（见 ## 4）。
3. **预热请求数，三家三个数字。** vLLM 默认 `0`（不预热，`vllm:vllm/benchmarks/serve.py:1693-1695`）；
   SGLang 默认 `1`，只有 CI 环境变量或显式传参才会预热后刷新前缀缓存
   （`sglang:python/sglang/benchmark/serving.py:1457-1464`）；TensorRT-LLM 默认 `2`
   （`tensorrt-llm:tensorrt_llm/bench/benchmark/throughput.py:207-210`）。TGI 更极端——
   它的官方 benchmark **直接绕开 HTTP 路由层，对 gRPC shard 发请求**
   （`tgi:benchmark/src/main.rs:57-60`），跟"打 API 服务"根本不是同一个被测系统。
4. **"goodput"这个指标，六家里只有一家定义。** vLLM 在 `benchmark_metrics` 里实现了基于
   TTFT/TPOT/E2EL 服务水平目标的 goodput 计算（`vllm:vllm/benchmarks/serve.py:622-639`），
   其余五家（SGLang、TensorRT-LLM、LMDeploy、TGI、llama.cpp）的官方 benchmark 目录里
   全文检索 `goodput` 零命中——这不是行号能证的事，是查过五个仓库之后的"没有"本身。

本篇不给出替代数字，给两样东西：一张"读到一个吞吐数字时该问的问题清单"（## 8.1），
和一张"自己要做对比测试时必须钉死的最小口径表"（## 8.2）。

## 1. 它在系统里的位置

`04-横向对比/` 这个子目录下的其余五篇——API 兼容性、调度策略、KV 缓存、工程规模、选型

这个问题回答到底：不能测硬件，但**能审计测试脚本本身**，而这恰恰是读者拿到一个陌生数字时
最容易跳过的一步。

一个吞吐/延迟数字，形式化地写，是四元函数：


四个自变量里，"引擎实现"本库其余篇目已经带行号解剖过（[[03-vLLM-调度器解剖]]、
[[02-SGLang-Scheduler事件循环]] 等）；"硬件"本库明确放弃（[[00-总览与阅读地图]] 第 36 行）；
"工作负载"和"测试脚本实现"这两个变量，恰好是**读源码就能查清楚、不需要跑代码**的部分——
这正是本篇存在的理由：把另外两个自变量钉死，读者才有能力判断"网上那个数字到底在测什么"。

## 3. 指标定义的形式化

### 3.1 TTFT——起点定义一致，但"起点"被谁控制不一致

TTFT 的形式化定义在 vLLM 和 SGLang 里几乎逐字相同：`TTFT = t(收到第一个 chunk) - t(函数入口)`。

vLLM：函数入口记时 `st = time.perf_counter()`（`vllm:vllm/benchmarks/lib/endpoint_request_func.py:197`），
收到第一个 chunk 时算差：

```python
if not first_chunk_received:
    first_chunk_received = True
    ttft = time.perf_counter() - st
    output.ttft = ttft
```
（`vllm:vllm/benchmarks/lib/endpoint_request_func.py:233-236`）

SGLang 原生 `/generate` backend 写法结构完全一样：`ttft = time.perf_counter() - st`
（`sglang:python/sglang/benchmark/serving.py:749-751`）。公式本身是六个指标里最一致的
一个，但"函数入口"这个时间点是否等于"这条请求被判定要发出去的时间点"，两家都不成立——
见 ## 3.4。

llama.cpp 的 k6 脚本用了完全不同的命名和口径：变量叫 `llamacpp_emit_first_token_second`，
在收到第一个 SSE `event` 时用 `new Date()` 记录客户端时间戳，与请求发出时刻作差
（`tools/server/bench/script.js`，见 ## 7 的详细讨论）。语义上等价于 TTFT，但连"TTFT"这个
名字都没用，第一次读这份脚本的人搜不到 `ttft` 这个词。

非流式请求下 TTFT 会退化：vLLM 明确把非流式的 TTFT 直接赋值成总延迟——

```python
output.ttft = (
    output.latency
)  # For non-streaming, TTFT = total latency
```
（`vllm:vllm/benchmarks/lib/endpoint_request_func.py:480-482`）

也就是说同一份脚本报出来的"TTFT"，流式和非流式模式下衡量的根本不是同一件事：流式下是
"到第一个 token 的延迟"，非流式下是"到全部输出完成的延迟"，字段名没变，语义变了。

### 3.2 TPOT——公式一致到像是抄来的（确实是）

三家的 TPOT 公式字面上完全相同：`TPOT = (总延迟 - TTFT) / (输出token数 - 1)`。

```python
tpot = 0.0
if output_len > 1:
    latency_minus_ttft = outputs[i].latency - outputs[i].ttft
    tpot = latency_minus_ttft / (output_len - 1)
    tpots.append(tpot)
```
（`vllm:vllm/benchmarks/serve.py:607-611`）

SGLang 与 LMDeploy 的实现在字面上完全相同，都写成 `(outputs[i].latency -
outputs[i].ttft) / (output_len - 1)`（`sglang:python/sglang/benchmark/serving.py:1134-1135`；
`lmdeploy:benchmark/profile_restful_api.py:941`）。三处代码字面相同不是巧合——LMDeploy
这份脚本的类名、字段名、函数结构与 vLLM/SGLang 高度同源，是这条生态里"抄一份改一改"最
直接的证据（LMDeploy 甚至能直接拉起 vLLM/SGLang 的 server 来跑同一份测试脚本，见 ## 2
表格 `lmdeploy:benchmark/benchmark_serving.py:9-17`）。

TensorRT-LLM 的 `intertoken_latency` 结构等价（本质也是"生成阶段总时长 / 生成 token 数"），
但它的文档字符串把公式写反了——这条留到 ## 7 详细展开，因为这不是口径分歧，是真的写错了。

### 3.3 ITL——同名不同义的重灾区

朴素定义：ITL 是相邻两个 token 到达时间的差，一条请求产出 `N-1` 个 ITL 样本（`N` 是输出
token 数）。三家的实际实现分出至少四种互不等价的算法：

**算法一：原始 chunk 间隔，不管这个 chunk 装了几个 token。** vLLM 的 OpenAI Completions
客户端和 SGLang 自己实现的 OpenAI 兼容客户端写法完全一样：

```python
else:
    output.itl.append(timestamp - most_recent_timestamp)
```
（vLLM：`vllm:vllm/benchmarks/lib/endpoint_request_func.py:240`；SGLang：
`sglang:python/sglang/benchmark/serving.py:344-348`，多了一行把文本片段存进
`output.text_chunks`，供后面算法三使用，核心的 `append` 那一行逻辑不变）

**算法二：chunk 间隔除以这次新增的 token 数，再展开成多条相同的样本。** SGLang 原生
`/generate` backend（`--backend sglang`）：

```python
num_new_tokens = output_len - last_output_len
if num_new_tokens == 0:
    continue
chunk_gap = timestamp - most_recent_timestamp
adjust_itl = chunk_gap / num_new_tokens
output.itl.extend([adjust_itl] * num_new_tokens)
```
（`sglang:python/sglang/benchmark/serving.py:755-760`）

**算法一和算法二共存在同一个文件里，被同一套 `ASYNC_REQUEST_FUNCS` 映射表分派**
（`sglang:python/sglang/benchmark/serving.py:939-944`）——用户只需要把 `--backend`
从 `sglang` 换成 `sglang-oai`，打同一个 server、跑同一批请求，ITL 这个字段的计算公式
就换了一套。如果服务端一次 decode step 产出的 token 数经常大于 1（overlap 调度、多步解码
批量 flush 等场景很常见），算法一会把"多 token 打包的一次网络往返延迟"错记成"一个 token
的延迟"，直接虚高单 token ITL 的数值；算法二不会犯这个错，但依赖服务端在响应里给出准确的
累计 token 计数。

**算法三：算法一的结果再按重新 tokenize 的粒度摊薄，专为投机解码场景加的修正。** 当
backend 是 `sglang-oai`/`sglang-oai-chat` 且检测到接受长度（spec decode 场景）时：

```python
use_retokenized_itl = (
    accept_length is not None
    and accept_length > 0
    and backend in ("sglang-oai", "sglang-oai-chat")
)
...
if use_retokenized_itl:
    for k, itl in enumerate(outputs[i].itl):
        num_tokens = len(
            tokenizer.encode(
                outputs[i].text_chunks[k], add_special_tokens=False
            )
        )
        adjusted_itl = itl / num_tokens
        retokenized_itls.extend([adjusted_itl] * num_tokens)
```
（`sglang:python/sglang/benchmark/serving.py:1116-1119`、`1136-1144`）

一个脚本文件、三套 ITL 公式，靠 `--backend` 参数和是否命中投机解码条件切换。这不是"跨引擎
不可比"，是**同一个引擎的同一份官方脚本内部就不可比**——这一点比任何跨引擎差异都更值得
在开头强调。

### 3.4 E2E Latency 与"计时起点"里藏着的排队时间

vLLM 和 SGLang 都用并发信号量限制并发请求数（`--max-concurrency`），且实现方式几乎一样：

```python
async def limited_request_func(request_func_input, session, pbar):
    async with semaphore:
        return await request_func(
            request_func_input=request_func_input, session=session, pbar=pbar
        )
```
（`vllm:vllm/benchmarks/serve.py:963-973`，`semaphore` 为空时退化成 `nullcontext()`）

SGLang 的对应实现结构相同（`sglang:python/sglang/benchmark/serving.py:1379-1386`），紧挨着
一行注释，写明这段并发限制代码抄自 vLLM 某个历史 PR（注释里贴了 PR 链接，本篇不重复
抄录 URL）——两家的实现确实同源。

关键是：真正设置计时起点 `st = time.perf_counter()` 的代码，在 `request_func` 函数体的
第一行（`vllm:vllm/benchmarks/lib/endpoint_request_func.py:197`、
`sglang:python/sglang/benchmark/serving.py:700`），而 `request_func` 是被
`async with semaphore:` **包在里面**才调用的。换句话说：**计时器在拿到并发槽位之后才启动**，
排队等一个空闲槽位的时间，不计入 TTFT、不计入 E2E latency、不计入任何一个百分位统计。

这个细节不容易被发现，因为它不改变任何一个字段的公式，只改变字段"从哪一刻开始算"。而
`--max-concurrency` 恰恰是最常被用来模拟真实生产环境限流的旋钮——用它的人十有八九是想
看服务在饱和状态下的排队延迟，但两家工具默认报出来的延迟里根本不含这段排队时间。

### 3.5 百分位算法本身也不同

vLLM、SGLang、LMDeploy 三家的百分位计算都调用 `numpy.percentile`（numpy 默认用线性插值法）：

```python
percentiles_ttft_ms=[
    (p, np.percentile(ttfts or 0, p) * 1000) for p in selected_percentiles
],
```
（`vllm:vllm/benchmarks/serve.py:739-741`）

TensorRT-LLM 自己实现了一套百分位统计，用的是最近秩法（nearest-rank）：先排序，再用
截断取整的下标直接索引：

```python
return cls(
    p50=sorted_values[int(length * 0.50)],
    p90=sorted_values[int(length * 0.90)],
    p95=sorted_values[int(length * 0.95)],
    p99=sorted_values[int(length * 0.99)],
    average=average,
    minimum=min(values),
```
（`tensorrt-llm:tensorrt_llm/bench/dataclasses/statistics.py:126-132`）

两种算法在样本量足够大、分布连续时数值接近，但不是同一个统计量的两种写法——`int(length *
0.99)` 是向下取整的下标（一种最近秩估计），`np.percentile` 默认做线性插值。在样本量较小
（比如小规模冒烟测试常见的几十到几百条请求）或分布有台阶（比如输出长度固定导致延迟高度
聚集）时，两者的差可以不是舍入误差级别的。**"p99"这三个字符，在 TensorRT-LLM 自己的报告
里和在 vLLM/SGLang/LMDeploy 的报告里，是用两种不同公式算出来的两个不同统计量，只是刚好
同名。**

### 3.6 Goodput——六家里只有一家定义的指标

vLLM 的 goodput 概念：给定用户指定的 TTFT/TPOT/E2EL 服务水平目标（SLO），统计"三项全部
达标"的请求占比：

```python
if goodput_config_dict:
    valid_metrics = []
    slo_values = []

    if "ttft" in goodput_config_dict:
        valid_metrics.append(ttfts)
        slo_values.append(
            goodput_config_dict["ttft"] / MILLISECONDS_TO_SECONDS_CONVERSION
        )
    if "tpot" in goodput_config_dict:
        valid_metrics.append(all_tpots)
        slo_values.append(
            goodput_config_dict["tpot"] / MILLISECONDS_TO_SECONDS_CONVERSION
        )
```
（`vllm:vllm/benchmarks/serve.py:622-635`）

这是一个显式 opt-in 的开关（`--goodput`，`vllm:vllm/benchmarks/serve.py:1779`），不传就
不计算，默认报告里不会出现。它的帮助文本里贴了一篇论文和一篇技术博客作为概念出处（具体
链接见该文件该行原文，本篇不重复抄录 URL——理由见开头"不编 URL"的红线）。

对 SGLang、TensorRT-LLM、LMDeploy、TGI、llama.cpp 五个仓库的 benchmark 相关目录分别做过
全文检索，`goodput` 字符串零命中。这五家的官方脚本从概念上就没有"多少比例请求同时满足
TTFT 和 TPOT 目标"这个维度——想比较两个引擎的 goodput，唯一的办法是自己用原始的
per-request TTFT/TPOT 序列在外面重新算，不能指望任何一家的官方脚本直接吐出来。

## 4. 主流程走读（工作负载决定一切）

把 vLLM `serve.py` 和 SGLang `serving.py` 的主流程并排走一遍，在每个环节标出"这里藏着一个
自由变量，改了它两个数字就不可比"：

**第一步：数据集采样，决定输入/输出长度分布。**

vLLM `RandomDataset` 的默认值：输入 1024、输出 128、range_ratio（长度采样的浮动比例）0.0：

```python
DEFAULT_PREFIX_LEN = 0
DEFAULT_RANGE_RATIO = 0.0
DEFAULT_INPUT_LEN = 1024
DEFAULT_OUTPUT_LEN = 128
```
（`vllm:vllm/benchmarks/datasets/datasets.py:573-577`）

SGLang 对应的三个参数默认值紧挨着定义（`sglang:python/sglang/benchmark/serving.py:2313-2328`）：

```python
"--random-input-len", type=int, default=1024,     # 与 vLLM 相同
"--random-output-len", default=1024, type=int,     # vLLM 默认只有 128
"--random-range-ratio", type=float, default=0.0,   # 同样定长、零方差
```

输入长度默认相同（1024），**输出长度默认相差 8 倍**（vLLM 128 vs SGLang 1024），且两家
`range_ratio` 都默认 0（定长，零方差）。同一个 `--dataset-name random`，两家工具跑出来的
默认工作负载完全不是同一个东西，这还没涉及任何引擎实现的差异。

**第二步：前缀共享率，由数据集选择决定，不是一个数字，是一个隐含假设。** ShareGPT 类真实
对话数据天然带共享前缀（多轮对话、系统提示重复），对 RadixAttention/前缀缓存友好；random
数据集用无关随机 token 拼出的合成 prompt，前缀几乎不共享。本篇不现场跑分去量化这个共享率
数值——这需要真实 tokenizer 和真实数据文件，本机没有 GPU 也没必要为了一个定性事实去下载
数据集——但**共享率是任何吞吐对比里必须报告的自由变量**：同一个引擎在 ShareGPT 上和在
random 数据集上跑出来的吞吐可以有本质区别，机制细节见 [[03-SGLang-RadixAttention与前缀缓存]]
和 [[04-vLLM-KV缓存与前缀缓存]]。

**第三步：并发数与到达过程。** vLLM 支持 Poisson（默认，burstiness=1.0）、gamma 分布
（burstiness ≠ 1）、以及线性/指数斜坡（ramp-up）：

```python
"--burstiness",
type=float,
default=1.0,
```
（`vllm:vllm/benchmarks/serve.py:1667-1669`）

```python
theta = 1.0 / (current_request_rate * burstiness)
delay_ts.append(np.random.gamma(shape=burstiness, scale=theta))
```
（`vllm:vllm/benchmarks/serve.py:465-467`）

SGLang 只有纯指数分布（等价于 burstiness 恒为 1 的 Poisson 过程），没有可调旋钮：

```python
interval = np.random.exponential(1.0 / request_rate)
```
（`sglang:python/sglang/benchmark/serving.py:1089-1090`）

两家的 `--request-rate` 默认都是 `float("inf")`：

```python
"--request-rate",
type=float,
default=float("inf"),
```
（`vllm:vllm/benchmarks/serve.py:1658-1660`；`sglang:python/sglang/benchmark/serving.py:2367-2369`
写法一致）

`request_rate=inf` 意味着**默认情况下所有请求在 t=0 一次性全部发出**，不是任何形式的在线
到达过程模拟。同时两家的 `--max-concurrency` 默认都是 `None`（`vllm:vllm/benchmarks/serve.py:1589-1591`）
——默认配置是一次性把全部请求（默认 1000 条）无限并发地砸给服务端，测的是"瞬时过载下的
极限行为"，不是"稳态在线服务"。这两件事叠加起来是本篇 ## 5 第一条决策的主题。

**第四步：是否流式。** `--disable-stream` 默认关（即默认走流式）。非流式模式下 TTFT
退化为总延迟（见 ## 3.1），如果两个对比对象一个走流式一个不走，TTFT 这一栏直接失去意义。

**第五步：batch 是否同质。** 由第一步的 `range_ratio=0.0`（定长）和 `ignore_eos`（是否
提前在自然终止符处停止）共同决定。这是 ## 5 第三条决策展开的主题：默认配置下这一步几乎
锁死了"同质批量"这个最不利于连续批处理的场景。

**第六步：并发控制的计时起点。** 见 ## 3.4——`--max-concurrency` 排队时间不计入延迟，
这个变量在"到达过程"和"并发数"两个自由变量之外，是第三个容易被忽略的隐藏维度。

至此六个自由变量全部列完：输入长度分布、输出长度分布、前缀共享率、并发数、到达过程、
是否流式——外加"batch 是否同质"这个由前两者派生出的合成变量。**任何一个不同，两个吞吐/
延迟数字就不可比。**

## 5. 设计决策与代价

### 决策一：默认瞬时全量发送 + 无并发上限（vLLM 与 SGLang 一致）

`--request-rate` 默认 `inf`、`--max-concurrency` 默认 `None`（`vllm:vllm/benchmarks/serve.py:1589-1591`、
`:1658-1660`；`sglang:python/sglang/benchmark/serving.py:2367-2369` 同样默认 `inf`）。

- **为什么这样**：这是压测里最简单也最容易复现的一种负载——不需要标定到达速率、不需要
  猜测生产流量的统计特征，直接测"服务端在拿到全部请求后能多快吃完"，适合快速冒烟测试和
  纯吞吐上限估计。
- **不这样会怎样**：如果默认改成某个有限速率，用户必须先知道一个"合理"的速率才能拿到
  有意义的结果——但"合理速率"恰恰是压测本身要回答的问题，会变成鸡生蛋的循环；默认给
  `inf` 至少保证脚本不依赖用户先验知识就能跑。
- **什么时候可以不这样**：任何要模拟"在线服务在正常负载下的用户体感延迟"的场景，都必须
  显式传 `--request-rate` 和/或 `--max-concurrency`，而且要按 [[02-调度策略横向对比]]
  里讨论的真实流量特征去标定——默认配置测出来的是"服务端的极限吞吐上限"，不是"用户会
  感受到的延迟"，把前者当后者用是最常见的误用。

### 决策二：SGLang 默认预热 1 条请求，且默认不刷新前缀缓存

```python
"--warmup-requests",
type=int,
default=1,
```
（`sglang:python/sglang/benchmark/serving.py:2599-2602`）

```python
should_flush_cache = (
    "sglang" in backend and _get_bool_env_var("SGLANG_IS_IN_CI")
) or flush_cache
if should_flush_cache:
    flush_server_cache(base_url, backend, flush_cache_timeout)
```
（`sglang:python/sglang/benchmark/serving.py:1460-1464`）

- **为什么这样**：预热请求的目的是让服务端跑过一次首请求特有的冷启动路径（CUDA Graph
  捕获、JIT 编译、算子首次调用的懒加载），避免这部分一次性开销被算进正式统计；不刷新
  缓存则是因为默认场景下用户通常想尽快开始正式测试，主动刷新反而会额外拖慢脚本、还要求
  server 暴露一个开发态的缓存管理接口。
- **不这样会怎样**：完全不预热（像 vLLM 默认那样，见决策三）会让冷启动开销摊进前几条
  正式请求的延迟里；预热了但不刷新缓存，若预热用过的 prompt 与正式请求存在前缀重叠
  （比如反复复用同一条 warmup 样本做 smoke test），正式测试会不知不觉吃到一次"免费"的
  前缀缓存命中，让前缀缓存相关的结论比真实情况更好看。
- **什么时候可以不这样**：专门评估"前缀缓存收益"的测试必须显式传 `--flush-cache`（或在
  CI 环境变量下让它自动生效）切断这层污染；反过来，专门评估"服务在缓存预热状态下的稳态
  表现"（更贴近生产里跑了很久的服务）则应该主动多预热几轮，而不是依赖默认的 1 条。

### 决策三：vLLM 默认不预热（`--num-warmups` 默认 0）

```python
"--num-warmups",
type=int,
default=0,
```
（`vllm:vllm/benchmarks/serve.py:1693-1695`）

- **为什么这样**：不预热的测试结果包含了冷启动开销，如果这正是你想测的东西（比如
  评估"服务刚启动就来一波流量"的最坏情况延迟），默认不预热就是对的；把选择权交给用户
  比替用户做假设更诚实。
- **不这样会怎样**：如果目标是测量稳态服务能力（这是绝大多数吞吐/延迟对比想要的），
  不预热会让第一批请求携带 CUDA Graph 捕获、JIT 编译等一次性成本，污染均值和尾部百分位，
  且请求量越少（冒烟测试常见的几十条）这部分污染占比越大。
- **什么时候可以不这样**：只要测试目的是稳态吞吐/延迟对比，就应该显式加预热，且预热量
  要与正式测试量在同一量级——TensorRT-LLM 把默认值设成 2（`tensorrt-llm:tensorrt_llm/bench/benchmark/throughput.py:207-210`）
  而不是 0，说明"默认不预热"并不是这条生态里唯一被接受的答案，是每个项目各自的取舍。

### 决策四：随机数据集默认强制 `ignore_eos`（vLLM 与 SGLang 一致）

```python
# when using random datasets, default to ignoring EOS
# so generation runs to the requested length
if (
    args.dataset_name in ("random", "random-mm")
    and args.backend in OPENAI_COMPATIBLE_BACKENDS
):
    args.ignore_eos = True
```
（`vllm:vllm/benchmarks/serve.py:2091-2097`）

```python
"--disable-ignore-eos",
action="store_true",
help="Disable ignoring EOS.",
```
（`sglang:python/sglang/benchmark/serving.py:2446-2449`，`action="store_true"` 意味着默认值
是 `False`，而 payload 里 `ignore_eos = not args.disable_ignore_eos`，所以默认仍然是 `True`）

- **为什么这样**：random 数据集里的 prompt 是无语义的随机 token 拼接，模型对着这种输入
  几乎不可能在指定长度前自然生成 EOS——如果不强制忽略 EOS，大量请求会在远早于目标长度处
  意外终止，实际测出来的"输出长度"和你用 `--random-output-len` 设定的目标值对不上，
  数据集就白配置了。
- **不这样会怎样**：忽略 EOS 意味着每条请求都被迫生成到恰好指定长度，输出长度分布退化成
  一个常数（配合 `range_ratio=0.0` 更是彻底没有方差，见 ## 4 第五步、## 0 结论二），直接
  抹掉了连续批处理最大的收益来源——不同请求在不同时刻结束、腾出槽位给新请求进来的异质性。
  同质批量下这部分收益会显著收窄，对比结论会系统性低估连续批处理引擎之间的真实差距。
- **什么时候可以不这样**：想测"真实生成行为下的吞吐"就应该换用真实对话数据集（ShareGPT 等），
  这类数据集里模型会在自然位置停止，输出长度天然异质；如果一定要用 random 数据集又想保留
  异质性，至少应该把 `--random-range-ratio` 调大到非零（虽然这只影响输入/输出 token 数的
  采样范围，不影响"是否忽略 EOS"这件事本身，两者要同时调整才有效）。

### 决策五：TGI 绕过 HTTP 路由层，直接对 gRPC shard 发请求

`text-generation-benchmark` 的文档字符串明确写着"完全绕过路由，直接对 gRPC 进程说话"
（`tgi:benchmark/src/main.rs:57-60`）；它的输入/输出长度默认值是 10/8 个 token
（`tgi:benchmark/src/main.rs:38-47`），并发模式是批大小扫描 `[1, 2, 4, 8, 16, 32]`
（`tgi:benchmark/src/main.rs:134`），不是开环到达过程模拟。

- **为什么这样**：绕开路由层能拿到最纯净的"模型前向计算延迟"信号，不掺杂 HTTP 序列化、
  路由调度、多副本负载均衡这些工程细节，适合定位"prefill/decode 本身有多快"这类内核/
  调度层面的问题；批大小扫描能直接画出延迟随批大小变化的曲线，一眼看出从访存受限转向
  计算受限的拐点——这正是该文档字符串明确写出的设计目的（`tgi:benchmark/src/main.rs:25-29`）。
- **不这样会怎样**：拿这份工具的数字去跟 vLLM/SGLang 走 HTTP API、模拟 Poisson 到达的
  `benchmark_serving.py` 结果放进同一张表比较，比较的根本不是同一个被测系统——一个测
  "裸模型前向 + 批处理调度"，另一个测"完整服务栈在模拟流量下的表现"，中间隔着一整层
  路由、鉴权、多进程通信开销。
- **什么时候可以不这样**：如果就是想单独评估 TGI 路由层之外的开销，这种绕过设计反而是
  必需的对照组，不该改；要测端到端用户体感延迟，必须用走完整 HTTP 路径的工具（TGI 仓库
  里另有 `load_tests/` 用 k6 走完整路径，本篇未展开）。

## 7. 踩坑与反直觉

**SGLang 自己的注释说谎了。** `async_request_openai_chat_completions` 里紧挨着 `ignore_eos`
赋值的注释写着"默认 False，行为更真实（尊重 EOS token）"：

```python
# Add ignore_eos default only if not specified in extra_request_body
# Default to False for more realistic behavior (respect EOS tokens)
if "ignore_eos" not in request_func_input.extra_request_body:
    payload["ignore_eos"] = not args.disable_ignore_eos
```
（`sglang:python/sglang/benchmark/serving.py:442-445`）

但 `args.disable_ignore_eos` 的 argparse 定义是 `action="store_true"`，默认值是 `False`
（`sglang:python/sglang/benchmark/serving.py:2446-2449`），所以 `not False = True`——实际
默认行为是 `ignore_eos=True`，跟注释字面意思完全相反。一个只读注释不读代码的人，会以为
SGLang 的 chat completions 基准默认会尊重模型的自然停止点、产出异质长度的输出；实际上
它跟其它 backend 一样，默认强制生成到指定长度。这条不是"口径分歧"，是源码里注释和代码
真的对不上——`_lab` 的静态分析工具查不出这类问题，只有逐行读代码才能发现。

**TensorRT-LLM 的公式文档字符串把分子分母写反了。**

```python
@computed_field
def intertoken_latency(self) -> float:
    """
    Returns the time-per-output-token latency of the request [(OSL - 1) / (E2E Latency - TTFT)].
    """
    return ((self.end_timestamp - self.first_token_timestamp) /
            self.num_generated_tokens
            if self.num_generated_tokens > 0 else 0.0)
```
（`tensorrt-llm:tensorrt_llm/bench/dataclasses/statistics.py:65-72`）

文档字符串写的是 `(OSL - 1) / (E2E Latency - TTFT)`——token 数除以时长，量纲是"每秒
token 数"，是一个速率；实际代码算的是 `(end_timestamp - first_token_timestamp) /
num_generated_tokens`——时长除以 token 数，量纲是"每 token 毫秒数"，是一个延迟。代码本身
是对的（字段名 `intertoken_latency` 和调用方把它当延迟用都印证了这一点），错的是文档
字符串把分子分母的位置写颠倒了。这种"代码对、注释错"的情况比"代码错"更危险——因为读代码
的人往往优先信任注释，尤其是在快速扫读、没有逐行核对时。

**llama.cpp k6 脚本里的变量名有误导性。** `promptEvalEndTime` 这个名字听起来像是服务端
自己报告的"prompt 求值结束时间"（一个服务端内部事件），但赋值逻辑是纯客户端计时：收到
第一个 SSE `event` 时执行 `promptEvalEndTime = new Date()`，再与请求发出时的 `startTime`
作差记进 `llamacpp_emit_first_token_second`（`tools/server/bench/script.js`）。它就是
"客户端收到第一个 SSE 事件时的墙钟时间"，与 vLLM/SGLang 的 TTFT 打点在机制上完全等价
（都是客户端观测的首字节延迟，都包含网络往返），只是起了一个容易让人误以为是服务端
内部指标的名字。

**并发限流下的排队时间是"双方都不容易被发现"的隐藏口径。** 已在 ## 3.4 详细展开，这里
只强调一点：这个问题不是某一家做错了，是 vLLM 和 SGLang **各自独立**（借着共享的代码起点）
做出了同一个选择——计时器放在信号量内部——却都没有在帮助文本或文档里显式说明这一点。
两份脚本各自的注释都聚焦在"如何控制并发数"，没有一处提到"计时器什么时候启动"，这恰恰是
读者最容易凭直觉（错误地）以为"延迟从请求被创建那一刻就开始算"的地方。

## 8. 可改进点

### 8.1 读到一个吞吐/延迟数字时该问的问题清单

每条给出"不问会被误导成什么"：

1. **硬件型号、卡数、互联拓扑是什么？** 不问会把不同算力等级的结果直接横向比较。
2. **模型和精度（FP16/BF16/FP8/INT4/…）是什么？** 不问会把不同量化精度下的数字当成
   同一模型的性能。
3. **输入长度分布是定长还是有方差？均值和分布形状是什么？** 不问会把"定长合成 prompt"
   跑出的数字当成真实业务流量下的表现（见 ## 4 第一步）。
4. **输出长度分布是定长还是有方差？是否强制忽略了 EOS？** 不问会误以为测的是自然生成
   行为，实际上很可能是被迫生成到固定长度的同质批量（见 ## 5 决策四）。
5. **前缀共享率如何？用的是 ShareGPT 类真实数据还是随机合成数据？** 不问会把
   RadixAttention/前缀缓存友好场景下的优势，当成通用场景下的优势。
6. **到达过程是什么——瞬时全发、固定速率、Poisson、有界并发，还是轨迹回放？** 不问会把
   "极限吞吐压测"的数字当成"稳态在线延迟"来用（见 ## 5 决策一）。
7. **是否设置了 `--max-concurrency`？如果设置了，排队等待时间算不算进延迟？** 不问会
   漏掉 ## 3.4 描述的隐藏排队时间。
8. **是否预热，预热了几条？预热后缓存状态如何？** 不问会把冷启动开销（或反过来，
   预热带来的"免费"缓存命中）混进正式统计（见 ## 5 决策二、三）。
9. **报告的百分位是用什么算法算的（线性插值还是最近秩法）？样本量是多少？** 不问会把
   两种不同算法算出来的"p99"当成同一个统计量比较（见 ## 3.5）。
10. **ITL/TPOT 的计算是否除以了实际 token 数？服务端是否存在多 token 一次性 flush 的
    情况？** 不问会把"多 token 打包的一次网络往返"误记成"单 token 延迟"（见 ## 3.3）。
11. **是否走了完整的服务栈（HTTP 路由/鉴权/多副本），还是绕过了某些层直连内部组件？**
    不问会把裸模型前向延迟和端到端服务延迟混为一谈（见 ## 5 决策五）。
12. **测试脚本本身来自哪个项目？是不是被测引擎自己的官方脚本？** 不问会忽略"主场作战"
    偏差——LMDeploy 的官方 benchmark 就自带拉起 vLLM/SGLang server 的选项
    （`lmdeploy:benchmark/benchmark_serving.py:9-17`），测试方法论、指标计算方式、
    数据集格式全部由被比较对象之一的仓库决定，天然有利于该仓库的强项。
13. **只报了均值/p99，还是给出了完整分布（标准差、样本量、多个随机种子的方差）？** 不问
    会把一次性抽样的偶然波动、或某个种子下前缀恰好命中率高之类的运气，误当成引擎的
    稳定能力（见 8.2）。

### 8.2 自己做对比测试的最小口径表

如果本库将来要做跨引擎的对比测试（本机无 GPU，目前做不了，但这张表是给"以后谁在有 GPU
的机器上复现"用的），至少要固定并报告以下内容：

**必须固定并在报告里写明的量：**

| 类别 | 具体项 |
|---|---|
| 硬件 | GPU 型号、卡数、互联方式、驱动/CUDA 版本 |
| 模型 | 模型名与版本、精度（FP16/BF16/FP8/INT4/…）、上下文长度上限 |
| 工作负载 | 数据集名称与来源、输入长度分布（均值+标准差或分位数，不能只写均值）、输出长度分布（同）、是否忽略 EOS、前缀共享率（如可估计） |
| 并发/到达 | 到达过程类型（瞬时/固定速率/Poisson/有界并发/轨迹回放）、并发数或速率的具体数值、是否设置 `--max-concurrency`（并说明排队时间是否计入延迟） |
| 预热 | 预热请求数、预热后是否清空/保留缓存状态 |
| 引擎配置 | 引擎版本（commit sha）、关键旋钮（batch size、并行策略、注意力后端、是否开启前缀缓存/投机解码等） |

**必须报告的输出量：**

- 每个指标（TTFT/TPOT/ITL/E2E/吞吐）的**均值、标准差、p50、p90、p99**，不能只报均值或
  只报一个百分位；
- 明确写出百分位算法（线性插值还是最近秩法，见 ## 3.5）；
- 样本量（完成的请求数）；
- 至少 **3 个不同随机种子**的重复实验，报告种子间的方差范围，而不是单次运行的单个数字；
- 如果用了 `--max-concurrency`，额外报告"排队等待时间"这个通常被忽略的分量（哪怕是
  自己在客户端侧另外打点补上）。

**核心提醒：只报均值不报分布的对比等于没做。** 单次运行的单个均值数字，既不能告诉你
这个结果有多稳定，也不能告诉你两个引擎的差异是不是噪声范围内的波动——本篇整理的所有
口径分歧（数据集、到达过程、ITL 公式、百分位算法……）都会通过"样本方差"这一个渠道
最终体现出来，不报方差就等于把所有这些分歧都藏起来不让读者看见。
