## 0. 结论先行

- **这十篇（含本篇）加 `01-vLLM/`、`02-SGLang/` 两个子库，一共回答的是同一个问题的十四种答案：给定"要跑一个大语言模型的推理"这件事，你愿意在哪些地方多花代价、少花代价。** 没有一个引擎在所有维度上都赢——赢的前提是先承认自己只服务一部分场景。
- **按"解什么问题"分族比按知名度排序更有信息量。** 12 个引擎落进四族：集群多租户吞吐（vLLM/SGLang/TensorRT-LLM/LMDeploy/LightLLM/TGI）、单机端侧可跑（llama.cpp/MLC-LLM/KTransformers）、引擎的基础设施而非引擎本身（Mooncake/Dynamo）、研究性单一工作点（Tokasaurus）。`## 3` `## 4` 会论证这条分法，并指出它不是唯一正确的分法。
- **"解什么问题"和"技术路线"是两个独立维度，不能用其中一个预测另一个。** 最反直觉的证据是 LightLLM——它和 vLLM/SGLang/TensorRT-LLM/LMDeploy 一样瞄准"集群多租户吞吐"这个问题族，但在技术路线上是本库 12 个引擎里唯一一个自研 CUDA 文件数为 0、把算子全部交给 Triton 的（`_lab/out/repo_stats.json` 的 `engines.lightllm.kernels`）。同一个问题族里，工程投入形状可以完全不同。
- **本篇能找到的最硬一条血缘证据不是论文引用，是一行代码注释**：`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:2` 的文件头第二行原文写着 `# modify from: https://github.com/vllm-project/vllm`——LMDeploy 自己承认了这一份调度器是从 vLLM 改的，不需要任何推断。`## 4` 会把这条和其余几条能找到证据的血缘关系摆在一起，找不到证据的一律标"未查证"，不编。
- **"编译式 vs 解释式"这个常见的二分标签，在 TensorRT-LLM 身上是反的。** 它历史上是"编译式"阵营的代表，但这份快照里 AOT engine 编译路线已经被整体移除，默认执行是 eager PyTorch；反倒是"解释式"代表 vLLM，V1 默认把 `CompilationConfig.mode` 解析成 `VLLM_COMPILE`（走 `torch.compile`）。`## 6` 会把这条已经在 `[[01-TensorRT-LLM]]` 里查实的反转，摆进整张谱系图里重新定位。
- **API 协议层正在变成公共品，这件事本身削弱了"按接口分类"的意义。** 12 家里 10 家实现了 `/v1/chat/completions`，6 家实现了 Anthropic `/v1/messages`——协议表面趋同到已经分不出谁是谁，差异化被完全挤到了实现层。这是本篇选"解什么问题 × 技术路线"两个内部维度而不是"支持什么协议"来分类的理由之一（**本库推断**，`## 6` 展开）。

## 3. 分类维度的定义

### 3.1 维度一：解什么问题（问题族）

判据是"这个引擎的默认工作点假设了什么"——不是它理论上能不能做别的事，是它的架构决策为哪种假设买了单。四族：

**族 A · 集群多租户吞吐**（vLLM、SGLang、TensorRT-LLM、LMDeploy、LightLLM、TGI）——共享假设：GPU 显存是充裕的、部署形态是一台或多台服务器级 GPU、请求来自多个互不相关的客户端、优化目标是同一份显存预算下能撑住更高的并发。这条假设直接决定了这六家都要有：连续批处理调度器、某种形式的前缀/KV 复用、OpenAI 兼容 HTTP 层。

**族 B · 单机/端侧可跑**（llama.cpp、MLC-LLM、KTransformers）——共享假设：目标硬件不确定甚至可能没有独立显卡，用户是单人或极小规模并发，"部署得上、跑得起来"本身就是要解决的问题，不是解决完之后才谈的锦上添花。这条假设决定了这三家都在打通尽可能多的硬件后端（llama.cpp 16 条 `register_backend()`，`## 1.1` 已在 [[05-llama.cpp-server]] 里核过；MLC-LLM 靠 TVM 的 codegen 后端广度打通 CUDA/ROCm/Metal/Vulkan/Android/iOS/WebGPU；KTransformers 把显存不够这件事当成默认前提去解决，而不是回避）。

**族 C · 不是引擎，是引擎的基础设施**（Mooncake、Dynamo）——共享假设：单个引擎进程看不到、也不该看到的东西——跨机字节传输、跨实例路由决策——需要被抽成独立的、可以同时服务多个引擎的产品。这条假设决定了它们都刻意不摸模型计算（Mooncake 全库没有一行 attention/GEMM kernel；Dynamo 仅有的两个 CUDA 文件是内存搬运 kernel，见 `## 2`），也决定了它们的对外接口都不是给终端用户的 HTTP API，而是给别的引擎调用的库/RPC 契约。

**族 D · 研究性/单一工作点**（Tokasaurus）——共享假设：不存在，因为只有一个成员。它的坐标是"CPU 开销要压到最低、服务对象是大批量重复采样/rollout"这一个窄工作点，代码规模（13,219 行）比族 A 任何一家小一到两个数量级。单独成族不是凑数，是因为它证明了"一个推理引擎最少需要几个零件"这个问题本身有一个可以直接数出来的答案（三进程：HTTP、CPU 编排、GPU 执行，见 [[10-Tokasaurus]] `## 1`），而这个答案对理解族 A 那六家"多出来的复杂度花在哪"很有参照价值。

### 3.2 维度二：技术路线

判据是"模型的计算图/调度决策，最终以什么形式变成可执行代码"：

- **运行时解释式**：Python（或其它高级语言）进程在服务运行期间逐请求做决策，模型前向调用的是提前编译好的通用算子库，整个引擎本身没有一次性的"编译成目标平台专属产物"这一步。vLLM、SGLang、LightLLM、TGI 是这条路线的代表——**TensorRT-LLM 现在也要算进这一格，这一条本身是本篇要专门讲清楚的一次改判**：`tensorrt-llm:tensorrt_llm/commands/` 这份快照里只剩 `bench.py`/`eval.py`/`serve.py`/`utils.py`/`_serve_stability.py`/`__init__.py` 六个文件，`trtllm-build`（曾经把模型编译成 `.engine` 文件的命令）已经不在其中；`docs/source/legacy/tensorrt-backend-removal.md` 开篇的 `{note}` 原文写得很直接——"**Breaking change.** The TensorRT engine backend has been removed. PyTorch is now the sole execution backend for TensorRT LLM (AutoDeploy, built on the PyTorch backend, remains available)."（本库现场核对：该目录与该文档在 `_src/tensorrt-llm` 里确实如此，非转述）。当前默认路径是 eager PyTorch，`torch_compile_config` 默认 `None`（`tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:5407`-`5408`）——这条判据和 vLLM/SGLang 归入这一格用的是同一把尺子："当前快照默认执行路径有没有一次性编译产物"，TensorRT-LLM 现在的答案是"没有"，所以按 `## 3.2` 的判据它就该归进解释式，不该因为项目历史上叫得出"编译"两个字就继续算它编译式。**这一格里唯一还留着"编译式血统"的部分是调度决策，不是模型图**：in-flight batching 的调度算法（`CapacityScheduler`）默认走 C++、通过 nanobind 暴露给 Python（`tensorrt-llm:tensorrt_llm/_torch/pyexecutor/_util.py:3082`-`3094`），这是一种"把决策逻辑下沉到更底层语言换执行效率"的选择，和"把模型计算图提前编译成平台专属产物"是两件完全不同的事，`## 6.1` 会把这条区分摊开讲。
- **编译式**：存在一个显式的"把模型/配置变成一份可执行产物"的步骤，跑起来的东西是这一步的输出，不是每次启动都重新解释——**这份快照里，这一格只剩 MLC-LLM 一个成员**（`mlc_llm compile` 产出 `.so`/`.wasm`/`.tar`，`[[06-MLC-LLM]]` `## 4.1`）。TensorRT-LLM 曾经是这条路线在本库里的旗舰代表（`trtllm-build` 把 HF checkpoint 编译成绑定了具体并行度/精度的 `.engine` 文件），但这条路线已经被整体移除，不再是"可选但不推荐"，是代码里已经找不到——上一条已经给出源码与文档证据。
- **手写 C++ 单体**：性能敏感路径是人手写的 C++/CUDA，没有中间语言、没有运行时解释层，一个二进制文件承担从 HTTP 到 kernel 的全部职责。llama.cpp 是最纯粹的代表。
- **异构卸载**：不是一种独立的执行范式，是"把计算拆到不同硬件"这个正交的额外约束，可以叠加在前面任何一种路线之上。KTransformers 现在的形态是"CPU MoE 算子库（C++/AMX）+ 借用别人的运行时解释式宿主（SGLang fork）"，技术路线上其实横跨两格。

### 3.4 为什么不选其它维度组合

写这张矩阵之前本篇考虑过至少三种别的分法，都放弃了，理由值得摆出来——这不是回避质疑，是让读者知道这些候选被认真想过、而不是没想到。

**候选一：按主语言分类（Python/C++/Rust/混合）**——直接被 `## 3.2` 的定义否决，因为主语言和技术路线经常不是一回事：TGI 主语言是 Rust+Python 混合，但它的技术路线仍然是"运行时解释式"（模型前向仍是 eager PyTorch，只是调度决策搬进了 Rust，`[[03-TGI]]` `## 0`）；llama.cpp 主语言是纯 C/C++，但按主语言分类会把它和"C++/Python 混合"的 TensorRT-LLM、LMDeploy 归进模糊的"有 C++"一类，却看不出 llama.cpp 是唯一一个没有任何运行时解释层的项目。主语言是"这个项目用什么写"，技术路线是"计算图/调度决策最终怎么变成可执行代码"——前者是实现细节，后者才是架构选择，`## 4.1` 总表把主语言单独列成一列，正是承认它是有用信息，但不能替代 `## 3.2` 的技术路线判据。

**候选二：按"开源治理模式"分类（公司主导 / 社区主导 / 研究组维护）**——本篇最终没有把它作为正式的第三维，原因是这个信息本库缺乏系统取证手段：`_PLAN.md` §1 的红线不允许本库产出没有网络权限核实的公司决策/团队规模数字，而"谁在主导"这件事往往需要看 GitHub 组织归属、核心贡献者所属机构这类本库无法系统核实的信息。能从源码/文档直接观察到的替代信号只有两条——`## 4` 已给出的代码规模量级和 `## 7` 已给出的最后提交日期——本篇选择只呈现这两条可核实的信号，不去猜测背后的治理结构。这不代表这维度不重要，只代表它超出了本库"每条断言必须能回到一行真实源码"的取证标准（`_PLAN.md` §1 第 1 条）。

**候选三：按"自研 kernel 深度"单独开一维（自研 CUDA/Triton 多 vs 全部外包）**——这条曾经很有吸引力，因为 `## 4.2` 已经用它当反直觉证据（LightLLM 0 自研 CUDA vs vLLM 169 个）。最终没有单独开维，是因为它更适合作为"技术路线"这个维度内部的一条子刻度，而不是一个独立正交轴：`## 3.2` 定义的四条技术路线里，"运行时解释式"这一支内部本来就允许自研 kernel 深度差异很大（vLLM/SGLang 重度自研，LightLLM/Tokasaurus 几乎全部外包给 Triton/flashinfer），把它拆成独立维度会让矩阵从 4×4 膨胀到更高维，边际信息量的增加配不上多出来的复杂度——两维矩阵已经够用来承载 `## 4.2` `## 4.3` 这些具体对比，第三维目前不是必需品，`## 8` 会把这条留作以后如果证据更充分时再考虑的方向。

### 4.2 族内共性：为什么这个假设决定了那样的架构

**族 A（集群多租户吞吐）** 的六家，无一例外都要在"KV 显存怎么切给谁"和"下一步该跑谁的请求"这两件事上做选择，区别只在选择的粒度和语言。粒度上：vLLM/SGLang/LightLLM 默认贴近 token 粒度（`vllm:vllm/config/cache.py:81` 的 `block_size` 与 `sglang:python/sglang/srt/arg_groups/overrides.py:2378`-`2395` 的 `page_size` 默认 1，`## 2` 已给出），LMDeploy TurboMind 用固定容量槽位（`[[02-LMDeploy与TurboMind]]` `## 3.4` 的 `Engine::Impl::State::rc`），llama.cpp 干脆没有这层抽象（`[[05-llama.cpp-server]]` `## 6` 的"固定车位 vs 弹性车道"）。语言上：TGI 把这个决策整体搬进 Rust（`[[03-TGI]]` `## 5` 决策一），TensorRT-LLM 把它交给 C++（`[[01-TensorRT-LLM]]` `## 5` 决策三），其余四家留在 Python。**共同点是这六家都认为"这个决策值得被认真做"**——这是族 A 和其它三族最本质的分野：族 B 的 llama.cpp 因为 slot 数量本来就小（个位数到几十），线性扫描（`llama.cpp:tools/server/server-context.cpp:1500`）就够用，不需要族 A 那套复杂度；族 D 的 Tokasaurus 因为工作负载本身高度同构（同一 prompt 重复采样），调度可以简化到"提前算好未来 8 步"（`[[10-Tokasaurus]]` `## 5` 决策三）。

**族 B（单机/端侧可跑）** 的三家在"怎么打通更多硬件"这件事上给出了三种不同答案：llama.cpp 靠手写（16 条 `register_backend()` 各自独立实现，CPU 后端 `ggml-cpu/` 反而比 CUDA 后端代码量大一倍，因为没有 cuBLAS 这类库可以借力，`[[05-llama.cpp-server]]` `## 1.1`）；MLC-LLM 靠编译器后端广度（同一份 Relax IR，`Target`/`BuildFunc` 换一对就能落到新平台，`[[06-MLC-LLM]]` `## 5` 决策一）；KTransformers 干脆不追求"打通更多硬件"，只解决"这一份显存不够用怎么办"这个更窄的问题，硬件矩阵反而分层退化（AMX > AVX512 > llamafile/AVX2，`[[07-KTransformers]]` `## 7`）。三家共享的是"单机部署"这个交付形态，不是"怎么做"这个具体路线——这再次印证了 `## 3` 两维分类法的意义：问题族相同不代表技术路线也相同。

**族 C（引擎的基础设施）** 的两家分别在"数据面"和"控制面"上做纯化：Mooncake 拒绝把字节搬运做成网络服务（编译进调用方进程，`[[08-Mooncake传输引擎]]` `## 5` 决策五），因为微秒级操作隔一层 HTTP/gRPC 就亏了；Dynamo 反过来把路由决策独立成网络服务（`RadixTree` 在 Rust 里跑成单独进程，`## 2` 已引用），因为路由需要跨多个 worker 的全局视野，天生就不该是任何单个引擎进程内部的事。两者一个坚决不做网络边界、一个坚决做网络边界，理由都是"这件事需要被多少方共享/独立扩缩容"——判据一致，落点相反，这是本库另一处反复出现的模式（详见 `[[08-Mooncake传输引擎]]` `## 5` 决策五末段）。

**族 D（研究性单点）** 只有 Tokasaurus 一员，它存在的价值是给族 A 提供了一个"最小骨架"的对照组——13,219 行能撑起一个完整的三进程推理服务这件事本身，说明族 A 那六家动辄几十万上百万行，绝大部分不是"跑起来"必需的，是"跑得快、跑得稳、接得住多少种客户端/多少种模型架构"这些额外目标层层加码的结果（[[10-Tokasaurus]] `## 6` 用"调度器只有 684 行 vs 2,179～3,823 行才是可比数字"这条具体证据把这笔账拆开算过一次）。

### 4.3 技术路线族内共性：为什么这四条路线彼此不能互相替代

**运行时解释式**这一支（vLLM、SGLang、LightLLM、TGI、LMDeploy pytorch backend、TensorRT-LLM，`## 6.1` 会展开最后一个成员为什么归在这里）共享的收益是"新模型架构接入快"——直接复用 PyTorch/HuggingFace 生态已有的模型定义，不需要为每个新架构重新实现一遍图构建代码，代价是需要精心管理 Python 解释器和 GPU 忙循环之间的干扰（GIL、序列化开销），六家给出的具体规避手法各不相同：vLLM 拆独立进程（`## 2` 引用之外，`[[01-vLLM-全景与代码地图]]` `## 5` 决策一）、TGI 把调度整段搬进 Rust（`[[03-TGI]]` `## 5` 决策一）、TensorRT-LLM 把调度决策交给 C++、LMDeploy pytorch backend 和 SGLang/LightLLM 则直接接受这份 Python 内代价，靠"kernel launch 是异步的、Python 很快把控制权交还事件循环"这一条经验撑住。

**编译式**这一支目前只剩 MLC-LLM 一个成员，它换来的是"一份 Relax IR、多种硬件后端"（`## 3.2`），代价是新模型架构必须先手写 `nn.Module` 定义再走一遍完整编译流水线才能验证对不对，不能像解释式那样改一行代码立刻用新请求验证。TensorRT-LLM 曾经也在这一支，退出的直接后果是**不再需要给每个（模型、精度、并行度）组合单独编译并存盘一份 `.engine`**——这正是 `[[01-TensorRT-LLM]]` `## 5` 决策一里"不这样会怎样"论证链的核心：维护两套模型定义（HF 原始 + TRT-LLM checkpoint 转换脚本）的技术债，是它退出编译式阵营的直接动机。

**手写 C++ 单体**这一支（llama.cpp、LMDeploy TurboMind）换来的是"没有中间语言、没有运行时解释层，能榨到硬件允许的极限"，代价是新硬件/新架构接入必须有人手写对应的图构建代码或专用 kernel——llama.cpp 的 `src/models/` 下 151 个文件对应 151 种手写架构定义（`[[05-llama.cpp-server]]` `## 5` 决策一），TurboMind 的白名单卡在约 15 个架构且几年才涨到这个数（`[[02-LMDeploy与TurboMind]]` `## 5` 决策一）——这条路线的接入速度天花板，直接体现为这两个项目各自最不适合的场景（`## 4.1` 总表里 llama.cpp/LMDeploy 两行的"不适合什么"列）。

**异构卸载**这一支目前只有 KTransformers，它不是一种独立的执行方式，是"计算怎么在硬件之间分配"这个正交问题的解，可以叠加在任何一种执行路线之上（历史上 KTransformers 自己就叠加在"手写 C++ 单体"之上——旧架构自研调度器，见 `## 4.4`；现在叠加在"运行时解释式"之上——借用 SGLang fork）。这条路线换来的是"显存不够也能跑"，代价是 CPU 算力和 PCIe 带宽会在并发升高时先于其它资源被打满（`[[07-KTransformers]]` `## 5` 决策一已用官方吞吐数字的硬件配置注明过这条边界）。

### 4.4 血缘与相互借鉴：谁抄了谁的想法

这一节只写能在源码/文档里找到证据的关系，找不到证据的一律标"未查证"，不按行业常识或个人印象补。

**PagedAttention → 各家块管理**：块/页粒度的 KV 显存管理，是族 A 六家里除 llama.cpp（族 B，压根没有这层抽象，`[[05-llama.cpp-server]]` `## 6`）之外的共识——vLLM 默认 `block_size=16`（`vllm:vllm/config/cache.py:81`），SGLang 默认 `page_size=1`（`sglang:python/sglang/srt/arg_groups/overrides.py:2378`-`2395`），LMDeploy TurboMind 用固定容量槽位而非严格意义的分页（`[[02-LMDeploy与TurboMind]]` `## 3.4`），MLC-LLM 的 KV cache 类直接继承 TVM Relax 前端自带的分页实现（`mlc-llm:python/mlc_llm/nn/kv_cache.py:13` 的 `class PagedKVCache(TVMPagedKVCache)`），Tokasaurus 也有自己的 `BlockAllocator`（`tokasaurus:tokasaurus/manager/allocator.py:129`）。**这条证据链能证明的是"分页/块粒度管理 KV 显存"已经是族 A 的事实标准，不能证明"后来者的具体实现是照抄 vLLM 代码"**——本篇没有在 MLC-LLM/Tokasaurus 源码里找到任何一处注释指向 vLLM 或 PagedAttention 论文，唯一带直接血缘证据的是下一条。

**连续批处理与调度器实现 → LMDeploy pytorch backend 直接承认改自 vLLM**：这是本篇能找到的唯一一条无需推断的直接血缘证据——`lmdeploy:lmdeploy/pytorch/paging/scheduler.py:2` 文件头第二行原文 `# modify from: https://github.com/vllm-project/vllm`，`[[02-LMDeploy与TurboMind]]` `## 4` ③ 已经指出它的核心结构（`SchedulerSession`/`SchedulerSequence`、`block_manager` 分页分配、`block_trie` 前缀树匹配）和 vLLM V1 调度器在概念骨架上高度相似。**至于"连续批处理"这个调度范式本身最早出自哪个项目、哪一年提出，本篇未查证，不编造论文标题与时间线**——能确定的只是：族 A 六家（LMDeploy TurboMind 除外，见 `## 3.2`）都实现了某种连续批处理，其中至少一家（LMDeploy pytorch backend）有源码级证据指向直接借鉴 vLLM，TGI 的 Rust 实现（`[[03-TGI]]` `## 3`）在结构上是独立设计（`Entry`/`Queue`/`State` 三层 actor 模式，没有类似的"modify from"注释）。

**RadixAttention → 各家前缀树**：`sglang:python/sglang/srt/mem_cache/unified_radix_cache.py:148` 的 `UnifiedRadixCache` 是这个名字的源头（SGLang 自己的招牌设计，`[[01-SGLang-全景与代码地图]]`）。同一个"radix"命名在另外两处独立出现——MLC-LLM 的 `prefix_cache_mode` 默认值就叫 `kRadix`（`mlc-llm:cpp/serve/config.h:287`），TGI 有自己的 `RadixAllocator`（`tgi:backends/v3/src/radix.rs:20`）。**本篇在 MLC-LLM 和 TGI 源码里都没有找到任何一处注释credit SGLang 或 RadixAttention——这条只能算"命名收敛"，不能算"确凿血缘"**：既可能是三家独立借用了计算机科学里本来就存在的经典数据结构名字（radix trie/基数树），也可能是确实参考了 SGLang 的开源实现，本篇未查证，只如实列出现象。反例同样值得记一笔：vLLM 明确选择了不同的路线——块哈希表而非前缀树（`00-总览与阅读地图.md` §4 已查实的"前缀缓存的驱逐不是真 LRU"那条硬结论）——**不是所有族 A 成员都在往同一个数据结构收敛**。这个"radix"的想法后来还被搬到了一个新问题上：Dynamo 的 `RadixTree`（`dynamo:lib/kv-router/src/indexer/radix_tree.rs:49`）解决的不是单实例内的前缀缓存，是跨 worker 的 KV 感知路由索引——同一种树结构，被应用到了 `## 3.1` 定义的完全不同的问题族（族 C 而非族 A）上。

**投机解码：EAGLE 被至少三家独立实现**：SGLang 有 `EAGLEWorkerV2`（`sglang:python/sglang/srt/speculative/eagle_worker_v2.py:1050`），vLLM 有专门的投机解码提议器基类（`vllm:vllm/v1/spec_decode/llm_base_proposer.py:71` 的 `SpecDecodeBaseProposer`），本库现场核实 llama.cpp 的 `llama.cpp:common/common.h:173` 也有 `COMMON_SPECULATIVE_TYPE_DRAFT_EAGLE3` 这个具体枚举值（对应 EAGLE3 变体，`llama.cpp:common/arg.cpp:375`-`377` 的 `spec_type_draft_eagle3` 判断分支），MLC-LLM 有独立的 `EagleForCausalLM` 模型定义（`mlc-llm:python/mlc_llm/model/eagle/eagle_model.py:76`）。**EAGLE 是一种公开发表的投机解码算法，四家各自实现是"照着论文各自实现"还是"互相抄代码"，本篇没有找到任何一处交叉引用的注释，未查证，不下结论**——能确定的只是：这四家都认为这个算法值得投入实现，这本身也是一种收敛信号。

**依赖锁定，不是相互借鉴，但值得放在血缘这一节一起看**：KTransformers 现在只能用 `kvcache-ai/sglang` 这份私有 fork，不能用官方 SGLang（`ktransformers:kt-kernel/README.md:280` "Use `sglang-kt`（kvcache-ai fork）, not the official `sglang` package"）——这不是"借鉴思路"，是直接的代码依赖，`[[07-KTransformers]]` `## 5` 决策三已指出这条依赖把 KTransformers 的可用性焊死在了这份 fork 的更新节奏上。反向的一条声明也值得摆出来但不采信为交叉验证：LightLLM 的 README 自称 vLLM 与 SGLang 都"部分借用了 LightLLM 的 kernel"（`lightllm:README.md:54`、`lightllm:README.md:55` 原文 "some LightLLM's kernel used"）——**这是 LightLLM 单方面的自述，本篇没有在 vLLM/SGLang 源码里找到对应的 credit 注释去交叉核实，血缘不总是单向的，但单方声明也不能直接当作双向验证过的事实**。

### 4.5 两个维度合起来能预测什么，不能预测什么

把 `## 3.1`（问题族）和 `## 3.2`（技术路线）叠在一起看，能预测的是"这个引擎大概率会有什么子系统"——族 A 成员大概率都有某种连续批处理调度器和某种前缀/KV 复用机制（`## 4.2` 已逐一核对），技术路线是"运行时解释式"的成员大概率能更快接住新模型架构，是"手写 C++ 单体"的成员大概率在打通新硬件上要付更高代价（`## 4.3` 已逐一核对）。**不能预测的是"这个引擎具体会做出什么设计决策"**——同样是族 A×运行时解释式，vLLM 选块哈希表、SGLang 选前缀树，两者都在这一格，但 KV 复用的具体数据结构完全不同（`## 4.4` 已指出）；同样是族 A，TGI 把调度决策搬进 Rust、vLLM 把它留在 Python，两者对"值得为这个决策换语言"给出了相反答案（`## 4.2` 已指出）。**两维分类图能收敛到"这个引擎大概率长什么样的骨架"，收敛不到"这个引擎具体每一根骨头怎么长"——后者只能靠读单篇原文，这也是本篇为什么要在 `## 4.1` 的每一行末尾都挂一个"本库对应篇目"链接，而不是假装一张表能替代十篇原文。**

## 5. 设计决策与代价

本节的"决策"不是某个引擎的架构决策，是本篇分类方法本身做的几个取舍——**给读者一个可以拿来质疑本篇的抓手，而不是只给结论**。

### 决策一：按"解什么问题"分族，不按 star 数/知名度排序

- **为什么这么设计**：知名度排序是一个滞后指标（反映过去被讨论的程度），不解释"为什么长成这样"；按目标工作点分族能直接回答"这个架构决策在为哪种假设买单"这个问题，`## 4.2` 的每一条族内共性论证都依赖这条前提成立。
- **不这样会怎样**：如果按知名度/代码规模排序（比如把 TensorRT-LLM 排在最前因为它总行数最大），读者会得到一份"谁更重要"的印象，却看不出 TensorRT-LLM 和 vLLM 其实在解同一个问题、只是选择了不同的语言分工（`[[01-TensorRT-LLM]]` `## 6` 已经证实这一点）——按规模排序会把"问题相同、路线不同"这条最有信息量的对比关系埋掉。
- **什么时候可以不这样**：如果读者的目标是"选一个团队规模验证过的选项去生产环境用"，知名度/成熟度信号（issue 响应速度、发布节奏、生产案例数量）确实是更直接相关的判据——但本库没有网络权限核实这些信号（`_PLAN.md` §1 的红线），也不是这十篇单篇解剖的取证范围，这类判据留给读者自己在部署前另外核实。

### 决策二：两个正交维度，不合并成一个

- **为什么这么设计**：`## 4.2` 已经给出反例——LightLLM 和 vLLM 问题族相同、技术路线截然不同（0 自研 CUDA vs 169 个 CUDA 文件）；llama.cpp 和 MLC-LLM 问题族相同、技术路线截然不同（手写单体 vs 编译器生成）。如果只留一个维度，要么把 LightLLM 和 vLLM 强行归成"一类"抹掉它们最大的工程差异，要么把 llama.cpp 单独开一族只为了容纳它一个，两种做法都会丢信息。
- **不这样会怎样**：单维分类法在遇到 LMDeploy 这种"一个项目、两条技术路线"的对象时会被迫做取舍——要么承认它同时属于两类（打破"单维分类互斥"的基本假设），要么强行只算一类（丢掉 TurboMind 或 pytorch backend 其中一半的真实情况）。两维分类法允许 LMDeploy 合法地出现在矩阵的两个格子里，不需要强行二选一。
- **什么时候可以不这样**：如果目标只是"给 12 个引擎排个座次表方便记忆"，单维（比如只按问题族）已经够用，两维矩阵对这个目标是过度设计；两维矩阵真正有用的场景是"我已经知道自己的问题族（比如确定要做集群服务），要在同一问题族里的多个技术路线之间选型"——这正是 [[05-选型决策树]] 要做的下一步工作，本篇止步于画图，不替读者做选择。

### 决策三：把 Mooncake 和 Dynamo 单独开一族，不强行塞进"引擎"的框架里比较

- **为什么这么设计**：`## 2` 已经给出源码证据——Mooncake 全库没有一行 attention/GEMM kernel，`_lab/api_surface.py` 对它的 HTTP 路由扫描结果是 0（且这条 0 是脚本作者故意在配置里留白确认的，不是漏报，`[[08-Mooncake传输引擎]]` `## 0`）；Dynamo 仅有的两个 CUDA 文件是内存搬运 kernel，不含任何计算逻辑。如果把它们塞进"引擎"的评价维度里（比如问"Dynamo 的调度器和 vLLM 的调度器谁更好"），这个问题本身就问错了对象——`[[09-NVIDIA-Dynamo]]` `## 6` 明确指出 Dynamo 解决的是 vLLM/SGLang 单进程视角天然看不到的问题（跨机 KV 感知路由），不是替代品。
- **不这样会怎样**：如果强行把 Mooncake/Dynamo 塞进"12 个引擎"的排位里一起比较，读者会带着"它们该有多快""它们的调度策略够不够聪明"这类错误的问题去读这两篇文章，而这两个项目自己刻意回避了这些问题（不摸计算、不做面向终端用户的服务）——错误的问题框架会让读者觉得这两篇"没讲到重点"，实际是提问的坐标系本身错了。
- **什么时候可以不这样**：如果本库未来要新增一篇专门讲"KV 传输/跨实例编排"这个子领域的横向对比（类似 [[03-KV缓存与前缀复用横向对比]] 那样聚焦在一个具体问题上），Mooncake/Dynamo 就应该被拉回来和 vLLM/SGLang 各自的 PD 分离实现（[[12-vLLM-PD分离与KV-Connector]]、[[11-SGLang-PD分离与HiCache分层]]）放在同一张对比表里——那时候比较的对象是"同一个子问题的不同解法"，是合法的比较，不是本篇这种"引擎 vs 基础设施"的范畴错误。

### 决策四：本篇不给排名，只给"什么场景选什么"的判据

- **为什么这么设计**：`## 4.1` 总表的"不适合什么"这一列是硬性要求，不许为空——这个设计本身就是在强制每一行都必须承认代价，排名式的表达（"最好的是 X"）系统性地隐藏代价，只留优点。一张只列优点的谱系图，读者拿着它做选型决策时会在"不适合什么"这一步吃亏，因为文章根本没告诉过他。
- **不这样会怎样**：如果本篇给出"综合最强"这类结论，等于替读者的具体场景做了一次未经他们同意的加权——比如"TensorRT-LLM 综合最强"这句话对一个没有 NVIDIA GPU 的读者毫无意义，对一个需要跨硬件部署的读者甚至是误导。
- **什么时候可以不这样**：如果读者的约束条件已经完全确定（比如"我只用 NVIDIA GPU、只做集群服务、模型架构在 TurboMind 白名单里"），在这组约束下确实可以问"这几个选项里哪个更适合"并得到一个相对靠谱的答案——但那已经是把本篇的"问题族 × 技术路线"坐标系代入了具体约束后收窄出来的子集比较，不是本篇这种跨越四个问题族的全局排名，这类收窄留给 [[05-选型决策树]] 去做。

## 6. 分类的边界与争议

### 6.1 "编译式"标签在 TensorRT-LLM 身上不只是过时，是这份快照里已经不成立——本篇因此把它移出了"编译式"格子

这是本篇写作过程中自己改判过一次的地方，值得把改判的证据摆出来，而不是只给结论。把 vLLM 定为"运行时解释式"、TensorRT-LLM 定为"编译式"，是这两个项目还叫得出各自历史名字的年代留下的印象。本库直接在 `_src/tensorrt-llm`（取证基准 `75b023cd`）里核对了两处：

- `tensorrt-llm:tensorrt_llm/commands/` 目录现场 `ls` 只剩 `__init__.py`、`_serve_stability.py`、`bench.py`、`eval.py`、`serve.py`、`utils.py` 六个文件——曾经把 HF checkpoint 编译成绑定了并行度/精度的 `.engine` 文件的 `trtllm-build` 命令**不在其中**。
- `tensorrt-llm:docs/source/legacy/tensorrt-backend-removal.md` 开篇的 `{note}` 原文：「**Breaking change.** The TensorRT engine backend has been removed. PyTorch is now the sole execution backend for TensorRT LLM (AutoDeploy, built on the PyTorch backend, remains available).」

再逐行核对默认配置，结论要反过来说：

| | 默认执行模式 | 依据 |
|---|---|---|
| TensorRT-LLM | **eager PyTorch**，`torch_compile_config` 默认 `None` | `tensorrt-llm:tensorrt_llm/llmapi/llm_args.py:5407`-`5408` |
| vLLM | **默认走 `torch.compile`**，`CompilationConfig.mode` 为 `None` 时解析成 `VLLM_COMPILE`（=3） | `vllm:vllm/config/compilation.py:447`-`459` |

**这条反转比"标签过时"更进一步**：`## 3.2` 定义"技术路线"这个维度的判据是"这份快照的默认执行路径有没有一次性编译产物"，TensorRT-LLM 当前的答案是"没有"——所以本篇 `## 3.3` 的矩阵**没有**把它继续留在"编译式"格子里当历史遗产供着，而是按同一条判据把它挪进了"运行时解释式"，和 vLLM/SGLang 归在一格。矩阵上标的 ★ 提醒的是它和这一格其它成员不完全一样的地方：调度决策（in-flight batching 的 `CapacityScheduler`）默认走 C++、经 nanobind 暴露给 Python（`tensorrt-llm:tensorrt_llm/_torch/pyexecutor/_util.py:3082`-`3094`），vLLM/SGLang 的等价决策留在纯 Python（`vllm:vllm/v1/core/sched/scheduler.py:484`、`sglang:python/sglang/srt/managers/scheduler.py:384`）——**它下沉到底层语言换执行效率的是"决策"，不是"模型计算图"，这两者是两个不同的东西，混着讲才会把它错判成"编译式"。** 同一条纪律——判据必须落到"这份快照实际在做什么"，不能落到"这个项目的名字/历史印象暗示了什么"——在 `[[01-TensorRT-LLM]]` `## 7` 踩坑 1（`attn_backend='TRTLLM'` 这个字符串和已移除的 TensorRT engine 后端没有任何关系）里已经出现过一次。

### 6.2 "编译"这个词，在不同引擎里指的根本不是同一件事

这是比上一条更容易被忽略的边界问题。MLC-LLM 的"编译"（`mlc_llm compile`）是**必要条件**——不跑这一步，模型在目标平台上完全没法执行，产出的 `.so`/`.wasm`/`.tar` 就是唯一的可执行形态（`[[06-MLC-LLM]]` `## 4.1`）。vLLM/TensorRT-LLM 语境下的"编译"（`torch.compile`/CUDA Graph 捕获）是**可选的加速手段**——不开它，模型一样能跑，只是每一步都要走一遍未优化的 eager 路径，慢但不会不可用。把这两种"编译"混为一谈，会得出"vLLM 现在也是编译式了，和 MLC-LLM 是同一类"这种错误推论——`[[06-MLC-LLM]]` `## 6` 已经用一张三角对比表（vLLM/TensorRT-LLM/MLC-LLM）把这条边界画清楚了，本篇复用这条结论：**"编译式"和"跨硬件"是两个独立的轴，不能因为一家是编译式就默认它跨硬件（TensorRT-LLM 历史上的编译路线只服务 NVIDIA 一家），也不能因为两家都叫"编译"就默认它们的编译在系统里扮演同样的角色。**

### 6.3 LMDeploy 一个项目跨两个格子，这不是分类失败，是它本身就是两个引擎

`## 3.3` 矩阵里 LMDeploy 出现两次不是排版冗余。`[[02-LMDeploy与TurboMind]]` `## 0` 的第一条结论原话就是"LMDeploy 不是'一个引擎加几个后端选项'，是两套完全独立的执行栈"——两套配置表（42 字段 vs 48 字段，重叠不到一半）、两套调度模型（固定容量槽位 vs 每步重建）、两套 KV 量化 kernel（CUDA C++ 手写 vs Triton 独立实现）。如果按项目名（"LMDeploy"）而不是按执行栈来分类，会把这个项目内部两条已经在演化方向上分岔的路线（`[[02-LMDeploy与TurboMind]]` `## 3.1`：TurboMind 在"同一批经典架构榨得更快"，pytorch backend 在"接住更多新架构"）当成一件事来讨论，读者会得到一个模糊掉内部矛盾的印象。**这条边界问题的教训是**：本篇的分类单位严格来说不是"项目仓库"，是"执行栈"——大多数情况下一个仓库对应一个执行栈，LMDeploy 是这份快照里唯一的例外。

### 6.4 KTransformers 的技术路线标签本身在这份快照发生过一次迁移

`[[07-KTransformers]]` `## 1.2` 记录了这个项目"从一体化框架到算子库+fork"的转向——旧架构（`archive/`）有自己用 C++ 手写的连续批处理调度器（`ktransformers:archive/csrc/balance_serve/sched/scheduler.h:161` 的 `class Scheduler`），技术路线上属于"手写 C++"这一支；新架构把调度整体委托给 SGLang fork，只保留 CPU MoE 算子库这一层，技术路线上退化成"借用运行时解释式宿主"。`## 3.3` 矩阵按当前快照把它标在"异构卸载×族B"，但**这个坐标不是这个项目的永久属性**——如果本库半年后重新 clone 这个仓库，它完全可能因为再一次架构调整落进不同的格子。这条边界提醒本篇自己：**分类图是这份快照（2026-08-17～2026-08-22）的截面，不是对项目的永久判决**，`## 7` 会把这条延伸到活跃度事实的讨论。

### 6.5 API 协议层的收敛，正在让"支持什么协议"这个维度失去分类价值

统计 `## 2` 之外各单篇已经核实过的协议覆盖（12 家里，Mooncake 不是 HTTP 服务、KTransformers 委托给 SGLang fork 不算自己实现，故分母按 10 算）：

| 引擎 | `/v1/chat/completions`（OpenAI） | `/v1/messages`（Anthropic） |
|---|---|---|
| vLLM | 有 | 有 |
| SGLang | 有 | 有 |
| TensorRT-LLM | 有（`tensorrt-llm:tensorrt_llm/serve/openai_server.py:1021`） | 未查证 |
| LMDeploy | 有 | 有（`lmdeploy:lmdeploy/serve/anthropic/endpoints/messages.py:70`） |
| TGI | 有（仅 3 条 `/v1/*`，原生 `/generate` 才是主入口） | 未查证（README 未提及） |
| LightLLM | 有 | 有 |
| llama.cpp | 有（`llama.cpp:tools/server/server.cpp:245`） | 有（`llama.cpp:tools/server/server.cpp:251`，注释原文"anthropic messages API"） |
| MLC-LLM | 有 | 明确没有（`[[06-MLC-LLM]]` `## 4.3` 已核实） |
| Dynamo | 有（默认路径，`dynamo:lib/llm/src/http/service/openai.rs:3896`） | 有（`dynamo:lib/llm/src/http/service/anthropic.rs:72`、`:80`） |
| Tokasaurus | 有 | 未查证 |

10 家全部实现了 OpenAI `/v1/chat/completions`；至少 6 家（vLLM、SGLang、LMDeploy、LightLLM、llama.cpp、Dynamo）确认实现了 Anthropic `/v1/messages`。**本库推断**：这个趋势意味着"这个引擎支持什么协议"正在从一个能区分引擎的信号，变成一个几乎所有候选都满足的准入门槛——`00-总览与阅读地图.md` §4 已经指出"OpenAI 协议是事实标准"这句话正在被改写成"OpenAI + Anthropic 双标准"，本篇在 12 个引擎的尺度上重新核实了一遍这条判断，结论一致。这正是本篇选"解什么问题 × 技术路线"这两个内部维度、而不是"支持什么外部协议"来画谱系图的原因之一：协议层的差异化正在被时间抹平，真正还留着区分度的是本篇 `## 3` 定义的这两个维度。

值得补一句的是，"10 家都实现了"这句话本身也不能读成"这 10 家的协议层因此变得可以互换"——`## 6.5` 这张表只回答"有没有这个端点"，回答不了"这个端点接受的字段范围一不一样"。`00-总览与阅读地图.md` §4 已经查实过一个具体例子：vLLM 与 SGLang 的 `ChatCompletionRequest` 都是 68 个字段，命中 OpenAI 官方字段的只有 22 个，三分之二是各家私货——协议表面收敛到"同一个路径都存在"，不等于收敛到"同一个路径接受同一组参数"。Tokasaurus 是这条区分最极端的样本：它有 `/v1/chat/completions`（`## 4.1` 已列入总表），但 `validate_args()` 会主动拒绝 `stream=True`、非默认 `top_p`/`frequency_penalty`/`presence_penalty`/`logit_bias`（`[[10-Tokasaurus]]` `## 5` 决策五）——**同一个路径字符串，背后接受的参数子集可以窄到只服务一种工作负载**，这条边界只有拿着请求体逐字段核对才能看出来，本篇 `## 6.5` 的"有/没有"表格本身也是一种简化，读者不能把它当成"协议完全等价"的证明。

**跨引擎的行数对比本身就是一个反复被推翻的陷阱，本篇也不例外地会犯一次。** `## 4.1` 总表里 Dynamo 总行数 2,220,830，逼近 SGLang（2,317,985），乍看像是"Dynamo 的工程体量和一个完整推理引擎差不多"——但 `[[09-NVIDIA-Dynamo]]` `## 1.2` 已经查实全仓库最大的单一目录是 `container/compliance`（652,930 行，全是许可证合规扫描 SBOM 快照），比排第二的 `lib/llm`（359,818 行）还多出近 30 万行。类似的坑在 Mooncake（`mooncake-store/tests/` 一个目录就有 82,187 行）和 KTransformers（六成行数在 `archive/`，`## 4.1` 已注明）身上都出现过。**读本篇总表的行数列时，"总行数"这一列量级上可以比较，但不能直接读成"工程复杂度"或"团队投入"，具体要读哪一部分被算进去了，请回到对应单篇的 `## 1` 核实。**

**同一个词在不同引擎里被拿来描述完全不同的东西，本篇 `## 6.2` 已经拆过"编译"一词，这里再补一个例子："零校准"。** LMDeploy TurboMind 的 KV cache INT4/INT8 量化是"零校准"（运行时现算 min/max，`[[02-LMDeploy与TurboMind]]` `## 4` ④），这曾经是它相对 vLLM/SGLang 的一条鲜明护城河；但 `[[02-LMDeploy与TurboMind]]` `## 6` 同位对照已经指出，vLLM 这份快照的 `CacheDType` 里也出现了 `int4_per_token_head`/`turboquant_k8v4` 这类选项——**招牌设计不是永久优势，"某一时刻的对比结论"和"这个特性今天还独一无二"是两回事**，本篇 `## 4.1` 总表里任何一条"招牌设计"，都建议按这条纪律去对应单篇的 `## 6` 核实它是否仍然独一无二，而不是当成一次性写死的事实。

**"总行数"这个数字对不同语言的密度不公平，`## 7` 上一条已经讲过"混进无关文件"这类污染，这里补一条更根本的：同样一件事，不同语言写出来的行数天生不在一个量级上。** `[[03-TGI]]` `## 6` 已经查实过一个具体对照：TGI 用 23,443 行 Rust 实现了完整的调度决策（请求排队、token 预算记账、连续批处理选择），vLLM 对应的等价逻辑（`vllm:vllm/v1/core/sched/`）在 `00-总览与阅读地图.md` §4 记录的 `scheduler` 子系统里是 8,424 行 Python——**这不是说 TGI 的调度逻辑比 vLLM 复杂近三倍，两边解决的是同一类问题，只是 Rust 的类型系统/所有权检查/显式错误处理天然比 Python 写得"长"（或者说 Python 的动态类型天然写得"短"）。** 跨语言比较"谁的调度器行数更多"这件事本身没有意义，`## 4.1` 总表刻意不把"行数"和"复杂度"挂钩，只用行数做体量的粗略感知，具体到某个子系统的复杂度对比，要看 `04-横向对比/` 里更细粒度的分析（`[[04-工程规模与代码结构对比]]`），本篇不越界下结论。

**12 个引擎里有 3 个（Dynamo、TensorRT-LLM、LightLLM）是靠 GitHub zipball 取证，不是 `git clone`，这条边界会影响 `## 7` 第一条活跃度表格的可信边界。** `_lab/out/repo_stats.json` 的 `ref.remote` 字段对这三家标注了 `(zipball)`——`[[09-NVIDIA-Dynamo]]` `## 1` 与 `[[04-LightLLM]]` `## 1` 都各自记录过这一点。zipball 抓取拿到的 `commit_date` 仍然是这个具体 commit 的真实提交日期（来自 GitHub API 元数据，不是伪造的），但**本地没有完整 git 历史**——如果需要核实"这个 commit 之前的十次提交都改了什么"这类问题，zipball 来源的三家做不到，只有走 `git clone` 的其余九家可以。`## 7` 第一条活跃度表格里的日期数字本身是可信的，但"这个项目最近的开发节奏是加速还是放缓"这类需要看多个历史提交对比的问题，本篇没有能力回答，也没有在正文里假装回答过。

## 8. 可改进点

以下均标注为**本库推断**，是写这篇收束时观察到、但超出了本篇篇幅范围的方向：

1. **血缘证据的取证方式目前完全依赖人工 grep 注释和同名标识符，没有更系统化的工具支持。** `## 2` 列出的证据链里，唯一一条"确凿"证据（LMDeploy 的 `# modify from` 注释）能被找到纯属运气好——这个项目恰好在文件头留了credit。如果一个团队照抄了实现但没写注释，本篇现有的取证方法完全找不到。一个可行的改进方向是给 `_lab/` 加一个"跨引擎 API 签名相似度"或"标识符命名相似度"的比对脚本，把"值得人工核实的候选血缘对"筛出来，而不是依赖偶然发现。
2. **两维分类矩阵目前是静态的，`## 6.4` 已经指出 KTransformers 半年内坐标发生过迁移，但本篇没有机制去跟踪这种漂移。** 一个可行的方向是给 `_lab/out/` 加一份"分类坐标"的结构化记录（比如 `taxonomy.json`），每次重新 clone 时对比上一次记录，自动标出哪些引擎的技术路线/问题族坐标可能变了，而不是要等人工重读全篇才能发现。
3. **API 协议覆盖表（`## 6.5`）目前是本篇手工从十篇单篇里摘抄整理的，容易漏项或过时。** `_lab/api_surface.py` 已经能 AST 抽取路由，但目前没有一个跨引擎汇总"哪些引擎支持哪些协议方言"的产物（`out/api_surface.json` 是逐引擎独立的）。一个 `compare.py` 式的跨引擎协议覆盖矩阵，能让 `## 6.5` 这张表下次不用手工核对十篇原文就能重新生成。
4. **本篇的两维分类法本身可能需要第三维才能刻画演化型项目。** `## 6.4` 已经指出 KTransformers 从"一体化框架"演化到"算子库+fork"，这种"治理模式/演化阶段"（公司主导独立维护 vs 依赖社区 fork vs 研究组维护）目前完全没有被本篇两个维度捕捉到——这条留给以后有余力时再论证是否值得加成第三维，还是应该单独开一节讨论，本篇不下定论。
5. **`## 7` 指出的"跨语言行数不可比"这条纪律，目前只是正文里的一句提醒，没有变成 `_lab/` 里的任何工具约束。** 一个可行的方向是给 `_lab/repo_stats.py` 的输出加一个"按语言分别统计的调度/前缀缓存子系统行数"字段（而不是只给一个跨语言合并的总数），这样下次做类似 TGI vs vLLM 调度器行数对比时，能直接从 `out/repo_stats.json` 里读到分语言的数字，不用像本篇这样手工去两篇原文里各摘一个数字再拼起来。
