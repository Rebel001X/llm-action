**一、原始候选池的来源清单**（`## 4` 第 1 步的输入）：

```
33 篇正文各自的 ## 8 小节（01-vLLM 12篇 + 02-SGLang 11篇 + 03-其他引擎 11篇）
+ 05-改进机会/01-vLLM可改进点.md 的 ## 8（17条，六字段模板）

+ _lab/out/improve.json 的 summary/god_files/hotspots_*/samples* 字段（聚合数字，用于"不建议改"第1条的证据）
```

本篇独立统计：33 篇 `## 8` 小节合计给出约 90-100 条原始候选（每篇平均 3-6 条），这是本篇筛选的起点规模；`03-其他引擎/11-开源推理引擎谱系图.md` 的 `## 8` 全部指向"本库自己工具链该怎么改进"，不含可以直接提给某个引擎的候选，本篇不从这一篇取材。

**二、`## 8` 每条改进点的记录格式**（任务规定的七字段模板）：

```
### [A/B/C-N] <一句话标题> · <引擎>
- 改哪里          <引擎:文件:行，可多条>
- 现状            <事实，带证据>
- 改成什么         <具体行为>
- 怎么验证         <CPU 可验证的写清楚，需要 GPU 的明说>
- 规模估计         <行数 + 文件数>

```

这七个字段和 `05-改进机会/02-SGLang可改进点` 用的六字段模板（现状/问题/证据等级/改进方向/代价与反驳/难度）不同——本篇的模板由任务本身指定，更偏向"能不能直接照着开工"而不是"这个问题严重不严重"，这个差异反映了本篇和 `05-02` 的定位不同：`05-02` 是"深入分析一个引擎的问题全景"，本篇是"从全部问题里筛出能直接动手的子集"。

**三、A/B/C 分档的准入标准**（`## 8` 开头会重复一遍，这里先给出结构）：

```
C档：架构级                             →  写清楚为什么值得、为什么上游可能不接
```

## 4. 主流程走读

本篇的写作过程是一条五步过滤流水线：

1. **收集全部候选**——逐篇打开 33 篇正文的 `## 8` 小节（方法见 `## 3` 一），摘出每一条带 `file:line` 或至少带明确函数名的具体断言，累计约 90-100 条原始候选；同时读 `05-改进机会/01-vLLM可改进点.md`（17 条）、`05-改进机会/02-SGLang可改进点.md`（12 条）已经过一轮六字段模板整理的候选，以及 `05-改进机会/03-跨引擎共性缺口.md` 的 6 条共性缺口（按 `## 1` 的分工边界，本篇不照搬 `03` 的抽象缺口本身，只把它作为交叉印证信号）。
2. **应用准入门槛淘汰**——任务给的判准是"一条建议如果不能让人读完就打开编辑器，它就不该在这份清单里"，据此淘汰了相当一部分候选：纯粹的"观察"（比如"这个类的设计不够优雅"这类没有具体改动方向的评论）、需要真实压测数据才能判断值不值得做的方向（比如 HiCache `write_through_threshold` 的自适应化，原始材料自己也标注为"长期方向而非可落地 PR"）、以及本库自己工具链（`_lab/`）的改进（比如 `_lab/api_surface.py` 该怎么改进抽取逻辑）——后者不是"给上游引擎提 PR"的候选，不属于本篇范围。
3. **独立复核每一条幸存候选**——对通过准入门槛的条目，逐条重新 `grep -n` 定位到当前 `_src` 快照，不信任任何一篇兄弟文章里已经写好的行号（哪怕是同一个库内的姊妹篇）。这一步筛出了两处需要更正的地方（详见 `## 7`）：`test_server_args_namespaces.py` 的"440 下界"实际上是冗余断言而非安全网缺口；`_disable_tc_piecewise_cudagraph_if_incompatible` 的规则数经独立计数是约 20 条而非 18 条。
4. **分档**——按 `## 3` 三给出的标准，判断每条候选属于 A/B/C：核心判断依据是"改动本身要不要先经过一轮社区讨论"（接口/默认值变更 → 至少 B 档）、"改动范围是不是局限在一两个文件、一两百行内"（超出 → 至少 B 档，通常 C 档）。这一步也淘汰了少数看着诱人但证据不够扎实的候选，移入 `## 8` "不建议改"小节而不是直接丢弃——这一步是为了让"过滤"这个动作本身可见，不让读者以为这些候选被漏掉了。
5. **补齐 PR 前置清单**——本库在写作过程中反复确认自己**没有**检索任何一个引擎的 open issue/PR 列表（遵守 `_PLAN.md` 红线 6），这个事实本身被写进 `## 8` "提 PR 之前该做的事"清单第一条，而不是藏在免责声明里。

## 5. 设计决策与代价

本篇的排序不是随手按发现顺序排的，三条判据各自要回答"为什么这样排 / 不这样会怎样 / 什么时候这个排序失效"。

**判据一：以"投入产出比"（诊断成本 vs 修复成本）作为主轴，决定 A/B/C 归档**

- 为什么这样排：一条建议的价值不在于"发现了什么"，而在于"读完这条建议的人，愿不愿意现在就打开编辑器"——诊断成本低（改动范围明确、不涉及接口/默认值）、验证成本低（不需要 GPU、能写单测）的条目排进最容易执行的 A 档，让贡献者能立刻上手；需要先讨论接口/默认值的排 B 档；需要架构级改动或治理决策的排 C 档。
- 不这样排会怎样：如果按"发现时的技术含金量"排序（比如把最有意思的架构洞察放最前面），清单会变成一份"技术观察报告"而不是"贡献清单"——本篇任务判准是"一条建议如果不能让人读完就打开编辑器，它就不该在这份清单里"，技术含金量高但需要先讨论、先设计的条目放在最前面，反而会让读者以为"这些都是能立刻动手的"，造成错误预期。
- 什么时候这个排序失效：如果读者的目标不是"找一个能立刻上手的 PR"，而是"了解这个引擎架构上最深的问题在哪"，那么 A/B/C 的顺序应该反过来看——C 档虽然排在最后，但恰恰是最值得读的架构级讨论，读者不应该因为它排在清单末尾就认为它不重要。

**判据二：是否有交叉印证（同一发现在两篇独立文章里各自出现）作为置信度加权，同档内优先靠前**

- 为什么这样排：比如 A-6（`event_loop_normal`/`event_loop_overlap` 重复代码）在 `02-SGLang-Scheduler事件循环`（单篇正文的 `## 8`）和 `05-改进机会/02-SGLang可改进点`（独立的收束文章）两处被独立指出，说明这不是某一次写作时的一次性观察，而是两个不同写作时间点、读同一段代码都得出的一致结论，误判概率更低；只出现过一次的发现（比如很多 C 档条目）本篇无法用这种方式交叉验证，置信度天然更低。
- 不这样排会怎样：如果不考虑交叉印证，单纯按"文字描述听起来多有说服力"排序，容易把一次性的、可能带有个人解读色彩的观察和反复验证过的结构性问题混在同一优先级，读者没有办法区分"这个结论有多可信"。
- 什么时候这个排序失效：交叉印证只能证明"两次独立观察一致"，不能证明"这个问题真的重要"——本库 12 篇 vLLM 正文和 11 篇 SGLang 正文都是同一批写作方法论下产出的，如果某个方法论偏差（比如某类静默异常被系统性地过度解读）贯穿了所有文章，交叉印证只会让这个系统性偏差看起来更可信，不会纠正它；这也是为什么 `## 7` 要专门去做独立的 grep 复核，而不是只统计"被提到几次"。

**判据三：能否不依赖 GPU 独立验证，作为同档内的执行优先级**

- 为什么这样排：本库没有 GPU 环境（`_PLAN.md` 红线 4），这条清单的第一批读者大概率也不是每个人都随时有 GPU 可用——能用纯 CPU 单测/静态检查验证收益的条目（比如 A 档几乎全部），贡献者可以在提交前就自己确认改动有效，不需要等 CI 跑 GPU 测试或者求助于有硬件的同事；C-1 这类"收益依赖真实前向执行环境"的条目，连贡献者自己都没办法在本地独立确认"这样改真的更快"，这类条目的实际推进速度会天然更慢。
- 不这样排会怎样：如果不考虑验证门槛，把"改动小但验证需要 GPU"的条目和"改动小且 CPU 就能验证"的条目混在同一优先级，会让读者高估自己独立完成这条 PR 全流程（包括验证）的能力——尤其对 `## 8` 前言里说的"首次贡献友好"这个定位，验证门槛本身就是友好度的一部分，不只是改动行数。
- 什么时候这个排序失效：如果读者本身就是有 GPU 资源、且长期跟进某个特定子系统（比如 CUDA Graph/投机解码）的核心贡献者，"要不要 GPU"这个门槛对他们几乎不构成障碍，这时候更应该按"技术价值"或判据一/二排序，而不是被这条门槛判据拖累优先级。

## 6. 同位对照

同一类"静默决策该不该打日志"的问题，在不同引擎、甚至同一个引擎内部的不同代码路径上，成熟度并不一致：

| 引擎 | 静默覆盖/降级场景 | 是否已有可见日志 | 本篇涉及条目 |
|---|---|---|---|
| vLLM | `enforce_eager` 覆盖 `compilation_config` | 有（`warning_once`） | 反例参照，不在清单里 |
| vLLM | `SamplingParams` 贪心覆盖 `top_p`/`top_k`/`min_p` | 无 | A-2 |
| vLLM | 鉴权白名单外的路径不设防 | 仅文档说明（`vllm:docs/usage/security.md:231`），代码层面无运行时提示 | B-1 |
| SGLang | `_handle_attention_backend_compatibility` 关闭 CUDA Graph | 有（`logger.warning`） | 反例参照 |
| SGLang | `_disable_tc_piecewise_cudagraph_if_incompatible` 约 20 条规则关闭 CUDA Graph | 无 | A-3 |
| SGLang | llguidance 结构标签校验用 `assert` | 无，且 `-O` 下可被跳过 | A-4 |

| llama.cpp | API key 比较非常量时间 | 不是日志问题，是实现方式问题 | A-9 |

三点读表格要注意的地方：

1. 同一类"静默决策该不该打日志"的问题，在不同引擎、甚至同一个引擎内部的不同代码路径，成熟度并不一致——vLLM 自己就同时有"`enforce_eager` 已经打了日志"和"`SamplingParams` 完全没打日志"两种状态并存，说明这不是团队整体风格问题，而是每条具体路径各自演化出来的历史状态。
2. 已经有日志的场景不代表就此完美——LMDeploy 的一行 warning 缺乏原因分类，llama.cpp 的 `SRV_WRN` 级别偏低、且没有进入 `/props` 这类运行时自省接口，这两条本篇没有单独收录为条目，因为姊妹篇的 `## 8` 已经把它们记录过，本篇 `## 2` 代码地图已经引用，不重复展开成独立条目。
3. "静默覆盖该打日志"这类问题之所以能在完全不相关的引擎、完全不相关的子系统里反复出现，说明它不是某个团队的疏忽，而是"配置系统天然倾向于把大量分支判断埋在构造函数/初始化路径里，而日志基础设施默认不会主动提示决策过程"这个更结构性的模式——这也是 `## 0` 结论先行里点出的"整个研究库最高杠杆的一类修复"的证据来源。

#### [B-6] PRIORITY 抢占受害者选择改堆结构 · vLLM

- **改哪里**：`vllm:vllm/v1/core/sched/scheduler.py:652-655`（`max(self.running, key=lambda r: (r.priority, r.arrival_time))`）
- **现状**：每次触发 PRIORITY 模式抢占，都要对 `self.running` 做一次 O(n) 线性扫描找出优先级最低/到达最晚的受害者；若一步内连续触发多次抢占（比如新来一个超大 prompt 一次挤出好几个低优先级请求），退化成 O(n²)。默认 `max_num_seqs=128`（`vllm:vllm/config/scheduler.py:44`）下影响有限，但高并发 + 频繁抢占场景下值得关注。
- **改成什么**：把 `self.running` 的抢占候选维护成一个按 `(priority, arrival_time)` 排序的小顶堆（或者一个独立的优先级索引结构），单次选择降到 O(log n)；代价是当前 RUNNING 循环依赖"按下标顺序扫描 `self.running`"这个隐性顺序语义，引入堆结构后需要重新审视所有依赖这个顺序的地方。
- **怎么验证**：纯 CPU——构造一个大量请求 + 频繁触发 PRIORITY 抢占的模拟调度场景（不需要真实模型前向，`Scheduler` 的准入/抢占逻辑本身是纯 Python 状态机，可以用 mock 的 `Request` 对象跑），断言堆实现和线性扫描在相同输入序列下选出完全相同的受害者，且时间复杂度按预期下降（可以用请求数递增来观察调用次数量级）。
- **规模估计**：核心改动集中在 1 个文件，但堆结构需要在请求状态变化的多个位置（新增/移除/优先级变化）同步维护，预计涉及 `scheduler.py` 里 4-6 处调用点、净改动 80-120 行。
- **上游可能怎么反驳**：默认部署下 `self.running` 规模就是 `max_num_seqs`（通常几十到几百），O(n) 在这个规模下的实际耗时可能远小于一次前向步的耗时，优化收益在大多数部署里不可测量；引入堆结构增加的代码复杂度（需要在多处状态变化点保持堆的一致性，这正是 `03-vLLM-调度器解剖` 已经警告过的"两处必须手动同步"的风险源）可能得不偿失。
- **前置**：需要先有真实压测数据证明 PRIORITY 模式 + 高并发 + 频繁抢占这个组合场景在实际部署中确实存在且量级足够大（本库无 GPU，未产出这类数据）——这也是它被放进 B 档而不是更高位置的原因。

- **上游可能怎么反驳**：现有的生产集成经过了实际生产环境的打磨，`BaseWorkerHandler` 即使"历史遗留"也是经过验证、稳定工作的代码；强行统一到 `LLMEngine` 契约的收益（代码整洁度、新集成的一致性）可能不足以覆盖"重构正在生产使用的关键路径"带来的回归风险——这类"能不能工作 vs 能不能维护得更整洁"的取舍，上游维护者大概率会选择"能工作的不要动"，除非有具体的维护成本痛点能证明现状已经造成了实际损失。
- **前置**：需要先确认 SGLang/TRT-LLM 的 Dynamo 集成具体走的是 `LLMEngine` 契约还是各自的独立 handler（本篇原始材料只明确提到 vLLM 走 `BaseWorkerHandler`，未逐一核实另外两个引擎的现状，未查证）。

### 我不会去提的

看着能改、但本库判断不该独立开 PR 的条目——这一节体现的是判断力，比清单本身更重要。

**1. vLLM 823 处 `NotImplementedError`——不该被当作"未完成清单"批量处理。** 机械识别（形式化 `ABC`/`Protocol` 基类 + `@abstractmethod` 装饰器 + "必须被子类实现"类消息，见 `_lab/out/improve.json` 的 `engines.vllm.summary.not_impl=823`）能确认至少 40% 是接口占位；`05-改进机会/01-vLLM可改进点.md` `## 0` 记录的人工抽样复核结果是真实占位比例约 45%-50%。把这个 823 当"vLLM 里有 823 处没写完的代码"来读、进而想批量提 PR"清理"是对这个数字的误读——大多数是设计上刻意要求子类实现的抽象方法占位符，删除或"补全"反而会破坏这类接口契约。这条不是"这里能改"的候选，而是提醒读者不要被这类大数字诱导写出无意义的 PR。

**2. 探测型代码里的 `except ImportError`/`except Exception: pass`——不该无差别加日志/改成显式抛错。** 用两个跨引擎例子：`vllm:vllm/distributed/kv_transfer/kv_connector/v1/hf3fs/hf3fs_connector.py:82`（可选依赖 `hf3fs_fuse` 导入失败，`HF3FS_AVAILABLE = False`，这是合法的"这个能力在当前环境下可能存在也可能不存在"语义）和 `sglang:python/sglang/kernels/ops/attention/flash_attention_v4.py:15-22`（`flash_attn.cute` 可选导入失败，记录 `_flash_attn_import_error` 供后续按需报错，同样是合法探测）。给每一处都加日志会在没装可选依赖的正常环境里刷出大量无意义警告，把真正的问题淹没在噪音里——顺带一提，同一个 `hf3fs_connector.py` 文件里另一处 `except Exception as e`（`:347-351`）实际通过 `_fail_task`（`:422-427`）把错误信息传给了 `logger.error`，机器信号会把这种"间接记录"误标成"完全没记录"，写正文前必须去看它调用的辅助函数，不能只信静态扫描的标签本身。

**3. TensorRT-LLM `_to_pybind()` 命名整改——口味之争，不值得单独开 PR。** `01-TensorRT-LLM` `## 8` 已经指出这个方法名容易让人联想到已移除的旧后端，改成更中性的名字（比如 `_to_cpp_enum()`）是合理的可读性改进——但这是纯命名问题，不涉及行为，TRT-LLM 自己的 `AGENTS.md` 明确写了"No low-value busywork PRs"这条原则，单独为改名开 PR 大概率会被要求"搭车"到别的改动里，不值得作为独立条目出现在这份清单的可执行档位。

**4. SGLang `server_args.py` 万行集中配置文件——不该被强行拆分。** `sglang:python/sglang/srt/server_args.py` 全文件 10,142 行（本篇独立核实，`wc -l`）——虽然远超 SGLang 自己 `.claude/rules/general-code-style.md` 写的"~2k LOC"上限五倍多，但 `_run_resolution_pipeline` 有一份写在 docstring 里的排序原则，是有纪律的分发器模式；把 476 个字段集中在一处让"这个旋钮默认值是什么"的排查只需要 `grep` 一个文件。B-2 已经指出真正值得做的是局部收敛（白名单收敛成注册表视图），而不是把这个文件强行拆成十个互相 import 的小文件——那样复杂度未必真的下降，只是换了个地方存在。

**5. llama.cpp `--tools-runtime` 默认不隔离（`llama.cpp:tools/server/README.md:201`：默认值 `none`，即"use host environment"）——不该由本库主动提议反转默认值。** 这条初看和 B-1（vLLM 鉴权默认反转）是同一类问题：`exec_shell_command` 这类高风险工具默认在宿主机本机权限下跑，要靠用户自己读文档、自己想起来去配 `docker:<image>` 才会走容器隔离。但和 B-1 不同的是，本篇判断这条**不该**收进 A/B/C 任何一档去提议"改默认值"——原因有二：(a) 默认值改变会破坏所有现有依赖 host 环境跑工具的部署，而 `--tools-runtime` 本身已经明确标注为 `experimental`，说明上游本来就在观察这个特性该怎么定型，此时外部贡献者去动默认值容易撞上正在进行中的设计迭代；(b) 本库没有找到任何证据表明当前默认值是"疏忽"而非"刻意先给一个能跑起来的基线，再让用户按需收紧"的常见开源项目节奏。真正站得住的改动是**提升警告可见度**（这条已经在 `03-其他引擎/05-llama.cpp-server` 的兄弟篇 `## 8` 里给出过——只在检测到高风险工具且未显式配置 `--tools-runtime` 时提升日志级别），本篇不把"反转默认值"本身列为候选，这是本条和 B-1 判断不同的分界线：B-1 有上游文档明确写着"这是已知限制"作为佐证，这条没有等价的佐证，本篇的证据不足以支撑更激进的动作。

### 提 PR 之前该做的事

**本库没有核实上游是否已有相关 issue/PR**——`## 0` 已经声明过这一点，这里落成一份操作清单，第一条就是补这个缺口：

1. **先搜索是否已有重复 issue/PR**——用症状描述 + 涉及文件名在 GitHub 搜索框里搜一遍，如果搜到已关闭的 PR，先读讨论内容理解被拒的真实理由，不要原样重提。本篇全部 20 条改进点都没有做这一步核实，这是本篇留给读者的第一份作业。
2. **读 CONTRIBUTING.md / AGENTS.md / 项目自己的代码风格规范**——不同项目对 commit 信息格式、DCO 签名、测试覆盖率要求不同（比如 SGLang 有 `.claude/rules/comment-style.md` 这类细粒度约定，TensorRT-LLM 有 `AGENTS.md`）；直接套用一个模板大概率会踩到某个项目特有的要求。
3. **跑一遍项目自己的测试套件**（至少跑改动涉及的那个子目录的单测），确认改动没有引入回归——不要只靠肉眼读代码就相信正确性，尤其是 A 档看着"显然安全"的改动（比如 A-5 删除冗余断言）也要实际跑一次测试确认其余断言依然完整覆盖契约。
4. **小改也要在 PR 描述里给复现步骤**——"加了个日志"这种描述对 review 人没有帮助，要写清楚"怎么触发这条静默路径 / 加了日志之后应该看到什么输出"，让 review 人不需要自己搭环境复现就能判断改动是否达到目的。
5. **一个 PR 只做一件事**——遇到"顺手也把这里的命名改了"的冲动要忍住，开新 PR；混在一起的 PR 更难 review，也更容易因为其中一部分有争议而拖累整个 PR 的合并。
6. **B/C 档在动手写完整 patch 之前，先开一个轻量 discussion/issue 说明方向**——尤其是涉及默认值或接口变更的条目（比如 B-1 的鉴权默认模型反转），闭门造出一个完整 PR 再等维护者反馈方向不对，是对双方时间的浪费。
7. **检查改动涉及的文件最近有没有其它 PR 在改**（`git log --oneline -- <file>` 看最近若干次提交），避免和进行中的重构或修复冲突——A-6 已经明确点出过这个风险。
8. **日志级别要符合项目现有约定**——不要自己发明新的日志级别或格式，先看同文件/同模块里已有的日志调用用的是 `info`/`warning`/`debug` 哪一级，跟着用同一套习惯（A-2/A-3 两条都刻意在字段里讨论过该用哪个级别）。
