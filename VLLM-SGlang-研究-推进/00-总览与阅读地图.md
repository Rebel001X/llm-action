# 00 · 总览与阅读地图

> 这一篇是我亲笔写的，不是 agent 代写的。它负责三件事：**说清这个库的立场**、
> **给一张能直接照着走的阅读路线**、**把已经查实的硬结论摆在最前面，省得你翻 40 篇**。

## 1. 这个库的立场

市面上讲推理引擎的材料，绝大多数停在两种形态：

- **参数手册**：把 `--max-num-seqs` 是什么抄一遍，不告诉你调它会牺牲什么；
- **架构图 + 形容词**：一张方框图，配上"高吞吐""零拷贝""业界领先"。

两种都有一个共同毛病：**没法证伪**。你读完之后并不知道自己该信几分，
也没法验证作者到底有没有打开过那个文件。

所以这个库只做一件事：**把每一句关于代码的话，钉到一行真实源码上。**

具体落成三条机制：

1. **行号引用**。正文里凡是讲实现，都写成下面这个形状（跨引擎时前面再加 `sglang:` 之类的前缀）：

   ```
   `vllm/v1/core/sched/scheduler.py:123`
   ```

2. **`_verify.py` 逐条核对**。它会真的打开那个文件、数到那一行，越界就 FAIL。
   全库目前有**四千多条**这样的引用，每一条都被核过 —— 具体数字跑一次 `python _verify.py`
   就会打在第一行（这里不写死，免得它随续写过期）。
3. **取证基准头**。每篇开头写死 `` `<engine>` @ `<sha>` ``，与 `_lab` 记录的 clone sha
   不一致直接 FAIL —— 防止"拿 A 版本的代码讲 B 版本的行号"。

再加一条内容上的红线：**每个"它很好"后面必须跟"什么时候这是错的"**。
只夸不说代价的段落一律回炉。

还有一条能力边界，写在最前面免得你误会：**本机没有 GPU，本库不产出任何实测吞吐/延迟数字。**
凡是涉及性能的量化，要么是带公式和假设的解析计算（会明确标注），
要么是引上游文档并注明出处文件与完整口径（硬件/模型/长度分布/并发）。
给不全口径的数字，本库宁可不写。

## 4. 已经查实的硬结论（不用读完全库也能带走）

下面每条都能在正文里找到带行号的出处。**这些是本库目前最反直觉的部分。**

**关于规模的直觉是反的 —— 但"反"到什么程度，取决于你怎么划边界。**
按整仓算：SGLang 2,317,985 行 / Python 产品码 1,254,674，**都大于** vLLM 的 1,914,984 / 932,277。
"SGLang 是那个更轻的"这个印象，在整仓口径上不成立。

**但把 SGLang 的 `python/sglang`（1,543,126 行）拆到三级目录看，结论会翻一次**：
它把自带 kernel 库（`kernels/`）、多模态生成运行时（`multimodal_gen/`）和
注册式测试（`test/registered/`）都放在同一个包里；真正对标 vLLM 的服务引擎核心 `srt/`
只有 763,754 行 —— **扣掉那些之后，SGLang 的引擎核心反而比 vLLM 小约 17%**。
（含 kernel 库的口径下 SGLang 仍大约 15%。）
所以正确说法不是"谁更大"，而是**"你要不要把人家自带的算子仓库算进服务引擎"** ——
这个边界一换，排名就换。详见 [[04-工程规模与代码结构对比]]。

顺带：两家都已经不是纯 Python 项目了 —— vLLM 有 109,867 行 Rust，SGLang 有 156,078 行。

**"OpenAI 兼容"是个需要逐字段核的说法。**
vLLM 与 SGLang 的 `ChatCompletionRequest` 都是 68 个字段，其中命中 OpenAI 官方字段的
只有 22 个 —— 也就是说**三分之二的字段是各家私货**，两家各自缺 8 个 OpenAI 标准字段。
拿"兼容 OpenAI"当无损替换的前提，会在这 46 个私有字段和 8 个缺口上出事。

**两家都在悄悄做 Anthropic 兼容。**
vLLM 和 SGLang 都实现了 `/v1/messages` 与 `/v1/messages/count_tokens`（Anthropic Messages API），
vLLM 还多一层 Cohere（`/cohere/v2/chat`）。llama.cpp 与 Dynamo 也有 `/v1/messages`。
"OpenAI 协议是事实标准"这句话正在被改写成"OpenAI + Anthropic 双标准"。

**旋钮数量差了一倍，但生成方式更值得看。**
SGLang 的 `ServerArgs` 有 **476 个字段**，而 `server_args.py` 里只有 **29 处 `add_argument(`** ——
CLI 是从 dataclass 自动生成的。vLLM 的 `EngineArgs` 是 **233 个字段 / 228 处显式 `add_argument`**。
自动生成让加旋钮的边际成本趋近于零，这既是 476 的成因，也是它的代价。

**"默认值不同"这件事，我自己的工具先给出了假答案。**
`compare.py` 最初报"41 个同名旋钮默认值不同"。逐条看才发现绝大多数是假的：
vLLM 的 `EngineArgs` 把默认值转交给子配置（写成 `ModelConfig.dtype`），
拿这种引用去和 SGLang 的字面量比，**必然**判成"不同"。
加了 `classify_default()` 只比字面量之后，真正可比且不同的只剩 **4 个**
（`block_size` / `enable_lora` / `enable_metrics` / `enable_prefix_caching`），37 个被判为不可比。
这条留在这里当纪念：**跨项目对比里，最容易造假数据的不是别人，是你自己的脚本。**

**vLLM 的 CUDA 路径上已经没有自己的 paged attention kernel 了。**
那个让 vLLM 出名的手写 `paged_attention_v1/v2`，在这个快照的 NVIDIA 路径上已经不在 ——
`csrc/attention/` 目录现在只剩 6 个 dtype 头文件（`attention_dtypes.h`、`dtype_fp8.cuh` 等），
kernel 本体没了，注意力全部外包给 FlashAttention / FlashInfer / Triton。
**但这句话有个必须说清的边界（我自己 grep 复核出来的）**：这个名字并没有从仓库里消失，
它还活在 ROCm 路径上 —— `csrc/rocm/attention.cu`、`csrc/rocm/ops.h`、`csrc/rocm/torch_bindings.cpp`，
以及 `vllm:vllm/v1/attention/backends/rocm_aiter_fa.py:1362` 调用的 `torch.ops.aiter.paged_attention_v1`
（那是 AMD AITER 库提供的算子，不是 vLLM 自己的）。
所以准确说法是**"NVIDIA 路径上退役了"，不是"整个项目删掉了"**。
另外 `VLLM_ATTENTION_BACKEND` 环境变量已全仓零命中，改成 `--attention-backend`。

**前缀缓存的驱逐不是真 LRU。**
vLLM 没有维护时间戳，而是靠**调用顺序**近似最近性：`BlockPool.free_blocks` 把释放的块分两路，
没缓存过的走 LIFO（为 GPU 局部性），带 hash 的走 FIFO（为缓存寿命）；
释放一个请求时还会先把它的块列表**倒序**，让尾部（最不可能被共享的）块排在前面等着被驱逐。

**SGLang 那个教科书级的 `RadixCache` 不是默认生产路径。**
`radix_cache.py` 里 863 行的 `RadixCache` 现在主要是 `HiRadixCache` / `PureSWARadixCache` 的父类，
工厂函数兜底选中的是另一个 2,894 行的 `UnifiedRadixCache`。照着教程读源码容易读错文件。

**CUDA Graph 掉回 eager 是完全静默的。**
`vllm/compilation/cuda_graph.py` 在 fallback 时直接转发给未编译的可调用对象，一句日志都不打。
cascade attention 和 encoder-decoder 的首步都会触发它。想看见，只能开 `--cudagraph-metrics`（默认关）。

**抢占选的是最新的请求，不是最老的。**
vLLM 在 FCFS 下的抢占受害者选择是 `self.running.pop()` —— LIFO。
直觉上"先来后到，该保老的"，代码上确实也是保老的：**踢掉最新的才等于保护最老的。**

**TensorRT-LLM 已经把 TensorRT 引擎后端整个删了 —— "编译式 vs 解释式"这条分界线塌了。**
`docs/source/legacy/tensorrt-backend-removal.md` 开篇原文就是
"**Breaking change.** The TensorRT engine backend has been removed. PyTorch is now
the sole execution backend for TensorRT LLM"，`trtllm-build` 也从
`tensorrt_llm/commands/` 里消失了（现在只剩 `bench` / `eval` / `serve` / `utils`）。
我自己 `ls` 与 `head` 复核过这两条。
更反讽的是：TRT-LLM 的 PyTorch 后端默认 **eager**（`torch_compile_config=None`），
而 vLLM 的 V1 引擎默认走 `torch.compile`。
**"那个以编译出名的引擎现在默认不编译，那个以运行时出名的引擎默认编译"** ——
沿用多年的标签这次是反的。TRT-LLM 还保留的编译式部分是**调度器**（C++ nanobind 绑定的
`CapacityScheduler`），不是模型图。

**SGLang 的招牌优化 jump-forward decoding，在这个快照里是死代码。**
四个语法后端（xgrammar / llguidance / outlines / reasoner 包装）都完整实现了
`try_jump_forward` / `jump_forward_str_state` / `jump_and_retokenize`，
连 tokenizer 边界的回滚重分词逻辑都写了 —— 但**调度器里一个调用点都没有**。
我自己 grep 复核过：全仓唯一的调用是
`sglang:python/sglang/srt/constrained/reasoner_grammar_backend.py:228` 的委托转发。
vLLM 那边则是从来就没有这套接口。所以**两家目前都不在生产路径上执行 jump-forward**。
开关的"存在"与"生效"之间，没有任何东西在强制校验。

**vLLM 的 `--api-key` 只保护一部分路径。**
鉴权只覆盖 `/v1`、`/v2`、`/inference`、`/cohere` 四个前缀，
于是 `/invocations`、`/sleep`、`/collective_rpc`、`/scale_elastic_ep` 这些端点
**即便配了 key 也完全无鉴权** —— 而 `/collective_rpc` 能在 worker 上执行任意方法。
这一条上游自己是知道的，`docs/usage/security.md` 里有详细说明，
**所以它不是"vLLM 没意识到"，而是"部署的人必须自己在网络层兜住"**。

**「块哈希表 vs 基数树」这个框架，在命中率上几乎不成立（有实验支撑）。**
[[01-前缀缓存差分实验-亲笔]] 把两家策略如实重实现后喂同一批 trace：
共享前缀充裕时两家命中率差 **0.00–0.01 个百分点**；唯一可测的匹配差异（0.91pp）
只在共享前缀长度不是 block_size 整数倍时出现，而 vLLM 把 hash 单元调到 1 就能**完全抹平**
（代价是查表次数 +33%）。容量吃紧时的差异**全部来自驱逐策略**，匹配贡献 0.00pp ——
而且方向和直觉相反：最紧容量下 **vLLM 反而略胜 0.56pp**，
因为它的「倒序释放」编码了一条朴素 LRU 没有的先验。
**这一条我第一版做错过**：把 vLLM 误建模成 FIFO，凭空造出「SGLang 领先 8.72pp」，
建模误差比我原本想报告的"发现"还大。

**LPM「提升吞吐」这句话缺了前提（也有实验支撑）。**
[[04-调度公平性差分实验-亲笔]] 测出：**缓存充裕时 LPM 相对 FCFS 一分命中率都不多赚**
（0.3750 vs 0.3750），只是把公平差从 −8.5 推到 165.6；
只有缓存吃紧（容量 512）时才 +13.87pp。
更意外的是：给它加防饥饿几乎免费（公平差 −57%，命中率 −1.2% 相对），
而**这份公平性收益主要不来自 age credit 公式，来自它制造的「并列」让到达序 tiebreak 生效** ——
T 不变、只换 tiebreak，收益就消失大半。

**"静默吞异常"的密度可以横向比 —— 但这个指标我改了三版才敢用。**
`_lab/improve.py` 统计"except 之后既不重抛也不记日志"的处数。
第一版按**全仓**密度排名，结果热点前几名全是 `collect_env.py` / `check_env.py` /
`platforms/cuda.py` 这类**探测型**文件 —— 那里吞异常本来就正当，排名被它们主导，毫无意义。
第二版按文件角色过滤后，剩下的又大半是 `except ImportError: pass`（处理可选依赖的标准写法）。
第三版才得到能用的口径 —— **热路径**（调度 / KV / 注意力 / 模型执行 / PD 分离 / 投机 / 结构化输出）
每万行热路径代码的处数：

> LMDeploy 1.2 · **vLLM 1.9** · **SGLang 4.9** · TensorRT-LLM 5.7 · LightLLM 8.0 ·
> MLC-LLM 8.6 · KTransformers 9.5 · TGI 11.5 · Mooncake 15.5 · Dynamo 21.8
> （llama.cpp 无热路径 Python 命中；Tokasaurus 为 0）

推理引擎里静默降级比报错危险 —— 用户看不见自己掉进了慢路径或错路径。

**第四版的结论是：连这个口径也别拿来排名。**
写 [[02-SGLang可改进点]] 时我要求 agent 去逐条抽样"SGLang 是 vLLM 2.6 倍"这个差距，
结论是**大部分仍是工具造的**：被判为热路径的命中里有不少是**一次性的导入期探测**，
而且 vLLM 的热路径分母几乎是 SGLang 的两倍宽（分母不同，密度自然不可比）；
真正查出来的诊断缺口只有个位数条。
所以这组数字的正当用法是**当线索去翻代码**，不是当排行榜。
全仓口径与分角色明细都在 `_lab/out/improve.json` 里，可复核。

## 6. 怎么自己验一遍

这个库最该被使用的方式不是"读完信了"，而是**抽查**：

```bash
cd VLLM-SGlang-研究-推进

# 1) 全库体检：取证基准头 + 每条 file:line + 双链 + 占位符
python _verify.py

# 2) 重算所有统计数字（需要先按 _PLAN.md §2 把源码 clone 到 _src/）
cd _lab
python repo_stats.py && python api_surface.py && python struct_map.py
python compare.py && python improve.py

# 3) 工具自身的回归测试（不依赖 _src 也能跑一半）
python -m pytest tests -q
```

随便挑一篇里的任意一条行号引用，打开 `_src/` 下那个文件翻到那一行。
**如果对不上，那就是本库的 bug，不是你的理解问题。**
