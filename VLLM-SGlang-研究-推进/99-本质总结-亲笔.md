# 99 · 本质总结（亲笔）

> 这一篇是我自己写的。前面三十多篇是**解剖**，这一篇是**收束**：
> 读完十二个引擎的源码之后，我认为真正值得记住的是哪几条，以及我在过程中被打脸的地方。
> 每条原理后面都能追回具体篇目；追不回的，我会标「本库推断」。

---

## 一、七条原理

### 原理 1 · 推理引擎的核心矛盾不是"算得快"，是"显存怎么切"

十二个引擎，算子几乎都外包了。vLLM 在这个快照里连自己那个成名的 `paged_attention` CUDA kernel
都从 NVIDIA 路径上退役了（`csrc/attention/` 只剩六个 dtype 头文件），注意力全交给
FlashAttention / FlashInfer / Triton。SGLang 把算子收进 `python/sglang/kernels/`，
但那些也大多是 vendored 或对上游的封装。LightLLM 干脆一个 CUDA 文件都没有，全 Triton。

**算子层正在商品化。** 那各家在拼什么？拼**同一块显存怎么切给同时在跑的几十上百个请求**：
块还是页、定长还是变长、哈希表还是基数树、驱逐按什么序、放不下时踢谁。
`01-vLLM/04`、`02-SGLang/03`、`02-SGLang/04`、`04-横向对比/03` 四篇讲的都是这件事。

推论：**评价一个引擎，先看它的 KV 管理，再看它的调度，最后才看它用了什么 kernel。**

### 原理 2 · 静默降级是这个领域的系统性缺陷

这是全库最强的一条共性，横跨所有引擎：

- vLLM 的 CUDA Graph 掉回 eager 时，`vllm/compilation/cuda_graph.py` 直接转发给未编译的可调用对象，
  **一句日志都不打**；想看见只能开默认关闭的 `--cudagraph-metrics`。
- vLLM 至少七处会**无条件覆盖**用户显式设置的配置（`enforce_eager=True` 清空
  `compilation_config.mode`；`enable_sleep_mode` 强制 `enable_cumem_allocator=True`
  哪怕你显式传了 `False`），而且这几处的日志级别还不一致。
- LMDeploy 的 `TurbomindEngineConfig` 会静默降级引擎选择，只留一条 warning；
  `QuantPolicy.TURBO_QUANT` 两个引擎的配置都收，但 TurboMind 侧**零实现**。
- SGLang 的 jump-forward decoding —— 它 2024 年的招牌优化 —— 四个语法后端全都完整实现了
  `try_jump_forward` / `jump_and_retokenize`，但**调度器里零调用点**（我自己 grep 复核过：
  全仓唯一的调用是 `sglang:python/sglang/srt/constrained/reasoner_grammar_backend.py:228` 的委托）。开关在，功能不在。

**为什么这比报错危险**：报错会被发现、被上报、被修。静默降级只会让你的 p99 悄悄变差，
让你在 benchmark 上得到一个自己都解释不了的数字，然后归因到"玄学"。

**这条的行动出口**：接手任何引擎前，先找它的**降级信号在哪**。
找不到统一信号，就假设你正在跑的路径不是你以为的那条。详见 `05-改进机会/03`。

### 原理 3 · "OpenAI 兼容"是一句需要逐字段核的话

vLLM 与 SGLang 的 `ChatCompletionRequest` 都是 **68 个字段**，
其中命中 OpenAI 官方字段的只有 **22 个** —— **三分之二是各家私货**，
而且两家各自还缺 8 个 OpenAI 标准字段。

所以"把 base_url 一换就能迁移"这个假设，只在你恰好没用到那 46 个私有字段、
也没依赖那 8 个缺口时才成立。更麻烦的是同名不同义。

顺带一个趋势观察（标「本库推断」）：**协议正在从单标准走向双标准。**
vLLM、SGLang、llama.cpp、LMDeploy、Dynamo 都实现了 Anthropic 的 `/v1/messages`，
vLLM 还多一层 Cohere。协议层在变成公共品，差异化被挤到实现层和运维端点上。
详见 `04-横向对比/01`。

### 原理 4 · 旋钮的边际成本决定了旋钮的数量

SGLang 的 `ServerArgs` 有 **476 个字段**，而 `server_args.py` 里只有 **29 处 `add_argument`** ——
CLI 是从 dataclass 自动生成的。vLLM 的 `EngineArgs` 是 **233 字段 / 228 处显式 `add_argument`**。

这不是"谁更复杂"的问题，是**机制决定结果**：当加一个旋钮的成本从"写一段 argparse + 文档"
降到"加一行 dataclass 字段"，旋钮就会长到 476 个。

代价是组合爆炸：476 个旋钮的两两组合就是十万量级，**测试覆盖在数学上不可能**。
于是默认值成为事实标准，非默认路径长期无人验证 —— 这正好又回到原理 2。

### 原理 5 · 每个"优化"都有一个它不成立的工作点

这是我给全库定的写作红线（每个"它很好"后面必须跟"什么时候这是错的"），
写完之后发现它本身就是最重要的结论：

| 优化 | 收益来源 | 什么时候归零甚至为负 |
|---|---|---|
| 连续批处理 | 输出长度**异质** + 在线到达 | 同质输入 + 离线批量时收益接近 0 |
| 前缀缓存 / RadixAttention | 请求间**共享前缀** | 无共享前缀时，纯是 hash / 树维护开销 |
| 投机解码 | GPU 在 decode 时**没吃饱** | 高并发把 GPU 喂饱后，草稿是纯浪费 |
| PD 分离 | prefill 与 decode 的**资源画像不同** | 短 prompt 或传输带宽不足时，一跳网络吃掉全部收益 |
| CUDA Graph | 小 batch 时**CPU 启动开销占比高** | 大 batch 下占比可忽略；且与动态特性冲突会静默失效 |
| 编译式（MLC-LLM 的 TVM 路线） | 形状固定、长期服务同一模型、要跨平台 | 模型迭代快、多模型共存时，编译期是纯成本 |
| 异构卸载（KTransformers） | 显存装不下，**否则根本跑不起来** | 显存够时纯亏；多并发下 CPU 侧算力被打爆 |

**每一行的右列，都是某人在某个 benchmark 上得到"反常"结果的原因。**

### 原理 6 · 跨项目对比里，最容易造假数据的是你自己的脚本

这条是我在这个库里被打脸最狠的一次，留在这儿当纪念。

`compare.py` 第一版报出「41 个同名旋钮默认值不同」。看着像个很有价值的发现。
逐条打开才知道 **37 个是假的**：vLLM 的 `EngineArgs` 大量把默认值**转交给子配置**
（写成 `ModelConfig.dtype`），拿这种引用去和 SGLang 的字面量比，**必然**判成"不同"。
加了 `classify_default()` 只比字面量之后，真正可比且不同的只剩 **4 个**。

`improve.py` 也一样，连着错了两轮：
第一版按全仓"静默吞异常"密度排名 —— 热点前几名全是 `collect_env.py` / `check_env.py` /
`platforms/cuda.py` 这类**探测型**文件，那里吞异常本来就正当。
第二版按文件角色过滤后，剩下的又大半是 `except ImportError: pass`（可选依赖的标准写法）。
第三版才得到能用的口径：**热路径** silent-except 密度（vLLM 1.9 / SGLang 4.9 / Dynamo 21.8 每万行）。

教训不是"要小心"，是**具体的**：
**任何跨项目的自动统计，第一版几乎必然被某一类系统性噪声主导。
拿到结果先问"排名第一的那条，是不是因为它属于某个我没排除的类别"，
而不是先问"这个结论有多有趣"。**

### 原理 7 · 空结果是 bug，不是事实

抽 vLLM 的 API 表面，第一次跑出「0 条路由」。
如果当时把它写成"vLLM 没有装饰器式路由"，整篇就废了。
真相是 2026 版 vLLM 把 entrypoints 拆成了每端点一个包
（`vllm/entrypoints/<family>/<endpoint>/{api_router,protocol,serving}.py`），我的 glob 过期了。
改完 glob，63 条路由、188 个协议类全出来了。

同样的事又发生了三次：TensorRT-LLM 报 0 条路由（它用 `add_api_route` 函数调用式注册，
不是装饰器）；KTransformers 报 0 个文件（包整体挪进了 `archive/`）；
llama.cpp 报 0 条路由（路径写在 `ctx_http.post("/v1/...")` 里）。

**四次里四次都是我的工具错了，没有一次是"这个引擎真的没有"。**
唯一那个真的是 0 的是 Mooncake —— 因为它根本不是 HTTP 推理服务，是传输引擎。

## 二、我在这个库里被打脸的地方（完整清单）

诚实比好看重要，所以这一节不修饰：

1. **`compare.py` 的 41 个"默认值差异"，37 个是假的。**（原理 6）
2. **`improve.py` 的密度指标连错两轮**，第三版才可用。（原理 6）
3. **`struct_map.py` 的子系统分类是文件名匹配，有假阳性。**
   它报 vLLM 的 scheduler 桶有 20 文件 / 8,424 行，写调度器那篇的时候回源码点数，
   真正的连续批处理调度器只有 **6 文件 / 4,012 行** —— 混进来的是 KV-connector 与 EPLB。
   写分布式那篇时又发现 distributed 桶报的 138 文件 / 54,851 行里，**63% 其实属于 PD 分离**。
   这个缺陷我写进了工具的注释里，没有掩盖。
4. **"vLLM 删掉了 paged attention kernel"这句话我一开始写太满了。**
   grep 复核后收窄成"**在 NVIDIA 路径上退役**"——它还活在 `csrc/rocm/attention.cu`
   与 `rocm_aiter_fa.py` 调用的 `torch.ops.aiter.paged_attention_v1`（那是 AMD AITER 提供的）。
5. **我一度把整个主仓库的工作区搞坏了。** `git clone` 失败后目录是空的，
   紧跟着的 `git -C _src/tensorrt-llm sparse-checkout set ...` **向上找到了父仓库**，
   给整个 `llm-action` 开了 sparse-checkout。已复原（`git ls-files --deleted` 为 0），
   但用户此前本地删除的十来个文件被一并"复活"，这个副作用无法精确回滚。
   规矩已写进 `_PLAN.md` §7：对 `_src/` 下任何仓库跑 git 前，
   先断言 `git rev-parse --show-toplevel` 等于该目录本身。

## 三、五道闭卷题

不看正文，能答上来才算读过这个库。

1. vLLM 的前缀缓存驱逐既没有时间戳也没有堆，它靠什么近似"最近最少使用"？
   为什么释放一个请求的块时要**先把块列表倒序**？

2. SGLang 的 `ServerArgs` 有 476 个字段，但 `server_args.py` 里只有 29 处 `add_argument`。
   这 447 个差额是怎么来的？这个机制**同时**解释了什么好处和什么代价？

3. "把 base_url 从 vLLM 换成 SGLang，客户端代码不用改" —— 这句话在什么前提下成立？
   给出至少两个会让它不成立的具体字段类别。

4. 有人给你一个 benchmark：同样的硬件和模型，A 引擎吞吐比 B 高 40%。
   在相信它之前，你必须先问哪三个关于**工作负载**的问题？每个问题问不到会被误导成什么？

5. 你写了个脚本统计十二个开源项目的"代码异味密度"，跑出来 X 项目是第二名的三倍。
   在把这个结论写进报告之前，你应该先做的**那一件事**是什么？（提示：见原理 6）

## 四、这个库之后该往哪走

按价值排序，留给续写的人（也可能是我自己）：

1. **拿到 GPU 之后，把 `_lab` 从"静态抽取"扩成"可实测"。**
   本库现在一个实测数字都没有，这是能力边界不是选择。
   有 GPU 后第一件该做的不是跑吞吐排名，而是**验证原理 5 的那张表** ——
   逐行构造让优化归零的工作负载，看它是不是真的归零。
2. **把 `05-改进机会/04` 的清单真的提成 PR。** 读源码读到能挑毛病只是中间态，
   提出去被上游反驳（或接受）才是闭环。
3. **把 `_verify.py` 接进 CI。** 现在它靠人跑；一旦上游源码更新，
   全库 4,500 多条行号引用会集体过期，需要一个"按 sha 重新校准"的流程。
4. **补 `_lab/` 的时间维度**：现在是单点快照。同一个抽取器跑在多个 sha 上，
   就能看出"这个子系统在最近半年长了多少"，那比静态数字有价值得多。
