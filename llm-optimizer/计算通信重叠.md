## 0. 一句话锚点

一次分布式 step 里有两类工作：**计算**（matmul / 反向）和**通信**（跨 GPU 搬数据：AllReduce、AllGather、P2P）。

- 如果**串行**做：总时间 $T = T_{\text{compute}} + T_{\text{comm}}$。
- 如果让通信**在计算进行时悄悄做完**：总时间 $T = \max(T_{\text{compute}},\, T_{\text{comm}})$。

> **暴露(exposed)通信** = 没被计算盖住、必须干等的那部分通信。
> **隐藏(hidden)通信** = 与计算并行、不额外占时间的那部分。
> 计算-通信重叠的全部目标：**把 exposed 压到 0**。

```
不重叠:  [==== 计算 ====][---- 通信 ----]   T = Tc + Tm
重叠  :  [==== 计算 ====]
         [---- 通信 ----]                  T = max(Tc, Tm)   ← 通信被藏进计算里
```

## 1. 地基：你必须先有的几个原子概念

### 1.1 GPU 是异步执行的
CPU 向 GPU 下发的不是「立即执行」，而是把 kernel **入队**到一条 **stream**。GPU 按 stream 内顺序执行；CPU 下发完可以继续干别的。这是一切重叠的物理前提——**下发≠完成**。

### 1.2 stream（流）= 一条 GPU 上的有序队列
- **同一条 stream 内**：kernel 严格按入队顺序串行，前一个没完后一个不开始。
- **不同 stream 之间**：可以**并发**执行（受硬件资源限制）。
- 默认所有 op 都进 **default stream**，所以默认是串行的——这就是为什么「天然不重叠」。

要重叠，就必须把**通信 kernel** 放到一条**单独的 stream**（通常叫 comm stream），与**计算 stream** 并行。

```
计算 stream:  K1 → K2 → K3 → K4 → ...
                    │（K2 算完产出数据）
                    ▼
通信 stream:        AllReduce(K2的输出)  ←─ 与 K3、K4 并发跑
```

### 1.3 event（事件）= 跨 stream 的同步红绿灯
两条 stream 并发，但有依赖（通信要等计算产出数据；下一步计算要等通信结果）。用 **event** 表达：
- `record(event)`：在 stream A 上插一个标记。
- `wait(event)`：让 stream B 阻塞，直到 A 跑到那个标记。

没有 event，重叠就会**读到脏数据**（通信读了还没算完的 buffer）。

### 1.4 为什么通信「慢」——带宽数量级差
| 通道 | 典型带宽 |
|---|---|
| GPU 片上 HBM | ~2–3 TB/s |
| NVLink（卡间，单链路聚合） | ~数百 GB/s |
| PCIe 4.0 x16 | ~32 GB/s |
| 跨机 IB/RoCE（单网卡） | ~25–50 GB/s |

> 跨机网络比 HBM 慢**两个数量级**。所以模型一旦切到多机，通信极易成为瓶颈——这正是必须重叠的根本原因。（具体带宽以你的硬件/官方文档为准。）

## 2. 通信暴露成本：不重叠到底亏多少

设一层的计算时间 $T_c$、该层产生的通信时间 $T_m$，共 $L$ 层。

- **串行（不重叠）**：$T = \sum_{i=1}^{L}(T_c^{(i)} + T_m^{(i)})$。
- **完美重叠**：$T = \sum_{i=1}^{L}\max(T_c^{(i)}, T_m^{(i)})$。

定义**通信占比** $\rho = T_m/(T_c+T_m)$。完美重叠相对串行的加速：

$$\text{speedup} = \frac{T_c+T_m}{\max(T_c,T_m)}$$

当 $T_c=T_m$（$\rho=0.5$）时 speedup = 2；当 $T_m \le T_c$（通信完全被盖住）时，通信时间**等于白送**。

```
ρ=0.5 :  Tc │====│         理论 speedup = 2.0
         Tm │----│
重叠后:      │====│ ← 只剩 Tc
```

**关键洞察**：重叠不能让通信变快，只能让它「不再额外花时间」。所以重叠的收益上限 = 当前 exposed 通信占比。通信若远大于计算（$\rho \to 1$），光靠重叠救不了，还得减通信量（量化、ReduceScatter 代替 AllReduce、更大 batch 摊薄）。

## 3. 用多 stream / 异步把通信藏到计算后面

核心套路三步：

1. **拆**：把一个大算子拆成若干 **chunk/micro-block**，让「算第 k 块」和「传第 k−1 块」能同时进行。
2. **错位流水**：comm stream 比 compute stream 慢一拍，形成软件流水线（pipelining）。
3. **event 缝合**：每块算完 record，通信 wait 该 event；下一步用到结果前再 wait 回来。

```
时间 →
compute:  [算块0][算块1][算块2][算块3]
comm   :         [传块0][传块1][传块2][传块3]
                    ↑ 块0 算完立即开传，与块1 计算并发
末尾只剩 [传块3] 这一小段是 exposed（流水线 drain）
```

暴露的只剩**第一块的填充(prologue)**和**最后一块的排空(epilogue)**——块数越多，这两段占比越小，越接近 $\max$。

> 经验阈值：chunk 太小 → kernel launch 开销和通信启动延迟(latency)占主导，反而变慢；chunk 太大 → 流水线填充/排空占比高，重叠不充分。需要按消息大小调到「通信带宽打满」的甜点区。

## 4. DDP：梯度 AllReduce 与反向传播重叠（最经典案例）

### 4.1 为什么反向天然适合重叠
反向传播**从最后一层往前算**。第 L 层的梯度**最先算完**——此时第 L−1、L−2… 层还在算。完全可以**立刻把第 L 层梯度发去 AllReduce**，不必等整个反向结束。

```
反向方向 ←──────────────
计算梯度:  ...[g3][g2][g1]   (g_L 先出)
                │   │   │
AllReduce:      ▼   ▼   ▼     每出一层就规约一层，与后续层反向并发
              AR3  AR2  AR1
反向结束时，只剩第 1 层(最早需要、最晚出？不——最后算出的那批)的 AR 还在收尾
```

### 4.2 bucket（分桶）：不要一个 tensor 一个 AllReduce
单参数粒度的 AllReduce 消息太小，被启动延迟拖死。框架把多个相邻参数的梯度**攒进一个 bucket**（如 25 MB），桶满即触发一次 AllReduce。这样：
- 消息够大 → 带宽利用率高；
- 仍有多个 bucket → 仍能与反向重叠。

### 4.3 实现机制（通用原理，不依赖具体 API）
给每个参数注册一个**梯度就绪 hook**：该参数梯度算完时回调，标记它所在 bucket 的计数；bucket 内全部就绪 → 在 comm stream 上异步发起该 bucket 的 AllReduce。`optimizer.step()` 前等所有 bucket 的 AllReduce 完成（用 event 同步）。

### 4.4 逐数手算
设：反向计算 $T_c = 100$ ms；全部梯度 AllReduce 串行需 $T_m = 40$ ms。
- 不重叠：$100 + 40 = 140$ ms。
- 理想重叠：$\max(100,40)=100$ ms。但首尾有 drain，实测常 ~105–110 ms。
- 加速：$140/105 \approx 1.33\times$，即省掉约 25% step 时间。通信越重，省得越多。

## 5. 张量并行(TP)里的重叠

TP 把一个 matmul 沿权重维切到多卡。前向里 RowParallel 的输出需要一次 **AllReduce**（把各卡部分和加起来）；这次通信卡在 matmul 之后、下一层之前，是**关键路径上的硬同步**，比 DDP 难藏。详见 [[llm-inference/大模型推理张量并行]]。

### 5.1 朴素 TP 的痛点
```
GEMM(列并行) → [无通信] → GEMM(行并行) → AllReduce → 下一层
                                            ↑↑↑ 这段没事可干，纯暴露
```
AllReduce 在两个 GEMM 之间，前后都依赖它的结果，**没有现成的计算去盖**。

### 5.2 解法一：分块 + 流水（fine-grained overlap）
把行并行 GEMM 沿 token/行维切成 N 块。算完第 k 块的局部结果，**立刻 ReduceScatter/AllReduce 第 k 块**，同时算第 k+1 块：

```
GEMM:  [块0][块1][块2][块3]
comm:       [RS0][RS1][RS2][RS3]
重叠后只暴露 RS3 的尾巴
```
代价：拆块降低单个 GEMM 的算力利用率（小 GEMM 不够「胖」），需权衡。

### 5.3 解法二：算子内核融合（Flux 思路）
字节 **Flux** 把通信**写进 GEMM kernel 内部**：一个 GPU kernel 一边算 tile、一边把算好的 tile 通过 NVLink 推给别的卡，通信粒度细到 tile 级，几乎无暴露，且省掉单独通信 kernel 的启动开销。本质是把「分块流水」做到 SM 指令级。（具体实现以官方仓库为准。）

### 5.4 序列并行(SP)配合
把 AllReduce 拆成 **ReduceScatter + AllGather**，分摊在不同位置，每段都更容易找到计算去重叠，同时降低激活显存。这是 Megatron-SP 的核心动机之一。

## 6. 流水并行(PP)：气泡(bubble)的来源与压缩

PP 把模型按层切成多个 **stage**，放在不同卡上，像工厂流水线一样传 micro-batch。

### 6.1 气泡从哪来
流水线**填充**(warm-up：前面 stage 已在干、后面 stage 还没数据)和**排空**(cool-down)阶段，部分卡空闲——这就是 **bubble**。

设 stage 数 $p$，micro-batch 数 $m$，每个 micro-batch 单 stage 计算 $t$。
- 总有效计算（理想）：$m \cdot p \cdot t$ 分摊到 $p$ 卡 = 每卡 $m t$。
- 气泡时间（GPipe 经典结论）：约 $(p-1)t$（前向）。
- **气泡占比** $\approx \dfrac{p-1}{m+p-1}$。

```
GPipe (p=4):
stage0: F F F F             B B B B
stage1:   F F F F         B B B B
stage2:     F F F F     B B B B
stage3:       F F F F B B B B
        └bubble┘             └bubble┘   ← 头尾的空格就是气泡
```

### 6.2 手算气泡
$p=4, m=8$：bubble 占比 $=\frac{3}{8+3}=\frac{3}{11}\approx 27\%$。
把 $m$ 提到 32：$\frac{3}{32+3}\approx 8.6\%$。**结论：micro-batch 越多，气泡越小**（但 $m$ 太大激活显存爆）。

### 6.3 1F1B：用调度压气泡 + 省显存
**1F1B(one-forward-one-backward)** 让每个 stage 一旦能反向就立刻反向，稳态期 F 和 B 交替，使**在飞激活数**从 $m$ 降到约 $p$，显存大降，气泡与 GPipe 同阶但峰值显存友好。

### 6.4 interleaved 1F1B（虚拟 stage）
把每张卡再切成多个**虚拟 stage**（一卡管不连续的几段层），让流水线「更密」，气泡占比再降一档（约除以虚拟 stage 数），代价是通信次数变多。

### 6.5 DualPipe（DeepSeek）：双向流水 + 计算盖住 P2P 通信
**DualPipe** 同时从两端喂数据（双向流水），并精心编排，使**反向计算**正好盖住相邻 stage 间的 **P2P 通信**，把 PP 的气泡和暴露通信一起压到很低。本质仍是「找计算去盖通信」，只是调度做到了极致。（细节以论文/官方为准。）

```
PP 气泡压缩三段论:
  加 micro-batch  → 缩短头尾气泡占比
  1F1B/interleave → 调度更密 + 省激活显存
  DualPipe        → 双向 + 让反向计算盖住 P2P 通信
```

## 7. ZeRO / FSDP：参数 AllGather 与前向重叠

FSDP 把参数**分片**存（每卡只存 $1/N$）。用到某层前，要先 **AllGather** 把整层参数拼回来。朴素做法：算到第 L 层才 gather 第 L 层 → 纯暴露。

**prefetch（预取）**：算第 L 层时，**提前**在 comm stream 上 AllGather 第 L+1 层参数；等算到 L+1 时参数已就位。反向同理预取，并把梯度 **ReduceScatter** 与反向计算重叠。

```
compute:  [算L层 ]            [算L+1层]
comm   :  [AllGather L+1 ]            [AllGather L+2]
              ↑ 提前一层取，藏进 L 层计算里
```
用完即释放整参数（只留分片），所以省显存又靠 prefetch 保速度。

## 数值示例：一个完整 step 的重叠收益手算

假设 4 卡 TP+DDP 混合，一个 step：
- 前向计算 $T_{fwd}=60$ ms，反向计算 $T_{bwd}=120$ ms。
- TP 前向 AllReduce 总 $T_{tp}=30$ ms，DDP 梯度 AllReduce 总 $T_{ar}=50$ ms。

**全串行**：$60+30+120+50 = 260$ ms。

**重叠后**：
- TP AllReduce 用分块流水盖进前向：exposed 仅 ~5 ms（尾块）。前向段 $\approx \max(60,30)+5 \approx 65$ ms。
- DDP AllReduce 与反向重叠：$\max(120,50)=120$ ms，加 drain ~6 ms → ~126 ms。

合计 $\approx 65 + 126 = 191$ ms。

**加速** $= 260/191 \approx 1.36\times$，省下约 26% 的 step 时间。其中 DDP 的 50 ms 几乎全被盖住（因为 $50 < 120$），是「白赚」的部分；TP 的 30 ms 只盖住一半，因为它在关键路径上更难藏——印证了第 5 节的难点。

## 对照表：各并行方式的通信与重叠手段

| 并行 | 通信原语 | 何时发生 | 是否在关键路径 | 重叠手段 | 难度 |
|---|---|---|---|---|---|
| DDP | AllReduce(梯度) | 反向后 | 否（反向天然可错开） | bucket + 反向边算边规约 | 易 |
| TP | AllReduce/ReduceScatter | 每层 GEMM 后 | **是** | 分块流水 / kernel 融合(Flux) | 难 |
| SP | ReduceScatter+AllGather | 层内拆分点 | 部分 | 与相邻计算重叠 | 中 |
| PP | P2P(send/recv) | stage 边界 | 半（气泡里） | 1F1B/interleave/DualPipe | 中 |
| ZeRO/FSDP | AllGather(参数)+RS(梯度) | 用参数前/梯度后 | 是 | prefetch 预取 | 中 |

> 通用规律：**反向计算最适合当「遮盖布」**（量大、可乱序）；**TP 的关键路径通信最难藏**（前后强依赖），所以才催生 Flux 这类内核级方案。

## 常见问题

| 疑问 | 真相 |
|---|---|
| 重叠能让通信变快吗？ | 不能。只是让通信时间被计算盖住、不再额外计入总时间。 |
| 为什么默认就不重叠？ | 所有 op 默认进同一条 default stream，串行执行；不主动开 comm stream 就不会并发。 |
| 多 stream 一定更快吗？ | 不一定。stream 切换、event 同步、小 chunk 的 launch 开销都可能反噬；要看通信是否真在关键路径上。 |
| chunk 越小越好？ | 否。太小→延迟主导、带宽打不满；太大→流水填充/排空占比高。有甜点区。 |
| 通信比计算还多怎么办？ | 重叠救不了（speedup 上限 = exposed 占比）。得减通信量：量化、RS 替 AllReduce、加大 batch 摊薄、换拓扑。 |
| 气泡靠重叠消除吗？ | 气泡是「计算空闲」不是「通信暴露」，靠**调度**（多 micro-batch、1F1B、DualPipe）压，不是靠多 stream。 |
| TP 为什么比 DDP 难重叠？ | DDP 的 AllReduce 在反向后、可与后续层乱序并发；TP 的 AllReduce 夹在两个 GEMM 之间、前后强依赖，关键路径上没现成计算可盖。 |
| event 不加会怎样？ | 通信读到没算完的 buffer → 数值错误且难复现（竞态）。重叠正确性全靠 event。 |
