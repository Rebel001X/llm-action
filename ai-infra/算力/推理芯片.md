## 0. 一句话锚点

> **训练卡的工作是「学」（一次，规模巨大，能容忍高延迟），推理芯片的工作是「答」（无数次，规模零散，对延迟/成本极敏感）。** 推理芯片为后者优化：砍掉训练才需要的高精度与全互联，换成更高的访存效率、更低的单 token 能耗和更稳定的延迟。

## 1. 地基 / 前置：推理到底在算什么

### 1.1 自回归生成

大语言模型推理 = 自回归（autoregressive）生成：给定已有 token 序列，预测下一个 token，再把它接回输入，循环往复。

```
输入: "今天 天气"
  → 模型 → 预测 "很"      (第1次前向)
输入: "今天 天气 很"
  → 模型 → 预测 "好"      (第2次前向)
输入: "今天 天气 很 好"
  → 模型 → 预测 "。"      (第3次前向)
...直到输出 <eos>
```

关键观察：**生成 N 个 token 就要做 N 次模型前向**。这是推理慢、贵的根源。

### 1.2 两个阶段：Prefill 与 Decode

一次推理请求被切成性质完全不同的两段：

```
        Prefill (预填充)              Decode (逐字解码)
   ┌──────────────────────┐   ┌───────────────────────────┐
   │ 把整段 prompt 一次性  │   │ 每步只送 1 个 token,       │
   │ 喂进模型, 并行算完     │   │ 算 1 次前向, 出 1 个 token │
   │ → 大矩阵×矩阵 (GEMM)  │   │ → 小矩阵×向量 (GEMV)       │
   │ → 算力密集, 吃 FLOPS  │   │ → 访存密集, 吃带宽         │
   └──────────────────────┘   └───────────────────────────┘
      决定 TTFT(首字延迟)          决定 TPOT(每字延迟) & 吞吐
```

- **Prefill**：把用户输入（比如 1000 个 token）一次性并行算完，得到 KV Cache，并吐出第 1 个 token。计算量大但高度并行，是**算力密集**型。
- **Decode**：之后每生成 1 个 token 只做 1 次前向，权重要全部从显存搬一遍，但实际计算量很小，是**访存（带宽）密集**型。

### 1.3 KV Cache：推理省算力的关键，也是吃显存的元凶

注意力机制里，每个新 token 都要和前面所有 token 算注意力。如果每步都重算前面所有 token 的 Key/Value，复杂度是 $O(N^2)$。**KV Cache** 把已经算过的 K、V 缓存下来，每步只算新 token 的 K、V，复杂度降到 $O(N)$。

代价：KV Cache 占显存，且随序列长度线性增长。单个 token 的 KV 显存：

$$\text{KV/token} = 2 \times L \times H \times d_h \times \text{bytes}$$

其中 $L$=层数，$H$=KV 头数，$d_h$=每头维度，$2$=K 和 V，bytes=精度字节数。这块「会膨胀的显存」直接决定了一张推理卡能同时服务多少并发、多长上下文。

## 2. 推理为什么和训练「计算特征」根本不同

这是理解推理芯片设计的核心，必须讲透。

| 维度 | 训练 | 推理 |
|------|------|------|
| 计算模式 | 前向 + 反向 + 梯度 + 优化器 | 只有前向 |
| 主要算子 | 大 batch 的 GEMM（矩阵×矩阵） | Decode 阶段是 GEMV（矩阵×向量） |
| 瓶颈 | 算力（FLOPS）+ 多卡通信 | **访存带宽**（搬权重）|
| 精度需求 | 需要 FP16/BF16/FP32 保梯度数值稳定 | INT8/FP8/INT4 即可，甚至更激进 |
| Batch | 可以攒很大（成百上千） | 在线服务 batch 小、零散、动态 |
| 延迟容忍 | 高（跑几天没关系） | 极低（用户在等，毫秒级敏感） |
| 显存内容 | 权重+梯度+优化器状态+激活 | 权重 + KV Cache |
| 互联需求 | 极高（梯度全归约 All-Reduce） | 相对低（单卡或少卡即可） |

**最关键的一句话**：Decode 阶段每生成一个 token，要把模型**全部权重**从显存读一遍，但只做一次「矩阵×向量」，计算量小到芯片的算力单元大部分时间在**空等数据**。所以推理（尤其 Decode）是被**显存带宽**而不是算力卡住的——这与训练截然不同。

```
训练 (GEMM, batch 大):                推理 Decode (GEMV, batch≈1):
权重读1次 → 复用给 N 个样本算         权重读1次 → 只算 1 个向量
[算力单元: 忙■■■■■■■■]               [算力单元: 闲□□□□□■]  ← 大量空泡
→ 受算力限制                          → 受带宽限制
```

## 3. 三个核心指标：低延迟、高吞吐、高能效

### 3.1 延迟（latency）——用户体感

- **TTFT (Time To First Token)**：从请求到第一个字出来的时间，主要由 Prefill 决定。决定「等待感」。
- **TPOT (Time Per Output Token)**：之后每个字的间隔，由 Decode 决定。决定「打字流畅度」。一般要求 TPOT < 50ms（约 >20 token/s）才不卡顿。

```
请求 ──TTFT──> "你" ─TPOT─> "好" ─TPOT─> "," ─TPOT─> ...
     └预填充┘   └────────逐字解码────────┘
```

### 3.2 吞吐（throughput）——服务商体感

单位时间所有用户加起来生成多少 token（token/s），决定单卡能服务多少人、单位 token 成本多低。**吞吐和单请求延迟是一对矛盾**：增大 batch（同时塞更多请求）能提吞吐、摊薄成本，但单请求会变慢。推理芯片/系统的艺术就在这条权衡曲线上。

### 3.3 能效（energy efficiency）——账单体感

**token / 焦耳** 或 **每百万 token 的电费**。商业化阶段，推理是「永远在线、海量调用」，电费是长期主成本。能效 = 性能 / 功耗（perf/W），是推理芯片真正的胜负手，比峰值算力更重要。

## 4. 推理芯片 vs 训练卡：设计取舍

既然计算特征不同，硬件就该不同。专用推理芯片相对通用训练卡（如 H100）通常做这些取舍：

```
       训练卡 (通用 GPU)              推理芯片 (专用)
   ┌───────────────────┐         ┌───────────────────┐
   │ 大量 FP16/BF16 算力 │  砍 →  │ 主推 INT8/FP8/INT4 │
   │ 高速全互联(NVLink)  │  砍 →  │ 弱互联(单卡为主)    │
   │ 反向传播相关单元    │  砍 →  │ 只留前向通路        │
   │ 通用可编程性强      │  减 →  │ 为 Transformer 定制 │
   │ 大容量HBM(带宽优先) │  改 →  │ 大SRAM/带宽极致优化  │
   │                     │  加 →  │ 更高 perf/W、低延迟  │
   └───────────────────┘         └───────────────────┘
```

- **降精度**：推理对数值误差容忍度高，用 INT8/FP8 甚至 INT4，算力翻倍、带宽减半、显存减半。这是推理芯片最大的红利。
- **砍互联**：很多推理负载单卡或双卡就够，不需要训练那种昂贵的全互联拓扑。
- **专用化**：固定算子（Attention、GEMM、Softmax）做成硬连线，换取极致 perf/W，代价是灵活性下降。
- **存储策略分化**：要么堆 HBM 拼带宽（如 GPU），要么干脆把整个模型塞进片上 SRAM 消除外部访存（Groq 路线）。

## 5. Roofline：用一张图说清推理为什么卡带宽

**算术强度（Arithmetic Intensity）** $I$ = 计算量 / 访存量（FLOPs / Byte）。Roofline 模型说：

$$\text{可达性能} = \min(\;\text{峰值算力},\;\; I \times \text{峰值带宽}\;)$$

```
性能(FLOPS)
  ▲
  │            ┌──────────── 峰值算力屋顶 (compute bound)
  │           /
  │          /  ← 斜线斜率 = 带宽
  │         /
  │   Decode● (I 很低 → 落在斜坡上 → 被带宽限制)
  │      ●Prefill (I 较高 → 接近屋顶 → 被算力限制)
  └────┴──────────────────────────────► 算术强度 I (FLOP/Byte)
```

- **Decode**（GEMV，batch 小）算术强度极低（读一堆权重只做一点点乘加），落在屋顶线的**斜坡**上 → **带宽决定性能**。
- **Prefill**（GEMM，batch 大）算术强度高，落在**平台**附近 → 算力决定性能。

结论：要让 Decode 更快，要么**加带宽**（HBM3e、片上 SRAM），要么**提高算术强度**（增大 batch、量化减少 Byte、MoE 减少激活权重）。推理芯片所有的设计都在围着这两点转。

## 6. 典型玩家：Groq / TPU / 国产推理卡

> 以下为公开资料的典型量级，具体规格**以官方为准**。

### 6.1 Groq LPU——把模型塞进 SRAM 的极端低延迟路线

Groq 的 LPU（Language Processing Unit）走了一条和 GPU 完全相反的路：**不用 HBM，用海量片上 SRAM**。

```
GPU 路线:  算力单元 ──慢──> HBM(几十 GB, 带宽 TB/s 级)
                            权重存这里, 每步搬一遍 → 受带宽限

LPU 路线:  算力单元 ── SRAM(片上, 极快, 容量小) 权重就在身边
           单芯片容量小 → 用几百张芯片拼起来装下整个模型
           → 几乎没有外部访存 → Decode 极快、延迟极稳
```

- **优点**：片上 SRAM 带宽是 HBM 的几十倍，且确定性强（无缓存抖动），TPOT 极低，单用户 token/s 非常高，体感「秒回」。
- **代价**：单芯片 SRAM 容量小（约几十 MB 量级），装一个大模型要**几百张芯片**串起来，初期资本/部署门槛高；在「单请求超低延迟」上极强，在「海量并发摊成本」上未必最划算。
- **定位**：适合对延迟极敏感的交互场景。

### 6.2 Google TPU——推理友好的脉动阵列

TPU（Tensor Processing Unit）以**脉动阵列（systolic array）**为核心：让数据像「心跳」一样在算力网格中流动，最大化权重复用、减少访存。

```
脉动阵列 (示意):
   权重固定在格子里, 数据横向流入, 部分和纵向累加
   in→[w][w][w][w]
   in→[w][w][w][w]   每个格子: 乘加并把结果传给下一个
   in→[w][w][w][w]   → 极高的 MAC 利用率、低控制开销
```

- 早期 TPU 就是为推理（INT8）而生，后续版本兼顾训练与推理。
- 配合 Google 自家软件栈（XLA / JAX），对 Transformer 这类规整算子效率很高。
- 推理版强调高 INT8/BF16 算力 + 大带宽 + 高能效，是「自研芯片省成本」的标杆。

### 6.3 国产推理卡——商业化下半场的主战场

国产路线大体分几类（具体规格以官方为准）：

- **昇腾（Ascend）NPU**：达芬奇架构，训推一体，国内生态最完整之一，详见 [[ai-infra/算力/昇腾NPU]]。
- **互联网/芯片公司自研推理卡**（如各家 ASIC）：面向自家大模型服务，主打 INT8/FP16 推理能效与单位 token 成本。
- **GPGPU 路线**：兼容 CUDA 生态、训推通用，降低迁移成本。

国产推理卡的共同主题：**在被外部高端训练卡限制的背景下，推理因为对单卡算力/互联要求相对低、对量化更友好，是国产芯片更容易突破和规模落地的方向。** 这正呼应了「下半场是商业化比拼」——谁能用更低的每 token 成本提供稳定服务，谁就赢。

```
为什么推理是国产突破口:
  推理需求特征:  低精度OK + 弱互联够用 + 单卡即可起量
        │
        ▼
  对先进制程/全互联的依赖 < 训练
        │
        ▼
  更易用国产工艺 + 自研生态 规模落地
```

## 7. 趋势：从「堆算力」到「省电、省钱、省带宽」

商业化阶段，推理优化的方向不是更高峰值算力，而是更低的每 token 成本，主线有：

1. **更低精度**：FP8 → INT4 → 甚至 1-bit/三值权重。每降一档，带宽/显存近乎减半，是 Decode 提速的最直接杠杆。
2. **MoE（混合专家）**：模型很大但每个 token 只激活一小部分专家 → 算术强度的「分母」变小、实际搬的激活权重变少 → 推理更省，是大模型推理经济性的关键架构趋势。
3. **推测解码（Speculative Decoding）**：用小模型一次猜多个 token，大模型一次性并行验证 → 把「访存密集的串行 Decode」变成「算力密集的并行验证」，绕开带宽瓶颈。
4. **KV Cache 优化**：PagedAttention（vLLM）、MQA/GQA（减少 KV 头）、KV 量化 → 省 KV 显存、提并发。
5. **专用化 / Chiplet**：推理 ASIC、存算一体（把计算搬到存储旁，根治访存墙）。
6. **训推分离（Prefill/Decode 解耦）**：因为两阶段计算特征相反，用不同硬件/集群分别承接，各自打满利用率。

```
旧目标: 峰值 FLOPS 越高越好
新目标:        每百万 token 的「美元 + 焦耳」越低越好
   降精度 ─┐
   MoE   ─┤
   推测解码─┼─→  ↓ 带宽压力  ↓ 显存  ↓ 能耗  ↓ 成本
   KV优化 ─┤
   存算一体─┘
```

## 数值例子 / 对照（动手算一遍）

> 以下用整数近似，便于建立直觉；真实数字以官方/实测为准。

**例 1：Decode 是不是真的卡带宽？**
设模型权重 70B 参数，INT8（1 byte/参数）→ 权重约 70 GB。Decode 每生成 1 个 token，要把这 70 GB 权重读一遍。若显存带宽约 3 TB/s（3000 GB/s），则每 token 至少：

$$t_{\min} = \frac{70\ \text{GB}}{3000\ \text{GB/s}} \approx 23\ \text{ms}$$

→ 单用户上限约 $1000/23 \approx 43$ token/s，**完全由带宽决定，和算力几乎无关**。这就是「Decode 受带宽限制」的硬证据。换 FP16（权重翻倍到 140 GB）则慢一倍——所以量化对推理这么重要。

**例 2：量化省多少带宽/显存？**
同一个 70B 模型：

| 精度 | 权重显存 | 单 token 搬运 | 相对 Decode 速度 |
|------|----------|---------------|------------------|
| FP16 | ~140 GB | 140 GB | 1× |
| INT8 | ~70 GB | 70 GB | ~2× |
| INT4 | ~35 GB | 35 GB | ~4× |

→ 精度每降一半，Decode 吞吐大致翻倍，显存占用减半（能塞更长上下文/更多并发）。

**例 3：KV Cache 吃多少显存？**
设 $L=80$ 层，KV 头 $H=8$，每头 $d_h=128$，FP16（2 byte）：

$$\text{KV/token} = 2 \times 80 \times 8 \times 128 \times 2 = 327680\ \text{byte} \approx 0.31\ \text{MB}$$

一条 8K 上下文的请求：$0.31 \times 8192 \approx 2.5\ \text{GB}$。并发 32 条就要约 **80 GB** 只为 KV Cache → 解释了为什么大并发推理这么吃显存，以及为什么 GQA/KV 量化/PagedAttention 这么关键。

**例 4：batch 怎么救带宽？**
batch=1 时读一次权重只服务 1 个 token；batch=32 时读一次权重同时服务 32 个 token → 权重搬运成本被摊薄 32 倍，算术强度提高，Decode 从「带宽限」往「算力限」移动 → 吞吐大涨（但单请求延迟略增）。这就是吞吐 vs 延迟权衡的微观原因。

## 常见问题

| 问题 | 简答 |
|------|------|
| 训练卡能做推理吗？ | 能，但「杀鸡用牛刀」：高精度算力和全互联在推理时大量闲置，perf/W 和成本不划算。 |
| 推理一定比训练简单吗？ | 单次前向是简单，但「永远在线 + 海量并发 + 低延迟 + 低成本」让系统层极难，胜负在工程。 |
| 为什么推理更看带宽不看算力？ | Decode 是 GEMV，搬一遍全部权重却只做一点点计算，算力单元大量空等 → 带宽是瓶颈。 |
| Groq 为什么快？ | 用片上 SRAM 取代 HBM，带宽高几十倍且确定性强，单用户 TPOT 极低。 |
| 为什么量化对推理是「免费午餐」？ | 推理对数值误差容忍高，降精度直接减半带宽/显存、翻倍速度，几乎不掉效果。 |
| 国产为什么从推理切入？ | 推理对先进制程/全互联依赖低、对量化友好，更易用国产工艺规模落地，且是商业化主战场。 |
| Prefill 和 Decode 要不要分开部署？ | 趋势上是的：两者计算特征相反，解耦后各自打满利用率（训推分离/PD 分离）。 |
| 衡量推理芯片最该看哪个数？ | 不是峰值 TFLOPS，而是「每百万 token 的成本与能耗」（perf/W、$/Mtok）。 |
