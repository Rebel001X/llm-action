## 0. 一句话锚点

- **NCCL** = GPU 之间做"集合通信"的事实标准库（AllReduce 等），自动用 NVLink/IB，是 PyTorch GPU 训练的默认后端。
- **MPI** 是一套"进程间消息传递"的**接口规范**；OpenMPI / MPICH 是它的两个**实现**。在 AI 里主要负责**启动多机进程**和提供**通用 CPU 集合通信**。
- **Gloo** = CPU 上的集合通信库（也能做点 GPU），无 IB 环境/纯 CPU/调试时的退路。
- **UCX** = 更底层的**传输框架**（统一封装 TCP/共享内存/IB Verbs/CUDA），让上层库不用各自适配每种网卡。

记忆口诀：**算什么用 NCCL，起进程用 MPI，没卡用 Gloo，传输底座是 UCX。**

## 1. 地基：两类通信 + 一个关键区分

要看懂这一摞库，先把两个最原子的概念立住。

**(a) 点对点通信（Point-to-Point, P2P）**：一个发、一个收，明确的"我把这块数据给你"。
- 接口长这样：`send(tensor, dst)` / `recv(tensor, src)`。
- 典型用途：流水线并行（Pipeline Parallel）里，上一段把激活值传给下一段。

**(b) 集合通信（Collective Communication）**：**一组进程**一起参与的"集体动作"，一条指令所有人协同完成。最常用的几个（详见 [[ai-infra/网络/集合通信原语]]）：

```
AllReduce   每个 rank 出一份 → 求和(或max...) → 结果发回所有 rank   ← 数据并行梯度同步就靠它
Broadcast   一个 rank 的数据 → 复制给所有 rank                      ← 同步初始权重
AllGather   每个 rank 出一份 → 所有 rank 都拿到"全部拼接"           ← ZeRO/张量并行收集
ReduceScatter 求和后把结果切片分给各 rank                          ← ZeRO 切分梯度
```

**为什么这个区分重要**：训练里 99% 的通信开销是**集合通信**（尤其 AllReduce）。所以"通信库快不快"，主要看它的集合通信实现得好不好——这正是 NCCL 存在的理由。

**一个常被混淆的点**：MPI 既能做点对点也能做集合通信；NCCL 也是。它们不是"P2P 库 vs 集合库"的对立，而是"**在什么硬件上、为谁优化**"的分工。

## 2. 架构总览：一摞库怎么叠起来的

```
┌───────────────────────────────────────────────────────────┐
│  训练框架  PyTorch DDP / FSDP / DeepSpeed / Megatron        │  ← 你写的代码
├───────────────────────────────────────────────────────────┤
│  torch.distributed (c10d)  统一 API: all_reduce / send ...  │  ← 框架的通信抽象层
├───────────────┬───────────────┬───────────────────────────┤
│    NCCL       │     Gloo      │   MPI (OpenMPI/MPICH)       │  ← 可选"后端 backend"
│  (GPU集合)    │  (CPU集合)    │  (起进程+通用集合)          │
├───────────────┴───────────────┴───────────────────────────┤
│         UCX (可选)：统一传输层 (TCP/SHM/IB Verbs/CUDA)      │  ← 底层传输框架(NCCL/MPI都可走它)
├───────────────────────────────────────────────────────────┤
│  硬件驱动 + Verbs API   CUDA / NVLink / RDMA(IB/RoCE) / PCIe │  ← 真正搬数据的地方
└───────────────────────────────────────────────────────────┘
```

关键认知：**这些库不是互斥的，而是分层 + 可替换**。
- 上层 PyTorch 通过 c10d 选一个**后端**（NCCL/Gloo/MPI）。
- NCCL 自己内部又可以选择走 IB Verbs、走 NVLink、或回退 TCP。
- UCX 是横切的传输底座，MPI 和（部分配置的）NCCL 都能架在它上面。

## 3. NCCL：GPU 集合通信的事实标准

**是什么**：NCCL（NVIDIA Collective Communication Library，读作 "Nickel"）是 NVIDIA 出的、专门做 **GPU 间集合通信**的库。提供 AllReduce / Broadcast / AllGather / ReduceScatter / 以及 Send/Recv 等原语。

**解决什么问题**：GPU 训练时，梯度同步要在几十上百张卡之间高速搬数据。直接用 TCP socket 太慢、也不会用 NVLink。NCCL 把"怎么用最快的链路、走什么拓扑算法"全包了。

**核心机制（为什么快）**：

1. **拓扑感知（topology-aware）**：NCCL 启动时探测机内 GPU 互联（NVLink/PCIe）和机间网卡（IB），自动构建**环（Ring）**或**树（Tree）**拓扑，让数据沿最高带宽链路流动。

```
Ring AllReduce 直觉图 (4 卡):
   GPU0 → GPU1 → GPU2 → GPU3 → (回到)GPU0
   分两阶段:① ReduceScatter 绕一圈累加  ② AllGather 绕一圈散结果
   好处: 每张卡同时只和"邻居"通信, 带宽利用率高且与卡数 N 几乎无关
```

2. **链路自适应**：机内优先 **NVLink**（带宽远高于 PCIe），机间用 **GPUDirect RDMA** 直接让网卡读写 GPU 显存，**绕过 CPU 和系统内存拷贝**。

3. **计算/通信重叠**：在 CUDA stream 上异步执行，训练 backward 算梯度的同时就能开始 AllReduce。

**关键环境变量（讲含义，不背默认值；以官方文档为准）**：

| 变量 | 含义 / 权衡 |
|---|---|
| `NCCL_DEBUG=INFO` | 打印 NCCL 选了哪条链路、哪种算法——排错第一招 |
| `NCCL_IB_DISABLE` | 置 1 强制不走 IB（退回 socket），用于隔离"是不是 IB 配置问题" |
| `NCCL_SOCKET_IFNAME` | 指定走哪块网卡（多网卡机器易选错网卡导致极慢） |
| `NCCL_P2P_DISABLE` | 关掉机内 GPU 直连（NVLink/PCIe P2P），排查机内异常用 |
| `NCCL_ALGO` | 强制 Ring / Tree 算法（默认按规模自动选） |

**和谁配合**：单进程多卡可直接用；多机时常借 **MPI 启动进程**，但**数据搬运仍由 NCCL 做**（MPI 只管 bootstrap）。详见 [[ai-infra/网络/NCCL]]。

## 4. MPI / OpenMPI / MPICH：进程层的"通用基础设施"

**先分清三个名字**：
- **MPI** = Message Passing Interface，是一份**标准/接口规范**（不是某个软件）。
- **OpenMPI**、**MPICH** = MPI 标准的两个主流**开源实现**（厂商库如 Intel MPI 多基于 MPICH）。
- 关系类比：MPI 像"USB 标准"，OpenMPI/MPICH 像"两家做 USB 线的厂商"。

**MPI 在 AI 里的两个角色**：

```
角色① 进程启动器 (launcher)
   mpirun -np 16 -H node1,node2 python train.py
   → 在多台机器上拉起 16 个进程, 分配 rank, 建立互相发现(bootstrap)
   注意: torchrun 是 PyTorch 自带的等价替代, 很多场景已不需要 mpirun

角色② 通用集合通信库 (尤其 CPU, 或非 NVIDIA 硬件)
   MPI_Allreduce / MPI_Bcast ... 历经 HPC 几十年打磨, 极成熟
```

**为什么不全用 MPI 做 GPU 通信**：传统 MPI 对 GPU 显存、NVLink、GPUDirect 的优化不如 NCCL（虽有 CUDA-aware MPI，但生态/性能上 GPU 训练仍以 NCCL 为主）。所以常见组合是 **MPI 起进程 + NCCL 搬数据**。

**实践要点**：用 PyTorch 时，MPI 后端**需要从源码编译** PyTorch 才有（不在预编译 wheel 里）；而 NCCL/Gloo 是开箱即用的。这往往是"为什么我选不了 mpi 后端"的答案。

## 5. Gloo：CPU 集合通信 / 没有 IB 时的退路

**是什么**：Facebook 出的集合通信库，**主打 CPU**（也支持有限的 GPU 集合）。PyTorch 自带、开箱即用。

**解决什么 / 何时用**：
- 纯 **CPU 分布式训练**（没有 GPU）。
- 需要在 **CPU 张量**上做集合通信的步骤（例如某些参数服务器逻辑、在 CPU 上聚合）。
- **没有 NCCL/IB 环境**或想快速验证分布式代码能不能跑——Gloo 走 TCP，依赖最少，最稳。
- 调试：当 NCCL 报错查不出时，临时切 Gloo 看是不是 NCCL/网卡的问题。

**权衡**：GPU 上的性能远不如 NCCL（不会高效用 NVLink/GPUDirect），所以 **GPU 训练别用 Gloo 当主力**，它是"通用/退路"角色。

```
选 Gloo 的典型信号:
  无 GPU ──────────────► Gloo
  有 GPU 但想先跑通逻辑 ─► 先 Gloo 验证, 再换 NCCL 提速
  NCCL 起不来要二分排错 ─► 临时 Gloo
```

## 6. UCX：底层"统一传输框架"

**是什么**：UCX（Unified Communication X）是一个**传输层框架**，不直接给用户用集合通信，而是**统一封装各种底层通信手段**：TCP、共享内存（机内进程间）、InfiniBand/RoCE 的 RDMA Verbs、CUDA（GPU 显存直传）。

**解决什么问题**：如果没有 UCX，每个上层库（MPI、各种框架）都要自己写一遍"怎么用 IB、怎么用共享内存、怎么 fallback TCP"。UCX 把这些**抽象成统一接口**，上层只管"发数据"，UCX 自动挑当前环境最快的传输。

```
        上层: OpenMPI / 框架 / 自研通信
                     │  (统一 API: 我要发这块内存到那个 rank)
                ┌────▼────┐
                │   UCX   │  运行时探测 + 选最优传输
                └──┬───┬──┬───┘
     ┌────────────┘   │  └────────────┐
   共享内存         IB/RoCE          TCP / CUDA
  (同机进程)        (RDMA)         (退路 / GPU直传)
```

**在 AI 栈里的位置**：你通常**不直接接触 UCX**。它常作为 **OpenMPI 的传输后端**出现（OpenMPI 用 UCX 来真正搬字节）。理解它的价值在于：当你看到日志里 `ucx`/`uct`、或排查"为什么 MPI 没走上 IB"时，知道这一层在做传输选择。

## 7. PyTorch 后端怎么选

PyTorch 的 `torch.distributed.init_process_group(backend=...)` 决定底层用哪个通信库。三个候选：`nccl` / `gloo` / `mpi`。

```
                    ┌─────────────────────────────┐
                    │  你的训练是用 GPU 吗?        │
                    └──────────┬──────────────────┘
                  是           │            否
        ┌────────────────┘            └────────────────┐
        ▼                                              ▼
   backend="nccl"  ◄── 几乎总是这个              backend="gloo"
   (用 NVLink/IB/GPUDirect,                      (CPU 集合, TCP)
    数据并行/FSDP/TP 标配)
        │
        └─ 特殊: 需要复用已有 HPC/MPI 生态, 且自编译了 PyTorch → backend="mpi"
```

**官方经验法则**：
- **GPU 训练 → `nccl`**（性能最好，DDP/FSDP/DeepSpeed/Megatron 全默认它）。
- **CPU 训练 / 无 GPU → `gloo`**。
- **`mpi`**：仅当你已有成熟 MPI 生态、或要用 MPI 特性，且**愿意源码编译 PyTorch** 时才选。

**易错点**：
- 选了 `nccl` 但跑在没 GPU 的机器上 → 直接报错。
- 选了 `gloo` 却抱怨 GPU 训练慢 → 后端选错了。
- 多网卡机器 NCCL 选错网卡导致龟速 → 设 `NCCL_SOCKET_IFNAME`（见 §3）。

## 8. "何时用哪个"决策表

| 场景 | 进程启动 | 数据搬运后端 | 说明 |
|---|---|---|---|
| 单机多 GPU 数据并行 | `torchrun` | **NCCL** | 走 NVLink，最常见 |
| 多机多 GPU（有 IB） | `torchrun` 或 `mpirun` | **NCCL** | NCCL 走 GPUDirect RDMA over IB |
| 多机多 GPU（无 IB，仅以太网） | `torchrun` | **NCCL**（走 TCP）| 能跑但带宽受限，注意选对网卡 |
| 纯 CPU 分布式 | `torchrun`/`mpirun` | **Gloo** 或 **MPI** | 没 GPU 用不上 NCCL |
| 想先验证分布式逻辑 | `torchrun` | **Gloo** | 依赖少、稳，跑通再换 NCCL |
| NCCL 报错二分排查 | — | 临时 **Gloo** | 排除是不是 NCCL/网卡问题 |
| 已有 HPC/MPI 重度生态 | `mpirun` | **MPI**（需自编译）| 复用既有调度/工具链 |

## 9. 与硬件的关系：库怎么落到 IB / NVLink / PCIe

这是最容易"知其然不知其所以然"的地方。把链路按**机内/机间**分开看。

```
┌─────────────────── 节点 A (机内) ───────────────────┐   机间   ┌──── 节点 B ────┐
│  GPU0 ══NVLink══ GPU1                                │          │  GPU0   GPU1   │
│   ║(NVLink)        ║                                 │          │                │
│  GPU2 ══════════ GPU3                                │          │                │
│        │ PCIe                                        │          │                │
│      [NIC: IB/RoCE 网卡] ◄── GPUDirect RDMA ─────────┼──IB链路──┼─► [NIC] ─► GPU │
│        │ (网卡可直接读写 GPU 显存, 不经 CPU/内存)     │          │                │
└─────────────────────────────────────────────────────┘          └────────────────┘
```

**机内（同一台机器的多卡）**：
- **NVLink**：GPU 与 GPU 之间的高速直连（带宽远超 PCIe）。NCCL 优先用它做机内 AllReduce。
- **PCIe**：没有 NVLink 时的退路；也是 GPU↔网卡的通道。
- NCCL 的 `NCCL_P2P_*` 控制机内 GPU 直连是否启用。

**机间（跨机器）**：
- **InfiniBand (IB) / RoCE**：提供 **RDMA**——网卡直接读写远端内存，**绕过 CPU**，低延迟高带宽。是大规模 GPU 集群的主流。详见 [[ai-infra/网络/IB软件]]。
- **GPUDirect RDMA**：让 IB 网卡**直接读写 GPU 显存**，省掉"GPU→系统内存→网卡"的多次拷贝。NCCL 在有 IB 的环境会自动用。
- 没有 IB 时，NCCL 走 **TCP/IP over 以太网**，能跑但慢很多。

**一句话因果链**：上层调 `all_reduce` → NCCL 探测拓扑 → 机内挑 NVLink、机间挑 IB+GPUDirect → 如果环境缺这些就逐级退到 PCIe / TCP。**软件库的价值就是"自动选最快的硬件路径"**。

## 10. 数值例子 / 手算（数字为说明用途，量级以官方/实测为准）

**例 1：一次梯度同步要搬多少数据？**
- 模型参数量 $P = 7 \times 10^9$（7B），梯度用 FP16（2 字节/参数）。
- 单个梯度张量大小：$M = P \times 2 = 1.4 \times 10^{10}\ \text{B} \approx 13\ \text{GiB}$。

**例 2：Ring AllReduce 实际传输量。**
$N$ 张卡做 Ring AllReduce，每张卡总收发量约为
$$ \text{每卡通信量} \approx 2\cdot\frac{N-1}{N}\cdot M $$
当 $N$ 很大时趋近 $2M$。代入 $M=13\ \text{GiB}$，每卡约要搬 $\approx 26\ \text{GiB}$。
- **关键洞察**：Ring AllReduce 的每卡通信量**几乎与卡数无关**（恒为约 $2M$），这就是它能扩展到上千卡的原因。

**例 3：用 NVLink vs 用以太网，时间差多少？**
设有效带宽：
- NVLink（机内，约/以官方为准）：~$300\ \text{GB/s}$ 量级。
- IB（机间，单端口，约）：~$25\ \text{GB/s}$ 量级（200Gb/s 链路折算）。
- 10GbE 以太网：~$1.25\ \text{GB/s}$。

搬 $26\ \text{GiB} \approx 27.9\ \text{GB}$ 所需时间 $t = \text{量}/\text{带宽}$：

| 链路 | 带宽(约) | 时间 $t$ |
|---|---|---|
| NVLink | 300 GB/s | $27.9/300 \approx 0.093\ \text{s}$ |
| IB 200Gb | 25 GB/s | $27.9/25 \approx 1.12\ \text{s}$ |
| 10GbE | 1.25 GB/s | $27.9/1.25 \approx 22.3\ \text{s}$ |

**结论**：同样的 AllReduce，走 10GbE 比走 IB 慢约 20 倍、比 NVLink 慢约 240 倍。这就是"为什么大模型训练堆 IB 和 NVLink""为什么选错网卡会让训练变成龟速"——**而把这些链路用对，正是 NCCL 这层软件的核心价值。**

## 常见问题

| 问题 | 解答 |
|---|---|
| NCCL 和 MPI 是竞争关系吗？ | 不是。常组合使用：MPI 起进程，NCCL 搬数据。MPI 也能做集合通信，但 GPU 上 NCCL 更快。 |
| OpenMPI 和 MPICH 选哪个？ | 都是 MPI 实现，功能等价。看集群/厂商生态（如 Intel MPI 基于 MPICH），没强偏好则跟随环境已装的。 |
| PyTorch 为什么我选不了 `mpi` 后端？ | `mpi` 后端不在预编译 wheel 里，需从源码编译 PyTorch；NCCL/Gloo 开箱即用。 |
| Gloo 能做 GPU 训练吗？ | 能跑但慢，不用 NVLink/GPUDirect。GPU 训练应用 NCCL，Gloo 作 CPU/退路/调试用。 |
| UCX 我需要手动配吗？ | 通常不用直接接触；它多作为 OpenMPI 的传输后端。排查"MPI 没走上 IB"时才需要了解它。 |
| 没有 IB 还能多机训练吗？ | 能，NCCL 会退到 TCP over 以太网，但带宽低很多（见 §10），大模型会被通信卡死。 |
| 训练突然极慢但不报错？ | 常见是 NCCL 选错网卡走了管理网/慢网卡。设 `NCCL_SOCKET_IFNAME`，并用 `NCCL_DEBUG=INFO` 看选了哪条链路。 |
| 怎么确认 NCCL 真用上了 NVLink/IB？ | `NCCL_DEBUG=INFO` 看日志里的链路/算法选择；再用 nccl-tests 跑 AllReduce 看实测带宽是否接近硬件上限。 |
