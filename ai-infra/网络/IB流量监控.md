## 0. 一句话锚点

InfiniBand 不走内核 TCP/IP 协议栈（它走 RDMA verbs，**绕过内核**），所以**任何基于 `/proc/net/dev` 的工具（ifstat、nload、bmon、sar -n DEV）都看不到 IB 流量**。要监控 IB，必须直接去读 **HCA（主机通道适配器）和交换机端口上的硬件性能计数器**，这些计数器通过 **PMA（Performance Management Agent）** 暴露，用 `perfquery`、`/sys/class/infiniband/*/ports/*/counters/`、DCGM、Prometheus exporter 等方式读取。

## 1. 地基：为什么 IB 流量"隐身"了

先回顾普通以太网流量是怎么被监控的：

```
应用 send() → socket → 内核 TCP/IP 协议栈 → 网卡驱动 → 计数 /proc/net/dev → 网线
                                                         ↑
                              ifstat / nload / sar 在这里读 rx_bytes/tx_bytes
```

普通工具读的是内核维护的 `/proc/net/dev`（即 `rx_bytes`/`tx_bytes`）。**只要数据经过内核协议栈，这个文件就会累加。**

而 RDMA over InfiniBand 是这样的：

```
应用 → libibverbs (用户态 verbs) → HCA 硬件 DMA 直接搬数据 → IB 链路
        （内核旁路 kernel-bypass，零拷贝 zero-copy）
                          ↑
        数据完全没经过 TCP/IP 协议栈，/proc/net/dev 不增长 → ifstat 显示 0
```

所以原始 seed 里那句话是完全正确的：

> ifstat、nload 这些工具都只能监控 TCP/IP 的流量，因此虽然其上面能显示出 IB 卡（比如 `ib0`），但其实并不能监控到出入 IB 的真实流量，结果中对应部分一直都是 0。

注意：`ib0` 这个网络接口是 **IPoIB（IP over InfiniBand）** 的接口，它只承载"走 IP 的那一小部分流量"（比如 ssh、ping）。真正的 RDMA 大流量（NCCL all-reduce、GPUDirect RDMA）根本不经过 `ib0`，所以即使你监控 `ib0` 也只能看到零头。

**结论：IB 流量必须从硬件计数器读，而不是从内核接口读。**

## 2. 数据从哪来：硬件性能计数器 + PMA

IB 子系统里，每个**端口**（HCA 端口、交换机端口）内部都有一组硬件维护的 64 位/32 位计数器，持续累加经过该端口的数据量、包数、错误数。

```
            ┌─────────── IB 子网 (Subnet) ───────────┐
            │                                         │
  ┌─────────┴─────────┐                   ┌───────────┴────────┐
  │  Host A           │                   │  IB Switch         │
  │  ┌─────────────┐  │  IB link (HDR)    │  ┌──────────────┐  │
  │  │ HCA mlx5_0  │──┼───────────────────┼──│ port 1..N    │  │
  │  │  port 1     │  │                   │  │ 每口都有计数器 │  │
  │  │  ┌────────┐ │  │                   │  └──────────────┘  │
  │  │  │PMA 计数器│ │  │                   └────────────────────┘
  │  │  └────────┘ │  │                            ▲
  │  └─────────────┘  │                            │ SMP/GMP 管理包
  └───────────────────┘                            │
            ▲                                       │
            │ 读取路径：                            │
            │ ① /sys/class/infiniband/.../counters  (本地直接读)
            │ ② perfquery → PMA (MAD 管理包，可读本地也可读远端 LID)
            │ ③ DCGM / ibdiagnet / exporter (封装上面两者)
```

关键名词（原子拆解）：

- **HCA**（Host Channel Adapter）：IB 网卡，Mellanox/NVIDIA 上设备名形如 `mlx5_0`、`mlx5_1`。
- **端口（port）**：一张 HCA 通常有 1~2 个物理端口，编号从 1 开始。
- **LID**（Local Identifier）：子网管理器（SM）给每个端口分配的 16 位本地地址，`perfquery` 可以用 LID 远程查别人的计数器。
- **PMA**（Performance Management Agent）：跑在每个端口上的"性能管理代理"，响应性能查询管理包（PerfMgt MAD），返回计数器值。
- **计数器宽度**：很多老计数器是 32 位的，**会很快溢出（wrap）**；新平台提供 64 位扩展计数器，这是工程上一个大坑（见第 7、常见问题）。

> 具体计数器名、是否 64 位、能否硬件清零，**以厂商/固件文档与 `perfquery` 实际输出为准**，不同代次 HCA 略有差异。

## 3. 端口计数器分几类（按"做什么用"理解，不背默认值）

把计数器按用途分成三大类，监控时各看各的：

| 类别 | 代表计数器（类别名，非逐字 API） | 它回答什么问题 | 单位要点 |
| --- | --- | --- | --- |
| **吞吐量** | 发送/接收的"数据"计数、发送/接收的"包"计数 | 这口跑了多少流量、QPS 多大 | **数据计数通常以"4 字节字（word）"为单位**，要乘 4 才是字节（关键坑） |
| **错误/丢包** | 符号错误、链路恢复、链路下线、接收错误、接收remote物理错误、丢弃等 | 链路质量好不好、有没有坏线/坏口 | 计数（次数），非零且持续增长才警惕 |
| **拥塞** | 进/出"等待"计数（XmitWait 类）、拥塞标记相关 | 端口是否因为对端来不及收而被迫等待 | 等待值持续涨 = 链路/对端是瓶颈 |

**最重要的换算规则（务必记住）**：IB 标准里的"数据吞吐"计数器一般记的是 **32-bit word（4 字节）数**，不是字节数。所以：

$$\text{字节数} = \text{计数器值} \times 4$$

很多人第一次算带宽算出来只有 1/4，就是漏了这个 ×4。

## 4. 用什么命令看（讲机制与用途，不背确切默认参数）

### 4.1 直接读 sysfs（最轻量、最适合脚本/exporter）

每个端口的计数器都暴露在文件系统里，路径形如：

```
/sys/class/infiniband/<设备>/ports/<端口号>/counters/        ← 32 位经典计数器
/sys/class/infiniband/<设备>/ports/<端口号>/counters_ext/    ← 64 位扩展计数器(若支持)
/sys/class/infiniband/<设备>/ports/<端口号>/hw_counters/     ← 厂商硬件/RDMA 计数器
```

里面每个文件就是一个计数器的当前累加值（一行一个数）。优点：**不需要发管理包、不需要 root 也能读、开销极低**，所以几乎所有 Prometheus exporter 底层都是 `cat` 这些文件。

监控吞吐的标准做法（**这些计数器是单调累加值，必须做差分**）：

```
速率(bit/s) = (本次值 - 上次值) × 4(字节/word) × 8(bit/字节) ÷ 采样间隔Δt(秒)
```

### 4.2 `perfquery`（rdma-core / infiniband-diags 自带）

`perfquery` 通过 PMA 读计数器，能力比裸读 sysfs 更全：

- 不带参数：读本机默认端口的计数器；
- 可指定**设备/端口**：查本机某张卡某个口；
- 可指定**远端 LID/端口**：查交换机或别的主机的口（IB 网管的杀手锏）；
- 支持**读取后清零**、读取**扩展(64 位)计数器**等开关（具体选项名以 `perfquery --help` 为准，不同版本有差异）。

典型用途：怀疑某条链路有问题，用 SM 给的 LID 把链路两端端口的错误计数都拉出来对比。

### 4.3 `ibdiagnet`（全网体检）

`ibdiagnet` 是 OFED 工具集里的"全网一键体检"：它遍历整个子网，采集所有端口计数器、检查链路速率/宽度是否达标、汇总错误、生成报告文件。**适合"整网巡检"而不是"实时秒级监控"**。它能一次性发现"某根线只协商到了一半速率"这类问题。

### 4.4 DCGM（GPU 集群里最常用）

NVIDIA DCGM（Data Center GPU Manager）除了管 GPU，还能采集**与 GPU 绑定的 NIC/IB 端口的吞吐与错误字段**，并通过 `dcgm-exporter` 直接出 Prometheus 指标。在 GPU 训练集群里，这是把 GPU 利用率和 IB 流量画在同一张 Grafana 面板上的最省事方案。

### 4.5 其它配套（属于 [[ai-infra/网络/IB软件]]）

| 工具 | 干什么 | 监控视角 |
| --- | --- | --- |
| `ibstat` / `ibstatus` | 看端口状态、速率(HDR/NDR)、链路宽度(4x)、LID、是否 Active | 静态状态，不是流量 |
| `iblinkinfo` | 看每条链路两端连到哪、协商速率 | 拓扑/降速排查 |
| `ibnetdiscover` | 发现整个子网拓扑 | 画拓扑图 |
| `ibqueryerrors` | 专门遍历全网错误计数器 | 错误巡检 |
| `mlnx_perf` / `neohost` | 厂商级细粒度 PCIe/HCA 性能 | 深挖瓶颈 |

## 5. 数值例子：把计数器算成 Gbps

假设你在 t=0 和 t=10s 两次读取某 HDR 端口的"发送数据"计数器（PortXmitData 类），值分别是：

- t=0：$C_0 = 1{,}000{,}000{,}000$（word）
- t=10s：$C_1 = 1{,}500{,}000{,}000$（word）

计算发送速率：

$$\Delta C = C_1 - C_0 = 5\times10^{8}\ \text{word}$$
$$\text{字节} = \Delta C \times 4 = 2\times10^{9}\ \text{byte}$$
$$\text{速率} = \frac{2\times10^{9}\ \text{byte} \times 8}{10\ \text{s}} = 1.6\times10^{9}\ \text{bit/s} = 1.6\ \text{Gbps}$$

对照：HDR 单口理论线速 ~200 Gbps，说明此刻这条口只用了 0.8% 带宽——如果你期望它在 all-reduce 阶段打满，那 1.6 Gbps 就意味着**瓶颈不在网络**（可能在计算、在数据加载、或 NCCL 没走 RDMA）。这正是 IB 流量监控对调训练吞吐的核心价值。

> 注意：如果该平台计数器是 32 位的，$1.5\times10^9$ 早就超过 $2^{32}\approx4.29\times10^9$ 的一半，10 秒内极可能**发生 wrap**，差分会算出负数或离谱值——这时必须改用 64 位扩展计数器或缩短采样间隔（见常见问题）。

## 6. 全网批量采集 → 画图 → 告警（生产做法）

单机 `cat` 只能看一台。生产集群的监控链路一般是：

```
每个节点                          中心
┌───────────────────────┐
│ node_exporter /        │  HTTP /metrics   ┌────────────┐    ┌─────────┐
│ dcgm-exporter /        │ ───────────────▶ │ Prometheus │ ─▶ │ Grafana │
│ 自写 ib-exporter       │   (pull 拉取)     │  (TSDB+做差分│    │  面板    │
│  └ 读 sysfs counters,  │                  │   /rate())  │    │  +告警   │
│    每端口 rate 计算     │                  └────────────┘    └─────────┘
└───────────────────────┘                         │
                                                   ▼ Alertmanager
                                         (端口降速/错误激增/单口打满 告警)
```

要点：

1. **差分在采集侧或 Prometheus 侧做**：sysfs 给的是累加值，Prometheus 用 `rate()`/`irate()` 算速率最自然。
2. **采样间隔 vs 计数器宽度要匹配**：高速口 + 32 位计数器，间隔太长会 wrap，建议优先 64 位扩展计数器。
3. **维度要带齐**：`{host, device=mlx5_0, port=1}`，否则多卡多口混在一起没法定位。
4. **错误类计数器单独看**：它们不是"速率"而是"次数"，告警逻辑是"单位时间内增量 > 阈值"。

## 7. 怎么读这些信号（吞吐/错误/拥塞）

| 信号 | 现象 | 通常意味着 |
| --- | --- | --- |
| 吞吐远低于线速 | 训练慢但 IB 几乎不动 | 瓶颈不在网络（算力/IO/未走 RDMA）；或 NCCL 没启用 IB |
| 收发严重不对称 | 某口只发不收 | 路由/拓扑异常，或对端没回 ACK |
| 符号错误/链路恢复 持续涨 | 错误计数不停增 | 物理层问题：线缆/光模块/接口脏，需换线或清洁 |
| 链路降速 | `ibstatus` 显示 100G 而非预期 200G | 线缆/端口只协商到一半，按 [[ai-infra/网络/InfiniBand]] 排查 |
| XmitWait（发送等待）持续涨 | 端口频繁被迫等待 | 拥塞：对端来不及收，或链路上有瓶颈，考虑 QoS/ECN |
| 差分出现负数/暴涨 | 速率曲线尖刺 | 32 位计数器 wrap，换 64 位或缩短间隔 |

## 常见问题 / 坑

| 坑 | 原因 | 应对 |
| --- | --- | --- |
| `ifstat`/`nload`/`sar -n DEV` 永远显示 0 | RDMA 内核旁路，不进 `/proc/net/dev` | 必须读硬件计数器（sysfs/perfquery/DCGM），别用 TCP/IP 工具 |
| 监控 `ib0` 只看到零头 | `ib0` 是 IPoIB，只承载走 IP 的少量流量，RDMA 大流量不经过它 | 监控 HCA 端口计数器，不是 `ib0` 接口 |
| 算出来的带宽只有真实值的 1/4 | 数据计数器单位是 4 字节 word，忘了 ×4 | 字节 = 计数器值 × 4 |
| 速率曲线出现负数/巨大尖峰 | 32 位计数器在高速口上溢出 wrap | 用 `counters_ext`(64 位) 或缩短采样间隔 |
| 直接把累加值当速率画图 | 计数器是单调累加值不是瞬时速率 | 必须两次采样做差分再除以 Δt |
| 错误计数一直很大但网络其实没事 | 计数器是开机以来累加、从没清零 | 看"增量/单位时间"，必要时 `perfquery` 清零后再观察增长 |
| 单看本机看不出链路谁的锅 | 链路是两端的事 | 用 LID 把链路两端端口计数都拉出来对比 |
| 想知道"哪根线降速了" | 单端口计数器看不出协商速率 | 用 `iblinkinfo`/`ibdiagnet` 看协商的 speed×width |
