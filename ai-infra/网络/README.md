## 0. 一句话锚点

> **AI 网络 = 让"通信不要成为木桶最短板"。** 训练时 GPU 算得越快，越要求把梯度/激活搬运得越快；网络决定了集群"规模化效率"(scaling efficiency)的天花板。

## 1. 地基：网络解决什么问题

单块 GPU 显存和算力有限，装不下、也算不完一个千亿/万亿参数模型。于是我们把模型和数据切分到成百上千块 GPU 上(数据并行 / 张量并行 / 流水线并行 / 专家并行)。**只要做了"切分"，就必然产生"GPU 之间交换数据"的需求**：

- **数据并行(DP)**：每步要做一次 **All-Reduce**，把所有 GPU 上的梯度求和再分发。通信量 ≈ 模型参数量。
- **张量并行(TP)**：每层前向/反向都要 **All-Reduce / All-Gather**，频率极高，对**延迟和带宽都极度敏感**，所以 TP 通常只在**单节点内**(走 NVLink)做。
- **流水线并行(PP)**：相邻 stage 之间传激活值，点对点(P2P)通信，量小但要求低延迟。
- **专家并行(MoE)**：每步要做 **All-to-All**，把 token 路由到不同专家所在的 GPU，对网络对分带宽(bisection bandwidth)要求极高。

**核心矛盾**：计算可以靠堆 GPU 线性扩展，但通信会随规模增长甚至超线性增长。如果网络慢，GPU 大部分时间在"等数据"，利用率(MFU)暴跌。所以 AI-Infra 里有一句话：

> "训练大模型，一半是算力工程，一半是网络工程。"

## 2. 通信的两个层级：Scale-up vs Scale-out

理解整套网络的关键，是分清"机箱内"和"机箱间"两套截然不同的互联：

```
                ┌───────────── 一台 GPU 服务器(节点) ─────────────┐
                │                                                 │
                │   GPU0 ── NVLink ── GPU1 ── NVLink ── GPU2 ...   │  ← Scale-up
                │     \                 |                  /       │   (节点内纵向扩展)
                │      \           NVSwitch 全互联        /        │   带宽: 数百 GB/s ~ TB/s
                │       \________________|_______________/        │   延迟: 纳秒~亚微秒级
                │                        |                        │
                │                  CPU ─ PCIe ─ NIC(网卡)         │
                └────────────────────────┼────────────────────────┘
                                          │  ← Scale-out
                          InfiniBand / RoCE 交换机网络            (节点间横向扩展)
                                          │                      带宽: 单口 100/200/400 Gbps
                ┌─────────────────────────┼─────────────────────┐ 延迟: 微秒级
                │  节点2  │  节点3  │  节点4  │ ... │  节点 N  │
                └──────────────────────────────────────────────┘
```

| 维度 | Scale-up (节点内) | Scale-out (节点间) |
| --- | --- | --- |
| 代表技术 | NVLink / NVSwitch / PCIe | InfiniBand / RoCE(以太网) |
| 单位 | GB/s(字节) | Gbps(比特，÷8 才是 GB/s) |
| 带宽量级 | 数百 GB/s 到 TB/s | 单口 100~400 Gbps |
| 延迟量级 | 纳秒~亚微秒 | 微秒级 |
| 适合的并行 | 张量并行、专家内通信 | 数据并行、流水线并行、跨机 MoE |

**记忆口诀**：节点内"堆带宽降延迟"靠 NVLink，节点间"扩规模"靠 InfiniBand/RoCE。两者带宽常差一个数量级，所以并行策略要"按通信亲和性排布":高频通信放节点内，低频通信跨节点。

## 3. 节点内互联：PCIe → NVLink → NVSwitch

### 3.1 PCIe：通用但不够快的"老总线"

PCIe(PCI Express)是服务器里 CPU、GPU、网卡、SSD 共用的标准外设总线。它的特点是**通用、点对点串行、带宽按"代"和"通道数(x16/x8)"翻倍**：每升一代，单通道速率大致翻倍。GPU 通常接在 PCIe x16 槽上。

PCIe 的问题：
- **带宽相对有限**：作为所有外设共享的"主干道"，多 GPU 之间互传会争抢，且要绕经 CPU/根复合体(Root Complex)。
- **延迟较高**、协议开销大。

所以 PCIe 适合做 CPU↔GPU、GPU↔网卡的"接入",但**不适合做大量 GPU 之间的高频互传**——这正是 NVLink 出现的原因。

> 具体每一代 PCIe 的精确速率以 PCI-SIG 官方规范为准，这里只讲"逐代翻倍"的趋势。

### 3.2 NVLink：GPU 之间的"专用高速直连"

NVLink 是 NVIDIA 为 GPU↔GPU(以及部分 GPU↔CPU)设计的专用高速互联，绕开 PCIe，带宽比同期 PCIe 高出数倍乃至一个数量级。

```
       仅靠 NVLink 直连(早期 / 小规模)          经 NVSwitch 全互联(现代 8 卡服务器)

        GPU0 ════ GPU1                          GPU0  GPU1  GPU2  GPU3
         ║  ╲    ╱  ║                             │    │    │    │
         ║   ╲  ╱   ║                          ┌──┴────┴────┴────┴──┐
        GPU3 ════ GPU2                         │     NVSwitch       │  任意两卡
                                               └──┬────┬────┬────┬──┘  等带宽全互联
   每卡 NVLink 数有限，直连难以               GPU4  GPU5  GPU6  GPU7
   做到所有卡两两等带宽
```

要点：
- NVLink 提供**双向、高带宽**链路，多条 NVLink 可绑定(bonding)到同一对 GPU 之间叠加带宽。
- 多代演进的主线是：**每条链路速率提升 + 每卡链路数量增加 ⇒ 单卡聚合带宽持续翻倍**。
- 但"纯直连"在卡数变多时会遇到**全互联难题**：每卡链路数有限，无法让任意两卡都拥有满带宽直连。解决办法就是 NVSwitch。

### 3.3 NVSwitch：把 NVLink 变成"全互联交换"

NVSwitch 是一颗 NVLink 交换芯片，把节点内所有 GPU 的 NVLink 汇聚起来，使**任意两块 GPU 都能以满 NVLink 带宽通信**(无阻塞全互联)。原始 stub 提到的关键事实：

> 第三代 NVSwitch 基于 NVLink 构建，为计算密集型负载提供更高带宽、更低延迟；每个 NVSwitch 有多个 NVLink 端口，并配有 **NVIDIA SHARP** 引擎，可做**网络内归约(in-network reduction)和组播加速**。

为什么 SHARP 重要：传统 All-Reduce 要在 GPU 之间多轮传输+本地相加；**SHARP 让交换芯片自己做加法**，把"求和"卸载到网络里(in-network computing)，减少数据来回搬运，进一步降低集合通信延迟。NVLink 还能跨节点扩展(NVLink Switch System / NVLink 网络),把多个机箱的 GPU 域连成更大的 NVLink 域。

| 技术 | 作用 | 一句话 |
| --- | --- | --- |
| PCIe | 通用外设接入 | 什么都能连，但不够快 |
| NVLink | GPU↔GPU 专用高速直连 | 一对一/几对几的高带宽链路 |
| NVSwitch | NVLink 的"交换机" | 让一柜子 GPU 任意两两满带宽互通 |

## 4. 节点间网络：RDMA / InfiniBand / RoCE

跨服务器通信不能再用 NVLink(物理上不连)，要走网卡(NIC)+交换机。核心技术是 **RDMA**。

### 4.1 RDMA：绕过 CPU 的"远程直接内存访问"

传统 TCP/IP 收发数据，要经过：用户态→内核态拷贝→协议栈→网卡，CPU 全程参与、多次内存拷贝、延迟高。**RDMA(Remote Direct Memory Access)** 让网卡**直接读写远端主机/GPU 内存**，绕过对端 CPU 和内核协议栈：

```
   传统 TCP/IP                              RDMA
  ┌─────────┐                          ┌─────────┐
  │  App    │                          │  App    │  ← 一次注册内存(MR)
  ├─────────┤  多次拷贝 + CPU 中断      ├─────────┤
  │ Kernel  │  内核协议栈              │ (bypass)│  ← 零拷贝、内核旁路
  │ TCP/IP  │  CPU 忙于搬数据          │         │
  ├─────────┤                          ├─────────┤
  │  NIC    │ ───────────────────────► │  NIC    │ ──直接写对端内存──►
  └─────────┘                          └─────────┘     CPU 几乎不参与
```

RDMA 三大收益：**零拷贝(zero-copy)、内核旁路(kernel-bypass)、CPU 卸载**。对 AI 训练意味着：跨机 All-Reduce 时 CPU 不被通信拖死，延迟低、带宽高。

RDMA 主要有三种落地形态：**InfiniBand、RoCE、iWARP**。AI 集群以前两种为主。

### 4.2 InfiniBand (IB)：为 HPC 而生的专用网络

InfiniBand 是一套**从物理层到传输层全栈自研**的高速网络(独立于以太网)，原生支持 RDMA。优点：

- **延迟极低、带宽极高**，硬件级流控(credit-based)做到**无损(lossless)**，不丢包。
- 自带**子网管理器(Subnet Manager, SM)** 统一管理路由。
- 支持 **SHARP** 网络内计算，加速集合通信。

代价：交换机/网卡/线缆是专用的，**成本高、生态相对封闭**。详见 [[InfiniBand]]、[[IB流量监控]]、[[IB软件]]。

### 4.3 RoCE：在以太网上跑 RDMA

RoCE(RDMA over Converged Ethernet)让 RDMA 跑在**标准以太网**上,复用以太网生态(交换机便宜、运维熟悉)。常见 RoCE v2 基于 UDP/IP，可路由。

**关键难点**:以太网默认会丢包，而 RDMA 怕丢包(丢一个就要重传，性能雪崩)。所以 RoCE 必须配置**无损以太网**:

- **PFC(Priority Flow Control)**：基于优先级的流控，在队列将满时让上游"暂停"，避免丢包。
- **ECN(Explicit Congestion Notification)+ DCQCN**：拥塞通知 + 端到端拥塞控制，让发送端主动降速。

调不好 PFC/ECN，RoCE 会出现"PFC 风暴""死锁"等坑。详见 [[roce]]。

| 对比 | InfiniBand | RoCE(以太网) |
| --- | --- | --- |
| 协议栈 | 全栈专用 | 复用以太网 |
| 无损保障 | 硬件原生、相对省心 | 靠 PFC/ECN 精细调优 |
| 成本/生态 | 高 / 封闭 | 低 / 开放、运维熟 |
| 典型场景 | 极致性能 HPC/大模型训练 | 性价比、已有以太网投入 |

## 5. 网络拓扑：把线路组织成集群

有了链路，还要"怎么连"。两个核心概念：

- **无阻塞(non-blocking)/ 满对分带宽**：理想情况下任意一半节点同时给另一半发数据都不降速。
- **收敛比(oversubscription)**：上联带宽 < 下联带宽的比例，省钱但会成为瓶颈。

最主流的是 **Spine-Leaf(脊叶,即 Fat-Tree 的两层形态)**:

```
            ┌────────┐   ┌────────┐   ┌────────┐
            │ Spine1 │   │ Spine2 │   │ Spine3 │   ← 脊交换机(核心层)
            └───┬────┘   └───┬────┘   └───┬────┘
         ┌──────┼────────────┼────────────┼──────┐
         │      │            │            │      │   每个 Leaf 连到每个 Spine
      ┌──┴──┐ ┌─┴───┐     ┌──┴──┐      ┌──┴──┐         (全连接)
      │Leaf1│ │Leaf2│     │Leaf3│      │Leaf4│       ← 叶交换机(接入层)
      └──┬──┘ └──┬──┘     └──┬──┘      └──┬──┘
       服务器   服务器      服务器       服务器
```

- 任意两台服务器之间跳数固定(可预测延迟)，横向扩展容易,加机柜就加 Leaf。
- AI 训练集群常做成 **Rail-optimized(轨道优化)** 拓扑：把每台服务器的 8 张网卡分别接到 8 个不同的 Leaf(rail),让"相同编号 GPU"之间通信路径最短,优化 All-Reduce。

详见 [[Spine-Leaf和InfiniBand网络架构区别简述]]、[[网络硬件]]。

## 6. 软件栈：硬件如何被用起来

硬件再快，也要软件去驱动。AI 通信软件栈大致分层：

```
   ┌──────────────────────────────────────────────┐
   │  框架: PyTorch DDP / DeepSpeed / Megatron-LM   │  调用 all_reduce 等
   ├──────────────────────────────────────────────┤
   │  集合通信库: NCCL(NVIDIA) / 厂商 CCL           │  实现 Ring/Tree 算法、拓扑感知
   ├──────────────────────────────────────────────┤
   │  传输加速: GPUDirect RDMA / GPUDirect P2P      │  GPU 显存直通网卡/对端 GPU
   ├──────────────────────────────────────────────┤
   │  驱动/Verbs: IB Verbs(libibverbs) / UCX        │  RDMA 编程接口
   ├──────────────────────────────────────────────┤
   │  硬件: NVLink/NVSwitch + IB/RoCE NIC + 交换机   │
   └──────────────────────────────────────────────┘
```

- **NCCL**：NVIDIA 的集合通信库，自动探测拓扑、在 NVLink/PCIe/IB 之间选最优路径,实现 Ring/Tree All-Reduce。是 PyTorch 多卡训练的默认后端。详见 [[NCCL]]、[[集合通信原语]]。
- **GPUDirect RDMA**：让网卡**直接 DMA 读写 GPU 显存**，数据不经过 CPU 内存中转,是跨机 GPU 通信高效的关键。
- **集合通信原语**:All-Reduce / All-Gather / Reduce-Scatter / Broadcast / All-to-All 等，是上层并行策略的"积木"。详见 [[集合通信原语]]。

性能验证常用工具：`nccl-test`(测集合通信带宽)、`ib_*` perftest、`nvbandwidth`(测 NVLink/PCIe 带宽)。详见 [[nccl-test-集合通讯的性能测试]]、[[nvbandwidth]]、[[HPC性能测试]]。

## 参数与选型：怎么权衡(讲含义，不背默认值)

| 你要决定的事 | 关注的"旋钮"(含义) | 权衡 |
| --- | --- | --- |
| 节点内 8 卡怎么连 | NVLink 数量 / 是否带 NVSwitch | 有 NVSwitch ⇒ 任意两卡满带宽,适合大 TP |
| 跨机选 IB 还是 RoCE | 预算 / 现有以太网 / 运维能力 | IB 省心但贵；RoCE 便宜但要会调 PFC/ECN |
| 网卡速率选多少 | 100/200/400 Gbps(单口) | 越高越好，但要匹配交换机和收敛比 |
| RoCE 无损配置 | PFC 优先级、ECN/DCQCN 阈值 | 太激进→丢包性能崩；太保守→吞吐上不去 |
| 拓扑收敛比 | oversubscription(如 1:1 / 2:1) | 1:1 无阻塞但贵；收敛比大省钱但通信会卡 |
| 启用 SHARP | 是否用网络内归约 | 大规模 All-Reduce 明显获益，需硬件+软件支持 |
| NCCL 调优 | 通道数 / 算法(Ring/Tree)/ 缓冲区 | 不同规模/消息大小最优解不同,以实测为准 |

> 以上参数的**确切名字、默认值、阈值**请以 NVIDIA/厂商官方文档与实测为准,不要照搬记忆值。

## 常见问题/坑

| 现象 | 可能原因 | 方向 |
| --- | --- | --- |
| 多机训练比单机慢/扩展性差 | 跨机带宽成瓶颈、未开 GPUDirect RDMA | 检查 NCCL 是否走 IB、是否 GDR 直通 |
| RoCE 偶发性能雪崩 | 丢包触发重传、PFC/ECN 没配好 | 核对无损以太网配置、PFC 风暴/死锁 |
| GPU 利用率高但 MFU 低 | 通信占比过高、并行策略排布不当 | 高频通信(TP)收回节点内走 NVLink |
| NCCL 选了 PCIe 而非 NVLink | 拓扑探测/亲和性/驱动问题 | 看 NCCL 日志确认走的链路 |
| 把 Gbps 当 GB/s 估算 | 单位混淆 | 比特÷8 才是字节,400Gbps≈50GB/s |
| MoE 训练 All-to-All 卡顿 | 对分带宽不足、拓扑不友好 | 用 rail-optimized 拓扑、提高对分带宽 |
| 误以为线路升级就一定提速 | 软件栈/拓扑/收敛比是真瓶颈 | 端到端 benchmark 定位真瓶颈 |
