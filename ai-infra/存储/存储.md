## 0. 一句话锚点

**AI 训练存储 = 在"够快"和"够便宜"之间，为三股数据流（训练样本读、checkpoint 写、KV/中间态）搭一套分层供给系统**，目标是让价值百万的 GPU 集群"一刻也不挨饿"。

一句话直觉：GPU 是发动机，存储是油箱+油管。油箱再大，油管（带宽）太细，发动机照样熄火。

## 1. 地基：为什么存储是训练瓶颈

先建立最底层的事实：一张 H100 的算力约 $\sim 1000$ TFLOPS（FP16），价格以官方/市场为准约数万美元。上千张 GPU 组成的集群每秒能"吃掉"海量样本。如果数据供给跟不上，GPU 利用率（MFU, Model FLOPs Utilization）就掉下来——**买了发动机却没油**。

三个最基本的存储度量，必须分清：

- **容量（Capacity）**：能存多少，单位 TB/PB。决定"数据集放得下吗"。
- **带宽（Bandwidth / Throughput）**：每秒搬多少字节，单位 GB/s。决定"顺序读大文件快不快"。
- **IOPS**：每秒完成多少次 I/O 操作。决定"随机读海量小文件快不快"。

```
        容量 = 油箱多大
        带宽 = 油管多粗（GB/s）   ← 大文件顺序读写看这个
        IOPS = 每秒能开关多少次阀门 ← 海量小文件随机读看这个
        延迟 = 拧开阀门到出油的时间（μs/ms）
```

为什么这四个要分开看？因为**训练数据读**主要拼带宽+IOPS，**checkpoint 写**主要拼带宽，而**小文件多的数据集**（如每张图一个文件）会被 IOPS 卡死，哪怕带宽富余。

## 2. 三类存储需求拆解

大模型训练里，数据不是一团，而是三股性质完全不同的流。**搞混它们 = 选错存储**。

```
 ┌──────────────────────────────────────────────────────┐
 │                  训练集群里的三股数据流                  │
 ├──────────────┬───────────────┬───────────────────────┤
 │ ① 训练数据    │ ② Checkpoint  │ ③ KV Cache / 中间态     │
 │  (读为主)     │   (写为主)     │   (推理侧为主)          │
 ├──────────────┼───────────────┼───────────────────────┤
 │ 规模 TB~PB    │ 单次 GB~TB     │ 单请求 MB~GB            │
 │ 高带宽顺序读   │ 突发大带宽写    │ 低延迟随机读写          │
 │ +高IOPS小文件 │ 周期性(每N步)   │ 显存↔CPU↔SSD 分层      │
 │ 冷热分层       │ 写放大问题严重   │ 见 [[llm-inference/Mooncake]] │
 └──────────────┴───────────────┴───────────────────────┘
```

**① 训练数据**：原始语料/图片/视频，PB 级。训练时反复 epoch 顺序+shuffle 读。难点：既要带宽（大文件），又要 IOPS（小文件多）。

**② Checkpoint**：模型权重 + 优化器状态 + 训练元信息的快照，用于**断点续训**和**容错**（千卡集群每隔几小时必有一张卡挂）。难点：突发巨量写、写放大、写时不能阻塞训练太久。

**③ KV Cache**：严格说属于推理。自回归生成时缓存历史 token 的 Key/Value 避免重算。当其超出显存，要溢出（offload）到 DRAM/NVMe，这正是 [[llm-inference/Mooncake]] 等"以存储为中心"推理架构解决的问题。本文聚焦训练侧①②，③点到为止。

## 3. 存储介质金字塔

最底层认知：**速度越快 → 越贵 → 容量越小**。所以分层（tiering），让热数据在快层、冷数据在慢层。

```
   速度↑ 成本/GB↑ 容量↓
   ┌─────────────────────────────────────────────┐
   │ HBM (GPU片上显存)  ~3 TB/s   80GB/卡  极贵      │ ← 当前 batch
   ├─────────────────────────────────────────────┤
   │ DRAM (CPU内存)     ~100 GB/s  TB级    贵        │ ← prefetch缓冲
   ├─────────────────────────────────────────────┤
   │ 本地 NVMe SSD      ~7 GB/s    TB级    中        │ ← 数据缓存/暂存
   ├─────────────────────────────────────────────┤
   │ 网络并行文件系统    ~100+GB/s  PB级   中(聚合)   │ ← 数据集+ckpt
   │ (Lustre/GPFS)      聚合带宽                      │
   ├─────────────────────────────────────────────┤
   │ 对象存储(S3类)      ~GB/s/连接 EB级   便宜       │ ← 冷数据/归档
   ├─────────────────────────────────────────────┤
   │ HDD 机械盘/磁带     ~200 MB/s  PB级   最便宜     │ ← 长期归档
   └─────────────────────────────────────────────┘
   注：带宽为单设备/单连接典型量级，"约/以官方为准"。
```

典型工作流：**对象存储（冷，全量）→ 并行文件系统（温，本轮训练用）→ 本地 NVMe（热缓存）→ DRAM（prefetch）→ HBM（计算）**。数据像水一样从慢层流向快层。

## 4. NVMe：现代训练的本地快层

承接原仓库链接（[硬盘科普 M.2/PCIe/NVMe](https://zhuanlan.zhihu.com/p/396745362)、[NVMe/AHCI/PCIe/SATA 小结](https://blog.csdn.net/wujinglin7/article/details/122826608)）。这里把三个最容易混的概念**彻底拆开**——它们分别回答不同问题：

```
 ┌────────────┬───────────────────────────┬─────────────────┐
 │ 维度        │ 是什么                     │ 例子             │
 ├────────────┼───────────────────────────┼─────────────────┤
 │ 物理接口    │ 插槽的形状/物理规范         │ M.2 / U.2 / SATA│
 │ (Form)     │ "盘怎么插上去"              │                 │
 ├────────────┼───────────────────────────┼─────────────────┤
 │ 传输通道    │ 数据走的电路总线            │ PCIe / SATA总线 │
 │ (Channel)  │ "数据走哪条路"              │                 │
 ├────────────┼───────────────────────────┼─────────────────┤
 │ 通讯协议    │ 主机与盘对话的语言/规则     │ NVMe / AHCI     │
 │ (Protocol) │ "用什么语言交流"            │                 │
 └────────────┴───────────────────────────┴─────────────────┘
```

**演进路线（沿用原文方向）**：

```
 机械硬盘(HDD)  ──►  SATA + M.2 固态  ──►  NVMe(PCIe) + M.2 固态
 ~200 MB/s          ~550 MB/s             ~7000 MB/s (PCIe4.0)
 SATA通道+AHCI协议   SATA瓶颈600MB/s封顶    PCIe通道+NVMe协议
```

**为什么 NVMe 这么快？** 核心在协议设计，不只是介质：

1. **走 PCIe 直连 CPU**，绕开 SATA 的 600 MB/s 天花板。PCIe 4.0 x4 单盘理论约 8 GB/s（以官方为准）。
2. **AHCI（老协议）只有 1 个命令队列、深度 32**；**NVMe 支持多达 65535 个队列、每队列深度 65536**。

```
   AHCI (为机械盘设计):          NVMe (为闪存设计):
   ┌──┐                         ┌──┐┌──┐┌──┐ ... 多达64K队列
   │Q │ 1队列×32深度            │Q ││Q ││Q │  每队列64K深度
   └──┘                         └──┘└──┘└──┘
   单车道                        多车道高速公路，多核CPU并行下发
```

机械盘磁头只有一个，多队列没意义；闪存可大规模并行，NVMe 的多队列才把闪存潜力榨干。**这就是"协议要匹配介质"的本质。** 详见 [[ai-infra/存储/nvme-ssd]]。

训练侧用途：本地 NVMe 常作为**数据集缓存**（把本轮要用的 shard 从网络存储拉到本地盘，避免反复走网络）和**checkpoint 暂存盘**（先快速落本地，再异步上传网络/对象存储）。

## 5. 并行文件系统（Lustre / GPFS）

**问题**：单台存储服务器的带宽（几 GB/s）远喂不饱上千张 GPU（需要上百 GB/s 聚合）。**解法**：把一个文件**切片（stripe）打散到多台存储服务器**，客户端并行读多台，带宽叠加。这就是并行文件系统的核心思想。

```
        ┌─────────────────────────────────────────┐
        │     上千个GPU计算节点 (并行文件系统客户端)    │
        └───────┬───────┬───────┬───────┬─────────┘
                │       │       │       │  高速网络(IB/RoCE)
        ┌───────┴───┐ ┌─┴─────┐ ┌┴──────┐ ┌┴──────┐
        │ 元数据服务  │ │数据服务│ │数据服务│ │数据服务│
        │ (MDS/NSD) │ │ OSS1  │ │ OSS2  │ │ OSS3  │
        │ 管文件名/  │ │ OST   │ │ OST   │ │ OST   │
        │ 目录/权限  │ │(存数据)│ │(存数据)│ │(存数据)│
        └───────────┘ └───────┘ └───────┘ └───────┘
   一个大文件被 stripe 到 OST1/OST2/OST3 → 读时三路并行 → 带宽×3
```

关键设计——**元数据与数据分离**：
- **元数据**（文件名、目录树、权限、文件由哪些块组成）由专门的元数据服务管理。海量小文件时，元数据服务常成为瓶颈（每个 `open()` 都查它）。
- **数据**分散在多个对象存储目标上，按 stripe 并行读写。

**Lustre**（开源，HPC/AI 主流）：术语 MDS（元数据服务器）+ OSS/OST（对象存储服务器/目标）。客户端通过 LNet 网络访问。优点：聚合带宽极高（可达 TB/s 级，规模相关）；缺点：小文件元数据压力大、运维复杂。

**GPFS / IBM Spectrum Scale**（商业）：每个节点都可参与（NSD 模型），元数据可分布式，对小文件和企业级容灾更友好。

```
   选型直觉：
   大文件顺序读(视频/大shard) ─► 并行FS强项，带宽线性扩展
   海量小文件(每图一个jpg)    ─► 元数据瓶颈，需先打包(WebDataset/tar)
```

**实践要点**：训练前把海量小文件**打包成大 shard**（如 tar/WebDataset/TFRecord），把"随机小 I/O"变成"顺序大 I/O"，绕开元数据与 IOPS 瓶颈——这是 AI 数据工程最常见的优化之一。

## 6. 对象存储（S3 类）

**对象存储**不是文件系统，而是一个巨大的 key→value 仓库：`key`（如 `dataset/img_0001.jpg`）映射到一个不可部分修改的 `object`（数据 + 元数据）。**没有真正的目录树**，"文件夹"只是 key 前缀的视觉假象（扁平命名空间）。

```
   文件系统(有树):              对象存储(扁平):
   /data/                       bucket: my-dataset
     ├ a/                       ├ key="a/img1.jpg" → object
     │  └ img1.jpg              ├ key="a/img2.jpg" → object
     └ b/                       ├ key="b/img3.jpg" → object
        └ img3.jpg             (前缀"a/"只是字符串，非真目录)
   通过路径+inode访问           通过 HTTP GET/PUT + key 访问
```

特征与适用：
- **访问方式**：HTTP REST（GET/PUT/DELETE），不是 POSIX。不能 `seek` 到对象中间改 1 字节，只能整体覆盖。
- **优点**：近乎无限容量（EB 级）、最便宜、内置多副本/纠删码高可靠、跨地域。
- **缺点**：单连接延迟高（ms 级）、不支持随机写、元数据操作弱。
- **角色**：训练里做**数据湖/冷存与原始全量库**。训练时把需要的部分拉到并行文件系统或本地 NVMe。Checkpoint 归档也常落对象存储。

兼容生态：S3 API 已是事实标准，MinIO、Ceph RGW、各云对象存储都兼容它，训练框架（如通过 `s3fs`、`fsspec`）可直接流式读取。

## 7. Checkpoint 与写放大

**Checkpoint = 训练状态快照**，包含三块，体积远超你以为的"模型大小"：

```
   一份完整 checkpoint =
   ┌─ 模型权重 (Weights)         : P 个参数 × 2字节(fp16/bf16)
   ├─ 优化器状态 (Optimizer)     : Adam 存 m,v 两个动量 → 通常×2(fp32各4字节)
   ├─ 主权重副本(fp32 master)    : 混合精度训练常额外存
   └─ 元信息(step/lr/rng种子等)  : 小
```

**Adam 优化器是 checkpoint 膨胀的元凶**。对 $P$ 个参数，常见混合精度配置每参数约需：
- 权重 fp16：2 字节
- fp32 主权重：4 字节
- Adam 一阶动量 $m$ fp32：4 字节
- Adam 二阶动量 $v$ fp32：4 字节

合计约 **16 字节/参数**。所以 checkpoint 体积 $\approx 16P$ 字节，**约为"裸模型 fp16 大小（$2P$）的 8 倍**。

### 写放大（Write Amplification）

这个词有两层含义，都要懂：

**含义 A（系统/语义层）**：你逻辑上想存一个 70B 模型（约 140 GB 权重），实际却写下约 16×70B ≈ 1.1 TB。**放大倍数 ≈ 实际写入量 / 模型权重量**。

**含义 B（SSD 闪存层）**：闪存以"块"为单位擦除，改一点数据可能触发整块"读-改-写+垃圾回收"，导致底层物理写 > 主机请求写。这缩短 SSD 寿命，是 NVMe 选型要看 DWPD（每日全盘写次数）的原因。

```
   逻辑视角:  "我存个 70B 模型"          → 期望 140 GB
   实际写入:  权重+fp32+m+v             → ~1.1 TB  (≈8× 写放大A)
   SSD底层:  擦除块对齐+GC             → 物理写更多 (写放大B)
   多副本/分片冗余:  ×副本数            → 再放大
```

### 频率与中断成本的权衡

Checkpoint 太频 → I/O 抢带宽、拖慢训练；太稀 → 一旦崩溃，回滚损失的算力大。

设单次 checkpoint 写耗时 $T_{ckpt}$，间隔 $T_{interval}$，节点平均故障间隔 MTBF。期望浪费 ≈ 写开销占比 $+$ 崩溃回滚期望。直觉公式：每步均摊浪费时间

$$ \text{Overhead} \approx \frac{T_{ckpt}}{T_{interval}} + \frac{T_{interval}/2}{\text{MTBF}} $$

对其求最优间隔（Young/Daly 近似）得 $T_{interval}^{*} \approx \sqrt{2 \cdot T_{ckpt} \cdot \text{MTBF}}$。**越大规模集群 MTBF 越短，越要快而频的 checkpoint。**

### 工程优化（必会）

```
   ① 异步/分阶段:  GPU→CPU内存(快, 阻塞短) ─异步─► 落盘/上传(慢, 不阻塞)
   ② 分布式分片(Sharded): 每个rank只存自己那片(配合ZeRO/FSDP)，并行写，带宽×N
   ③ 增量/去重:    只写变化部分
   ④ 本地先落NVMe: 利用本地高带宽快速落，再后台同步到并行FS/对象存储
```

代表工作如 **DeepSpeed/Megatron 的分片 checkpoint**、**异步 checkpoint**、字节/微软等的快速 checkpoint 方案，核心都是"把阻塞训练的时间压到最短，把慢搬运挪到后台"。

## 8. 带宽瓶颈与数据流水线

最坏的浪费：**GPU 等数据**。理想是数据预取（prefetch）与计算重叠，让 GPU 永远有下一批就绪。

```
   坏 (串行, GPU饥饿):
   读数据█████ 算██ 读数据█████ 算██ 读数据█████ 算██
                   ↑GPU空转等读盘

   好 (流水线重叠, prefetch):
   读批1█████
        读批2█████  读批3█████  读批4█████   (CPU多worker并行读+解码)
        算批1██     算批2██     算批3██       (GPU连续不空转)
```

**判断瓶颈在哪**（实践方法论）：
- GPU 利用率高但 MFU 低、`nvidia-smi` 显示 GPU 周期性掉到 0% → **数据供给瓶颈**（存储/DataLoader）。
- 监控 DataLoader 的 `num_workers`、是否 `pin_memory`、是否 `prefetch_factor` 足够。
- 顺序大文件读慢 → 看**带宽**（并行FS stripe 数、网络是否打满）。
- 小文件读慢、IOPS 打满 → 先**打包数据**（见第 5 节）。

**带宽预算（决定能不能喂饱）**：

$$ \text{所需读带宽} = \frac{\text{每步样本字节数} \times \text{global batch}}{\text{每步耗时}} $$

只要它小于存储能提供的聚合带宽，且被 prefetch 良好重叠，GPU 就不饿。

## 9. 数值例子 / 手算

**例 1：70B 模型 checkpoint 有多大？**
- 参数 $P = 70 \times 10^9$。
- 混合精度 + Adam ≈ 16 字节/参数。
- 体积 $= 70\times10^9 \times 16 = 1.12\times10^{12}$ 字节 $\approx$ **1.12 TB**。
- 裸 fp16 权重仅 $70\times10^9\times2 = 140$ GB → **写放大约 8×**。

**例 2：这份 checkpoint 写多久？**
- 假设本地 NVMe 顺序写约 5 GB/s（约/以官方为准）。
- 单盘写 $1120 / 5 = 224$ 秒 ≈ **3.7 分钟**（阻塞训练，太久！）。
- 用分布式分片到 64 个 rank 并行写：$224 / 64 \approx$ **3.5 秒**。→ 这就是为什么必须分片+异步。

**例 3：数据集放得下本地盘吗？**
- 15T tokens 语料，若以 bf16 token id/embedding 不直接存；存原始文本约每 token ~4 字节打包后更小。以打包后约 $15\times10^{12}\times2$ 字节估 ≈ **30 TB** 量级（视格式而定）。
- 单机本地 NVMe 通常几 TB → **放不下** → 必须放并行文件系统/对象存储，训练时流式读 + 本地缓存热 shard。

**例 4：喂饱 1024 张 GPU 需要多少读带宽？**
- 设每 GPU 每步处理样本约 1 MB，每步耗时 0.5 s，1024 卡。
- 所需带宽 $= \dfrac{1\text{MB} \times 1024}{0.5\text{s}} = 2048$ MB/s $\approx$ **2 GB/s**。
- 远小于 Lustre 聚合带宽（数百 GB/s），所以**纯带宽不是瓶颈，瓶颈常在小文件 IOPS 与 DataLoader CPU 解码**。

**对照表：三类介质/系统怎么选**

| 需求 | 首选 | 为什么 |
|---|---|---|
| 海量原始数据集冷存 | 对象存储(S3) | 最便宜、EB级、高可靠 |
| 本轮训练数据高带宽读 | 并行FS(Lustre/GPFS) | 聚合带宽线性扩展 |
| 热数据/ckpt 暂存 | 本地 NVMe | 单盘 GB/s、低延迟 |
| 小文件多 | 先打包成大shard | 避开元数据/IOPS瓶颈 |
| KV Cache 溢出 | DRAM→NVMe分层 | 见[[llm-inference/Mooncake]] |

## 常见问题

| 问题 | 答案 |
|---|---|
| NVMe 和 SSD 是一回事吗？ | 不是。SSD 是介质（固态），NVMe 是协议。可以有 SATA 协议的 SSD（慢）和 NVMe 协议的 SSD（快）。 |
| M.2 就等于 NVMe 吗？ | 不。M.2 是物理接口形状，既能跑 SATA 也能跑 NVMe，要看走的通道和协议。 |
| 为什么 checkpoint 比模型大那么多？ | 还要存优化器状态（Adam 的 m、v）和 fp32 主权重，约 16 字节/参数，是裸 fp16 权重的约 8 倍。 |
| 数据集小文件多为什么慢？ | 每个文件 open 都查元数据服务，IOPS 被打满，带宽再大也没用。解法：打包成大 shard。 |
| Lustre 和 GPFS 选哪个？ | Lustre 开源、HPC/AI 聚合带宽强；GPFS 商业、小文件与企业容灾更友好。看预算与负载特征。 |
| 对象存储能直接当训练数据盘吗？ | 可流式读，但延迟高、不支持随机写。通常作冷存，训练时拉到并行FS/本地NVMe。 |
| 怎么知道瓶颈是存储？ | 看 GPU 是否周期性掉到 0% 利用率、MFU 低；用 prefetch/多 worker/打包数据逐项排查。 |
| KV Cache 算训练存储吗？ | 主要属推理。当超显存需 offload 到 DRAM/NVMe，是以存储为中心推理的核心，见 Mooncake。 |
