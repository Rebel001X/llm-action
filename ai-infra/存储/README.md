## 0. 一句话锚点

一句话：**存储的唯一使命，是让昂贵的 GPU 永远不因为"等数据"而空转。**

GPU 是集群里最贵的资源（一张 H100 公开报价约数万美元，以官方为准）。如果训练一步要算 100ms，但数据从磁盘读出来要 200ms，那么 GPU 有一半时间在干等——这叫 **I/O bound（受 I/O 限制）**，等于把一半的钱烧成了热量。

```
       理想：算力满载                  现实：存储拖后腿
   GPU |████████████████|          GPU |████░░░░████░░░░|
       计算 计算 计算 计算              算 等  算  等
                                          ↑ 数据没读上来 → GPU 空泡(bubble)
```

所以 AI 存储不是"找个硬盘存文件"那么简单，而是要在 **容量（能不能装下）**、**带宽（喂得够不够快）**、**IOPS（小文件够不够多）**、**成本（多少钱一 TB）** 这四个维度之间做精细权衡。

## 1. 地基 / 前置：四个最原子的概念

不假设你记得，从字节讲起。

**(1) 容量 = 能装多少**。单位是字节 B：
$$1\text{ KB}=10^3\text{B},\quad 1\text{ MB}=10^6,\quad 1\text{ GB}=10^9,\quad 1\text{ TB}=10^{12},\quad 1\text{ PB}=10^{15}$$
（注意：内存厂商有时用 $2^{10}$ 进制的 KiB/MiB；本文除特别说明用 $10$ 进制。）

**(2) 带宽（Bandwidth）= 单位时间能搬多少字节**，单位 GB/s。这是"水管有多粗"。读 1 个 100GB 的大文件，带宽决定快慢。

**(3) IOPS = 每秒能完成多少次独立 I/O 操作**（Input/Output Operations Per Second）。这是"水管开关能开合多少次"。读 100 万个 1KB 的小文件，IOPS 决定快慢。

**(4) 延迟（Latency）= 发出一次请求到拿到第一个字节的等待时间**，单位 ms 或 μs。这是"拧开水龙头到出水的反应时间"。

四者的关系，用一个水管比喻就清楚了：

```
   带宽 = 水管横截面积 × 流速   (一次能流多少)
   IOPS = 每秒能开合水龙头几次  (碎操作多快)
   延迟 = 拧开到出水的反应时间  (单次反应快慢)
   容量 = 水池有多大           (总共能存多少)
```

**关键洞察**：带宽和 IOPS 经常是**两套不同的瓶颈**。
- 读 **大文件**（如训练数据分片、checkpoint）→ 拼**带宽**，IOPS 用不完。
- 读 **海量小文件**（如几千万张小图、小 JSON）→ 拼**IOPS** 和**延迟**，带宽根本跑不满。

一条简单公式把三者连起来：
$$\text{有效带宽} \approx \min\!\Big(\text{裸带宽},\; \text{IOPS}\times\text{平均请求大小}\Big)$$
读 4KB 小文件、设备只有 10 万 IOPS 时：$10^5 \times 4\text{KB} = 0.4\text{ GB/s}$——即便设备标称 7GB/s，你也只能跑到 0.4GB/s。**小文件会把带宽锁死在 IOPS 上限。**

## 2. 四类工作负载：存储需求各不相同

AI 集群里产生 I/O 的不是一种东西，而是四类，画风完全不同：

```
            ┌──────────────────────────────────────────────┐
            │            大模型训练/推理 I/O 全景            │
            ├──────────────┬───────────────┬───────────────┤
            │  ① 训练数据   │  ② Checkpoint │  ③ KV Cache   │
            │  (海量只读)   │  (周期性巨写) │  (推理态高频) │
            ├──────────────┴───────────────┴───────────────┤
            │  ④ 日志/指标 (持续小写, 低带宽高频)            │
            └──────────────────────────────────────────────┘
```

### ① 训练数据（Training Data）
- **特征**：只读、超大总量（PB 级语料）、被反复扫（每个 epoch 全读一遍）。可能是**少量大分片**（如 webdataset 打包的 .tar）或**海量小文件**（原始图片）。
- **诉求**：**高顺序带宽** + 多节点并发读不互相拖累。打包成大分片是为了避开小文件的 IOPS 地狱。
- **典型放法**：并行文件系统（PFS）或对象存储（OBS）做主存，本地 NVMe 做缓存。

### ② Checkpoint（检查点）
- **特征**：**周期性、突发性的巨量写**。训练每隔 N 步把全部模型权重+优化器状态落盘，**写完之前训练通常要停**（同步 checkpoint）。
- **大小估算**：参数量 $P$，混合精度训练下 checkpoint 体量约为
$$\text{Size} \approx P \times (\underbrace{2}_{\text{fp16权重}} + \underbrace{4}_{\text{fp32主权重}} + \underbrace{4+4}_{\text{Adam的m和v}})\ \text{字节} = 14P\ \text{字节}$$
  即一个 70B 模型的 checkpoint 约 $70\times10^9 \times 14 \approx 980$ GB（接近 1TB！）。
- **诉求**：**极高的瞬时写带宽**（否则训练长时间停摆）。是数据中心存储的"心跳式负载"——平时很闲，一到点就井喷。

### ③ KV Cache（推理键值缓存）
- **特征**：**推理**时每个请求的注意力 K/V 张量，**显存放不下时下沉**到 CPU 内存或本地 NVMe（即 KV offload / 分级缓存）。访问高频、对**延迟极敏感**。
- **大小估算**：$\text{KV} = 2 \times L \times n_{kv} \times d_{head} \times \text{seq} \times \text{batch} \times \text{dtype}$（2 是 K 和 V，$L$ 层数）。长上下文场景下单请求可达数 GB。
- **诉求**：**超低延迟 + 高随机 IOPS**。这是本地 NVMe（甚至 NVMe-oF）大显身手的地方，详见 [[ai-infra/存储/nvme-ssd]]。

### ④ 日志 / 指标（Logs & Metrics）
- **特征**：持续不断的**小块追加写**（loss、lr、梯度范数、各 rank 的 metric）。单条很小，但频率高、来源多（成百上千个进程同时写）。
- **诉求**：高 IOPS、能容忍最终一致；带宽需求低。常落对象存储或专用日志系统，**不要和训练数据抢同一条 I/O 路径**。

> 一句话总结这一节：**别用一种存储伺候四种负载**。下一节的三层架构，就是为了把四类负载放到各自最合适的层。

## 3. 三层存储金字塔：PFS / 对象存储 / 本地 NVMe

这是 AI 存储架构的**核心心智模型**。从"远而大而慢而便宜"到"近而小而快而贵"，分三层：

```
          慢、大、便宜、共享
        ┌───────────────────────────────────────┐
        │   ③ 对象存储 (Object Storage, OBS)     │   ← 冷数据/原始语料/归档
        │   S3 / OSS / Ceph-RGW   PB~EB 级        │     HTTP API, 高吞吐, 高延迟
        └───────────────────────────────────────┘
                       ↑ 灌数据 / 归档
        ┌───────────────────────────────────────┐
        │   ② 并行文件系统 (Parallel FS, PFS)    │   ← 训练主战场/checkpoint
        │   Lustre / GPFS / BeeGFS / WekaFS       │     POSIX, 多节点聚合带宽
        └───────────────────────────────────────┘
                       ↑ 预取/缓存
        ┌───────────────────────────────────────┐
        │   ① 本地 NVMe SSD                       │   ← 缓存/KV offload/临时
        │   每节点直挂, μs 级延迟, GB/s 带宽      │     最快但不共享、易丢
        └───────────────────────────────────────┘
          快、小、贵、私有        见 [[ai-infra/存储/nvme-ssd]]
```

### 第①层：本地 NVMe SSD（最快，私有）
- **是什么**：插在 GPU 节点 PCIe 总线上的固态盘，离 CPU/GPU 最近。延迟 μs 级，单盘顺序带宽数 GB/s（详见 [[ai-infra/存储/nvme-ssd]]）。
- **解决什么**：① 当训练数据的**本地缓存**（第一个 epoch 从 PFS 拉，之后从本地读）；② KV cache 的 **offload 落点**；③ 临时 scratch 空间。
- **权衡**：最快，但**不共享**（A 节点的盘 B 节点看不见）、**易失**（节点挂了数据没了），所以只放"丢了能重建"的东西。

### 第②层：并行文件系统 PFS（训练主战场）
- **是什么**：把几十上百台存储服务器的盘**聚合成一个统一的 POSIX 文件系统**，对训练进程透明（像访问本地目录一样 `/data/...`）。代表：Lustre、GPFS/Spectrum Scale、BeeGFS、WekaFS。
- **核心机制——为什么能快**：一个大文件被**条带化（striping）**切成块，分散到 N 台存储服务器上；读时 N 台**同时**吐数据，带宽叠加。

```
   一个 100GB 文件 → 按 stripe 切块 → 散到 4 台存储服务器
        ┌──block0──┐┌──block1──┐┌──block2──┐┌──block3──┐
   读取: │ Server0 ││ Server1 ││ Server2 ││ Server3 │  ← 4 路并行
        └────┬────┘└────┬────┘└────┬────┘└────┬────┘
             └──────────┴───聚合带宽────┴──────────┘ → 客户端
```
- **解决什么**：训练数据共享读 + checkpoint 高带宽写。**所有 GPU 节点看到同一份数据**，无需各自拷贝。
- **关键参数（讲含义不背默认值）**：
  - **stripe count（条带数）**：一个文件铺到几台服务器。越大单文件带宽越高，但元数据开销和小文件浪费也大。
  - **stripe size（条带块大小）**：每块多大。大块利于顺序大文件，小块利于随机。
  - **元数据服务器（MDS/MDT）**：管理"文件名→数据在哪"。**海量小文件会把 MDS 压垮**——这是 PFS 最常见的瓶颈。
- **权衡**：聚合带宽极高、强一致 POSIX，但**部署运维复杂**、小文件元数据是软肋、成本高于对象存储。

### 第③层：对象存储 OBS（最便宜，海量）
- **是什么**：用 **HTTP API（PUT/GET key→value）** 存"对象"，没有目录树和 POSIX 语义。代表：AWS S3、阿里云 OSS、MinIO、Ceph RGW。容量近乎无限，按量付费。
- **解决什么**：存**原始语料库、数据集归档、冷 checkpoint**。便宜（每 TB/月成本远低于 PFS）、跨地域、11 个 9 的持久性（以各云官方为准）。
- **权衡**：**延迟高**（HTTP 往返几十 ms）、**无随机改写**（对象通常整体覆盖）、**最终一致**。所以**不直接拿来当训练时的 random-access 文件系统**，而是配合"打包成大分片 + 流式顺序读"使用。

### 三层如何协作（数据流）

```
   [对象存储 OBS]  原始语料/归档 (PB, 冷, 便宜)
        │  ① 预处理/打包成大分片(.tar/.parquet), 灌入
        ▼
   [并行文件系统 PFS]  训练数据 + checkpoint (TB~PB, 温, 高带宽共享)
        │  ② 训练时按 epoch 预取
        ▼
   [本地 NVMe 缓存]  当前 epoch 的热分片 (热, μs 延迟, 私有)
        │  ③ DataLoader 读出 → 解码 → 组 batch
        ▼
   [CPU 内存] → (H2D 拷贝) → [GPU 显存]  ← 真正喂给计算
```

## 4. 带宽与 IOPS：顺序 vs 随机，到底谁卡谁

这是存储选型最容易踩坑的地方。同一块盘，**读法不同，性能能差几十倍**。

```
   顺序大块读 (Sequential)        随机小块读 (Random)
   ┌─┬─┬─┬─┬─┬─┬─┬─┐             ┌─┐  ┌─┐    ┌─┐ ┌─┐
   │█│█│█│█│█│█│█│█│  连续        │█│  │█│    │█│ │█│  到处跳
   └─┴─┴─┴─┴─┴─┴─┴─┘             └─┘  └─┘    └─┘ └─┘
   → 拼带宽, 跑满 GB/s            → 拼 IOPS+延迟, 带宽跑不满
   (大分片/checkpoint)           (小文件/随机shuffle)
```

**为什么随机读慢**：每次随机读都要付**一次完整的延迟代价**（寻址、协议往返），而且无法预取。读 100 万个 4KB 小文件：
$$\text{若 IOPS}=20\text{万},\quad \text{耗时}=\frac{10^6}{2\times10^5}=5\text{ 秒},\quad \text{但只搬了 }10^6\times4\text{KB}=4\text{ GB}$$
有效带宽仅 $4/5 = 0.8$ GB/s——盘标称 7GB/s 也没用。

**工程上的破解办法**（三招）：
1. **打包（packing）**：把海量小文件预先打成大分片（webdataset .tar、Parquet、TFRecord），把"随机读小文件"变成"顺序读大文件 + 内部偏移"。**这是大模型数据工程的第一原则。**
2. **shuffle buffer（缓冲洗牌）**：要随机性？不在磁盘层做随机寻址，而是**顺序读入一个内存缓冲区，再在内存里 shuffle**。磁盘看到的永远是顺序读。
3. **多并发 / 队列深度（QPS / queue depth）**：NVMe 靠**深队列**把多个 I/O 排队并发，掩盖单次延迟。`num_workers` 多进程预取就是这个道理。

> 记住口诀：**大文件拼带宽，小文件拼 IOPS；能打包就打包，能顺序就别随机。**

## 5. 数据加载流水线：从磁盘到 GPU 的接力赛

存储再快，如果 CPU 解码跟不上、拷贝跟不上，GPU 照样饿。所以要把整条链路看成一条**流水线（pipeline）**，每一棒都不能掉。

```
   [存储] →(读)→ [CPU 解码/增广] →(组batch)→ [Pinned 内存] →(H2D拷贝)→ [GPU]
     ①磁盘I/O      ②CPU计算          ③内存          ④PCIe搬运      ⑤计算
        │              │                                │
        └─ num_workers 多进程预取 ─┘            └─ pin_memory + 异步拷贝 ─┘
```

**逐棒拆解（以 PyTorch DataLoader 为例，讲机制不背默认值）**：

- **① 读盘**：`num_workers` 个**子进程**并行从存储取数据。worker 越多并发 I/O 越深，越能掩盖延迟；但太多会爆 CPU/内存，且小文件下把 PFS 元数据压垮。
- **② 解码 / 数据增广**：图片 JPEG 解码、文本 tokenize、resize/crop 都吃 CPU。**这一棒常是真正的瓶颈**——人们误以为是磁盘慢，其实是 CPU 解码慢。可用 GPU 解码（如 DALI / nvJPEG）卸载。
- **③ prefetch（预取）**：在 GPU 算第 $i$ 个 batch 时，DataLoader 已经在后台准备第 $i{+}1$ 个 batch。`prefetch_factor` 控制每个 worker 预存几个 batch。**预取是隐藏 I/O 延迟的核心。**
- **④ pin_memory + 异步 H2D**：`pin_memory=True` 把 batch 放进**锁页内存（不会被换出）**，使 CPU→GPU 拷贝能用 DMA 异步进行，和计算重叠。
- **⑤ sharding（分片）**：分布式训练时，每个 rank 只读数据集的一个**不重叠子集**（用 `DistributedSampler` 或 webdataset 的 shard 划分），避免 N 个 GPU 重复读同一份、把存储带宽放大 N 倍。

**目标——让 I/O 时间被计算时间"藏住"**：
$$T_{\text{step}} = \max\big(T_{\text{compute}},\; T_{\text{dataload}}\big)\quad(\text{重叠理想时})$$
只要 $T_{\text{dataload}} \le T_{\text{compute}}$，存储就**完全不拖后腿**。所有优化的终极目标，就是把数据加载塞进计算的影子里。

```
   不重叠(串行):  |--load--||--compute--||--load--||--compute--|   慢
   重叠(流水线):  |--load--||--compute--|              ← load 被藏住
                          |--load--||--compute--|       快
```

## 6. Checkpoint：周期性巨写的存储难题与解法

第 2 节说过 checkpoint 是"心跳式巨写"。它有个致命问题：**同步 checkpoint 期间训练停摆**。

```
   朴素做法(同步):
   计算 → 停！全部权重落盘(几分钟) → 计算 → 停！落盘 → ...
                  ↑ GPU 全程空转, 越大的模型停得越久
```

**核心解法（讲机制）**：

1. **异步 checkpoint（async）**：先把权重**快速从显存拷到 CPU 内存**（快），然后让一个**后台线程慢慢写盘**，训练立刻继续。把"停摆时间"从"写盘时间"缩短到"显存→内存拷贝时间"。
2. **分片 checkpoint（sharded / distributed）**：不让 rank 0 一个人写整个模型，而是**每个 rank 只写自己那一份分片**，N 个节点**并行写**到 PFS，写带宽叠加 N 倍。这是 PFS 高聚合写带宽的主用武之地。
3. **去重 / 增量**：只存与上次 checkpoint 的**差异**，或对相同张量去重，省容量。
4. **多副本与生命周期**：近期 checkpoint 留在 PFS（快，可秒级恢复），老 checkpoint 滚到对象存储归档（便宜）。

**为什么写带宽这么关键**——手算停摆代价：一个 70B 模型 checkpoint 约 980GB（见第 2 节）。若 PFS 写带宽只有 10GB/s，单纯写盘就要 $980/10 \approx 98$ 秒；若用分片 + 异步，停摆能压到几秒甚至亚秒。每隔 1000 步存一次、训练几十万步，节省的累计停摆时间极其可观。

## 7. 数值例子 / 对照表 / 实践要点

### 例 1：训练数据需要多大顺序带宽？（手算）
设：1024 张 GPU，每卡每步处理 batch 中数据 1MB（解码后），每步耗时 100ms。
则集群每秒需要的数据量：
$$\frac{1024 \times 1\text{MB}}{0.1\text{s}} = 10240\ \text{MB/s} \approx 10\ \text{GB/s}$$
结论：存储系统至少要持续吐 **约 10GB/s** 才不拖后腿。单盘做不到（详见 [[ai-infra/存储/nvme-ssd]]），**必须靠 PFS 的聚合带宽 + 本地 NVMe 缓存**。

### 例 2：本地 NVMe 缓存能装下多少？（手算）
设：每节点本地 NVMe 8TB，数据集打包后 200TB。
则单节点缓存命中率上限 $\approx 8/200 = 4\%$。
结论：缓存装不下整份数据时，要么**只缓存热分片**，要么**用一致性哈希让不同节点缓存不同分片**协同覆盖。

### 三层存储对照表

| 维度 | 本地 NVMe | 并行文件系统 PFS | 对象存储 OBS |
|---|---|---|---|
| 典型延迟 | μs 级 | 亚 ms ~ ms | 几十 ms |
| 单位带宽 | 单盘 GB/s | 聚合可达数十~数百 GB/s | 高吞吐但单连接低 |
| 共享性 | 私有(单节点) | 全集群共享 | 全局共享(HTTP) |
| 持久性 | 弱(节点挂即丢) | 强 | 极强(多副本/EC) |
| 接口 | 块/本地 FS | POSIX | HTTP API(key-value) |
| 单位成本 | 高 | 中~高 | 低 |
| 最适合 | 缓存/KV offload/scratch | 训练数据共享读+checkpoint | 原始语料/归档/冷数据 |
| 软肋 | 不共享、易失 | 海量小文件压垮元数据 | 高延迟、无随机改写 |

### 四类负载 × 存储层 速查

| 负载 | 主诉求 | 推荐放法 |
|---|---|---|
| ① 训练数据 | 高顺序带宽、共享 | PFS 主存 + 本地 NVMe 缓存；先打包成大分片 |
| ② Checkpoint | 高瞬时写带宽 | PFS 分片+异步写；老的滚到 OBS |
| ③ KV cache | 超低延迟、高随机 IOPS | 显存→CPU 内存→本地 NVMe 分级 |
| ④ 日志/指标 | 高 IOPS、可最终一致 | OBS / 专用日志系统，独立 I/O 路径 |

### 实践要点（避坑清单）
- **先打包再训练**：海量小文件是 PFS 元数据杀手，务必预打包成 .tar/.parquet/.webdataset。
- **分布式必须 shard**：否则 N 个 GPU 重复读同一份数据，把存储压力放大 N 倍。
- **先查瓶颈在哪一棒**：GPU 空泡不一定是磁盘慢——常是 CPU 解码或拷贝慢。用 profiler 定位再优化。
- **checkpoint 用异步+分片**：别让训练为了存盘长时间停摆。
- **冷热分层**：热数据上 NVMe/PFS，冷数据沉 OBS，按生命周期自动迁移省钱。
- **别让四类负载抢同一条 I/O 路径**：日志写爆了能拖慢训练数据读。

## 常见问题

| 问题 | 解答 |
|---|---|
| 为什么不全用最快的本地 NVMe？ | 不共享(每节点各存一份浪费爆炸)、易失(节点挂数据没了)、容量装不下 PB 数据。 |
| 对象存储延迟那么高，怎么还用它存训练数据？ | 不直接随机读。先打包成大分片 + 流式顺序读/预取到 PFS/NVMe，把高延迟摊薄。 |
| 训练数据是大分片好还是小文件好？ | 几乎永远是大分片。小文件把带宽锁死在 IOPS 上限，还压垮 PFS 元数据。 |
| GPU 利用率低一定是存储慢吗？ | 不一定。可能是 CPU 解码、H2D 拷贝、甚至通信慢。必须先 profile 定位是哪一棒。 |
| checkpoint 为什么常成为瓶颈？ | 它是突发巨量写(70B 模型近 1TB)，同步写盘期间训练停摆。用异步+分片缓解。 |
| KV cache 为什么要 offload 到 NVMe？ | 长上下文/大并发时显存放不下 KV，下沉到 CPU 内存/本地 NVMe；对延迟极敏感，故选最快的本地盘。详见 [[ai-infra/存储/nvme-ssd]]。 |
| 带宽和 IOPS 我该看哪个？ | 看你读法：大文件顺序读看带宽；海量小文件/随机读看 IOPS 与延迟。 |
| PFS 的元数据服务器为什么常爆？ | 每个文件的"名字→位置"映射都过元数据服务器；海量小文件 = 海量元数据操作，把它压垮。 |
