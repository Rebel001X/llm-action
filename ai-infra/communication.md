## 0. 一句话锚点

**通信 = 多个计算单元（GPU）为了协同完成一个任务，把各自手里的中间数据"搬"给对方的过程。**

一个模型大到单卡放不下、或单卡算不快时，我们就把它切到 N 张卡上并行。但"切开"必然带来一个代价：每张卡只算了一部分，结果必须**汇总/交换**才能继续。这个汇总/交换就是通信。

> 核心矛盾：**算力（FLOPS）增长远快于互联带宽（GB/s）增长**。卡越快、卡越多，"等数据"的时间占比就越高，通信就成了天花板。

## 1. 地基/前置

把后面要用的原子概念先钉死，后文不再重复解释。

### 1.1 带宽与延迟（最容易混淆的一对）

- **带宽 Bandwidth**：单位时间能搬多少数据，单位 GB/s。像水管的"粗细"。
- **延迟 Latency**：一条消息从发出到对方收到的固定时间，单位 μs（微秒）。像水从管子一头流到另一头要等的"起步时间"。

一次传输的耗时模型（α-β 模型，必背）：

$$T = \alpha + \frac{n}{\beta}$$

- $\alpha$：固定延迟（启动开销，发一个字节也得付）
- $\beta$：带宽（GB/s）
- $n$：传输字节数

**直觉**：小消息被 $\alpha$ 主导（延迟敏感），大消息被 $n/\beta$ 主导（带宽敏感）。所以"小而多的通信"和"大而少的通信"优化方向完全不同。

```
耗时 T
 │
 │   小消息区        大消息区
 │  (延迟主导)      (带宽主导)
 │ ───────────╮
α├──────       ╲____斜率=1/β____
 │                              ╲___
 └───────────────────────────────────► 消息大小 n
```

### 1.2 数据类型的字节数（算通信量必备）

| 类型 | 字节/元素 | 常见用途 |
|------|-----------|----------|
| FP32 | 4 | 优化器状态、主权重 |
| FP16/BF16 | 2 | 训练激活/梯度 |
| FP8 | 1 | 前沿训练/推理 |

一个 7B（70 亿）参数模型，BF16 权重 = $7\times10^9 \times 2\text{B} = 14$ GB。记住这个换算，后面全靠它。

### 1.3 并行模式速记（通信由它决定）

| 并行 | 切什么 | 通信发生在哪 |
|------|--------|--------------|
| 数据并行 DP | 切数据（每卡完整模型副本） | 反向后同步**梯度** |
| 张量并行 TP | 切单层矩阵（行/列切） | 每层前向/反向都通信**激活** |
| 流水并行 PP | 切层（不同卡放不同层） | 层边界传**激活**（点对点） |
| 专家并行 EP | 切 MoE 的专家 | 路由时 **All-to-All** token |

记住一句：**TP 通信最密（层内）、PP 通信最稀（层间点对点）、DP 通信最大块（整套梯度）、EP 通信最不规则（All-to-All）。**

## 2. 为什么通信是分布式瓶颈

### 2.1 阿姆达尔/扩展性视角

设单卡计算时间 $T_{comp}$，加卡后引入通信时间 $T_{comm}$。理想 N 卡应快 N 倍，但实际：

$$T_{N} = \frac{T_{comp}}{N} + T_{comm}(N)$$

随 N 增大，$T_{comp}/N \to 0$，而 $T_{comm}$ 往往**不降反升**（卡越多要同步的对象越多）。于是曲线"压不下去"，这就是扩展性墙。

```
理想加速 (线性)        实际加速 (被通信压平)
speedup                speedup
  │      ╱               │     ╱‾‾‾‾‾  ← 通信封顶
  │     ╱                │    ╱
  │    ╱                 │   ╱
  │   ╱                  │  ╱
  └──────► GPU数          └──────► GPU数
```

- **强扩展（Strong scaling）**：问题规模固定，加卡求更快。通信占比上升最快，最难。
- **弱扩展（Weak scaling）**：每卡问题规模固定，加卡做更大的事。相对友好。

### 2.2 算力 vs 带宽的"剪刀差"（根因）

| 代际 | GPU 算力（BF16，约） | 机内互联（约） | 机间网络（约） |
|------|---------------------|----------------|----------------|
| 上一代 | 数百 TFLOPS | NVLink ~数百 GB/s | IB ~100–200 Gbps |
| 当代 | 接近/超过 PFLOPS 级 | NVLink ~900 GB/s+ | IB ~400 Gbps |

> 数据为典型公开量级，**以官方为准**。

算力几年涨了一个量级，但**机间网络只涨了约 2–4 倍**。结果：每做一份计算，可"配套"的通信带宽相对变少了——通信自然成为瓶颈。这就是为什么"重叠"和"减少通信量"是 AI-Infra 永恒主题。

### 2.3 一个直观的"计算/通信比"判据

定义算术强度（每搬 1 字节能做多少次浮点运算）。当一个并行方案的算术强度 **低于** 硬件的"计算/带宽比"时，该方案就是**通信受限（communication-bound）**，加再多算力也没用。这正是 Roofline 模型的分布式版本。

## 3. 通信层级（机内 vs 机间）

数据从一张卡到另一张卡，要走的"路"决定了快慢。路有等级：

```
┌──────────────────── 一台服务器(Node) ────────────────────┐
│                                                          │
│   GPU0 ──NVLink(900GB/s级)── GPU1 ──NVLink── GPU2 ...     │
│     │  全互联或经 NVSwitch                                 │
│     └── 机内最快层级                                       │
│                                                          │
│   GPU ──PCIe(数十GB/s)── CPU/内存  (GPU↔Host 慢通道)      │
│                                                          │
│              NIC/HCA 网卡 (RDMA)                          │
└──────────────────────────┬───────────────────────────────┘
                           │ InfiniBand / RoCE
              ┌────────────┴────────────┐
            Leaf 交换机              Leaf 交换机
              │                        │
            其他 Node               其他 Node
```

### 3.1 机内（同一台机器内的 GPU 之间）

- **NVLink / NVSwitch**：GPU 直连的高速私有总线，带宽约 900 GB/s 量级（当代，**以官方为准**），延迟极低。NVSwitch 让一台机内 8 卡做到"任意两卡全带宽全互联"。**机内通信首选走这里。**
- **PCIe**：通用总线，GPU↔CPU 内存、或没有 NVLink 时 GPU↔GPU 的退路，带宽只有 NVLink 的几十分之一（数十 GB/s 量级）。能避开就避开。

### 3.2 机间（跨服务器）

- **InfiniBand (IB)**：HPC/AI 集群主流，配 **RDMA**（远程直接内存访问）：网卡直接读写对端显存，**绕过 CPU 和操作系统内核**，省去拷贝和中断，延迟低到约 1–2 μs 量级。当代单端口约 400 Gbps（**以官方为准**）。
- **RoCE (RDMA over Converged Ethernet)**：在以太网上跑 RDMA，复用以太网生态、成本更友好，但对网络无损/拥塞控制（PFC/ECN）要求苛刻，调优更难。
- **GPUDirect RDMA**：让网卡直接 DMA 到/从 GPU 显存，不经过 CPU 内存中转，是机间高效通信的关键拼图。

> 带宽断层是关键认知：**NVLink ≫ IB ≫ PCIe（GPU↔Host）**。同样一次 AllReduce，能留在机内就别出机；必须出机时，机间这一跳往往是整条链路的瓶颈。

### 3.3 量级对照（典型公开值，约）

| 通道 | 带宽量级 | 延迟量级 | 用途 |
|------|----------|----------|------|
| NVLink/NVSwitch | ~900 GB/s | 亚 μs | 机内 GPU↔GPU |
| PCIe Gen5 x16 | ~64 GB/s（双向约128） | μs 级 | GPU↔Host、退路 |
| InfiniBand (单口) | ~50 GB/s (400Gbps) | ~1–2 μs | 机间 RDMA |

注意单位：网络习惯用 **Gbps（比特/秒）**，1 字节=8 比特，400 Gbps = 50 GB/s。算通信量时务必统一到字节。

## 4. 集合通信原语（Collective Communication）

多卡协同的"标准动作"。由 **NCCL**（NVIDIA Collective Communication Library）等库实现，被 PyTorch DDP/FSDP、Megatron、DeepSpeed 调用。详见 [[ai-infra/网络/集合通信原语]]。

设 P 张卡，每卡一份大小为 V 的数据。下面用 ASCII 把每个原语"画"出来。

### 4.1 Broadcast（广播）：一份发给所有人
```
卡0:[A]  卡1:[ ]  卡2:[ ]  卡3:[ ]
              ↓ broadcast
卡0:[A]  卡1:[A]  卡2:[A]  卡3:[A]
```
用途：把初始权重/超参从 rank0 发给所有卡。

### 4.2 Reduce / AllReduce（规约 / 全规约）
Reduce：所有卡的数据按 op（如 sum）聚到一张卡；**AllReduce = Reduce 后再 Broadcast**，结果人手一份。
```
卡0:[1]  卡1:[2]  卡2:[3]  卡3:[4]
           ↓ AllReduce(sum)
卡0:[10] 卡1:[10] 卡2:[10] 卡3:[10]   (1+2+3+4=10)
```
用途：**数据并行同步梯度的主力**。

### 4.3 AllGather（全收集）：把各自的拼成完整的
```
卡0:[A]  卡1:[B]  卡2:[C]  卡3:[D]
           ↓ AllGather
卡k: [A B C D]  (每卡都有全集)
```
用途：FSDP/ZeRO 在前向时把分片的权重临时拼回完整层。

### 4.4 ReduceScatter（规约散射）：边求和边切分
```
卡0:[a0 a1 a2 a3]  卡1:[b0 b1 b2 b3] ...
   ↓ ReduceScatter(sum)，卡k 只拿第k段的和
卡0:[Σ_0]  卡1:[Σ_1]  卡2:[Σ_2]  卡3:[Σ_3]
```
关键等式（FSDP/ZeRO 核心）：

$$\text{AllReduce} = \text{ReduceScatter} + \text{AllGather}$$

### 4.5 All-to-All（全交换）：转置式重排
每张卡都给其他每张卡发一块不同的数据，像矩阵转置。
```
        发往→ 卡0 卡1 卡2 卡3
卡0 发:  [00][01][02][03]      收后 卡0:[00][10][20][30]
卡1 发:  [10][11][12][13]  ⇒  收后 卡1:[01][11][21][31]
卡2 发:  [20][21][22][23]      ...
卡3 发:  [30][31][32][33]
```
用途：**MoE 专家并行**按路由把 token 发到对应专家所在卡，是 EP 的标志性、也最难优化的通信（不规则、易拥塞）。字节跳动 Flux/COMET 等正是针对此做计算-通信融合优化（见底部链接）。

### 4.6 环形 AllReduce 为何带宽最优（直觉）

朴素 AllReduce 让一张卡汇总全部，它会被打爆。**Ring（环形）算法**把数据切成 P 块，沿环转 $2(P-1)$ 步（前半 ReduceScatter、后半 AllGather），每步每卡只收发 1/P，使**总传输量与卡数 P 几乎无关**，逼近带宽下限：

$$T_{ring} \approx 2(P-1)\alpha + 2\frac{P-1}{P}\cdot\frac{V}{\beta} \xrightarrow{P\text{大}} \frac{2V}{\beta}$$

含义：**一次 AllReduce 的有效通信量约等于 2V（每卡），与卡数基本无关**——这是后面通信量分析的基石。

## 5. 通信量分析（每种并行传多少字节）

把"传多少"算清楚，才能预测瓶颈。下面 $\Psi$ = 模型参数量，字节按 BF16=2B。

### 5.1 数据并行 DP（同步梯度）
每个 step 反向后做一次梯度 AllReduce。按 §4.6，每卡通信量约：

$$C_{DP} \approx 2 \times (\text{梯度字节}) = 2 \times 2\Psi = 4\Psi \ \text{字节/卡/step}$$

特点：**与 batch 无关、与卡数基本无关**，但每 step 都来一发，且发生在反向尾部——天然适合与反向计算**重叠**（§6）。

### 5.2 ZeRO/FSDP（分片，用通信换显存）
权重/梯度/优化器状态切成 P 片省显存，代价是前向要 AllGather 拼权重、反向要 ReduceScatter 聚梯度：

$$C_{FSDP} \approx \underbrace{2\Psi}_{\text{AllGather}} + \underbrace{2\Psi}_{\text{ReduceScatter}} = 4\Psi \ \text{字节/卡}$$

量级与 DP 同阶，但把通信"摊"到了每一层，更好重叠；省下大量显存。**通信换显存**的经典权衡。

### 5.3 张量并行 TP（层内切矩阵）
列并行 + 行并行配对，**每个 Transformer 块的前向需 2 次 AllReduce，反向再 2 次**，传的是**激活**而非权重：

$$C_{TP} \propto (\text{batch} \times \text{seq} \times \text{hidden}) \quad \text{每层都来}$$

特点：通信量随 **batch×序列长** 增长，且**频繁、在关键路径上、难以隐藏**。所以 TP 几乎只在**机内**用（靠 NVLink 抗住），一出机就崩。

### 5.4 流水并行 PP（层间点对点）
相邻 stage 只在层边界用 **Send/Recv（P2P）** 传一份激活，通信量小：

$$C_{PP} \propto (\text{batch} \times \text{seq} \times \text{hidden}) \quad \text{仅在 stage 边界}$$

代价不是带宽而是**气泡（bubble）**：流水启动/排空阶段部分卡空转。气泡占比 ≈ $\frac{P-1}{M+P-1}$（M=微批数），所以**多塞微批**来摊薄气泡。

### 5.5 专家并行 EP（MoE）
每层两次 **All-to-All**（dispatch 把 token 发给专家、combine 收回结果），通信量随**被路由 token 数 × hidden** 走，且不规则、易热点。是 MoE 训练/推理的头号通信难题。

### 5.6 一张表收口

| 并行 | 原语 | 传的内容 | 量级 | 在不在关键路径 |
|------|------|----------|------|----------------|
| DP | AllReduce | 梯度 | ~4Ψ/卡/step | 反向尾部，可重叠 |
| FSDP/ZeRO | AllGather+ReduceScatter | 权重+梯度 | ~4Ψ/卡 | 逐层，可重叠 |
| TP | AllReduce | 激活 | ∝bs·seq·h，每层×4 | **是，难隐藏** |
| PP | Send/Recv | 激活 | 小，仅边界 | 边界，靠气泡管理 |
| EP | All-to-All | token | ∝路由token·h | **是，易热点** |

## 6. 计算通信重叠（Overlap）

详见 [[llm-optimizer/计算通信重叠]]。核心思想一句话：**让 GPU 一边算、一边在后台搬数据，把通信时间"藏"进计算时间里。**

### 6.1 为什么能藏

GPU 的计算引擎（SM）和数据搬运（DMA/copy engine、NIC）是**不同的硬件单元，可并行工作**。只要让通信用独立的 CUDA stream，它就能和计算 stream 同时跑。

```
不重叠 (串行)：
 计算████████  通信░░░░  计算████████  通信░░░░   → 总时长 = 计算+通信
 时间 ──────────────────────────────────────►

重叠 (并行)：
 计算████████████████████                        ← 计算流
 通信     ░░░░░░░░    ░░░░░░░░                     ← 通信流(后台)
                                                  → 总时长 ≈ max(计算, 通信)
```

理想下：$T = \max(T_{comp}, T_{comm})$ 而非 $T_{comp}+T_{comm}$。当 $T_{comm}<T_{comp}$ 时，**通信完全免费**。

### 6.2 三个经典手法

1. **梯度桶 + 反向重叠（DDP）**：反向是从后往前算的，先算完的层的梯度先打包成"桶"立刻 AllReduce，不等整套反向结束。后面的层还在算，前面的梯度已在传。
2. **FSDP prefetch**：算第 i 层时，后台 AllGather 第 i+1 层的权重，算到时正好就位。
3. **TP/序列并行 + 计算融合**：把 All-to-All / AllReduce 拆细，和 GEMM 分块交错（如 Flux/COMET 把通信算子融进 kernel），消除暴露的通信。

### 6.3 重叠不是免费午餐（权衡）

- 通信会**抢占 SM 资源**（NCCL kernel 也占 SM），重叠后计算可能轻微变慢。
- 需要额外 buffer（prefetch 的权重要先存着），**多吃显存**。
- 切太碎 → 每块都付一次延迟 $\alpha$，小消息把延迟项放大。**粒度要调。**

判据：当**暴露通信时间**（exposed comm = 没被算盖住的部分）→ 0，就榨干了重叠收益。

## 7. 网络拓扑（Topology）

拓扑 = 交换机和网卡怎么连。它决定了"任意两卡之间有没有快路、会不会堵车"。详见 [[ai-infra/ai-hardware/GPU-network]]。

### 7.1 关键指标

- **对分带宽 Bisection BW**：把集群劈成两半，跨越切口的总带宽。越高越能扛 AllReduce 这类全局通信。
- **直径/跳数 Hops**：两点间最多过几台交换机，影响延迟。
- **收敛比 Oversubscription**：上行带宽 < 下行带宽的比例。1:1 叫**无阻塞（non-blocking）**，AI 集群追求于此。

### 7.2 Fat-Tree / Clos（数据中心主流）
多级交换机，上层不断加宽以保证任意机架间满带宽，可做到无阻塞。
```
              Spine  Spine  Spine        ← 核心层(加宽)
               │  ╲ ╱ │ ╲ ╱ │
              Leaf   Leaf   Leaf         ← 汇聚层
              ╱│╲    ╱│╲    ╱│╲
            Node...Node...Node...        ← 服务器(机架)
```
优点：规整、无阻塞、易扩展；缺点：交换机和线缆多、贵。

### 7.3 Rail-optimized（轨道优化，AI 集群常用）
每台机的第 k 张网卡都连到第 k 个独立的 Leaf 平面（"轨道"）。同号 GPU 跨机走自己的专用轨，AllReduce 不互相打架。
```
Node A: NIC0─轨0─┐   NIC1─轨1─┐
Node B: NIC0─轨0─┤   NIC1─轨1─┤
                Leaf-Rail0      Leaf-Rail1
```
优点：把"同号 GPU 互联"做成无阻塞，特别契合数据并行/张量并行的通信模式。

### 7.4 Torus / Mesh（环面/网格，TPU、部分 NPU）
GPU/芯片排成 2D/3D 网格，每个只连最近的邻居，环形闭合。
```
●─●─●─●
│ │ │ │
●─●─●─●     (再各自首尾相连成环面)
│ │ │ │
●─●─●─●
```
优点：连线规整、成本低、近邻通信（如 Ring AllReduce）天然高效；缺点：远点跳数多，全局通信不如 Fat-Tree。

### 7.5 Dragonfly（超大规模）
组内全互联 + 组间少量长链，降低线缆数和直径，适合超大集群。优点是性价比与可扩展，缺点是路由复杂、易局部拥塞。

### 7.6 拓扑感知很重要
NCCL 会**探测拓扑**，自动选最优算法与路径（Ring vs Tree、走哪条链）。运维要做的是**让逻辑并行映射匹配物理拓扑**：把 TP 组放进同一台机（吃 NVLink），DP 组沿同一条 rail 跨机。错配会让本可机内的通信被迫出机，性能断崖。

## 8. 数值例子 / 对照 / 实践

### 8.1 手算：7B 模型数据并行的梯度同步耗时
- 参数 $\Psi=7\times10^9$，BF16 梯度 = $14$ GB。
- DP AllReduce 每卡通信量 ≈ $2\times14=28$ GB（§4.6）。
- 走 NVLink（~900 GB/s）：$28/900 \approx 31$ ms。
- 走单口 IB（400 Gbps = 50 GB/s）：$28/50 = 560$ ms。

**结论**：同一次同步，出机比机内慢了约 **18 倍**。这就是"能机内别出机"的硬数字。

### 8.2 手算：重叠的收益
设单 step 反向计算 200 ms，梯度同步（机内）31 ms。
- 不重叠：$200+31 = 231$ ms。
- 完美重叠：$\max(200,31)=200$ ms。
- **省下 31 ms，约 13% 提速**，且通信"白嫖"。若机间 560 ms > 200 ms，则变成**通信受限**，重叠也只能压到 560 ms——这时必须先**降通信量**（FP8 梯度、分级 AllReduce）。

### 8.3 手算：单位换算别踩坑
"400 Gbps 网卡，传 10 GB 要多久？"
- 400 Gbps = 400/8 = 50 GB/s。
- $10 / 50 = 0.2$ s = 200 ms。
- 若错按 400 GB/s 算会得 25 ms，**差 8 倍**——比特/字节混淆是最常见低级错误。

### 8.4 选型对照

| 场景 | 优先 | 原因 |
|------|------|------|
| 机内 8 卡 TP | NVLink/NVSwitch | 层内高频通信，唯有 NVLink 抗住 |
| 跨机数据并行 | IB/RoCE + 重叠 | 大块梯度，块大可重叠 |
| MoE EP | All-to-All + rail 拓扑 + 融合算子 | 缓解不规则热点 |
| 省显存优先 | FSDP/ZeRO | 通信换显存 |

## 9. 常见问题

| 问题 | 答案 |
|------|------|
| 通信和带宽不够，先优化哪个？ | 先看"暴露通信"。能重叠的先重叠（不花钱）；藏不住再降通信量（FP8/分级）；最后才谈换硬件 |
| 为什么 TP 不能跨机？ | TP 每层都 AllReduce 激活、在关键路径、无法隐藏；机间带宽低十几倍，直接拖垮 |
| AllReduce 为什么和卡数无关？ | Ring 算法每卡每步只收发 1/P，总量逼近 2V，与 P 基本解耦 |
| Gbps 和 GB/s 怎么换？ | ÷8。400 Gbps = 50 GB/s。算通信务必统一到字节 |
| RDMA 到底快在哪？ | 网卡直读写对端显存，绕过 CPU/内核/拷贝，延迟降到 μs 级 |
| 重叠是免费的吗？ | 不是。抢 SM、吃额外显存、切太碎放大延迟，粒度需调 |
| 气泡（bubble）是通信问题吗？ | 是 PP 的计算空转，非带宽问题；靠增加微批数摊薄 |
| MoE 为什么通信最头疼？ | All-to-All 不规则、易热点拥塞；需融合算子（Flux/COMET）救 |
