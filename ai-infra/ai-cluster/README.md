## 0. 一句话锚点

**AI 训练集群 = GPU 节点 (算) + 高速网络 (连) + 共享存储 (喂) + 调度系统 (管)。**

一个直观的类比：

```
        单张 GPU           =  一个工人
   一台 8 卡服务器(节点)   =  一个工位(8 人围一张桌子)
   一个机柜(rack)         =  一个车间(几张工位)
   整个集群               =  一座工厂
   ┌─────────────────────────────────────────┐
   │  网络  = 工厂的传送带(工位之间传零件)    │
   │  存储  = 工厂的原料仓库(图纸/原材料)      │
   │  调度  = 工厂的排班主管(谁干什么活)       │
   └─────────────────────────────────────────┘
```

为什么需要"集群"而不是一台超强机器？因为大模型训练有两堵墙：
- **显存墙**：一个 70B 模型，仅参数 (FP16) 就要 $70\times10^9 \times 2\,\text{B} = 140\,\text{GB}$，加上梯度、优化器状态、激活值，单卡 80GB 根本放不下，必须切分到多卡（见 [[00-知识地图]] 里的并行策略）。
- **算力墙**：训一个万亿 token 的模型，单卡要算几十年，必须几千卡并行。

> 核心矛盾：**一旦切分到多卡，卡与卡之间就要频繁交换数据（梯度、激活）。** 这个"交换"快不快，决定了集群是"超级计算机"还是"一堆各干各的服务器"。网络因此成为 AI 集群的灵魂。

## 1. 地基 / 前置

### 1.1 一个最小知识：GPU 为什么要"互联"

数据并行 (Data Parallel) 下，每张卡算自己那份数据的梯度，然后所有卡要把梯度**求平均**——这就是 **AllReduce** 集合通信（见 [[ai-infra/网络/InfiniBand]] 与集合通信原语）。每一步训练都要做一次。如果网络慢，所有 GPU 都在"等"，算力白白浪费。

```
   step 计算  →  AllReduce(同步梯度)  →  step 计算  →  AllReduce  → ...
   ┌────────┐    ┌──────────────┐
   │ GPU 算 │    │ 网络在传梯度  │   ← 这段时间 GPU 在干等就是浪费
   └────────┘    └──────────────┘
```

### 1.2 GPU 互联的"三个层级"（速度从快到慢）

| 层级 | 在哪里 | 典型技术 | 典型带宽(单向，约) | 谁连谁 |
|---|---|---|---|---|
| 卡内/板内 | 一台服务器内部 | **NVLink / NVSwitch** | 数百 GB/s 级 | 同节点 8 卡互联 |
| 节点间 | 服务器到服务器 | **InfiniBand / RoCE** | 单口 200~400 Gb/s | 跨节点 GPU |
| 管理 | 全集群 | 普通以太网 | 1~25 Gb/s | 控制/监控 |

> 数量级直觉：NVLink (GB/s, 字节) 比 IB (Gb/s, 比特) 快约一个数量级。$1\,\text{GB/s} = 8\,\text{Gb/s}$，换算时务必小心**大 B (字节) 和小 b (比特)**。

补充一个本仓库已有的硬件事实：**A800 是 A100 的"特供版"，只把 NVLink 高速互连带宽从约 600 GB/s 降到约 400 GB/s，其余规格基本不变**（以官方为准）。这正说明：在大集群里，互联带宽被当作最敏感的指标来"卡"。

## 2. 集群组成（一）：GPU 节点内部

一台典型的 8 卡训练服务器（以 NVIDIA HGX 形态为例，规格"约/以官方为准"）：

```
            一台 GPU 服务器(节点 / node)
 ┌──────────────────────────────────────────────────────────┐
 │  CPU0 ── PCIe ─┐                          ┌─ PCIe ── CPU1  │
 │                │                          │               │
 │   ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐                  │
 │   │GPU0  │──│GPU1  │──│GPU2  │──│GPU3  │   全部 GPU 经     │
 │   └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘   NVSwitch 全互联 │
 │      └─────────┴───NVSwitch───┴─────────┐                  │
 │   ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐│                  │
 │   │GPU4  │──│GPU5  │──│GPU6  │──│GPU7  │┘                  │
 │   └──────┘  └──────┘  └──────┘  └──────┘                  │
 │      │        │         │         │                       │
 │   [NIC0]   [NIC1]    [NIC2]    [NIC3] ... (每卡配一张 IB)  │
 │   本地 NVMe SSD(暂存/缓存) ·  内存 1~2 TB                   │
 └──────────────────────────────────────────────────────────┘
        │ │ │ │  8 张 IB/RoCE 网卡 → 出节点 → 计算网交换机
```

关键设计点，逐个说"为什么"：

1. **8 卡通过 NVSwitch 全互联**：任意两卡之间都是满带宽，不分远近。这样节点内的 AllReduce/AllGather 极快，是"切分模型时优先切在节点内"的物理原因（张量并行 TP 通常只在节点内做）。
2. **每张 GPU 配一张独立网卡 (NIC)**：常见 8 GPU 配 8 张 IB 卡，让每张卡都有自己的"出口带宽"，避免抢路。这是后面 **Rail 拓扑**的前提。
3. **GPUDirect RDMA**：网卡可以**绕过 CPU 和系统内存**，直接把数据从本节点 GPU 显存搬到远端 GPU 显存。少了 CPU 中转，延迟和带宽都更好。
4. **本地 NVMe**：放数据缓存、临时 checkpoint，减轻共享存储压力。

## 3. 集群组成（二）：三张网络

很多人以为集群只有一张网，其实**至少三张物理隔离的网**：

```
                  ┌───────────────── 集群三张网 ─────────────────┐
   ① 计算网(后端 / Backend, GPU↔GPU)
      技术: InfiniBand 或 RoCE(以太网跑 RDMA)
      用途: AllReduce 同步梯度、TP/PP 通信  ← 决定训练速度
      带宽: 每节点 8×(200~400Gb/s)，要求"无阻塞"

   ② 存储网(前端 / Frontend / 南北向)
      技术: 高速以太网或独立 IB
      用途: 节点 ↔ 并行文件系统 / 对象存储(读数据、写ckpt)

   ③ 管理网(带外 / Out-of-Band, OOB)
      技术: 普通千兆/万兆以太网 + BMC/IPMI
      用途: 开关机、监控温度、装系统、收日志(GPU 不参与)
                  └──────────────────────────────────────────────┘
```

为什么要分开？因为**带梯度的计算流量绝对不能被读数据、传日志的流量挤占**——一旦计算网拥塞，全集群 GPU 集体卡住。物理隔离是最稳妥的"保护带宽"手段。

> 计算网技术对比（详见 [[ai-infra/网络/InfiniBand]] 与 [[ai-infra/网络/roce]]）：
> - **InfiniBand**：原生为 HPC 设计，低延迟、无损、生态成熟（NCCL 一等公民），贵、需专用交换机。
> - **RoCE (RDMA over Converged Ethernet)**：在以太网上跑 RDMA，复用以太生态、便宜，但要靠 PFC/ECN 做无损配置，调优更费心。

## 4. 网络拓扑：胖树 (Fat-Tree) 与 Rail-Optimized

### 4.1 为什么拓扑很重要

交换机端口有限（如一台 64 口）。要连几千张卡，必须多层交换机堆叠。**怎么堆，决定了"任意两卡之间还能不能跑满带宽"**。

### 4.2 胖树 (Fat-Tree / Clos)：保证无阻塞

朴素树形（根部带宽不变）会在顶层被"卡脖子"。胖树的思想：**越往上，链路越"粗"**，让上行总带宽 = 下行总带宽，做到 **非阻塞 (non-blocking)**。

```
            ┌─ Spine(脊) ─┐  ┌─ Spine ─┐   ← 顶层，上行带宽=下行
            │  交换机      │  │ 交换机  │
            └──┬───┬───┬──┘  └─┬──┬──┬─┘
   上下行 1:1   │   │   │       │  │  │
            ┌──┴─┐┌┴──┐┌┴───┐ ...   (Leaf 层 / 接入)
            │Leaf││Leaf││Leaf│
            └─┬──┘└─┬─┘└─┬──┘
              ▼      ▼     ▼
          [节点][节点][节点] ...

   "无阻塞"= 任意一半节点同时给另一半节点发数据，都不会因为
            上层链路不够而降速。代价:交换机和光模块数量巨大、贵。
```

收敛比 (oversubscription) $= \dfrac{\text{下行带宽}}{\text{上行带宽}}$。$1:1$ 即完全无阻塞；$2:1$ 表示上行只有下行的一半，省钱但可能拥塞。AI 后端计算网通常追求 **1:1 无阻塞**。

### 4.3 Rail-Optimized（轨道优化）：为 AI 量身定制

回忆 §2：每个节点有 8 张网卡 (NIC0~NIC7)。Rail 的核心约定：

> **所有节点的第 $k$ 号网卡，连到第 $k$ 号 Leaf 交换机（叫第 $k$ 条 "rail / 轨道"）。** 即 8 条平行轨道，编号相同的卡走同一条轨道。

```
   节点A: NIC0─┐ NIC1─┐ ...        节点B: NIC0─┐ NIC1─┐
              │      │                        │      │
   Rail-0 交换机 ◄───┼───────────────── 节点B-NIC0  │
   Rail-1 交换机 ◄──────┼─────────────────── 节点B-NIC1
   ...
   Rail-7 交换机

   好处: NCCL 做 AllReduce 时，每个 GPU 在自己专属轨道上通信，
        8 条轨道完全并行、互不抢占 → 把节点 8 张卡的带宽全榨出来。
        同号 GPU 之间往往一跳直达(Leaf 内)，延迟最低。
```

实践中常把 **Rail（保证同号卡高速）** 与 **Fat-Tree（保证跨号卡也能通）** 组合：轨道内一跳直达，跨轨道再上 Spine。这与 [[ai-infra/网络/Spine-Leaf和InfiniBand网络架构区别简述]] 描述的 Spine-Leaf 思路一脉相承。

## 5. 存储：把数据"喂"进 GPU

GPU 很贵，绝不能让它"等数据"。存储要同时满足两个矛盾需求：**海量数据高吞吐顺序读** + **超大 checkpoint 瞬间写**。

```
   ┌──────────────────────────────────────────────────────┐
   │ 训练数据(冷, PB 级)  →  对象存储(S3/OSS)  便宜、海量    │
   │        │ 预取/缓存                                     │
   │        ▼                                              │
   │ 高速层(热)  →  并行文件系统(Lustre/GPFS/BeeGFS)        │
   │              多个存储节点并行供数 → 聚合吞吐 TB/s 级    │
   │        │                                              │
   │        ▼  DataLoader 多进程预取                        │
   │ 节点本地 NVMe 缓存  →  GPU 显存                         │
   └──────────────────────────────────────────────────────┘
   写 checkpoint: 几千卡同时写 → 瞬时洪峰 →
        策略: 分片/异步/分层(先写本地NVMe再后台刷到远端)
```

要点："**读**"靠**并行文件系统**把吞吐做大（很多存储节点同时供数）；"**写 ckpt**"是周期性洪峰，靠**异步 + 本地暂存**削峰，避免几千卡同时写把存储网打满、拖慢训练。

## 6. 调度：Slurm vs Kubernetes

调度器解决：**几百个用户 / 几千张卡，谁的作业先跑、跑在哪几张卡上、跑完怎么回收。**

### 6.1 关键概念：Gang Scheduling（成组调度）

分布式训练要求 **N 张卡同时就位**才能开跑——只给 3/4 的卡毫无意义，反而占着不放导致死锁。**Gang 调度 = 要么一次性凑齐全部所需 GPU 才启动，要么一张都不占。** 这是 AI 调度和普通 Web 服务调度最大的区别。

### 6.2 Slurm vs Kubernetes 对比

```
   ┌──────────── Slurm(HPC 阵营) ───────────┐  ┌──────── Kubernetes(云原生) ────────┐
   │ sbatch 提交批作业                       │  │ 提交 Pod / Job / 自定义资源(CRD)    │
   │ 静态分区(partition)、队列、抢占          │  │ 弹性、声明式、自愈、生态庞大        │
   │ 原生 MPI/IB 友好，HPC 几十年积累         │  │ 默认无 Gang，需 Volcano/Kueue 等插件 │
   │ 轻量、调度延迟低、超大规模成熟           │  │ 容器化天然，CI/CD、多租户、可观测好   │
   │ 偏"裸金属 + 科研" 场景                   │  │ 偏"平台化 + 工程化生产" 场景          │
   └─────────────────────────────────────────┘  └─────────────────────────────────────┘
```

| 维度 | Slurm | Kubernetes |
|---|---|---|
| 作业模型 | 批作业 (batch job) | 容器 Pod / Job |
| 成组调度 | 原生支持 | 需插件 (Volcano / Kueue / Koordinator) |
| GPU 接入 | 直接、生态老到 | NVIDIA Device Plugin + GPU Operator |
| 弹性/自愈 | 较弱 | 强（声明式、控制器自动拉起） |
| 学习/运维成本 | 较低 | 较高（组件多） |
| 典型用户 | 超算中心、科研 | 互联网公司、AI 平台 (MLOps) |

> 何时用谁：纯训练、追求极致网络效率、团队懂 HPC → **Slurm**；要和在线服务/CI 统一平台、多租户、追求工程化与可观测 → **Kubernetes**（见 [[llmops/kubernetes]]）。现实中也常见"K8s 管平台、底层 Slurm 管训练"或用 Volcano 让 K8s 具备 HPC 调度能力的混合方案。具体组件版本/用法**以官方文档为准**。

## 7. 故障容错：万卡每天都坏

铁律：**集群越大，故障越频繁。** 直觉公式——若单卡日故障率为 $p$，$N$ 卡集群"当天至少一处故障"的概率：

$$P_{\text{fail}} = 1 - (1-p)^N$$

只要 $N$ 足够大，$P_{\text{fail}}$ 迅速逼近 1（数值见末节）。所以容错不是"锦上添花"，是**必备能力**。

```
   故障类型           应对手段
   ───────────────    ──────────────────────────────────────
   GPU 掉卡/ECC 报错   健康检查剔除 → 调度器把作业重排到好卡
   网卡/光模块抖动     链路监控告警 → 自动隔离故障链路
   节点宕机            从最近 checkpoint 恢复(下面这条是核心)
   慢节点(straggler)   检测异常慢的卡 → 隔离/替换，避免拖垮同步

   ┌─────────── Checkpoint 容错主循环 ───────────┐
   │ 训练 → 每 N 步存 ckpt → ...崩了... →          │
   │ 替换坏节点 → 加载最近 ckpt → 从断点继续训练   │
   │ 损失 = 最多丢掉"上次 ckpt 到崩溃"这段计算      │
   └──────────────────────────────────────────────┘
```

工程要点：
- **存 ckpt 频率是权衡**：太勤 → 写盘开销大、拖慢训练；太疏 → 崩一次丢很多算力。要按"故障间隔"反推最优频率。
- **异步/分布式 checkpoint**：边训边后台刷盘，缩短"暂停存盘"时间。
- **热备节点 (hot spare)**：预留少量空闲节点，坏一个立刻顶上，不必等采购。
- **静默错误 (SDC)**：GPU 算错但不报错最可怕，需定期校验/对拍。

## 8. 利用率：MFU 与你的钱花得值不值

买了 1 万张 GPU，真正用在"有效计算"上的比例叫利用率。最常用指标 **MFU (Model FLOPs Utilization)**：

$$\text{MFU} = \frac{\text{模型训练实际达到的有效 FLOPs/s}}{\text{硬件理论峰值 FLOPs/s}}$$

直觉：MFU 像"高速公路实际车速 / 限速"。理论峰值是限速，MFU 是你真跑出来的速度占比。大模型训练能稳定做到 **40%~55% MFU 就算相当优秀**（公开经验，"约"）。掉下来的部分去哪了？

```
   理论峰值 100%
   ├─ 通信气泡(等 AllReduce / 流水线 bubble) ─┐
   ├─ 数据加载等待(DataLoader 没喂上)          │  这些都是
   ├─ 故障重启 / 慢节点拖累                    │  "被吃掉的利用率"
   ├─ 显存换出 / 重计算开销                    │
   └─ 实际有效计算  ← 这才是 MFU 想最大化的     ┘
```

提升利用率的方向：通信与计算**重叠 (overlap)**、选对并行切分、调好流水线减少 bubble、保证数据预取不断流、快速剔除慢节点。

## 9. 万卡集群的真正挑战

把规模从千卡推到万卡，难度**不是线性增加，而是质变**：

```
   规模 →    网络           容错            利用率          运维
   ─────    ───────────    ───────────    ────────────    ──────────
   千卡      Fat-Tree 够    偶尔崩，能扛    较易上 50%+     人能盯过来
   万卡      多层拓扑、     几乎天天崩，     通信占比飙升，   必须高度
            光模块上万，    必须秒级自愈     易掉到 30%       自动化
            一跳变多跳

   叠加的物理现实:
   ⚡ 供电: 单机柜功率飙到几十 kW，机房电力/PDU 成瓶颈
   ❄ 散热: 风冷到极限 → 液冷(冷板/浸没)成标配
   💡 光模块: 数量上万，是新的高发故障源(坏一根拖一作业)
   🌐 拓扑: 跨 Spine 的多跳通信延迟拉高，长尾明显
   🔁 同步: 一卡慢，全军等(木桶效应),straggler 影响被放大
```

一句话总结万卡难点：**"快"靠拓扑和重叠，"稳"靠容错和自愈，"省"靠利用率，三者在万卡尺度互相拉扯，任何一环掉链子，几千万的硬件就在空转。**

## 数值例子 / 对照（手算）

### 例 1：梯度同步要传多少数据、花多久

- 模型参数 70B，梯度 FP16（2 字节/参数）。
- 一次 AllReduce 的"实际传输量"经验上约为参数量的 $2\times$（Ring-AllReduce 每卡收发约 $2(N-1)/N \approx 2$ 倍数据量）。

单卡需要进出的梯度数据量约：

$$70\times10^9 \times 2\,\text{B} \times 2 \approx 2.8\times10^{11}\,\text{B} = 280\,\text{GB}$$

假设单卡可用互联带宽约 $200\,\text{GB/s}$（NVLink 域内为主），同步耗时：

$$t = \frac{280\,\text{GB}}{200\,\text{GB/s}} = 1.4\,\text{s}$$

> 启示：若每步计算只要 2 s，而同步要 1.4 s 且**不重叠**，则近 $\frac{1.4}{2+1.4}\approx 41\%$ 时间在等网络——这正是 MFU 上不去的元凶，也是"通信/计算重叠"如此重要的原因。

### 例 2：单口 IB 400 Gb/s 到底多快

$$400\,\text{Gb/s} \div 8 = 50\,\text{GB/s（理论，扣协议开销后更低）}$$

传一个 280 GB 的梯度需 $280/50 = 5.6\,\text{s}$（单口）。这就是为什么要 **8 口并行 (Rail)**：理想下提速约 8 倍到 $\approx 0.7\,\text{s}$。

### 例 3：万卡故障概率

设单卡日故障率 $p = 0.001$（千分之一，乐观值）。

| 规模 $N$ | $P_{\text{fail}}=1-(1-p)^N$（当天至少一坏） |
|---|---|
| 100 | $\approx 9.5\%$ |
| 1,000 | $\approx 63\%$ |
| 10,000 | $\approx 99.995\%$ |

> 结论：万卡集群**几乎天天有故障**。所以"从 checkpoint 自动恢复 + 热备 + 慢节点剔除"不是可选项，而是基础设施的底座。

### 例 4：MFU 算一笔账

某 GPU 理论峰值 $1000\,\text{TFLOPs}$（FP16，约值）。某次训练实测有效算力 $450\,\text{TFLOPs}$：

$$\text{MFU} = \frac{450}{1000} = 45\%$$

意味着你买的算力**有 55% 在"等网络/等数据/故障/气泡"中蒸发**。把 MFU 从 30% 提到 45%，等于硬件白赚 50% 产出——这就是 AI-Infra 工程师的核心价值所在。

## 常见问题

| 问题 | 一句话答案 |
|---|---|
| 集群最核心的部件是哪个？ | 计算网（后端 IB/RoCE），它直接决定训练快慢 |
| NVLink 和 InfiniBand 区别？ | NVLink 连节点内 8 卡 (GB/s)；IB 连跨节点 (Gb/s)，量级差约 8 倍，注意 B/b |
| 为什么 8 卡配 8 张网卡？ | 让每卡有独立出口，配合 Rail 拓扑把带宽全榨出来 |
| Fat-Tree 和 Rail 是替代关系吗？ | 不是，常组合：Rail 保同号卡一跳直达，Fat-Tree 保跨号卡可达且无阻塞 |
| Slurm 还是 K8s？ | 极致网络/科研选 Slurm；平台化/多租户/工程化选 K8s（需 Volcano 等补 Gang） |
| 什么是 Gang 调度？ | 所需 GPU 一次性凑齐才启动，否则一张都不占，避免死锁 |
| checkpoint 存多勤合适？ | 按故障间隔权衡：太勤拖慢训练，太疏崩一次丢太多算力 |
| MFU 多少算好？ | 大模型能稳定 40%~55% 就很优秀（公开经验，约） |
| 万卡最大的坎是什么？ | 故障频率质变（天天坏）+ 通信占比飙升导致利用率下滑 |
| A800 和 A100 差在哪？ | 仅 NVLink 带宽从约 600GB/s 降到约 400GB/s，其余基本相同（以官方为准） |
