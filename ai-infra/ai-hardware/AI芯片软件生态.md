## 0. 一句话锚点

**一颗 AI 芯片的价值 = 峰值算力 × 软件能把这些算力榨出来的比例。** 后者完全由软件生态决定。

一个常被忽视的事实：买回来的 GPU/NPU，**裸硬件本身一行用户代码都跑不了**。从「Python 写一行 `torch.matmul(a, b)`」到「芯片上的乘加单元真的动起来」，中间隔着至少 5 层软件。任何一层缺失或不成熟，硬件的标称 TFLOPS 就只是 PPT 上的数字。

```
  开发者写的:  loss.backward()         <- 一行 Python
       │
  ┌────▼─────────────────────────────────────────┐
  │  软件生态 (本文主题)                            │
  │  框架后端 → 编译器 → 算子库 → 通信库 → 运行时    │
  └────┬─────────────────────────────────────────┘
       │
  硬件:  ████ 乘加阵列 / SRAM / HBM / 互联 ████
```

NVIDIA 的统治力，**90% 来自上面那个框，10% 来自下面那排方块**。

## 1. 地基：一颗芯片要被用起来，需要哪几层软件？

把「在芯片上算一个神经网络」拆到最原子，从下往上是 5 层。任何一家做 AI 芯片的公司，这 5 层都得自己补齐（或兼容别人的）。

```
 第5层  框架后端      PyTorch / TensorFlow / JAX 怎么调到你的芯片
   ▲    (Backend)     —— 没有它，用户得改框架源码才能用你的卡
   │
 第4层  图编译器       把整张计算图做算子融合、内存规划、调度
   │    (Compiler)    —— 决定"理论算力"能榨出多少
   │
 第3层  算子库         conv / matmul / softmax / attention 的高性能实现
   │    (Kernel Lib)  —— 每个算子都要为本芯片手工或自动调优
   │
 第2层  通信库         多卡/多机之间 AllReduce、AllGather
   │    (Collective)  —— 大模型训练的命脉
   │
 第1层  运行时+驱动     管理设备、显存、流(stream)、内核启动
   ▼    (Runtime/Driver) —— 和操作系统、PCIe、HBM 打交道
```

**为什么分这么多层？** 因为「关注点分离」：

- 算法工程师只想写数学（第 5 层），不想关心显存怎么分配（第 1 层）。
- 芯片公司想改硬件时，只动底层，不破坏上层用户代码（向后兼容）。
- 每一层都是一个**独立的工程巨坑**，需要专门的团队、数年时间打磨。

NVIDIA 在每一层都有旗舰产品：**驱动 + CUDA Runtime（第1）、NCCL（第2）、cuDNN/cuBLAS（第3）、nvcc/TensorRT（第4）、PyTorch CUDA backend（第5，与社区共建）**。这一整套统称 **CUDA 生态**。

## 2. CUDA 护城河：为什么 18 年积累难以撼动？

CUDA 于 **2007 年**发布（以官方为准）。护城河由三个相乘的因素构成：

$$\text{护城河} = \underbrace{\text{时间}}_{\sim 18\,\text{年}} \times \underbrace{\text{开发者规模}}_{\text{数百万}} \times \underbrace{\text{代码惯性}}_{\text{海量存量代码}}$$

```
  价值/壁垒
    ▲
    │                                   ╱ CUDA (复利曲线)
    │                              ╱╱╱
    │                         ╱╱╱
    │                    ╱╱╱
    │               ╱╱╱        ← 每个新库/新论文/新教程
    │          ╱╱╱               都默认 CUDA，正反馈滚雪球
    │     ╱╱╱
    │ ╱╱        ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  国产/AMD 起步线
    └──────────────────────────────────▶ 时间
   2007                            2025
```

护城河的具体形态：

1. **代码惯性**：GitHub 上数十万个仓库、几乎每篇 AI 论文的开源实现，都写死了 `.cuda()`、`device='cuda'`、自定义 CUDA kernel。换芯片 = 改这一切。
2. **人才惯性**：高校课程、面试题、博客教程全是 CUDA。一个新人入行第一天学的就是 CUDA，形成「默认选项」。
3. **网络效应（核心）**：用户多 → 框架优先适配 CUDA → 库优先支持 CUDA → 论文优先用 CUDA → 用户更愿意买 N 卡 → 用户更多。**这是一个自我强化的闭环。**
4. **长尾算子**：见第 4 节。主流算子谁都能写，难的是那 5% 罕见算子和无数边角组合。

> **关键洞察**：护城河不在「能不能跑一个 ResNet」，而在「能不能跑**任意一份从 GitHub 拉下来的、明天刚发的**代码而几乎不改」。CUDA 能，别人暂时不能。

## 3. cuDNN / cuBLAS / NCCL：三大基石库（必须讲清）

这三个库是 CUDA 生态里**复用率最高、最难复刻**的部分。它们是「第 3 层算子库 + 第 2 层通信库」的旗舰。

### 3.1 cuBLAS —— 线性代数（矩阵乘）

- **解决什么问题**：神经网络 90% 以上的算力消耗在**矩阵乘法（GEMM）**上。`Linear` 层、Attention 的 QK^T、FFN，本质都是 GEMM。
- **BLAS** = Basic Linear Algebra Subprograms，一套有几十年历史的标准接口（Level 1 向量、Level 2 矩阵-向量、Level 3 矩阵-矩阵）。
- **难点**：同一个 `C = A·B`，朴素三重循环和极致优化版本，在同一张卡上性能可差 **10~100 倍**。差距来自：分块（tiling）贴合 L2/SRAM、利用 Tensor Core、避免 bank conflict、流水线隐藏访存延迟。

```
  GEMM 分块思想（为什么手写难）:
   C[M×N] = A[M×K] · B[K×N]
   把大矩阵切成小块，让每块刚好装进高速 SRAM:
   ┌──┬──┬──┐        每个 ■ tile 在片上算完才换下一块,
   │■ │  │  │  ← M   最大化数据复用、最小化访问慢速 HBM。
   ├──┼──┼──┤        tile 多大、怎么排，每代硬件都要重调。
   │  │■ │  │
   └──┴──┴──┘
```

### 3.2 cuDNN —— 深度学习专用算子（Deep Neural Network）

- **解决什么问题**：除了 GEMM，DL 还有大量**专用算子**：卷积、池化、BatchNorm、激活、RNN、（新版）注意力等。cuDNN 为每个算子在每代硬件上提供高度优化实现，并能根据张量形状**自动选择最优算法**（如卷积可走 im2col+GEMM、FFT、Winograd 等多种实现）。
- **难点**：算子 × 数据类型（fp32/fp16/bf16/int8） × 形状 × 硬件代际 = 组合爆炸，每个格子都要调优。

### 3.3 NCCL —— 多卡多机通信（Collective Communications）

- **解决什么问题**：大模型一张卡放不下，要切到几十上千张卡。卡之间要做**集合通信原语**：`AllReduce`（梯度求和）、`AllGather`、`ReduceScatter`、`Broadcast`。
- 训练里最频繁的是 **AllReduce**：每步反向后，所有卡的梯度要加起来再分发回去。
- NCCL 的价值：自动**感知拓扑**（NVLink、NVSwitch、PCIe、跨机 InfiniBand），选最优通信算法（如 Ring / Tree AllReduce），把带宽吃满。

```
  Ring AllReduce（N 张卡环形传梯度，带宽利用率最优）:
   GPU0 ──► GPU1 ──► GPU2 ──► GPU3
     ▲                          │
     └──────────────────────────┘
   每张卡同时收发，总传输量 ≈ 2·(N-1)/N · 数据量，与 N 几乎无关
```

> **三库的共同点**：都是「对硬件极致压榨」的产物，每出一代新卡就要重写调优。国产芯片要对标，等于要把这三个库**各自重做一遍并持续维护**——这是巨大的、看不见的工程量。

## 4. 为什么「生态」比「硬件」更难追？

很多人直觉认为：硬件（流片、HBM、先进制程）才是最难的。**恰恰相反**——硬件难在「投入大」，生态难在「时间换不来」。

```
  硬件追赶              vs        生态追赶
  ───────────                    ───────────
  钱 + 人 + 时间                  钱 + 人 + 时间 + ★网络效应★
  → 可以"砸"出来                  → 砸钱也加速不了用户惯性
  目标静止(对标某代卡)             目标在移动(CUDA 每月在长)
  一次性达标                      要永远跟随长尾算子
```

四个根本原因：

1. **目标在移动**：你照着 CUDA 12.x 适配完，CUDA 13、新算子、新论文又来了。你永远在追一个加速跑的人。
2. **长尾的诅咒**：覆盖 90% 主流算子相对容易，但用户跑的代码里总有那 10% 冷门算子/罕见组合。**缺一个，整个模型就跑不通**——这是「全或无」，不是「打分」。
3. **网络效应是单向的**：硬件不会因为「别人用得多」而变好，但生态会。CUDA 用户越多越好用，国产越少人用越没人帮你填坑，恶性循环。
4. **信任成本**：算子写错一个边界、精度对不齐，结果错得很隐蔽（loss 不收敛、推理答案微妙偏差）。用户被坑一次就不敢再用——而 CUDA 经过亿万次验证。

> 一句总结：**硬件是「能造出来」的问题，生态是「能让全世界开发者愿意改用」的问题。后者是社会学问题，不是工程学问题。**

## 5. 国产 / 第三方路线：自建 vs 兼容

面对 CUDA 护城河，两条路线：

```
  ┌─────────────────────────────────────────────┐
  │  路线 A：兼容 CUDA（移植/翻译）                  │
  │   AMD ROCm(HIP)、海光 DCU、部分创业公司          │
  │   思路：提供"近似 CUDA 的 API"，一键转译用户代码    │
  │   优点：迁移成本低，借力现成生态                   │
  │   缺点：永远慢半拍、受制于人、被卡接口             │
  ├─────────────────────────────────────────────┤
  │  路线 B：自建生态（另起炉灶）                     │
  │   华为昇腾 CANN、寒武纪 Neuware                  │
  │   思路：自己定义编程模型、算子库、编译器           │
  │   优点：自主可控、不被"釜底抽薪"                  │
  │   缺点：从零积累，要说服开发者迁移，最苦最慢       │
  └─────────────────────────────────────────────┘
```

| 厂商 / 平台 | 路线 | 软件栈名称 | 编程模型类比 | 备注 |
|---|---|---|---|---|
| NVIDIA | 原生 | CUDA | CUDA C++ | 事实标准，见 [[ai-infra/ai-hardware/CUDA]] |
| 华为昇腾 | 自建 | **CANN** | AscendC / 图模式 | NPU，详见 [[ai-infra/算力/昇腾NPU]] |
| 寒武纪 | 自建 | **Neuware**（BANG C） | BANG C | 自建最早的国产之一 |
| AMD | 兼容 | **ROCm**（HIP） | HIP（近似 CUDA） | HIP 源码可近乎一对一映射 CUDA |
| 海光 DCU | 兼容 | 基于 **ROCm** | HIP | 借力 AMD 生态 |
| 瑞芯微 | 推理 | **RKNN**（RKNN-Toolkit） | 转换+部署 | 端侧 NPU，离线转模型再部署 |

**RKNN 这类「端侧推理路线」是另一种生态**：不追求「跑任意训练代码」，而是「把训练好的模型转换、量化、部署到端侧芯片」。工具链是 `模型(onnx/pt) → RKNN-Toolkit 转换+量化 → .rknn → 板端运行时推理`，算子覆盖以**推理常见算子**为主，复杂度远小于训练全栈，但同样面临算子覆盖问题（不支持的算子要回退 CPU 或手工实现）。

> 业界共识（公开判断，非精确数字）：**自建生态是长久之道**。兼容路线短期省力，但接口、专利、技术演进都受制于被兼容方，存在被「卡脖子」的结构性风险；自建虽苦，却换来真正的自主可控。华为昇腾、寒武纪走自建更稳更远；海光借力 ROCm 短期顺，长期受制；创业公司（摩尔线程、壁仞、登临等）则面临最大的生态构建压力。

## 6. 迁移挑战：算子覆盖率与精度对齐

「把一个 CUDA 上的模型搬到国产卡」听起来像换个 `device`，实际是冰山。两大拦路虎：

### 6.1 算子覆盖率（Operator Coverage）

一个模型 = 一张计算图 = 若干算子的组合。**只要图里有一个算子目标平台不支持，整个模型就跑不起来**（或回退到极慢的 CPU）。

```
  模型计算图（节点=算子）:
   [Embed]→[LayerNorm]→[QKV-Matmul]→[Softmax]→[RoPE]→[FFN-GELU]→...
                                                  ▲
                                                  └─ 假设国产栈缺 RoPE 的融合实现
   结果：要么整图跑不通，要么这里回退、性能崩。
   迁移工作 = 把缺的算子一个个补齐 + 调优 + 对齐精度
```

定义**算子覆盖率**：

$$\text{覆盖率} = \frac{\text{平台已高质量支持的算子数}}{\text{目标模型用到的算子总数}}$$

注意这是**乘性瓶颈**而非加性：覆盖 99% 听起来很高，但若那 1% 在关键路径上，模型照样跑不通。所以迁移的真实指标是「**端到端能否原样跑通**」，不是覆盖率百分比。

### 6.2 精度对齐（Numerical Alignment）

即使算子都「有」，实现细节差异会导致数值不一致：

- 浮点累加顺序不同 → 最后几位 bit 不同 → 多层放大 → loss 曲线偏离。
- fp16/bf16 的舍入、溢出处理、softmax 的减最大值技巧实现差异。
- 这类 bug **极其隐蔽**：不报错，只是结果「悄悄错了」，训练不收敛或推理答案变差，排查动辄数周。

### 6.3 迁移工具

各家都提供「自动迁移工具」降低成本，例如把 CUDA 源码做语法层翻译（如 ROCm 的 HIPify、各家的代码转换器），但**翻译只能解决 API 名字，解决不了语义差异、性能差异和长尾算子缺失**。所以「一键迁移」永远只是第一步，真正的成本在后面的调试与调优。

## 7. 编译器路线：从「手写算子」到「自动生成」

第 3 节说每个算子都要为每代硬件手工调优——这显然不可持续（组合爆炸）。**编译器路线**的目标：让机器自动生成高性能算子，而不是人海战术。这也是国产芯片**弯道超车**的最大希望所在。

```
  传统路线（人力密集）:
    每个算子 × 每代硬件 × 每种数据类型 = 人手写、手调
    → 永远追不上 NVIDIA 的库团队规模

  编译器路线（自动化）:
    高层描述(数学语义)  ──编译器──►  自动生成本芯片最优 kernel
    → 一次写规则，吃下整条算子长尾
```

主流技术栈（以官方文档为准）：

| 技术 | 定位 | 一句话 |
|---|---|---|
| **MLIR** | 编译基础设施 | 多层中间表示，提供「搭编译器的乐高」，国产栈大量采用 |
| **Triton** | Python 写 kernel | 用 Python 写高性能 GPU/NPU kernel，自动处理分块/调度，见 [[ai-compiler/triton-lang/README]] |
| **TVM** | 端到端编译 | 图优化 + 自动调优（AutoTVM/Ansor），偏推理与多后端部署 |
| **XLA** | 图编译器 | JAX/TF 的后端，融合算子、整图优化 |

**为什么编译器是国产的希望**：

1. **绕开「逐个手写算子」的人力差距**——用编译规则一次覆盖大量算子。
2. **Triton 等已把「算子」抽象到与硬件解耦的高度**：理论上为新后端补齐一个 Triton 后端，就能让大量已有 Triton kernel（含很多前沿 attention 实现）直接复用。
3. **MLIR 提供统一中间层**：从 PyTorch 图 → MLIR → 各家硬件，避免每家从零造编译器轮子。

权衡：编译器自动生成的 kernel，**性能通常仍不及顶级手工算子**（差几成到几倍不等），且编译器本身也是数年工程。它是「降低追赶斜率」的杠杆，不是「一夜抹平」的银弹。

```
  生态追赶的两种斜率:
    壁垒差距
      │
      │＼ 纯手写：斜率平缓，差距长期存在
      │  ＼┄┄┄┄┄┄┄┄┄┄┄┄
      │    ＼
      │      ＼  编译器路线：斜率更陡，追得更快
      │        ＼＼＼＼＼
      └──────────────────────► 时间
```

## 数值例子 / 对照（手算）

### 例 1：算子覆盖率的「全或无」效应

设某 LLM 计算图用到 **120** 个不同算子，国产平台支持其中 **117** 个，覆盖率：

$$\frac{117}{120} = 97.5\%$$

听起来很高。但剩下 **3** 个若有任意一个在主路径（如某种融合 attention），则**端到端跑通率 = 0%**，直到补齐为止。这说明**覆盖率百分比会严重高估「可用性」**——真实门槛是「跑通率」这个 0/1 指标。

### 例 2：迁移工作量粗估（量级感，非精确）

假设缺 3 个算子，每个：实现 ≈ 5 人日，性能调优 ≈ 10 人日，精度对齐+调试 ≈ 10 人日：

$$3 \times (5 + 10 + 10) = 3 \times 25 = 75 \text{ 人日} \approx 3.5 \text{ 人月}$$

这还只是**一个模型**。换个新模型架构，可能又冒出新的缺失算子。这就是「长尾永远填不完」的直观体感。

### 例 3：NCCL AllReduce 通信量手算

8 卡 Ring-AllReduce，每卡梯度 **2 GB**，理解为何「与卡数几乎无关」：

每卡总传输量 $\approx 2 \times \frac{N-1}{N} \times D = 2 \times \frac{7}{8} \times 2\,\text{GB} = 3.5\,\text{GB}$。

若 NVLink 单向有效带宽约 **150 GB/s**（典型量级，以官方为准），单次 AllReduce 通信耗时：

$$t \approx \frac{3.5\,\text{GB}}{150\,\text{GB/s}} \approx 23.3\,\text{ms}$$

每个训练 step 都要做一次。**这就是为什么 NCCL 这类通信库的优化质量，直接决定大模型训练的扩展效率**——通信库是国产栈另一个必须自研到位的硬骨头。

## 常见问题

| 问题 | 简答 |
|---|---|
| CUDA 护城河本质是什么？ | 不是硬件，是 18 年积累的软件栈 + 数百万开发者惯性 + 自我强化的网络效应。 |
| cuDNN 和 cuBLAS 区别？ | cuBLAS 管通用线性代数（GEMM）；cuDNN 管 DL 专用算子（卷积/BN/激活等）并自动选最优算法。 |
| NCCL 解决什么？ | 多卡多机集合通信（AllReduce 等），是大模型分布式训练的命脉。 |
| 为什么生态比硬件难追？ | 硬件砸钱可达标；生态是移动靶 + 长尾 + 网络效应 + 信任成本，时间换不来。 |
| 自建 vs 兼容怎么选？ | 兼容（ROCm/HIP）省力但受制于人；自建（CANN/Neuware）苦但自主可控、长久。 |
| 迁移最大的坑？ | 算子覆盖率（全或无）+ 精度对齐（隐蔽 bug），「一键迁移」只解决 API 名字。 |
| 编译器为什么是希望？ | 用 MLIR/Triton/TVM 自动生成算子，绕开「逐个手写」的人力规模差距，降低追赶斜率。 |
| RKNN 属于哪类？ | 端侧推理路线：模型转换+量化+部署，不追求跑任意训练代码，复杂度小于训练全栈。 |
