# Treebeard：面向决策树 ML 推理的优化编译器

> Treebeard 是一个基于 MLIR 的优化编译器，把"训练好的决策树/GBDT 模型"编译成对 CPU 高度友好的本地代码，从而把决策树推理跑得比通用解释器（如 XGBoost 自带 predict、Treelite）更快。📍 导航：[[00-知识地图]]

## 0. 一句话锚点

> **决策树推理本质是"一堆不可预测的 if-else 分支 + 随机内存访问"，对现代 CPU 极不友好。Treebeard 用领域知识（它知道这是决策树）把模型经过三层 MLIR IR 逐步 lowering，把分支变成数据驱动的循环、把随机访问变成规整的数组遍历，最后生成可向量化、可并行、cache 友好的本地代码。**

把一句话拆成原子：
- **决策树 / GBDT 模型**：训练阶段产物，是一棵棵二叉树。推理时从根节点开始，每个内部节点做一次"特征 x[i] 和阈值 t 比较"，根据结果走左或走右，直到叶子，叶子给出一个数值（回归值或分类 logit）。GBDT 把几百上千棵树的叶子值求和。
- **优化编译器**：不是解释执行模型，而是把模型"编译"成机器码。
- **MLIR**：LLVM 生态里的多层中间表示框架，支持自定义"方言（dialect）"和逐层 lowering。Treebeard 自己定义了表示决策树的方言。
- **领域知识（domain knowledge）**：编译器明确知道"我在编译决策树"，所以能做通用编译器做不到的优化（例如知道所有树结构相似、可以 unroll/interchange）。

## 1. 地基：决策树推理为什么慢？（它解决什么问题）

要理解 Treebeard 的价值，先理解朴素决策树推理为什么是 CPU 的噩梦。

一棵树的朴素推理伪代码：

```
node = root
while node 不是叶子:
    if  x[node.featureIndex] < node.threshold:
        node = node.left
    else:
        node = node.right
return node.value
```

这段代码对 CPU 有三个根本性问题：

```
┌───────────────────────────────────────────────────────────┐
│  问题1：分支预测失败 (branch misprediction)                │
│    每个节点一个 if，走左还是走右取决于数据，CPU 猜不准     │
│    → 流水线频繁清空，几十个周期白白浪费                    │
├───────────────────────────────────────────────────────────┤
│  问题2：随机内存访问 (pointer chasing)                     │
│    node = node.left 是指针跳转，下一个节点在内存哪儿不确定 │
│    → cache miss 频繁，等内存几百个周期                     │
├───────────────────────────────────────────────────────────┤
│  问题3：无法向量化 / 批处理利用率低                        │
│    一次只处理一个样本走一条路径，SIMD 宽度浪费             │
│    同一批样本在同一棵树上可能走不同路径，难以并行          │
└───────────────────────────────────────────────────────────┘
```

数值直觉：假设一棵树深度 8（256 个叶子），一个 GBDT 有 1000 棵树，批大小 4096。朴素方式是 $4096 \times 1000 \times 8 \approx 3.3 \times 10^7$ 次"比较 + 不可预测分支 + 指针跳转"。其中绝大部分时间不是花在算术上，而是花在**分支预测失败和 cache miss 上**。

**Treebeard 要解决的就是这个问题**：用编译手段把"控制流密集、访存随机"的推理，重写成"数据流规整、访存可预测、可向量化、可并行"的循环。

为什么编译器能做、手写库做不到那么好？因为最优策略和具体模型形状（树深、树数、批大小、特征数）、目标硬件（cache 大小、SIMD 宽度）都相关。手写库只能针对几种情况调优；编译器可以为每个具体模型 + 硬件**自动搜索**最佳调度（schedule）。

## 2. 整体架构：三层 IR

Treebeard 的核心思想是**逐层降低抽象**。每一层 IR 只关心一类优化，关注点分离，互不干扰。

```
        训练好的模型 (XGBoost / LightGBM JSON 等)
                       │  解析
                       ▼
   ┌──────────────────────────────────────────────┐
   │  高层 IR  (High-level, 基于树的 IR)            │
   │  抽象：还是"树"，节点/叶子/阈值都在            │
   │  优化：模型级 —— 树的表示、tiling、概率重排    │
   └──────────────────────────────────────────────┘
                       │  lowering（树 → 循环）
                       ▼
   ┌──────────────────────────────────────────────┐
   │  中层 IR  (Mid-level, 与内存布局无关的循环 IR) │
   │  抽象："遍历一批样本 × 一组树"的嵌套循环       │
   │  优化：循环级 —— unroll / interchange / tile  │
   │        （独立于具体内存怎么排）                │
   └──────────────────────────────────────────────┘
                       │  lowering（循环 → 具体数组+布局）
                       ▼
   ┌──────────────────────────────────────────────┐
   │  低层 IR  (Low-level, 与内存布局相关的 IR)     │
   │  抽象：具体数组、索引算术、向量寄存器          │
   │  优化：向量化 (SIMD)、内存布局相关优化         │
   └──────────────────────────────────────────────┘
                       │  lowering to LLVM / 标准 MLIR 方言
                       ▼
            LLVM IR → 本地机器码 (.so / 可执行)
```

> 对应原始论文图：三个抽象级别——**高级 IR 做模型级优化，中级 IR 做与内存布局无关的循环优化，低级 IR 做向量化和内存布局相关优化**。

这种分层的好处（为什么这么设计）：
- **关注点分离**：在"还是树"的层面做模型重排很自然；在"已经是循环"的层面做 tiling 很自然；硬要在一层做完所有事会让 pass 互相纠缠。
- **可组合的调度**：每层暴露一组旋钮（见"优化空间"），上层不必关心下层细节。
- **复用 MLIR 通用能力**：lowering 到标准方言后，并行（OpenMP）、向量化等可直接借用 MLIR 现成 pass，不必重造轮子。

## 3. 高层 IR：模型级优化（基于树）

这一层 IR 仍然把模型表示成"树的集合"，做的是和"树长什么样"强相关的优化。

### 3.1 树的表示：稠密 vs 稀疏

最朴素的存法是把每棵树存成节点数组（稠密），但深而稀疏的树会浪费大量空间。Treebeard 支持多种表示，关键是 **tiling（节点平铺）**：把树里相邻的若干节点打包成一个"tile"，一次比较多个节点，减少遍历步数。

```
原始二叉树 (tile size nt = 3 的示意)：
                T1                tile = {1 个内部 3 节点子树}
               /  \
            l1     T2
                  /  \             T2 是"非叶 tile"，需要额外 hop
               l2     l3
              /  \   /  \
             l4 l5  l6  l7        叶子被搬进单独的 leaves 数组

→ tiling 后：内部节点打包成 tile，叶子集中存放，
   对非叶 tile（如 T2）补充 extra hop 指向其叶子的存放位置。
```

> 对应原始论文图 6（Sparse representation, tile size nt = 3）：叶子 l4..l7 移入 leaves 数组；因 T2 是非叶 tile，给 l1/l2/l3 增加 extra hops；新加的、作为 l1/l2/l3 子节点的叶子也移入 leaves 数组。

**tile size $n_t$ 怎么权衡？**

| tile size | 好处 | 代价 |
| --- | --- | --- |
| 小（如 1，即不 tiling） | 实现简单、无额外结构 | 遍历步数多、分支多 |
| 大（如 3、7） | 一次跳多层、减少循环迭代、利于向量比较 | 内存膨胀（稀疏树补占位）、非叶 tile 需 extra hop |

直觉：tile size 越大，单步处理的节点越多，越能把"一连串不可预测分支"压成"一次批量比较"，但树越稀疏，padding 浪费越大。最优值依赖树的形状，因此交给编译器/autotuner 搜索。

### 3.2 概率/统计相关的重排（leaf-biased）

论文里提到 **leaf-biased** 树的概念（带参数 $\langle \alpha, \beta \rangle$，例如 $\alpha = 0.075, \beta = 0.9$）：很多真实 GBDT 里，样本到达不同叶子的概率极不均匀，少数路径承载大部分样本。利用这种统计偏置，可以把高概率路径放在前面 / 让分支预测更易命中。具体阈值与定义以论文/源码为准，这里讲机制：**编译器知道"哪些路径更常走"，就能据此重排，减少期望遍历开销。**

## 4. 中层 IR：循环级优化（与内存布局无关）

经过 lowering，树被"摊平"成嵌套循环。最核心的二重循环是：

```
for each batch of samples:      # 样本维
    for each tree:              # 树维
        walk(sample, tree)      # 在一棵树上遍历到叶子
        accumulate(result)      # 叶子值累加
```

这一层把推理看成一个**循环嵌套调度问题**，可施加经典的循环变换：

```
┌─────────────── 循环交换 (loop interchange) ───────────────┐
│  先遍历树、再遍历样本  vs  先遍历样本、再遍历树           │
│  → 改变数据复用模式：哪个在内层决定了 cache 里复用什么    │
│    (树常驻 cache？还是样本特征常驻 cache？)               │
├─────────────── 循环展开 (loop unrolling) ─────────────────┤
│  把固定深度的 walk 展开成无循环的直线代码                 │
│  → 消除循环开销、给后端更多指令调度/向量化机会            │
├─────────────── 循环分块 (tiling / blocking) ──────────────┤
│  把"批 × 树"切成小块，让一块的工作集放进 L1/L2 cache     │
│  → 减少 cache miss                                       │
└───────────────────────────────────────────────────────────┘
```

**为什么领域知识在这层特别值钱？** 因为通用编译器面对 `while (node != leaf)` 这种不定次数循环，无从展开；而 Treebeard 知道"树深有上界"，可以安全地把遍历展开成定长直线代码，把"数据相关的控制流"转成"数据相关的索引计算"，从而让向量化成为可能。

"与内存布局无关"的含义：这一层只决定**循环怎么嵌套、怎么切、怎么展开**，但还不规定数组到底怎么排在内存里——那是下一层的事。这样同一套循环调度可以搭配不同内存布局尝试。

## 5. 低层 IR：内存布局与向量化

最后一层落到具体的数组和索引算术，做和硬件/布局强相关的优化。

```
样本批 (batch × features)         模型 (tiles + thresholds + leaves)
   ┌──────────────┐                 ┌─────────────────────────────┐
   │ row-major?   │                 │ thresholds 数组：连续放置   │
   │ col-major?   │  ── 索引算术 ──▶│ featureIndices 数组         │
   │ 影响 SIMD     │                 │ leaves 数组（集中存放）     │
   │ gather 效率   │                 │ → 顺序遍历、cache 友好       │
   └──────────────┘                 └─────────────────────────────┘
            │
            ▼  向量化：用一条 SIMD 指令同时比较多个样本/多个节点阈值
   ┌────────────────────────────────────────────────────────────┐
   │  vcmp  x[f0..f7] < t[0..7]   → mask                         │
   │  用 mask 选择下一步索引（无分支，blend/select 实现）        │
   └────────────────────────────────────────────────────────────┘
```

关键机制：
- **数组化（SoA）**：把"节点对象的指针图"变成几个并列的扁平数组（阈值数组、特征索引数组、叶子数组），遍历变成"算下一个下标"，访存从随机变顺序。
- **无分支遍历**：用比较结果生成的 mask/掩码做 `select`，避免真正的条件跳转，消除分支预测失败。
- **向量化**：一条 SIMD 指令同时处理多个样本（样本维向量化）或同时比较一个 tile 内多个阈值（节点维向量化），把 CPU 的 SIMD 宽度用满。
- **内存布局选择**：样本是 row-major 还是 column-major，直接影响 gather 是连续还是跨步，进而影响向量化效率。这层负责为具体硬件挑布局。

lowering 到这里之后，再降到 LLVM 方言交给 LLVM 后端生成机器码；并行（多核）可直接用 MLIR/OpenMP 现成能力包外层循环。

## 编译流程示例（端到端，讲含义不背具体 API）

```
[1] 加载模型
    XGBoost/LightGBM 导出的 JSON  ──▶  Treebeard 前端解析
                                       生成 高层(树) IR
[2] 模型级优化  (高层 IR pass)
    选择树表示（稠密/稀疏）、tile size、概率重排
[3] lowering：树 → 循环
    生成 中层(循环) IR
[4] 循环级优化  (中层 IR pass)
    interchange / unroll / tiling，按 schedule 配置
[5] lowering：循环 → 数组 + 布局
    生成 低层 IR
[6] 内存布局优化 + 向量化  (低层 IR pass)
[7] lowering to LLVM 方言 →（OpenMP 并行）→ LLVM IR
[8] LLVM 后端 → 目标 CPU 机器码（.so / 可链接对象）
[9] 运行期：喂入 batch 特征矩阵，调用生成的 predict，得到分数
```

> 整个项目基于 MLIR，因此像"用 OpenMP 做并行"这类通用优化可以直接复用 MLIR 已有 pass，不必自己实现。

## 优化空间与调度（autotuning）

Treebeard 的强大之处是把上述各层旋钮组合成一个**优化空间**，对给定模型 + 硬件搜索最佳组合（对应论文 Table II "Space of optimizations explored"）。可调维度大致包括：

| 维度 | 含义 | 怎么权衡 |
| --- | --- | --- |
| 树表示 | 稠密 / 稀疏 | 稀疏省内存但有 extra hop；稠密遍历快但占空间 |
| tile size $n_t$ | 一个 tile 打包几个节点 | 大 tile 减少步数、利于向量化，但稀疏树 padding 浪费 |
| 循环顺序 | 样本维 / 树维谁在内层 | 决定 cache 里复用样本还是复用树 |
| unroll 因子 | 遍历展开程度 | 展开越多直线代码越长，利于调度但增大代码体积 |
| tiling/blocking | 批×树的分块大小 | 让工作集进 cache，块太小开销大、太大溢出 cache |
| 向量化维度 | 沿样本 or 沿节点向量化 | 取决于 batch 大小、SIMD 宽度、树形 |
| 内存布局 | row/col-major、数组排布 | 影响 gather 连续性与 SIMD 效率 |

> 论文报告的结果（图 9）：在多种 batch size 上，Treebeard 相对 XGBoost、Treelite 取得几何平均加速（单核）。**具体加速倍数、benchmark 列表（Table I）与最优参数请以原论文/官方仓库为准，不要凭记忆引用确切数字。**

为什么需要搜索而不是写死？因为最优组合是"模型形状 × 硬件参数"的函数：浅树和深树、小 batch 和大 batch、L1 大小不同的 CPU，最优调度都不一样。编译器 + autotuner 能为每个具体场景定制，这正是它打败通用库的根因。

## 与同类方案对比

```
方案            执行方式           优化粒度           领域知识利用
──────────────────────────────────────────────────────────────
XGBoost predict 解释执行/内置遍历  通用、固定          有限
Treelite        生成 C 代码        预设模板编译        中等
Treebeard       MLIR 多层编译      可调度+autotune     高（三层 IR）
```

- **XGBoost 自带 predict**：通用解释器，控制流密集，难充分利用 CPU 流水线/SIMD。
- **Treelite**：会把模型编译成 C 代码再交给 C 编译器，比解释执行快，但优化空间相对固定（模板化）。
- **Treebeard**：把整个优化空间显式建模为可调度的多层 IR，能针对模型 + 硬件自动搜索，因此通常更快、可移植性更好（换硬件重编译/重搜即可）。

## 常见问题 / 坑

| 现象 / 坑 | 原因 | 建议 |
| --- | --- | --- |
| 加速不明显 | 没做 autotune，用了默认调度 | 针对你的模型形状 + 目标 CPU 搜索 tile size / 循环顺序 / 布局 |
| 大 batch 才快、小 batch 反而慢 | 向量化/分块的收益依赖批量；小 batch 摊不开开销 | 小 batch 用不同调度，或合批后再推理 |
| 内存占用偏高 | 稀疏树用大 tile size，padding 浪费 | 调小 tile size 或换稠密表示，按内存/速度权衡 |
| 换 CPU 后性能回退 | 调度是针对原硬件（cache/SIMD）搜出来的 | 在新硬件上重新 autotune / 重编译 |
| 结果和原模型有微小数值差 | 浮点累加顺序、向量化重排导致 | 确认可接受的数值容差；分类阈值附近样本留意 |
| 误以为它是训练框架 | 它只做"推理"编译，不训练 | 训练仍用 XGBoost/LightGBM，导出后交给 Treebeard |

## 一句话总结

> 决策树推理慢在"控制流密集、访存随机、难向量化"。Treebeard 借助领域知识，用三层 MLIR IR 把模型从"树"逐层 lowering 成"规整循环 → 扁平数组 + 向量化代码"，并把所有优化旋钮组成可 autotune 的调度空间，针对具体模型与硬件定制，从而显著加速 GBDT 推理。**精确参数名、版本与性能数字请以官方论文/源码为准。**
